Control Center answers two authorisation questions, and they are genuinely
different. **"May this person call this operation?"** is about humans, roles
and repositories. **"May this agent cause this effect?"** is about actions,
arguments and blast radius — that one is [Guardrails](/en-GB/manual/concepts/guardrails/).

This page is the first question, plus the record both of them leave behind.

## One decision point

Every human-side authorisation decision resolves through a single function:

```
can(principal, permission, resource) → allow | deny + why
```

A **permission** is `<domain>:<tier>` — `tickets:write`,
`members:administer`, `repos:read`. The catalogue is **derived**, not
hand-written: it is computed from the operation surface itself (the op's name
prefix gives the domain, the role floor it already enforces gives the tier),
so all ~550 operations carry a permission without anyone typing one.

That derivation is the property worth protecting. It means a NEW operation is
gated by default — the failure mode of a hand-annotated model is that
somebody forgets, and the thing they forget is the gate. A ratchet test pins
the resulting domain set, so adding an operation under a new prefix is a
naming decision a human makes rather than an accident.

The four tiers map exactly onto the built-in roles:

| Tier | Role floor | Example |
|---|---|---|
| `read` | guest | `tickets:read` |
| `write` | member | `tickets:write` |
| `administer` | admin | `members:administer` |
| `own` | owner | `workspace:own` |

## Roles

Five built-in roles — **owner, admin, member, viewer, guest** — are presets
over that catalogue. Ownership is a single seat per workspace, handed over
explicitly with **Transfer ownership** (an owner who leaves is otherwise
unremovable: SCIM deprovisioning refuses any workspace owner — transfer
first).

**Custom roles are subtractive.** A custom role names a base preset (`admin`,
`member`, `viewer` or `guest` — never `owner`) and a set of permissions
REMOVED from it — "admin, but cannot manage members". It can never grant more
than its base, which is what makes them safe to introduce into an existing
install: every existing check remains a sound upper bound. Members hold them
as `custom:<id>`, and a client too old to understand that value falls back
to guest rather than guessing.

Underneath roles sit **per-repo grants** (`none` / `read` / `review` /
`write`, see [Changing code needs the write grant](#changing-code-needs-the-write-grant)):
workspace membership never silently out-privileges the forge. Every
surface that exposes code checks them — including the ones that reach code
sideways, like a terminal or an editor session opened on a space's worktree.

## Code follows the forge

A grant alone does not open a repository's code. To see its files, diffs or
search results, or to open a terminal on it, a member needs the Control Center
grant **and** their own forge sign-in must be able to read the repository.
Workspace admins are not exempt; the server owner is, because the checkout is
on their machine. A repository with no forge remote needs only the grant.

- When an admin grants a repository to someone whose forge account cannot read
  it, the grant is saved and the admin sees a warning.
- When the forge cannot be reached to check, the answer is no, never a guess:
  the person sees "Couldn't confirm your GitHub access. Try again." (with
  their forge's name) and tries again later.
- Pull requests and everything made from them follow the same rule.

### Changing code needs the write grant

A repository grant has three levels, and each includes the one before it:

- **read**: see the repository's files, diffs and search results, provided your
  own forge sign-in can read it too.
- **review**: read, plus approving, requesting changes and the other review
  actions on its pull requests.
- **write**: review, plus changing the code and driving agent runs that write
  to the repository. Changing the code covers saving or reverting files in the
  editor, syncing a worktree to its pull request's head, committing and pushing,
  publishing a branch, and the stack actions that cut, check out or publish a
  part.

Every push made for a person, by them or by an agent run they asked for, checks their write grant on that repository at the moment of the push, on GitHub, GitLab and Bitbucket alike. Publishing a stack checks every repository in the stack before it pushes any of them.

A refusal names the grant that is missing. Without read access the app says
"You don't have read access to this repository. A workspace admin can grant it."
With read but not write it says "You can read this repository but not change it. A workspace admin can grant write access."

### Spaces follow their repositories

What agents wrote about code follows the code. A space's content (its
messages, transcripts and tool output, search results, run logs, todos,
activity and notifications) carries the code of the repositories it works on,
so a space opens only for a member who holds a read grant on, and whose own
forge sign-in can read, every repository the space uses. Those are the
repositories selected for it, or all of the workspace's repositories when the
space has no selection recorded. A space created with no repositories is open
to every member.

A space someone cannot open is not listed for them anywhere, including search,
run logs, todos, activity and notifications. Workspace admins hold every grant
but are not exempt from the forge half; the server owner is.

For a conversation everyone should be able to read, create the space with no
repositories, or only with repositories everyone can read.

## The server owner

The person who set the server up is its **owner**. The server records them
once, at first start, and nothing sent over the network changes that. A
workspace admin, or a workspace owner, is not the server owner: anyone can be
given a workspace, but the server's machine has one owner.

**Nothing runs on the server's own machine outside a sandbox unless the server
owner started it or approved that kind of host execution.** Concretely, only
the server owner can:

- Create a workspace. Everyone else sees a screen asking them to have the
  owner create one or a workspace admin invite them.
- Open the host shell in the server-hosted terminal. Everyone else gets a
  sandboxed terminal, with an agent's limits, in the workspace's own
  directories.
- Open the embedded code editor. It runs as the server's own user, with its
  terminal, tasks and extensions.
- Open a pull request or a conversation's worktree in a native editor. The
  editor starts on the server's own screen, as the server's user.
- Save or approve an [environment](/en-GB/manual/guides/environments/) definition
  that runs anything on the host: host placement, a check that runs a
  command, or a provision or archive task.
- Run agents on a server whose machine has no sandbox. Everyone else's runs
  are refused there, unless the owner started the server with `--sandbox off`,
  which runs every member's agents unconfined (see
  [Agents on a host without a sandbox](/en-GB/manual/concepts/sandbox-security/#agents-on-a-host-without-a-sandbox)).
- Link a repository checkout that lives outside the workspace's own storage,
  confirm one linked before that rule, and browse the server's folders when
  adding a repository (see [Add repositories](/en-GB/manual/guides/add-repos/)).
- See and stop every running agent process on the server. Everyone else sees
  and stops only live agent runs in workspaces they belong to.
- Let agents use personal MCP servers: the ones configured in the server user's own tools (Claude,
  Codex, Cursor and the rest) and the ones the owner adds. Only runs the owner is accountable for
  receive them; see [Personal servers](/en-GB/manual/guides/mcp-server/#personal-servers).
- Approve a workspace MCP server that runs a command on the server's machine or reaches its private
  network (see [Workspace servers](/en-GB/manual/guides/mcp-server/#workspace-servers)).
- Confirm a person's email address, so single sign-on can match it (see
  [Connect an OpenID Connect provider](/en-GB/manual/guides/sso-oidc/#how-sign-ins-match-existing-accounts)).
- Change install-wide settings: SSO, provider credentials, the MCP endpoint
  and its token, model management, Connect, and whole-install backups. These
  operations declare **server authority** and are refused for everyone else.

There is deliberately one operator identity and one definition of it.

## The audit trail

Every authorisation decision — **allow and deny** — is appended to a
per-workspace, hash-chained audit trail.

A deny-only log answers "what did we block?" but not "what did this agent
actually do, and who authorised it?", which is the question an incident review
starts from. So each entry records the full attribution chain: the acting
principal, the human it acted on behalf of, the delegation it arrived through,
the action and its arguments (as a digest), the decision, and **the rule that
decided**.

Entries are chained: each one's hash covers the previous one's, so editing,
deleting or reordering any row breaks every hash after it. **Verify chain**
re-derives the whole thing and names the first link that does not hold. An
audit log you cannot check is a log; one you can re-derive is evidence.

Two consequences worth knowing:

- The audit table is **exempt from age-based pruning**. A hash chain cannot
  be trimmed from the middle. Retention is export-then-truncate, and the
  truncation leaves a checkpoint carrying the removed segment's terminal
  hash, so what survives still verifies back to the beginning.
- It sits **beside** the activity timeline, not on top of it. The timeline is
  what people did; this is what was authorised and refused. A shared
  correlation id reads one call across both.

It exports as newline-delimited JSON and can stream to a SIEM (Splunk,
Elastic, Sentinel — an HTTP endpoint with a bearer token). Streaming is
best-effort by design: a SIEM being down must never block an agent's tool
call, and the durable, verifiable copy is on disk either way.

## Sessions

An install can set a **maximum session age** and an **idle timeout**. Both are
enforced at the device-credential check every authenticated lane funnels
through — a session bound a client could ignore answers a questionnaire, not
an attacker. An install can also require SSO, which disables manual pairing
for new devices (with a lockout guard: it refuses while no working SSO
connection exists).

## What this is not

- **Not per-object ACLs.** There is no per-ticket or per-message permission,
  deliberately. Repository-level separation is what teams actually ask for
  and it exists; per-object sharing is a combinatorial surface with no
  demonstrated demand here.
- **Not a policy engine you configure in a DSL.** The vocabulary is closed on
  purpose, so the whole policy can be rendered, explained and enumerated.
- **Not enforced anywhere but the server.** Client-side checks exist only to
  avoid offering a control that will be refused. The authoritative decision
  is always the server's.
