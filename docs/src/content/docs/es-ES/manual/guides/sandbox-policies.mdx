Que una ejecución de agente esté en un entorno aislado se decide en el servidor,
al arrancar (`--sandbox`). El interruptor **Activar sandboxing**, el selector
**Backend** y los interruptores **Capacidades predeterminadas · conversaciones
nuevas** de **Ajustes → Servidor → Diagnóstico y privacidad** son preferencias
que se guardan en tu dispositivo. La detección de host de la tarjeta
**Aislamiento** informa de qué puede envolver el host del servidor.

Dos controles llegan a una ejecución y esta guía cubre ambos: los **Permisos del
sandbox** por agente que se describen más abajo y el propio flag `--sandbox` del
servidor.

## Qué limita una ejecución de agente

Seis cosas sujetan a un agente. La primera es el entorno aislado del sistema
operativo y es la única condicional: las otras cinco se aplican en cualquier
host.

| Frontera                 | Qué hace                                                                                                                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| El entorno aislado del sistema operativo | Seatbelt en macOS, bubblewrap en Linux y WSL2. Envuelve la CLI de Claude Code, los adaptadores ACP y la herramienta `bash` del arnés. **Ausente en Windows y en Linux sin `bwrap` y `socat`** |
| Su propio worktree         | Cada conversación recibe un checkout con copia en escritura. El checkout original se incorpora a la ejecución como ruta de denegación de escritura, y es el entorno aislado quien lo aplica                                            |
| Credenciales del bróker     | El bróker de credenciales emite un entorno por ejecución a partir de las capacidades del agente y lo revoca al desmontar. Sin capacidad no hay token en el entorno                                            |
| Barandillas de acciones        | Cada herramienta mutadora declara sus clases de efecto y la barandilla las resuelve antes de que se ejecute la llamada. Un `prompt` sin ningún aprobador conectado se deniega                                                 |
| Saneamiento del entorno | ACP y la herramienta `bash` del arnés reciben un entorno filtrado. Claude Code a través de `NoSandboxAdapter` hereda el entorno del host                                                                  |
| La superficie de herramientas del modo  | Un modo de solo lectura elimina por completo las herramientas que mutan el worktree y fija el propio verbo de salida del modo para que este siga pudiendo entregar                                                                         |

Tres cosas son más débiles de lo que parecen:

- Solo el **arnés integrado** aplica la puerta de herramientas, los contratos de
  finalización y las reglas estructurales del modo. El adaptador de Claude Code
  no. En particular, Claude Code se lanza con `--dangerously-skip-permissions`,
  porque un `claude -p` no interactivo se quedaría bloqueado para siempre en su
  propio prompt; así que Control Center ni ve ni pone puertas a las propias
  llamadas de lectura, escritura, edición y bash de Claude. Donde el entorno
  aislado está activado, es la frontera que los rodea.
- Las herramientas de archivos en proceso del arnés (read, write, edit, apply
  patch, search, find, search_files) se ejecutan dentro del proceso del servidor,
  así que ningún perfil de entorno aislado las limita. Solo la herramienta `bash`
  pasa por el ejecutor de comandos aislado. Esas herramientas están acotadas por
  su propio confinamiento de rutas y por las barandillas de acciones.
- En un host sin backend, la primera fila no se aplica en absoluto. ACP y la
  herramienta `bash` del arnés recurren al saneamiento del entorno más la
  política de comandos; Claude Code hereda el entorno del host a través de
  `NoSandboxAdapter`. El servidor lo indica en su registro de arranque. Consulta
  el tuyo más abajo.

## Definir las capacidades de un agente

Este es el único control de capacidades que lee el servidor. Es por agente y
decide qué pone el bróker de credenciales en el entorno de ese agente.

1. Ve a **Ajustes → Espacio de trabajo → Agentes**
2. Selecciona el agente en la lista
3. En la pestaña **Ajustes**, desplázate hasta **Permisos del sandbox**
4. Activa el interruptor: el texto de la fila cambia de **Usar valor por defecto del espacio de trabajo**
5. Configura los cuatro interruptores:

| Interruptor                           | Qué controla                                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Permitir git push**               | Con esto desactivado, la ejecución recibe `GIT_ASKPASS=/usr/bin/false` y `GIT_TERMINAL_PROMPT=0`, así que un push no puede pedir una credencial                                                                                                                   |
| **Permitir llamadas a la API de GitHub**       | Junto con **Permitir git push**, controla si el bróker inyecta el token de GitHub como `GH_TOKEN` / `GITHUB_TOKEN`                                                                                                                               |
| **Permitir llamadas a la API de tickets**    | Controla si el bróker inyecta `TICKETING_API_KEY`                                                                                                                                                                                             |
| **Permitir acceso general a la red** | Cuando el entorno aislado está activado, esta es una puerta de salida real: si está desactivada, la lista de permitidos de la ejecución queda vacía y el proxy rechaza todas las peticiones salientes. Cuando no hay backend, se registra en la ejecución, pero no bloquea nada de lo que haga un proceso lanzado |

6. Guarda

Punto de control: vuelve a abrir el agente y el interruptor sigue activado con
tus opciones; un conjunto de capacidades guardado va y vuelve por el servidor, y
un agente sin ninguno recurre al valor predeterminado conservador (push
desactivado, API de GitHub desactivada, tickets desactivados, red activada).

:::caution[Dos formas en que esto pasa factura]
El texto dice **Usar valor por defecto del espacio de trabajo**, pero no existe
ningún ajuste de capacidades a nivel de espacio de trabajo que lea el servidor.
Un agente con el interruptor desactivado recibe el valor predeterminado
conservador integrado.

Por otro lado, la credencial de GitHub de la ejecución es siempre la del bróker
—un token de instalación de la GitHub App con alcance de repositorio, o la
alternativa PAT del entorno—, nunca el token propio almacenado de la persona
solicitante. `actingUserId` se pasa para que el bróker pueda *retener* el PAT del
servidor a una persona que no sea la propietaria y que no haya conectado GitHub;
no superpone un token personal a una capacidad que está desactivada. No trates
**Permitir llamadas a la API de GitHub** como una frontera de salida estricta en
un host sin entorno aislado del sistema operativo: un proceso lanzado todavía
puede llegar a la red.
:::

## Comprobar si tus ejecuciones de agente están en un entorno aislado

Lo deciden dos cosas, ambas en el servidor: si el host ofrece un backend y si
`--sandbox` está activado. Compruébalas en ese orden.

1. Ve a **Ajustes → Servidor → Diagnóstico y privacidad**
2. Consulta la tarjeta **Aislamiento**. El dato **Host** es la máquina en la que
   se ejecuta `cc_server`, no la que estás mirando. El campo **Backend** muestra
   **Native sandbox** (Seatbelt en macOS, bubblewrap en Linux y WSL2) o
   **No isolation**. El dato **En vigor** es la preferencia de este dispositivo,
   no el envoltorio que usa realmente el servidor.
3. Consulta el registro de arranque del servidor. Imprime exactamente una de estas tres líneas:
   - `agent sandbox ON` más la nota del backend: las ejecuciones van envueltas
   - `no OS-native agent sandbox on this host` más una indicación de instalación
     cuando existe: las ejecuciones no van envueltas
   - `agent sandbox DISABLED by --sandbox off`: una exclusión deliberada

`GET /healthz` no informa del estado del entorno aislado, así que el registro de
arranque es la comprobación.

Para desactivar el entorno aislado a propósito —un host en el que el perfil se
comporta mal es la razón de que exista esta opción—, inicia el servidor con
`--sandbox off` o define `CC_SERVER_SANDBOX=off`. El valor predeterminado es `on`,
y `on` significa «usar un backend si el host tiene uno», nunca «exigir uno».

Hay dos situaciones que nunca reciben un envoltorio de entorno aislado nativo. En
**Windows**, la sonda nativa siempre informa de que no está disponible y no hay
nada que instalar: el despacho de agentes usa `none`. El backend `microvm` es
aparte (terminales interactivas y rigs) y está sujeto a sonda según su propio
runtime. En **Linux y WSL2**, tanto `bwrap` como `socat` deben estar en el
`PATH`; sin ellos, la sonda informa de que no está disponible y nombra los
paquetes que faltan.

En Linux/WSL2 con bubblewrap instalado, los globs de archivos de secretos de la
política estándar no se pueden aplicar a los archivos que un agente cree después.
Esa ejecución nativa ahora falla en lugar de ignorar las reglas en silencio. Por
tanto, una sonda de arranque positiva no garantiza que un despacho en Linux pueda
iniciarse. `--sandbox off` es una exclusión deliberada sin confinamiento, no una
frontera de seguridad sustitutiva.

## Saber qué prohíbe ya un modo

El modo se guarda por espacio y alimenta al resolutor de barandillas como la capa
de **preajuste del modo**. Tres de los cuatro modos son de solo lectura, y un
modo de solo lectura rechaza once clases de efecto de plano:

| Modo               | Worktree  | Rechazadas por el preajuste                                                                                                                                                            |
| ------------------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent** (`chat`) | Se puede escribir  | Ninguna: se aplican los valores predeterminados integrados                                                                                                                                            |
| **Plan**           | Solo lectura | Eliminar un archivo, escribir fuera del worktree, hacer commit, hacer push, abrir una PR, publicar o fusionar, escribir en un proveedor externo de tickets, instalar un paquete, lanzar un proceso, cambiar la estructura del espacio de trabajo, arrancar o controlar un recinto |
| **Review**         | Solo lectura | Las mismas once. No lo puede seleccionar el usuario: el compositor solo ofrece Agent, Plan y Orchestrate                                                                                         |
| **Orchestrate**    | Solo lectura | Las mismas once                                                                                                                                                                     |

Los modos de solo lectura no rechazan a propósito el acceso a la red ni a los
secretos: la investigación es justo su objetivo.

## Exigir aprobación antes de que se ejecute una acción

La aprobación es una decisión de las barandillas, no un ajuste del entorno
aislado.

1. Ve a **Ajustes → Espacio de trabajo → Permisos de agentes**
2. Define la clase de acción como **Preguntar primero** en el ámbito de espacio de trabajo, agente o espacio

Una decisión **Preguntar primero** interrumpe la ejecución y te pregunta. Si no
hay ningún aprobador conectado, falla en cerrado y la acción se deniega. Consulta
[Configurar barandillas](/es-ES/manual/guias/configurar-barandillas/) para ver el
orden de resolución completo.

## Solución de problemas

### Un agente no puede hacer push y yo nunca lo denegué

Comprueba los **Permisos del sandbox** del agente. Un agente sin conjunto de
capacidades personalizado recibe el valor predeterminado conservador, que tiene
**Permitir git push** desactivado; así que el bróker no inyecta ningún token de
GitHub y git no tiene forma de autenticarse.

### La tarjeta Aislamiento informa de que no hay entorno aislado nativo

Entonces las ejecuciones de agente en ese host no van envueltas por Seatbelt ni
bubblewrap, y las fronteras restantes son las que tienes. En Linux y WSL2,
instala las dos herramientas que faltan —`sudo apt-get install bubblewrap socat`—
y reinicia el servidor; el registro de arranque debería indicar entonces que el
entorno aislado está activado. En Windows no hay ningún backend nativo que
instalar, así que ajusta mejor las barandillas: consulta
[Configurar barandillas](/es-ES/manual/guias/configurar-barandillas/).

### Un agente llegó a un archivo fuera de su worktree

La herramienta con la que llegó decide si esto es lo esperado.

Las herramientas de archivos en proceso del arnés (read, write, edit, apply
patch, search, find, search_files) se ejecutan en el proceso del servidor, así
que no se les aplica ningún perfil de entorno aislado: su límite es su propio
confinamiento de rutas más las barandillas. Un comando `bash` o la CLI de Claude
Code _sí_ van envueltos donde existe un backend, y tus checkouts registrados
tienen la escritura denegada dentro de ese envoltorio en todos los modos,
incluidas sus grafías resueltas por enlaces simbólicos (en macOS, una ruta a la
que se llega a través de `/tmp` o `/var/folders` se resuelve bajo `/private`, y
ahora se deniegan ambas grafías). En un host sin backend, nada de eso se aplica.
En cualquier caso, las barandillas pueden rechazar **Escribir fuera del árbol de
trabajo** de plano.
