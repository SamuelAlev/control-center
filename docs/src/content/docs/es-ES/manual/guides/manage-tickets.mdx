Esta guía te muestra cómo crear y gestionar tickets.

## Crear un ticket

### Desde la interfaz

1. Haz clic en **Tickets** en la barra lateral del espacio de trabajo.
2. Pulsa **Nuevo ticket**.
3. Rellena:
   - **Título** — resumen breve. Es el único campo obligatorio.
   - **Descripción** — markdown, con una barra de formato.
   - **Estado** — **Por hacer** (el valor predeterminado) o **Backlog**. Los
     estados ya iniciados y los terminales se alcanzan mediante el ciclo de
     vida, no en el momento de la creación.
   - **Prioridad** — ninguna, urgente, alta, media o baja.
   - **Asignado a** — tú mismo o cualquier agente del espacio de trabajo.
   - **Proyecto** — agrupación opcional.
4. Pulsa **Crear**, o activa antes **Crear más** para mantener abierto el
   cuadro de diálogo e introducir tickets rápidamente.

En el cuadro de diálogo no hay selector de proveedor. El ticket se crea con
el proveedor de tickets activo del espacio de trabajo.

### Desde un agente

Pide a un agente en un espacio:

> Crea un ticket para arreglar el problema de tiempo de espera de inicio de
> sesión en conexiones lentas.

Llama a la herramienta MCP `create_ticket`. La prioridad en esa herramienta es
un **entero**, no un nombre:

```
create_ticket(
  workspace_id: "...",
  title: "Fix login timeout on slow connections",
  description: "...",
  priority: 2
)
```

| Valor | Prioridad |
| ----- | --------- |
| `0`   | Ninguna   |
| `1`   | Urgente   |
| `2`   | Alta      |
| `3`   | Media     |
| `4`   | Baja      |

Solo `workspace_id` y `title` son obligatorios; `description`, `priority`,
`assignee` (un id de agente) y `team_id` son opcionales. La herramienta está
clasificada como escritura de sincronización con el proveedor y solicita tu
aprobación antes de ejecutarse.

## Cambiar el estado de un ticket

Los tickets siguen este ciclo de vida:

```
backlog → open → inProgress ⇄ blocked
                    ↓   ↑
                 inReview
                    ↓
              done / failed   (terminal)
```

`done`, `failed` y `cancelled` son estados terminales. Se puede llegar a
`cancelled` desde cualquier estado no terminal. Se puede llegar a `done` y
`failed` desde `inProgress` o `inReview`; `open` también puede pasar
directamente a `blocked`. El selector de estado de la interfaz lista todos los
estados excepto `failed`: los agentes marcan ese con `fail_ticket`.

Para cambiarlo, usa cualquiera de estos:

- la fila **Estado** en la barra de propiedades del ticket,
- el submenú **Estado** del menú contextual de un ticket en la lista,
- el chip **Estado** de la barra flotante tras seleccionar varios tickets.

:::note[El grafo del ciclo de vida vincula a los agentes, no a ti]
Todos los cambios de estado hechos desde la interfaz se fuerzan y se saltan el
grafo por completo: puedes mover un ticket a cualquier estado que liste el
selector, incluido reabrir uno `done`, `failed` o `cancelled`. El selector no
ofrece `failed` como destino. El diagrama anterior gobierna a los agentes y la
automatización: una transición ilegal intentada por una herramienta MCP o un
reconciliador se registra y se ignora, no se aplica.
:::

Los cambios de estado emiten eventos de dominio (`TicketStatusChanged`,
`TicketCompleted` y otros) que pueden disparar pipelines. Consulta
[Configurar disparadores de pipeline](/es-ES/manual/guias/disparadores-de-pipeline/).

## Asignar un ticket

1. Abre el ticket.
2. En la barra de propiedades, define **Asignado a** — tú mismo, otro miembro
   del espacio de trabajo o un agente.

:::caution[Asignar no inicia ningún trabajo]
La asignación registra la responsabilidad y nada más. No crea ningún espacio,
no cambia ningún estado y no despacha ningún agente: `TicketAssigned` es una
señal de auditoría pura, sin ningún despachador detrás. Para que un agente se
ponga a trabajar, escríbele en un espacio (consulta
[Chatear con un agente](/es-ES/manual/guias/chatear-con-agente/)).

La única excepción: `TicketAssigned` es un tipo de evento al que puedes
conectar un disparador de pipeline, de modo que una plantilla propia puede
reaccionar a una asignación.
:::

## Añadir etiquetas

Las etiquetas se aplican en bloque desde la lista de tickets, no desde un
ticket individual: la barra de propiedades no tiene ningún control de
etiquetas.

1. Pasa el cursor sobre una fila de la lista de tickets y marca su casilla.
   Marca tantas como necesites; en cuanto haya algo seleccionado, aparece una
   barra flotante.
2. En esa barra, abre el chip **Etiquetas**.
3. Elige una etiqueta. Se añade a todos los tickets seleccionados que no la
   tengan; las etiquetas existentes nunca se borran. **Borrar etiquetas** las
   quita todas. El selector lista las etiquetas que ya hay en algún ticket del
   espacio de trabajo. Los agentes pueden añadir un nombre nuevo mediante
   `update_ticket` o `tickets.patch`.

## Vincular tickets

Las relaciones viven en la tarjeta **Relaciones** del ticket, en la barra de
propiedades, o detrás de **Relacionar con** en el menú contextual de la lista.

1. Abre el ticket y busca la tarjeta **Relaciones**.
2. Pulsa su control de añadir y elige la relación:

| Relación             | Significado                            |
| -------------------- | -------------------------------------- |
| **Subtarea de…**     | El padre de este ticket es el otro     |
| **Padre de…**        | El otro ticket es hijo de este         |
| **Bloqueado por…**   | Este ticket está bloqueado por el otro |
| **Bloquea…**         | Este ticket bloquea al otro            |
| **Relacionado con…** | Simétrica, sin dirección implícita     |
| **Duplicado de…**    | Este ticket duplica al otro            |

3. Elige el ticket de destino.

**Duplicado por** aparece en la tarjeta pero no en el selector: es la inversa
de **Duplicado de** y se define desde el otro ticket. Cada relación listada se
puede pulsar para abrir el ticket vinculado y se puede quitar al pasar el
cursor por encima.

Las relaciones de padre y subtarea se guardan en el propio ticket, no como
filas de vínculo, así que eliminar un padre se propaga en cascada a sus hijos
(consulta más abajo), mientras que los vínculos de bloqueo y de relación no.

## Añadir colaboradores

Los colaboradores son un listado del ticket: quién participa y con qué rol.

1. Abre el ticket.
2. Pulsa el control de persona con signo más de la tarjeta **Añadir
   colaborador**.
3. Elige un agente.

Los tres roles son **assignee**, **collaborator** (el predeterminado) y
**reviewer**. El selector de la interfaz solo lista agentes del espacio de
trabajo y siempre escribe el rol predeterminado; las personas pueden aparecer
como filas, pero no se ofrecen en ese menú. La herramienta MCP
`add_ticket_collaborator` acepta un `role`.

Añadir un colaborador escribe una fila y no publica ningún evento de dominio;
no concede acceso a ningún espacio. Para meter a un agente en una conversación,
añádelo como participante desde la cabecera del espacio: consulta
[Espacios](/es-ES/manual/guias/espacios/).

## Eliminar un ticket

Usa **Eliminar ticket** en la parte inferior de la barra de propiedades, el
menú contextual o la acción de eliminar de la barra flotante tras seleccionar
varios tickets.

:::caution[Eliminar es solo local]
Un ticket que vino de un sistema de seguimiento externo no se elimina allí
—ningún proveedor lo admite—, así que puede reaparecer en la siguiente
sincronización. Además, eliminar se propaga en cascada: los colaboradores del
ticket y cualquier ticket hijo se van con él.
:::
