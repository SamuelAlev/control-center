Control Center puede enviar **eventos de uso seudónimos** a una instancia de [Umami](https://umami.is). Las analíticas de uso están **desactivadas hasta que el operador del servidor las activa**. El ajuste pertenece al servidor y se aplica a todos los clientes conectados a él: la aplicación de escritorio, la aplicación web, el teléfono y el propio servidor.

Las analíticas de uso son independientes de **Compartir informes de fallos**, que es un ajuste por dispositivo para los diagnósticos de fallos y errores.

## Quién decide

| Interruptor | Dónde | Efecto |
| --- | --- | --- |
| **Compartir analíticas de uso** | Incorporación (paso del sandbox) y **Ajustes → Privacidad**. Solo el operador del servidor puede cambiarlo; los demás miembros ven el valor actual en modo de solo lectura | Para todo el servidor. Se guarda como `telemetry.usage_analytics` en los ajustes del servidor. Desactivado salvo que se establezca en `true` |
| Tipo de compilación | Automático | Las compilaciones debug y profile no envían nada. En su lugar, escriben cada evento en el log de depuración |
| `CC_ANALYTICS_DEBUG=1` | Entorno de `cc_server` o su `.env` | Permite que las compilaciones debug y profile del servidor, y de todos los clientes conectados a él, envíen de verdad, para hacer pruebas. El interruptor anterior tiene que seguir activado |
| `DO_NOT_TRACK=1` | Entorno de `cc_server` | Detiene los informes propios del servidor, diga lo que diga el interruptor. Los clientes siguen haciendo caso al interruptor |
| Servidor de demostración | Automático | El servidor de demostración público no envía nada por su cuenta. Los visitantes no pueden cambiar el interruptor |

Los clientes leen el ajuste del servidor (`telemetry.config` y después en directo mediante `telemetry.watch`). Hasta que llega la respuesta, los eventos esperan en un pequeño búfer en memoria. Si la respuesta es no, el búfer se descarta. Al desactivar el interruptor se descarta todo lo que siga en cola y se deja de enviar al instante, en todos los clientes.

## Qué no se envía nunca

- El contenido de mensajes, tickets, revisiones o reuniones, títulos, prompts, comandos de shell y consultas de búsqueda
- Nombres, inicios de sesión, direcciones de correo electrónico, avatares y nombres visibles
- Rutas de archivo, nombres de repositorio, nombres de rama, nombres de host y URL (un repositorio solo se envía como `repo_id` seudónimo, y un enlace de reunión, solo como su proveedor)
- Identificadores sin procesar de cualquier tipo

Cada evento pasa por una política de propiedades antes de salir del proceso. El texto, las rutas, las URL, las direcciones de correo electrónico, los ID sin seudonimizar y las cadenas bajo claves como `email`, `*_name`, `path`, `title`, `prompt`, `content` o `token` se descartan en lugar de enviarse. Una cadena solo se envía si es un token corto de un vocabulario cerrado, como un valor de enumeración, una versión, una configuración regional o un ID de modelo.

## ID seudónimos

Los ID se envían, pero solo como seudónimos. Cada ID de espacio de trabajo, espacio, conversación, agente, ejecución, usuario y dispositivo se sustituye por un HMAC-SHA256 con la sal secreta propia de la instalación (`telemetry.pseudonym_salt`), truncado a 20 caracteres hexadecimales. El mismo espacio de trabajo informa siempre del mismo valor, de modo que los eventos se pueden relacionar y contar, pero el ID sin procesar nunca sale de la instalación. La sal se crea en el primer arranque del servidor y nunca se envía al proveedor de analíticas. Borrar el directorio de datos del servidor crea una sal y un ID de instalación nuevos, lo que desvincula todo lo registrado antes.

| Propiedad | Ejemplo | Significado |
| --- | --- | --- |
| `app_type` | `desktop` | `desktop`, `web`, `remote` (el teléfono) o `server`. También se usa como nombre de host en Umami |

| `server_mode` | `local` | `local` (escritorio con su propio servidor) o `remote` |

## Vistas de pantalla

Cada navegación registra una vista de página cuya URL es la **plantilla de ruta**, como `/workspaces/:workspaceId/spaces/:spaceId`, nunca la dirección concreta. El nombre de la pantalla son los segmentos literales de la plantilla, así que en ese ejemplo es `workspaces_spaces`. Los parámetros de ruta que terminan en `Id` se adjuntan como propiedades `*_id` seudónimas, y los numéricos (como un número de PR), como números. Todos los demás parámetros se descartan.

## Entrega

Los eventos se envían de uno en uno a `<host>/api/send` desde una cola en memoria de hasta 200 eventos. Un error de red, un tiempo de espera agotado, un `429` o un `5xx` conservan el evento y lo reintentan con espera exponencial, desde 1 segundo hasta 5 minutos. Cualquier otro `4xx` lo descarta. No se escribe nada en disco, así que los eventos que sigan en cola al cerrar la aplicación se pierden. La cola se vacía cuando la aplicación pasa a segundo plano y cuando el servidor se apaga.

## Apuntar una compilación a otra instancia

El destino se fija al compilar:

```bash
--dart-define=CC_ANALYTICS_HOST=https://analytics.example.com/
--dart-define=CC_ANALYTICS_WEBSITE_ID=<website uuid>
```

El adaptador del proveedor está en `packages/cc_analytics`. Para admitir otro servicio de analíticas hay que añadir ahí un adaptador. El plan de seguimiento y las reglas de privacidad no cambian.
