Todo lo que Control Center puede copiar, entregar o adoptar, y la forma exacta de cada
artefacto. Para hacer una copia de seguridad de verdad, consulta
[Hacer copia de seguridad y restaurar](/es-ES/manual/guias/copia-de-seguridad-y-restauracion/);
para entender por qué la persistencia está dividida de esta forma, consulta
[Espacios de trabajo y aislamiento](/es-ES/manual/conceptos/espacios-de-trabajo/).

## Artefactos

Hay tres artefactos de copia de la base de datos, con ámbitos y políticas de eliminación distintos.

| Artefacto                            | Escrito por                  | Forma                                                | Cubre                                   |
| ------------------------------------ | ---------------------------- | ---------------------------------------------------- | --------------------------------------- |
| **Instantánea de la instalación**    | `server.backupNow`           | Un **directorio** con marca de tiempo                | Todas las bases de datos de la instalación |
| **Copia de seguridad de un espacio de trabajo** | Pipeline `Workspace backup` | Directorio con marca de tiempo con un archivo `.db` | La base de datos de un espacio de trabajo |
| **Exportación de un espacio de trabajo** | `workspace.export`       | Un único **archivo** `.db`                           | La base de datos de un espacio de trabajo |

Todos se escriben con `VACUUM INTO` de SQLite, que es seguro frente a una base de datos
WAL activa: toma una transacción de lectura, produce una copia desfragmentada y
transaccionalmente coherente, y nunca exige detener el servidor.

Estos archivos y las copias descargadas **no están cifrados en reposo** por
Control Center. La transferencia cifrada de extremo a extremo protege los bytes
en tránsito entre un cliente emparejado y su `cc_server`, tanto en conexiones
directas como a través del relé. Protege por separado el almacenamiento local y
las copias fuera de la máquina; el servidor y cualquier destinatario autorizado
pueden leer los archivos de base de datos.

## Estructura de la instantánea

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

La estructura replica exactamente el directorio de datos activo, que es lo que hace que
restaurar una instalación sea copiar de vuelta en lugar de traducir. El nombre del
directorio es la marca de tiempo UTC con `:` y `.` sustituidos por `-`, de modo que es
seguro para el sistema de archivos en Windows y se ordena cronológicamente como una
cadena simple.

Las copias de seguridad programadas de espacios de trabajo viven aparte, en
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Cada una tiene un `manifest.json` para ese único archivo y no `global.db`; no son instantáneas de la instalación. Una restauración conserva la base de datos que sustituye en el mismo lugar, como `<timestamp>-pre-restore`.
El paso de retención del pipeline semanal elimina únicamente las copias de seguridad de
su propio espacio de trabajo más antiguas que la antigüedad configurada (30 días de forma
predeterminada); las instantáneas de la instalación creadas a mano nunca se rotan con ese
paso. `server.listBackups` solo lista instantáneas de la instalación, incluidas las sin verificar; `workspace.listBackups` lista las copias de seguridad programadas de un
espacio de trabajo.

Eliminar un espacio de trabajo deja este directorio en su sitio. La programación del espacio
de trabajo se detiene con él, así que ya nada rota esas copias de seguridad, y se quedan ahí
hasta que el propietario de la instalación las elimine. `server.listOrphanedBackups` las
notifica.


### `manifest.json`

| Campo                       | Tipo            | Significado                                                         |
| --------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                   | int             | Formato del manifiesto. Actualmente `2`                 |
| `created_at`                | ISO-8601 UTC    | Cuándo se tomó la instantánea                                       |
| `global`                   | object          | El registro de `global.db`. Ausente de una copia de seguridad programada de espacio de trabajo |
| `workspaces[]`              | array           | Un registro por espacio de trabajo capturado                        |
| `workspaces[].workspace_id` | string          | El espacio de trabajo al que pertenece este archivo                 |
| `skipped_workspaces[]`     | array           | Espacios de trabajo que la copia de seguridad **no** pudo capturar                         |
| `skipped_workspaces[].workspace_id` | string | El espacio de trabajo que se dejó fuera                                     |
| `skipped_workspaces[].reason` | string       | `no_file`, `damaged` o `failed`                                    |

`global` y cada registro de `workspaces[]` describen un archivo copiado, medido en la copia después de escribirla:

| Campo            | Tipo   | Significado                                                                    |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`         | string          | Ruta relativa a la raíz de la instantánea: `global.db` o `<workspaceId>/workspace.db` |
| `bytes`        | int             | Tamaño de la copia                                               |
| `sha256`         | string | SHA-256 de la copia, en hexadecimal en minúsculas                              |
| `quick_check`    | string | Lo que dijo el `quick_check` de SQLite sobre la copia: `ok`, o su hallazgo      |
| `user_version`   | int    | Versión del esquema de la copia                                                |
| `application_id` | int    | `application_id` de SQLite de la copia                                         |

Un espacio de trabajo se omite cuando está registrado pero nunca se ha escrito en él (`no_file`), cuando su base de datos no supera la comprobación de integridad (`damaged`; nunca se toma una copia dañada), o cuando su copia o la comprobación de esa copia falló (`failed`). En cualquier caso, la instantánea se completa igualmente y el manifiesto indica qué falta. El manifiesto se escribe el último.

### Completitud

`server.listBackups` informa de un indicador `complete` por instantánea. Es falso cuando el manifiesto falta, no se puede analizar o tiene otro formato, cuando falta un archivo que nombra o tiene otro tamaño, o cuando una copia no superó su comprobación. La aplicación muestra una instantánea así como **Sin verificar**. Las instantáneas tomadas antes del formato `2` están en ese estado.

Una instantánea sin verificar se lista igualmente, porque una instantánea que un operador no
puede ver es una instantánea que cree tener. Cuando el manifiesto no se puede leer, el
listado recurre a la propia estructura e informa de los archivos
`<workspaceId>/workspace.db` que encuentre; esos siguen siendo adoptables individualmente
mediante `workspace.import` aunque la instantánea en su conjunto no pueda restaurar una
instalación.

Una instantánea o copia de seguridad programada listada lleva `pinned_reason: "last_good_copy"` mientras conserva la copia verificada más reciente de un espacio de trabajo cuya base de datos activa está dañada. El paso de retención la omite hasta que ese espacio de trabajo se restaure.

## Qué no contiene una copia de seguridad

Ambos artefactos son **solo bases de datos**. El directorio de un espacio de trabajo
contiene más que su base de datos, y nada del resto viaja:

| Ruta                                | ¿En una instantánea? | ¿En una exportación de espacio de trabajo? |
| ----------------------------------- | -------------------- | ------------------------------------------ |
| `global.db`                         | Sí                   | No                                         |
| `<workspaceId>/workspace.db`        | Sí                   | Sí (el archivo *es* este)                  |
| `<workspaceId>/code_index.db`       | No             | No                     |
| `<workspaceId>/blobs/`              | No                   | No                                         |
| `<workspaceId>/skills/`             | No                   | No                                         |
| `<workspaceId>/agents/`             | No                   | No                                         |
| `<workspaceId>/chat_credentials/`   | No                   | No                                         |
| `<workspaceId>/spaces/<spaceId>/`   | No                   | No                                         |
| `<workspaceId>/pr_clones/`          | No                   | No                                         |
| `secrets.json`                      | No                   | No                                         |
| `models/`                           | No                   | No                                         |
| `meetings/<meetingId>/`             | No                   | No                                         |
| `rigs/`                             | No                   | No                                         |
| `_agent_hooks/`                     | No                   | No                                         |

Parte de eso es prescindible: `spaces/` contiene worktrees con copy-on-write que se reaprovisionan desde los repos, `pr_clones/` es una caché, `code_index.db` se reconstruye, `models/` se vuelve a descargar y `rigs/` es estado de la máquina. Parte no lo es: `blobs/` contiene imágenes pegadas a las que apuntan filas de la base de datos, `skills/` y `agents/` contienen los archivos con los que se ejecuta un agente, y `secrets.json` contiene todas las claves de emparejamiento, credenciales de proveedores y ajustes de SSO de la instalación. Consulta [Hacer copia de seguridad y restaurar](/es-ES/manual/guias/copia-de-seguridad-y-restauracion/#copiar-las-copias-de-seguridad-fuera-de-la-máquina) para cubrir el resto.
:::note[Los secretos no se guardan en las bases de datos]
`workspace.db` es todo el espacio de trabajo: conversaciones, registros de ejecución, vínculos con repositorios, definiciones de entornos y miembros. Los tokens de webhook de las canalizaciones y los secretos de webhook de sincronización de tickets están en `secrets.json`: la base de datos guarda una referencia a cada uno, y el índice de rutas guarda un hash con clave de cada token. Por eso, un espacio de trabajo restaurado en otra instalación no recibe ningún webhook hasta que sus disparadores se guarden de nuevo allí. Los inicios de sesión de proveedores, las claves de dispositivos y los secretos de usuario están en `global.db` y `secrets.json`.
:::

:::note[Los tokens de chat se quedan atrás a propósito]
Que `chat_credentials/` esté junto a la base de datos en lugar de dentro de ella es por lo
que un espacio de trabajo entregado a otra persona no lleva tokens de bot activos.
Consulta la [referencia del puente de chat](/es-ES/manual/referencia/puente-de-chat/).
:::

## Operaciones

Las RPC de copia de seguridad de la instalación y la exportación e importación de espacios
de trabajo son solo para `fullClient`: un teléfono emparejado no puede activarlas. Todas
están ausentes por completo —no se rechazan, faltan estructuralmente— en un servidor sin
el puerto de copia de seguridad conectado, como el servidor de demostración.

| Operación             | Tipo     | Ámbito     | Rol mínimo                        | Argumentos    | Devuelve                      |
| --------------------- | -------- | ---------- | --------------------------------- | ------------- | ----------------------------- |
| `server.backupNow`    | mutación | Instalación | **propietario** de la instalación | ninguno       | `{ok, path}`                  |
| `server.listBackups`  | lectura  | Instalación | **propietario** de la instalación | ninguno       | `{backups: [...]}`            |
| `server.deleteBackup` | mutación | Instalación | **propietario** de la instalación | `name`        | `{ok}`                        |
| `server.listOrphanedBackups` | lectura | Instalación | **propietario** de la instalación | ninguno | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutación | Instalación | **propietario** de la instalación | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | lectura | Espacio de trabajo | `admin` | ninguno | `{backups: [...]}` |
| `workspace.deleteBackup` | mutación | Espacio de trabajo | `owner` | `name` | `{ok}` |
| `workspace.export`    | lectura  | Espacio de trabajo | `admin`                    | ninguno       | `{ok, path}`                  |
| `workspace.import`    | mutación | Espacio de trabajo | `owner`, y el propietario del servidor | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | lectura | Espacio de trabajo | `owner`, y el propietario del servidor | ninguno | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutación | Espacio de trabajo | `owner`, y el propietario del servidor | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`    | mutación | Instalación* | `owner`                         | `id`          | fila del registro marcada como eliminada |

* `workspace.delete` no tiene ámbito porque la fila que marca vive en el registro global;
su manejador comprueba la pertenencia de quien llama al espacio de trabajo nombrado y
exige `owner`.

La `path` de cada respuesta es una ruta del **host del servidor**.

`server.listOrphanedBackups` devuelve una entrada por cada espacio de trabajo que ya no está
activo: `workspace_id`, `workspace_name` cuando el registro aún lo conoce, y `backups`.
Un espacio de trabajo eliminado ya no puede superar una comprobación de rol de espacio de
trabajo, así que sus copias de seguridad pertenecen al propietario de la instalación.
`server.deleteOrphanedBackup` rechaza un espacio de trabajo activo, cuyas copias de seguridad
siguen protegidas por `workspace.deleteBackup` y por los roles de ese espacio de trabajo.
Ambas operaciones de eliminación solo aceptan un nombre de directorio de marca de tiempo
listado, no una ruta.

`workspace.importHolds.list` devuelve lo que retuvo una importación. Cada retención tiene un `id`, un `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` o `invite`), el `payload` que volvería a poner, `imported_at` y `source_install_id`. `workspace.importHolds.resolve` con `accept: true` la concede de nuevo y con `false` la descarta. `applied` es false cuando la persona o el elemento al que iba destinada la concesión ya no está en el espacio de trabajo.

:::note[Una instantánea de toda la instalación está reservada al propietario en ambos canales]
`server.backupNow`, `server.listBackups` y `server.deleteBackup` exigen el
**propietario** de la instalación (`ServerAuthority.serverOwner`), la misma puerta que
`GET /backup/snapshot`. Una instantánea captura la base de datos de todos los espacios de
trabajo, así que ser administrador de un espacio de trabajo no basta para gestionar los
demás. La eliminación solo acepta el nombre del directorio con marca de tiempo que aparece
en el listado, no una ruta arbitraria del servidor, y elimina la instantánea completa
(incluidas las instantáneas sin verificar). Las exportaciones por espacio de trabajo y las descargas de copias programadas siguen correspondiendo al administrador del espacio de trabajo.
:::

:::note[La restauración es del propietario del servidor]
`workspace.import` y `POST /backup/restore` hacen que el servidor adopte un archivo de base de datos cuyas filas después trata como propias: los vínculos con repositorios y quién los creó, las definiciones de entornos que se ejecutan en el host, y las rutas de worktrees y registros. Por eso ambas requieren al propietario del servidor (`ServerAuthority.serverOwner`), que además debe ser el propietario del espacio de trabajo. Cualquier otro, y todo llamador en un host sin propietario registrado, recibe un rechazo con `server_owner_required`. No se adopta ningún disparador, vista, columna ni restricción que traiga el archivo.
:::

### Respuesta de `server.listBackups`

De la más reciente a la más antigua, ordenadas por nombre de directorio (que es la marca
de tiempo, así que el orden se mantiene incluso para una instantánea cuyo manifiesto no se
pudo leer).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` se omite cuando el manifiesto no se pudo leer. `bytes` en el nivel superior es
el tamaño real en disco de todo el directorio, no la suma del propio manifiesto: la
pregunta que se hace un operador que poda instantáneas es cuánto ocupa el directorio, no
cuánto pretendía escribir la copia de seguridad.

Cada `workspaces[].path` es exactamente lo que `workspace.import` toma como
`source_path`. Es deliberado: «restaurar este espacio de trabajo desde esta instantánea»
*es* la operación de importación, así que ambas no pueden divergir hacia tratamientos
distintos del mismo archivo.

### Validación de `workspace.import`

Antes de sustituir nada, el archivo candidato se copia a un archivo de preparación junto al destino y se comprueba allí. Un rechazo no toca nada y lleva su tipo como `data.kind`.

| Condición                                                | Resultado                                                       |
| -------------------------------------------------------- | --------------------------------------------------------------- |
| El archivo no existe | Se rechaza, `import.missing_source` |
| No es una base de datos SQLite legible, o no supera `quick_check` | Se rechaza, `import.damaged` |
| Viene de una instantánea y su SHA-256 difiere del que figura en el manifiesto | Se rechaza, `import.checksum_mismatch` |
| Una versión más reciente del servidor lo escribió | Se rechaza, `import.newer_schema` |
| Otro `application_id`, o no tiene `workspace_meta` | Se rechaza, `import.foreign_file` |
| No se puede llevar al esquema de este servidor | Se rechaza, `import.schema_mismatch` |
| Sus webhooks o invitaciones ya apuntan a otro espacio de trabajo | Se rechaza, `import.route_conflict` |
| El id de espacio de trabajo registrado ≠ el de destino    | **Se permite**. Sus filas se reasignan al id de destino. Así es como se duplica un espacio de trabajo o se restaura con un id nuevo |
| El id de instalación registrado ≠ esta instalación        | **Se permite**. Sus ids de usuario pertenecen a esa instalación y no se resolverán aquí |

Al aceptarlo, el archivo preparado se lleva al esquema de este servidor y después debe coincidir exactamente con él. Las concesiones que un archivo no puede darse a sí mismo se le quitan: las aprobaciones para ejecutar una definición de entorno en el host se borran, y las reglas de acción que permiten o que piden confirmación, las concesiones de ejecución en sandbox, las concesiones de repositorio por encima de lectura, los roles por encima de miembro y las invitaciones a esos roles pasan a retenciones que el propietario del servidor debe revisar. Quien importa conserva o recibe el rol de propietario. La base de datos que se sustituye se conserva como copia de seguridad programada llamada `<timestamp>-pre-restore`; el archivo preparado se renombra y ocupa su lugar con las conexiones del espacio de trabajo cerradas, `code_index.db` se elimina para reconstruirlo, y los índices FTS se reconstruyen.

## Rutas de transferencia

Las operaciones de exportación/importación y de listado de instantáneas anteriores
hablan en rutas del lado del servidor, lo cual es una respuesta completa solo
cuando el servidor es tu propia máquina. Estas rutas con forma de HTTP
transportan los bytes de la copia de seguridad **dentro del mismo túnel de
recursos autenticado y cifrado de extremo a extremo** que otros recursos
sensibles, tanto si la conexión RPC es directa como si pasa por el relé. No son
endpoints públicos de transferencia de archivos HTTP: una petición a uno de ellos
en el listener público devuelve `426 Upgrade Required`, incluso desde loopback.
Dentro del túnel cifrado, el dispositivo autenticado con Noise debe coincidir con
`d`; el manejador comprueba además la firma del dispositivo sobre su cadena de
destino usando su PSK de emparejamiento y el rol de más abajo.

| Ruta                    | Método | Consulta        | Destino firmado                  | Requiere                     |
| ----------------------- | ------ | --------------- | -------------------------------- | ---------------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **admin** del espacio de trabajo |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **propietario** de la instalación |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **admin** del espacio de trabajo; **propietario** de la instalación una vez eliminado el espacio de trabajo |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **propietario** de la instalación que además es **propietario** del espacio de trabajo (`403` con `server_owner_required` en otro caso) |

`w` es un id de espacio de trabajo, `n` un nombre de directorio de instantánea o de copia de
seguridad programada, `d` el id del dispositivo que llama y `s` la firma. En `/backup/snapshot`,
`n` se resuelve contra el listado de copias de
seguridad en lugar de concatenarse a la raíz de las copias de seguridad, así que la ruta
no puede apuntarse a un directorio que el listado no habría mostrado. En `/backup/stored`
debe ser un nombre de marca de tiempo, y el archivo debe ser un archivo real dentro del
directorio de copias de seguridad propio de ese espacio de trabajo.

| Estado | Causa                                                                              |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | Falta un parámetro de consulta obligatorio, un nombre de copia de seguridad no es válido, el cuerpo de una subida está vacío, o el archivo subido fue rechazado (el cuerpo es `{error, kind}` con un tipo `import.*`) |
| `403`  | Dispositivo desconocido o revocado, firma incorrecta, o quien llama carece del rol   |
| `404`  | No hay puerto de copia de seguridad en este host, o la instantánea, la copia de seguridad o el archivo de espacio de trabajo indicados no existen |
| `405`  | Se llama a `/backup/restore` con algo distinto de `POST`                             |
| `413`  | El cuerpo de la subida supera los 8 GiB, por la longitud de contenido declarada o por los bytes leídos realmente |
| `426`  | Cualquier petición directa a una ruta de transferencia en el listener HTTP público; usa el túnel de recursos cifrado de un cliente emparejado |
| `500`  | La exportación o el archivado falló en el lado del servidor                          |

Las tres descargas responden con `Cache-Control: no-store` y `Accept-Ranges: none`.
`/backup/workspace` y `/backup/snapshot` acuñan una copia **nueva** por solicitud y la eliminan una vez transmitida, así que una
respuesta cacheada o reanudada uniría bytes de dos exportaciones distintas en un único
archivo que parece válido y no lo es.

`/backup/stored` es la excepción: transmite una copia de seguridad programada como `<workspaceId>-<name>.db`
y deja el archivo en su sitio, porque ese archivo es la copia de seguridad.

`/backup/snapshot` devuelve `<name>.zip`, con las entradas relativas a la raíz de la
instantánea, de modo que descomprimirlo reproduce `manifest.json` + `global.db` +
`<workspaceId>/workspace.db`. Las entradas se escriben en orden de clasificación, así que
dos archivos comprimidos de la misma instantánea son idénticos.

`/backup/restore` transmite el cuerpo directamente a un archivo de preparación en lugar de
almacenarlo en búfer, lo acota antes y durante la lectura, y elimina el archivo preparado
en **todas** las salidas posibles, incluida una denegación.

::::caution[La conexión directa y el relé usan la misma transferencia cifrada]
El relé transporta peticiones de recursos, respuestas en streaming y bytes de
subida como texto cifrado; no puede leer el contenido de las copias de seguridad.
Una ruta del lado del servidor sigue siendo una ruta en el host del servidor, no
un archivo en el relé. El acceso sigue requiriendo el dispositivo emparejado, la
firma del destino y el rol aplicable de espacio de trabajo o de instalación.
Ninguno de los dos transportes cifra los archivos de copia de seguridad
resultantes en reposo.
::::

## Rutas y límites

| Cosa                               | Valor                                                        |
| ---------------------------------- | ------------------------------------------------------------ |
| Instantáneas                       | `<dataDir>/backups/<timestamp>/`                             |
| Copias de seguridad programadas de espacios de trabajo | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Exportaciones de espacios de trabajo | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Base de datos sustituida por una restauración | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Bases de datos tal como estaban antes de que una actualización cambiara su formato | `<dataDir>/pre_upgrade/` y `<dataDir>/<workspaceId>/pre_upgrade/`, las dos más recientes de cada una |
| Preparación de transferencias      | `<dataDir>/backups/transfer/` — un banco de trabajo, barrido por la ruta que escribe en él |
| Nombre del archivo de la instantánea | `<snapshot directory name>.zip`                              |
| Techo de subida                    | 8 GiB por subida cifrada a `/backup/restore`                 |
| Retención                          | Instantáneas de la instalación: eliminación manual. Copias de seguridad de espacios de trabajo: pipeline semanal, 30 días de forma predeterminada, o eliminación manual. Copias de seguridad de un espacio de trabajo eliminado: solo eliminación manual |

Los directorios `exports/`, `transfer/` y `workspace-backups/` no son instantáneas de la
instalación y se excluyen de `server.listBackups`. Solo el último directorio tiene
retención programada, y solo mientras exista su espacio de trabajo; eliminar una instantánea de la instalación exige la acción explícita
del propietario de la instalación.
