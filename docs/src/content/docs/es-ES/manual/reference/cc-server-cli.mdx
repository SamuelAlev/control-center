Cada flag del proceso se da como flag de CLI o como variable de entorno: gana el
flag, después la variable de entorno y, por último, el valor predeterminado. Las
credenciales de los proveedores son la excepción — consulta
[Apps de proveedor y Connect](#apps-de-proveedor-y-connect).

:::caution[Los flags desconocidos se ignoran en silencio]
El analizador de argumentos está hecho a mano y se salta todo lo que no reconoce, así que una errata (`--tls-key-file`, `--bindany`) no produce ningún error — el servidor simplemente arranca con el valor predeterminado. Revisa las líneas del registro de arranque cuando un flag parezca no tener efecto. Un [flag del modo código](#modo-código) con un valor que no acepta es distinto: el servidor se niega a arrancar.
:::

## Opciones principales

| Flag            | Variable de entorno    | Predeterminado                                   | Significado                                                                                                    |
| --------------- | ---------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `--data-dir`    | `CC_SERVER_DATA_DIR`   | el directorio de datos de aplicación por usuario del sistema operativo (ver abajo) | Bases de datos, secretos, modelos y medios en caché |
| `--port`        | `CC_SERVER_PORT`       | `9030`                                           | Puerto TCP (`0` = efímero)                                                                                     |
| `--bind`        | `CC_SERVER_BIND`       | `loopback`                                       | `loopback`, o `any`/`all`/`0.0.0.0` para todas las interfaces (necesita TLS o `--insecure`)                    |
| `--repo-roots`  | `CC_SERVER_REPO_ROOTS` | el directorio personal del usuario del servidor  | Directorios base separados por comas que un cliente puede explorar al registrar un repo. Se rechaza explorar por encima de una raíz |
| `--log-level`   | `CC_SERVER_LOG_LEVEL`  | `warning`                                        | `debug`, `info`, `warning` o `error`. Las líneas de arranque y de preparado siempre se imprimen               |
| `--server-name` | `CC_SERVER_NAME`       | el nombre de host de la máquina                  | Nombre que se muestra en los selectores, el descubrimiento y las pantallas de emparejamiento                   |

## Apps de proveedor y Connect

Ninguna compilación lleva credenciales de proveedores. Con Control Center Connect activado, Connect ejecuta cada proveedor, y estas apps propias se quedan guardadas pero sin usar. Con **Usar mis propias apps**, cada proveedor funciona con la app propia del servidor cuando hay una configurada por completo; si no, no está disponible. Una app propia del espacio de trabajo se aplica en ambos casos.
Las apps propias se configuran en **Ajustes → Servidor → Inicio de sesión
único → Aplicaciones de proveedor**, o se siembran una vez desde el archivo
`.env` del servidor. No hay flags para ellas: un secreto en una línea de
comandos se puede leer con `ps`.

| Variable                       | Significado                                                                                   |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| `GITHUB_APP_ID`                | El id de la GitHub App del servidor                                                           |
| `GITHUB_APP_PRIVATE_KEY`       | Su clave privada, en una sola línea con escapes `\n`. **Solo en `.env`**                      |
| `GITHUB_CLIENT_ID`             | Su id de cliente, para iniciar la sesión de las personas                                      |
| `GITHUB_CLIENT_SECRET`         | Su secreto de cliente. **Solo en `.env`**                                                     |
| `GOOGLE_OAUTH_CLIENT_ID`       | El cliente de Google de tipo aplicación web del servidor                                      |
| `GOOGLE_OAUTH_CLIENT_SECRET`   | Su secreto. **Solo en `.env`**                                                                |
| `LINEAR_CLIENT_ID`             | La aplicación de Linear del servidor (PKCE, sin secreto)                                      |
| `LINEAR_API_KEY`               | Una clave de servicio de Linear para la automatización. **Solo en `.env`**                    |
| `KLIPY_APP_KEY`                | La clave de Klipy propia del servidor para la búsqueda de GIF, usada solo con **Usar mis propias apps** |
| `CC_CONNECT_URL`               | `hosted`, `off` o una URL de Connect. Bloquea la elección de Connect; Ajustes ya no puede cambiarla |
| `CC_SERVER_CONNECT_HOST`       | `on` monta Control Center Connect en `<server>/connect`, configurado con variables `CONNECT_*`. Consulta [Ejecutar un servidor Connect](/es-ES/manual/guias/ejecutar-servidor-connect/#montar-connect-dentro-de-cc_server) |

El archivo `.env` se lee del directorio de trabajo del servidor, junto al
ejecutable, o de un checkout del código fuente por encima de él; en Docker,
móntalo en `/app/bin/.env`. El servidor **se niega a arrancar** (código de
salida `78`) cuando `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`,
`GOOGLE_OAUTH_CLIENT_SECRET`, `LINEAR_API_KEY` o cualquier `SLACK_*SECRET*`
están exportados en el entorno de su proceso, donde cualquier proceso hijo
podría leerlos. El sembrado desde `.env` ocurre una vez por campo, así que una
edición posterior en Ajustes no queda deshecha por un reinicio. Un valor vacío
se interpreta como no definido.

Ninguna credencial de host de código sale del entorno: GitHub, GitLab y Bitbucket
actúan todos con el inicio de sesión o el token propio de un miembro, o con tokens
de GitHub App limitados a un único repositorio.

### `--sandbox`

El servidor sondea el host una vez al arrancar y envuelve la ejecución de comandos
de los agentes en el entorno aislado nativo del sistema operativo cuando hay un
backend disponible: `sandbox-exec` (Seatbelt) en macOS, y `bwrap` más `socat` en
Linux y WSL2. La decisión se toma una vez y se mantiene hasta que el servidor se
reinicia. Hay tres resultados, cada uno mostrado en la línea de exposición de arranque:

| `sandbox=`    | Cuándo                                  | Qué ejecuciones de agentes arrancan                                              |
| ------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| `native`      | Hay un backend disponible y `--sandbox` es `on` | Las de todos, envueltas                                                    |
| `off`         | `--sandbox off`                         | Las de todos, sin confinar en este host                                          |
| `unavailable` | `--sandbox on` y no hay backend (Windows, o Linux sin `bwrap` y `socat`) | Solo las que es responsable el propietario del servidor, sin confinar. Las demás se rechazan con «Este servidor no tiene sandbox, así que solo su propietario puede ejecutar agentes aquí.» |

Para la automatización, la persona responsable es aquella a la que está vinculada la automatización. Sin propietario de servidor registrado, no arranca ninguna ejecución en un host `unavailable`. En Linux y WSL2 con bubblewrap instalado, el despacho nativo actualmente falla de forma cerrada para cada ejecución; consulta [Backends de sandbox](/es-ES/manual/referencia/backends-de-entorno-aislado/#linux-bubblewrap).

`--sandbox off` es la decisión del propietario del servidor para todos los que usan el servidor: ejecuta los agentes de todos los miembros sin confinar en esta máquina. Úsalo en un host donde el propio perfil del entorno aislado se comporta mal, o para que los miembros ejecuten agentes en un host sin backend. No necesita recompilarse, y el servidor registra una advertencia durante toda la vida del proceso para que el estado nunca pase desapercibido.

### `--tool-deferral`

Las ejecuciones del arnés integrado envían un pequeño conjunto directo de definiciones de herramientas más un índice solo con los nombres del resto, cuyos esquemas se cargan la primera vez que se usan o que se llaman desde un script de `repl`. Mantiene el conjunto siempre visible dentro del rango en el que los modelos seleccionan herramientas de forma fiable. Medido sobre el registro que construyen las pruebas, las herramientas de chat estándar del agente integrado suman 14 definiciones: unos 16,5 KB con `repl` (unos 4 KB de ellos de `repl`, cuya definición no puede superar 4.096 bytes), y unos 13 KB en un servidor que no puede ejecutar scripts. Las herramientas diferidas siguen siendo invocables por su nombre en todo momento, y `search_tools` las encuentra por intención. Consulta [Contexto de herramientas y caché de prompts](/es-ES/manual/conceptos/contexto-de-herramientas/).

`--tool-deferral off` envía la definición de cada herramienta admitida por adelantado, salvo que una ejecución con `repl` sigue llamando desde scripts a las herramientas que un script puede llamar. Es el interruptor de emergencia para un modelo que lleva mal la superficie de dos niveles: un flag en lugar de una recompilación. Solo afecta al arnés integrado; el `tools/list` de MCP que ven los clientes externos es el catálogo completo, salvo para una ejecución de agente en un servidor que puede ejecutar scripts del [modo código](/es-ES/manual/conceptos/modo-codigo/).

### `--credential-gate`

Una ejecución cuya credencial de proveedor falta o está agotada se **aparca** en
lugar de fallar: el operador recibe un aviso para arreglarla, y la ejecución se
reanuda si lo hace. El plazo predeterminado es de 900 segundos (15 minutos),
acotado entre 0 y 3600.

El plazo es deliberadamente mucho más largo que el del aviso de aprobación: una
aprobación es una decisión que alguien toma en segundos, mientras que arreglar una
credencial implica abrir un terminal, iniciar sesión y volver. Ese techo es lo que
evita que una ejecución desatendida —un paso de pipeline, un disparador de cron,
un webhook— se quede esperando a alguien que está durmiendo. Cuando vence, la
ejecución falla con el mensaje con el que habría fallado de todos modos.

`--credential-gate=0` es el interruptor de emergencia: nunca se aparca nada y una
credencial defectuosa termina el turno exactamente como lo hacía antes de que
existiera esta puerta.

### Modo código

El [modo código](/es-ES/manual/conceptos/modo-codigo/) permite a un agente ejecutar un script de JavaScript que llama a sus herramientas. No hay ningún flag que lo active o lo desactive: cada ejecución recibe la herramienta `repl` cuando el servidor puede ejecutar scripts, y un servidor de demostración público no ejecuta ninguno.

Los scripts se ejecutan en `cc_codemode`, un programa incluido con el servidor en `bin/codemode/`. El servidor no arranca sin él: imprime una línea con lo que falta y sale con código `78`. Al arrancar ejecuta la autoprueba del bloqueo del programa e imprime una línea (solo se silencia con `--log-level error`):

```text
cc_server: code_mode=available (cc_codemode 0.1.0 quickjs-ng 0.16.2 protocol 2; 16 scripts at once, at most 12 per workspace; up to 64 more runners kept for scripts waiting on a person; heap at most 1024 MiB per script)
cc_server: code_mode=unavailable (<reason>) — runs on this host get no repl tool; scripts never run without full lockdown
```

`unavailable` significa que el programa no puede bloquearse en este host, por ejemplo dentro de un contenedor cuyo perfil de seguridad rechaza uno de sus pasos, o que no sea una compilación de versión. El servidor funciona con normalidad, ninguna ejecución recibe `repl` y los ajustes del modo código del espacio de trabajo muestran el motivo.

El servidor sigue comprobando mientras se ejecuta. Cuando el programa no arranca por una razón que no es la del script, el servidor vuelve a ejecutar la autoprueba, como máximo una vez por minuto. Si falla, el servidor imprime la línea `unavailable` con su motivo y no ejecuta scripts: las ejecuciones que empiecen mientras tanto no reciben `repl`, y una ejecución que ya lo tiene llama a sus herramientas directamente ([Cuando no se pueden ejecutar scripts](/es-ES/manual/conceptos/modo-codigo/#cuando-no-se-pueden-ejecutar-scripts)). Sigue comprobando, como máximo una vez por minuto, y cuando la autoprueba vuelve a pasar imprime la línea `available` y vuelve a ejecutar scripts. Solo una autoprueba que falló al arrancar necesita un reinicio. El motivo que muestran los ajustes del espacio de trabajo no incluye las rutas de la máquina; la línea de registro lo muestra completo.

Los dos flags del modo código acotan lo que pueden usar los scripts. `--code-mode-max-processes` limita los scripts que se ejecutan a la vez en todos los espacios de trabajo (por defecto, el doble de los núcleos del procesador, como máximo 16; se aceptan de 1 a 64). Con un límite de 2 o más, un espacio de trabajo usa como máximo el límite menos una cuarta parte de él, así que ningún espacio de trabajo puede ocupar todos los lugares, y los scripts en espera se admiten por turnos entre espacios de trabajo. Un script que espera la aprobación o la respuesta de una persona cede su lugar a otro script y no inicia ninguna llamada a herramienta hasta que se le responda; se conservan hasta cuatro veces el límite de estos scripts en espera, como máximo tres cuartas partes de ellos proceden de un mismo espacio de trabajo, y cada uno puede seguir calculando dentro de su propio límite de tiempo de procesador. `--code-mode-max-heap-mb` es la memoria máxima que puede usar un script.

Un valor que estos flags no aceptan (un número fuera de rango, o algo que no es un número) detiene el servidor al arrancar (código de salida `78`) con un mensaje que nombra los valores aceptados. Nunca se interpreta como el valor predeterminado.

## Subcomandos

| Comando                                       | Qué hace                                                                                            |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `cc_server`                                   | Ejecuta el servidor hasta que recibe `SIGINT`/`SIGTERM`                                             |
| `cc_server pair`                              | Aprovisiona un dispositivo e imprime su id y su clave de emparejamiento. Es seguro aunque un servidor ya esté sirviendo ese directorio de datos — el servidor en ejecución detecta el dispositivo sin reiniciarse |
| `cc_server connect <command>`                 | Muestra o cambia qué Control Center Connect usa este servidor, sin arrancarlo                      |
| `cc_server update`                            | Busca, descarga y verifica una versión independiente más reciente                                   |
| `cc_server --version`                         | Imprime la versión de compilación y el SHA de git — la misma identidad que anuncian `/healthz` y el handshake de RPC |

### `pair`

| Flag           | Predeterminado                                            | Significado                                                                                                                                                          |
| -------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device`     | `web-client`                                              | El id del dispositivo. La plataforma se infiere de él, así que `--device desktop` crea una fila de escritorio y `--device ios`/`android` una fila de teléfono; cualquier otro valor se trata como web |
| `--label`      | el nombre de la plataforma más el nombre de host de esta máquina | Nombre visible en la lista de dispositivos                                                                                                                    |
| `--host`       | `localhost`, o `<this-host>` cuando se enlaza a cualquier interfaz | Host que se incluye en la URL impresa. Defínelo con la IP de la LAN o el host del túnel al que un cliente se conectará de verdad                            |
| `--client-url` | sin definir                                               | Origen del cliente **web** alojado. Añade un enlace directo escaneable y un QR de terminal                                                                           |

`pair` también acepta los flags principales `--data-dir`, `--port` y `--bind`:
seleccionan el directorio de datos en el que escribir y determinan la forma de la
URL de servidor que se imprime (`ws` en loopback, `wss` con `--bind any`). Volver
a ejecutar `pair` para el mismo `--device` rota su clave y corta las sesiones
activas de ese dispositivo. Una credencial generada aquí **no caduca**, a
diferencia de los 30 días que fija un emparejamiento hecho desde la aplicación.

:::caution[El QR de `--client-url` no es el QR del teléfono]
`pair --client-url` rellena el formulario de conexión del cliente **web** (URL del
servidor, id de dispositivo y clave en el fragmento de la URL). El teléfono se
empareja con una carga útil distinta, generada desde el panel de emparejamiento
de la aplicación — el descriptor de conexión completo del servidor más una
caducidad. Las dos no son intercambiables — consulta [Emparejar un dispositivo](/es-ES/manual/guias/emparejar-dispositivo/).
:::

### `connect`

Lee y escribe los mismos ajustes que la tarjeta **Control Center Connect** de
**Ajustes → Servidor → Inicio de sesión único**, desde el directorio de datos.
Un servidor en marcha recoge un cambio en un plazo de 10 minutos o al
reiniciarse.

| Comando                         | Qué hace                                                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `cc_server connect status`      | Muestra el modo, la URL, si `CC_CONNECT_URL` lo bloquea, el id de instalación, el estado y el origen de cada carril (`own`, `connect` u `off`) |
| `cc_server connect enable`      | Usa el Connect alojado de Control Center                                                                         |
| `cc_server connect enable --url <url>` | Usa un Connect propio en esa URL (HTTPS, o `http` en loopback)                                            |
| `cc_server connect disable`     | Deja de usar Connect. Solo las apps propias del servidor inician la sesión de las personas                       |

`status` sin comando es el valor predeterminado. Cada comando acepta
`--data-dir`. `CC_CONNECT_URL` prevalece sobre lo que guarden estos comandos. Un
comando desconocido termina con `64`. Consulta
[Control Center Connect](/es-ES/manual/referencia/connect/) para ver los modos,
la identidad de instalación y los códigos de estado.

### `update`

`--apply` sustituye la instalación; se rechaza mientras un servidor siga
respondiendo en el puerto configurado, salvo que pases `--force`.
`--allow-downgrade` permite una versión anterior.

El comando se niega directamente, con una explicación en lugar de un error, ante
instalaciones que no le pertenecen:

| Entorno                       | Cómo se detecta                             | Qué dice                                                     |
| ----------------------------- | ------------------------------------------- | ------------------------------------------------------------ |
| El servidor integrado del escritorio | `CC_EMBEDDED=1` o `CC_BOOTSTRAP_DEVICE_ID` | Actualiza la aplicación en su lugar — el instalador sustituye todo el árbol |
| Un checkout del código fuente con `dart run` | la ruta del script termina en `.dart` | Actualízalo con git                                          |
| Docker                        | marcadores de contenedor                    | Descarga una imagen más reciente                             |

## Ciclo de vida del proceso

`cc_server` se ejecuta hasta recibir `SIGINT` / `SIGTERM`. Lo controla una
variable de entorno adicional, y la define el escritorio, no tú:

| Variable                 | Efecto                                                                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `CC_EXIT_WITH_PARENT=1`  | El servidor termina cuando lo hace su proceso padre, algo que se detecta porque el padre cierra el extremo de escritura de su tubería de stdin. El escritorio la define para que una aplicación que se cae nunca deje huérfano un servidor que retiene el directorio de datos |

Defínela tú mismo solo si supervisas `cc_server` como proceso hijo y quieres esa
misma garantía.

`DO_NOT_TRACK=1` (cualquier valor salvo vacío, `0` o `false`) detiene las
[analíticas de uso](/es-ES/manual/referencia/analiticas-de-uso/) propias del servidor aunque el interruptor
de todo el servidor esté activado. Los clientes siguen haciendo caso al interruptor.

## Estructura del directorio de datos

El directorio de datos predeterminado es `~/Library/Application Support/control-center`
en macOS, `%APPDATA%\control-center` en Windows y `$XDG_DATA_HOME/control-center`
(o, si no, `~/.local/share/control-center`) en el resto de sistemas. Solo se usa un
`.cc_server` relativo al directorio de trabajo actual cuando no se resuelve ningún
directorio home ni de datos de aplicación.

El servidor mantiene el directorio de datos privado para su propia cuenta (`0700`). No arranca (código de salida `78`) si no puede hacerlo, si `global.db` está dañado o lo escribió una versión más reciente, o si no se puede leer su archivo de identidad.

| Ruta                              | Contenido                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------- |
| `global.db`                       | El registro de espacios de trabajo, los usuarios, los dispositivos emparejados, las noticias y la cola de la flota |
| `<workspaceId>/workspace.db`      | Una base de datos por espacio de trabajo — agentes, espacios, tickets, memoria |
| `<workspaceId>/code_index.db` | El grafo de código de ese espacio de trabajo. Se reconstruye cuando falta, nunca se incluye en la copia de seguridad |
| `pre_upgrade/`, `<workspaceId>/pre_upgrade/` | Las dos copias más recientes de una base de datos de antes de que una actualización cambiara su formato |
| `<workspaceId>/chat_credentials/` | Tokens de bots de chat, en JSON simple, para que viajen con el espacio de trabajo |
| `secrets.json`                    | Claves de emparejamiento, la clave de instalación de Connect, las apps de proveedor, los inicios de sesión de las personas (sellados cuando se hacen a través de Connect), secretos de webhook, SSO (`0600`) |
| `backups/<timestamp>/`            | Una instantánea por instalación — `manifest.json`, `global.db` y una copia de cada espacio de trabajo |
| `backups/exports/`                | Exportaciones de un solo espacio de trabajo, `<workspaceId>-<timestamp>.db`    |
| `backups/transfer/`               | Zona de preparación para descargas y subidas de copias de seguridad; la limpia la ruta que escribe en ella |
| `models/`                         | Modelos de embeddings, diarización y voz en el propio dispositivo               |
| `codemode/` | Una copia de desarrollo del ejecutor del modo código, instalada por `scripts/natives/build_codemode.sh`; las distribuciones de versión la incluyen en `bin/codemode/` |
| `meetings/<meetingId>/`           | Audio de reuniones conservado                                                   |
| `rigs/images/`                    | Imágenes de disco de rigs importadas (la superficie de escritorio QEMU)         |
| `rigs/smolvm/<rigId>/`            | Estado de ejecución del microVM de cada rig (el secreto del broker, `0600`)      |
| `rigs/smolvm-packs/`              | Paquetes de máquina preextraídos — la caché que hace rápidos los arranques repetidos de un rig |
| `rigs/tls/`                       | La autoridad de certificación del dominio de desarrollo para HTTPS de los rigs (claves `0600`) |
| `rigs/run/<rigId>/`               | Superposiciones de QEMU, imágenes semilla y claves por VM (`0600`)               |
