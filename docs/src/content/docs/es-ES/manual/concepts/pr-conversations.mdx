Una pull request ya es el lugar donde ocurre la conversación sobre el código.
Las conversaciones de PR la convierten en una superficie de un espacio de
trabajo de Control Center, igual que un
[puente de chat](/es-ES/manual/conceptos/puentes-de-chat/) convierte Slack en
una: menciona a `@usectrl`
en una PR, responde dentro de sus hilos de revisión o añade la etiqueta
`ai-review`, y el trabajo ocurre en el espacio de revisión de la PR — bajo la
misma atribución y las mismas barandillas que cualquier cosa escrita en la
aplicación. Un comentario y una etiqueta se controlan de la misma forma: por el
miembro que lo escribió o la añadió. Las respuestas vuelven a GitHub, en el
mismo hilo en el que se hizo la pregunta.

Tres decisiones dan forma a la función, y cada una es la misma que tomó el
puente de chat para el chat, reformulada para un host de código: **en qué
dirección va la conexión**, **qué autoriza un comentario que llega de fuera** y
**a quién se atribuye cada lado**.

## El sondeo es el transporte

El único canal de envío que GitHub ofrece a una app es un webhook, y un webhook
necesita una URL de entrada — justo lo único que esta superficie nunca exige de
forma deliberada. Así que el descubrimiento es un barrido: una búsqueda con
alias por cada instalación de la app pide a GitHub las PR que mencionan `@usectrl` y las PR abiertas que llevan la etiqueta de revisión; a las PR
que ya tienen un espacio de revisión se les leen sus hilos de comentarios, y
todo se compara por id de comentario con lo visto en el barrido anterior. Una
app propia barre cada minuto como máximo 25 PR. A través de Connect, las
llamadas consumen la cuota de GitHub de los propios miembros, así que el barrido
se ejecuta cada dos minutos sobre 10 PR como máximo, y un espacio de trabajo por
debajo del 15 % de su cuota se omite hasta que se recupera. Connect en sí nunca
ve el contenido de las PR.

Merece la pena nombrar las consecuencias de este diseño:

- **La latencia es un intervalo de barrido, no un evento.** El acuse de recibo
  👀 llega en un barrido. Nada urgente depende de él.
- **Exactamente una vez, por comentario.** Los id de comentario son únicos en
  todo GitHub; cada uno se registra en el momento en que se clasifica como
  apto, antes de que nada actúe sobre él. Un fallo puede perder el procesamiento
  de un comentario, pero nunca dispararlo dos veces.
- **El tiempo sin conexión se recupera, no se reproduce.** El conjunto de lo
  visto se persiste, así que un reinicio entrega lo que llegó mientras estaba
  caído. La única excepción es el primer barrido de todos: al no haber memoria
  con la que comparar, todo lo pendiente se registra en silencio — un operador
  que etiquetó veinte PR antes de que existiera este servidor no debe volver y
  encontrarse con veinte revisiones en marcha.
- **La etiqueta es un conjunto, no un evento.** La búsqueda informa de la
  _presencia_ de la etiqueta, así que una PR etiquetada se dispara una sola vez,
  y nunca más. Volver a añadir una etiqueta tras quitarla es invisible para el
  barrido; una mención es la vía para volver a ejecutarlo.

La búsqueda se ejecuta una vez por cada cuenta de instalación, con el cliente
propio de ese propietario, porque un token solo ve los repos de su propia
instalación — una única credencial para todo el servidor pasaría por alto en
silencio todas las PR de las demás instalaciones de la app.

## La pertenencia autoriza, no el comentario

Un comentario de PR llega con un autor — una identidad externa sin autenticar
hasta que se demuestre lo contrario. El servidor resuelve el id numérico e
inmutable de la cuenta de GitHub del autor (nunca el login, que se puede
cambiar y reutilizar) contra los inicios de sesión de GitHub de los miembros
del espacio de trabajo, que se reconstruyen según un TTL porque la gente inicia
sesión y recibe invitaciones mientras el servidor está en marcha. En el caso de
la etiqueta `ai-review`, la persona resuelta es quien la añadió por última vez.

Tres comprobaciones, en orden, y no superar cualquiera de ellas es silencioso —
no se publica nada:

- **Un miembro con sesión iniciada.** La cuenta tiene que pertenecer a un
  miembro de _este_ espacio de trabajo que haya iniciado sesión en GitHub en
  este servidor
- **Un rol con escritura.** `viewer` y `guest` no pueden iniciar trabajo
- **Acceso de push.** Las respuestas usan un token para ese único repositorio, limitado al acceso de ese miembro a él. Si el servidor no puede emitir uno, no continúa

Todas las comprobaciones se ejecutan antes de cualquier acuse de recibo, así que
un desconocido no recibe ni reacción ni respuesta. Un comentario nunca se
atribuye a alguien que no lo escribió, y las palabras de un desconocido nunca
entran en un espacio de trabajo que no pueden ver.

### La reclamación

El último paso antes de cualquier trabajo es una reacción 👀, añadida con el
propio inicio de sesión de GitHub del autor. GitHub responde `201` a una
reacción nueva y `200` a una que ya existe, así que la reacción funciona también
como cerrojo: cuando la misma persona tiene sesión iniciada en dos servidores
que vinculan el repositorio, solo el primero en reaccionar hace el trabajo. Un
comentario que ven varios espacios de trabajo de un mismo servidor se ofrece a
cada uno, y decide la misma reclamación.

## Dos identidades, a propósito

Cada lado de la conversación lleva una identidad distinta, y esa diferencia es
la función:

- **En GitHub, la respuesta es automatización en tu nombre.** Cada respuesta
  usa un token para ese único repositorio, limitado al acceso del miembro que
  pregunta, y la firma la cuenta `[bot]` de la app. Una excepción: en la app
  compartida de Control Center Connect, el bot publica en los hilos de revisión
  solo cuando el operador de Connect ha incluido la instalación; si no, una
  respuesta dentro de un hilo de revisión la firma la cuenta propia del miembro
  que pregunta. En cualquier caso, cada respuesta
  empieza por `**Control Center** (for @login):`, que dice quién preguntó y sirve
  también de protección contra bucles. Las menciones @ en las palabras del agente
  quedan inertes, así que una respuesta nunca notifica a un usuario ni a un
  equipo.
- **En el espacio, la pregunta es tuya.** El mensaje se atribuye al miembro al
  que se resolvió el autor, y la ejecución del agente corre en su nombre: sus
  commits son suyos, y el dial de autonomía del espacio y las
  barandillas de acciones se aplican exactamente igual que a un mensaje escrito
  en la aplicación. Las escrituras en el host de código que hace la ejecución
  usan tokens de un solo repositorio acotados por ese miembro, nunca su inicio
  de sesión entregado por completo.

Publicar los hallazgos de la revisión de vuelta en GitHub sigue siendo una
decisión de una persona, tomada en Control Center. Una mención puede _iniciar_
una revisión; solo un humano publica una.

## La protección contra bucles

Todo lo que firma una cuenta de bot se descarta antes de que se ejecute
cualquier filtro — el nuestro en concreto, y cualquier sufijo `[bot]`, para que
el bot de revisión de otra app tampoco pueda despertar al nuestro —, y lo mismo
ocurre con cualquier comentario que empiece por el prefijo
`**Control Center** (for @`, ya que una respuesta en un hilo de revisión a través
de Connect puede firmarla la cuenta de una persona. Sin esto, las respuestas llegarían como comentarios
nuevos y volverían a disparar el puente indefinidamente.

Solo `@usectrl` inicia trabajo. El propio login de la App (`<slug>[bot]`) y su slug sin sufijo no dirigen nada: GitHub no ofrece autocompletado para una cuenta de app, y un slug sin sufijo puede pertenecer a un usuario humano.

## Lo que deliberadamente no se ofrece

- **Sin publicación automática.** Los hallazgos llegan al espacio de revisión;
  publicarlos en GitHub es una acción humana aparte
- **Sin identidad difusa.** El autor se resuelve a exactamente un miembro o se
  ignora — no hay atribución por aproximación
- **Sin aprobación automatizada.** La automatización puede comentar y pedir
  cambios, pero una revisión `APPROVE` se rechaza antes de enviarse. Aprobar es
  un acto de una persona
- **Sin webhook de la GitHub App.** Esta superficie nunca registra uno, así que
  no hay URL de entrada que exponer para los comentarios de PR. Los demás
  webhooks del producto (pipelines, sincronización de tickets) son una
  configuración aparte y opcional.
