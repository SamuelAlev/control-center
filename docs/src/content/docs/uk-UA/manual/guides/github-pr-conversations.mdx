Цей посібник показує, як працювати з Control Center, не виходячи з GitHub:
попросіть ШІ-рев’ю зі сторінки PR, поставте ботові запитання в коментарі та
продовжте розмову в гілках його рев’ю.

Відповіді надходять через канал GitHub робочого простору: власний
[GitHub App](/uk-UA/керівництво/практичні-посібники/github-app/) вашого сервера або
спільний App від Control Center через Connect. Нічого нового не реєструється, і
ніщо не має бути доступним з інтернету: сервер
дізнається про сказане на GitHub через опитування, тож ноутбук за NAT поводиться
точно як публічне розгортання.

## Передумови

- Робочий простір має канал GitHub: власний GitHub App сервера або Connect,
  причому застосунок [установлено](/uk-UA/керівництво/практичні-посібники/github-app/#установіть-його-там-де-ваші-репозиторії)
  на обліковому записі, якому належить репозиторій. Власному застосунку потрібні
  **Pull requests** та **Issues** на читання й запис — **Створити мій застосунок
  GitHub** уже їх надає
- Репозиторій пов’язано з робочим простором у Control Center
- Ви [увійшли в GitHub](/uk-UA/керівництво/практичні-посібники/інтеграція-github/) на цьому
  сервері й можете робити push у репозиторій
- Жодної URL webhook, жодного тунелю, жодного зворотного виклику — на боці
  мережі налаштовувати нічого

## Знайдіть ім’я бота

Згадайте `@usectrl` — окремий обліковий запис Control Center на GitHub. Це єдиний спосіб виклику: згадка власного логіна застосунку нічого не робить. Канал GitHub вашого робочого простору і далі обробляє запит та публікує відповіді. Облікові дані запису `usectrl` вам не потрібні.

## Запросіть рев’ю з GitHub

Два способи, і обидва запускають той самий вбудований конвеєр `pr_review`, який
запускає кнопка **Запитати AI**:

- **Додайте мітку `ai-review`** до PR. Це найближче до призначення бота
  рецензентом, що GitHub узагалі пропонує — облікові записи застосунків не
  можуть займати рідне місце запитаного рецензента. Ваш обліковий запис ставить
  на PR реакцію 👀, і рев’ю починається в Control Center; коментар не
  публікується
- **Напишіть коментар `@usectrl review`** (або просто `@usectrl`) у розмові PR.
  На вашому коментарі з’являється 👀, а потім відповідь повідомляє, що рев’ю
  почалося (або що воно вже виконується)

Рецензенти працюють у просторі рев’ю цього PR; читайте та публікуйте знахідки,
як описано в [Використовувати ШІ-перевірку](/uk-UA/керівництво/практичні-посібники/ші-перевірка/). Публікація назад на GitHub
залишається рішенням, яке ви ухвалюєте в Control Center — запуск рев’ю з GitHub
сам собою нічого на GitHub не публікує.

Мітка спрацьовує один раз на PR: її додавання і є запитом, і вона не зводиться
знову, коли її зняти й додати повторно. Щоб запустити рев’ю ще раз — скажімо,
після push — згадайте бота.

## Поставте запитання

Напишіть коментар у розмові PR:

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

Що відбувається, по порядку:

1. На вашому коментарі з’являється 👀 від вашого власного облікового запису,
   щоб ви знали, що коментар побачили
2. Запитання публікується в просторі рев’ю цього PR **від вашого імені** — з
   тією самою атрибуцією, якби ви набрали його в Control Center
3. Агент відповідає в просторі, і відповідь публікується назад у PR. Кожна
   відповідь починається з `**Control Center** (for @your-login):`

Запитання в PR, де рев’ю ще не було, пробуджує CEO-агента робочого простору;
після того як рев’ю вже виконувалося, відповідає агент, який говорив останнім,
тож подальші запитання потрапляють до того, у кого є контекст.

## Продовжте в гілці рев’ю

Дайте відповідь у вбудованій гілці рев’ю, учасником якої є бот — у його
коментарі до diff або у відповіді, яку він опублікував у цій гілці. Згадка не
потрібна; сама гілка **і є** адресацією:

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

Багатоходовість працює так само: кожна відповідь — це ще одне запитання в тій
самій розмові, з простором рев’ю як контекстом, і відповідь повертається в
гілку.

Подальше запитання в хронології розмови PR — це новий коментар верхнього рівня,
тож йому все ще потрібна @-згадка.

## З ким говорить бот

Перш ніж щось робити, сервер зіставляє автора коментаря або того, хто додав
мітку `ai-review`:

- **У цей обліковий запис GitHub має бути виконано вхід** на цьому сервері.
  Зіставлення йде за числовим id облікового запису GitHub, а не за логіном.
  Увійдіть у **Налаштування →
  Ви → Профіль → Хостинг коду**
- **Людина має бути учасником із роллю на запис** (`member`, `admin` або
  `owner`) у робочому просторі, який пов’язує репозиторій
- **Людина має мати право push** у репозиторій на GitHub. Відповіді
  використовують токен, обмежений доступом цієї людини, тож той, хто може лише
  читати, відповіді не отримує

Усіх інших мовчки ігнорують: нічого не публікується, і їхні слова ніколи не
потрапляють у робочий простір. Коментарі ботів і власні відповіді Control Center
ніколи не вважаються запитаннями.

### Два сервери, один PR

👀 — це ще й спосіб, у який сервери домовляються, хто відповідає. Реакцію
ставить власний вхід автора, і GitHub повідомляє серверу, чи вона нова. Якщо ви
ввійшли на двох серверах Control Center, які обидва пов’язали репозиторій,
відповідає той, хто відреагував першим, а інший мовчить. Те саме стосується й
мітки.

## Чого очікувати

| Що                   | Поведінка                                                                  |
| -------------------- | -------------------------------------------------------------------------- |
| Підтвердження        | 👀 від вашого облікового запису на коментарі (або на PR, для мітки) протягом одного проходу |
| Відповіді            | Публікуються в тій самій розмові, де поставили запитання, і починаються з `**Control Center** (for @your-login):`. Автор — бот застосунку. У спільному застосунку Connect відповідь у гілці рев’ю авторизує ваш обліковий запис, якщо оператор Connect не додав цю інсталяцію до списку |
| Атрибуція в просторі | Запитання належить вам; агент працює від вашого імені, за налаштуваннями автономності простору |
| Рев’ю                | Знахідки потрапляють у простір рев’ю; публікація на GitHub — вручну        |

На власному застосунку прохід виконується щохвилини й перевіряє до 25 pull
request; через Connect — раз на дві хвилини й до 10, бо ці виклики витрачають
власну квоту GitHub кожного учасника. Робочий простір, у якого лишилося менше
15 % квоти GitHub, пропускається, доки вона не відновиться. Затримка — це ціна
за те, що вхідний доступ до мережі не потрібен узагалі. Ніщо не губиться, поки
сервер офлайн — коментар, що надійшов під час простою, буде підхоплено на
наступному проході.

## Усунення несправностей

**На коментар, який згадує бота, нічого не відбувається.**

- Чи **встановлено** застосунок на обліковому записі, якому належить репозиторій,
  і чи **пов’язано** репозиторій із робочим простором? Непов’язаний репозиторій
  пропускають, перш ніж щось записати, тож якщо пов’язати його пізніше, доставка
  все одно відбудеться
- Чи ви ввійшли в GitHub на цьому сервері, чи ви учасник із роллю на запис і чи
  можете робити push у репозиторій? Усіх інших сервер ігнорує без відповіді
- Усе ще нічого? Коли щось не вдається, журнал сервера називає прохід і PR;
  шукайте `pr_conversation:` (опитувач) і `github_pr_conversation:` (міст)

**Мітка не запускає рев’ю.**

Вона спрацьовує один раз на PR, і той, хто її додав, проходить ті самі
перевірки, що й автор коментаря. Якщо рев’ю вже виконувалося або мітку додали
ще до того, як сервер уперше побачив PR (перший прохід тихо фіксує накопичене,
а не штурмує його), натомість згадайте бота — `@usectrl review` завжди запускає
рев’ю, якщо воно вже не виконується.

**Відповідь бота не з’явилася на GitHub.**

Сама відповідь ніколи не губиться — вона в просторі рев’ю цього PR у Control
Center. Невдалу публікацію (GitHub недоступний, змінилися дозволи) записують у
журнал, і відповідь не повторюють; якщо це важливо, запитайте ще раз у гілці.
