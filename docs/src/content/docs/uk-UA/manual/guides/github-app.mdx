Цей посібник показує, як дати вашому серверу власний GitHub App. Це займає
близько двох хвилин, робити це має лише власник сервера, і потрібно це один раз
на сервер.

:::note[Можливо, він вам не потрібен]
Коли ввімкнено Control Center Connect, люди входять у GitHub через спільний App
від Control Center або через App, який використовує Connect вашої організації.
Реєструйте власний застосунок, якщо ви вибрали **Використовувати власні
застосунки**: застосунок сервера використовується лише тоді. Див. [Control Center Connect](/uk-UA/керівництво/довідка/connect/).
:::

Щоб після цього ввійти у власний обліковий запис, див.
[Налаштувати інтеграцію GitHub](/uk-UA/керівництво/практичні-посібники/інтеграція-github/).

## Що робить застосунок

Одна реєстрація відповідає на два різні завдання:

| Завдання              | Що на нього відповідає                         | Чому це важливо                                                                          |
| --------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **Людина входить**    | ID клієнта й секрет клієнта застосунку         | Кожен має власні облікові дані GitHub — на сервері й на кожному пристрої                |
| **Сервер діє**        | ID застосунку й приватний ключ                 | Агенти, конвеєри, опитувачі й відповіді бота отримують токени для одного репозиторію за раз |

Друге завдання ніколи не позичає облікові дані людини цілком. Кожен токен, який
випускає сервер, охоплює один репозиторій і обмежений тим, що може робити там
відповідальний учасник. Для читання пов’язаного репозиторію достатньо
застосунку; для всього, що записує, потрібен учасник, який може робити push.
Автоматизація ніколи не схвалює pull request.

Власний застосунок сервера застосовується лише за **Використовувати власні застосунки**. З Control Center Connect або власним Connect Connect обслуговує всі канали, включно з GitHub; застосунок сервера лишається збереженим, але невикористаним, доки ви не перемкнетеся назад. Робочий простір на власних застосунках ([Надайте одному робочому простору власний застосунок](#надайте-одному-робочому-простору-власний-застосунок)) використовує власний застосунок незалежно від режиму сервера. Застосунок із незаповненими полями — це помилка, а не перехід на запасний варіант: входи в GitHub відхиляються, доки не задано всі поля.

## Передумови

- Ви — **власник сервера**. Картку **Застосунки провайдера** не бачить ніхто
  інший
- Обліковий запис GitHub. Застосунок створюється під ним
- Адреса сервера, доступна вашому браузеру. Публічний URL сервера (або loopback
  для власного сервера застосунку для комп’ютера) — це те місце, куди GitHub вас
  повертає

## Створіть його одним кліком

1. Перейдіть у **Налаштування → Сервер → Єдиний вхід** і прокрутіть до картки
   **Застосунки провайдера**
2. У блоці **GitHub** за бажання вкажіть у полі **Організація (необов’язково)**
   організацію GitHub, якій має належати застосунок. Залиште поле порожнім, щоб
   створити застосунок під власним обліковим записом; для створення під
   організацією потрібен власник цієї організації
3. Натисніть **Створити мій застосунок GitHub**
4. Браузер відкриє GitHub із уже заповненим застосунком. Натисніть
   **Create GitHub App**
5. GitHub поверне вас на сервер, який збереже id застосунку, приватний ключ, id
   клієнта й секрет клієнта, а потім відкриє сторінку встановлення застосунку

Нічого не копіюється вручну, а код перетворення йде прямо з GitHub на ваш
сервер. Посилання працює один раз і спливає через десять хвилин; якщо воно
сплило, знову натисніть **Створити мій застосунок GitHub**.

Застосунок називається `Control Center <code>` і запитує рівно те, що
використовує Control Center:

| Дозвіл                                     | Доступ             |
| ------------------------------------------ | ------------------ |
| Metadata                                   | Читання            |
| Contents                                   | Читання й запис    |
| Pull requests                              | Читання й запис    |
| Issues                                     | Читання й запис    |
| Checks, Actions, Commit statuses           | Читання            |
| Organization members                       | Читання            |

Вебхуки вимкнено: сервер опитує. Щоб пізніше перенести застосунок, створений під
власним обліковим записом, в організацію, скористайтеся **Transfer ownership** у
розширених налаштуваннях застосунку на GitHub.

Контрольна точка: блок GitHub показує «Сервер може діяти від свого імені, і люди
можуть входити».

## Установіть його там, де ваші репозиторії

Зареєстрований, але не встановлений застосунок може виконувати вхід людей, але
нічого не може читати.

1. На сторінці встановлення, яку відкрив GitHub, виберіть обліковий запис або
   організацію, якій належать ваші репозиторії
2. Виберіть **All repositories** або позначте ті, які має бачити цей сервер

Щоб пізніше встановити його на інший обліковий запис, адміністратор робочого
простору відкриває **Налаштування → Робочий простір → Інтеграції**, знаходить
**Встановлення застосунку GitHub** на картці **Застосунок GitHub** у розділі Хостинг коду і натискає
**Установити застосунок GitHub**. У списку видно всі облікові записи, на яких
установлено застосунок, а призупинену інсталяцію позначено.

## Поділіться інсталяцією організації

Організація встановлює GitHub App один раз. Після цього кожен в організації, хто
входить у GitHub на сервері Control Center, може користуватися інсталяцією, на
будь-якому сервері: вашому, колеги чи власному. Авторизовувати кожен сервер окремо
не потрібно.

Кожен токен, який отримує сервер, належить людині, яка увійшла, обмежений одним
репозиторієм і її роллю в ньому, тож не дає більше, ніж вона може на GitHub.
Журнал аудиту GitHub показує цю людину, яка діє через застосунок.

Щоб зупинити доступ Control Center до організації, власник організації видаляє
інсталяцію або звужує її репозиторії на GitHub. Видалення людини з організації
теж припиняє її доступ.

## Зареєструйте його вручну

Картка **Застосунки провайдера** приймає й значення напряму — для застосунку,
який ви зареєстрували самі:

| Група                          | Поля                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **Роль сервера**               | **ID застосунку** і **Приватний ключ** (увесь `.pem` разом із рядками `BEGIN` і `END`)                 |
| **Вхід користувачів**          | **ID клієнта** і **Секрет клієнта**. **URL зворотного виклику** показує URL для реєстрації дослівно      |
| **Розмови в pull request**     | **Логін бота**, визначається під час перевірки підключення                                             |

Зареєструйте URL зворотного виклику `<server origin>/oauth/github/callback`
точно так, як його показує картка, залиште **Expire user authorization tokens**
увімкненим і надайте дозволи з таблиці вище. Натисніть **Тест**: він запитує в
GitHub, на яких облікових записах установлено застосунок, щоб не плутати
«збережено» і «працює».

## Налаштуйте його з `.env` сервера

Для headless- або скриптового встановлення сервер заповнює кожне поле зі свого
файлу `.env` уперше, коли не має збереженого значення:

```bash
GITHUB_APP_ID=123456
GITHUB_CLIENT_ID=Iv23li0123456789abcd
GITHUB_CLIENT_SECRET=<secret>
GITHUB_APP_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\nMIIEow…\n-----END RSA PRIVATE KEY-----"
```

Записуйте ключ **одним рядком**: значення в `.env` — це один рядок, а `\n`
усередині подвійних лапок декодується в перенесення рядка. Сервер відмовляється
запускатися, якщо `GITHUB_APP_PRIVATE_KEY` або `GITHUB_CLIENT_SECRET`
експортовано в середовище його процесу, де їх міг би прочитати будь-який
дочірній процес; тримайте їх у файлі `.env` (у Docker змонтуйте його в
`/app/bin/.env`). Заповнення відбувається **один раз для кожного поля**, тож
зміна в «Налаштуваннях» не скасовується наступним перезапуском.

## Надайте одному робочому простору власний застосунок

Робочий простір може працювати на власному застосунку замість застосунку сервера:

1. Адміністратор робочого простору відкриває **Налаштування → Робочий простір → Інтеграції**
2. На картці **Control Center Connect** він обирає **Використовувати власні застосунки** і натискає **Застосувати**. Усі в робочому просторі входять знову через застосунки робочого простору
3. Картка **Застосунок GitHub** у розділі Хостинг коду тепер містить поля застосунку: **ID застосунку** і **Приватний ключ** під **Діє від імені цього робочого простору**, **ID клієнта** і **Секрет клієнта** під **Вхід користувачів**. Після заповнення натисніть **Тест**

Учасники входять у цей застосунок для цього робочого простору. Робочий простір на власних застосунках ніколи не переходить на застосунок сервера чи на Connect: доки його поля не заповнено, його робота з GitHub відхиляється. Той самий вибір охоплює Google Calendar, Linear і пошук GIF, кожен з власними полями поруч із провайдером на цій самій сторінці. Див. [Надайте одному робочому простору власний застосунок Linear](/uk-UA/керівництво/практичні-посібники/інтеграція-linear/#надайте-одному-робочому-простору-власний-застосунок-linear) і [Надайте одному робочому простору власний клієнт Google](/uk-UA/керівництво/практичні-посібники/підключити-календар/#надайте-одному-робочому-простору-власний-клієнт-google). Інші вибори на цій картці та те, що кожен з них робить, описано в [Вибір для кожного робочого простору](/uk-UA/керівництво/довідка/connect/#вибір-для-кожного-робочого-простору).

## Усунення несправностей

### «Створити мій застосунок GitHub» повідомляє, що сервер не має адреси

Сервер не має публічного URL, на який міг би повернутися браузер. Задайте
`CC_SERVER_PUBLIC_URL` (або `--public-url`) і спробуйте знову.

### GitHub повідомляє, що посилання сплило

Одноразову сторінку вже використано, або минуло десять хвилин. Почніть знову з
«Налаштувань».

### Тест повідомляє, що облікові дані працюють, але застосунок ніде не встановлено

Реєстрація й встановлення — окремі кроки. Відкрийте сторінку встановлення
застосунку або скористайтеся **Установити застосунок GitHub** у розділі «Робочий
простір → Інтеграції».

### Тест повідомляє, що не вдалося прочитати приватний ключ

Вставте файл `.pem` цілком, разом із рядками `-----BEGIN` і `-----END`. Ключ
`ed25519` або EC використовувати не можна: GitHub Apps підписують за допомогою
RSA.

### Учасник увійшов, але не бачить жодного репозиторію

Застосунок не встановлено на обліковому записі, якому вони належать, або його
інсталяція вибирає інші репозиторії. Вхід дає лише те, що може бачити
застосунок.

### Агенти повідомляють, що інсталяцію GitHub App призупинено

Хтось призупинив інсталяцію на GitHub. Відновіть її в розділі облікового запису
**Settings → Applications → Installed GitHub Apps**.
