Control Center працює з трьома хостами коду, які в застосунку всюди називають **forges**: **GitHub**, **GitLab** і **Bitbucket Cloud**. Жоден із них не типовий. Підключіть один — і все працює; підключіть кілька — і один робочий простір може одночасно містити репозиторії всіх трьох.

Хост коду — це властивість кожного **репозиторію**, яка зчитується з його remote `origin` під час реєстрації. Ви ніколи його не вибираєте, і немає налаштування рівня робочого простору, яке можна було б задати неправильно.

## Підключити хост коду

1. Відкрийте **Налаштування → Ви → Профіль** (`/settings/you/profile`).
2. Знайдіть картку **Хостинг коду**. Тут перелічено кожен підтримуваний хост коду — підключений чи ні.
3. Для **GitHub** натисніть **Увійти в GitHub**. Для **GitLab** або **Bitbucket** натисніть **Додати токен** і вставте токен.

**У GitHub можна лише ввійти.** Вхід проходить через власний GitHub App сервера або через Control Center Connect — залежно від того, що налаштував власник сервера, або через застосунки, які адміністратор робочого простору обрав для нього в **Налаштування → Робочий простір → Інтеграції** (див. [Налаштувати інтеграцію GitHub](/uk-UA/керівництво/практичні-посібники/інтеграція-github/)); вставляти токен GitHub не потрібно. GitLab і Bitbucket і далі приймають особистий токен.

У будь-якому разі облікові дані **ваші й зберігаються на сервері**, з прив’язкою до вашого ідентифікатора користувача: токен не зберігається на машині, у яку ви його ввели, кожен пристрій, з якого ви входите, використовує той самий, і жоден інший учасник не може його прочитати. Він набирає чинності з **наступним запитом** — перезапускати нічого не треба, а від’єднання негайно припиняє його надсилання.

Картка показує, де використовуються ваші облікові записи. Токен GitLab або Bitbucket належить вам у **кожному робочому просторі на сервері**, тож його достатньо вставити один раз. Так само з входом у GitHub, якщо тільки робочий простір не має власних застосунків для входу: тоді цей робочий простір зберігає власний вхід у GitHub, і картка називає його.

Кожен рядок показує стан **вашого** облікового запису. Лише ваші власні облікові дані відповідають за вас; нічого іншого не підміняє їх:

| Рядок показує                                                                 | Значення                                                                                                                                                                                  |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Ви увійшли як octocat`                                                       | Використовуються ваші власні облікові дані                                                      |
| `Не під’єднано`                                                               | У вас немає облікових даних для цього хоста коду                                                                                                                                          |
| `Ваш вхід у GitHub як octocat закінчився. Увійдіть знову.`                    | Ваш вхід закінчився або був відкликаний на хості коду                                                                                                                                     |
| `Призупинено: служба входу цього робочого простору змінилася`                 | Робочий простір перейшов до іншої служби входу. Ваш вхід зберігається і знову працює, якщо робочий простір повернеться назад, тож кнопки входу немає                                    |
| `Зараз не вдається зв’язатися з GitHub. Повторюємо спробу.`                   | Тимчасовий збій. Control Center продовжує спроби; нічого робити не треба                                                                                                                  |
| Речення, що пояснює, чому вхід недоступний                                    | Наприклад `Вхід через GitHub не налаштовано для цього робочого простору.` або `Служба входу цього робочого простору змінила ідентифікацію. Адміністратор має це підтвердити.` Адміністратори отримують кнопку до налаштування, яке це виправляє |

### Який токен потрібен кожному хосту коду

| Хост коду     | Токен                                                                                                        | Де його створити                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| **GitLab**    | Персональний токен доступу з областю дії `api`                                                               | gitlab.com → User settings → Access tokens          |
| **Bitbucket** | Токен Atlassian API і адреса електронної пошти вашого облікового запису                                      | id.atlassian.com → Security → API tokens            |

Bitbucket автентифікується, використовуючи **адресу електронної пошти облікового запису як ім’я користувача**, а токен API — як пароль, тож діалог Bitbucket просить обидва. Токен доступу до репозиторію, проєкту або робочого простору Bitbucket не належить жодній людині, тому цей діалог його відхиляє: натомість його додають як [токен автоматизації](#додати-токен-автоматизації). Те саме стосується **токена доступу проєкту** або **групи** GitLab: GitLab запитує, кому належить токен, перш ніж його зберегти, а токен бота тут відхиляється.

Токен ніколи не прив’язаний до одного робочого простору: у вас один на кожен хост коду, і його використовує кожен робочий простір на сервері. **Відключити** видаляє його для всіх них.

### Фонова робота

Роботі, за якою не стоїть людина (запуски агентів, конвеєри, опитування PR), теж потрібні облікові дані, і кожен хост коду вирішує це по-своєму:

- **GitHub** — токен для одного репозиторію за раз, випущений із GitHub App сервера або через Connect і обмежений тим, що може робити там відповідальний учасник. Це ніколи не вхід людини, переданий цілком, і ні змінна середовища, ні вставлений токен його не замінюють. Див. [Налаштувати інтеграцію GitHub](/uk-UA/керівництво/практичні-посібники/інтеграція-github/#від-чийого-імені-діють-ваші-облікові-дані)
- **GitLab** і **Bitbucket** — лише **токен автоматизації** репозиторію: токен доступу бота, який адміністратор робочого простору додає для цього репозиторію або для кожного репозиторію цього хоста коду в робочому просторі. Власний токен репозиторію має перевагу над токеном робочого простору. Опитування pull requests, коментарі рев’ю ШІ, а також push і merge requests, яких ніхто не просив, використовують саме його, тож на хості коду вони відображаються як цей бот, а не як учасник. Персональний токен жодного учасника їх не замінює, і загального для сервера токена чи змінної середовища немає. Без нього фонова робота для репозиторію призупиняється, а сповіщення про доступ до репозиторію про це каже.

Робота, яку просить учасник (коментар, рев’ю, merge request агента, відкритий для нього), і далі використовує власний токен цього учасника.

## Додати токен автоматизації

Токени автоматизації бачать і змінюють лише адміністратори робочого простору. Кожен токен перевіряється з хостом коду під час збереження: токен, що діє як людина (персональний токен GitLab, токен API Atlassian або будь-який токен Bitbucket, що входить як чийсь обліковий запис), відхиляється, так само як і токен, який не може прочитати репозиторій, для якого призначений.

- **Для одного репозиторію:** відкрийте **Налаштування → Робочий простір → Репозиторії**. Картка **Токени автоматизації** перелічує кожен репозиторій GitLab і Bitbucket разом із ботом, що в ньому діє: **Використовує токен робочого простору** або **Немає токена. Автоматизацію тут призупинено.** Натисніть **Додати токен** у рядку репозиторію.
- **Для кожного репозиторію хоста коду:** відкрийте **Налаштування → Робочий простір → Інтеграції**, знайдіть картку **Токени автоматизації** і натисніть **Додати токен** у рядку GitLab або Bitbucket. Репозиторії, які токен не може прочитати, називаються після збереження і лишаються призупиненими.

Якщо фонова робота вже призупинена, адміністратори також бачать **Додати токен** одразу у сповіщенні про доступ до репозиторію. **Оновити токен** замінює токен; кнопка з кошиком його видаляє, а будь-який репозиторій, що лишився без токена, призупиняється. Якщо хост коду згодом відхиляє збережений токен (відкликаний або прострочений), його рядок про це каже, а репозиторії, які він покривав, призупиняються, доки ви його не замінете.

| Хост коду     | Токен автоматизації                                                                                                                                                       | Де його створити                                                       |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **GitLab**    | **Токен доступу проєкту** або **групи** з `read_api` і `read_repository`; додайте `api` і `write_repository` для коментарів, merge requests і push                         | Проєкт або група → Settings → Access tokens                            |
| **Bitbucket** | **Токен доступу репозиторію**, **проєкту** або **робочого простору** з читанням репозиторію, а також записом pull requests для коментарів і pull requests (запис у репозиторій для push) | Репозиторій, проєкт або робочий простір → Settings → Access tokens     |

GitLab показує роботу як бот-користувача токена; Bitbucket показує її під назвою токена доступу.

### Bitbucket: токен доступу чи токен API

Bitbucket має два типи токенів, і Control Center розділяє їх:

- **Токен API** (id.atlassian.com) належить вашому обліковому запису Atlassian і використовується разом із вашою адресою електронної пошти. Це **ваші** облікові дані, і він іде в розділ **Хостинг коду** у **Налаштування → Ви → Профіль**.
- **Токен доступу** (створюється в налаштуваннях репозиторію, проєкту або робочого простору) належить цьому репозиторію, проєкту чи робочому простору, а не людині. Це **токен автоматизації**, і він іде в розділ **Токени автоматизації**.

Кожен діалог відхиляє інший тип і каже, куди він належить.

## На кожному хості коду ви — інша людина

Та сама людина — це `octocat` на GitHub і зовсім хтось інший на GitLab. Control Center визначає вашу ідентичність **для кожного хоста коду окремо** і використовує потрібну для кожного репозиторію — саме тому в змішаному робочому просторі правильно працюють «потрібен мій перегляд», «створені мною» і «ви це схвалили».

Якщо ідентичність хоста коду не визначено, його репозиторії нічого не додають до вхідних, а не збігаються з усім підряд. Вхідні про це повідомляють, а не стверджують, що ви все переглянули.

## Ви бачите лише те, що видно вашому обліковому запису

Pull requests репозиторію доходять до вас лише тоді, коли ваша роль у робочому просторі дозволяє цей репозиторій **і ваш власний обліковий запис на цьому хості коду може його читати**. Адміністратори робочого простору та власник дотримуються того самого правила. Коли частину репозиторіїв приховано, вхідні та черга PR кажуть, скільки їх і чому, але без назв:

- **Увійдіть у GitHub, щоб бачити pull requests ще з 3 репозиторіїв**: ви ще не підключили цей хост коду тут. Увійдіть, і вони з’являться
- **3 репозиторії приховано, бо ваш обліковий запис GitHub їх не бачить**: попросіть когось із доступом на хості коду
- **3 репозиторії приховано, бо у вас немає доступу до них у цьому робочому просторі**: попросіть адміністратора робочого простору надати доступ
- **Перевіряємо ваш доступ до інших репозиторіїв: 3…**: з’являється на короткий час, поки Control Center підтверджує, що може читати ваш обліковий запис

Код підпорядковується тому самому правилу. Щоб відкрити файли репозиторію, діфи чи пошук у ньому або термінал на ньому, вам потрібне право доступу до нього в цьому робочому просторі, і ваш власний обліковий запис на хості коду має мати змогу його читати; адміністратори робочого простору теж, виняток — лише власник сервера. Коли хост коду не можна перевірити, ви бачите «Не вдалося підтвердити ваш доступ на хостингу коду. Спробуйте ще раз.» (з назвою хоста коду) Див. [Код іде за хостом коду](/uk-UA/керівництво/поняття/авторизація/#код-іде-за-forge).

Той самий принцип поширюється на все, створене з цих pull requests. Простір перегляду, його повідомлення й запуски агентів зникають, поки ви не бачите його pull request, а відкритий простір перегляду закривається, якщо ви втрачаєте доступ. Запуски конвеєрів щодо прихованого pull request зникають зі списку ваших запусків. Агенти, які працюють для вас, також не можуть читати ці простори перегляду. Список репозиторіїв робочого простору показує кожен репозиторій, до якого у вас є доступ у цьому робочому просторі, навіть той, до якого ваш обліковий запис на хості коду ще не може достукатися.

Якщо хост коду обмежує частоту запитів або недоступний, Control Center ще кілька хвилин показує те, що востаннє підтвердив, а потім приховує ці pull requests, доки не зможе перевірити знову.

## Одні вхідні для кожного хоста коду

Вхідні та черга PR розходяться по всіх хостах коду, представлених у робочому просторі, і зливають результати в один потік — pull request із GitHub і pull request із Bitbucket стоять поруч, упорядковані за часом, а не згруповані за постачальником.

Збої ізольовані. Хост коду, який недоступний або обмежений за частотою запитів, не зачіпає решту, а його репозиторії зберігають останній відомий стан, доки він не відновиться; він ніколи не спорожнює всі вхідні. Репозиторій, до якого сервер більше не має доступу, зникає зі списку замість того, щоб показувати застарілі pull requests, а **сповіщення про доступ до репозиторію** називає його разом із виправленням: установіть GitHub App в організації репозиторію, додайте репозиторій до репозиторіїв App, поновіть призупинену інсталяцію або попросіть відповідального учасника знову ввійти, або додайте токен автоматизації для репозиторію GitLab чи Bitbucket. Адміністратори отримують кнопку для кроків з GitHub App і для додавання токена.

## Що вміє кожен хост коду

Кожен хост коду підтримує основний цикл: показувати список і відкривати pull requests, читати диффи, коментувати в рядку й на верхньому рівні, проводити рев’ю, мерджити й закривати. Поза цим вони справді різняться, і Control Center ховає те, чого хост коду не вміє, замість того щоб показувати елемент керування, який мовчки не спрацьовує.

| Можливість                                           | GitHub | GitLab | Bitbucket |
| ---------------------------------------------------- | :----: | :----: | :-------: |
| Пакетні (відкладені) рев’ю                           |   ✓    |   ✓    |     —     |
| Запит змін                                           |   ✓    |   ✓    |     ✓     |
| Синхронізований стан «переглянуто» для кожного файлу |   ✓    |   —    |     —     |
| Реакції емодзі                                       |   ✓    |   ✓    |     —     |
| Рев’юери з команди / групи                           |   ✓    |   ✓    |     —     |
| Запропоновані рев’юери                               |   ✓    |   —    |     ✓     |
| Результати CI у PR                                   |   ✓    |   ✓    |     ✓     |
| Перегляд кроків і логів завдання CI                  |   ✓    |   ✓    |     —     |
| Стекові pull requests                                |   ✓    |   —    |     —     |
| Шаблони опису PR                                     |   ✓    |   ✓    |     —     |
| Опитування сповіщень                                 |   ✓    |   —    |     —     |
| Докладні профілі користувачів                        |   ✓    |   ✓    |     —     |
| Серверне посилання head для PR                       |   ✓    |   ✓    |     —     |

Там, де можливості бракує, функція чесно деградує:

- **Стан «переглянуто»** й далі працює, але лише на тому пристрої, де ви його позначили.
- **Пакетні рев’ю** в Bitbucket публікуються коментар за коментарем, тож рев’юери бачать, як вони надходять поодинці, а не всі одразу.
- **Відсутність серверного посилання head для PR** у Bitbucket означає, що під час перемикання на pull request його вихідна гілка забирається за назвою, а це перестає працювати, щойно гілку видалять.

## Термінологія

GitLab називає pull request **merge request**. Control Center у власній моделі всюди каже «pull request» і вживає власний термін кожного хоста коду там, де йдеться саме про нього.

## Усунення несправностей

### Список PR порожній і повідомляє, що хост коду не підключено

У вас немає облікових даних для цього хоста коду. Увійдіть у GitHub або вставте токен GitLab чи Bitbucket у **Налаштування → Ви → Профіль → Хостинг коду**. Репозиторії інших хостів коду не зачіпаються.

### Я підключив хост коду, але його репозиторії досі нічого не показують

Перевірте стан рядка, потім сповіщення над списком PR. «Увійдіть у … щоб бачити pull requests з інших репозиторіїв» означає, що ваш власний обліковий запис для них не підключений; «Приховано … репозиторіїв, яких не бачить ваш обліковий запис …» означає, що хост коду не надає вам доступу. Для GitHub сповіщення про доступ до репозиторію скаже, коли GitHub App не встановлено в організації репозиторію або він не охоплює цей репозиторій.

### Фонова робота в репозиторії GitLab або Bitbucket призупинена

У репозиторію немає токена автоматизації, який міг би його прочитати. Адміністратор робочого простору додає такий для репозиторію або для всього робочого простору; див. [Додати токен автоматизації](#додати-токен-автоматизації). Ваш особистий токен не поновлює роботу: фонова робота ніколи не використовує токен учасника.

### Репозиторій не реєструється

Для реєстрації потрібні всі три умови: шлях лежить усередині робочого дерева git, у нього є remote `origin`, і цей remote вказує на github.com, gitlab.com або bitbucket.org. Цей `origin` також має бути тим репозиторієм, який ви прив’язуєте, а папку поза сховищем власного робочого простору може прив’язати лише власник сервера. Див. [Додати репозиторії до робочого простору](/uk-UA/керівництво/практичні-посібники/додати-репозиторії/).

### Маю право доступу, але репозиторій каже, що мій обліковий запис не може його читати

Ваш власний обліковий запис на хості коду не може читати цей репозиторій, тож його код лишається закритим для вас, що б не дозволяв робочий простір. Увійдіть у хост коду в розділі **Хостинг коду** вище або отримайте доступ до репозиторію на самому хості коду.

### «Не вдалося підтвердити ваш доступ на хостингу коду»

Хост коду не вдалося перевірити, тож Control Center відмовив, а не вгадував. Спробуйте ще раз за мить.

### Репозиторій каже, що тепер вказує на інший репозиторій

Репозиторій за цим шляхом змінився: його видалили й створили знову або перенесли й замінили. Control Center нічого йому не надсилає, доки адміністратор робочого простору не натисне **Перепідключити** у сповіщенні або в рядку репозиторію. Просте перейменування чи передача відстежуються самі й ніколи цього не показують.

### Після інтенсивного використання все на якийсь час перестає працювати

Це запобіжник на випадок обмеження частоти запитів. Коли хост коду повідомляє про досягнення основного ліміту, клієнт починає локально відхиляти подальші запити, без мережевого звернення, доки не спливе вікно, — тож шквал повторних спроб не може поглибити ліміт. Тимчасові збої повторюються з експоненційною затримкою.
