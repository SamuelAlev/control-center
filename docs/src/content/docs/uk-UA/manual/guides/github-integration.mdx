Цей посібник охоплює частини налаштування, специфічні для GitHub. GitHub — один
із трьох підтримуваних хостингів коду; див.
[Підключити хост коду](/uk-UA/керівництво/практичні-посібники/підключити-хост-коду/)
про підключення GitLab чи Bitbucket і про те, як робочий простір поєднує їх.

## Передумови

- Обліковий запис GitHub із доступом до репозиторіїв, з якими хочете працювати
- Сервер, який уміє виконувати вхід людей у GitHub: або власний GitHub App (див.
  [Створити GitHub App](/uk-UA/керівництво/практичні-посібники/github-app/)), або Control Center
  Connect — вибір робить власник сервера в **Налаштування → Сервер → Єдиний вхід**

:::note[Облікові дані живуть на сервері й прив’язані до вас]
Нічого не зберігається на машині, з якої ви друкуєте. Ваш вхід у GitHub тримає
`cc_server`, з прив’язкою до вашого ідентифікатора користувача, і кожен пристрій,
з якого ви входите, користується ним — комп’ютер, веб і телефон. Інший учасник
того самого сервера не може ним скористатися, а вхід для них — це те, що вони
роблять самі.
:::

## Увійти в GitHub

GitHub працює лише через вхід: токена для вставлення немає.

1. Перейдіть у **Налаштування → Ви → Профіль → Хостинг коду** (або
   перший крок початкового налаштування)
2. У рядку **GitHub** натисніть **Увійти в GitHub**
3. Браузер відкриє GitHub. Підтвердьте застосунок

Як завершиться вхід, залежить від того, хто його виконує:

- **Власний застосунок сервера:** GitHub повертає браузер на сервер, і діалог
  сам це помічає. Вводити нічого не треба
- **Control Center Connect:** сторінка в браузері показує 8-символьний код.
  Введіть його в діалозі або дозвольте браузеру відкрити Control Center за
  посиланням `control-center://`, і вводити код не доведеться

Контрольна точка: рядок **GitHub** показує «Ви увійшли як _your-username_».

Діалог відхиляє код або посилання, які він не запускав сам, з повідомленням
**Вхід розпочато не тут**. Якщо хтось надсилає вам посилання для входу, не
продовжуйте: завершивши його, ви підключили б свій обліковий запис до сервера
цієї людини.

Натисніть **Від’єднатися**, щоб прибрати свій вхід. Вихід із GitHub або
вилучення з робочого простору також відкидає всі токени, які сервер випустив від
вашого імені.

## Від чийого імені діють ваші облікові дані

Control Center дотримується поділу GitHub між діями **від імені людини** і діями **від імені застосунку**:

| Що відбувається | Як це видно на GitHub |
| --- | --- |
| Усе, що робите ви самі: коментар, рев’ю, схвалення, злиття, запит рев’юерів | **Ви**. GitHub позначає коментар у розмові як зроблений застосунком Control Center; рев’ю та його рядкові коментарі такої позначки не мають |
| Рев’ю ШІ, відповіді й коментарі агентів у розмовах PR, мітки, робота конвеєрів і бота | **Бот Control Center**. У спільному застосунку Connect рев’ю є ботовим лише для інсталяції, яку оператор Connect додав до списку; інакше воно показується як відповідальна людина |
| Pull request, який агент відкриває для вас, його редагування назви або опису цього pull request, його push і його коміти | **Ви**. Control Center зазначається як співавтор, коли зазначення співавтора увімкнено |
| Робота, якої ніхто не замовляв (розклади, webhook) | **Бот Control Center**, так само як автор його комітів. На Control Center Connect він ніколи не робить push і не відкриває pull request |

- **Усе, що робите ви**, виконується на **вашому** вході й більше ні на чому. Якщо ви не ввійшли, застосунок просить увійти. Жодні інші облікові дані вас не підміняють
- **Робота бота** отримує токен для одного репозиторію за раз, обмежений тим, що може робити там відповідальний учасник: учасник, який попросив, а інакше власник робочого простору. Учасник, який не може робити push, обмежує бота читанням. Відповіді бота, що діють від чийогось імені, починаються з **Control Center (for @login)**
- **Агенти відкривають pull requests через Control Center**, ніколи з власної пісочниці, тож pull request належить вам, а правила самого GitHub не дають вам його схвалити. Control Center також відхиляє схвалення від людини, яка попросила агента про цю роботу, і від автора pull request. Для запуску за розкладом або webhook це охоплює кожного адміністратора, який увімкнув його тригер або редагував його конвеєр, поки той був увімкнений. Схвалити має хтось інший. Якщо Control Center не може підтвердити, хто відкрив pull request, або який обліковий запис на хості коду ваш, він відмовляє й просить спробувати ще раз
- **Коментарі агентів також проходять через Control Center.** Токен GitHub, який отримує запуск агента, лише читає. Коли агент коментує pull request, над яким працює, Control Center публікує коментар від імені бота, починаючи з **Control Center (for @login)**, якщо хтось попросив запуск. Агент може коментувати лише власний pull request: у тому самому репозиторії, не форк, чий останній коміт агент запушив або є поточним комітом гілки його простору. @-згадки в коментарі агента нікого не сповіщають. Агент також може змінювати назву або опис свого pull request, поки той відкритий. Ця зміна робиться так само, як було відкрито pull request (від вашого імені, якщо ви попросили запуск), і за замовчуванням спершу запитує схвалення. Опис pull request зберігає свої @-згадки, коли агент його відкриває і коли редагує, тож названі в ньому люди отримують сповіщення
- **На Control Center Connect бот ніколи не робить push і не відкриває pull request.** Push, створення гілки або відкриття pull request там потребують людини, яка про це попросила, і виконуються з її входом. Запуск за розкладом або webhook, що намагається зробити push, зупиняється з повідомленням про це. Щоб безнаглядні запуски могли робити push, дайте робочому простору власний GitHub App у **Налаштування**
- **Що може бот Connect.** У спільному застосунку Connect бот коментує, ставить мітки та реагує. Він публікує рев’ю (рев’ю ШІ, коментарі до рев’ю, запити рев’юерів) лише тоді, коли оператор Connect додав інсталяцію цього сервера до списку. Інакше рев’ю йде з власного входу відповідальної людини й з’являється під її іменем. Бот ніколи не відкриває, не змінює, не закриває й не перейменовує pull request, не відхиляє рев’ю і не змінює та не видаляє коментарі; для цього потрібна людина, яка попросила, з власним входом. Connect не прив’язує встановлення вашої організації до одного сервера Control Center: будь-який сервер, де учасник, який може робити push до репозиторію й ввійшов через Connect, може отримати для цього репозиторію токен коментарів бота
- **Сервер або робочий простір із власним застосунком GitHub** зберігає бота для всього вище, зокрема рев’ю
- **Автоматизація ніколи не схвалює** pull request. Схвалення — дія людини

Після прив’язки репозиторію Control Center перевіряє, чи бачить ваш обліковий запис цей репозиторій, і попереджає, коли GitHub App не встановлено на його організації або він не охоплює репозиторій, з посиланням для виправлення. Прив’язувати й відв’язувати репозиторії може адміністратор робочого простору, а checkout поза сховищем робочого простору може прив’язати лише власник сервера; див. [Додати репозиторії до робочого простору](/uk-UA/керівництво/практичні-посібники/додати-репозиторії/).

Прив’язка йде за постійним ідентифікатором репозиторію на GitHub, тож перейменування чи передача нічого від вас не вимагають. Якщо шлях згодом вказує на інший репозиторій, Control Center перестає надсилати йому що-небудь і показує сповіщення, доки адміністратор робочого простору не натисне **Перепідключити**.

Відкриття коду репозиторію (файлів, диффів, пошуку, терміналу) потребує і його гранту в робочому просторі, і вашого входу в GitHub, який може його читати. Адміністратори робочого простору дотримуються того самого правила; звільняється лише власник сервера.

## Що дає інтеграція

| Можливість             | Як                                                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| Список PR і подробиці  | GitHub REST API, із сервера, на вашому власному вході                                                            |
| Запуски перевірок      | GitHub Checks API                                                                                               |
| Публікація рев’ю       | Крок, який запускає користувач і який публікує ваше рев’ю в PR від вашого імені                                  |
| Реєстрація репозиторію | Копію приймають, якщо її remote `origin` указує на github.com — або на gitlab.com / bitbucket.org              |
| Доступ агента до GitHub | Усередині запуску `git fetch` проходить через Control Center, який отримує репозиторії, з якими працює запуск, за токеном лише для читання, якого запуск ніколи не тримає. `gh` читає їх за токеном лише для читання, який Control Center видає на запит і відкликає, коли запуск завершується. Push, pull requests, зміни в них і коментарі проходять через Control Center         |
| Сповіщення             | Серверне опитування вашої скриньки сповіщень GitHub породжує «Згадка в pull request» і «Запит на рев’ю»        |
| Профілі користувачів   | Картки профілю при наведенні та фільтрування PR за автором                                                       |

Деякі шляхи використовують GraphQL API замість REST там, де це дешевше —
активність гілки для вибору гілки під час створення PR і живий стан рев’ю, який
вирішує, чи запит на рев’ю ще чинний.

## Знайте, як агенти діють у GitHub

- Агент, що працює у worktree GitHub, отримує токен для цього одного репозиторію. Він може лише читати код, issues і pull requests; коментарі проходять через Control Center, як описано вище. Push проходить через Control Center, який запитує правило **Надіслати на віддалений репозиторій**, а тоді передає його з токеном запису, якого агент ніколи не має. Див. [Налаштувати політики пісочниці](/uk-UA/керівництво/практичні-посібники/політики-пісочниці/)
- Роботу, яку ви розпочали, коміт пишете від свого імені. Коли ви просите агента про щось або комітите в IDE, ви автор і committer, з адресою, яку підтвердив ваш хостинг коду: вашою адресою noreply GitHub з входу в GitHub або, на GitLab і Bitbucket, електронною поштою, яку повідомляє ваш вхід там. Ідентичність Git робочого простору використовується лише для коміту, який ви зробили вручну в репозиторії, де жоден хостинг коду не підтверджує вашої адреси. Якщо ви не ввійшли в цей хостинг коду, коміти агента натомість належать боту, а нотатки запуску про це повідомляють
- Роботу, про яку ніхто не просив, коміть бот. Запуск за розкладом або webhook комітить від імені GitHub App робочого простору (`<app>[bot]`, з його адресою noreply GitHub) або як `Control Center <hi@usectrl.dev>`, коли немає GitHub App або репозиторій на GitLab чи Bitbucket
- **Зазначати Control Center як співавтора** (**Налаштування** → **Ви** → **Коміти**) додає трейлер `Co-Authored-By:` для іншої сторони: Control Center у ваших комітах, а в комітах бота кожну людину, яка ввімкнула тригер запуску. Увімкнено, доки ви його не вимкнете. Адмін робочого простору може визначити це для всіх за допомогою **Зазначення співавторів** в **Налаштування** → **Робочий простір** → **Загальні**; ваш власний вибір тоді зберігається, але в цьому робочому просторі не застосовується. Власне зазначення авторства Claude Code завжди вимкнено
- Ваші коміти можна підписувати. У розділі **Перевірені коміти** в **Налаштування** → **Ви** → **Коміти** виберіть **Створити ключ підпису** і додайте його публічну частину до свого облікового запису GitHub або GitLab як ключ підпису; відтоді коміти запусків, які ви просите, і коміти, які ви робите в IDE, показуються як перевірені. Приватна частина лишається на вашому сервері, тож хто контролює цей сервер, може підписувати коміти від вашого імені, поки ключ є у вашому обліковому записі; а на GitHub коміт, уже показаний як перевірений, лишається перевіреним після того, як ви видалите ключ. Bitbucket не має ключів лише для підпису: не додавайте ключ туди, і коміти на Bitbucket не підписуються. Коміти бота ніколи не підписуються
- Коміти, які ви робите на панелі **Керування кодом** в IDE, пропускають Git-хуки репозиторію, як це робить `git commit --no-verify`, а Git сервера ігнорує допоміжні програми для облікових даних, редактори, зовнішні інструменти диффів і підписувачі, які налаштовує репозиторій: він запускає Git на власній машині, у дереві, яке може змінити агент або pull request. Див. [Коміт і push із Керування кодом](/uk-UA/керівництво/практичні-посібники/перевірити-й-змерджити-pr/#коміт-і-push-із-керування-кодом)
- Кожен коміт, який агент пушить, спершу перевіряється, зокрема шари, які `stack_publish` пушить для стека. Push, що називає когось іншого, прибирає або позичає зазначення, додає sign-off або не підписаний так, як велять ваші налаштування, відхиляється. Коміти, які ви пушите самі з IDE, належать вам і не перевіряються так
- Термінал, який ви відкриваєте на rig, отримує ваш власний вхід, звужений до
  одного репозиторію, тож push звідти — ваші
- Коли токен не вдається випустити (ніхто відповідальний не ввійшов, застосунок
  не встановлено на власнику або інсталяцію призупинено), команда, яка його запросила,
  пояснює чому. Запасних облікових даних немає

## Усунення несправностей

### Список PR порожній і повідомляє, що GitHub не підключено

Ви не ввійшли в GitHub на цьому сервері. Натисніть **Увійти в GitHub** у
розділі **Налаштування → Ви → Профіль → Хостинг коду**. Репозиторіїв інших хостингів коду це не зачіпає.

### Рядок GitHub повідомляє, що вхід на цьому сервері не налаштовано

Сервер не має ні власного GitHub App, ні Connect. Власник сервера вибирає один
варіант у **Налаштування → Сервер → Єдиний вхід**: **Створити мій застосунок
GitHub** займає близько двох хвилин. Див.
[Створити GitHub App](/uk-UA/керівництво/практичні-посібники/github-app/).

У робочому просторі на власних застосунках рядок повідомляє про це, коли GitHub App робочого простору відсутній або заповнений не повністю. Адміністратор робочого простору заповнює його на картці **Застосунок GitHub** у **Налаштування → Робочий простір → Інтеграції**; див. [Надайте одному робочому простору власний застосунок](/uk-UA/керівництво/практичні-посібники/github-app/#надайте-одному-робочому-простору-власний-застосунок).

### Діалог повідомляє, що код не збігається

Введіть код точно так, як його показує браузер: 8 літер і цифр. П’ять
неправильних кодів завершують вхід; почніть його знову.

### Вхід повідомляє, що застосунок не встановлено

GitHub App не має інсталяції на обліковому записі, якому належить репозиторій.
Адміністратор робочого простору встановлює його в **Налаштування → Робочий
простір → Інтеграції → Встановлення застосунку GitHub**.

### Усім доводиться входити в GitHub знову

Власник сервера змінив ключ Connect сервера, перейшов на інший сервер Connect,
або каталог даних відновили на іншій машині. Входи через Connect прив’язані до
сервера, який їх виконав.

### Додавання репозиторію відхилено

Для реєстрації потрібні всі три умови: шлях лежить усередині робочого дерева git,
у нього є remote `origin`, і цей remote указує на підтримуваний хостинг коду
(github.com, gitlab.com або bitbucket.org). `origin` має бути тим репозиторієм,
який ви прив’язуєте, а папку поза сховищем робочого простору може прив’язати
лише власник сервера. Див.
[Додати репозиторії до робочого простору](/uk-UA/керівництво/практичні-посібники/додати-репозиторії/).

### Маю грант, але репозиторій каже, що мій обліковий запис не може його читати

Ваш обліковий запис GitHub не може читати цей репозиторій, тож його код лишається для вас закритим, навіть із грантом робочого простору. Увійдіть у GitHub у розділі **Хостинг коду** або запитайте доступ до репозиторію на GitHub.

### «Не вдалося підтвердити ваш доступ до GitHub»

Не вдалося звернутися до GitHub, щоб перевірити ваш доступ, тож Control Center відмовив, а не вгадував. Спробуйте ще раз трохи згодом.

### Рев’ю в Connect з’являються під моїм іменем, а не від бота

У спільному застосунку Connect бот публікує рев’ю лише для інсталяцій, які оператор Connect додав до списку. Скрізь інакше рев’ю йде з власного входу відповідальної людини. Щоб бот публікував рев’ю, дайте робочому простору власний GitHub App.

### Після інтенсивного використання все на якийсь час перестає працювати

Це запобіжник на випадок обмеження частоти запитів. GitHub повідомляє про
досягнення основного ліміту відповіддю `403` із заголовком
`x-ratelimit-remaining: 0` і часом скидання; побачивши таку, клієнт локально
відхиляє подальші запити, без мережевого звернення, доки не спливе вікно, — тож
шквал повторних спроб не може поглибити ліміт. Тимчасові збої повторюють до трьох
разів з експоненційною затримкою, поважаючи `retry-after`.
