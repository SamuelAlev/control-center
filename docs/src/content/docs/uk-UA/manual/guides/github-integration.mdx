Цей посібник охоплює частини налаштування, специфічні для GitHub. GitHub — один
із трьох підтримуваних хостингів коду; див.
[Підключити хост коду](/uk-UA/керівництво/практичні-посібники/підключити-хост-коду/)
про підключення GitLab чи Bitbucket і про те, як робочий простір поєднує їх.

## Передумови

- Обліковий запис GitHub із доступом до репозиторіїв, з якими хочете працювати
- Або зареєстрований для вашого сервера GitHub App (див.
  [Створити GitHub App](/uk-UA/керівництво/практичні-посібники/github-app/)), щоб ви могли **увійти**, **або**
  персональний токен доступу з `repo` і `read:org`, який можна вставити

:::note[Облікові дані живуть на сервері й прив’язані до вас]
Нічого не зберігається на машині, з якої ви друкуєте. Ваші облікові дані тримає
`cc_server`, з прив’язкою до вашого ідентифікатора користувача, і кожен пристрій,
з якого ви входите, користується ними — комп’ютер, веб і телефон. Інший учасник
того самого сервера не може їх прочитати, а вхід для них — це те, що вони
роблять самі.
:::

## Увійти через GitHub

**device flow**: GitHub показує вам короткий код, ви підтверджуєте його на
github.com, і сервер отримує облікові дані — без URL зворотного виклику, без
порту, нічого не треба відкривати назовні. Доступний завжди, коли на сервері є ID
клієнта, — офіційна збірка вже його містить.

1. Перейдіть у **Налаштування → Робочий простір → Профіль і ідентичність → Хостинг коду** (або
   перший крок початкового налаштування)
2. У рядку **GitHub** натисніть **Увійти через GitHub**
3. У діалоговому вікні з’явиться код із восьми символів і відкриється
   [github.com/login/device](https://github.com/login/device) у вашому браузері.
   Код уже в буфері обміну
4. Вставте його, підтвердьте застосунок і поверніться. Рядок сам зміниться на
   «Ви увійшли як _your-username_»

Діалогове вікно можна закрити, поки ви завершуєте справу в браузері — сервер
продовжує опитувати, доки код не спливе (приблизно 15 хвилин), тож вхід усе одно
зарахується.

## Або вставте токен

Запасний варіант, коли на сервері немає застосунку, коли застосунок не
встановлено на потрібному вам обліковому записі або коли ви просто волієте
скористатися PAT.

1. Перейдіть у **Налаштування → Робочий простір → Профіль і ідентичність → Хостинг коду**
2. У рядку **GitHub** натисніть **Додати токен**
3. Вставте токен із `repo` і `read:org` (класичний) і збережіть. **Fine-grained**
   токену потрібні для репозиторію **Contents** і **Pull requests** (читання й
   запис), а також **Checks** і **Actions** (читання).

Токен перевіряють одразу під час збереження, тож рядок може назвати обліковий
запис, якому він належить. Натисніть **Від’єднатися**, щоб його прибрати.

Контрольна точка: рядок **GitHub** показує «Ви увійшли як _your-username_». Коли
відповідають не ваші облікові дані, суфікс називає джерело — «через застосунок
цього сервера» або «із середовища».

:::note[Порядок пріоритету фіксований]
Запит, зроблений від вашого імені, використовує **ваші** облікові дані й більше
нічого — середовище — це облікові дані сервера, а не ваші, тож воно ніколи не
підміняє вас. Робота, за якою не стоїть людина (вебхуки, опитування PR,
синхронізація тікетів), використовує ідентичність застосунку сервера, потім
облікові дані власника сервера, а потім середовище.
:::

## Що дає інтеграція

| Можливість             | Як                                                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| Список PR і подробиці  | GitHub REST API, із сервера, від ідентичності застосунку або ваших власних облікових даних                      |
| Запуски перевірок      | GitHub Checks API                                                                                               |
| Публікація рев’ю       | Крок, який запускає користувач і який публікує ваше рев’ю в PR                                                   |
| Реєстрація репозиторію | Копію приймають, якщо її remote `origin` указує на github.com — або на gitlab.com / bitbucket.org              |
| Доступ агента до GitHub | Брокер облікових даних впорскує токен як `GH_TOKEN` / `GITHUB_TOKEN`, з урахуванням можливостей агента         |
| Сповіщення             | Серверне опитування вашої скриньки сповіщень GitHub породжує «Згадка в pull request» і «Запит на рев’ю»        |
| Профілі користувачів   | Картки профілю при наведенні та фільтрування PR за автором                                                       |

Деякі шляхи використовують GraphQL API замість REST там, де це дешевше —
активність гілки для вибору гілки під час створення PR і живий стан рев’ю, який
вирішує, чи запит на рев’ю ще чинний.

## Стежте за збоями GitHub

У рядку заголовка з’являється індикатор стану, коли в провайдера проблеми, — це
стосується GitHub, Claude, OpenAI і Kimi. **Поки все гаразд, він прихований** —
присутність повідомляє про проблему, а не про її відсутність.

Натисніть індикатор, щоб відкрити висувну панель зі станом кожного провайдера та
кнопкою оновлення. Статуси оновлюються самі кожні дві хвилини.

## Знайте, як агенти діють у GitHub

- Агент отримує токен GitHub, лише якщо в нього ввімкнено **Дозволити виклики GitHub API** або
  **Дозволити git push**. Див.
  [Налаштувати політики пісочниці](/uk-UA/керівництво/практичні-посібники/політики-пісочниці/)
- Коміти, які створює агент, автором мають **самого агента** — ім’я для
  відображення плюс ` (agent)`, за синтетичною адресою, прив’язаною до
  ідентифікатора агента — і ніколи людину. Людину, яка зробила запит, зазначають
  трейлером `Co-Authored-By`
- Коли налаштовано GitHub App, брокер для кожного запуску карбує fine-grained
  токени інсталяції з обмеженням на репозиторій і строком близько однієї години,
  замість того щоб віддавати широкий токен. Інсталяцію визначають за
  **власником** репозиторію запуску, тож один застосунок, установлений на кількох
  облікових записах, правильно прив’язується до того, якого торкається запуск.
  Без застосунку агенти отримують токен із середовища
- Запуск, який попросив учасник, що ввійшов, діє від **ідентичності GitHub цього
  учасника** — його облікові дані додають після середовища брокера, тож коміт чи
  коментар, який агент робить для нього, приписують йому

## Усунення несправностей

### Список PR порожній і повідомляє, що GitHub не підключено

У вас немає облікових даних GitHub на цьому сервері. Увійдіть або вставте токен у
розділі **Хостинг коду**. Репозиторіїв інших хостингів коду це не зачіпає —
нічого не додають лише репозиторії GitHub.

### Рядок пропонує «Додати токен», але не «Увійти через GitHub»

На сервері немає ID клієнта — це нормальний стан для збірки з вихідного коду,
адже облікові дані вшито лише в офіційні збірки. Див.
[Створити GitHub App](/uk-UA/керівництво/практичні-посібники/github-app/): це займає близько двох хвилин
і зробити це має лише власник сервера — один раз.

### Діалогове вікно входу каже, що провайдер не повернув код пристрою

GitHub App існує, але його прапорець **Device flow** вимкнено. Увімкніть його в
налаштуваннях застосунку (General → Device flow) і спробуйте знову.

### Рядок каже «через застосунок цього сервера», хоча я чекав на власний обліковий запис

Ви не ввійшли; те, що ви бачите, — це відповідь ідентичності застосунку сервера.
Натисніть **Увійти через GitHub** у цьому рядку.

### У fine-grained PAT немає кнопки злиття чи стану перевірок

Токену потрібні **Contents** і **Pull requests** (читання й запис), а також
**Checks** і **Actions** (читання). Змінивши його, вставте його знову в розділі
Хостинг коду.

### Додавання репозиторію відхилено

Для реєстрації потрібні всі три умови: шлях лежить усередині робочого дерева git,
у нього є remote `origin`, і цей remote указує на підтримуваний хостинг коду
(github.com, gitlab.com або bitbucket.org). Див.
[Додати репозиторії до робочого простору](/uk-UA/керівництво/практичні-посібники/додати-репозиторії/).

### Після інтенсивного використання все на якийсь час перестає працювати

Це запобіжник на випадок обмеження частоти запитів. GitHub повідомляє про
досягнення основного ліміту відповіддю `403` із заголовком
`x-ratelimit-remaining: 0` і часом скидання; побачивши таку, клієнт локально
відхиляє подальші запити, без мережевого звернення, доки не спливе вікно, — тож
шквал повторних спроб не може поглибити ліміт. Тимчасові збої повторюють до трьох
разів з експоненційною затримкою, поважаючи `retry-after`.
