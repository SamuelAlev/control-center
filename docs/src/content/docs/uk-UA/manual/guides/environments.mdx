**Середовище** — це запущений стек одного простору: сервіси, потрібні гілці, ізольовані від усіх інших просторів, видимі на бічній панелі й доступні агентам. Воно є і в пул-реквестів, бо PR уже має власний простір.

Адміністратор робочого простору один раз пише **визначення**. Після цього учасники натискають **Запустити** у розділі **Середовище** бічної панелі простору або PR. Визначення зберігаються в базі даних робочого простору, тому гілка з новою функцією ніколи не змінює те, що запускає Control Center, хоча інструменти все одно виконують код цієї гілки.

## Створення визначення

1. Відкрийте **Налаштування → Робочий простір → Середовища**. Змінювати визначення можуть лише адміністратори робочого простору.
2. Натисніть **Нове визначення**, потім **Порожнє визначення** або **Чернетка з репозиторію**. Чернетка шукає в репозиторії файли compose, `Procfile` і скрипти `package.json`, а результат перевіряєте ви.
3. Заповніть форму або скористайтеся вкладкою **JSON**. Приклади на цій сторінці показують цей JSON.
4. Натисніть **Запустити тест**. Запуститься одноразове середовище; Control Center дочекається готовності й знищить його.

Щоб зберігати визначення в репозиторії, використовуйте **Пов'язати файл репозиторію**. Control Center читає файл лише з типової гілки й запускає лише версію, схвалену адміністратором. Новіша версія показує **Доступне оновлення** і нічого не змінює до схвалення.

## Найменше визначення

Простому репозиторію з compose потрібно лише це:

```jsonc
{
  "contract": 1,
  "name": "Shop",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "components": [ { "kind": "compose", "id": "stack" } ]
}
```

Усе інше має типові значення: файл compose знаходиться сам, запускаються всі сервіси, призначаються порти, визначаються кінцеві точки HTTP, а середовище отримує назву гілки.

## Види компонентів

Середовище — це впорядкований список компонентів. Кожен чекає на готовність попереднього, якщо `after` не називає інші, а зупинка йде у зворотному порядку. `enabledWhen` ставить компонент у залежність від параметра чи ролі, наприклад `opt.seed`, `!opt.seed` або `repo.web`.

| Вид | Хто запускає | Для чого |
| --- | --- | --- |
| `compose` | Драйвер compose у Control Center | Будь-який файл compose, один на середовище |
| `cli` | Ваш інструмент. Control Center викликає призначені дієслова й читає JSON | Інструмент, який сам володіє життєвим циклом, доменами й даними |
| `process` | Control Center у контрольованому сеансі термінала | Сервери розробки й воркери |
| `task` | Control Center, один раз на тригер | Встановлення, міграції, тести |
| `app` | Control Center, коли хтось натискає **Відкрити** | Настільний застосунок |

Компоненти `task` приймають список `when`:

| Тригер | Коли виконується |
| --- | --- |
| `provision` | Під час створення worktree (див. завдання worktree нижче) |
| `create` | Один раз на середовище і знову після скидання |
| `start` | Під час кожного запуску |
| `change` | Після синхронізації, якщо змінений шлях збігається з `onChange` |
| `manual` | На запит: **Виконати**, `cc-env run <id>` або `environment_run_task` |
| `archive` | Безпосередньо перед знищенням worktree |

Команда у вигляді масиву — це argv, тому значення параметрів ніколи не проходять через оболонку. Рядок або `script` з масивом рядків виконуються в `bash -lc`. Заповнювачі на кшталт `{name}`, `{branch}`, `{stateDir}`, `{repo.<role>}`, `{port.<key>}`, `{opt.<key>}` і `{url.<role>}` розгортаються лише в argv. Команди оболонки читають ті самі значення зі змінних `CC_ENV_*`, наприклад `$CC_ENV_PORT_WEB`.

Кожна команда й термінал простору також отримують `CC_ENV_NAME`, `CC_ENV_STATE_DIR`, `CC_ENV_URL`, `CC_SPACE_ID`, `CC_REPO_PATH_<ROLE>`, а в просторах PR ще `CC_PR_NUMBER` і `CC_PR_IS_FORK`. З компонентом compose вони отримують і `COMPOSE_PROJECT_NAME` та `COMPOSE_FILE`, тож `docker compose exec` у завданні потрапляє в потрібний проєкт.

## Ролі та робочий каталог

Визначення прив’язує **ролі** до репозиторіїв робочого простору, тому один стек може охоплювати кілька репозиторіїв:

```jsonc
"repos": {
  "api": { "repoId": "<api>", "anchor": true, "required": true },
  "web": { "repoId": "<web>", "anchor": true },
  "e2e": { "repoId": "<e2e>", "whenMissing": "useSource" }
}
```

- `anchor`: простір може запустити середовище, якщо в ньому є принаймні одна якірна роль. Якщо підходять два визначення, обирає той, хто запускає.
- `required`: без цього репозиторію стек не працює.
- `whenMissing`: що робити, якщо в просторі немає цієї ролі. `addToSpace` додає репозиторій на типовій гілці й є типовим значенням для ролей `required`. `useSource` передає вашу зареєстровану копію, яку слід вважати доступною лише для читання. `skip` залишає змінну незаданою і діє типово в решті випадків.
- Для запуску потрібні право `write` на якірний репозиторій у просторі та доступ на читання до всіх інших прив’язаних репозиторіїв.

Команда виконується в першій ролі з `repos`, яка є в просторі, тому у визначенні з одним репозиторієм про це можна не згадувати. Будь-який компонент може змінити це за допомогою `"cwd": { "role": "e2e", "path": "packages/ui" }`. Обидва поля необов’язкові.

## Порти й URL

Control Center призначає порти хоста ще до запуску, зі спільного для хоста діапазону (типово від 42000 до 49999, блоками по 32). Порт не змінюється протягом усього життя середовища, а порти compose прив’язуються лише до `127.0.0.1`.

- Порти compose оголошувати не потрібно. Читайте їх як `{port.postgres.5432}` або `CC_ENV_PORT_POSTGRES_5432`.
- Інші порти оголошуються там, де використовуються, за допомогою `"port": "web"` або `"ports": ["web", "hmr"]`, і читаються як `{port.web}`. Процес із портом також отримує `PORT` і `HOST=127.0.0.1`.

Кінцеві точки HTTP отримують URL на маршрутизаторі сервера, який слухає один порт loopback:

```text
http://<endpoint>--<name>--<project>.localhost:<router port>
http://web--fix-login--shop.localhost:7355
```

- `<name>` — гілка у вигляді слага або `pr-<n>` у просторі PR. `<project>` — це `naming.project`, а інакше назва визначення.
- Імена `*.localhost` вказують на loopback, тому їм не потрібні записи hosts і DNS, а ім’я хоста розділяє cookie між середовищами.
- Порти compose, що відповідають через HTTP, визначаються автоматично, а `http` у компоненті замінює це припущення. Процесу потрібен `"endpoint": { "role": "web", "primary": true }`, який також робить доступним `{url.web}`.
- У браузері (ВМ) використовуйте **Відкрити в Browser (VM)**. `https://web--fix-login--shop.localhost/` веде там на той самий маршрут.
- Уся мітка вміщується в 63 символи, тому довгі імена скорочуються за допомогою хешу.
- Дві кінцеві точки не мають спільного батьківського домену. Застосунок, якому потрібен один cookie для обох, має обслуговувати їх з однієї кінцевої точки.

Для URL, які потрібно зареєструвати заздалегідь, наприклад перенаправлень OAuth, `"naming": { "pool": { "names": "cc{n}", "size": 8 }, "project": "shop" }` дає фіксований набір імен.

`policy` визначає, коли працюють середовища. `autoCreate` має значення `off`, `prSpaces` або `allSpaces`, `idleStopMinutes` типово дорівнює 240, `followPrHead` синхронізує середовище PR, коли зсувається його head, а за `maxRunning` (типово 6) кнопка **Запустити** пропонує зупинити середовище, яке найдавніше використовували.

## Приклад: застосунок на compose

Вебзастосунок і Postgres з одного файлу compose, з ігнорованим git файлом `.env`, міграціями й завданням тестів. `seedFiles` копіює вказані файли з вашої зареєстрованої копії в кожен новий worktree.

```jsonc
{
  "contract": 1,
  "name": "Shop",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "naming": { "project": "shop" },
  "seedFiles": [".env"],
  "components": [
    { "kind": "compose", "id": "stack",
      "services": ["postgres", "web"],
      "healthchecks": { "postgres": ["pg_isready", "-U", "postgres"] } },
    { "kind": "task", "id": "migrate", "when": ["create", "change"],
      "onChange": ["db/migrations/**"],
      "command": "docker compose exec -T web bin/migrate" },
    { "kind": "task", "id": "test", "when": ["manual"],
      "command": "docker compose exec -T web bin/test" }
  ]
}
```

`healthchecks` дає змогу сервісу без власної перевірки стану затримати наступний компонент. Без неї запущений контейнер вважається готовим, і міграції можуть випередити базу даних, яка ще запускається.

## Приклад: власний CLI

Вигаданий інструмент `acme`, який сам володіє контейнерами, доменами й TLS. Control Center передає `{name}`, а все інше дізнається зі `status`. Він ніколи не виводить імена хостів інструмента й ніколи не редагує `/etc/hosts`.

```jsonc
{
  "contract": 1,
  "name": "Acme",
  "repos": {
    "server": { "repoId": "<server>", "anchor": true, "required": true },
    "web": { "repoId": "<web>", "anchor": true }
  },
  "routing": { "mode": "tool", "domain": "acme.test", "upstream": "127.0.0.1:443",
               "tls": true, "caFile": "~/.acme/tls/ca.crt" },
  "components": [
    { "kind": "cli", "id": "acme",
      "verbs": {
        "create":  ["acme", "env", "create", "{name}", "--json",
                    { "if": "repo.web", "args": ["--web-dir", "{repo.web}"] }],
        "start":   ["acme", "env", "start", "{name}"],
        "stop":    ["acme", "env", "stop", "{name}"],
        "destroy": ["acme", "env", "destroy", "{name}", "--yes"],
        "reset":   ["acme", "env", "reset-db", "{name}"],
        "status":  ["acme", "env", "status", "{name}", "--json"],
        "list":    ["acme", "env", "ls", "--json"],
        "logs":    ["acme", "env", "logs", "{name}",
                    { "if": "service", "args": ["{service}"] },
                    "--tail", "{tail}",
                    { "if": "follow", "args": ["--follow"] }],
        "exec":    ["acme", "env", "exec", "{name}", "{service}", "{command}"]
      },
      "keepsDataOnStop": false,
      "statusMap": {
        "state": [
          { "when": { "path": "/status/ready", "equals": true }, "state": "ready" },
          { "when": { "none": "/status/containers", "where": { "state": "running" } },
            "state": "stopped" },
          { "when": { "path": "/status/phase", "equals": "failed" }, "state": "failed" },
          { "state": "starting" }
        ],
        "detail": "phase: {/status/phase}",
        "warnings": [
          { "when": { "path": "/status/dnsWorking", "equals": false },
            "message": "Not resolvable on this host" }
        ],
        "endpoints": [
          { "role": "app", "label": "App", "url": "/urls/app", "primary": true },
          { "role": "db", "hostPort": "/ports/db" }
        ],
        "services": "/status/containers/*/service",
        "list": "/*/slug",
        "missingErrorCodes": ["env.not-found"]
      } }
  ]
}
```

- `create`, `status` і `destroy` обов’язкові. Control Center обирає `create` або `start` за прочитаним статусом. Будь-яке дієслово може бути `{ "shell": "…" }` замість argv.
- `statusMap` читає власний JSON інструмента за допомогою вказівників JSON, де `*` відповідає кожному елементу. Правила стану впорядковані, і перемагає перший збіг. Умова — це `path` з `equals` або `any` чи `none` з `where`.
- `keepsDataOnStop: false` вимикає зупинку під час простою й додає до **Зупинити** попередження про втрату даних. Задавайте його, коли зупинка втрачає дані.
- `routing.mode: "tool"` під’єднує імена хостів інструмента до браузера (ВМ) і агентів. Домен має закінчуватися на `.test`, `.localhost` або `.internal`, а повідомлений URL поза ним відкидається.

Ваш власний інструмент може обійтися без `statusMap` і виводити контракт статусу, описаний наприкінці цієї сторінки.

## Приклад: монорепозиторій pnpm

Лише процеси й завдання, без контейнерів. Вебзастосунок знаходить API через `{url.api}`.

```jsonc
{
  "contract": 1,
  "name": "Monorepo",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "naming": { "project": "mono" },
  "options": [ { "key": "seed", "type": "bool", "default": true, "agentDefault": false } ],
  "components": [
    { "kind": "task", "id": "install", "when": ["provision", "change"],
      "onChange": ["pnpm-lock.yaml"],
      "command": ["pnpm", "install", "--frozen-lockfile"] },
    { "kind": "process", "id": "api", "label": "API", "port": "api",
      "cwd": { "path": "apps/api" },
      "command": ["pnpm", "dev"],
      "endpoint": { "role": "api" },
      "ready": { "http": "http://127.0.0.1:{port.api}/health", "timeout": 120 },
      "restartOn": ["pnpm-lock.yaml"] },
    { "kind": "task", "id": "seed", "when": ["create"], "enabledWhen": "opt.seed",
      "cwd": { "path": "apps/api" },
      "command": ["pnpm", "db:seed"] },
    { "kind": "process", "id": "web", "label": "Dev server", "port": "web",
      "cwd": { "path": "apps/web" },
      "env": { "API_URL": "{url.api}" },
      "command": ["pnpm", "dev", "--port", "{port.web}", "--host", "127.0.0.1"],
      "endpoint": { "role": "web", "primary": true },
      "ready": { "http": "http://127.0.0.1:{port.web}/" } },
    { "kind": "task", "id": "lint", "when": ["manual"], "command": ["pnpm", "lint"] }
  ]
}
```

- Кожен процес — це вкладка термінала, яку можна відкрити, читати й у якій можна друкувати. Закриття вкладки його не зупиняє.
- `ready` приймає `http`, `tcp` або `logMatch`. `restart` приймає `on-failure` (типово), `always` або `never`. `restartOn` перезапускає процес, коли збігається змінений шлях.
- `options` перетворюються на форму біля **Запустити**, а `agentDefault` застосовується до запусків агентом.

## Приклад: настільний застосунок

Настільний застосунок із кроком збирання. Застосунок працює однаково, незалежно від технології, бо Control Center працює на рівні вікон ОС і не потребує хуків чи SDK у застосунку.

```jsonc
{
  "contract": 1,
  "name": "Studio",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "components": [
    { "kind": "task", "id": "build", "when": ["manual"], "command": ["pnpm", "build"] },
    { "kind": "app", "id": "desktop", "label": "Studio", "prepare": "build",
      "command": ["dist/mac-arm64/Studio.app/Contents/MacOS/Studio"],
      "isolate": "home" }
  ]
}
```

Застосунок не запускається разом із середовищем. Хтось натискає **Відкрити**, і спершу виконується `prepare`. **Перезібрати й перезапустити** виконує цю пару знову. Чистий вихід показується як закриття, збій показує останні рядки журналу без перезапуску, перезапуск сервера ніколи не запускає застосунок знову, а зупинка під час простою не чіпає запущений застосунок.

### Дозволи й обмеження настільних застосунків

- У macOS один раз надайте Control Center дозволи **Запис екрана** та **Доступність** у Системних параметрах. Хост сервера потребує графічного сеансу: сервер без GUI відмовляється запускати застосунок.
- Запускайте бінарний файл напряму. `open -a` передає застосунок LaunchServices, і він покидає дерево процесів, яке відстежує Control Center. `"window": { "match": { "bundleId": "…" } }` покриває цей випадок, але безпечно лише з однією запущеною копією.
- Вікна залишаються на дисплеї. macOS не захоплює вікно за межами всіх дисплеїв, тому застосунок, яким користується агент, видно на екрані сервера. Фокус йому не потрібен.
- `"isolate": "home"` дає застосунку приватний домашній каталог через `HOME`, `XDG_*` і `CFFIXED_USER_HOME`, щоб копії з двох просторів працювали поруч. `NSUserDefaults` не ізолюється, тому налаштування Cocoa й `shared_preferences` у Flutter залишаються спільними для копій.
- `isolate` діє лише на запущений процес. Лаунчеру інструментів на кшталт `flutter run` потрібен справжній домашній каталог, тому поєднуйте `isolate` зі зібраним бінарним файлом. Якщо застосунок має власне налаштування, наприклад `--user-data-dir`, краще використовуйте його.
- Агенти керують вікном через `app_use`, якому доступне лише дерево процесів цього середовища. Агент бачить вікно, а не робочий стіл. Запуски агентами проходять через політику дій і типово потребують підтвердження, а введення агента зупиняється, поки керування в людини.
- `"input": "background"` (типово) надсилає події процесу. `"foreground"` активує вікно й перехоплює курсор.

## Завдання worktree замінюють скрипти репозиторію

Завдання `provision` і `archive` замінюють старі скрипти налаштування й архівації для кожного репозиторію. **Наявні скрипти перенесено автоматично:** кожен репозиторій зі скриптами тепер має визначення з його назвою, а в завданнях `setup` і `archive` лежить той самий текст скриптів. Значок у рядку репозиторію в **Налаштування → Робочий простір → Репозиторії** відкриває його. Минулі запуски скриптів залишаються як історія лише для читання.

Ці завдання йдуть за worktree, а не за середовищем, тому виконуються і в просторах, де ніхто не натискає **Запустити**:

| | `provision` | `archive` |
| --- | --- | --- |
| Виконується | Під час створення worktree ролі, у будь-якому просторі | Безпосередньо перед знищенням цього worktree |
| У разі збою | Підготовка завершується помилкою, і worktree знищується | Записується, ніколи не блокує видалення |
| Типовий тайм-аут | 5 хвилин | 2 хвилини |
| Бачить | `CC_WORKSPACE_PATH`, `CC_ROOT_PATH`, `CC_SPACE_*`, `CC_REPO_NAME` | Те саме |

Репозиторію без стека потрібне лише визначення з його завданнями. Запускати нічого, тож якірна роль не потрібна:

```jsonc
{
  "contract": 1,
  "name": "Web",
  "repos": { "app": { "repoId": "<id>" } },
  "components": [
    { "kind": "task", "id": "setup", "when": ["provision"],
      "script": ["pnpm install", "cp \"$CC_ROOT_PATH/.env\" .env"] }
  ]
}
```

- Середовища ще немає, тому в цих завданнях не можна використовувати `{name}`, `{port.*}`, `{url.*}`, `{opt.*}` і `enabledWhen`, і вони не отримують `env` визначення.
- Завдання `provision` і `archive` для репозиторію може містити лише одне визначення. Інші можуть прив’язувати його для всього іншого.
- `"when": ["provision", "change"]` також перевстановлює залежності, коли змінюється lock-файл, чого скрипти налаштування ніколи не робили.
- Завдання виконується для worktree своєї ролі `cwd`, тому визначення з кількома репозиторіями може налаштовувати кожен окремо.
- Тестовий запуск задає `CC_SCRIPT_TEST=1`. Повторна спроба починається з чистого worktree, тому пишіть завдання, які витримають повторний запуск.

## Агенти

Агенти ніколи не отримують сокет Docker. У просторі з придатним визначенням запуск отримує `cc-env` у своєму `PATH`. Простір береться із запуску, тому агент може діяти лише у власному середовищі, а кожна команда проходить через політику дій.

```bash
cc-env status
cc-env up
cc-env down
cc-env reset
cc-env destroy
cc-env restart <process>
cc-env logs <name>
cc-env exec <service> -- <cmd>
cc-env run <task> -- <args>
```

З компонентом compose шим `docker` також дозволяє `docker compose` із `ps`, `logs`, `exec`, `port`, `restart` і `top`. Перед дієсловом не можна ставити прапорці, `logs` не може стежити за виводом, а `exec` приймає лише `-T`. Усе інше завершується з кодом 5 і повідомленням «not available in Control Center agent runs».

Репозиторій, чиї навички викликають його власний інструмент, може робити це й далі. Блок `agentPassthrough` у компоненті `cli` оголошує, які команди можуть виконувати агенти:

```jsonc
"agentPassthrough": {
  "binary": "acme",
  "allow": [
    { "argv": ["env", "ls"], "maps": "status", "nameFilter": true },
    { "argv": ["env", "status|url"], "maps": "status", "positionalName": 2 },
    { "argv": ["env", "create"], "maps": "up", "positionalName": 2,
      "pathFlags": ["--web-dir"], "denyFlags": ["--force"] },
    { "argv": ["env", "logs"], "maps": "logs", "positionalName": 2,
      "denyFlags": ["--follow"] }
  ]
}
```

`maps` називає операцію, чия політика застосовується. `positionalName` примусово підставляє в цей аргумент середовище цього простору, `nameFilter` фільтрує за ним вивід JSON, а кожне значення `pathFlags` має розв’язуватися всередині worktree запуску. Команда, що не збігається з жодним правилом, завершується з кодом 5.

Ті самі операції доступні як інструменти: `environment_status`, `environment_up`, `environment_down`, `environment_reset`, `environment_destroy`, `environment_restart`, `environment_exec`, `environment_logs`, `environment_run_task`, `environment_launch_app` і `environment_stop_app`. Агенти в пісочниці звертаються до своїх портів напряму, а до імен хостів свого середовища через проксі запуску, тому просіть їх читати кінцеві точки зі `environment_status`, а не вгадувати URL.

## Пул-реквести з форків

Коду PR із форка не можна довіряти, а за розміщення на хості він виконується від імені користувача ОС сервера. `policy.forkPrs` вирішує, що станеться:

| Значення | Дія | Типово для |
| --- | --- | --- |
| `rig` | Файл compose виконується у ВМ без запиту | Визначень лише з компонентами `compose` і `task` |
| `approval` | Кожен запуск потребує адміністратора | Усіх інших визначень |
| `deny` | Відмова | Жодних |

- `seedFiles` ніколи не копіюються для форка, бо зазвичай це секрети. Файл compose, який монтує такий файл, повідомляє про відсутній файл за назвою.
- Завдання `provision` і `archive` пропускаються, крім випадку, коли політика дорівнює `rig`: тоді вони виконуються у ВМ.
- За розміщення на хості для форка відхиляються `privileged`, простори імен хоста, монтування сокета Docker, `devices` і монтування поза worktree простору. У довірених просторах вони дають лише попередження.

## Розміщення в rig

`"placement": "rig"` виконує компоненти `compose` і `task` у виділеній microVM. Визначення з компонентами `process`, `cli` або `app` не підходять. Файл compose виконується без змін, без сокета Docker хоста й облікових даних оператора, а доступ до мережі обмежено реєстрами, потрібними його образам. Worktree монтується наживо.

- **Гостьові системи arm64.** На Apple Silicon гостьові системи працюють на arm64, тому образи лише для amd64 не запустяться.
- **Приватні реєстри відхиляються.** Гостьові системи не мають облікових даних реєстрів, тому образ із реєстру поза відомими публічними відхиляється до завантаження ВМ. Приватний репозиторій у публічному реєстрі завершиться помилкою під час отримання гостем.
- **16 ГіБ сховища.** Усі образи й томи стека ділять один диск на 16 ГіБ, і збільшити його не можна.
- **Перше завантаження повільне.** Шари образів у кожної ВМ свої, тому перше завантаження отримує все. Зупинений rig зберігає свій диск.
- **Базові образи мають бути читабельними.** Dockerfile, що називає базовий образ через змінну, не можна спланувати, бо доступ до мережі фіксується під час завантаження.
- **Час життя.** `policy.rigTtlHours` завершує ВМ, типово через 24 години.

## Контракт статусу для авторів інструментів

Компонент `cli` без `statusMap` очікує нативний контракт `cc-env/1`. Дієслово `status` виводить цей об’єкт у stdout:

```json
{
  "state": "ready",
  "detail": "migrations applied, HTTP 200",
  "endpoints": [
    { "role": "app", "label": "App", "url": "https://fix-login.acme.test", "primary": true },
    { "role": "postgres", "label": "Postgres", "hostPort": 49213 }
  ],
  "services": ["server", "postgres"],
  "needsRecreate": false,
  "error": { "code": "post-start-failed", "message": "…", "hint": "…", "command": "…" }
}
```

- `state` має значення `ready`, `starting`, `stopped`, `failed` або `missing`. `missing` веде до `create`, а `stopped` і `failed` ведуть до `start`. Повідомляйте `missing` з кодом виходу 0: невдалий `status` вважається `failed`.
- Обов’язковий лише `state`. Невідомі поля ігноруються, а вивід, який не вдається розібрати, показується як погіршений, із сирим текстом у деталях.
- URL має бути loopback, `*.localhost` або під `routing.domain`, інакше він відкидається.
- `needsRecreate: true` показує **Створити заново**, що видаляє дані. Control Center ніколи не діє за цим прапорцем сам.
- Дієслово `list` виводить масив JSON з імен або об’єктів із `name`.

Коди виходу діють для всіх дієслів:

| Код | Значення |
| --- | --- |
| 0 | ОК |
| 3 | Потрібне налаштування хоста. **Виконати в терміналі** відкриває термінал простору з уведеною, але не виконаною командою, потім **Повторити** пробує знову. Control Center ніколи не виконує `sudo` |
| 4 | Потрібна автентифікація |
| 5 | Залежність недоступна |
| Інший | Збій |

Перебіг виконання йде в stderr як JSON з розділенням за рядками:

```json
{"type":"step","label":"Pull images","state":"running"}
{"type":"note","message":"Hosts entries stayed behind after destroy"}
{"type":"error","code":"hosts-missing","message":"Add the hosts entry","hint":"Needs sudo","command":"sudo acme hosts add fix-login"}
```

Рядки `step` показуються як живий список кроків, а рядки `note` — як є. Останній рядок типу `error` стає структурованою помилкою, а `command` пропонується скопіювати. Без нього Control Center показує останні 20 рядків stderr. Усе, що не JSON, вважається звичайним журналом.
