Цей посібник показує, де зберігаються кожні облікові дані, які використовує
Control Center, і як їх змінити.

**Нічого не зберігається на машині, з якої ви працюєте.** Кожні облікові дані
живуть на сервері; які саме відповідають на конкретний запит, залежить від
того, чи стоїть за ним людина.

| Облікові дані                                | Де зберігаються                                                                 | Хто їх використовує                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Ваш вхід у хостинг коду / тікетинг           | Файл секретів 0600 на сервері, прив’язаний до ідентифікатора вашого користувача | Усе, що робите ви: поверхня PR, рев’ю, злиття, ваші дії в Linear              |
| Застосунки провайдерів сервера               | Той самий файл, плюс `server_settings` для несекретних даних                    | Вхід людей і токени для одного репозиторію для агентів, конвеєрів і опитування |
| Ключ встановлення Connect                    | Той самий файл (`connect_install_key`)                                          | Ідентифікація цього сервера перед Control Center Connect                      |
| Ключі постачальників моделей і токени OAuth  | Власне сховище облікових даних сервера                                          | Вбудований адаптер, для кожного робочого простору в інсталяції                |
| Облікові дані ботів Slack                    | `<dataDir>/<workspaceId>/chat_credentials/` на сервері                          | Чат-міст для цього робочого простору: токени вашого власного застосунку або запечатаний грант спільного застосунку |
| Облікові дані зовнішніх CLI                  | Те, що використовує цей CLI                                                     | Claude Code, на хості сервера                                                 |

## GitHub: ваш вхід і токени для одного репозиторію

- **Ваш** — з **Увійти в GitHub**. Саме його використовує кожен запит, зроблений
  *від вашого імені*, тож рев’ю, опубліковане за вас, несе ваше ім’я. Інший
  учасник не може ним скористатися й входить сам. Вставляти токен GitHub не
  потрібно
- **Робота, за якою ніхто не друкує** (агенти, конвеєри, опитування, відповіді
  бота), отримує токен для одного репозиторію за раз, випущений із GitHub App
  сервера або через Control Center Connect і обмежений тим, що може робити там
  відповідальний учасник. Це ніколи не ваш вхід, переданий цілком

Ваш задається в картці **Хостинг коду** за шляхом **Налаштування → Робочий
простір → Профіль і ідентичність**; застосунок сервера — у **Застосунки
провайдера** за шляхом **Налаштування → Сервер → Єдиний вхід**. Див.
[Налаштувати інтеграцію GitHub](/uk-UA/керівництво/практичні-посібники/інтеграція-github/)
і [Створити GitHub App](/uk-UA/керівництво/практичні-посібники/github-app/).

GitLab і Bitbucket і далі приймають вставлений особистий токен, що зберігається
так само. Див. [Підключити хост коду](/uk-UA/керівництво/практичні-посібники/підключити-хост-коду/).

:::note[Існує також екран, доступний лише за URL]
`/workspaces/<workspaceId>/api-keys` показує ті самі дві картки, що й перший
крок онбордингу. Він **не має жодного запису в навігації інтерфейсу**; до нього
можна дістатися лише, ввівши URL. Натомість скористайтеся Налаштування →
Робочий простір → Профіль і ідентичність.
:::

## Задайте ключі постачальників моделей

Вбудований адаптер сам автентифікує провайдерів, і ці облікові дані зберігаються
на сервері.

1. Перейдіть до **Налаштування → Сервер → Постачальники моделей**
2. Прокрутіть до **Провайдери й моделі**
3. Підключіть провайдера — OAuth у браузері для OpenAI, Codex, Cursor і Kimi
   Code; API-ключ для Anthropic та решти

Повний список і додавання власного ендпоінта див. у [Керувати адаптерами та
моделями](/uk-UA/керівництво/практичні-посібники/адаптери/).

Ці облікові дані **глобальні для хоста**: один ключ обслуговує кожен робочий
простір в інсталяції. Токени OAuth оновлюються до завершення їхнього терміну дії.

Зовнішні CLI адаптерів тримають власні облікові дані у власній конфігурації на
хості сервера — Control Center ними не керує. Автентифікуйте Claude Code так, як
каже його власна документація, на машині, де працює `cc_server`.

Діалог **Змінні середовища**, що належить окремому адаптеру, виглядає як місце,
де можна покласти ключ для одного з них, але це не так: він пише на ваш
пристрій, а сервер читає власну копію, і ніщо ці дві не з’єднує. Див.
[Керувати адаптерами та моделями](/uk-UA/керівництво/практичні-посібники/адаптери/).

## Підключіть провайдера тікетів

Картка **Тікетинг** за шляхом **Налаштування → Робочий простір → Загальні**
містить обидві половини одного рішення: у якого провайдера живуть ваші тікети і
ким Control Center виступає, коли з ним спілкується. Вибір **Локально** ховає
рядки Linear — локальні тікети живуть у власній базі даних цього сервера, і
автентифікуватися їм ні до чого.

Linear має два входи й жодного вставлюваного ключа: **Linear** — ваш, для того,
що робите ви, а **Автоматизація Linear** — це застосунок Control Center робочого
простору, який підключає адміністратор, для синхронізації тікетів, конвеєрів і
агентів. Сервер також може тримати **Сервісний ключ API** (**Застосунки
провайдера**) для робочих просторів без підключеної автоматизації. Жодні облікові
дані тікетингу не вставляються в пісочницю агента;
агенти пишуть тікети через інструменти Control Center, які запитують правило
**Запис у зовнішній трекер**. Див. [Налаштувати
інтеграцію Linear](/uk-UA/керівництво/практичні-посібники/інтеграція-linear/).

## Змініть або відкличте

- **Ваш вхід у GitHub**: натисніть **Від’єднатися**, потім знову **Увійти в
  GitHub**. Від’єднання також відкидає всі токени, які сервер випустив від
  вашого імені
- **Токен GitLab або Bitbucket**: натисніть **Оновити токен** і вставте новий,
  потім відкличте старий на хості коду
- **Застосунок сервера**: згенеруйте новий приватний ключ або клієнтський секрет
  на сторінці застосунку в провайдера, вставте його в **Застосунки провайдера** і
  натисніть **Тест**
- **Ключ встановлення Connect**: **Змінити ключ** на картці **Control Center
  Connect** або `cc_server connect rotate-key --yes`. Усі, хто входив через
  Connect, входять знову. Див. [Control Center Connect](/uk-UA/керівництво/довідка/connect/)
- **Постачальник моделей**: у його рядку вийдіть (OAuth) або видаліть ключ, потім
  підключіть знову
- **Slack**: для власного застосунку вставте токени заново в діалозі
  підключення. Спільний застосунок Control Center не має токена для зміни: його
  токен бота оновлюється через Connect, а **Відключити** відкликає його й видаляє
  бота зі Slack. Див. [Налаштувати
  інтеграцію Slack](/uk-UA/керівництво/практичні-посібники/інтеграція-slack/)

## Усунення проблем

### Токен GitLab або Bitbucket працює в `curl`, але не тут

Перевірте підзаголовок рядка **Хостинг коду**. Якщо там указано «із середовища»,
відповідають облікові дані сервера, а не ваші, — ваші не збереглися.

### Токен GitLab або Bitbucket приймається, але наступні запити не проходять

Токен перевіряють таким, як він збережений, тож рядок називає обліковий запис за
ним — але лише запис, не області доступу. Токен із надто вузькими областями
доступу підключається, а потім не проходить окремі запити. Перевірте його
області доступу й термін дії на хості коду.

### Провайдер повідомляє, що вхід на цьому сервері не налаштовано

Сервер не має ні власного застосунку для цього провайдера, ні Control Center
Connect. Власник сервера вибирає один із варіантів у **Налаштування → Сервер →
Єдиний вхід**.
