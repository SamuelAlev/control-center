Це **прив’язані до сервера** інструменти, які вбудоване середовище виконання агента реєструє безпосередньо — мовний сервер, структурний пошук, налагоджувач, ядра, скрипти режиму коду, запитання й керування воркерами — на противагу [інструментам MCP](/uk-UA/керівництво/довідка/інструменти-mcp/), які воно під’єднує, та загальним інструментам для файлів, пошуку й оболонки із середовища виконання harness. Їх немає в реєстрі MCP: зовнішній клієнт MCP їх не побачить, бо кожен із них прив’язаний до живого ресурсу на боці сервера — процесу мовного сервера, налагоджувального адаптера, інтерпретатора — що належить одному запуску.

Кожен інструмент тут реєструється лише тоді, коли його опорний ресурс підключено для запуску — наглядач мовного сервера чи налагодження, парсер tree-sitter, фабрика ядер, порт запитань, перелік vibe-воркерів. Виявлення мовного сервера чи налагоджувального адаптера для *цього чекаута* — це окрема, пізніша перевірка (`status` / `adapters`): ці інструменти залишаються на поверхні, щоб агент міг спитати, чому ніщо не придатне, а не здогадуватися.

## Рівні схвалення

Кожен інструмент оголошує рівень, і рівень вирішує, **які поверхні його бачать** — а не лише те, чи він запитує дозвіл. Режим плану та субагенти лише для читання обмежені рівнем `read`, тож інструмент рівня `write` або `exec` взагалі відсутній у їхній схемі.

| Рівень  | Значення                      | Інструменти тут                                   |
| ------- | ----------------------------- | ------------------------------------------------- |
| `read`  | Без побічних ефектів          | `lsp`, `ast_grep`, `ask_user`, `repl`, п’ять `vibe_*` |
| `write` | Змінює файли                  | `lsp_rename`, `ast_edit`, `resolve`               |
| `exec`  | Запускає процес або керує ним | `debug`, `eval`                                   |

## Прямий виклик, лише зі скрипта або завантаження при першому використанні

Коли сервер може запускати скрипти, запуск викликає кілька інструментів напряму, а решту досягає через скрипт [`repl`](#repl--запуск-скрипта-що-викликає-ваші-інструменти); повне правило див. у [Режим коду](/uk-UA/керівництво/поняття/режим-коду/#які-інструменти-агент-викликає-напряму). Для інструментів на цій сторінці:

| Інструмент | З `repl` | Без `repl` |
| ---- | ----------- | -------------- |
| `repl` | Прямий | Відсутній |
| `ask_user` | Прямий | Прямий |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Лише зі скрипта | Завантажується при першому використанні |
| `eval` | Завантажується при першому використанні (скрипт не може його викликати) | Завантажується при першому використанні |
| `vibe_*` | Прямий у режимі vibe, ніколи зі скрипта | Прямий у режимі vibe |

Інструмент, позначений як «Лише зі скрипта», завантажується при першому використанні, щойно сервер не може запускати скрипти запуску ([Коли скрипти не можуть працювати](/uk-UA/керівництво/поняття/режим-коду/#коли-скрипти-не-можуть-працювати)).

## `lsp` — запити до мовного сервера

Реєструється, коли запуск має наглядача мовного сервера та робочий каталог. Чи сервер справді може відповісти, визначається під час виклику як **перетин**: кореневий маркер має існувати *і* бінарник сервера має резолвитися. Кожна з умов окремо означає, що жоден сервер не запуститься — `status` це підтверджує — а не тихий здогад.

Сервери беруться лише зі вбудованої таблиці; файл `lsp.json` з репозиторію не читається. У запуску в пісочниці кожен запуск має власну сесію мовного сервера, тож сервери стартують знову з кожним запуском. Локальні для проєкту бінарники (`node_modules/.bin`) використовуються лише в запуску в пісочниці, а корінь проєкту ніколи не резолвиться вище робочого каталогу запуску.

Позиції адресуються `line` плюс підрядком `symbol`, ніколи не стовпцем. Модель, яку просять указати стовпець, здогадується, а хибний здогад резолвиться в інший символ у тому ж рядку — відповідь, що виглядає правильною, але стосується чогось іншого. Пропуск `symbol` у навігаційній дії — це помилка, а не здогад про перший стовпець.

| Дія               | Аргументи                        | Повертає                                   |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (або `"*"`)               | Помилки та попередження; `"*"` замість цього запускає перевірку проєкту |
| `definition`      | `file`, `line`, `symbol`         | Де оголошено символ                        |
| `type_definition` | `file`, `line`, `symbol`         | Де оголошено його тип                      |
| `implementation`  | `file`, `line`, `symbol`         | Конкретні реалізації                       |
| `references`      | `file`, `line`, `symbol`         | Кожне використання, не більше 50           |
| `hover`           | `file`, `line`, `symbol`         | Сигнатура й коментар документації           |
| `symbols`         | `query` або `file`               | Пошук у робочому просторі за `query` (не більше 100); символи документа за `file` (не більше 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Швидкі виправлення, які пропонує сервер     |
| `status`          | —                                | Які сервери працюють і для яких коренів     |
| `reload`          | —                                | Перезапускає сервер для цього кореня        |

### Діагностика під час запису

Виграш не в інструменті. `write`, `edit` і `apply_patch` **обгорнуто**: після запису файл синхронізується та зберігається через мовний сервер, і до результату інструмента долучаються лише **нові** діагностичні повідомлення. Агент дізнається, що зламав збірку, тієї ж миті, коли її зламав, і йому не треба пам’ятати, щоб спитати.

Уже повідомлену діагностику пригнічує журнал на кожен запуск, заведений за рівнем серйозності, кодом і повідомленням — позицію навмисно виключено, тож діагностика, яка лише з’їхала на чотири рядки вниз, не позначається знову як нова.

## `lsp_rename` — перейменування в межах проєкту

Окремий інструмент рівня `write` рівно з однієї причини: рівень визначає видимість. Якби перейменування вбудували в `lsp`, це або дало б досліднику лише для читання змогу переписувати репозиторій, або поставило б кожен `hover` за запитом на схвалення.

| Аргумент   | Значення                                    |
| ---------- | ------------------------------------------- |
| `file`     | Де розташований символ                      |
| `line`     | Рядок з індексацією від 1                   |
| `symbol`   | Підрядок, що ідентифікує його в цьому рядку |
| `new_name` | Як його назвати                             |

## `ast_grep` — структурний пошук

Знаходить код за **формою**, а не за текстом. `$NAME` зіставляє будь-який вузол, `$$$NAME` — послідовність сусідніх вузлів, а `$_` — це шаблонний символ, який нічого не зв’язує.

Властивість, яка робить його механізмом зіставлення, а не regex із зайвими кроками: метазмінна, повторена в одному шаблоні, має захопити той самий текст.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

зіставляє захисну умову, яка звільняє саме те, що перевірила, і **не** зіставляє ту, яка звільняє щось інше.

| Аргумент      | Значення                                                    |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | Фрагмент коду з метазмінними                                |
| `path`        | Файл або каталог для пошуку; типово — весь робочий простір  |
| `language`    | Ідентифікатор граматики з постачання (`dart`, `python`, `rust`, `c`, …). Виводиться, коли `path` називає файл |
| `max_results` | Типово 50                                                   |

:::note[Шаблон розбирається тією ж граматикою, що й файл]
Тож `dispose(x)` зіставляє виклик, як би його не розставляли пробілами, не переносили чи не коментували, — і ніколи не зіставляє ті самі символи всередині рядкового літерала чи коментаря.
:::

:::caution[Фрагмент розбирається в каркасі, а не голим]
`dispose(x)`, розібраний на верхньому рівні Dart, — це коректна *сигнатура функції*. Компілятор шаблонів пробує драбину контекстів (інструкція, вираз, член класу, оголошення) і використовує перший, який приймає фрагмент. Шаблон, який не приймає жоден контекст, позначають як непридатний до розбору, а не шукають і тихо не знаходять.
:::

## `ast_edit` — структурний перезапис із підготовкою

Те саме зіставлення, плюс шаблон `rewrite` із підставленими назад метазмінними. **Нічого не записується.** Зміну підготовлено, і результат називає `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Аргумент   | Значення                                           |
| ---------- | -------------------------------------------------- |
| `pattern`  | Що зіставляти                                      |
| `rewrite`  | Що поставити натомість, із підставленими `$NAME`   |
| `path`     | Обсяг; типово — весь робочий простір               |
| `language` | Ідентифікатор мови                                 |

## `resolve` — зафіксувати або відкинути підготовлену зміну

| Аргумент  | Значення                   |
| --------- | -------------------------- |
| `edit_id` | З результату `(proposed)`  |
| `action`  | `accept` або `discard`     |

Кожен файл звіряють із вмістом, зафіксованим у момент підготовки, і **будь-яка** розбіжність відхиляє всю зміну. Частково застосований структурний перезапис лишає дерево, яке не компілюється ні за старою формою, ні за новою.

## `debug` — керувати налагоджувачем

Реєструється, коли запуск має наглядача сесій налагодження, робочий каталог та ідентифікатор розмови. Чи адаптер справді може запуститися, визначається під час виклику за тим самим правилом перетину, що й для мовного сервера (кореневий маркер *і* бінарник). Рівень `exec`; не безпечний для паралелі (сесія — це стан між викликами, тож `continue`, який обганяє `stack`, прочитав би кадр, що вже зсунувся).

Одна сесія на розмову, з жорстким TTL (30 хвилин). Другий `launch` відхиляють, а не тихо замінюють ним перший. У запуску в пісочниці сесія зберігає свою пісочницю між ходами, доки не завершиться, тобто щонайбільше ці 30 хвилин.

| Операція      | Аргументи                     | Примітки                                       |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Які адаптери тут придатні й чому ні            |
| `status`      | —                             | Чи працює сесія і де вона зупинилася           |
| `breakpoints` | `file`, `lines[]`             | Порожній `lines` очищає файл. Можна ставити **до** запуску |
| `launch`      | `program`, `args[]`           | Запускає програму, зупинену на ваших точках зупину |
| `attach`      | `port`                        | Під’єднується до вже запущеної програми, яку налагоджують, на одному з власних перенаправлених портів запуску; будь-який інший порт відхиляється до того, як щось стартує |
| `continue`    | `thread_id?`                  | Виконується до наступної зупинки               |
| `pause`       | `thread_id?`                  | Зупиняє її там, де вона є                      |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Переміщує на один крок            |
| `threads`     | —                             | Ідентифікатори та назви потоків                |
| `stack`       | `thread_id?`                  | Кадри, не більше 30                            |
| `scopes`      | `frame_id`                    | Області видимості кадру, кожна з `reference`   |
| `variables`   | `reference`                   | Дочірні елементи, не більше 50; значення — не більше 400 символів |
| `evaluate`    | `expression`, `frame_id?`     | Обчислюється у власній області видимості кадру |
| `output`      | —                             | stdout/stderr програми, яку налагоджують, обмежено |
| `terminate`   | —                             | Завершує сесію й убиває адаптер                |

### Адаптери

| Ідентифікатор | Команда                      | Кореневі маркери                                 |
| ------------- | ---------------------------- | ------------------------------------------------ |
| `dart`        | `dart debug_adapter`         | `pubspec.yaml`                                   |
| `debugpy`     | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`        | `lldb-dap`                   | `Cargo.toml`, `CMakeLists.txt`                   |
| `delve`       | `dlv dap`                    | `go.mod`                                         |

`debugpy` надає перевагу локальним для проєкту `.venv/bin` або `venv/bin` над `$PATH` у запуску в пісочниці: Python із `$PATH` — це інше середовище, і під’єднання не з того середовища падає так, що це читається як зламаний код. Без пісочниці він використовує лише `$PATH`, тож репозиторій не може вибрати інтерпретатор, що виконується на хості.

## `repl` — запуск скрипта, що викликає ваші інструменти

Є в кожному запуску, коли сервер може запускати скрипти ([Коли запуск має `repl`](/uk-UA/керівництво/поняття/режим-коду/#коли-запуск-має-repl)). Скрипт — це звичайний JavaScript, тіло асинхронної функції, який виконується в новому, обмеженому інтерпретаторі у власному процесі: без доступу до файлової системи, мережі, процесів чи модулів. Сам `repl` належить до рівня `read` і захищає себе сам, бо кожен виклик інструмента, який робить скрипт, перевіряється окремо. Також доступний на кінцевій точці MCP для запусків агента на сервері, який може запускати скрипти.

| Аргумент | Значення |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | Скрипт. Не більше 256 KiB |
| `description` | Обов’язково. Коротка назва для рядка в розмові |
| `timeout_ms` | Необов’язково. Коротший ліміт часу, ніж у робочому просторі; ніколи довший |
| `max_output_tokens` | Необов’язково. Менший бюджет виводу, ніж у робочому просторі; ніколи більший |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

Опис `repl` повідомляє агентові: «Інструмента, який не входить до твоїх прямих інструментів, немає у визначеннях цього запиту. Перш ніж уперше викликати такий інструмент, знайди його через `describeTool(name)` або `searchTools(query)`, якщо його точна форма виклику вже не була показана тобі в цій розмові.»

`describeTool(name)` повертає опис інструмента, його оголошення, схеми вхідних і вихідних даних і примітку до результату, якщо вона є: те, що скрипт отримує від завершеного виклику, власними словами інструмента. В описі `repl` перелічено примітки прямих інструментів, які скрипт може викликати. Результат інструмента, який є текстом JSON, надходить уже розібраним, якщо тільки він не містить більше 131 072 значень; тоді він надходить як текст, і скрипт розбирає його сам через `JSON.parse`. Текст результату інструмента зовнішнього сервера MCP обрізається на 262 144 символах, і обрізаний текст більше не розбирається.

- `tools.<name>(args)` викликає інструмент через той самий фільтр, обмеження й схвалення, що й прямий виклик, і відхиляється з помилкою, коли виклик відмовлено або він не вдався. Виклики лише для читання можна виконувати разом; виклики, що щось змінюють, виконуються по одному, у тому порядку, в якому їх зробив скрипт. Поки один із його викликів чекає на людину, жоден інший виклик скрипта не починається.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` і `describeNamespace(name)` знаходять інструменти, зокрема інструменти підключених серверів MCP. Інструмент поза прямим набором, який скрипт може викликати, доступний лише зі скрипта; прямий виклик такого інструмента повертає, як викликати його з `repl`. Щойно сервер не може запускати скрипти запуску, такий інструмент натомість завантажується при першому використанні.
- Пошуки обмежено: запит до 1 024 символів, назва або простір імен до 256, `limit` від 0 до 50, і не більше 200 пошуків, що разом займають 2 секунди часу сервера, на кожен скрипт; водночас усі скрипти одного робочого простору ділять 2 секунди часу пошуку, які повертаються зі швидкістю чверть секунди за кожну секунду; після вичерпання будь-якого з обмежень подальші пошуки відхиляються. У дуже великому каталозі описи в `ALL_TOOLS` рівно ділять приблизно мільйон символів, а обрізаний опис закінчується на `…`; `describeTool` завжди повертає повний опис. Тип, занадто великий для показу, має вигляд `unknown /* too large to show */`, а невідома назва отримує відповідь із найближчими назвами.
- Інструменти згруповано в простори імен: `builtin` (власні інструменти harness), `control-center` (інструменти Control Center) і по одному на кожен підключений сервер MCP, названий за сервером. Сервер, названий `builtin`, `control-center` або `script`, або чия назва починається з `external-`, у будь-якому поєднанні великих і малих літер і з пробілами навколо чи без них, відображається як `external-`, за яким іде його назва, і жоден інструмент ніколи не належить до `script`.
- Повертається лише те, що скрипт повертає або передає в `text()`, `image()` чи `console.*`. Вивід за межами бюджету зберігає початок і кінець, а решту можна прочитати через `read_output`.
- `store(key, value)` / `load(key)` зберігають значення JSON для пізніших скриптів тієї самої розмови й агента, записуючи їх лише тоді, коли скрипт завершується. Скрипти субагента не мають сховища.
- `await tools.ask_user(...)` ставить запитання; його відповідь також додається до результату. `sleep(ms)`, `setTimeout`, `limits()` і `models.embed` / `rank` / `classify` (ембединги на пристрої) теж доступні.
- `describeTool(name)` і `searchTools(query)` також відповідають для власних функцій скрипта, які не є інструментами: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` і `models.*`, у просторі імен `script`.
- Не можна викликати зі скрипта: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` і дієслова `vibe_*`.
- Скрипт читає минуле власного запуску: `history({start, role, tool, limit})` гортає транскрипт розмови (не більше 50 рядків за виклик; передайте `next_start` попередньої сторінки як `start`), `outputs()` перелічує виходи інструментів, збережені для цієї розмови й агента, а `loadOutput(handle)` читає 16 384 символи одного з них. `storedKeys()` перелічує збережені ключі з їхніми розмірами. `keep(value, label)` зберігає велике значення як вихід, який пізніший скрипт або `read_output` зможе прочитати; зберігається лише тоді, коли скрипт завершився (1 МіБ на значення, 64 значення і 16 МіБ за запуск). `limits().returnBudgetChars` показує, скільки лишилося з бюджету виходу. Запуск лише для читання (рев’ю цілі) може читати, але не може ні зберігати, ні keep. На Claude Code й ACP `history()` працює, а `outputs()`, `loadOutput()` і `keep()` відмовляють, бо Control Center не зберігає виходів інструментів цих запусків.
- Помилка через тайм-аут, переповнення виходу або ліміт викликів пояснює, як її виправити.

Один запуск виконує один скрипт за раз. Ліміти та те, що відбувається з кожним із них, описано на сторінці [режиму коду](/uk-UA/керівництво/поняття/режим-коду/#ліміти); кожен скрипт записується в **Спостережуваність → Виконання коду**.

## `eval` — постійні інтерпретатори

Комірка Python або JavaScript, чиї змінні, імпорти та завантажені дані зберігаються між викликами. Рівень `exec`; не безпечний для паралелі. Її не можна викликати зі скрипта `repl`, а комірка не може викликати інструменти запуску: щоб викликати інструменти з коду, скористайтеся [`repl`](#repl--запуск-скрипта-що-викликає-ваші-інструменти).

| Аргумент      | Значення                                       |
| ------------- | ---------------------------------------------- |
| `code`        | Комірка                                        |
| `description` | Обов’язковий. 5–10 слів для мітки в транскрипті |
| `language`    | `python` (типово) або `javascript`             |
| `reset`       | Відкинути інтерпретатор і спершу почати чисто  |

- Останній вираз повертається так, як це робить блокнот.
- `display()` працює, фрейм pandas відображається як таблиця, а фігура matplotlib повертається як **зображення, яке показує транскрипт**.
- Ідіоми IPython, які люди набирають рефлекторно — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — переписуються у звичайний код. `%pip` ще й витісняє `sys.modules`, тож наступний `import` бачить те, що щойно встановили.
- Комірка, що друкує більше, ніж її бюджет виходу, зберігає перші три чверті та останню чверть, з одним рядком, що каже, скільки символів і зображень відкинуто.
- Якщо інтерпретатор зник без запиту, наступна комірка один раз дізнається, що її попередні змінні зникли.

:::note[Де виконується ядро]
В **ізольованому середовищі** розмови, якщо воно в неї є, інакше — в пісочниці запуску на хості. За вимкненої або недоступної пісочниці воно працює без обмежень, а `eval` запитує схвалення виконання на хості. Воно не завантажує ізольоване середовище, щоб туди дістатися, — те саме правило, яке не дає вкладці rig запускатися автоматично.
:::

## `bash` у фоні

`bash` з `run_in_background: true` запускає команду й одразу повертає дескриптор (`b1`, `b2`, …) замість очікування. Агент продовжує роботу або завершує свій хід, і його пробуджують, коли команда завершиться.

| Аргумент | Значення |
| ------------------- | ------- |
| `run_in_background` | `true`: запустити й одразу повернути керування |
| `timeout_seconds` | Секунди до вбивання команди: за замовчуванням 600, найбільше 3 600 |
| `notify` | Необов’язково. Простий шаблон; кожен рядок виводу, що збігається, надсилається агентові, поки команда виконується (наприклад, `listening on\|FAILED`) |

- Одночасно в одному запуску виконується не більше 4 фонових команд. Кожна вбивається за своїм тайм-аутом і при завершенні запуску разом з усіма процесами, які вона запустила.
- Коли команда завершується, агент отримує сповіщення з кодом виходу, останніми 2 000 символами виводу та дескриптором `read_output` для решти.
- Агент, у якого залишилася лише фонова команда, чекає без виклику моделі, а сторожовий таймер тиші запуску призупиняється, поки він чекає.
- `bash_output(handle)` читає стан команди й останній вивід; `bash_kill(handle)` зупиняє її. Обидва повідомляють, коли результат уже доставлено.
- Скрипт не може запустити фонову команду. Claude Code має власний фоновий Bash; Control Center утримує той запуск відкритим не більше 10 хвилин після ходу, який залишив завдання працювати.

## `compact` — звільнити місце у вікні контексту

Стискає старіший контекст розмови перед наступним викликом моделі, зберігаючи те, що називає `focus` (не більше 1 000 символів). Найновіші ходи лишаються дослівно. Рядок бюджету ходу агента показує використання контексту на 70, 80 і 90%, і інструмент варто викликати після приблизно 70% перед довгою новою фазою роботи. Хук `preCompact` власника сервера може додати до фокуса ([Shell-хуки](/uk-UA/керівництво/довідка/конфігурація-агента/#shell-хуки)). Після стиснення сервер додає блок «Still in flight»: ціль, очікувані пробудження, відкриті запити, фонові команди, чекліст і збережені ключі, кожен із викликом, що його відновлює.

## `ask_user` — поставити людині запитання

Рівень `read`. **Єдиний** спосіб, яким запуск щось питає в оператора. Він показує в розмові пронумеровану картку й блокує, доки хтось не відповість, не пропустить або доки запитання не вичерпає тайм-аут. Ніколи не пишіть запитання як повідомлення в чаті — це завершує хід.

| Аргумент          | Значення                                   |
| ----------------- | ------------------------------------------ |
| `question`        | Що спитати                                 |
| `context`         | Необов’язково: чому ви питаєте і що залежить від відповіді |
| `options[]`       | Варіанти, кожен `{label, description?}`    |
| `allow_free_text` | Чи приймається введена відповідь           |
| `multi_select`    | Чи можна вибрати кілька варіантів          |

Пропуск — це успіх: продовжуйте на заявленому припущенні й не питайте знову. Тайм-аут — це помилка з тією самою інструкцією. Запити на дозвіл («чи можна мені це зробити?») — це окремий шлюз, і вони показуються як така сама картка в розмові.

Реєструється лише тоді, коли існують і порт запитань, і цільовий простір. Без під’єднаної людини виклик **падає**, а не блокується назавжди — та сама позиція відмови за замовчуванням, яку займає `prompt` обмеження, коли не під’єднано жодного того, хто схвалює.

## `vibe_*` — керування фоновими воркерами

Реєструється лише поки увімкнено [режим vibe](/uk-UA/керівництво/практичні-посібники/керувати-фоновими-воркерами/). Усі п’ять мають рівень `read`: шлюз належить інструментам воркера, де власне й відбувається редагування.

| Інструмент   | Аргументи                       | Примітки                                       |
| ------------ | ------------------------------- | ---------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`       | Повертає керування негайно; воркер працює далі |
| `vibe_send`  | `worker_id`, `message`          | Дописує до брифу й перезапускає                |
| `vibe_wait`  | `worker_id`, `timeout_seconds?` | Блокує, доки він не завершиться                |
| `vibe_kill`  | `worker_id`                     | Зупиняє його                                   |
| `vibe_list`  | —                               | Рівень, статус, витрачений час і останній результат |

`tier` — це `fast` (механічна робота з чіткою специфікацією) або `good` (проєктування, судження чи перевірка того, що створив `fast`-воркер).
