Кожен параметр процесу задається або прапорцем CLI, або змінною середовища; пріоритет
має прапорець, далі змінна середовища, далі типове значення. Виняток — облікові дані
провайдерів: див. [Застосунки провайдерів і Connect](#застосунки-провайдерів-і-connect).

:::caution[Невідомі прапорці ігноруються мовчки]
Синтаксичний аналізатор аргументів написано вручну, і він пропускає все, що не розпізнає, тож одрук (`--tls-key-file`, `--bindany`) не дає помилки — сервер просто запускається зі значенням за замовчуванням. Перевіряйте рядки журналу запуску, коли прапорець, здається, не діє. [Прапорець режиму коду](#режим-коду) зі значенням, якого він не приймає, — інший випадок: сервер відмовляється запускатися.
:::

## Застосунки провайдерів і Connect

Жодна збірка не містить облікових даних провайдерів. З увімкненим Control Center Connect з усіма провайдерами працює Connect, а власні застосунки сервера лишаються збереженими, але невикористаними. За **Використовувати власні застосунки** кожен провайдер працює на власному застосунку сервера, якщо той повністю налаштований, інакше недоступний. Застосунок робочого простору перемагає в обох випадках. Власні застосунки
задаються в **Налаштування → Сервер → Єдиний вхід → Застосунки провайдера** або
одноразово заповнюються з файлу `.env` сервера. Прапорців для них немає: секрет
у командному рядку можна прочитати через `ps`.

| Змінна                         | Значення                                                                                      |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| `GITHUB_APP_ID`                | Id GitHub App сервера                                                                         |
| `GITHUB_APP_PRIVATE_KEY`       | Його приватний ключ, одним рядком з екрануванням `\n`. **Лише `.env`**                       |
| `GITHUB_CLIENT_ID`             | Його id клієнта, для входу людей                                                              |
| `GITHUB_CLIENT_SECRET`         | Його секрет клієнта. **Лише `.env`**                                                          |
| `GOOGLE_OAUTH_CLIENT_ID`       | Клієнт Google сервера типу «Вебзастосунок»                                                    |
| `GOOGLE_OAUTH_CLIENT_SECRET`   | Його секрет. **Лише `.env`**                                                                  |
| `LINEAR_CLIENT_ID`             | Застосунок Linear сервера (PKCE, без секрету)                                                 |
| `LINEAR_API_KEY`               | Сервісний ключ Linear для автоматизації. **Лише `.env`**                                      |
| `KLIPY_APP_KEY`                | Власний ключ Klipy сервера для пошуку GIF, використовується лише за **Використовувати власні застосунки**       |
| `CC_CONNECT_URL`               | `hosted`, `off` або URL Connect. Фіксує вибір Connect; Налаштування тоді не можуть його змінити |
| `CC_SERVER_CONNECT_HOST`       | `on` монтує Control Center Connect за адресою `<server>/connect`, що налаштовується змінними `CONNECT_*`. Див. [Запустити сервер Connect](/uk-UA/керівництво/практичні-посібники/запустити-сервер-connect/#змонтувати-connect-усередині-cc_server) |

Файл `.env` читається з робочого каталогу сервера, поряд із виконуваним файлом або
з копії вихідного коду вище нього; у Docker змонтуйте його в `/app/bin/.env`.
Сервер **відмовляється запускатися** (код виходу `78`), коли
`GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_SECRET`,
`LINEAR_API_KEY` або будь-який `SLACK_*SECRET*` експортовано в середовище його
процесу, де його міг би прочитати будь-який дочірній процес. Заповнення з `.env`
відбувається один раз для кожного поля, тож пізніша зміна в Налаштуваннях не
скасовується перезапуском. Порожнє значення читається як не задане.

Жоден облікові дані хоста коду не надходять із середовища: GitHub, GitLab і Bitbucket
працюють від імені входу або токена самого учасника, або від токенів GitHub App для
одного репозиторію, обмежених цим учасником.

### `--sandbox`

Сервер зондує хост один раз під час запуску й загортає виконання команд агента в
рідну для ОС пісочницю, коли доступний бекенд: `sandbox-exec` (Seatbelt) на macOS,
`bwrap` разом із `socat` у Linux і WSL2. Рішення ухвалюється один раз і діє до перезапуску сервера. Є три результати, кожен з яких показано в рядку exposure під час запуску:

| `sandbox=`    | Коли                                                                            | Чиї запуски агентів стартують                                                                                                  |
| ------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `native`      | Бекенд доступний і `--sandbox` має `on`                                         | Усіх, загорнуті                                                                                                                |
| `off`         | `--sandbox off`                                                                 | Усіх, без обмежень на цьому хості                                                                                              |
| `unavailable` | `--sandbox on` і бекенда немає (Windows або Linux без `bwrap` і `socat`)        | Лише запуски, за які відповідає власник сервера, без обмежень. Решту відхиляють з повідомленням «На цьому сервері немає пісочниці, тож тут агенти можуть запускатися лише власником.» |

Для автоматизації відповідальна особа — та, до якої прив’язано автоматизацію. Якщо власника сервера не записано, жоден запуск не стартує на хості зі станом `unavailable`. У Linux і WSL2 з встановленим bubblewrap нативна диспетчеризація наразі завершується з відмовою для кожного запуску; див. [Бекенди пісочниці](/uk-UA/керівництво/довідка/бекенди-пісочниці/#linux-bubblewrap).

`--sandbox off` — це вибір власника сервера для всіх, хто ним користується: він запускає агентів кожного учасника без обмежень на цій машині. Використовуйте його на хості, де сама поведінка профілю пісочниці збоїть, або щоб дозволити учасникам запускати агентів на хості без бекенда. Він не потребує перезбірки, а сервер пише попередження протягом усього часу роботи процесу, тож цей стан ніколи не лишається непоміченим.

### `--tool-deferral`

Запуски вбудованого harness надсилають невеликий прямий набір визначень інструментів плюс індекс лише назв решти, які завантажують свої схеми при першому використанні або викликаються зі скрипта `repl`. Це тримає постійно видимий набір у межах, де моделі надійно обирають інструменти. Виміряно на реєстрі, який збирають тести, стандартні інструменти чату вбудованого агента становлять 14 визначень: близько 16,5 КБ із `repl` (близько 4 КБ з них — визначення `repl`, яке не може перевищувати 4 096 байтів), близько 13 КБ на сервері, який не може запускати скрипти. Відкладені інструменти й далі можна викликати за назвою, а `search_tools` знаходить їх за наміром. Див. [Контекст інструментів і кеш промптів](/uk-UA/керівництво/поняття/контекст-інструментів/).

`--tool-deferral off` надсилає визначення кожного допущеного інструмента наперед, за винятком того, що запуск із `repl` і далі викликає зі скриптів ті інструменти, які скрипт може викликати. Це аварійний вимикач для моделі, яка погано поводиться з дворівневою поверхнею, — прапорець, а не перезбірка. Він впливає лише на вбудований harness; поверхня MCP `tools/list`, яку бачать зовнішні клієнти, містить повний каталог, окрім запусків агента на сервері, що може запускати [скрипти режиму коду](/uk-UA/керівництво/поняття/режим-коду/).

### `--credential-gate`

Запуск, у якого облікові дані провайдера відсутні або вичерпані, **припарковують**, а
не провалюють: оператор отримує запит виправити їх, і запуск відновлюється, якщо він це
зробить. Типовий граничний термін — 900 секунд (15 хвилин), обмежений діапазоном 0–3600.

Цей термін навмисно значно довший за термін запиту на схвалення: схвалення — це
рішення, яке людина ухвалює за секунди, а виправлення облікових даних означає відкрити
термінал, увійти й повернутися. Саме стеля не дає запуску без нагляду — кроку конвеєра,
тригера cron, вебхука — чекати на когось, хто спить. Коли термін спливає, запуск падає
з тим самим повідомленням, з яким упав би й так.

`--credential-gate=0` — це аварійний вимикач: нічого ніколи не паркують, і погані
облікові дані завершують хід точно так, як це було до появи цієї брами.

### Режим коду

[Режим коду](/uk-UA/керівництво/поняття/режим-коду/) дозволяє агентові запускати скрипт JavaScript, що викликає його інструменти. Немає прапорця, який його вмикає чи вимикає: кожен запуск отримує інструмент `repl`, коли сервер може запускати скрипти, а публічний демо-сервер не запускає жодного.

Скрипти виконуються в `cc_codemode`, програмі, що постачається з сервером у `bin/codemode/`. Без неї сервер не запускається: він виводить один рядок із назвою того, чого бракує, і завершується з кодом `78`. Під час запуску він виконує самоперевірку обмежень програми й виводить один рядок (придушується лише через `--log-level error`):

```text
cc_server: code_mode=available (cc_codemode 0.1.0 quickjs-ng 0.16.2 protocol 2; 16 scripts at once, at most 12 per workspace; up to 64 more runners kept for scripts waiting on a person; heap at most 1024 MiB per script)
cc_server: code_mode=unavailable (<reason>) — runs on this host get no repl tool; scripts never run without full lockdown
```

`unavailable` означає, що програма не може обмежити себе на цьому хості, наприклад у контейнері, чий профіль безпеки відхиляє один із її кроків, або якщо це не релізна збірка. Сервер працює звичайно, жоден запуск не отримує `repl`, а сторінка налаштувань режиму коду робочого простору показує причину.

Сервер продовжує перевіряти під час роботи. Коли програма не запускається з причини, що не стосується скрипта, сервер повторно запускає самоперевірку, але не частіше ніж раз на хвилину. Якщо вона не проходить, сервер виводить рядок `unavailable` із причиною і не запускає скриптів: запуски, які стартують тим часом, не отримують `repl`, а запуск, який його вже має, викликає свої інструменти напряму ([Коли скрипти не можуть працювати](/uk-UA/керівництво/поняття/режим-коду/#коли-скрипти-не-можуть-працювати)). Він продовжує перевіряти, не частіше ніж раз на хвилину, і коли самоперевірка знову проходить, виводить рядок `available` і знову запускає скрипти. Лише самоперевірка, яка не пройшла на старті, потребує перезапуску. Причина, яку показують налаштування робочого простору, має вилучені шляхи хоста; рядок журналу містить її повністю.

Два прапорці режиму коду обмежують, що можуть використовувати скрипти. `--code-mode-max-processes` обмежує скрипти, що одночасно виконуються в усіх робочих просторах (типово удвічі більше за кількість ядер процесора, але не більше 16; приймаються значення від 1 до 64). Якщо обмеження становить 2 або більше, один робочий простір використовує не більше ніж обмеження мінус його чверть, тож жоден робочий простір не може зайняти всі місця, а скрипти, що чекають, допускаються по черзі між робочими просторами. Скрипт, що чекає на схвалення або відповідь людини, поступається місцем іншому скрипту і не починає жодного виклику інструмента, доки на нього не відповіли; можна зберігати до чотирьох разів більше таких скриптів, що чекають, ніж саме обмеження, причому не більше трьох чвертей їх — від одного робочого простору, і кожен може далі обчислювати в межах власного ліміту часу процесора. `--code-mode-max-heap-mb` — це найбільший обсяг пам’яті, який може використати один скрипт.

Значення, яких ці прапорці не приймають (число поза діапазоном або не число), зупиняють сервер під час запуску (код виходу `78`) з повідомленням, яке називає прийнятні значення. Таке значення ніколи не сприймається як типове.

## Підкоманди

| Команда                                       | Що робить                                                                                           |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `cc_server`                                   | Запускає сервер до `SIGINT`/`SIGTERM`                                                               |
| `cc_server pair`                              | Створює пристрій і друкує його ідентифікатор і ключ спарювання. Безпечно щодо каталогу даних, який сервер уже обслуговує — запущений сервер підхоплює пристрій без перезапуску |
| `cc_server connect <command>`                 | Показує або змінює, який Control Center Connect використовує цей сервер, не запускаючи його      |
| `cc_server update`                            | Перевіряє наявність, завантажує й перевіряє новіший автономний випуск                                |
| `cc_server --version`                         | Друкує версію збірки та git SHA — той самий ідентифікатор, який оголошують `/healthz` і рукостискання RPC |

### `pair`

| Прапорець      | Типово                                                    | Значення                                                                                                                                                             |
| -------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device`     | `web-client`                                              | Ідентифікатор пристрою. Платформа виводиться з нього, тож `--device desktop` створює рядок десктопа, а `--device ios`/`android` — рядок телефона; будь-що інше вважається вебклієнтом |
| `--label`      | назва платформи плюс ім’я хоста цієї машини                | Показувана назва у списку пристроїв                                                                                                                                  |
| `--host`       | `localhost` або `<this-host>`, коли прив’язка до всіх інтерфейсів | Хост, який вбудовують у надрукований URL. Задайте його як IP-адресу в LAN або хост тунелю, до якого клієнт справді звертатиметься                                     |
| `--client-url` | не задано                                                 | Джерело розміщеного **веб**клієнта. Додає глибоке посилання для сканування та QR-код у терміналі                                                                      |

`pair` також приймає основні прапорці `--data-dir`, `--port` і `--bind`: вони вибирають
каталог даних для запису та формують надрукований URL сервера (`ws` на loopback, `wss`
при `--bind any`). Повторний запуск `pair` для того самого `--device` оновлює його ключ
і розриває активні сесії цього пристрою. Створені тут облікові дані **не мають терміну
дії**, на відміну від 30 днів, які задає спарювання в застосунку.

:::caution[QR-код `--client-url` — не телефонний QR]
`pair --client-url` заповнює форму підключення **веб**клієнта (URL сервера,
ідентифікатор пристрою та ключ у фрагменті URL). Телефон спарюється з іншим
навантаженням, яке створюють у панелі спарювання в застосунку, — повний дескриптор
з’єднання із сервером плюс термін дії. Ці два не взаємозамінні — див.
[Прив’язати пристрій](/uk-UA/керівництво/практичні-посібники/сполучити-пристрій/).
:::

### `connect`

Читає й записує ті самі налаштування, що й картка **Control Center Connect** у
**Налаштування → Сервер → Єдиний вхід**, прямо з каталогу даних. Запущений сервер
підхоплює зміну протягом 10 хвилин або під час перезапуску.

| Команда                         | Що робить                                                                                                        |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `cc_server connect status`      | Друкує режим, URL, чи фіксує його `CC_CONNECT_URL`, ідентифікатор встановлення, стан і джерело кожного каналу (`own`, `connect` або `off`) |
| `cc_server connect enable`      | Використовує розміщений Connect від Control Center                                                               |
| `cc_server connect enable --url <url>` | Використовує власний Connect за цим URL (HTTPS або `http` на loopback)                                  |
| `cc_server connect disable`     | Припиняє використовувати Connect. Вхід людей виконують лише власні застосунки сервера                             |

Без команди типово виконується `status`. Кожна команда приймає `--data-dir`.
`CC_CONNECT_URL` перевизначає все, що вони зберігають. Невідома команда
завершується з кодом `64`. Режими, ідентичність встановлення й коди стану описано
в [Control Center Connect](/uk-UA/керівництво/довідка/connect/).

### `update`

`--apply` замінює інсталяцію; його відхиляють, поки сервер усе ще відповідає на
налаштованому порту, якщо ви не передасте `--force`. `--allow-downgrade` дозволяє
старіший випуск.

Для інсталяцій, якими вона не володіє, команда відмовляється одразу — з поясненням,
а не помилкою:

| Середовище                    | Виявляється за                              | Що вона каже                                                |
| ----------------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| Вбудований сервер настільного застосунку | `CC_EMBEDDED=1` або `CC_BOOTSTRAP_DEVICE_ID` | Натомість оновіть застосунок — інсталятор замінює все дерево |
| Checkout джерел для `dart run` | шлях скрипту закінчується на `.dart`        | Оновіть його через git                                      |
| Docker                        | маркери контейнера                          | Завантажте новіший образ                                    |

## Життєвий цикл процесу

`cc_server` працює до `SIGINT` / `SIGTERM`. Цим керує ще одна змінна середовища, і її
задає настільний застосунок, а не ви:

| Змінна                   | Вплив                                                                                                                                      |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `CC_EXIT_WITH_PARENT=1`  | Сервер завершується, коли завершується його батьківський процес; це визначають за тим, що батько закриває кінець запису власного каналу stdin. Настільний застосунок задає її, щоб застосунок, який упав, ніколи не залишив осиротілого сервера, що тримає каталог даних |

Задавайте її самостійно, лише якщо ви наглядаєте за `cc_server` як за дочірнім
процесом і хочете такої самої гарантії.

`DO_NOT_TRACK=1` (будь-яке значення, крім порожнього, `0` або `false`) вимикає власну
[статистику використання](/uk-UA/керівництво/довідка/статистика-використання/) сервера, навіть коли загальносерверний перемикач
увімкнено. Клієнти й далі дотримуються перемикача.

## Структура каталогу даних

Типовий каталог даних — `~/Library/Application Support/control-center` на macOS,
`%APPDATA%\control-center` у Windows і `$XDG_DATA_HOME/control-center` (інакше
`~/.local/share/control-center`) на решті платформ. Відносний до робочого каталогу
`.cc_server` використовується лише тоді, коли не вдається визначити ні домашній
каталог, ні каталог даних застосунку.

Сервер тримає каталог даних закритим для власного облікового запису (`0700`). Він відмовляється запускатися (код виходу `78`), коли не може цього досягти, коли `global.db` пошкоджено або записано новішою версією чи коли не читається його файл ідентичності.

| Шлях                              | Вміст                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------- |
| `global.db`                       | Реєстр робочих просторів, користувачі, прив’язані пристрої, стрічка новин і черга флоту |
| `<workspaceId>/workspace.db`      | Одна база даних на робочий простір — агенти, простори, тікети, пам’ять |
| `<workspaceId>/code_index.db`     | Граф коду цього робочого простору. Перебудовується, коли відсутній, і ніколи не резервується |
| `pre_upgrade/`, `<workspaceId>/pre_upgrade/` | Дві найновіші копії бази даних до оновлення, яке змінило її формат |
| `<workspaceId>/chat_credentials/` | Токени чат-ботів у звичайному JSON, тож вони живуть разом із робочим простором   |
| `secrets.json`                    | Ключі спарювання, ключ встановлення Connect, застосунки провайдерів, входи людей (запечатані, якщо зроблені через Connect), секрети вебхуків, SSO (`0600`) |
| `backups/<timestamp>/`            | Один знімок інсталяції — `manifest.json`, `global.db` і копія кожного робочого простору |
| `backups/exports/`                | Експорти окремих робочих просторів, `<workspaceId>-<timestamp>.db`               |
| `backups/transfer/`               | Проміжне сховище для завантажень і вивантажень резервних копій; його прибирає маршрут, що його записує |
| `models/`                         | Моделі ембедингів, діаризації та розпізнавання мовлення на пристрої              |
| `codemode/` | Копія раннера режиму коду для розробки, встановлюється `scripts/natives/build_codemode.sh`; релізні пакети містять його в `bin/codemode/` |
| `meetings/<meetingId>/`           | Збережене аудіо зустрічей                                                       |
| `rigs/images/`                    | Імпортовані дискові образи rig (поверхня десктопа QEMU)                          |
| `rigs/smolvm/<rigId>/`            | Стан виконання microVM для кожного rig (секрет брокера, `0600`)                   |
| `rigs/smolvm-packs/`              | Попередньо розпаковані пакети машин — кеш, який робить повторні завантаження rig швидкими |
| `rigs/tls/`                       | Центр сертифікації dev-домену для HTTPS rig (ключі `0600`)                       |
| `rigs/run/<rigId>/`               | Оверлеї QEMU, seed-образи та ключі для кожної ВМ (`0600`)                        |
