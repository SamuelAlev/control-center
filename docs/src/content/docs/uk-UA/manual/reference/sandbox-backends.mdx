:::caution[Чи потрапляє запуск у пісочницю, залежить від хоста]
`cc_server` один раз під час завантаження вирішує, як агенти запускаються на цьому хості, і це рішення діє до перезапуску:

- **Ізольовано** (`native`): зонд знайшов бекенд, а `--sandbox` не дорівнює `off`. Загорнуто обидва шви диспетчеризації: CLI Claude Code — через порт пісочниці, а ACP разом із вбудованим інструментом `bash` harness — через менеджер пісочниці.
- **Вимкнено** (`off`): власник сервера запустив його з `--sandbox off`. Агенти кожного учасника працюють на цій машині без обмежень, незалежно від того, хто їх запустив.
- **Недоступно** (`unavailable`): пісочницю увімкнено, але зонд не знайшов бекенда (**у Windows це завжди так**, а також Linux або WSL2 без `bwrap` і `socat`). Запуск стартує лише тоді, коли відповідальна за нього особа — [власник](/uk-UA/керівництво/поняття/авторизація/#власник-сервера) сервера: той, хто його попросив, або для автоматизації — особа, з якою її прив’язано. Запуск будь-кого іншого відхиляється ще до випуску облікових даних, взяття оренди чи старту процесу. Якщо власника не записано, жоден запуск не стартує.

Відхилений запуск завершується з кодом `sandbox_unavailable`. Застосунок показує його як **Агентам потрібна пісочниця на цьому сервері**: «На цьому сервері немає пісочниці, тож тут агенти можуть запускатися лише власником. Власник може встановити пісочницю або вимкнути її для всіх.»

Запуск, який стартує без пісочниці (за `off` або власний запуск власника за `unavailable`), виконується безпосередньо на хості. ACP та інструмент `bash` harness усе одно запускаються з очищеним середовищем; Claude Code проходить через `NoSandboxAdapter` і успадковує середовище хоста. Решта меж — це власний worktree запуску (copy-on-write там, де постачається `rift`; `git worktree` у Windows), токен хостингу коду лише для читання, який брокер видає на кожен запуск і відкликає під час згортання, push, якому треба пройти правило push у шлюзі запусків агентів, політика команд для кожного режиму, уніфіковані [обмеження дій](/uk-UA/керівництво/поняття/обмеження/) (fail-closed), очищення середовища на шляхах ACP та `bash` harness і поверхня інструментів, яку дозволяє режим.

Внутрішньопроцесні файлові інструменти harness (read, write, edit, apply patch, search, find, search_files) перебувають поза пісочницею на кожному хості: вони виконуються в процесі сервера, тож загортається лише `bash`.

Хост ніколи не є запасним варіантом для сервера з пісочницею. Якщо сервер ізолює агентів, але не має пісочниці, яку можна дати запуску, його процеси інструментів і команди `bash` відхиляються, а не стартують на хості. Та сама політика визначає дрібні процеси навколо запуску: одноразові допоміжні процеси ACP (назви розмов, `/btw`, `/handoff`, `/goal`) і golden-тести PR у Review Studio виконуються в пісочниці, коли сервер ізолює агентів, без обмежень за `off`, а за `unavailable` — лише для запиту, за який відповідає власник сервера; інакше їх пропущено.

## Огляд бекендів

| Бекенд        | Значення  | Платформа                                     | Доступність                                                                                                                                                                        |
| ------------- | --------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ізольована ВМ | `microvm` | macOS, Linux, Windows (гіпервізор мікроВМ)    | Доступний лише після зондування середовища виконання мікроВМ; застосовується до інтерактивних терміналів — шел виконується всередині [rig](/uk-UA/керівництво/поняття/rigs/), а не на хості |
| Нативний      | `native`  | macOS (Seatbelt), Linux і WSL2 (bubblewrap)   | Зондується під час завантаження; Linux відмовляє в запуску, який вимагає заборон запису за глобом імені файлу, яких bubblewrap не може забезпечити                              |
| Немає         | `none`    | Усі                                           | Типове значення розбору та типове значення термінала; диспетчеризація агентів використовує його за `--sandbox off`, а також для власних запусків власника, коли жоден бекенд недоступний                                                   |

`SandboxBackend.fromName` повертає `none` для null або нерозпізнаного збереженого значення.

**`microvm` — єдиний бекенд із межею ядра** — робоче навантаження
справді не виконується на хості. Він ніколи не буває тихим запасним варіантом у
жодному напрямку: явний запит на нього на хості, який не може завантажити ВМ,
гучно зривається («я просив ВМ, а отримав ноутбук» — це єдина деградація, яку
оболонка не може собі дозволити), і лише *незазначене типове значення*
знижується до `native`, про що є рядок у журналі. Фактичний бекенд сесії
повертається клієнту й позначається бейджем, тож термінал ніколи не може
стверджувати, що він ізольований, виконуючись на хості. Життєвий цикл, образи й
вихідний трафік самої ВМ описано в [довідці про rigs](/uk-UA/керівництво/довідка/rigs/).

**У Windows нативної пісочниці немає.** `NativeSandboxAdapter.probe` повертає `available: false` на кожному хості, який не є macOS або Linux/WSL2, тож сервер у Windows має стан `unavailable`: стартують лише запуски агентів власника сервера, без обмежень, а решта відхиляються. Щоб дозволити кожному учаснику запускати там агентів, власник запускає сервер з `--sandbox off`, що виконує всіх без обмежень. Бекенд `microvm` — окремий: він доступний лише після зондування середовища виконання мікроВМ і застосовується до інтерактивних терміналів і rigs, а не до загортання `bash` на хості.

## Результати зондування

Саме зонд визначає, чи буде примус. Він виконується один раз, під час завантаження сервера.

| Хост                                    | `available` | Примітка / підказка                                                        |
| --------------------------------------- | ----------- | -------------------------------------------------------------------------- |
| macOS                                   | `true`      | `sandbox-exec` (Seatbelt) — ізоляція просторів імен, без межі ядра          |
| Linux або WSL2 з `bwrap` і `socat`      | `true`      | bubblewrap — ізоляція просторів імен, без межі ядра                        |
| Linux або WSL2, де бракує одного з інструментів | `false`     | `requiresInstall: true`, з підказкою щодо встановлення, яка називає відсутні пакети |
| Будь-яка інша платформа                 | `false`     | Нативна пісочниця на цій платформі не пропонується                          |

Сервер записує результат одним рядком під час запуску: `agent sandbox ON` разом із приміткою; `no OS-native agent sandbox on this host` разом із підказкою, яка додає, що стартуватимуть лише запуски, за які відповідає власник сервера; або `agent sandbox DISABLED by --sandbox off`. Рядок про відкритість, надрукований під час запуску, несе те саме рішення як `sandbox=native`, `sandbox=off` або `sandbox=unavailable`. `GET /healthz` не несе поля про пісочницю.

`--sandbox` / `CC_SERVER_SANDBOX` приймає `on` (типово) або `off`. `on` загортає кожен запуск, коли хост пропонує бекенд, і допускає лише запуски власника, коли не пропонує. `off` виконує агентів кожного учасника без обмежень на цьому хості; це вибір власника для всіх, а не налаштування окремого запуску.

## Нативний бекенд

### macOS: Seatbelt

Використовує механізм пісочниці Seatbelt від Apple (ту саму систему, яку застосовує macOS App Sandbox).

Згенерований профіль **типово дозвільний** (`(allow default)`) і вирізає заборони, бо цілком заборонний за замовчуванням профіль робить інтерактивний шел непридатним — викликів dyld, XPC і Mach забагато, щоб їх перелічити. Практичний наслідок: агент усе ще може читати більшість хоста; ваші зареєстровані робочі копії захищені явними заборонами запису й перейменування, а не невидимістю.

- **Читання файлової системи**: заборонено для шляхів із секретами (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` і решти набору заборон на читання)
- **Запис у файлову систему**: скидається до заборони, далі явні дозволи для підшляхів, а обов’язково заборонені шляхи (файли rc шела, `.git/hooks`, конфігурація Claude, захищені робочі копії) заблоковано навіть усередині кореня з правом запису. `file-write-unlink` заборонено на кожному забороненому шляху та його предках, тож перейменування не може обійти заборону запису
- **Процеси**: заборони `process-exec` для завжди небезпечних бінарників, плюс блокування виконання будь-чого з каталогу з правом запису. Відомі дерева встановлення інструментів у вашому домашньому каталозі (кеші corepack, npx і `pnpm dlx`, менеджери версій node, браузери Playwright, rustup і cargo, Go, fvm і кеш pub, pyenv, uv і pipx, rbenv, sdkman, mise, asdf та `~/.local/bin`) знову відкриваються під цим блокуванням. Спільні тимчасові каталоги також заблоковано. Натомість кожна сесія отримує приватний `TMPDIR` у `/private/tmp`, де можуть запускатися програми, які вона зібрала (бінарник `go test`, збірка cargo). Заборони для завжди небезпечних бінарників застосовуються після цих дозволів
- **Мережа**: обмежена портами проксі в процесі плюс DNS — loopback не дозволено цілком, а прослуховування TCP заборонено. Unix-сокети дозволені лише всередині приватного `TMPDIR` сесії; це охоплює інструменти на кшталт tsx і Chrome, які зберігають там IPC-сокет. Ваш SSH-агент та інші сокети залишаються недоступними. Проксі забезпечують список дозволених доменів для кожної сесії (див. [Вихідний трафік](#вихідний-трафік))
- **Конфігурація**: профілі генеруються на кожен запуск із `SandboxSpec`
- **Команди самого сервера**: жодна пряма дочірня папка тих, з яких сервер запускає програми (кожен запис `PATH` і типові папки інструментів користувача на кшталт `~/.local/bin`, з розв’язаними посиланнями менеджерів версій, як-от `~/fvm/default`), не може бути створена, замінена, видалена чи перейменована, як і встановлений пакет, на який указує пов’язана команда. Див. [Папки команд сервера](#папки-команд-сервера)
- **Файли запуску**: кожен домашній шлях, читання якого профіль забороняє, також заборонено для запису, а файли запуску оболонок і сеансів користувача сервера (`.zshenv`, `.zlogin`, `.bash_login`, конфігурація fish, користувацькі юніти systemd, записи автозапуску тощо) заборонені для запису в кожному режимі

Вимоги:

- `sandbox-exec` (`/usr/bin/sandbox-exec`), частина кожного встановлення macOS — додаткові інструменти не потрібні

### Linux: bubblewrap

Використовує bubblewrap (`bwrap`) для створення просторів імен монтування та PID.

- **Файлова система**: створює простір імен монтування, у якому видно лише змонтовані шляхи
- **Мережа**: працює в неспільному просторі імен мережі; трафік досягає проксі хоста через Unix-сокетні мости `socat`
- **Процеси**: ізоляція простору імен PID
- **Команди сервера та файли запуску**: ті самі захисти, що й у macOS, виражені як прив’язки bubblewrap. Їх ще не перевірено в Linux, і відсутня папка команд там ще може бути створена

Вимоги:

- Встановлені `bubblewrap` і `socat` (`sudo apt-get install bubblewrap socat` у Debian/Ubuntu)
- Підтримка просторів імен ядра (стандартна в сучасному Linux)

Bubblewrap може затіняти наявний шлях, але не може заборонити *новий* файл
`.env`, `*.key` чи `*.pem` усередині придатного для запису bind. Стандартна
політика диспетчеризації вимагає цих заборон за глобом імені файлу, тож нативна
диспетчеризація агентів наразі **зривається із забороною за замовчуванням на
Linux/WSL2, навіть коли зонд знаходить bubblewrap**. Вона не виконується з тихо
послабленою політикою. Щоб відновити нативну диспетчеризацію в Linux, потрібен
бекенд із правилами імен файлів на етапі створення. Вимкнення пісочниці — це
явна відмова від обмежень, а не рівноцінний обхідний шлях.

На практиці сервер Linux або WSL2 сьогодні запускає агентів одним із двох способів. Запущений з `--sandbox off`, він виконує агентів кожного учасника без обмежень. Без встановлених bubblewrap або `socat` він має стан `unavailable` і запускає лише агентів власника сервера, без обмежень. Коли обидва інструменти встановлені, а пісочницю увімкнено, кожен запуск відмовляє за замовчуванням, включно із запусками власника.

## Папки команд сервера

Сервер один раз під час запуску знаходить кожну папку, з якої запускає програми: кожен запис свого `PATH`, типові папки інструментів користувача, які він перевіряє (як-от `~/.local/bin`, `~/.bun/bin` і глобальні папки npm, yarn та pnpm), і реальну папку за кожним посиланням на шляху (посилання менеджерів версій на кшталт `~/fvm/default` або типове значення fnm). У пісочниці агент не може додати, замінити, видалити чи перейменувати команду в цих папках, посилання, що веде до неї, або встановлений пакет, на який указує пов’язана команда, і не може перейменувати папки над ними. Інакше запуск у пісочниці міг би підкласти програму, яку сервер або людина згодом запустить поза пісочницею.

Що це змінює для запуску:

- Глобальні встановлення з запуску в пісочниці завершуються з помилкою «Operation not permitted»: `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, а також `cargo install`, `go install` або `dart pub global activate`, коли їхня папка bin є в `PATH` сервера.
- Перемикання типової версії завершується так само (`fnm default`, `nvm alias default`, `fvm global`), як і самооновлення інструмента на місці.
- Встановлення в межах проєкту (`node_modules/.bin`), `npx`, `pnpm dlx`, менеджери пакетів, якими керує corepack, кеші SDK і звичайні збірки продовжують працювати.

Щоб зробити глобальний інструмент доступним агентам, встановіть його на самому сервері, від імені користувача сервера, і перезапустіть сервер, щоб нову команду теж було захищено. Або встановіть його в проєкті. Команда, встановлена після запуску сервера, повністю захищається лише з наступного запуску.

Забезпечено і протестовано в macOS. У Linux ті самі правила є прив’язками bubblewrap, які ще не перевірено. Windows пісочниці не має.

## Бекенд «Немає»

Жодної пісочниці. Процес виконується безпосередньо на хості, з доступом хоста до файлової системи, мережі та процесів. ACP та інструмент `bash` harness усе одно отримують очищення середовища й політику команд; Claude Code через `NoSandboxAdapter` успадковує середовище хоста. Диспетчеризація агентів використовує його для кожного запуску за `--sandbox off`, а на хості без доступного бекенда — лише для власних запусків власника; запуск будь-кого іншого там відхиляється. Для термінала це оболонка хоста, яку може відкрити лише власник сервера.

## Термінал на сервері

Термінал на сервері відкриває оболонку хоста лише для [власника](/uk-UA/керівництво/поняття/авторизація/#власник-сервера) сервера. Усі інші отримують термінал у пісочниці, з обмеженнями агента, у каталогах самого робочого простору.

Так обирається бекенд для сеансу:

| Запитано | Власник сервера | Усі інші |
| --- | --- | --- |
| Нічого | Типовий бекенд сервера | Типовий, де `none` замінено на `native` |
| `none` (оболонка хоста) | Оболонка хоста | Відхиляється: оболонка хоста працює на сервері без пісочниці |
| `native` | Нативна пісочниця, профіль власника | Нативна пісочниця, профіль агента |
| `microvm` | Ізольована ВМ | Ізольована ВМ |
| Невідома назва | Відхиляється | Відхиляється |

- **Профіль власника.** `$HOME` і робочий каталог сеансу доступні для запису, мережа відкрита, а `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` і `~/Library/Keychains` заборонені для читання.
- **Профіль агента** (`memberTerminalSandboxConfig`). Та сама політика, за якою в цьому робочому просторі працює агент: записи лишаються в робочому каталозі, у приватному каталозі запуску, у `/tmp` і в частинах `$HOME`, куди агенту дозволено писати; секрети заборонені для читання; мережа — це дозволений список вихідного трафіку агента; програми запускаються лише з робочого каталогу та встановлених інструментів.
- Термінал відкривається лише всередині власних каталогів робочого простору. Робочий каталог поза ними відхиляється, а не підмінюється іншим.
- Лише особа, яка відкрила термінал, може читати його, вводити в нього, змінювати розмір чи закривати. Для всіх інших його ідентифікатор виглядає невідомим.
- `microvm`, запитаний явно на хості без служби rig, зривається, а не переходить до запасного варіанта. Типове значення `microvm` на такому хості знижується до `native`, і про це повідомляє журнал.

Токен хостингу коду лише для читання та шлюз push до терміналів не застосовуються: це питання диспетчеризації. Якщо загортання не підтримується, сеанс зривається, а не показує бейдж пісочниці на сеансі оболонки хоста.

## Вихідний трафік

Коли пісочниця запускається, вихідний доступ до мережі забезпечують проксі в процесі, а не правила брандмауера ядра. Запуск, який не ізольовано пісочницею (кожен запуск за `--sandbox off` або власний запуск власника на хості без бекенда), не отримує нічого з цього: процес, який він породжує, дістається мережі так само, як користувач сервера.

- Середовище виконання пісочниці запускає проксі HTTP/HTTPS і проксі SOCKS5 на `127.0.0.1` усередині процесу `cc_server`, **по одній парі на кожну обмежену сесію** (`http_proxy.dart`, `socks_proxy.dart`). Паралельні запуски не ділять пару.
- Процеси в пісочниці отримують змінні середовища проксі (`HTTP_PROXY`/`HTTPS_PROXY` → проксі HTTP, `ALL_PROXY` → проксі SOCKS; `GIT_SSH_COMMAND` спрямовує git-over-SSH через проксі SOCKS). У Linux простір імен мережі неспільний, тож проксі — єдиний шлях назовні; у macOS пісочниця ділить loopback хоста й спілкується з ними напряму.
- Цільовий хост кожного з’єднання зіставляється зі списком дозволених доменів сесії; усе інше відхиляється. Дві форми шаблону з рівно одним `*` кожна: на початку `*.example.com` збігається з будь-яким піддоменом (зокрема `a.b.example.com`), але не з самим доменом; у середній мітці `bedrock.*.amazonaws.com` збігається рівно з однією міткою (`bedrock.us-east-1.amazonaws.com`, а не `bedrock.evil.attacker.amazonaws.com`).
- Список дозволених розв’язується для кожної сесії з дбайливо підібраного базового набору (`kBaselineAllowedDomains`: провайдери LLM, хостинг Git, реєстри пакетів), плюс домени GitHub (`kGithubDomains`), плюс `SandboxSpec.egressAllowlist`. Шлях диспетчеризації ніколи не передає додаткових записів `egressAllowlist`, тож на практиці кожен запуск отримує базовий набір плюс GitHub.
- Фіксований список заборонених (`kBaselineDeniedDomains`: кінцеві точки метаданих хмари, стоки телеметрії) має перевагу над усіма дозволами.
- `networkEnabled: false` усе одно запускає проксі для сесії, але список дозволених порожній, тож кожне вихідне з’єднання відхиляється. Диспетчеризація задає це значення під час старту запуску за правилом **Доступ до мережі**: заборона вимикає мережу, дозволити й спочатку запитати залишають її ввімкненою.

## SandboxSpec

Специфікація, яку передають у `SandboxPort.launch`:

| Поле              | Тип                                         | Опис                                                                                                                                                     |
| ----------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | Стабільний ідентифікатор сесії (зазвичай id простору)                                                                                                    |
| `workspaceId`     | `String`                                    | Id робочого простору-власника                                                                                                                           |
| `agentId`         | `String?`                                   | Агент, наразі прив’язаний до пісочниці, якщо є                                                                                                           |
| `bindMounts`      | `List<SandboxBindMount>`                    | Монтування хост→гість; пісочниця бачить лише перелічені тут шляхи хоста                                                                                  |
| `networkEnabled`  | `bool` (типово `true`)                      | Задається під час диспетчеризації за правилом вихідного мережевого трафіку (вимкнено лише тоді, коли воно розв’язується в заборону). Коли вимкнено, проксі для сесії все одно стартують, але список дозволених порожній, тож кожне вихідне з’єднання відхиляється |
| `egressAllowlist` | `List<String>` (типово `[]`)                | Додаткові дозволені домени вихідного трафіку; шаблони підтримуються (`*.example.com`, а також середня форма з однією міткою). Диспетчеризація ніколи це не заповнює, тож загорнутий запуск отримує дбайливо підібраний базовий набір плюс домени GitHub |
| `guestWorkdir`    | `String?`                                   | Типовий робочий каталог усередині пісочниці; окремі виклики `exec` можуть його перевизначити                                                              |
| `mode`            | `Mode` (типово `chat`)                      | Вирізає правила запису у файлову систему: `chat` лишає bind-монтування доступними для запису; `review`, `plan` та `orchestrate` — лише для читання        |
| `protectedPaths`  | `List<String>` (типово `[]`)                | Шляхи хоста, які ніколи не повинні бути доступними для запису всередині пісочниці, в жодному режимі                                                     |
| `runnerStateDirs` | `List<String>` (типово `[]`)                | Каталоги хоста, у яких раннер тримає власний стан, доступні для запису в кожному режимі (нині це керований Control Center `CLAUDE_CONFIG_DIR`)           |
| `execGrantRoots`  | `List<String>` (типово `[]`)                | Схвалені оператором дерева каталогів, які знову відкривають блокування exec для каталогів із правом запису в macOS. Linux їх ігнорує — у bwrap немає блокування exec для `$HOME`, яке можна знову відкрити |

`protectedPaths` містить оригінальні зареєстровані робочі копії репозиторіїв, розв’язані на кожну диспетчеризацію з репозиторіїв робочого простору. Агенти працюють виключно у власних worktree з copy-on-write для кожної розмови, тож оригінали ніколи не повинні бути доступними для запису зсередини пісочниці — інакше в macOS загальний дозвіл Seatbelt на запис у `$HOME` лишав би їх доступними для запису через `bash`. Вони долучаються до набору заборон на запис для секретів у кожному режимі, включно з `chat`.

Кожен шлях заборони читання й заборони запису видається і в буквальному написанні, і в розв’язаному через символьні посилання. Ядро зіставляє правило заборони з розв’язаним шляхом, тож правило, написане проти шляху із символьним посиланням, ніколи не спрацьовує — а в macOS це радше звичайний, ніж екзотичний випадок, адже `/tmp` розв’язується в `/private/tmp`, а `/var/folders/…` — у `/private/var/folders/…`. Записи, що містять `*` або `?`, вважаються глобами й лишаються без змін; шлях, який не розв’язується, зберігається як написано.

## SandboxBindMount

| Поле        | Тип                      | Опис                                                                                                     |

| `guestPath` | `String`                 | Шлях усередині пісочниці (з нативною пісочницею дорівнює `hostPath`; збережено для симетрії адаптерів)   |

## SandboxHandle

Повертає `SandboxPort.launch`:

| Поле        | Тип                    | Опис                                                                     |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | Ідентифікатор сесії                                                      |
| `backend`   | `SandboxBackend`       | Який бекенд виконується                                                  |
| `state`     | `SandboxState`         | Стан життєвого циклу                                                     |
| `error`     | `Object?`              | Встановлюється, коли `state` дорівнює `error`                            |
| `details`   | `Map<String, Object?>` | Внутрішній облік адаптера (робочий каталог, PID, шлях до профілю тощо)   |

### SandboxState

| Стан        | Опис                                         |
| ----------- | -------------------------------------------- |
| `created`   | Специфікацію створено, але ВМ ще не запущено |
| `warm`      | Виконується й готова приймати команди exec   |
| `active`    | Наразі виконує команду                       |
| `suspended` | Призупинено / знято контрольну точку на диск, щоб заощадити RAM |
| `destroyed` | Згорнуто; дескриптор більше не чинний        |
| `error`     | Запуск не вдався — див. `SandboxHandle.error` |
