Pull request — це вже те місце, де точиться розмова про код. Розмови в PR
роблять його такою самою поверхнею робочого простору Control Center, якою
[чат-міст](/uk-UA/керівництво/поняття/чат-мости/) робить Slack: @-згадайте
`@usectrl` в PR, дайте відповідь у його
обговореннях рев’ю або додайте мітку `ai-review` — і робота відбувається в
просторі рев’ю цього PR, під тією самою атрибуцією й тими самими обмеженнями,
що й будь-що набране в застосунку. Коментар і мітка перевіряються однаково: за
учасником, який їх написав або додав. Відповіді повертаються на GitHub — в те
саме обговорення, де прозвучало запитання.

Функцію формують три рішення, і кожне з них — те саме рішення, яке чат-міст
ухвалив для чату, переказане для forge: **у якому напрямку встановлюється
з’єднання**, **що авторизує коментар, який надходить ззовні**, і **кому
приписується кожен бік**.

## Транспорт — це опитування

Єдиний push-канал, який GitHub надає застосунку, — це webhook, а webhook
потребує вхідного URL — саме того, чого ця поверхня свідомо ніколи не вимагає.
Тож виявлення — це прохід: один пошук за аліасом на кожну інсталяцію
застосунку запитує в GitHub PR, які згадують `@usectrl`, і
відкриті PR із міткою рев’ю; у PR, які вже мають простір рев’ю, читаються
обговорення їхніх коментарів, а все порівнюється за id коментаря з тим, що
бачили під час минулого проходу. Власний застосунок проходить щохвилини не
більше ніж 25 PR. Через Connect виклики витрачають власну квоту GitHub
учасників, тож прохід виконується раз на дві хвилини не більше ніж по 10 PR, а
робочий простір, у якого лишилося менше 15 % квоти, пропускається, доки вона не
відновиться. Сам Connect ніколи не бачить вмісту PR.

Наслідки такого рішення варто назвати:

- **Затримка — це інтервал між проходами, а не подія.** Реакція 👀 з’являється
  протягом одного проходу. Нічого термінового на цьому не тримається.
- **Рівно один раз на коментар.** Ідентифікатори коментарів унікальні в межах
  усього GitHub; кожен записується тієї ж миті, коли його визнано придатним, —
  ще до того, як щось почне з ним діяти. Аварійне завершення може втратити
  опрацювання коментаря, але ніколи не запустить його двічі.
- **Час офлайну надолужується, а не відтворюється.** Набір побаченого
  зберігається на диску, тож після перезапуску доставляється все, що надійшло,
  поки сервер не працював. Єдиний виняток — найперший прохід: коли немає пам’яті,
  з чим порівнювати, усе наявне тихо фіксується — оператор, який позначив
  двадцять PR ще до появи цього сервера, не повинен повернутися до двадцяти
  запущених рев’ю.
- **Мітка — це множина, а не подія.** Пошук повідомляє про _наявність_ мітки,
  тож позначений PR запускається один раз — і більше ніколи. Повторне додавання
  мітки після її зняття прохід не помічає; щоб запустити знову, потрібна згадка.

Пошук виконується один раз на кожен обліковий запис інсталяції, клієнтом самого
власника, бо токен бачить лише репозиторії власної інсталяції — єдині
облікові дані на весь сервер непомітно пропустили б кожен PR під іншими
інсталяціями застосунку.

## Авторизує членство, а не коментар

Коментар у PR приходить з автором — неавтентифікованою зовнішньою ідентичністю,
доки її не підтверджено. Сервер зіставляє незмінний числовий id облікового запису
GitHub автора (ніколи не логін, який можна перейменувати й використати повторно)
із входами в GitHub учасників робочого простору; індекс перебудовується за TTL,
бо люди входять і отримують запрошення, поки сервер працює. Для мітки
`ai-review` зіставляється той, хто додав її останнім.

Три перевірки по черзі, і непроходження будь-якої з них відбувається мовчки —
нічого не публікується:

- **Учасник, що ввійшов.** Обліковий запис має належати учаснику _цього_
  робочого простору, який увійшов у GitHub на цьому сервері
- **Роль із правом запису.** `viewer` і `guest` не можуть починати роботу
- **Доступ на push.** Відповіді використовують токен для цього одного
  репозиторію, обмежений доступом цього учасника до нього. Якщо сервер не може
  його випустити, він не продовжує

Усі перевірки виконуються до будь-якого підтвердження, тож стороння людина не
отримує ні реакції, ні відповіді. Коментар ніколи не приписується тому, хто його
не надсилав, і слова сторонньої людини ніколи не потрапляють у робочий простір,
якого вона не бачить.

### Заявка

Останній крок перед будь-якою роботою — реакція 👀, додана власним входом автора
в GitHub. GitHub відповідає `201` на нову реакцію й `200` на вже наявну, тож
реакція працює ще й як блокування: якщо та сама людина ввійшла на двох серверах,
які обидва пов’язали репозиторій, роботу виконує лише той, хто відреагував
першим. Коментар, який бачать кілька робочих просторів на одному сервері,
пропонується кожному, і вирішує та сама заявка.

## Дві ідентичності — навмисно

Кожен бік розмови несе різну ідентичність, і саме ця різниця й є суттю функції:

- **На GitHub відповідь — це автоматизація від вашого імені.** Кожна відповідь
  іде з токеном для цього одного репозиторію, обмеженим доступом учасника,
  який запитав, і її автором є обліковий запис `[bot]` застосунку. Один виняток:
  на спільному застосунку Control Center Connect бот публікує в гілках рев’ю
  лише тоді, коли оператор Connect додав інсталяцію до списку; інакше відповідь
  у гілці рев’ю написана обліковим записом учасника, який запитав. Так чи так кожна відповідь починається з
  `**Control Center** (for @login):`, що повідомляє, хто запитав, і заодно слугує
  захистом від зациклення. @-згадки у словах агента нейтралізуються, тож відповідь
  ніколи не сповіщає користувача чи команду.
- **У просторі запитання — ваше.** Повідомлення приписується тому учаснику, яким
  виявився автор, і запуск агента виконується від його імені: коміти належать цьому
  учаснику, а регулятор автономності простору й обмеження дій
  застосовуються так само, як до повідомлення, набраного в застосунку. Записи у
  forge з цього запуску використовують токени для одного репозиторію, обмежені
  цим учасником, і ніколи — його вхід, переданий цілком.

Публікація знахідок рев’ю назад на GitHub залишається рішенням людини, ухваленим
у Control Center. Згадка може _запустити_ рев’ю; публікує його лише людина.

## Захист від зациклення

Усе, створене обліковим записом бота, відкидається ще до того, як спрацює
будь-який шлюз — і наш власний, і будь-який суфікс `[bot]`, щоб бот рев’ю іншого
застосунку теж не міг розбудити нашого, — а також кожен коментар, що починається
з префікса `**Control Center** (for @`, бо відповідь у гілці рев’ю через Connect
може бути написана обліковим записом людини. Без цього відповіді приходили б як нові коментарі й
запускали б міст знову й знову.

Лише `@usectrl` запускає роботу. Власний логін застосунку (`<slug>[bot]`) і його голий slug нічого не адресують: GitHub не пропонує автодоповнення для облікового запису застосунку, а голий slug може належати людині-користувачеві.

## Що свідомо не пропонується

- **Жодної автопублікації.** Знахідки потрапляють у простір рев’ю; публікація на
  GitHub — окрема дія, яку виконує людина
- **Жодної нечіткої ідентичності.** Автор зіставляється рівно з одним учасником
  або ігнорується — атрибуції за здогадом не існує
- **Жодного автоматичного схвалення.** Автоматизація може коментувати й
  запитувати зміни, але рев’ю `APPROVE` відхиляється ще до надсилання.
  Схвалення — дія людини
- **Жодного webhook GitHub App.** Ця поверхня ніколи його не реєструє, тож
  немає вхідного URL, який треба було б відкривати для коментарів у PR. Інші
  webhooks продукту (конвеєри, синхронізація тікетів) налаштовуються окремо й
  необов’язково.
