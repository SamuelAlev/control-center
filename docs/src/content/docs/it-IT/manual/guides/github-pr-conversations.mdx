Questa guida mostra come lavorare con Control Center senza uscire da GitHub:
richiedi una revisione IA dalla pagina della PR, fai una domanda al bot in un
commento e continua la conversazione nei suoi thread di revisione.

Le risposte passano dal canale GitHub dello spazio di lavoro: la
[GitHub App](/it-IT/manuale/guide/github-app/) del tuo server, oppure l'App
condivisa di Control Center tramite Connect. Non viene registrato nulla di nuovo
e nulla deve essere raggiungibile da internet: il server scopre cosa è stato
detto su GitHub tramite polling, quindi un portatile dietro NAT si comporta
esattamente come un deployment pubblico.

## Prerequisiti

- Lo spazio di lavoro ha un canale GitHub: la GitHub App del server o Connect,
  con l'app [installata](/it-IT/manuale/guide/github-app/#installala-dove-si-trovano-i-tuoi-repository)
  sull'account proprietario del repository. Un'app propria richiede **Pull
  requests** e **Issues** in lettura e scrittura, che **Crea la mia app GitHub**
  concede già
- Il repository è collegato a uno spazio di lavoro in Control Center
- Hai [effettuato l'accesso a GitHub](/it-IT/manuale/guide/integrazione-github/)
  su questo server e puoi eseguire push sul repository
- Nessun URL di webhook, nessun tunnel, nessun callback — non c'è nulla da
  configurare sul lato rete

## Trova il nome del bot

Menziona `@usectrl`, l'account GitHub dedicato a Control Center. È il comando predefinito; il canale GitHub del tuo spazio di lavoro continua a gestire la richiesta e a pubblicare le risposte. Non servono le credenziali dell'account `usectrl`.

Funzionano anche il login dell'app, `<appslug>[bot]`, e la forma breve `@appslug`. Per trovare questo alias facoltativo sulla tua app:

1. Vai su **Impostazioni → Server → Accesso single sign-on** e scorri fino alla
   scheda **App del fornitore**
2. Apri il blocco **GitHub** e fai clic su **Test**
3. Copia **Login del bot** quando viene compilato. Se mostra ancora il
   suggerimento vuoto, il login è sempre `<appslug>[bot]` — digita quello,
   oppure la forma breve `@appslug`

GitHub non mostra gli account delle App nel completamento automatico di `@`, quindi gli alias dell'App vanno digitati o copiati. L'utente dedicato `@usectrl` è la modalità predefinita; sia `@myapp` sia `@myapp[bot]` restano alias accettati per l'App.

:::note[Scegli un nome di app distintivo]
La forma breve viene confrontata come testo. Se un utente GitHub umano ha per
caso lo stesso slug della tua app, menzionare quell'utente con la forma breve
raggiunge comunque il bot. La forma completa `@myapp[bot]` è sempre
inequivocabile.
:::

## Richiedi una revisione da GitHub

Due modi, entrambi avviano la stessa pipeline `pr_review` preconfigurata che
avvia il pulsante **Ask AI**:

- **Aggiungi l'etichetta `ai-review`** alla PR. È la cosa più vicina che GitHub
  offra ad assegnare il bot come revisore — gli account app non possono
  occupare lo slot nativo di revisore richiesto. Il tuo account reagisce alla PR
  con 👀 e la revisione inizia in Control Center; non viene pubblicato alcun
  commento
- **Commenta `@usectrl review`** (oppure solo `@usectrl`) nella conversazione della
  PR. Sul tuo commento compare un 👀, poi una risposta indica che la revisione è
  iniziata (o che una è già in esecuzione)

I revisori lavorano nello spazio di revisione della PR; leggi e pubblica i
rilievi come in [Usa la revisione basata sull'IA](/it-IT/manuale/guide/revisione-ia/).
La pubblicazione di nuovo su GitHub resta una decisione che prendi tu in Control
Center — avviare una revisione da GitHub non pubblica nulla su GitHub da solo.

L'etichetta scatta una volta per PR: aggiungerla è la richiesta, e non viene
riarmata quando la rimuovi e la riaggiungi. Per eseguire di nuovo una revisione
— dopo un push, ad esempio — menziona il bot.

## Fai una domanda

Commenta nella conversazione della PR:

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

Cosa succede, in ordine:

1. Sul tuo commento compare un 👀, dal tuo stesso account, così sai che il
   commento è stato visto
2. La domanda viene pubblicata nello spazio di revisione della PR **a tuo
   nome** — la stessa attribuzione che avresti se l'avessi digitata in Control
   Center
3. Un agente risponde nello spazio e la risposta viene pubblicata di nuovo
   sulla PR. Ogni risposta inizia con `**Control Center** (for @your-login):`

Una domanda su una PR che non ha ancora una revisione risveglia l'agente lead
(CEO) dello spazio di lavoro; dopo che una revisione è stata eseguita, risponde
l'agente che ha parlato per ultimo, quindi i seguiti arrivano a chi ha il
contesto.

## Continua in un thread di revisione

Rispondi all'interno di un thread di revisione inline di cui il bot fa parte —
un commento sul diff che ha lasciato, o una risposta che ha pubblicato in quel
thread. Non serve alcuna menzione; il thread **è** l'indirizzamento:

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

Il multi-turno funziona allo stesso modo: ogni risposta è un'altra domanda
nella stessa conversazione, con lo spazio di revisione come contesto, e la
risposta torna nel thread.

Un seguito sulla timeline della conversazione della PR è un nuovo commento di
primo livello, quindi richiede comunque una @menzione.

## Con chi parla il bot

Il server risolve l'autore di un commento, o chi ha aggiunto l'etichetta
`ai-review`, prima di fare qualsiasi cosa:

- **L'account GitHub deve aver effettuato l'accesso** su questo server. La
  corrispondenza avviene sull'id numerico dell'account GitHub, mai sul login.
  Accedi da **Impostazioni → Spazio di lavoro → Profilo e identità → Hosting del
  codice**
- **Deve essere un membro con un ruolo di scrittura** (`member`, `admin` o
  `owner`) nello spazio di lavoro che collega il repository
- **Deve poter eseguire push** sul repository su GitHub. Le risposte usano un
  token limitato all'accesso di quella persona, quindi chi può solo leggere non
  riceve risposta

Chiunque altro viene ignorato in silenzio: non viene pubblicato nulla e le sue
parole non entrano mai nello spazio di lavoro. I commenti dei bot, e le
risposte di Control Center stesso, non vengono mai trattati come domande.

### Due server, una PR

Il 👀 è anche il modo in cui i server si accordano su chi risponde. Viene
aggiunto con l'accesso dell'autore stesso, e GitHub dice al server se quella
reazione è nuova. Se hai effettuato l'accesso su due server Control Center che
collegano entrambi il repository, risponde il primo che reagisce e l'altro resta
in silenzio. Lo stesso vale per l'etichetta.

## Cosa aspettarsi

| Elemento              | Comportamento                                                            |
| --------------------- | ------------------------------------------------------------------------ |
| Conferma              | 👀 dal tuo account sul commento (o sulla PR, per l'etichetta), entro una scansione |
| Risposte              | Pubblicate nella corsia in cui è stata posta la domanda, a partire da `**Control Center** (for @your-login):`. Con un'app propria l'autore è il bot dell'app; tramite Connect è il tuo account, che agisce tramite l'App condivisa |
| Attribuzione nello spazio | La domanda è tua; l'agente viene eseguito per tuo conto, secondo le impostazioni di autonomia dello spazio |
| Revisioni             | I rilievi arrivano nello spazio di revisione; la pubblicazione su GitHub è manuale |

Una scansione viene eseguita ogni minuto con un'app propria e controlla fino a
25 pull request; tramite Connect viene eseguita ogni due minuti e ne controlla
fino a 10, perché quelle chiamate condividono la quota GitHub di ciascun membro.
Uno spazio di lavoro la cui quota GitHub è sotto il 15% viene saltato finché non
si riprende. La latenza è il prezzo da pagare per non aver bisogno di alcun
accesso di rete in ingresso. Nulla va perso mentre il server è offline — un
commento che arriva durante un'interruzione viene recuperato alla scansione
successiva.

## Risoluzione dei problemi

**Non succede nulla per un commento che menziona il bot.**

- L'app è **installata** sull'account che possiede il repo e il repo è
  **collegato** a uno spazio di lavoro? Un repo non collegato viene ignorato
  prima che qualsiasi cosa venga registrata, quindi collegarlo in seguito lo
  consegna comunque
- Hai effettuato l'accesso a GitHub su questo server, sei un membro con un ruolo
  di scrittura e puoi eseguire push sul repo? Il server ignora chiunque altro
  senza rispondere
- Con l'App condivisa di Control Center, l'installazione dell'organizzazione è
  autorizzata per questo server? Vedi
  [Autorizza questo server per un'organizzazione](/it-IT/manuale/guide/github-app/#autorizza-questo-server-per-unorganizzazione)
- Ancora nulla? Il log del server indica la scansione e la PR quando qualcosa
  fallisce; cerca `pr_conversation:` (il poller) e
  `github_pr_conversation:` (il bridge)

**L'etichetta non avvia una revisione.**

Scatta una volta per PR, e la persona che l'ha aggiunta supera gli stessi
controlli dell'autore di un commento. Se una revisione è già stata eseguita, o
l'etichetta è stata aggiunta prima che il server vedesse mai la PR (la prima
scansione registra l'arretrato in silenzio invece di scatenarlo), menziona il
bot — `@usectrl review` ne avvia sempre una, a meno che una revisione sia già in
corso.

**La risposta del bot non è mai arrivata su GitHub.**

La risposta in sé non va mai persa — è nello spazio di revisione della PR in
Control Center. Un errore di pubblicazione (GitHub non raggiungibile, permessi
cambiati) viene registrato e la risposta non viene ritentata; chiedi di nuovo
nel thread se è importante.
