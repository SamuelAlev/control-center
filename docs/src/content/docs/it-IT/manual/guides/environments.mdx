Un **ambiente** è lo stack in esecuzione di uno spazio: i servizi di cui ha bisogno un branch, isolati da tutti gli altri spazi, visibili nella barra laterale e raggiungibili dagli agenti. Ne ricevono uno anche le pull request, perché una PR ha già il proprio spazio.

Un amministratore dello spazio di lavoro scrive una **definizione** una sola volta. I membri premono poi **Avvia** nella sezione **Ambiente** della barra laterale di uno spazio o di una PR. Le definizioni risiedono nel database dello spazio di lavoro, quindi un branch di funzionalità non cambia mai ciò che Control Center esegue, anche se gli strumenti eseguono comunque il codice di quel branch.

## Creare una definizione

1. Apri **Impostazioni → Spazio di lavoro → Ambienti**. Solo gli amministratori dello spazio di lavoro possono modificare le definizioni.
2. Fai clic su **Nuova definizione**, poi su **Definizione vuota** o **Crea bozza dal repo**. Una bozza cerca nel repo file compose, un `Procfile` e script di `package.json`, e tu controlli il risultato.
3. Compila il modulo oppure usa la scheda **JSON**. Gli esempi in questa pagina sono quel JSON.
4. Fai clic su **Esegui test**. Avvia un ambiente usa e getta, attende che sia pronto e lo distrugge.

Per tenere una definizione in un repo, usa **Collega un file del repo**. Control Center legge il file solo dal branch predefinito ed esegue solo la versione approvata da un amministratore. Una versione più recente mostra **Aggiornamento disponibile** e non cambia nulla finché non viene approvata.

## La definizione più piccola

A un semplice repo compose basta questo:

```jsonc
{
  "contract": 1,
  "name": "Shop",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "components": [ { "kind": "compose", "id": "stack" } ]
}
```

Tutto il resto ha un valore predefinito: il file compose viene individuato, ogni servizio viene eseguito, le porte vengono assegnate, gli endpoint HTTP vengono rilevati e l'ambiente prende il nome dal branch.

## Tipi di componenti

Un ambiente è un elenco ordinato di componenti. Ognuno attende che il precedente sia pronto, a meno che `after` non ne indichi altri, e l'arresto avviene in ordine inverso. `enabledWhen` subordina un componente a un'opzione o a un ruolo, ad esempio `opt.seed`, `!opt.seed` o `repo.web`.

| Tipo | Chi lo esegue | A cosa serve |
| --- | --- | --- |
| `compose` | Il driver compose di Control Center | Qualsiasi file compose, uno per ambiente |
| `cli` | Il tuo strumento. Control Center chiama i verbi mappati e legge JSON | Uno strumento che gestisce ciclo di vita, domini e dati |
| `process` | Control Center, in una sessione di terminale supervisionata | Server di sviluppo e worker |
| `task` | Control Center, una volta per trigger | Installazioni, migrazioni, test |
| `app` | Control Center, quando qualcuno preme **Lancia** | Un'app desktop |

I componenti `task` accettano un elenco `when`:

| Trigger | Quando viene eseguito |
| --- | --- |
| `provision` | Alla creazione del worktree (vedi i task di worktree più avanti) |
| `create` | Una volta per ambiente, e di nuovo dopo un ripristino |
| `start` | A ogni avvio |
| `change` | Dopo una sincronizzazione, se un percorso modificato corrisponde a `onChange` |
| `manual` | Su richiesta: **Esegui**, `cc-env run <id>` o `environment_run_task` |
| `archive` | Subito prima che il worktree venga distrutto |

Un comando dato come array è argv, quindi i valori delle opzioni non passano mai da una shell. Una stringa, o `script` con un array di righe, viene eseguita con `bash -lc`. I segnaposto come `{name}`, `{branch}`, `{stateDir}`, `{repo.<role>}`, `{port.<key>}`, `{opt.<key>}` e `{url.<role>}` vengono espansi solo in argv. I comandi shell leggono gli stessi valori come variabili `CC_ENV_*`, ad esempio `$CC_ENV_PORT_WEB`.

Ogni comando e terminale di spazio riceve anche `CC_ENV_NAME`, `CC_ENV_STATE_DIR`, `CC_ENV_URL`, `CC_SPACE_ID`, `CC_REPO_PATH_<ROLE>` e, negli spazi delle PR, `CC_PR_NUMBER` e `CC_PR_IS_FORK`. Con un componente compose ricevono anche `COMPOSE_PROJECT_NAME` e `COMPOSE_FILE`, così `docker compose exec` in un task raggiunge il progetto giusto.

## Ruoli e directory di lavoro

Una definizione lega dei **ruoli** ai repo dello spazio di lavoro, così uno stack può coprire più repo:

```jsonc
"repos": {
  "api": { "repoId": "<api>", "anchor": true, "required": true },
  "web": { "repoId": "<web>", "anchor": true },
  "e2e": { "repoId": "<e2e>", "whenMissing": "useSource" }
}
```

- `anchor`: uno spazio può avviare l'ambiente se contiene almeno un ruolo àncora. Se due definizioni corrispondono, sceglie chi avvia.
- `required`: lo stack non può funzionare senza questo repo.
- `whenMissing`: cosa succede quando allo spazio manca il ruolo. `addToSpace` aggiunge il repo sul suo branch predefinito ed è il valore predefinito per i ruoli `required`. `useSource` passa il tuo checkout registrato, da trattare in sola lettura. `skip` lascia la variabile non impostata ed è il valore predefinito negli altri casi.
- Per avviare servono un permesso `write` su un repo àncora dello spazio e l'accesso in lettura a tutti gli altri repo legati.

Un comando viene eseguito nel primo ruolo di `repos` presente nello spazio, quindi una definizione con un solo repo non ne parla mai. Qualsiasi componente può cambiarlo con `"cwd": { "role": "e2e", "path": "packages/ui" }`. Entrambi i campi sono facoltativi.

## Porte e URL

Control Center assegna le porte dell'host prima che qualcosa si avvii, da un intervallo unico per tutto l'host (da 42000 a 49999 per impostazione predefinita, in blocchi da 32). Una porta resta la stessa per tutta la vita dell'ambiente, e le porte compose si legano solo a `127.0.0.1`.

- Le porte compose non vanno dichiarate. Leggile come `{port.postgres.5432}` o `CC_ENV_PORT_POSTGRES_5432`.
- Le altre porte si dichiarano dove servono, con `"port": "web"` o `"ports": ["web", "hmr"]`, e si leggono come `{port.web}`. Un processo con una porta riceve anche `PORT` e `HOST=127.0.0.1`.

Gli endpoint HTTP ricevono un URL sul router del server, che ascolta su un'unica porta di loopback:

```text
http://<endpoint>--<name>--<project>.localhost:<router port>
http://web--fix-login--shop.localhost:7355
```

- `<name>` è il branch come slug, oppure `pr-<n>` in uno spazio di PR. `<project>` è `naming.project`, altrimenti il nome della definizione.
- I nomi `*.localhost` si risolvono sul loopback, quindi non richiedono voci hosts né DNS, e il nome host tiene separati i cookie tra gli ambienti.
- Le porte compose che rispondono in HTTP vengono rilevate, e `http` sul componente sostituisce il rilevamento. Un processo ha bisogno di `"endpoint": { "role": "web", "primary": true }`, che rende disponibile anche `{url.web}`.
- Nel browser (VM), usa **Apri in Browser (VM)**. `https://web--fix-login--shop.localhost/` lì raggiunge la stessa rotta.
- L'intera etichetta resta entro 63 caratteri, quindi i nomi lunghi vengono accorciati con un hash.
- Due endpoint non condividono un dominio padre. Un'app che ha bisogno di un cookie su entrambi deve servirli da un unico endpoint.

Per gli URL da registrare in anticipo, come i redirect OAuth, `"naming": { "pool": { "names": "cc{n}", "size": 8 }, "project": "shop" }` fornisce un insieme fisso di nomi.

`policy` decide quando gli ambienti sono in esecuzione. `autoCreate` è `off`, `prSpaces` o `allSpaces`, `idleStopMinutes` vale 240 per impostazione predefinita, `followPrHead` sincronizza l'ambiente di una PR quando la sua head si sposta e `maxRunning` (predefinito 6) fa sì che **Avvia** proponga di fermare l'ambiente usato meno di recente.

## Esempio: app compose

Un'app web e Postgres da un unico file compose, con un `.env` ignorato da git, migrazioni e un task di test. `seedFiles` copia file specifici dal tuo checkout registrato in ogni nuovo worktree.

```jsonc
{
  "contract": 1,
  "name": "Shop",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "naming": { "project": "shop" },
  "seedFiles": [".env"],
  "components": [
    { "kind": "compose", "id": "stack",
      "services": ["postgres", "web"],
      "healthchecks": { "postgres": ["pg_isready", "-U", "postgres"] } },
    { "kind": "task", "id": "migrate", "when": ["create", "change"],
      "onChange": ["db/migrations/**"],
      "command": "docker compose exec -T web bin/migrate" },
    { "kind": "task", "id": "test", "when": ["manual"],
      "command": "docker compose exec -T web bin/test" }
  ]
}
```

`healthchecks` permette a un servizio senza un proprio controllo di integrità di trattenere il componente successivo. Senza, un container in esecuzione conta come pronto e le migrazioni possono anticipare un database ancora in avvio.

## Esempio: CLI personalizzata

Uno strumento immaginario `acme` che gestisce i propri container, domini e TLS. Control Center fornisce `{name}` e ricava tutto il resto da `status`. Non deduce mai i nomi host di uno strumento e non modifica mai `/etc/hosts`.

```jsonc
{
  "contract": 1,
  "name": "Acme",
  "repos": {
    "server": { "repoId": "<server>", "anchor": true, "required": true },
    "web": { "repoId": "<web>", "anchor": true }
  },
  "routing": { "mode": "tool", "domain": "acme.test", "upstream": "127.0.0.1:443",
               "tls": true, "caFile": "~/.acme/tls/ca.crt" },
  "components": [
    { "kind": "cli", "id": "acme",
      "verbs": {
        "create":  ["acme", "env", "create", "{name}", "--json",
                    { "if": "repo.web", "args": ["--web-dir", "{repo.web}"] }],
        "start":   ["acme", "env", "start", "{name}"],
        "stop":    ["acme", "env", "stop", "{name}"],
        "destroy": ["acme", "env", "destroy", "{name}", "--yes"],
        "reset":   ["acme", "env", "reset-db", "{name}"],
        "status":  ["acme", "env", "status", "{name}", "--json"],
        "list":    ["acme", "env", "ls", "--json"],
        "logs":    ["acme", "env", "logs", "{name}",
                    { "if": "service", "args": ["{service}"] },
                    "--tail", "{tail}",
                    { "if": "follow", "args": ["--follow"] }],
        "exec":    ["acme", "env", "exec", "{name}", "{service}", "{command}"]
      },
      "keepsDataOnStop": false,
      "statusMap": {
        "state": [
          { "when": { "path": "/status/ready", "equals": true }, "state": "ready" },
          { "when": { "none": "/status/containers", "where": { "state": "running" } },
            "state": "stopped" },
          { "when": { "path": "/status/phase", "equals": "failed" }, "state": "failed" },
          { "state": "starting" }
        ],
        "detail": "phase: {/status/phase}",
        "warnings": [
          { "when": { "path": "/status/dnsWorking", "equals": false },
            "message": "Not resolvable on this host" }
        ],
        "endpoints": [
          { "role": "app", "label": "App", "url": "/urls/app", "primary": true },
          { "role": "db", "hostPort": "/ports/db" }
        ],
        "services": "/status/containers/*/service",
        "list": "/*/slug",
        "missingErrorCodes": ["env.not-found"]
      } }
  ]
}
```

- `create`, `status` e `destroy` sono obbligatori. Control Center sceglie `create` o `start` in base allo stato che legge. Qualsiasi verbo può essere `{ "shell": "…" }` invece di argv.
- `statusMap` legge il JSON dello strumento con puntatori JSON, dove `*` corrisponde a ogni elemento. Le regole di stato sono ordinate e vince la prima corrispondenza. Una condizione è `path` con `equals`, oppure `any` o `none` con `where`.
- `keepsDataOnStop: false` disattiva l'arresto per inattività e aggiunge un avviso di perdita dati a **Ferma**. Impostalo quando l'arresto perde dati.
- `routing.mode: "tool"` collega i nomi host dello strumento al browser (VM) e agli agenti. Il dominio deve terminare con `.test`, `.localhost` o `.internal`, e un URL segnalato al di fuori viene scartato.

Uno strumento di cui sei autore può fare a meno di `statusMap` e stampare il contratto di stato descritto alla fine di questa pagina.

## Esempio: monorepo pnpm

Solo processi e task, senza container. L'app web trova l'API tramite `{url.api}`.

```jsonc
{
  "contract": 1,
  "name": "Monorepo",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "naming": { "project": "mono" },
  "options": [ { "key": "seed", "type": "bool", "default": true, "agentDefault": false } ],
  "components": [
    { "kind": "task", "id": "install", "when": ["provision", "change"],
      "onChange": ["pnpm-lock.yaml"],
      "command": ["pnpm", "install", "--frozen-lockfile"] },
    { "kind": "process", "id": "api", "label": "API", "port": "api",
      "cwd": { "path": "apps/api" },
      "command": ["pnpm", "dev"],
      "endpoint": { "role": "api" },
      "ready": { "http": "http://127.0.0.1:{port.api}/health", "timeout": 120 },
      "restartOn": ["pnpm-lock.yaml"] },
    { "kind": "task", "id": "seed", "when": ["create"], "enabledWhen": "opt.seed",
      "cwd": { "path": "apps/api" },
      "command": ["pnpm", "db:seed"] },
    { "kind": "process", "id": "web", "label": "Dev server", "port": "web",
      "cwd": { "path": "apps/web" },
      "env": { "API_URL": "{url.api}" },
      "command": ["pnpm", "dev", "--port", "{port.web}", "--host", "127.0.0.1"],
      "endpoint": { "role": "web", "primary": true },
      "ready": { "http": "http://127.0.0.1:{port.web}/" } },
    { "kind": "task", "id": "lint", "when": ["manual"], "command": ["pnpm", "lint"] }
  ]
}
```

- Ogni processo è una scheda di terminale che puoi aprire, leggere e in cui puoi digitare. Chiudere la scheda non lo ferma.
- `ready` accetta `http`, `tcp` o `logMatch`. `restart` è `on-failure` (predefinito), `always` o `never`. `restartOn` riavvia il processo quando un percorso modificato corrisponde.
- `options` diventa un modulo su **Avvia**, e `agentDefault` si applica alle esecuzioni avviate da un agente.

## Esempio: app desktop

Un'app desktop con un passaggio di build. Un'app funziona allo stesso modo con qualsiasi tecnologia, perché Control Center lavora al livello delle finestre del sistema operativo e non ha bisogno di hook o SDK nell'app.

```jsonc
{
  "contract": 1,
  "name": "Studio",
  "repos": { "app": { "repoId": "<id>", "anchor": true, "required": true } },
  "components": [
    { "kind": "task", "id": "build", "when": ["manual"], "command": ["pnpm", "build"] },
    { "kind": "app", "id": "desktop", "label": "Studio", "prepare": "build",
      "command": ["dist/mac-arm64/Studio.app/Contents/MacOS/Studio"],
      "isolate": "home" }
  ]
}
```

Un'app non si avvia con l'ambiente. Qualcuno preme **Lancia** e `prepare` viene eseguito prima. **Ricompila e rilancia** ripete la coppia. Un'uscita pulita appare come chiusa, un crash mostra le ultime righe di log senza riavviare, un riavvio del server non la rilancia mai e l'arresto per inattività lascia stare un'app in esecuzione.

### Autorizzazioni e limiti delle app desktop

- Su macOS, concedi una volta a Control Center **Registrazione schermo** e **Accessibilità** in Impostazioni di Sistema. L'host del server ha bisogno di una sessione grafica: un server headless rifiuta di avviare un'app.
- Avvia direttamente il binario. `open -a` passa l'app a LaunchServices, che la porta fuori dall'albero dei processi seguito da Control Center. `"window": { "match": { "bundleId": "…" } }` copre quel caso, ma è sicuro solo con una copia in esecuzione.
- Le finestre restano su uno schermo. macOS non cattura una finestra parcheggiata fuori da ogni schermo, quindi un'app usata da un agente è visibile sullo schermo del server. Non serve che abbia il focus.
- `"isolate": "home"` dà all'app una home privata tramite `HOME`, `XDG_*` e `CFFIXED_USER_HOME`, così copie di due spazi possono girare affiancate. `NSUserDefaults` non è isolato, quindi le preferenze Cocoa e `shared_preferences` di Flutter restano condivise tra le copie.
- `isolate` si applica solo al processo avviato. Un launcher di toolchain come `flutter run` ha bisogno della home reale, quindi abbina `isolate` a un binario compilato. Se l'app ha una propria impostazione, come `--user-data-dir`, preferisci quella.
- Gli agenti guidano la finestra con `app_use`, che raggiunge solo l'albero dei processi di questo ambiente. Un agente vede la finestra, non il desktop. Gli avvii da parte degli agenti passano dalla policy delle azioni e per impostazione predefinita chiedono conferma, e l'input dell'agente si ferma mentre una persona ha il controllo.
- `"input": "background"` (predefinito) invia gli eventi al processo. `"foreground"` attiva la finestra e prende il controllo del cursore.

## I task di worktree sostituiscono gli script dei repo

I task `provision` e `archive` sostituiscono i vecchi script di configurazione e archiviazione per repo. **Gli script esistenti sono stati migrati automaticamente:** ogni repo che aveva script ora ha una definizione con il suo nome, con i task `setup` e `archive` che contengono lo stesso testo. L'icona sulla riga di un repo in **Impostazioni → Spazio di lavoro → Repository** la apre. Le esecuzioni passate restano come cronologia di sola lettura.

Questi task seguono il worktree, non l'ambiente, quindi vengono eseguiti anche negli spazi dove nessuno preme **Avvia**:

| | `provision` | `archive` |
| --- | --- | --- |
| Viene eseguito | Alla creazione del worktree del ruolo, in qualsiasi spazio | Subito prima che quel worktree venga distrutto |
| In caso di errore | Il provisioning fallisce e il worktree viene distrutto | Registrato, non blocca mai l'eliminazione |
| Timeout predefinito | 5 minuti | 2 minuti |
| Vede | `CC_WORKSPACE_PATH`, `CC_ROOT_PATH`, `CC_SPACE_*`, `CC_REPO_NAME` | Lo stesso |

A un repo senza stack basta una definizione con i suoi task. Non essendoci nulla da avviare, non serve un ruolo àncora:

```jsonc
{
  "contract": 1,
  "name": "Web",
  "repos": { "app": { "repoId": "<id>" } },
  "components": [
    { "kind": "task", "id": "setup", "when": ["provision"],
      "script": ["pnpm install", "cp \"$CC_ROOT_PATH/.env\" .env"] }
  ]
}
```

- Non esiste ancora un ambiente, quindi questi task non possono usare `{name}`, `{port.*}`, `{url.*}`, `{opt.*}` o `enabledWhen`, e non ricevono l'`env` della definizione.
- Solo una definizione può contenere task `provision` e `archive` per un repo. Le altre possono comunque legarlo per tutto il resto.
- `"when": ["provision", "change"]` reinstalla anche quando cambia un lockfile, cosa che gli script di configurazione non facevano.
- Un task viene eseguito per il worktree del suo ruolo `cwd`, quindi una definizione con più repo può configurare ogni repo separatamente.
- Un'esecuzione di test imposta `CC_SCRIPT_TEST=1`. Un nuovo tentativo parte da un worktree pulito, quindi scrivi task che reggano una riesecuzione.

## Agenti

Gli agenti non ricevono mai il socket Docker. In uno spazio con una definizione idonea, un'esecuzione riceve `cc-env` nel proprio `PATH`. Lo spazio deriva dall'esecuzione, quindi un agente può agire solo sul proprio ambiente, e ogni comando passa dalla policy delle azioni.

```bash
cc-env status
cc-env up
cc-env down
cc-env reset
cc-env destroy
cc-env restart <process>
cc-env logs <name>
cc-env exec <service> -- <cmd>
cc-env run <task> -- <args>
```

Con un componente compose, uno shim `docker` consente anche `docker compose` con `ps`, `logs`, `exec`, `port`, `restart` e `top`. Prima del verbo non può esserci alcun flag, `logs` non può seguire l'output e `exec` accetta solo `-T`. Tutto il resto esce con codice 5 e "not available in Control Center agent runs".

Un repo le cui skill chiamano il proprio strumento può continuare a farlo. Un blocco `agentPassthrough` su un componente `cli` dichiara quali comandi possono eseguire gli agenti:

```jsonc
"agentPassthrough": {
  "binary": "acme",
  "allow": [
    { "argv": ["env", "ls"], "maps": "status", "nameFilter": true },
    { "argv": ["env", "status|url"], "maps": "status", "positionalName": 2 },
    { "argv": ["env", "create"], "maps": "up", "positionalName": 2,
      "pathFlags": ["--web-dir"], "denyFlags": ["--force"] },
    { "argv": ["env", "logs"], "maps": "logs", "positionalName": 2,
      "denyFlags": ["--follow"] }
  ]
}
```

`maps` indica l'operazione di cui si applica la policy. `positionalName` forza quell'argomento sull'ambiente di questo spazio, `nameFilter` filtra l'output JSON su di esso e ogni valore di `pathFlags` deve risolversi nei worktree dell'esecuzione. Un comando che non corrisponde ad alcuna regola esce con codice 5.

Le stesse operazioni esistono come strumenti: `environment_status`, `environment_up`, `environment_down`, `environment_reset`, `environment_destroy`, `environment_restart`, `environment_exec`, `environment_logs`, `environment_run_task`, `environment_launch_app` e `environment_stop_app`. Gli agenti in sandbox raggiungono direttamente le proprie porte e i nomi host del proprio ambiente tramite il proxy dell'esecuzione, quindi di' loro di leggere gli endpoint da `environment_status` invece di indovinare un URL.

## Pull request da fork

Il codice di una PR da fork non è attendibile, e con il posizionamento sull'host viene eseguito come utente di sistema del server. `policy.forkPrs` decide cosa succede:

| Valore | Effetto | Predefinito per |
| --- | --- | --- |
| `rig` | Il file compose viene eseguito in una VM senza conferma | Definizioni con soli componenti `compose` e `task` |
| `approval` | Ogni avvio richiede un amministratore | Tutte le altre definizioni |
| `deny` | Rifiutato | Nessuna |

- I `seedFiles` non vengono mai copiati per un fork, perché di solito sono segreti. Un file compose che ne monta uno segnala il file mancante per nome.
- I task `provision` e `archive` vengono saltati, a meno che la policy non sia `rig`: in quel caso vengono eseguiti nella VM.
- Con il posizionamento sull'host, `privileged`, i namespace dell'host, un bind del socket Docker, `devices` e i bind al di fuori dei worktree dello spazio vengono rifiutati su un fork. Negli spazi attendibili generano solo un avviso.

## Posizionamento in rig

`"placement": "rig"` esegue i componenti `compose` e `task` in una microVM dedicata. Le definizioni con componenti `process`, `cli` o `app` non sono idonee. Il file compose viene eseguito senza modifiche, senza socket Docker dell'host e senza credenziali dell'operatore, e l'accesso alla rete è limitato ai registri necessari alle sue immagini. Il worktree viene montato dal vivo.

- **Guest arm64.** I guest sono arm64 su Apple Silicon, quindi le immagini solo amd64 non funzionano.
- **I registri privati vengono rifiutati.** I guest non hanno credenziali di registro, quindi un'immagine su un registro esterno a quelli pubblici noti viene rifiutata prima dell'avvio della VM. Un repository privato su un registro pubblico fallisce quando il guest lo scarica.
- **16 GiB di spazio.** Tutte le immagini e i volumi dello stack condividono un disco da 16 GiB, che non può essere ampliato.
- **Il primo avvio è lento.** I layer delle immagini sono per VM, quindi il primo avvio scarica tutto. Un rig fermo conserva il disco.
- **Le immagini di base devono essere leggibili.** Un Dockerfile che indica l'immagine di base tramite una variabile non può essere pianificato, perché l'accesso alla rete è fissato all'avvio.
- **Durata.** `policy.rigTtlHours` termina la VM, dopo 24 ore per impostazione predefinita.

## Contratto di stato per gli autori di strumenti

Un componente `cli` senza `statusMap` si aspetta il contratto nativo, `cc-env/1`. Il verbo `status` stampa questo oggetto su stdout:

```json
{
  "state": "ready",
  "detail": "migrations applied, HTTP 200",
  "endpoints": [
    { "role": "app", "label": "App", "url": "https://fix-login.acme.test", "primary": true },
    { "role": "postgres", "label": "Postgres", "hostPort": 49213 }
  ],
  "services": ["server", "postgres"],
  "needsRecreate": false,
  "error": { "code": "post-start-failed", "message": "…", "hint": "…", "command": "…" }
}
```

- `state` è `ready`, `starting`, `stopped`, `failed` o `missing`. `missing` porta a `create`, `stopped` e `failed` portano a `start`. Segnala `missing` con codice di uscita 0: uno `status` fallito conta come `failed`.
- Serve solo `state`. I campi sconosciuti vengono ignorati, e un output non analizzabile appare come degradato, con il testo grezzo come dettaglio.
- Un URL deve essere di loopback, `*.localhost` o sotto `routing.domain`, altrimenti viene scartato.
- `needsRecreate: true` mostra **Ricrea**, che scarta i dati. Control Center non agisce mai da solo su questo valore.
- Il verbo `list` stampa un array JSON di nomi, o di oggetti con un `name`.

I codici di uscita valgono per ogni verbo:

| Codice | Significato |
| --- | --- |
| 0 | OK |
| 3 | Configurazione dell'host richiesta. **Esegui nel terminale** apre un terminale di spazio con il comando digitato ma non eseguito, poi **Riprova** riprova. Control Center non esegue mai `sudo` |
| 4 | Autenticazione richiesta |
| 5 | Dipendenza non disponibile |
| Altro | Errore |

L'avanzamento va su stderr come JSON delimitato da newline:

```json
{"type":"step","label":"Pull images","state":"running"}
{"type":"note","message":"Hosts entries stayed behind after destroy"}
{"type":"error","code":"hosts-missing","message":"Add the hosts entry","hint":"Needs sudo","command":"sudo acme hosts add fix-login"}
```

Le righe `step` appaiono come elenco di passaggi in tempo reale e le righe `note` così come sono. Un'ultima riga di tipo `error` diventa un errore strutturato, con `command` proposto da copiare. Altrimenti Control Center mostra le ultime 20 righe di stderr. Tutto ciò che non è JSON è normale output di log.
