Questa guida copre le cinque cose che si fanno davvero con i backup: crearne uno,
raccoglierlo, spostare uno spazio di lavoro, rimetterne uno a posto e tenere copie fuori
dalla macchina. Per la forma esatta di ogni artefatto e di ogni operazione, vedi il
[riferimento sul backup](/it-IT/manuale/riferimento/backup/).

Tutto quello che c'è qui vive in **Impostazioni → Server → Backup e ripristino**.

## Prerequisiti

- Un **client completo** — l'app desktop o web. Un telefono associato non può attivare nulla di tutto questo, per scelta progettuale.
- Per creare, elencare, scaricare o eliminare un'**istantanea dell'installazione**: il **proprietario** dell'installazione.
- Per le azioni su un singolo spazio di lavoro: **admin** di quello spazio di lavoro per esportarlo o per elencarne e scaricarne i backup pianificati, **proprietario** per eliminarlo o per eliminare uno dei suoi backup.
- Per **ripristinare** uno spazio di lavoro, da un file caricato, un backup pianificato o un'istantanea: il [proprietario del server](/it-IT/manuale/concetti/autorizzazione/#il-proprietario-del-server), che deve anche essere proprietario di quello spazio di lavoro. Un ripristino fa adottare al server un file di database come proprio, quindi è una decisione del proprietario del server. Chiunque altro vede «Solo il proprietario del server può ripristinare i backup. Puoi comunque scaricarli.» al posto delle azioni di ripristino.
- Per i download e gli upload: un client completo associato, su una connessione diretta o tramite relay. Entrambi i percorsi trasportano i byte del file attraverso lo stesso tunnel delle risorse autenticato e cifrato end-to-end; il relay non può leggerli.

:::caution[Le istantanee dell'installazione sono manuali]
**Esegui backup ora** crea comunque un'istantanea dell'intera installazione solo su
richiesta. La pipeline integrata **Workspace backup** può invece fare un backup del
database di uno spazio di lavoro una volta alla settimana e rimuovere i backup di quello
spazio di lavoro più vecchi di 30 giorni. Non copia `global.db`, altri spazi di lavoro né
i file accanto al database. Conserva separatamente le copie fuori dalla macchina.
::::

::::caution[I backup non sono cifrati a riposo]
Il trasferimento cifrato termina sul tuo client e su `cc_server`. Le directory delle
istantanee, le esportazioni degli spazi di lavoro, i file scaricati e i database del
server non sono cifrati a riposo da Control Center. Proteggi l'host del server, i tuoi
download e le copie fuori dalla macchina con la tua crittografia di archiviazione e i tuoi
controlli di accesso.
::::

## Cosa copre un backup

Entrambi gli artefatti sono **solo database**:

- Un'**istantanea dell'installazione** è una directory con data e ora: `manifest.json`, `global.db` e un `<workspaceId>/workspace.db` per ogni spazio di lavoro.
- Un'**esportazione dello spazio di lavoro** è quel singolo file `workspace.db`.

Il database di uno spazio di lavoro è l'intero spazio di lavoro: le sue conversazioni, i log delle esecuzioni, i collegamenti dei repository, le definizioni degli ambienti e i membri. Non contiene segreti: i token dei webhook delle pipeline, i segreti dei webhook di sincronizzazione dei ticket, gli accessi ai provider, le chiavi dei dispositivi e i segreti degli utenti stanno nel database globale e nell'archivio segreti del server. È comunque tutto ciò che lo spazio di lavoro ha detto e fatto, quindi conserva un backup o un'esportazione scaricati con la stessa riservatezza dello spazio di lavoro stesso. L'indice del codice è un file separato accanto al database, `code_index.db`. Nessun backup lo include; il server lo ricostruisce.

Nessuno dei due porta con sé il resto della directory dei dati: `secrets.json` (chiavi di
associazione, credenziali dei fornitori, segreti dei webhook, SSO), i `blobs/` di uno spazio di lavoro (immagini
incollate nei messaggi), `skills/`, `agents/`, `chat_credentials/`, l'audio delle riunioni
registrate o le immagini dei rig. Una parte è usa e getta e una parte no — la
[tabella completa è nel riferimento](/it-IT/manuale/riferimento/backup/#cosa-non-contiene-un-backup),
e coprirla è esattamente lo scopo della [sezione fuori dalla macchina](#copia-i-backup-fuori-dalla-macchina).

## Scatta un'istantanea dell'intera installazione

1. Apri **Impostazioni → Server → Backup e ripristino**.
2. Sotto **Istantanee dell'installazione**, premi **Esegui backup ora**.
3. L'avviso indica la directory che è stata scritta, sull'host del server. La nuova istantanea compare in cima all'elenco.

Il server resta in esecuzione per tutto il tempo. Ogni file viene scritto con `VACUUM INTO`,
che è coerente anche su un database in uso, quindi non c'è alcuna finestra di manutenzione
né bisogno di fermare gli agenti.

Ogni riga dell'elenco mostra la data e l'ora, la dimensione su disco, quanti spazi di lavoro sono stati acquisiti e se l'istantanea è **Completa** o **Non verificata**. Ogni copia viene controllata dopo la scrittura, e il manifest registra la sua dimensione e la sua checksum. Non verificata significa che il server non può garantire l'istantanea: il suo manifest manca o non è leggibile, oppure un file che elenca è assente o ha cambiato dimensione. Succede con un backup interrotto da un crash o da un disco pieno, o con uno fatto prima che le istantanee registrassero le checksum. Vengono comunque elencate di proposito: un'istantanea che non vedi è un'istantanea che credi di avere. Un'istantanea non verificata non può ripristinare un'intera installazione, ma i file degli spazi di lavoro che contiene si possono ancora ripristinare uno per uno.

Una riga può anche dire **_n_ spazi di lavoro non acquisiti**. È uno spazio di lavoro registrato ma in cui non è mai stato scritto nulla (il file non esiste ancora), uno il cui database è danneggiato (una copia danneggiata non viene mai acquisita), oppure uno la cui copia non è riuscita — controlla il log del server.

Un'istantanea o un backup pianificato contrassegnato come **Ultima copia valida** conserva la copia valida più recente di uno spazio di lavoro il cui database è stato poi danneggiato. La pulizia pianificata non lo tocca, ed eliminarlo chiede una conferma, finché quello spazio di lavoro non viene ripristinato.

## Pianifica i backup degli spazi di lavoro e la conservazione

Apri **Impostazioni → Spazio di lavoro → Modelli di pipeline** per lo spazio di lavoro e cerca
**Workspace backup**. La sua pianificazione attiva viene eseguita ogni
domenica alle 03:00 UTC: **Back up workspace**, seguito da **Delete backups older than**
(30 giorni per impostazione predefinita). Il secondo nodo viene eseguito solo dopo il
successo del backup. Puoi cambiare i giorni di conservazione sul nodo o disattivare la
pianificazione. Se il server è offline all'ora prevista, la pianificazione recupera una
volta sola al suo ritorno, invece di ripetere ogni settimana saltata.

I backup degli spazi di lavoro vivono sul server in
`backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`. Il nodo di
conservazione elimina solo i backup vecchi di questo spazio di lavoro; non elimina mai le
istantanee dell'installazione né i backup di altri spazi di lavoro. Questi file contengono
solo database. Per una conservazione fuori dalla macchina, scaricali o copiali in modo
indipendente.

## Trova e ripristina un backup pianificato

**Backup pianificati** si trova tra **Istantanee dell'installazione** e
**Dati dello spazio di lavoro**, con una riga per ogni spazio di lavoro: quando è stato
eseguito l'ultimo backup, quanti ne ha conservati e lo spazio che occupano. Uno spazio di lavoro la cui
pipeline non ha ancora prodotto nulla mostra **Ancora nessun backup**. Uno spazio di lavoro
di cui non sei admin lo segnala nella sua riga invece di elencare i backup.

Espandi una riga per vedere ogni backup, dal più recente:

- **Ripristina** sostituisce il database attuale dello spazio di lavoro con questo backup. Il database sostituito viene conservato in questo elenco, con un nome che termina in `-pre-restore`, così puoi tornare indietro. Richiede il proprietario del server, che deve anche essere proprietario dello spazio di lavoro.
- **Scarica** salva il file sulla macchina che stai usando. Il backup resta sul server.
- **Copia percorso** copia la sua posizione sul server.
- **Elimina** rimuove definitivamente questo backup, dopo che hai digitato il nome dello spazio di lavoro. Richiede **proprietario**.

### Backup di uno spazio di lavoro eliminato

L'eliminazione di uno spazio di lavoro lascia i suoi backup pianificati sul server e,
poiché la sua pianificazione si ferma con esso, si ferma anche la conservazione: restano
finché qualcuno non li rimuove. Il **proprietario** dell'installazione li vede nello stesso
elenco, contrassegnati con **Spazio di lavoro eliminato**, e può scaricarli o eliminarli da
lì. Nessun altro vede quelle righe.

Non hanno **Ripristina**, perché non c'è uno spazio di lavoro in cui ripristinarli. Per
recuperarne uno, scaricalo, crea uno spazio di lavoro (solo il proprietario del server può farlo) e carica il file come descritto in
[Sposta uno spazio di lavoro su un'altra installazione](#sposta-uno-spazio-di-lavoro-su-unaltra-installazione).

## Elimina un'istantanea dell'installazione

Sotto **Istantanee dell'installazione**, espandi l'istantanea, anche una non verificata, e usa
**Elimina istantanea** nella zona pericolosa. Conferma il suo nome. L'intera directory
dell'istantanea viene rimossa definitivamente dal server; scaricala prima se ti serve una
copia. Una pipeline di backup degli spazi di lavoro non elimina mai queste istantanee.

## Raccogli una copia sulla tua macchina

I percorsi che la pagina mostra sono sulla macchina che esegue `cc_server`. Quando non è la
macchina su cui sei seduto, usa i pulsanti **Scarica**:

- Accanto a ogni **spazio di lavoro**, sotto **Dati dello spazio di lavoro** → **Scarica**, per un singolo file `.db`.
- Accanto a ogni **istantanea**, sotto **Istantanee dell'installazione** → **Scarica**, per l'intera istantanea come `.zip`.
- Accanto a ogni backup, sotto **Backup pianificati** → **Scarica**, per il file `.db` di quel backup.

Su desktop scegli dove finisce il file e l'avviso lo indica; sul web finisce nei download
del browser. In entrambi i casi tutti e tre riportano il progresso in byte, perché questi
payload arrivano a gigabyte.

I download dello spazio di lavoro e dell'istantanea generano una copia nuova nel momento in
cui premi il pulsante, la trasmettono in streaming e poi eliminano la copia del server — un
download non è «recuperare il file che il pulsante di esportazione aveva creato prima». Un
backup pianificato è l'eccezione: ricevi il file archiviato, che resta sul server.

Estrarre un archivio di istantanea riproduce esattamente la struttura dell'istantanea, ed è
ciò che rende il suo ripristino una semplice copia di ritorno.

## Sposta uno spazio di lavoro su un'altra installazione

Uno spazio di lavoro è un solo file di database, quindi passarlo a qualcun altro è
un'operazione su file.

1. Sul server **di origine**, **Impostazioni → Server → Backup e ripristino → Dati dello spazio di lavoro**, espandi lo spazio di lavoro e premi **Scarica**.
2. Sul server **di destinazione**, crea (o scegli) lo spazio di lavoro che lo riceverà.
3. Espandi quello spazio di lavoro e, sotto **Ripristina da questo dispositivo**, premi **Scegli un file e caricalo**. Scegli il `.db` che hai scaricato.

Il passaggio 3 è un ripristino, quindi richiede il proprietario del server di destinazione, che deve anche essere proprietario di quello spazio di lavoro.

Se entrambi i server sono la macchina su cui sei seduto, **Salva sul server** sull'origine,
poi il percorso del file in **File di database dello spazio di lavoro** e **Importa** sulla destinazione,
fanno la stessa cosa senza il viaggio di andata e ritorno; quel percorso viene risolto sull'host del server.

:::caution[L'importazione sostituisce tutto]
Importare sostituisce tutto ciò che lo spazio di lavoro di destinazione contiene attualmente. Il database sostituito viene conservato in **Backup pianificati** con un nome che termina in `-pre-restore`; ripristinalo per tornare indietro.
:::

Un file proveniente da un altro spazio di lavoro o da un'**installazione diversa** viene accettato: è così che duplichi uno spazio di lavoro, lo ripristini sotto un nuovo id o lo passi a qualcun altro. Gli id utente di un'altra installazione non si risolvono su questa — i dati dello spazio di lavoro sono intatti, ma ricontrolla l'appartenenza dopo averlo adottato.

Un file ripristinato non può concedere nulla da solo su questo server. I permessi che porta oltre la normale appartenenza vengono tolti ed elencati in **Trattenute dalle copie ripristinate** in cima alla pagina: regole d'azione che permettono agli agenti di agire senza approvazione o dopo una, percorsi che una sandbox può eseguire, accesso ai repository oltre la sola lettura, ruoli superiori a membro e inviti aperti a quei ruoli. **Accetta** lo concede di nuovo; **Rifiuta** lo elimina. Le approvazioni per eseguire una definizione di ambiente sull'host vengono annullate, quindi approva di nuovo quelle definizioni. Chi ripristina mantiene o ottiene il ruolo di proprietario.

I token dei bot di chat, gli accessi ai provider e i segreti dei webhook vivono fuori dal database, quindi l'installazione che lo riceve ricollega i propri. I trigger dei webhook e i webhook di sincronizzazione dei ticket arrivano senza i loro segreti e non ricevono nulla su un altro server finché non li salvi di nuovo lì, il che assegna a ogni trigger un nuovo URL.

## Ripristina un solo spazio di lavoro da un'istantanea

Devi essere il proprietario del server e proprietario dello spazio di lavoro.

1. Sotto **Istantanee dell'installazione**, espandi l'istantanea che vuoi.
2. Trova la riga dello spazio di lavoro e premi **Ripristina**.
3. Conferma. Tutto ciò che quello spazio di lavoro ha fatto da quando è stata scattata l'istantanea va perso.

È la stessa operazione di un'importazione, puntata sulla copia che l'istantanea contiene
del file di quello spazio di lavoro — di proposito, così non c'è un secondo meccanismo che
possa trattare lo stesso file in modo diverso. La copia viene prima verificata con la checksum registrata dall'istantanea.

Una riga può dire **Non è più su questo server**, con **Ripristina** disattivato:
l'istantanea contiene uno spazio di lavoro che questa installazione non ha più. Riportalo
indietro a mano — crea uno spazio di lavoro (solo il proprietario del server), poi sotto **Dati dello spazio di lavoro**
inserisci `<snapshot path>/<old workspace id>/workspace.db` nel suo campo **File di database dello spazio di lavoro** e premi **Importa**. L'istantanea
espansa mostra il suo **Percorso sul server** in un campo copiabile, e il titolo della riga
è il vecchio id dello spazio di lavoro, quindi hai entrambe le metà di quel percorso davanti
a te.

## Ripristinare uno spazio di lavoro danneggiato

Uno spazio di lavoro il cui database non supera il controllo di integrità diventa in sola lettura: tutto resta leggibile e ogni modifica viene rifiutata. I membri vedono **Questo spazio di lavoro è in sola lettura** in cima allo spazio di lavoro, il proprietario del server lo vede sotto **Richiede la tua attenzione** in questa pagina, e il backup più recente che contiene una copia valida viene conservato come **Ultima copia valida**. Ripristina lo spazio di lavoro da quella copia, come descritto sopra, per renderlo di nuovo scrivibile. Il database danneggiato viene conservato come backup `-pre-restore`.

## Ripristina un'intera installazione

Non esiste un pulsante per farlo, e non dovrebbe esistere: sostituisce i database che il
server in esecuzione tiene aperti.

1. **Ferma `cc_server`.** Se usi l'app desktop con il suo server incorporato, chiudi l'app.
2. Copia il contenuto dell'istantanea sopra la directory dei dati. La struttura dell'istantanea rispecchia quella attiva, quindi è una semplice copia:

   ```bash
   # macOS default; see the CLI reference for other platforms
   DATA_DIR="$HOME/Library/Application Support/control-center"
   SNAPSHOT="$DATA_DIR/backups/2026-07-28T09-12-33-000Z"

   cp "$SNAPSHOT/global.db" "$DATA_DIR/global.db"
   for d in "$SNAPSHOT"/*/; do
     id=$(basename "$d")
     mkdir -p "$DATA_DIR/$id"
     cp "$d/workspace.db" "$DATA_DIR/$id/workspace.db"
   done
   ```

3. Elimina i file `-wal` e `-shm` che si trovano accanto ai database che hai sostituito. Appartengono ai vecchi file, e un file rimasto lì accanto a un database ripristinato è un rischio di corruzione.
4. Avvia di nuovo il server.

L'istantanea non contiene `secrets.json`, quindi un'installazione ripristinata su un host
**nuovo** conserva i suoi dati ma non le sue credenziali: dispositivi associati, token dei
fornitori e impostazioni SSO vanno ristabiliti, oppure ripristinati da dove hai conservato
quel file. Ripristinare sullo stesso host, dove `secrets.json` non è mai andato perso,
conserva tutto.

## Copia i backup fuori dalla macchina

Un'istantanea sullo stesso disco del database che ha copiato ti protegge da un'importazione
sbagliata, non dal disco. Niente in Control Center spedisce una copia da nessuna parte,
quindi questa parte tocca a te.

### Sincronizza le istantanee

Le istantanee sono immutabili una volta scritte e nominate per data e ora, quindi qualsiasi
strumento di sincronizzazione le gestisce bene. Escludi `transfer/`, che è un banco di
lavoro per download e upload in corso:

```bash
DATA_DIR="$HOME/Library/Application Support/control-center"

# To another host over ssh
rsync -a --delete --exclude 'transfer/' \
  "$DATA_DIR/backups/" backup-host:/srv/control-center-backups/

# To object storage
aws s3 sync --exclude 'transfer/*' \
  "$DATA_DIR/backups/" s3://my-bucket/control-center/backups/

# Or with deduplication, encryption and its own retention
restic backup --exclude 'transfer' "$DATA_DIR/backups"
```

`--delete` rispecchia sul remoto la tua pulizia locale. Toglilo se vuoi che il remoto
conservi le istantanee più a lungo dell'host.

:::danger[Non sincronizzare mai direttamente i database in uso]
Non puntare rsync, `aws s3 sync` o un agente di backup a livello di file su `global.db` o
`<workspaceId>/workspace.db` mentre il server è in esecuzione. Un database SQLite in uso ha
un file `-wal` collaterale, e una copia file per file cattura i due in istanti diversi — il
risultato è un file che spesso si apre ma perde silenziosamente le scritture recenti,
oppure che non si apre affatto. Copia l'**istantanea**, che è stata scritta all'interno di
una transazione di lettura, oppure creane una con `VACUUM INTO` come qui sotto.
:::

### Includi ciò che un'istantanea lascia fuori

Per poter ricostruire l'installazione e non solo i suoi dati, copia anche questi. Sono file
normali, sicuri da copiare mentre il server è in esecuzione:

```bash
rsync -a \
  "$DATA_DIR/secrets.json" \
  backup-host:/srv/control-center-backups/config/

rsync -a --relative \
  "$DATA_DIR"/./*/chat_credentials \
  "$DATA_DIR"/./*/blobs \
  "$DATA_DIR"/./*/skills \
  "$DATA_DIR"/./*/agents \
  backup-host:/srv/control-center-backups/workspace-files/
```

`secrets.json` è `0600` e contiene ogni chiave di associazione, credenziale di fornitore e
impostazione SSO dell'installazione. Ovunque finisca deve essere almeno altrettanto
protetto dell'host del server — cifrato a riposo, e non un bucket che chiunque altro possa
leggere.

Salta `spaces/` (worktree copy-on-write, riprovisionati dai tuoi repo), `pr_clones/` (una
cache), `models/` (riscaricati), `media_cache/` e `rigs/` (stato della macchina, e grandi).
L'audio delle riunioni registrate sotto `meetings/` vale la pena di includerlo se conservi
le riunioni.

### Pianifica un'istantanea dell'intera installazione fuori dall'app

La pipeline integrata esegue il backup di un solo spazio di lavoro. Per un'istantanea
**dell'intera installazione** senza supervisione non esiste un sottocomando CLI, e l'RPC
dell'istantanea richiede un client completo associato che sia il proprietario
dell'installazione. Un timer lato host può usare `VACUUM INTO` sui database in uso:

```bash
#!/usr/bin/env bash
set -euo pipefail

DATA_DIR="${CC_SERVER_DATA_DIR:-$HOME/.local/share/control-center}"
DEST="/srv/control-center-snapshots/$(date -u +%Y-%m-%dT%H-%M-%SZ)"
mkdir -p "$DEST"

sqlite3 "$DATA_DIR/global.db" "VACUUM INTO '$DEST/global.db'"

for db in "$DATA_DIR"/*/workspace.db; do
  id=$(basename "$(dirname "$db")")
  mkdir -p "$DEST/$id"
  sqlite3 "$db" "VACUUM INTO '$DEST/$id/workspace.db'"
done
```

Eseguilo come lo stesso utente che possiede la directory dei dati, da cron o da un timer
systemd, e poi sincronizza `DEST` fuori dall'host. `VACUUM INTO` richiede SQLite 3.27 o
successivo.

Scrivilo **fuori** da `<dataDir>/backups/`. Una directory creata a mano lì dentro non ha
`manifest.json`, quindi l'app la elencherebbe come un'istantanea non verificata e l'elenco
smetterebbe di essere un registro onesto di ciò che il server ha prodotto da sé.

### Elimina le vecchie istantanee dell'intera installazione

Puoi eliminare le singole istantanee dell'installazione nell'app. Per una politica di
conservazione lato host, tieni la directory dei backup degli spazi di lavoro separata dalle
istantanee dell'installazione:

```bash
find "$DATA_DIR/backups" -mindepth 1 -maxdepth 1 -type d \
  ! -name exports ! -name transfer ! -name workspace-backups \
  -mtime +30 -exec rm -rf {} +
```

Controlla l'output di un'esecuzione con `-print` prima di aggiungere `-exec`. Conservane più
di una: il guasto da cui ti proteggi è spesso «anche l'ultimo backup ha lo stesso problema».

## Verifica che un backup sia buono

Un backup che nessuno ha ripristinato è un'ipotesi.

Verifica rapida — il file si apre e le sue pagine sono intatte:

```bash
sqlite3 "$SNAPSHOT/global.db" 'PRAGMA integrity_check;'   # expects: ok
```

Verifica reale — adottalo. Crea uno spazio di lavoro di prova su un'installazione non di
produzione, importa al suo interno un file di spazio di lavoro e guarda se gli spazi, i
ticket e i messaggi che ti aspetti ci sono. Questo esercita lo stesso percorso di un
ripristino reale, compresa la ricostruzione FTS, ed è l'unica verifica che ti dice che
il backup è ripristinabile e non solo leggibile.

Fallo una volta quando imposti i backup, e di nuovo ogni volta che cambi dove sono
conservati.

Scaricare uno spazio di lavoro richiede admin; ripristinarne uno richiede il proprietario del server, che deve anche essere proprietario dello spazio di lavoro |
| «I trasferimenti di file non sono ancora configurati per questa connessione. Riconnettiti al server per scaricare o caricare un backup.» | Questa connessione al server non ha una corsia di trasferimento file, quindi **Scarica** e il caricamento sono disattivati. Riconnettiti al server, poi riprova |
| «Solo il proprietario del server può ripristinare i backup. Puoi comunque scaricarli.» | Il ripristino sostituisce il database di uno spazio di lavoro sull'host del server, quindi solo il proprietario del server ripristina. Scarica il backup e chiediglielo |
| «Questo server non espone alcuna superficie di backup.»                   | L'host non ha alcuna porta di backup cablata — un server demo. Le operazioni sono assenti invece che rifiutate               |
| «Il file supera la dimensione accettata dal server.»                      | Gli upload sono limitati a 8 GiB. Metti il file sull'host del server e inserisci il suo percorso in **File di database dello spazio di lavoro**            |
| Un ripristino viene rifiutato e non viene sostituito nulla | Il file non ha superato un controllo, e il messaggio dice quale: non è un database di uno spazio di lavoro, è danneggiato, differisce dalla checksum registrata dalla sua istantanea, lo ha scritto una versione più recente del server, oppure i suoi webhook o inviti appartengono già a un altro spazio di lavoro su questo server. Usa un'altra copia oppure aggiorna prima il server |
| Un'istantanea è elencata come **Non verificata** | Non è mai stata completata, oppure è stata creata prima che le istantanee registrassero le checksum. Creane una nuova; nel frattempo ripristina da essa i singoli file degli spazi di lavoro |
| Un'istantanea dice che alcuni spazi di lavoro non sono stati acquisiti   | Quegli spazi di lavoro non hanno mai ricevuto scritture, sono danneggiati, oppure la loro copia non è riuscita. Controlla il log del server     |
| Uno spazio di lavoro mostra **Questo spazio di lavoro è in sola lettura** | Il suo database non ha superato il controllo di integrità. Nulla al suo interno può essere modificato finché il proprietario del server non lo ripristina da un backup |
| I webhook smettono di arrivare dopo che uno spazio di lavoro passa a un altro server | I segreti dei webhook non viaggiano con il database. Salva di nuovo ogni trigger dei webhook e ogni connessione di sincronizzazione dei ticket sul nuovo server, poi comunica al mittente il nuovo URL |
| A un'installazione ripristinata mancano le credenziali della forge o dell'SSO | `secrets.json` non è dentro un'istantanea. Ripristinalo da dove l'hai conservato, oppure ricollega i fornitori           |
| A uno spazio di lavoro ripristinato mancano le immagini incollate        | I blob vivono accanto al database, non al suo interno. Copia anche `<workspaceId>/blobs/`                                    |
