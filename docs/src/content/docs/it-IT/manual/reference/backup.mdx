Tutto ciò che Control Center può copiare, cedere o adottare, e la forma esatta di ogni
artefatto. Per creare davvero un backup, vedi
[Backup e ripristino](/it-IT/manuale/guide/backup-e-ripristino/); per capire perché la
persistenza è suddivisa in questo modo, vedi
[Spazi di lavoro e isolamento](/it-IT/manuale/concetti/spazi-di-lavoro/).

## Artefatti

Esistono tre artefatti di copia del database, con ambiti e politiche di eliminazione
diversi.

| Artefatto                       | Scritto da                   | Forma                                 | Copre                         |
| ------------------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **Istantanea dell'installazione** | `server.backupNow`         | Una **directory** con data e ora      | Tutti i database dell'installazione |
| **Backup dello spazio di lavoro** | pipeline `Workspace backup` | Directory con data e ora con un solo `.db` | Il database di uno spazio di lavoro |
| **Esportazione dello spazio di lavoro** | `workspace.export`  | Un singolo **file** `.db`             | Il database di uno spazio di lavoro |

Tutti vengono scritti con `VACUUM INTO` di SQLite, che è sicuro su un database WAL in
uso: apre una transazione di lettura, produce una copia deframmentata e
transazionalmente coerente e non richiede mai di fermare il server.

Questi file e le copie scaricate **non sono cifrati a riposo** da Control Center. Il
trasferimento cifrato end-to-end protegge i byte in transito tra un client associato e
il suo `cc_server`, su connessioni dirette o tramite relay. Proteggi separatamente
l'archiviazione locale e le copie fuori dalla macchina; il server e qualsiasi
destinatario autorizzato possono leggere i file di database.

## Struttura dell'istantanea

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

La struttura rispecchia esattamente la directory dei dati attiva, ed è ciò che rende il
ripristino di un'installazione una copia di ritorno anziché una traduzione. Il nome
della directory è la data e ora UTC con `:` e `.` sostituiti da `-`, quindi è sicuro
per i filesystem di Windows e si ordina cronologicamente come semplice stringa.

I backup pianificati degli spazi di lavoro vivono separatamente in
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Ciascuno ha un `manifest.json` per quel solo file e nessun `global.db`; non sono istantanee dell'installazione. Un ripristino conserva nello stesso punto il database che sostituisce, come `<timestamp>-pre-restore`.
Il passaggio di conservazione della pipeline settimanale elimina solo i backup del
proprio spazio di lavoro più vecchi dell'età configurata (30 giorni per impostazione
predefinita); le istantanee dell'installazione create manualmente non vengono mai
ruotate da quel passaggio. `server.listBackups` elenca solo le istantanee
dell'installazione, comprese quelle non verificate; `workspace.listBackups` elenca i backup
pianificati di un singolo spazio di lavoro.

L'eliminazione di uno spazio di lavoro lascia al suo posto questa directory. La
pianificazione dello spazio di lavoro si ferma con esso, quindi nulla ruota più quei
backup, che restano finché il proprietario dell'installazione non li rimuove.
`server.listOrphanedBackups` li segnala.


### `manifest.json`

| Campo                      | Tipo            | Significato                                                         |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                   | int             | Formato del manifest. Attualmente `2`                  |
| `created_at`               | ISO-8601 UTC    | Quando l'istantanea è stata scattata                                |
| `global` | oggetto | Il registro di `global.db`. Assente da un backup pianificato di uno spazio di lavoro |
| `workspaces[]`             | array           | Un record per ogni spazio di lavoro acquisito                        |
| `workspaces[].workspace_id`| stringa         | Lo spazio di lavoro contenuto in questo file                        |
| `skipped_workspaces[]`     | array           | Spazi di lavoro che il backup **non** è riuscito ad acquisire |
| `skipped_workspaces[].workspace_id` | stringa | Lo spazio di lavoro lasciato fuori |
| `skipped_workspaces[].reason` | stringa | `no_file`, `damaged` oppure `failed` |

`global` e ogni voce di `workspaces[]` registrano un file copiato, misurato sulla copia dopo che è stata scritta:

| Campo | Tipo | Significato |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | stringa         | Percorso relativo alla radice dell'istantanea: `global.db` oppure `<workspaceId>/workspace.db` |
| `bytes`       | int             | Dimensione della copia                                             |
| `sha256` | stringa | SHA-256 della copia, in esadecimale minuscolo |
| `quick_check` | stringa | Esito di `quick_check` di SQLite sulla copia: `ok`, oppure il suo rilievo |
| `user_version` | int | Versione dello schema della copia |
| `application_id` | int | `application_id` di SQLite della copia |

Uno spazio di lavoro viene saltato quando è registrato ma non vi è mai stato scritto nulla (`no_file`), quando il suo database non supera il controllo di integrità (`damaged`; una copia danneggiata non viene mai acquisita), oppure quando la sua copia o il controllo di quella copia non è riuscito (`failed`). In entrambi i casi l'istantanea viene comunque completata e il manifest indica ciò che manca. Il manifest viene scritto per ultimo.

### Completezza

`server.listBackups` riporta un flag `complete` per ogni istantanea. È false quando il manifest è assente, non analizzabile o di un altro formato, quando un file che nomina manca o ha un'altra dimensione, oppure quando una copia non ha superato il proprio controllo. L'app mostra un'istantanea del genere come **Non verificata**. Le istantanee create prima del formato `2` si trovano in questo stato.

Un'istantanea non verificata viene comunque elencata, perché un'istantanea che un operatore
non vede è un'istantanea che crede di avere. Quando il manifest non è leggibile,
l'elenco ripiega sulla struttura stessa e riporta tutti i file
`<workspaceId>/workspace.db` che trova: quelli restano adottabili singolarmente tramite
`workspace.import`, anche se l'istantanea nel suo complesso non può ripristinare
un'installazione.

Un'istantanea o un backup pianificato elencato riporta `pinned_reason: "last_good_copy"` finché conserva la copia verificata più recente di uno spazio di lavoro il cui database attivo è danneggiato. Il passaggio di conservazione lo salta finché quello spazio di lavoro non viene ripristinato.

## Cosa non contiene un backup

Entrambi gli artefatti sono **solo database**. La directory di uno spazio di lavoro
contiene più del suo database, e niente del resto viaggia:

| Percorso                            | In un'istantanea? | In un'esportazione dello spazio di lavoro? |
| ----------------------------------- | ----------------- | ------------------------------------------ |
| `global.db`                         | Sì                | No                                         |
| `<workspaceId>/workspace.db`        | Sì                | Sì (è *proprio* il file)                   |
| `<workspaceId>/code_index.db`       | No             | No                     |
| `<workspaceId>/blobs/`              | No                | No                                         |
| `<workspaceId>/skills/`             | No                | No                                         |
| `<workspaceId>/agents/`             | No                | No                                         |
| `<workspaceId>/chat_credentials/`   | No                | No                                         |
| `<workspaceId>/spaces/<spaceId>/`   | No                | No                                         |
| `<workspaceId>/pr_clones/`          | No                | No                                         |
| `secrets.json`                      | No                | No                                         |
| `models/`                           | No                | No                                         |
| `meetings/<meetingId>/`             | No                | No                                         |
| `rigs/`                             | No                | No                                         |
| `_agent_hooks/`                     | No                | No                                         |

Una parte è usa e getta: `spaces/` contiene worktree copy-on-write che vengono riprovisionati dai repo, `pr_clones/` è una cache, `code_index.db` viene ricostruito, `models/` viene riscaricato, `rigs/` è stato della macchina. Una parte no: `blobs/` contiene le immagini incollate a cui puntano le righe del database, `skills/` e `agents/` contengono i file con cui viene eseguito un agente, e `secrets.json` contiene ogni chiave di associazione, credenziale di fornitore e impostazione SSO dell'installazione. Vedi [Backup e ripristino](/it-IT/manuale/guide/backup-e-ripristino/#copia-i-backup-fuori-dalla-macchina) per coprire il resto.
:::note[I segreti restano fuori dai database]
`workspace.db` è l'intero spazio di lavoro: conversazioni, log delle esecuzioni, collegamenti ai repository, definizioni degli ambienti e membri. I token dei webhook delle pipeline e i segreti dei webhook di sincronizzazione dei ticket stanno in `secrets.json`: il database contiene un riferimento a ciascuno, e l'indice delle rotte contiene un hash con chiave di ciascun token. Uno spazio di lavoro ripristinato su un'altra installazione quindi non riceve webhook finché i suoi trigger non vengono salvati di nuovo lì. Accessi ai provider, chiavi dei dispositivi e segreti utente stanno in `global.db` e `secrets.json`.
:::

:::note[I token della chat restano deliberatamente indietro]
Il fatto che `chat_credentials/` si trovi accanto al database invece che al suo interno è
il motivo per cui uno spazio di lavoro passato a qualcun altro non porta con sé token bot
attivi. Vedi il
[riferimento sul ponte di chat](/it-IT/manuale/riferimento/ponte-di-chat/).
:::

## Operazioni

Gli RPC di backup dell'installazione e l'esportazione/importazione degli spazi di lavoro
sono riservati ai `fullClient`: un telefono associato non può attivarli. Su un server
senza porta di backup cablata, come il server demo, sono del tutto assenti — non
rifiutati, ma strutturalmente mancanti.

| Operazione            | Tipo      | Ambito            | Ruolo minimo        | Argomenti     | Restituisce                   |
| --------------------- | --------- | ----------------- | ------------------- | ------------- | ----------------------------- |
| `server.backupNow`    | mutazione | Installazione     | **proprietario** dell'installazione | nessuno | `{ok, path}`      |
| `server.listBackups`  | lettura   | Installazione     | **proprietario** dell'installazione | nessuno | `{backups: [...]}` |
| `server.deleteBackup` | mutazione | Installazione     | **proprietario** dell'installazione | `name`  | `{ok}`            |
| `server.listOrphanedBackups` | lettura | Installazione | **proprietario** dell'installazione | nessuno | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutazione | Installazione | **proprietario** dell'installazione | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | lettura | Spazio di lavoro | `admin` | nessuno | `{backups: [...]}` |
| `workspace.deleteBackup` | mutazione | Spazio di lavoro | `owner` | `name` | `{ok}` |
| `workspace.export`    | lettura   | Spazio di lavoro  | `admin`             | nessuno       | `{ok, path}`                  |
| `workspace.import`    | mutazione | Spazio di lavoro  | `owner`, e il proprietario del server | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | lettura | Spazio di lavoro | `owner`, e il proprietario del server | nessuno | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutazione | Spazio di lavoro | `owner`, e il proprietario del server | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`    | mutazione | Installazione*    | `owner`             | `id`          | riga di registro contrassegnata come eliminata |

* `workspace.delete` non ha ambito perché la riga che contrassegna vive nel registro
globale; il suo handler verifica l'appartenenza del chiamante allo spazio di lavoro
indicato e richiede `owner`.

`path` in ogni risposta è un percorso sull'**host del server**.

`server.listOrphanedBackups` restituisce una voce per ogni spazio di lavoro non più attivo:
`workspace_id`, `workspace_name` quando il registro lo conosce ancora, e `backups`. Uno
spazio di lavoro eliminato non può più superare un controllo di ruolo dello spazio di
lavoro, quindi i suoi backup appartengono al proprietario dell'installazione.
`server.deleteOrphanedBackup` rifiuta uno spazio di lavoro attivo, i cui backup restano
dietro `workspace.deleteBackup` e i ruoli propri di quello spazio di lavoro. Entrambe le
operazioni di eliminazione accettano solo un nome di directory con timestamp presente
nell'elenco, non un percorso.

`workspace.importHolds.list` restituisce ciò che un'importazione ha trattenuto. Ogni trattenuta ha un `id`, un `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` oppure `invite`), il `payload` che verrebbe ripristinato, `imported_at` e `source_install_id`. `workspace.importHolds.resolve` con `accept: true` lo concede di nuovo e con `false` lo elimina. `applied` è false quando chi o che cosa era destinatario della concessione non è più nello spazio di lavoro.

:::note[Un'istantanea dell'intera installazione richiede il proprietario su entrambi i canali]
`server.backupNow`, `server.listBackups` e `server.deleteBackup` richiedono il
**proprietario** dell'installazione (`ServerAuthority.serverOwner`), lo stesso controllo
di `GET /backup/snapshot`. Un'istantanea acquisisce il database di ogni spazio di
lavoro, quindi essere admin di un solo spazio di lavoro non basta per gestire gli altri.
L'eliminazione accetta solo il nome della directory con data e ora presente nell'elenco,
non un percorso arbitrario del server, e rimuove l'intera istantanea (comprese quelle
non verificate). Esportazione e download dei backup pianificati per singolo spazio di lavoro restano in capo
solo all'admin dello spazio di lavoro.
:::

:::note[Il ripristino spetta al proprietario del server]
`workspace.import` e `POST /backup/restore` fanno sì che il server adotti un file di database
le cui righe tratta poi come sue: collegamenti ai repository e chi li ha creati, definizioni
degli ambienti che girano sull'host, percorsi di worktree e di log. Per questo entrambi
richiedono il proprietario del server (`ServerAuthority.serverOwner`), che deve anche essere
il proprietario dello spazio di lavoro. Chiunque altro, e ogni chiamante su un host senza un
proprietario registrato, viene rifiutato con `server_owner_required`. Nessun trigger, vista, colonna o vincolo
portato dal file viene adottato.
:::


### Risposta di `server.listBackups`

Dalla più recente, ordinate per nome della directory (che è la data e ora, quindi
l'ordine vale anche per un'istantanea il cui manifest non è stato leggibile).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` viene omesso quando il manifest non è stato leggibile. `bytes` al livello
superiore è la dimensione reale su disco dell'intera directory, non la somma del
manifest: la domanda che si pone un operatore che ripulisce le istantanee è quanto costa
la directory, non quanto il backup intendeva scrivere.

Ogni `workspaces[].path` è esattamente ciò che `workspace.import` accetta come
`source_path`. È deliberato: «ripristina questo spazio di lavoro da questa istantanea»
*è* l'operazione di importazione, quindi le due non possono divergere in trattamenti
diversi dello stesso file.

### Convalida di `workspace.import`

Prima che venga sostituito qualcosa, il file candidato viene copiato in un file di staging accanto alla destinazione e controllato lì. Un rifiuto non tocca nulla e riporta il proprio tipo come `data.kind`.

| Condizione                                       | Risultato                                                        |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| Il file non esiste | Rifiutato, `import.missing_source` |
| Non è un database SQLite leggibile, o non supera `quick_check` | Rifiutato, `import.damaged` |
| Proviene da un'istantanea e il suo SHA-256 differisce da quello del manifest | Rifiutato, `import.checksum_mismatch` |
| Lo ha scritto una versione più recente del server | Rifiutato, `import.newer_schema` |
| Un altro `application_id`, o manca `workspace_meta` | Rifiutato, `import.foreign_file` |
| Non può essere portato allo schema di questo server | Rifiutato, `import.schema_mismatch` |
| I suoi webhook o inviti sono già instradati verso un altro spazio di lavoro | Rifiutato, `import.route_conflict` |
| Id di spazio di lavoro registrato ≠ quello di destinazione | **Consentito**. Le sue righe vengono riassociate alla destinazione. È così che uno spazio di lavoro viene duplicato o ripristinato sotto un nuovo id |
| Id dell'installazione registrato ≠ quello di questa installazione | **Consentito**. I suoi id utente appartengono a quell'installazione e non si risolveranno qui |

Al momento dell'accettazione il file di staging viene portato allo schema di questo server e deve poi corrispondervi esattamente. Le concessioni che un file non può darsi da solo vengono tolte: le approvazioni per eseguire una definizione di ambiente sull'host vengono annullate, e le regole d'azione che consentono o chiedono conferma, le concessioni di exec nella sandbox, le concessioni sui repository oltre la sola lettura, i ruoli superiori a membro e gli inviti a quei ruoli diventano trattenute che il proprietario del server deve esaminare. Chi importa mantiene o ottiene il ruolo di proprietario. Il database sostituito viene conservato come backup pianificato denominato `<timestamp>-pre-restore`; il file di staging viene spostato al suo posto con le connessioni dello spazio di lavoro chiuse, `code_index.db` viene eliminato per essere ricostruito, e gli indici FTS vengono ricostruiti.

## Route di trasferimento

Le operazioni di esportazione/importazione e di elencazione delle istantanee qui sopra
parlano in termini di percorsi lato server, il che è una risposta completa solo quando
il server è la tua macchina. Queste route in forma di HTTP trasportano i byte del backup
**dentro lo stesso tunnel delle risorse autenticato e cifrato end-to-end** di altre
risorse sensibili, sia che la connessione RPC sia diretta sia intermediata. Non sono
endpoint pubblici di trasferimento file HTTP: una richiesta a uno di essi sul listener
pubblico restituisce `426 Upgrade Required`, anche dal loopback. Nel tunnel cifrato, il
dispositivo autenticato con Noise deve corrispondere a `d`; il gestore verifica inoltre
la firma del dispositivo sulla sua stringa di destinazione usando la sua PSK di
abbinamento e il ruolo riportato sotto.

| Route                   | Metodo | Query           | Destinazione firmata           | Richiede                   |
| ----------------------- | ------ | --------------- | ------------------------------ | -------------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **admin** dello spazio di lavoro |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **proprietario** dell'installazione |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **admin** dello spazio di lavoro; **proprietario** dell'installazione una volta eliminato lo spazio di lavoro |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **proprietario** dell'installazione che è anche **proprietario** dello spazio di lavoro (`403` con `server_owner_required` altrimenti) |

`w` è un id di spazio di lavoro, `n` un nome di directory di istantanea o di backup
pianificato, `d` l'id del dispositivo chiamante, `s` la firma. Su `/backup/snapshot`, `n`
viene risolto rispetto all'elenco dei backup anziché concatenato alla radice dei backup,
quindi la route non può essere puntata su una directory che l'elenco non avrebbe mostrato.
Su `/backup/stored` deve essere un nome con timestamp, e il file deve essere un file reale
all'interno della directory di backup di quello stesso spazio di lavoro.

| Stato | Causa                                                                             |
| ------ | --------------------------------------------------------------------------------- |
| `400`  | Manca un parametro di query obbligatorio, un nome di backup non è valido, il corpo di un caricamento è vuoto, oppure il file caricato è stato rifiutato (il corpo è `{error, kind}` con un valore `import.*`) |
| `403`  | Dispositivo sconosciuto o revocato, firma non valida, o il chiamante non ha il ruolo |
| `404`  | Nessuna porta di backup su questo host, o il file di istantanea, backup o spazio di lavoro indicato non esiste |
| `405`  | `/backup/restore` chiamato con un metodo diverso da `POST`                         |
| `413`  | Il corpo del caricamento supera gli 8 GiB, per content-length dichiarato o per byte effettivamente letti |
| `426`  | Qualsiasi richiesta diretta a una route di trasferimento sul listener HTTP pubblico; usa il tunnel delle risorse cifrato di un client associato |
| `500`  | L'esportazione o l'archiviazione non è riuscita lato server                        |

Tutti e tre i download rispondono con `Cache-Control: no-store` e `Accept-Ranges: none`.
`/backup/workspace` e `/backup/snapshot` generano una copia **nuova** per ogni richiesta e
la eliminano dopo averla trasmessa in streaming, quindi una risposta in cache o ripresa
unirebbe i byte di due esportazioni diverse in un unico file che sembra valido e non lo è.

`/backup/stored` è l'eccezione: trasmette in streaming un backup pianificato come
`<workspaceId>-<name>.db` e lascia il file al suo posto, perché quel file è il backup.

`/backup/snapshot` restituisce `<name>.zip`, con voci relative alla radice
dell'istantanea, così l'estrazione riproduce `manifest.json` + `global.db` +
`<workspaceId>/workspace.db`. Le voci vengono scritte in ordine, quindi due archivi
della stessa istantanea sono lo stesso archivio.

`/backup/restore` trasmette il corpo direttamente in un file temporaneo anziché
bufferizzarlo, lo limita prima e durante la lettura, ed elimina il file temporaneo su
**ogni** percorso di uscita, compreso un rifiuto.

::::caution[La connessione diretta e il relay usano lo stesso trasferimento cifrato]
Il relay trasporta richieste di risorse, risposte in streaming e byte di caricamento
come testo cifrato; non può leggere il contenuto dei backup. Un percorso lato server
resta un percorso sull'host del server, non un file sul relay. L'accesso richiede
comunque il dispositivo associato, la firma della destinazione e il ruolo applicabile
di spazio di lavoro o installazione. Nessuno dei due trasporti cifra a riposo i file
di backup risultanti.
::::

## Percorsi e limiti

| Elemento                        | Valore                                                       |
| ------------------------------- | ------------------------------------------------------------ |
| Istantanee                      | `<dataDir>/backups/<timestamp>/`                             |
| Backup pianificati degli spazi di lavoro | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Esportazioni degli spazi di lavoro | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`  |
| Database sostituito da un ripristino | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Database com'erano prima che un aggiornamento cambiasse il loro formato | `<dataDir>/pre_upgrade/` e `<dataDir>/<workspaceId>/pre_upgrade/`, i due più recenti di ciascuno |
| Staging dei trasferimenti       | `<dataDir>/backups/transfer/` — un banco di lavoro, ripulito dalla route che lo scrive |
| Nome dell'archivio dell'istantanea | `<snapshot directory name>.zip`                           |
| Limite di caricamento           | 8 GiB per caricamento cifrato verso `/backup/restore`        |
| Conservazione                   | Istantanee dell'installazione: eliminazione manuale. Backup degli spazi di lavoro: pipeline settimanale, 30 giorni per impostazione predefinita, o eliminazione manuale. Backup di uno spazio di lavoro eliminato: solo eliminazione manuale |

Le directory `exports/`, `transfer/` e `workspace-backups/` non sono istantanee
dell'installazione e sono escluse da `server.listBackups`. Solo l'ultima directory ha
una conservazione pianificata, e solo finché il suo spazio di lavoro esiste;
l'eliminazione di un'istantanea dell'installazione richiede l'azione esplicita del
