Control Center può inviare **eventi di utilizzo pseudonimi** a un'istanza di [Umami](https://umami.is). Le statistiche di utilizzo sono **disattivate finché l'operatore del server non le attiva**. L'impostazione appartiene al server e si applica a ogni client connesso: l'app desktop, l'app web, il telefono e il server stesso.

Le statistiche di utilizzo sono distinte da **Condividi i rapporti di arresto anomalo**, un'impostazione per singolo dispositivo dedicata alla diagnostica di arresti anomali ed errori.

## Chi decide

| Interruttore | Dove | Effetto |
| --- | --- | --- |
| **Condividi le statistiche di utilizzo** | Onboarding (passaggio del sandbox) e **Impostazioni → Privacy**. Solo l'operatore del server può modificarlo; gli altri membri vedono il valore attuale in sola lettura | Per tutto il server. Salvato come `telemetry.usage_analytics` nelle impostazioni del server. Disattivato se non è impostato a `true` |
| Tipo di build | Automatico | Le build di debug e di profiling non inviano nulla. Scrivono invece ogni evento nel log di debug |
| `CC_ANALYTICS_DEBUG=1` | Ambiente di `cc_server` o il suo `.env` | Consente alle build di debug e di profiling del server, e di ogni client connesso, di inviare davvero gli eventi, a scopo di test. L'interruttore precedente deve comunque essere attivo |
| `DO_NOT_TRACK=1` | Ambiente di `cc_server` | Interrompe l'invio da parte del server stesso, qualunque sia il valore dell'interruttore. I client continuano a seguire l'interruttore |
| Server demo | Automatico | Il server demo pubblico non invia nulla di suo. I visitatori non possono modificare l'interruttore |

I client leggono l'impostazione dal server (`telemetry.config`, poi in tempo reale tramite `telemetry.watch`). Finché la risposta non arriva, gli eventi attendono in un piccolo buffer in memoria. Se la risposta è no, il buffer viene scartato. Disattivare l'interruttore scarta tutto ciò che è ancora in coda e interrompe subito l'invio, su ogni client.

## Cosa non viene mai inviato

- Contenuto di messaggi, ticket, revisioni o riunioni, titoli, prompt, comandi di shell e query di ricerca
- Nomi, login, indirizzi email, avatar e nomi visualizzati
- Percorsi di file, nomi di repository, nomi di branch, nomi host e URL (un repository viene inviato solo come `repo_id` pseudonimo; il link di una riunione solo come nome del suo provider)
- Identificatori grezzi di qualsiasi tipo

Ogni evento passa attraverso una policy sulle proprietà prima di lasciare il processo. Testi, percorsi, URL, indirizzi email, ID non incapsulati e stringhe sotto chiavi come `email`, `*_name`, `path`, `title`, `prompt`, `content` o `token` vengono scartati anziché inviati. Una stringa viene inviata solo se è un token breve di un vocabolario chiuso, come un valore enum, una versione, una lingua o un ID di modello.

## ID pseudonimi

Gli ID vengono inviati, ma solo come pseudonimi. Ogni ID di spazio di lavoro, spazio, conversazione, agente, esecuzione, utente e dispositivo viene sostituito da un HMAC-SHA256 calcolato con il sale segreto dell'installazione (`telemetry.pseudonym_salt`), troncato a 20 caratteri esadecimali. Lo stesso spazio di lavoro riporta sempre lo stesso valore, quindi gli eventi possono essere collegati e contati, ma l'ID grezzo non lascia mai l'installazione. Il sale viene creato al primo avvio del server e non viene mai inviato al fornitore di statistiche. Eliminare la directory dei dati del server crea un nuovo sale e un nuovo ID di installazione, scollegando tutto ciò che è stato registrato in precedenza.

## Visualizzazioni di schermate

Ogni navigazione registra una visualizzazione di pagina il cui URL è il **modello di route**, ad esempio `/workspaces/:workspaceId/spaces/:spaceId`, mai l'indirizzo concreto. Il nome della schermata è formato dai segmenti letterali del modello, quindi nell'esempio è `workspaces_spaces`. I parametri di route che terminano in `Id` vengono allegati come proprietà pseudonime `*_id`, e quelli numerici (come il numero di una PR) come numeri. Tutti gli altri parametri vengono scartati.

## Consegna

Gli eventi vengono inviati uno alla volta a `<host>/api/send` da una coda in memoria che contiene fino a 200 eventi. Un errore di rete, un timeout, un `429` o un `5xx` conservano l'evento e lo ritentano con un backoff esponenziale, da 1 secondo fino a 5 minuti. Qualsiasi altro `4xx` lo scarta. Nulla viene scritto su disco, quindi gli eventi ancora in coda quando l'app si chiude vanno persi. La coda viene svuotata quando l'app passa in background e quando il server si arresta.

## Puntare una build a un'altra istanza

La destinazione è fissata al momento della build:

```bash
--dart-define=CC_ANALYTICS_HOST=https://analytics.example.com/
--dart-define=CC_ANALYTICS_WEBSITE_ID=<website uuid>
```

L'adattatore del fornitore si trova in `packages/cc_analytics`. Per supportare un altro servizio di statistiche basta aggiungere lì un adattatore. Il piano di tracciamento e le regole sulla privacy restano gli stessi.
