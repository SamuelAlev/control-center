description: Why an agent is shown a small set of tools rather than all of them, how it reaches the rest, and the rules that keep the provider's prompt cache warm across a run.
---

Two things are true of every request the built-in harness makes: the tool definitions are the largest fixed cost in it, and almost none of them will be used. This page explains what Control Center does about that, and why the answer is not simply "send fewer tools".

## The problem is attention, not bytes

Control Center has about 160 tools of its own. Sent in full, their definitions would ride along on **every request** — a cost no compaction can touch, because tool definitions travel in a separate part of the request from the conversation.

The token bill is the obvious complaint, and with prompt caching it is also the smaller one. The real cost is **selection accuracy**. Published evaluations of tool-calling agree that models pick the right tool reliably up to somewhere around 30–50 tools in context, and get progressively worse beyond that. The named cause is not the token count but **semantic overlap**: once a catalogue contains several tools whose descriptions read alike, the model is choosing between look-alikes rather than recalling a capability.

At about 160 tools, an agent is well past that band on every single turn — including the many turns where it only needed to read a file.

## One small direct set

A run is therefore shown two things:

- a **direct** set of about fifteen tools, sent with full schemas on every request;
- a **name index** of everything else, grouped under headings like "Tickets and projects" or "Memory and knowledge", costing a few hundred tokens for the whole catalogue.

Measured on the registry the tests build, the built-in agent's standard chat tools come to 14 tool definitions and about 16.5 KB with `repl`, of which `repl` is about 4 KB (its definition may not exceed 4,096 bytes), and to 14 definitions and about 13 KB on a server that cannot run scripts. That is a measurement of one surface, not of every install. Every other tool is reached from a script or loads on first use.

The direct set is the tools most runs use in their first turns and the ones a run must never have to look for: `read`, `write`, `edit`, `search`, `find`, `bash` and `read_output`; `ask_user` and `task`; `todo_write`, `search_memory` and `send_message`; and whatever verb the current [mode](/manual/concepts/modes) must call to deliver its output. A mode's own output verb is always direct — a run must never have to go looking for the one call that produces its deliverable. A tool earns a place by being used in most runs, not by being important when it is used: every name in the set is a definition on every turn of every run.

### Scripts reach the rest

When the server can run scripts, every run also has [`repl`](/manual/concepts/code-mode/), first in the list. The rule for the rest of the catalogue is then:

- a tool a script may call is reached **only from a script**: it is in the name index, and a `repl` script calls it as `tools.<name>(args)` after looking it up with `searchTools()` or `describeTool()`, until the server cannot run the run's scripts and it loads on first use instead ([When scripts cannot run](/manual/concepts/code-mode/#when-scripts-cannot-run));
- a tool a script may not call (`eval`, `task`, approvals, delegation and a few others) is **deferred**: it loads on first use, as described below;
- `search_tools` is added when anything is deferred.

A run without `repl` gets the same direct set, and everything else is deferred.

The direct set is the same with or without `repl`, on purpose. The agent learns one surface, the head of every request is the same tools in the same order, and adding `repl` changes nothing the agent already relied on.

What it saves: a script-only tool's schema is never sent to the provider, so the hundred or so tools outside the direct set cost only their names. A script that needs ten of them pays for none of their schemas, and its intermediate results never enter the context.

What it costs: a tool outside the direct set takes a script to call, and the script has to look up the tool's arguments first. For one quick call that is an extra step a direct call would not need. That is why the tools most runs call in their first turns stay direct.

### Deferred does not mean unavailable

This is the part that makes the design safe rather than merely cheap. **A deferred tool is callable from the first turn.** Only its schema is withheld.

The agent sees the name in its prompt. If it calls that name directly, the harness loads the schema and runs the tool in the same step — no error, no round trip. The model does not need to know that the tool was ever "unloaded".

When the agent knows the task but not the name, `search_tools` takes a plain-language description ("assign a ticket to someone"), ranks the run's whole surface, and returns the matches *with their schemas already loaded*, so the very next turn can call one. A match that is callable only from a script is returned with how to call it from a script instead, unless the run's scripts can no longer run: then it loads like any other match. If a search finds nothing, it says so plainly and suggests different wording or a wider search — deliberately, because an agent that reads an empty search as "this capability does not exist" will invent a substitute instead of looking again.

`search_tools` exists only in the built-in harness. External MCP clients have `search_tool_bm25` instead, which ranks the same index but only describes matches — those clients already received every schema from `tools/list`, so there is nothing to load.

### What the surface never does

Deferral and scripts are applied **after** the mode's tool filter, never instead of it. They hide a schema; they cannot reveal a tool the mode denied. A loaded tool and a script's call still pass the approval prompt and the [action guardrails](/manual/concepts/guardrails) exactly as a direct call would, and neither can reach a name that was not on the run's surface to begin with.

The MCP surface external clients see is **not** deferred. `tools/list` returns the complete catalogue, because MCP clients validate tool names against their own cached list and refuse anything unlisted without ever asking the server, so a "hidden but callable" tool would be simply unreachable. Deferral lives in the harness, where loading a tool mid-run is something the harness can actually do.

An agent run that reaches Control Center through its MCP endpoint while the server can run scripts is the one exception. Its `tools/list` holds `repl`, the direct tools and every tool a script may not call, and it calls the rest from scripts. A direct call to one of those is answered with how to call it from a script.

### Turning deferral off

`--tool-deferral=off` (or `CC_SERVER_TOOL_DEFERRAL=off`) turns deferral off: a run without `repl` gets every admitted tool in full, and a run with `repl` gets the tools a script may not call in full while the rest stay script-only. See the [`cc_server` CLI reference](/manual/reference/cc-server-cli).

## Prompt caching

Agent workloads are lopsided: they send enormous prompts and receive small answers, turn after turn, with the same prefix each time. Providers cache that prefix, and a cache read costs about a tenth of a fresh one. Cache hit rate is therefore a first-class property of the harness rather than an optimisation — and on Anthropic it also buys throughput, because cached tokens do not count against the per-minute input limit.

Caching works on an exact prefix match, which yields one governing rule.

### Never rewrite what was already sent

Any byte that changes invalidates the cache from that point onward. So the harness only ever **appends**: new messages at the end, and newly activated tool schemas *after* the cached tool block rather than merged into it. That ordering is the reason activation is cheap — the cached prefix stays identical and the run pays only for the schemas it just loaded.

The loop also trims stale tool output from older turns to reclaim context. It
waits until there is enough to reclaim to be worth the rewrite, so a trim is a
rare deep rewrite instead of a continuous cache miss.

### Where the breakpoints go

A provider allows a limited number of cache markers, and Control Center spends them deliberately:

| Marker                       | Covers                             | Lifetime |
| ---------------------------- | ---------------------------------- | -------- |
| Last **direct** tool         | The tool block                     | 1 hour   |
| Last system block            | Tools + system prompt              | 1 hour   |
| Previous turn's tail         | History up to the last request     | 5 min    |
| Current turn's tail          | The full history                   | 5 min    |

The last two are a rolling pair, and the reason for the pair is subtle: a cache lookup searches backwards a bounded number of blocks for something an earlier request stored. A single turn that runs many tools in parallel can emit more blocks than that window, at which point one tail marker quietly misses and the request pays full price with nothing in the response to say so. Marking the exact spot the previous request stopped makes the hit structural instead of a race.

The tools-and-system prefix takes the long lifetime because it is constant for the whole run, is shared by every run and subagent with the same shape, and because the clock starts when a request *begins* — a turn that streams for several minutes has already spent most of a short window before the next request forms.

### Subagents share one prefix

Subagents of the same type produce byte-identical prompt prefixes, so they should read one cache entry rather than each writing their own. But an entry only becomes readable once the request that wrote it starts responding, so a fan-out launched all at once has every child paying the premium for a prefix they all share.

The harness lets the first child of a given shape start, then releases its siblings as soon as it begins streaming. The wait is bounded: a slow first child costs a cache hit, never the fan-out itself. For the same reason, every subagent gets the same direct tool set regardless of its profile — varying it per profile would fragment the shared prefix for no gain, since the profile has already decided what the child may call.

## Watching it work

Both halves are observable rather than assumed:

- The **context explorer** on a conversation reports the direct tools, the deferred index and what each withheld schema *would* cost, built from the same code path a real run uses.
- Each run records which deferred tools it loaded and what triggered it, so a search that finds nothing is visible as a retrieval miss rather than disappearing into an agent quietly doing something adjacent.
- Observability reports **Cache rate** as cache reads over all prompt tokens processed, cache writes included — a run that keeps rebuilding its prefix scores low, instead of scoring like one that never needed a cache.
