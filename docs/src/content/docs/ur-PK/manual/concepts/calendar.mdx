Control Center Google Calendar سے جڑتا ہے تاکہ آپ کا دن آپ کے fleet کے ساتھ رہے۔ یہ آپ کے events کو sync کرتا ہے، انہیں month، week، day اور agenda views میں دکھاتا ہے، events بنانے، منتقل کرنے، ان کا جواب دینے اور انہیں حذف کرنے دیتا ہے، میٹنگ شروع ہونے سے پہلے خبردار کرتا ہے، اور کسی بھی event کو ایک ریکارڈ شدہ اور خلاصہ شدہ [میٹنگ](/ur-PK/ہدایت-نامہ/تصورات/میٹنگز/) میں بدل سکتا ہے۔

## Google پر یہ کیا بدلتا ہے

صرف وہی جو آپ خود کریں۔ آپ دعوت نامے کا جواب دے سکتے ہیں، ایک event بُک کر سکتے ہیں (time grid پر ڈریگ کر کے یا **+** بٹن سے) اور event حذف کر سکتے ہیں۔ ہر تبدیلی سرور آپ کے اپنے account کے sign-in سے، آپ کے اپنے calendars میں کرتا ہے، اور سرور کسی دوسرے رکن کے account پر یا کسی ایسے shared calendar پر event کو رد کرتا ہے جو آپ کے ساتھ صرف پڑھنے کے لیے بانٹا گیا ہو۔ Google مہمانوں کو ای میل بھیجتا ہے، جیسے Google Calendar سے بھیجتا ہے۔ کسی recurring event کے ایک occurrence کو حذف کرنے سے باقی سلسلہ برقرار رہتا ہے۔ آپ grid پر کسی event کو منتقل یا پھیلا سکتے ہیں؛ صرف آپ کے اپنے events اور وہ جنہیں آپ منظم کرتے ہیں منتقل ہوتے ہیں۔

ہر connect، چاہے Connect کے ذریعے ہو یا سرور کے اپنے Google client کے ذریعے، `calendar.events` (events پڑھنا اور بدلنا) اور `calendar.calendarlist.readonly` (دیکھنا کہ account کے پاس کون سے calendars ہیں) کے ساتھ `openid email` کی درخواست کرتا ہے۔ سرور ایسا sign-in قبول نہیں کرتا جو کسی اور مجموعے کے ساتھ واپس آئے، اس لیے پچھلے read-only scope کے ساتھ جڑا ہوا account دوبارہ جوڑنا ہوگا۔

events **سرور پر** workspace کے اپنے database (`<dataDir>/<workspaceId>/workspace.db`) میں sync ہوتے ہیں، اور ہر کلائنٹ انہیں RPC کے ذریعے دکھاتا ہے۔ کوئی کلائنٹ Google credential نہیں رکھتا۔

## فی workspace accounts

calendar accounts، Control Center کی باقی ہر چیز کی طرح، workspace کے دائرے میں ہوتے ہیں، اور ہر ایک اس رکن کا ہے جس نے اسے جوڑا۔ ہر [workspace](/ur-PK/ہدایت-نامہ/تصورات/ورک-اسپیسز/) اپنے Google accounts جوڑتا ہے، اور ایک workspace کے events اور credentials کبھی دوسرے سے نظر نہیں آتے۔ دو ارکان جو ایک ہی Google پتہ جوڑیں ان کے دو accounts بنتے ہیں۔ workspace بدلنے سے یہ بدلتا ہے کہ آپ کون سے calendars دیکھتے ہیں۔

ایک workspace **کئی** Google accounts جوڑ سکتا ہے، جیسے ایک کام کا اور ایک ذاتی، اور ان کے events ایک ہی views میں ضم ہو جاتے ہیں۔

## sign-in سرور تک کیسے پہنچتا ہے

جوڑنا ایک براؤزر sign-in ہے، اور سرور اسے مکمل کرتا ہے۔ کون سا کلائنٹ اسے چلائے، یہ سرور کے مالک کا انتخاب ہے:

- **سرور کا اپنا Google client۔** ایک Web application client جو `<server origin>/oauth/google/callback` redirect کے ساتھ رجسٹر ہو۔ Google براؤزر کو سیدھا سرور پر واپس بھیجتا ہے، اس لیے براؤزر کو اس تک پہنچنا ہوگا
- **Control Center Connect۔** Google براؤزر کو Connect پر واپس بھیجتا ہے، جو 8 حروف کا کوڈ اور ایک `control-center://` لنک دکھاتا ہے۔ شخص کوڈ app میں ٹائپ کرتا ہے، یا لنک پر جاتا ہے، اور سرور اسی سے sign-in claim کرتا ہے۔ اس کے لیے سرور کو عوامی پتے کی ضرورت نہیں، اور یہی وجہ ہے کہ نجی نیٹ ورک پر ایک headless سرور calendars جوڑ سکتا ہے

اپنا client ہمیشہ مقدم ہوتا ہے۔ بغیر secret کے client id ایک نامکمل سیٹ اپ ہے اور sign-ins رد کرتا ہے، Connect پر واپس نہیں جاتا۔

اعتبارنامے کبھی سرور سے باہر نہیں جاتے۔ یہ سرور کی data directory میں `secrets.json` میں لکھے جاتے ہیں، `google_google:<workspaceId>:<userId>:<email>` کی کلید کے ساتھ، databases کے ساتھ اور اسی host-filesystem trust boundary کے تحت۔ اپنے client سے sign-in اپنے access اور refresh tokens محفوظ کرتا ہے۔ Connect کے ذریعے sign-in صرف ایک sealed credential محفوظ کرتا ہے جسے Connect صرف اس سرور کے لیے کھولتا ہے؛ access token memory میں رہتا ہے۔ سرور access خودکار طور پر refresh کرتا ہے، اور جب Google کسی account کو مستقل طور پر باطل کر دے (منسوخ یا بہت پرانا session)، تو `CalendarAuthExpired` شائع کرتا ہے اور خاموشی سے ناکام ہونے کے بجائے **reconnect** بینر دکھاتا ہے۔ وہ sign-in جو یہ سرور اب استعمال نہیں کر سکتا (کسی اور اپنے client نے جاری کیا، یا کسی اور install یا Connect کے لیے sealed ہے) اگلی بار پڑھے جانے پر صاف ہو جاتا ہے اور وہی بینر دکھاتا ہے۔

کوئی build Google credentials ساتھ نہیں رکھتا۔ سرور کا client **ترتیبات → سرور → سنگل سائن آن → فراہم کنندہ ایپس** سے یا سرور کی `.env` فائل سے آتا ہے (`GOOGLE_OAUTH_CLIENT_ID`، `GOOGLE_OAUTH_CLIENT_SECRET`)۔ جان بوجھ کر کوئی command-line فلیگ نہیں ہے: کمانڈ لائن پر secret `ps` سے پڑھا جا سکتا ہے، اور سرور شروع ہونے سے انکار کرتا ہے جب secret اس کے process ماحول میں ایکسپورٹ ہو۔

اپنا Google پروجیکٹ چلانے کے لیے دیکھیں [Google Calendar جوڑیں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/کیلنڈر-جوڑیں/)۔

## مطابقت سازی

سرور ہر جڑے ہوئے account کے events کی ایک متحرک window ہر **دو منٹ** بعد کھینچتا ہے — account کا ہر calendar، صرف primary نہیں — اور مانگنے پر بھی (شروع، connect، دستی refresh)۔ یہ مختصر وقفہ اس لیے مقرون بہ صرفہ ہے کیونکہ بررسی افزائشی ہے: ہر calendar اپنا sync token رکھتا ہے، اس لیے بغیر تبدیلی والا calendar پانچ ماہ کی window دوبارہ لانے کے بجائے ایک تقریباً خالی جواب کی لاگت رکھتا ہے۔

دہرائے جانے والے events سرور پر کھولے جاتے ہیں، اس لیے کوئی کلائنٹ کبھی recurrence rule کا تجزیہ نہیں کرتا۔ موجودہ window سے باہر کے مہینے پر جانا اس بازے کو سست بارگی سے لوڈ کرتا ہے۔ حذف شدہ یا window سے باہر جانے والے events اگلے sync پر صاف ہو جاتے ہیں۔

## مناظر

| View           | کیا دکھاتا ہے                                              |
| -------------- | ---------------------------------------------------------- |
| **مہینہ**      | پورے مہینے کا grid (`kalender` package کے ذریعے)            |
| **ہفتہ**       | ایک ہفتے کے وقت والے events ایک time-grid میں               |
| **دن**        | ایک دن کے وقت والے events ایک time-grid میں                 |
| **ایجنڈا**     | آنے والے events کی scrollable فہرست                          |

کیلنڈر `/calendar` پر کھولیں؛ کوئی event چننے سے اس کی تفصیل `/calendar/:eventId` پر کھلتی ہے۔ آپ جو view چنتے ہیں وہ اس کلائنٹ کی اپنی ترجیحات میں محفوظ ہوتا ہے، اس لیے وہ کسی اور آلے پر نہیں جاتا۔

## میٹنگ الرٹس

ایک فی منٹ scheduler ان events کو دیکھتا ہے جو قابلِ ترتیب lead window میں شروع ہونے والے ہوں، اور **"meeting starting soon"** اعلان فائر کرتا ہے (ایک `MeetingStartingSoon` [domain event](/ur-PK/ہدایت-نامہ/تصورات/ڈومین-ایونٹس/))۔ اعلان موجود ہو تو join URL ساتھ لاتا ہے، اور اس پر کلک کرنے سے event کی تفصیل کھلتی ہے۔ اس اعلان کے **میٹنگ میں شامل ہوں** اور **شامل ہوں اور ریکارڈ کریں** اعمال، ایپ کے اندر بینر اور OS نوٹیفکیشن دونوں پر، event کو پہلے کھولے بغیر کال کھولتے ہیں؛ جس event میں کال کا لنک نہ ہو، وہاں اس کے بجائے **میٹنگ ریکارڈ کریں** پیش کیا جاتا ہے۔ الرٹس event کے `alertedAt` کے خلاف deduplicate ہوتے ہیں، اس لیے وہی میٹنگ دو بار الرٹ نہیں کرتی، یہاں تک کہ restarts کے بعد بھی، اور وہ event جس کا آغاز اس وقت گزر گیا جب ایپ بند تھی کبھی دوبارہ نہیں چلتا۔

دو حدیں آسانی سے غلطی میں پڑ جاتی ہیں۔ scheduler **کلائنٹ کی طرف desktop پر** چلتا ہے اور صرف اس workspace کے لیے جو آپ اس وقت کھولے ہوئے ہیں — جس workspace میں آپ نہیں، وہ کوئی الرٹ نہیں اٹھاتا۔ اور web build میں سرے سے OS-notification pipeline نہیں ہے، اس لیے وہ بھی کوئی الرٹ نہیں اٹھاتا۔

## ریکارڈ اور لنک

کسی calendar event سے آپ ایک [میٹنگ ریکارڈنگ](/ur-PK/ہدایت-نامہ/تصورات/میٹنگز/) شروع کر سکتے ہیں جو event کے عنوان سے شروع ہو۔ Control Center ریکارڈنگ اور event کے درمیان ایک سے ایک لنک محفوظ کرتا ہے، تاکہ میٹنگ کے نوٹس اور calendar کی entry بغیر اس کے کہ کوئی ایک فیچر دوسرے پر منحصر ہو جڑے رہیں۔

**شامل ہوں اور ریکارڈ کریں** صرف desktop پر ہے۔ web کلائنٹ پر یہ عمل بتاتا ہے کہ ریکارڈنگ دستیاب نہیں ہے — حالانکہ میٹنگز کی اسکرین کا اپنا ریکارڈ فلو براؤزر میں کام کرتا ہے۔

:::note[ایجنٹس آپ کا calendar نہیں پڑھ سکتے]
کوئی calendar MCP tool نہیں ہے۔ ایک ایجنٹ events کی فہرست نہیں بنا سکتا، کسی event کی تفصیلات نہیں پڑھ سکتا، یا آپ کی جانب سے event بنا، منتقل یا حذف نہیں کر سکتا، یا RSVP نہیں کر سکتا؛ `calendar.*` سطح صرف انسانی کلائنٹس کے لیے RPC ہے۔
:::
