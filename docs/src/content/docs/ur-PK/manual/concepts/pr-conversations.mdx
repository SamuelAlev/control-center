pull request میں پہلے ہی کوڈ کے بارے میں گفتگو ہوتی ہے۔ PR گفتگوئیں اسے Control Center workspace کی ایک سطح بنا دیتی ہیں، بالکل جیسے ایک [chat bridge](/ur-PK/ہدایت-نامہ/تصورات/چیٹ-برجز/) Slack کو ایک بناتا ہے: PR پر `@usectrl` (یا workspace کے GitHub App کے بوٹ) کو mention کریں، اس کے ریویو تھریڈز میں جواب دیں، یا `ai-review` لیبل شامل کریں، اور کام PR کی review space میں ہوتا ہے — اسی انتساب اور guardrails کے تحت جو ایپ میں ٹائپ کیے گئے کسی بھی پیغام پر لاگو ہوتے ہیں۔ تبصرہ اور لیبل ایک ہی طریقے سے محدود ہیں: اس رکن پر جس نے اسے لکھا یا شامل کیا۔ جوابات GitHub پر واپس آتے ہیں، اسی lane میں جہاں سوال پوچھا گیا تھا۔

تین فیصلے اس فیچر کو شکل دیتے ہیں، اور ہر ایک وہی فیصلہ ہے جو chat bridge نے chat کے لیے کیا تھا، یہاں ایک forge کے لیے دوبارہ بیان کیا گیا: **کنکشن کس سمت میں چلتا ہے**، **باہر سے آنے والا تبصرہ کیا چیز مجاز کرتی ہے**، اور **گفتگو کا ہر فریق کس سے منسوب ہے**۔

## polling ہی ٹرانسپورٹ ہے

GitHub کا ایپ کے لیے واحد push چینل webhook ہے، اور webhook کو ایک inbound URL درکار ہے — وہی چیز جو یہ سطح جان بوجھ کر کبھی نہیں مانگتی۔ اس لیے دریافت ایک sweep ہے: ہر ایپ انسٹالیشن کے لیے ایک aliased search GitHub سے وہ PRs مانگتی ہے جو بوٹ (یا اس کا مختصر slug) کو mention کرتے ہیں اور وہ کھلے PRs جن پر ریویو لیبل ہے؛ جن PRs کی پہلے سے review space ہے ان کی تبصرہ تھریڈز پڑھی جاتی ہیں، اور سب کچھ comment id کے ذریعے پچھلے sweep میں دیکھی گئی چیزوں سے diff ہوتا ہے۔ اپنی app ہر منٹ زیادہ سے زیادہ 25 PRs پر sweep کرتی ہے۔ Connect کے ذریعے کالیں ہر رکن کے اپنے GitHub کوٹے پر چلتی ہیں، اس لیے sweep ہر دو منٹ زیادہ سے زیادہ 10 PRs پر چلتا ہے، اور جو workspace اپنے کوٹے کا 15% سے کم رکھتا ہو وہ بحال ہونے تک چھوڑ دیا جاتا ہے۔ Connect خود کبھی PR کا مواد نہیں دیکھتا۔

ڈیزائن کے نتائج جن کا ذکر ضروری ہے:

- **تاخیر ایک sweep کا وقفہ ہے، واقعہ نہیں۔** 👀 کی تصدیق ایک sweep کے اندر آتی ہے۔ اس پر کوئی فوری چیز منحصر نہیں۔
- **فی تبصرہ بالکل ایک بار۔** comment ids GitHub پر یکتا ہیں؛ ہر ایک اسی لحظے ریکارڈ ہو جاتا ہے جب اسے اہل قرار دیا جائے، کسی بھی کارروائی سے پہلے۔ کوئی خرابی تبصرے کے ہینڈلنگ کو کھو سکتی ہے، کبھی دو بار فائر نہیں کرتی۔
- **آف لائن وقت پورا کیا جاتا ہے، دوبارہ چلایا نہیں جاتا۔** دیکھے گئے سیٹ کو محفوظ کیا جاتا ہے، اس لیے restart وہ دیتا ہے جو بند ہونے کے دوران آیا تھا۔ واحد استثنا پہلا sweep ہے: جب مقابلے کے لیے کوئی یادداشت نہ ہو، تو ہر زیرِ التوا چیز خاموشی سے ریکارڈ ہو جاتی ہے — ایک آپریٹر جس نے اس سرور کے وجود میں آنے سے پہلے بیس PRs کو لیبل کیا ہو، اسے بیس چلتے ہوئے ریویوز واپس نہیں ملنے چاہئیں۔
- **لیبل ایک سیٹ ہے، واقعہ نہیں۔** سرچ لیبل کی _موجودگی_ رپورٹ کرتی ہے، اس لیے لیبل والا PR ایک بار، ہمیشہ کے لیے، فائر کرتا ہے۔ ہٹا کر دوبارہ شامل کرنا sweep کو نظر نہیں آتا؛ mention دوبارہ چلانے کا راستہ ہے۔

سرچ ہر انسٹالیشن اکاؤنٹ کے لیے اس مالک کے اپنے کلائنٹ پر ایک بار چلتی ہے، کیونکہ ایک ٹوکن صرف اپنی انسٹالیشن کے repos دیکھتا ہے — ایک سرور گیر اکیلا credential خاموشی سے ایپ کی دوسری انسٹالیشنز کے تمام PRs کھو دیتا۔

## عضویت اجازت دیتی ہے، تبصرہ نہیں

PR تبصرہ ایک مصنف کے ساتھ آتا ہے — ایک غیر تصدیق شدہ بیرونی شناخت جب تک ثابت نہ ہو۔ سرور مصنف کے نہ بدلنے والے عددی GitHub account id کو حل کرتا ہے (کبھی login کو نہیں، جو بدلا یا دوبارہ استعمال کیا جا سکتا ہے) workspace کے اراکین کے GitHub sign-ins کے خلاف، جو TTL پر دوبارہ بنائے جاتے ہیں کیونکہ لوگ سرور چلتے وقت sign in اور مدعو ہوتے ہیں۔ `ai-review` لیبل کے لیے، حل شدہ شخص وہ ہے جس نے اسے آخری بار شامل کیا۔

تین جانچیں، ترتیب سے، اور ان میں سے کسی ایک میں ناکامی خاموش ہے — کچھ پوسٹ نہیں ہوتا:

- **sign in رکن۔** اکاؤنٹ _اس_ workspace کے رکن کا ہونا چاہیے جو اس سرور پر GitHub میں sign in ہو
- **نقش نوشتن۔** `viewer` اور `guest` کام شروع نہیں کر سکتے
- **push کی رسائی۔** جوابات ایک `bot` ٹوکن استعمال کرتے ہیں جو اس رکن کی repository تک رسائی تک محدود ہو۔ اگر سرور ایسا ٹوکن جاری نہ کر سکے تو آگے نہیں بڑھتا

ہر جانچ کسی بھی تصدیق سے پہلے چلتی ہے، اس لیے اجنبی کو نہ کوئی ردعمل ملتا ہے نہ جواب۔ کوئی تبصرہ کبھی ایسے شخص سے منسوب نہیں ہوتا جس نے اسے نہ بھیجا ہو، اور کسی اجنبی کے الفاظ کبھی ایسی workspace میں داخل نہیں ہوتے جسے وہ دیکھ نہیں سکتا۔

### دعویٰ

کسی بھی کام سے پہلے آخری قدم 👀 ری ایکشن ہے، جو مصنف کے اپنے GitHub sign-in کے ساتھ شامل ہوتا ہے۔ GitHub ایک نئے ری ایکشن کے لیے `201` اور پہلے سے موجود کے لیے `200` دیتا ہے، اس لیے ری ایکشن ایک lock کا بھی کام کرتا ہے: جب وہی شخص دو سرورز پر sign in ہو جو دونوں repository کو جوڑتے ہوں، تو صرف پہلا جو ری ایکٹ کرے کام کرتا ہے۔ ایک تبصرہ جو ایک سرور پر کئی workspaces دیکھیں، ہر ایک کو پیش کیا جاتا ہے، اور وہی claim فیصلہ کرتا ہے۔

## دو شناختیں، جان بوجھ کر

گفتگو کا ہر فریق ایک مختلف شناخت رکھتا ہے، اور یہ فرق ہی فیچر ہے:

- **GitHub پر، جواب آپ کی جانب سے خودکار عمل ہے۔** ہر جواب اس ایک repository کے لیے `bot` ٹوکن پر جاتا ہے، جو پوچھنے والے رکن کی رسائی تک محدود ہے۔ اپنی app پر مصنف app کا `[bot]` اکاؤنٹ ہوتا ہے۔ Connect کے ذریعے مشترکہ App کے لیے ٹوکن یوزر ٹوکن ہوتا ہے، اس لیے جواب پوچھنے والے رکن کے اکاؤنٹ سے لکھا جاتا ہے، جو App کے ذریعے عمل کرتا ہے۔ دونوں صورتوں میں ہر جواب `**Control Center** (for @login):` سے شروع ہوتا ہے، جو بتاتا ہے کہ کس نے پوچھا اور وہ loop guard کے طور پر بھی کام کرتا ہے۔
- **space میں، سوال آپ کا ہے۔** پیغام اس رکن سے منسوب ہوتا ہے جس کو مصنف نے حل کیا، اور ایجنٹ کا run ان کی جانب سے چلتا ہے: کمٹس انہیں co-author کرتے ہیں، اور space کا خودمختاری dial اور action guardrails بالکل اسی طرح لاگو ہوتے ہیں جیسے ایپ میں ٹائپ کیے گئے پیغام پر۔ run سے forge کی تحریریں اس رکن تک محدود ایک-ریپو ٹوکن استعمال کرتی ہیں، کبھی ان کا پورا sign-in نہیں۔

ریویو کے نتائج کو GitHub پر واپس شائع کرنا ایک فرد کا فیصلہ رہتا ہے، جو Control Center میں ہوتا ہے۔ mention ایک ریویو _شروع_ کر سکتا ہے؛ اسے صرف ایک انسان شائع کرتا ہے۔

## loop guard، اور مختصر نام

بوٹ اکاؤنٹ کا لکھا ہوا ہر چیز کسی بھی گیٹ سے پہلے گرا دی جاتی ہے — خصوصاً ہمارا اپنا، اور ہر `[bot]` لاحقہ — اور اسی طرح ہر وہ تبصرہ جو `**Control Center** (for @` سے شروع ہو، کیونکہ Connect کے ذریعے جواب کسی فرد کے اکاؤنٹ سے لکھا جاتا ہے۔ اس کے بغیر جوابات نئے تبصروں کے طور پر آتے اور bridge کو ہمیشہ دوبارہ فعال کرتے رہتے۔

`[bot]` لاحقہ ہی مختصر شکل کے وجود کی وجہ ہے۔ GitHub ایک app اکاؤنٹ کا login `<slug>[bot]` پر طے کرتا ہے، اس کے لیے کوئی خودکار تکمیل نہیں دیتا، اور کبھی `@slug` کو app سے حل نہیں کرتا — اس لیے خالی slug کو قبول کرنا _ہمارے_ matcher کا فیصلہ ہے، اور اسے دریافت کرنے کے لیے GitHub کے mention index کے بجائے خام تبصرہ **متن** کی تلاش کا راستہ درکار ہے۔ قیمت بیان کی گئی ہے، ہموار نہیں کی گئی: ایک انسانی user جو app کا slug رکھتا ہو، اپنے آپ کو ہر مختصر شکل کے mention کے ذریعے بوٹ کو مخاطب کرتا ہے۔ منفرد app نام اس تصادم کو فرضی بنا دیتے ہیں۔

## جو جان بوجھ کر پیش نہیں کیا جاتا

- **خودکار اشاعت نہیں۔** نتائج review space میں آتے ہیں؛ GitHub پر اشاعت ایک الگ، انسانی عمل ہے
- **مبہم شناخت نہیں۔** مصنف یا تو بالکل ایک رکن کو حل ہوتا ہے یا نظرانداز — کوئی اندازے پر مبنی انتساب نہیں
- **خودکار منظوری نہیں۔** خودکارسازی تبصرہ اور تبدیلیاں مانگ سکتی ہے، لیکن `APPROVE` ریویو بھیجے جانے سے پہلے رد کیا جاتا ہے۔ منظوری ایک فرد کا عمل ہے
- **GitHub App کا webhook نہیں۔** یہ سطح کبھی ایک رجسٹر نہیں کرتی، اس لیے PR تبصروں کے لیے کوئی inbound URL ظاہر کرنے کو نہیں۔ دوسرے product webhooks (pipelines، ticket sync) ایک الگ، اختیاری سیٹ اپ ہیں
