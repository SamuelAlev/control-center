## ٹکٹ اسٹیٹس

| اسٹیٹس       | اسٹوریج اسٹرنگ | تفصیل                                            |
| ------------ | -------------- | ------------------------------------------------ |
| `backlog`    | `backlog`      | محفوظ، ابھی فعال قطار میں ٹرائیج نہیں ہوا        |
| `open`       | `open`         | ٹرائیج شدہ اور کام کے لیے تیار، شروع نہیں ہوا     |
| `inProgress` | `inProgress`   | فعال طور پر کام جاری                             |
| `blocked`    | `blocked`      | شروع ہوا مگر کسی بیرونی چیز پر بلاک              |
| `inReview`   | `inReview`     | کام ہو گیا، ریویو کا انتظار                      |
| `done`       | `done`         | کامیابی سے مکمل (ٹرمینل)                         |
| `failed`     | `failed`       | خرابی کے ساتھ مکمل (ٹرمینل)                      |
| `cancelled`  | `cancelled`    | ترک کر دیا گیا (ٹرمینل)                          |

اسٹیٹس ویلیوز camelCase میں محفوظ ہوتی ہیں (`inProgress`، `inReview`)، کبھی `in_progress` نہیں۔ null محفوظ ویلیو `open` کے طور پر پارس ہوتی ہے؛ نامعلوم ویلیو کوسٹ کرنے کے بجائے استثنا پھینکتی ہے۔

`tryParseLoose` ایجنٹ کی فراہم کردہ عرفیات قبول کرتا ہے، اور کیس نیز `-` / `_` / اسپیس نظر انداز کرتا ہے:

| اسٹیٹس      | قبول شدہ عرفیات                               |
| ----------- | --------------------------------------------- |
| `open`       | `todo`, `ready`, `pending`, `new`             |
| `inProgress` | `doing`, `started`, `active`, `wip`           |
| `blocked`    | `stuck`                                       |
| `inReview`   | `review`, `reviewing`                         |
| `done`       | `closed`, `complete`, `completed`, `finished` |
| `failed`     | `error`, `errored`                            |
| `cancelled`  | `canceled`, `abandoned`, `dropped`            |

## اسٹیٹس کی منتقلیاں

```
backlog ──→ open ──→ inProgress ──→ inReview ──→ done
                     │    │           │
                     │    └──→ failed ┘
                     └──→ blocked ──→ inProgress

Any non-terminal status ──→ cancelled; inReview ──→ failed
```

**یہ گراف صرف ایجنٹس اور آٹومیشن کو باندھتا ہے۔** `TicketWorkflowService.transitionStatus` اسے اُس وقت چیک کرتا ہے جب `force` false ہو — یعنی MCP ٹولز اور ری کنسائلرز۔ وہاں غیر قانونی منتقلی لاگ ہو کر نظر انداز کر دی جاتی ہے۔ UI میں صارف کے ہر عمل سے ہونے والی تبدیلی `force: true` بھیجتی ہے اور گراف کو مکمل طور پر نظر انداز کر دیتی ہے، اس لیے کوئی انسان ٹکٹ کو پکر کی فہرست میں موجود کسی بھی اسٹیٹس پر لے جا سکتا ہے (`failed` کے سوا ہر اسٹیٹس)، بشمول کسی ٹرمینل اسٹیٹس کو دوبارہ کھولنا۔ ایجنٹس `failed` کو `fail_ticket` سے نشان زد کرتے ہیں۔

کوئی اسٹیٹس ہمیشہ اپنے آپ میں منتقل ہو سکتا ہے۔ ٹرمینل حالتوں سے باہر جانے والا کوئی کنارہ نہیں ہوتا۔

| سے           | اجازت یافتہ اہداف                                    |
| ------------ | ---------------------------------------------------- |
| `backlog`    | `open`, `cancelled`                                  |
| `open`       | `inProgress`, `blocked`, `cancelled`                 |
| `inProgress` | `blocked`, `inReview`, `done`, `failed`, `cancelled` |
| `blocked`    | `inProgress`, `cancelled`                            |
| `inReview`   | `inProgress`, `done`, `failed`, `cancelled`          |
| `done`       | — (ٹرمینل)                                           |
| `failed`     | — (ٹرمینل)                                           |
| `cancelled`  | — (ٹرمینل)                                           |

## ٹکٹ کی ترجیحات

Linear کے مقامی 0–4 پیمانے پر ایک انٹیجر کے طور پر محفوظ ہوتی ہے۔ نامعلوم ویلیو `none` کے طور پر پارس ہوتی ہے۔

| ترجیح   | محفوظ بطور |
| -------- | --------- |
| `none`   | `0`       |
| `urgent` | `1`       |
| `high`   | `2`       |
| `medium` | `3`       |
| `low`    | `4`       |

## ٹکٹ فراہم کنندگان

نامعلوم یا null محفوظ ویلیو `local` کے طور پر پارس ہوتی ہے۔

| فراہم کنندہ | اسٹیٹس                                                  |
| -------- | ------------------------------------------------------ |
| `local`  | مکمل طور پر ورک اسپیس ڈیٹا بیس میں محفوظ؛ ڈیفالٹ        |
| `linear` | ریموٹ کی ملکیت، مقامی طور پر آئینہ شدہ                   |

سنک اڈاپٹرز `packages/cc_infra/lib/src/tickets/sync/` کے تحت Linear، GitHub Issues، Jira Cloud اور ClickUp کے لیے رہتے ہیں۔ GitHub Issues صرف ایک سنک-اڈاپٹر وینڈر (`vendorId: github`) ہے — یہ کوئی `TicketProvider` ویلیو نہیں، اس لیے GitHub سے کھینچا گیا ایشو `originKind: externalSync` اور ڈیفالٹ `provider: local` کے ساتھ محفوظ ہوتا ہے۔ وینڈر میپنگ `ticket_sync_links` پر رہتی ہے۔

## ٹکٹ کی ابتدا

`createTicket` `manual` لکھتا ہے۔ وینڈر سے آنے والا پل `externalSync` لکھتا ہے۔ تفویض شدہ ذیلی ٹکٹس `manual` رہتے ہیں۔

| ویلیو          | مطلب                                                         |
| -------------- | ------------------------------------------------------------ |
| `manual`       | `createTicket` پر ڈیفالٹ (انسانی، ایجنٹ اور تفویض شدہ قطاریں) |
| `externalSync` | وینڈر پل پر `TicketSyncEngine` کی طرف سے سیٹ                  |

## ٹکٹ کے تعلقات

محفوظ کنارے `ticket_links` میں سمتی قطاریں ہیں:

| قسم          | اسٹوریج اسٹرنگ | مطلب                            |
| ------------- | -------------- | ------------------------------- |
| `blocks`      | `blocks`       | ماخذ ہدف کو بلاک کرتا ہے        |
| `relatesTo`   | `relates_to`   | دوطرفہ تعلق                     |
| `duplicateOf` | `duplicate_of` | ماخذ ہدف کی نقل ہے              |

جو الفاظ UI اور `ticket_relation` استعمال کرتے ہیں وہ `TicketRelationKind` ہے، جو ایک محفوظ کنارے اور اِس بات سے اخذ ہوتا ہے کہ موضوع کس سرے پر بیٹھا ہے:

| قسم           | ماخوذ از                                             |
| ------------- | ---------------------------------------------------- |
| `blockedBy`    | ایک `blocks` قطار جہاں موضوع ہدف ہے                  |
| `blocking`     | ایک `blocks` قطار جہاں موضوع ماخذ ہے                 |
| `relatedTo`    | ایک `relates_to` قطار (دوطرفہ)                       |
| `duplicateOf`  | ایک `duplicate_of` قطار جہاں موضوع ماخذ ہے           |
| `duplicatedBy` | ایک `duplicate_of` قطار جہاں موضوع ہدف ہے            |
| `subIssueOf`   | موضوع پر `tickets.parent_ticket_id`                  |
| `parentOf`     | دوسرے ٹکٹ پر `tickets.parent_ticket_id`              |

والد اور ذیلی ایشو کے لنکس `ticket_links` قطاریں **نہیں** ہیں — وہ `tickets.parent_ticket_id` پر رہتے ہیں۔

## ڈومین ایونٹس

یہ آٹھ کلاسز `packages/cc_domain/lib/core/domain/events/ticketing_events.dart` میں رہتی ہیں۔ کوئی `TicketStarted`، `TicketDelegated`، `TicketCollaboratorAdded` یا `ExternalTicketWebhookReceived` نہیں ہے۔

| ایونٹ                     | کب فائر ہوتا ہے                                    |
| ------------------------- | -------------------------------------------------- |
| `TicketCreated`           | ٹکٹ بنتا ہے                                        |
| `TicketAssigned`          | ٹکٹ کسی پرنسپل یا ٹیم کو اسائن ہوتا ہے             |
| `TicketCompleted`         | کام کامیابی سے مکمل ہوتا ہے                        |
| `TicketFailed`            | کام ناکام ہوتا ہے                                  |
| `TicketCancelled`         | ٹکٹ منسوخ ہوتا ہے                                  |
| `TicketStatusChanged`     | کوئی بھی اسٹیٹس تبدیلی                             |
| `TicketReassigned`        | ٹکٹ دوبارہ اسائن ہوتا ہے                           |
| `TicketDetailsUpdated`    | عنوان، تفصیل، ترجیح یا لیبلز بدلتے ہیں             |

`TicketAssigned` ایک آڈٹ اور اطلاعاتی سگنل اور ایک پائپ لائن ٹریگر ہے۔ کسی ایجنٹ کو اسائن کرنے سے کوئی رن شروع نہیں ہوتا — کوئی ٹکٹ ڈسپیچر ایسا نہیں جو `assignedAgentId` پر نظر رکھے۔ ٹیم کو اسائن کرنا استثنا ہے: `TeamRoutingService` ٹیم لیڈر کو ڈسپیچ کرتا ہے۔ کوئی تعاون کنندہ شامل کرنا ایک قطار لکھتا ہے اور کچھ شائع نہیں کرتا۔ وینڈر ویب ہک کسی ڈومین ایونٹ کے بغیر `TicketSyncEngine` کے ذریعے لاگو ہوتا ہے۔

## میوٹیشن چوک پوائنٹ

`TicketWorkflowService` ہر میوٹیشن کی مالک ہے۔

| میکانزم                | تفصیل                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| واحد چوک پوائنٹ         | تمام میوٹیشنز `_mutate` سے گزرتی ہیں، جو لاگو کرنے سے پہلے قطار لوڈ کرتا ہے اور `_assertWorkspace` کال کرتا ہے                                      |
| ورک اسپیس کی تنہائی     | `_assertWorkspace` `WorkspaceMismatchException` پھینکتا ہے جب لوڈ شدہ قطار کا `workspaceId` کالر سے میل نہ کھائے                                   |
| آپٹیمسٹک کنکرنسی        | `_mutate` لکھتے وقت `expectedVersion` کو اُس `version` پر سیٹ کرتا ہے جو اُس نے ابھی پڑھا، اور تازہ حالت دوبارہ پڑھ کر `ConcurrencyConflictException` پر دوبارہ کوشش کرتا ہے |
| خصوصی کلیم              | `tryCheckout` / `releaseCheckout`؛ چیک آؤٹ شدہ ٹکٹ کا دعویٰ کرنے والے دوسرے ایجنٹ کو `CheckoutConflictException` ملتا ہے                            |
| منتقلی گارڈ             | `canTransitionTo`، صرف اُس وقت لاگو جب `force` false ہو                                                                                            |
