یہ گائیڈ سیٹ اپ کے GitHub سے مخصوص حصوں کا احاطہ کرتی ہے۔ GitHub تین تعاون یافتہ code hosts میں سے ایک ہے۔ GitLab یا Bitbucket جوڑنے کے لیے، اور یہ دیکھنے کے لیے کہ ایک workspace انہیں کیسے ملاتا ہے، دیکھیں [کوڈ ہوسٹ جوڑیں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/کوڈ-ہوسٹ-جوڑیں/)۔

## پیشگی شرائط

- ایک GitHub اکاؤنٹ جس کی ان repos تک رسائی ہو جن پر آپ کام کرنا چاہتے ہیں
- ایک سرور جو لوگوں کو GitHub میں sign in کرا سکے: یا اپنی GitHub App (دیکھیں [GitHub App بنائیں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/github-app/))، یا Control Center Connect، جسے سرور کا مالک **ترتیبات → سرور → سنگل سائن آن** میں چنتا ہے

:::note[اعتبارنامے سرور پر رہتے ہیں اور آپ سے منسلک ہیں]
جس مشین پر آپ ٹائپ کر رہے ہیں اس پر کچھ بھی محفوظ نہیں ہوتا۔ آپ کا GitHub sign-in آپ کے `cc_server` کے پاس رہتا ہے، آپ کے user id سے کلید کیا ہوا، اور جس آلے سے بھی آپ sign in کریں وہ اسے استعمال کرتا ہے: desktop، web اور phone۔ اسی سرور کا کوئی اور رکن اسے استعمال نہیں کر سکتا، اور انہیں sign in کرانا ان کا اپنا کام ہے۔
:::

## GitHub میں sign in

GitHub صرف sign-in ہے: کوئی ٹوکن چسپاں کرنے کی ضرورت نہیں۔

1. **ترتیبات → آپ → پروفائل → کوڈ ہوسٹنگ** پر جائیں (یا آن بورڈنگ کے پہلے مرحلے پر)
2. **GitHub** قطار پر، **Sign in to GitHub** پر کلک کریں
3. آپ کا براؤزر GitHub کھولتا ہے۔ app کی منظوری دیں

sign-in کیسے ختم ہوتا ہے، اس کا انحصار اس پر ہے کہ اسے کون چلا رہا ہے:

- **سرور کی اپنی app:** GitHub آپ کے براؤزر کو سرور پر واپس بھیجتا ہے اور dialog خود پہچان لیتا ہے۔ ٹائپ کرنے کو کچھ نہیں
- **Control Center Connect:** براؤزر کا صفحہ ایک 8 حروف کا کوڈ دکھاتا ہے۔ اسے dialog میں ٹائپ کریں، یا براؤزر کو `control-center://` لنک کے ذریعے Control Center کھولنے دیں اور ٹائپ کرنے سے بچیں

checkpoint: **GitHub** قطار پڑھتی ہے "Signed in as _your-username_"۔

dialog ایسا کوڈ یا لنک رد کرتا ہے جو اس نے خود شروع نہیں کیا، اور **یہ سائن اِن یہاں سے شروع نہیں ہوا** دکھاتا ہے۔ اگر کوئی آپ کو sign-in کا لنک بھیجے تو آگے نہ بڑھیں: اسے مکمل کرنے سے آپ کا اکاؤنٹ ان کے سرور سے جڑ جائے گا۔

اپنا sign-in ہٹانے کے لیے **منقطع کریں** پر کلک کریں۔ GitHub سے sign out کرنا، یا workspace سے ہٹایا جانا، سرور کے آپ کی جانب سے جاری کیے ہوئے ہر ٹوکن کو بھی باطل کر دیتا ہے۔

## آپ کا credential کس کی نمائندگی کرتا ہے

Control Center GitHub کی اپنی تقسیم کی پیروی کرتا ہے: **ایک شخص کے طور پر** عمل اور **ایپ کے طور پر** عمل کے درمیان:

| کیا ہوتا ہے | GitHub پر یہ اس طرح دکھتا ہے |
| --- | --- |
| آپ کے اپنے تمام کام: تبصرہ، ریویو، منظوری، merge، ریویوورز کی درخواست | **آپ**۔ GitHub گفتگو میں کسی تبصرے کو Control Center ایپ سے بنایا گیا ظاہر کرتا ہے؛ ریویو اور اس کے درون خطی تبصروں پر ایسا کوئی نشان نہیں ہوتا |
| AI ریویو، PR گفتگو میں ایجنٹ کے جوابات اور تبصرے، labels، pipeline اور بوٹ کا کام | **Control Center بوٹ**۔ مشترکہ Connect ایپ پر ریویو صرف اُس انسٹالیشن کے لیے بوٹ کا ہوتا ہے جسے Connect آپریٹر نے فہرست میں ڈالا ہو؛ ورنہ وہ ذمہ دار شخص کے طور پر دکھتا ہے |
| ایجنٹ کی کھولی ہوئی pull request جو آپ کے لیے ہو، اس pull request کے عنوان یا تفصیل میں اس کی ترامیم، اس کے pushes اور اس کے کمیٹس | **آپ**۔ جب شریک مصنف کا کریڈٹ آن ہو تو Control Center کو کریڈٹ دیا جاتا ہے |
| ایسا کام جو کسی نے نہیں مانگا (schedules، webhooks) | **Control Center بوٹ**، اپنے کمیٹس کے مصنف کے طور پر بھی۔ Control Center Connect پر یہ کبھی push یا pull request نہیں کھولتا |

- **آپ جو بھی کرتے ہیں** آپ کے اپنے sign-in پر چلتا ہے اور کسی اور پر نہیں۔ اگر آپ sign in نہیں ہیں تو ایپ sign in کرنے کو کہتی ہے۔ کوئی اور credential آپ کی جگہ نہیں لیتا
- **بوٹ کا کام** ایک وقت میں ایک ریپو کے لیے ٹوکن لیتا ہے، جو اس تک محدود ہے جو ذمہ دار رکن وہاں کر سکتا ہے: جس نے درخواست کی، ورنہ ورک اسپیس کا مالک۔ جو رکن push نہیں کر سکتا وہ اسے صرف پڑھنے تک محدود کر دیتا ہے۔ کسی کی جانب سے عمل کرنے والے بوٹ کے جوابات **Control Center (for @login)** سے شروع ہوتے ہیں
- **ایجنٹس pull requests Control Center کے ذریعے کھولتے ہیں**، کبھی اپنی sandbox سے نہیں، اس لیے pull request آپ کی ہے اور GitHub کے اپنے قواعد آپ کو اس کی منظوری سے روکتے ہیں۔ Control Center اُس شخص کی منظوری بھی رد کرتا ہے جس نے ایجنٹ سے یہ کام کہا تھا، اور pull request کے مصنف کی منظوری بھی۔ شیڈول یا webhook رن کے لیے اس میں ہر وہ ایڈمن شامل ہے جس نے اس کا trigger فعال کیا یا اس کی pipeline میں ترمیم کی جب وہ فعال تھی۔ کسی اور کو ریویو کرنا ہوگا۔ اگر Control Center یہ تصدیق نہ کر سکے کہ pull request کس نے کھولی، یا forge پر آپ کا اکاؤنٹ کون سا ہے، تو وہ رد کرتا ہے اور دوبارہ کوشش کرنے کو کہتا ہے
- **ایجنٹ تبصرے بھی Control Center کے ذریعے کرتے ہیں۔** ایجنٹ کے رن کو ملنے والا GitHub ٹوکن صرف پڑھ سکتا ہے۔ جب ایجنٹ اُس pull request پر تبصرہ کرتا ہے جس پر وہ کام کر رہا ہے، تو Control Center تبصرہ بوٹ کے طور پر پوسٹ کرتا ہے، اور اگر کسی نے رن کی درخواست کی ہو تو **Control Center (for @login)** سے شروع ہوتا ہے۔ ایجنٹ صرف اپنے pull request پر تبصرہ کر سکتا ہے: اسی repository میں، fork نہیں، جس کا آخری commit ایجنٹ نے push کیا ہو یا جو اس کی space branch کا موجودہ commit ہو۔ ایجنٹ کے تبصرے میں @-mentions کسی کو مطلع نہیں کرتے۔ ایجنٹ کھلے ہونے کے دوران اپنے pull request کا عنوان یا تفصیل بھی بدل سکتا ہے۔ یہ تبدیلی اُسی طرح کی جاتی ہے جس طرح pull request کھولا گیا تھا (آپ کے طور پر، جب آپ نے رن کی درخواست کی ہو)، اور بطورِ ڈیفالٹ پہلے منظوری لیتی ہے۔ pull request کی تفصیل اپنے @-mentions برقرار رکھتی ہے، چاہے ایجنٹ اسے کھولے یا بدلے، چنانچہ اس میں نامزد لوگوں کو مطلع کیا جاتا ہے
- **Control Center Connect پر، بوٹ کبھی push یا pull request نہیں کھولتا۔** وہاں push کرنا، branch بنانا یا pull request کھولنا اُس شخص کو مانگتا ہے جس نے درخواست کی ہو، اور وہ اُسی شخص کے sign-in پر چلتا ہے۔ شیڈول یا webhook رن جو push کی کوشش کرے، اس بارے میں پیغام کے ساتھ رک جاتا ہے۔ غیر نگرانی والے رنز کو push کی اجازت دینے کے لیے، **ترتیبات** میں ورک اسپیس کو اپنی GitHub App دیں
- **Connect بوٹ کیا کر سکتا ہے۔** مشترکہ Connect ایپ کے ساتھ بوٹ تبصرے، labels اور reactions کرتا ہے۔ وہ ریویو (AI ریویو، ریویو کے تبصرے، ریویورز کی درخواستیں) صرف اُس وقت پوسٹ کرتا ہے جب Connect آپریٹر نے اس سرور کی انسٹالیشن کو فہرست میں ڈالا ہو۔ ورنہ ریویو ذمہ دار شخص کے اپنے sign-in پر جاتا ہے اور اُن کے نام سے دکھائی دیتا ہے۔ بوٹ کبھی کوئی pull request نہیں کھولتا، ترمیم، بند یا عنوان نہیں بدلتا، کوئی ریویو رد نہیں کرتا، اور کسی تبصرے میں ترمیم یا حذف نہیں کرتا؛ ان کے لیے وہ شخص درکار ہے جس نے درخواست کی، اپنے sign-in کے ساتھ۔ Connect آپ کی تنظیم کی انسٹالیشن کو کسی ایک Control Center سرور سے نہیں باندھتا: کوئی بھی سرور جہاں ایسا رکن ہو جو اس repository میں push کر سکتا ہو اور Connect کے ذریعے سائن ان ہو، اس repository کے لیے بوٹ کا تبصرے والا ٹوکن حاصل کر سکتا ہے
- **ایک سرور یا ورک اسپیس جس کی اپنی GitHub App ہو** اوپر کے تمام کاموں کے لیے بوٹ رکھتا ہے، ریویوز سمیت
- **خودکارسازی کبھی pull request کو منظور نہیں کرتی۔** منظوری ایک فرد کا کام ہے

جب آپ کوئی repo لنک کرتے ہیں تو Control Center جانچتا ہے کہ آپ کا اکاؤنٹ اسے دیکھ سکتا ہے، اور جب GitHub App اس repo کی تنظیم پر انسٹال نہ ہو یا repo کو شامل نہ کرے تو اصلاح کے لنک کے ساتھ خبردار کرتا ہے۔ لنک اور ان لنک کرنے کے لیے ورک اسپیس کا ایڈمن درکار ہے، اور ورک اسپیس کے اپنے اسٹوریج سے باہر کا checkout صرف سرور کا مالک لنک کر سکتا ہے؛ دیکھیں [ورک اسپیس میں repos شامل کریں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/ریپوز-شامل-کریں/)۔

لنک ریپوزٹری کی مستقل GitHub id کے ساتھ چلتا ہے، اس لیے نام بدلنے یا منتقلی کے لیے آپ کو کچھ نہیں کرنا پڑتا۔ اگر راستہ بعد میں کسی اور ریپوزٹری کا نام بتائے، تو Control Center اسے کچھ بھیجنا بند کر دیتا ہے اور ایک نوٹس دکھاتا ہے جب تک ورک اسپیس کا ایڈمن **دوبارہ لنک کریں** پر کلک نہ کرے۔

کسی ریپوزٹری کا کوڈ (فائلیں، diffs، تلاش، ٹرمینل) کھولنے کے لیے ورک اسپیس میں اس کا گرانٹ اور آپ کا GitHub sign-in، جو اسے پڑھ سکے، دونوں درکار ہیں۔ ورک اسپیس کے ایڈمن بھی یہی اصول مانتے ہیں؛ صرف سرور کا مالک مستثنیٰ ہے۔

## انضمام آپ کو کیا دیتا ہے

| خصوصیت                 | طریقہ                                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| PR فہرست اور تفصیل     | سرور سے GitHub REST API، آپ کے اپنے sign-in پر                                                                               |
| Check runs             | GitHub Checks API                                                                                                             |
| ریویو اشاعت            | ایک user-gated قدم جو آپ کا ریویو آپ کے نام سے PR پر پوسٹ کرتا ہے                                                             |
| Repo رجسٹریشن          | checkout قبول ہوتا ہے اگر اس کا `origin` remote github.com، یا gitlab.com / bitbucket.org کی طرف اشارہ کرے                       |
| ایجنٹ کی GitHub رسائی  | رن کے اندر `git fetch` Control Center کے ذریعے جاتا ہے، جو رن کی repositories کو ایک ایسے صرف پڑھنے والے ٹوکن کے ساتھ fetch کرتا ہے جو رن کبھی نہیں رکھتا۔ `gh` انہیں صرف پڑھنے والے ٹوکن پر پڑھتا ہے جو Control Center مانگنے پر دیتا ہے اور رن ختم ہونے پر منسوخ کر دیتا ہے۔ Pushes، pull requests، ان میں تبدیلیاں اور تبصرے Control Center کے ذریعے جاتے ہیں                       |
| اطلاعی pings           | آپ کے GitHub notification inbox کا سرور کی جانب سے poll "mentioned in pull request" اور "review requested" اٹھاتا ہے          |
| صارف پروفائلز          | پروفائل ہوور کارڈز اور ہر مصنف کے لحاظ سے PR فلٹرنگ                                                                            |

کچھ راستے REST کے بجائے GraphQL API استعمال کرتے ہیں جہاں یہ سستا ہو: compose-PR picker کے لیے branch activity، اور وہ live review state جو طے کرتی ہے کہ "review requested" اطلاع ابھی زیرِ التوا ہے یا نہیں۔

## GitHub کی outages پر نظر رکھیں

جب کوئی provider خراب ہو تو title bar ایک status chip دکھاتا ہے، جو GitHub، Claude، OpenAI اور Kimi کو کور کرتا ہے۔ **جب سب کچھ صحت مند ہو تو یہ چھپا رہتا ہے**: presence مسئلہ بتاتا ہے، اس کی غیر موجودگی نہیں۔

chip پر کلک کریں تو ہر provider کی حالت اور refresh بٹن کے ساتھ ایک flyout کھلتا ہے۔ statuses ہر دو منٹ بعد خود refresh ہوتے ہیں۔

## جانیں کہ ایجنٹس GitHub پر کیسے عمل کرتے ہیں

- GitHub worktree میں کام کرنے والا ایجنٹ اس ایک repository کا ٹوکن لیتا ہے۔ وہ صرف کوڈ، issues اور pull requests پڑھ سکتا ہے؛ تبصرے اوپر بیان کیے گئے مطابق Control Center سے گزرتے ہیں۔ push Control Center سے گزرتا ہے، جو **push to a remote** قاعدے سے پوچھتا ہے اور پھر اسے ایک write ٹوکن پر آگے بڑھاتا ہے جو ایجنٹ کبھی نہیں رکھتا۔ دیکھیں [sandbox policies ترتیب دیں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/سینڈ-باکس-پالیسیاں/)
- آپ کے شروع کردہ کام آپ کے نام سے کمیٹ ہوتے ہیں۔ جب آپ کسی ایجنٹ سے کچھ مانگتے ہیں، یا IDE میں کمیٹ کرتے ہیں، تو آپ مصنف اور کمیٹر ہوتے ہیں، ایسے پتے کے تحت جسے آپ کے forge نے تصدیق کیا ہو: آپ کے GitHub sign-in سے آپ کا GitHub noreply پتہ، یا GitLab اور Bitbucket پر وہ ای میل جو وہاں کا sign-in رپورٹ کرے۔ ورک اسپیس کی Git شناخت صرف اُس کمیٹ کے لیے استعمال ہوتی ہے جو آپ خود ایسے ریپوزٹری میں کریں جہاں کوئی forge آپ کے کسی پتے کی ضمانت نہ دیتا ہو۔ اگر آپ اس forge میں سائن ان نہیں ہیں تو ایجنٹ کے کمیٹس اس کے بجائے بوٹ کے ہوتے ہیں اور رن کے notes یہ بتاتے ہیں
- جو کام کسی نے نہیں مانگا وہ بوٹ کے طور پر کمیٹ ہوتا ہے۔ شیڈول یا webhook رن ورک اسپیس کی GitHub App کے طور پر کمیٹ کرتا ہے (`<app>[bot]`، اس کے GitHub noreply پتے کے ساتھ)، یا `Control Center <hi@usectrl.dev>` کے طور پر جب کوئی GitHub App نہ ہو یا repository GitLab یا Bitbucket پر ہو۔
- **Control Center کو شریک مصنف کے طور پر کریڈٹ دیں** (**ترتیبات** → **آپ** → **کمیٹس**) ایک `Co-Authored-By:` trailer شامل کرتا ہے: آپ کے کمیٹس پر Control Center کا، اور بوٹ کے کمیٹس پر ہر اُس شخص کا جس نے رن کے پیچھے trigger کو فعال کیا تھا۔ یہ ڈیفالٹ طور پر آن ہے جب تک آپ اسے بند نہ کریں۔ ورک اسپیس کا ایڈمن **شریک مصنف کا کریڈٹ** کا فیصلہ سب کے لیے کر سکتا ہے، **ترتیبات** → **ورک اسپیس** → **عام** میں؛ تب آپ کی اپنی پسند محفوظ تو ہوتی ہے مگر اُس ورک اسپیس میں لاگو نہیں ہوتی۔ Claude Code کی اپنی attribution ہمیشہ غیر فعال ہوتی ہے
- آپ کے کمیٹس سائن ہو سکتے ہیں۔ **ترتیبات** → **آپ** → **کمیٹس** کے تحت **تصدیق شدہ کمیٹس** میں **سائننگ کلید بنائیں** چنیں اور اس کا عوامی حصہ اپنے GitHub یا GitLab اکاؤنٹ میں سائننگ کلید کے طور پر شامل کریں؛ اس کے بعد آپ کے مانگے ہوئے رنز کے کمیٹس، اور IDE میں آپ کے کیے ہوئے کمیٹس، تصدیق شدہ دکھائی دیتے ہیں۔ نجی حصہ آپ کے سرور پر رہتا ہے، اس لیے جو اس سرور کو کنٹرول کرتا ہے وہ، جب تک کلید آپ کے اکاؤنٹ پر ہو، آپ کے نام سے کمیٹس سائن کر سکتا ہے، اور GitHub پر وہ کمیٹ جو پہلے سے تصدیق شدہ دکھائی دے رہا ہو، کلید ہٹانے کے بعد بھی تصدیق شدہ رہتا ہے۔ Bitbucket کے پاس صرف سائننگ والی کلید نہیں ہوتی: وہاں کلید نہ جوڑیں، اور Bitbucket پر کمیٹس سائن نہیں ہوتے۔ بوٹ کے کمیٹس کبھی سائن نہیں ہوتے
- IDE کے **سورس کنٹرول** پینل میں آپ کے کیے گئے کمیٹس ریپوزٹری کے Git hooks کو چھوڑ دیتے ہیں، جیسے `git commit --no-verify` کرتا ہے، اور سرور کا Git وہ credential helpers، editors، external diff tools اور signers نظرانداز کرتا ہے جو ریپوزٹری کنفیگر کرتی ہے: وہ اپنی مشین پر، ایک ایسے tree میں Git چلاتا ہے جسے ایجنٹ یا pull request بدل سکتا ہے۔ دیکھیں [سورس کنٹرول سے commit اور push کریں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/pr-ریویو-اور-مرج/#سورس-کنٹرول-سے-کمٹ-اور-پش)
- ایجنٹ کا push کیا ہوا ہر کمیٹ پہلے جانچا جاتا ہے، بشمول وہ layers جو `stack_publish` کسی stack کے لیے push کرتا ہے۔ ایسا push جو کسی اور کا نام لے، کسی کریڈٹ کو ہٹائے یا ادھار لے، sign-off شامل کرے، یا اس طرح سائن نہ ہو جس طرح آپ کی سیٹنگز کہتی ہیں، رد ہو جاتا ہے۔ آپ کے اپنے IDE سے push کیے ہوئے کمیٹس آپ کے ہیں اور اس طرح جانچے نہیں جاتے
- rig پر آپ جو terminal کھولتے ہیں وہ آپ کا اپنا sign-in لیتا ہے، ایک repository تک محدود، اس لیے وہاں کے pushes آپ کے ہیں
- جب کوئی ٹوکن جاری نہ ہو سکے (کوئی ذمہ دار شخص sign in نہیں، app مالک پر انسٹال نہیں، یا installation معطل ہے)، تو وہ کمانڈ جس نے اسے مانگا، وجہ بتاتی ہے۔ کوئی fallback credential نہیں

## خرابیوں کا ازالہ

### PR فہرست خالی ہے اور کہتی ہے GitHub متصل نہیں

آپ اس سرور پر GitHub میں sign in نہیں ہیں۔ **ترتیبات → آپ → پروفائل → کوڈ ہوسٹنگ** کے تحت **Sign in to GitHub** پر کلک کریں۔ دوسرے forges کے repos متاثر نہیں ہوتے۔

### GitHub قطار کہتی ہے اس سرور پر sign-in سیٹ نہیں

سرور کے پاس نہ اپنی GitHub App ہے نہ Connect۔ سرور کا مالک **ترتیبات → سرور → سنگل سائن آن** میں ایک چنتا ہے: **میری GitHub ایپ بنائیں** تقریباً دو منٹ لیتا ہے۔ دیکھیں [GitHub App بنائیں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/github-app/)۔

ایک workspace جو اپنی ایپس پر ہو، وہاں قطار بتاتی ہے کہ workspace کی GitHub App غائب ہے یا نامکمل ہے۔ ایک workspace admin اسے **ترتیبات → ورک اسپیس → انٹیگریشنز** پر **GitHub App** کارڈ میں بھرتا ہے؛ دیکھیں [ایک workspace کو اپنی app دیں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/github-app/#ایک-workspace-کو-اپنی-app-دیں)۔

### dialog کہتا ہے کوڈ میل نہیں کھاتا

کوڈ بالکل ویسے ٹائپ کریں جیسے براؤزر دکھاتا ہے: 8 حروف اور ہندسے۔ پانچ غلط کوڈ sign-in ختم کر دیتے ہیں؛ دوبارہ شروع کریں۔

### sign-in کہتا ہے app انسٹال نہیں ہے

GitHub App کی اس اکاؤنٹ پر کوئی installation نہیں جس کی ملکیت میں repository ہے۔ ایک workspace admin اسے **ترتیبات → ورک اسپیس → انٹیگریشنز → GitHub ایپ کی انسٹالیشنز** سے انسٹال کرتا ہے۔

### سب کو دوبارہ GitHub میں sign in کرنا پڑتا ہے

سرور کے مالک نے سرور کی Connect key rotate کی، Connect سرورز بدلے، یا data directory کسی اور مشین پر بحال ہوئی۔ Connect کے ذریعے sign-ins اس سرور سے جڑے ہوتے ہیں جس نے انہیں بنایا۔

### repo شامل کرنا رد ہوتا ہے

رجسٹریشن کے لیے تینوں شرائط درکار ہیں: راستہ git work tree کے اندر ہو، اس کا `origin` remote ہو، اور وہ remote کسی تعاون یافتہ forge (github.com، gitlab.com یا bitbucket.org) کی طرف اشارہ کرے۔ `origin` وہی ریپوزٹری ہونا چاہیے جسے آپ لنک کر رہے ہیں، اور ورک اسپیس کے اپنے اسٹوریج سے باہر کا فولڈر صرف سرور کا مالک لنک کر سکتا ہے۔ دیکھیں [workspace میں repos شامل کریں](/ur-PK/ہدایت-نامہ/طریقہ-کار-گائیڈز/ریپوز-شامل-کریں/)۔

### میرے پاس گرانٹ ہے مگر ریپوزٹری کہتی ہے کہ میرا اکاؤنٹ اسے نہیں پڑھ سکتا

آپ کا GitHub اکاؤنٹ اس ریپوزٹری کو نہیں پڑھ سکتا، اس لیے ورک اسپیس گرانٹ کے باوجود اس کا کوڈ آپ کے لیے بند رہتا ہے۔ **کوڈ ہوسٹنگ** کے تحت GitHub میں sign in کریں، یا GitHub پر اس ریپوزٹری تک رسائی مانگیں۔

### "آپ کی GitHub تک رسائی کی تصدیق نہیں ہو سکی"

GitHub تک جانچ کے لیے پہنچا نہیں جا سکا، اس لیے Control Center اندازہ لگانے کے بجائے رد کرتا ہے۔ کچھ دیر بعد دوبارہ کوشش کریں۔

### Connect پر ریویوز بوٹ کے بجائے میرے نام سے دکھائی دیتے ہیں

مشترکہ Connect ایپ پر بوٹ صرف اُن انسٹالیشنز کے لیے ریویو پوسٹ کرتا ہے جنہیں Connect آپریٹر نے فہرست میں ڈالا ہو۔ باقی ہر جگہ ریویو ذمہ دار شخص کے اپنے sign-in پر جاتا ہے۔ بوٹ سے ریویو پوسٹ کروانے کے لیے ورک اسپیس کو اپنی GitHub App دیں۔

### بھاری استعمال کے بعد کچھ دیر کے لیے سب کچھ رک جاتا ہے

یہ rate-limit circuit breaker ہے۔ GitHub اپنی بنیادی حد `x-ratelimit-remaining: 0` اور reset وقت والے `403` کے ذریعے بتاتا ہے؛ کلائنٹ ایسا دیکھ کر مزید درخواستوں کو نیٹ ورک کال کے بغیر مقامی طور پر ناکام کرتا ہے جب تک وقفہ نہ گزر جائے، تاکہ retry کا طوفان حد کو اور گہرا نہ کر سکے۔ عارضی ناکامیوں کی exponential backoff کے ساتھ تین بار تک retry ہوتی ہے، `retry-after` کا احترام کرتے ہوئے۔
