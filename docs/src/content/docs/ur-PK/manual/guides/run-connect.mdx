Control Center Connect ان سرورز کے لیے provider sign-ins (GitHub، Google Calendar، Linear اور Slack) چلاتا ہے جنہوں نے اپنی apps رجسٹر نہیں کیں۔ یہ گائیڈ دکھاتی ہے کہ اپنا Connect کیسے چلائیں، تاکہ provider apps، ان کے secrets، اور ان سرورز کی فہرست جنہیں ان کے استعمال کی اجازت ہے، سب آپ کے پاس رہیں۔

Connect کیا دیکھ سکتا ہے اور کیا نہیں، یہ [Connect reference](/ur-PK/ہدایت-نامہ/حوالہ/connect/) میں ہے۔ اگر آپ فیصلہ کر رہے ہیں کہ Connect چلانا ہے یا نہیں، تو پہلے اسے پڑھیں۔

:::note[ہو سکتا ہے آپ کو اس کی ضرورت نہ ہو]
ایک سرور اس کے بجائے اپنی apps خود رجسٹر کر سکتا ہے: **Settings → Server → Single sign-on → Provider apps**، جہاں **Create my GitHub App** ایک قدم میں GitHub سیٹ کر دیتا ہے۔ کسی provider کے لیے صرف **Use my own apps** کے تحت سرور کی اپنی app استعمال ہوتی ہے: Control Center Connect یا custom Connect کے ساتھ Connect ہر lane چلاتا ہے، اور workspace کی اپنی app ہر mode میں لاگو رہتی ہے۔ Connect اس وقت چلائیں جب کئی سرورز کو apps کا ایک ہی مجموعہ بانٹنا ہو۔
:::

## پیشگی شرائط

- Connect کے لیے ایک عوامی **HTTPS** پتہ، جیسے `https://connect.example.com`، جو TLS ختم کرنے والے proxy کے پیچھے ہو۔ سادہ `http` صرف loopback پر قبول ہوتا ہے
- Docker، یا ایک `cc_server` جسے آپ اضافی environment variables کے ساتھ دوبارہ شروع کر سکیں
- ہر اس provider کے لیے apps رجسٹر کرنے کی اجازت جسے آپ سروس دینا چاہتے ہیں
- وہ سرورز جو اسے استعمال کریں گے، ان کے owners دستیاب ہوں: ہر سرور کا ایک install id ہوتا ہے جسے آپ Connect کی allowlist میں شامل کرتے ہیں

## مرحلہ 1: پتہ منتخب کریں

ابھی پتہ چنیں اور اسے محفوظ رکھیں۔ `CONNECT_PUBLIC_URL` Connect کے ہر کام میں شامل ہے: request signatures، sealed credentials، provider redirect URLs، اور ہر سرور کا install id، یہ سب اسی سے منسلک ہیں۔ بعد میں اسے تبدیل کرنے کا مطلب ہے redirects دوبارہ رجسٹر کرنا اور ہر شخص کو دوبارہ sign in کرانا۔

## مرحلہ 2: provider apps رجسٹر کریں

صرف وہی providers رجسٹر کریں جنہیں آپ سروس دینا چاہتے ہیں۔ جس provider کے variables نامکمل ہوں وہ Connect کی configuration سے نکال دیا جاتا ہے، اور سرورز اسے unavailable دیکھتے ہیں۔ نیچے `<base>` سے مراد آپ کا `CONNECT_PUBLIC_URL` ہے۔

| Provider       | رجسٹریشن                                                                                                                                                                                                                                                              | محفوظ رکھیں                                  |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **GitHub App** | Callback URL ‏`<base>/oauth/github/callback`۔ Setup URL ‏`<base>/oauth/github/setup` کے ساتھ **Redirect on update** فعال۔ **Request user authorization (OAuth) during installation** غیر فعال رکھیں: فعال ہونے پر GitHub setup URL کو نظرانداز کرتا ہے۔ **Expire user authorization tokens** فعال رکھیں | App id، slug، client id، client secret         |
| **Google**     | redirect URI ‏`<base>/oauth/google/callback` کے ساتھ **Web application** قسم کا OAuth client، اور Google Calendar API فعال                                                                                                                                              | Client id، client secret                     |
| **Linear**     | callback URLs ‏`<base>/oauth/linear/callback` اور `<base>/oauth/linear_app/callback` کے ساتھ OAuth application                                                                                                                                                       | صرف Client id                                |
| **Slack**      | Redirect URLs ‏`<base>/oauth/slack_oidc/callback` اور `<base>/oauth/slack/callback`۔ Event Subscriptions ‏`<base>/v1/hooks/slack/events` پر (`app_mention`، `message.*`، `assistant_thread_*`، `app_uninstalled`، `tokens_revoked`)۔ Slash commands ‏`<base>/v1/hooks/slack/commands` پر۔ Token rotation فعال | App id، client id، client secret، signing secret |

GitHub App کو یہ repository permissions دیں: **Metadata** read، **Contents** read اور write، **Pull requests** read اور write، **Issues** read اور write، اور **Checks**، **Actions** اور **Commit statuses** read۔ team review requests کے لیے organization **Members** read شامل کریں۔ Webhooks بند رہ سکتے ہیں: سرورز polling کرتے ہیں۔

Connect کو کبھی GitHub App کی private key کی ضرورت نہیں ہوتی۔ اس کے بجائے وہ شخص کے اپنے sign-in سے ایک repository تک محدود tokens جاری کرتا ہے۔ Linear کو بھی کسی secret کی ضرورت نہیں: Connect code سرور کو واپس دیتا ہے، اور سرور خود exchange مکمل کرتا ہے۔

## مرحلہ 3: install ids جمع کریں

Connect صرف ان سرورز کو جواب دیتا ہے جو اس کی allowlist پر ہوں۔ ہر سرور پر، اسے اپنے Connect کی طرف اشارہ کریں، پھر اس کا install id پڑھیں:

1. **Settings → Server → Single sign-on** پر جائیں، **Control Center Connect** کارڈ کھولیں، اور **Use a custom Connect server** منتخب کریں
2. اپنا URL درج کریں اور save کریں۔ کارڈ سرور کا **Install id** دکھاتا ہے

سرور کے host پر terminal سے وہی کام یوں ہوتا ہے:

```bash
cc_server connect enable --url https://connect.example.com
cc_server connect status
```

`status` install id پرنٹ کرتا ہے۔ یہ `install_blocked` دکھاتا ہے جب تک مرحلہ 5 مکمل نہ ہو، اور یہ متوقع ہے۔

install id ہر Connect کے پتے کے لحاظ سے اخذ ہوتا ہے، اس لیے ایک ہی سرور کا ہر اس Connect کے لیے مختلف id ہوتا ہے جس سے وہ بات کرتا ہے۔ یہ صرف اس وقت بدلتا ہے جب اس کا owner key rotate کرے۔

## مرحلہ 4: ایک seal key بنائیں

Connect ہر credential جو وہ واپس دیتا ہے اسے seal key سے encrypt کرتا ہے۔ ایک بنائیں اور اسے secret file کے طور پر محفوظ رکھیں:

```bash
docker run --rm ghcr.io/samuelalev/cc-connect:latest \
  cc-connect-config seal-key > seal_keys
chmod 600 seal_keys
```

seal key کھو دینے کا مطلب ہے سب کو sign out کرنا: اس کے بغیر کوئی seal نہیں کھولا جا سکتا۔

## مرحلہ 5: container شروع کریں

ہر release `ghcr.io/samuelalev/cc-connect` کو build provenance کے ساتھ شائع کرتا ہے۔ production میں ایک version tag pin کریں۔

```bash
docker run -d --name cc-connect -p 8790:8790 \
  -e CONNECT_PUBLIC_URL=https://connect.example.com \
  -e CONNECT_ALLOWED_INSTALLS=<install id>,<install id> \
  -e CONNECT_SEAL_KEYS_FILE=/run/secrets/seal_keys \
  -v "$PWD/seal_keys:/run/secrets/seal_keys:ro" \
  -e CONNECT_GITHUB_APP_ID=123456 \
  -e CONNECT_GITHUB_APP_SLUG=acme-control-center \
  -e CONNECT_GITHUB_CLIENT_ID=Iv23li0123456789abcd \
  -e CONNECT_GITHUB_CLIENT_SECRET_FILE=/run/secrets/github \
  -v "$PWD/github_secret:/run/secrets/github:ro" \
  -v cc-connect-data:/data \
  ghcr.io/samuelalev/cc-connect:latest
```

اپنا reverse proxy port `8790` کی طرف اشارہ کریں۔ image ایک غیر مراعات یافتہ user کے طور پر چلتی ہے، اپنی state `/data` volume میں رکھتی ہے، اور اس میں built-in health check ہے (`cc-connect --healthcheck`، جو `/healthz` کو probe کرتا ہے)۔

Connect شروع ہونے سے انکار کرتا ہے (exit code `78`) جب اس کی configuration کھلی، غیر محفوظ یا نامکمل ہو، اور بتاتا ہے کہ کون سا variable غلط ہے۔ allowlist کا نہ ہونا، loopback کے علاوہ `http` پتہ، غلط seal key، یا `NAME` اور `NAME_FILE` دونوں کا مقرر ہونا، یہ سب اسے روک دیتے ہیں۔

Checkpoint: ہر سرور پر Connect کارڈ **Working** پڑھتا ہے، اور **Where each sign-in runs** ہر اس provider کے لیے **Connect** دکھاتا ہے جو آپ نے رجسٹر کیا۔ `cc_server connect status` ایک `Health: ok` اور وہی lanes پرنٹ کرتا ہے۔

## cc_server کے اندر Connect mount کریں

سرور الگ container کے بجائے خود Connect میزبانی کر سکتا ہے۔ mount کی گئی سروس وہی ہے جو image چلاتی ہے۔

1. `CONNECT_*` variables سرور کی `.env` فائل (یا environment) میں رکھیں، جیسا کہ مرحلہ 5 میں ہے
2. `CC_SERVER_CONNECT_HOST=on` شامل کریں
3. سرور دوبارہ شروع کریں۔ اس کا log `embedded Connect at <url>` پرنٹ کرتا ہے

```bash
CC_SERVER_CONNECT_HOST=on
CONNECT_ALLOWED_INSTALLS=<install id>
CONNECT_SEAL_KEYS=<output of cc-connect-config seal-key>
CONNECT_GITHUB_APP_ID=123456
CONNECT_GITHUB_APP_SLUG=acme-control-center
CONNECT_GITHUB_CLIENT_ID=Iv23li0123456789abcd
CONNECT_GITHUB_CLIENT_SECRET=<secret>
```

Connect پھر `<server>/connect` پر دستیاب ہوتا ہے:

- `CONNECT_PUBLIC_URL` پیشگی طور پر سرور کے عوامی URL کا origin plus `/connect` ہوتا ہے۔ proxy کے پیچھے اسے واضح طور پر سیٹ کریں۔ راستہ بالکل `/connect` ہونا چاہیے، اور loopback نہ ہو تو HTTPS ہونا لازمی ہے
- صرف `CONNECT_*` variables mount کی گئی سروس تک پہنچتے ہیں، اس لیے یہ کبھی سرور کی اپنی provider apps استعمال نہیں کرتی
- `CONNECT_ALLOWED_INSTALLS` پھر بھی لازمی ہے، میزبان سرور کے لیے بھی
- غلط mount سرور کو boot ہونے سے روک دیتا ہے، کھلا broker پیش کرنے کے بجائے
- demo سرور اسے کبھی mount نہیں کرتا

provider redirects کو `https://<server>/connect` کے خلاف رجسٹر کریں، پھر سرورز (میزبان سمیت) کو مرحلہ 3 کی طرح اسی URL کی طرف اشارہ کریں۔

## configuration کا حوالہ

ہر setting ایک environment variable ہے۔ کوئی بھی secret ایک mount کی ہوئی فائل سے آ سکتا ہے: `NAME` کے بجائے `NAME_FILE` مقرر کریں۔ Connect فائل کو زیادہ سے زیادہ ہر 30 سیکنڈ بعد دوبارہ پڑھتا ہے اور آخری درست قدر رکھتا ہے۔ **dual** نشان والے secrets rotation کے دوران `NAME_PREVIOUS` (یا `NAME_PREVIOUS_FILE`) بھی قبول کرتے ہیں۔

| Variable                        | Default   | مطلب                                                                                                                             |
| ------------------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `CONNECT_PUBLIC_URL`            | لازمی     | معیاری عوامی URL۔ HTTPS، یا loopback پر `http`۔ راستہ mount کی نشاندہی کرتا ہے۔ کوئی query یا fragment نہیں                       |
| `CONNECT_ALLOWED_INSTALLS`      | لازمی     | کاما سے جدا install ids۔ `*` صرف `CONNECT_SIGNED_CONFIG_FILE` کے ساتھ قبول ہے                                                    |
| `CONNECT_DENY_INSTALLS`         |           | وہ install ids جو اجازت ہونے کے باوجود مسترد ہوں                                                                                 |
| `CONNECT_GITHUB_ALLOWED_OWNERS` |           | عددی GitHub owner ids۔ مقرر ہونے پر repository tokens صرف انہی owners کی repositories کے لیے جاری ہوتے ہیں                         |
| `CONNECT_HOST`، `CONNECT_PORT`  | `0.0.0.0`، `8790` | bind پتہ اور port                                                                                                                 |
| `CONNECT_TRUST_PROXY`           | `0`       | `X-Forwarded-For` میں قابلِ اعتماد proxy hops (0 تا 8)۔ صرف فی پتہ rate limit کے لیے استعمال ہوتا ہے                              |

## ایک سے زیادہ instances چلانا

زیادہ تر تنظیموں کے لیے `CONNECT_STATE=memory` کے ساتھ ایک instance کافی ہے۔ ایک پتے کے پیچھے کئی instances کو `CONNECT_STATE=redis` چاہیے، اور ساتھ میں ایک مشترکہ `CONNECT_DATA_DIR` یا `CONNECT_BINDINGS=firestore`، تاکہ ایک instance پر شروع ہونے والا sign-in دوسری پر مکمل ہو سکے۔

## provider secret rotate کرنا

کسی کو sign out نہیں ہوتا:

1. provider کے پاس نیا secret بنائیں اور پرانا رکھیں
2. پرانی قدر `NAME_PREVIOUS` میں منتقل کریں، نئی `NAME` میں رکھیں، اور `CONNECT_<LANE>_SECRET_GENERATION` بڑھائیں۔ mount کی گئی فائلیں 30 سیکنڈ کے اندر اٹھا لی جاتی ہیں
3. sign-ins کے refresh ہونے کا انتظار کریں، پھر provider پر پرانا secret حذف کریں اور `NAME_PREVIOUS` ہٹا دیں

seal key rotate کرنے کے لیے، پہلے `CONNECT_SEAL_KEYS` کے آغاز میں نیا `cc-connect-config seal-key` entry ڈالیں اور پرانا entry اس وقت تک رکھیں جب تک اس کی seals refresh نہ ہو جائیں۔

## app تبدیل کرنا

سرورز اپنے پہلے استعمال پر یاد رکھتے ہیں کہ آپ کے Connect نے کون سی app اور client ids کا اعلان کیا تھا۔ اگر آپ کوئی app بدلتے ہیں تو ہر سرور کے Connect کارڈ پر **Connect's apps changed** ظاہر ہوتا ہے، اور Connect کے ذریعے sign-ins اس وقت تک رک جاتے ہیں جب تک اس کا owner **Trust new apps** نہ دبائے۔ تبدیلی سے پہلے سرور owners کو بتا دیں، تاکہ وہ جانیں کہ یہ prompt آپ کی طرف سے ہے۔

## سرور کو block کرنا

اس کا install id `CONNECT_DENY_INSTALLS` میں شامل کریں اور restart کریں۔ اس کا owner دیکھتا ہے "Connect has blocked this server's install id" اور اس پر ہر Connect sign-in رک جاتا ہے۔

## خرابیوں کا ازالہ

### ایک سرور کہتا ہے Connect نے اسے block کیا ہے

اس کا install id `CONNECT_ALLOWED_INSTALLS` میں نہیں ہے، یا `CONNECT_DENY_INSTALLS` میں ہے۔ id اس وقت بدلتا ہے جب اس کا owner key rotate کرے؛ نیا id مانگیں۔

### ایک provider unavailable دکھاتا ہے

اس کا ایک variable غائب ہے، اس لیے Connect نے وہ lane نکال دی۔ startup log اور اوپر کی tables دیکھیں۔ GitHub کو چاروں درکار ہیں: app id، slug، client id اور client secret؛ Google کو client id اور secret دونوں چاہئیں۔

### sign-ins redirect mismatch سے ناکام ہوتے ہیں

provider کے پاس رجسٹر کیا گیا redirect `CONNECT_PUBLIC_URL` سے بالکل مطابقت نہیں رکھتا۔ mount شدہ Connect کے لیے scheme، host، port اور `/connect` راستہ موازنہ کریں۔

### سب کو دوبارہ sign in کرنا پڑا

seal key بدل گئی یا گم ہو گئی، کسی سرور نے اپنی key rotate کی، یا کسی سرور کا ڈیٹا کسی دوسری مشین پر بحال ہوا۔ ایک sealed credential صرف اسی install اور Connect کے لیے کھلتا ہے جنہوں نے اسے بنایا۔
