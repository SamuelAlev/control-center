`cc_server` héberge un registre d'outils MCP (JSON-RPC 2.0) unique, exposé sur le port principal du serveur (par défaut `9030`) en `POST /mcp` et `GET /sse`, version de protocole `2024-11-05`. Tous les clients atteignent le même registre : l'application de bureau, la version web, les clients MCP externes et le moteur d'agents intégré. Les serveurs MCP externes peuvent être raccordés au même registre sous forme de couche dynamique.

## Taille du registre

| Mesure | Nombre |
| --- | --- |
| Outils enregistrés par `cc_server` | 110 |
| Provenant de `packages/cc_mcp` | 108 |
| Provenant de `packages/cc_mcp_client` (découverte d'outils) | 2 |
| Enregistrés dans le registre de base (`server_mcp_registry.dart`) | 63 |
| Enregistrés après le démarrage, à mesure que leurs services montent (`cc_server_runtime.dart`) | 47 |
| Sur les 63 du registre de base, conditionnés à un dépôt de graphe de code | 5 |

Les cinq outils de graphe de code ne sont enregistrés que lorsque l'hôte transmet un dépôt de graphe de code à `buildServerMcpRegistry`. `cc_server` en transmet toujours un, donc les 110 outils sont actifs dans le binaire livré.

Le registre complet est annoncé dans `tools/list`, sans filtrage de découverte. Les modifications de tickets sont des outils typés.

:::note[Les clients externes voient toujours tout le catalogue]
`tools/list` n'est jamais tronqué. Les clients MCP valident les noms d'outils par rapport à leur propre copie en cache de cette liste et refusent tout ce qui n'y figure pas sans interroger le serveur ; un outil dissimulé à cet endroit est donc inatteignable, et pas simplement discret.

Le **harnais intégré** fonctionne autrement : il ne charge par requête qu'un sous-ensemble résident de définitions et récupère le reste au premier usage, ce qui relève du harnais et ne change rien à ce registre. Voir [Contexte des outils et cache de prompts](/fr-FR/manuel/concepts/contexte-des-outils).
:::

:::note[Chaque classe d'outil est enregistrée]
Un fichier source sous `packages/cc_mcp/lib/src/tools/` correspond à un outil qu'un agent peut
appeler. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
fait échouer la compilation si une nouvelle classe d'outil n'est instanciée nulle part.
:::

## Paramètres communs

### `workspace_id`

**Obligatoire** sur tout outil qui touche à des données propres à un espace de travail. Un `workspace_id` manquant ou invalide renvoie une erreur explicite, et une valeur qui ne correspond pas à l'espace de travail de l'entité visée est rejetée plutôt qu'ignorée en silence. Omettez-le sur les outils réellement globaux : `list_workspaces` et les six outils de fil d'actualités (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), qui utilisent la liste de flux personnelle du propriétaire du serveur. Les outils de découverte (`search_tool_bm25`, `list_my_tools`) le prennent en option afin de pouvoir classer ce qui est appelable selon le mode de conversation. Lorsqu'un agent est lancé par le serveur, l'espace de travail est imposé côté serveur : l'agent ne peut donc pas atteindre un autre espace de travail en passant un identifiant étranger.

## Découverte des outils

Tous deux proviennent de `cc_mcp_client`, et non de `cc_mcp`, et consultent tous deux le garde-fou de mode afin de signaler ce qui est appelable dans le mode de conversation _en cours_.

| Outil | Description |
| --- | --- |
| `search_tool_bm25` | Recherche dans le catalogue d'outils par mot-clé ; renvoie les outils correspondants, leur schéma d'arguments et s'ils sont appelables à l'instant |
| `list_my_tools` | Liste les outils appelables à l'instant dans cette conversation, filtrés par son mode |

Un troisième outil de découverte, **`search_tools`**, n'existe qu'à l'intérieur du harnais intégré et ne fait pas partie de ce registre MCP. Il classe la surface d'outils de l'exécution elle-même et, contrairement à `search_tool_bm25`, **charge** les schémas de ce qu'il trouve afin que l'agent puisse appeler une correspondance au tour suivant. Les agents sur le harnais devraient le préférer ; les clients MCP disposent de `search_tool_bm25`.

## Messagerie et délégation entre agents pairs

Les agents communiquent entre eux via des espaces (durables, visibles dans l'effectif). `ask_agent` fonctionne en requête/réponse avec un délai d'attente obligatoire ; `delegate_task` est encadré côté serveur par un plafond de profondeur, une détection de cycles, une enveloppe budgétaire et un plafond d'autonomie.

| Outil | Description |
| --- | --- |
| `send_to_agent` | Envoie un message à sens unique à un autre agent, adressé par `to_agent_id` ou par `to_agent_name` exact |
| `ask_agent` | Pose une question à un autre agent et attend sa réponse, ou expire |
| `delegate_task` | Délègue une tâche à un autre agent sous forme de ticket enfant suivi |
| `consult_agent` | Ajoute à l'espace le spécialiste dont les skills correspondent le mieux et le lance avec une consigne ciblée |
| `todo_read` | Lit la liste de tâches persistée de cette conversation |

## Outils d'enceinte (rig)

Pilotez des machines jetables — un navigateur ou un bureau Linux en enceinte, un
émulateur Android ou un simulateur iOS — depuis l'intérieur d'une exécution. Enregistrés après
le démarrage, inconditionnellement : savoir si une machine peut réellement démarrer est une
question de sonde à laquelle les outils répondent à chaque appel. Des appels répétés dans une
même conversation réutilisent une seule machine ; les captures d'écran reviennent comme contenu
image avec un budget d'une image par résultat, et le contenu de page/UI extrait est délimité
comme données non fiables. Les quatre outils d'usage plus `rig_close` déclarent la
[classe d'actions](/fr-FR/manuel/concepts/garde-fous/) `enclosureControl`
(les outils d'usage déclarent en outre `networkEgress` et `processSpawn` ; `mobile_use` et
`ios_use` déclarent en outre `packageInstall`), si bien que les modes en lecture seule les refusent.
`rig_list` n'en déclare aucune — il ne fait que lire l'état de l'espace de travail. Le vocabulaire
complet des verbes par surface figure dans la [référence des rigs](/fr-FR/manuel/reference/rigs/#action-verbs).

| Outil | Description |
| --- | --- |
| `computer_use` | Pilote un bureau Linux dans une VM en enceinte : déplacer, cliquer, glisser, faire défiler, saisir, redimensionner, presse-papiers, capture d'écran |
| `browser_use` | Pilote un Chromium, Firefox ou WebKit sans interface (`engine`) : naviguer, cliquer, remplir, extraire (a11y/DOM/console), presse-papiers, capture d'écran |
| `mobile_use` | Pilote Android via ADB : inspecter/saisir, captures d'écran, installer/démarrer/arrêter/réinitialiser/désinstaller des applications, liens profonds et commandes d'appareil au format argv |
| `ios_use` | Pilote le simulateur iOS via WebDriverAgent/CoreSimulator : inspecter/saisir, captures d'écran, installer/démarrer/arrêter/désinstaller des applications, liens profonds et processus de simulateur au format argv |
| `rig_list` | Liste les rigs d'un espace de travail avec leur surface, leur statut, leur taille d'affichage et leur contrôleur |
| `rig_close` | Détruit un rig et abandonne l'état de machine qu'il possède |

## Non exposés via MCP

Le calendrier et les réunions n'ont pas d'outils MCP. Les agents ne peuvent pas lire votre calendrier, vos réunions, vos transcriptions, vos actions à mener ni vos décisions. Le résumé qui produit les actions à mener et les décisions s'exécute comme le [pipeline `meeting_summary` intégré](/fr-FR/manuel/concepts/reunions/), et non comme un outil qu'un agent peut appeler.

## Filtrage des outils par mode

Le filtrage est appliqué deux fois à partir d'une seule table (`ModeToolPolicy`) : une fois dans le répartiteur MCP pour l'adaptateur Claude Code, et une fois dans le registre du harnais intégré. Un appel bloqué renvoie la raison.

| Mode | Surface d'outils |
| --- | --- |
| `chat` | Tous les outils enregistrés ; aucune liste d'autorisation |
| `plan` | Une liste d'autorisation restreinte. Aucune écriture dans l'arbre de travail et aucun verbe de ticket `create` / `assign` / `delegate`, mais la mémoire, les artefacts, les listes de tâches, `submit_plan`, `exit_plan_mode` et les verbes d'achèvement de ticket sur le ticket lancé sont autorisés |
| `review` | Une liste d'autorisation restreinte : participation aux revues, communication, récupérateurs de contexte en lecture seule et l'ensemble complet des verbes de ticket, y compris `create_ticket` et `assign_ticket` |
| `orchestrate` | Une liste d'autorisation restreinte : outils de recherche et de lecture, plus `propose_orchestration`, `create_playbook` et `run_playbook`. L'embauche, la décomposition et l'achèvement des tickets ont lieu de façon déterministe après approbation, jamais en cours d'exécution |

Autorisés dans tous les modes, quelle que soit la liste d'autorisation :

| Ensemble | Outils |
| --- | --- |
| Mémoire et artefacts | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Graphe de code | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact` |
| Mécanique d'exécution | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read` |

Figurer sur une liste d'autorisation ne rend pas un outil appelable, et l'inverse est vrai aussi : la capacité de poser une question à l'opérateur est un outil du **harnais** (`ask_user`), donc il n'apparaît jamais dans ce catalogue MCP.

## Outils soumis à approbation

Un outil peut déclarer `requiresApproval`. Le répartiteur construit alors un `ApprovalPayload` et le présente via le `ConfirmationPort` avant l'exécution de l'outil ; `cc_server` câble ce port, donc la porte est active.

Outils enregistrés qui le déclarent : `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

Indépendamment, les garde-fous d'action unifiés filtrent tout outil qui déclare un ensemble `ActionClass` non vide. Une décision `prompt` sans approbateur connecté est refusée. Voir [Garde-fous](/fr-FR/manuel/concepts/garde-fous/).

## Capacités sans outil derrière elles

Toutes les capacités du produit ne sont pas accessibles à un agent. Celles-ci n'ont aucun outil,
donc un nom que vous auriez pu voir cité ailleurs renvoie « unknown tool » :

| Capacité | Où cela se trouve à la place |
| --- | --- |
| Embaucher, renvoyer ou modifier un agent | L'interface des agents. Il n'existe aucun outil `hire_agent` / `fire_agent` / `update_agent` |
| Créer un espace de travail | `workspace.upsert` via RPC, qui initialise et estampille la propriété |
| Projets (créer / lister / modifier / classer) | L'interface des tickets. Les projets sont une surface d'opérateur — voir [Projets](/fr-FR/manuel/guides/projets/) |
| Poser à l'opérateur une question bloquante | L'outil `ask_user` du **harnais**, et non MCP. Il affiche un formulaire dans la conversation et bloque jusqu'à la réponse |
| Diagnostics par agent | Rien. Il n'existe aucun `doctor` — voir [Diagnostiquer un agent](/fr-FR/manuel/guides/diagnostiquer-agent/) |
| Calendrier et réunions | RPC réservé aux clients humains (voir plus haut) |
