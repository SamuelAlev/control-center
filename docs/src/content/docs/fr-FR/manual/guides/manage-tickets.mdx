Ce guide vous montre comment créer et gérer des tickets.

## Créer un ticket

### Depuis l’interface

1. Cliquez sur **Tickets** dans la barre latérale de l’espace de travail.
2. Appuyez sur **Nouveau ticket**.
3. Renseignez :
   - **Titre** — bref résumé. C’est le seul champ obligatoire.
   - **Description** — markdown, avec une barre d’outils de mise en forme.
   - **Statut** — **À faire** (la valeur par défaut) ou **Backlog**. Les états
     démarrés et terminaux s’atteignent par le cycle de vie, pas à la création.
   - **Priorité** — aucune, urgente, élevée, moyenne ou basse.
   - **Assigné à** — vous-même ou tout agent de l’espace de travail.
   - **Projet** — regroupement facultatif.
4. Appuyez sur **Créer**, ou activez d’abord **En créer d’autres** pour garder la
   boîte de dialogue ouverte et saisir plusieurs tickets rapidement.

La boîte de dialogue ne comporte aucun sélecteur de fournisseur. Le ticket est
créé auprès du fournisseur de tickets actif de l’espace de travail.

### Depuis un agent

Demandez à un agent dans un espace :

> Créez un ticket pour corriger le problème d’expiration de connexion sur les connexions lentes.

Il appelle l’outil MCP `create_ticket`. La priorité de cet outil est un **entier**,
pas un nom :

```
create_ticket(
  workspace_id: "...",
  title: "Fix login timeout on slow connections",
  description: "...",
  priority: 2
)
```

| Valeur | Priorité |
| ------ | -------- |
| `0`    | Aucune   |
| `1`    | Urgent   |
| `2`    | Élevée   |
| `3`    | Moyenne  |
| `4`    | Basse    |

Seuls `workspace_id` et `title` sont obligatoires ; `description`, `priority`,
`assignee` (un identifiant d’agent) et `team_id` sont facultatifs. L’outil est
classé comme écriture de synchronisation fournisseur et demande votre
approbation avant de s’exécuter.

## Modifier le statut d’un ticket

Les tickets suivent ce cycle de vie :

```
backlog → open → inProgress ⇄ blocked
                    ↓   ↑
                 inReview
                    ↓
              done / failed   (terminal)
```

`done`, `failed` et `cancelled` sont terminaux. `cancelled` est atteignable
depuis n’importe quel statut non terminal. `done` et `failed` sont atteignables
depuis `inProgress` ou `inReview` ; `open` peut aussi passer directement à
`blocked`. Le sélecteur de statut de l’interface liste tous les statuts sauf
`failed` — les agents le définissent avec `fail_ticket`.

Pour le changer, utilisez l’un des moyens suivants :

- la ligne **Statut** dans le panneau des propriétés du ticket,
- le sous-menu **Statut** du menu contextuel d’un ticket dans la liste,
- la puce **Statut** de la barre flottante après avoir sélectionné plusieurs
  tickets.

:::note[Le graphe de cycle de vie s’impose aux agents, pas à vous]
Toute modification de statut effectuée depuis l’interface est forcée, en
contournant entièrement le graphe — vous pouvez déplacer un ticket vers
n’importe quel statut proposé par le sélecteur, y compris rouvrir un ticket
`done`, `failed` ou `cancelled`. Le sélecteur ne propose pas `failed` comme
cible. Le diagramme ci-dessus régit les agents et l’automatisation : une
transition illégale tentée par un outil MCP ou un réconciliateur est journalisée
et ignorée, jamais appliquée.
:::

Les changements de statut émettent des événements de domaine
(`TicketStatusChanged`, `TicketCompleted` et d’autres) qui peuvent déclencher
des pipelines. Voir
[Configurer des déclencheurs de pipeline](/fr-FR/manuel/guides/declencheurs-de-pipeline/).

## Attribuer un ticket

1. Ouvrez le ticket.
2. Dans le panneau des propriétés, définissez **Assigné à** — vous-même, un
   autre membre de l’espace de travail ou un agent.

:::caution[L’attribution ne lance aucun travail]
L’attribution consigne la propriété et rien d’autre. Elle ne crée aucun espace,
ne change aucun statut et ne lance aucun agent — `TicketAssigned` est un pur
signal d’audit, sans répartiteur derrière lui. Pour faire travailler un agent,
adressez-lui un message dans un espace
(voir [Discuter avec un agent](/fr-FR/manuel/guides/discuter-avec-agent/)).

La seule exception : `TicketAssigned` est un type d’événement auquel vous pouvez
rattacher un déclencheur de pipeline, de sorte qu’un modèle qui vous est propre
peut réagir à une attribution.
:::

## Ajouter des étiquettes

Les étiquettes s’appliquent en bloc depuis la liste des tickets, et non depuis
un ticket isolé — le panneau des propriétés n’a aucune commande d’étiquette.

1. Survolez une ligne de la liste des tickets et cochez sa case. Cochez-en
   autant que nécessaire ; une barre flottante apparaît dès qu’un élément est
   sélectionné.
2. Dans cette barre, ouvrez la puce **Étiquettes**.
3. Choisissez une étiquette. Elle est ajoutée à chaque ticket sélectionné qui ne
   la possède pas ; les étiquettes existantes ne sont jamais supprimées.
   **Effacer les étiquettes** les retire toutes. Le sélecteur liste les
   étiquettes déjà présentes sur un ticket de l’espace de travail. Les agents
   peuvent ajouter un nouveau nom via `update_ticket` ou `tickets.patch`.

## Lier des tickets

Les relations se trouvent sur la carte **Relations** du ticket, dans le panneau
des propriétés, ou derrière **Lier à** dans le menu contextuel de la liste.

1. Ouvrez le ticket et repérez la carte **Relations**.
2. Appuyez sur sa commande d’ajout et choisissez la relation :

| Relation           | Signification                            |
| ------------------ | ---------------------------------------- |
| **Sous-tâche de…** | Le ticket parent est l’autre             |
| **Parent de…**     | L’autre ticket est un enfant de celui-ci |
| **Bloqué par…**    | Ce ticket est bloqué par l’autre         |
| **Bloque…**        | Ce ticket bloque l’autre                 |
| **Lié à…**         | Symétrique, sans direction implicite     |
| **Doublon de…**    | Ce ticket est un doublon de l’autre      |

3. Choisissez le ticket cible.

**Dupliqué par** apparaît dans la carte mais pas dans le sélecteur — c’est
l’inverse de **Doublon de** et il est défini depuis l’autre ticket. Chaque
relation listée est cliquable pour ouvrir le ticket lié et supprimable au
survol.

Les relations parent et sous-tâche sont stockées sur le ticket lui-même plutôt
que sous forme de lignes de lien ; supprimer un parent se répercute donc en
cascade sur ses enfants (voir ci-dessous), contrairement aux liens de blocage et
de liaison.

## Ajouter des collaborateurs

Les collaborateurs forment une liste rattachée au ticket : qui est impliqué, à
quel titre.

1. Ouvrez le ticket.
2. Appuyez sur la commande « personne + » de la carte
   **Ajouter un collaborateur**.
3. Choisissez un agent.

Les trois rôles sont **assignee**, **collaborator** (celui par défaut) et
**reviewer**. Le sélecteur de l’interface ne liste que les agents de l’espace de
travail et écrit toujours le rôle par défaut ; des humains peuvent apparaître
sous forme de lignes, mais ne sont pas proposés dans ce menu. L’outil MCP
`add_ticket_collaborator` accepte un `role`.

Ajouter un collaborateur écrit une ligne et ne publie aucun événement de
domaine ; cela n’accorde aucun accès à l’espace. Pour placer un agent dans une
conversation, ajoutez-le plutôt comme participant depuis l’en-tête de l’espace —
voir [Utiliser les espaces](/fr-FR/manuel/guides/espaces/).

## Supprimer un ticket

Utilisez **Supprimer le ticket** en bas du panneau des propriétés, le menu
contextuel, ou l’action de suppression de la barre flottante après une sélection
multiple.

:::caution[La suppression est locale uniquement]
Un ticket provenant d’un outil de suivi externe n’y est pas supprimé — aucun
fournisseur ne le prend en charge — il peut donc réapparaître à la prochaine
synchronisation. La suppression se répercute aussi en cascade : les
collaborateurs du ticket et ses éventuels tickets enfants disparaissent avec
lui.
:::
