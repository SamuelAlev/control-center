Ce guide couvre les aspects de la configuration propres à GitHub. GitHub est l’un
des trois hébergeurs de code pris en charge. Consultez
[Connecter un hébergeur de code](/fr-FR/manuel/guides/connecter-hebergeur-de-code/)
pour connecter GitLab ou Bitbucket, et pour savoir comment un espace de travail
combine les trois.

## Prérequis

- Un compte GitHub ayant accès aux dépôts sur lesquels vous voulez travailler
- Un serveur capable de connecter les personnes à GitHub : soit avec sa propre
  GitHub App (voir [Créer la GitHub App](/fr-FR/manuel/guides/github-app/)), soit
  avec Control Center Connect, au choix du propriétaire du serveur dans
  **Paramètres → Serveur → Authentification unique**

:::note[Les identifiants résident sur le serveur, rattachés à vous]
Rien n’est stocké sur la machine depuis laquelle vous tapez. Votre connexion
GitHub est détenue par votre `cc_server`, indexée par votre ID utilisateur, et
chaque appareil depuis lequel vous vous connectez l’utilise : ordinateur, web et
téléphone. Un autre membre du même serveur ne peut pas l’utiliser, et se
connecter est une chose qu’il fait lui-même.
:::

## Se connecter à GitHub

Pour GitHub, il n’y a que la connexion : aucun jeton à coller.

1. Accédez à **Paramètres → Vous → Profil → Hébergement de
   code** (ou à la première étape de la configuration initiale)
2. Sur la ligne **GitHub**, cliquez sur **Se connecter à GitHub**
3. Votre navigateur ouvre GitHub. Approuvez l’application

La façon dont la connexion se termine dépend de qui l’exécute :

- **L’application propre au serveur :** GitHub renvoie votre navigateur vers le
  serveur et la boîte de dialogue le remarque d’elle-même. Rien à saisir
- **Control Center Connect :** la page du navigateur affiche un code de
  8 caractères. Saisissez-le dans la boîte de dialogue, ou laissez le navigateur
  ouvrir Control Center via le lien `control-center://` pour éviter de le saisir

Point de contrôle : la ligne **GitHub** affiche « Connecté en tant que
_your-username_ ».

La boîte de dialogue refuse un code ou un lien qu’elle n’a pas lancé elle-même,
avec **Connexion non lancée d’ici**. Si quelqu’un vous envoie un lien de
connexion, ne continuez pas : aller au bout connecterait votre compte à son
serveur.

Cliquez sur **Déconnecter** pour supprimer votre connexion. Vous déconnecter de
GitHub, ou être retiré d’un espace de travail, invalide aussi tous les jetons que
le serveur a émis en votre nom.

## Pour qui parle votre identifiant

Control Center suit la séparation de GitHub entre agir **en tant que personne** et agir **en tant qu’application** :

| Ce qui se passe | Apparaît sur GitHub comme |
| --- | --- |
| Tout ce que vous faites vous-même : commenter, réviser, approuver, fusionner, demander des relecteurs | **Vous**. GitHub marque un commentaire de la conversation comme rédigé avec l’application Control Center ; une revue et ses commentaires en ligne ne portent aucune marque de ce type |
| Revue par IA, réponses et commentaires des agents dans les conversations de PR, étiquettes, travail des pipelines et du bot | **Le bot Control Center**. Sur l’application Connect partagée, une revue n’est celle du bot que pour une installation que l’opérateur de Connect a listée. Sinon, elle apparaît au nom de la personne responsable |
| Une pull request qu’un agent ouvre pour vous, ses modifications du titre ou de la description de cette pull request, ses push et ses commits | **Vous**. Control Center est crédité comme coauteur lorsque le crédit de co-auteur est activé |
| Travail que personne n’a demandé (planifications, webhooks) | **Le bot Control Center**, auteur aussi de ses commits. Sur Control Center Connect, il ne pousse jamais et n’ouvre jamais de pull request |

- **Tout ce que vous faites** s’exécute avec **votre** connexion et rien d’autre. Si vous n’êtes pas connecté, l’application vous demande de vous connecter. Aucun autre identifiant ne vous remplace
- **Le travail du bot** reçoit un jeton limité à un seul dépôt à la fois, borné à ce qu’un membre responsable peut y faire : le membre qui a demandé, sinon le propriétaire de l’espace de travail. Un membre qui ne peut pas pousser restreint le jeton à la lecture. Les réponses du bot qui agissent pour quelqu’un commencent par **Control Center (for @login)**
- **Les agents ouvrent des pull requests via Control Center**, jamais depuis leur bac à sable : la pull request est donc à vous, et les règles propres à GitHub vous empêchent de l’approuver vous-même. Control Center refuse aussi une approbation de la personne qui a demandé le travail à l’agent et de l’auteur de la pull request. Pour une exécution planifiée ou déclenchée par un webhook, cela vaut pour chaque administrateur qui a armé son déclencheur ou modifié son pipeline pendant qu’il était armé. Une autre personne doit relire. Si Control Center ne peut pas confirmer qui a ouvert la pull request, ni quel compte sur la forge est le vôtre, il refuse et vous demande de réessayer
- **Les agents commentent aussi via Control Center.** Le jeton GitHub qu’une exécution d’agent reçoit ne fait que lire. Lorsqu’un agent commente la pull request sur laquelle il travaille, Control Center publie le commentaire en tant que bot, en commençant par **Control Center (for @login)** lorsqu’une personne a demandé l’exécution. Un agent ne peut commenter que sa propre pull request : une dans le même dépôt, jamais un fork, dont le dernier commit a été poussé par l’agent ou correspond au commit courant de la branche de son espace. Les @-mentions dans le commentaire d’un agent ne notifient personne. Un agent peut aussi modifier le titre ou la description de sa propre pull request tant qu’elle est ouverte. Cette modification se fait de la même façon que la pull request a été ouverte (en votre nom, lorsque vous avez demandé l’exécution), et demande d’abord une approbation par défaut. La description d’une pull request conserve ses @-mentions, lorsque l’agent l’ouvre comme lorsqu’il la modifie : les personnes qu’elle nomme sont donc notifiées
- **Sur Control Center Connect, le bot ne pousse jamais et n’ouvre jamais de pull request.** Pousser, créer une branche ou ouvrir une pull request y exige une personne qui l’a demandé, et s’exécute avec la connexion de cette personne. Une exécution planifiée ou déclenchée par un webhook qui tente de pousser s’arrête avec un message qui l’indique. Pour permettre aux exécutions sans surveillance de pousser, donnez à l’espace de travail sa propre GitHub App dans **Paramètres**
- **Ce que peut faire le bot Connect.** Avec l’application Connect partagée, le bot commente, pose des étiquettes et réagit. Il publie une revue (une revue par IA, des commentaires de revue, des demandes de relecteurs) seulement lorsque l’opérateur de Connect a listé l’installation de ce serveur. Sinon, la revue part avec la connexion propre à la personne responsable et apparaît à son nom. Le bot n’ouvre, ne modifie, ne ferme ni ne renomme jamais une pull request, ne rejette jamais une revue, et ne modifie ni ne supprime jamais un commentaire. Ces actions exigent une personne qui les a demandées, avec sa propre connexion. Connect ne lie pas l’installation de votre organisation à un seul serveur Control Center : tout serveur où un membre pouvant pousser sur un dépôt s’est connecté via Connect peut obtenir le jeton de commentaire du bot pour ce dépôt
- **Un serveur ou un espace de travail disposant de sa propre GitHub App** garde le bot pour tout ce qui précède, revues comprises
- **L’automatisation n’approuve jamais** une pull request. L’approbation est un acte humain

Lorsque vous liez un dépôt, Control Center vérifie que votre compte peut le voir, et signale lorsque la GitHub App n’est pas installée sur son organisation ou ne l’inclut pas, avec un lien pour corriger. Lier et délier un dépôt exigent un administrateur d’espace de travail, et une copie de travail située hors du stockage de l’espace de travail ne peut être liée que par le propriétaire du serveur ; voir [Ajouter des dépôts à un espace de travail](/fr-FR/manuel/guides/ajouter-des-depots/).

Le lien suit l’identifiant GitHub permanent du dépôt, de sorte qu’un renommage ou un transfert ne demande rien de votre part. Si le chemin désigne plus tard un autre dépôt, Control Center cesse de lui envoyer quoi que ce soit et affiche un avis jusqu’à ce qu’un administrateur d’espace de travail clique sur **Relier à nouveau**.

Ouvrir le code d’un dépôt (fichiers, diff, recherche, un terminal) exige à la fois son autorisation dans l’espace de travail et une connexion GitHub à vous qui peut le lire. Les administrateurs d’espace de travail suivent la même règle ; seul le propriétaire du serveur est exempté.

## Ce que l’intégration vous apporte

| Fonctionnalité            | Fonctionnement                                                                                                        |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Liste et détail des PR    | L’API REST GitHub, depuis le serveur, avec votre propre connexion                                                     |
| Exécutions de vérification | L’API GitHub Checks                                                                                                  |
| Publication des revues    | Une étape soumise à une action de l’utilisateur, qui publie votre revue sur la PR, en votre nom                       |
| Enregistrement des dépôts | Un checkout est accepté si son dépôt distant `origin` pointe vers github.com, ou vers gitlab.com / bitbucket.org      |
| Accès GitHub des agents | Dans une exécution, `git fetch` passe par Control Center, qui récupère les dépôts sur lesquels l’exécution travaille avec un jeton de lecture seule que l’exécution ne détient jamais. `gh` les lit avec un jeton de lecture seule que Control Center délivre sur demande et révoque à la fin de l’exécution. Les push, les pull requests, leurs modifications et les commentaires passent par Control Center |
| Signaux de notification   | Une interrogation côté serveur de votre boîte de réception GitHub déclenche « Mentionné dans une pull request » et « Revue demandée » |
| Profils utilisateur       | Cartes de profil au survol et filtrage des PR par auteur                                                              |

Certains chemins passent par l’API GraphQL plutôt que REST lorsque c’est moins
coûteux : l’activité des branches pour le sélecteur de composition de PR et
l’état de revue en direct qui détermine si une notification de revue demandée est
encore en attente.

## Surveiller les pannes de GitHub

La barre de titre affiche une pastille d’état lorsqu’un fournisseur est dégradé,
pour GitHub, Claude, OpenAI et Kimi. **Elle est masquée tant que tout va bien** :
c’est la présence qui signale un problème, pas son absence.

Cliquez sur la pastille pour ouvrir un volet indiquant l’état de chaque
fournisseur, avec un bouton d’actualisation. Les états s’actualisent d’eux-mêmes
toutes les deux minutes.

## Savoir comment les agents agissent sur GitHub

- Un agent qui travaille dans un arbre de travail GitHub reçoit un jeton limité à
  ce seul dépôt. Il ne peut que lire le code, les tickets et les pull requests ; les commentaires
  passent par Control Center, comme décrit plus haut. Un
  push passe par Control Center, qui interroge la règle **Pousser vers un dépôt
  distant** puis le transmet avec un jeton d’écriture que l’agent ne détient
  jamais. Voir
  [Configurer les politiques de bac à sable](/fr-FR/manuel/guides/politiques-de-bac-a-sable/)
- Le travail que vous lancez est commité sous votre nom. Lorsque vous demandez quelque chose à un agent, ou que vous commitez dans l’IDE, vous êtes l’auteur et le committer, sous une adresse vérifiée par votre forge : votre adresse noreply GitHub depuis votre connexion GitHub, ou sur GitLab et Bitbucket l’e-mail que votre connexion là-bas signale. Votre identité Git de l’espace de travail n’est utilisée que pour un commit que vous faites à la main dans un dépôt où aucune forge ne garantit une adresse à vous. Si vous n’êtes pas connecté à cette forge, les commits d’un agent sont alors ceux du bot, et les notes de l’exécution le disent
- Le travail que personne n’a demandé est commité sous le nom du bot. Une exécution planifiée ou déclenchée par un webhook commite sous le nom de la GitHub App de l’espace de travail (`<app>[bot]`, avec son adresse noreply GitHub), ou sous `Control Center <hi@usectrl.dev>` lorsqu’il n’y a pas de GitHub App ou que le dépôt est sur GitLab ou Bitbucket
- **Créditer Control Center comme co-auteur** (**Paramètres** → **Vous** → **Commits**) ajoute une ligne `Co-Authored-By:` pour l’autre partie : Control Center sur vos commits, et sur les commits du bot chaque personne qui a armé le déclencheur à l’origine de l’exécution. Elle est active tant que vous ne la désactivez pas. Un administrateur d’espace de travail peut la décider pour tout le monde avec **Crédit de co-auteur** dans **Paramètres** → **Espace de travail** → **Général** ; votre propre choix est alors enregistré mais ne s’applique pas dans cet espace de travail. L’attribution propre à Claude Code est toujours désactivée
- Vos commits peuvent être signés. Sous **Commits vérifiés** dans **Paramètres** → **Vous** → **Commits**, choisissez **Créer la clé de signature**, puis ajoutez sa moitié publique à votre compte GitHub ou GitLab comme clé de signature. À partir de là, les commits des exécutions que vous demandez, ainsi que ceux que vous faites dans l’IDE, apparaissent comme vérifiés. La moitié privée reste sur votre serveur : quiconque contrôle ce serveur peut donc signer des commits à votre place tant que la clé est sur votre compte, et sur GitHub un commit déjà présenté comme vérifié le reste après que vous avez retiré la clé. Bitbucket n’a pas de clé de signature seule : n’ajoutez pas la clé là-bas, et les commits sur Bitbucket ne sont pas signés. Les commits du bot ne sont jamais signés
- Les commits que vous faites dans le panneau **Contrôle de source** de l’IDE ignorent les hooks Git du dépôt, comme le fait `git commit --no-verify`. Le Git du serveur ignore les assistants d’identifiants, éditeurs, outils de diff externes et signataires que le dépôt configure : il exécute Git sur sa propre machine, dans un arbre qu’un agent ou une pull request peut modifier. Voir [Commiter et pousser depuis Contrôle de source](/fr-FR/manuel/guides/examiner-et-fusionner-pr/#valider-et-pousser-depuis-contrôle-de-source)
- Chaque commit poussé par un agent est vérifié au préalable, y compris les couches que `stack_publish` pousse pour une pile. Un push qui nomme quelqu’un d’autre, supprime ou emprunte un crédit, ajoute une ligne de validation, ou n’est pas signé comme vos réglages l’exigent est refusé. Les commits que vous poussez vous-même depuis l’IDE vous appartiennent et ne sont pas vérifiés de cette façon
- Un terminal que vous ouvrez sur un rig reçoit votre propre connexion,
  restreinte à ce seul dépôt : les push qui en partent sont donc les vôtres
- Lorsqu’aucun jeton ne peut être émis (personne de responsable n’est connecté,
  l’application n’est pas installée sur le propriétaire, ou l’installation est
  suspendue), la commande qui l’a demandé indique la raison.
  Il n’existe aucun identifiant de repli

## Dépannage

### La liste des PR est vide et indique que GitHub n’est pas connecté

Vous n’êtes pas connecté à GitHub sur ce serveur. Cliquez sur **Se connecter à
GitHub** dans **Paramètres → Vous → Profil → Hébergement de code**. Les dépôts des autres forges ne sont pas
touchés.

### La ligne GitHub indique que la connexion n’est pas configurée sur ce serveur

Le serveur n’a ni GitHub App propre ni Connect. Le propriétaire du serveur
choisit l’un ou l’autre dans **Paramètres → Serveur → Authentification
unique** : **Créer mon application GitHub** prend environ deux minutes. Voir
[Créer la GitHub App](/fr-FR/manuel/guides/github-app/).

Dans un espace de travail sur ses propres applications, la ligne le signale lorsque
l’application GitHub de l’espace de travail manque ou est incomplète. Un administrateur
de l’espace de travail la complète sur la carte **Application GitHub**, dans
**Paramètres → Espace de travail → Intégrations** ; voir
[Donner à un espace de travail sa propre application](/fr-FR/manuel/guides/github-app/#donner-à-un-espace-de-travail-sa-propre-application).

### La boîte de dialogue indique que le code ne correspond pas

Saisissez le code exactement tel que le navigateur l’affiche : 8 lettres et
chiffres. Cinq codes erronés mettent fin à la connexion ; relancez-la.

### La connexion indique que l’application n’est pas installée

La GitHub App n’a aucune installation sur le compte propriétaire du dépôt. Un
administrateur de l’espace de travail l’installe depuis **Paramètres → Espace de
travail → Intégrations → Installations de l’application GitHub**.

### Tout le monde doit se reconnecter à GitHub

Le propriétaire du serveur a renouvelé la clé Connect du serveur, changé de
serveur Connect, ou le répertoire de données a été restauré sur une autre
machine. Les connexions via Connect sont liées au serveur qui les a établies.

### Un dépôt refuse de s’enregistrer

L’enregistrement exige les trois conditions suivantes : le chemin se trouve à
l’intérieur d’un arbre de travail Git, il possède un dépôt distant `origin`, et ce
dépôt distant pointe vers une forge prise en charge (github.com, gitlab.com ou
bitbucket.org). L’`origin` doit être le dépôt que vous reliez, et un dossier situé hors du stockage de l’espace de travail ne peut être relié que par le propriétaire du serveur. Voir
[Ajouter des dépôts à un espace de travail](/fr-FR/manuel/guides/ajouter-des-depots/).

### J’ai une autorisation, mais le dépôt indique que mon compte ne peut pas le lire

Votre compte GitHub ne peut pas lire ce dépôt, si bien que son code reste fermé pour vous même avec une autorisation de l’espace de travail. Connectez-vous à GitHub sous **Hébergement de code**, ou demandez l’accès au dépôt sur GitHub.

### « Impossible de confirmer votre accès à GitHub »

GitHub n’a pas pu être joint pour vérifier votre accès, si bien que Control Center a refusé plutôt que de deviner. Réessayez dans un instant.

### Les revues sur Connect apparaissent à mon nom, et non à celui du bot

Sur l’application Connect partagée, le bot ne publie des revues que pour les installations que l’opérateur de Connect a listées. Partout ailleurs, la revue part avec la connexion propre à la personne responsable. Pour que le bot publie les revues, donnez à l’espace de travail sa propre GitHub App.

### Tout cesse de fonctionner un moment après un usage intensif

C’est le coupe-circuit de la limite de débit. GitHub signale sa limite principale
par un `403` portant `x-ratelimit-remaining: 0` et une heure de réinitialisation ;
à la vue d’une telle réponse, le client fait échouer localement les requêtes
suivantes sans appel réseau jusqu’à l’écoulement de la fenêtre, de sorte qu’une
tempête de nouvelles tentatives ne peut pas aggraver la limite. Les défaillances
transitoires sont réessayées jusqu’à trois fois avec un délai exponentiel, en
respectant `retry-after`.
