Ce guide vous montre comment donner à votre serveur sa propre GitHub App. Cela
prend environ deux minutes, seul le propriétaire du serveur s’en charge, et il
ne faut le faire qu’une fois par serveur.

:::note[Vous n’en avez peut-être pas besoin]
Lorsque Control Center Connect est activé, les personnes se connectent à GitHub
au travers de l’App partagée de Control Center, ou de l’App qu’utilise le
Connect de votre organisation. Enregistrez la vôtre lorsque vous avez choisi
**Utiliser mes propres applications** : l’App du serveur n’est utilisée que dans ce
cas. Voir
[Control Center Connect](/fr-FR/manuel/reference/connect/).
:::

Pour vous connecter ensuite à votre propre compte, voir
[Configurer l’intégration GitHub](/fr-FR/manuel/guides/integration-github/).

## Ce que fait l’application

Une même inscription répond à deux tâches différentes :

| Tâche                         | Ce qui y répond                                     | Pourquoi c’est important                                                                       |
| ----------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **Une personne se connecte**  | L’identifiant client et le secret client de l’application | Chacun obtient un identifiant GitHub qui lui est propre, sur le serveur, sur chaque appareil |
| **Le serveur agit**           | L’identifiant de l’application et sa clé privée     | Les agents, les pipelines, les tâches d’interrogation et les réponses du bot reçoivent des jetons limités à un seul dépôt à la fois |

La seconde tâche n’emprunte jamais l’identifiant d’une personne en bloc. Chaque
jeton émis par le serveur couvre un seul dépôt et se limite à ce qu’un membre
responsable peut y faire. Lire un dépôt lié ne requiert que l’application ; tout
ce qui écrit requiert un membre capable de pousser. L’automatisation n’approuve
jamais une pull request.

L’application du serveur ne s’applique que sous **Utiliser mes propres
applications**. Avec Control Center ou un Connect personnalisé, Connect exécute
chaque voie, GitHub compris ; l’application du serveur reste enregistrée mais
inutilisée jusqu’à ce que vous reveniez en arrière. Un espace de travail sur ses propres applications
([Donner à un espace de travail sa propre application](#donner-à-un-espace-de-travail-sa-propre-application))
utilise sa propre application à la place, quel que soit le mode du serveur. Une application dont certains champs
manquent est une erreur, pas un repli : les
connexions GitHub sont refusées tant que tous les champs ne sont pas remplis.

## Prérequis

- Vous êtes le **propriétaire du serveur**. La carte **Applications
  fournisseur** est invisible pour tous les autres
- Un compte GitHub. L’application est créée sous ce compte
- Une adresse de serveur que votre navigateur peut joindre. L’URL publique du
  serveur (ou la boucle locale, pour le serveur propre à un ordinateur de bureau)
  est l’endroit où GitHub vous renvoie

## La créer en un clic

1. Allez dans **Paramètres → Serveur → Authentification unique** et faites
   défiler jusqu’à la carte **Applications fournisseur**
2. Dans le bloc **GitHub**, saisissez si vous le souhaitez, dans
   **Organisation (facultatif)**, l’organisation GitHub qui doit posséder
   l’application. Laissez le champ vide pour créer l’application sous votre
   propre compte ; la créer sous une organisation exige d’être propriétaire
   de cette organisation
3. Cliquez sur **Créer mon application GitHub**
4. Votre navigateur ouvre GitHub avec l’application déjà renseignée. Cliquez sur
   **Create GitHub App**
5. GitHub vous renvoie vers le serveur, qui enregistre l’identifiant de
   l’application, la clé privée, l’identifiant client et le secret client, puis
   ouvre la page d’installation de l’application

Rien n’est copié à la main, et le code de conversion va directement de GitHub à
votre serveur. Le lien ne fonctionne qu’une fois et expire au bout de dix
minutes ; s’il a expiré, cliquez de nouveau sur **Créer mon application GitHub**.

L’application s’appelle `Control Center <code>` et demande exactement ce
qu’utilise Control Center :

| Permission                                 | Accès                |
| ------------------------------------------ | -------------------- |
| Metadata                                   | Lecture              |
| Contents                                   | Lecture et écriture  |
| Pull requests                              | Lecture et écriture  |
| Issues                                     | Lecture et écriture  |
| Checks, Actions, Commit statuses           | Lecture              |
| Organization members                       | Lecture              |

Les webhooks sont désactivés : le serveur interroge GitHub. Pour transférer
plus tard à une organisation une application créée sous votre propre compte,
utilisez **Transfer ownership** dans les paramètres avancés de l’application sur
GitHub.

Point de contrôle : le bloc GitHub indique « Le serveur peut agir en son nom, et
les personnes peuvent se connecter ».

## Installer là où se trouvent vos dépôts

Une application enregistrée mais non installée peut connecter des personnes,
mais ne peut rien lire.

1. Sur la page d’installation que GitHub a ouverte, choisissez le compte ou
   l’organisation propriétaire de vos dépôts
2. Choisissez **All repositories**, ou sélectionnez ceux que ce serveur doit
   voir

Pour l’installer plus tard sur un autre compte, un administrateur de l’espace de
travail se rend dans **Paramètres → Espace de travail → Intégrations**, repère
**Installations de l’application GitHub** sur la carte **Application GitHub** sous
Hébergement de code et clique sur **Installer l’application GitHub**. La liste indique chaque compte
sur lequel l’application est installée et signale une installation suspendue.

## Partager l’installation d’une organisation

Une organisation installe la GitHub App une seule fois. Ensuite, toute personne de
l’organisation qui se connecte à GitHub sur un serveur Control Center peut utiliser
l’installation, quel que soit ce serveur : le sien, celui d’un collègue ou un serveur
à elle. Il n’y a rien à autoriser serveur par serveur.

Chaque jeton qu’obtient un serveur appartient à la personne connectée, est limité à
un dépôt et à son rôle sur ce dépôt, si bien qu’il ne dépasse jamais ce qu’elle
pourrait faire sur GitHub. Le journal d’audit de GitHub montre cette personne agissant
par l’intermédiaire de l’application.

Pour que Control Center cesse d’accéder à une organisation, un propriétaire de
l’organisation supprime l’installation ou réduit ses dépôts sur GitHub. Retirer une
personne de l’organisation lui retire aussi son accès.

## L’enregistrer plutôt à la main

La carte **Applications fournisseur** accepte aussi directement les valeurs,
pour une application que vous avez enregistrée vous-même :

| Groupe                                 | Champs                                                                                                   |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Agir en tant que serveur**           | **Identifiant d’application**, et **Clé privée** (le `.pem` complet, lignes `BEGIN` et `END` comprises)  |
| **Connexion des utilisateurs**         | **Identifiant client** et **Secret client**. **URL de rappel** affiche l’URL à enregistrer, à l’identique |
| **Conversations de pull request**      | **Login du bot**, résolu lorsque vous testez la connexion                                               |

Enregistrez l’URL de rappel `<server origin>/oauth/github/callback` exactement
telle que la carte l’affiche, laissez **Expire user authorization tokens**
activé et accordez les permissions du tableau ci-dessus. Cliquez sur
**Tester** : cela demande à GitHub sur quels comptes l’application est
installée, afin de ne pas confondre « enregistré » et « fonctionne ».

## La configurer depuis le `.env` du serveur

Pour une installation sans interface ou scriptée, le serveur amorce chaque champ
à partir de son fichier `.env` la première fois qu’il n’a aucune valeur stockée :

```bash
GITHUB_APP_ID=123456
GITHUB_CLIENT_ID=Iv23li0123456789abcd
GITHUB_CLIENT_SECRET=<secret>
GITHUB_APP_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\nMIIEow…\n-----END RSA PRIVATE KEY-----"
```

Mettez la clé sur **une seule ligne** : une valeur `.env` tient sur une ligne,
et `\n` entre guillemets doubles se décode en saut de ligne. Le serveur refuse
de démarrer lorsque `GITHUB_APP_PRIVATE_KEY` ou `GITHUB_CLIENT_SECRET` est
exporté dans l’environnement de son processus, où chaque processus enfant
pourrait le lire ; conservez-les dans le fichier `.env` (sous Docker, montez-le
sur `/app/bin/.env`). L’amorçage n’a lieu **qu’une fois par champ**, si bien
qu’une modification dans Paramètres n’est pas annulée au redémarrage suivant.

## Donner à un espace de travail sa propre application

Un espace de travail peut fonctionner avec une application à lui plutôt que celle
du serveur :

1. Un administrateur de l’espace de travail se rend dans **Paramètres → Espace de
   travail → Intégrations**
2. Sur la carte **Control Center Connect**, il choisit **Utiliser mes propres
   applications** puis clique sur **Appliquer**. Tout le monde dans l’espace de
   travail se reconnecte alors par les applications de l’espace de travail
3. La carte **Application GitHub** sous Hébergement de code contient maintenant
   les champs de l’application : **Identifiant d’application** et **Clé privée**
   sous **Agit pour cet espace de travail**, **Identifiant client** et **Secret
   client** sous **Connexion des utilisateurs**. Cliquez sur **Tester** une fois
   qu’ils sont renseignés

Les membres se connectent alors à cette application pour cet espace de travail.
Un espace de travail sur ses propres applications ne se rabat jamais sur
l’application du serveur ni sur Connect : tant que ses champs ne sont pas complets,
son travail GitHub est refusé. Le même choix couvre Google Calendar, Linear et la
recherche de GIF, chacun avec ses propres champs à côté de son fournisseur sur la
même page. Voir
[Donner à un espace de travail sa propre application Linear](/fr-FR/manuel/guides/integration-linear/#donner-à-un-espace-de-travail-sa-propre-application-linear)
et [Donner à un espace de travail son propre client Google](/fr-FR/manuel/guides/connecter-calendrier/#donner-à-un-espace-de-travail-son-propre-client-google).
Les autres choix de cette carte, et ce que fait chacun, sont décrits dans
[Choix par espace de travail](/fr-FR/manuel/reference/connect/#choix-par-espace-de-travail).

## Dépannage

### Créer mon application GitHub indique que le serveur n’a pas d’adresse

Le serveur n’a aucune URL publique vers laquelle un navigateur pourrait revenir.
Définissez `CC_SERVER_PUBLIC_URL` (ou `--public-url`) et réessayez.

### GitHub indique que le lien a expiré

La page à usage unique a déjà été utilisée, ou dix minutes se sont écoulées.
Recommencez depuis Paramètres.

### Tester indique que les identifiants fonctionnent mais que l’application n’est installée nulle part

L’enregistrement et l’installation sont deux étapes distinctes. Ouvrez la page
d’installation de l’application, ou utilisez **Installer l’application GitHub**
dans Espace de travail → Intégrations.

### Tester indique que la clé privée n’a pas pu être lue

Collez le fichier `.pem` entier, y compris les lignes `-----BEGIN` et
`-----END`. Une clé `ed25519` ou EC ne peut pas être utilisée : les GitHub Apps
signent en RSA.

### Un membre s’est connecté mais ne voit aucun dépôt

L’application n’est pas installée sur le compte qui en est propriétaire, ou son
installation sélectionne d’autres dépôts. Une connexion n’accorde que ce que
l’application est autorisée à voir.

### Les agents indiquent que l’installation de la GitHub App est suspendue

Quelqu’un a suspendu l’installation sur GitHub. Réactivez-la dans **Settings →
Applications → Installed GitHub Apps** du compte concerné.
