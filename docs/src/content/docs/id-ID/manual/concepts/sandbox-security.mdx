:::note[Sejauh mana sandbox OS menjangkau dan tidak menjangkau]
`cc_server` menyelidiki host saat boot dan membungkus eksekusi perintah agen
dalam sandbox bawaan OS bila tersedia — Seatbelt di macOS, bubblewrap di
Linux dan WSL2 (yang memerlukan `bwrap` dan `socat` di `PATH`). Bila tidak ada
backend — Windows, atau mesin Linux yang kehilangan alat tersebut — hanya
eksekusi agen milik pemilik server yang dimulai, tanpa kurungan, dan eksekusi milik
orang lain ditolak. Pemilik server dapat memulainya dengan `--sandbox off`, yang
menjalankan agen setiap anggota tanpa kurungan di mesin itu. Log startup menyebutkan
kasus mana yang berlaku; lihat [Agen di host tanpa sandbox](#agen-di-host-tanpa-sandbox).

Dua celah tetap bertahan meski ada sandbox dan perlu diingat:

- **Alat berkas dalam proses** milik harness bawaan (`read`, `write`, `edit`,
  `apply_patch`, `search`, `find`, `search_files`) berjalan di dalam proses
  server, jadi hanya `bash` yang dibungkus. Yang membatasinya adalah
  pembatasan jalur di dalam alat itu sendiri plus pagar pengaman tindakan.
- **Claude Code diluncurkan dengan `--dangerously-skip-permissions`**, karena
  `claude -p` yang non-interaktif akan tersendat selamanya pada prompt-nya
  sendiri. Panggilan berkasnya karena itu tidak dijaga oleh pagar pengaman Control Center, dan perintah shell-nya hanya oleh hook yang membaca baris perintah — sandbox OS adalah batas di sekelilingnya.
  :::

## Mengapa isolasi penting di sini

Agen membaca berkas, menjalankan perintah shell, dan memanggil API eksternal
atas nama Anda. Kegagalan yang Anda khawatirkan jarang berupa niat jahat —
melainkan agen yang salah membaca jalur lalu menulis ulang checkout kerja
Anda, atau agen yang mendorong cabang yang belum selesai Anda tinjau. Jadi
pertanyaan yang harus dijawab produk ini bukan “apakah agen ini dapat
dipercaya” melainkan “seberapa besar radius dampaknya saat agen salah”.

Control Center menjawabnya secara berlapis, dan lapisan-lapisan itu sengaja
dibuat independen. Jika satu hilang, yang lain tetap bertahan. Itu penting,
karena lapisan terluar — sandbox OS — adalah satu-satunya yang bersyarat: ia
bergantung pada host yang menyediakan backend, dan di Windows tidak ada host
yang menyediakannya. Jika tidak ada, server tidak diam-diam menjalankan agen setiap orang tanpanya.

## Agen di host tanpa sandbox

Server memutuskan sekali saat boot cara agen berjalan di mesinnya, dan mempertahankan keputusan itu hingga server dimulai ulang:

- **Dalam sandbox.** Host memiliki backend dan sandbox aktif. Setiap run dibungkus.
- **Nonaktif.** Pemilik server memulai server dengan `--sandbox off`. Agen setiap anggota berjalan tanpa kurungan di mesin ini. Itu pilihan pemilik untuk semua orang yang memakai server, bukan pengaturan untuk satu run.
- **Tidak tersedia.** Sandbox aktif tetapi host tidak memiliki backend. Sebuah run hanya dimulai bila orang yang bertanggung jawab atasnya adalah [pemilik](/id-ID/panduan-pengguna/konsep/otorisasi/#pemilik-server) server: orang yang memintanya, atau untuk jadwal, webhook, atau otomatisasi lain, orang yang diikatnya. Run milik orang lain ditolak sebelum kredensial dibuat atau proses dimulai, dengan pesan "Server ini tidak memiliki sandbox, sehingga hanya pemiliknya yang dapat menjalankan agen di sini. Pemilik dapat memasang sandbox atau mematikan sandboxing untuk semua orang."

Alasannya adalah kepemilikan mesin. Agen tanpa kurungan dapat melakukan apa pun yang dapat dilakukan akun pengguna server, jadi hanya orang yang memiliki akun itu yang menjalankannya, kecuali ia memutuskan lain untuk semua orang. Server Windows selalu berada dalam kasus tidak tersedia. Linux memiliki kekhasan sendiri, dibahas dalam [referensi backend sandbox](/id-ID/panduan-pengguna/referensi/backend-sandbox/#linux-bubblewrap): dispatch native saat ini gagal tertutup di sana meski bubblewrap terpasang.

Aturan yang sama berlaku untuk hal-hal kecil yang memulai proses untuk Anda:

- **Pembantu cepat yang berjalan lewat CLI ACP**: judul percakapan, `/btw`, `/handoff`, dan `/goal`. Saat server men-sandbox agen, mereka berjalan di dalam sandbox, dalam sesinya sendiri. Di bawah `--sandbox off` mereka berjalan tanpa kurungan. Tanpa sandbox yang tersedia, mereka hanya berjalan untuk permintaan yang dipertanggungjawabkan kepada pemilik server; untuk orang lain mereka dilewati, sehingga tidak ada judul yang dibuat dan pertanyaan sampingan melaporkan bahwa Content synthesizer tidak memiliki runner yang berfungsi. Pembantu yang tidak memulai alat tidak terpengaruh.
- **Golden test** sebuah pull request dalam pemeriksaan visual Review Studio mengikuti aturan yang sama.
- **Proses alat dan `bash`** dalam sebuah run tidak pernah kembali ke host. Jika server diatur untuk men-sandbox agen tetapi tidak memiliki sandbox untuk diberikan kepada run, run itu ditolak.
- **Pemeriksaan sebuah tujuan** berjalan dalam sandbox sekali pakai di atas worktree percakapan, dibatasi seperti `bash` milik agen. Tanpa sandbox, pemeriksaan tidak berjalan dan tujuan berhenti menunggu seseorang; di bawah `--sandbox off`, pemeriksaan berjalan seperti `bash` agen.
- **Tinjauan sebuah tujuan** berjalan hanya-baca pada setiap adapter: hanya membaca, worktree dipasang hanya-baca, tanpa `bash`, tanpa subagen, tanpa web. Adapter yang tidak dapat menjaga run tetap hanya-baca (agen ACP) tidak dipakai sebagai peninjau.

## Apa yang benar-benar membatasi agen

Ada lima hal yang membatasi eksekusi agen di setiap host, dengan atau tanpa
sandbox. Tidak satu pun merupakan batas kernel; semuanya nyata. Bila host
menyediakan backend, sandbox OS berada di atasnya, dan “Apa yang ditambahkan
sandbox dan di mana batasnya” di bawah membahas apa yang berubah karenanya.

**Worktree copy-on-write-nya sendiri.** Setiap percakapan menyediakan
checkout-nya sendiri untuk tiap repo yang ditautkan, diklon secara
copy-on-write melalui `rift` native yang dibundel alih-alih disalin byte demi
byte, sehingga isolasinya cukup murah untuk dijadikan bawaan. Repositori
terdaftar yang Anda tambahkan ke ruang kerja bukanlah direktori tempat agen
bekerja — dua percakapan yang menyentuh repo yang sama tidak dapat melihat
suntingan satu sama lain dan keduanya tidak menyunting checkout Anda.

Butirannya perlu diperjelas: **worktree bersifat per percakapan, bukan per
agen.** Dua agen dalam percakapan yang sama mendapat direktori kerja overlay
yang berbeda yang _berbagi_ `repos/` percakapan tersebut — dan memang itu
tujuannya, karena keduanya berkolaborasi pada satu perubahan — sementara
direktori agen privat masing-masing tetap terpisah. Copy-on-write adalah
satu-satunya backend di mana pun `rift` tersedia: sistem berkas yang tidak
dapat melakukan reflink, atau direktori data pada volume berbeda dari repo,
menggagalkan penyediaan alih-alih beralih ke cara lain. Windows adalah
pengecualian — tidak ada backend copy-on-write di sana, jadi `git worktree`
adalah backendnya, bukan degradasi diam-diam.

**Pembatasan jalur di alat berkas harness bawaan.** Alat `read`, `write`,
`edit`, `apply_patch`, `search`, `find`, dan `search_files` milik harness
menyelesaikan setiap jalur terhadap direktori kerja eksekusi plus akar
bersama — direktori `repos/` percakapan, tempat worktree berada, dan direktori
lampiran space bila ada — dan menolak apa pun yang berada di luarnya. Jalur
absolut hanya diterima jika memang sudah berada di dalam. Symlink di dalam
worktree yang menunjuk ke luar juga diselesaikan lalu ditolak. Inilah sebabnya
agen tidak dapat `write` ke `~/.ssh` bahkan tanpa sandbox sama sekali.

**Permukaan alat milik mode.** [Mode](/id-ID/panduan-pengguna/konsep/mode/)
sebuah percakapan menentukan alat mana yang diwujudkan untuk eksekusi
tersebut. Dalam mode hanya-baca (`plan`, `review`, `orchestrate`), alat yang
mengubah keadaan memang tidak ada di registri dan kebijakan perintah shell
untuk mode tersebut menolak setiap perintah yang mengubah keadaan secara
langsung — `git commit`, `git push`, `npm install`, `docker`, dan lainnya —
alih-alih menanyakannya. Alat yang tidak ada tidak dapat dipanggil, dan itu
jaminan yang lebih kuat daripada alat yang ada tetapi dijaga.

**Pagar pengaman tindakan yang terpadu.** Setiap alat yang mengubah keadaan
mendeklarasikan kelas efek yang dapat dihasilkannya dan mesin kebijakan
menyelesaikan masing-masingnya menjadi izinkan, tanya, atau tolak sebelum
panggilan berjalan. Sebuah `prompt` tanpa penyetuju yang terhubung
diselesaikan menjadi _ditolak_ — pertanyaan yang tidak dapat dijawab siapa pun
tidak pernah menjadi ya. Lihat
[Pagar pengaman](/id-ID/panduan-pengguna/konsep/pagar-pengaman/) untuk model
penyelesaiannya.

**Kredensial dari broker dan lingkungan yang disanitasi.** Kredensial dibuat per peluncuran dan dilepas saat eksekusi berakhir, dan token GitHub yang dipegang eksekusi dapat membaca tetapi tidak dapat push — lihat "Push melewati Control Center" di bawah. ACP, `bash` harness, dan Claude Code di
bawah pembungkus native mendapat lingkungan yang dibersihkan dari vektor
injeksi dynamic-linker dan interpreter (`LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`,
`NODE_OPTIONS`, `GIT_SSH_COMMAND`, dan sejenisnya) sebelum proses dimulai.
Claude Code melalui `NoSandboxAdapter` mewarisi lingkungan host.

### Di mana batas-batas itu menipis

Alat berkas milik harness berjalan _di dalam proses server_, bukan di proses
anak, sehingga tidak ada profil sandbox yang dapat membatasinya bahkan jika
dipasang — hanya `bash` yang melewati runner perintah yang di-sandbox.
Pembatasannya adalah pemeriksaan jalur yang dijelaskan di atas, dan karena itu
pemeriksaan tersebut bersifat menopang, bukan sekadar lapisan pertahanan
kedua.

Alat `bash` adalah tempat lain yang perlu ketelitian. Perintahnya dievaluasi
terhadap kebijakan perintah mode lalu dijalankan dengan lingkungan yang
disanitasi dan worktree sebagai direktori kerjanya. Bila backend tersedia,
proses itu dibungkus, jadi sandbox-lah yang mencegah perintah shell menulis di
luar worktree; bila tidak ada (setiap run di bawah `--sandbox off`, dan run milik pemilik sendiri di Windows atau di Linux tanpa `bwrap` dan `socat`) —
kebijakan perintah adalah satu-satunya yang berdiri antara perintah dan sisa
disk. Dalam mode `chat` kebijakan menolak secara keras daftar tetap (eskalasi
hak istimewa, penghancuran sistem dan disk, pelarian kontainer dan namespace)
dan menanyakan mutasi keadaan jarak jauh (`git push`, `gh pr create`,
publikasi dan pemasangan paket). Apa pun yang tidak ada di kedua daftar itu
akan berjalan. Pipeline, rantai, dan sub-shell diurai dan tiap sub-perintah
dievaluasi terpisah, dengan keputusan paling ketat yang menang.

Claude Code, saat dipakai sebagai adapter, adalah kasus ketika sandbox
memikul beban terbesar. Control Center meluncurkannya dengan
`--dangerously-skip-permissions`, karena `claude -p` yang non-interaktif akan
tersendat selamanya pada prompt persetujuannya sendiri. Panggilan baca, tulis, dan edit-nya terjadi di dalam prosesnya sendiri dan Control Center tidak pernah melihatnya. Panggilan `Bash`-nya dikirim, sebelum dijalankan, ke hook di server yang mengklasifikasikan baris perintah dan menanyakan aturan yang cocok, dan alat `mcp__*` yang dilayani Control Center melewati gerbang seperti biasa. Bila backend tersedia,
panggilan tak terlihat itu tetap terjadi di dalam pembungkus sandbox, jadi
OS-lah batas di sekelilingnya. Bila tidak ada, tidak ada apa pun. Setiap
adapter menyatakan hal ini dalam matriks penegakannya — lihat [matriks
kejujuran adapter](/id-ID/panduan-pengguna/konsep/pagar-pengaman/#matriks-kejujuran-adapter).

## Push melewati Control Center

Tidak ada flag izin per agen. Apakah agen boleh membuat commit, melakukan push,
membuka pull request, menulis ke pelacak, atau menjangkau jaringan ditentukan
oleh [pagar pengaman](/id-ID/panduan-pengguna/konsep/pagar-pengaman/) — izinkan, tanyakan dulu, atau
tolak — dan aturan yang sama berlaku adapter mana pun yang menjalankan agen.

Push adalah aksi yang harus tetap bertahan bahkan terhadap agen yang mencoba
mengakali aturan, jadi push ditegakkan lewat apa yang dipegang agen, bukan lewat
apa yang dijalankannya. Run tidak memegang token forge saat dimulai, dan `git`-nya tidak pernah mendapatkannya. Ketika `gh` membutuhkannya, Control Center memberikan token untuk satu repositori GitHub yang dikerjakan run, dicetak dari App GitHub ruang kerja, App milik server, atau Control Center Connect. Token itu hanya dapat membaca: tidak dapat push, berkomentar, atau mengubah. Konfigurasi git eksekusi menulis ulang setiap URL push GitHub (`https://github.com/`,
`git@github.com:`, `ssh://git@github.com/`) ke **gateway run agen**, sebuah
endpoint loopback di `cc_server`. Gateway membaca ref mana yang diperbarui oleh
push, menanyakan aturan **Push ke remote** — sehingga aturan yang dibatasi ke
branch, seperti "tolak push ke `main`", ikut berlaku — dan baru setelah itu
meneruskan push ke GitHub dengan token tulis yang dibuatnya untuk keperluan itu
dan tidak pernah diserahkan ke agen. Push yang ditolak muncul di keluaran git
itu sendiri:

```text
 ! [remote rejected] main -> main (Control Center policy: …)
```

Gateway hanya meneruskan push ke repo milik worktree itu sendiri atau ke repo
GitHub yang ditautkan ke ruang kerja. Fetch juga melewati gateway, di GitHub, GitLab, dan Bitbucket: gateway mengambil repositori yang dikerjakan run dengan kredensial yang disimpannya sendiri dan tidak pernah dilihat run. Di GitLab dan Bitbucket itu adalah token Anda sendiri ketika Anda meminta run tersebut, dan token otomatisasi repositori ketika tidak ada yang memintanya. Fetch tidak meminta persetujuan siapa pun, dan hanya aturan Tolak pada **Akses jaringan** yang menolaknya.

Perintah shell lainnya menemui gerbang yang lebih lunak. Alat `bash` milik
harness dan, melalui hook, alat `Bash` milik Claude Code mengklasifikasikan
setiap baris perintah dan menanyakan aturan yang menaunginya: `git commit`,
`merge`, `rebase`, `cherry-pick`, `revert`, dan `am` adalah **Buat commit**;
`gh pr create` adalah **Buka pull request**; `gh pr merge`, `review`,
`comment`, dan `close` adalah **Perbarui atau gabungkan pull request**;
`gh issue create`, `edit`, `comment`, dan `close` adalah **Tulis ke pelacak
eksternal**; instalasi paket adalah **Instal paket**; `curl` dan `wget` adalah
**Akses jaringan**. Menulis ke GitHub dari shell menjadi pengecualian: `gh pr create`, `gh pr comment`, `gh pr edit`, `gh pr merge`, dan penulisan `gh issue` tidak berfungsi dalam run, yang token-nya hanya dapat membaca, dan agen diarahkan ke alat Control Center, yang menanyakan aturan-aturan ini. Ini mengenali penulisan lazim sebuah aksi, dan agen yang
bertekad menyembunyikannya (`eval`, berkas skrip, panggilan API langsung) bisa
melakukannya. Push tidak bergantung pada hal ini.

Setiap token GitHub yang diterima eksekusi dibatasi dua kali: ke satu repositori, dan ke
apa yang dapat dilakukan anggota yang bertanggung jawab (yang meminta, jika tidak pemilik
ruang kerja) di repositori itu. Tidak ada kredensial cadangan. Ketika tidak ada token yang
dapat dicetak, perintah yang memintanya menjelaskan alasannya.

Tidak ada kunci API tiket yang ditaruh di sandbox. Agen menulis tiket melalui
alat MCP Control Center, yang menanyakan **Tulis ke pelacak eksternal**.

Aturan **Akses jaringan** dibaca sekali, saat eksekusi dimulai. Jaringan sandbox
hanya bisa menyala atau mati, jadi tolak mematikannya sementara izinkan dan
tanyakan dulu membiarkannya menyala; alat `web_fetch` dan `web_search` milik
harness tetap bertanya di setiap panggilan. Handle kredensial eksekusi dilepas
saat eksekusi dibongkar. Token di baliknya dibagikan per anggota dan repositori serta
kedaluwarsa dalam sekitar satu jam; anggota yang keluar dari GitHub atau meninggalkan
ruang kerja langsung membatalkan setiap token yang dicetak atas nama mereka.

## Repositori yang hanya bisa dibaca agen

Sebuah run agen hanya boleh mengubah checkout repositori yang dipegang [izin tulis](/id-ID/panduan-pengguna/konsep/otorisasi/#mengubah-kode-membutuhkan-izin-tulis) oleh orang yang diwakilinya. Admin ruang kerja memegangnya pada setiap repositori yang ditautkan. Run yang tidak diminta siapa pun, seperti jadwal atau otomatisasi lain, dinilai oleh orang bertanggung jawab yang sama dengan yang membatasi token otomatisasinya.

Di space yang memiliki repositori yang hanya bisa dibaca oleh orang itu, agen tetap dapat membaca dan mencari repositori tersebut, tetapi tidak dapat mengubah berkasnya. Alat berkasnya menolak dengan pesan yang diawali `<repo> is read-only for this run` dan menyatakan bahwa mengubah checkout memerlukan izin tulis, yang tidak dimiliki orang yang diwakili run, dan bahwa admin ruang kerja dapat memberikannya. Di dalam sandbox, checkout bersifat hanya-baca bagi setiap proses, sehingga perintah shell yang menulis di sana gagal dengan "Operation not permitted". Itu termasuk `git commit` dan build atau tes yang menulis keluarannya di dalam checkout. Repositori yang dapat ditulis orang itu berperilaku seperti biasa, sehingga admin, dan siapa pun yang memiliki akses tulis ke setiap repositori di space, tidak melihat perbedaan.

Ini diputuskan sekali, saat run dimulai. Perubahan grant berlaku pada run agen berikutnya, begitu pula repositori yang ditambahkan ke space selama sebuah run.

Jika pemilik server mematikan sandbox, hanya alat berkas agen dan alat tulis Claude Code yang ditolak, dan perintah shell tetap dapat mengubah checkout. Tidak ada yang dapat di-push tanpa izin tulis dalam kedua kasus, karena setiap push diperiksa terhadapnya. Proses mana yang dikurung sandbox di setiap platform ada di [backend sandbox](/id-ID/panduan-pengguna/referensi/backend-sandbox/).

## Apa yang ditambahkan sandbox dan di mana batasnya

Enum `SandboxBackend` memiliki tiga nilai — `native` (Seatbelt di macOS,
bubblewrap di Linux dan WSL2), `none`, dan `microvm`. Pembungkusan perintah
agen hanya memakai dua yang pertama: `microvm` adalah backend VM tertutup
untuk terminal interaktif dan rigs, bukan peningkatan diam-diam dari pembungkus
`bash`. Memahami bentuk native menjelaskan apa yang Anda dapatkan saat backend
terpasang dan apa yang memang tidak akan pernah diberikannya.

`cc_server` menyelidiki host sekali saat boot dan bila backend merespons ia
mengisi kedua titik sambung yang dimiliki jalur pengiriman, karena transportnya
tidak berbagi satu. Yang pertama (`SandboxPort`) membungkus CLI Claude Code.
Yang kedua (`SandboxManager`) membungkus adapter ACP dan alat `bash` harness
bawaan. Mengisi hanya salah satu akan membuat yang lain dijalankan tanpa
pembungkus, dan itulah yang dahulu terjadi. Di bawah `--sandbox off` semuanya dijalankan tanpa
pembungkus; di host tanpa backend hanya run milik pemilik yang dimulai, juga tanpa
pembungkus. Server menyebutkan kasus mana yang Anda alami di baris startup-nya. ACP dan `bash`
harness tetap menyanitasi lingkungan; Claude Code melalui `NoSandboxAdapter`
mewarisi lingkungan host.

Terminal yang dihosting server membuka shell host hanya untuk
[pemilik](/id-ID/panduan-pengguna/konsep/otorisasi/#pemilik-server) server. Orang lain mendapat
terminal yang di-sandbox, dengan batas milik agen, di direktori milik ruang kerja.
Hanya orang yang membuka terminal yang dapat mengetik ke dalamnya, membacanya, atau
menutupnya.

Di Linux, `bubblewrap` membangun namespace mount, sehingga agen benar-benar
hanya melihat apa yang di-bind ke dalamnya. Di macOS, `sandbox-exec` menerapkan
profil Seatbelt yang **permisif secara bawaan** — profil yang sepenuhnya
menolak secara bawaan membuat shell interaktif tidak dapat dipakai, karena
jumlah panggilan dyld, XPC, dan Mach yang harus dienumerasi tidak praktis.
Karena itu profil macOS dimulai dari `(allow default)` lalu memahat
penolakannya: pembacaan jalur rahasia, kebijakan tulis yang diatur ulang ke
tolak dengan izin eksplisit di atasnya, pemblokiran unlink pada setiap jalur
yang ditolak beserta leluhurnya agar rename tidak dapat melewati penolakan
tulis, penolakan exec untuk biner yang selalu berbahaya dan untuk apa pun yang
disalin ke direktori yang dapat ditulis, serta jaringan yang dibatasi ke port
proksi loopback plus DNS. Instalasi toolchain di bawah home Anda (pnpm dari corepack, pengelola versi node, browser Playwright, rustup, fvm, uv dan sejenisnya) tetap dapat dijalankan di dalam blok exec tersebut, sehingga agen dapat menggunakannya tanpa solusi tambahan. Penolakan untuk biner yang selalu berbahaya tetap berlaku di dalamnya. Setiap sesi juga mendapatkan `TMPDIR` pribadinya sendiri. Itulah satu-satunya direktori sementara tempat agen boleh menjalankan program yang dibangunnya atau membuka Unix socket.

Dua perlindungan lagi berlaku di setiap mode. Sandbox tidak dapat menambah, mengganti, menghapus, atau mengganti nama perintah di folder tempat server menjalankan program (setiap folder di `PATH`-nya dan folder alat per pengguna yang lazim), sehingga run yang di-sandbox tidak dapat menanam program yang kemudian dimulai server di luar sandbox. Instalasi global dan pergantian versi bawaan dari dalam run karena itu gagal dengan "Operation not permitted", sementara instalasi lokal proyek dan run gaya `npx` tetap berjalan; pasang alat global di server itu sendiri lalu mulai ulang. Dan setiap path home yang tidak dapat dibaca sandbox juga tidak dapat ditulis, dengan berkas start-up shell dan sesi milik pengguna server tidak pernah dapat ditulis. Rincian dan batas platform ada di [Folder perintah server](/id-ID/panduan-pengguna/referensi/backend-sandbox/#folder-perintah-server).

Sandbox alat sebuah run menjadi milik run itu dan dilepas saat run berakhir. Language server dimulai dari awal pada setiap run yang di-sandbox. Sesi debug mempertahankan sandbox-nya antar giliran hingga sesi berakhir, paling lama 30 menit.

Konsekuensi praktisnya: di Linux pandangan agen terhadap sistem berkas
dipersempit; di macOS agen masih dapat _membaca_ sebagian besar host dan
checkout terdaftar Anda dilindungi oleh penolakan tulis dan rename yang
eksplisit, bukan oleh ketaknampakan. Keduanya adalah isolasi tingkat namespace,
bukan batas keamanan kernel — para backend menyatakannya di catatan kemampuan
mereka masing-masing.

Himpunan bind-mount itulah tempat batas antaragen ditarik. Pengiriman overlay
(Claude Code dan ACP) me-mount hingga empat jalur, yang diselesaikan per
eksekusi: direktori kerja overlay agen dengan akses baca-tulis, direktori
konfigurasi agen dengan akses hanya-baca, direktori `repos/` bersama milik
percakapan dengan akses baca-tulis bila ada, dan direktori lampiran space
dengan akses hanya-baca bila ada. Direktori agen saudara tidak pernah
di-mount. Pembungkus `bash` harness lebih sempit: ia hanya me-bind-mount
direktori kerja eksekusi. Ini bentuk yang sama dengan yang ditegakkan
pemeriksaan jalur dalam proses milik harness di perangkat lunak, jadi keduanya
sejalan — tetapi hanya pemeriksaan jalur yang mencakup alat berkas milik
harness sendiri, yang sama sekali tidak pernah mencapai namespace mount.

Checkout terdaftar Anda bergabung ke himpunan tolak-tulis di atas itu, dalam
setiap mode dan pada ketiga jalur yang dibungkus (Claude Code, ACP, `bash`
harness), dan tiap aturan dikeluarkan dalam ejaan literalnya maupun ejaan yang
sudah diselesaikan symlink-nya. Ejaan kedua bukan sekadar kerapian: kernel
mencocokkan aturan tolak terhadap jalur yang sudah diselesaikan dan macOS
menjadikan penyelesaian itu kasus umum, bukan kasus langka — `/tmp` sebenarnya
`/private/tmp`, `/var/folders/…` sebenarnya `/private/var/folders/…` — sehingga
checkout yang dicapai lewat keduanya akan dapat ditulis padahal profil tampak
melarangnya.

Jaringan, di bawah sandbox, adalah daftar izin **domain** per sesi yang
ditegakkan oleh proksi loopback dalam proses. Egress ditolak secara bawaan:
saat jaringan mati, proksi tetap dimulai tetapi daftar izinnya kosong, jadi
setiap koneksi keluar ditolak. Saat menyala, resolver menyusun daftar izin dari
baseline terkurasi — penyedia API LLM, hosting git, registri paket, katalog
model — plus domain GitHub, lalu mencocokkan host tujuan setiap koneksi
dengannya. Wildcard berfungsi (`*.example.com` cocok dengan subdomain, bukan
apex-nya). Daftar yang selalu ditolak terpisah menang atas daftar izin dan
mencakup endpoint metadata cloud serta tujuan telemetri. Yang _tidak_ dapat
dikonfigurasi adalah daftar itu sendiri: spesifikasi membawa bidang
`egressAllowlist` untuk domain tambahan, tetapi tidak ada apa pun di jalur
pengiriman yang mengisinya, jadi dalam praktiknya setiap eksekusi mendapat
baseline plus GitHub dan tidak lebih.

Penolakan, di macOS, dapat diamati: sebuah monitor menyadap log sistem untuk
penolakan Sandbox, menyaring derau yang dikenal, menghilangkan duplikat badai
percobaan ulang, dan memunculkan masing-masingnya sebagai `SandboxViolation`
yang menyebutkan apa yang dicoba dan apa yang diblokir. Di
Linux jalur pembungkus mengurai stderr untuk `EPERM`,
`Operation not permitted`, dan `Permission denied` lalu memancarkan jenis
peristiwa yang sama — tidak ada penyadapan log sistem. Peristiwa itu tiba di
aliran peristiwa milik eksekusi, sehingga panggilan sistem yang ditolak muncul
di transkrip, bukan hanya di log. Telemetri ini hanya ada selama sandbox native
benar-benar membungkus proses — di host tanpa backend tidak ada apa pun untuk
diamati. Ini juga tidak berkaitan dengan pagar pengaman: pelanggaran berasal dari panggilan sistem yang ditolak, tidak pernah dari pencarian aturan.

## Skrip dalam mode kode

Skrip [mode kode](/id-ID/panduan-pengguna/konsep/mode-kode/) adalah kasus terpisah, dan sama sekali tidak bergantung pada sandbox agen. Skrip tidak pernah berjalan di dalam server dan tidak pernah berjalan di sandbox agen. Skrip berjalan di prosesnya sendiri, `cc_codemode`, sebuah program yang dikemas bersama server, yang mengunci dirinya sebelum membaca skrip dan melaporkan sejauh mana kuncinya berlaku. Server hanya mengirim skrip ketika kuncinya lengkap.

| Host | Yang diterapkan runner pada dirinya sendiri |
| --- | --- |
| Linux | Filter panggilan sistem (seccomp) yang membiarkannya tidak jauh lebih dari membaca input, menulis output, mengelola memorinya sendiri, membaca jam, dan keluar; tanpa hak istimewa baru dan tanpa capabilities; tanpa core dump; tanpa penulisan berkas, tanpa proses baru, dan paling banyak tiga berkas terbuka; ruang alamat 3 GiB; batas waktu prosesor yang keras. Landlock ditambahkan di tempat kernelnya mendukungnya. |
| macOS | Profil sandbox tolak-secara-default yang juga menolak informasi proses, pemeriksaan keberadaan berkas, informasi sistem dan perangkat keras, serta panggilan kernel terkait; tanpa core dump, tanpa penulisan berkas, dan dengan batas waktu prosesor yang keras. |
| Windows | AppContainer baru untuk setiap skrip, dalam job yang hanya mengizinkan satu proses, 3 GiB memori, dan tanpa antarmuka pengguna, dengan kode dinamis, proses anak, dan panggilan win32k dinonaktifkan. **Belum diuji di Windows.** |

Runner dimulai tanpa variabel lingkungan, tanpa berkas terbuka selain input dan outputnya, dan tanpa kredensial. Satu-satunya yang dapat dilakukannya di luar memorinya sendiri adalah meminta server menjalankan alat, dan server menjalankan panggilan itu melalui filter mode, [pagar pengaman](/id-ID/panduan-pengguna/konsep/pagar-pengaman/), dan persetujuan yang sama seperti panggilan langsung.

Server memeriksa semua ini saat mulai: ia menjalankan self-test runner, yang menerapkan kunci, mencoba membaca dan membuat berkas, membuka koneksi jaringan, dan memulai proses (serta lebih banyak lagi untuk setiap sistem), lalu menjalankan skrip sungguhan di bawahnya. Jika ada yang tidak ditolak, server tidak menjalankan skrip di mesin itu: tidak ada run yang mendapat `repl`, dan server menyebutkan alasannya saat mulai serta di halaman pengaturan mode kode. Runner yang bukan build rilis ditolak dengan cara yang sama. Tidak ada cadangan yang lebih lemah.

Runner juga melaporkan di mana dalam skrip setiap panggilan dibuat, sehingga percakapan dapat menampilkan struktur skrip. Server memeriksa posisi itu terhadap skrip dan hanya menggunakannya untuk tampilan: ia tidak pernah menentukan apakah sebuah panggilan diizinkan, dan posisi itu tidak tercatat dalam audit pagar pengaman.

Yang tidak tercakup: skrip tetap dapat melakukan apa pun yang diizinkan alat-alat run, karena panggilan alatnya adalah panggilan alat sungguhan; di macOS ia masih dapat mengetahui apakah sebuah id proses ada; dan cacat pada mesin JavaScript atau kernel dibatasi oleh kunci, tetapi tidak dicegah olehnya.

## Konfirmasi berasal dari pagar pengaman, bukan sandbox

Sandbox tidak punya jalur persetujuan. Ia meluncurkan, mengeksekusi,
memancarkan peristiwa, lalu membongkar; tidak ada tempat di dalamnya bagi
manusia untuk menjawab pertanyaan. Saat Anda melihat konfirmasi di sebuah
space — setujui push ini, setujui penghapusan ini — konfirmasi itu dimunculkan
oleh mesin pagar pengaman (atau kebijakan perintah harness) _sebelum_ tindakan
itu mencapai runtime sama sekali.

Urutan ini disengaja. Persetujuan yang terjadi setelah panggilan sistem
hanyalah catatan audit, bukan gerbang. Itu juga sebabnya aturan gagal-tertutup
berada di pagar pengaman: bila tidak ada penyetuju yang terhubung, keputusan
dibuat sebelum apa pun berjalan dan hasilnya adalah penolakan.

manual.

## Konsep terkait

- [Mode kode](/id-ID/panduan-pengguna/konsep/mode-kode/): skrip yang memanggil alat, dan runner yang membatasinya

- [Pagar pengaman](/id-ID/panduan-pengguna/konsep/pagar-pengaman/): lapisan kebijakan di atas dasar OS dan tempat persetujuan sebenarnya berasal
- [Siklus hidup pengiriman agen](/id-ID/panduan-pengguna/konsep/siklus-hidup-pengiriman/): tempat isolasi masuk ke dalam alur pengiriman
- [Mode](/id-ID/panduan-pengguna/konsep/mode/): bagaimana mode mempersempit permukaan alat dan kebijakan perintah
- [Referensi backend sandbox](/id-ID/panduan-pengguna/referensi/backend-sandbox/): backend dan konfigurasinya
