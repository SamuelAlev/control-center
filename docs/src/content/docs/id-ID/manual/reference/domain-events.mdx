## Bus peristiwa

`DomainEventBus` adalah bus publish/subscribe siaran dalam proses. Penerbit memanggil `publish(event)`; pelanggan mengonsumsi aliran `on<T>()` yang bertipe. Setiap peristiwa mengimplementasikan `DomainEvent` dan membawa `occurredAt`.

**Bus ini berjalan di dalam `cc_server`.** Setiap penerbit dan setiap pelanggan yang aktif berada di sana. Tidak ada klien yang melihat bus ini — server meneruskan subset terkurasi sebagai frame JSON-RPC `notifications/*`, yang difilter per pelanggan berdasarkan keanggotaan ruang kerja.

| Ukuran                                                      | Jumlah                                      |
| ----------------------------------------------------------- | --------------------------------------------- |
| Kelas peristiwa konkret                                     | 53                                          |
| Berkas sumber (`packages/cc_domain/lib/core/domain/events/`) | 14 (ditambah `domain_event_bus.dart`)       |
| Basis abstrak yang tidak pernah diterbitkan secara langsung | 1 (`TaskLifecycleEvent`, hierarki sealed)   |

Setiap peristiwa dalam katalog di bawah ini berada di satu direktori tersebut; tidak ada peristiwa domain yang dideklarasikan di tempat lain.

## Peristiwa siklus hidup tugas

Aliran siklus hidup tugas yang terpadu — satu run agen yang dikirim, dikunci oleh id log run-nya. Setiap peristiwa membawa `taskId`, `seq` per tugas yang monoton, `workspaceId?`, `agentId?` dan sebuah `phase`; baris-baris di bawah ini hanya mencantumkan kolom tambahannya.

| Peristiwa                   | Payload                       | Dipicu saat                                                                                      |
| --------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `TaskDispatched`            | —                             | Tugas diserahkan ke backend untuk dieksekusi                                                     |
| `TaskRunning`               | —                             | Tugas mulai menghasilkan output                                                                  |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | Tugas diparkir — tugas lain memegang kunci jalur di disk yang dibutuhkannya                      |
| `TaskProgress`              | `note?`                       | Pos pemeriksaan kemajuan di tengah run                                                           |
| `TaskMessage`               | `messageType`, `content`      | Pesan yang dialirkan (text/thinking/tool_use/tool_result/error); dilaporkan dalam fase `progress` |
| `TaskCompleted`             | `summary?`                    | Tugas selesai dengan sukses                                                                      |
| `TaskFailed`                | `errorMessage`                | Tugas selesai dengan kesalahan                                                                   |
| `TaskCancelled`             | —                             | Tugas dibatalkan sebelum selesai                                                                 |

Enum `TaskPhase` juga memiliki anggota `queued`, tetapi tidak ada yang menerbitkan peristiwa queued — tidak ada kelas `TaskQueued`. Frame pertama yang dapat diamati dari sebuah tugas adalah `TaskDispatched`.

## Peristiwa pipeline

| Peristiwa              | Payload                                       | Dipicu saat                                                                 |
| ---------------------- | --------------------------------------------- | --------------------------------------------------------------------------- |
| `PipelineRunCompleted` | `workspaceId`, `pipelineRunId`, `templateId`  | Run selesai                                                                 |
| `PipelineRunCancelled` | `workspaceId`, `pipelineRunId`, `templateId`  | Run dibatalkan (oleh pengguna atau sistem) — penghentian yang disengaja, bukan kesalahan |

Hanya transisi terminal yang diterbitkan. Tidak ada `PipelineRunStarted` dan tidak ada peristiwa per langkah: kemajuan sebuah langkah sampai ke klien melalui baris milik run itu sendiri dan aliran siklus hidup tugas dari agen apa pun yang dikirimnya, bukan melalui bus.

| Peristiwa                    | Payload                         | Dipicu saat                                                                                               |

| `WorkspaceMemberRemoved`     | `workspaceId`, `userId`         | Seorang anggota dihapus — sesi aktif pengguna tersebut yang tercakup ke ruang kerja harus segera memeriksa ulang aksesnya |

## Peristiwa rig

| Peristiwa           | Payload                                       | Dipicu saat                                                                                                                      |
| ------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `RigClosedEvent`    | `workspaceId`, `rigId`, `reason`              | Sebuah rig hilang, beserta alasan penutupannya; konsumen hanya bertindak atas `backendFailure` — semua alasan lainnya diminta atau disertai `RigReaped` |
| `RigControlChanged` | `workspaceId`, `rigId`, `controller?`         | Seorang manusia mengambil kendali eksklusif atas sebuah rig atau mengembalikannya (`controller` null saat dilepas — peristiwa ini tidak mencatat siapa yang melepasnya) |
| `RigReaped`         | `workspaceId`, `rigId`, `reason`, `agentId?`  | Sistem mengambil kembali sebuah mesin: pengusiran karena idle, TTL, atau tekanan memori (dilaporkan sebagai `idleTimeout`), beserta agen yang menggerakkannya |

Sebuah rig yang **dibuka** bukanlah peristiwa. Proses boot selesai dan baris rig berubah menjadi siap; tidak ada yang diterbitkan, jadi tidak ada `RigOpened` untuk dilanggani.

## Subdomain yang tidak memiliki peristiwa sama sekali

Beberapa subsistem yang dari luar tampak digerakkan oleh peristiwa ternyata bukan. Semuanya dicantumkan di sini karena ketiadaan peristiwanya adalah keputusan desain yang perlu diketahui sebelum Anda mencari-cari hook:

| Subdomain           | Bagaimana status berpindah sebagai gantinya                                                             |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| Memori              | `record_memory_fact` dan kawan-kawan menulis lalu kembali; recall membaca. Tidak ada yang menerbitkan apa pun saat ada fakta atau konflik |
| Orkestrasi          | Proposal, persetujuannya, dan run pipeline yang dihasilkan adalah baris dan panggilan RPC               |
| Dokumen rencana     | `submit_plan` menulis revisi; persetujuan mewujudkan sebuah orkestrasi. Keduanya tidak diumumkan        |
| Artefak             | `publish_artifact` / `revise_artifact` menulis revisi secara langsung                                    |
| Persetujuan         | Eskalasi ditangani di dalam layanan alur kerja persetujuan                                              |
| Sinkronisasi tiket  | Koordinator vendor berlangganan peristiwa tiket di atas; webhook masuk diterapkan secara langsung       |
| Penyegaran kalender | Sinkronisasi melakukan upsert peristiwa dan klien membacanya ulang; tidak ada siaran penyegaran         |
| Penggabungan worktree | Dicatat di `worktree_merge_log` dan dibaca dari sana                                                  |

`TicketAssigned` adalah sinyal audit dan notifikasi sekaligus pemicu pipeline. Penugasan kepada agen mencatat kepemilikan dan tidak memulai run apa pun — tidak ada dispatcher tiket. Penugasan kepada tim (`assignedTeamId` diisi) adalah pengecualiannya: `TeamRoutingService` mengirim pemimpin tim.

`TicketRemoteSyncHandler` dideklarasikan tetapi tidak pernah dikonstruksi di kode produksi, jadi saat ini ia tidak berlangganan apa pun. `NotificationEventMapper` di sisi klien hanya dikonstruksi di pengujiannya sendiri — ia adalah sisa dari jalur dalam proses sebelum pemisahan klien/server. Toast langsung berasal dari frame yang dijelaskan di bawah ini.

## Pemetaan notifikasi

Di server, `NotificationFeedRecorder` dan `RemoteEventForwarder` mengubah peristiwa-peristiwa ini menjadi frame wire `notifications/*` (`notification_wire.dart`). Di klien, `RpcNotificationMapper` → `mapNotificationFrame` mengubah sebuah frame menjadi `AppNotification`.

Tepat ada **enam belas** kategori notifikasi. Beberapa peristiwa dipetakan ke lebih dari satu metode wire, karena frame membawa transisinya (gagal versus pulih) sementara kategori membawa pertanyaannya ("apa yang sedang dilakukan CI?").

| Kategori               | Peristiwa sumber          | Metode wire                                                            |
| ---------------------- | ------------------------- | ------------------------------------------------------------------------ |
| `newMessage`           | `MessageReceived`         | `notifications/message_received` (menyebut Anda)                       |
| `agentRunCompleted`    | `MessageReceived`         | `notifications/message_received` (`is_agent_message`, tidak menyebut Anda) |
| `ticketAssigned`       | `TicketAssigned`          | `notifications/ticket_assigned`                                        |
| `ticketStatusChanged`  | `TicketStatusChanged`     | `notifications/ticket_status_changed`                                  |
| `pullRequestPublished` | `PullRequestPublished`    | `notifications/pr_published`                                           |
| `prMerged`             | `PrMerged`                | `notifications/pr_merged`                                              |
| `prMerged`             | `ExternalPrMerged`        | `notifications/external_pr_merged`                                     |
| `prMentioned`          | `PrMentioned`             | `notifications/pr_mentioned`                                           |
| `prMentioned`          | `PrCommentMentioned`      | `notifications/pr_comment_mentioned`                                   |
| `reviewRequested`      | `PrReviewRequested`       | `notifications/pr_review_requested`                                    |
| `reviewStale`          | `ReviewBecameStale`       | `notifications/review_stale`                                           |
| `prMergeReadiness`     | `PrMergeReadinessChanged` | `notifications/pr_ready_to_merge` / `pr_merge_blocked`                 |
| `prReviewDecision`     | `PrReviewDecisionChanged` | `notifications/pr_approved` / `pr_changes_requested` / `pr_review_dismissed` |
| `prChecksStatus`       | `PrChecksStatusChanged`   | `notifications/pr_checks_failed` / `pr_checks_recovered`               |
| `prThreadActivity`     | `PrThreadReplied`         | `notifications/pr_thread_replied`                                      |
| `prThreadActivity`     | `PrThreadResolved`        | `notifications/pr_thread_resolved`                                     |
| `meetingStartsSoon`    | `MeetingStartingSoon`     | `notifications/meeting_starting_soon`                                  |
| `calendarAuthExpired`  | `CalendarAuthExpired`     | `notifications/calendar_auth_expired`                                  |
| `rigStatusChanged`     | `RigControlChanged`       | `notifications/rig_control_changed`                                    |
| `rigStatusChanged`     | `RigReaped`               | `notifications/rig_reaped`                                             |
| `rigStatusChanged`     | `RigClosedEvent`          | `notifications/rig_closed`                                             |

Frame pengambilalihan rig tidak dikirim kembali kepada siapa pun yang mengambil alih, pelepasan tidak difilter (peristiwa ini tidak mencatat siapa yang melepasnya), dan hanya penutupan `backendFailure` yang menghasilkan frame `rig_closed` — alasan lainnya diminta atau sudah tercakup oleh frame reap.

Kelima kategori PR yang Anda tulis membawa `forUserId`, sehingga sampai ke penulisnya alih-alih ke semua orang di ruang kerja.

`RemoteEventForwarder` juga meneruskan `TicketReassigned` sebagai `notifications/ticket_reassigned` dan setiap `TaskLifecycleEvent` sebagai `notifications/task_<phase>`. Keduanya tidak dipetakan ke kategori notifikasi — keduanya menggerakkan UI langsung, bukan pusat notifikasi. Peristiwa keanggotaan tidak diteruskan sebagai frame: peristiwa itu membatalkan cache forwarder, dan host sesi menjatuhkan langganan ruang kerja anggota yang dihapus.
