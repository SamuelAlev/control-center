Semua yang bisa disalin, diserahkan, atau diadopsi Control Center, beserta bentuk persis
setiap artefaknya. Untuk benar-benar membuat cadangan, lihat
[Cadangkan dan pulihkan](/id-ID/panduan-pengguna/panduan-praktis/cadangkan-dan-pulihkan/); untuk alasan persistensi
dipisah seperti ini, lihat [Ruang kerja dan isolasi](/id-ID/panduan-pengguna/konsep/ruang-kerja/).

## Artefak

Ada tiga artefak salinan basis data, dengan cakupan dan kebijakan penghapusan yang berbeda.

| Artefak                 | Ditulis oleh                 | Bentuk                                | Cakupan                        |
| ----------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **Snapshot instalasi**  | `server.backupNow`           | **Direktori** bertanda waktu          | Setiap basis data di instalasi |
| **Cadangan ruang kerja**| Pipeline `Workspace backup`  | Direktori bertanda waktu dengan satu `.db` | Basis data satu ruang kerja |
| **Ekspor ruang kerja**  | `workspace.export`           | Satu **file** `.db`                   | Basis data satu ruang kerja    |

Semuanya ditulis dengan `VACUUM INTO` SQLite, yang aman terhadap basis data WAL yang
aktif: perintah ini mengambil transaksi baca, menghasilkan salinan yang didefragmentasi
dan konsisten secara transaksional, serta tidak pernah memerlukan penghentian server.

File-file ini dan salinan yang diunduh **tidak dienkripsi saat tersimpan** oleh
Control Center. Transfer terenkripsi ujung ke ujung melindungi byte saat transit
antara klien yang dipasangkan dan `cc_server`-nya, baik pada koneksi langsung
maupun melalui relay yang diperantarai. Lindungi penyimpanan lokal serta salinan di
luar mesin secara terpisah; server dan penerima mana pun yang berwenang dapat
membaca file basis data.

## Tata letak snapshot

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Tata letaknya mencerminkan direktori data aktif dengan persis, itulah yang membuat
pemulihan sebuah instalasi sekadar menyalin kembali, bukan menerjemahkan. Nama
direktorinya adalah stempel waktu UTC dengan `:` dan `.` diganti `-`, jadi aman untuk
sistem berkas di Windows dan terurut secara kronologis sebagai string biasa.

Cadangan ruang kerja terjadwal berada terpisah di
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Setiap cadangan memiliki `manifest.json` untuk berkas itu saja dan tanpa `global.db`; cadangan itu bukan snapshot instalasi. Pemulihan menyimpan basis data yang digantikannya di tempat yang sama, sebagai `<timestamp>-pre-restore`.
Langkah retensi pipeline mingguan hanya menghapus cadangan ruang kerjanya sendiri
yang lebih tua dari usia yang dikonfigurasi (bawaannya 30 hari); snapshot instalasi
yang dibuat secara manual tidak pernah dipangkas oleh langkah itu. `server.listBackups`
hanya mendaftarkan snapshot instalasi, termasuk yang belum diverifikasi;
`workspace.listBackups` mendaftarkan cadangan terjadwal satu ruang kerja.

Menghapus ruang kerja membiarkan direktori ini tetap ada. Jadwal ruang kerja itu ikut
berhenti, sehingga tidak ada lagi yang memangkas cadangan tersebut, dan cadangan itu tetap
ada sampai pemilik instalasi menghapusnya. `server.listOrphanedBackups` melaporkannya.


### `manifest.json`

| Kolom                      | Tipe            | Arti                                                                |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                  | int             | Format manifest. Saat ini `2`                                 |
| `created_at`               | ISO-8601 UTC    | Kapan snapshot diambil                                              |
| `global` | object | Catatan `global.db`. Tidak ada di cadangan ruang kerja terjadwal |
| `workspaces[]`             | array           | Satu catatan per ruang kerja yang terekam                             |
| `workspaces[].workspace_id`| string          | Ruang kerja yang dimuat file ini                                    |
| `skipped_workspaces[]` | array | Ruang kerja yang **tidak** bisa direkam oleh cadangan |
| `skipped_workspaces[].workspace_id` | string | Ruang kerja yang dilewati |
| `skipped_workspaces[].reason` | string | `no_file`, `damaged` atau `failed` |

`global` dan setiap catatan `workspaces[]` mencatat satu berkas yang disalin, diukur pada salinan setelah ditulis:

| Kolom | Tipe | Arti |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | string          | Path relatif terhadap akar snapshot: `global.db` atau `<workspaceId>/workspace.db`  |
| `bytes`       | int             | Ukuran salinan                                                     |
| `sha256` | string | SHA-256 salinan, dalam hex huruf kecil |
| `quick_check` | string | Hasil `quick_check` SQLite untuk salinan itu: `ok`, atau temuannya |
| `user_version` | int | Versi skema salinan |
| `application_id` | int | `application_id` SQLite salinan |

Ruang kerja dilewati ketika ruang kerja itu terdaftar tetapi belum pernah ditulisi (`no_file`), ketika basis datanya gagal pemeriksaan integritas (`damaged`; salinan yang rusak tidak pernah dibuat), atau ketika salinannya atau pemeriksaan atas salinan itu gagal (`failed`). Dengan cara apa pun, snapshot tetap selesai dan manifest menyebutkan apa yang hilang. Manifest ditulis paling akhir.

### Kelengkapan

`server.listBackups` melaporkan flag `complete` per snapshot. Flag itu bernilai false ketika manifest tidak ada, tidak bisa diurai, atau berformat lain, ketika sebuah file yang disebutnya tidak ada atau ukurannya berbeda, atau ketika sebuah salinan tidak lolos pemeriksaannya. Aplikasi menampilkan snapshot seperti itu sebagai **Belum diverifikasi**. Snapshot yang dibuat sebelum format `2` berada dalam kondisi itu.

Snapshot yang belum diverifikasi tetap didaftarkan, karena snapshot yang tidak bisa dilihat
operator adalah snapshot yang mereka yakini mereka miliki. Ketika manifest tidak bisa
dibaca, daftar itu beralih ke tata letak itu sendiri dan melaporkan file
`<workspaceId>/workspace.db` apa pun yang ditemukannya — file-file itu tetap bisa
diadopsi satu per satu melalui `workspace.import` meskipun snapshot secara keseluruhan
tidak bisa memulihkan instalasi.

Snapshot atau cadangan terjadwal yang tercantum membawa `pinned_reason: "last_good_copy"` selama menyimpan salinan terverifikasi terbaru dari ruang kerja yang basis data aktifnya rusak. Langkah retensi melewatinya sampai ruang kerja itu dipulihkan.

## Apa yang tidak dimuat cadangan

Kedua artefak itu **hanya basis data**. Direktori ruang kerja memuat lebih dari sekadar
basis datanya, dan tidak ada bagian lain yang ikut berpindah:

| Path                                | Ada di snapshot? | Ada di ekspor ruang kerja? |
| ----------------------------------- | ---------------- | -------------------------- |
| `global.db`                         | Ya               | Tidak                      |
| `<workspaceId>/workspace.db`        | Ya               | Ya (*itulah* filenya)      |
| `<workspaceId>/code_index.db`       | Tidak           | Tidak                  |
| `<workspaceId>/blobs/`              | Tidak            | Tidak                      |
| `<workspaceId>/skills/`             | Tidak            | Tidak                      |
| `<workspaceId>/agents/`             | Tidak            | Tidak                      |
| `<workspaceId>/chat_credentials/`   | Tidak            | Tidak                      |
| `<workspaceId>/spaces/<spaceId>/`   | Tidak            | Tidak                      |
| `<workspaceId>/pr_clones/`          | Tidak            | Tidak                      |
| `secrets.json`                      | Tidak            | Tidak                      |
| `models/`                           | Tidak            | Tidak                      |
| `meetings/<meetingId>/`             | Tidak            | Tidak                      |
| `rigs/`                             | Tidak            | Tidak                      |
| `_agent_hooks/`                     | Tidak            | Tidak                      |

Sebagian dari itu bisa dibuang — `spaces/` menyimpan worktree copy-on-write yang
disediakan ulang dari repo, `pr_clones/` adalah cache, `code_index.db` dibangun ulang, `models/` diunduh ulang, `rigs/`
adalah status mesin. Sebagiannya lagi tidak: `blobs/` menyimpan gambar yang ditempelkan
dan dirujuk baris-baris di basis data, `skills/` dan `agents/` menyimpan file yang dipakai
agen untuk berjalan, dan `secrets.json` menyimpan setiap kunci pemasangan, kredensial
penyedia, dan pengaturan SSO di instalasi. Lihat
[Cadangkan dan pulihkan](/id-ID/panduan-pengguna/panduan-praktis/cadangkan-dan-pulihkan/#menyalin-cadangan-ke-luar-mesin)
untuk menutupi sisanya.
:::note[Rahasia tetap berada di luar basis data]
`workspace.db` adalah seluruh ruang kerja: percakapan, log run, tautan repositori, definisi lingkungan, dan anggotanya. Token webhook pipeline dan rahasia webhook sinkronisasi tiket berada di `secrets.json`: basis data hanya menyimpan referensi untuk masing-masing, dan indeks rute menyimpan hash berkunci dari setiap token. Ruang kerja yang dipulihkan di instalasi lain karena itu tidak menerima webhook sampai pemicunya disimpan ulang di sana. Proses masuk penyedia, kunci perangkat, dan rahasia pengguna berada di `global.db` dan `secrets.json`.
:::

:::note[Token chat sengaja ditinggalkan]
`chat_credentials/` berada di samping basis data alih-alih di dalamnya, itulah sebabnya
ruang kerja yang diserahkan kepada orang lain tidak membawa token bot yang aktif. Lihat
[referensi jembatan chat](/id-ID/panduan-pengguna/referensi/jembatan-chat/).
:::

## Operasi

RPC cadangan instalasi dan ekspor/impor ruang kerja hanya untuk `fullClient`: ponsel yang
dipasangkan tidak bisa memicunya. Semuanya sama sekali tidak ada — bukan ditolak,
melainkan tidak ada secara struktural — pada server yang tidak memiliki port cadangan,
seperti server demo.

| Operasi              | Jenis  | Cakupan    | Peran minimum     | Argumen       | Hasil                         |
| -------------------- | ------ | ---------- | ----------------- | ------------- | ----------------------------- |
| `server.backupNow`   | mutasi | Instalasi  | **pemilik** instalasi | tidak ada | `{ok, path}`                  |
| `server.listBackups` | baca   | Instalasi  | **pemilik** instalasi | tidak ada | `{backups: [...]}`            |
| `server.deleteBackup` | mutasi | Instalasi | **pemilik** instalasi | `name` | `{ok}` |
| `server.listOrphanedBackups` | baca | Instalasi | **pemilik** instalasi | tidak ada | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutasi | Instalasi | **pemilik** instalasi | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | baca | Ruang kerja | `admin` | tidak ada | `{backups: [...]}` |
| `workspace.deleteBackup` | mutasi | Ruang kerja | `owner` | `name` | `{ok}` |
| `workspace.export`   | baca   | Ruang kerja | `admin`          | tidak ada     | `{ok, path}`                  |
| `workspace.import`   | mutasi | Ruang kerja | `owner`, dan pemilik server | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | baca | Ruang kerja | `owner`, dan pemilik server | tidak ada | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutasi | Ruang kerja | `owner`, dan pemilik server | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | mutasi | Instalasi* | `owner`          | `id`          | baris pendaftaran ditandai terhapus |

* `workspace.delete` tidak bercakupan karena baris yang ditandainya berada di pendaftaran
global; handler-nya memeriksa keanggotaan pemanggil pada ruang kerja yang disebut
dan mewajibkan `owner`.

`path` di setiap respons adalah path di **host server**.

`server.listOrphanedBackups` mengembalikan satu entri per ruang kerja yang tidak lagi
aktif: `workspace_id`, `workspace_name` jika pendaftaran masih mengenalnya, dan `backups`.
Ruang kerja yang dihapus tidak bisa lagi lolos pemeriksaan peran ruang kerja, jadi
cadangannya menjadi milik pemilik instalasi. `server.deleteOrphanedBackup` menolak ruang
kerja yang masih aktif, yang cadangannya tetap berada di balik `workspace.deleteBackup`
dan peran ruang kerja itu sendiri. Kedua operasi penghapusan hanya menerima nama direktori
stempel waktu yang terdaftar, bukan path.

`workspace.importHolds.list` mengembalikan apa yang ditahan oleh sebuah impor. Setiap penahanan memiliki `id`, `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` atau `invite`), `payload` yang akan dikembalikannya, `imported_at`, dan `source_install_id`. `workspace.importHolds.resolve` dengan `accept: true` memberikannya kembali dan dengan `false` membuangnya. `applied` bernilai false ketika tujuan pemberian izin itu sudah tidak ada lagi di ruang kerja.

:::note[Snapshot seluruh instalasi dibatasi pemilik di kedua jalur]
`server.backupNow`, `server.listBackups`, dan `server.deleteBackup` mewajibkan
**pemilik** instalasi (`ServerAuthority.serverOwner`), gerbang yang sama dengan
`GET /backup/snapshot`. Snapshot merekam basis data setiap ruang kerja, jadi
menjadi admin di satu ruang kerja tidak cukup untuk mengelola ruang kerja lainnya.
Penghapusan hanya menerima nama direktori stempel waktu yang terdaftar, bukan path
server sembarang, dan menghapus seluruh snapshot (termasuk snapshot yang belum diverifikasi). Ekspor per ruang kerja dan unduhan cadangan terjadwal tetap berada di tangan admin ruang kerja.
:::

:::note[Pemulihan adalah milik pemilik server]
`workspace.import` dan `POST /backup/restore` membuat server mengadopsi berkas basis data yang barisnya kemudian diperlakukannya sebagai miliknya sendiri: tautan repositori dan siapa yang membuatnya, definisi lingkungan yang berjalan di host, serta path worktree dan log. Karena itu keduanya memerlukan pemilik server (`ServerAuthority.serverOwner`), yang juga harus menjadi pemilik ruang kerja tersebut. Pemanggil lain, dan setiap pemanggil di host tanpa pemilik yang tercatat, ditolak dengan `server_owner_required`. Tidak ada pemicu, tampilan, kolom, atau batasan yang dibawa berkas itu yang diadopsi.
:::

### Respons `server.listBackups`

Terbaru lebih dulu, diurutkan berdasarkan nama direktori (yang merupakan stempel waktu,
jadi urutannya tetap berlaku bahkan untuk snapshot yang manifest-nya tidak bisa dibaca).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` dihilangkan ketika manifest tidak bisa dibaca. `bytes` di tingkat teratas
adalah ukuran nyata di disk dari seluruh direktori, bukan jumlah dari manifest itu
sendiri — pertanyaan yang diajukan operator yang memangkas snapshot adalah berapa biaya
direktori itu, bukan berapa yang dimaksudkan untuk ditulis oleh cadangan.

Setiap `workspaces[].path` persisnya adalah nilai yang diterima `workspace.import`
sebagai `source_path`. Itu memang sengaja: "memulihkan ruang kerja ini dari snapshot ini"
*adalah* operasi impor, jadi keduanya tidak bisa menyimpang menjadi perlakuan yang
berbeda terhadap file yang sama.

### Validasi `workspace.import`

Sebelum apa pun diganti, file kandidat disalin ke berkas staging di samping target dan diperiksa di sana. Penolakan tidak menyentuh apa pun dan membawa jenisnya sebagai `data.kind`.

| Kondisi                                          | Hasil                                                           |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| Berkas tidak ada | Ditolak, `import.missing_source` |
| Bukan basis data SQLite yang bisa dibaca, atau gagal `quick_check` | Ditolak, `import.damaged` |
| Berasal dari snapshot dan SHA-256-nya berbeda dari yang tercatat di manifest | Ditolak, `import.checksum_mismatch` |
| Ditulis oleh versi server yang lebih baru | Ditolak, `import.newer_schema` |
| `application_id` lain, atau tidak ada `workspace_meta` | Ditolak, `import.foreign_file` |
| Tidak bisa disesuaikan dengan skema server ini | Ditolak, `import.schema_mismatch` |
| Webhook atau undangannya sudah diarahkan ke ruang kerja lain | Ditolak, `import.route_conflict` |
| Id ruang kerja yang tercatat ≠ target            | **Diizinkan**. Barisnya dipetakan ulang ke target. Beginilah ruang kerja diduplikasi atau dipulihkan dengan id baru |
| Id instalasi yang tercatat ≠ instalasi ini       | **Diizinkan**. Id pengguna milik instalasi itu tidak akan dikenali di sini |

Saat diterima, berkas staging dibawa ke skema server ini dan kemudian harus sama persis dengannya. Izin yang tidak boleh diberikan berkas kepada dirinya sendiri dicabut darinya: persetujuan untuk menjalankan definisi lingkungan di host dihapus, dan aturan tindakan yang mengizinkan atau meminta persetujuan, izin exec sandbox, izin repositori di atas baca, peran di atas anggota, serta undangan ke peran-peran tersebut menjadi penahanan yang ditinjau pemilik server. Pengimpor mempertahankan atau memperoleh peran pemilik. Basis data yang digantikan disimpan sebagai cadangan terjadwal bernama `<timestamp>-pre-restore`, berkas staging dipindahkan ke tempatnya dengan koneksi ruang kerja ditutup, `code_index.db` dihapus untuk dibangun ulang, dan indeks FTS dibangun ulang.

## Rute transfer

Operasi ekspor/impor dan penampilan daftar snapshot di atas berbicara dalam path
sisi server, yang merupakan jawaban lengkap hanya ketika server itu mesin Anda
sendiri. Rute berbentuk HTTP ini membawa byte cadangan **di dalam terowongan
sumber daya terautentikasi dan terenkripsi ujung ke ujung yang sama** dengan
sumber daya sensitif lainnya, baik koneksi RPC-nya langsung maupun diperantarai.
Rute ini bukan endpoint transfer file HTTP publik: permintaan ke salah satunya
pada listener publik mengembalikan `426 Upgrade Required`, bahkan dari loopback.
Di dalam terowongan terenkripsi, perangkat yang terautentikasi Noise harus cocok
dengan `d`; handler juga memeriksa tanda tangan perangkat pada string targetnya
memakai PSK pairing dan peran di bawah ini.

| Rute                    | Metode | Kueri           | Target bertanda tangan         | Memerlukan             |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **admin** ruang kerja |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **pemilik** instalasi |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **admin** ruang kerja; **pemilik** instalasi setelah ruang kerja dihapus |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **pemilik** instalasi yang juga **pemilik** ruang kerja (`403` dengan `server_owner_required` jika tidak) |

`w` adalah id ruang kerja, `n` nama direktori snapshot atau cadangan terjadwal, `d` id
perangkat pemanggil, `s` tanda tangannya. Pada `/backup/snapshot`, `n` diselesaikan
terhadap daftar cadangan alih-alih digabungkan ke akar cadangan, sehingga rute itu tidak
bisa diarahkan ke direktori yang tidak akan ditampilkan oleh daftar. Pada `/backup/stored`,
`n` harus berupa nama stempel waktu, dan filenya harus berupa file sungguhan di dalam
direktori cadangan milik ruang kerja itu sendiri.

| Status | Penyebab                                                                            |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | Parameter kueri yang diwajibkan hilang, nama cadangan tidak valid, isi unggahan kosong, atau berkas yang diunggah ditolak (isinya `{error, kind}` dengan jenis `import.*`) |
| `403`  | Perangkat tidak dikenal atau dicabut, tanda tangan buruk, atau pemanggil tidak memiliki peran itu |
| `404`  | Tidak ada port cadangan di host ini, atau file snapshot, cadangan, atau ruang kerja yang disebut tidak ada |
| `405`  | `/backup/restore` dipanggil dengan apa pun selain `POST`                            |
| `413`  | Isi unggahan melebihi 8 GiB, baik menurut content-length yang dideklarasikan maupun menurut byte yang benar-benar dibaca |
| `426`  | Permintaan langsung apa pun ke rute transfer pada listener HTTP publik; gunakan terowongan sumber daya terenkripsi milik klien yang dipasangkan |
| `500`  | Ekspor atau arsip gagal di sisi server                                              |

Ketiga unduhan merespons `Cache-Control: no-store` dengan `Accept-Ranges: none`.
`/backup/workspace` dan `/backup/snapshot` membuat salinan **baru** per permintaan dan
menghapusnya setelah dialirkan, jadi respons yang di-cache atau dilanjutkan akan
menyambung byte dari dua ekspor berbeda menjadi satu file yang tampak valid padahal tidak.

`/backup/stored` adalah pengecualian: rute itu mengalirkan cadangan terjadwal sebagai
`<workspaceId>-<name>.db` dan membiarkan file itu di tempatnya, karena file itulah
cadangannya.

`/backup/snapshot` mengembalikan `<name>.zip`, dengan entri relatif terhadap akar snapshot
sehingga penguraiannya mereproduksi `manifest.json` + `global.db` +
`<workspaceId>/workspace.db`. Entri ditulis dalam urutan terurut, jadi dua arsip dari
snapshot yang sama adalah arsip yang sama.

`/backup/restore` mengalirkan isinya langsung ke file staging alih-alih menampungnya di
buffer, membatasinya sebelum dan selama pembacaan, dan menghapus file yang di-staging pada
**setiap** jalur keluar termasuk saat penolakan.

::::caution[Koneksi langsung dan relay memakai transfer terenkripsi yang sama]
Relay membawa permintaan sumber daya, respons yang dialirkan, dan byte unggahan
sebagai ciphertext; ia tidak dapat membaca isi cadangan. Path sisi server tetap
merupakan path pada host server, bukan file pada relay. Akses tetap memerlukan
perangkat yang dipasangkan, tanda tangan target, dan peran ruang kerja atau
instalasi yang berlaku. Tidak ada transport yang mengenkripsi file cadangan yang
dihasilkan saat tersimpan.
::::

## Path dan batas

| Hal                            | Nilai                                                        |
| ------------------------------ | ------------------------------------------------------------ |
| Snapshot                       | `<dataDir>/backups/<timestamp>/`                             |
| Cadangan ruang kerja terjadwal | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Ekspor ruang kerja             | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Basis data yang digantikan oleh pemulihan | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Basis data sebelum pembaruan mengubah formatnya | `<dataDir>/pre_upgrade/` dan `<dataDir>/<workspaceId>/pre_upgrade/`, dua yang terbaru dari masing-masing |
| Staging transfer               | `<dataDir>/backups/transfer/` — sebuah meja kerja, dibersihkan oleh rute yang menulisinya |
| Nama arsip snapshot            | `<snapshot directory name>.zip`                              |
| Batas unggahan                 | 8 GiB per unggahan terenkripsi ke `/backup/restore`          |
| Retensi                        | Snapshot instalasi: penghapusan manual. Cadangan ruang kerja: pipeline mingguan, bawaan 30 hari, atau penghapusan manual. Cadangan ruang kerja yang dihapus: hanya penghapusan manual |

Direktori `exports/`, `transfer/`, dan `workspace-backups/` bukan snapshot instalasi dan
dikecualikan dari `server.listBackups`. Hanya direktori terakhir yang memiliki retensi
terjadwal, dan hanya selama ruang kerjanya ada; menghapus snapshot instalasi memerlukan
tindakan eksplisit dari pemilik instalasi.
