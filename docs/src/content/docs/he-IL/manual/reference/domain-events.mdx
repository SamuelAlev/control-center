## אפיק אירועים

ה-`DomainEventBus` הוא אפיק פרסום/מינוי לשידור בתוך התהליך. המפרסמים קוראים ל-`publish(event)`; המנויים צורכים זרם `on<T>()` טיפוסי. כל אירוע מממש `DomainEvent` ונושא `occurredAt`.

**האפיק פועל בתוך `cc_server`.** כל מפרסם וכל מנוי פעיל יושבים שם. שום לקוח אינו רואה את האפיק הזה — השרת מעביר הלאה תת־קבוצה נבחרת כמסגרות `notifications/*` ב־JSON-RPC, מסוננת לכל מנוי לפי החברות שלו בסביבת עבודה.

| מדד                                                     | מספר                                       |
| ----------------------------------------------------------- | --------------------------------------------- |
| מחלקות אירועים קונקרטיות                                      | 53                                          |
| קובצי מקור (`packages/cc_domain/lib/core/domain/events/`) | 14 (בתוספת `domain_event_bus.dart`)           |
| בסיסים מופשטים שלעולם אינם מפורסמים ישירות            | 1 (`TaskLifecycleEvent`, היררכיה חתומה)           |

כל אירוע בקטלוג שלהלן חי באותה תיקייה אחת; אין אירועי תחום שמוצהרים במקום אחר.

## אירועי מחזור חיי משימה

זרם מחזור חיי המשימות המאוחד — הרצת סוכן נשלחת אחת, שמזוהה לפי מזהה יומן ההרצה שלה. כל אירוע נושא `taskId`, `seq` מונוטוני לכל משימה, `workspaceId?`, `agentId?` ו-`phase`; השורות שלהלן מפרטות רק את השדות הנוספים.

| אירוע                       | מטען                       | נורה כאשר                                                                                       |
| --------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `TaskDispatched`            | —                             | המשימה נמסרה לבקאנד להרצה                                                           |
| `TaskRunning`               | —                             | המשימה החלה להפיק פלט                                                                    |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | המשימה הוחנתה — משימה אחרת מחזיקה בנעילת הנתיב על הדיסק שהיא זקוקה לה                                   |
| `TaskProgress`              | `note?`                       | נקודת ביקורת התקדמות באמצע ההרצה                                                                      |
| `TaskMessage`               | `messageType`, `content`      | הודעה נזרמת (text/thinking/tool_use/tool_result/error); מדווחת תחת השלב `progress` |
| `TaskCompleted`             | `summary?`                    | המשימה הסתיימה בהצלחה                                                                       |
| `TaskFailed`                | `errorMessage`                | המשימה הסתיימה בשגיאה                                                                      |
| `TaskCancelled`             | —                             | המשימה בוטלה לפני שהסתיימה                                                                 |

למבנה `TaskPhase` יש גם איבר `queued`, אבל שום דבר אינו מפרסם אירוע queued — אין מחלקת `TaskQueued`. המסגרת הראשונה שנצפית של משימה היא `TaskDispatched`.

## תת־תחומים בלי אירועים כלל

כמה תת־מערכות שנראות מונעות אירועים מבחוץ אינן כאלה. הן מופיעות כאן משום שההיעדרות שלהן היא החלטת תכנון שכדאי להכיר לפני שיוצאים לחפש נקודת חיבור:

| תת־תחום           | איך המצב זז במקום זאת                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| זיכרון              | `record_memory_fact` וחבריו כותבים ומחזירים; האחזור קורא. שום דבר אינו מפרסם על עובדה או התנגשות |
| תזמור       | ההצעה, האישור שלה והרצת הפייפליין שנוצרה הם שורות וקריאות RPC                        |
| מסמכי תוכנית      | `submit_plan` כותב גרסה; אישור מממש תזמור. אף אחד מהם אינו מוכרז           |
| ארטיפקטים           | `publish_artifact` / `revise_artifact` כותבים גרסאות ישירות                                          |
| אישורים           | ההסלמה מטופלת בתוך שירות זרימת העבודה של האישורים                                              |
| סנכרון כרטיסים         | מתאם הספקים נרשם לאירועי הכרטיסים שלמעלה; וובהוקים נכנסים מיושמים ישירות     |
| רענון לוח שנה    | סנכרון מבצע upsert לאירועים והלקוח קורא מחדש; אין שידור רענון                            |
| מיזוגי עצי עבודה     | נרשמים ב-`worktree_merge_log` ונקראים משם                                                    |

| `LocalRpcServer` / `RemoteRelayHost` | `WorkspaceMemberRemoved` — מפיל את המינויים של אותו משתמש לסביבות העבודה שאליהן הוא מחובר; השקע נשאר פתוח |

`TicketAssigned` הוא אות ביקורת והתראה וטריגר לפייפליין. הקצאה לסוכן רושמת בעלות ואינה מתחילה הרצה — אין משגר כרטיסים. הקצאה לצוות (`assignedTeamId` מוגדר) היא החריג: `TeamRoutingService` שולח את מוביל הצוות.

`TicketRemoteSyncHandler` מוצהר אבל לעולם אינו נבנה בקוד הייצור, ולכן הוא אינו נרשם לשום דבר היום. ה-`NotificationEventMapper` שבצד הלקוח נבנה רק בבדיקה שלו עצמו — הוא שאריות הנתיב שבתוך התהליך מלפני הפיצול בין לקוח לשרת. התראות קופצות חיות מגיעות מהמסגרות שלהלן.

## מיפוי התראות

בשרת, `NotificationFeedRecorder` ו-`RemoteEventForwarder` הופכים את האירועים האלה למסגרות תעבורה `notifications/*` (`notification_wire.dart`). בלקוח, `RpcNotificationMapper` → `mapNotificationFrame` הופך מסגרת ל-`AppNotification`.

יש בדיוק **שש עשרה** קטגוריות התראה. כמה אירועים ממופים ליותר משיטת תעבורה אחת, משום שהמסגרת נושאת את המעבר (נכשל לעומת התאושש) ואילו הקטגוריה נושאת את השאלה ("מה עושה ה-CI?").

| `ticketAssigned`       | `TicketAssigned`          | `notifications/ticket_assigned`                                        |

| `prMentioned`          | `PrCommentMentioned`      | `notifications/pr_comment_mentioned`                                   |

מסגרת ההשתלטות של תחנה אינה נמסרת חזרה למי שהשתלט, השחרור אינו מסונן (האירוע אינו מתעד מי עזב), ורק סגירה מסוג `backendFailure` מפיקה מסגרת `rig_closed` — שאר הסיבות התבקשו או שכבר מכוסות במסגרת הפינוי.

חמש הקטגוריות של בקשות משיכה שיצרתם נושאות `forUserId`, ולכן הן מגיעות למחבר ולא לכולם בסביבת העבודה.

`RemoteEventForwarder` מעביר בנוסף את `TicketReassigned` בתור `notifications/ticket_reassigned` ואת כל `TaskLifecycleEvent` בתור `notifications/task_<phase>`. אף אחד מהם אינו ממופה לקטגוריית התראה — הם מניעים ממשק משתמש חי, לא את מרכז ההתראות. אירועי חברות אינם מועברים כמסגרות: הם מבטלים את המטמון של המעביר, ומארחי הסשנים מפילים את המינויים של החבר שהוסר.
