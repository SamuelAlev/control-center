Den här guiden visar hur du ansluter en extern MCP-klient – Claude Code, en
editor, MCP Inspector – till Control Centers egen verktygsserver.

Control Center registrerar **110** verktyg och betjänar dem över Model Context
Protocol i protokollversionen `2024-11-05`. Hela verktygsfamiljer som du kanske
förväntar dig saknas: det finns inga mötes- eller kalenderverktyg och inga
projektverktyg.

## Hitta slutpunkten

MCP-ytan delar den huvudsakliga `cc_server`-lyssnaren. Det finns ingen separat
MCP-port.

| Slutpunkt | Metod    | Syfte                                                    |
| --------- | -------- | -------------------------------------------------------- |
| `/mcp`    | `POST`   | Streamable HTTP-transport – det här är vad en klient talar |
| `/mcp`    | `DELETE` | Avsluta en session                                       |
| `/sse`    | `GET`    | Server-sent-aviseringsström                              |

Så en standardinstallation lokalt ligger på `http://127.0.0.1:9030/mcp`.

1. Gå till **Inställningar → Server → MCP-servrar**
2. Läs kortet **MCP-server** – det visar om den körs eller är stoppad och vilken
   port den lyssnar på

Ytan är på som standard i en nyinstallation. Token på kortet syns bara för
serverägaren, och endast serverägaren kan starta eller stoppa slutpunkten.
**Starta vid applansering** styr om den kommer tillbaka efter en omstart;
**Starta** / **Stoppa** är sessionskontroller som inte ändrar den inställningen.

Servern binder till loopback som standard, så slutpunkten nås bara från
maskinen som `cc_server` kör på, om du inte startade den med `--bind any`.

## Hämta token

Varje begäran behöver serverns MCP-token, från vilken maskin som helst, även från
loopback. Servern skapar den första gången den startar. Det finns inget sätt att
stänga av den och inget sätt att rensa den.

1. Gå till **Inställningar → Server → MCP-servrar** och hitta raden **Autentiseringstoken**
2. Tryck på **Visa token** och kopiera den
3. För att ersätta den, tryck på **Rotera token**. Servern byter till den nya
   token direkt, och varje klient som fortfarande använder den gamla avvisas tills
   du ger den den nya

## Anslut en klient

Peka din klient mot Streamable HTTP-slutpunkten och skicka token som
`Authorization: Bearer <token>` i varje begäran, `GET /sse` inkluderad. Det finns
inget annat sätt att skicka den: en token i URL:en godtas inte. Exakt hur
konfigurationen ser ut är upp till din klient.

```json
{
  "mcpServers": {
    "control-center": {
      "type": "http",
      "url": "http://127.0.0.1:9030/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```

### Claude Code

Claude Code plockar inte upp detta från en `.mcp.json` i projektet – den lägger
projektspecifika MCP-servrar bakom en godkännandeprompt som en icke-interaktiv
`claude -p` aldrig svarar på. Skicka med konfigurationen explicit:

```bash
claude --mcp-config /path/to/mcp.json --strict-mcp-config
```

`--strict-mcp-config` gör att Claude bara använder den filen, så att samma
server inte också upptäcks från projektet och registreras två gånger.

Kontrollpunkt: be klienten lista sina verktyg. Du bör se `mcp__*`-poster som
täcker ärenden, ytor, minne, kodgraf och granskning.

## Vad slutpunkten vägrar

Token öppnar varje verktyg på servern, så slutpunkten avvisar också allt som en
webbsida kan ha skickat, innan den tittar på token:

| Begäran | Svar |
| ------- | ---- |
| En `Origin`-header som inte är en sida på den här maskinen (`http://localhost`, `http://127.0.0.1` eller `http://[::1]`, vilken port som helst) | `403`, "Cross-origin requests are not accepted" |
| En `Host`-header som varken är denna lyssnares loopback-adress och port eller serverns publika värdnamn | `403`, "Unknown host" |
| En `POST` vars brödtext inte är `application/json` | `415` |
| Ingen token, eller fel token | `401` |

För att betjäna MCP utanför värden, starta servern med `--bind any` och skicka
token från den andra maskinen, och adressera servern med dess publika värdnamn.

## Begränsa varje anrop till en arbetsyta

Varje verktyg som rör arbetsytespecifik data kräver `workspace_id`, och ett
anrop utan det avvisas i stället för att lösas mot någon ”aktuell” arbetsyta:

```json
{
  "workspace_id": "acme",
  "title": "Fix login bug",
  "priority": "high"
}
```

Id:t är det som står i webbläsarens eller appens URL:
`/workspaces/<workspace_id>/…`. De enda undantagen är verktyg som verkligen
spänner över arbetsytor, som `list_workspaces` och nyhetsflödesverktygen –
nyhetsflödet gäller per användare och en agent har ingen egen användare, så de
verktygen arbetar mot serverägarens flöden.

Repospecifika verktyg kontrollerar dessutom att repot är länkat till den
arbetsytan.

## Vet vad ytan vägrar

- **Lägesstyrning.** Ett anrop löses mot läget för den anropande agentens yta,
  på serversidan. En agent i ett skrivskyddat läge kan inte nå ett skrivverktyg
  genom att utelämna `space_id` – läget slås i stället upp från dess aktiva
  körning.
- **Åtgärdsräcken.** Förändrande verktyg deklarerar sina effektklasser och
  passerar samma policy som resten av produkten använder. Se
  [Konfigurera räcken](/sv-SE/handbok/how-to-guider/konfigurera-racken/).
- **Bekräftelse.** Vissa destruktiva verktyg bygger en bekräftelsenyttolast som
  måste godkännas innan anropet fortsätter.

Hela katalogen annonseras i `tools/list` utan upptäcktsstyrning – en extern
MCP-klient vägrar anropa ett verktyg som inte finns i dess cachade lista, så att
dölja verktyg förstör dem i stället för att snygga till dem.

## MCP-servrar som agenterna använder

Den här guiden handlar om Control Centers egen slutpunkt. Den andra riktningen är MCP-servrar som Control Center ansluter till och ger till de agenter det kör. De ställs in under **Inställningar → Server → MCP-servrar**, på två nivåer. Oavsett nivå ansluter Control Center till MCP-servern själv och skickar dess verktyg till körningen, så att det inbyggda harnesset och Claude Code får samma verktyg och samma godkännandefrågor. En Claude Code-körning ser dem under MCP-servern `control-center` som `mcp__control-center__mcp__<server>__<tool>`.

### MCP-servrar för arbetsytan

Arbetsytans administratörer lägger till dessa under **MCP-servrar för arbetsytan**. Varje agentkörning på arbetsytan får deras verktyg, och körningar på andra arbetsytor gör det inte.

1. Välj **Lägg till server** och ge den ett kort namn: bokstäver, siffror, `-` och `_`, upp till 24 tecken. Verktygen visas som `mcp__<name>__<tool>`.
2. Välj hur MCP-servern nås:
   - **Kommando (stdio):** ett körbart program och dess argument, plus eventuella miljövariabler som behövs.
   - **URL (HTTP eller SSE):** slutpunkten, plus eventuella headers som behövs, till exempel `Authorization: Bearer …`.
3. Spara. Kontrollpunkt: MCP-servern visar **Ansluten** med ett antal verktyg.

Värden för miljövariabler och headers lagras i MCP-serverns hemlighetsfil och visas aldrig igen. För att ändra ett värde ersätts det; för att ta bort det tas namnet bort.

Ett kommando körs på MCP-serverns maskin som serverns egen användare, så det startar inte förrän serverägaren godkänner det. Tills dess står det **Väntar på godkännande**. En URL-server fungerar direkt men når bara publika adresser tills serverägaren godkänner den, vilket också tillåter `localhost` och privata nätverk. När serverägaren sparar en MCP-server räknas det som godkännande. Om någon annan ändrar hur en MCP-server startar eller var den ansluter behövs nytt godkännande. Att slå på eller av en MCP-server behåller godkännandet.

### Personliga MCP-servrar

Personliga MCP-servrar tillhör serverägaren och listas under **Externa MCP-servrar**. MCP-servrar som är konfigurerade på serverns maskin för Claude, Codex, Cursor, Gemini, VS Code, Windsurf, OpenCode eller i en `.mcp.json` hittas där automatiskt. Serverägaren kan också lägga till egna MCP-servrar via **Lägg till server**, med samma formulär. En MCP-server som läggs till går före en upptäckt MCP-server med samma namn.

De agerar med serverägarens identitet och uppgifter:

- De är bara tillgängliga i körningar som serverägaren startar eller ansvarar för, inklusive automatisering på en arbetsyta som ägaren ansvarar för. Det gäller både inbyggda harness-körningar och Claude Code-körningar.
- En medlems körning, automatisering bunden till en medlem och varje körning på en MCP-server utan registrerad ägare får ingen av dem. Där listas verktygen inte, de kan inte anropas och de syns inte i verktygssökningen.
- Varken personliga MCP-servrar eller MCP-servrar för arbetsytan skickas till MCP-token eller till parkopplade enheter, och deras resurser och prompts vidarebefordras inte.

Att logga in på en MCP-server med OAuth går inte via formuläret. Använd en MCP-server som accepterar en token i en header, eller konfigurera den för något av verktygen ovan, där den upptäcks.

## Felsökning

### Klienten ser inga verktyg

- Kontrollera att kortet **MCP-server** säger att den körs
- Kontrollera att porten matchar din `cc_server`-port
- I Claude Code: kontrollera att du skickade med `--mcp-config` och
  `--strict-mcp-config`

### 401 Unauthorized

Begäran bar ingen token, eller en gammal. Kopiera den aktuella token från raden
**Autentiseringstoken** och skicka den som `Authorization: Bearer <token>`. En
token i URL:en ignoreras.

### 403 från en klient som tidigare fungerade

Begäran bar en `Origin` från en webbsida, eller en `Host` som servern inte svarar
på. Anropa slutpunkten från en klient i stället för en webbsida, med serverns
loopback-adress eller dess publika värdnamn.

### 415 Unsupported Media Type

Skicka `POST /mcp`-brödtexter som `application/json`.

### Ett verktygsanrop misslyckas med "Missing or invalid argument: workspace_id"

Lägg till `workspace_id`. Det finns ingen implicit arbetsyta.

### Ett verktygsanrop avvisas som okänt

[MCP-verktyg](/sv-SE/handbok/referens/mcp-verktyg/) listar katalogen. Anropa
namnet exakt som det står där.
