Varje processflagga styrs av en CLI-flagga eller en miljövariabel; flaggan vinner,
sedan miljön och sist standardvärdet. Undantaget är leverantörernas
autentiseringsuppgifter – se [Leverantörsappar och Connect](#leverantörsappar-och-connect).

:::caution[Okända flaggor ignoreras tyst]
Argumentparsern är handskriven och hoppar över allt den inte känner igen, så en felstavning (`--tls-key-file`, `--bindany`) ger inget fel – servern startar bara med standardvärdet. Kontrollera loggraderna vid start när en flagga verkar sakna effekt. En [flagga för kodläge](#kodläge) med ett värde den inte accepterar är annorlunda: servern vägrar starta.
:::

## Leverantörsappar och Connect

Inget bygge innehåller leverantörernas autentiseringsuppgifter. Med Control Center Connect påslaget kör Connect alla leverantörer, och dessa egna appar
förblir sparade men oanvända. Under **Använd mina egna appar** körs varje leverantör
på serverns egen app när en är fullständigt konfigurerad, annars är den otillgänglig.
En arbetsytas egna app vinner i båda fallen. Egna appar anges
under **Inställningar → Server → Enkel inloggning → Leverantörsappar**, eller
fylls i en gång från serverns `.env`-fil. Det finns inga flaggor för dem: en
hemlighet på en kommandorad går att läsa via `ps`.

| Variabel                       | Betydelse                                                                                     |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| `GITHUB_APP_ID`                | ID för serverns GitHub-app                                                                    |
| `GITHUB_APP_PRIVATE_KEY`       | Dess privata nyckel, på en rad med `\n`-escapes. **Endast `.env`**                            |
| `GITHUB_CLIENT_ID`             | Dess klient-ID, för att logga in personer                                                     |
| `GITHUB_CLIENT_SECRET`         | Dess klienthemlighet. **Endast `.env`**                                                       |
| `GOOGLE_OAUTH_CLIENT_ID`       | Serverns Google-klient av typen webbapplikation                                               |
| `GOOGLE_OAUTH_CLIENT_SECRET`   | Dess hemlighet. **Endast `.env`**                                                             |
| `LINEAR_CLIENT_ID`             | Serverns Linear-applikation (PKCE, ingen hemlighet)                                           |
| `LINEAR_API_KEY`               | En Linear-tjänstnyckel för automatisering. **Endast `.env`**                                  |
| `KLIPY_APP_KEY`                | Serverns egen Klipy-nyckel för GIF-sökning, används bara under **Använd mina egna appar**           |
| `CC_CONNECT_URL`               | `hosted`, `off` eller en Connect-URL. Låser Connect-valet; Inställningar kan då inte ändra det |
| `CC_SERVER_CONNECT_HOST`       | `on` monterar Control Center Connect på `<server>/connect`, konfigurerad med `CONNECT_*`-variabler. Se [Kör en Connect-server](/sv-SE/handbok/how-to-guider/kor-connect-server/#montera-connect-i-cc_server) |

`.env`-filen läses från serverns arbetskatalog, bredvid den körbara filen, eller
från en källkodsutcheckning ovanför den; i Docker monterar du den på
`/app/bin/.env`. Servern **vägrar starta** (avslutningskod `78`) när
`GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_SECRET`,
`LINEAR_API_KEY` eller någon `SLACK_*SECRET*` är exporterad i dess processmiljö,
där varje underprocess skulle kunna läsa den. Ifyllningen från `.env` sker en
gång per fält, så en senare ändring i Inställningar skrivs inte över vid en
omstart. Ett tomt värde läses som oangivet.

Ingen kodvärdsautentisering kommer från miljön: GitHub, GitLab och Bitbucket agerar
alla med en medlems egen inloggning eller token, eller med GitHub-app-tokens för ett
repo i taget som är begränsade till en sådan.

### `--sandbox`

Servern sonderar värden en gång vid start och lindar in agentens kommandokörning i
den inbyggda OS-sandlådan när en backend finns: `sandbox-exec` (Seatbelt) på macOS,
`bwrap` plus `socat` på Linux och WSL2. Beslutet fattas en gång och gäller tills
servern startar om. Det finns tre utfall, och vart och ett visas på startloggens
exponeringsrad:

| `sandbox=`    | När                                     | Vems agentkörningar startar                                                      |
| ------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| `native`      | En backend finns och `--sandbox` är `on` | Allas, inlindade                                                                 |
| `off`         | `--sandbox off`                         | Allas, obegränsade på den här värden                                             |
| `unavailable` | `--sandbox on` och ingen backend (Windows, eller Linux utan `bwrap` och `socat`) | Bara körningar som serverägaren är ansvarig för, obegränsade. Andra nekas med ”Den här servern har ingen sandlåda, så bara dess ägare kan köra agenter här.” |

För automation är den ansvariga personen den som automationen är bunden till. Utan
registrerad serverägare startar ingen körning på en `unavailable`-värd. På Linux och
WSL2 med bubblewrap installerat misslyckas inbyggd dispatch för närvarande stängt för
varje körning; se [Sandlådebackends](/sv-SE/handbok/referens/sandladebackends/#linux-bubblewrap).

`--sandbox off` är serverägarens val för alla som använder servern: den kör varje
medlems agenter obegränsade på den här maskinen. Använd det på en värd där själva
sandlådeprofilen beter sig fel, eller för att låta medlemmar köra agenter på en värd
utan någon backend. Den kräver ingen ombyggnad, och servern loggar en varning under
hela processens livstid så att tillståndet aldrig är tyst.

### `--tool-deferral`

Inbyggda harnesskörningar skickar en liten direkt uppsättning verktygsdefinitioner plus ett index med bara namn över resten, som läser in sina scheman första gången de används eller anropas från ett `repl`-skript. Det håller den alltid synliga uppsättningen inom det intervall där modeller väljer verktyg tillförlitligt. Mätt på registret som testerna bygger kommer den inbyggda agentens vanliga chattverktyg till 14 definitioner: omkring 16,5 KB med `repl` (omkring 4 KB av dem är `repl`s, vars definition inte får överstiga 4 096 byte), omkring 13 KB på en server som inte kan köra skript. Uppskjutna verktyg går fortfarande att anropa vid namn hela tiden, och `search_tools` hittar dem utifrån avsikt. Se [Verktygskontext och promptcache](/sv-SE/handbok/koncept/verktygskontext/).

`--tool-deferral off` skickar varje tillåtet verktygs definition i förväg, förutom att en körning med `repl` fortfarande anropar från skript de verktyg som ett skript får anropa. Det är dödarknappen för en modell som hanterar ytan i två nivåer dåligt – en flagga i stället för en ombyggnad. Den påverkar bara den inbyggda harnessen; den MCP-`tools/list` som externa klienter ser är hela katalogen, utom för en agentkörning på en server som kan köra skript i [Kodläge](/sv-SE/handbok/koncept/kodlage/).

### `--credential-gate`

En körning vars leverantörsautentiseringsuppgift saknas eller är förbrukad blir
**parkerad** i stället för misslyckad: operatören får en uppmaning att åtgärda den,
och körningen återupptas om den gör det. Standardtidsfristen är 900 sekunder
(15 minuter), begränsad till 0–3600.

Tidsfristen är medvetet mycket längre än godkännandepromptens: ett godkännande är ett
beslut någon fattar på sekunder, medan att åtgärda en autentiseringsuppgift innebär
att öppna en terminal, logga in och komma tillbaka. Taket är det som hindrar en
obevakad körning – ett pipelinesteg, en cron-trigger, en webhook – från att vänta på
någon som sover. När den löper ut misslyckas körningen med meddelandet den ändå skulle
ha misslyckats med.

`--credential-gate=0` är dödarknappen: inget parkeras någonsin och en dålig
autentiseringsuppgift avslutar turen precis som innan grinden fanns.

### Kodläge

[Kodläge](/sv-SE/handbok/koncept/kodlage/) låter en agent köra ett JavaScript-skript som anropar sina verktyg. Det finns ingen flagga som slår på eller av det: varje körning får verktyget `repl` när servern kan köra skript, och en offentlig demoserver kör inga.

Skript körs i `cc_codemode`, ett program som följer med servern i `bin/codemode/`. Servern startar inte utan det: den skriver ut en rad med vad som saknas och avslutas med kod `78`. Vid start kör den programmets låsningsself-test och skriver ut en rad (tystas bara av `--log-level error`):

```text
cc_server: code_mode=available (cc_codemode 0.1.0 quickjs-ng 0.16.2 protocol 2; 16 scripts at once, at most 12 per workspace; up to 64 more runners kept for scripts waiting on a person; heap at most 1024 MiB per script)
cc_server: code_mode=unavailable (<reason>) — runs on this host get no repl tool; scripts never run without full lockdown
```

`unavailable` betyder att programmet inte kan låsa sig självt på den här värden, till exempel i en container vars säkerhetsprofil nekar ett av sina steg, eller att det inte är ett release-bygge. Servern körs normalt, ingen körning får `repl`, och arbetsytans inställningar för kodläge visar skälet.

Servern fortsätter att kontrollera medan den körs. När programmet inte startar av en orsak som inte beror på skriptet kör servern självtestet igen, högst en gång per minut. Om det misslyckas skriver servern ut raden `unavailable` med sitt skäl och kör inga skript: körningar som startar under tiden får ingen `repl`, och en körning som redan har den anropar sina verktyg direkt ([När skript inte kan köras](/sv-SE/handbok/koncept/kodlage/#när-skript-inte-kan-köras)). Den fortsätter att kontrollera, högst en gång per minut, och när självtestet lyckas igen skriver den ut raden `available` och kör skript igen. Bara ett självtest som misslyckades vid start kräver en omstart. Skälet som arbetsytans inställningar visar har värdsökvägar borttagna; loggraden har det helt.

De två flaggorna för kodläge begränsar vad skript får använda. `--code-mode-max-processes` begränsar skripten som körs samtidigt över alla arbetsytor (standard dubbelt så många som processorkärnorna, högst 16; accepteras 1–64). Med ett tak på 2 eller mer använder en arbetsyta högst taket minus en fjärdedel av taket, så att ingen enskild arbetsyta kan ta alla platser, och väntande skript släpps in om tur över arbetsytorna. Ett skript som väntar på en persons godkännande eller svar ger sin plats till ett annat skript och startar inget verktygsanrop förrän det har fått svar; upp till fyra gånger taket av sådana väntande skript behålls, högst tre fjärdedelar av dem från en och samma arbetsyta, och var och en kan fortfarande räkna inom sin egen processortidsgräns. `--code-mode-max-heap-mb` är det högsta minne ett enskilt skript får använda.

Ett värde som dessa flaggor inte accepterar (ett tal utanför intervallet, eller inte ett tal) stoppar servern vid start (utgångskod `78`) med ett meddelande som anger de godkända värdena. Det tolkas aldrig som standardvärdet.

## Underkommandon

| Kommando                                      | Vad det gör                                                                                                                            |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `cc_server`                                   | Kör servern tills `SIGINT`/`SIGTERM`                                                                                                   |
| `cc_server pair`                              | Provisionerar en enhet och skriver ut dess ID och parkopplingsnyckel. Säker mot en datakatalog som en server redan betjänar – den körande servern plockar upp enheten utan omstart |
| `cc_server connect <command>`                 | Visar eller ändrar vilken Control Center Connect den här servern använder, utan att starta den                                        |
| `cc_server update`                            | Söker efter, hämtar och verifierar en nyare fristående release                                                                         |
| `cc_server --version`                         | Skriver ut byggversionen och git-SHA:t – samma identitet som `/healthz` och RPC-handskakningen annonserar                              |

### `pair`

| Flagga         | Standard                                                       | Betydelse                                                                                                                                                          |
| -------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device`     | `web-client`                                                   | Enhets-ID:t. Plattformen härleds från det, så `--device desktop` skapar en rad för skrivbord och `--device ios`/`android` en rad för telefon; allt annat behandlas som webb |
| `--label`      | plattformsnamn plus den här maskinens värdnamn                 | Visningsnamn i enhetslistan                                                                                                                                        |
| `--host`       | `localhost`, eller `<this-host>` när den är bunden till alla gränssnitt | Värd att bädda in i den utskrivna URL:en. Sätt den till LAN-IP:n eller tunnelvärden som en klient faktiskt kommer att anropa                                        |
| `--client-url` | oangivet                                                       | Origin för den hostade **webb**klienten. Lägger till en skanningsbar djuplänk och en QR-kod i terminalen                                                            |

`pair` accepterar också kärnflaggorna `--data-dir`, `--port` och `--bind`: de väljer
vilken datakatalog som skrivs och formar den utskrivna server-URL:en (`ws` på
loopback, `wss` vid `--bind any`). Att köra `pair` igen för samma `--device` roterar
dess nyckel och släpper enhetens aktiva sessioner. En autentiseringsuppgift som
skapas här har **ingen utgång**, till skillnad från de 30 dagar en parkoppling i
appen sätter.

:::caution[`--client-url`-QR-koden är inte telefonens QR-kod]
`pair --client-url` fyller i **webb**klientens anslutningsformulär (server-URL,
enhets-ID och nyckel i URL-fragmentet). Telefonen parkopplas med en annan nyttolast
som skapas från parkopplingspanelen i appen – serverns fullständiga
anslutningsbeskrivning plus en utgång. De två går inte att byta mot varandra – se
[Para en enhet](/sv-SE/handbok/how-to-guider/para-enhet/).
:::

### `connect`

Läser och skriver samma inställningar som kortet **Control Center Connect** under
**Inställningar → Server → Enkel inloggning**, från datakatalogen. En server som
körs plockar upp en ändring inom 10 minuter eller vid omstart.

| Kommando                        | Vad det gör                                                                                                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `cc_server connect status`      | Skriver ut läget, URL:en, om `CC_CONNECT_URL` låser den, installations-id:t, hälsan och varje spårs källa (`own`, `connect` eller `off`) |
| `cc_server connect enable`      | Använder Control Centers hostade Connect                                                                         |
| `cc_server connect enable --url <url>` | Använder en egen Connect på den URL:en (HTTPS, eller `http` på loopback)                                  |
| `cc_server connect disable`     | Slutar använda Connect. Bara serverns egna appar loggar in personer                                              |

`status` utan kommando är standard. Varje kommando accepterar `--data-dir`.
`CC_CONNECT_URL` åsidosätter det som dessa lagrar. Ett okänt kommando avslutar
med `64`. Se [Control Center Connect](/sv-SE/handbok/referens/connect/) för lägena,
installationsidentiteten och statuskoderna.

### `update`

`--apply` ersätter installationen; det nekas medan en server fortfarande svarar på
den konfigurerade porten om du inte anger `--force`. `--allow-downgrade` tillåter en
äldre release.

Kommandot nekar rakt av, med en förklaring i stället för ett fel, för installationer
det inte äger:

| Miljö                          | Upptäcks av                                 | Vad den säger                                               |
| ------------------------------ | ------------------------------------------- | ----------------------------------------------------------- |
| Skrivbordsappens inbäddade server | `CC_EMBEDDED=1` eller `CC_BOOTSTRAP_DEVICE_ID` | Uppdatera appen i stället – installationsprogrammet byter ut hela trädet |
| En källkodsutcheckning med `dart run` | skriptsökvägen slutar på `.dart`       | Uppdatera den med git                                       |
| Docker                         | containermarkörer                           | Hämta en nyare avbildning                                   |

## Processlivscykel

`cc_server` körs tills `SIGINT` / `SIGTERM`. En extra miljövariabel styr det, och den
sätts av skrivbordsappen snarare än av dig:

| Variabel                | Effekt                                                                                                                                                                                       |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CC_EXIT_WITH_PARENT=1` | Servern avslutas när dess förälderprocess gör det, vilket upptäcks genom att föräldern stänger skrivänden av sin stdin-pipe. Skrivbordsappen sätter den så att en kraschad app aldrig lämnar en övergiven server som håller datakatalogen |

Sätt den själv bara om du övervakar `cc_server` som en barnprocess och vill ha samma
garanti.

`DO_NOT_TRACK=1` (vilket värde som helst utom tomt, `0` eller `false`) stoppar serverns egen
[användningsstatistik](/sv-SE/handbok/referens/anvandningsstatistik/) även när det serveromfattande reglaget är
på. Klienterna följer fortfarande reglaget.

## Datakatalogens layout

Standarddatakatalogen är `~/Library/Application Support/control-center` på macOS,
`%APPDATA%\control-center` på Windows och `$XDG_DATA_HOME/control-center` (annars
`~/.local/share/control-center`) på andra plattformar. En `.cc_server` relativ till
cwd används bara när ingen hem- eller appdatakatalog kan lösas upp.

Servern håller datakatalogen privat för sitt eget konto (`0700`). Den vägrar starta (avslutningskod `78`) när den inte kan det, när `global.db` är skadad eller skriven av en nyare version, eller när dess identitetsfil inte kan läsas.

| Sökväg                            | Innehåll                                                                         |
| --------------------------------- | -------------------------------------------------------------------------------- |
| `global.db`                       | Arbetsyteregistret, användare, parkopplade enheter, nyhetsflödet och fleet-kön   |
| `<workspaceId>/workspace.db`      | En databas per arbetsyta – agenter, ytor, ärenden, minnet             |
| `<workspaceId>/code_index.db`     | Arbetsytans kodgraf. Byggs om när den saknas, och säkerhetskopieras aldrig |
| `pre_upgrade/`, `<workspaceId>/pre_upgrade/` | De två senaste kopiorna av en databas från innan en uppdatering ändrade dess format |
| `<workspaceId>/chat_credentials/` | Chattbottokens, som ren JSON, så att de följer med arbetsytan                    |
| `secrets.json`                    | Parkopplingsnycklar, Connects installationsnyckel, leverantörsappar, personers inloggningar (förseglade när de görs via Connect), webhook-hemligheter, SSO (`0600`) |
| `backups/<timestamp>/`            | En ögonblicksbild av installationen – `manifest.json`, `global.db` och en kopia av varje arbetsyta |
| `backups/exports/`                | Exporter av enstaka arbetsytor, `<workspaceId>-<timestamp>.db`                   |
| `backups/transfer/`               | Mellanlagring för ned- och uppladdning av säkerhetskopior; städas av rutten som skriver den |
| `models/`                         | Inbäddnings-, diariserings- och talmodeller på enheten                           |
| `codemode/` | En utvecklingskopia av kodlägeskörare, installerad av `scripts/natives/build_codemode.sh`; releasepaket bär den i `bin/codemode/` |
| `meetings/<meetingId>/`           | Bevarat mötesljud                                                                |
| `rigs/images/`                    | Importerade skivavbildningar för stationer (QEMU-skrivbordsytan)                 |
| `rigs/smolvm/<rigId>/`            | Körtidstillstånd per station för microVM:er (brokerns hemlighet, `0600`)         |
| `rigs/smolvm-packs/`              | Förut extraherade maskinpaket – cachen som gör att upprepade stationsstarter går snabbt |
| `rigs/tls/`                       | Certifikatutfärdaren för dev-domänen till stationernas HTTPS (nycklar `0600`)    |
| `rigs/run/<rigId>/`               | QEMU-overlaylager, startavbildningar och nycklar per VM (`0600`)                 |
