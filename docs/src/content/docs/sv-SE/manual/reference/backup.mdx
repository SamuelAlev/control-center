Allt som Control Center kan kopiera, lämna över eller ta över, och den exakta formen på
varje artefakt. För att faktiskt ta en säkerhetskopia, se
[Säkerhetskopiera och återställ](/sv-SE/handbok/how-to-guider/sakerhetskopiera-och-aterstall/); för varför
beständigheten är uppdelad så här, se [Arbetsytor och isolering](/sv-SE/handbok/koncept/arbetsytor/).

## Artefakter

Det finns tre artefakter för databaskopior, med olika omfattning och olika regler för
borttagning.

| Artefakt                     | Skrivs av                    | Form                                  | Omfattar                      |
| ---------------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **Installationsögonblicksbild** | `server.backupNow`        | En tidsstämplad **katalog**           | Varje databas i installationen |
| **Säkerhetskopia av arbetsyta** | pipelinen `Workspace backup` | Tidsstämplad katalog med en `.db`   | En arbetsytas databas         |
| **Arbetsytaexport**          | `workspace.export`           | En enda `.db`-**fil**                 | En arbetsytas databas         |

Alla skrivs med SQLite `VACUUM INTO`, som är säkert mot en levande WAL-databas:
det tar en lästransaktion, producerar en defragmenterad och transaktionellt konsekvent
kopia och kräver aldrig att servern stoppas.

De här filerna och hämtade kopior **krypteras inte i vila** av Control Center.
Den end-to-end-krypterade överföringen skyddar byten under vägen mellan en
parkopplad klient och dess `cc_server`, på direkta eller reläförmedlade
anslutningar. Skydda lokal lagring och kopior utanför maskinen separat; servern
och varje auktoriserad mottagare kan läsa databasfilerna.

## Ögonblicksbildens struktur

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Strukturen speglar den levande datakatalogen exakt, vilket är det som gör att en
återställning av en installation blir en tillbakakopiering i stället för en
översättning. Katalognamnet är UTC-tidsstämpeln med `:` och `.` utbytta mot `-`, så det
är filsystemssäkert på Windows och sorteras kronologiskt som en vanlig sträng.

Schemalagda säkerhetskopior av arbetsytor ligger separat under
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Var och en har ett `manifest.json` för just den filen och ingen `global.db`; de är inte
installationsögonblicksbilder. En återställning behåller databasen den ersätter på samma plats, som `<timestamp>-pre-restore`. Veckopipelinens bevarandesteg tar bara bort
säkerhetskopior från sin egen arbetsyta som är äldre än den konfigurerade åldern
(30 dagar som standard); manuellt skapade installationsögonblicksbilder roteras
aldrig av det steget. `server.listBackups` listar bara
installationsögonblicksbilder, även overifierade sådana; `workspace.listBackups` listar
en arbetsytas schemalagda säkerhetskopior.

Att radera en arbetsyta lämnar den här katalogen kvar. Arbetsytans schema stoppas med
den, så inget roterar längre de säkerhetskopiorna, och de ligger kvar tills
installationens ägare tar bort dem. `server.listOrphanedBackups` rapporterar dem.


### `manifest.json`

| Fält                      | Typ             | Betydelse                                                           |
| ------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                 | int             | Manifestformat. För närvarande `2`                       |
| `created_at`              | ISO-8601 UTC    | När ögonblicksbilden togs                                           |
| `global`                   | object          | Posten för `global.db`. Saknas i en schemalagd arbetsytesäkerhetskopia |
| `workspaces[]`            | array           | En post per fångad arbetsyta                                        |
| `workspaces[].workspace_id`| string         | Arbetsytan som den här filen innehåller                            |
| `skipped_workspaces[]`     | array           | Arbetsytor som säkerhetskopian **inte** kunde fånga                 |
| `skipped_workspaces[].workspace_id` | string | Arbetsytan som lämnades utanför                                     |
| `skipped_workspaces[].reason` | string       | `no_file`, `damaged` eller `failed`                                    |

`global` och varje post i `workspaces[]` registrerar en kopierad fil, uppmätt på kopian
efter att den skrevs:

| Fält             | Typ | Betydelse                                                                      |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`                     | string          | Sökväg relativt ögonblicksbildens rot: `global.db` eller `<workspaceId>/workspace.db` |
| `bytes`      | int             | Storleken på kopian                                              |
| `sha256`         | string | SHA-256 för kopian, med små hexadecimala tecken                                |
| `quick_check`    | string | Vad SQLites `quick_check` sa om kopian: `ok`, eller dess fynd                  |
| `user_version`   | int    | Schemaversionen för kopian                                                     |
| `application_id` | int    | SQLite-`application_id` för kopian                                             |

En arbetsyta hoppas över när den är registrerad men aldrig har skrivits till (`no_file`), när dess databas inte klarar integritetskontrollen (`damaged`; en skadad kopia tas aldrig), eller när kopian eller kontrollen av den kopian misslyckades (`failed`). Hur som helst slutförs ögonblicksbilden ändå, och manifestet namnger det som saknas. Manifestet skrivs sist.

### Fullständighet

`server.listBackups` rapporterar en `complete`-flagga per ögonblicksbild. Den är falsk när manifestet saknas, inte går att tolka eller har ett annat format, när en fil som det namnger saknas eller har en annan storlek, eller när en kopia inte klarade sin kontroll. Appen visar en sådan ögonblicksbild som **Overifierad**. Ögonblicksbilder som togs före format `2` är i det tillståndet.

En overifierad ögonblicksbild listas ändå, för en ögonblicksbild som en operatör inte
kan se är en ögonblicksbild som operatören tror sig ha. När manifestet inte går att
läsa faller listningen tillbaka på själva strukturen och rapporterar de
`<workspaceId>/workspace.db`-filer den hittar – de kan fortfarande tas över var för sig
via `workspace.import`, även om ögonblicksbilden som helhet inte kan återställa en
installation.

En listad ögonblicksbild eller schemalagd säkerhetskopia bär `pinned_reason: "last_good_copy"` medan den håller den senaste verifierade kopian av en arbetsyta vars databas är skadad. Bevarandesteget hoppar över den tills arbetsytan har återställts.

## Vad en säkerhetskopia inte innehåller

Båda artefakterna är **enbart databaser**. En arbetsytekatalog innehåller mer än sin
databas, och inget av resten följer med:

| Sökväg                              | I en ögonblicksbild? | I en arbetsytaexport?  |
| ----------------------------------- | -------------------- | ---------------------- |
| `global.db`                         | Ja                   | Nej                    |
| `<workspaceId>/workspace.db`        | Ja                   | Ja (den *är* filen)    |
| `<workspaceId>/code_index.db`       | Nej                  | Nej                    |
| `<workspaceId>/blobs/`              | Nej                  | Nej                    |
| `<workspaceId>/skills/`             | Nej                  | Nej                    |
| `<workspaceId>/agents/`             | Nej                  | Nej                    |
| `<workspaceId>/chat_credentials/`   | Nej                  | Nej                    |
| `<workspaceId>/spaces/<spaceId>/`   | Nej                  | Nej                    |
| `<workspaceId>/pr_clones/`          | Nej                  | Nej                    |
| `secrets.json`                      | Nej                  | Nej                    |
| `models/`                           | Nej                  | Nej                    |
| `meetings/<meetingId>/`             | Nej                  | Nej                    |
| `rigs/`                             | Nej                  | Nej                    |
| `_agent_hooks/`                     | Nej                  | Nej                    |

En del av det är umbärligt – `spaces/` innehåller copy-on-write-worktrees som återskapas från repona, `pr_clones/` är en cache, `code_index.db` byggs om, `models/` laddas ner på nytt, `rigs/` är maskintillstånd. En del är det inte: `blobs/` innehåller inklistrade bilder som rader i databasen pekar på, `skills/` och `agents/` innehåller filerna som en agent körs med, och `secrets.json` innehåller varje parkopplingsnyckel, leverantörsuppgift och SSO-inställning i installationen. Se [Säkerhetskopiera och återställ](/sv-SE/handbok/how-to-guider/sakerhetskopiera-och-aterstall/#kopiera-säkerhetskopior-bort-från-maskinen) för att täcka resten.
:::note[Hemligheter hålls utanför databaserna]
`workspace.db` är hela arbetsytan: konversationer, körloggar, repolänkar, miljödefinitioner och medlemmar. Webhook-tokens för pipelinen och webhook-hemligheter för ärendesynk finns i `secrets.json`: databasen innehåller en referens till var och en, och ruttindexet innehåller en nyckelhash av varje token. En arbetsyta som återställs på en annan installation får därför inga webhooks förrän dess triggers har sparats på nytt där. Leverantörsinloggningar, enhetsnycklar och användarhemligheter finns i `global.db` och `secrets.json`.
:::

:::note[Chattbottens tokens stannar kvar med avsikt]
Att `chat_credentials/` ligger bredvid databasen i stället för i den är varför en
arbetsyta som lämnas till någon annan inte bär några levande bottokens. Se
[referensen för chattbryggan](/sv-SE/handbok/referens/chattbrygga/).
:::

## Åtgärder

RPC:er för säkerhetskopiering av installationen och export/import av arbetsytor är
endast för `fullClient`: en parkopplad telefon kan inte utlösa dem. Alla saknas helt –
inte avvisade, utan strukturellt frånvarande – på en server där ingen port för
säkerhetskopiering är inkopplad, som demoservern.

| Åtgärd               | Typ    | Omfattning | Minsta roll           | Argument      | Returnerar                    |
| -------------------- | ------ | ---------- | --------------------- | ------------- | ----------------------------- |
| `server.backupNow`   | mutate | Installation | installationens **ägare** | inga      | `{ok, path}`                  |
| `server.listBackups` | read   | Installation | installationens **ägare** | inga      | `{backups: [...]}`            |
| `server.deleteBackup` | mutate | Installation | installationens **ägare** | `name`    | `{ok}`                        |
| `server.listOrphanedBackups` | read | Installation | installationens **ägare** | inga | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutate | Installation | installationens **ägare** | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | read | Arbetsyta | `admin` | inga | `{backups: [...]}` |
| `workspace.deleteBackup` | mutate | Arbetsyta | `owner` | `name` | `{ok}` |
| `workspace.export`   | read   | Arbetsyta  | `admin`               | inga          | `{ok, path}`                  |
| `workspace.import`   | mutate | Arbetsyta  | `owner` och serverägaren | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | read | Arbetsyta | `owner` och serverägaren | inga | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutate | Arbetsyta | `owner` och serverägaren | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | mutate | Installation* | `owner`           | `id`          | registerrad markerad som borttagen |

* `workspace.delete` saknar omfattning eftersom raden den markerar ligger i det globala
registret; dess hanterare kontrollerar anroparens medlemskap i den namngivna arbetsytan
och kräver `owner`.

`path` i varje svar är en sökväg på **servervärden**.

`server.listOrphanedBackups` returnerar en post per arbetsyta som inte längre är aktiv:
`workspace_id`, `workspace_name` när registret fortfarande känner till det, och `backups`.
En raderad arbetsyta kan inte längre klara en rollkontroll för arbetsytan, så dess
säkerhetskopior tillhör installationens ägare. `server.deleteOrphanedBackup` nekar en
aktiv arbetsyta, vars säkerhetskopior förblir bakom `workspace.deleteBackup` och den
arbetsytans egna roller. Båda borttagningsåtgärderna accepterar bara ett listat
katalognamn med tidsstämpel, inte en sökväg.

`workspace.importHolds.list` returnerar det som en import höll tillbaka. Varje tillbakahållning har ett `id`, en `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` eller `invite`), `payload` som den skulle ha återställt, `imported_at` och `source_install_id`. `workspace.importHolds.resolve` med `accept: true` ger den tillbaka, och med `false` avvisas den. `applied` är false när den eller det som beviljandet gällde inte längre finns i arbetsytan.

:::note[En ögonblicksbild av hela installationen kräver ägare på båda kanalerna]
`server.backupNow`, `server.listBackups` och `server.deleteBackup` kräver
installationens **ägare** (`ServerAuthority.serverOwner`), samma grind som
`GET /backup/snapshot`. En ögonblicksbild fångar varje arbetsytas databas, så
att vara admin för en arbetsyta räcker inte för att hantera de andra. Borttagning
accepterar bara det listade tidsstämpelkatalognamnet, inte en godtycklig sökväg
på servern, och tar bort hela ögonblicksbilden (även overifierade ögonblicksbilder).
Export av arbetsyta och nedladdning av schemalagda säkerhetskopior ligger kvar hos
arbetsytans admin.
:::

:::note[Återställning tillhör serverägaren]
`workspace.import` och `POST /backup/restore` gör att servern tar över en databasfil vars rader den sedan behandlar som sina egna: repolänkar och vem som skapade dem, miljödefinitioner som körs på värden, worktree- och loggsökvägar. Därför kräver båda serverägaren (`ServerAuthority.serverOwner`), som också måste vara arbetsytans ägare. Alla andra, och varje anropare på en värd utan någon registrerad ägare, nekas med `server_owner_required`. Ingen trigger, vy, kolumn eller begränsning som filen tar med sig tas över.
:::

### Svaret från `server.listBackups`

Nyast först, sorterat efter katalognamn (som är tidsstämpeln, så ordningen håller även
för en ögonblicksbild vars manifest inte kunde läsas).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` utelämnas när manifestet inte kunde läsas. `bytes` på översta nivån är den
verkliga storleken på disken för hela katalogen, inte manifestets egen summa – frågan
en operatör som gallrar bland ögonblicksbilder ställer är vad katalogen kostar, inte vad
säkerhetskopian avsåg att skriva.

Varje `workspaces[].path` är exakt det som `workspace.import` tar som `source_path`. Det
är avsiktligt: "återställ den här arbetsytan från den här ögonblicksbilden" *är*
importåtgärden, så de två kan inte glida isär till olika behandlingar av samma fil.

### Validering i `workspace.import`

Innan något ersätts kopieras kandidatfilen till en mellanlagringsfil bredvid målet och kontrolleras där. En avvisning rör ingenting och bär sin typ som `data.kind`.

| Villkor                                          | Resultat                                                        |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| Filen finns inte | Avvisas, `import.missing_source` |
| Inte en läsbar SQLite-databas, eller den klarar inte `quick_check` | Avvisas, `import.damaged` |
| Den kommer från en ögonblicksbild, och dess SHA-256 skiljer sig från manifestets | Avvisas, `import.checksum_mismatch` |
| En nyare version av servern skrev den | Avvisas, `import.newer_schema` |
| Ett annat `application_id`, eller ingen `workspace_meta` | Avvisas, `import.foreign_file` |
| Den kan inte föras över till den här serverns schema | Avvisas, `import.schema_mismatch` |
| Dess webhooks eller inbjudningar dirigeras redan till en annan arbetsyta | Avvisas, `import.route_conflict` |
| Registrerat arbetsyte-id ≠ målet                  | **Tillåts**. Dess rader nycklas om till målet. Så här dupliceras en arbetsyta eller återställs under ett nytt id |
| Registrerat installations-id ≠ den här installationen | **Tillåts**. Dess användar-id:n tillhör den installationen och löses inte upp här |

Vid godkännande förs den mellanlagrade filen till den här serverns schema och måste sedan stämma exakt med det. Behörigheter som en fil inte får ge sig själv tas bort ur den: godkännanden att köra en miljödefinition på värden rensas, och åtgärdsregler som tillåter eller frågar, sandlådekörningsbehörigheter, repobehörigheter utöver läsning, roller över medlem och inbjudningar till dessa roller blir tillbakahållningar som serverägaren ska granska. Den som importerar behåller eller får ägarrollen. Databasen som ersätts behålls som en schemalagd säkerhetskopia med namnet `<timestamp>-pre-restore`, den mellanlagrade filen flyttas till sin plats med arbetsytans anslutningar stängda, `code_index.db` raderas för att byggas om, och FTS-indexen byggs om.

## Överföringsvägar

Export-/import- och listningsåtgärderna för ögonblicksbilder ovan talar i sökvägar på
serversidan, vilket bara är ett fullständigt svar när servern är din egen maskin. De här
HTTP-formade vägarna bär säkerhetskopiebyten **inuti samma autentiserade,
end-to-end-krypterade resurstunnel** som andra känsliga resurser, oavsett om
RPC-anslutningen är direkt eller förmedlad. De är inte publika
HTTP-filöverföringsändpunkter: en begäran till en av dem på den publika lyssnaren
returnerar `426 Upgrade Required`, även från loopback. I den krypterade tunneln måste
enheten som autentiserats med Noise matcha `d`; hanteraren kontrollerar dessutom enhetens
signatur över dess målsträng med dess parkopplings-PSK och rollen nedan.

| Väg                     | Metod  | Fråga           | Signerat mål                   | Kräver                  |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | Arbetsytans **admin** |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | Installationens **ägare** |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | Arbetsytans **admin**; installationens **ägare** när arbetsytan har raderats |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | Installationens **ägare** som också är arbetsytans **ägare** (annars `403` med `server_owner_required`) |

`w` är ett arbetsyte-id, `n` ett namn på en katalog för en ögonblicksbild eller en
schemalagd säkerhetskopia, `d` det anropande enhets-id:t och `s` signaturen. På
`/backup/snapshot` löses `n` upp mot listan över säkerhetskopior i stället för att fogas
till backups-roten, så vägen kan inte riktas mot en katalog som listningen inte skulle ha
visat. På `/backup/stored` måste det vara ett tidsstämpelnamn, och filen måste vara en
verklig fil i den arbetsytans egen katalog för säkerhetskopior.

| Status | Orsak                                                                               |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | En obligatorisk frågeparameter saknas, ett namn på en säkerhetskopia är ogiltigt, uppladdningskroppen är tom, eller den uppladdade filen avvisades (kroppen är `{error, kind}` med ett `import.*`-kind) |
| `403`  | Okänd eller återkallad enhet, felaktig signatur, eller så saknar anroparen rollen     |
| `404`  | Ingen port för säkerhetskopiering på den här värden, eller så finns inte den namngivna ögonblicksbilden, säkerhetskopian eller arbetsytefilen |
| `405`  | `/backup/restore` anropad med något annat än `POST`                                  |
| `413`  | Uppladdningskroppen överstiger 8 GiB, antingen enligt angiven content-length eller enligt antalet faktiskt lästa byten |
| `426`  | Varje direkt begäran till en överföringsväg på den publika HTTP-lyssnaren; använd en parkopplad klients krypterade resurstunnel |
| `500`  | Exporten eller arkiveringen misslyckades på serversidan                               |

Alla tre hämtningarna svarar med `Cache-Control: no-store` och `Accept-Ranges: none`.
`/backup/workspace` och `/backup/snapshot` skapar en **färsk** kopia per begäran och raderar
den när den har strömmats, så ett cachelagrat eller återupptaget svar skulle sammanfoga
byten från två olika exporter till en fil som ser giltig ut men inte är det.

`/backup/stored` är undantaget: den strömmar en schemalagd säkerhetskopia som
`<workspaceId>-<name>.db` och lämnar filen kvar, eftersom den filen är säkerhetskopian.

`/backup/snapshot` returnerar `<name>.zip`, med poster relativa till ögonblicksbildens
rot så att uppackning återskapar `manifest.json` + `global.db` +
`<workspaceId>/workspace.db`. Posterna skrivs i sorterad ordning, så två arkiv av samma
ögonblicksbild är samma arkiv.

`/backup/restore` strömmar kroppen direkt till en mellanlagringsfil i stället för att
buffra den, begränsar den före och under läsningen och raderar den mellanlagrade filen på
**varje** väg ut, även vid en avvisning.

::::caution[Direkt och relä använder samma krypterade överföring]
Reläet bär resursbegäranden, strömmade svar och uppladdningsbyten som chiffertext;
det kan inte läsa säkerhetskopians innehåll. En sökväg på serversidan förblir en
sökväg på servervärden, inte en fil på reläet. Åtkomst kräver fortfarande den
parkopplade enheten, målsignaturen och den tillämpliga arbetsyte- eller
installationsrollen. Ingen av transporterna krypterar de resulterande
säkerhetskopiefilerna i vila.
::::

## Sökvägar och gränser

| Sak                            | Värde                                                        |
| ------------------------------ | ------------------------------------------------------------ |
| Ögonblicksbilder               | `<dataDir>/backups/<timestamp>/`                             |
| Schemalagda säkerhetskopior av arbetsytor | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Arbetsytaexporter              | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Databas som ersatts av en återställning | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Databaser som de såg ut innan en uppdatering ändrade deras format | `<dataDir>/pre_upgrade/` och `<dataDir>/<workspaceId>/pre_upgrade/`, de två senaste av varje |
| Mellanlagring för överföringar | `<dataDir>/backups/transfer/` – en arbetsbänk som städas av vägen som skriver till den |
| Ögonblicksbildens arkivnamn    | `<snapshot directory name>.zip`                              |
| Övre gräns för uppladdning     | 8 GiB per krypterad `/backup/restore`-uppladdning            |
| Bevarande                      | Installationsögonblicksbilder: manuell borttagning. Säkerhetskopior av arbetsytor: veckopipeline, 30 dagar som standard, eller manuell borttagning. Säkerhetskopior av en raderad arbetsyta: endast manuell borttagning |

Katalogerna `exports/`, `transfer/` och `workspace-backups/` är inte
installationsögonblicksbilder och utesluts från `server.listBackups`. Bara den sista
katalogen har schemalagt bevarande, och bara så länge dess arbetsyta finns; att radera en installationsögonblicksbild kräver
installationens ägares uttryckliga åtgärd.
