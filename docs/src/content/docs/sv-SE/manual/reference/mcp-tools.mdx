`cc_server` har ett enda MCP-register (JSON-RPC 2.0) för verktyg, som betjänas på serverns huvudport (standard `9030`) under `POST /mcp` och `GET /sse`, med protokollversion `2024-11-05`. Varje klient når samma register: skrivbordsappen, webbversionen, externa MCP-klienter och den inbyggda agentköraren. Externa MCP-servrar kan bryggas in i samma register som ett dynamiskt lager.

## Registrets storlek

| Mått                                                                      | Antal |
| ------------------------------------------------------------------------- | ----- |
| Verktyg som registreras av `cc_server`                                    | 110   |
| Från `packages/cc_mcp`                                                    | 108   |
| Från `packages/cc_mcp_client` (verktygsupptäckt)                          | 2     |
| Registrerade i basregistret (`server_mcp_registry.dart`)                  | 63    |
| Registrerade efter start allteftersom tjänsterna kommer upp (`cc_server_runtime.dart`) | 47 |
| Av basregistrets 63, villkorade av ett kodgraf-repo                       | 5     |

De fem kodgrafverktygen registreras bara när värden skickar in ett kodgraf-repo till `buildServerMcpRegistry`. `cc_server` skickar alltid in ett, så alla 110 är aktiva i den levererade binärfilen.

Hela registret annonseras i `tools/list` utan någon upptäcktsgrind. Ändringar av ärenden görs med typade verktyg.

:::note[Externa klienter ser alltid hela katalogen]
`tools/list` beskärs aldrig. MCP-klienter validerar verktygsnamn mot sin egen cachade kopia av listan och avvisar allt som inte står där utan att fråga servern, så ett verktyg som döljs där går inte att nå – det är inte bara tyst.

Den **inbyggda harnessen** fungerar annorlunda: den läser bara in en resident delmängd av definitionerna per förfrågan och hämtar resten vid första användning, vilket är ett beteende på harness-sidan och inte ändrar det här registret. Se [Verktygskontext och promptcache](/sv-SE/handbok/koncept/verktygskontext).
:::

:::note[Varje verktygsklass registreras]
En källfil under `packages/cc_mcp/lib/src/tools/` är ett verktyg som en agent kan
anropa. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
får bygget att misslyckas om en ny verktygsklass inte konstrueras av någonting.
:::

## Gemensamma parametrar

### `workspace_id`

**Obligatorisk** för varje verktyg som rör data knuten till en arbetsyta. Ett saknat eller ogiltigt `workspace_id` ger ett uttryckligt fel, och ett värde som inte matchar målentitetens arbetsyta avvisas i stället för att tyst ignoreras. Utelämna den på de verkligt globala verktygen: `list_workspaces` och de sex nyhetsflödesverktygen (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), som följer serverägarens användarspecifika flödeslista. Upptäcktsverktygen (`search_tool_bm25`, `list_my_tools`) tar den frivilligt så att de kan klassificera anropbarhet efter samtalsläge. När en agent skickas ut av servern tvingas arbetsytan fram på serversidan, så agenten kan inte nå en annan arbetsyta genom att skicka in ett främmande id.

## Verktygsupptäckt

Båda kommer från `cc_mcp_client`, inte `cc_mcp`, och båda konsulterar lägesvakten så att de rapporterar vad som är anropbart i det _aktuella_ samtalsläget.

| Verktyg            | Beskrivning                                                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `search_tool_bm25` | Sök i verktygskatalogen med nyckelord; returnerar matchande verktyg, deras argumentscheman och huruvida var och ett är anropbart just nu |
| `list_my_tools`    | Lista de verktyg som är anropbara just nu i det här samtalet, filtrerat efter dess läge                                     |

Ett tredje upptäcktsverktyg, **`search_tools`**, finns bara inuti den inbyggda harnessen och ingår inte i det här MCP-registret. Det rangordnar körningens egen verktygsyta och **läser in** – till skillnad från `search_tool_bm25` – scheman för det den hittar, så att agenten kan anropa en träff i sin nästa tur. Agenter som kör på harnessen bör föredra det; MCP-klienter har `search_tool_bm25`.

## Verktyg för avskilda miljöer (stationer)

Kör engångsmaskiner – en innesluten webbläsare eller Linux-skrivbord, en Android-
emulator eller en iOS-simulator – inifrån en körning. Registreras efter start,
ovillkorligt: huruvida en maskin verkligen kan starta är en sondfråga som
verktygen svarar på per anrop. Upprepade anrop i ett samtal återanvänder en maskin;
skärmbilder returneras som bildinnehåll med en budget på en bild per resultat, och
extraherat sida-/gränssnittsinnehåll inramas som opålitlig data. De fyra
användningsverktygen plus `rig_close` deklarerar `enclosureControl`
[åtgärdsklassen](/sv-SE/handbok/koncept/racken/) (användningsverktygen deklarerar också `networkEgress` och
`processSpawn`; `mobile_use` och `ios_use` deklarerar också `packageInstall`), så
skrivskyddade lägen nekar dem. `rig_list` deklarerar ingen – det läser bara
arbetsytans tillstånd. Hela verbförrådet per yta finns i
[stationsreferensen](/sv-SE/handbok/referens/stationer/#action-verbs).

| Verktyg        | Beskrivning                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------ |
| `computer_use` | Styr ett Linux-skrivbord i en avskild VM: flytta, klicka, dra, rulla, skriva, ändra storlek, urklipp, skärmbild |
| `browser_use`  | Styr en headless Chromium, Firefox eller WebKit (`engine`): navigera, klicka, fylla i, extrahera (a11y/DOM/konsol), urklipp, skärmbild |
| `mobile_use`   | Styr Android över ADB: inspektera/mata in, skärmbilder, installera/starta/stoppa/återställa/avinstallera appar, djuplänkar och argv-formade enhetskommandon |
| `ios_use`      | Styr iOS-simulatorn via WebDriverAgent/CoreSimulator: inspektera/mata in, skärmbilder, installera/starta/stoppa/avinstallera appar, djuplänkar och argv-formade simulatorprocesser |
| `rig_list`     | Lista en arbetsytas stationer med yta, status, skärmstorlek och styrenhet                      |
| `rig_close`    | Förstör en station och kassera dess ägda maskintillstånd                                        |

## Exponeras inte över MCP

Kalender och möten har inga MCP-verktyg. Agenter kan inte läsa din kalender, dina möten, transkript, åtgärdspunkter eller beslut. Sammanfattningen som tar fram åtgärdspunkter och beslut körs som den inbyggda [`meeting_summary`-pipelinen](/sv-SE/handbok/koncept/moten/), inte som ett verktyg en agent kan anropa.

## Verktygsgrindar per läge

Grindarna tillämpas två gånger från en och samma tabell (`ModeToolPolicy`): en gång i MCP-dispatchern för Claude Code-adaptern och en gång i den inbyggda harnessens register. Ett blockerat anrop returnerar orsaken.

| Läge          | Verktygsyta                                                                                                                                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | Alla registrerade verktyg; ingen tillåtelselista                                                                                                                                                                                     |
| `plan`        | En kurerad tillåtelselista. Inga worktree-skrivningar och inga `create`- / `assign`- / `delegate`-ärendeverb, men minne, artefakter, att-göra-poster, `submit_plan`, `exit_plan_mode` och ärendeslutförandeverben på det utskickade ärendet är tillåtna |
| `review`      | En kurerad tillåtelselista: granskningsdeltagande, kommunikation, skrivskyddade kontexthämtare och hela uppsättningen ärendeverb inklusive `create_ticket` och `assign_ticket`                                                     |
| `orchestrate` | En kurerad tillåtelselista: forsknings- och läsverktyg plus `propose_orchestration`, `create_playbook` och `run_playbook`. Anställning, nedbrytning och ärendeavslut sker deterministiskt efter godkännande, aldrig mitt i körningen |

Tillåtet i alla lägen oavsett tillåtelselista:

| Uppsättning        | Verktyg                                                                                                                                                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Minne och artefakter | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Kodgraf            | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                       |
| Körningsmekanik    | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                    |

Att stå på en tillåtelselista gör inte ett verktyg anropbart, och det omvända gäller också: förmågan att ställa frågor till operatören är ett **harness**-verktyg (`ask_user`), så det förekommer aldrig i den här MCP-katalogen.

## Verktyg bakom godkännande

Ett verktyg kan deklarera `requiresApproval`. Dispatchern bygger då en `ApprovalPayload` och visar den via `ConfirmationPort` innan verktyget körs; `cc_server` kopplar in den porten, så godkännandegrinden är aktiv.

Registrerade verktyg som deklarerar det: `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

Oberoende av detta grindar de enhetliga åtgärdsräckena varje verktyg som deklarerar en icke-tom uppsättning `ActionClass`. Ett `prompt`-beslut utan ansluten godkännare nekas. Se [Räcken](/sv-SE/handbok/koncept/racken/).

| Förmåga                                 | Var den finns i stället                                                                      |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| Att anställa, avskeda eller redigera en agent | Agentgränssnittet. Det finns inget `hire_agent` / `fire_agent` / `update_agent`-verktyg     |
| Att skapa en arbetsyta                  | `workspace.upsert` över RPC, som skapar grunddata och stämplar ägandet                        |
| Projekt (skapa / lista / uppdatera / lägga in) | Ärendegränssnittet. Projekt är en operatörsyta – se [Projekt](/sv-SE/handbok/how-to-guider/projekt/) |
| Att ställa en blockerande fråga till operatören | **harness**-verktyget `ask_user`, inte MCP. Det renderar ett formulär i samtalet och blockerar på svaret |
| Felsökning per agent                    | Ingenting. Det finns ingen `doctor` – se [Felsök en agent](/sv-SE/handbok/how-to-guider/felsok-agent/) |
| Kalender och möten                      | RPC endast för mänskliga klienter (se ovan)                                                   |
