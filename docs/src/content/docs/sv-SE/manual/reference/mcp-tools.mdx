`cc_server` har ett enda MCP-register (JSON-RPC 2.0) för verktyg, som betjänas på serverns huvudport (standard `9030`) under `POST /mcp` och `GET /sse`, med protokollversion `2024-11-05`. Varje klient når samma register: skrivbordsappen, webbversionen, externa MCP-klienter och den inbyggda agentköraren. Externa MCP-servrar bryggas in i samma register i egna lager: ett per arbetsyta för de MCP-servrar dess administratörer konfigurerar, och ett för serverägarens personliga MCP-servrar. Den här endpointen listar, anropar och söker i dem bara för en agentkörning: arbetsytans egna MCP-servrar, plus de personliga när serverägaren ansvarar för körningen. MCP-token och parkopplade enheter ser dem aldrig (se [MCP-servrar som agenterna använder](/sv-SE/handbok/how-to-guider/mcp-server/#mcp-servrar-som-agenterna-använder)).

## Registrets storlek

| Mått                                                                      | Antal |
| ------------------------------------------------------------------------- | ----- |
| Verktyg som registreras av `cc_server`                                    | 116   |
| Från `packages/cc_mcp`                                                    | 114   |
| Från `packages/cc_mcp_client` (verktygsupptäckt)                          | 2     |
| Registrerade i basregistret (`server_mcp_registry.dart`)                  | 64    |
| Registrerade efter start allteftersom tjänsterna kommer upp (`cc_server_runtime.dart`) | 52 |
| Av basregistrets 64, villkorade av ett kodgraf-repo                       | 5     |
| Av basregistrets 64, villkorat av kodlägesköraren (`repl`) | 1 |

De fem kodgrafverktygen registreras bara när värden skickar in ett kodgraf-repo till `buildServerMcpRegistry`, och `repl` bara när den skickar in kodlägesköraren. `cc_server` skickar alltid in båda (den startar inte utan köraren), så alla 111 är registrerade i den levererade binärfilen; den offentliga demoservern registrerar ingen `repl`.

Hela registret annonseras i `tools/list` utan någon upptäcktsgrind, utom för en agentkörning som kan köra skript (nedan). Ändringar av ärenden görs med typade verktyg.

:::note[Externa klienter ser alltid hela katalogen]
`tools/list` beskärs aldrig, utom för serverägarens personliga MCP-servrar, som den aldrig innehåller, och [Kodläge](/sv-SE/handbok/koncept/kodlage/): `repl` listas bara för en agentkörning på en server som kan köra skript, och den körningen listas med `repl`, de direkta verktygen (`read`, `write`, `edit`, `search`, `find`, `bash`, `read_output`, `ask_user`, `task`, `todo_write`, `search_memory`, `send_message` och lägets egna verb där registret har dem) och de verktyg ett skript inte får anropa. Den anropar resten från ett skript; ett direkt anrop till ett av dem besvaras med hur det anropas från `repl`. MCP-klienter validerar verktygsnamn mot sin egen cachade kopia av listan och avvisar allt som inte står där utan att fråga servern, så ett verktyg som döljs där går inte att nå – det är inte bara tyst.

Den **inbyggda harnessen** fungerar annorlunda: den läser bara in en liten direkt uppsättning definitioner per förfrågan och når resten från skript eller läser in dem vid första användning, vilket är ett beteende på harness-sidan och inte ändrar det här registret. Se [Verktygskontext och promptcache](/sv-SE/handbok/koncept/verktygskontext/).
:::

:::note[Varje verktygsklass registreras]
En källfil under `packages/cc_mcp/lib/src/tools/` är ett verktyg som en agent kan
anropa. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
får bygget att misslyckas om en ny verktygsklass inte konstrueras av någonting.
:::

## Gemensamma parametrar

### `workspace_id`

**Obligatorisk** för varje verktyg som rör data knuten till en arbetsyta. Ett saknat eller ogiltigt `workspace_id` ger ett uttryckligt fel, och ett värde som inte matchar målentitetens arbetsyta avvisas i stället för att tyst ignoreras. Utelämna den på de verkligt globala verktygen: `list_workspaces` och de sex nyhetsflödesverktygen (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), som följer serverägarens användarspecifika flödeslista. Upptäcktsverktygen (`search_tool_bm25`, `list_my_tools`) tar den frivilligt så att de kan klassificera anropbarhet efter samtalsläge. När en agent skickas ut av servern tvingas arbetsytan fram på serversidan, så agenten kan inte nå en annan arbetsyta genom att skicka in ett främmande id.

## Verktygsupptäckt

Båda kommer från `cc_mcp_client`, inte `cc_mcp`, och båda konsulterar lägesvakten så att de rapporterar vad som är anropbart i det _aktuella_ samtalsläget.

| Verktyg            | Beskrivning                                                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `search_tool_bm25` | Sök i verktygskatalogen med nyckelord; returnerar matchande verktyg, deras argumentscheman och huruvida var och ett är anropbart just nu |
| `list_my_tools`    | Lista de verktyg som är anropbara just nu i det här samtalet, filtrerat efter dess läge                                     |

Ett tredje upptäcktsverktyg, **`search_tools`**, finns bara inuti den inbyggda harnessen och ingår inte i det här MCP-registret. Det rangordnar körningens egen verktygsyta och **läser in** – till skillnad från `search_tool_bm25` – scheman för det den hittar, så att agenten kan anropa en träff i sin nästa tur. Agenter som kör på harnessen bör föredra det; MCP-klienter har `search_tool_bm25`.

## Kodläge

| Verktyg | Beskrivning |
| ------ | ----------- |
| `repl` | Kör ett JavaScript-skript som anropar körningens övriga verktyg som `tools.<id>(args)` och returnerar bara det det behöver. Listas bara för en agentkörning på en server som kan köra [Kodläge](/sv-SE/handbok/koncept/kodlage/)-skript. Varje kapslat anrop passerar samma grind som ett `tools/call`. Tar `code`, `description`, `timeout_ms?`, `max_output_tokens?` |

Ett skript kan inte anropa `repl`, `search_tool_bm25`, `list_my_tools` eller något verktyg som startar eller meddelar en annan agentkörning, tilldelar eller kommenterar ett ärende, skickar ett meddelande, skapar, beslutar eller kommenterar ett godkännande, föreslår eller ändrar policy, installerar eller ändrar färdigheter, skapar en körprofil, skickar in en plan, lämnar planläge, slutför konversationens mål eller skickar in en pipelinekörnings utdata. De verktygen deklarerar `scriptCallable` som false och anropas alltid direkt; i den inbyggda harnessen läses ett sällan använt verktyg utanför den direkta uppsättningen in vid första användning. `create_ticket` kan bara anropas från ett skript utan en `assignee`.

## Meddelanden och delegering mellan agenter

Agenter pratar med varandra över ytor (varaktigt, synligt i listan). `ask_agent` antingen väntar på svaret (`mode: wait`, 600 sekunder som standard, högst 1 800) eller returnerar direkt (`mode: background`); i båda fallen väcks frågeställaren en gång med svaret när det inte kom tillbaka direkt. `send_to_agent`, `ask_agent`, `consult_agent`, `request_peer_review` och `delegate_task` passerar samma grind på servern: djup (3), cykeldetektering, budgetram, autonomitak och en hastighetsgräns per par av agenter. Avsändarens identitet kommer alltid från den anropande körningen. Se [Agenter som samarbetar](/sv-SE/handbok/how-to-guider/agenter-samarbetar/).

| Verktyg         | Beskrivning                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------- |
| `send_to_agent` | Skicka ett enkelriktat meddelande till en annan agent, adresserat med `to_agent_id` eller exakt `to_agent_name`; svarar med `delivery_status` `woken`, `queued_behind_run` eller `refused` |
| `ask_agent`     | Ställ en fråga till en annan agent; vänta på svaret, eller fortsätt och väck när det kommer    |
| `delegate_task` | Delegera en uppgift till en annan agent som ett spårat underordnat ärende                      |
| `consult_agent` | Lägg till den specialist som matchar bäst på skills i ytan och skicka ut den med en fokuserad uppdragsbeskrivning |
| `todo_read`     | Läs det här samtalets sparade uppgiftschecklista                                               |
| `agent_activity` | Läs vad en annan agent gör nu och gjorde senast (status, aktuellt verktyg, senaste meddelanden), utan att väcka den |

## Verktyg för väckningar och mål

En agent använder dessa i stället för att vila eller fråga på nytt. Var och en agerar bara för den anropande agenten i dess egen konversation; agenten är aldrig ett argument. Se [Scheman och väckningar](/sv-SE/handbok/how-to-guider/scheman-vackningar/) och [Arbeta mot ett mål](/sv-SE/handbok/how-to-guider/arbeta-mot-mal/).

| Verktyg | Beskrivning |
| ------------- | ----------- |
| `wake_me` | Be om att bli väckt senare: vid en tidpunkt (`in:20m`, `at:<ISO time>`), med ett intervall (`every:30m`), med en cron (`cron:0 9 * * 1-5`, med `tz`), i egen takt inne i en självstyrd loop (`next`, med `delay` från 1 till 60 minuter), eller när något händer (`on:pr_checks`, `on:pr_review`, `on:pr_merged`, `on:environment`, `on:ticket:<id>`, `on:pipeline_run:<id>`). Valfria `note`, `max_runs`, `expires_in`, `when_busy` (`skip` eller `queue`) och `deliver` (`run` eller `notify`) |
| `list_wakes` | Listar vad agenten har i väntan i den här konversationen: scheman, bevakningar, väntande väckningar och obesvarade frågor |
| `cancel_wake` | Avbryt ett schema eller en bevakning som agenten själv satt upp, med dess id |
| `goal_status` | Läs agentens aktiva mål: kontrakt, segment, utgifter och kvarvarande budget, varningar för inga framsteg, parkering, senaste verifiering och väntande målväckningar |

`complete_goal` (under [Verktyg för planer, playbooks och artefakter](#verktyg-för-planer-playbooks-och-artefakter)) är det enda sättet för en agent att säga att ett mål är klart, och det är ett påstående, inte en slutförning.

## Verktyg för avskilda miljöer (stationer)

Kör engångsmaskiner – en innesluten webbläsare eller Linux-skrivbord, en Android-
emulator eller en iOS-simulator – inifrån en körning. Registreras efter start,
ovillkorligt: huruvida en maskin verkligen kan starta är en sondfråga som
verktygen svarar på per anrop. Upprepade anrop i ett samtal återanvänder en maskin;
skärmbilder returneras som bildinnehåll med en budget på en bild per resultat, och
extraherat sida-/gränssnittsinnehåll inramas som opålitlig data. De fyra
användningsverktygen plus `rig_close` deklarerar `enclosureControl`
[åtgärdsklassen](/sv-SE/handbok/koncept/racken/) (användningsverktygen deklarerar också `networkEgress` och
`processSpawn`; `mobile_use` och `ios_use` deklarerar också `packageInstall`), så
skrivskyddade lägen nekar dem. `rig_list` deklarerar ingen – det läser bara
arbetsytans tillstånd. Hela verbförrådet per yta finns i
[stationsreferensen](/sv-SE/handbok/referens/stationer/#åtgärdsverb).

| Verktyg        | Beskrivning                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------ |
| `computer_use` | Styr ett Linux-skrivbord i en avskild VM: flytta, klicka, dra, rulla, skriva, ändra storlek, urklipp, skärmbild |
| `browser_use`  | Styr en headless Chromium, Firefox eller WebKit (`engine`): navigera, klicka, fylla i, extrahera (a11y/DOM/konsol), urklipp, skärmbild |
| `mobile_use`   | Styr Android över ADB: inspektera/mata in, skärmbilder, installera/starta/stoppa/återställa/avinstallera appar, djuplänkar och argv-formade enhetskommandon |
| `ios_use`      | Styr iOS-simulatorn via WebDriverAgent/CoreSimulator: inspektera/mata in, skärmbilder, installera/starta/stoppa/avinstallera appar, djuplänkar och argv-formade simulatorprocesser |
| `rig_list`     | Lista stationerna i körningens yta med yta, status, skärmstorlek och styrenhet                      |
| `rig_close`    | Förstör en station och kassera dess ägda maskintillstånd                                        |

Bara agentkörningar kan anropa de här verktygen; alla andra anropare nekas. En körning når bara stationerna i den yta den leasades för: `space_id` kommer från körningens behörighet, aldrig från anropet, och en station i en annan yta, eller i ingen yta, svarar exakt som en saknad.

`app_use` är ett femte use-verktyg: det styr fönstren i en skrivbordsapp som startats i en yta, direkt på värden i stället för i en VM, och deklarerar också `fileWriteOutsideWorktree` och `fileDelete`. Det och `environment_*`-verktygen beskrivs i [Konfigurera miljöer](/sv-SE/handbok/how-to-guider/miljoer/).

## Exponeras inte över MCP

Kalender och möten har inga MCP-verktyg. Agenter kan inte läsa din kalender, dina möten, transkript, åtgärdspunkter eller beslut. Sammanfattningen som tar fram åtgärdspunkter och beslut körs som den inbyggda [`meeting_summary`-pipelinen](/sv-SE/handbok/koncept/moten/), inte som ett verktyg en agent kan anropa.

## Verktygsgrindar per läge

Grindarna tillämpas två gånger från en och samma tabell (`ModeToolPolicy`): en gång i MCP-dispatchern för Claude Code-adaptern och en gång i den inbyggda harnessens register. Ett blockerat anrop returnerar orsaken.

| Läge          | Verktygsyta                                                                                                                                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | Alla registrerade verktyg; ingen tillåtelselista                                                                                                                                                                                     |
| `plan`        | En kurerad tillåtelselista. Inga worktree-skrivningar och inga `create`- / `assign`- / `delegate`-ärendeverb, men minne, artefakter, att-göra-poster, `submit_plan`, `exit_plan_mode` och ärendeslutförandeverben på det utskickade ärendet är tillåtna |
| `review`      | En kurerad tillåtelselista: granskningsdeltagande, kommunikation, skrivskyddade kontexthämtare och hela uppsättningen ärendeverb inklusive `create_ticket` och `assign_ticket`                                                     |
| `orchestrate` | En kurerad tillåtelselista: forsknings- och läsverktyg plus `propose_orchestration`, `create_playbook` och `run_playbook`. Anställning, nedbrytning och ärendeavslut sker deterministiskt efter godkännande, aldrig mitt i körningen |

Tillåtet i alla lägen oavsett tillåtelselista:

| Uppsättning        | Verktyg                                                                                                                                                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Minne och artefakter | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Kodgraf            | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                       |
| Körningsmekanik    | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                    |

Att stå på en tillåtelselista gör inte ett verktyg anropbart, och det omvända gäller också: förmågan att ställa frågor till operatören är ett **harness**-verktyg (`ask_user`), så det förekommer aldrig i den här MCP-katalogen.

## Verktyg bakom godkännande

Ett verktyg kan deklarera `requiresApproval`. Dispatchern bygger då en `ApprovalPayload` och visar den via `ConfirmationPort` innan verktyget körs; `cc_server` kopplar in den porten, så godkännandegrinden är aktiv.

Registrerade verktyg som deklarerar det: `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

Oberoende av detta grindar de enhetliga åtgärdsräckena varje verktyg som deklarerar en icke-tom uppsättning `ActionClass`. Ett `prompt`-beslut utan ansluten godkännare nekas. Se [Räcken](/sv-SE/handbok/koncept/racken/).

## Förmågor utan verktyg bakom sig

Inte varje förmåga i produkten går att nå för en agent. De här har inget verktyg
alls, så ett namn du kan ha sett hänvisat till någon annanstans returnerar "unknown tool":

| Förmåga                                 | Var den finns i stället                                                                      |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| Att anställa, avskeda eller redigera en agent | Agentgränssnittet. Det finns inget `hire_agent` / `fire_agent` / `update_agent`-verktyg     |
| Att skapa en arbetsyta                  | `workspace.create` över RPC, bara för serverägaren, som skapar grunddata och stämplar ägandet |
| Projekt (skapa / lista / uppdatera / lägga in) | Ärendegränssnittet. Projekt är en operatörsyta – se [Projekt](/sv-SE/handbok/how-to-guider/projekt/) |
| Att ställa en blockerande fråga till operatören | **harness**-verktyget `ask_user`, inte MCP. Det renderar ett formulär i samtalet och blockerar på svaret |
| Felsökning per agent                    | Ingenting. Det finns ingen `doctor` – se [Felsök en agent](/sv-SE/handbok/how-to-guider/felsok-agent/) |
| Kalender och möten                      | RPC endast för mänskliga klienter (se ovan)                                                   |
