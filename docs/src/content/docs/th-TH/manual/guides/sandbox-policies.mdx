การรันของเอเจนต์จะอยู่ในแซนด์บ็อกซ์หรือไม่นั้นถูกตัดสินบนเซิร์ฟเวอร์ตอนบูต (`--sandbox`) สวิตช์ **เปิดใช้แซนด์บ็อกซ์** และตัวเลือก **แบ็กเอนด์** ภายใต้ **การตั้งค่า → เซิร์ฟเวอร์ → การวินิจฉัยและความเป็นส่วนตัว** เป็นค่ากำหนดที่จัดเก็บไว้บนอุปกรณ์ของคุณ การตรวจหาโฮสต์ของการ์ด **แซนด์บ็อกซ์** รายงานว่าโฮสต์ของเซิร์ฟเวอร์ห่ออะไรได้บ้าง

มีส่วนควบคุมสองอย่างที่ไปถึงการรัน และคู่มือนี้ครอบคลุมทั้งคู่: กฎการกระทำใน **การตั้งค่า → เวิร์กสเปซ → สิทธิ์ของเอเจนต์** ซึ่งตัดสินว่าเอเจนต์พุช เปิด หรือเข้าถึงอะไรได้ และแฟล็ก `--sandbox` ของเซิร์ฟเวอร์เอง

## อะไรที่เป็นข้อจำกัดต่อการรันของเอเจนต์

มีหกสิ่งที่เป็นข้อจำกัดต่อเอเจนต์ อย่างแรกคือแซนด์บ็อกซ์ของ OS และเป็นสิ่งเดียวที่มีเงื่อนไข — อีกห้าสิ่งคงอยู่บนทุกโฮสต์

| ขอบเขต | สิ่งที่มันทำ |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| แซนด์บ็อกซ์ของ OS | Seatbelt บน macOS, bubblewrap บน Linux และ WSL2 ห่อ Claude Code CLI อะแดปเตอร์ ACP และเครื่องมือ `bash` ของฮาร์เนส **ไม่มีบน Windows และบน Linux ที่ไม่มี `bwrap` และ `socat` ซึ่งมีเพียงการรันของเจ้าของเซิร์ฟเวอร์เท่านั้นที่เริ่มทำงาน** |
| worktree ของตัวเอง | การสนทนาแต่ละรายการได้เช็กเอาต์แบบ copy-on-write เช็กเอาต์ต้นฉบับถูกพับเข้าในการรันเป็นเส้นทางที่ห้ามเขียน และแซนด์บ็อกซ์คือสิ่งที่บังคับใช้มัน |
| ข้อมูลรับรองที่ผ่านนายหน้า | นายหน้าข้อมูลรับรองสร้างสภาพแวดล้อมต่อการรันหนึ่งครั้ง และเพิกถอนมันตอนรื้อถอน โทเคน GitHub ในนั้นอ่านได้แต่พุชไม่ได้: การพุชผ่าน Control Center ซึ่งถามกฎการพุชก่อน |
| กฎคุมการกระทำ | เครื่องมือที่เปลี่ยนแปลงสถานะทุกตัวประกาศคลาสผลกระทบของมัน และตัวคุมแปลงคลาสเหล่านั้นก่อนที่การเรียกจะรัน `prompt` ที่ไม่มีผู้อนุมัติเชื่อมต่ออยู่จะถูกปฏิเสธ |
| การชำระล้างสภาพแวดล้อม | ACP และเครื่องมือ `bash` ของฮาร์เนสได้สภาพแวดล้อมที่ถูกกรอง Claude Code ผ่าน `NoSandboxAdapter` สืบทอดสภาพแวดล้อมของโฮสต์ |
| พื้นผิวเครื่องมือของโหมด | โหมดอ่านอย่างเดียวถอดเครื่องมือที่เปลี่ยนแปลง worktree ออกไปเลย และตรึงคำกริยาผลลัพธ์ของโหมดเองไว้เพื่อให้ยังส่งมอบได้ |

มีสามสิ่งที่ยังอ่อนกว่าที่มันดู:

- มีเพียง **ฮาร์เนสในตัว** เท่านั้นที่บังคับใช้ด่านเครื่องมือ ข้อกำหนดการเสร็จงาน และกฎเชิงโครงสร้างของโหมด อะแดปเตอร์ Claude Code ไม่ทำเช่นนั้น โดยเฉพาะ Claude Code นั้นถูกเรียกใช้ด้วย `--dangerously-skip-permissions` เพราะ `claude -p` แบบไม่มีการโต้ตอบจะค้างอยู่ตลอดไปที่พรอมต์ของมันเอง — การเรียกอ่าน เขียน และแก้ไขของ Claude เองจึงไม่ถูกมองเห็นและไม่ผ่านด่านของ Control Center และคำสั่ง bash ถูกตรวจเพียงโดยฮุกที่อ่านบรรทัดคำสั่ง ที่ใดแซนด์บ็อกซ์เปิดอยู่ มันคือขอบเขตรอบ ๆ การเรียกเหล่านั้น
- เครื่องมือไฟล์ในโปรเซสของฮาร์เนส (read, write, edit, apply patch, search, find, search_files) ทำงานอยู่ภายในโปรเซสของเซิร์ฟเวอร์ จึงไม่มีโปรไฟล์แซนด์บ็อกซ์ใดคุมมัน มีเพียงเครื่องมือ `bash` เท่านั้นที่ผ่านตัวรันคำสั่งที่อยู่ในแซนด์บ็อกซ์ เครื่องมือเหล่านั้นถูกจำกัดด้วยการจำกัดเส้นทางในตัวมันเองบวกกับกฎคุมการกระทำ
- บนโฮสต์ที่ไม่มีแบ็กเอนด์ มีเพียงการรันที่เจ้าของเซิร์ฟเวอร์รับผิดชอบเท่านั้นที่เริ่มทำงาน และสำหรับการรันเหล่านั้นแถวแรกใช้ไม่ได้ การรันของคนอื่นจะถูกปฏิเสธ ภายใต้ `--sandbox off` การรันของสมาชิกทุกคนเริ่มทำงานโดยไม่มีแถวแรก ไม่ว่าในกรณีใด ACP และเครื่องมือ `bash` ของฮาร์เนสถอยกลับไปพึ่งการชำระล้างสภาพแวดล้อมบวกกับนโยบายคำสั่ง และ Claude Code สืบทอดสภาพแวดล้อมของโฮสต์ผ่าน `NoSandboxAdapter` เซิร์ฟเวอร์บอกว่าคุณอยู่กรณีใดในล็อกเริ่มต้นของมัน ตรวจสอบของตัวเองด้านล่าง

## ตัดสินว่าเอเจนต์พุชอะไรได้บ้าง

git push, GitHub, ตั๋วงาน และเครือข่าย ไม่มีสวิตช์รายเอเจนต์ แต่ละอย่างคือกฎการกระทำ:

| กฎ | ค่าเริ่มต้นในตัว | ครอบคลุม |
| -- | ---------------- | -------- |
| **พุชไปยังรีโมต** | ถามก่อน | ทุก `git push` ไปยัง GitHub จากอะแดปเตอร์ใดก็ได้ |
| **เปิด pull request** | ถามก่อน | เครื่องมือ pull request ของ Control Center `gh pr create` ใช้ไม่ได้ในการรัน |
| **อัปเดตหรือรวม pull request** | ถามก่อน | ความคิดเห็นของเอเจนต์บน pull request ของมัน การแก้ไขชื่อหรือคำอธิบาย และรีวิวที่เผยแพร่ ผ่านเครื่องมือของ Control Center `gh pr comment`, `gh pr edit`, `gh pr review`, `gh pr merge` และ `gh pr close` ใช้ไม่ได้ในการรัน |
| **เขียนไปยังตัวติดตามภายนอก** | ถามก่อน | การเขียนตั๋วงานผ่านเครื่องมือของ Control Center และ `gh issue` |
| **เข้าถึงเครือข่าย** | อนุญาต | แซนด์บ็อกซ์มีเครือข่ายหรือไม่ และเครื่องมือเว็บของฮาร์เนส |

1. ไปที่ **การตั้งค่า → เวิร์กสเปซ → สิทธิ์ของเอเจนต์**
2. เลือกขอบเขต — **เวิร์กสเปซ**, **เอเจนต์** หรือ **สเปซ** — แล้วเลือก **อนุญาต**,
   **ถามก่อน** หรือ **ปฏิเสธ** ในแถวของกฎ

กฎการพุชที่จำกัดตามสาขา เช่นกฎที่ปฏิเสธการพุชไป `main` ก็มีผลด้วย: ดู
[กฎคุม](/th-TH/คู่มือ/แนวคิด/กฎคุม/)

จุดตรวจสอบ: สั่งเอเจนต์ให้พุชสาขาหนึ่ง เมื่อตั้งเป็น **ถามก่อน** คุณจะได้คำขออนุมัติที่ระบุ
รีโปและ ref เมื่อตั้งเป็น **ปฏิเสธ** git จะพิมพ์
`! [remote rejected] <ref> (Control Center policy: …)`

แต่ละกฎไปถึงการรันอย่างไร:

- **การพุช** ถูกบังคับใช้ด้วยสิ่งที่การรันถืออยู่ โทเคน GitHub ของมันครอบคลุมรีโปเดียวของการรัน และพุชไม่ได้: อ่านเนื้อหาได้ และเมื่อสมาชิกที่รับผิดชอบพุชได้ ก็แสดงความคิดเห็นบน pull request ได้ การตั้งค่า git
  ของมันส่งทุกการพุชไปยัง GitHub ไปที่เกตเวย์ลูปแบ็กบน `cc_server` ซึ่งถามกฎก่อน แล้วจึง
  ส่งการพุชต่อด้วยโทเคนเขียนที่เอเจนต์ไม่เคยเห็น เกตเวย์ส่งต่อไปยังรีโปของ worktree เอง
  หรือรีโป GitHub ที่ลิงก์กับเวิร์กสเปซเท่านั้น สิ่งนี้เป็นจริงกับทุกอะแดปเตอร์
- **pull request และ issue จากเชลล์** ถูกจดจำจากบรรทัดคำสั่ง: ในเครื่องมือ `bash` ของ
  ฮาร์เนส และผ่านฮุกในเครื่องมือ `Bash` ของ Claude Code เอเจนต์ที่ซ่อนคำสั่ง (สคริปต์,
  `eval`, การเรียก API โดยตรง) เลี่ยงการตรวจนี้ได้ แต่เลี่ยงเกตเวย์การพุชไม่ได้
- **คีย์ตั๋วงาน** ไม่เคยถูกใส่ลงในแซนด์บ็อกซ์ เอเจนต์เขียนตั๋วงานผ่านเครื่องมือ MCP ของ
  Control Center ซึ่งถามกฎ
- **เครือข่าย** ถูกตัดสินครั้งเดียวตอนเริ่มรัน **ปฏิเสธ** ปิดเครือข่ายของแซนด์บ็อกซ์
  **อนุญาต** และ **ถามก่อน** คงไว้ให้เปิด และภายใต้ **ถามก่อน** เครื่องมือ `web_fetch` และ
  `web_search` ของฮาร์เนสยังถามทุกครั้งที่เรียก GitHub อยู่ในรายการขาออกที่อนุญาตเสมอ
  ตราบที่เครือข่ายเปิดอยู่

:::note[โทเคน GitHub ของการรันมาจากไหน]
โทเคนถูกออกให้การรันนี้จาก GitHub App ของเวิร์กสเปซ แอปของเซิร์ฟเวอร์เอง หรือ Control Center Connect
และจำกัดให้อยู่ในขอบเขตของสิ่งที่สมาชิกที่รับผิดชอบ (ผู้ร้องขอ หรือหากไม่มีคือเจ้าของเวิร์กสเปซ) ทำได้บนรีโปนั้น
มันไม่ใช่การลงชื่อเข้าใช้ของสมาชิกที่ส่งต่อทั้งชุด และไม่มีโทเคนสำรองใด ๆ เมื่อไม่สามารถออกโทเคนได้
การรันจะเริ่มโดยไม่มีโทเคน และหมายเหตุจะระบุเหตุผล
:::

## ตรวจสอบว่าการรันเอเจนต์ของคุณอยู่ในแซนด์บ็อกซ์หรือไม่

มีสองสิ่งตัดสินเรื่องนี้ ทั้งคู่อยู่บนเซิร์ฟเวอร์: ว่าโฮสต์มีแบ็กเอนด์ให้หรือไม่ และว่า `--sandbox` เปิดอยู่หรือไม่ ตรวจตามลำดับนั้น

1. ไปที่ **การตั้งค่า → เซิร์ฟเวอร์ → การวินิจฉัยและความเป็นส่วนตัว**
2. อ่านการ์ด **แซนด์บ็อกซ์** ข้อเท็จจริง **โฮสต์** คือเครื่องที่ `cc_server` รันอยู่ ไม่ใช่เครื่องที่คุณกำลังดูอยู่ ฟิลด์ **แบ็กเอนด์** แสดง **แซนด์บ็อกซ์เนทีฟ** (Seatbelt บน macOS, bubblewrap บน Linux และ WSL2) หรือ **ไม่แยก** ข้อเท็จจริง **มีผล** คือค่ากำหนดของอุปกรณ์นี้ ไม่ใช่การห่อที่เซิร์ฟเวอร์ใช้จริง
3. อ่านล็อกเริ่มต้นของเซิร์ฟเวอร์ มันพิมพ์หนึ่งในสามบรรทัดนี้เท่านั้น:
   - `agent sandbox ON` บวกกับบันทึกแบ็กเอนด์: การรันถูกห่อ
   - `no OS-native agent sandbox on this host` บวกกับคำแนะนำการติดตั้งเมื่อมี: เฉพาะการรันที่เจ้าของเซิร์ฟเวอร์รับผิดชอบเท่านั้นที่เริ่มทำงาน โดยไม่ถูกห่อ และการรันของคนอื่นจะถูกปฏิเสธ
   - `agent sandbox DISABLED by --sandbox off`: การรันของสมาชิกทุกคนเริ่มทำงาน โดยไม่ถูกห่อ
4. บรรทัดการเปิดเผยที่พิมพ์ตอนเริ่มทำงานบอกสิ่งเดียวกันเป็นคำเดียว: `sandbox=native`, `sandbox=off` หรือ `sandbox=unavailable`

`GET /healthz` ไม่รายงานสถานะแซนด์บ็อกซ์ ล็อกเริ่มต้นจึงเป็นการตรวจสอบ

เฉพาะเจ้าของเซิร์ฟเวอร์เท่านั้นที่ตัดสินใจรันโดยไม่มีแซนด์บ็อกซ์ หากต้องการทำเช่นนั้นสำหรับทุกคน ให้เริ่มเซิร์ฟเวอร์ด้วย `--sandbox off` หรือตั้ง `CC_SERVER_SANDBOX=off` เอเจนต์ของสมาชิกทุกคนจะรันโดยไม่ถูกจำกัดบนเครื่องนั้น ดังนั้นนี่คือการตัดสินใจเกี่ยวกับทุกคนที่ใช้เซิร์ฟเวอร์ ทำครั้งเดียวตอนบูต ค่าเริ่มต้นคือ `on`: ห่อทุกการรันเมื่อโฮสต์มีแบ็กเอนด์ และเมื่อไม่มี จะเริ่มเฉพาะการรันของเจ้าของ

มีสองสถานการณ์ที่ไม่เคยได้รับการห่อด้วยแซนด์บ็อกซ์เนทีฟ บน **Windows** การตรวจหาแบบเนทีฟจะรายงานว่าไม่มีให้ใช้เสมอ และไม่มีอะไรให้ติดตั้ง ดังนั้นจะเริ่มเฉพาะการรันของเจ้าของเซิร์ฟเวอร์ เว้นแต่เจ้าของจะใช้ `--sandbox off` แบ็กเอนด์ `microvm` แยกต่างหาก (เทอร์มินัลแบบโต้ตอบและริก) และถูกกั้นด้วยการตรวจหาบนรันไทม์ของมันเอง บน **Linux และ WSL2** ทั้ง `bwrap` และ `socat` ต้องอยู่บน `PATH`; หากไม่มี การตรวจหาจะรายงานว่าไม่มีให้ใช้และระบุชื่อแพ็กเกจที่ขาดไป และจะเริ่มเฉพาะการรันของเจ้าของเท่านั้น

บน Linux/WSL2 ที่ติดตั้ง bubblewrap แล้ว กลอบของไฟล์ลับในนโยบายมาตรฐานไม่สามารถบังคับใช้กับไฟล์ที่เอเจนต์สร้างขึ้นในภายหลังได้ ดังนั้นทุกการรันแบบเนทีฟจะล้มเหลวแทนที่จะเพิกเฉยต่อกฎอย่างเงียบ ๆ รวมถึงของเจ้าของด้วย การตรวจหาตอนบูตที่ผ่านจึงไม่ได้หมายความว่าการสั่งงานบน Linux จะเริ่มได้: ปัจจุบันเซิร์ฟเวอร์ Linux รันเอเจนต์ด้วย `--sandbox off` หรือโดยไม่มี bubblewrap สำหรับเจ้าของคนเดียว `--sandbox off` เป็นการเลือกปิดโดยเจตนาให้ไม่ถูกกักขอบ ไม่ใช่ขอบเขตความปลอดภัยทดแทน

## รู้ว่าโหมดหนึ่งห้ามอะไรไว้แล้ว

โหมดถูกจัดเก็บเป็นรายสเปซ และป้อนเข้าตัวแปลงคำตัดสินของกฎคุมในฐานะชั้น **พรีเซ็ตโหมด** สามในสี่โหมดเป็นอ่านอย่างเดียว และโหมดอ่านอย่างเดียวจะปฏิเสธคลาสผลกระทบสิบสองคลาสทันที:

| โหมด | Worktree | ถูกปฏิเสธโดยพรีเซ็ต |
| ------------------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **เอเจนต์** (`chat`) | เขียนได้ | ไม่มี — ค่าเริ่มต้นในตัวมีผล |
| **แผน** | อ่านอย่างเดียว | ลบไฟล์, เขียนนอก worktree, คอมมิต, พุช, เปิด PR, เผยแพร่หรือรวม, เขียนไปยังตัวติดตามภายนอก, ติดตั้งแพ็กเกจ, รันโปรเซส, เปลี่ยนโครงสร้างเวิร์กสเปซ, บูตหรือควบคุมเอนโคลเจอร์, รันคำสั่งบนโฮสต์ |
| **รีวิว** | อ่านอย่างเดียว | สิบสองคลาสเดิม ไม่ให้ผู้ใช้เลือก — ช่องเขียนข้อความมีเพียงเอเจนต์ แผน และประสานงาน |
| **ประสานงาน** | อ่านอย่างเดียว | สิบสองคลาสเดิม |

การเข้าถึงเครือข่ายและการเข้าถึงข้อมูลลับนั้น _ไม่_ ถูกปฏิเสธโดยโหมดอ่านอย่างเดียวโดยเจตนา: การค้นคว้าคือจุดหมายของมัน

## กำหนดให้ต้องอนุมัติก่อนการกระทำจะรัน

การอนุมัติเป็นคำตัดสินของกฎคุม ไม่ใช่การตั้งค่าแซนด์บ็อกซ์

1. ไปที่ **การตั้งค่า → เวิร์กสเปซ → สิทธิ์ของเอเจนต์**
2. ตั้งคลาสการกระทำเป็น **ถามก่อน** ที่ขอบเขตเวิร์กสเปซ เอเจนต์ หรือสเปซ

คำตัดสิน **ถามก่อน** จะขัดจังหวะการรันและถามคุณ เมื่อไม่มีผู้อนุมัติเชื่อมต่ออยู่ มันจะปิดเมื่อล้มเหลวและการกระทำนั้นถูกปฏิเสธ ดู[ตั้งค่ากฎคุม](/th-TH/คู่มือ/วิธีทำ/ตั้งค่ากฎคุม/) สำหรับลำดับการแปลงคำตัดสินทั้งหมด

## การแก้ปัญหา

### เอเจนต์พุชไม่ได้และฉันไม่ได้ห้ามมันเลย

ดูว่า git พิมพ์อะไรออกมา `Control Center policy: …` หมายความว่ากฎปฏิเสธการพุช หรือ
**ถามก่อน** ไม่ได้รับคำตอบ `… is not linked to this workspace` หมายความว่าเป้าหมายไม่ใช่
รีโปของ worktree เองและไม่ได้ลิงก์กับเวิร์กสเปซ
`Control Center has no GitHub credential that can push …` หมายความว่าไม่สามารถสร้างโทเคนสำหรับการพุชได้: ติดตั้งแอปบนรีโปนั้น หรือเชื่อม GitHub

### การรันเอเจนต์ของฉันถูกปฏิเสธด้วย “เซิร์ฟเวอร์นี้ไม่มีแซนด์บ็อกซ์”

การรันแสดง **เอเจนต์ต้องมีแซนด์บ็อกซ์บนเซิร์ฟเวอร์นี้** พร้อมข้อความ “เซิร์ฟเวอร์นี้ไม่มีแซนด์บ็อกซ์ ดังนั้นมีเพียงเจ้าของเท่านั้นที่รันเอเจนต์ที่นี่ได้ เจ้าของสามารถติดตั้งแซนด์บ็อกซ์หรือปิดการใช้แซนด์บ็อกซ์สำหรับทุกคนได้” โฮสต์ของเซิร์ฟเวอร์ไม่มีแซนด์บ็อกซ์ของ OS และบุคคลที่รับผิดชอบการรันนั้นไม่ใช่เจ้าของเซิร์ฟเวอร์ จึงไม่มีอะไรเริ่มทำงาน สำหรับตารางเวลา webhook หรือระบบอัตโนมัติอื่น บุคคลที่รับผิดชอบคือคนที่ระบบนั้นผูกไว้ ไม่ใช่ใครก็ตามที่กำลังดูอยู่

มีเพียงเจ้าของเซิร์ฟเวอร์เท่านั้นที่เปลี่ยนแปลงสิ่งนี้ได้ บน Linux และ WSL2 พวกเขาติดตั้ง `bubblewrap` และ `socat` แล้วรีสตาร์ตเซิร์ฟเวอร์ (แต่อ่านหมายเหตุของ Linux ด้านบนก่อน) บน Windows ไม่มีแบ็กเอนด์ให้ติดตั้ง อีกทางเลือกคือรีสตาร์ตเซิร์ฟเวอร์ด้วย `--sandbox off` ซึ่งรันเอเจนต์ของสมาชิกทุกคนโดยไม่ถูกจำกัดบนเครื่องนั้น

### การ์ดแซนด์บ็อกซ์รายงานว่าไม่มีแซนด์บ็อกซ์เนทีฟ

แสดงว่าการรันเอเจนต์บนโฮสต์นั้นไม่ถูกห่อด้วย Seatbelt หรือ bubblewrap: มีเพียงการรันของเจ้าของเซิร์ฟเวอร์เท่านั้นที่เริ่มทำงาน และขอบเขตที่เหลืออยู่คือสิ่งที่พวกเขามี บน Linux และ WSL2 ให้ติดตั้งเครื่องมือที่ขาดทั้งสองตัว (`sudo apt-get install bubblewrap socat`) แล้วรีสตาร์ตเซิร์ฟเวอร์ ล็อกเริ่มต้นจึงควรบอกว่าแซนด์บ็อกซ์เปิดอยู่ บน Windows ไม่มีแบ็กเอนด์เนทีฟให้ติดตั้ง จึงควรกระชับกฎคุมสำหรับการรันของเจ้าของเองแทน: ดู[ตั้งค่ากฎคุม](/th-TH/คู่มือ/วิธีทำ/ตั้งค่ากฎคุม/)

### เอเจนต์เข้าถึงไฟล์นอก worktree ของมัน

เครื่องมือตัวใดที่เข้าถึงมันเป็นตัวตัดสินว่านี่เป็นเรื่องที่คาดหมายได้หรือไม่

เครื่องมือไฟล์ในโปรเซสของฮาร์เนส (read, write, edit, apply patch, search, find, search_files) ทำงานในโปรเซสของเซิร์ฟเวอร์ จึงไม่มีโปรไฟล์แซนด์บ็อกซ์ใดใช้กับมัน — ขอบเขตของมันคือการจำกัดเส้นทางในตัวมันเองบวกกับกฎคุม คำสั่ง `bash` หรือ Claude Code CLI _ถูก_ ห่อที่ใดมีแบ็กเอนด์ และเช็กเอาต์ที่ลงทะเบียนไว้ของคุณเป็นเส้นทางที่ห้ามเขียนภายในที่ห่อนั้นในทุกโหมด รวมถึงรูปที่แปลงซิมลิงก์แล้วของมันด้วย (บน macOS เส้นทางที่เข้าถึงผ่าน `/tmp` หรือ `/var/folders` จะแปลงค่าอยู่ใต้ `/private` และทั้งสองรูปแบบถูกปฏิเสธ) ภายใต้ `--sandbox off` หรือสำหรับการรันของเจ้าของเองบนโฮสต์ที่ไม่มีแบ็กเอนด์ ไม่มีข้อใดนั้นใช้เลย ไม่ทางใดก็ทางหนึ่ง กฎคุมสามารถปฏิเสธ **เขียนนอก worktree** ได้ทันที
