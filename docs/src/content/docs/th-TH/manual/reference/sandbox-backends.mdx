:::caution[การรันจะอยู่ในแซนด์บ็อกซ์หรือไม่นั้นขึ้นอยู่กับโฮสต์]
`cc_server` ตัดสินครั้งเดียวตอนบูตว่าเอเจนต์รันบนโฮสต์นี้อย่างไร และการตัดสินนั้นมีผลจนกว่าจะรีสตาร์ต:

- **อยู่ในแซนด์บ็อกซ์** (`native`): การตรวจหาพบแบ็กเอนด์ และ `--sandbox` ไม่ใช่ `off` รอยต่อการสั่งงานทั้งสองถูกห่อ: Claude Code CLI ผ่านพอร์ตแซนด์บ็อกซ์ และ ACP บวกเครื่องมือ `bash` ของฮาร์เนสในตัวผ่านตัวจัดการแซนด์บ็อกซ์
- **ปิด** (`off`): เจ้าของเซิร์ฟเวอร์เริ่มด้วย `--sandbox off` เอเจนต์ของสมาชิกทุกคนรันโดยไม่มีการจำกัดขอบเขตบนเครื่องนี้ ไม่ว่าใครเป็นคนเริ่มก็ตาม
- **ไม่พร้อมใช้** (`unavailable`): แซนด์บ็อกซ์เปิดอยู่แต่การตรวจหาไม่พบแบ็กเอนด์ (**Windows เสมอ** และ Linux หรือ WSL2 ที่ไม่มี `bwrap` และ `socat`) การรันจะเริ่มก็ต่อเมื่อบุคคลที่รับผิดชอบการรันนั้นคือ[เจ้าของ](/th-TH/คู่มือ/แนวคิด/การอนุญาต/#เจ้าของเซิร์ฟเวอร์)เซิร์ฟเวอร์: คนที่ขอให้รัน หรือสำหรับระบบอัตโนมัติ คือคนที่มันผูกอยู่ การรันของคนอื่นจะถูกปฏิเสธก่อนมีการออกข้อมูลรับรอง การจองลีส หรือการเริ่มโปรเซส หากไม่มีเจ้าของที่บันทึกไว้ จะไม่มีการรันของใครเริ่มเลย

การรันที่ถูกปฏิเสธจะล้มเหลวด้วยรหัส `sandbox_unavailable` แอปแสดงเป็น **เอเจนต์ต้องมีแซนด์บ็อกซ์บนเซิร์ฟเวอร์นี้**: "เซิร์ฟเวอร์นี้ไม่มีแซนด์บ็อกซ์ ดังนั้นมีเพียงเจ้าของเท่านั้นที่รันเอเจนต์ที่นี่ได้ เจ้าของสามารถติดตั้งแซนด์บ็อกซ์หรือปิดการใช้แซนด์บ็อกซ์สำหรับทุกคนได้"

การรันที่เริ่มโดยไม่มีแซนด์บ็อกซ์ (ภายใต้ `off` หรือการรันของเจ้าของเองภายใต้ `unavailable`) จะรันตรงบนโฮสต์ ACP และเครื่องมือ `bash` ของฮาร์เนสยังสปอว์นพร้อมการชำระล้างสภาพแวดล้อม; Claude Code ผ่าน `NoSandboxAdapter` และสืบทอดสภาพแวดล้อมของโฮสต์ ขอบเขตที่เหลืออยู่คือ worktree ของการรันเอง (แบบ copy-on-write ที่ใดที่ `rift` ถูกส่งมาให้ใช้; `git worktree` บน Windows) โทเคนโฮสต์โค้ดแบบอ่านอย่างเดียวซึ่งผ่านนายหน้าต่อการเรียกใช้หนึ่งครั้งและถูกเพิกถอนเมื่อรื้อถอน การพุชที่ต้องผ่านกฎการพุชที่เกตเวย์การรันเอเจนต์ นโยบายคำสั่งรายโหมด [กฎคุมการกระทำ](/th-TH/คู่มือ/แนวคิด/กฎคุม/)แบบรวมศูนย์ (ปิดเมื่อล้มเหลว) การชำระล้างสภาพแวดล้อมบนเส้นทาง ACP และ `bash` ของฮาร์เนส และพื้นผิวเครื่องมือที่โหมดของมันอนุญาต

เครื่องมือไฟล์ในโปรเซสของฮาร์เนส (read, write, edit, apply patch, search, find, search_files) อยู่นอกแซนด์บ็อกซ์บนทุกโฮสต์: มันรันในโปรเซสของเซิร์ฟเวอร์ จึงมีเพียง `bash` เท่านั้นที่ถูกห่อ

โฮสต์ไม่เคยเป็นตัวถอยกลับสำหรับเซิร์ฟเวอร์ที่แซนด์บ็อกซ์เอเจนต์ หากเซิร์ฟเวอร์แซนด์บ็อกซ์เอเจนต์แต่ไม่มีแซนด์บ็อกซ์ให้การรัน เครื่องมือโปรเซสและคำสั่ง `bash` ของมันจะถูกปฏิเสธ ไม่ถูกเริ่มบนโฮสต์ ท่าทีเดียวกันนี้กำหนดโปรเซสเล็ก ๆ รอบ ๆ การรัน: ตัวช่วย ACP แบบครั้งเดียว (ชื่อการสนทนา, `/btw`, `/handoff`, `/goal`) และการทดสอบ golden ของ pull request ใน Review Studio รันในแซนด์บ็อกซ์เมื่อเซิร์ฟเวอร์แซนด์บ็อกซ์เอเจนต์ ไม่จำกัดขอบเขตภายใต้ `off` และภายใต้ `unavailable` รันเฉพาะคำขอที่เจ้าของเซิร์ฟเวอร์รับผิดชอบ มิฉะนั้นจะถูกข้าม
:::

## ภาพรวมแบ็กเอนด์

| แบ็กเอนด์     | ค่า     | แพลตฟอร์ม                                      | ความพร้อมใช้                                                                                                      |
| ----------- | --------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| VM ที่หุ้ม | `microvm` | macOS, Linux, Windows (ไฮเปอร์ไวเซอร์ microVM)    | ถูกกั้นด้วยการตรวจหาบนรันไทม์ของ microVM; ใช้กับเทอร์มินัลแบบโต้ตอบ — เชลล์รันอยู่ภายใน[ริก](/th-TH/คู่มือ/แนวคิด/ริก/) ไม่ใช่บนโฮสต์ |
| เนทีฟ      | `native`  | macOS (Seatbelt), Linux และ WSL2 (bubblewrap) | ตรวจหาตอนบูต; Linux ปฏิเสธการรันที่ต้องมีข้อปฏิเสธการเขียนตามกลอบชื่อไฟล์ ซึ่ง bubblewrap บังคับใช้ไม่ได้ |
| ไม่แยก      | `none`    | ทั้งหมด                                           | ค่าเริ่มต้นของการแยกวิเคราะห์และค่าเริ่มต้นของเทอร์มินัล การสั่งงานเอเจนต์ใช้มันภายใต้ `--sandbox off` และสำหรับการรันของเจ้าของเองเมื่อไม่มีแบ็กเอนด์ให้ใช้ |

`SandboxBackend.fromName` คืนค่า `none` สำหรับค่าที่จัดเก็บไว้เป็น null หรือที่ไม่รู้จัก

**`microvm` เป็นแบ็กเอนด์เดียวที่มีขอบเขตระดับเคอร์เนล** — งานที่รันอยู่ไม่ได้รันบนโฮสต์จริง ๆ มันไม่เคยเป็นตัวถอยกลับแบบเงียบในทิศทางใดเลย: การขอมันอย่างชัดเจนบนโฮสต์ที่บูต VM ไม่ได้จะล้มเหลวอย่างส่งเสียง (“ผมขอ VM แต่ได้แล็ปท็อปของผมเอง” คือการเสื่อมสภาพอย่างเดียวที่เอนโคลเจอร์รับไม่ได้) และมีเพียง *ค่าเริ่มต้นที่ไม่ระบุ* เท่านั้นที่ถอยลงไปใช้ `native` พร้อมบรรทัดล็อกที่บอกเช่นนั้น แบ็กเอนด์จริงของเซสชันจะถูกรายงานกลับไปยังไคลเอนต์และติดป้าย เทอร์มินัลจึงอ้างว่าถูกปิดล้อมอยู่ทั้งที่รันบนโฮสต์ไม่ได้ วงจรชีวิต อิมเมจ และการเชื่อมต่อขาออกของ VM เองมีอยู่ใน[เอกสารอ้างอิงริก](/th-TH/คู่มือ/อ้างอิง/ริก/)

**Windows ไม่มีแซนด์บ็อกซ์เนทีฟ** `NativeSandboxAdapter.probe` คืนค่า `available: false` บนทุกโฮสต์ที่ไม่ใช่ macOS หรือ Linux/WSL2 เซิร์ฟเวอร์ Windows จึงเป็น `unavailable`: เฉพาะการรันเอเจนต์ของเจ้าของเซิร์ฟเวอร์ที่เริ่มได้ โดยไม่มีการจำกัดขอบเขต และของคนอื่นจะถูกปฏิเสธ หากต้องการให้สมาชิกทุกคนรันเอเจนต์ที่นั่น เจ้าของต้องเริ่มเซิร์ฟเวอร์ด้วย `--sandbox off` ซึ่งรันทั้งหมดโดยไม่มีการจำกัดขอบเขต แบ็กเอนด์ `microvm` แยกต่างหาก: มันถูกกั้นด้วยการตรวจหาบนรันไทม์ของ microVM และใช้กับเทอร์มินัลแบบโต้ตอบและริก ไม่ใช่กับการห่อ `bash` บนโฮสต์

## ผลการตรวจหา

การตรวจหาคือสิ่งที่กั้นการบังคับใช้ มันรันครั้งเดียว ตอนบูตเซิร์ฟเวอร์

| โฮสต์                                   | `available` | บันทึก / คำแนะนำ                                                               |
| -------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS                                  | `true`      | `sandbox-exec` (Seatbelt) — การแยกตัวระดับเนมสเปซ ไม่มีขอบเขตระดับเคอร์เนล       |
| Linux หรือ WSL2 ที่มี `bwrap` และ `socat` | `true`      | bubblewrap — การแยกตัวระดับเนมสเปซ ไม่มีขอบเขตระดับเคอร์เนล                      |
| Linux หรือ WSL2 ที่ขาดเครื่องมือตัวใดตัวหนึ่ง      | `false`     | `requiresInstall: true` พร้อมคำแนะนำการติดตั้งที่ระบุชื่อแพ็กเกจที่ขาดไป |
| แพลตฟอร์มอื่นใด                     | `false`     | แซนด์บ็อกซ์เนทีฟไม่ถูกเสนอบนแพลตฟอร์มนี้                            |

เซิร์ฟเวอร์บันทึกผลลัพธ์ไว้ในบรรทัดเริ่มต้นบรรทัดเดียว: `agent sandbox ON` บวกกับบันทึก; `no OS-native agent sandbox on this host` บวกกับคำแนะนำ ซึ่งเพิ่มว่ามีเพียงการรันที่เจ้าของเซิร์ฟเวอร์รับผิดชอบเท่านั้นที่จะเริ่ม; หรือ `agent sandbox DISABLED by --sandbox off` บรรทัดการเปิดเผยที่พิมพ์ตอนเริ่มมีการตัดสินเดียวกันเป็น `sandbox=native`, `sandbox=off` หรือ `sandbox=unavailable` `GET /healthz` ไม่มีฟิลด์แซนด์บ็อกซ์

`--sandbox` / `CC_SERVER_SANDBOX` รับค่า `on` (ค่าเริ่มต้น) หรือ `off` `on` ห่อทุกการรันเมื่อโฮสต์มีแบ็กเอนด์ให้ใช้ และรับเฉพาะการรันของเจ้าของเมื่อไม่มี `off` รันเอเจนต์ของสมาชิกทุกคนโดยไม่มีการจำกัดขอบเขตบนโฮสต์นี้ มันเป็นทางเลือกของเจ้าของสำหรับทุกคน ไม่ใช่การตั้งค่าต่อการรัน

## แบ็กเอนด์เนทีฟ

### macOS: Seatbelt

ใช้กลไกแซนด์บ็อกซ์ Seatbelt ของ Apple (ระบบเดียวกับที่ macOS App Sandbox ใช้)

โปรไฟล์ที่สร้างขึ้น **ผ่อนปรนโดยค่าเริ่มต้น** (`(allow default)`) แล้วเจาะออกเป็นข้อปฏิเสธ เพราะโปรไฟล์ที่ปฏิเสธโดยค่าเริ่มต้นทั้งหมดจะทำให้เชลล์แบบโต้ตอบใช้ไม่ได้ — มีการเรียก dyld, XPC และ Mach มากเกินกว่าจะแจกแจงได้ ผลในทางปฏิบัติคือเอเจนต์ยังอ่านโฮสต์ส่วนใหญ่ได้; เช็กเอาต์ที่ลงทะเบียนไว้ของคุณได้รับการปกป้องด้วยข้อปฏิเสธการเขียนและการเปลี่ยนชื่อที่ระบุชัดเจน ไม่ใช่ด้วยการมองไม่เห็น

- **การอ่านระบบไฟล์**: ถูกปฏิเสธสำหรับเส้นทางลับ (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` และส่วนที่เหลือของชุดปฏิเสธการอ่าน)
- **การเขียนระบบไฟล์**: รีเซ็ตเป็นปฏิเสธ แล้วจึงมีข้อยกเว้นแบบอนุญาตสำหรับพาธย่อยที่ระบุชัดเจน โดยเส้นทางที่ห้ามตายตัว (ไฟล์ rc ของเชลล์, `.git/hooks`, การกำหนดค่า Claude, เช็กเอาต์ที่ได้รับการปกป้อง) ถูกบล็อกแม้จะอยู่ภายในรูทที่เขียนได้ `file-write-unlink` ถูกปฏิเสธบนทุกเส้นทางที่ถูกปฏิเสธและบรรพบุรุษของมัน การเปลี่ยนชื่อจึงข้ามข้อปฏิเสธการเขียนไม่ได้
- **โปรเซส**: `process-exec` ปฏิเสธไบนารีที่อันตรายเสมอ บวกกับการบล็อกการเรียกใช้ทุกอย่างจากไดเรกทอรีที่เขียนได้ โฟลเดอร์ติดตั้งเครื่องมือที่รู้จักใต้โฮมไดเรกทอรีของคุณ (แคชของ corepack, npx และ `pnpm dlx`, ตัวจัดการเวอร์ชัน node, เบราว์เซอร์ Playwright, rustup และ cargo, Go, fvm และแคช pub, pyenv, uv และ pipx, rbenv, sdkman, mise, asdf และ `~/.local/bin`) ถูกเปิดให้เข้าถึงอีกครั้งภายใต้การบล็อกนั้น ไดเรกทอรีชั่วคราวที่ใช้ร่วมกันก็ถูกบล็อกด้วย แต่ละเซสชันจะได้ `TMPDIR` ส่วนตัวภายใต้ `/private/tmp` แทน ซึ่งโปรแกรมที่สร้างขึ้นเอง (ไบนารี `go test` หรือการ build ด้วย cargo) รันได้ การปฏิเสธไบนารีที่อันตรายเสมอถูกนำไปใช้หลังการอนุญาตเหล่านี้
- **เครือข่าย**: จำกัดไว้ที่พอร์ตพร็อกซีในโปรเซสบวก DNS — ลูปแบ็กไม่ถูกอนุญาตแบบครอบคลุม และไม่อนุญาตให้รับฟังด้วย TCP ยูนิกซ์ซ็อกเก็ตอนุญาตเฉพาะภายใน `TMPDIR` ส่วนตัวของเซสชันเท่านั้น ซึ่งครอบคลุมเครื่องมืออย่าง tsx และ Chrome ที่เก็บ IPC ซ็อกเก็ตไว้ตรงนั้น ส่วน SSH agent และซ็อกเก็ตอื่น ๆ ยังเข้าไม่ถึง พร็อกซีบังคับใช้รายการที่อนุญาตระดับโดเมนต่อเซสชัน (ดู[เครือข่ายขาออก](#เครือข่ายขาออก))
- **การกำหนดค่า**: โปรไฟล์ถูกสร้างต่อการเรียกใช้หนึ่งครั้งจาก `SandboxSpec`
- **คำสั่งของเซิร์ฟเวอร์เอง**: ไม่มีโฟลเดอร์ย่อยโดยตรงของโฟลเดอร์ที่เซิร์ฟเวอร์รันโปรแกรมจาก (ทุกรายการใน `PATH` และโฟลเดอร์เครื่องมือรายผู้ใช้ที่พบบ่อย เช่น `~/.local/bin` โดยลิงก์ตัวจัดการเวอร์ชันอย่าง `~/fvm/default` จะถูกแก้ไปยังเป้าหมายจริง) ที่สร้าง แทนที่ ลบ หรือเปลี่ยนชื่อได้ และแพ็กเกจที่ติดตั้งซึ่งคำสั่งที่ลิงก์ชี้ไปก็เช่นกัน ดู[โฟลเดอร์คำสั่งของเซิร์ฟเวอร์](#โฟลเดอร์คำสั่งของเซิร์ฟเวอร์)
- **ไฟล์เริ่มต้นระบบ**: ทุกพาธในโฮมที่โปรไฟล์ปฏิเสธการอ่านก็ถูกปฏิเสธการเขียนด้วย และไฟล์เริ่มต้นของเชลล์และเซสชันของผู้ใช้เซิร์ฟเวอร์ (`.zshenv`, `.zlogin`, `.bash_login`, การตั้งค่า fish, ยูนิต systemd ของผู้ใช้, รายการเปิดอัตโนมัติ และอื่น ๆ ที่คล้ายกัน) ถูกปฏิเสธการเขียนในทุกโหมด

สิ่งที่ต้องมี:

- `sandbox-exec` (`/usr/bin/sandbox-exec`) ซึ่งมีอยู่ในการติดตั้ง macOS ทุกเครื่อง — ไม่ต้องมีเครื่องมือเพิ่มเติม

### Linux: bubblewrap

ใช้ bubblewrap (`bwrap`) เพื่อสร้างเมานต์เนมสเปซและเนมสเปซ PID

- **ระบบไฟล์**: สร้างเมานต์เนมสเปซที่มองเห็นเฉพาะเส้นทางที่ถูกผูกเข้ามา
- **เครือข่าย**: รันในเนมสเปซเครือข่ายที่ไม่ใช้ร่วมกัน; ทราฟฟิกไปถึงพร็อกซีของโฮสต์ผ่านบริดจ์ยูนิกซ์ซ็อกเก็ตของ `socat`
- **โปรเซส**: การแยกตัวด้วยเนมสเปซ PID
- **คำสั่งของเซิร์ฟเวอร์เองและไฟล์เริ่มต้นระบบ**: การป้องกันเดียวกับบน macOS แสดงออกเป็นการผูกของ bubblewrap ยังไม่ได้ตรวจสอบบน Linux และโฟลเดอร์คำสั่งที่หายไปที่นั่นยังอาจถูกสร้างขึ้นได้

สิ่งที่ต้องมี:

- ติดตั้ง `bubblewrap` และ `socat` (`sudo apt-get install bubblewrap socat` บน Debian/Ubuntu)
- การรองรับเนมสเปซของเคอร์เนล (มาตรฐานบน Linux สมัยใหม่)

Bubblewrap ซ่อนเส้นทางที่มีอยู่แล้วได้ แต่ห้ามไฟล์ `.env`, `*.key` หรือ `*.pem` *ใหม่* ภายในบินด์ที่เขียนได้ไม่ได้ นโยบายการสั่งงานมาตรฐานต้องมีข้อปฏิเสธตามกลอบชื่อไฟล์เหล่านี้ การสั่งงานเอเจนต์แบบเนทีฟบน Linux/WSL2 ตอนนี้จึง **ปิดเมื่อล้มเหลวแม้การตรวจหาจะพบ bubblewrap** มันไม่รันด้วยนโยบายที่อ่อนกว่าอย่างเงียบ ๆ ต้องมีแบ็กเอนด์ที่มีกฎชื่อไฟล์ตอนสร้างจึงจะคืนการสั่งงานแบบเนทีฟบน Linux ได้ การปิดแซนด์บ็อกซ์เป็นการเลือกปิดโดยเจตนาให้ไม่ถูกกักขอบ ไม่ใช่ทางแก้ที่เทียบเท่ากัน

ในทางปฏิบัติ เซิร์ฟเวอร์ Linux หรือ WSL2 รันเอเจนต์วันนี้ได้สองวิธี เมื่อเริ่มด้วย `--sandbox off` มันรันเอเจนต์ของสมาชิกทุกคนโดยไม่มีการจำกัดขอบเขต หากไม่ได้ติดตั้ง bubblewrap หรือ `socat` มันจะเป็น `unavailable` และรันเฉพาะเอเจนต์ของเจ้าของเซิร์ฟเวอร์โดยไม่มีการจำกัดขอบเขต เมื่อติดตั้งทั้งสองและเปิดแซนด์บ็อกซ์ การรันทุกครั้งจะล้มเหลวแบบปิด รวมถึงของเจ้าของด้วย

## โฟลเดอร์คำสั่งของเซิร์ฟเวอร์

เซิร์ฟเวอร์ค้นหาโฟลเดอร์ทั้งหมดที่มันรันโปรแกรมจากครั้งเดียวตอนเริ่ม: แต่ละรายการของ `PATH` โฟลเดอร์เครื่องมือรายผู้ใช้ที่มันตรวจ (เช่น `~/.local/bin`, `~/.bun/bin` และโฟลเดอร์ global ของ npm, yarn และ pnpm) และโฟลเดอร์จริงเบื้องหลังลิงก์ทุกตัวบนเส้นทาง (ลิงก์ตัวจัดการเวอร์ชันอย่าง `~/fvm/default` หรือค่าเริ่มต้นของ fnm) ภายในแซนด์บ็อกซ์ เอเจนต์ไม่สามารถเพิ่ม แทนที่ ลบ หรือเปลี่ยนชื่อคำสั่งในโฟลเดอร์เหล่านั้น ลิงก์ที่นำไปยังคำสั่งนั้น หรือแพ็กเกจที่ติดตั้งซึ่งคำสั่งที่ลิงก์ชี้ไป และเปลี่ยนชื่อโฟลเดอร์เหนือมันไม่ได้ มิฉะนั้นการรันที่อยู่ในแซนด์บ็อกซ์อาจวางโปรแกรมที่เซิร์ฟเวอร์หรือคนนั้นจะเริ่มในภายหลังนอกแซนด์บ็อกซ์ได้

สิ่งที่เปลี่ยนสำหรับการรัน:

- การติดตั้ง global จากการรันที่อยู่ในแซนด์บ็อกซ์ล้มเหลวด้วย "Operation not permitted": `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install` และ `cargo install`, `go install` หรือ `dart pub global activate` เมื่อโฟลเดอร์ bin ของมันอยู่บน `PATH` ของเซิร์ฟเวอร์
- การสลับเวอร์ชันเริ่มต้นล้มเหลวในลักษณะเดียวกัน (`fnm default`, `nvm alias default`, `fvm global`) และเครื่องมือที่อัปเดตตัวเองในที่เดิมก็เช่นกัน
- การติดตั้งเฉพาะโปรเจกต์ (`node_modules/.bin`), `npx`, `pnpm dlx`, ตัวจัดการแพ็กเกจที่ corepack จัดการ, แคช SDK และการ build ปกติยังทำงานได้

หากต้องการให้เอเจนต์ใช้เครื่องมือ global ให้ติดตั้งบนเซิร์ฟเวอร์เอง ในฐานะผู้ใช้ของเซิร์ฟเวอร์ แล้วรีสตาร์ตเซิร์ฟเวอร์เพื่อให้คำสั่งใหม่ได้รับการป้องกันด้วย หรือติดตั้งในโปรเจกต์ คำสั่งที่ติดตั้งหลังจากเซิร์ฟเวอร์เริ่มจะได้รับการป้องกันเต็มที่ตั้งแต่การเริ่มครั้งถัดไปเท่านั้น

บังคับใช้และทดสอบแล้วบน macOS บน Linux กฎเดียวกันเป็นการผูกของ bubblewrap ที่ยังไม่ได้ตรวจสอบ Windows ไม่มีแซนด์บ็อกซ์

## แบ็กเอนด์ที่ไม่แยก

ไม่มีการแซนด์บ็อกซ์ โปรเซสรันบนโฮสต์โดยตรงด้วยการเข้าถึงระบบไฟล์ เครือข่าย และโปรเซสของโฮสต์ ACP และเครื่องมือ `bash` ของฮาร์เนสยังได้รับการชำระล้างสภาพแวดล้อมและนโยบายคำสั่ง; Claude Code ผ่าน `NoSandboxAdapter` สืบทอดสภาพแวดล้อมของโฮสต์ การสั่งงานเอเจนต์ใช้มันสำหรับทุกการรันภายใต้ `--sandbox off` และบนโฮสต์ที่ไม่มีแบ็กเอนด์ให้ใช้สำหรับการรันของเจ้าของเองเท่านั้น การรันของคนอื่นจะถูกปฏิเสธที่นั่น สำหรับเทอร์มินัลมันคือเชลล์ของโฮสต์ ซึ่งเฉพาะเจ้าของเซิร์ฟเวอร์เท่านั้นที่เปิดได้

## เทอร์มินัลที่โฮสต์บนเซิร์ฟเวอร์

เทอร์มินัลที่โฮสต์บนเซิร์ฟเวอร์เปิดเชลล์ของโฮสต์ได้เฉพาะสำหรับ[เจ้าของ](/th-TH/คู่มือ/แนวคิด/การอนุญาต/#เจ้าของเซิร์ฟเวอร์)ของเซิร์ฟเวอร์ คนอื่นจะได้เทอร์มินัลในแซนด์บ็อกซ์ พร้อมขีดจำกัดของเอเจนต์ ในไดเรกทอรีของเวิร์กสเปซนั้นเอง

วิธีเลือกแบ็กเอนด์สำหรับเซสชัน:

| ขอ | เจ้าของเซิร์ฟเวอร์ | คนอื่น |
| --- | --- | --- |
| ไม่ระบุ | แบ็กเอนด์เริ่มต้นของเซิร์ฟเวอร์ | ค่าเริ่มต้น โดยแทนที่ `none` ด้วย `native` |
| `none` (เชลล์ของโฮสต์) | เชลล์ของโฮสต์ | ถูกปฏิเสธ: เชลล์ของโฮสต์รันบนเซิร์ฟเวอร์โดยไม่มีแซนด์บ็อกซ์ |
| `native` | แซนด์บ็อกซ์เนทีฟ โปรไฟล์เจ้าของ | แซนด์บ็อกซ์เนทีฟ โปรไฟล์เอเจนต์ |
| `microvm` | VM ที่หุ้ม | VM ที่หุ้ม |
| ชื่อที่ไม่รู้จัก | ถูกปฏิเสธ | ถูกปฏิเสธ |

- **โปรไฟล์เจ้าของ** `$HOME` และไดเรกทอรีทำงานของเซสชันเขียนได้ เครือข่ายเปิด และ `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` และ `~/Library/Keychains` ถูกปฏิเสธการอ่าน
- **โปรไฟล์เอเจนต์** (`memberTerminalSandboxConfig`) นโยบายเดียวกับที่เอเจนต์ในเวิร์กสเปซนั้นรันภายใต้: การเขียนอยู่ในไดเรกทอรีทำงาน ไดเรกทอรีรันส่วนตัว `/tmp` และส่วนของ `$HOME` ที่เอเจนต์เขียนได้; ความลับถูกปฏิเสธการอ่าน; เครือข่ายคือรายการที่อนุญาตขาออกของเอเจนต์; โปรแกรมรันได้เฉพาะจากไดเรกทอรีทำงานและชุดเครื่องมือที่ติดตั้งไว้
- เทอร์มินัลจะเปิดได้เฉพาะภายในไดเรกทอรีของเวิร์กสเปซนั้นเอง ไดเรกทอรีทำงานที่อยู่นอกนั้นจะถูกปฏิเสธ ไม่ถูกสลับไปเป็นอีกที่หนึ่ง
- เฉพาะคนที่เปิดเทอร์มินัลเท่านั้นที่อ่าน พิมพ์ใส่ ปรับขนาด หรือปิดมันได้ สำหรับคนอื่น id ของมันจะดูเหมือนไม่รู้จัก
- `microvm` ที่ขอโดยชัดแจ้งบนโฮสต์ที่ไม่มี rig service จะล้มเหลวแทนการถอยกลับ ค่าเริ่มต้น `microvm` บนโฮสต์เช่นนั้นจะลดลงเป็น `native` และแจ้งไว้ในล็อก

โทเคนอ่านอย่างเดียวและเกตเวย์การพุชไม่ใช้กับเทอร์มินัล: นั่นเป็นเรื่องของการสั่งงาน หากการห่อไม่รองรับ เซสชันจะล้มเหลว แทนที่จะแสดงป้ายแซนด์บ็อกซ์บนเซสชันเชลล์ของโฮสต์

## เครือข่ายขาออก

เมื่อแซนด์บ็อกซ์ถูกเรียกใช้ การเข้าถึงเครือข่ายขาออกถูกบังคับใช้ด้วยพร็อกซีในโปรเซส ไม่ใช่ด้วยกฎไฟร์วอลล์ของเคอร์เนล การรันที่ไม่ได้แซนด์บ็อกซ์ (ทุกการรันภายใต้ `--sandbox off` หรือการรันของเจ้าของบนโฮสต์ที่ไม่มีแบ็กเอนด์) ไม่ได้รับสิ่งนี้เลย: โปรเซสที่มันสปอว์นจะเข้าถึงเครือข่ายได้เหมือนที่ผู้ใช้เซิร์ฟเวอร์ทำ

- รันไทม์แซนด์บ็อกซ์รันพร็อกซี HTTP/HTTPS และพร็อกซี SOCKS5 บน `127.0.0.1` ภายในโปรเซส `cc_server`, **หนึ่งคู่ต่อเซสชันที่ถูกจำกัด** (`http_proxy.dart`, `socks_proxy.dart`) การรันพร้อมกันไม่ใช้คู่ร่วมกัน
- โปรเซสที่อยู่ในแซนด์บ็อกซ์ได้รับตัวแปรสภาพแวดล้อมของพร็อกซี (`HTTP_PROXY`/`HTTPS_PROXY` → พร็อกซี HTTP, `ALL_PROXY` → พร็อกซี SOCKS; `GIT_SSH_COMMAND` ทำให้ git-over-SSH ผ่านพร็อกซี SOCKS) บน Linux เนมสเปซเครือข่ายไม่ถูกใช้ร่วมกัน พร็อกซีจึงเป็นทางออกเดียว; บน macOS แซนด์บ็อกซ์ใช้ลูปแบ็กของโฮสต์ร่วมกันและคุยกับพร็อกซีโดยตรง
- โฮสต์เป้าหมายของการเชื่อมต่อแต่ละครั้งถูกจับคู่กับรายการที่อนุญาตระดับโดเมนของเซสชัน; อะไรนอกนั้นถูกปฏิเสธ มีไวลด์การ์ดสองรูปแบบ แต่ละรูปแบบมี `*` ตัวเดียวพอดี: รูปแบบที่ขึ้นต้นด้วย `*.example.com` จับคู่ซับโดเมนใดก็ได้ (รวม `a.b.example.com`) แต่ไม่ใช่โดเมนหลักเอง; รูปแบบป้ายกลางอย่าง `bedrock.*.amazonaws.com` จับคู่พอดีหนึ่งเลเบล (`bedrock.us-east-1.amazonaws.com` ไม่ใช่ `bedrock.evil.attacker.amazonaws.com`)
- รายการที่อนุญาตถูกแปลงค่าต่อเซสชันจากฐานที่คัดสรรไว้ (`kBaselineAllowedDomains`: ผู้ให้บริการ LLM, โฮสติ้ง Git, รีจิสทรีแพ็กเกจ) บวกโดเมน GitHub (`kGithubDomains`) บวก `SandboxSpec.egressAllowlist` เส้นทางการสั่งงานไม่เคยส่งรายการ `egressAllowlist` เพิ่มเติมมา ดังนั้นในทางปฏิบัติทุกการรันจะได้ฐานบวก GitHub
- รายการที่ถูกปฏิเสธแบบตายตัว (`kBaselineDeniedDomains`: ปลายทางเมทาดาทาของคลาวด์, จุดรับส่งเทเลเมตรี) มาก่อนการอนุญาตทั้งหมด
- `networkEnabled: false` ยังเริ่มพร็อกซีต่อเซสชัน แต่รายการที่อนุญาตว่างเปล่า ทุกการเชื่อมต่อขาออกจึงถูกปฏิเสธ การสั่งงานตั้งค่านี้ตอนเริ่มรันจากกฎ **เข้าถึงเครือข่าย**: ปฏิเสธจะปิดเครือข่าย อนุญาตและถามก่อนคงไว้ให้เปิด

## SandboxSpec

สเปกที่ส่งให้ `SandboxPort.launch`:

| ฟิลด์             | ชนิด                                        | คำอธิบาย                                                                                                                                 |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | ตัวระบุเซสชันที่คงที่ (โดยทั่วไปคือไอดีสเปซ)                                                                                          |
| `workspaceId`     | `String`                                    | ไอดีเวิร์กสเปซเจ้าของ                                                                                                                         |
| `agentId`         | `String?`                                   | เอเจนต์ที่ผูกกับแซนด์บ็อกซ์อยู่ในขณะนี้ หากมี                                                                                                |
| `bindMounts`      | `List<SandboxBindMount>`                    | การเมานต์โฮสต์→เกสต์; แซนด์บ็อกซ์มองเห็นเฉพาะเส้นทางโฮสต์ที่ระบุไว้ที่นี่                                                                         |
| `networkEnabled`  | `bool` (ค่าเริ่มต้น `true`)                     | ตั้งตอนสั่งงานจากกฎการส่งออกเครือข่าย (ปิดเฉพาะเมื่อตัดสินเป็นปฏิเสธ) เมื่อปิด พร็อกซีต่อเซสชันยังเริ่มทำงานแต่รายการที่อนุญาตว่างเปล่า ทุกการเชื่อมต่อขาออกจึงถูกปฏิเสธ |
| `egressAllowlist` | `List<String>` (ค่าเริ่มต้น `[]`)               | โดเมนขาออกที่อนุญาตเพิ่มเติม; รองรับไวลด์การ์ด (`*.example.com` บวกแบบป้ายกลางหนึ่งเลเบล) การสั่งงานไม่เคยใส่ค่านี้ การรันที่ถูกห่อจึงได้ฐานที่คัดสรรไว้บวกโดเมน GitHub |
| `guestWorkdir`    | `String?`                                   | ไดเรกทอรีทำงานเริ่มต้นภายในแซนด์บ็อกซ์; การเรียก `exec` แต่ละครั้งเขียนทับได้                                                       |
| `mode`            | `Mode` (ค่าเริ่มต้น `chat`)                     | กำหนดกฎการเขียนระบบไฟล์: `chat` ทำให้การเมานต์แบบผูกเขียนได้; `review`, `plan` และ `orchestrate` เป็นอ่านอย่างเดียว                      |
| `protectedPaths`  | `List<String>` (ค่าเริ่มต้น `[]`)               | เส้นทางโฮสต์ที่ต้องไม่เขียนได้ภายในแซนด์บ็อกซ์ในโหมดใดเลย                                                                      |
| `runnerStateDirs` | `List<String>` (ค่าเริ่มต้น `[]`)               | ไดเรกทอรีโฮสต์ที่ตัวรันเก็บสถานะของตัวเองไว้ เขียนได้ในทุกโหมด (`CLAUDE_CONFIG_DIR` ที่ Control Center จัดการคือตัวปัจจุบัน) |
| `execGrantRoots`  | `List<String>` (ค่าเริ่มต้น `[]`)               | โครงไดเรกทอรีที่ผู้ปฏิบัติงานอนุมัติ ซึ่งเปิดการบล็อก exec ในไดเรกทอรีที่เขียนได้กลับคืนบน macOS Linux ไม่สนใจค่าเหล่านี้ — bwrap ไม่มีการบล็อก exec ของ `$HOME` ให้เปิดกลับคืน |

`protectedPaths` เก็บเช็กเอาต์รีโปที่ลงทะเบียนต้นฉบับ ซึ่งแปลงค่าต่อการสั่งงานหนึ่งครั้งจากรีโปของเวิร์กสเปซ เอเจนต์ทำงานใน worktree แบบ copy-on-write ต่อการสนทนาเท่านั้น ต้นฉบับจึงต้องไม่เขียนได้จากภายในแซนด์บ็อกซ์ — บน macOS การอนุญาตเขียน `$HOME` แบบครอบคลุมของ Seatbelt จะทำให้มันยังเขียนได้ผ่าน `bash` พวกมันเข้าร่วมชุดปฏิเสธการเขียนข้อมูลลับในทุกโหมด รวมถึง `chat`

เส้นทางที่ถูกปฏิเสธการอ่านและปฏิเสธการเขียนทุกเส้นทางถูกปล่อยออกมาทั้งในรูปตามตัวอักษรและรูปที่แปลงซิมลิงก์แล้ว เคอร์เนลจับคู่กฎปฏิเสธกับเส้นทางที่แปลงค่าแล้ว กฎที่เขียนกับเส้นทางที่เป็นซิมลิงก์จึงไม่เคยทำงาน — และบน macOS นั่นคือกรณีปกติมากกว่ากรณีพิเศษ เพราะ `/tmp` แปลงค่าเป็น `/private/tmp` และ `/var/folders/…` เป็น `/private/var/folders/…` รายการที่มี `*` หรือ `?` ถูกถือเป็นกลอบและปล่อยไว้ตามเดิม; เส้นทางที่แปลงค่าไม่ได้จะถูกเก็บตามที่เขียนไว้

## SandboxBindMount

| ฟิลด์       | ชนิด                     | คำอธิบาย                                                                                             |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `hostPath`  | `String`                 | เส้นทางแบบสัมบูรณ์บนโฮสต์                                                                               |
| `guestPath` | `String`                 | เส้นทางภายในแซนด์บ็อกซ์ (กับแซนด์บ็อกซ์เนทีฟ มันเท่ากับ `hostPath`; เก็บไว้เพื่อความสมมาตรของอะแดปเตอร์) |
| `readOnly`  | `bool` (ค่าเริ่มต้น `false`) | เมานต์แบบอ่านอย่างเดียวเมื่อเป็น true                                                                               |

## SandboxHandle

คืนค่าจาก `SandboxPort.launch`:

| ฟิลด์       | ชนิด                   | คำอธิบาย                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | ตัวระบุเซสชัน                                                       |
| `backend`   | `SandboxBackend`       | แบ็กเอนด์ใดกำลังทำงานอยู่                                                 |
| `state`     | `SandboxState`         | สถานะวงจรชีวิต                                                          |
| `error`     | `Object?`              | ถูกตั้งค่าเมื่อ `state` เป็น `error`                                              |
| `details`   | `Map<String, Object?>` | การบันทึกภายในของอะแดปเตอร์ (ไดเรกทอรีทำงาน, PID, เส้นทางโปรไฟล์ ฯลฯ) |

### SandboxState

| สถานะ       | คำอธิบาย                                 |
| ----------- | ------------------------------------------- |
| `created`   | สร้างสเปกแล้วแต่ VM ยังไม่เริ่ม |
| `warm`      | กำลังทำงานและพร้อมรับคำสั่ง exec          |
| `active`    | กำลังรันคำสั่งอยู่               |
| `suspended` | หยุดชั่วคราว / เช็กพอยต์ลงดิสก์เพื่อประหยัด RAM   |
| `destroyed` | รื้อถอนแล้ว; แฮนเดิลใช้ไม่ได้อีกต่อไป    |
| `error`     | การเรียกใช้ล้มเหลว — ดู `SandboxHandle.error`   |

## เหตุการณ์ของแซนด์บ็อกซ์

| ชนิดเหตุการณ์  | คำอธิบาย                                                  |
| ----------- | ------------------------------------------------------------ |
| `stdout`    | เอาต์พุตมาตรฐานจากแซนด์บ็อกซ์                             |
| `stderr`    | ข้อผิดพลาดมาตรฐานจากแซนด์บ็อกซ์                              |
| `exit`      | โปรเซสแซนด์บ็อกซ์ออกแล้ว (พก `exitCode` มาด้วย)                  |
| `starting`  | แซนด์บ็อกซ์กำลังเริ่มทำงาน                                       |
| `ready`     | แซนด์บ็อกซ์พร้อมรับการเรียก exec                        |
| `killed`    | โปรเซสถูกลงมือฆ่าโดยโฮสต์ (OOM, หมดเวลา, หยุดด้วยมือ)       |
| `violation` | นโยบายแซนด์บ็อกซ์ถูกละเมิด (พก `SandboxViolation` มาด้วย) |

## SandboxViolation

| ฟิลด์                 | ชนิด      | คำอธิบาย                                                                |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action`              | `String`  | คำกริยาที่ถูกปฏิเสธ (เช่น `file-read*`, `network-outbound`)                    |
| `target`              | `String`  | เส้นทางหรือโฮสต์ที่เป็นเป้าหมายของการดำเนินการที่ถูกปฏิเสธ                   |
| `raw`                 | `String?` | บรรทัดล็อกดิบ มีประโยชน์สำหรับดีบัก                                         |
