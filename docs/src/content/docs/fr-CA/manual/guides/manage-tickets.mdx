Ce guide montre comment créer et gérer des tickets.

## Créer un ticket

### Depuis l’interface

1. Cliquez sur **Tickets** dans la barre latérale de l’espace de travail.
2. Appuyez sur **Nouveau ticket**.
3. Remplissez les champs suivants :
   - **Titre** — bref résumé. C’est le seul champ obligatoire.
   - **Description** — du markdown, avec une barre d’outils de mise en forme.
   - **Statut** — **À faire** (la valeur par défaut) ou **Backlog**. Les états
     commencés et terminaux sont atteints par le cycle de vie, et non à la
     création.
   - **Priorité** — aucune, urgente, élevée, moyenne ou basse.
   - **Assigné à** — vous-même ou n’importe quel agent de l’espace de travail.
   - **Projet** — regroupement facultatif.
4. Appuyez sur **Créer** ou activez d’abord **En créer d’autres** pour garder la
   boîte de dialogue ouverte et enchaîner les saisies.

La boîte de dialogue ne contient aucun sélecteur de fournisseur. Le ticket est
créé auprès du fournisseur de tickets actif de l’espace de travail.

### Depuis un agent

Demandez à un agent dans un espace :

> Créez un ticket pour corriger le problème de délai d’attente de connexion sur
> les connexions lentes.

Il appelle l’outil MCP `create_ticket`. La priorité de cet outil est un
**entier**, et non un nom :

```
create_ticket(
  workspace_id: "...",
  title: "Fix login timeout on slow connections",
  description: "...",
  priority: 2
)
```

| Valeur | Priorité |
| ------ | -------- |
| `0`    | Aucune   |
| `1`    | Urgente  |
| `2`    | Élevée   |
| `3`    | Moyenne  |
| `4`    | Basse    |

Seuls `workspace_id` et `title` sont obligatoires ; `description`, `priority`,
`assignee` (un id d’agent) et `team_id` sont facultatifs. L’outil est classé
comme une écriture de synchronisation de fournisseur et demande votre
approbation avant de s’exécuter.

## Modifier le statut d’un ticket

Les tickets suivent ce cycle de vie :

```
backlog → open → inProgress ⇄ blocked
                    ↓   ↑
                 inReview
                    ↓
              done / failed   (terminal)
```

`done`, `failed` et `cancelled` sont terminaux. `cancelled` est accessible depuis
n’importe quel statut non terminal. `done` et `failed` sont accessibles depuis
`inProgress` ou `inReview` ; `open` peut aussi passer directement à `blocked`.
Le sélecteur de statut de l’interface liste tous les statuts sauf `failed` — les
agents le définissent avec `fail_ticket`.

Pour le modifier, utilisez l’un des éléments suivants :

- la ligne **Statut** du volet des propriétés du ticket,
- le sous-menu **Statut** du menu contextuel d’un ticket dans la liste,
- la puce **Statut** de la barre flottante après avoir sélectionné plusieurs
  tickets.

:::note[Le graphe du cycle de vie lie les agents, pas vous]
Tout changement de statut effectué depuis l’interface est appliqué de force, ce
qui contourne entièrement le graphe — vous pouvez déplacer un ticket vers
n’importe quel statut listé dans le sélecteur, y compris rouvrir un ticket
`done`, `failed` ou `cancelled`. Le sélecteur n’offre pas `failed` comme cible.
Le diagramme ci-dessus régit les agents et l’automatisation : une transition
illégale tentée par un outil MCP ou un réconciliateur est journalisée et ignorée,
et non appliquée.
:::

Les changements de statut émettent des événements de domaine
(`TicketStatusChanged`, `TicketCompleted` et d’autres) qui peuvent déclencher des
pipelines. Voir
[Configurer des déclencheurs de pipeline](/fr-CA/manuel/guides/declencheurs-de-pipeline/).

## Assigner un ticket

1. Ouvrez le ticket.
2. Dans le volet des propriétés, définissez **Assigné à** — vous-même, un autre
   membre de l’espace de travail ou un agent.

:::caution[Assigner ne lance aucun travail]
L’attribution consigne la propriété et rien d’autre. Elle ne crée aucun espace,
ne change aucun statut et ne lance aucun agent — `TicketAssigned` est un pur
signal de vérification sans répartiteur derrière lui. Pour faire travailler un
agent, envoyez-lui un message dans un espace (voir
[Clavarder avec un agent](/fr-CA/manuel/guides/clavarder-avec-agent/)).

Une seule exception : `TicketAssigned` est un type d’événement auquel vous pouvez
brancher un déclencheur de pipeline, de sorte qu’un modèle de votre cru peut
réagir à une attribution.
:::

## Ajouter des étiquettes

Les étiquettes s’appliquent en lot depuis la liste des tickets, et non depuis un
ticket individuel — le volet des propriétés n’offre aucun contrôle d’étiquette.

1. Survolez une ligne de la liste des tickets et cochez sa case. Cochez-en
   autant que nécessaire ; une barre flottante apparaît dès que quelque chose
   est sélectionné.
2. Dans cette barre, ouvrez la puce **Étiquettes**.
3. Choisissez une étiquette. Elle est ajoutée à chaque ticket sélectionné qui ne
   la porte pas ; les étiquettes existantes ne sont jamais effacées. **Effacer
   les étiquettes** les supprime toutes. Le sélecteur liste les étiquettes déjà
   présentes sur un ticket de l’espace de travail. Les agents peuvent ajouter un
   nouveau nom avec `update_ticket` ou `tickets.patch`.

## Lier des tickets

Les relations se trouvent sur la carte **Relations** du ticket, dans le volet
des propriétés, ou derrière **Lier à** dans le menu contextuel de la liste.

1. Ouvrez le ticket et repérez la carte **Relations**.
2. Appuyez sur son contrôle d’ajout et choisissez la relation :

| Relation           | Signification                           |
| ------------------ | --------------------------------------- |
| **Sous-tâche de…** | Le parent de ce ticket est l’autre      |
| **Parent de…**     | L’autre ticket est un enfant de celui-ci |
| **Bloqué par…**    | Ce ticket est bloqué par l’autre        |
| **Bloque…**        | Ce ticket bloque l’autre                |
| **Lié à…**         | Symétrique, aucune direction implicite  |
| **Doublon de…**    | Ce ticket est un doublon de l’autre     |

3. Choisissez le ticket cible.

**Dupliqué par** apparaît dans la carte, mais pas dans le sélecteur — c’est
l’inverse de **Doublon de** et il est défini depuis l’autre ticket. Chaque
relation listée est cliquable pour ouvrir le ticket lié et peut être retirée au
survol.

Les relations parent et sous-tâche sont stockées sur le ticket lui-même plutôt
que sous forme de lignes de lien, de sorte que la suppression d’un parent se
répercute en cascade sur ses enfants (voir ci-dessous), contrairement aux liens
de blocage et de relation.

## Ajouter des collaborateurs

Les collaborateurs forment un registre sur le ticket — qui est impliqué, et à
quel titre.

1. Ouvrez le ticket.
2. Appuyez sur le contrôle d’ajout de personne de la carte **Ajouter un
   collaborateur**.
3. Choisissez un agent.

Les trois rôles sont **assignee**, **collaborator** (le rôle par défaut) et
**reviewer**. Le sélecteur de l’interface ne liste que les agents de l’espace de
travail et écrit toujours le rôle par défaut ; les humains peuvent apparaître
comme lignes, mais ne sont pas proposés dans ce menu. L’outil MCP
`add_ticket_collaborator` accepte un `role`.

Ajouter un collaborateur écrit une ligne et ne publie aucun événement de
domaine ; cela n’accorde aucun accès à un espace. Pour faire entrer un agent dans
une conversation, ajoutez-le plutôt comme participant depuis l’en-tête de
l’espace — voir [Utiliser les espaces](/fr-CA/manuel/guides/espaces/).

## Supprimer un ticket

Utilisez **Supprimer le ticket** au bas du volet des propriétés, le menu
contextuel, ou l’action de suppression de la barre flottante après avoir
sélectionné plusieurs tickets.

:::caution[La suppression n’est que locale]
Un ticket provenant d’un outil de suivi externe n’y est pas supprimé — aucun
fournisseur ne le permet — de sorte qu’il peut réapparaître à la prochaine
synchronisation. La suppression se répercute aussi en cascade : les
collaborateurs du ticket et tous les tickets enfants disparaissent avec lui.
:::
