Une demande de tirage est déjà l’endroit où se déroule la conversation sur le code. Les
conversations de PR en font une surface d’un espace de travail Control Center, de la même
manière qu’une [passerelle de clavardage](/fr-CA/manuel/concepts/passerelles-de-clavardage/)
fait de Slack une surface : @mentionnez `@usectrl` (ou le robot de la GitHub App
de l’espace de travail) dans une PR, répondez dans ses fils de révision ou
ajoutez l’étiquette `ai-review`, et le travail se fait dans l’espace de révision de la PR —
sous la même attribution et les mêmes garde-fous que tout ce qui est saisi dans
l’application. Un commentaire et une étiquette sont contrôlés de la même façon : sur le
membre qui l’a écrit ou ajoutée. Les réponses reviennent sur GitHub, dans la voie où la
question a été posée.

Trois décisions façonnent la fonctionnalité, et chacune est la même décision que la
passerelle de clavardage a prise pour le clavardage, reformulée pour une forge : **dans
quel sens la connexion s’établit**, **ce qui autorise un commentaire qui arrive de
l’extérieur** et **à qui chaque partie est attribuée**.

## L’interrogation périodique est le transport

Le seul canal de poussée que GitHub offre à une application est le webhook, et un webhook
exige une URL entrante — précisément ce que cette surface ne requiert jamais,
délibérément. La découverte se fait donc par balayage : une recherche avec alias par
installation de l’application demande à GitHub les PR qui mentionnent le robot (ou son
slug court) ainsi que les PR ouvertes qui portent l’étiquette de révision, les PR qui ont
déjà un espace de révision voient leurs fils de commentaires lus, et le tout est comparé
par identifiant de commentaire avec ce qui a été vu au balayage précédent. Une app propre
balaie chaque minute au plus 25 PR. Par Connect, les appels puisent dans le quota GitHub
propre aux membres : le balayage a donc lieu toutes les deux minutes sur au plus 10 PR, et
un espace de travail sous 15 % de son quota est sauté jusqu’à ce qu’il se rétablisse.
Connect lui-même ne voit jamais le contenu des PR.

Les conséquences de ce choix méritent d’être nommées :

- **La latence correspond à un intervalle de balayage, pas à un événement.** L’accusé de
  réception 👀 arrive en l’espace d’un balayage. Rien d’urgent n’en dépend.
- **Une seule fois, par commentaire.** Les identifiants de commentaire sont uniques dans
  tout GitHub; chacun est consigné dès qu’il est classé comme admissible, avant que quoi
  que ce soit agisse sur lui. Un plantage peut faire perdre le traitement d’un
  commentaire, jamais le déclencher deux fois.
- **Le temps hors ligne est rattrapé, pas rejoué.** L’ensemble des commentaires vus est
  conservé, de sorte qu’un redémarrage livre ce qui est arrivé pendant l’arrêt. La seule
  exception est le tout premier balayage : faute de mémoire pour comparer, tout ce qui est
  en attente est consigné en silence — un opérateur qui a étiqueté vingt PR avant
  l’existence de ce serveur ne doit pas retrouver vingt révisions en cours.
- **L’étiquette est un ensemble, pas un événement.** La recherche signale la _présence_ de
  l’étiquette, donc une PR étiquetée déclenche une seule fois, pour de bon. Réajouter une
  étiquette après l’avoir retirée est invisible pour le balayage; une mention est la voie
  de réexécution.

La recherche s’exécute une fois par compte d’installation, sur le client de ce propriétaire,
car un jeton ne voit que les dépôts de sa propre installation — un identifiant unique à
l’échelle du serveur manquerait silencieusement toutes les PR relevant des autres
installations de l’application.

## C’est l’appartenance qui autorise, pas le commentaire

Un commentaire de PR arrive avec un auteur — une identité externe non authentifiée
jusqu’à preuve du contraire. Le serveur résout l’identifiant numérique immuable du compte
GitHub de l’auteur (jamais l’identifiant de connexion, qui peut être renommé et réutilisé)
au moyen des connexions GitHub des membres de l’espace de travail, reconstruites selon un
TTL parce que des gens se connectent et sont invités pendant que le serveur fonctionne.
Pour l’étiquette `ai-review`, la personne résolue est celle qui l’a ajoutée le plus
récemment.

Trois vérifications, dans l’ordre, et l’échec de l’une d’elles est silencieux — rien n’est
publié :

- **Un membre connecté.** Le compte doit appartenir à un membre de _cet_ espace de travail
  qui s’est connecté à GitHub sur ce serveur
- **Un rôle en écriture.** `viewer` et `guest` ne peuvent pas lancer de travail
- **Un accès en poussée.** Les réponses utilisent un jeton `bot` limité à l’accès de ce
  membre au dépôt. Si le serveur ne peut pas en émettre un, il ne poursuit pas

Chaque vérification s’exécute avant tout accusé de réception, de sorte qu’un inconnu
n’obtient ni réaction ni réponse. Un commentaire n’est jamais attribué à quelqu’un qui ne
l’a pas envoyé, et les propos d’un inconnu n’entrent jamais dans un espace de travail
qu’il ne peut pas voir.

### La revendication

La dernière étape avant tout travail est une réaction 👀, ajoutée avec la connexion GitHub
propre à l’auteur. GitHub répond `201` pour une nouvelle réaction et `200` pour une
réaction qui existe déjà : la réaction sert donc aussi de verrou. Quand la même personne
est connectée sur deux serveurs qui lient tous deux le dépôt, seul le premier à réagir fait
le travail. Un commentaire que plusieurs espaces de travail d’un même serveur voient est
offert à chacun, et la même revendication tranche.

## Deux identités, délibérément

Chaque partie de la conversation porte une identité différente, et cette différence est la
fonctionnalité même :

- **Sur GitHub, la réponse est une automatisation qui agit en votre nom.** Chaque réponse
  utilise un jeton `bot` pour ce seul dépôt, limité à l’accès du membre qui pose la
  question. Avec une app propre, l’auteur est le compte `[bot]` de l’app. Par Connect, un
  jeton de l’App partagée est un jeton d’utilisateur : la réponse est donc rédigée par le
  compte du membre qui pose la question, agissant par l’entremise de l’App. Dans les deux
  cas, chaque réponse commence par `**Control Center** (for @login):`, qui indique qui a
  posé la question et sert aussi de garde anti-boucle.
- **Dans l’espace, la question est la vôtre.** Le message est attribué au membre obtenu par
  résolution de l’auteur, et l’exécution de l’agent se fait en son nom : les commits le
  désignent comme coauteur, et le cadran d’autonomie de l’espace ainsi que les garde-fous
  d’action s’appliquent exactement comme à un message saisi dans l’application. Les
  écritures vers la forge provenant de l’exécution utilisent des jetons limités à un dépôt
  et bornés par ce membre, jamais sa connexion remise telle quelle.

Publier les constatations de révision vers GitHub demeure une décision humaine, prise dans
Control Center. Une mention peut _lancer_ une révision; seul un humain en publie une.

## Le garde anti-boucle et le nom court

Tout ce qui est produit par un compte de robot est écarté avant l’exécution de quelque
filtre que ce soit — le nôtre en particulier, et tout suffixe `[bot]`, pour qu’un robot de
révision appartenant à une autre application ne puisse pas non plus réveiller le nôtre —
tout comme chaque commentaire qui commence par le préfixe `**Control Center** (for @`,
puisqu’une réponse par Connect est rédigée par le compte d’une personne. Sans cela, les
réponses arriveraient comme de nouveaux commentaires et redéclencheraient la passerelle
sans fin.

Le suffixe `[bot]` explique aussi l’existence de la forme courte. GitHub fixe l’identifiant
de connexion d’un compte d’application à `<slug>[bot]`, n’offre aucune saisie
semi-automatique pour celui-ci et ne résout jamais `@slug` vers l’application — accepter le
slug seul relève donc d’une décision de _notre_ mécanisme de correspondance, et le
découvrir exige une voie de recherche brute dans le **texte** des commentaires plutôt que
l’index des mentions de GitHub. Le coût est énoncé plutôt que lissé : un utilisateur humain
qui partage le slug de l’application interpelle le robot à chacune de ses propres mentions
en forme courte. Des noms d’application distinctifs rendent cette collision hypothétique.

## Ce qui n’est délibérément pas offert

- **Aucune publication automatique.** Les constatations arrivent dans l’espace de révision;
  publier vers GitHub est une action humaine distincte
- **Aucune identité approximative.** L’auteur est résolu vers exactement un membre ou bien
  est ignoré — il n’y a pas d’attribution à l’estime
- **Aucune approbation automatisée.** L’automatisation peut commenter et demander des
  modifications, mais une révision `APPROVE` est refusée avant d’être envoyée. Approuver
  est un geste humain
- **Aucun webhook de GitHub App.** Cette surface n’en enregistre jamais, donc il n’y a
  aucune URL entrante à exposer pour les commentaires de PR. Les autres webhooks du
  produit (pipelines, synchronisation des tickets) relèvent d’une configuration distincte
  et facultative.
