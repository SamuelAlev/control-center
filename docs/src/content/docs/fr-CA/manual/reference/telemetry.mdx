Control Center peut envoyer des **événements d’utilisation pseudonymes** à une instance [Umami](https://umami.is). Les statistiques d’utilisation sont **désactivées tant que l’opérateur du serveur ne les active pas**. Le réglage appartient au serveur et s’applique à tous les clients qui y sont connectés : l’application de bureau, l’application web, le téléphone et le serveur lui-même.

Les statistiques d’utilisation sont distinctes de **Partager les rapports de plantage**, un réglage propre à chaque appareil pour les diagnostics de plantage et d’erreur.

## Qui décide

| Interrupteur | Où | Effet |
| --- | --- | --- |
| **Partager les statistiques d'utilisation** | Intégration (étape du bac à sable) et **Réglages → Confidentialité**. Seul l’opérateur du serveur peut le modifier ; les autres membres voient la valeur actuelle en lecture seule | Pour tout le serveur. Stocké sous `telemetry.usage_analytics` dans les réglages du serveur. Désactivé sauf s’il vaut `true` |
| Type de build | Automatique | Les builds debug et profile n’envoient rien. Ils écrivent chaque événement dans le journal de débogage à la place |
| `CC_ANALYTICS_DEBUG=1` | Environnement de `cc_server` ou son `.env` | Permet aux builds debug et profile du serveur, et de tous les clients qui y sont connectés, d’envoyer réellement, pour les tests. L’interrupteur ci-dessus doit quand même être activé |
| `DO_NOT_TRACK=1` | Environnement de `cc_server` | Arrête les remontées propres au serveur, quelle que soit la position de l’interrupteur. Les clients continuent de suivre l’interrupteur |
| Serveur de démonstration | Automatique | Le serveur de démonstration public n’envoie rien de lui-même. Les visiteurs ne peuvent pas changer l’interrupteur |

Les clients lisent le réglage auprès du serveur (`telemetry.config`, puis en direct via `telemetry.watch`). En attendant la réponse, les événements attendent dans un petit tampon en mémoire. Si la réponse est non, le tampon est vidé. Désactiver l’interrupteur supprime tout ce qui reste en file d’attente et arrête immédiatement l’envoi, sur tous les clients.

## Ce qui n’est jamais envoyé

- Le contenu des messages, tickets, revues ou réunions, les titres, les prompts, les commandes shell et les requêtes de recherche
- Les noms, identifiants de connexion, adresses de courriel, avatars et noms d’affichage
- Les chemins de fichiers, noms de dépôts, noms de branches, noms d’hôte et URL (un dépôt n’est envoyé que sous forme de `repo_id` pseudonyme, et un lien de réunion que sous la forme de son fournisseur)
- Les identifiants bruts, quels qu’ils soient

Chaque événement passe par une politique de propriétés avant de quitter le processus. Le texte, les chemins, les URL, les adresses de courriel, les ID non pseudonymisés et les chaînes placées sous des clés comme `email`, `*_name`, `path`, `title`, `prompt`, `content` ou `token` sont supprimés au lieu d’être envoyés. Une chaîne n’est envoyée que s’il s’agit d’un jeton court issu d’un vocabulaire fermé, comme une valeur d’énumération, une version, une langue ou un ID de modèle.

## ID pseudonymes

Les ID sont envoyés, mais uniquement sous forme de pseudonymes. Chaque ID d’espace de travail, d’espace, de conversation, d’agent, d’exécution, d’utilisateur et d’appareil est remplacé par un HMAC-SHA256 calculé avec le sel secret propre à l’installation (`telemetry.pseudonym_salt`), tronqué à 20 caractères hexadécimaux. Un même espace de travail renvoie toujours la même valeur, ce qui permet de relier et de compter les événements, mais l’ID brut ne quitte jamais l’installation. Le sel est créé au premier démarrage du serveur et n’est jamais envoyé au fournisseur de statistiques. Supprimer le répertoire de données du serveur crée un nouveau sel et un nouvel ID d’installation, ce qui dissocie tout ce qui a été enregistré auparavant.

## Propriétés présentes sur chaque événement

| Propriété | Exemple | Signification |
| --- | --- | --- |
| `app_type` | `desktop` | `desktop`, `web`, `remote` (le téléphone) ou `server`. Sert aussi de nom d’hôte dans Umami |
| `app_version` | `0.0.11` | Version publiée |
| `app_build` | `4baf980` | Commit git abrégé du build |
| `platform` | `macos` | `macos`, `windows`, `linux`, `web` ou le système du téléphone (`ios`, `android`) |
| `locale` | `fr_FR` | Langue de l’interface |
| `server_mode` | `local` | `local` (bureau exécutant son propre serveur) ou `remote` |
| `server_version` | `0.0.11` | Version du serveur connecté, si elle est connue |
| `is_demo` | `false` | Indique si le client est connecté à la démo publique |
| `install_id` | pseudonyme | L’installation du serveur |
| `user_id` | pseudonyme | L’utilisateur connecté, dès qu’il est connu |
| `device_id` | pseudonyme | L’appareil appairé, dès qu’il est connu. C’est aussi l’ID distinct dans Umami |
| `launch_id` | pseudonyme | Un lancement de l’application, pour ordonner les événements d’une session |
| `event_seq` | `12` | Position de l’événement dans le lancement |

Umami reçoit en outre l’adresse IP de la requête, dont il déduit le pays et la région sans conserver l’adresse, ainsi que le User-Agent et la taille de l’écran.

## Vues d’écran

Chaque navigation enregistre une vue de page dont l’URL est le **modèle de route**, par exemple `/workspaces/:workspaceId/spaces/:spaceId`, jamais l’adresse concrète. Le nom de l’écran est formé des segments littéraux du modèle : dans cet exemple, `workspaces_spaces`. Les paramètres de route qui se terminent par `Id` sont joints sous forme de propriétés `*_id` pseudonymes, et les paramètres numériques (comme un numéro de PR) sous forme de nombres. Tous les autres paramètres sont supprimés.

## Acheminement

Les événements sont envoyés un par un à `<host>/api/send` depuis une file d’attente en mémoire de 200 événements au plus. Une erreur réseau, un dépassement de délai, un `429` ou un `5xx` conserve l’événement et le renvoie avec un délai exponentiel, de 1 seconde jusqu’à 5 minutes. Tout autre `4xx` le supprime. Rien n’est écrit sur le disque : les événements encore en file d’attente quand l’application se ferme sont perdus. La file est vidée quand l’application passe en arrière-plan et quand le serveur s’arrête.

## Diriger un build vers une autre instance

La destination est fixée à la compilation :

```bash
--dart-define=CC_ANALYTICS_HOST=https://analytics.example.com/
--dart-define=CC_ANALYTICS_WEBSITE_ID=<website uuid>
```

L’adaptateur du fournisseur se trouve dans `packages/cc_analytics`. Prendre en charge un autre service de statistiques revient à y ajouter un adaptateur. Le plan de suivi et les règles de confidentialité restent les mêmes.
