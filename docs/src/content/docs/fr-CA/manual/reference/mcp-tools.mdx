`cc_server` héberge un seul registre d’outils MCP (JSON-RPC 2.0), servi sur le port principal du serveur (`9030` par défaut) à `POST /mcp` et `GET /sse`, version de protocole `2024-11-05`. Tous les clients atteignent le même registre : l’application de bureau, la version web, les clients MCP externes et l’environnement d’exécution d’agents intégré. Les serveurs MCP externes peuvent être raccordés au même registre comme couche dynamique.

## Taille du registre

| Mesure                                                                                     | Nombre |
| ------------------------------------------------------------------------------------------ | ------ |
| Outils enregistrés par `cc_server`                                                          | 110    |
| Provenant de `packages/cc_mcp`                                                              | 108    |
| Provenant de `packages/cc_mcp_client` (découverte des outils)                               | 2      |
| Enregistrés dans le registre de base (`server_mcp_registry.dart`)                           | 63     |
| Enregistrés après le démarrage, à mesure que leurs services se lancent (`cc_server_runtime.dart`) | 47     |
| Parmi les 63 du registre de base, conditionnés à un dépôt de graphe de code                 | 5      |

Les cinq outils de graphe de code ne sont enregistrés que lorsque l’hôte passe un dépôt de graphe de code à `buildServerMcpRegistry`. `cc_server` en passe toujours un, donc les 110 sont actifs dans le binaire livré.

Le registre complet est annoncé dans `tools/list` sans filtrage de découverte. Les modifications de tickets sont des outils typés.

:::note[Les clients externes voient toujours le catalogue au complet]
`tools/list` n’est jamais élagué. Les clients MCP valident les noms d’outils contre leur propre copie en cache de cette liste et refusent tout ce qui n’y figure pas sans interroger le serveur, si bien qu’un outil qui y est caché est inatteignable plutôt que simplement discret.

Le **harnais intégré** est différent : il ne charge qu’un sous-ensemble résident de définitions par requête et tire le reste au premier usage, ce qui est un comportement propre au harnais et ne change rien à ce registre. Voir [Contexte des outils et cache de prompts](/fr-CA/manuel/concepts/contexte-des-outils).
:::

:::note[Chaque classe d’outil est enregistrée]
Un fichier source sous `packages/cc_mcp/lib/src/tools/` est un outil qu’un agent peut
appeler. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
fait échouer la compilation si une nouvelle classe d’outil n’est construite par rien.
:::

## Paramètres communs

### `workspace_id`

**Requis** sur chaque outil qui touche des données liées à un espace de travail. Un `workspace_id` manquant ou invalide renvoie une erreur explicite, et une valeur qui ne correspond pas à l’espace de travail de l’entité cible est rejetée plutôt que silencieusement ignorée. Omettez-le sur les outils réellement globaux : `list_workspaces` et les six outils de fil de nouvelles (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), qui s’appuient sur la liste de fils par utilisateur du propriétaire du serveur. Les outils de découverte (`search_tool_bm25`, `list_my_tools`) le prennent facultativement afin de pouvoir classer ce qui est appelable selon le mode de conversation. Lorsqu’un agent est lancé par le serveur, l’espace de travail est imposé côté serveur, de sorte que l’agent ne peut pas atteindre un autre espace de travail en passant un identifiant étranger.

## Découverte des outils

Les deux viennent de `cc_mcp_client`, et non de `cc_mcp`, et tous deux consultent le garde de mode pour rapporter ce qui est appelable dans le mode de conversation _courant_.

| Outil              | Description                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `search_tool_bm25` | Rechercher le catalogue d’outils par mot-clé ; renvoie les outils correspondants, leurs schémas d’arguments et si chacun est appelable immédiatement |
| `list_my_tools`    | Lister les outils appelables immédiatement dans cette conversation, filtrés selon son mode                                        |

Un troisième outil de découverte, **`search_tools`**, n’existe qu’à l’intérieur du harnais intégré et ne fait pas partie de ce registre MCP. Il classe la surface d’outils de l’exécution elle-même et, contrairement à `search_tool_bm25`, **charge** les schémas de ce qu’il trouve afin que l’agent puisse appeler une correspondance au tour suivant. Les agents sur le harnais devraient le préférer ; les clients MCP disposent de `search_tool_bm25`.

## Messagerie et délégation entre agents pairs

Les agents se parlent entre eux par les espaces (durables, visibles dans l’effectif). `ask_agent` est une requête-réponse avec délai d’attente obligatoire ; `delegate_task` est encadré côté serveur par un plafond de profondeur, une détection de cycle, une enveloppe budgétaire et un plafond d’autonomie.

| Outil           | Description                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------- |
| `send_to_agent` | Envoyer un message unidirectionnel à un autre agent, adressé par `to_agent_id` ou par `to_agent_name` exact |
| `ask_agent`     | Poser une question à un autre agent et attendre sa réponse, ou expirer                           |
| `delegate_task` | Déléguer une tâche à un autre agent sous forme de ticket enfant suivi                            |
| `consult_agent` | Ajouter à l’espace le spécialiste dont les skills correspondent le mieux et le lancer avec une consigne ciblée |
| `todo_read`     | Lire la liste de tâches persistée de cette conversation                                          |

## Outils d’enceinte (rigs)

Pilotez des machines jetables — un navigateur ou un bureau Linux en enceinte, un
émulateur Android ou un simulateur iOS — depuis l’intérieur d’une exécution.
Enregistrés après le démarrage, sans condition : savoir si une machine peut
réellement démarrer est une question à laquelle les outils répondent à chaque
appel, par sondage. Des appels répétés dans une même conversation réutilisent une
seule machine ; les captures d’écran reviennent comme contenu image avec un budget
d’une image par résultat, et le contenu de page ou d’interface extrait est encadré
comme données non fiables. Les quatre outils d’utilisation, plus `rig_close`,
déclarent la [classe d’action](/fr-CA/manuel/concepts/garde-fous/) `enclosureControl`
(les outils d’utilisation déclarent aussi `networkEgress` et `processSpawn` ;
`mobile_use` et `ios_use` déclarent en outre `packageInstall`), de sorte que les
modes en lecture seule les refusent. `rig_list` n’en déclare aucune — il ne fait que
lire l’état de l’espace de travail. Le vocabulaire complet des verbes par surface se
trouve dans la [référence des rigs](/fr-CA/manuel/reference/rigs/#action-verbs).

| Outil          | Description                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------- |
| `computer_use` | Piloter un bureau Linux dans une VM en enceinte : déplacer, cliquer, glisser, faire défiler, saisir, redimensionner, presse-papiers, capture d’écran |
| `browser_use`  | Piloter un Chromium, Firefox ou WebKit sans interface (`engine`) : naviguer, cliquer, remplir, extraire (a11y/DOM/console), presse-papiers, capture d’écran |
| `mobile_use`   | Piloter Android par ADB : inspecter et saisir, captures d’écran, installer, démarrer, arrêter, réinitialiser et désinstaller des applications, liens profonds et commandes d’appareil au format argv |
| `ios_use`      | Piloter le simulateur iOS par WebDriverAgent/CoreSimulator : inspecter et saisir, captures d’écran, installer, démarrer, arrêter et désinstaller des applications, liens profonds et processus de simulateur au format argv |
| `rig_list`     | Lister les rigs d’un espace de travail avec leur surface, leur statut, la taille de l’affichage et le contrôleur |
| `rig_close`    | Détruire un rig et jeter l’état des machines qu’il possède                                          |

## Non exposé par MCP

Le calendrier et les réunions n’ont aucun outil MCP. Les agents ne peuvent pas lire votre calendrier, vos réunions, vos transcriptions, vos points d’action ni vos décisions. Le résumé qui produit les points d’action et les décisions s’exécute comme [pipeline `meeting_summary`](/fr-CA/manuel/concepts/reunions/) intégré, et non comme un outil qu’un agent peut appeler.

## Filtrage des outils selon le mode

Le filtrage est appliqué deux fois à partir d’une seule table (`ModeToolPolicy`) : une fois dans le répartiteur MCP pour l’adaptateur Claude Code et une fois dans le registre du harnais intégré. Un appel bloqué renvoie la raison.

| Mode          | Surface d’outils                                                                                                                                                                                                                   |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | Tous les outils enregistrés ; aucune liste d’autorisation                                                                                                                                                                            |
| `plan`        | Une liste d’autorisation restreinte. Aucune écriture dans l’arbre de travail et aucun verbe de ticket `create` / `assign` / `delegate`, mais la mémoire, les artefacts, les listes de tâches, `submit_plan`, `exit_plan_mode` et les verbes d’achèvement de ticket sur le ticket lancé sont permis |
| `review`      | Une liste d’autorisation restreinte : la participation à la révision, la communication, les récupérateurs de contexte en lecture seule et l’ensemble complet des verbes de ticket, y compris `create_ticket` et `assign_ticket`     |
| `orchestrate` | Une liste d’autorisation restreinte : les outils de recherche et de lecture, plus `propose_orchestration`, `create_playbook` et `run_playbook`. L’embauche, la décomposition et l’achèvement des tickets se font de façon déterministe après l’approbation, jamais en cours d’exécution |

Permis dans tous les modes, peu importe la liste d’autorisation :

| Ensemble              | Outils                                                                                                                                                                                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mémoire et artefacts  | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Graphe de code        | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                        |
| Mécanique d’exécution | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                     |

Figurer sur une liste d’autorisation ne rend pas un outil appelable, et l’inverse est vrai aussi : la capacité de question à l’opérateur est un outil du **harnais** (`ask_user`), donc elle n’apparaît jamais dans ce catalogue MCP.

## Outils soumis à approbation

Un outil peut déclarer `requiresApproval`. Le répartiteur construit alors un `ApprovalPayload` et le présente par le `ConfirmationPort` avant l’exécution de l’outil ; `cc_server` câble ce port, donc la barrière est active.

Outils enregistrés qui le déclarent : `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

Indépendamment, les garde-fous d’action unifiés filtrent tout outil qui déclare un ensemble `ActionClass` non vide. Une décision `prompt` sans approbateur connecté est refusée. Voir [Garde-fous](/fr-CA/manuel/concepts/garde-fous/).

## Capacités sans outil derrière elles

Toutes les capacités du produit ne sont pas accessibles à un agent. Celles-ci n’ont
aucun outil, donc un nom que vous auriez vu mentionné ailleurs renvoie « unknown tool » :

| Capacité                                | Où elle se trouve plutôt                                                                                    |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Embaucher, congédier ou modifier un agent | L’interface des agents. Il n’existe aucun outil `hire_agent` / `fire_agent` / `update_agent`                |
| Créer un espace de travail              | `workspace.upsert` par RPC, qui amorce l’espace de travail et estampille la propriété                        |
| Projets (créer / lister / mettre à jour / classer) | L’interface des tickets. Les projets sont une surface d’opérateur — voir [Projets](/fr-CA/manuel/guides/projets/) |
| Poser une question bloquante à l’opérateur | L’outil `ask_user` du **harnais**, et non MCP. Il affiche un formulaire dans la conversation et bloque jusqu’à la réponse |
| Diagnostic par agent                    | Rien. Il n’existe aucun `doctor` — voir [Diagnostic d’un agent](/fr-CA/manuel/guides/diagnostiquer-agent/)   |
| Calendrier et réunions                  | RPC pour les clients humains seulement (voir plus haut)                                                      |
