Tout ce que Control Center peut copier, céder ou adopter, et la forme exacte de chaque
artéfact. Pour prendre réellement une sauvegarde, voir
[Sauvegarder et restaurer](/fr-CA/manuel/guides/sauvegarder-et-restaurer/) ; pour comprendre
pourquoi la persistance est ainsi divisée, voir
[Espaces de travail et isolation](/fr-CA/manuel/concepts/espaces-de-travail/).

## Artéfacts

Il existe trois artéfacts de copie de base de données, aux portées et aux politiques de
suppression différentes.

| Artéfact                        | Écrit par                    | Forme                                 | Couvre                        |
| ------------------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **Instantané de l’installation** | `server.backupNow`          | Un **répertoire** horodaté            | Chaque base de données de l’installation |
| **Sauvegarde d’espace de travail** | pipeline `Workspace backup` | Répertoire horodaté avec un seul `.db` | La base de données d’un espace de travail |
| **Export d’espace de travail**  | `workspace.export`           | Un **fichier** `.db` unique           | La base de données d’un espace de travail |

Tous sont écrits avec `VACUUM INTO` de SQLite, qui ne craint pas une base de données WAL
active : il prend une transaction de lecture, produit une copie défragmentée et cohérente
du point de vue transactionnel, et n’exige jamais d’arrêter le serveur.

Ces fichiers et les copies téléchargées ne sont **pas chiffrés au repos** par
Control Center. Le transfert chiffré de bout en bout protège les octets en transit
entre un client associé et son `cc_server`, sur les connexions directes comme
relayées. Protégez séparément le stockage local et les copies hors machine ; le
serveur et tout destinataire autorisé peuvent lire les fichiers de base de données.

## Disposition des instantanés

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

La disposition reflète exactement le répertoire de données actif, ce qui fait de la
restauration d’une installation une recopie plutôt qu’une conversion. Le nom du répertoire
est l’horodatage UTC, `:` et `.` remplacés par `-`, de sorte qu’il est sécuritaire pour le
système de fichiers sous Windows et qu’il se trie chronologiquement comme une simple
chaîne.

Les sauvegardes d’espace de travail planifiées vivent séparément à `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`. Chacune comporte un `manifest.json` pour ce seul fichier et aucun `global.db` ; ce ne sont pas des instantanés de l’installation. Une restauration conserve la base de données qu’elle remplace au même endroit, sous le nom `<timestamp>-pre-restore`. L’étape de rétention du pipeline hebdomadaire ne supprime que les sauvegardes de son propre espace de travail plus anciennes que la durée configurée (30 jours par défaut) ; les instantanés de l’installation créés manuellement ne sont jamais supprimés par cette étape. `server.listBackups` ne liste que les instantanés de l’installation, y compris les non vérifiés ; `workspace.listBackups` liste les sauvegardes planifiées d’un espace de travail.

Supprimer un espace de travail laisse ce répertoire en place. L’horaire de l’espace de
travail s’arrête avec lui, donc plus rien n’effectue la rotation de ces sauvegardes, et
elles restent jusqu’à ce que le propriétaire de l’installation les retire.
`server.listOrphanedBackups` les signale.


### `manifest.json`

| Champ                      | Type            | Signification                                                       |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                  | int             | Format du manifeste. Actuellement `2`                    |
| `created_at`               | ISO-8601 UTC    | Moment où l’instantané a été pris                                   |
| `global`                   | object          | L’enregistrement de `global.db`. Absent d’une sauvegarde planifiée d’espace de travail |
| `workspaces[]`             | array           | Un enregistrement par espace de travail capturé                           |
| `workspaces[].workspace_id`| string          | L’espace de travail que ce fichier contient                        |
| `skipped_workspaces[]`     | array           | Espaces de travail que la sauvegarde n’a **pas** pu capturer        |
| `skipped_workspaces[].workspace_id` | string | L’espace de travail laissé de côté |
| `skipped_workspaces[].reason` | string | `no_file`, `damaged` ou `failed` |

`global` et chaque enregistrement de `workspaces[]` consignent un fichier copié, mesuré sur la copie une fois celle-ci écrite :

| Champ | Type | Signification |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | string          | Chemin relatif à la racine de l’instantané : `global.db` ou `<workspaceId>/workspace.db` |
| `bytes`       | int             | Taille de la copie                                                |
| `sha256`         | string | SHA-256 de la copie, en hexadécimal minuscule                                  |
| `quick_check`    | string | Ce que dit le `quick_check` de SQLite au sujet de la copie : `ok`, ou sa constatation |
| `user_version`   | int    | Version du schéma de la copie                                                  |
| `application_id` | int    | `application_id` SQLite de la copie                                            |

Un espace de travail est ignoré lorsqu’il est enregistré mais n’a jamais été écrit (`no_file`), lorsque sa base de données échoue au contrôle d’intégrité (`damaged` ; une copie endommagée n’est jamais prise), ou lorsque sa copie, ou le contrôle de cette copie, a échoué (`failed`). Dans tous les cas, l’instantané se termine quand même et le manifeste nomme ce qui manque. Le manifeste est écrit en dernier.

### Complétude

`server.listBackups` signale un indicateur `complete` par instantané. Il est faux lorsque le manifeste est absent, illisible ou d’un autre format, lorsqu’un fichier qu’il nomme est absent ou n’a pas la taille attendue, ou lorsqu’une copie n’a pas réussi son contrôle. L’application affiche un tel instantané comme **Non vérifié**. Les instantanés pris avant le format `2` se trouvent dans cet état.

Un instantané non vérifié est tout de même listé, parce qu’un instantané qu’un opérateur ne
voit pas est un instantané qu’il croit posséder. Lorsque le manifeste est illisible, la
liste se rabat sur la disposition elle-même et signale tous les fichiers
`<workspaceId>/workspace.db` qu’elle trouve — ceux-ci demeurent adoptables un par un au
moyen de `workspace.import`, même si l’instantané dans son ensemble ne peut pas restaurer
une installation.

Tout instantané ou sauvegarde planifiée répertorié porte `pinned_reason: "last_good_copy"` tant qu’il contient la copie vérifiée la plus récente d’un espace de travail dont la base de données active est endommagée. L’étape de rétention l’ignore jusqu’à ce que cet espace de travail soit restauré.

## Ce qu’une sauvegarde ne contient pas

Les deux artéfacts sont **des bases de données uniquement**. Un répertoire d’espace de
travail contient plus que sa base de données, et rien du reste ne voyage :

| Chemin                              | Dans un instantané ? | Dans un export d’espace de travail ? |
| ----------------------------------- | -------------------- | ------------------------------------ |
| `global.db`                         | Oui                  | Non                                  |
| `<workspaceId>/workspace.db`        | Oui                  | Oui (c’est *le* fichier)             |
| `<workspaceId>/code_index.db`       | Non                  | Non                     |
| `<workspaceId>/blobs/`              | Non                  | Non                                  |
| `<workspaceId>/skills/`             | Non                  | Non                                  |
| `<workspaceId>/agents/`             | Non                  | Non                                  |
| `<workspaceId>/chat_credentials/`   | Non                  | Non                                  |
| `<workspaceId>/spaces/<spaceId>/`   | Non                  | Non                                  |
| `<workspaceId>/pr_clones/`          | Non                  | Non                                  |
| `secrets.json`                      | Non                  | Non                                  |
| `models/`                           | Non                  | Non                                  |
| `meetings/<meetingId>/`             | Non                  | Non                                  |
| `rigs/`                             | Non                  | Non                                  |
| `_agent_hooks/`                     | Non                  | Non                                  |

Une partie de cela est jetable — `spaces/` contient des arbres de travail copie sur écriture qui sont reprovisionnés à partir des dépôts, `pr_clones/` est un cache, `code_index.db` est reconstruit, `models/` se retélécharge, `rigs/` est un état de machine. Une autre partie ne l’est pas : `blobs/` contient des images collées vers lesquelles pointent des lignes de la base de données, `skills/` et `agents/` contiennent les fichiers avec lesquels un agent s’exécute, et `secrets.json` contient chaque clé d’appairage, chaque identifiant de fournisseur et chaque paramètre SSO de l’installation. Voir
[Sauvegarder et restaurer](/fr-CA/manuel/guides/sauvegarder-et-restaurer/#copier-les-sauvegardes-hors-de-la-machine)
pour couvrir le reste.
:::note[Les secrets restent hors des bases de données]
`workspace.db` est tout l’espace de travail : conversations, journaux d’exécution, liens vers les dépôts, définitions d’environnement et membres. Les jetons de webhook de pipeline et les secrets de webhook de synchronisation des tickets se trouvent dans `secrets.json` : la base de données contient une référence à chacun, et l’index des routes contient un hachage à clé de chaque jeton. Un espace de travail restauré sur une autre installation ne reçoit donc aucun webhook tant que ses déclencheurs n’y ont pas été enregistrés de nouveau. Les connexions aux fournisseurs, les clés d’appareil et les secrets d’utilisateur se trouvent dans `global.db` et `secrets.json`.
:::

:::note[Les jetons de clavardage restent délibérément à l’écart]
Le fait que `chat_credentials/` se trouve à côté de la base de données plutôt qu’à
l’intérieur explique pourquoi un espace de travail remis à quelqu’un d’autre ne transporte
aucun jeton de robot actif. Voir la
[référence sur la passerelle de clavardage](/fr-CA/manuel/reference/passerelle-de-clavardage/).
:::

## Opérations

Les RPC de sauvegarde de l’installation et l’export/import d’espace de travail ne sont
accessibles qu’aux `fullClient` : un téléphone appairé ne peut pas les déclencher. Tous
sont totalement absents — non pas refusés, mais structurellement manquants — sur un
serveur sans port de sauvegarde câblé, comme le serveur de démonstration.

| Op                   | Type     | Portée            | Rôle minimal              | Arguments     | Retourne                      |
| -------------------- | -------- | ----------------- | ------------------------- | ------------- | ----------------------------- |
| `server.backupNow`   | mutation | Installation      | **propriétaire** de l’installation | aucun | `{ok, path}`          |
| `server.listBackups` | lecture  | Installation      | **propriétaire** de l’installation | aucun | `{backups: [...]}`    |
| `server.deleteBackup` | mutation | Installation     | **propriétaire** de l’installation | `name` | `{ok}`              |
| `server.listOrphanedBackups` | lecture | Installation | **propriétaire** de l’installation | aucun | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutation | Installation | **propriétaire** de l’installation | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | lecture | Espace de travail | `admin` | aucun | `{backups: [...]}` |
| `workspace.deleteBackup` | mutation | Espace de travail | `owner` | `name` | `{ok}` |
| `workspace.export`   | lecture  | Espace de travail | `admin`                   | aucun         | `{ok, path}`                  |
| `workspace.import`   | mutation | Espace de travail | `owner`, et le propriétaire du serveur | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | lecture | Espace de travail | `owner`, et le propriétaire du serveur | aucun | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutation | Espace de travail | `owner`, et le propriétaire du serveur | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | mutation | Installation*     | `owner`                   | `id`          | ligne du registre marquée supprimée |

* `workspace.delete` n’a pas de portée parce que la ligne qu’il marque vit dans le
registre global ; son gestionnaire vérifie l’appartenance de l’appelant à l’espace de
travail nommé et exige `owner`.

Le `path` de chaque réponse est un chemin sur l’**hôte du serveur**.

`server.listOrphanedBackups` renvoie une entrée par espace de travail qui n’est plus actif :
`workspace_id`, `workspace_name` lorsque le registre le connaît encore, et `backups`.
Un espace de travail supprimé ne peut plus passer une vérification de rôle d’espace de
travail, ses sauvegardes reviennent donc au propriétaire de l’installation.
`server.deleteOrphanedBackup` refuse un espace de travail actif, dont les sauvegardes restent
derrière `workspace.deleteBackup` et les rôles propres à cet espace de travail. Les deux
opérations de suppression n’acceptent qu’un nom de répertoire horodaté listé, pas un chemin.

`workspace.importHolds.list` renvoie ce qu’une importation a mis en attente. Chaque mise en attente possède un `id`, un `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` ou `invite`), le `payload` qu’elle remettrait en place, `imported_at` et `source_install_id`. `workspace.importHolds.resolve` avec `accept: true` l’accorde à nouveau, et avec `false` la supprime. `applied` vaut faux lorsque le bénéficiaire de l’autorisation, personne ou chose, ne fait plus partie de l’espace de travail.

:::note[Un instantané de toute l’installation est réservé au propriétaire sur les deux voies]
`server.backupNow`, `server.listBackups` et `server.deleteBackup` exigent le
**propriétaire** de l’installation (`ServerAuthority.serverOwner`), le même verrou que
`GET /backup/snapshot`. Un instantané capture la base de données de chaque espace de
travail, donc être administrateur d’un seul espace de travail ne suffit pas pour gérer les
autres. La suppression n’accepte que le nom du répertoire horodaté listé, et non un chemin
de serveur arbitraire, et supprime tout l’instantané (y compris les instantanés
non vérifiés). Les exports par espace de travail et les téléchargements de sauvegardes planifiées restent réservés à l’administrateur de l’espace de travail.
:::

:::note[La restauration appartient au propriétaire du serveur]
`workspace.import` et `POST /backup/restore` font adopter au serveur un fichier de base de données dont il traite ensuite les lignes comme siennes : liens vers les dépôts et qui les a créés, définitions d’environnement qui s’exécutent sur l’hôte, chemins des arbres de travail et des journaux. Les deux exigent donc le propriétaire du serveur (`ServerAuthority.serverOwner`), qui doit aussi être le propriétaire de l’espace de travail. Tout autre appelant, et tout appelant sur un hôte sans propriétaire enregistré, est refusé avec `server_owner_required`. Aucun déclencheur, aucune vue, aucune colonne ni aucune contrainte apportés par le fichier ne sont adoptés.
:::

### Réponse de `server.listBackups`

Du plus récent au plus ancien, trié par nom de répertoire (qui est l’horodatage, de sorte
que l’ordre tient même pour un instantané dont le manifeste n’a pas pu être lu).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` est omis lorsque le manifeste n’a pas pu être lu. La valeur `bytes` du niveau
supérieur est la taille réelle sur le disque de tout le répertoire, et non la somme du
manifeste lui-même — la question que se pose un opérateur qui élague les instantanés est
ce que coûte le répertoire, et non ce que la sauvegarde comptait écrire.

Chaque `workspaces[].path` est exactement ce que `workspace.import` prend comme
`source_path`. C’est délibéré : « restaurer cet espace de travail à partir de cet
instantané » *est* l’opération d’import, de sorte que les deux ne peuvent pas diverger
vers des traitements différents du même fichier.

### Validation de `workspace.import`

Avant que quoi que ce soit soit remplacé, le fichier candidat est copié dans un fichier de préparation à côté de la cible, et il y est vérifié. Un refus ne touche à rien et porte sa catégorie dans `data.kind`.

| Condition                                                | Résultat                                                        |
| -------------------------------------------------------- | ---------------------------------------------------------------- |
| Le fichier n’existe pas | Refusé, `import.missing_source` |
| Base de données SQLite illisible, ou qui échoue à `quick_check` | Refusé, `import.damaged` |
| Il provient d’un instantané et son SHA-256 diffère de celui du manifeste | Refusé, `import.checksum_mismatch` |
| Une version plus récente du serveur l’a écrit | Refusé, `import.newer_schema` |
| Un autre `application_id`, ou aucun `workspace_meta` | Refusé, `import.foreign_file` |
| Il ne peut pas être amené au schéma de ce serveur | Refusé, `import.schema_mismatch` |
| Ses webhooks ou invitations sont déjà rattachés à un autre espace de travail | Refusé, `import.route_conflict` |
| Identifiant d’espace de travail enregistré ≠ la cible     | **Permis**. Ses lignes sont réattribuées à la cible. C’est ainsi qu’un espace de travail est dupliqué ou restauré sous un nouvel identifiant |
| Identifiant d’installation enregistré ≠ cette installation | **Permis**. Ses identifiants d’utilisateur appartiennent à cette installation et ne se résoudront pas ici |

À l’acceptation, le fichier préparé est amené au schéma de ce serveur et doit ensuite lui correspondre exactement. Les autorisations qu’un fichier ne peut pas s’accorder à lui-même lui sont retirées : les approbations d’exécution d’une définition d’environnement sur l’hôte sont effacées, et les règles d’action qui permettent ou demandent une confirmation, les autorisations d’exécution dans le bac à sable, les accès aux dépôts au-delà de la lecture, les rôles au-delà de membre et les invitations à ces rôles deviennent des mises en attente que le propriétaire du serveur doit examiner. Celui qui importe conserve ou obtient le rôle de propriétaire. La base de données remplacée est conservée comme sauvegarde planifiée nommée `<timestamp>-pre-restore` ; le fichier préparé est renommé à sa place, les connexions de l’espace de travail étant fermées ; `code_index.db` est supprimé pour être reconstruit, et les index FTS sont reconstruits.

## Routes de transfert

Les opérations d’export/import et de listage d’instantanés ci-dessus s’expriment en
chemins côté serveur, ce qui n’est une réponse complète que lorsque le serveur est
votre propre machine. Ces routes en forme de HTTP transportent les octets de
sauvegarde **à l’intérieur du même tunnel de ressources authentifié et chiffré de
bout en bout** que d’autres ressources sensibles, que la connexion RPC soit directe
ou relayée. Ce ne sont pas des points de terminaison publics de transfert de
fichiers HTTP : une requête vers l’un d’eux sur l’écouteur public renvoie
`426 Upgrade Required`, même depuis la boucle locale. Dans le tunnel chiffré,
l’appareil authentifié par Noise doit correspondre à `d` ; le gestionnaire vérifie
en outre la signature de l’appareil sur sa chaîne cible au moyen de sa PSK
d’appairage et du rôle ci-dessous.

| Route                   | Méthode | Requête         | Cible signée                   | Exige                   |
| ----------------------- | ------- | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET     | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **administrateur** de l’espace de travail |
| `/backup/snapshot`      | GET     | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **propriétaire** de l’installation |
| `/backup/stored`        | GET     | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **administrateur** de l’espace de travail ; **propriétaire** de l’installation une fois l’espace de travail supprimé |
| `/backup/restore`       | POST    | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **propriétaire** de l’installation, également **propriétaire** de l’espace de travail (sinon `403` avec `server_owner_required`) |

`w` est un identifiant d’espace de travail, `n` un nom de répertoire d’instantané ou de
sauvegarde planifiée, `d` l’identifiant de l’appareil appelant, `s` la signature. Sur
`/backup/snapshot`, `n` est résolu à partir de la
liste des sauvegardes plutôt que joint à la racine des sauvegardes, de sorte que la route
ne peut pas viser un répertoire que la liste n’aurait pas montré. Sur `/backup/stored`, il
doit s’agir d’un nom horodaté, et le fichier doit être un vrai fichier dans le répertoire de
sauvegarde propre à cet espace de travail.

| Statut | Cause                                                                                |
| ------ | ------------------------------------------------------------------------------------ |
| `400`  | Un paramètre de requête obligatoire manque, un nom de sauvegarde est invalide, le corps d’un téléversement est vide, ou le fichier téléversé a été refusé (le corps est `{error, kind}` avec une catégorie `import.*`) |
| `403`  | Appareil inconnu ou révoqué, signature invalide, ou l’appelant n’a pas le rôle       |
| `404`  | Aucun port de sauvegarde sur cet hôte, ou l’instantané, la sauvegarde ou le fichier d’espace de travail nommé n’existe pas |
| `405`  | `/backup/restore` appelé avec autre chose que `POST`                                 |
| `413`  | Le corps du téléversement dépasse 8 GiB, selon la longueur de contenu déclarée ou les octets réellement lus |
| `426`  | Toute requête directe vers une route de transfert sur l’écouteur HTTP public ; utilisez le tunnel de ressources chiffré d’un client associé |
| `500`  | L’export ou l’archivage a échoué côté serveur                                        |

Les trois téléchargements répondent `Cache-Control: no-store` avec `Accept-Ranges: none`.
`/backup/workspace` et `/backup/snapshot` créent une copie **fraîche** par requête et la suppriment une fois diffusée, de sorte qu’une
réponse mise en cache ou reprise souderait les octets de deux exports différents en un
seul fichier qui a l’air valide sans l’être.

`/backup/stored` fait exception : il diffuse une sauvegarde planifiée sous le nom `<workspaceId>-<name>.db`
et laisse le fichier en place, car ce fichier est la sauvegarde.

`/backup/snapshot` renvoie `<name>.zip`, dont les entrées sont relatives à la racine de
l’instantané, de sorte que la décompression reproduit `manifest.json` + `global.db` +
`<workspaceId>/workspace.db`. Les entrées sont écrites en ordre trié, de sorte que deux
archives du même instantané sont la même archive.

`/backup/restore` diffuse le corps directement vers un fichier de préparation plutôt que
de le mettre en mémoire tampon, le borne avant et pendant la lecture, et supprime le
fichier préparé sur **chaque** chemin de sortie, y compris en cas de refus.

::::caution[La connexion directe et le relais utilisent le même transfert chiffré]
Le relais transporte les requêtes de ressources, les réponses diffusées et les
octets de téléversement sous forme de texte chiffré ; il ne peut pas lire le
contenu des sauvegardes. Un chemin côté serveur reste un chemin sur l’hôte du
serveur, et non un fichier sur le relais. L’accès exige toujours l’appareil
associé, la signature de la cible et le rôle applicable d’espace de travail ou
d’installation. Aucun des deux transports ne chiffre au repos les fichiers de
sauvegarde produits.
::::

## Chemins et limites

| Élément                        | Valeur                                                       |
| ------------------------------ | ------------------------------------------------------------ |
| Instantanés                    | `<dataDir>/backups/<timestamp>/`                             |
| Sauvegardes d’espace de travail planifiées | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Exports d’espace de travail    | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Base de données remplacée par une restauration | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Bases de données telles qu’elles étaient avant qu’une mise à jour ne change leur format | `<dataDir>/pre_upgrade/` et `<dataDir>/<workspaceId>/pre_upgrade/`, les deux plus récentes de chaque |
| Préparation des transferts     | `<dataDir>/backups/transfer/` — un établi, balayé par la route qui l’écrit |
| Nom de l’archive d’instantané  | `<snapshot directory name>.zip`                              |
| Plafond de téléversement       | 8 GiB par téléversement chiffré vers `/backup/restore`       |
| Rétention                      | Instantanés de l’installation : suppression manuelle. Sauvegardes d’espace de travail : pipeline hebdomadaire, 30 jours par défaut, ou suppression manuelle. Sauvegardes d’un espace de travail supprimé : suppression manuelle seulement |

Les répertoires `exports/`, `transfer/` et `workspace-backups/` ne sont pas des instantanés
de l’installation et sont exclus de `server.listBackups`. Seul le dernier répertoire a une
rétention planifiée, et seulement tant que son espace de travail existe ; supprimer un instantané de l’installation exige l’action explicite
du propriétaire de l’installation.
