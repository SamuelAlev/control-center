Chaque paramètre du processus accepte une option de ligne de commande ou une
variable d’environnement; l’option l’emporte, puis la variable d’environnement,
puis la valeur par défaut. Les identifiants des fournisseurs font exception —
voir [Applications fournisseur et Connect](#applications-fournisseur-et-connect).

:::caution[Les options inconnues sont ignorées en silence]
L’analyseur d’arguments est écrit à la main et saute tout ce qu’il ne reconnaît pas, si bien qu’une coquille (`--tls-key-file`, `--bindany`) ne produit aucune erreur — le serveur démarre simplement avec la valeur par défaut. Vérifiez les lignes du journal de démarrage quand une option semble sans effet. Une [option du mode code](#mode-code) dont la valeur n’est pas acceptée est différente : le serveur refuse de démarrer.
:::

## Fondamentaux

| --------------- | ---------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `--data-dir`    | `CC_SERVER_DATA_DIR`   | le répertoire de données d’application par utilisateur du système d’exploitation (voir ci-dessous) | Bases de données, secrets, modèles et médias en cache                                                          |
| `--port`        | `CC_SERVER_PORT`       | `9030`                                            | Port TCP (`0` = éphémère)                                                                                      |
| `--bind`        | `CC_SERVER_BIND`       | `loopback`                                        | `loopback`, ou `any`/`all`/`0.0.0.0` pour toutes les interfaces (exige TLS ou `--insecure`)                    |
| `--repo-roots`  | `CC_SERVER_REPO_ROOTS` | le répertoire personnel de l’utilisateur du serveur | Répertoires de base séparés par des virgules qu’un client peut parcourir au moment d’enregistrer un dépôt. Tout parcours au-dessus d’une racine est refusé |
| `--log-level`   | `CC_SERVER_LOG_LEVEL`  | `warning`                                         | `debug`, `info`, `warning` ou `error`. Les lignes de démarrage et de disponibilité s’affichent toujours         |
| `--server-name` | `CC_SERVER_NAME`       | le nom d’hôte de la machine                       | Nom affiché dans les sélecteurs, la découverte et les surfaces d’association                                   |

## Applications fournisseur et Connect

Aucune version n’embarque d’identifiants de fournisseur. Avec Control Center Connect activé, Connect exécute chaque fournisseur, et ces applications propres restent enregistrées mais inutilisées. Sous **Utiliser mes propres applications**, chaque fournisseur s’exécute avec l’application propre au serveur lorsqu’elle est entièrement configurée, sinon il est indisponible. Une application propre à l’espace de travail s’applique dans les deux cas. Les applications propres se définissent dans **Paramètres →
Serveur → Authentification unique → Applications fournisseur**, ou sont
initialisées une seule fois à partir du fichier `.env` du serveur. Il n’existe
aucune option pour elles : un secret passé sur la ligne de commande est lisible
au moyen de `ps`.

| Variable | Signification |
| --- | --- |
| `GITHUB_APP_ID` | L’identifiant de la GitHub App du serveur |
| `GITHUB_APP_PRIVATE_KEY` | Sa clé privée, sur une seule ligne avec des échappements `\n`. **`.env` seulement** |
| `GITHUB_CLIENT_ID` | Son identifiant client, pour connecter les gens |
| `GITHUB_CLIENT_SECRET` | Son secret client. **`.env` seulement** |
| `GOOGLE_OAUTH_CLIENT_ID` | Le client Google de type Web application du serveur |
| `GOOGLE_OAUTH_CLIENT_SECRET` | Son secret. **`.env` seulement** |
| `LINEAR_CLIENT_ID` | L’application Linear du serveur (PKCE, sans secret) |
| `LINEAR_API_KEY` | Une clé de service Linear pour l’automatisation. **`.env` seulement** |
| `KLIPY_APP_KEY` | La clé Klipy propre au serveur pour la recherche de GIF, utilisée seulement sous **Utiliser mes propres applications** |
| `CC_CONNECT_URL` | `hosted`, `off` ou une URL Connect. Verrouille le choix de Connect; Paramètres ne peut alors plus le modifier |
| `CC_SERVER_CONNECT_HOST` | `on` monte Control Center Connect sur `<server>/connect`, configuré par les variables `CONNECT_*`. Voir [Exécuter un serveur Connect](/fr-CA/manuel/guides/executer-serveur-connect/#monter-connect-dans-cc_server) |

Le fichier `.env` est lu dans le répertoire de travail du serveur, à côté de
l’exécutable, ou dans une copie du code source située au-dessus; sous Docker,
montez-le sur `/app/bin/.env`. Le serveur **refuse de démarrer** (code de sortie
`78`) lorsque `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`,
`GOOGLE_OAUTH_CLIENT_SECRET`, `LINEAR_API_KEY` ou un `SLACK_*SECRET*` quelconque
est exporté dans l’environnement de son processus, où chaque processus enfant
pourrait le lire. L’initialisation à partir de `.env` se fait une fois par
champ, donc une modification ultérieure dans Paramètres n’est pas annulée par un
redémarrage. Une valeur vide équivaut à une absence de définition.

Aucun identifiant de forge ne provient de l’environnement : GitHub, GitLab et Bitbucket agissent tous avec la connexion ou le jeton d’un membre, ou avec des jetons d’application GitHub limités à un seul dépôt et bornés par un membre responsable.

### `--sandbox`

Le serveur sonde l’hôte une fois au démarrage et encapsule l’exécution des commandes
des agents dans le bac à sable natif du système d’exploitation lorsqu’un backend est
disponible : `sandbox-exec` (Seatbelt) sur macOS, `bwrap` et `socat` sur Linux et
WSL2. La décision est prise une fois et reste valable jusqu’au redémarrage du serveur.
Il existe trois issues, chacune affichée sur la ligne d’exposition au démarrage :

| `sandbox=`    | Quand                                                                         | Dont les exécutions d’agents démarrent                                                                                                                                       |
| ------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `native`      | Un backend est disponible et `--sandbox` vaut `on`                            | Celles de tous, encapsulées                                                                                                                                                  |
| `off`         | `--sandbox off`                                                               | Celles de tous, sans confinement sur cet hôte                                                                                                                                |
| `unavailable` | `--sandbox on` et aucun backend (Windows, ou Linux sans `bwrap` ni `socat`)   | Seulement les exécutions dont le propriétaire du serveur est responsable, sans confinement. Les autres sont refusées avec « Ce serveur n’a pas de bac à sable : seul son propriétaire peut y lancer des agents. » |

Pour l’automatisation, la personne responsable est celle à laquelle l’automatisation
est liée. Sans propriétaire de serveur enregistré, aucune exécution ne démarre sur un
hôte `unavailable`. Sur Linux et WSL2 avec bubblewrap installé, l’envoi natif échoue
actuellement en mode fermé pour chaque exécution ; voir [Backends de bac à
sable](/fr-CA/manuel/reference/backends-de-bac-a-sable/#linux--bubblewrap).

`--sandbox off` est le choix du propriétaire du serveur pour tous ceux qui utilisent le
serveur : il exécute les agents de chaque membre sans confinement sur cette machine.
Utilisez-le sur un hôte où le profil de bac à sable lui-même se comporte mal, ou pour
permettre aux membres de lancer des agents sur un hôte sans backend. Il n’exige aucune
reconstruction, et le serveur consigne un avertissement pendant toute la durée de vie
du processus, de sorte que l’état n’est jamais silencieux.

### `--tool-deferral`

Les exécutions du harnais intégré envoient un petit ensemble direct de définitions d’outils, plus un index qui ne contient que les noms du reste, dont les schémas se chargent à la première utilisation ou qui sont appelés depuis un script `repl`. Cela maintient l’ensemble toujours visible dans la plage où les modèles choisissent leurs outils de façon fiable. Mesurés sur le registre que construisent les tests, les outils de chat standard de l’agent intégré représentent 14 définitions : environ 16,5 Ko avec `repl` (dont environ 4 Ko pour `repl`, dont la définition ne peut pas dépasser 4 096 octets), environ 13 Ko sur un serveur qui ne peut pas exécuter de scripts. Les outils différés restent appelables par leur nom tout au long de l’exécution, et `search_tools` les trouve par intention. Voir [Contexte des outils et cache de prompts](/fr-CA/manuel/concepts/contexte-des-outils/).

`--tool-deferral off` envoie la définition de chaque outil admis d’emblée, sauf qu’une exécution avec `repl` continue d’appeler depuis des scripts les outils qu’un script peut appeler. C’est le coupe-circuit pour un modèle qui gère mal la surface à deux niveaux — une option plutôt qu’une reconstruction. Il ne touche que le harnais intégré ; le `tools/list` MCP que voient les clients externes correspond au catalogue complet, sauf pour une exécution d’agent sur un serveur qui peut exécuter des scripts en [mode code](/fr-CA/manuel/concepts/mode-code/).

### `--credential-gate`

Une exécution dont l’identifiant du fournisseur est absent ou épuisé est **mise en
attente** plutôt que mise en échec : l’exploitant reçoit une invite pour le corriger,
et l’exécution reprend s’il le fait. Le délai par défaut est de 900 secondes
(15 minutes), borné entre 0 et 3600.

Ce délai est délibérément beaucoup plus long que celui de l’invite d’approbation : une
approbation est une décision qui se prend en quelques secondes, tandis que corriger un
identifiant suppose d’ouvrir un terminal, de se connecter et de revenir. C’est le
plafond qui empêche une exécution non surveillée — une étape de pipeline, un
déclencheur cron, un webhook — d’attendre quelqu’un qui dort. À l’expiration,
l’exécution échoue avec le message qui l’aurait fait échouer de toute façon.

`--credential-gate=0` est le coupe-circuit : rien n’est jamais mis en attente et un
mauvais identifiant met fin au tour exactement comme avant l’existence du contrôle.

### Mode code

Le [mode code](/fr-CA/manuel/concepts/mode-code/) permet à un agent d’exécuter un script JavaScript qui appelle ses outils. Aucune option ne l’active ni ne le désactive : chaque exécution reçoit l’outil `repl` lorsque le serveur peut exécuter des scripts, et un serveur de démonstration public n’en exécute aucun.

Les scripts s’exécutent dans `cc_codemode`, un programme fourni avec le serveur dans `bin/codemode/`. Le serveur ne démarre pas sans lui : il affiche une ligne nommant ce qui manque et quitte avec le code `78`. Au démarrage, il exécute l’autotest de verrouillage du programme et affiche une ligne (silencieuse seulement avec `--log-level error`) :

```text
cc_server: code_mode=available (cc_codemode 0.1.0 quickjs-ng 0.16.2 protocol 2; 16 scripts at once, at most 12 per workspace; up to 64 more runners kept for scripts waiting on a person; heap at most 1024 MiB per script)
cc_server: code_mode=unavailable (<reason>) — runs on this host get no repl tool; scripts never run without full lockdown
```

`unavailable` signifie que le programme ne peut pas se verrouiller sur cet hôte, par exemple dans un conteneur dont le profil de sécurité refuse l’une de ses étapes, ou qu’il ne soit pas un build de publication. Le serveur fonctionne normalement, aucune exécution ne reçoit `repl`, et les réglages du mode code de l’espace de travail affichent la raison.

Le serveur continue de vérifier pendant son exécution. Lorsque le programme ne démarre pas pour une raison qui n’est pas celle du script, le serveur relance l’autotest, au plus une fois par minute. Si celui-ci échoue, le serveur affiche la ligne `unavailable` avec sa raison et n’exécute aucun script : les exécutions qui démarrent entre-temps ne reçoivent pas `repl`, et une exécution qui en dispose déjà appelle directement ses outils ([Lorsque les scripts ne peuvent pas s’exécuter](/fr-CA/manuel/concepts/mode-code/#lorsque-les-scripts-ne-peuvent-pas-sexécuter)). Il continue de vérifier, au plus une fois par minute, et lorsque l’autotest réussit de nouveau, il affiche la ligne `available` et exécute de nouveau des scripts. Seul un autotest ayant échoué au démarrage exige un redémarrage. La raison affichée dans les réglages de l’espace de travail ne contient pas les chemins de l’hôte ; la ligne du journal la donne en entier.

Les deux options du mode code bornent ce que les scripts peuvent utiliser. `--code-mode-max-processes` plafonne les scripts exécutés en même temps dans tous les espaces de travail (par défaut le double du nombre de cœurs du processeur, au plus 16 ; accepté de 1 à 64). Avec un plafond de 2 ou plus, un espace de travail utilise au plus le plafond diminué d’un quart de celui-ci, si bien qu’aucun espace de travail ne peut prendre toutes les places, et les scripts en attente sont admis à tour de rôle entre les espaces de travail. Un script qui attend l’approbation ou la réponse d’une personne cède sa place à un autre script et ne démarre aucun appel d’outil tant qu’il n’a pas reçu de réponse ; jusqu’à quatre fois le plafond de ces scripts en attente sont conservés, et au plus les trois quarts d’entre eux viennent d’un même espace de travail, chacun pouvant tout de même calculer dans sa propre limite de temps processeur. `--code-mode-max-heap-mb` est la mémoire maximale qu’un script peut utiliser.

Une valeur que ces options n’acceptent pas (un nombre hors plage, ou qui n’est pas un nombre) arrête le serveur au démarrage (code de sortie `78`) avec un message nommant les valeurs acceptées. Elle n’est jamais lue comme la valeur par défaut.

## Sous-commandes

| Commande                                      | Ce qu’elle fait                                                                                     |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `cc_server`                                   | Exécute le serveur jusqu’à `SIGINT`/`SIGTERM`                                                       |
| `cc_server pair`                              | Provisionne un appareil et affiche son identifiant et sa clé d’association. Sans risque vis-à-vis d’un répertoire de données qu’un serveur dessert déjà — le serveur en cours d’exécution prend l’appareil en compte sans redémarrage |
| `cc_server connect <command>`                 | Affiche ou modifie le Control Center Connect qu’utilise ce serveur, sans le démarrer                |
| `cc_server update`                            | Vérifie l’existence d’une nouvelle version autonome, la télécharge et la vérifie                     |
| `cc_server --version`                         | Affiche la version de compilation et le SHA git — la même identité qu’annoncent `/healthz` et la poignée de main RPC |

### `pair`

| Option         | Valeur par défaut                                         | Signification                                                                                                                                                        |
| -------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device`     | `web-client`                                              | L’identifiant de l’appareil. La plateforme en est déduite, de sorte que `--device desktop` génère une ligne de bureau et `--device ios`/`android` une ligne de téléphone; toute autre valeur est traitée comme le web |
| `--label`      | le nom de la plateforme suivi du nom d’hôte de cette machine | Nom affiché dans la liste des appareils                                                                                                                             |
| `--host`       | `localhost`, ou `<this-host>` en cas de liaison à toutes les interfaces | Hôte à intégrer à l’URL affichée. Définissez-le sur l’adresse IP du réseau local ou l’hôte du tunnel qu’un client joindra réellement                                 |
| `--client-url` | non défini                                                | Origine du client **web** hébergé. Ajoute un lien profond scannable et un code QR dans le terminal                                                                   |

`pair` accepte aussi les options fondamentales `--data-dir`, `--port` et `--bind` :
elles déterminent le répertoire de données à écrire et façonnent l’URL du serveur
affichée (`ws` sur loopback, `wss` avec `--bind any`). Réexécuter `pair` pour le même
`--device` fait tourner sa clé et ferme les sessions actives de cet appareil. Un
identifiant généré ici n’a **aucune expiration**, contrairement aux 30 jours que fixe
une association faite dans l’application.

:::caution[Le code QR de `--client-url` n’est pas celui du téléphone]
`pair --client-url` remplit le formulaire de connexion du client **web** (URL du
serveur, identifiant de l’appareil et clé dans le fragment de l’URL). Le téléphone
s’associe avec une charge utile différente, générée à partir du panneau d’association
de l’application — le descripteur de connexion complet du serveur, plus une expiration.
Les deux ne sont pas interchangeables — voir
[Associer un appareil](/fr-CA/manuel/guides/associer-appareil/).
:::

### `connect`

Lit et écrit les mêmes réglages que la carte **Control Center Connect** dans
**Paramètres → Serveur → Authentification unique**, à partir du répertoire de
données. Un serveur en cours d’exécution prend en compte une modification dans
les 10 minutes ou au redémarrage.

| Commande | Ce qu’elle fait |
| --- | --- |
| `cc_server connect status` | Affiche le mode, l’URL, si `CC_CONNECT_URL` le verrouille, l’identifiant d’installation, l’état de santé et la source de chaque voie (`own`, `connect` ou `off`) |
| `cc_server connect enable` | Utilise le Connect hébergé de Control Center |
| `cc_server connect enable --url <url>` | Utilise un Connect personnalisé à cette URL (HTTPS, ou `http` sur la boucle locale) |
| `cc_server connect disable` | Cesse d’utiliser Connect. Seules les apps propres au serveur connectent les gens |

`status` sans commande est le comportement par défaut. Chaque commande accepte
`--data-dir`. `CC_CONNECT_URL` l’emporte sur ce qu’elles enregistrent. Une
commande inconnue se termine avec `64`. Voir
[Control Center Connect](/fr-CA/manuel/reference/connect/) pour les modes,
l’identité d’installation et les codes d’état.

### `update`

`--apply` remplace l’installation; elle est refusée tant qu’un serveur répond encore
sur le port configuré, à moins de passer `--force`. `--allow-downgrade` permet une
version antérieure.

La commande refuse carrément, avec une explication plutôt qu’une erreur, les
installations qu’elle ne possède pas :

| Environnement                 | Détecté par                                 | Ce qu’elle dit                                              |
| ----------------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| Le serveur intégré de l’application de bureau | `CC_EMBEDDED=1` ou `CC_BOOTSTRAP_DEVICE_ID` | Mettez plutôt l’application à jour — l’installateur remplace tout l’arbre |
| Une copie de source `dart run` | le chemin du script se termine par `.dart`  | Mettez-la à jour avec git                                   |
| Docker                        | les marqueurs de conteneur                  | Récupérez une image plus récente                            |

## Cycle de vie du processus

`cc_server` s’exécute jusqu’à `SIGINT` / `SIGTERM`. Une variable d’environnement
supplémentaire régit ce comportement, et c’est l’application de bureau qui la définit,
pas vous :

| Variable                | Effet                                                                                                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `CC_EXIT_WITH_PARENT=1`  | Le serveur quitte lorsque son processus parent quitte, ce qui est détecté par la fermeture, par le parent, de l’extrémité d’écriture de son tube stdin. L’application de bureau la définit pour qu’une application plantée ne laisse jamais un serveur orphelin qui occupe le répertoire de données |

Ne la définissez vous-même que si vous supervisez `cc_server` comme processus enfant
et souhaitez la même garantie.

`DO_NOT_TRACK=1` (toute valeur autre que vide, `0` ou `false`) arrête les
[statistiques d’utilisation](/fr-CA/manuel/reference/statistiques-utilisation/) propres au serveur, même
quand l’interrupteur global du serveur est activé. Les clients continuent de suivre l’interrupteur.

## Organisation du répertoire de données

Le répertoire de données par défaut est `~/Library/Application Support/control-center`
sur macOS, `%APPDATA%\control-center` sur Windows et
`$XDG_DATA_HOME/control-center` (sinon `~/.local/share/control-center`) ailleurs. Un
`.cc_server` relatif au répertoire de travail courant n’est utilisé que lorsqu’aucun
répertoire personnel ou de données d’application ne peut être résolu.

Le serveur garde le répertoire de données privé à son propre compte (`0700`). Il refuse de démarrer (code de sortie `78`) lorsqu’il ne peut pas le faire, lorsque `global.db` est endommagé ou a été écrit par une version plus récente, ou lorsque son fichier d’identité ne peut pas être lu.

| Chemin                            | Contenu                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------- |
| `global.db`                       | Le registre des espaces de travail, les utilisateurs, les appareils associés, le fil de nouvelles et la file d’attente de la flotte |
| `<workspaceId>/workspace.db`      | Une base de données par espace de travail — agents, espaces, tickets, mémoire |
| `<workspaceId>/code_index.db`     | Le graphe de code de cet espace de travail. Reconstruit lorsqu’il manque, jamais sauvegardé |
| `pre_upgrade/`, `<workspaceId>/pre_upgrade/` | Les deux copies les plus récentes d’une base de données antérieure à une mise à jour qui a changé son format |
| `<workspaceId>/chat_credentials/` | Jetons des robots de clavardage, en JSON brut, pour qu’ils suivent l’espace de travail |
| `secrets.json`                    | Clés d’association, clé d’installation Connect, apps des fournisseurs, connexions des gens (scellées quand elles passent par Connect), secrets de webhook, SSO (`0600`) |
| `backups/<timestamp>/`            | Un instantané d’installation — `manifest.json`, `global.db` et une copie de chaque espace de travail |
| `backups/exports/`                | Exportations d’un seul espace de travail, `<workspaceId>-<timestamp>.db`         |
| `backups/transfer/`               | Zone de transit pour les téléchargements et téléversements de sauvegardes; purgée par la route qui l’écrit |
| `models/`                         | Modèles d’incorporation, de diarisation et de reconnaissance vocale exécutés sur l’appareil |
| `codemode/` | Une copie de développement de l’exécuteur du mode code, installée par `scripts/natives/build_codemode.sh` ; les paquets de version le contiennent dans `bin/codemode/` |
| `meetings/<meetingId>/`           | Audio de réunion conservé                                                       |
| `rigs/images/`                    | Images disque de rigs importées (la surface de bureau QEMU)                      |
| `rigs/smolvm/<rigId>/`            | État d’exécution de la microVM de chaque rig (le secret du courtier, `0600`)     |
| `rigs/smolvm-packs/`              | Paquets de machines préextraits — le cache qui accélère les démarrages répétés de rigs |
| `rigs/tls/`                       | L’autorité de certification du domaine de développement pour le HTTPS des rigs (clés `0600`) |
| `rigs/run/<rigId>/`               | Surcouches QEMU, images d’amorçage et clés par machine virtuelle (`0600`)        |
