## イベントバス

`DomainEventBus` はインプロセスのブロードキャスト型パブリッシュ/サブスクライブバスです。パブリッシャーは `publish(event)` を呼び出し、サブスクライバーは型付きの `on<T>()` ストリームを消費します。すべてのイベントは `DomainEvent` を実装し、`occurredAt` を保持します。

**バスは `cc_server` の内部で動作します。** すべてのパブリッシャーと、稼働中のすべてのサブスクライバーはそこに存在します。このバスを目にするクライアントはありません。サーバーが厳選されたサブセットを `notifications/*` JSON-RPC フレームとして転送し、サブスクライバーごとにワークスペースのメンバーシップでフィルタリングします。

| 項目                                                        | 数                                          |
| ----------------------------------------------------------- | --------------------------------------------- |
| 具象イベントクラス                                          | 54                                          |
| ソースファイル（`packages/cc_domain/lib/core/domain/events/`） | 14（および `domain_event_bus.dart`）        |
| 直接発行されない抽象基底                                    | 1（`TaskLifecycleEvent`、sealed 階層）      |

以下のカタログにあるすべてのイベントは、この 1 つのディレクトリに存在します。ほかで宣言されているドメインイベントはありません。

## タスクライフサイクルのイベント

統合されたタスクライフサイクルのストリームです。ディスパッチされた 1 回のエージェント実行を、実行ログの id でキー付けします。すべてのイベントが `taskId`、タスクごとに単調増加する `seq`、`workspaceId?`、`agentId?`、および `phase` を保持します。以下の行は追加フィールドのみを挙げています。

| イベント                    | ペイロード                    | 発行されるタイミング                                                                             |
| --------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `TaskDispatched`            | —                             | タスクが実行のためにバックエンドに渡されたとき                                                   |
| `TaskRunning`               | —                             | タスクが出力を生成し始めたとき                                                                   |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | タスクが待機したとき。別のタスクが必要なオンディスクのパスロックを所有しています                 |
| `TaskProgress`              | `note?`                       | 実行途中の進捗チェックポイント                                                                   |
| `TaskMessage`               | `messageType`, `content`      | ストリーミングされたメッセージ（text/thinking/tool_use/tool_result/error）。`progress` フェーズで報告されます |
| `TaskCompleted`             | `summary?`                    | タスクが正常に終了したとき                                                                       |
| `TaskFailed`                | `errorMessage`                | タスクがエラーで終了したとき                                                                     |
| `TaskCancelled`             | —                             | タスクが完了前にキャンセルされたとき                                                             |

`TaskPhase` enum には `queued` メンバーもありますが、queued イベントを発行するものはありません。`TaskQueued` クラスは存在しません。タスクで最初に観測できるフレームは `TaskDispatched` です。

| `RigClosedEvent`    | `workspaceId`, `rigId`, `reason`              | リグがクローズ理由とともに消滅したとき。コンシューマーが作用するのは `backendFailure` のみで、それ以外の理由は要求されたものか、`RigReaped` を伴うものです |

リグの**オープン**はイベントではありません。ブートが完了してリグの行が ready に切り替わるだけで、何も発行されません。したがってサブスクライブできる `RigOpened` は存在しません。

## イベントをまったく持たないサブドメイン

外から見るとイベント駆動に見えるのに、そうではないサブシステムがいくつかあります。ここに挙げるのは、フックを探しに行く前に知っておく価値のある設計判断として、それらが存在しないからです。

| サブドメイン        | 代わりに状態がどう動くか                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| メモリ              | `record_memory_fact` などが書き込んで返し、recall が読み取ります。ファクトや競合で発行されるものはありません |
| オーケストレーション | 提案、その承認、生成されたパイプライン実行は、行と RPC 呼び出しです                                      |
| プランドキュメント  | `submit_plan` がリビジョンを書き込み、承認がオーケストレーションを実体化します。どちらもアナウンスされません |
| アーティファクト    | `publish_artifact` / `revise_artifact` がリビジョンを直接書き込みます                                    |
| 承認                | エスカレーションは承認ワークフローサービスの内部で処理されます                                          |
| チケット同期        | ベンダーコーディネーターが上記のチケットイベントをサブスクライブします。受信 Webhook は直接適用されます  |
| カレンダー更新      | 同期が予定を upsert し、クライアントが再読み取りします。更新のブロードキャストはありません              |
| ワークツリーのマージ | `worktree_merge_log` に記録され、そこから読み取られます                                                |

## 通知のマッピング

サーバーでは、`NotificationFeedRecorder` と `RemoteEventForwarder` がこれらのイベントを `notifications/*` ワイヤフレーム（`notification_wire.dart`）に変換します。クライアントでは、`RpcNotificationMapper` → `mapNotificationFrame` がフレームを `AppNotification` に変換します。

通知カテゴリはちょうど **17** 個あります。いくつかのイベントは複数のワイヤメソッドにマッピングされます。フレームがエッジ（失敗か復旧か）を運び、カテゴリが問い（「CI は何をしているか」）を運ぶからです。

| ---------------------- | ------------------------- | ------------------------------------------------------------------------ |
| `newMessage`           | `MessageReceived`         | `notifications/message_received`（あなたへのメンション）                          |
| `agentRunCompleted`    | `MessageReceived`         | `notifications/message_received`（`is_agent_message`、あなたへのメンションなし）     |
| `agentAwaitingInput`   | `AgentAwaitingInput`      | `notifications/agent_awaiting_input`                                   |
| `ticketAssigned`       | `TicketAssigned`          | `notifications/ticket_assigned`                                        |
| `ticketStatusChanged`  | `TicketStatusChanged`     | `notifications/ticket_status_changed`                                  |
| `pullRequestPublished` | `PullRequestPublished`    | `notifications/pr_published`                                           |
| `prMerged`             | `PrMerged`                | `notifications/pr_merged`                                              |
| `prMerged`             | `ExternalPrMerged`        | `notifications/external_pr_merged`                                     |
| `prMentioned`          | `PrMentioned`             | `notifications/pr_mentioned`                                           |
| `prMentioned`          | `PrCommentMentioned`      | `notifications/pr_comment_mentioned`                                   |

| `prChecksStatus`       | `PrChecksStatusChanged`   | `notifications/pr_checks_failed` / `pr_checks_recovered`               |

| `prThreadActivity`     | `PrThreadResolved`        | `notifications/pr_thread_resolved`                                     |

リグのテイクオーバーのフレームは、ハンドルを握った本人には返送されません。解放はフィルタリングされず（イベントは誰が手放したかを記録しません）、`backendFailure` によるクローズだけが `rig_closed` フレームを生成します。それ以外の理由は、要求されたものであるか、回収のフレームですでにカバーされています。

`AgentAwaitingInput` は `AgentAwaitingInputPublisher` が発行します。このパブリッシャーは承認と認証情報ブロックのレジストリを監視して新しいエントリを検出し、`ask_user` の各質問については `AgentQuestionService` から通知を受けます。1 回の待機が 1 つのイベントです。待機が終わったときには何も発行されません。

5 つの自作 PR カテゴリは `forUserId` を保持するため、ワークスペースの全員ではなく作成者に届きます。

`RemoteEventForwarder` はさらに、`TicketReassigned` を `notifications/ticket_reassigned` として、すべての `TaskLifecycleEvent` を `notifications/task_<phase>` として転送します。どちらも通知カテゴリにはマッピングされません。これらは通知センターではなく、ライブ UI を駆動します。メンバーシップイベントはフレームとして転送されません。それらはフォワーダーのキャッシュを無効化し、セッションホストは削除されたメンバーのワークスペース購読を破棄します。
