:::caution[実行がサンドボックス化されるかどうかはホスト次第です]
`cc_server` は、このホスト上でエージェントをどのように実行するかを起動時に一度決定し、その決定は再起動するまで有効です:

- **サンドボックス化**（`native`）: プローブがバックエンドを見つけ、かつ `--sandbox` が `off` ではありません。両方のディスパッチ継ぎ目がラップされます。Claude Code CLI はサンドボックスポートを経由し、ACP と内蔵ハーネスの `bash` ツールはサンドボックスマネージャーを経由します。
- **オフ**（`off`）: サーバーオーナーが `--sandbox off` で起動しました。誰が起動したかに関係なく、すべてのメンバーのエージェントがこのマシン上で制限なしに動きます。
- **利用不可**（`unavailable`）: サンドボックスはオンですが、プローブがバックエンドを見つけませんでした（**常に Windows**、および `bwrap` と `socat` のない Linux または WSL2）。実行が開始されるのは、その実行に責任を負う人がサーバー[オーナー](/ja-JP/マニュアル/コンセプト/認可/#サーバーオーナー)である場合だけです。つまり、依頼した人、または紐付けられた人の自動化です。それ以外の人の実行は、認証情報の発行、リースの取得、プロセスの開始の前に拒否されます。記録されたオーナーがいない場合、誰の実行も開始されません。

拒否された実行は、`sandbox_unavailable` コードで失敗します。アプリでは **エージェントにはこのサーバーのサンドボックスが必要です** と表示され、「このサーバーにはサンドボックスがないため、ここでエージェントを実行できるのはそのオーナーだけです。オーナーはサンドボックスをインストールするか、全員のサンドボックスをオフにできます。」と説明されます。

サンドボックスなしで開始される実行（`off` の下、または `unavailable` の下でのオーナー自身の実行）は、ホスト上で直接動作します。ACP とハーネスの `bash` ツールは、それでも環境のサニタイズ付きでスポーンします。Claude Code は `NoSandboxAdapter` を経由し、ホストの環境を継承します。残る境界は、実行自身のワークツリー（`rift` が同梱される場所ではコピーオンライト、Windows では `git worktree`）、起動ごとにブローカー経由で発行され、終了時に取り消される読み取り専用のフォージトークン、エージェント実行ゲートウェイでプッシュのルールを通過しなければならないプッシュ、モードごとのコマンドポリシー、統一された[アクションガードレール](/ja-JP/マニュアル/コンセプト/ガードレール/)（フェイルクローズド）、ACP とハーネスの `bash` の経路における環境のサニタイズ、そしてそのモードが許可するツールサーフェスです。

ハーネスのインプロセスのファイルツール（read、write、edit、apply patch、search、find、search_files）は、どのホストでもサンドボックスの外側にあります。これらはサーバープロセス内で動作するため、ラップされるのは `bash` だけです。

サーバーがサンドボックス化されている場合、ホストはフォールバックになりません。サーバーがエージェントをサンドボックス化しているのに実行に与えるサンドボックスがない場合、そのツールプロセスと `bash` コマンドは、ホストで開始されるのではなく拒否されます。同じ姿勢が、実行の周囲の小さなプロセスも決定します。ACP のワンショットヘルパー（会話のタイトル、`/btw`、`/handoff`、`/goal`）と、Review Studio におけるプルリクエストのゴールデンテストは、サーバーがエージェントをサンドボックス化している場合はサンドボックス内で、`off` の下では制限なしで、`unavailable` の下ではサーバーオーナーが責任を負うリクエストに限って実行されます。それ以外はスキップされます。
:::

## バックエンドの概要

| バックエンド     | 値     | プラットフォーム                                      | 可用性                                                                                                      |
| ----------- | --------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 閉じ込め VM | `microvm` | macOS、Linux、Windows（microVM ハイパーバイザー）    | microVM ランタイムを対象にプローブでゲートされます。対話ターミナルに適用されます — シェルはホスト上ではなく [リグ](/ja-JP/マニュアル/コンセプト/リグ/) の内部で動作します |
| ネイティブ      | `native`  | macOS（Seatbelt）、Linux と WSL2（bubblewrap） | 起動時にプローブされます。Linux では、bubblewrap が強制できないファイル名 glob の書き込み拒否を必要とする実行を拒否します |
| なし      | `none`    | すべて                                           | パース時のデフォルトとターミナルのデフォルトです。`--sandbox off` の下ではエージェントのディスパッチがこれを使い、利用できるバックエンドがない場合はオーナー自身の実行にだけ使われます |

`SandboxBackend.fromName` は、保存された値が null または認識できない場合に `none` を返します。

**`microvm` はカーネル境界を持つ唯一のバックエンドです** — ワークロードは
本当にホスト上では動作しません。どちらの方向でも暗黙のフォールバックには
なりません。VM を起動できないホストで明示的に要求すると明確に失敗します
（「VM を要求したのに手元のノート PC が返ってきた」は、エンクロージャーが
許容できない唯一の劣化です）。そして `native` に降格するのは*指定されていない
デフォルト*だけであり、その旨がログ行に出力されます。セッションの実際の
バックエンドはクライアントに報告されてバッジ表示されるため、ターミナルが
ホスト上で動作しながら閉じ込められていると主張することは決してできません。
VM 自体のライフサイクル、イメージ、エグレスについては、[リグのリファレンス](/ja-JP/マニュアル/リファレンス/リグ/)で説明しています。

**Windows にはネイティブサンドボックスがありません。** `NativeSandboxAdapter.probe` は、macOS または Linux/WSL2 以外のすべてのホストで `available: false` を返すため、Windows のサーバーは `unavailable` になります。オーナーのエージェントの実行だけが制限なしで開始され、それ以外の人の実行は拒否されます。すべてのメンバーがそこでエージェントを実行できるようにするには、オーナーが `--sandbox off` でサーバーを起動します。これにより、すべての実行が制限なしで動作します。`microvm` バックエンドは別系統です。microVM ランタイムを対象にプローブでゲートされ、ホスト上の `bash` のラップではなく、対話ターミナルとリグに適用されます。

## プローブの結果

強制をゲートするのはプローブです。プローブはサーバーの起動時に一度だけ実行されます。

| ホスト                                   | `available` | 注記 / ヒント                                                               |
| -------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS                                  | `true`      | `sandbox-exec`（Seatbelt） — 名前空間の分離であり、カーネル境界はありません       |
| `bwrap` と `socat` のある Linux または WSL2 | `true`      | bubblewrap — 名前空間の分離であり、カーネル境界はありません                      |
| いずれかのツールを欠く Linux または WSL2      | `false`     | `requiresInstall: true`、不足しているパッケージを名指しするインストールのヒント付き |
| その他のプラットフォーム                     | `false`     | このプラットフォームではネイティブサンドボックスは提供されません                            |

サーバーは結果を起動時の 1 行でログに記録します。`agent sandbox ON` とその注記、`no OS-native agent sandbox on this host` とそのヒント（それに加えて、オーナーが責任を負う実行だけが開始されることが示されます）、または `agent sandbox DISABLED by --sandbox off` のいずれかです。起動時に表示される公開の行には、同じ決定が `sandbox=native`、`sandbox=off`、`sandbox=unavailable` のいずれかとして示されます。`GET /healthz` にサンドボックスのフィールドはありません。

`--sandbox` / `CC_SERVER_SANDBOX` は `on`（デフォルト）または `off` を受け付けます。`on` は、ホストがバックエンドを提供する場合にすべての実行をラップし、提供しない場合はオーナーの実行だけを許可します。`off` はこのホスト上ですべてのメンバーのエージェントを制限なしで実行します。これは実行ごとの設定ではなく、全員に対するオーナーの選択です。

## ネイティブバックエンド

### macOS: Seatbelt

Apple の Seatbelt サンドボックス機構（macOS App Sandbox が使うのと同じシステム）を使用します。

生成されるプロファイルは**デフォルトで許可**（`(allow default)`）であり、そこから拒否を切り出します。完全なデフォルト拒否のプロファイルでは対話シェルが使えなくなるからです — 列挙するには dyld、XPC、Mach の呼び出しが多すぎます。実際上の結果として、エージェントは依然としてホストのほとんどを読み取れます。登録済みのチェックアウトは、不可視化によってではなく、明示的な書き込みと名前変更の拒否によって保護されます。

- **ファイルシステムの読み取り**: シークレットパス（`~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config/gh`、`~/Library/Keychains`、および読み取り拒否セットの残り）は拒否されます
- **ファイルシステムの書き込み**: 拒否にリセットしてから、明示的なサブパスの許可を加えます。必須拒否パス（シェルの rc ファイル、`.git/hooks`、Claude の設定、保護されたチェックアウト）は、書き込み可能なルートの内部であってもブロックされます。`file-write-unlink` は、すべての拒否パスとその祖先で拒否されるため、名前変更で書き込み拒否を回避することはできません
- **プロセス**: `process-exec` は常に危険なバイナリを拒否し、さらに書き込み可能なディレクトリからの実行をブロックします。ホーム配下の既知のツールチェーンのインストール先ディレクトリ（corepack、`npx` と `pnpm dlx` のキャッシュ、Node のバージョンマネージャー、Playwright のブラウザー、rustup と cargo、Go、fvm と pub キャッシュ、pyenv、uv と pipx、rbenv、sdkman、mise、asdf、`~/.local/bin`）は、そのブロックの下で再び開かれます。共有の一時ディレクトリもブロックされます。代わりに各セッションには `/private/tmp` 配下のプライベート `TMPDIR` が与えられ、そこでエージェントがビルドしたプログラム（`go test` のバイナリや cargo のビルド）を実行できます。常に危険なバイナリの拒否は、これらの許可の後に適用されます
- **ネットワーク**: インプロセスのプロキシポートと DNS に制限されます — ループバックが一律で許可されることはなく、TCP の待ち受けは拒否されます。Unix ソケットは、セッション専用の `TMPDIR` の内側でのみ許可されます。ここには IPC ソケットを置く tsx や Chrome などのツールが含まれます。SSH エージェントやその他のソケットには引き続き到達できません。プロキシがセッションごとのドメイン許可リストを強制します（[ネットワークエグレス](#ネットワークエグレス) を参照）
- **構成**: プロファイルは起動ごとに `SandboxSpec` から生成されます
- **サーバー自身のコマンド**: サーバーがプログラムを実行するフォルダー（`PATH` のすべてのエントリと、`~/.local/bin` などの一般的なユーザーごとのツールフォルダー。`~/fvm/default` などのバージョンマネージャーのリンクは解決されます）の直下にあるものは、作成、置換、削除、名前変更できません。リンクが指すコマンドがインストールされたパッケージも同様です。[サーバーのコマンドフォルダー](#サーバーのコマンドフォルダー)を参照してください
- **起動時のファイル**: プロファイルが読み取りを拒否するすべてのホームパスは、書き込みも拒否されます。また、サーバーユーザーのシェルとセッションの起動時のファイル（`.zshenv`、`.zlogin`、`.bash_login`、fish の設定、systemd のユーザーユニット、自動起動エントリなど）は、すべてのモードで書き込みが拒否されます

要件:

- `sandbox-exec`（`/usr/bin/sandbox-exec`）。すべての macOS インストールに含まれます — 追加のツールは不要です

### Linux: bubblewrap

bubblewrap（`bwrap`）を使ってマウント名前空間と PID 名前空間を作成します。

- **ファイルシステム**: バインドされたパスだけが見えるマウント名前空間を作成します
- **ネットワーク**: 共有されていないネットワーク名前空間で動作します。トラフィックは `socat` の Unix ソケットブリッジを通ってホストのプロキシに到達します
- **プロセス**: PID 名前空間の分離
- **サーバー自身のコマンドと起動時のファイル**: macOS と同じ保護を、bubblewrap のバインドとして表現します。Linux ではまだ検証されておらず、そこではコマンドフォルダーが欠けている場合にまだ作成されることがあります

要件:

- `bubblewrap` と `socat` がインストールされていること（Debian/Ubuntu では `sudo apt-get install bubblewrap socat`）
- カーネルの名前空間サポート（現代の Linux では標準）

bubblewrap は既存のパスを覆い隠すことはできますが、書き込み可能なバインドの内部で*新しい* `.env`、
`*.key`、`*.pem` ファイルを禁止することはできません。標準のディスパッチポリシーは
これらのファイル名 glob の拒否を要求するため、現在ネイティブのエージェント
ディスパッチは、**プローブが bubblewrap を見つけた場合でも Linux/WSL2 では
フェイルクローズドします**。黙って弱められたポリシーで動作することはありません。
Linux のネイティブディスパッチを復活させるには、作成時のファイル名ルールを
備えたバックエンドが必要です。サンドボックス化を無効にするのは、明示的な
非閉じ込めのオプトアウトであり、同等の回避策ではありません。

実際には、Linux または WSL2 のサーバーは現在、次の 2 つのいずれかの方法でエージェントを実行します。`--sandbox off` で起動した場合は、すべてのメンバーのエージェントを制限なしで実行します。bubblewrap または `socat` がインストールされていない場合は `unavailable` となり、サーバーオーナーのエージェントだけを制限なしで実行します。両方のツールがインストールされ、サンドボックスがオンの場合は、オーナーのものを含め、すべての実行がフェイルクローズドします。

## サーバーのコマンドフォルダー

サーバーは、起動時に一度、プログラムを実行するすべてのフォルダーを見つけます。それは `PATH` の各エントリ、サーバーが探索するユーザーごとのツールフォルダー（`~/.local/bin`、`~/.bun/bin`、npm、yarn、pnpm のグローバルフォルダーなど）、そしてその途中のすべてのリンクの背後にある実際のフォルダーです（`~/fvm/default` などのバージョンマネージャーのリンク、または fnm のデフォルト）。サンドボックス内では、エージェントはそれらのフォルダー内のコマンド、そのコマンドへのリンク、リンクされたコマンドが指すインストール済みパッケージを、追加、置換、削除、名前変更できず、その上のフォルダーを名前変更することもできません。そうでなければ、サンドボックス化された実行が、後でサーバーや人がサンドボックスの外で開始するプログラムを仕込めてしまうからです。

これが実行に与える変化は次のとおりです。

- サンドボックス化された実行の内部からのグローバルインストールは、「Operation not permitted」で失敗します。`npm i -g`、`pnpm add -g`、`yarn global add`、`bun add -g`、`corepack enable`、`pipx install`、`uv tool install`、そして bin フォルダーがサーバーの `PATH` にある場合の `cargo install`、`go install`、`dart pub global activate` です。
- デフォルトのバージョンの切り替えも同様に失敗します（`fnm default`、`nvm alias default`、`fvm global`）。ツールが自分自身をその場で更新する場合も同様です。
- プロジェクトローカルのインストール（`node_modules/.bin`）、`npx`、`pnpm dlx`、corepack が管理するパッケージマネージャー、SDK のキャッシュ、通常のビルドは、引き続き動作します。

エージェントが使えるグローバルツールにするには、サーバーのユーザーとして、サーバー自体にそのツールをインストールし、新しいコマンドも保護されるようにサーバーを再起動します。またはプロジェクトにインストールしてください。サーバーの起動後にインストールされたコマンドは、次の起動から完全に保護されます。

macOS で強制され、テストされています。Linux では、同じルールが bubblewrap のバインドとして表現されますが、まだ検証されていません。Windows にはサンドボックスがありません。

## なしバックエンド

サンドボックス化はありません。プロセスはホスト上で直接動作し、ホストのファイルシステム、ネットワーク、プロセスへのアクセスを持ちます。ACP とハーネスの `bash` ツールには依然として環境のサニタイズとコマンドポリシーが適用されます。`NoSandboxAdapter` 経由の Claude Code はホストの環境を継承します。エージェントのディスパッチは、`--sandbox off` の下ではすべての実行にこれを使い、利用できるバックエンドがないホストではオーナー自身の実行にだけ使います。それ以外の人の実行はそこで拒否されます。ターミナルの場合はホストのシェルであり、それを開けるのはサーバーオーナーだけです。

## サーバーがホストするターミナル

サーバーがホストするターミナルがホストのシェルを開くのは、サーバーの[オーナー](/ja-JP/マニュアル/コンセプト/認可/#サーバーオーナー)だけです。それ以外の人には、エージェントの制限を持つサンドボックス化されたターミナルが、ワークスペース自身のディレクトリ内で与えられます。

セッションのバックエンドの選び方は次のとおりです。

| 要求 | サーバーオーナー | それ以外の人 |
| --- | --- | --- |
| 何も指定しない | サーバーのデフォルトバックエンド | デフォルト。ただし `none` は `native` に置き換えられます |
| `none`（ホストのシェル） | ホストのシェル | 拒否されます。ホストのシェルはサンドボックスなしでサーバー上で動作するためです |
| `native` | ネイティブサンドボックス、オーナープロファイル | ネイティブサンドボックス、エージェントプロファイル |
| `microvm` | 閉じ込め VM | 閉じ込め VM |
| 未知の名前 | 拒否 | 拒否 |

- **オーナープロファイル。** `$HOME` とセッションの作業ディレクトリは書き込み可能で、ネットワークは開いており、`~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config/gh`、`~/Library/Keychains` は読み取りが拒否されます。
- **エージェントプロファイル**（`memberTerminalSandboxConfig`）。そのワークスペースでエージェントが実行されるのと同じポリシーです。書き込みは作業ディレクトリ、プライベートの実行ディレクトリ、`/tmp`、およびエージェントが書き込める `$HOME` の一部にとどまります。シークレットは読み取りが拒否されます。ネットワークはエージェントのエグレス許可リストです。プログラムは作業ディレクトリと、インストール済みのツールチェーンからのみ実行されます。
- ターミナルは、ワークスペース自身のディレクトリの内側でのみ開きます。その外側の作業ディレクトリは拒否され、別のものに置き換えられることはありません。
- ターミナルを開いた本人だけが、それを読み、入力し、サイズを変更し、閉じることができます。それ以外の人には、その ID は未知のものに見えます。
- 要求された `microvm` がリグサービスのないホストで明示的に指定された場合、フォールバックせずに失敗します。そのようなホストでの `microvm` のデフォルトは `native` に降格し、ログにその旨が記録されます。

読み取り専用のフォージトークンとプッシュのゲートウェイは、ターミナルには適用されません。それらはディスパッチの関心事です。ラップがサポートされていない場合、セッションは、ホストシェルのセッションにサンドボックスのバッジを表示するのではなく、失敗します。

## ネットワークエグレス

サンドボックスが起動されると、外向きのネットワークアクセスはカーネルのファイアウォールルールではなく、インプロセスのプロキシによって強制されます。サンドボックス化されていない実行（`--sandbox off` の下のすべての実行、またはバックエンドのないホストでのオーナーの実行）は、これの恩恵を受けません。そこでスポーンされたプロセスは、サーバーユーザーとまったく同じようにネットワークに到達します。

- サンドボックスランタイムは、`cc_server` プロセス内の `127.0.0.1` で HTTP/HTTPS プロキシと SOCKS5 プロキシを実行します。**制限付きセッションごとに 1 組**です（`http_proxy.dart`、`socks_proxy.dart`）。同時に動作する実行が 1 組のペアを共有することはありません。
- サンドボックス化されたプロセスはプロキシの環境変数を受け取ります（`HTTP_PROXY`/`HTTPS_PROXY` → HTTP プロキシ、`ALL_PROXY` → SOCKS プロキシ。`GIT_SSH_COMMAND` は git-over-SSH を SOCKS プロキシ経由にルーティングします）。Linux ではネットワーク名前空間が共有されていないため、プロキシが唯一の出口です。macOS ではサンドボックスがホストのループバックを共有し、プロキシと直接通信します。
- 各接続のターゲットホストはセッションのドメイン許可リストと照合されます。それ以外は拒否されます。ワイルドカードの形式は 2 つあり、いずれも `*` はちょうど 1 つです。先頭の `*.example.com` は任意のサブドメイン（`a.b.example.com` を含む）に一致しますが、頂点ドメイン自体には一致しません。中間ラベルの `bedrock.*.amazonaws.com` はちょうど 1 つのラベルに一致します（`bedrock.us-east-1.amazonaws.com` には一致しますが、`bedrock.evil.attacker.amazonaws.com` には一致しません）。
- 許可リストは、セッションごとに、厳選されたベースライン（`kBaselineAllowedDomains`: LLM プロバイダー、Git ホスティング、パッケージレジストリ）、GitHub のドメイン（`kGithubDomains`）、さらに `SandboxSpec.egressAllowlist` から解決されます。ディスパッチ経路は追加の `egressAllowlist` エントリを決して渡さないため、実際にはすべての実行がベースラインと GitHub を取得します。
- 固定の拒否リスト（`kBaselineDeniedDomains`: クラウドメタデータのエンドポイント、テレメトリの送信先）は、すべての許可より優先されます。
- `networkEnabled: false` でも、セッションごとのプロキシは起動しますが、許可リストが空であるため、外向きの接続はすべて拒否されます。ディスパッチは実行の開始時に**ネットワークにアクセス**のルールからこの値を設定します: 拒否はネットワークをオフにし、許可と先に確認はオンのままにします。

## SandboxSpec

`SandboxPort.launch` に渡される仕様:

| フィールド             | 型                                        | 説明                                                                                                                                 |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | 安定したセッション識別子（通常はスペース id）                                                                                          |
| `workspaceId`     | `String`                                    | 所有するワークスペースの id                                                                                                                         |
| `agentId`         | `String?`                                   | 現在サンドボックスにバインドされているエージェント（存在する場合）                                                                                                |
| `bindMounts`      | `List<SandboxBindMount>`                    | ホスト→ゲストのマウント。サンドボックスはここに列挙されたホストパスだけを見ます                                                                         |
| `networkEnabled`  | `bool`（デフォルト `true`）                     | ディスパッチ時にネットワークエグレスのルールから設定されます（拒否に解決された場合にのみオフ）。オフの場合、セッションごとのプロキシは起動しますが、許可リストが空であるため、外向きの接続はすべて拒否されます |
| `egressAllowlist` | `List<String>`（デフォルト `[]`）               | 追加で許可するエグレスドメイン。ワイルドカードをサポートします（`*.example.com`、および 1 ラベルの中間形式）。ディスパッチがこれを設定することはないため、ラップされた実行は厳選されたベースラインと GitHub ドメインを取得します |
| `guestWorkdir`    | `String?`                                   | サンドボックス内のデフォルトの作業ディレクトリ。個々の `exec` 呼び出しで上書きできます                                                       |
| `mode`            | `Mode`（デフォルト `chat`）                     | ファイルシステムの書き込みルールを切り出します。`chat` はバインドマウントを書き込み可能に保ち、`review`、`plan`、`orchestrate` は読み取り専用です                      |
| `protectedPaths`  | `List<String>`（デフォルト `[]`）               | どのモードでも、サンドボックス内で決して書き込み可能にしてはならないホストパス                                                                      |
| `runnerStateDirs` | `List<String>`（デフォルト `[]`）               | ランナーが自身の状態を保持するホストディレクトリ。どのモードでも書き込み可能です（現在は Control Center が管理する `CLAUDE_CONFIG_DIR` です） |
| `execGrantRoots`  | `List<String>`（デフォルト `[]`）               | macOS で書き込み可能ディレクトリの exec ブロックを再び開く、オペレーターが承認したディレクトリツリー。Linux では無視されます — bwrap には再度開くべき `$HOME` の exec ブロックがありません |

`protectedPaths` は、登録済みの元のリポジトリチェックアウトを保持し、ディスパッチごとにワークスペースのリポジトリから解決されます。エージェントは会話ごとのコピーオンライトのワークツリーでのみ作業するため、元のチェックアウトはサンドボックス内から決して書き込み可能にしてはなりません — macOS では、そうしなければ Seatbelt の `$HOME` への一律の書き込み許可により、`bash` 経由でそれらが書き込み可能なままになってしまいます。これらは `chat` を含むどのモードでも、シークレットの書き込み拒否セットに加わります。

すべての読み取り拒否パスと書き込み拒否パスは、その文字どおりの綴りと、シンボリックリンクを解決した綴りの両方で出力されます。カーネルは拒否ルールを解決後のパスと照合するため、シンボリックリンクのパスに対して書かれたルールは決して発動しません — そして macOS では、`/tmp` が `/private/tmp` に、`/var/folders/…` が `/private/var/folders/…` に解決されるため、これは例外的なケースではなく一般的なケースです。`*` または `?` を含むエントリは glob として扱われ、そのままにされます。解決できないパスは書かれたまま保持されます。

## SandboxBindMount

| フィールド       | 型                     | 説明                                                                                             |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `hostPath`  | `String`                 | ホスト上の絶対パス                                                                               |
| `guestPath` | `String`                 | サンドボックス内のパス（ネイティブサンドボックスでは `hostPath` と等しくなります。アダプターの対称性のために保持されています） |
| `readOnly`  | `bool`（デフォルト `false`） | true の場合は読み取り専用でマウントします                                                                               |

## SandboxHandle

`SandboxPort.launch` が返す値:

| フィールド       | 型                   | 説明                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | セッション識別子                                                       |
| `backend`   | `SandboxBackend`       | 実行中のバックエンド                                                 |
| `state`     | `SandboxState`         | ライフサイクルの状態                                                          |
| `error`     | `Object?`              | `state` が `error` のときに設定されます                                              |
| `details`   | `Map<String, Object?>` | アダプター固有の管理情報（作業ディレクトリ、PID、プロファイルパスなど） |

### SandboxState

| 状態       | 説明                                 |
| ----------- | ------------------------------------------- |
| `created`   | 仕様は作成されましたが、VM はまだ起動していません |
| `warm`      | 実行中で、コマンドを exec する準備ができています          |
| `active`    | 現在コマンドを実行しています               |
| `suspended` | RAM を節約するために一時停止され、ディスクにチェックポイントされています   |
| `destroyed` | 破棄済み。ハンドルはもう有効ではありません    |
| `error`     | 起動に失敗しました — `SandboxHandle.error` を参照してください   |

## サンドボックスイベント

| イベントの種類  | 説明                                                  |
| ----------- | ------------------------------------------------------------ |
| `stdout`    | サンドボックスからの標準出力                             |
| `stderr`    | サンドボックスからの標準エラー                              |
| `exit`      | サンドボックスのプロセスが終了しました（`exitCode` を保持します）                  |
| `starting`  | サンドボックスが起動中です                                       |
| `ready`     | サンドボックスが exec 呼び出しを受け付けられる状態です                        |
| `killed`    | プロセスがホストによって強制終了されました（OOM、タイムアウト、手動停止）       |
| `violation` | サンドボックスポリシーに違反しました（`SandboxViolation` を保持します） |

## SandboxViolation

| フィールド                 | 型      | 説明                                                                |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action`              | `String`  | 拒否された動詞（例: `file-read*`、`network-outbound`）                    |
| `target`              | `String`  | 拒否された操作の対象であったパスまたはホスト                   |
| `raw`                 | `String?` | 生のログ行。デバッグに役立ちます                                         |
