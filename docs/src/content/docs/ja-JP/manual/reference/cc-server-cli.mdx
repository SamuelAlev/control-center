すべてのプロセスフラグは CLI フラグまたは環境変数で指定します。優先されるのはフラグ、
次に環境変数、最後にデフォルトです。プロバイダーの資格情報は例外です — [プロバイダーアプリと Connect](#プロバイダーアプリと-connect) を参照してください。

:::caution[不明なフラグは黙って無視されます]
引数パーサーは手書きで、認識しないものをすべてスキップするため、タイプミス （`--tls-key-file`、`--bindany`）はエラーになりません — サーバーはデフォルトのまま起動するだけです。 フラグが効いていないように見えるときは、起動ログの行を確認してください。受け付けない値を指定した[コードモードのフラグ](#コードモード)は別で、サーバーは起動を拒否します。
:::

## コア

| フラグ          | 環境変数               | デフォルト                                       | 意味                                                                                                           |
| --------------- | ---------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `--data-dir`    | `CC_SERVER_DATA_DIR`   | OS のユーザー単位のアプリケーションデータディレクトリ（以下を参照） | データベース、シークレット、モデル、キャッシュ済みメディア                                                     |
| `--port`        | `CC_SERVER_PORT`       | `9030`                                           | TCP ポート（`0` = 一時ポート）                                                                                  |
| `--bind`        | `CC_SERVER_BIND`       | `loopback`                                       | `loopback`、またはすべてのインターフェースを対象にする `any`/`all`/`0.0.0.0`（TLS または `--insecure` が必要）  |
| `--repo-roots`  | `CC_SERVER_REPO_ROOTS` | サーバーユーザーのホームディレクトリ             | リポジトリを登録するときにクライアントが参照できる、カンマ区切りのベースディレクトリ。ルートより上への参照は拒否される |
| `--log-level`   | `CC_SERVER_LOG_LEVEL`  | `warning`                                        | `debug`、`info`、`warning`、`error`。起動中/準備完了の行は常に出力される                                        |
| `--server-name` | `CC_SERVER_NAME`       | マシンのホスト名                                 | ピッカー、検出、ペアリングの各画面に表示される名前                                                             |

| ------------------------ | ------------------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `--sandbox`              | `CC_SERVER_SANDBOX`             | `on`                                  | `on` ではエージェントの実行をホストの OS ネイティブサンドボックスで包み、サンドボックスのないホストではサーバーオーナーの実行だけを開始します。`off` は、このホスト上で全メンバーのエージェントを制限なしで実行します。以下を参照 |
| `--code-index`           | `CC_SERVER_CODE_INDEX`          | `on`                                  | バックグラウンドのコードグラフインデックス作成に対するフィールドのキルスイッチ。`off` にすると、再ビルドなしでクリーンに起動する |
| `--code-index-defer`     | `CC_SERVER_CODE_INDEX_DEFER`    | `15`                                  | 準備完了バナー後に最初のインデックススイープを保留する秒数（0〜300 にクランプ）                                              |
| `--tool-deferral`        | `CC_SERVER_TOOL_DEFERRAL`       | `on`                                  | ハーネスの実行が、少数の直接呼び出しセットと名前インデックスを送信し、残りは初回使用時に読み込むかどうか。以下を参照         |
| `--credential-gate`      | `CC_SERVER_CREDENTIAL_GATE`     | `900`                                 | 資格情報がその実行に使えないときに、人間が修正するのを待って実行がパークする秒数（0〜3600 にクランプ）。以下を参照           |
| `--code-mode-max-processes` | `CC_SERVER_CODE_MODE_MAX_PROCESSES` | `min(16, 2 × cores)` | このサーバーで同時に実行されるコードモードのスクリプトの数（人の承認を待っているものは含まない）、1〜64。下記を参照 |
| `--code-mode-max-heap-mb` | `CC_SERVER_CODE_MODE_MAX_HEAP_MB` | `1024` | 1 つのスクリプトが使えるメモリの最大値、16〜1024 MiB。ワークスペースのより高いメモリ上限は、この値まで引き下げられます |

## プロバイダーアプリと Connect

プロバイダーの資格情報を含むビルドはありません。Control Center Connect がオンの場合、Connect
がすべてのプロバイダーを担当し、これらの自前のアプリは保存されたまま使われません。**自分のアプリを使う**
の下では、各プロバイダーは、サーバー自身のアプリが完全に設定されていればそれで実行され、そうでなければ
利用できません。ワークスペース自身のアプリは、どちらの場合も優先されます。自前のアプリは **設定 → サーバー →
シングルサインオン → プロバイダーアプリ** で設定するか、サーバーの `.env` ファイルから 1 回だけ
シードします。これらのフラグはありません。コマンドライン上のシークレットは `ps` から読めてしまうためです。

| 変数                           | 意味                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| `GITHUB_APP_ID`                | サーバーの GitHub App の ID                                                                   |
| `GITHUB_APP_PRIVATE_KEY`       | その秘密鍵。`\n` エスケープを使って 1 行で記述します。**`.env` のみ**                          |
| `GITHUB_CLIENT_ID`             | 人々のサインインに使う、そのクライアント ID                                                   |
| `GITHUB_CLIENT_SECRET`         | そのクライアントシークレット。**`.env` のみ**                                                 |
| `GOOGLE_OAUTH_CLIENT_ID`       | サーバーの Google Web アプリケーションクライアント                                            |
| `GOOGLE_OAUTH_CLIENT_SECRET`   | そのシークレット。**`.env` のみ**                                                             |
| `LINEAR_CLIENT_ID`             | サーバーの Linear アプリケーション（PKCE、シークレットなし）                                  |
| `LINEAR_API_KEY`               | 自動化用の Linear サービスキー。**`.env` のみ**                                               |
| `KLIPY_APP_KEY`                | GIF 検索用のサーバー自身の Klipy キー。**自分のアプリを使う** の下でのみ使われます               |
| `CC_CONNECT_URL`               | `hosted`、`off`、または Connect の URL。Connect の選択を固定し、設定画面からは変更できなくなります |
| `CC_SERVER_CONNECT_HOST`       | `on` にすると、`CONNECT_*` 変数で構成された Control Center Connect を `<server>/connect` にマウントします。[Connect サーバーを実行](/ja-JP/マニュアル/ハウツーガイド/connect-サーバー実行/#cc_server-内に-connect-をマウントする)を参照 |

`.env` ファイルは、サーバーの作業ディレクトリ、実行ファイルの隣、またはその上位にある
ソースチェックアウトから読み込まれます。Docker では `/app/bin/.env` にマウントします。
`GITHUB_APP_PRIVATE_KEY`、`GITHUB_CLIENT_SECRET`、`GOOGLE_OAUTH_CLIENT_SECRET`、
`LINEAR_API_KEY`、またはいずれかの `SLACK_*SECRET*` が、すべての子プロセスから読めてしまう
プロセス環境にエクスポートされていると、サーバーは**起動を拒否します**（終了コード `78`）。
`.env` からのシードはフィールドごとに 1 回だけ行われるため、後から設定画面で編集した内容が
再起動で取り消されることはありません。空の値は未設定として扱われます。

どのコードホストの資格情報も環境変数からは来ません。GitHub、GitLab、Bitbucket はいずれも、
メンバー自身のサインインまたはトークンで動くか、それに限定された 1 リポジトリ用の GitHub App
トークンで動きます。

### `--sandbox`

サーバーは起動時に一度だけホストをプローブし、バックエンドが利用できる場合はエージェントの
コマンド実行を OS ネイティブのサンドボックスで包みます。macOS では `sandbox-exec`（Seatbelt）、
Linux と WSL2 では `bwrap` と `socat` です。判定は一度だけ行われ、サーバーが再起動するまで有効です。
結果は 3 通りあり、それぞれが起動時の exposure 行に表示されます:

| `sandbox=`    | いつ                                    | 開始されるエージェント実行                                                       |
| ------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| `native`      | バックエンドが利用可能で、`--sandbox` が `on` | 全員の実行。サンドボックスで包まれます                                      |
| `off`         | `--sandbox off`                         | 全員の実行。このホスト上で制限なし                                              |
| `unavailable` | `--sandbox on` かつバックエンドなし（Windows、または `bwrap` と `socat` のない Linux）   | サーバーオーナーが責任を負う実行だけで、制限なし。それ以外は「このサーバーにはサンドボックスがないため、ここでエージェントを実行できるのはそのオーナーだけです。」と表示されて拒否されます |

自動化では、責任を負う人は自動化がバインドされている人です。サーバーオーナーが記録されていない場合、`unavailable` のホストでは実行が一切開始されません。bubblewrap がインストールされた Linux と WSL2 では、ネイティブのディスパッチは現在すべての実行でフェイルクローズドに失敗します。[サンドボックスのバックエンド](/ja-JP/マニュアル/リファレンス/サンドボックスバックエンド/#linux-bubblewrap)を参照してください。

`--sandbox off` は、サーバーオーナーがサーバーを使うすべての人について行う選択です。このマシン上で全メンバーのエージェントを制限なしで実行します。サンドボックスプロファイル自体が誤動作するホストで使うほか、バックエンドのないホストでメンバーにエージェントを実行させるためにも使えます。再ビルドは不要で、サーバーはプロセスの存続中ずっと警告をログに記録するため、その状態が黙っていることはありません。

### `--tool-deferral`

内蔵ハーネスの実行は、少数の直接呼び出しセットのツール定義と、残りの名前だけのインデックスを送信します。残りのツールは、初回使用時にスキーマを読み込むか、`repl` のスクリプトから呼び出されます。これにより、常に表示されるセットは、モデルがツールを確実に選択できる範囲内に収まります。テストが構築するレジストリで測定すると、組み込みエージェントの標準チャットツールは 14 個の定義になり、`repl` 付きで約 16.5 KB（そのうち約 4 KB が `repl` のもので、その定義は 4,096 バイトを超えてはなりません）、スクリプトを実行できないサーバーでは約 13 KB です。遅延されたツールは実行を通じて名前で呼び出し可能なままで、`search_tools` が意図からそれらを見つけます。[ツールコンテキストとプロンプトキャッシュ](/ja-JP/マニュアル/コンセプト/ツールコンテキスト/)を参照してください。

`--tool-deferral off` は、許可されたすべてのツールの定義を事前に送信します。ただし `repl` のある実行では、スクリプトが呼び出してよいツールは引き続きスクリプトから呼び出されます。これは、二層のサーフェスをうまく扱えないモデルに対するキルスイッチです — 再ビルドではなくフラグです。影響するのは内蔵ハーネスだけです。外部クライアントが見る MCP の `tools/list` は完全なカタログです。ただし、[コードモード](/ja-JP/マニュアル/コンセプト/コードモード/)のスクリプトを実行できるサーバー上のエージェント実行は除きます。

### `--credential-gate`

プロバイダーの資格情報が欠けているか使い果たされている実行は、失敗させるのではなく
**パーク**されます。オペレーターに修正を促すプロンプトが表示され、修正すれば実行は
再開します。既定の期限は 900 秒（15 分）で、0〜3600 にクランプされます。

この期限は、承認プロンプトのものより意図的にずっと長く設定されています。承認は誰かが
数秒で下す判断ですが、資格情報の修正はターミナルを開き、サインインし、戻ってくることを
意味します。この上限があるおかげで、無人で走る実行 — パイプラインのステップ、cron
トリガー、webhook — が眠っている誰かを待ち続けることを防げます。期限が切れると、実行は
どのみち失敗していたはずのメッセージとともに失敗します。

`--credential-gate=0` はキルスイッチです。何もパークされず、不正な資格情報はこのゲートが
存在する前とまったく同じようにターンを終わらせます。

### コードモード

[コードモード](/ja-JP/マニュアル/コンセプト/コードモード/)を使うと、エージェントは JavaScript のスクリプトを実行して、そのツールを呼び出せます。オン・オフを切り替えるフラグはありません。サーバーがスクリプトを実行できる場合、すべての実行が `repl` ツールを受け取り、公開デモサーバーはスクリプトを一切実行しません。

スクリプトは、サーバーに同梱された `bin/codemode/` の中の `cc_codemode` で実行されます。このプログラムがなければ、サーバーは起動しません。その場合、不足しているものを名指しする行を出力し、終了コード `78` で終了します。起動時にサーバーはプログラムのロックダウンの自己テストを実行し、1 行を出力します（`--log-level error` の場合のみ抑制されます）：

```text
cc_server: code_mode=available (cc_codemode 0.1.0 quickjs-ng 0.16.2 protocol 2; 16 scripts at once, at most 12 per workspace; up to 64 more runners kept for scripts waiting on a person; heap at most 1024 MiB per script)
cc_server: code_mode=unavailable (<reason>) — runs on this host get no repl tool; scripts never run without full lockdown
```

`unavailable` は、プログラムがこのホスト上で自身をロックダウンできないことを意味します（たとえば、セキュリティプロファイルが手順のいずれかを拒否するコンテナー内など）、またはプログラムがリリースビルドでない場合。サーバーは通常どおり動作し、どの実行も `repl` を受け取らず、ワークスペースのコードモード設定に理由が表示されます。

サーバーは実行中も確認を続けます。プログラムがスクリプトの問題ではない理由で起動に失敗した場合、サーバーは自己テストを再実行します（最大で 1 分に 1 回）。それが失敗すると、サーバーは理由とともに `unavailable` の行を出力し、スクリプトを一切実行しません。その間に開始された実行は `repl` を受け取らず、すでにそれを持つ実行は、ツールを直接呼び出します（[スクリプトを実行できない場合](/ja-JP/マニュアル/コンセプト/コードモード/#スクリプトを実行できない場合)）。サーバーは最大で 1 分に 1 回確認を続け、自己テストが再び通ると `available` の行を出力して、再びスクリプトを実行します。起動時に失敗した自己テストだけが、再起動を必要とします。ワークスペースの設定に表示される理由からは、ホストのパスが取り除かれています。ログの行にはそのまま含まれます。

2 つのコードモードのフラグは、スクリプトが使える量を制限します。`--code-mode-max-processes` は、すべてのワークスペースにわたって同時に実行されるスクリプト数を制限します（既定値はプロセッサコア数の 2 倍で、最大 16。受け付ける値は 1〜64）。上限が 2 以上の場合、1 つのワークスペースが使えるのは、上限から上限の 4 分の 1 を引いた数までです。そのため、単一のワークスペースがすべての席を取ることはなく、待機中のスクリプトはワークスペースをまたいで順番に受け付けられます。人の承認や回答を待っているスクリプトは、その席を別のスクリプトに譲り、回答されるまでツール呼び出しを開始しません。そうした待機中のスクリプトは、上限の 4 倍まで保持されます。ただし、そのうち 1 つのワークスペースからのものは、最大 4 分の 3 までで、それぞれ自身のプロセッサ時間の上限の範囲内で計算を続けられます。`--code-mode-max-heap-mb` は、1 つのスクリプトが使えるメモリの最大量です。

これらのフラグが受け付けない値（範囲外の数値、または数値ではない値）があると、サーバーは起動時に停止し（終了コード `78`）、受け付ける値を示すメッセージを表示します。受け付けられない値が既定値として読まれることは決してありません。

## サブコマンド

| コマンド                                      | 動作                                                                                                |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `cc_server`                                   | `SIGINT`/`SIGTERM` までサーバーを実行する                                                           |
| `cc_server pair`                              | デバイスをプロビジョニングし、その id とペアリングキーを出力する。サーバーがすでに提供中のデータディレクトリに対しても安全 — 実行中のサーバーは再起動なしでそのデバイスを拾い上げる |
| `cc_server connect <command>`                 | このサーバーが使う Control Center Connect を、サーバーを起動せずに表示または変更する              |
| `cc_server update`                            | 新しいスタンドアロンリリースを確認し、ダウンロードして検証する                                      |
| `cc_server --version`                         | ビルドバージョンと git SHA を出力する — `/healthz` と RPC ハンドシェイクが通知するのと同じ識別情報   |

### `pair`

| フラグ         | デフォルト                                               | 意味                                                                                                                                                                 |
| -------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device`     | `web-client`                                             | デバイス id。プラットフォームはこれから推測されるため、`--device desktop` はデスクトップの行を、`--device ios`/`android` はスマートフォンの行を生成し、それ以外は Web として扱われる |
| `--label`      | プラットフォーム名とこのマシンのホスト名                 | デバイス一覧に表示される名前                                                                                                                                         |
| `--host`       | `localhost`、任意のインターフェースにバインドされている場合は `<this-host>` | 出力される URL に埋め込むホスト。クライアントが実際に接続する LAN IP またはトンネルホストに設定する                                                                  |
| `--client-url` | 未設定                                                   | ホストされた **Web** クライアントのオリジン。スキャン可能なディープリンクとターミナル QR を追加する                                                                  |

`pair` はコアの `--data-dir`、`--port`、`--bind` フラグも受け付けます。これらは書き込む
データディレクトリを選び、出力されるサーバー URL を形作ります（ループバックでは `ws`、
`--bind any` の場合は `wss`）。同じ `--device` に対して `pair` を再実行すると、そのキーが
ローテーションされ、そのデバイスのライブセッションが切断されます。ここで発行された資格情報
には**有効期限がありません**。アプリ内のペアリングが設定する 30 日とは異なります。

:::caution[`--client-url` の QR はスマートフォン用の QR ではない]
`pair --client-url` は **Web** クライアントの接続フォーム（サーバー URL、デバイス id、
URL フラグメント内のキー）を埋めます。スマートフォンは、アプリ内のペアリングパネルから
発行される別のペイロード — サーバーの完全な接続記述子と有効期限 — でペアリングします。
両者は互換性がありません — [デバイスをペアリング](/ja-JP/マニュアル/ハウツーガイド/デバイスのペアリング/)を参照してください。
:::

### `connect`

**設定 → サーバー → シングルサインオン** の **Control Center Connect** カードと同じ設定を、
データディレクトリから読み書きします。実行中のサーバーは、変更を 10 分以内か再起動時に反映します。

| コマンド                        | 動作                                                                                                             |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `cc_server connect status`      | モード、URL、`CC_CONNECT_URL` で固定されているかどうか、インストールID、ヘルス、各レーンのソース（`own`、`connect`、`off`）を出力します |
| `cc_server connect enable`      | Control Center がホストする Connect を使います                                                                   |
| `cc_server connect enable --url <url>` | その URL のカスタム Connect を使います（HTTPS、またはループバックでは `http`）                            |
| `cc_server connect disable`     | Connect の使用をやめます。サーバー自身のアプリだけが人々をサインインさせます                                     |

コマンドなしの `status` が既定です。各コマンドは `--data-dir` を受け付けます。
`CC_CONNECT_URL` は、これらが保存した内容を上書きします。不明なコマンドは終了コード `64` で終了します。
モード、インストールの識別情報、ステータスコードについては [Control Center Connect](/ja-JP/マニュアル/リファレンス/connect/) を参照してください。

### `update`

`--apply` はインストールを置き換えます。設定されたポートでサーバーがまだ応答している間は、
`--force` を渡さない限り拒否されます。`--allow-downgrade` は古いリリースを許可します。

このコマンドは、自身が所有していないインストールに対しては、エラーではなく説明とともに
明確に拒否します:

| 環境                          | 検出方法                                    | 表示内容                                                    |
| ----------------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| デスクトップの組み込みサーバー | `CC_EMBEDDED=1` または `CC_BOOTSTRAP_DEVICE_ID` | 代わりにアプリを更新してください — インストーラーがツリー全体を入れ替えます |
| `dart run` のソースチェックアウト | スクリプトパスが `.dart` で終わる         | git で更新してください                                       |
| Docker                        | コンテナのマーカー                          | 新しいイメージを取得してください                            |

## プロセスのライフサイクル

`cc_server` は `SIGINT` / `SIGTERM` まで実行されます。これを制御する環境変数がもう 1 つあり、
それはあなたではなくデスクトップが設定します:

| 変数                    | 効果                                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CC_EXIT_WITH_PARENT=1` | 親プロセスが終了するとサーバーも終了します。これは親が自身の stdin パイプの書き込み側を閉じることで検出されます。デスクトップがこれを設定するのは、クラッシュしたアプリがデータディレクトリを握ったままの孤児サーバーを残さないようにするためです |

自分で設定するのは、`cc_server` を子プロセスとして監督していて、同じ保証が欲しい場合
だけにしてください。

`DO_NOT_TRACK=1`（空、`0`、`false` 以外の任意の値）を設定すると、サーバー全体のスイッチがオンでも、サーバー自身の[利用状況の分析](/ja-JP/マニュアル/リファレンス/利用状況の分析/)を停止します。クライアントは引き続きスイッチに従います。

## データディレクトリのレイアウト

既定のデータディレクトリは、macOS では `~/Library/Application Support/control-center`、
Windows では `%APPDATA%\control-center`、それ以外では `$XDG_DATA_HOME/control-center`
（なければ `~/.local/share/control-center`）です。cwd 相対の `.cc_server` が使われるのは、
ホームディレクトリもアプリデータディレクトリも解決できない場合だけです。

サーバーはデータディレクトリを自身のアカウントだけに非公開にします（`0700`）。それができない場合、`global.db` が破損している、または新しいバージョンが書き込んだ場合、またはそのアイデンティティファイルを読めない場合には、起動を拒否します（終了コード `78`）。

| パス                              | 内容                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------- |
| `global.db`                       | ワークスペースレジストリ、ユーザー、ペアリング済みデバイス、ニュースフィード、フリートキュー |
| `<workspaceId>/workspace.db`      | ワークスペースごとに 1 つのデータベース — エージェント、スペース、チケット、メモリ |
| `<workspaceId>/code_index.db`     | そのワークスペースのコードグラフ。欠けているとき再構築され、バックアップされることはありません        |
| `pre_upgrade/`、`<workspaceId>/pre_upgrade/` | 更新でフォーマットが変わる前のデータベースの、最新の 2 つのコピー |
| `<workspaceId>/chat_credentials/` | チャットボットのトークン。プレーンな JSON なので、ワークスペースと一緒に移動する  |
| `secrets.json`                    | ペアリングキー、Connect のインストールキー、プロバイダーアプリ、人々のサインイン（Connect を通じたものは封印済み）、Webhook シークレット、SSO（`0600`） |
| `backups/<timestamp>/`            | 1 回分のインストールスナップショット — `manifest.json`、`global.db`、各ワークスペースのコピー |
| `backups/exports/`                | 単一ワークスペースのエクスポート、`<workspaceId>-<timestamp>.db`                |
| `backups/transfer/`               | バックアップのダウンロードとアップロードのステージング。書き込んだルートによって掃除される |
| `models/`                         | オンデバイスの埋め込み、話者分離、音声モデル                                    |
| `codemode/` | `scripts/natives/build_codemode.sh` でインストールされる、コードモードランナーの開発用コピー。リリースバンドルでは `bin/codemode/` に含まれます |
| `meetings/<meetingId>/`           | 保持されたミーティング音声                                                      |
| `rigs/images/`                    | インポートされたリグのディスクイメージ（QEMU デスクトップサーフェス）            |
| `rigs/smolvm/<rigId>/`            | リグごとの microVM ランタイム状態（ブローカーのシークレット、`0600`）           |
| `rigs/smolvm-packs/`              | 展開済みのマシンパック — 同じリグの再起動を高速にするキャッシュ                  |
| `rigs/tls/`                       | リグの HTTPS 用の開発ドメイン認証局（鍵は `0600`）                              |
| `rigs/run/<rigId>/`               | QEMU のオーバーレイ、シードイメージ、VM ごとの鍵（`0600`）                      |
