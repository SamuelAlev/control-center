Control Center がコピー、受け渡し、採用できるものすべてと、各アーティファクトの正確な形を
まとめます。実際にバックアップを取得する方法は
[バックアップと復元](/ja-JP/マニュアル/ハウツーガイド/バックアップと復元/)を、永続化が
このように分割されている理由は
[ワークスペースと分離](/ja-JP/マニュアル/コンセプト/ワークスペース/)を参照してください。

## アーティファクト

データベースのコピーを伴うアーティファクトは 3 つあり、スコープと削除ポリシーがそれぞれ異なります。

| アーティファクト                | 書き込み元                   | 形                                 | 対象                        |
| ----------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **インストール全体のスナップショット**    | `server.backupNow`           | タイムスタンプ付きの**ディレクトリ**           | インストール上のすべてのデータベース |
| **ワークスペースのバックアップ**    | `Workspace backup` パイプライン  | `.db` を 1 つ含むタイムスタンプ付きディレクトリ  | 1 つのワークスペースのデータベース      |
| **ワークスペースのエクスポート**    | `workspace.export`           | 単一の `.db` **ファイル**               | 1 つのワークスペースのデータベース      |

いずれも SQLite の `VACUUM INTO` で書き込まれるため、稼働中の WAL データベースに対しても
安全です。読み取りトランザクションを取得し、断片化を解消したトランザクション整合性のある
コピーを生成し、サーバーを停止する必要は一切ありません。

これらのファイルとダウンロードしたコピーは、Control Center によって**保存時に暗号化
されません**。エンドツーエンドで暗号化された転送は、ペアリング済みクライアントとその
`cc_server` の間を移動するバイトを、直接接続でもブローカー経由のリレー接続でも保護します。
ローカルストレージとマシン外のコピーは別途保護してください。サーバーと認可された受信者は、
データベースファイルを読むことができます。

## スナップショットのレイアウト

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

このレイアウトは稼働中のデータディレクトリを正確に反映しているため、インストールの復元は
変換ではなくコピーを書き戻すだけの操作になります。ディレクトリ名は UTC タイムスタンプの
`:` と `.` を `-` に置き換えたもので、Windows でもファイルシステム上安全であり、プレーンな
文字列として時系列順に並びます。

スケジュールされたワークスペースのバックアップは、別途 `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` に置かれます。それぞれに、そのファイル 1 つ分の `manifest.json` があり、`global.db` はありません。インストール全体のスナップショットではありません。復元では、置き換えられたデータベースが同じ場所に `<timestamp>-pre-restore` として保持されます。週次パイプラインの保持ステップが削除するのは、設定された期間（既定では 30 日）より古い、そのワークスペース自身のバックアップだけです。手動で作成したインストール全体のスナップショットがこのステップでローテーションされることはありません。`server.listBackups` が一覧に出すのはインストール全体のスナップショットだけで、未検証のものも含まれます。`workspace.listBackups` は 1 つのワークスペースの定期バックアップを一覧に出します。

ワークスペースを削除しても、このディレクトリはそのまま残ります。ワークスペースのスケジュールも
一緒に停止するため、これらのバックアップはローテーションされなくなり、インストールのオーナーが
削除するまで残ります。`server.listOrphanedBackups` がこれらを報告します。


### `manifest.json`

| フィールド                      | 型            | 意味                                                             |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                  | int             | マニフェストのフォーマット。現在は `2`                              |
| `created_at`               | ISO-8601 UTC    | スナップショットを取得した時刻                                         |
| `global`                   | object          | `global.db` の記録。定期ワークスペースバックアップにはありません |
| `workspaces[]`             | array           | 取得したワークスペースごとに 1 件のレコード                                    |
| `workspaces[].workspace_id`| string          | このファイルが保持するワークスペース                                       |
| `skipped_workspaces[]`     | array           | バックアップが取得**できなかった**ワークスペース                         |
| `skipped_workspaces[].workspace_id` | string | 除外されたワークスペース                                     |
| `skipped_workspaces[].reason` | string       | `no_file`、`damaged`、または `failed`                                    |

`global` と `workspaces[]` の各エントリは、書き込んだ後にコピーを計測して、コピーされたファイルを 1 つずつ記録します。

| フィールド | 型 | 意味 |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | string          | スナップショットルートからの相対パス: `global.db` または `<workspaceId>/workspace.db`    |
| `bytes`       | int             | コピーのサイズ                                                   |
| `sha256`         | string | コピーの SHA-256（小文字の 16 進数）                                          |
| `quick_check`    | string | コピーについて SQLite の `quick_check` が出した結果。`ok`、または検出内容         |
| `user_version`   | int    | コピーのスキーマバージョン                                                     |
| `application_id` | int    | コピーの SQLite `application_id`                                            |

ワークスペースがスキップされるのは、登録されているものの一度も書き込まれていない場合（`no_file`）、そのデータベースが整合性チェックに失敗する場合（`damaged`。破損したコピーは取得されません）、またはそのコピーもしくはコピーの確認に失敗した場合（`failed`）です。いずれの場合も、スナップショットは完了し、マニフェストに欠けているものが記録されます。マニフェストは最後に書き込まれます。

### 完全性

`server.listBackups` は、スナップショットごとに `complete` フラグを報告します。マニフェストが存在しない、解析できない、または別のフォーマットである場合、記載されたファイルが存在しない、またはサイズが異なる場合、あるいはコピーが検証に合格しなかった場合に false になります。アプリはそのようなスナップショットを**未検証**と表示します。フォーマット `2` より前に取得されたスナップショットがこの状態にあります。

未検証のスナップショットも引き続き一覧に表示されます。運用者に見えないスナップショットは、
持っていると信じてしまうスナップショットだからです。マニフェストが読めない場合、一覧は
レイアウトそのものにフォールバックし、見つかった `<workspaceId>/workspace.db` ファイルを
報告します。スナップショット全体としてはインストールを復元できませんが、これらは
`workspace.import` を通じて個別に採用できます。

一覧に表示されているスナップショットまたは定期バックアップは、ライブのデータベースが破損しているワークスペースの最新の検証済みコピーを保持している間、`pinned_reason: "last_good_copy"` を持ちます。保持ステップは、そのワークスペースが復元されるまでこれをスキップします。

## バックアップに含まれないもの

どちらのアーティファクトも**データベースのみ**です。ワークスペースのディレクトリには
データベース以外のものもあり、それらは一切持ち出されません。

| パス                                | スナップショットに含まれる？ | ワークスペースのエクスポートに含まれる？ |
| ----------------------------------- | -------------- | ---------------------- |
| `global.db`                         | はい            | いいえ                     |
| `<workspaceId>/workspace.db`        | はい            | はい（それ自体がそのファイル） |
| `<workspaceId>/code_index.db`       | いいえ          | いいえ                     |
| `<workspaceId>/blobs/`              | いいえ             | いいえ                     |
| `<workspaceId>/skills/`             | いいえ             | いいえ                     |
| `<workspaceId>/agents/`             | いいえ             | いいえ                     |
| `<workspaceId>/chat_credentials/`   | いいえ             | いいえ                     |
| `<workspaceId>/spaces/<spaceId>/`   | いいえ             | いいえ                     |
| `<workspaceId>/pr_clones/`          | いいえ             | いいえ                     |
| `secrets.json`                      | いいえ             | いいえ                     |
| `models/`                           | いいえ             | いいえ                     |
| `meetings/<meetingId>/`             | いいえ             | いいえ                     |
| `rigs/`                             | いいえ             | いいえ                     |
| `_agent_hooks/`                     | いいえ             | いいえ                     |

その一部は捨ててよいものです。`spaces/` はリポジトリから再プロビジョニングされるコピーオンライトのワークツリー、`pr_clones/` はキャッシュ、`code_index.db` は再構築されるもの、`models/` は再ダウンロードされるもの、`rigs/` はマシンの状態です。そうでないものもあります。`blobs/` はデータベースの行が参照する貼り付け画像を保持し、`skills/` と `agents/` はエージェントが実行時に使うファイルを保持し、`secrets.json` はインストール上のすべてのペアリングキー、プロバイダーの認証情報、SSO 設定を保持します。残りをカバーする方法は[バックアップと復元](/ja-JP/マニュアル/ハウツーガイド/バックアップと復元/#バックアップをマシン外にコピーする)を参照してください。
:::note[シークレットはデータベースに入りません]
`workspace.db` はワークスペース全体です。会話、実行ログ、リポジトリのリンク、環境の定義、メンバーが含まれます。パイプラインの Webhook トークンとチケット同期の Webhook シークレットは `secrets.json` にあります。データベースには、それぞれへの参照が保持され、ルートインデックスには各トークンのキー付きハッシュが保持されます。したがって、別のインストールに復元されたワークスペースは、そこでトリガーが保存し直されるまで Webhook を受け取りません。プロバイダーのサインイン、デバイスキー、ユーザーのシークレットは `global.db` と `secrets.json` にあります。
:::

:::note[チャットトークンは意図的に持ち出されません]
`chat_credentials/` がデータベースの中ではなく隣に置かれているため、他人に渡した
ワークスペースに有効なボットトークンは含まれません。詳しくは
[チャットブリッジのリファレンス](/ja-JP/マニュアル/リファレンス/チャットブリッジ/)を
参照してください。
:::

## 操作

インストールのバックアップ RPC とワークスペースのエクスポート／インポートは `fullClient`
専用です。ペアリングされたスマートフォンからは実行できません。バックアップポートが
構成されていないサーバー（デモサーバーなど）では、これらはすべて、拒否されるのではなく
構造的に存在しません。

| 操作                   | 種別   | スコープ     | 最小ロール | 引数     | 戻り値                       |
| -------------------- | ------ | --------- | ------------ | ------------- | ----------------------------- |
| `server.backupNow`   | 変更 | インストール   | インストールの**オーナー** | なし     | `{ok, path}`                  |
| `server.listBackups` | 読み取り   | インストール   | インストールの**オーナー** | なし     | `{backups: [...]}`            |
| `server.deleteBackup` | 変更 | インストール | インストールの**オーナー** | `name` | `{ok}` |
| `server.listOrphanedBackups` | 読み取り | インストール | インストールの**オーナー** | なし | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | 変更 | インストール | インストールの**オーナー** | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | 読み取り | ワークスペース | `admin` | なし | `{backups: [...]}` |
| `workspace.deleteBackup` | 変更 | ワークスペース | `owner` | `name` | `{ok}` |
| `workspace.export`   | 読み取り   | ワークスペース | `admin`      | なし          | `{ok, path}`                  |
| `workspace.import`   | 変更   | ワークスペース | `owner`、およびサーバーオーナー | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | 読み取り | ワークスペース | `owner`、およびサーバーオーナー | なし | `{holds: [...]}` |
| `workspace.importHolds.resolve` | 変更 | ワークスペース | `owner`、およびサーバーオーナー | `hold_id`、`accept` | `{ok, applied}` |
| `workspace.delete`   | 変更   | インストール*  | `owner`      | `id`          | レジストリの行に削除済みの印を付ける   |

* `workspace.delete` がスコープを持たないのは、印を付ける行がグローバルレジストリに
あるためです。そのハンドラーは、呼び出し元が指定されたワークスペースのメンバーかどうかを
確認し、`owner` を要求します。

すべてのレスポンスの `path` は、**サーバーホスト**上のパスです。

`server.listOrphanedBackups` は、存在しなくなったワークスペースごとに 1 つのエントリを返します。
内容は `workspace_id`、レジストリがまだ把握している場合は `workspace_name`、および `backups`
です。削除されたワークスペースはワークスペースのロールチェックを通過できなくなるため、その
バックアップはインストールのオーナーのものになります。`server.deleteOrphanedBackup` は
稼働中のワークスペースを拒否します。そのバックアップは引き続き `workspace.deleteBackup` と
そのワークスペース自身のロールで保護されます。どちらの削除操作も、一覧にあるタイムスタンプの
ディレクトリ名だけを受け付け、パスは受け付けません。

`workspace.importHolds.list` は、インポートが保留したものを返します。各保留には `id`、`kind`（`action_policy`、`sandbox_exec_grant`、`repo_grant`、`membership_role`、または `invite`）、戻されるはずだった `payload`、`imported_at`、`source_install_id` があります。`workspace.importHolds.resolve` は、`accept: true` で付与を再び与え、`false` で破棄します。付与の対象だった人またはものがワークスペースにもはや存在しない場合、`applied` は false になります。

:::note[インストール全体のスナップショットはどちらの経路でもオーナー限定です]
`server.backupNow`、`server.listBackups`、`server.deleteBackup` にはインストールの
**オーナー**（`ServerAuthority.serverOwner`）が必要で、`GET /backup/snapshot` と同じ
ゲートです。スナップショットはすべてのワークスペースのデータベースを取得するため、
1 つのワークスペースの管理者であるだけでは、他のワークスペースを管理するには足りません。
削除が受け付けるのは一覧に表示されるタイムスタンプのディレクトリ名だけで、任意の
サーバーパスは受け付けません。また、スナップショット全体（未検証のものも含む）を削除
します。ワークスペース単位のエクスポートとスケジュールバックアップのダウンロードは、ワークスペースの管理者の権限のままです。
:::

:::note[リストアはサーバーオーナーのものです]
`workspace.import` と `POST /backup/restore` は、サーバーがデータベースファイルを自分のものとして採用することを意味します。そのファイルの行を、サーバーは自分自身のものとして扱います。つまり、リポジトリのリンクとそれを作成した人、ホスト上で動く環境の定義、ワークツリーとログのパスです。そのため、どちらもサーバーオーナー（`ServerAuthority.serverOwner`）が必要で、さらにそのワークスペースのオーナーでもある必要があります。それ以外の人、および記録されたオーナーがいないホスト上のすべての呼び出し元は、`server_owner_required` で拒否されます。ファイルが持ち込むトリガー、ビュー、列、制約は、どれも採用されません。
:::

### `server.listBackups` のレスポンス

新しい順に、ディレクトリ名（タイムスタンプ）で並びます。そのため、マニフェストを
読み取れなかったスナップショットでも順序は保たれます。

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

マニフェストを読み取れなかった場合、`created_at` は省略されます。トップレベルの `bytes` は、
マニフェスト自身の合計ではなく、ディレクトリ全体のディスク上の実際のサイズです。
スナップショットを整理する運用者が知りたいのは、バックアップが書き込むつもりだった量では
なく、そのディレクトリが占める容量だからです。

各 `workspaces[].path` は、`workspace.import` が `source_path` として受け取る値そのものです。
これは意図的で、「このスナップショットからこのワークスペースを復元する」ことはインポート
操作そのものなので、両者が同じファイルを別々に扱う方向へずれていくことはありません。

### `workspace.import` の検証

何かを置き換える前に、候補のファイルを対象の隣にあるステージングファイルへコピーし、そこで確認します。拒否された場合は何にも触れず、その種類は `data.kind` として伝えられます。

| 条件                                        | 結果                                                          |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| ファイルが存在しない | 拒否、`import.missing_source` |
| 読み取り可能な SQLite データベースではない、または `quick_check` に失敗する | 拒否、`import.damaged` |
| スナップショット由来で、その SHA-256 がマニフェストのものと異なる | 拒否、`import.checksum_mismatch` |
| サーバーの新しいバージョンが書き込んだ | 拒否、`import.newer_schema` |
| 別の `application_id` である、または `workspace_meta` がない | 拒否、`import.foreign_file` |
| このサーバーのスキーマに合わせられない | 拒否、`import.schema_mismatch` |
| その Webhook や招待がすでに別のワークスペースにルーティングされている | 拒否、`import.route_conflict` |
| 記録されたワークスペース ID ≠ 対象                | **許可**されます。その行は対象に合わせて付け直されます。これがワークスペースを複製したり、新しい ID で復元したりする方法です |
| 記録されたインストール ID ≠ このインストール                | **許可**されます。そのユーザー ID はそのインストールに属しており、ここでは解決されません |

受け入れられると、ステージングされたファイルはこのサーバーのスキーマに合わせられ、その後それと正確に一致しなければなりません。ファイルが自分自身に与えてはならない付与は、ファイルから取り除かれます。ホストで環境定義を実行する承認はクリアされます。また、許可または確認を求めるアクションルール、サンドボックスの exec 付与、読み取りを超えるリポジトリ付与、メンバーを超えるロール、それらのロールへの招待は、サーバーオーナーが確認するための保留になります。インポートした人は、オーナーロールを保持するか、取得します。置き換えられるデータベースは、`<timestamp>-pre-restore` という名前の定期バックアップとして保持されます。ステージングされたファイルは、ワークスペースの接続が閉じられた状態で所定の位置にリネームされ、`code_index.db` は再構築のために削除され、FTS インデックスが再構築されます。

## 転送ルート

上記のエクスポート／インポートとスナップショット一覧の操作はサーバー側のパスで語るため、
サーバーが自分のマシンである場合にのみ完全な答えになります。これらの HTTP 形式のルートは、
他の機密リソースと**同じ認証済みでエンドツーエンドに暗号化されたリソーストンネルの内部**で
バックアップのバイトを運びます。RPC 接続が直接でもブローカー経由でも同様です。これらは
公開の HTTP ファイル転送エンドポイントではありません。公開リスナー上でこれらのいずれかに
対するリクエストは、ループバックからでも `426 Upgrade Required` を返します。暗号化された
トンネル内では、Noise で認証されたデバイスが `d` と一致しなければなりません。さらに
ハンドラーは、そのペアリング PSK を使ってデバイスの署名対象文字列に対する署名を検証し、
下記のロールを確認します。

| ルート                   | メソッド | クエリ           | 署名対象                  | 必要な権限                |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | ワークスペースの**管理者**   |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | インストールの**オーナー**     |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | ワークスペースの**管理者**。ワークスペースの削除後はインストールの**オーナー** |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | インストールの**オーナー**で、かつワークスペースの**オーナー**（それ以外は `403` と `server_owner_required`） |

`w` はワークスペース ID、`n` はスナップショットまたは定期バックアップのディレクトリ名、`d` は
呼び出し元のデバイス ID、`s` は署名です。`/backup/snapshot` では、`n` はバックアップの
ルートに連結されるのではなく、バックアップの一覧に対して解決されるため、一覧に表示されない
ディレクトリをルートに指定することはできません。`/backup/stored` では、`n` はタイムスタンプ名で
なければならず、ファイルはそのワークスペース自身のバックアップディレクトリ内の実ファイルで
なければなりません。

| ステータス | 原因                                                                              |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | 必須のクエリパラメータが欠けている、バックアップ名が無効である、アップロードのボディが空である、またはアップロードされたファイルが拒否された（ボディは `import.*` の種類を持つ `{error, kind}`） |
| `403`  | 不明または失効したデバイス、不正な署名、または呼び出し元にロールがありません              |
| `404`  | このホストにバックアップポートがない、または指定されたスナップショット、バックアップ、ワークスペースのファイルが存在しません |
| `405`  | `/backup/restore` が `POST` 以外で呼び出されました                                   |
| `413`  | アップロードのボディが 8 GiB を超えています（宣言された content-length でも、実際に読み取ったバイト数でも）     |
| `426`  | 公開 HTTP リスナー上の転送パスへの直接リクエスト。ペアリング済みクライアントの暗号化されたリソーストンネルを使ってください |
| `500`  | エクスポートまたはアーカイブがサーバー側で失敗しました                                            |

3 つのダウンロードはいずれも `Cache-Control: no-store` と `Accept-Ranges: none` を返します。
`/backup/workspace` と `/backup/snapshot` はリクエストごとに**新しい**コピーを作成し、
ストリーミングが終わるとそれを削除します。そのため、キャッシュされたり再開されたりした
レスポンスは、2 つの異なるエクスポートのバイトをつなぎ合わせ、有効に見えて実際には有効でない
1 つのファイルを作ってしまいます。

`/backup/stored` は例外で、定期バックアップを `<workspaceId>-<name>.db` としてストリーミングし、
ファイルはそのまま残します。そのファイルがバックアップそのものだからです。

`/backup/snapshot` は `<name>.zip` を返します。エントリはスナップショットルートからの
相対パスなので、展開すると `manifest.json` + `global.db` + `<workspaceId>/workspace.db` が
そのまま再現されます。エントリはソート順に書き込まれるため、同じスナップショットの
2 つのアーカイブは同一のアーカイブになります。

`/backup/restore` はボディをバッファリングせず、そのままステージングファイルへ
ストリーミングし、読み取り前と読み取り中にサイズを制限し、拒否を含む**あらゆる**終了経路で
ステージングファイルを削除します。

::::caution[直接接続とリレーは同じ暗号化転送を使います]
リレーは、リソースのリクエスト、ストリーミングされたレスポンス、アップロードのバイトを
暗号文として運びます。バックアップの内容を読むことはできません。サーバー側のパスは、
あくまでサーバーホスト上のパスであり、リレー上のファイルではありません。アクセスには
引き続き、ペアリング済みデバイス、対象の署名、該当するワークスペースまたはインストールの
ロールが必要です。どちらの転送も、生成されるバックアップファイルを保存時に暗号化しません。
::::

## パスと制限

| 項目                          | 値                                                        |
| ------------------------------ | ------------------------------------------------------------ |
| スナップショット                      | `<dataDir>/backups/<timestamp>/`                             |
| スケジュールされたワークスペースのバックアップ    | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| ワークスペースのエクスポート              | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| 復元によって置き換えられたデータベース | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| 更新でフォーマットが変わる前のデータベース | `<dataDir>/pre_upgrade/` と `<dataDir>/<workspaceId>/pre_upgrade/`（それぞれ最新の 2 つ） |
| 転送のステージング               | `<dataDir>/backups/transfer/` — 作業台であり、そこに書き込むルートによって掃除されます |
| スナップショットのアーカイブ名          | `<snapshot directory name>.zip`                              |
| アップロードの上限                 | 暗号化された `/backup/restore` アップロードあたり 8 GiB          |
| 保持                      | インストール全体のスナップショットは手動削除。ワークスペースのバックアップは週次パイプライン（既定は 30 日）または手動削除。削除されたワークスペースのバックアップは手動削除のみ |

`exports/`、`transfer/`、`workspace-backups/` の各ディレクトリはインストール全体の
スナップショットではなく、`server.listBackups` から除外されます。スケジュールされた保持が
あるのは最後のディレクトリだけで、それもワークスペースが存在する間に限られます。
インストール全体のスナップショットを削除するには、インストールのオーナーが明示的に操作する
必要があります。
