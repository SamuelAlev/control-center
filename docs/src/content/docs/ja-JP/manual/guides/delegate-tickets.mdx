このガイドでは、自分の手元にある作業をエージェントへ渡す方法と、エージェント
同士が作業をやり取りするときに何が起こるかを扱います。

:::caution[チケットをエージェントに割り当ててもディスパッチは行われません]
エージェントの担当者向けのチケットディスパッチャーはありません。割り当ては所有権を
記録するだけで、それ以上のことは何も起こりません — スペースは作成されず、ステータスも
変わらず、エージェントも起動しません。例外は、**チーム**に割り当てられたチケットで、
これはそのチームのリーダーを起こします。特定の担当者のエージェント作業は会話の中に
あります。したがって、始める場所もそこです。
:::

## チケットをエージェントに渡す

1. [チケットを作成](/ja-JP/マニュアル/ハウツーガイド/チケット管理/)します。作業の
   よりどころとして十分に正確なタイトルと説明を付けます。
2. その**担当者**をそのエージェントに設定し、所有権を記録に残します。
3. スペースを開く（または作成し）、そのエージェントを @メンションします。
4. メッセージ内で `#` メンションを使ってチケットを参照し（コンポーザーが
   ワークスペースのチケットを自動補完します）、何をしてほしいかを伝えます。

エージェントは会話から作業を拾い上げます。その進捗はそのスペースに
ストリーミングされます。

## エージェントが受け取るもの

- あなたのメッセージ（タグ付けしたチケット参照を含む）。
- 作業と報告を行うスペース。
- ワークスペースのリンクされたリポジトリから作られた、隔離されたワークツリー。
- スペースの**モード**。実行のツールサーフェスを左右するのはこれです。

モードはチケットではなくスペースのプロパティです — チケットにモードはありません。
したがって、同じエージェントが一方のスペースでは `chat`、もう一方では `plan` に
いることがあります。コンポーザーのモードドロップダウン（**Agent**、**Plan**、
**Orchestrate**）から選びます。`review` は PR レビューのスペースが設定するもので、
選択できません。[モード](/ja-JP/マニュアル/コンセプト/モード/)を参照してください。

## 構造化された結果を要求する

出力コントラクトは、チケットではなくディスパッチで宣言されます:
`expected_output_schema` と `output_contract_mode`（既定では strict）です。エージェントは
`submit_output` を呼び出してこれを満たします。`submit_output` はペイロードをスキーマに
対して検証し、適合しないものは拒否します。

承認された出力も、拒否も、どちらも**エージェントの実行ログ**に残ります。チケット
自体のステータスはこれに影響されません — コントラクトに失敗しても、チケットは
失敗しません。

## 進捗を監視する

- **スペース** — エージェントのライブアクティビティ。主要なビューです。
- **チケット** — そのステータス。動かした人が設定したとおりになります。
- **オブザーバビリティ → ライブ** (`/workspaces/<workspace-id>/observability`) —
  ライブのエージェント名簿。
- **オブザーバビリティ → インサイト** — 実行ログ。コストと所要時間付きです。

ダッシュボード画面はありません。ワークスペースの URL だけを開くと、受信トレイに
リダイレクトされます。

## エージェント同士で委任できるようにする

部分問題にぶつかったエージェントは、`delegate_task` MCP ツールで委任します。これは
別のエージェントに割り当てられた子チケットを作成し、`parent_ticket_id` を渡した
場合は、ガードが見られるように連鎖を記録します。

チケッティングのチョークポイントでは、プロンプトの指示によってではなく、常に
2 つの構造的ガードが実行されます:

- **深さの上限** — 3 ホップより深い連鎖は拒否されます。
- **循環検出** — すでに連鎖にいるエージェントへ戻るホップは拒否されます。

`from_agent_id` を渡すと、さらに 2 つのガードが実行されます（プロダクションは常に
リゾルバーポートを供給します）:

- **自律性の上限** — スペース内での委任先の実効レベルが、委任元を超えてはなりません。
- **予算のエンベロープ** — 委任は委任元の残りのハードストップ予算から引かれ、
  それ以上を生み出すことはできません。ポリシーがない場合、または無制限の
  ポリシーの場合は通過します。

拒否は声高です。ツールはガードの理由をそのまま返すため、委任したエージェントは
理由を正確に把握できます。`delegatedByAgentId` フィールドは誰が委任したかを記録し、
委任ツリーを形成します。

:::caution[`delegate_ticket` はすべてのガードをスキップします]
古い `delegate_ticket` ツールは今も登録されており、`createTicket` を直接呼び出します —
深さの上限も、循環のチェックも、自律性の上限も、予算のエンベロープもありません。
`delegate_task` を優先してください。
:::

この委任の深さの上限 3 は、内蔵ハーネスのサブエージェントのネスト上限 2 とは
別の制限です — 一方はエージェント間のチケットを制限し、もう一方は 1 回の実行内の
サブエージェントを制限します。

## 複数のエージェントを 1 つのチケットに割り当てる

チケットに**コラボレーター**として追加します（ロール: 担当者、コラボレーター、
レビュアー）。これは名簿、つまり誰が関わっているかの記録であり、それ自体では
何も付与しません。

実際にエージェントを同じ会話に入れるには、スペースのヘッダーから参加者として
追加します。そうすると、そこで互いに @メンションできるようになります。
[スペース](/ja-JP/マニュアル/ハウツーガイド/スペース/)を参照してください。

## 自動でのチケット作成

パイプラインのパレットにチケットを作成するノードはないため、パイプラインで作業を
割り当て済みチケットとして展開することはできません。

存在する経路はオーケストレーションです。提案を承認するとプロジェクトとチームが
作成され、提案のサブチケット DAG が**パイプラインテンプレート**にコンパイルされ
（サブチケットごとに 1 つの `promptAgent` ステップで、それぞれが `Ticket` 行に
なるわけではありません）、その実行が開始されます。
[オーケストレーションを実行](/ja-JP/マニュアル/ハウツーガイド/オーケストレーション実行/)
を参照してください。
