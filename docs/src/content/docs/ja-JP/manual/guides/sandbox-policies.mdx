エージェントの実行がサンドボックス化されるかどうかは、サーバー側で起動時に決まります
（`--sandbox`）。**設定 → サーバー →
診断とプライバシー** にある **サンドボックスを有効にする** トグル、**バックエンド** ピッカー、
**デフォルトの機能 · 新しいスペース** トグルは、お使いのデバイスに保存される設定です。
**サンドボックス化** カードのホスト検出は、サーバーホストが何をラップできるかを報告します。

実行に届く制御は 2 つあり、このガイドではその両方を扱います: 後述するエージェント単位の
**サンドボックスの権限** と、サーバー自身の `--sandbox` フラグです。

## エージェントの実行を制約するもの

エージェントを制約しているのは 6 つです。1 つ目は OS サンドボックスで、唯一条件付きの
ものです — 残りの 5 つはどのホストでも保たれます。

| 境界                 | 動作                                                                                                                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OS サンドボックス           | macOS では Seatbelt、Linux と WSL2 では bubblewrap。Claude Code CLI、ACP アダプター、ハーネスの `bash` ツールをラップします。**Windows、および `bwrap` と `socat` のない Linux では存在しません** |
| エージェント自身のワークツリー         | 会話ごとにコピーオンライトのチェックアウトを取得します。元のチェックアウトは書き込み拒否パスとして実行に折り込まれ、それを強制するのはサンドボックスです                                            |
| ブローカー経由の資格情報     | 資格情報ブローカーは、エージェントのケイパビリティから実行ごとの環境を発行し、終了時に取り消します。ケイパビリティがなければ、環境にトークンもありません                                            |
| アクションガードレール        | 変更を伴うすべてのツールがエフェクトクラスを宣言し、ガードが呼び出しの実行前にそれを解決します。承認者が接続されていない `prompt` は拒否されます                                                 |
| 環境のサニタイズ | ACP とハーネスの `bash` ツールはフィルタリングされた環境を受け取ります。`NoSandboxAdapter` 経由の Claude Code はホストの環境を継承します                                                                  |
| モードのツールサーフェス  | 読み取り専用モードはワークツリーを変更するツールを完全に取り除き、それでも成果を届けられるようモード自身の出力動詞を固定します                                                                         |

見た目よりも弱いままの点が 3 つあります:

- ツールゲート、完了契約、構造的なモードルールを強制するのは **内蔵ハーネス** だけです。
  Claude Code アダプターは強制しません。特に Claude
  Code は `--dangerously-skip-permissions` 付きで起動されます。非対話の
  `claude -p` はそうしなければ自身のプロンプトで永久にブロックしてしまうからです —
  そのため Claude 自身の read、write、edit、bash 呼び出しは Control Center
  からも見えず、ゲートもされません。サンドボックスがオンの場合、それらを取り囲む境界がサンドボックスです。
- ハーネスのインプロセスのファイルツール（read、write、edit、apply patch、search、
  find、search_files）はサーバープロセス内で動作するため、サンドボックスプロファイルが
  それらを制約することはありません。サンドボックス化されたコマンドランナーを通るのは `bash`
  ツールだけです。これらのツールは自身のパス閉じ込めとアクションガードレールによって制限されています。
- バックエンドのないホストでは、最初の行がまったく当てはまりません。ACP とハーネスの
  `bash` ツールは、環境のサニタイズとコマンドポリシーにフォールバックします。Claude Code は
  `NoSandboxAdapter` 経由でホストの環境を継承します。サーバーはその旨を起動ログで通知します。
  お使いの環境は後述の方法で確認してください。

## エージェントのケイパビリティを設定する

これはサーバーが読み取る唯一のケイパビリティ制御です。エージェント単位で、資格情報
ブローカーがそのエージェントの環境に何を入れるかを決めます。

1. **設定 → ワークスペース → エージェント** に移動します
2. 一覧からエージェントを選択します
3. **設定** タブで **サンドボックスの権限** までスクロールします
4. スイッチをオンにします — 行のキャプションが **ワークスペースのデフォルトを使用** から変わります
5. 4 つのトグルを設定します:

| トグル                           | 制御する内容                                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **git push を許可**               | これがオフの場合、実行には `GIT_ASKPASS=/usr/bin/false` と `GIT_TERMINAL_PROMPT=0` が設定されるため、プッシュが資格情報を要求することはできません                                                                                                                   |
| **GitHub API の呼び出しを許可**       | **git push を許可** と合わせて、ブローカーが GitHub トークンを `GH_TOKEN` / `GITHUB_TOKEN` として注入するかどうかを制御します                                                                                                                               |
| **チケット API の呼び出しを許可**    | ブローカーが `TICKETING_API_KEY` を注入するかどうかを制御します                                                                                                                                                                                             |
| **一般的なネットワークアクセスを許可** | サンドボックスがオンの場合、これは実際の外向き通信ゲートです: オフにすると実行の許可リストが空になり、外向きのあらゆるリクエストがプロキシで拒否されます。バックエンドがない場合は、実行に記録されるだけで、スポーンされたプロセスが行うことを何もブロックしません |

6. 保存

チェックポイント: エージェントを再度開くと、スイッチはオンのままでトグルも保持されています —
保存されたケイパビリティセットはサーバーを往復し、何も設定していないエージェントは
保守的なデフォルト（プッシュ オフ、GitHub API オフ、チケット オフ、
ネットワーク オン）にフォールバックします。

:::caution[この落とし穴に陥る 2 つの経路]
キャプションには **ワークスペースのデフォルトを使用** とありますが、サーバーが読み取る
ワークスペースレベルのケイパビリティ設定は存在しません。スイッチがオフのエージェントには、
組み込みの保守的なデフォルトが適用されます。

これとは別に、実行の GitHub 資格情報は常にブローカーのものだけです — リポジトリ単位の
GitHub App インストールトークン、または環境の PAT フォールバックであり —
要求したメンバー自身が保存したトークンが使われることは決してありません。`actingUserId` が
渡されるのは、オーナーではなく GitHub を接続していないメンバーからサーバーの PAT を
*伏せる*ためであり、オフのケイパビリティに個人トークンを上書きするものではありません。
OS サンドボックスのないホストでは、**GitHub API の呼び出しを許可** を厳格な外向き通信の
境界として扱わないでください: スポーンされたプロセスは依然としてネットワークに到達できます。
:::

## エージェントの実行がサンドボックス化されているか確認する

決めるのは 2 つで、どちらもサーバー側にあります: ホストがバックエンドを提供するかどうかと、
`--sandbox` がオンかどうかです。この順に確認します。

1. **設定 → サーバー → 診断とプライバシー** に移動します
2. **サンドボックス化** カードを読みます。**ホスト** の項目は `cc_server`
   が動作しているマシンであり、今見ているマシンではありません。**バックエンド** フィールドには
   **ネイティブサンドボックス**（macOS では Seatbelt、Linux と WSL2 では bubblewrap）または
   **分離なし** が表示されます。**有効** の項目はこのデバイスの設定であり、
   サーバーが実際に使うラップではありません。
3. サーバーの起動ログを読みます。次の 3 行のうち正確に 1 行が出力されます:
   - `agent sandbox ON` とバックエンドの注記 — 実行はラップされます
   - `no OS-native agent sandbox on this host` と、あればインストールのヒント —
     実行はラップされません
   - `agent sandbox DISABLED by --sandbox off` — 意図的なオプトアウト

`GET /healthz` はサンドボックスの状態を報告しないため、確認するのは起動ログです。

意図的にサンドボックスをオフにするには — プロファイルが誤動作するホストが、
このオプションの存在理由です — サーバーを `--sandbox off` で起動するか、
`CC_SERVER_SANDBOX=off` を設定します。デフォルトは `on` で、`on` は「ホストに
バックエンドがあれば使う」という意味であり、「バックエンドを必須にする」という意味では決してありません。

ネイティブサンドボックスのラップが得られない状況が 2 つあります。**Windows** では
ネイティブプローブが常に利用不可を報告し、インストールできるものもありません — エージェントの
ディスパッチは `none` を使います。`microvm` バックエンドは別系統（対話ターミナルとリグ）
であり、独自のランタイムを対象にプローブでゲートされます。**Linux と WSL2** では `bwrap` と
`socat` の両方が `PATH` 上になければなりません。なければプローブは利用不可を報告し、
不足しているパッケージを名指しします。

bubblewrap がインストールされた Linux/WSL2 では、標準ポリシーのシークレットファイル
glob を、エージェントが後から作成するファイルに対して強制できません。そのようなネイティブ
実行は、ルールを黙って無視するのではなく、今では失敗します。したがって、起動プローブが
成功しても、Linux のディスパッチが開始できることを保証するものではありません。`--sandbox off`
は意図的な非閉じ込めのオプトアウトであり、セキュリティ境界の代替ではありません。

## モードがすでに禁止していることを知る

モードはスペースごとに保存され、**モードプリセット** レイヤーとしてガードレール
リゾルバーに渡されます。4 つのモードのうち 3 つは読み取り専用で、読み取り専用モード
は 11 のエフェクトクラスを即座に拒否します:

| モード               | ワークツリー  | プリセットによる拒否                                                                                                                                                            |
| ------------------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent**（`chat`） | 書き込み可能  | なし — 組み込みのデフォルトが適用されます                                                                                                                                            |
| **Plan**           | 読み取り専用 | ファイルの削除、ワークツリー外への書き込み、コミット、プッシュ、PR の作成、公開またはマージ、外部トラッカーへの書き込み、パッケージのインストール、プロセスの実行、ワークスペース構造の変更、エンクロージャーの起動または操作 |
| **Review**         | 読み取り専用 | 同じ 11 個です。ユーザーが選択することはできません — コンポーザーが提供するのは Agent、Plan、Orchestrate だけです                                                                                         |
| **Orchestrate**    | 読み取り専用 | 同じ 11 個です                                                                                                                                                                     |

ネットワークアクセスとシークレットへのアクセスは、読み取り専用モードでも意図的に
拒否_されません_。調査こそが読み取り専用モードの目的だからです。

## アクションの実行前に承認を必須にする

承認はガードレールの決定であり、サンドボックスの設定ではありません。

1. **設定 → ワークスペース → エージェントの権限** に移動します
2. ワークスペース、エージェント、スペースのいずれかのスコープで、アクションクラスを **先に確認** に設定します

**先に確認** の決定は実行を中断してあなたに尋ねます。承認者が接続されていない場合は
フェイルクローズし、アクションは拒否されます。解決順序の全体は
[ガードレールを設定](/ja-JP/マニュアル/ハウツーガイド/ガードレール設定/) を参照してください。

## トラブルシューティング

### エージェントがプッシュできず、拒否した覚えもない

エージェントの **サンドボックスの権限** を確認します。カスタムのケイパビリティセットを
持たないエージェントには保守的なデフォルトが適用され、**git push を許可** はオフです —
そのためブローカーは GitHub トークンを注入せず、git には認証する手段がありません。

### サンドボックス化カードがネイティブサンドボックスなしと報告する

そのホストのエージェント実行は Seatbelt や bubblewrap でラップされておらず、
残りの境界があなたの持っているものです。Linux と WSL2 では、不足している両方の
ツール — `sudo apt-get install bubblewrap socat` — をインストールし、サーバーを
再起動します。そうすれば起動ログにサンドボックスがオンであると表示されるはずです。Windows には
インストールできるネイティブバックエンドがないため、代わりにガードレールを厳しくします:
[ガードレールを設定](/ja-JP/マニュアル/ハウツーガイド/ガードレール設定/) を参照してください。

### エージェントがワークツリー外のファイルに到達した

それに到達したのがどのツールかで、これが想定どおりかどうかが決まります。

ハーネスのインプロセスのファイルツール（read、write、edit、apply patch、search、
find、search_files）はサーバープロセス内で動作するため、サンドボックスプロファイルは
適用されません — それらの境界は、自身のパス閉じ込めとガードレールです。`bash` コマンドや Claude Code
CLI は、バックエンドが存在する場合はラップ_され_、登録済みの
チェックアウトはそのラップ内でどのモードでも書き込み拒否になります。シンボリックリンクを
解決した綴りも含まれます（macOS では `/tmp` や `/var/folders` を通して到達したパスは
`/private` 配下に解決され、どちらの綴りも拒否されるようになりました）。バックエンドの
ないホストでは、そのいずれも当てはまりません。どちらの場合でも、ガードレールは
**ワークツリー外への書き込み** を即座に拒否できます。
