このガイドでは、セットアップのうち GitHub に固有の部分を扱います。GitHub は対応している 3 つの
コードホストの 1 つです — GitLab や Bitbucket の接続方法と、ワークスペースでこれらを
併用する方法については、[コードホストを接続](/ja-JP/マニュアル/ハウツーガイド/コードホスト接続/)
を参照してください。

## 前提条件

- 作業したいリポジトリにアクセスできる GitHub アカウント
- 人々を GitHub にサインインさせられるサーバー。サーバー自身の GitHub App（
  [GitHub App を作成](/ja-JP/マニュアル/ハウツーガイド/github-app/)を参照）か Control Center
  Connect のどちらかで、サーバー所有者が **設定 → サーバー → シングルサインオン** で選びます

:::note[認証情報はサーバー上にあり、あなたに紐づきます]
入力しているマシン上には何も保存されません。あなたの GitHub サインインは
`cc_server` が保持し、あなたのユーザー id をキーとして管理されます。サインインしたすべてのデバイスが
それを使用します — デスクトップ、ウェブ、スマートフォンです。同じサーバーの別のメンバーはそれを
使うことはできず、その人のサインインはその人自身が行います。
:::

## GitHub にサインインする

GitHub はサインインのみです。貼り付けるトークンはありません。

1. **設定 → 自分 → プロフィール → コードホスティング**（またはオンボーディングの
   最初のステップ）に移動します
2. **GitHub** の行で **GitHubにサインイン** をクリックします
3. ブラウザーで GitHub が開きます。アプリを承認します

サインインの完了の仕方は、誰がそれを実行するかによって異なります:

- **サーバー自身のアプリ:** GitHub がブラウザーをサーバーに戻し、ダイアログが自動的にそれを
  検知します。入力するものはありません
- **Control Center Connect:** ブラウザーのページに 8 文字のコードが表示されます。それをダイアログに
  入力するか、`control-center://` リンクを通じてブラウザーに Control Center を開かせ、入力を省きます

チェックポイント: **GitHub** の行に「_your-username_としてサインインしています。」と表示されます。

ダイアログは、自分で開始していないコードやリンクを **ここで開始されたサインインではありません** と
表示して拒否します。誰かからサインインのリンクが送られてきても、続行しないでください。完了すると、
あなたのアカウントがその人のサーバーに接続されてしまいます。

サインインを削除するには **切断** をクリックします。GitHub からサインアウトするか、ワークスペースから
外されると、サーバーがあなたの代わりに発行したすべてのトークンも破棄されます。

## 認証情報が誰の代わりに動くか

Control Center は、人として行動することと、アプリとして行動することを区別する GitHub 自身の分け方に従います:

| 何が起きるか                                                                              | GitHub 上の表示                                                                  |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 自分で行うこと全般: コメント、レビュー、承認、マージ、レビュアーのリクエスト              | **あなた**。GitHub は会話内のコメントに Control Center アプリで作成されたものであることを示すマークを付けますが、レビューとそのインラインコメントにはそのマークは付きません |
| AI レビュー、PR 会話でのエージェントの返信とコメント、ラベル、パイプラインとボットの作業            | **Control Center のボット**。共有の Connect アプリでは、レビューは Connect の運営者が一覧に登録したインストールの場合にだけボットのものです。それ以外は責任を負う人として表示されます |
| エージェントがあなたのために開くプルリクエストと、そのプルリクエストのタイトルや説明への編集、そのプッシュおよびそのコミット            | **あなた**。共同作成者のクレジットがオンの場合、Control Center が共同作成者としてクレジットされます |
| 誰も依頼していない作業（スケジュール、Webhook）                                           | **Control Center のボット**（そのコミットの作者も兼ねます）。Control Center Connect では、プッシュもプルリクエストの作成も決して行いません |

- **自分で行うこと**は、すべて**あなたの**サインインで実行され、ほかのものは使われません。サインインしていない場合、アプリはサインインを求めます
- **ボットの作業**は、一度に 1 つのリポジトリ用のトークンを受け取ります。それは責任を負うメンバーがそこでできることに制限されます: 依頼した人、そうでなければワークスペース所有者。プッシュできないメンバーの場合は読み取りに限定されます。誰かの代わりに行動するボットの返信は、**Control Center（@login の代理）** で始まります
- **エージェントは Control Center を通じてプルリクエストを開きます**。サンドボックスから直接開くことはありません。そのためプルリクエストはあなたのものになり、GitHub 自身のルールにより、あなたは自分でそれを承認できません。Control Center は、エージェントに依頼した本人と、プルリクエストの作成者による承認も拒否します。スケジュールや Webhook の実行の場合、それは、その起動条件を有効にした、または有効中にパイプラインを編集したすべての管理者を含みます。別の人がレビューしなければなりません。Control Center がプルリクエストを開いたのが誰か、またはフォージ上のどのアカウントがあなたのものかを確認できない場合、それは拒否し、もう一度試すよう求めます
- **エージェントはコメントも Control Center を通じて行います**。エージェントの実行が受け取る GitHub トークンは読み取りしかできません。エージェントが作業中のプルリクエストにコメントすると、Control Center がボットとしてそのコメントを投稿します。実行を依頼した人がいる場合は **Control Center（@login の代理）** で始まります。エージェントは、同じリポジトリ内にあり（フォークではない）、最新のコミットをエージェント自身がプッシュしたか、そのスペースのブランチの現在のコミットであるプルリクエストにのみコメントできます。エージェントのコメント内の @メンションは、誰にも通知しません。エージェントは、作業中のプルリクエストのタイトルや説明を、そのプルリクエストが開いている間に変更することもできます。その編集は、プルリクエストを開いたときと同じ方法で行われ（実行を依頼した場合はあなたとして）、既定では先に承認を求めます。プルリクエストの説明は、エージェントが開くときも編集するときも @メンションを保持するため、そこで名指しされた人に通知されます
- **Control Center Connect では、ボットがプッシュやプルリクエストを開くことは決してありません**。そこでのプッシュ、ブランチの作成、プルリクエストの作成には、それを依頼した人が必要で、その人のサインインで実行されます。プッシュを試みるスケジュールや Webhook の実行は、その旨のメッセージとともに停止します。無人の実行にプッシュを許可するには、**設定**でワークスペースに独自の GitHub App を割り当ててください
- **共有 Connect アプリでのボットにできること。** 共有 Connect アプリでは、ボットはコメント、ラベル、リアクションを行います。レビュー（AI レビュー、レビューコメント、レビュアーの依頼）を投稿するのは、Connect の運営者がこのサーバーのインストールを一覧に登録している場合だけです。そうでなければ、レビューは責任を負う人自身のサインインで公開され、その人の名前で表示されます。ボットがプルリクエストを開く、編集する、クローズする、タイトルを変更する、レビューを却下する、コメントを編集または削除することは決してありません。それらには、依頼した人が自身のサインインで行う必要があります。Connect はあなたの組織のインストールを 1 つの Control Center サーバーに結び付けません。リポジトリにプッシュできるメンバーが Connect でサインインしていれば、どのサーバーでも、そのリポジトリのボットのコメント用トークンを取得できます
- **独自の GitHub App を持つサーバーやワークスペース**は、レビューを含め、上記すべてについてボットを保持します
- **自動化がプルリクエストを承認することは決してありません**。承認は人の行為です

リポジトリをリンクすると、Control Center はあなたのアカウントがそれを見られるかを確認します。また、GitHub App がそのリポジトリの組織にインストールされていない、またはリポジトリを含んでいない場合は警告し、修正用のリンクを表示します。リンクとリンク解除には、ワークスペース管理者が必要です。ワークスペース自身のストレージの外にあるチェックアウトは、サーバーオーナーだけがリンクできます。[ワークスペースにリポジトリを追加](/ja-JP/マニュアル/ハウツーガイド/リポジトリ追加/)を参照してください。

リポジトリのリンクは、リポジトリの永続的な GitHub ID に従うため、名前の変更や移管で何かをする必要はありません。後でパスが別のリポジトリを指すようになった場合、Control Center はそれに何も送らなくなり、ワークスペース管理者が **再リンク** をクリックするまで通知を表示します。

リポジトリのコード（ファイル、差分、検索、ターミナル）を開くには、ワークスペースでのその権限付与と、それを読めるあなた自身の GitHub サインインの両方が必要です。ワークスペース管理者も同じルールに従います。例外はサーバーオーナーだけです。

## インテグレーションでできること

| 機能             | 仕組み                                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------- |
| PR 一覧と詳細  | サーバーから、あなた自身のサインインで GitHub REST API を利用                                                    |
| チェック実行          | GitHub Checks API                                                                                          |
| レビューの公開   | あなたのレビューをあなたとして PR に投稿する、ユーザーの操作を必要とするステップ                                     |
| リポジトリの登録   | チェックアウトの `origin` リモートが github.com — または gitlab.com / bitbucket.org — を指していれば受け入れられます          |
| エージェントの GitHub アクセス | 実行中は、`git fetch` は Control Center を通ります。Control Center は、実行が保持しない読み取り専用トークンで、その実行が扱うリポジトリをフェッチします。`gh` は、Control Center が求めに応じて発行し、実行の終了時に失効させる読み取り専用トークンでそれらを読み取ります。プッシュ、プルリクエスト、その編集、コメントは Control Center を通ります |
| 通知ピング  | サーバー側で GitHub の通知受信トレイをポーリングし、「プルリクエストでメンション」と「レビュー依頼」を発生させます |
| ユーザープロフィール       | プロフィールのホバーカードと、作者ごとの PR フィルタリング                                                                |

一部の経路では、よりコストが低い箇所で REST の代わりに GraphQL API を使用します — PR 作成
ピッカーのブランチアクティビティと、レビュー依頼の通知がまだ保留中かどうかを判断する
ライブのレビュー状態です。

## GitHub の障害を監視する

プロバイダーが機能低下しているとき、タイトルバーにステータスチップが表示されます。対象は GitHub、
Claude、OpenAI、Kimi です。**すべてが正常な間は非表示になります** — 表示は障害の存在を
伝えるものであり、その不在を伝えるものではありません。

チップをクリックすると、各プロバイダーの状態と更新ボタンを備えたフライアウトが開きます。
ステータスは 2 分ごとに自動で更新されます。

## エージェントが GitHub でどのように動作するか

- GitHub のワークツリーで作業するエージェントは、そのリポジトリ 1 つだけを対象とするトークンを
  受け取ります。読み取れるのはコード、イシュー、プルリクエストだけです。コメントは上で説明したとおり
  Control Center を通ります。プッシュは Control Center を通り、Control Center は
  **リモートへプッシュ** のルールに問い合わせてから、エージェントが決して持たない書き込みトークンで
  プッシュを転送します。[サンドボックスポリシーを設定](/ja-JP/マニュアル/ハウツーガイド/サンドボックスポリシー/)を参照してください
- 自分で始めた作業は、あなた自身の名前でコミットされます。エージェントに何かを依頼した場合、または IDE でコミットした場合、あなたが作成者およびコミッターとなり、フォージが検証したアドレスで記録されます。GitHub サインインからの GitHub noreply アドレス、または GitLab や Bitbucket ではそこでのサインインが報告するメールです。ワークスペースの Git ID が使われるのは、フォージがあなたのアドレスを保証していないリポジトリで、手作業で行ったコミットだけです。そのフォージにサインインしていない場合、エージェントのコミットはその代わりにボットのものになり、実行のメモにその旨が記載されます
- 誰も依頼していない作業は、ボットとしてコミットされます。スケジュールや Webhook の実行は、ワークスペースの GitHub App（`<app>[bot]`、GitHub noreply アドレス付き）として、または GitHub App がない場合、またはリポジトリが GitLab や Bitbucket にある場合は `Control Center <hi@usectrl.dev>` としてコミットします
- **Control Center を共同作成者としてクレジットする**（**設定** → **自分** → **コミット**）は、もう一方の当事者のために `Co-Authored-By:` トレーラーを追加します。あなたのコミットには Control Center、ボットのコミットには、その実行の背後にあるトリガーを有効にした各人です。オフにしない限りオンです。ワークスペース管理者は、**設定** → **ワークスペース** → **一般** の **共同作成者のクレジット** で、それをすべての人について決められます。その場合、あなた自身の選択は保存されますが、そのワークスペースでは適用されません。Claude Code 自身の帰属表示は常に無効です
- あなたのコミットには署名できます。**設定** → **自分** → **コミット** の **検証済みのコミット** で **署名鍵を作成** を選び、その公開部分を GitHub または GitLab アカウントに署名鍵として追加します。それ以降、あなたが依頼した実行のコミットと、IDE で行ったコミットは検証済みとして表示されます。秘密の部分はサーバー上に残るため、鍵がアカウントに登録されている間は、そのサーバーを管理する人があなたとして署名できます。また GitHub では、検証済みと表示されたコミットは、鍵を削除した後も検証済みのままです。Bitbucket には署名専用の鍵がないため、そこには鍵を追加しないでください。Bitbucket のコミットは署名されません。ボットのコミットには決して署名されません
- IDE の **ソース管理** パネルで行ったコミットは、`git commit --no-verify` と同様に、リポジトリの Git フックを経由しません。また、サーバーの Git は、リポジトリが設定した認証情報ヘルパー、エディター、外部の差分ツール、署名ツールを無視します。Git はサーバー自身のマシン上で、エージェントやプルリクエストが変更できるツリーに対して実行されます。[ソース管理からコミットとプッシュ](/ja-JP/マニュアル/ハウツーガイド/pr-レビューとマージ/#ソース管理からコミットとプッシュする)を参照してください
- エージェントがプッシュするすべてのコミットは、まず検査されます。スタックの `stack_publish` がプッシュするレイヤーも含みます。別の人を指定する、クレジットを削除または借用する、sign-off を追加する、または設定どおりに署名されていないプッシュは拒否されます。あなたが IDE から自分でプッシュしたコミットはあなたのものであり、この方法では検査されません
- リグで開いたターミナルは、その 1 つのリポジトリに絞り込まれたあなた自身のサインインを受け取るため、
  そこでのプッシュはあなたのものになります
- トークンを発行できない場合（責任を負う人がサインインしていない、アプリが所有者にインストール
  されていない、インストールが一時停止されている）、そのトークンを求めたコマンドが、その理由を示します。フォールバックの認証情報はありません

## トラブルシューティング

### PR 一覧が空で、GitHub が接続されていないと表示される

このサーバーで GitHub にサインインしていません。**設定 → 自分 → プロフィール → コードホスティング** の下の **GitHubにサインイン**
をクリックしてください。他のコードホストのリポジトリには影響しません。

### GitHub の行に、このサーバーではサインインが設定されていないと表示される

サーバーには独自の GitHub App も Connect もありません。サーバー所有者が **設定 → サーバー →
シングルサインオン** でどちらかを選びます。**自分のGitHubアプリを作成** は約 2 分で完了します。
[GitHub App を作成](/ja-JP/マニュアル/ハウツーガイド/github-app/)を参照してください。

独自のアプリを使うワークスペースでは、ワークスペースの GitHub App が欠けているか不完全な場合に、その行にそう表示されます。ワークスペース管理者が **設定 → ワークスペース → 連携** の **GitHub App** カードでそれを補完します。詳しくは [1 つのワークスペースに独自の App を使わせる](/ja-JP/マニュアル/ハウツーガイド/github-app/#1-つのワークスペースに独自の-app-を使わせる)を参照してください。

### ダイアログに、コードが一致しないと表示される

ブラウザーに表示されたとおりにコードを入力してください。英数字 8 文字です。誤ったコードを 5 回
入力するとサインインは終了するので、最初からやり直してください。

### サインインで、アプリがインストールされていないと表示される

リポジトリを所有するアカウントに GitHub App のインストールがありません。ワークスペース管理者が
**設定 → ワークスペース → 連携 → GitHubアプリのインストール** からインストールします。

### 全員が GitHub に再度サインインしなければならない

サーバー所有者がサーバーの Connect 鍵を更新したか、Connect サーバーを切り替えたか、データ
ディレクトリが別のマシンに復元されました。Connect を通じたサインインは、それを作成したサーバーに
結び付けられています。

### リポジトリの追加が拒否される

登録には次の 3 つすべてが必要です。パスが git ワークツリーの内部にあること、`origin`
リモートがあること、そしてそのリモートが対応しているコードホスト（github.com、
gitlab.com、bitbucket.org）を指していることです。`origin` は、リンクしようとしているリポジトリでなければならず、ワークスペース自身のストレージの外にあるフォルダーは、サーバーオーナーだけがリンクできます。
[ワークスペースにリポジトリを追加](/ja-JP/マニュアル/ハウツーガイド/リポジトリ追加/)を参照してください。

### 権限付与はあるのに、リポジトリがアカウントで読めないと表示される

あなたの GitHub アカウントはそのリポジトリを読めないため、ワークスペースの権限付与があってもコードはあなたに対して閉じられたままです。**コードホスティング** の下で GitHub にサインインするか、GitHub でそのリポジトリへのアクセスを依頼してください。

### "GitHub へのアクセスを確認できませんでした"

GitHub に到達してアクセスを確認できなかったため、Control Center は推測せずに拒否しました。少し待ってから、もう一度試してください。

### Connect 上のレビューが、ボットではなく自分の名前で表示される

共有 Connect アプリでは、ボットは Connect の運営者が一覧に登録したインストールについてだけレビューを投稿します。それ以外の場所では、レビューは責任を負う人自身のサインインで公開されます。ボットにレビューを投稿させるには、ワークスペースに独自の GitHub App を割り当ててください。

### 集中的に使ったあと、しばらく何も動かなくなる

それはレート制限のサーキットブレーカーです。GitHub はプライマリ制限を、
`x-ratelimit-remaining: 0` とリセット時刻を伴う `403` で通知します。クライアントはそれを見ると、
ウィンドウが経過するまで、ネットワーク呼び出しを行わずに以降のリクエストをローカルで失敗させるため、
リトライの嵐が制限を深刻化させることはありません。一時的な失敗は、
指数バックオフで最大 3 回再試行され、`retry-after` が尊重されます。
