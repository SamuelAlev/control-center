このガイドでは、ひとつの大きな目標を、それ自体が動くチーム全体のプランに変える方法を説明します。仕組みについては[オーケストレーション](/ja-JP/マニュアル/コンセプト/オーケストレーション/)を参照してください。

## オーケストレーションをいつ使うか

依頼が 1 つのエージェントの手に余り、正確な手順をまだ把握していないときは、オーケストレーションを使います。単一のタスクなら[スペース](/ja-JP/マニュアル/ハウツーガイド/エージェントとチャット/)でエージェントにメッセージを送り、自分で手作業で書き出せるプロセスなら[パイプラインテンプレート](/ja-JP/マニュアル/ハウツーガイド/パイプライン作成/)を構築してください。

## ステップ 1: プランを依頼する

1. スペースを開き（または作成し）、**アンカーチケット** を用意します。すべての提案には 1 つ必要で（`propose_orchestration` は `ticket_id` を取ります）、共有スペースはそのチケットから決まります。
2. 任意で、コンポーザーのモードドロップダウンを **オーケストレート** に切り替えます。このモードでは、エージェントのできることが読み取りと提案（メモリ、コードグラフ、リポジトリとチケットの読み取り、`propose_orchestration`、プレイブックツール）に絞られるため、プランを立てる代わりにコードを書き始めることはできません。
3. オーケストレーター（通常は CEO エージェント）を @メンションし、目標を平易な言葉で伝えます:

> @ceo オフラインファーストのミーティングレコーダーについて競合状況を調査し、1 ページのポジショニングドキュメントを書いてください。

オーケストレーターは、スペースに構造化された **提案** カードで応答します。必要なロール、サブチケットに分解された作業、任意の調査とディスカッションのフェーズ、成果物を生成する統合ステップ、そして予算が含まれます。

提案は型付きオブジェクトであるため、何かが実行される前にアプリが検証します（整ったロール、宣言された出力スキーマ、循環のない DAG）。検証に失敗した提案は承認できません。

## ステップ 2: 提案をレビューして編集する

チャット内のカードには 3 つのアクションがあります: **プランを承認**、**却下**、**開く**。**開く** はプランをエディタータブとして Plan Studio で開きます。カード自体は編集できません。

何かを変更するには、**開く** を押して右側のインスペクターで作業します:

- 任意の作業ステップの **タイトル**、**説明**、**ロール**、**依存先**、**出力スキーマ**。ここでのロールとは、プランが既に持つロールキーのうちどれがそのステップを所有するかという意味です — インスペクターからロールを特定の名前付きエージェントに固定したり、採用リストを編集したりすることはできず、予算も編集できません。

読み取り専用なのは 2 つです。構造ノード（調査、ディスカッション、統合）と、すでに作業が実行されたノードです。編集できるのは、オーケストレーションがまだ `proposed` の間だけです。

承認する前に、承認バーの **見積もり** を押すと、コスト、所要時間、影響範囲の範囲を確認できます。エディターの全体像は [Plan Studio で作業する](/ja-JP/マニュアル/ハウツーガイド/plan-studio/) を参照してください。

:::note[予算は支出上限ではありません]
提案の予算は、承認バーの_見積もり_と比較されます。見積もりの上限が予算を超えると、合計が赤くなり予算超過の警告が表示されます。プランの実行中に支出をチェックするものはないため、実行を停止したり失敗させたりすることはありません。実際に支出を止めるには、エージェント単位の予算ポリシーを使います — [コスト管理](/ja-JP/マニュアル/ハウツーガイド/コスト管理/)を参照してください。
:::

## ステップ 3: 承認する

プランは、チャットのカードから、または Plan Studio の承認バーから承認します。**これがあなたが下す唯一の判断です。** 承認はオペレーター専用です — そのための MCP ツールは存在しないため、エージェントは提案と修正はできても、自分のプランを承認することはできません。

ここからは、決定論的なマテリアライザー（純粋関数で、LLM は使いません）が提案を実際の[パイプライン](/ja-JP/マニュアル/コンセプト/パイプライン/)に変換し、スキャフォールドを作成します:

- 新しいロールを採用します（採用したエージェント id を記録するため、承認途中でクラッシュしても重複採用なしで再開できます）
- ロールを **チーム** にまとめます
- **プロジェクト** を作成し、その下に親チケットを登録します
- すべてを動かす **パイプライン実行** を開始します

ステータスは `approved` に進み、次に `executing` になります。

## ステップ 4: 実行を見守る

サブチケットはパイプラインのステップとして実行されます。ディスカッションラウンドを有効にした場合、まず各ロールが立場を投稿します。進捗は、あなたがすでに確認している場所に表示されます:

- オーケストレーションを固定した **親チケット**
- チームが会話する共有 **スペース**。ここではプランの行が各ノードの状態を追跡します
- **パイプライン実行** の詳細。通常どおりウォーターフォールとステップごとのコストが表示されます — [パイプライン実行を監視](/ja-JP/マニュアル/ハウツーガイド/パイプライン監視/)を参照してください
- 親チケットを登録した **プロジェクト**

サブチケットが完了すると、ステータスは `synthesizing` に進み、統合ステップが成果物を生成します。そのテキストは共有スペースに投稿され、親チケットは完了としてマークされ、その後 `completed` になります。

## 途中で停止する

チャット内のカードで **オーケストレーションをキャンセル** を押すか、Plan Studio の承認バーで **実行をキャンセル** を押します。キャンセルすると、進行中の作業は破棄されます。

オーケストレーションは、マテリアライズが失敗したとき、または生成されたパイプライン実行が失敗したときに失敗します（調査、ディスカッション、統合、永続化 — これらのステップは失敗時に続行しません）。生成された **作業** ステップは常に失敗時も続行するため、サブチケットが 1 つ失敗しても実行全体は失敗しません。予算超過による失敗経路はなく、「すべてのサブチケットが失敗した」場合のしきい値もありません。
