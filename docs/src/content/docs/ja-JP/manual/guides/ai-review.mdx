このガイドでは、レビュアーエージェントにプルリクエストをレビューさせ、その結果を
GitHub に公開する方法を説明します。

## AI レビューを開始する

1. PR を開き、**概要**タブに移動します
2. アクション行の ⋯ オーバーフローメニューを開き、**AIに質問**を選択します

この項目は PR がオープンの間だけ表示されます — マージ前のアクションです。同じ
ボタンは、レビューがまだ存在しない**レビュー**タブの空の状態でも **AIに質問** と
して提供されます。

Control Center はシード済みの `pr_review` パイプラインを開始し、その様子を確認
できるように PR の**レビュー**タブを開きます。パイプラインは次のことを行います：

1. PR 自身のレビュースペースを開きます。その隔離されたワークツリーには、ヘッド
   時点の PR がチェックアウトされています
2. ワークスペースのレビューレベルに応じてレビュアーをファンアウトします —
   デフォルトでは 3 名（シード済みの **qa**、**architect**、**engineer**
   エージェントを並列で）。言語やドメインの検出は行いません
3. リード（CEO）エージェントに、それらの指摘をウォークスルーへ統合させます
4. ファイナライズします：指摘をコンセンサスのバケットに分類し、判定を算出します。
   関連付けが `awaiting approval` に達すると、**レビュー**タブに
   **GitHubに公開** が表示されます

レビューがどれだけ深く進むかは、ワークスペースの**レビューレベル** —
`light`（レビュアー 1 名）、`balanced`（3 名、デフォルト）、`thorough`
（5 名全員、セキュリティとパフォーマンスのスペシャリストを追加）— で決まり、
**設定 → ワークスペース → 全般**の**ワークスペースポリシー**カードで設定します。
軽いレベルでも登録される指摘の数はまったく同じで、前面に報告される数が少なくなる
だけです。

すべてのレビュアーは PR の単一のレビュースペースに投稿し、それによって彼らの指摘が
比較可能になります。各部がどのように組み合わさるかは
[AI レビュー](/ja-JP/マニュアル/コンセプト/ai-レビュー/)を参照してください。

`pr_review` には手動トリガーしか用意されていません。公開されたすべての PR で発火
させるには、自分でトリガーを追加します — 詳しくは
[レビュアーエージェントをディスパッチ](/ja-JP/マニュアル/ハウツーガイド/レビュアーのディスパッチ/)を参照してください。GitHub
側から開始することもでき、パイプライントリガーは不要です：PR でサーバーのボットに
メンションするか、`ai-review` ラベルを追加します — 詳しくは
[GitHub PR から Control Center に話しかける](/ja-JP/マニュアル/ハウツーガイド/github-pr-会話/)を参照してください。

このプルリクエストではレビューがすでに実行中だとトーストに表示された場合、すでに
1 つ進行中です。**レビュー**タブにとどまるか、**パイプライン**を開いて見つけて
ください。

## 指摘を読む

レビュアーは指摘を、レビュースペース内の**レビューノード**として記録します。各
ノードは次を保持します：

| フィールド     | 説明                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| 種別           | `bug`、`suggestion`、`recommendation`、`question`、`ticket`             |
| 優先度         | P0（重大）→ P3（些細な指摘）                                            |
| カテゴリ       | `security`、`stability`、`data_integrity`、`correctness`、`performance`、`maintainability` |
| ファイルと行   | 指摘がアンカーされている位置                                            |
| 元のコード     | 指摘の対象となるコード                                                  |
| 提案コード     | 提案された修正                                                          |
| 確信度         | レビュアーがどれだけ確信しているか                                      |
| ステータス     | `open` → `consensus-ready` → `resolved` または `dismissed`              |

指摘は、_ピア_のレビュアーが確認して初めて **consensus-ready** に達します。
エージェントは自分の指摘を確認できないため、単独のレビュアーの意見がそれだけで
昇格することはありません。

**レビュー**タブには、統合エージェントが公開した成果物の隣に、種別とステータスで
絞り込める指摘リストが表示され、却下済みの指摘を表示するトグルも付いています。
決定論的なビュー — コホート、多次元ダッシュボード、コントラクト diff とビジュアル
diff — はサーバー側で算出されますが、アプリに表示面はありません。このパスが何を
生み出すかは
[レビューコンピュート](/ja-JP/マニュアル/ハウツーガイド/レビューコンピュート/)を参照してください。

## 不一致パネルを確認する

2 人のレビュアーが同じファイルと行に指摘をアンカーしながら、その評価が大きく異なる
場合 — 優先度が 2 レベル以上離れている、あるいは一方が `bug` と呼び、もう一方が
`suggestion` と呼んでいる場合 —、指摘リストの上に不一致パネルが表示されます。まず
それらを読んでください：そこがレビュアーの意見の分かれる場所であり、あなたの判断が
最も価値を持つ場所です。

## 判定を読む

リードエージェントがファイナライズすると、**判定**を算出します：

| 判定      | 意味                                     |
| --------- | ---------------------------------------- |
| **Ship**  | ブロックするものは見つからなかった       |
| **Hold**  | マージ前に対処すべき問題がある           |
| **Block** | 修正しなければならない重大な問題がある   |

判定は、集約確信度スコアと優先度ごとの指摘件数を伴います。

その後レビューの軸が合流し、軸は判定を**より**厳しくすることしかできません。
ゲート対象の軸が失敗すれば **Block** が強制され、ゲート対象の軸が完了できなかった
（`partial`）場合、またはまったく実行できなかった（`unavailable`）場合は、
少なくとも **Hold** が強制されます。証拠がないことは、決してゲートをクリアしません。

## レビューを GitHub に公開する

公開は、意図的にユーザーがゲートする別個のステップです。`pr_review` パイプラインは
レビューを Control Center 内にとどめ、GitHub には投稿しません。

1. **レビュー**タブで、**GitHubに公開**が表示されるまで待ちます
2. **GitHubに公開**を押します

Control Center は **1 つ**の GitHub レビューを送信します。すでに解決済みまたは
却下済みの指摘はスキップされます。このボタンは残っているすべてのオープンな指摘を
含み、**Ship** の場合は `APPROVE` を送信します。（MCP ツール
`publish_review_to_github` は今もピアが確認した指摘のみをデフォルトとし、
`approve_on_ship` を渡さない限り承認しません。）ファイルと行のアンカーを持つ指摘は
インラインコメントになり、それ以外はすべてサマリー本文にまとめられ、それぞれに
「— Control Center AI review」というフッターが付くため、出所が曖昧になりません。
**Block** の判定は `REQUEST_CHANGES` として、**Hold** は `COMMENT` として、
**Ship** はこのボタンから `APPROVE` として送信されます。その後トーストに
**公開済み** と表示されます。レビューはサーバーのアプリ ID で投稿されます。

行が diff の一部でないために GitHub がインラインアンカーを拒否した場合、レビュー
全体が、すべての指摘を本文に畳み込んだ形で再送されるため、何も黙って落とされません。

:::caution[公開はガードレールでゲートされる]
`pr_review.publishReview` は `prPublish` アクションクラスを宣言し、ガードレールの
チョークポイントを通って実行されます。解決された決定が `prompt` で、承認者が接続
されていない場合、公開は拒否されます — ガードレールはフェイルクローズします。無人で
実行したい場合は、設定 → ワークスペース → エージェントの権限で明示的なルールを設定
してください。
:::

他の組み込みパイプラインは GitHub に直接投稿します：`cross_review`、`pr_triage`、
`ticket_to_pr`、`pre_merge_gate` はいずれもコメントステップで終わります。
`pr_review` だけが、その出力をあなたのために保留します。

## レビュアーを自分でディスパッチする

どのロールが PR をレビューするか、各ロールがどのファイルを見るかを制御するには、
既存のレビュースペース内で `dispatch_reviewers` MCP ツールを使うか、パイプラインに
レビュアーノードを追加します。どちらの方法も、ツールの正確なシグネチャとともに
[レビュアーエージェントをディスパッチ](/ja-JP/マニュアル/ハウツーガイド/レビュアーのディスパッチ/)に記載されています。
