このガイドでは、バックアップに関して実際によく行われる 5 つの作業、つまり取得、回収、
ワークスペースの移動、復元、マシン外へのコピー保持を扱います。各アーティファクトと
各操作の正確な形については、
[バックアップのリファレンス](/ja-JP/マニュアル/リファレンス/バックアップ/)を参照してください。

ここで説明する内容はすべて **設定 → サーバー → バックアップと復元** にあります。

## 前提条件

- **フルクライアント**（デスクトップまたは Web アプリ）が必要です。ペアリングされたスマートフォンでは、これらはいずれも設計上実行できません。
- **インストール全体のスナップショット**の取得、一覧表示、ダウンロード、削除には、インストールの**オーナー**である必要があります。
- ワークスペース単位の操作では、エクスポートおよび定期バックアップの一覧表示とダウンロードにはそのワークスペースの**管理者**、削除およびバックアップの削除には**オーナー**が必要です。
- ワークスペースを**復元**する場合（アップロードしたファイル、定期バックアップ、スナップショットのいずれから行う場合も）は、[サーバーオーナー](/ja-JP/マニュアル/コンセプト/認可/#サーバーオーナー)であり、そのワークスペースのオーナーでもある必要があります。復元によってサーバーはデータベースファイルを自身のものとして採用するため、これはサーバーオーナーの判断です。それ以外の人には、復元操作の代わりに「バックアップを復元できるのはサーバーオーナーだけです。ダウンロードは引き続き可能です。」と表示されます。
- ダウンロードとアップロードには、直接接続またはブローカー経由のリレー接続のいずれかでペアリングされたフルクライアントが必要です。どちらの経路も、認証済みでエンドツーエンドに暗号化された同じリソーストンネルを通じてファイルのバイトを運びます。リレーはそれを読むことはできません。

:::caution[インストール全体のスナップショットは手動です]
**今すぐバックアップ**は、要求されたときにのみインストール全体のスナップショットを作成します。
組み込みの **Workspace backup** パイプラインを使えば、代わりにワークスペースのデータベース
バックアップを週に 1 回取得し、そのワークスペースの 30 日より古いバックアップを削除できます。
`global.db`、他のワークスペース、データベースの隣にあるファイルはコピーしません。マシン外の
コピーは別途保管してください。
::::

::::caution[バックアップは保存時に暗号化されません]
暗号化された転送は、あなたのクライアントと `cc_server` の間で終わります。スナップショット
ディレクトリ、ワークスペースのエクスポート、ダウンロードしたファイル、サーバーのデータベースは、
Control Center によって保存時に暗号化されることはありません。サーバーホスト、ダウンロード、
マシン外のコピーは、独自のストレージ暗号化とアクセス制御で保護してください。
::::

## バックアップに含まれる範囲

どちらのアーティファクトも**データベースのみ**です。

- **インストール全体のスナップショット**はタイムスタンプ付きのディレクトリで、`manifest.json`、`global.db`、およびワークスペースごとの `<workspaceId>/workspace.db` から成ります。
- **ワークスペースのエクスポート**は、その単一の `workspace.db` ファイルです。

ワークスペースのデータベースはワークスペース全体です。会話、実行ログ、リポジトリのリンク、環境の定義、メンバーを含みます。シークレットは含みません。パイプライン Webhook トークン、チケット同期 Webhook シークレット、プロバイダーのサインイン、デバイスキー、ユーザーのシークレットは、グローバルデータベースとサーバーのシークレットストアにあります。それでもワークスペースが語ったこと、行ったことのすべてを含むため、ダウンロードしたワークスペースのバックアップやエクスポートは、ワークスペース自体と同じくらい非公開として扱ってください。コードインデックスは、データベースの隣にある別ファイル `code_index.db` です。どのバックアップにも含まれず、サーバーが再構築します。

どちらもデータディレクトリの残りの部分は含みません。`secrets.json`（ペアリングキー、
プロバイダーの認証情報、Webhook シークレット、SSO）、ワークスペースの `blobs/`（メッセージに貼り付けられた
画像）、`skills/`、`agents/`、`chat_credentials/`、録画したミーティングの音声、リグ画像
などです。その一部は捨ててよいものですが、そうでないものもあります。
[完全な表はリファレンスにあり](/ja-JP/マニュアル/リファレンス/バックアップ/#バックアップに含まれないもの)、
これらをカバーするのが[マシン外のセクション](#バックアップをマシン外にコピーする)の目的です。

## インストール全体のスナップショットを取得する

1. **設定 → サーバー → バックアップと復元**を開きます。
2. **インストール全体のスナップショット**で、**今すぐバックアップ**を押します。
3. トーストに、サーバーホスト上で書き込まれたディレクトリ名が表示されます。新しいスナップショットは一覧の先頭に表示されます。

サーバーはその間も動き続けます。各ファイルは `VACUUM INTO` で書き込まれ、これは
稼働中のデータベースに対しても整合性が保たれるため、メンテナンスウィンドウは不要で、
エージェントを停止する必要もありません。

一覧の各行には、タイムスタンプ、ディスク上のサイズ、取得されたワークスペースの数、およびスナップショットが**完了**か**未検証**かが表示されます。取得したコピーはすべて書き込まれた後に検証され、マニフェストにはそのサイズとチェックサムが記録されます。未検証とは、サーバーがそのスナップショットを保証できないことを意味します。マニフェストが存在しないか読めない、または記載されたファイルが存在しない、もしくはサイズが変わっている場合です。クラッシュやディスク容量不足で中断されたバックアップや、スナップショットがチェックサムを記録する前に取られたバックアップが該当します。これらも意図的に一覧に残されます。見えないスナップショットは、持っていると思い込んでしまうスナップショットだからです。未検証のスナップショットではインストール全体を復元できませんが、そこに含まれるワークスペースファイルは 1 つずつ復元できます。

行に **_n_ ワークスペースを取得せず**と表示されることもあります。これは、登録されている
ものの一度も書き込まれていないワークスペース（ファイルがまだ存在しない）、
データベースが破損しているワークスペース（破損したコピーは取得されません）、またはコピーに失敗したワークスペースです。サーバーログを確認してください。

**最後の正常なコピー**と表示されたスナップショットまたは定期バックアップには、データベースがその後破損したワークスペースの最新の正常なコピーが含まれています。そのワークスペースが復元されるまで、定期的なクリーンアップはこれを残し、削除するには確認が必要です。

## ワークスペースのバックアップと保持をスケジュールする

そのワークスペースの **設定 → ワークスペース → パイプラインテンプレート**を開き、
**Workspace backup** を見つけます。有効になっているスケジュールは毎週日曜日の
03:00 UTC に実行され、**Back up workspace** の後に **Delete backups older than**
（既定では 30 日）が続きます。2 つ目のノードはバックアップが成功した後にのみ
実行されます。保持日数はノードで変更でき、スケジュールを無効にすることもできます。
予定時刻にサーバーがオフラインだった場合、スケジュールは復帰時に 1 回だけ追いつき、
逃した週をすべて再生することはありません。

ワークスペースのバックアップはサーバー上の
`backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` にあります。
保持ノードが削除するのはこのワークスペースの古いバックアップだけで、インストール全体の
スナップショットや他のワークスペースのバックアップを削除することはありません。これらの
ファイルにはデータベースしか含まれません。マシン外で保持するには、これらをダウンロードするか、
別途コピーしてください。

## 定期バックアップを見つけて復元する

**定期バックアップ**は**インストール全体のスナップショット**と**ワークスペースデータ**の間にあり、
ワークスペースごとに 1 行で、最後のバックアップの実行日時、保持している数、使用容量を示します。
パイプラインがまだ何も作成していないワークスペースには**バックアップはまだありません**と
表示されます。自分が管理者ではないワークスペースは、バックアップを一覧表示する代わりに、
その旨を行に表示します。

行を展開すると、各バックアップが新しい順に表示されます。

- **復元**は、ワークスペースの現在のデータベースをこのバックアップで置き換えます。置き換えられたデータベースは、`-pre-restore` で終わる名前でこの一覧に残るため、元に戻せます。サーバーオーナーが必要で、さらにそのワークスペースのオーナーでもある必要があります。
- **ダウンロード**は、使用しているマシンにファイルを保存します。バックアップはサーバーに残ります。
- **パスをコピー**は、サーバー上の場所をコピーします。
- **削除**は、ワークスペース名を入力すると、このバックアップを完全に削除します。**オーナー**が必要です。

### 削除されたワークスペースのバックアップ

ワークスペースを削除しても、その定期バックアップはサーバーに残ります。スケジュールも一緒に
停止するため保持も停止し、誰かが削除するまで残り続けます。インストールの**オーナー**には
同じ一覧に**ワークスペース削除済み**と表示され、そこでダウンロードまたは削除できます。
他のユーザーにはこれらの行は表示されません。

復元先のワークスペースがないため、これらに**復元**はありません。元に戻すには、ダウンロードして
ワークスペースを作成し（サーバーオーナーだけが作成できます）、
[ワークスペースを別のインストールへ移動する](#ワークスペースを別のインストールへ移動する)の
説明に従ってファイルをアップロードします。

## インストール全体のスナップショットを削除する

**インストール全体のスナップショット**でスナップショット（未検証のものも含む）を展開し、
危険セクションの**スナップショットを削除**を使います。名前を確認します。スナップショットの
ディレクトリ全体がサーバーから完全に削除されます。コピーが必要な場合は先に
ダウンロードしてください。ワークスペースのバックアップパイプラインがこれらの
スナップショットを削除することはありません。

## 手元のマシンにコピーを回収する

このページに表示されるパスは、`cc_server` を実行しているマシン上のものです。それが自分が
操作しているマシンでない場合は、**ダウンロード**ボタンを使います。

- **ワークスペースデータ**の各**ワークスペース**の横にある **ダウンロード**。1 つの `.db` ファイル用です。
- **インストール全体のスナップショット**の各**スナップショット**の横にある **ダウンロード**。スナップショット全体を `.zip` として取得します。
- **定期バックアップ**の各バックアップの横にある **ダウンロード**。そのバックアップの `.db` ファイルを取得します。

デスクトップではファイルの保存先を選択し、トーストにその場所が表示されます。Web では
ブラウザーのダウンロード先に保存されます。どちらの場合も、3 つすべての進捗がバイト単位で
報告されます。これらのペイロードはギガバイト規模になりうるからです。

ワークスペースとスナップショットのダウンロードは、ボタンを押した時点で新しいコピーを作成して
ストリーミングし、その後サーバー側のコピーを削除します。ダウンロードは「エクスポートボタンが
以前に作成したファイルを取りに行く」ことではありません。定期バックアップは例外で、保存されている
ファイルをそのまま受け取り、ファイルはサーバーに残ります。

スナップショットのアーカイブを展開すると、スナップショットのレイアウトがそのまま
再現されます。だからこそ、その復元はコピーを戻すだけの操作になります。

## ワークスペースを別のインストールへ移動する

1 つのワークスペースは 1 つのデータベースファイルなので、その受け渡しはファイル操作です。

1. **ソース**サーバーで **設定 → サーバー → バックアップと復元 → ワークスペースデータ**を開き、ワークスペースを展開して**ダウンロード**を押します。
2. **移動先**サーバーで、受け取るワークスペースを作成（または選択）します。
3. そのワークスペースを展開し、**このデバイスから復元**の下にある**ファイルを選んでアップロード**を押します。ダウンロードした `.db` を選択します。

手順 3 は復元なので、移動先のサーバーオーナーである必要があり、さらにそのワークスペースのオーナーでもある必要があります。

両方のサーバーが自分が操作している同じマシンであれば、送信元で**サーバーに保存**を押し、移動先の**ワークスペースのデータベースファイル**にファイルのパスを入れて**インポート**を押すと、往復なしに同じことができます。そのパスはサーバーホスト上で解決されます。

:::caution[インポートはすべてを置き換えます]
インポートすると、対象ワークスペースが現在保持しているすべてが置き換えられます。置き換えられたデータベースは **定期バックアップ** の下に、`-pre-restore` で終わる名前で保持されます。元に戻すには、そのバックアップを復元してください。
:::

別のワークスペースのファイル、または**別のインストール**のファイルは受け入れられます。ワークスペースを複製したり、新しい ID で復元したり、別の人に渡したりするのはこの方法です。別のインストールのユーザー ID はこちらでは解決されません。ワークスペース自身のデータは無傷ですが、採用後にメンバーシップを再確認してください。

復元されたファイルは、それだけではこのサーバーで何の権限も与えられません。通常のメンバーシップを超えてファイルが持っていた権限は取り除かれ、ページ上部の**復元コピーから保留中**に一覧表示されます。承認なしに、または承認後にエージェントが行動できるようにするアクションルール、サンドボックスが実行できるパス、読み取りを超えるリポジトリアクセス、メンバーを超えるロール、それらのロールへの未処理の招待が含まれます。**承認**でそれを再び付与し、**却下**で破棄します。ホストで環境定義を実行する承認はクリアされるため、それらの定義は再度承認してください。復元を行った人がオーナーロールを保持するか、取得します。

チャットボットのトークン、プロバイダーのサインイン、Webhook シークレットはデータベースの外にあるため、受け取ったインストールが自身のものを接続します。Webhook トリガーとチケット同期の Webhook は、シークレットなしで届き、別のサーバーでは改めて保存するまで何も受信しません。その保存によって、各トリガーには新しい URL が割り当てられます。

## スナップショットから 1 つのワークスペースを復元する

サーバーオーナーであり、かつそのワークスペースのオーナーである必要があります。

1. **インストール全体のスナップショット**で、目的のスナップショットを展開します。
2. そのワークスペースの行を見つけて**復元**を押します。
3. 確認します。スナップショット取得後にそのワークスペースが行ったことはすべて失われます。

これはインポートと同じ操作を、スナップショット内のそのワークスペースのファイルの
コピーに対して行うものです。意図的にそうしてあり、同じファイルを別の扱いにする
第 2 の仕組みが存在しないようにしています。そのコピーは、まずスナップショットが記録したチェックサムと照合されます。

行に**このサーバーにはもう存在しません**と表示され、**復元**が無効になっていることが
あります。スナップショットが、このインストールにもはや存在しないワークスペースを
保持しているのです。手作業で戻します。ワークスペースを作成（サーバーオーナーのみ）し、次に**ワークスペースデータ**で、`<snapshot path>/<old workspace id>/workspace.db` をそのワークスペースの**ワークスペースのデータベースファイル**の欄に入力し、**インポート**を押します。展開したスナップショットには、自身の**サーバー上のパス**がコピー用
フィールドに表示され、行のタイトルが古いワークスペース ID なので、そのパスの前半と
後半の両方が目の前にそろうことになります。

## 破損したワークスペースを復元する

データベースが整合性チェックに失敗したワークスペースは、読み取り専用になります。内容はすべて読み取れますが、変更はすべて拒否されます。メンバーにはワークスペースの上部に**このワークスペースは読み取り専用です**と表示され、サーバーオーナーにはこのページの**対応が必要**の下に表示されます。正常なコピーを含む最新のバックアップは**最後の正常なコピー**として保持されます。上述のとおり、そのコピーからワークスペースを復元すると、再び書き込み可能になります。破損したデータベースは `-pre-restore` バックアップとして保持されます。

## インストール全体を復元する

これ用のボタンはありませんし、あるべきでもありません。稼働中のサーバーが開いている
データベースを置き換える操作だからです。

1. **`cc_server` を停止します。** 組み込みサーバー付きのデスクトップアプリを実行している場合は、アプリを終了します。
2. スナップショットの内容をデータディレクトリにコピーします。スナップショットのレイアウトは稼働中のものと同じなので、単純なコピーです。

   ```bash
   # macOS default; see the CLI reference for other platforms
   DATA_DIR="$HOME/Library/Application Support/control-center"
   SNAPSHOT="$DATA_DIR/backups/2026-07-28T09-12-33-000Z"

   cp "$SNAPSHOT/global.db" "$DATA_DIR/global.db"
   for d in "$SNAPSHOT"/*/; do
     id=$(basename "$d")
     mkdir -p "$DATA_DIR/$id"
     cp "$d/workspace.db" "$DATA_DIR/$id/workspace.db"
   done
   ```

3. 置き換えたデータベースの隣にある `-wal` および `-shm` ファイルを削除します。これらは古いファイルのもので、復元したデータベースの隣に古いものが残っていると破損のリスクがあります。
4. サーバーを再起動します。

スナップショットには `secrets.json` が含まれないため、**新しい**ホストに復元した
インストールはデータは保ちますが認証情報は保ちません。ペアリング済みデバイス、
プロバイダートークン、SSO 設定を再設定するか、そのファイルを保管しておいた場所から
復元する必要があります。`secrets.json` が失われていない同じホストに復元する場合は、
すべてが保たれます。

## バックアップをマシン外にコピーする

コピー元のデータベースと同じディスク上にあるスナップショットが守ってくれるのは、
誤ったインポートからであって、ディスクからではありません。Control Center はどこかへ
コピーを送ることはしないので、この部分は自分の責任です。

### スナップショットを同期する

スナップショットは一度書き込まれると不変で、タイムスタンプで命名されるため、どの同期
ツールでもうまく扱えます。進行中のダウンロードとアップロードの作業場である `transfer/` は
除外してください。

```bash
DATA_DIR="$HOME/Library/Application Support/control-center"

# To another host over ssh
rsync -a --delete --exclude 'transfer/' \
  "$DATA_DIR/backups/" backup-host:/srv/control-center-backups/

# To object storage
aws s3 sync --exclude 'transfer/*' \
  "$DATA_DIR/backups/" s3://my-bucket/control-center/backups/

# Or with deduplication, encryption and its own retention
restic backup --exclude 'transfer' "$DATA_DIR/backups"
```

`--delete` はローカルでの削除をリモートに反映します。リモートにホストより長く
スナップショットを保持させたい場合は外してください。

:::danger[稼働中のデータベースを直接同期しないでください]
サーバーの稼働中は、rsync、`aws s3 sync`、またはファイルレベルのバックアップエージェントを
`global.db` や `<workspaceId>/workspace.db` に向けないでください。稼働中の SQLite
データベースには `-wal` のサイドカーがあり、ファイル単位のコピーは両者を異なる瞬間に
取得します。その結果できるファイルは、開けても直近の書き込みが黙って欠けているか、
まったく開けないかのどちらかです。読み取りトランザクションの下で書き込まれた
**スナップショット**をコピーするか、後述のように `VACUUM INTO` で取得してください。
:::

### スナップショットが含まないものを含める

データだけでなくインストールそのものを再構築できるようにするには、これらもコピーします。
これらは通常のファイルで、サーバーの稼働中でも安全にコピーできます。

```bash
rsync -a \
  "$DATA_DIR/secrets.json" \
  backup-host:/srv/control-center-backups/config/

rsync -a --relative \
  "$DATA_DIR"/./*/chat_credentials \
  "$DATA_DIR"/./*/blobs \
  "$DATA_DIR"/./*/skills \
  "$DATA_DIR"/./*/agents \
  backup-host:/srv/control-center-backups/workspace-files/
```

`secrets.json` は `0600` で、インストール上のすべてのペアリングキー、プロバイダーの
認証情報、SSO 設定を保持します。その保存先は、少なくともサーバーホストと同じ程度に
保護されている必要があります。保存時に暗号化し、誰でも読めるバケットは避けてください。

`spaces/`（コピーオンライトのワークツリー。リポジトリから再プロビジョニングされます）、
`pr_clones/`（キャッシュ）、`models/`（再ダウンロードされる）、`media_cache/` と
`rigs/`（マシンの状態で、サイズも大きい）は対象外にしてかまいません。`meetings/` に
ある録画したミーティング音声は、ミーティングを保存しているなら含める価値があります。

### アプリの外でインストール全体のスナップショットをスケジュールする

組み込みのパイプラインがバックアップするのは 1 つのワークスペースだけです。無人で
**インストール全体**のスナップショットを取得するための CLI サブコマンドはなく、
スナップショットの RPC にはインストールのオーナーであるペアリング済みフルクライアントが
必要です。ホスト側のタイマーで、稼働中のデータベースに対して `VACUUM INTO` を使えます。

```bash
#!/usr/bin/env bash
set -euo pipefail

DATA_DIR="${CC_SERVER_DATA_DIR:-$HOME/.local/share/control-center}"
DEST="/srv/control-center-snapshots/$(date -u +%Y-%m-%dT%H-%M-%SZ)"
mkdir -p "$DEST"

sqlite3 "$DATA_DIR/global.db" "VACUUM INTO '$DEST/global.db'"

for db in "$DATA_DIR"/*/workspace.db; do
  id=$(basename "$(dirname "$db")")
  mkdir -p "$DEST/$id"
  sqlite3 "$db" "VACUUM INTO '$DEST/$id/workspace.db'"
done
```

データディレクトリを所有するのと同じユーザーで、cron または systemd タイマーから実行し、
その後 `DEST` をホスト外へ同期します。`VACUUM INTO` には SQLite 3.27 以降が必要です。

出力先は `<dataDir>/backups/` の**外**にしてください。そこに手作業で作ったディレクトリには
`manifest.json` がないため、アプリはそれを未検証のスナップショットとして一覧に載せ、
その一覧はサーバー自身が生成したものの正直な記録ではなくなってしまいます。

### 古いインストール全体のスナップショットを整理する

インストール全体のスナップショットはアプリで個別に削除できます。ホスト側の保持ポリシーを
設ける場合は、ワークスペースのバックアップディレクトリをインストール全体の
スナップショットとは分けておいてください。

```bash
find "$DATA_DIR/backups" -mindepth 1 -maxdepth 1 -type d \
  ! -name exports ! -name transfer ! -name workspace-backups \
  -mtime +30 -exec rm -rf {} +
```

`-exec` を付ける前に、`-print` での実行結果を確認してください。1 つだけでなく複数を
保持してください。備えたい障害は多くの場合「最後のバックアップにも同じ問題がある」
だからです。

## バックアップが良好か確認する

誰も復元したことのないバックアップは、仮説にすぎません。

手軽な確認 — ファイルが開き、ページが無傷であること。

```bash
sqlite3 "$SNAPSHOT/global.db" 'PRAGMA integrity_check;'   # expects: ok
```

本格的な確認 — 実際に採用してみます。非本番のインストールに使い捨てのワークスペースを
作成し、そこにワークスペースファイルをインポートして、期待するスペース、チケット、
メッセージがあるかを確認します。これは FTS の再構築を含め、実際の復元と同じ経路を
通り、バックアップが単に読めるだけでなく復元可能であることを教えてくれる唯一の確認です。

バックアップを設定したときに一度、保管場所を変更するたびに再度行ってください。

## トラブルシューティング

| 症状                                                                  | 原因と対処                                                                                                            |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 接続が変わった後にダウンロードまたはアップロードが失敗する | アクティブなペアリング済み接続で再試行してください。直接接続もリレーも暗号化されたファイル転送をサポートしており、どちらも平文 HTTP のフォールバックを公開しません |
| 「サーバーに拒否されました。ワークスペースのダウンロードにはワークスペースの管理者ロールが必要です。ワークスペースの復元には、そのワークスペースのオーナーでもあるサーバーオーナーが必要です。サーバー全体のスナップショットにはサーバーオーナーが必要です。」 | ロールの問題です。インストール全体のスナップショットの取得、一覧表示、ダウンロードにはサーバーオーナーが必要です。ワークスペースのダウンロードには管理者、復元にはサーバーオーナー（そのワークスペースのオーナーでもある必要があります）が必要です |
| 「この接続ではまだファイル転送が設定されていません。バックアップのダウンロードやアップロードには、サーバーに再接続してください。」 | この接続にはサーバーへのファイル転送の経路がないため、**ダウンロード**とアップロードは無効になっています。サーバーに再接続してから、もう一度お試しください |
| 「バックアップを復元できるのはサーバーオーナーだけです。ダウンロードは引き続き可能です。」 | ワークスペースのデータベースを、サーバーのホスト上で置き換えるため、復元できるのはサーバーオーナーだけです。バックアップをダウンロードし、サーバーオーナーに依頼してください |
| 「このサーバーにはバックアップの仕組みがありません。」                                      | ホストにバックアップポートが接続されていません — デモサーバーです。操作は拒否されるのではなく存在しません                          |
| 「ファイルがサーバーの受け入れ可能なサイズを超えています。」                             | アップロードは 8 GiB が上限です。ファイルをサーバーホストに置き、**ワークスペースのデータベースファイル**にそのパスを入力してください                 |
| 復元が拒否され、何も置き換えられません | ファイルがチェックに失敗しました。メッセージにその理由が示されます。ワークスペースのデータベースではない、破損している、スナップショットが記録したチェックサムと一致しない、サーバーの新しいバージョンが書き込んだ、またはその Webhook や招待がこのサーバー上の別のワークスペースにすでに属している、のいずれかです。別のコピーを使うか、先にサーバーを更新してください |
| スナップショットが**未検証**として一覧に表示される | 完了しなかったか、スナップショットがチェックサムを記録する前に取得されたものです。新しいものを取得してください。それまでの間は、そこから個々のワークスペースファイルを復元できます |
| スナップショットにワークスペースを取得していないと表示される                             | それらのワークスペースは一度も書き込まれていないか、破損しているか、コピーに失敗しています。サーバーログを確認してください                                  |
| ワークスペースに**このワークスペースは読み取り専用です**と表示される | そのデータベースが整合性チェックに失敗しました。サーバーオーナーがバックアップから復元するまで、その中の何も変更できません |
| ワークスペースを別のサーバーに移した後、Webhook が届かなくなる | Webhook のシークレットはデータベースと一緒には移動しません。新しいサーバーで各 Webhook トリガーとチケット同期の接続を保存し直し、送信元に新しい URL を伝えてください |
| 復元したインストールにコードホストまたは SSO の認証情報がない                       | `secrets.json` はスナップショットに含まれません。保管しておいた場所から復元するか、プロバイダーを再接続してください                     |
| 復元したワークスペースに貼り付けた画像がない                            | Blob はデータベースの中ではなく隣にあります。`<workspaceId>/blobs/` も併せてコピーしてください                                     |
