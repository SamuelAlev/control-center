## 作るもの

このチュートリアルを終えると、次のものが揃っています:

- Control Center サーバーとアイデンティティプロバイダー（例として Okta を使います）の間の SAML 接続
- 初回ログイン時に自動でプロビジョニングされる 1 人のユーザー
- あなたが意図的に選んだワークスペースメンバーシップポリシー

自分で管理するサーバー（**サーバー所有者** — インストールのオペレーター）と、設定できる IdP アプリケーションが必要です。所要時間の目安は 20 分です。

## 1. シングルサインオン設定を開く

Control Center にサインインし、**設定 → サーバー → シングルサインオン**を開きます。画面は **SAML** と **OpenID Connect** を切り替えられ、さらに **ユーザープロビジョニング（SCIM）**カードがあります。SAML のままにしておきます。

この画面の内容はすべてサーバー全体に及びます。1 つの IdP がすべてのワークスペースのユーザーを認証するため、編集できるのはサーバー所有者だけです。

## 2. IdP メタデータを貼り付ける

Okta でアプリの **Sign On** タブを開き、メタデータ XML をコピーします（またはダウンロードして、そのファイルの内容を貼り付けます）。Control Center に戻り、**IdPメタデータXML** に貼り付けて **接続をテスト**を押します。

トーストには IdP のサインオンエンドポイントが表示されます — メタデータが解析され、証明書が読み取られ、それを基にサーバーがログインリクエストを組み立てられることの証拠です（このテストは、ブラウザーの往復を除くすべてを実行します）。失敗した場合、その XML は完全な `EntityDescriptor` ではありませんでした（Okta の SAML タブではこれを「Metadata URL」と呼びます。その URL を開いて、配信される内容をコピーしてください）。**OpenID Connect** では、同じボタンが代わりに発行元のディスカバリドキュメントを確認します。期限切れが近い証明書の検出や、IdP が Control Center を認識しているかどうかの確認も行うには、[ステップ 6 のチェッカー](#6-このページから確認する)を使ってください。

## 3. IdP に Control Center を登録する

**SPメタデータをコピー**を押し、Okta 側を設定する担当者に渡します（または、相手が求める 2 つの値を伝えます）:

- **ACS URL**: `https://<your-server>/saml/acs`
- **エンティティ ID**: `https://<your-server>/saml`

これらの URL は、ユーザーのブラウザーが到達するオリジンから導出されます。サーバーがトンネルやリバースプロキシの背後で動作している場合は、オリジンが安定していることを確認してください（設定 → サーバー → 接続とステータス → このサーバーを共有 に公開 URL が表示されます）— または、**SPエンティティID** フィールドでエンティティ ID を明示的に固定します。

:::note[NAT の背後にある場合]
SAML ログインに公開 IP やドメインは **必要ありません**。IdP があなたのサーバーに接続することは決してなく、往復を運ぶのはユーザーのブラウザーです。そのため、localhost、LAN、VPN、Tailscale、トンネルのいずれでも機能します。押さえておくべき点が 2 つあります:

- ブラウザーが使うオリジンは、IdP に登録した ACS URL / エンティティ ID と **一致**していなければなりません（ユーザーが複数のオリジンでサーバーに到達する場合は、エンティティ ID を固定します）。
- **SCIM プロビジョニングは例外です** — IdP があなたのサーバーを直接呼び出すため、トンネルまたは公開 URL が必要です（[SCIM でユーザーをプロビジョニング](/ja-JP/マニュアル/ハウツーガイド/sso-scim)）。
  :::

## 4. ログインで何が付与されるかを選ぶ

初回ログインの動作を決めるポリシーが 2 つあります:

- **初回ログイン時にユーザーを全ワークスペースに追加** — SSO が信頼と同義である単一チームのデプロイではオンのままにします。複数のチームや顧客がサーバーを共有する場合はオフにします。その場合、新規参加者にはワークスペースへの明示的な招待が必要になり、これがより安全な既定です。
- **初回ログイン時に未知のユーザーをプロビジョニング** — 既定でオンです。アカウントがまだ存在しないユーザーを拒否するにはオフにします。

任意で、グループ名を運ぶ属性をマッピングし（Okta では一般に `groups` です）、マップでグループをロールに変換できます — 例えば `{"platform-leads": "admin"}` です。SSO がオーナーロールを付与することは決してありません。

## 5. 有効化してログインする

**サインインにSAMLを使用**をオンにし、**接続を保存**を押してから、プライベートブラウザーウィンドウで `https://<your-server>/saml/login` を開きます。Okta でサインインすると、Web クライアントに戻ります — ログイン済みで、アカウントが作成され、選んだポリシーに従ってメンバーシップが付与されています。

サーバーアドレスを入力した瞬間に、同じエントリーポイントが Web の接続画面に表示されます（**SAMLでサインイン**）。フォームはサーバーが提供する内容に適応します（OpenID Connect の場合は **OpenID Connectでサインイン** と表示されます）。このボタンは**新しいタブ**でサインインを開きます。往復が完了すると、待機していたタブが自動的にセッションを引き継ぎます。デスクトップのサーバーセットアップ画面も同じです。サーバー URL を入力すると **SAMLでサインイン** ボタンが表示され、それがブラウザーを開き、往復が完了するとアプリがログインします。

## 6. このページから確認する

SSO を展開する前に、またはログインが失敗したときに、ここで各部を確認してください。チェッカーは完全にあなたのブラウザー内で実行されます。このタブで貼り付けたメタデータを読み取り、サーバーと同じルールを適用します。サーバーアドレスを指定すると、そのサーバーに SAML サインインが有効かどうかも問い合わせます。

アプリの **接続をテスト**では見えないものを検出します。期限切れが近い署名証明書、署名付きリクエストを要求する IdP、そしてテストサインインによる、IdP が Control Center を認識しているかどうかです。
