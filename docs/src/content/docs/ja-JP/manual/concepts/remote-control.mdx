Control Center はデスクトップアプリですが、それが追跡する作業は、デスクを離れたとたんに止まるものではありません。**リモートコントロール**は、あなたのスマートフォンと `cc_server` をペアリングします。使用するのは、remote.usectrl.dev にあるコンパニオンアプリ **[Remote](https://remote.usectrl.dev/)** です。これにより、外出先からフリートを追いかけられます。エンドツーエンド暗号化接続を通じて、メッセージやチケットを読み、エージェントに返信し、ニュースフィードをトリアージできます。スマートフォンと `cc_server` は信頼された平文エンドポイントであり、リレーが運ぶのは暗号化されたアプリケーションレコードだけです。

読み取り中心の、デッキのコンパニオンだと考えてください。フルのデスクトップクライアントを置き換えるものではありません。

:::note[2 つの異なるリモートクライアント]
スマートフォンのコンパニオンと完全な **Web ビルド**（およびリモートサーバーを指定したデスクトップ）は、`cc_server` に直接接続することも、ブローカー経由の WebSocket リレーを使うこともできます。どちらの経路も同じ暗号化セッションを必要とし、スマートフォンが公開する操作はフルクライアントより少なくなっています。クライアントの違いは[デプロイメントとクライアント](/ja-JP/マニュアル/コンセプト/デプロイメント/)を参照してください。
:::

## トランスポート

スマートフォンは WebSocket 経由で `cc_server` に到達します。直接接続（ループバック、LAN、tailnet、または `wss://`）か、シグナリングブローカー上の招待制のルームです。どちらの経路も認証済みのエンドツーエンド暗号化セッションを必要とし、ブローカーが転送するのはその暗号化レコードだけです。ピアツーピアのデータチャネルはありません。

## スマートフォンでできること

ペアリングされたスマートフォンが到達できるのは、サーバーのサーフェスのうち、意図的に絞り込まれた小さな一部分です。

- **読み取り**: チケット、エージェント、スペースとそのメッセージ、およびニュースフィード
- **返信**: スペースへのメッセージ送信、チケットの更新または割り当て、記事を既読または保存済みにする
- **プレイブックの実行**: 保存済みのプランテンプレートをそのパラメーターでインスタンス化します。これはプランを_提案_するだけで、フルクライアントの Plan Studio でオペレーターが承認するまで、何も実行も消費もされません
- **ワークスペースの切り替え**: スマートフォン自身のピッカーから行います

ほぼこれで全部です。スマートフォンは、フルクライアントよりも**低い権限のプリンシパル**です。プロセスの起動、LLM 予算の消費、GitHub へのプッシュ、ワークスペースの作成はできません。これが単なる意図ではなく実際に強制される仕組みは[アクセスモデル](#アクセスモデル)を参照してください。

## リンクがどのように構築されるか

スマートフォンがサーバーに直接到達できない場合、接続は**ブローカー経由のリレー**を使います。サーバーは `wss://` ブローカー上の 1 つの招待制のルームにそのオーナーとして参加し、ペアリングされたクライアントが期限付きの入室トークンを使って参加します。3 つの要素が組み合わさります。

| 要素                     | 役割                                                                                                                                                                                                                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Remote（スマートフォンアプリ）** | コンパニオンの Web アプリ。デフォルトでは `remote.usectrl.dev` でホストされ、セルフホストも可能です。ブラウザーで読み込まれ、ペアリングの記録を IndexedDB に保持します。                                                                                                                     |
| **リレーブローカー**     | ステートレスな `wss://` リレー（`cc_signaling_server`）で、N 者間のルームをホストします。ペアリングの秘密やアプリの平文を含まずに暗号化レコードを転送しますが、ルーティング識別子、IP、レコードサイズ、タイミングは見えます。 |
| **`cc_server`**          | ルームのオーナー。他のすべてのクライアントが使うのと同じディスパッチャーを通じて、スマートフォンからの呼び出しに応答します。                                                                                                                                                                 |

ペアリングオファーは、サーバーへのすべての経路（LAN、tailnet、公開 `wss://`、リレー）とその識別フィンガープリントを列挙した**接続記述子**を運びます。スマートフォンのリゾルバーは到達可能な最良の経路を選びます。サーバーは暗号化ハンドシェイクに署名し、クライアントはそのフィンガープリントをピン留めします。初回接続時には、フィンガープリントを QR コードや別の信頼できる情報源と照合してください。最初の署名済み識別情報だけでは、どのサーバーに到達したかを証明できません。変更されたピンは、黙って再び信頼されるのではなく拒否されます。直接経路が存在しない場合、リレーは暗号文を運びますが、接続を中断したり遅延させたりすることは依然としてできます。

## ペアリングペイロードとは

ペアリングはアプリから発行され、ディープリンクとして届けられます。手順については[デバイスをペアリング](/ja-JP/マニュアル/ハウツーガイド/デバイスのペアリング/)を参照してください。ここで重要なのはその構造です。

```
https://<pwa-host>/#<payload>
```

ペイロードは URL の**フラグメント**、つまり `#` の後ろの、ブラウザーが PWA ホストへの HTTP リクエストで送ることのない部分に乗ります。ペイロードには、スマートフォンがサーバーに到達し、自分が誰であるかを証明するために必要なものがすべて含まれます。接続記述子（すべての経路と識別フィンガープリント）、新たに発行されたデバイス id、32 バイトの事前共有キー、そして有効期限のスタンプです。スマートフォンはそれをデコードし、ペアリングの記録をローカルに保存し、URL からフラグメントを取り除きます。Web アプリのコードはフラグメントを読めるため、信頼できるアプリホストを使い、リンクは秘密として扱ってください。

ペイロードの形は 2 つあり、それらは**互換性がありません**。アプリ内のペアリングパネルから発行されるスマートフォン用 QR は、上記の v2 `PairingPayload` で、Remote PWA ホストを指しています。`cc_server pair --client-url` は、**Web** クライアント専用の v1 リンク（`{s, i, k}` — サーバー URL、デバイス id、キー）を発行します。これらはペアリングのデータ形式であり、トランスポートのフォールバックではありません。どちらのクライアントも現在の暗号化セッションプロトコルをサポートする必要があります。

両者は有効期間も異なり、これを取り違えるのはたやすいことです。

| 発行元                                 | 資格情報の有効期限                         |
| -------------------------------------- | ------------------------------------------ |
| アプリ内のペアリングパネル（`pairing.mint`） | 常に 30 日                                 |
| コマンドラインの `cc_server pair`      | 有効期限はエンコードされていません。サーバーのポリシーは引き続き適用されます |

サーバー全体の最大デバイス経過時間とアイドルタイムアウトのポリシーは、どちらの
資格情報もそれより早く拒否することがあります。どちらのペアリング形式もこれらの
ポリシーを迂回しません。

## アクセスモデル

ペアリングされたデバイスは**認証済みですが信頼されていません**。承認された（あるいは漏洩した）ペアリングがサーバーの完全な制御につながることを、いくつかの独立したゲートが防ぎます。

### 1. 境界はペアリングではなくメンバーシップ

有効なペアリングキーが証明するのは、_どのデバイス_であるかということだけです。何を読み、何を変更できるかは**ワークスペースロール**によって決まり、これは呼び出しのたびに再解決されます。また、リポジトリの内容を公開するものについては、リポジトリ単位の許可によっても決まります。完全に有効なキーを保持していても、指定されたワークスペースのメンバーではないユーザーに属するデバイスは、「Not a member of this workspace」で拒否されます。

ロールの下限は、操作が自ら宣言しない限り、その操作の種類から導かれます。読み取りには `guest`、変更には `member`、破壊的操作には `admin` が必要です。

### 2. スマートフォンは下位のセッション階層

ロールチェックに加えて、スマートフォンのセッションは、デスクトップや Web のセッションよりも低いケイパビリティを持ちます。フルクライアント専用と宣言された操作は、その背後にいるユーザーがどれほど特権を持っていても、ハンドラーが実行される前にスマートフォンに対して拒否されます。デバイスペアリングの発行、一覧表示、名前変更、失効。トンネル接続の読み取りと設定。サーバーのバックアップとワークスペースのエクスポート／インポート。プロセスの検出と停止。アダプターのプローブ。サーバー設定。SSO 管理。フリート制御。そして実行中のエージェントの引き継ぎまたは返却です。

### 3. デフォルト拒否のツール許可リスト

特に MCP ツールサーフェス（`tools/call`）では、スマートフォンが呼び出せるツールをデフォルト拒否の許可リストが管理します。リストにないものは、実行される前に拒否されます。このリストは読み取りと観察が中心で、それに加えて**ローカル専用**の書き込みがいくつかあります。メッセージ、チケットの更新、記事のフラグなどで、LLM 予算を消費せず、プロセスを起動せず、外部システムに触れません。

例えば、拒否されるものは次のとおりです。エージェントへの相談、AI レビューの開始、エージェントの停止、レビューの GitHub への公開、エージェントの採用または解雇、ワークスペースの作成。

### 4. 呼び出しごとのワークスペーススコープ

サーバーは「現在のワークスペース」を**保持しません**。設計上ステートレスです。ワークスペーススコープのすべての呼び出しは、引数で対象の `workspace_id` を指定しなければならず、それが欠けている場合、あるいはサーバーに登録されていないワークスペースを指定している場合、ディスパッチャーは — 何かがデータベースを開く前に — その呼び出しを即座に拒否します。したがってスマートフォンが別のクライアントのスコープを継承したり、そこへ流れ込んだりすることは決してできませんし、外部のワークスペースを指定しても意味がありません。ゲート 1 のメンバーシップチェックが依然として適用されるからです。これは、プロダクトの他の部分が強制しているのと同じ[ワークスペースの分離](/ja-JP/マニュアル/コンセプト/ワークスペース/)の不変条件です。

### 5. 直接接続とリレー経由の接続におけるエンドツーエンド暗号化

直接接続でもリレー経由でも、すべてのクライアントセッションは署名済みの Noise ハンドシェイクを必要とします。ペアリングキーはそのハンドシェイクを認証します。各フレームをペアリングキーで密封するのではなく、新しい一時キーがトラフィックキーを導出します。サーバーは自身の識別情報をその交換に署名し、クライアントは保存したフィンガープリントのピンを検証します。平文や旧クライアント向けのフォールバックはありません。リレーの入室トークンはクライアントをルームに入れるだけで、レコードを復号することはできません。

アプリが発行した資格情報は 30 日に期限付けられています。それを過ぎると接続ゲートがそれを拒否し、スマートフォンは再度ペアリングする必要があります。失効は即時です。サーバーはデバイステーブルを監視し、失効したデバイスの開いているセッションを、次回の接続を待つことなく数秒以内に切断します。

### 6. プリンシパル単位のレート制限

スライディングウィンドウ方式のリミッターが、リモートのツールトラフィックを毎分 120 呼び出しに制限し、変更系の動詞にはより厳しい毎分 30 のサブ上限を課します。予算は**セッションではなくプリンシパル**に属します。あなたの 3 台のデバイスは 1 つの許容量から消費するため、乗っ取られたクライアントがセッションを増やして余裕を稼ぐことはできず、1 人の騒がしいメンバーが他のメンバーを枯渇させることもできません。

### 7. アプリの内容を読めないブローカー

リレーブローカーは一時的で招待制のルームをホストし、アプリの平文やペアリングキーを含まずに暗号化レコードを転送します。それでも IP アドレス、ルームとピアの識別子、レコードサイズ、タイミング、接続の存続時間は見え、トラフィックを破棄したり遅延させたりできます。平文のエンドポイントは、ペアリングされたクライアントと選択された `cc_server` です。サーバーのオペレーターと、サーバーが内容を送信する先のサービスは、その内容を見ることができます。転送中の暗号化は、サーバーの保存データを暗号化するものではありません。

## ライブ更新

ペアリングが済むと、スマートフォンは通知フレームとして**ライブ更新**を受け取ります。新しいエージェントのメッセージ、自分に割り当てられたチケット、ステータスの変更などで、デスクトップ自身の通知を反映したものです。サーバーは、イベントをセッションに転送する前にワークスペースのメンバーシップを確認します。クライアントはその後、そうした承認済みのイベントを、いま表示しているワークスペースに絞り込みます。この表示フィルターはアクセス境界ではありません。

## どこにあるか

| サーフェス                                                                          | 表示内容                                                                                                    |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **設定 → 自分 → 自分のデバイス**（`/workspaces/:workspaceId/settings/you/devices`） | ライブステータス付きのペアリング済みクライアント、および**新しいクライアントをペアリング**（Web ブラウザー、デスクトップアプリ、スマートフォン）と失効 |

同じパネルは、スマートフォンだけでなく、2 つ目のブラウザーやデスクトップアプリ用のペアリングも発行します。手順は同じで、異なるのはディープリンクだけです。

::::note
リモートコントロールはサーバー側の機能であり、MCP 経由では**公開されません**。スマートフォンは、暗号化された直接接続またはリレー経由の接続を通じて、サーバー自身のディスパッチャーと通信します。外部サーバーの MCP クライアントではありません。
::::
