Control Center は 2 つの認可の問いに答えます。そしてこの 2 つは本質的に異なります。**「この人物はこの操作を呼び出してよいか？」** は、人、ロール、リポジトリに関する問いです。**「このエージェントはこの効果を引き起こしてよいか？」** は、アクション、引数、影響範囲に関する問いで、こちらは[ガードレール](/ja-JP/マニュアル/コンセプト/ガードレール/)で扱います。

このページでは前者の問いを扱い、あわせて両者が残す記録について説明します。

## 単一の判断ポイント

人側の認可判断はすべて、単一の関数を通じて解決されます。

```
can(principal, permission, resource) → allow | deny + why
```

**権限**は `<domain>:<tier>` の形式です — `tickets:write`、`members:administer`、`repos:read`。カタログは手書きではなく**導出**されます。つまり、操作サーフェスそのものから計算されます（操作名の接頭辞がドメインを、その操作がすでに要求しているロールの下限が階層を与えます）。おかげで約 550 件の操作すべてが、誰かが 1 つずつ入力しなくても権限を持ちます。

守る価値があるのは、この導出という性質です。つまり、新しい操作はデフォルトでゲートされるということです。手作業で注釈を付けるモデルの失敗パターンは、誰かが付け忘れることであり、その付け忘れる対象こそがゲートです。ラチェットテストが導出されたドメイン集合を固定するので、新しい接頭辞の下に操作を追加することは、偶然ではなく人間が下す命名の判断になります。

4 つの階層は、組み込みロールに正確に対応します。

| 階層 | ロールの下限 | 例 |
|---|---|---|
| `read` | ゲスト | `tickets:read` |
| `write` | メンバー | `tickets:write` |
| `administer` | 管理者 | `members:administer` |
| `own` | オーナー | `workspace:own` |

## ロール

5 つの組み込みロール — **オーナー、管理者、メンバー、閲覧者、ゲスト** — は、このカタログに対するプリセットです。オーナー権はワークスペースごとに 1 席だけで、**所有権を譲渡**によって明示的に引き継ぎます（辞めるオーナーは、そうしなければ削除できません。SCIM のプロビジョニング解除はワークスペースのオーナーを拒否するので、先に譲渡してください）。

**カスタムロールは減算方式です。** カスタムロールは、基底となるプリセット（`admin`、`member`、`viewer`、`guest` のいずれか — `owner` は不可）と、そこから**削除**する権限の集合を指定します — 「管理者だがメンバーを管理できない」のように。基底より多くを付与することは決してできません。だからこそ、既存のインストールへ安全に導入できるのです。既存のチェックはすべて、そのまま妥当な上限であり続けます。メンバーはこれを `custom:<id>` として保持し、この値を理解できないほど古いクライアントは、推測せずにゲストへフォールバックします。

ロールの下には**リポジトリ単位の権限付与**（`none` / `read` / `review` / `write`、[コードの変更には書き込み権限が必要](#コードの変更には書き込み権限が必要)を参照）があります。ワークスペースのメンバーシップが、暗黙にコードホストより強い権限を与えることはありません。コードを露出させるすべてのサーフェスがこれをチェックします。スペースのワークツリー上で開いたターミナルやエディターセッションのように、間接的にコードへ到達するものも含まれます。

## コードはフォージに従う

権限付与だけでは、リポジトリのコードは開けません。ファイル、差分、検索結果を見る、またはそこでターミナルを開くには、メンバーは Control Center の権限付与**と**、自分自身のフォージのサインインでそのリポジトリを読めることが必要です。ワークスペース管理者も例外ではありません。サーバーオーナーは例外です。チェックアウトが彼らのマシン上にあるためです。フォージのリモートがないリポジトリは、権限付与だけで足ります。

- 管理者が、そのフォージアカウントでは読めない人にリポジトリを付与した場合、権限付与は保存され、管理者には警告が表示されます。
- 確認のためにフォージに到達できない場合、答えは「いいえ」であり、推測はしません。その人には、フォージの名前を入れた「GitHub へのアクセスを確認できませんでした。もう一度お試しください。」が表示され、後で再度試します。
- プルリクエストとそこから作られるものはすべて、同じルールに従います。

### コードの変更には書き込み権限が必要

リポジトリの権限付与は 3 段階あり、それぞれが前の段階を含みます。

- **read**: リポジトリのファイル、差分、検索結果を見られます。ただし、ご自身のフォージのサインインでもそのリポジトリを読めることが条件です。
- **review**: read に加え、そのプルリクエストの承認、変更の要求、その他のレビュー操作ができます。
- **write**: review に加え、コードを変更し、リポジトリに書き込むエージェントの実行を操作できます。コードの変更には、エディターでのファイルの保存や取り消し、ワークツリーのプルリクエストのヘッドへの同期、コミットとプッシュ、ブランチの公開、パートの切り出し、チェックアウト、公開などのスタック操作が含まれます。

人のために行われるすべてのプッシュは、本人がプッシュしたものでも、本人が依頼したエージェントの実行によるものでも、プッシュの時点でそのリポジトリに対する本人の書き込み権限付与を確認します。これは GitHub、GitLab、Bitbucket のいずれでも同じです。スタックを公開する場合は、いずれかのリポジトリをプッシュする前に、スタック内のすべてのリポジトリを確認します。

拒否の理由には、不足している権限付与が示されます。読み取りアクセスがない場合、アプリには「このリポジトリへの読み取りアクセス権がありません。ワークスペースの管理者が付与できます。」と表示されます。読み取りはできるが書き込みができない場合は、「このリポジトリは閲覧できますが、変更はできません。ワークスペースの管理者が書き込みアクセス権を付与できます。」と表示されます。

### スペースはリポジトリに従う

エージェントがコードについて書いたものは、そのコードに従います。スペースの内容（そのメッセージ、トランスクリプトとツールの出力、検索結果、実行ログ、TODO、アクティビティと通知）は、それが扱うリポジトリのコードを伴うため、スペースは、そのスペースが使うすべてのリポジトリに対して読み取り権限を持ち、かつ本人のフォージのサインインで読めるメンバーにのみ開かれます。それらは、そのスペースに選択されたリポジトリ、またはスペースに選択が記録されていない場合はワークスペースのすべてのリポジトリです。リポジトリを 1 つも指定せずに作成されたスペースは、すべてのメンバーに開かれます。

開けないスペースは、検索、実行ログ、TODO、アクティビティ、通知を含め、その人にはどこにも表示されません。ワークスペース管理者はすべての権限付与を保持しますが、フォージ側の条件は免除されません。免除されるのはサーバーオーナーだけです。

誰もが読めるべき会話には、リポジトリを指定せずにスペースを作成するか、全員が読めるリポジトリだけを指定してスペースを作成してください。

## サーバーオーナー

サーバーをセットアップした人が、その**オーナー**です。サーバーは初回起動時に 1 度だけその人を記録し、ネットワーク経由で送られたものでそれが変わることはありません。ワークスペースの管理者やワークスペースのオーナーは、サーバーオーナーではありません。誰にでもワークスペースを与えることはできますが、サーバーのマシンのオーナーは 1 人です。

**サーバーのマシン上では、サーバーオーナーが開始したか、その種のホスト実行を承認していない限り、サンドボックスの外で何も実行されません。** 具体的には、サーバーオーナーだけが次のことを行えます。

- ワークスペースを作成する。それ以外の人には、オーナーに作成を依頼するか、ワークスペース管理者に招待してもらうよう求める画面が表示されます。
- サーバーがホストするターミナルでホストのシェルを開く。それ以外の人には、ワークスペースの独自のディレクトリ内で、エージェントと同じ制限を持つサンドボックス化されたターミナルが与えられます。
- 埋め込みのコードエディターを開く。サーバー自身のユーザーとして、ターミナル、タスク、拡張機能とともに動作します。
- プルリクエストや会話のワークツリーをネイティブエディターで開く。エディターはサーバー自身の画面上で、サーバーのユーザーとして起動します。
- ホスト上で何かを実行する[環境](/ja-JP/マニュアル/ハウツーガイド/環境/)の定義を保存または承認する。ホストへの配置、コマンドを実行するチェック、またはプロビジョニングやアーカイブのタスクを含みます。
- サンドボックスのないマシンのサーバーでエージェントを実行する。そこでは、それ以外の人の実行は拒否されます。ただし、オーナーが `--sandbox off` で開始した場合を除きます。その場合は、すべてのメンバーのエージェントが制限なしで実行されます（[サンドボックスのないホストでのエージェント](/ja-JP/マニュアル/コンセプト/サンドボックスとセキュリティ/#バックエンドのないホストでのエージェント)を参照）。
- ワークスペース自身のストレージの外にあるリポジトリのチェックアウトをリンクする。また、上記のルールより前にリンクされたものを確認する。さらに、リポジトリを追加する際にサーバーのフォルダーを参照する（[リポジトリを追加](/ja-JP/マニュアル/ハウツーガイド/リポジトリ追加/)を参照）。
- サーバー上で実行中のすべてのエージェントプロセスを表示して停止する。それ以外の人には、所属するワークスペースのライブなエージェントの実行だけが表示され、停止できます。
- エージェントに、サーバーユーザー自身のツール（Claude、Codex、Cursor など）で構成された MCP サーバーを使わせる。オーナーが責任を負う組み込みのハーネスの実行だけがそれを取得します（[個人の MCP サーバーはオーナーのもの](/ja-JP/マニュアル/ハウツーガイド/mcp-サーバー/#個人の-mcp-サーバーはオーナーのもの)を参照）。
- 人のメールアドレスを確認する。SSO がそれと一致できるようにするため（[OpenID Connect プロバイダーを接続](/ja-JP/マニュアル/ハウツーガイド/sso-oidc/#サインインが既存のアカウントと一致する仕組み)を参照）。
- インストール全体の設定を変更する: SSO、プロバイダーの認証情報、MCP エンドポイントとそのトークン、モデル管理、Connect、インストール全体のバックアップ。これらの操作は**サーバー権限**を宣言し、それ以外のすべての人に対して拒否されます。

オペレーターの ID とその定義は、意図的にそれぞれ 1 つだけです。

## 監査証跡

すべての認可判断 — **許可と拒否の両方** — は、ワークスペース単位のハッシュチェーン化された監査証跡に追記されます。

拒否だけのログは「何をブロックしたか」には答えますが、「このエージェントが実際に何をし、誰がそれを認可したか」には答えられません。そして後者が、インシデントレビューが出発点とする問いです。そこで各エントリには、帰属の連鎖全体を記録します。行為主体であるプリンシパル、その代理として行動した人間、経由した委任、アクションとその引数（ダイジェストとして）、判断、そして**判断を下したルール**です。

エントリは連鎖します。各エントリのハッシュは前のエントリのハッシュを含むため、どの行を編集、削除、並べ替えても、それ以降のハッシュがすべて壊れます。**チェーンを検証**は、全体を再導出し、最初に破綻したリンクを名指しします。検証できない監査ログはただのログですが、再導出できるものは証拠になります。

知っておく価値のある帰結が 2 つあります。

- 監査テーブルは**経過時間ベースのプルーニングの対象外**です。ハッシュチェーンは途中から切り詰めることができません。保持は「エクスポートしてから切り詰める」方式で、切り詰め時には、削除された区間の末尾ハッシュを保持するチェックポイントが残ります。そのため、残った部分も先頭まで検証できます。
- これはアクティビティタイムラインの**横に並ぶ**もので、その上に載るものではありません。タイムラインは人が行ったことであり、こちらは何が認可され、何が拒否されたかです。共有の相関 ID を使えば、1 回の呼び出しを両方から読み取れます。

改行区切りの JSON としてエクスポートでき、SIEM（Splunk、Elastic、Sentinel — ベアラートークン付きの HTTP エンドポイント）へストリームできます。ストリーミングは設計上ベストエフォートです。SIEM がダウンしていてもエージェントのツール呼び出しをブロックしてはならず、耐久性があり検証可能なコピーはいずれにせよディスク上にあります。

## セッション

インストールでは、**セッションの最大有効期間**と**アイドルタイムアウト**を設定できます。どちらも、すべての認証済み経路が通るデバイス認証情報のチェック時に適用されます。クライアントが無視できる程度の制約では、攻撃者ではなくアンケートに答えることになります。インストールで SSO を必須にすることもでき、その場合、新しいデバイスの手動ペアリングが無効になります（ロックアウトガード付きで、機能する SSO 接続が 1 つも存在しない間は拒否します）。

## そうではないもの

- **オブジェクト単位の ACL ではありません。** チケット単位やメッセージ単位の権限は、意図的に存在しません。チームが実際に求めるのはリポジトリ単位の分離であり、それは存在します。オブジェクト単位の共有は組み合わせ的に膨らむ領域で、ここでは需要が示されたことはありません。
- **DSL で設定するポリシーエンジンではありません。** 語彙は意図的に閉じており、そのためポリシー全体を描画、説明、列挙できます。
- **サーバー以外では適用されません。** クライアント側のチェックは、拒否される操作を提示しないためにだけ存在します。権威ある判断は常にサーバー側のものです。
