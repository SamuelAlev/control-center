:::note[OS サンドボックスが届く範囲と届かない範囲]
`cc_server` は起動時にホストをプローブし、利用可能な場合にはエージェントのコマンド実行を OS ネイティブのサンドボックスでラップします — macOS では Seatbelt、Linux と WSL2 では bubblewrap です（後者には `PATH` 上の `bwrap` と `socat` が必要です）。バックエンドが存在しない場合 — Windows、またはこれらのツールを欠いた Linux マシン — は、サーバーオーナーのエージェント実行だけが、制限なしで開始されます。それ以外の人の実行は拒否されます。サーバーオーナーは代わりに `--sandbox off` で起動することもでき、その場合は全メンバーのエージェントがそのマシン上で制限なしに実行されます。起動ログにどのケースかが示されます。詳しくは[バックエンドのないホストでのエージェント](#バックエンドのないホストでのエージェント)を参照してください。

サンドボックスをすり抜けるまま残る 2 つの隙間があり、これらは覚えておく価値があります:

- 内蔵ハーネスの**インプロセスのファイルツール**（`read`、`write`、`edit`、`apply_patch`、`search`、`find`、`search_files`）はサーバープロセス内で動作するため、ラップされるのは `bash` だけです。これらを制約しているのは、ツール自体のパス制限とアクションガードレールです。
- **Claude Code は `--dangerously-skip-permissions` 付きで起動されます**。非対話の `claude -p` が自身のプロンプトで永久にブロックしてしまうからです。そのため、そのファイル呼び出しは Control Center のガードレールではゲートされず、シェルコマンドもコマンドラインを読むフックでしか確認されません — それらを取り囲む境界が OS サンドボックスです。
  :::

## ここで分離が重要になる理由

エージェントはあなたに代わってファイルを読み、シェルコマンドを実行し、外部 API を呼び出します。気にすべき障害が悪意であることはまれです — あるのは、パスを読み違えて作業中のチェックアウトを書き換えてしまうエージェントであり、レビューを終えていないブランチをプッシュしてしまうエージェントです。したがって、製品が答えなければならない問いは「エージェントは信頼できるか」ではなく、「エージェントが誤ったときの影響範囲はどこまでか」です。

Control Center はこれに層で答えており、その層は意図的に独立しています。ひとつが欠けても、ほかは保たれます。これは重要なことです。というのも、最も外側の層である OS サンドボックスだけが唯一の条件付きの層であり、バックエンドを提供するホストに依存し、Windows ではどのホストも提供しないからです。それがない場合でも、サーバーが黙って全員のエージェントをそれなしで実行することはありません。

## バックエンドのないホストでのエージェント

サーバーは起動時に、このマシン上でエージェントがどう実行されるかを一度決め、再起動するまでその判定を保ちます:

- **サンドボックス化。** ホストにバックエンドがあり、サンドボックスがオンです。すべての実行がラップされます。
- **オフ。** サーバーオーナーが `--sandbox off` でサーバーを起動しました。全メンバーのエージェントがこのマシン上で制限なしに実行されます。これは一つの実行向けの設定ではなく、サーバーを使うすべての人に対するオーナーの選択です。
- **利用不可。** サンドボックスはオンですが、ホストにバックエンドがありません。実行が開始されるのは、その実行に責任を負う人がサーバー[オーナー](/ja-JP/マニュアル/コンセプト/認可/#サーバーオーナー)である場合だけです。依頼した人、あるいはスケジュール、Webhook、その他の自動化の場合はそれがバインドされている人です。それ以外の人の実行は、認証情報が発行されたりプロセスが始まったりする前に拒否されます。「このサーバーにはサンドボックスがないため、ここでエージェントを実行できるのはそのオーナーだけです。オーナーはサンドボックスをインストールするか、全員のサンドボックスをオフにできます。」と表示されます。

理由はマシンの所有権です。制限のないエージェントは、サーバーのユーザーアカウントができることなら何でもできるため、そのアカウントを所有する人だけが、全員に対して別の判断をしない限り、実行します。Windows のサーバーは常に利用不可の場合に当たります。Linux には独自の注意点があり、[サンドボックスバックエンドのリファレンス](/ja-JP/マニュアル/リファレンス/サンドボックスバックエンド/#linux-bubblewrap)で扱われています。bubblewrap がインストールされていても、ネイティブのディスパッチは現在そこでフェイルクローズドに失敗します。

同じルールは、プロセスを代わりに開始するさらに小さなものにも適用されます:

- **ACP CLI を通って動く小さなヘルパー**: 会話のタイトル、`/btw`、`/handoff`、`/goal`。サーバーがエージェントをサンドボックス化している場合、それらは自分専用のセッション内でサンドボックスの中で動きます。`--sandbox off` の下では制限なしで動きます。利用可能なサンドボックスがない場合、サーバーオーナーが責任を負うリクエストに対してだけ動き、それ以外の人には実行されず、タイトルは生成されず、サイドの質問には Content synthesizer に動作するランナーがないと表示されます。ツールを起動しないヘルパーは影響を受けません。
- **Review Studio の視覚チェックにおけるプルリクエストのゴールデンテスト**も、同じルールに従います。
- **実行内のツールプロセスと `bash`** は、ホストに決してフォールバックしません。サーバーがエージェントをサンドボックス化するよう設定されているのに、実行に与えるサンドボックスがない場合、それらは拒否されます。
- **ゴールのチェック**は、会話のワークツリーに対する使い捨てのサンドボックスで実行され、エージェント自身の `bash` と同じ制限を受けます。サンドボックスがなければ実行されず、ゴールは担当者のために停止します。`--sandbox off` の下では、エージェントの `bash` と同じように実行されます。
- **ゴールのレビュー**は、すべてのアダプターで読み取り専用として実行されます。読み取りのみ、ワークツリーは読み取り専用でマウント、`bash` なし、サブエージェントなし、Web なし。実行を読み取り専用に保てないアダプター（ACP エージェント）はレビュアーとして使われません。

## エージェントを実際に制約しているもの

サンドボックスの有無にかかわらず、あらゆるホストでエージェントの実行を制約するものが 5 つあります。いずれもカーネルの境界ではありませんが、どれも現実のものです。ホストがバックエンドを提供する場合、OS サンドボックスはそれらの上に位置し、以下に挙げる「サンドボックスが追加するものと、それが止まる場所」で、それによって何が変わるかを説明します。

**エージェント自身のコピーオンライトのワークツリー。** すべての会話は、リンクされた各リポジトリのチェックアウトを独自に用意し、バイト単位のコピーではなく同梱の `rift` ネイティブによるコピーオンライトでクローンします。そのため、分離はデフォルトにできるほど低コストです。ワークスペースに追加した登録済みリポジトリは、エージェントが作業するディレクトリではありません — 同じリポジトリに触れる 2 つの会話は互いの編集を見ることができず、どちらもあなたのチェックアウトを編集していません。

粒度については正確に述べておく価値があります: **ワークツリーは会話単位であり、エージェント単位ではありません。** 同じ会話の 2 つのエージェントは、その会話の `repos/` を _共有_ する別々のオーバーレイ作業ディレクトリを受け取ります — ひとつの変更に対して協力しているのですから、これが狙いです — 一方で、それぞれのプライベートなエージェントディレクトリは分離されたままです。`rift` が出荷される環境ではコピーオンライトが唯一のバックエンドです。reflink できないファイルシステムや、リポジトリとは別のボリュームにあるデータディレクトリでは、フォールバックせずにプロビジョニングが失敗します。例外は Windows です。そこにはコピーオンライトのバックエンドが存在しないため、`git worktree` がバックエンドになります。これは暗黙の劣化ではありません。

**内蔵ハーネスのファイルツールにおけるパス制限。** ハーネスの `read`、`write`、`edit`、`apply_patch`、`search`、`find`、`search_files` ツールは、すべてのパスを実行の作業ディレクトリと共有ルート — 会話の `repos/` ディレクトリ（ワークツリーが置かれる場所）と、存在する場合のスペースの添付ファイルディレクトリ — を基準に解決し、その外側に着地するものは拒否します。絶対パスは、すでに内側にあった場合にのみ受け入れられます。ワークツリー内から外を指すシンボリックリンクも解決され、拒否されます。これが、サンドボックスが関与していなくてもエージェントが `~/.ssh` に `write` できない理由です。

**モードのツールサーフェス。** 会話の[モード](/ja-JP/マニュアル/コンセプト/モード/)は、その実行でどのツールがそもそも実体化されるかを決めます。読み取り専用のモード（`plan`、`review`、`orchestrate`）では、変更を伴うツールはそもそもレジストリに存在せず、それらのモードのシェルコマンドポリシーは、あらゆる変更コマンドをプロンプトするのではなく、そもそも拒否します — `git commit`、`git push`、`npm install`、`docker` などすべてです。存在しないツールは呼び出せません。これは、存在してゲートされているツールよりも強い保証です。

**統一されたアクションガードレール。** 変更を伴うすべてのツールは、生み出しうるエフェクトクラスを宣言し、ポリシーエンジンは呼び出しが実行される前に、それぞれを許可・確認・拒否のいずれかに解決します。承認者が接続されていない `prompt` は _拒否_ に解決されます — 誰も答えられない問いが「はい」になることはありません。解決モデルについては[ガードレール](/ja-JP/マニュアル/コンセプト/ガードレール/)を参照してください。

**ブローカー経由の資格情報とサニタイズされた環境。** 資格情報は起動ごとに発行され、実行の終了時に取り消されます。実行が持つ GitHub トークンは読み取りはできてもプッシュはできません — 後述の「プッシュは Control Center を通る」を参照してください。ACP、ハーネスの `bash`、ネイティブラップ下の Claude Code は、プロセスが始まる前に、動的リンカーとインタープリターのインジェクションベクター（`LD_PRELOAD`、`DYLD_INSERT_LIBRARIES`、`NODE_OPTIONS`、`GIT_SSH_COMMAND` とその類）を除去した環境を受け取ります。`NoSandboxAdapter` 経由の Claude Code はホストの環境を継承します。

### それらの境界が薄くなる場所

ハーネスのファイルツールは子プロセスではなく_サーバープロセス内_で動作するため、サンドボックスプロファイルが接続されたとしてもそれを制約できません — サンドボックス化されたコマンドランナーを通るのは `bash` だけです。それらの閉じ込めは前述のパスチェックであり、したがってこのチェックは第二の防衛線ではなく、まさに構造を支える要素です。

`bash` ツールは、正確さが求められるもうひとつの箇所です。そのコマンドはモードのコマンドポリシーに対して評価され、その後、サニタイズされた環境とワークツリーを作業ディレクトリとしてスポーンされます。バックエンドが存在する場合、そのスポーンはラップされるため、シェルコマンドがワークツリーの外に書き込むのを止めるのはサンドボックスです。存在しない場合（`--sandbox off` のすべての実行、および Windows または `bwrap` と `socat` のない Linux でのオーナー自身の実行）は、コマンドポリシーが、コマンドとディスクの残りの間にある唯一のものです。`chat` モードでは、ポリシーは固定リスト（特権昇格、システムとディスクの破壊、コンテナと名前空間の脱出）をハード拒否し、リモート状態の変更（`git push`、`gh pr create`、パッケージの公開とインストール）では確認を求めます。どちらのリストにもないものは実行されます。パイプライン、チェーン、サブシェルは解析され、各サブコマンドが個別に評価され、最も制限の厳しい決定が優先されます。

Claude Code をアダプターとして使う場合が、サンドボックスが最も大きな重みを担うケースです。Control Center はそれを `--dangerously-skip-permissions` 付きで起動します。非対話の `claude -p` が自身の承認プロンプトで永久にブロックしてしまうからです。その読み取り、書き込み、編集の呼び出しは自プロセス内で行われ、Control Center はそれらを決して見ません。`Bash` 呼び出しは実行前にサーバー上のフックへ送られ、フックがコマンドラインを分類して対応するルールに問い合わせます。Control Center が提供する `mcp__*` ツールは、これまでどおりゲートを通ります。バックエンドが存在する場合、それらの見えない呼び出しも依然としてサンドボックスのラップ内で行われるため、それらを取り囲む境界は OS です。存在しない場合、何もありません。各アダプターはこれを自身のエンフォースメントマトリクスで明示しています — [アダプターの正直さマトリクス](/ja-JP/マニュアル/コンセプト/ガードレール/#アダプターの正直さのマトリクス)を参照してください。

## プッシュは Control Center を通る

エージェント単位の権限フラグはありません。エージェントがコミットの作成、プッシュ、プルリクエストの作成、トラッカーへの書き込み、ネットワークへのアクセスをできるかどうかは[ガードレール](/ja-JP/マニュアル/コンセプト/ガードレール/)が決めます — 許可、先に確認、拒否のいずれかです — そして、どのアダプターがエージェントを実行しても同じルールが適用されます。

プッシュは、ルールを回避しようとするエージェントに対しても守られなければならないアクションです。そのため、エージェントが何を実行するかではなく、何を持っているかによって強制されます。実行は開始時にフォージのトークンを持たず、その `git` は決してトークンを受け取りません。`gh` が必要とすると、Control Center は、その実行が扱う 1 つの GitHub リポジトリを対象とするトークンを渡します。このトークンは、ワークスペースの GitHub App、サーバー自身のアプリ、または Control Center Connect から発行されます。読み取りしかできず、プッシュ、コメント、編集はできません。実行の git 設定は、GitHub へのすべてのプッシュ URL（`https://github.com/`、`git@github.com:`、`ssh://git@github.com/`）を、`cc_server` 上のループバックエンドポイントである**エージェント実行ゲートウェイ**に書き換えます。ゲートウェイはプッシュがどの ref を更新するかを読み取り、**リモートへプッシュ**のルールに問い合わせます — そのため「`main` へのプッシュを拒否」のようなブランチ限定のルールも適用されます — そしてその後で初めて、この目的のために発行し、エージェントには決して渡さない書き込みトークンでプッシュを GitHub へ転送します。拒否されたプッシュは git 自身の出力に表示されます:

```text
 ! [remote rejected] main -> main (Control Center policy: …)
```

ゲートウェイがプッシュを転送するのは、ワークツリー自身のリポジトリか、ワークスペースにリンクされた GitHub リポジトリだけです。フェッチもゲートウェイを通ります。GitHub、GitLab、Bitbucket のいずれでも、ゲートウェイは、実行が扱うリポジトリを、ゲートウェイが保持し実行からは決して見えない認証情報でフェッチします。GitLab と Bitbucket では、実行を依頼したのがあなたであれば、あなた自身のトークンを使い、誰も依頼していなければ、そのリポジトリの自動化トークンを使います。フェッチが確認を求めることはなく、**ネットワークにアクセス**が拒否に設定されている場合にのみ、フェッチは拒否されます。

その他のシェルコマンドは、より緩やかなゲートを通ります。ハーネスの `bash` ツールと、フック経由の Claude Code の `Bash` ツールは、各コマンドラインを分類し、該当するルールに問い合わせます: `git commit`、`merge`、`rebase`、`cherry-pick`、`revert`、`am` は**コミットを作成**、`gh pr create` は**プルリクエストを作成**、`gh pr merge`、`review`、`comment`、`close` は**プルリクエストの更新またはマージ**、`gh issue create`、`edit`、`comment`、`close` は**外部トラッカーへの書き込み**、パッケージのインストールは**パッケージをインストール**、`curl` と `wget` は**ネットワークにアクセス**です。GitHub への書き込みをシェルから行うのは例外です。`gh pr create`、`gh pr comment`、`gh pr edit`、`gh pr merge`、`gh issue` の書き込みは、トークンが読み取りしかできない実行では動作せず、エージェントは Control Center のツールに案内されます。そのツールがこれらのルールに問い合わせます。これはアクションの一般的な書き方を認識するものであり、隠そうと決めたエージェント（`eval`、スクリプトファイル、直接の API 呼び出し）はすり抜けられます。プッシュはこれに依存しません。

実行が受け取る GitHub トークンは、すべて二重に制限されます。1 つのリポジトリに、そして責任を負うメンバー（依頼した人、そうでなければワークスペース所有者）がそこでできることに。フォールバックの資格情報はありません。トークンを発行できない場合、そのトークンを求めたコマンドが、その理由を示します。

チケットの API キーはサンドボックスに置かれません。エージェントは Control Center の MCP ツールを使ってチケットを書き込み、それらのツールが**外部トラッカーへの書き込み**のルールに問い合わせます。

**ネットワークにアクセス**のルールは、実行の開始時に一度だけ読み取られます。サンドボックスのネットワークはオンかオフのどちらかしかないため、拒否はそれをオフにし、許可と先に確認はオンのままにします。ハーネスの `web_fetch` と `web_search` ツールは引き続き呼び出しごとに確認します。実行の資格情報ハンドルは、実行の終了時に解放されます。その背後にあるトークンはメンバーとリポジトリごとに共有され、約 1 時間以内に失効します。メンバーが GitHub からサインアウトするかワークスペースを離れると、その人の代わりに発行されたすべてのトークンが一度に破棄されます。

## エージェントが読み取りしかできないリポジトリ

実行されるエージェントが変更できるのは、その実行が代行する人が[書き込み権限](/ja-JP/マニュアル/コンセプト/認可/#コードの変更には書き込み権限が必要)を持つリポジトリのチェックアウトだけです。ワークスペースの管理者は、リンクされたすべてのリポジトリでその権限を持ちます。スケジュールやほかの自動化のように、依頼した人がいない実行は、その自動化のトークンを縛っている責任者によって同じように判断されます。

スペースに、その人が読み取りしかできないリポジトリがある場合、エージェントはそのリポジトリを読んで検索することはできますが、ファイルを変更することはできません。ファイルツールは、`<repo> is read-only for this run` で始まるメッセージで拒否します。そのメッセージは、チェックアウトを変更するには書き込み権限が必要であること、実行が代行する人がその権限を持っていないこと、そしてワークスペースの管理者が付与できることを伝えます。サンドボックス内では、チェックアウトはすべてのプロセスにとって読み取り専用なので、そこへ書き込むシェルコマンドは「Operation not permitted」で失敗します。これには `git commit` や、チェックアウト内に出力を書き込むビルドやテストも含まれます。書き込み可能なリポジトリは通常どおり動作するため、管理者や、スペース内のすべてのリポジトリへの書き込みアクセス権を持つ人には、違いは見えません。

この判断は実行の開始時に一度だけ行われます。権限の変更は次のエージェントの実行から有効になり、実行中にスペースへ追加されたリポジトリも同様です。

サーバーオーナーがサンドボックスをオフにしている場合は、エージェント自身のファイルツールと Claude Code の書き込みツールだけが拒否され、シェルコマンドはそれでもチェックアウトを変更できます。どちらの場合も、書き込み権限がなければ何もプッシュできません。すべてのプッシュがその権限に照らして確認されるからです。サンドボックスが各プラットフォームでどのプロセスを閉じ込めるかは、[サンドボックスバックエンド](/ja-JP/マニュアル/リファレンス/サンドボックスバックエンド/)にあります。

## サンドボックスが追加するものと、それが止まる場所

`SandboxBackend` enum には 3 つの値があります — `native`（macOS では Seatbelt、Linux と WSL2 では bubblewrap）、`none`、`microvm` です。エージェントのコマンドラッピングが使うのは最初の 2 つだけです。`microvm` は対話ターミナルとリグ向けの閉じ込め VM バックエンドであり、`bash` ラップの暗黙のアップグレードではありません。native の形を理解すると、接続されている場合に何を得られるのか、そしてそれが決して与えようとしなかったものは何かが分かります。

`cc_server` は起動時に一度だけホストをプローブし、バックエンドが応答する場合、ディスパッチ経路が持つ 2 つのシームの両方にそれを与えます。トランスポートが 1 つを共有しているわけではないからです。1 つ目（`SandboxPort`）は Claude Code CLI をラップします。2 つ目（`SandboxManager`）は ACP アダプターと内蔵ハーネスの `bash` ツールをラップします。片方だけに与えると、ほかはラップされずにスポーンされますが、以前はそうなっていました。`--sandbox off` の下では、それらはすべてラップされずにスポーンします。バックエンドのないホストでは、オーナーの実行だけが開始され、それもラップされません。サーバーは起動行でどちらのケースなのかを通知します。ACP とハーネスの `bash` は依然として環境をサニタイズします。`NoSandboxAdapter` 経由の Claude Code はホストの環境を継承します。

サーバーがホストするターミナルがホストシェルを開くのは、サーバーの[オーナー](/ja-JP/マニュアル/コンセプト/認可/#サーバーオーナー)に対してだけです。それ以外の人には、エージェントと同じ制限を受けたサンドボックス化されたターミナルが、ワークスペース自身のディレクトリ内で提供されます。ターミナルを開いた人だけが、それに入力したり、読んだり、閉じたりできます。

Linux では、`bubblewrap` がマウント名前空間を構築するため、エージェントはそこにバインドされたものだけを本当に見ます。macOS では、`sandbox-exec` が **デフォルトで許可** の Seatbelt プロファイルを適用します — 完全なデフォルト拒否のプロファイルでは、対話シェルが使えなくなります。列挙すべき dyld、XPC、Mach 呼び出しの数が非現実的だからです。そのため macOS のプロファイルは `(allow default)` から始まり、拒否を切り出します: シークレットパスの読み取り、明示的な許可を上に重ねてデフォルト拒否にリセットされた書き込みポリシー、拒否されたすべてのパスとその祖先に対する unlink の禁止（リネームで書き込み拒否を迂回できないようにするため）、常に危険なバイナリと書き込み可能ディレクトリにコピーされたものに対する exec の拒否、そしてループバックプロキシポートと DNS に制限されたネットワークです。ホーム配下のツールチェーンのインストール（corepack の pnpm、Node のバージョンマネージャー、Playwright のブラウザー、rustup、fvm、uv など）は、その exec ブロックの内側で実行可能なままなので、エージェントは回避策なしで利用できます。常に危険なバイナリの拒否は、その内側でも引き続き適用されます。さらに各セッションには専用のプライベート `TMPDIR` が割り当てられます。これは、エージェントがビルドしたプログラムを実行したり Unix ソケットを開いたりしてよい唯一の一時ディレクトリです。

どのモードでも、さらに 2 つの保護が適用されます。サンドボックスは、サーバーがプログラムを実行するフォルダー（`PATH` 上のすべてのフォルダーと、一般的なユーザーごとのツールフォルダー）内のコマンドを追加、置換、削除、名前変更することができません。そのため、サンドボックス化された実行が、後にサンドボックス外でサーバーが起動するプログラムを仕込むことはできません。実行の内側からのグローバルなインストールや既定バージョンの切り替えは、したがって「Operation not permitted」で失敗します。一方、プロジェクトローカルのインストールと `npx` 形式の実行は引き続き動作します。グローバルなツールは、サーバー自身にインストールし、サーバーを再起動してください。さらに、サンドボックスが読めないホームパスは書き込むこともできず、サーバーユーザーのシェルとセッション起動時のファイルは決して書き込めません。詳細とプラットフォームごとの制限は[サーバーのコマンドフォルダー](/ja-JP/マニュアル/リファレンス/サンドボックスバックエンド/#サーバーのコマンドフォルダー)にあります。

実行のツールサンドボックスは、その実行に属し、実行が終わると解放されます。言語サーバーはサンドボックス化された実行ごとに新しく起動します。デバッグセッションは、セッションが終わるまで、ターンをまたいでサンドボックスを保持します。その最大時間は 30 分です。

実際の結果はこうです: Linux ではエージェントから見えるファイルシステムが狭められ、macOS ではエージェントは依然としてホストのほとんどを _読み取る_ ことができ、あなたの登録済みチェックアウトは不可視性によってではなく、明示的な書き込みとリネームの拒否によって保護されます。どちらも名前空間レベルの分離であり、カーネルのセキュリティ境界ではありません — バックエンド自身がその能力ノートでそう述べています。

バインドマウントの集合が、エージェント間境界の引かれる場所です。オーバーレイディスパッチ（Claude Code と ACP）は、実行ごとに解決される最大 4 つのパスをマウントします: エージェントのオーバーレイ作業ディレクトリは読み書き可、エージェントの設定ディレクトリは読み取り専用、会話の共有 `repos/` ディレクトリは存在する場合に読み書き可、スペースの添付ファイルディレクトリは存在する場合に読み取り専用です。兄弟エージェントのディレクトリがマウントされることはありません。ハーネスの `bash` ラップはより狭く、実行の作業ディレクトリだけをバインドマウントします。これはハーネスのインプロセスのパスチェックがソフトウェアで強制するのと同じ形であり、両者は一致しています — ただしハーネス自身のファイルツールをカバーするのはパスチェックだけであり、それらはマウント名前空間にまったく到達しません。

あなたの登録済みチェックアウトは、その上に書き込み拒否の集合として加わります。すべてのモードで、3 つのラップされたパス（Claude Code、ACP、ハーネスの `bash`）すべてにおいてです。そして各ルールは、そのリテラルの綴りとシンボリックリンク解決後の綴りの両方で出力されます。2 つ目の綴りはおまけではありません: カーネルは拒否ルールを解決後のパスに対して照合し、macOS では解決は例外的なものではなく日常的なものです — `/tmp` は実際には `/private/tmp` であり、`/var/folders/…` は実際には `/private/var/folders/…` です — そのため、どちらかを通して到達したチェックアウトは、プロファイルが禁じているように見えながら書き込み可能でした。

サンドボックス下のネットワークは、インプロセスのループバックプロキシによって強制されるセッションごとの**ドメイン**許可リストです。外向き通信はデフォルト拒否です: ネットワークがオフの場合、プロキシは依然として起動しますが許可リストは空なので、外向き接続はすべて拒否されます。オンの場合、リゾルバーは、厳選されたベースライン — LLM API プロバイダー、git ホスティング、パッケージレジストリ、モデルカタログ — に GitHub のドメインを加えて許可リストを構築し、すべての接続のターゲットホストをそれに照合します。ワイルドカードは機能します（`*.example.com` はサブドメインに一致し、apex には一致しません）。別の常時拒否リストが許可リストに優先し、クラウドのメタデータエンドポイントとテレメトリのシンクをカバーします。設定_できない_のはリスト自体です: 仕様は追加ドメイン用の `egressAllowlist` フィールドを持ちますが、ディスパッチ経路のどこもそれを埋めないため、実際にはすべての実行がベースラインと GitHub だけを取得し、それ以上はありません。

macOS では、拒否は観測可能です: モニターが Sandbox の拒否についてシステムログを監視し、既知のノイズをフィルタリングし、リトライの嵐を重複排除し、それぞれを `SandboxViolation` として表面化します。何が試みられ、何がブロックされたかを名指ししてです。Linux では、ラップ経路が stderr を解析して `EPERM`、`Operation not permitted`、`Permission denied` を探し、同じイベントタイプを発行します — システムログのタップはありません。それらは実行自身のイベントストリームに届くため、拒否されたシステムコールはログだけでなくトランスクリプトにも現れます。テレメトリは、ネイティブサンドボックスが実際にプロセスをラップしている間だけ存在します — バックエンドのないホストでは観測するものがありません。またこれはガードレールとは無関係です。違反は拒否されたシステムコールから生じ、ルールの参照から生じることは決してありません。

## コードモードのスクリプト

[コードモード](/ja-JP/マニュアル/コンセプト/コードモード/)のスクリプトは、別の扱いになります。エージェントのサンドボックスにはまったく依存しません。スクリプトがサーバー内で実行されることも、エージェントのサンドボックス内で実行されることもありません。サーバーに同梱されたプログラム `cc_codemode` の独自のプロセスで実行されます。このプログラムは、スクリプトを読み込む前に自らをロックダウンし、ロックダウンがどこまで効いたかを報告します。サーバーは、ロックダウンが完全に効いている場合にのみ、スクリプトを送ります。

| ホスト | ランナーが自分自身に適用するもの |
| --- | --- |
| Linux | システムコールの許可リスト（seccomp）で、入力の読み取り、出力の書き込み、自身のメモリ管理、クロックの読み取り、終了といった、ごくわずかな操作しか許可しません。新たな権限の取得もケーパビリティもなし、コアダンプなし、ファイル書き込みなし、新しいプロセスなし、開くファイルは最大 3 つ、アドレス空間は 3 GiB、そして厳格なプロセッサ時間の上限があります。カーネルが対応している場合は Landlock も追加されます。 |
| macOS | 既定で拒否するサンドボックスプロファイル。プロセス情報、ファイルの存在確認、システムとハードウェアの情報、および関連するカーネル呼び出しも拒否します。コアダンプなし、ファイル書き込みなし、厳格なプロセッサ時間の上限があります。 |
| Windows | スクリプトごとに新しい AppContainer を使い、1 つのプロセス、3 GiB のメモリ、ユーザーインターフェースなしに制限されたジョブの中で実行します。動的コード、子プロセス、win32k 呼び出しは無効です。**Windows ではまだ実行検証されていません。** |

ランナーは、環境変数なし、入力と出力以外に開いているファイルなし、資格情報なしで起動します。自身のメモリの外でできることは、サーバーにツールの実行を依頼することだけです。サーバーは、その呼び出しを直接の呼び出しと同じモードフィルター、[ガードレール](/ja-JP/マニュアル/コンセプト/ガードレール/)、承認を通して実行します。

サーバーは、これらすべてを起動時に確認します。ランナーの自己テストを実行します。この自己テストはロックダウンを適用し、ファイルの読み取りと作成、ネットワーク接続、プロセスの起動を試みます（システムごとにさらに多くを試みます）。さらに、その下で実際のスクリプトを実行します。拒否されないものがあれば、そのマシンではサーバーはスクリプトを一切実行せず、どの実行も `repl` を受け取りません。サーバーは、起動時とコードモードの設定ページで、その理由を示します。リリースビルドではないランナーも、同じ方法で拒否されます。より弱い代替手段はありません。

ランナーは、スクリプト内で各呼び出しがどこで行われたかも報告するため、会話でスクリプトの構造を示せます。サーバーはその位置をスクリプトと照合し、表示にのみ使います。呼び出しを許可するかどうかを決めることは決してなく、ガードレールの監査にも含まれません。

カバーしないもの：スクリプトは、そのツール呼び出しが実際のツール呼び出しである以上、実行のツールが許す何でも依然として行えます。macOS では、プロセス ID が存在するかどうかを依然として知ることができます。また、JavaScript エンジンやカーネルの欠陥は、ロックダウンによって閉じ込められますが、それによって排除されるわけではありません。

## 確認はガードレールから来るのであり、サンドボックスからではない

サンドボックスには承認の経路がありません。起動し、実行し、イベントを発行し、終了します。そこに人間が問いに答える場所はありません。スペースで確認を見るとき — このプッシュを承認、この削除を承認 — それは、アクションがそもそもランタイムに到達する_前に_、ガードレールエンジン（またはハーネスのコマンドポリシー）が提起したものです。

この順序は意図的です。システムコールの後に起きた承認は、ゲートではなく監査記録になってしまいます。フェイルクローズのルールがガードレールにある理由もここにあります。承認者が接続されていない場合、決定は何かが実行される前に下され、それは拒否です。
