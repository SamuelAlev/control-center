:::note[OS サンドボックスが届く範囲と届かない範囲]
`cc_server` は起動時にホストをプローブし、利用可能な場合にはエージェントのコマンド実行を OS ネイティブのサンドボックスでラップします — macOS では Seatbelt、Linux と WSL2 では bubblewrap です（後者には `PATH` 上の `bwrap` と `socat` が必要です）。バックエンドが存在しない場合 — Windows、またはこれらのツールを欠いた Linux マシン — は、実行は以下に挙げる他の境界へフォールバックし、サーバーはその旨を起動ログで通知します。`--sandbox off` はそれを意図的に無効にします。

サンドボックスをすり抜けるまま残る 2 つの隙間があり、これらは覚えておく価値があります:

- 内蔵ハーネスの**インプロセスのファイルツール**（`read`、`write`、`edit`、`apply_patch`、`search`、`find`、`search_files`）はサーバープロセス内で動作するため、ラップされるのは `bash` だけです。これらを制約しているのは、ツール自体のパス制限とアクションガードレールです。
- **Claude Code は `--dangerously-skip-permissions` 付きで起動されます**。非対話の `claude -p` が自身のプロンプトで永久にブロックしてしまうからです。そのため、そのファイル呼び出しとシェル呼び出しは Control Center のガードレールではゲートされません — それらを取り囲む境界が OS サンドボックスです。
  :::

## ここで分離が重要になる理由

エージェントはあなたに代わってファイルを読み、シェルコマンドを実行し、外部 API を呼び出します。気にすべき障害が悪意であることはまれです — あるのは、パスを読み違えて作業中のチェックアウトを書き換えてしまうエージェントであり、レビューを終えていないブランチをプッシュしてしまうエージェントです。したがって、製品が答えなければならない問いは「エージェントは信頼できるか」ではなく、「エージェントが誤ったときの影響範囲はどこまでか」です。

Control Center はこれに層で答えており、その層は意図的に独立しています。ひとつが欠けても、ほかは保たれます。これは重要なことです。というのも、最も外側の層である OS サンドボックスだけが唯一の条件付きの層であり、バックエンドを提供するホストに依存し、Windows ではどのホストも提供しないからです。

## エージェントを実際に制約しているもの

サンドボックスの有無にかかわらず、あらゆるホストでエージェントの実行を制約するものが 5 つあります。いずれもカーネルの境界ではありませんが、どれも現実のものです。ホストがバックエンドを提供する場合、OS サンドボックスはそれらの上に位置し、以下に挙げる「サンドボックスが追加するものと、それが止まる場所」で、それによって何が変わるかを説明します。

**エージェント自身のコピーオンライトのワークツリー。** すべての会話は、リンクされた各リポジトリのチェックアウトを独自に用意し、バイト単位のコピーではなく同梱の `rift` ネイティブによるコピーオンライトでクローンします。そのため、分離はデフォルトにできるほど低コストです。ワークスペースに追加した登録済みリポジトリは、エージェントが作業するディレクトリではありません — 同じリポジトリに触れる 2 つの会話は互いの編集を見ることができず、どちらもあなたのチェックアウトを編集していません。

粒度については正確に述べておく価値があります: **ワークツリーは会話単位であり、エージェント単位ではありません。** 同じ会話の 2 つのエージェントは、その会話の `repos/` を _共有_ する別々のオーバーレイ作業ディレクトリを受け取ります — ひとつの変更に対して協力しているのですから、これが狙いです — 一方で、それぞれのプライベートなエージェントディレクトリは分離されたままです。`rift` が出荷される環境ではコピーオンライトが唯一のバックエンドです。reflink できないファイルシステムや、リポジトリとは別のボリュームにあるデータディレクトリでは、フォールバックせずにプロビジョニングが失敗します。例外は Windows です。そこにはコピーオンライトのバックエンドが存在しないため、`git worktree` がバックエンドになります。これは暗黙の劣化ではありません。

**内蔵ハーネスのファイルツールにおけるパス制限。** ハーネスの `read`、`write`、`edit`、`apply_patch`、`search`、`find`、`search_files` ツールは、すべてのパスを実行の作業ディレクトリと共有ルート — 会話の `repos/` ディレクトリ（ワークツリーが置かれる場所）と、存在する場合のスペースの添付ファイルディレクトリ — を基準に解決し、その外側に着地するものは拒否します。絶対パスは、すでに内側にあった場合にのみ受け入れられます。ワークツリー内から外を指すシンボリックリンクも解決され、拒否されます。これが、サンドボックスが関与していなくてもエージェントが `~/.ssh` に `write` できない理由です。

**モードのツールサーフェス。** 会話の[モード](/ja-JP/マニュアル/コンセプト/モード/)は、その実行でどのツールがそもそも実体化されるかを決めます。読み取り専用のモード（`plan`、`review`、`orchestrate`）では、変更を伴うツールはそもそもレジストリに存在せず、それらのモードのシェルコマンドポリシーは、あらゆる変更コマンドをプロンプトするのではなく、そもそも拒否します — `git commit`、`git push`、`npm install`、`docker` などすべてです。存在しないツールは呼び出せません。これは、存在してゲートされているツールよりも強い保証です。

**統一されたアクションガードレール。** 変更を伴うすべてのツールは、生み出しうるエフェクトクラスを宣言し、ポリシーエンジンは呼び出しが実行される前に、それぞれを許可・確認・拒否のいずれかに解決します。承認者が接続されていない `prompt` は _拒否_ に解決されます — 誰も答えられない問いが「はい」になることはありません。解決モデルについては[ガードレール](/ja-JP/マニュアル/コンセプト/ガードレール/)を参照してください。

**ケイパビリティでゲートされた資格情報とサニタイズされた環境。** 資格情報は起動ごとに会話のケイパビリティフラグから発行され、実行の終了時に取り消されます。ACP、ハーネスの `bash`、ネイティブラップ下の Claude Code は、プロセスが始まる前に、動的リンカーとインタープリターのインジェクションベクター（`LD_PRELOAD`、`DYLD_INSERT_LIBRARIES`、`NODE_OPTIONS`、`GIT_SSH_COMMAND` とその類）を除去した環境を受け取ります。`NoSandboxAdapter` 経由の Claude Code はホストの環境を継承します。

### それらの境界が薄くなる場所

ハーネスのファイルツールは子プロセスではなく_サーバープロセス内_で動作するため、サンドボックスプロファイルが接続されたとしてもそれを制約できません — サンドボックス化されたコマンドランナーを通るのは `bash` だけです。それらの閉じ込めは前述のパスチェックであり、したがってこのチェックは第二の防衛線ではなく、まさに構造を支える要素です。

`bash` ツールは、正確さが求められるもうひとつの箇所です。そのコマンドはモードのコマンドポリシーに対して評価され、その後、サニタイズされた環境とワークツリーを作業ディレクトリとしてスポーンされます。バックエンドが存在する場合、そのスポーンはラップされるため、シェルコマンドがワークツリーの外に書き込むのを止めるのはサンドボックスです。存在しない場合 — Windows、または `bwrap` と `socat` のない Linux — コマンドポリシーが、コマンドとディスクの残りの間にある唯一のものです。`chat` モードでは、ポリシーは固定リスト（特権昇格、システムとディスクの破壊、コンテナと名前空間の脱出）をハード拒否し、リモート状態の変更（`git push`、`gh pr create`、パッケージの公開とインストール）では確認を求めます。どちらのリストにもないものは実行されます。パイプライン、チェーン、サブシェルは解析され、各サブコマンドが個別に評価され、最も制限の厳しい決定が優先されます。

Claude Code をアダプターとして使う場合が、サンドボックスが最も大きな重みを担うケースです。Control Center はそれを `--dangerously-skip-permissions` 付きで起動します。非対話の `claude -p` が自身の承認プロンプトで永久にブロックしてしまうからです。その読み取り、書き込み、編集、シェル呼び出しは自プロセス内で行われ、Control Center はそれらを決して見ません。ゲートに到達する呼び出しは、Control Center 自身が提供する `mcp__*` ツールだけです。バックエンドが存在する場合、それらの見えない呼び出しも依然としてサンドボックスのラップ内で行われるため、それらを取り囲む境界は OS です。存在しない場合、何もありません。各アダプターはこれを自身のエンフォースメントマトリクスで明示しています — [アダプターの正直さマトリクス](/ja-JP/マニュアル/コンセプト/ガードレール/#the-adapter-honesty-matrix)を参照してください。

## ケイパビリティのゲートは「不在による強制」である

会話は 4 つのケイパビリティフラグを持ちます: リポジトリへのプッシュ、GitHub API の呼び出し、チケットプロバイダーの呼び出し、ネットワークへのアクセスです。これらはエージェントが行動するときにチェックされるのではありません。起動時に一度だけ、資格情報ブローカーによってチェックされます — そしてオフのケイパビリティとは、対応するトークンがそもそも環境に置かれないというだけのことです。

これが仕組みのすべてであり、はっきり述べておく価値があります。失敗の様相が、人が期待するものとは違うからです。「GitHub API の呼び出しを許可」をオフにしても、「ケイパビリティが拒否されました」というメッセージは出ません。送るべき `GH_TOKEN` が存在しないため、エージェントの内部でごく普通の `401` が出るだけです。エージェントはそれを資格情報の問題として語るかもしれません。不在による強制は堅牢です — 回避すべきチェックが存在しません — しかし静かであり、エージェントはなぜ失敗したのか分かりません。

ネットワークフラグも同じように振る舞います。オフの場合、ハーネスの `web_fetch` と `web_search` ツールはあらゆる呼び出しを拒否し、サンドボックス化されたスポーンのプロキシ許可リストは空になるため、外向きの接続はすべて拒否されます。

資格情報は実行の終了時に取り消されるため、ハンドルがそれを発行した実行より長生きすることはありません。

## サンドボックスが追加するものと、それが止まる場所

`SandboxBackend` enum には 3 つの値があります — `native`（macOS では Seatbelt、Linux と WSL2 では bubblewrap）、`none`、`microvm` です。エージェントのコマンドラッピングが使うのは最初の 2 つだけです。`microvm` は対話ターミナルとリグ向けの閉じ込め VM バックエンドであり、`bash` ラップの暗黙のアップグレードではありません。native の形を理解すると、接続されている場合に何を得られるのか、そしてそれが決して与えようとしなかったものは何かが分かります。

`cc_server` は起動時に一度だけホストをプローブし、バックエンドが応答する場合、ディスパッチ経路が持つ 2 つのシームの両方にそれを与えます。トランスポートが 1 つを共有しているわけではないからです。1 つ目（`SandboxPort`）は Claude Code CLI をラップします。2 つ目（`SandboxManager`）は ACP アダプターと内蔵ハーネスの `bash` ツールをラップします。片方だけに与えると、ほかはラップされずにスポーンされますが、以前はそうなっていました。バックエンドのないホスト、または `--sandbox off` の下では、それらはすべてラップされずにスポーンし、サーバーは起動行でどちらのケースなのかを通知します。ACP とハーネスの `bash` は依然として環境をサニタイズします。`NoSandboxAdapter` 経由の Claude Code はホストの環境を継承します。

ひとつのサーフェスだけが意図的に除外されます。サーバーがホストするターミナルはセッションごとのバックエンド引数を受け入れ、`cc_server` はそれをホストシェルをデフォルトとして構築します。そのため、アプリから開くターミナルは、クライアントが明示的に `native` を指定しない限り、サンドボックスなしで動作します。それはサーバーホスト上の本物のシェルであり、エージェントの実行ではありません。

Linux では、`bubblewrap` がマウント名前空間を構築するため、エージェントはそこにバインドされたものだけを本当に見ます。macOS では、`sandbox-exec` が **デフォルトで許可** の Seatbelt プロファイルを適用します — 完全なデフォルト拒否のプロファイルでは、対話シェルが使えなくなります。列挙すべき dyld、XPC、Mach 呼び出しの数が非現実的だからです。そのため macOS のプロファイルは `(allow default)` から始まり、拒否を切り出します: シークレットパスの読み取り、明示的な許可を上に重ねてデフォルト拒否にリセットされた書き込みポリシー、拒否されたすべてのパスとその祖先に対する unlink の禁止（リネームで書き込み拒否を迂回できないようにするため）、常に危険なバイナリと書き込み可能ディレクトリにコピーされたものに対する exec の拒否、そしてループバックプロキシポートと DNS に制限されたネットワークです。

実際の結果はこうです: Linux ではエージェントから見えるファイルシステムが狭められ、macOS ではエージェントは依然としてホストのほとんどを _読み取る_ ことができ、あなたの登録済みチェックアウトは不可視性によってではなく、明示的な書き込みとリネームの拒否によって保護されます。どちらも名前空間レベルの分離であり、カーネルのセキュリティ境界ではありません — バックエンド自身がその能力ノートでそう述べています。

バインドマウントの集合が、エージェント間境界の引かれる場所です。オーバーレイディスパッチ（Claude Code と ACP）は、実行ごとに解決される最大 4 つのパスをマウントします: エージェントのオーバーレイ作業ディレクトリは読み書き可、エージェントの設定ディレクトリは読み取り専用、会話の共有 `repos/` ディレクトリは存在する場合に読み書き可、スペースの添付ファイルディレクトリは存在する場合に読み取り専用です。兄弟エージェントのディレクトリがマウントされることはありません。ハーネスの `bash` ラップはより狭く、実行の作業ディレクトリだけをバインドマウントします。これはハーネスのインプロセスのパスチェックがソフトウェアで強制するのと同じ形であり、両者は一致しています — ただしハーネス自身のファイルツールをカバーするのはパスチェックだけであり、それらはマウント名前空間にまったく到達しません。

あなたの登録済みチェックアウトは、その上に書き込み拒否の集合として加わります。すべてのモードで、3 つのラップされたパス（Claude Code、ACP、ハーネスの `bash`）すべてにおいてです。そして各ルールは、そのリテラルの綴りとシンボリックリンク解決後の綴りの両方で出力されます。2 つ目の綴りはおまけではありません: カーネルは拒否ルールを解決後のパスに対して照合し、macOS では解決は例外的なものではなく日常的なものです — `/tmp` は実際には `/private/tmp` であり、`/var/folders/…` は実際には `/private/var/folders/…` です — そのため、どちらかを通して到達したチェックアウトは、プロファイルが禁じているように見えながら書き込み可能でした。

サンドボックス下のネットワークは、インプロセスのループバックプロキシによって強制されるセッションごとの**ドメイン**許可リストです。外向き通信はデフォルト拒否です: ネットワークケイパビリティがオフの場合、プロキシは依然として起動しますが許可リストは空なので、外向き接続はすべて拒否されます。オンの場合、リゾルバーは、厳選されたベースライン — LLM API プロバイダー、git ホスティング、パッケージレジストリ、モデルカタログ — に加えて、エージェントの GitHub またはプッシュのケイパビリティが獲得する GitHub ドメインから許可リストを構築し、すべての接続のターゲットホストをそれに照合します。ワイルドカードは機能します（`*.example.com` はサブドメインに一致し、apex には一致しません）。別の常時拒否リストが許可リストに優先し、クラウドのメタデータエンドポイントとテレメトリのシンクをカバーします。設定_できない_のはリスト自体です: 仕様は追加ドメイン用の `egressAllowlist` フィールドとチケットドメインのフックを持ちますが、ディスパッチ経路のどこもそのどちらも埋めないため、実際にはすべての実行がベースラインとケイパビリティ由来のドメインだけを取得し、それ以上はありません。

macOS では、拒否は観測可能です: モニターが Sandbox の拒否についてシステムログを監視し、既知のノイズをフィルタリングし、リトライの嵐を重複排除し、それぞれを `SandboxViolation` として表面化します。何が試みられ、どのケイパビリティがそれを解消するのかを名指ししてです。Linux では、ラップ経路が stderr を解析して `EPERM`、`Operation not permitted`、`Permission denied` を探し、同じイベントタイプを発行します — システムログのタップはありません。それらは実行自身のイベントストリームに届くため、拒否されたシステムコールはログだけでなくトランスクリプトにも現れます。テレメトリは、ネイティブサンドボックスが実際にプロセスをラップしている間だけ存在します — バックエンドのないホストでは観測するものがありません。またこれはケイパビリティのゲーティングとは無関係です。違反は拒否されたシステムコールから生じ、ケイパビリティの参照から生じることは決してありません。

## 確認はガードレールから来るのであり、サンドボックスからではない

サンドボックスには承認の経路がありません。起動し、実行し、イベントを発行し、終了します。そこに人間が問いに答える場所はありません。スペースで確認を見るとき — このプッシュを承認、この削除を承認 — それは、アクションがそもそもランタイムに到達する_前に_、ガードレールエンジン（またはハーネスのコマンドポリシー）が提起したものです。

この順序は意図的です。システムコールの後に起きた承認は、ゲートではなく監査記録になってしまいます。フェイルクローズのルールがガードレールにある理由もここにあります。承認者が接続されていない場合、決定は何かが実行される前に下され、それは拒否です。
