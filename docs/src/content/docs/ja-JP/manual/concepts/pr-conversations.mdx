プルリクエストは、もともとコードについての会話が行われる場所です。PR 会話は、[チャットブリッジ](/ja-JP/マニュアル/コンセプト/チャットブリッジ/)が Slack をそうするのと同じように、そこを Control Center ワークスペース上のサーフェスにします。PR 上で `@usectrl`（またはワークスペースの GitHub App ボット）を @メンションする、そのレビュースレッドの中で返信する、あるいは `ai-review` ラベルを付けると、作業はその PR のレビュースペースで行われます — アプリ内で入力したものと同じ帰属とガードレールのもとで。コメントとラベルは同じ方法で制限されます。それを書いた、または付けたメンバーによってです。回答は、質問が投げかけられたレーンで、GitHub 上に返ってきます。

この機能を形づくる判断は 3 つあり、いずれもチャットブリッジがチャットに対して下したものと同じ判断を、コードホスト向けに言い直したものです。**接続がどちらの方向に張られるか**、**外部から届いたコメントを何が認可するか**、そして**どちらの側が誰に帰属されるか**です。

## ポーリングがトランスポート

GitHub がアプリに対して提供する唯一のプッシュチャネルは Webhook であり、Webhook には受信用 URL が必要です — このサーフェスが意図的に決して要求しない、まさにそのものです。そこで検出はスイープで行います。アプリのインストールごとに 1 つの別名検索が GitHub に対して、ボット（またはその短縮スラッグ）に言及している PR とレビューラベルが付いたオープン PR を問い合わせ、すでにレビュースペースを持つ PR はコメントスレッドを読み取り、すべては前回のスイープで見たものとコメント id で差分比較されます。自前の App では、1 分ごとに最大 25 件の PR をスイープします。Connect を通じる場合、呼び出しはメンバー自身の GitHub クォータを使うため、スイープは 2 分ごとに最大 10 件の PR を対象に行われ、クォータの残りが 15% を下回ったワークスペースは回復するまでスキップされます。Connect 自身が PR の内容を見ることはありません。

設計上の帰結には名前を付けておく価値があります。

- **レイテンシはイベントではなく、スイープ間隔です。** 👀 の確認リアクションは 1 回のスイープのうちに付きます。緊急のものがこれに依存することはありません。
- **コメントごとにちょうど 1 回。** コメント id は GitHub 全体で一意です。各 id は、対象として分類された瞬間、何かが作用するよりも前に記録されます。クラッシュによって失われうるのはコメントの処理であって、二重に発火することはありません。
- **オフライン中の時間は再生されるのではなく、取り戻されます。** 既読セットは永続化されるため、再起動すると停止中に届いたものが配信されます。唯一の例外は最初のスイープです。差分を取る記憶がないため、未処理のものはすべて黙って記録されます — このサーバーが存在する前に 20 件の PR にラベルを付けたオペレーターが、戻ってきたら 20 件のレビューが走っていた、ということになってはなりません。
- **ラベルはイベントではなく、集合です。** 検索が報告するのはラベルの_存在_であるため、ラベルが付いた PR が発火するのはただ一度きりです。ラベルを外してから付け直してもスイープには見えません。再実行の経路はメンションです。

検索はインストールアカウントごとに、そのオーナー自身のクライアントで 1 回実行されます。トークンには自分のインストールのリポジトリしか見えないためです — サーバー全体で 1 つの資格情報を使うと、アプリの他のインストール配下の PR をすべて黙って見落とすことになります。

## 認可するのはメンバーシップであり、コメントではない

PR コメントは作者を伴って届きます — 証明されるまでは未認証の外部アイデンティティです。サーバーは、作者の変更不可能な数値の GitHub アカウント id（変更や再利用がありうるログイン名ではなく）を、ワークスペースのメンバーの GitHub サインインに照らして解決します。この対応は TTL で再構築されます。サーバーの稼働中にも人がサインインしたり招待されたりするからです。`ai-review` ラベルの場合、解決される人物は、最後にそれを付けた人です。

3 つのチェックが順に行われ、いずれかに失敗しても何も知らせません — 何も投稿されません:

- **サインイン済みのメンバー。** アカウントは、このサーバーで GitHub にサインインした、_この_ワークスペースのメンバーのものでなければなりません
- **書き込みロール。** `viewer` と `guest` は作業を開始できません
- **プッシュ権限。** 返信には、そのメンバーのリポジトリへのアクセス権に制限された `bot` トークンを使います。サーバーがそれを発行できない場合、処理は進みません

すべてのチェックは確認リアクションの前に行われるため、部外者にはリアクションも返信も届きません。コメントが送信者以外の誰かに帰属されることはなく、部外者の言葉が、その人が見られないワークスペースに入り込むこともありません。

### クレーム

作業の前の最後の手順は 👀 リアクションで、作者自身の GitHub サインインで付けられます。GitHub は新しいリアクションには `201` を、既存のリアクションには `200` を返すため、リアクションはロックも兼ねます。同じ人物が、どちらもそのリポジトリをリンクしている 2 つのサーバーにサインインしている場合、最初にリアクションを付けたサーバーだけが作業を行います。1 つのサーバー上の複数のワークスペースから見えるコメントはそれぞれに提示され、同じクレームが決着をつけます。

## 意図的に 2 つのアイデンティティ

会話の各側は異なるアイデンティティを持ち、その違いこそがこの機能です。

- **GitHub 上では、返信はあなたの代理の自動化です。** すべての返信は、そのリポジトリ 1 つ用で、依頼したメンバーのアクセス権に制限された `bot` トークンで行われます。自前の App では、作者は App の `[bot]` アカウントです。Connect を通じる場合、共有 App のトークンはユーザートークンなので、返信は依頼したメンバーのアカウントが App を通じて行ったものとして投稿されます。いずれの場合も、すべての返信は `**Control Center** (for @login):` で始まり、誰が依頼したかを示すと同時に、ループガードも兼ねます。
- **スペース内では、問いかけはあなたのものです。** メッセージは、作者が解決されたメンバーに帰属され、エージェント実行はその人の代理として実行されます。コミットにはその人が共作者として入り、スペースの自律度とアクションガードレールは、アプリ内で入力したメッセージとまったく同じように適用されます。実行からのコードホストへの書き込みには、そのメンバーで制限された 1 リポジトリ限定のトークンが使われ、その人のサインインがそのまま渡されることはありません。

レビューの指摘事項を GitHub に公開するかどうかは、Control Center で人が下す判断のままです。メンションはレビューを_開始_できますが、公開するのは人間だけです。

## ループガードと短縮名

ボットアカウントが作成したものはすべて、どのゲートが走るよりも前に捨てられます — 具体的には自分たちのもの、そして `[bot]` サフィックスを持つすべてです。これにより、別のアプリのレビューボットがこちらのボットを呼び覚ますこともできません。また、`**Control Center** (for @` という接頭辞で始まるコメントもすべて捨てられます。Connect を通じた返信は人のアカウントで投稿されるためです。これがなければ、回答が新しいコメントとして届き、ブリッジを永遠に再トリガーし続けることになります。

`[bot]` サフィックスは、短縮形が存在する理由でもあります。GitHub はアプリアカウントのログイン名を `<slug>[bot]` に固定し、そのオートコンプリートを提供せず、`@slug` をアプリに解決することもありません — そのため、素のスラッグを受け入れるかどうかは_私たちの_マッチャーの判断であり、それを見つけるには GitHub のメンションインデックスではなく、生のコメント**本文**検索レーンが必要です。このコストは滑らかにされるのではなく、明示されます。アプリのスラッグと同じ文字列を持つ人間のユーザーは、自分自身を短縮形でメンションするたびにボットに話しかけることになります。アプリ名が特徴的であれば、この衝突は仮定の話にとどまります。

## 意図的に提供しないもの

- **自動公開はしません。** 指摘事項はレビュースペースに届き、GitHub への公開は別の、人間による操作です
- **曖昧なアイデンティティはしません。** 作者はちょうど 1 人のメンバーに解決されるか、無視されます — 推測による帰属はありません
- **自動承認はしません。** 自動化はコメントや変更のリクエストはできますが、`APPROVE` のレビューは送信前に拒否されます。承認は人の行為です
- **GitHub App の Webhook は使いません。** このサーフェスは Webhook を一切登録しないため、PR コメント用に公開する受信用 URL はありません。他の製品 Webhook（パイプライン、チケット同期）は、別の任意の設定です。
