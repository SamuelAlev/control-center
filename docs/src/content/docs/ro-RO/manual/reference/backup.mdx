Tot ce poate Control Center să copieze, să predea sau să adopte, și forma exactă a fiecărui
artefact. Pentru a face efectiv un backup, vezi
[Backup și restaurare](/ro-RO/manual/ghiduri-practice/backup-si-restaurare/); pentru motivul
pentru care persistența este împărțită astfel, vezi
[Spații de lucru și izolare](/ro-RO/manual/concepte/spatii-de-lucru/).

## Artefacte

Există trei artefacte de copiere a bazei de date, cu sfere de aplicare și politici de
ștergere diferite.

| Artefact                     | Scris de                     | Formă                                 | Acoperă                        |
| ---------------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **Snapshot de instalare**    | `server.backupNow`           | Un **director** cu marcă de timp      | Fiecare bază de date din instalare |
| **Backup de spațiu de lucru**| pipeline-ul `Workspace backup` | Director cu marcă de timp cu un `.db` | Baza de date a unui spațiu de lucru |
| **Export de spațiu de lucru**| `workspace.export`           | Un singur **fișier** `.db`            | Baza de date a unui spațiu de lucru |

Toate sunt scrise cu SQLite `VACUUM INTO`, care este sigur față de o bază de date WAL
activă: ia o tranzacție de citire, produce o copie defragmentată și consistentă
tranzacțional și nu necesită niciodată oprirea serverului.

Aceste fișiere și copiile descărcate **nu sunt criptate în repaus** de Control
Center. Transferul criptat cap la cap protejează octeții în tranzit între un client
asociat și `cc_server`-ul lui, pe conexiuni directe sau prin releu. Protejează
separat stocarea locală și copiile din afara mașinii; serverul și orice destinatar
autorizat pot citi fișierele bazei de date.

## Structura snapshot-ului

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Structura oglindește exact directorul de date activ, ceea ce face ca restaurarea unei
instalări să fie o simplă copiere la loc, nu o translație. Numele directorului este marca
de timp UTC cu `:` și `.` înlocuite cu `-`, deci este sigur pentru sistemul de fișiere pe
Windows și se sortează cronologic ca un șir simplu.

Backup-urile programate de spațiu de lucru se află separat la
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Fiecare are un `manifest.json` pentru acel singur fișier și nu are `global.db`; nu sunt snapshot-uri de instalare. O restaurare păstrează în același loc baza de date pe care o înlocuiește, ca `<timestamp>-pre-restore`.
Pasul de retenție al pipeline-ului săptămânal elimină doar backup-urile propriului
spațiu de lucru mai vechi decât vârsta configurată (30 de zile implicit);
snapshot-urile de instalare create manual nu sunt niciodată rotite de acel pas.
`server.listBackups` listează doar snapshot-uri de instalare, inclusiv pe cele
neverificate; `workspace.listBackups` listează backup-urile programate ale unui spațiu de
lucru.

Ștergerea unui spațiu de lucru lasă acest director pe loc. Programul spațiului de lucru se
oprește odată cu el, așa că nimic nu mai rotește acele backup-uri, iar ele rămân până când
proprietarul instalării le elimină. `server.listOrphanedBackups` le raportează.


### `manifest.json`

| Câmp                       | Tip             | Semnificație                                                              |
| -------------------------- | --------------- | ------------------------------------------------------------------------- |
| `format`                   | int             | Formatul manifestului. În prezent `2`                          |
| `created_at`               | ISO-8601 UTC    | Când a fost făcut snapshot-ul                                              |
| `global` | object | Înregistrarea lui `global.db`. Lipsește dintr-un backup programat de spațiu de lucru |
| `workspaces[]`             | array           | O înregistrare pentru fiecare spațiu de lucru capturat                          |
| `workspaces[].workspace_id`| string          | Spațiul de lucru pe care îl conține acest fișier                           |
| `skipped_workspaces[]`     | array           | Spații de lucru pe care backup-ul **nu** le poate captura |
| `skipped_workspaces[].workspace_id` | string | Spațiul de lucru care a fost lăsat afară |
| `skipped_workspaces[].reason` | string | `no_file`, `damaged` sau `failed` |

`global` și fiecare înregistrare din `workspaces[]` înregistrează un fișier copiat, măsurat pe copie după ce a fost scris:

| Câmp | Tip | Semnificație |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | string          | Cale relativă la rădăcina snapshot-ului: `global.db` sau `<workspaceId>/workspace.db`      |
| `bytes`       | int             | Dimensiunea copiei                                                  |
| `sha256` | string | SHA-256 al copiei, în hexazecimal cu litere mici |
| `quick_check` | string | Ce a spus `quick_check` din SQLite despre copie: `ok`, sau constatarea lui |
| `user_version` | int | Versiunea schemei copiei |
| `application_id` | int | `application_id` din SQLite al copiei |

Un spațiu de lucru este omis când este înregistrat, dar nu s-a scris niciodată în el (`no_file`), când baza lui de date nu trece verificarea de integritate (`damaged`; o copie deteriorată nu se ia niciodată), sau când copia lui sau verificarea acelei copii a eșuat (`failed`). În ambele cazuri, snapshot-ul se finalizează totuși, iar manifestul numește ce lipsește. Manifestul se scrie ultimul.

### Completitudine

`server.listBackups` raportează un indicator `complete` pentru fiecare snapshot. Acesta este fals când manifestul lipsește, nu poate fi analizat sau are alt format, când un fișier pe care îl numește lipsește sau are altă dimensiune, ori când o copie nu a trecut verificarea ei. Aplicația arată un astfel de snapshot ca **Neverificat**. Snapshot-urile făcute înainte de formatul `2` se află în această stare.

Un snapshot neverificat este totuși listat, pentru că un snapshot pe care un operator nu îl
vede este un snapshot despre care crede că îl are. Când manifestul nu poate fi citit,
listarea se bazează pe structura propriu-zisă și raportează orice fișiere
`<workspaceId>/workspace.db` găsește — acelea rămân adoptabile individual prin
`workspace.import`, chiar dacă snapshot-ul în ansamblu nu poate restaura o instalare.

Un snapshot listat sau un backup programat poartă `pinned_reason: "last_good_copy"` câtă vreme păstrează cea mai recentă copie verificată a unui spațiu de lucru a cărui bază de date activă este deteriorată. Pasul de retenție o sare până când spațiul de lucru respectiv este restaurat.

## Ce nu conține un backup

Ambele artefacte sunt **doar baze de date**. Un director de spațiu de lucru conține mai
mult decât baza lui de date, iar nimic din rest nu călătorește:

| Cale                                | Într-un snapshot? | Într-un export de spațiu de lucru? |
| ----------------------------------- | ----------------- | ---------------------------------- |
| `global.db`                         | Da                | Nu                                 |
| `<workspaceId>/workspace.db`        | Da                | Da (chiar *este* fișierul)         |
| `<workspaceId>/code_index.db`       | Nu                | Nu                     |
| `<workspaceId>/blobs/`              | Nu                | Nu                                 |
| `<workspaceId>/skills/`             | Nu                | Nu                                 |
| `<workspaceId>/agents/`             | Nu                | Nu                                 |
| `<workspaceId>/chat_credentials/`   | Nu                | Nu                                 |
| `<workspaceId>/spaces/<spaceId>/`   | Nu                | Nu                                 |
| `<workspaceId>/pr_clones/`          | Nu                | Nu                                 |
| `secrets.json`                      | Nu                | Nu                                 |
| `models/`                           | Nu                | Nu                                 |
| `meetings/<meetingId>/`             | Nu                | Nu                                 |
| `rigs/`                             | Nu                | Nu                                 |
| `_agent_hooks/`                     | Nu                | Nu                                 |

O parte din asta este de unică folosință — `spaces/` conține worktree-uri copy-on-write care sunt reprovisionate din repo-uri, `pr_clones/` este un cache, `code_index.db` este reconstruit, `models/` se descarcă din nou, `rigs/` este stare de mașină. O parte nu este: `blobs/` conține imaginile lipite spre care indică rânduri din baza de date, `skills/` și `agents/` conțin fișierele cu care rulează un agent, iar `secrets.json` conține fiecare cheie de asociere, acreditare de provider și setare SSO din instalare. Vezi
[Backup și restaurare](/ro-RO/manual/ghiduri-practice/backup-si-restaurare/#copiază-backup-urile-în-afara-mașinii)
pentru acoperirea restului.
:::note[Secretele rămân în afara bazelor de date]
`workspace.db` este întregul spațiu de lucru: conversații, jurnale de rulare, legăturile cu repository-urile, definițiile de medii și membrii. Token-urile webhook ale pipeline-urilor și secretele webhook ale sincronizării de tichete se află în `secrets.json`: baza de date conține o referință la fiecare, iar indexul de rute conține un hash cu cheie al fiecărui token. Un spațiu de lucru restaurat pe o altă instalare nu primește deci niciun webhook până când trigger-ele lui nu sunt salvate din nou acolo. Autentificările la provideri, cheile dispozitivelor și secretele utilizatorilor se află în `global.db` și `secrets.json`.
:::

:::note[Token-urile de chat rămân deliberat pe dinafară]
Faptul că `chat_credentials/` stă lângă baza de date, nu în ea, este motivul pentru care
un spațiu de lucru predat altcuiva nu conține token-uri de bot active. Vezi
[referința pentru puntea de chat](/ro-RO/manual/referinta/punte-de-chat/).
:::

## Operațiuni

RPC-urile de backup la nivel de instalare și exportul/importul de spațiu de lucru sunt
numai pentru `fullClient`: un telefon asociat nu le poate declanșa. Toate lipsesc complet
— nu sunt refuzate, lipsesc structural — pe un server fără un port de backup configurat,
cum este serverul demo.

| Op                   | Tip         | Sferă          | Rol minim             | Argumente     | Returnează                    |
| -------------------- | ----------- | -------------- | --------------------- | ------------- | ----------------------------- |
| `server.backupNow`   | modificare  | Instalare      | **proprietar** al instalării | niciunul | `{ok, path}`             |
| `server.listBackups` | citire      | Instalare      | **proprietar** al instalării | niciunul | `{backups: [...]}`       |
| `server.deleteBackup` | modificare | Instalare      | **proprietar** al instalării | `name`  | `{ok}`                        |
| `server.listOrphanedBackups` | citire | Instalare | **proprietar** al instalării | niciunul | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | modificare | Instalare | **proprietar** al instalării | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | citire | Spațiu de lucru | `admin` | niciunul | `{backups: [...]}` |
| `workspace.deleteBackup` | modificare | Spațiu de lucru | `owner` | `name` | `{ok}` |
| `workspace.export`   | citire      | Spațiu de lucru | `admin`              | niciunul      | `{ok, path}`                  |
| `workspace.import`   | modificare  | Spațiu de lucru | `owner`, și proprietarul serverului | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | citire | Spațiu de lucru | `owner`, și proprietarul serverului | niciunul | `{holds: [...]}` |
| `workspace.importHolds.resolve` | modificare | Spațiu de lucru | `owner`, și proprietarul serverului | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | modificare  | Instalare*     | `owner`              | `id`          | rând de registru marcat ca șters |

* `workspace.delete` nu are sferă pentru că rândul pe care îl marchează trăiește în
registrul global; handler-ul lui verifică apartenența apelantului la spațiul de lucru
numit și cere `owner`.

`path` din fiecare răspuns este o cale pe **hostul serverului**.

`server.listOrphanedBackups` returnează o intrare pentru fiecare spațiu de lucru care nu
mai este activ: `workspace_id`, `workspace_name` când registrul îl mai cunoaște și
`backups`. Un spațiu de lucru șters nu mai poate trece de o verificare a rolului în
spațiul de lucru, așa că backup-urile lui aparțin proprietarului instalării.
`server.deleteOrphanedBackup` refuză un spațiu de lucru activ, ale cărui backup-uri rămân
în spatele `workspace.deleteBackup` și al rolurilor proprii acelui spațiu de lucru. Ambele
operațiuni de ștergere acceptă doar numele unui director cu marcă de timp din listă, nu o
cale.

`workspace.importHolds.list` returnează ce a reținut o importare. Fiecare reținere are un `id`, un `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` sau `invite`), `payload`-ul pe care l-ar pune înapoi, `imported_at` și `source_install_id`. `workspace.importHolds.resolve` cu `accept: true` o acordă din nou, iar cu `false` o elimină. `applied` este false când cel sau ceea ce era destinatarul concesiunii nu mai este în spațiul de lucru.

:::note[Un snapshot al întregii instalări este restricționat la proprietar pe ambele canale]
`server.backupNow`, `server.listBackups` și `server.deleteBackup` cer **proprietarul**
instalării (`ServerAuthority.serverOwner`), aceeași poartă ca `GET /backup/snapshot`. Un
snapshot capturează baza de date a fiecărui spațiu de lucru, așa că a fi admin al unui
spațiu de lucru nu este suficient pentru a le administra pe celelalte. Ștergerea acceptă
doar numele directorului cu marcă de timp din listă, nu o cale arbitrară de server, și
elimină întregul snapshot (inclusiv snapshot-urile neverificate). Exporturile per spațiu
de lucru și descărcările backup-urilor programate rămân la adminul spațiului de lucru.
:::

:::note[Restaurarea este a proprietarului serverului]
`workspace.import` și `POST /backup/restore` fac serverul să adopte un fișier de bază de date ale cărui rânduri le tratează apoi ca proprii: legăturile de repo-uri și cine le-a făcut, definițiile de medii care rulează pe gazdă, căile de worktree și de jurnale. De aceea ambele cer proprietarul serverului (`ServerAuthority.serverOwner`), care trebuie să fie și proprietarul spațiului de lucru. Oricine altcineva, și fiecare apelant pe o gazdă fără proprietar înregistrat, este refuzat cu `server_owner_required`. Niciun trigger, view, coloană sau constrângere adusă de fișier nu este adoptată.
:::

### Răspunsul `server.listBackups`

Cel mai nou primul, sortate după numele directorului (care este marca de timp, deci ordinea
se păstrează chiar și pentru un snapshot al cărui manifest nu a putut fi citit).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` este omis când manifestul nu a putut fi citit. `bytes` de la nivelul superior
este dimensiunea reală pe disc a întregului director, nu suma din manifest — întrebarea pe
care o pune un operator care curăță snapshot-uri este cât costă directorul, nu ce
intenționa backup-ul să scrie.

Fiecare `workspaces[].path` este exact ce ia `workspace.import` ca `source_path`. Acest
lucru este deliberat: „restaurează acest spațiu de lucru din acest snapshot” *este*
operațiunea de import, așa că cele două nu pot ajunge la tratamente diferite ale aceluiași
fișier.

### Validarea `workspace.import`

Înainte de a se înlocui ceva, fișierul candidat este copiat într-un fișier de staging alături de țintă și verificat acolo. Un refuz nu atinge nimic și își poartă tipul ca `data.kind`.

| Condiție                                          | Rezultat                                                        |
| ------------------------------------------------- | --------------------------------------------------------------- |
| Fișierul nu există | Refuzat, `import.missing_source` |
| Nu este o bază de date SQLite care poate fi citită, sau nu trece `quick_check` | Refuzat, `import.damaged` |
| Provine dintr-un snapshot, iar SHA-256 lui diferă de cel din manifest | Refuzat, `import.checksum_mismatch` |
| L-a scris o versiune mai nouă a serverului | Refuzat, `import.newer_schema` |
| Un alt `application_id`, sau lipsește `workspace_meta` | Refuzat, `import.foreign_file` |
| Nu poate fi adus la schema acestui server | Refuzat, `import.schema_mismatch` |
| Webhook-urile sau invitațiile lui sunt deja direcționate către alt spațiu de lucru | Refuzat, `import.route_conflict` |
| Id-ul de spațiu de lucru înregistrat ≠ cel al țintei | **Permis**. Rândurile lui sunt reasociate țintei. Așa se duplică un spațiu de lucru sau se restaurează sub un id nou |
| Id-ul de instalare înregistrat ≠ această instalare | **Permis**. Id-urile de utilizator ale lui aparțin acelei instalări și nu se vor rezolva aici |

La acceptare, fișierul de staging este adus la schema acestui server și trebuie apoi să corespundă exact. Concesiile pe care un fișier nu și le poate da singur sunt scoase din el: aprobările de a rula o definiție de mediu pe gazdă sunt șterse, iar regulile de acțiune care permit sau cer confirmare, concesiile de exec în sandbox, concesiile de repository peste simplul citit, rolurile peste membru și invitațiile către aceste roluri devin rețineri pe care proprietarul serverului le examinează. Cel care importă păstrează sau primește rolul de proprietar. Baza de date înlocuită este păstrată ca backup programat numit `<timestamp>-pre-restore`, fișierul de staging este mutat la locul lui cu conexiunile spațiului de lucru închise, `code_index.db` este șters ca să fie reconstruit, iar indecșii FTS sunt reconstruiți.

## Rute de transfer

Operațiunile de export/import și de listare a snapshot-urilor de mai sus vorbesc în
căi de pe partea de server, ceea ce este un răspuns complet doar când serverul este
propria ta mașină. Aceste rute în formă de HTTP transportă octeții de backup **în
interiorul aceluiași tunel de resurse autentificat și criptat cap la cap** ca alte
resurse sensibile, fie că conexiunea RPC este directă, fie intermediată. Nu sunt
puncte finale publice de transfer de fișiere HTTP: o cerere către una dintre ele pe
listenerul public returnează `426 Upgrade Required`, chiar și de pe loopback. În
tunelul criptat, dispozitivul autentificat cu Noise trebuie să corespundă cu `d`;
handlerul verifică în plus semnătura dispozitivului peste șirul său țintă folosind
PSK-ul de asociere și rolul de mai jos.

| Rută                    | Metodă | Interogare      | Țintă semnată                  | Necesită                |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **admin** al spațiului de lucru |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **proprietar** al instalării |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **admin** al spațiului de lucru; **proprietar** al instalării după ce spațiul de lucru este șters |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **proprietar** al instalării care este și **proprietar** al spațiului de lucru (`403` cu `server_owner_required` altfel) |

`w` este un id de spațiu de lucru, `n` un nume de director de snapshot sau de backup
programat, `d` id-ul dispozitivului apelant, `s` semnătura. Pe `/backup/snapshot`, `n` este
rezolvat față de listarea backup-urilor, nu concatenat la rădăcina backup-urilor, așa că
ruta nu poate fi îndreptată spre un director pe care listarea nu l-ar fi arătat. Pe
`/backup/stored` trebuie să fie un nume de marcă de timp, iar fișierul trebuie să fie un
fișier real din directorul de backup propriu al acelui spațiu de lucru.

| Status | Cauză                                                                              |
| ------ | ---------------------------------------------------------------------------------- |
| `400`  | Lipsește un parametru de interogare obligatoriu, numele unui backup este invalid, corpul unui upload este gol, sau fișierul încărcat a fost refuzat (corpul este `{error, kind}` cu o valoare `import.*`) |
| `403`  | Dispozitiv necunoscut sau revocat, semnătură greșită sau apelantul nu are rolul      |
| `404`  | Nu există un port de backup pe acest host sau fișierul de snapshot, de backup sau de spațiu de lucru numit nu există |
| `405`  | `/backup/restore` apelat cu orice altceva decât `POST`                               |
| `413`  | Corpul upload-ului depășește 8 GiB, după content-length declarat sau după octeții citiți efectiv |
| `426`  | Orice cerere directă către o rută de transfer pe listenerul HTTP public; folosește tunelul de resurse criptat al unui client asociat |
| `500`  | Exportul sau arhivarea a eșuat pe partea de server                                   |

Toate cele trei descărcări răspund cu `Cache-Control: no-store` și `Accept-Ranges: none`.
`/backup/workspace` și `/backup/snapshot` creează o copie **proaspătă** la fiecare cerere și
o șterg după ce a fost transmisă în flux, așa că un răspuns din cache sau reluat ar îmbina
octeți din două exporturi diferite într-un singur fișier care pare valid și nu este.

`/backup/stored` este excepția: transmite în flux un backup programat ca
`<workspaceId>-<name>.db` și lasă fișierul pe loc, pentru că acel fișier este backup-ul.

`/backup/snapshot` returnează `<name>.zip`, cu intrări relative la rădăcina snapshot-ului,
astfel încât dezarhivarea reproduce `manifest.json` + `global.db` +
`<workspaceId>/workspace.db`. Intrările sunt scrise în ordine sortată, așa că două arhive
ale aceluiași snapshot sunt aceeași arhivă.

`/backup/restore` transmite corpul direct într-un fișier de pregătire, în loc să îl pună
în buffer, îl limitează înainte și în timpul citirii și șterge fișierul pregătit pe
**fiecare** cale de ieșire, inclusiv la un refuz.

::::caution[Conexiunea directă și releul folosesc același transfer criptat]
Releul transportă cereri de resurse, răspunsuri transmise în flux și octeți de
upload ca text cifrat; nu poate citi conținutul backup-urilor. O cale de pe partea
de server rămâne o cale pe gazda serverului, nu un fișier pe releu. Accesul
necesită în continuare dispozitivul asociat, semnătura țintei și rolul aplicabil
de spațiu de lucru sau de instalare. Niciunul dintre cele două transporturi nu
criptează în repaus fișierele de backup rezultate.
::::

## Căi și limite

| Element                        | Valoare                                                      |
| ------------------------------ | ------------------------------------------------------------ |
| Snapshot-uri                   | `<dataDir>/backups/<timestamp>/`                             |
| Backup-uri programate de spațiu de lucru | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Exporturi de spațiu de lucru   | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Baza de date înlocuită printr-o restaurare | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Bazele de date așa cum erau înainte ca o actualizare să-și schimbe formatul | `<dataDir>/pre_upgrade/` și `<dataDir>/<workspaceId>/pre_upgrade/`, cele mai recente două din fiecare |
| Pregătire pentru transfer      | `<dataDir>/backups/transfer/` — un atelier, curățat de ruta care îl scrie |
| Numele arhivei de snapshot     | `<snapshot directory name>.zip`                              |
| Plafon de upload               | 8 GiB per upload criptat către `/backup/restore`             |
| Retenție                       | Snapshot-uri de instalare: ștergere manuală. Backup-uri de spațiu de lucru: pipeline săptămânal, 30 de zile implicit, sau ștergere manuală. Backup-urile unui spațiu de lucru șters: doar ștergere manuală |

Directoarele `exports/`, `transfer/` și `workspace-backups/` nu sunt snapshot-uri de
instalare și sunt excluse din `server.listBackups`. Doar ultimul director are retenție
programată și doar cât timp există spațiul lui de lucru; ștergerea unui snapshot de instalare necesită acțiunea explicită a
proprietarului instalării.
