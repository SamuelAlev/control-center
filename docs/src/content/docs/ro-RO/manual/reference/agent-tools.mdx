Acestea sunt instrumentele **legate de server** pe care runtime-ul de agent integrat le înregistrează direct — server de limbaj, căutare structurală, depanator, kerneluri, scripturi ale modului cod, întrebări și controlul workerilor — spre deosebire de [instrumentele MCP](/ro-RO/manual/referinta/instrumente-mcp/) pe care le aduce prin punte și de instrumentele generice de fișiere, căutare și shell din runtime-ul harness-ului. Nu se află în registrul MCP: un client MCP extern nu le va vedea, pentru că fiecare este legat de o resursă activă de pe server — un proces de server de limbaj, un adaptor de depanare, un interpretor — care aparține unei singure rulări.

Fiecare instrument de aici este înregistrat doar când resursa din spatele lui este conectată pentru rulare — un supraveghetor de server de limbaj sau de depanare, un analizor sintactic tree-sitter, o fabrică de kerneluri, un port de întrebări, o listă de vibe. Detectarea unui server de limbaj sau a unui adaptor de depanare pentru *acest checkout* este o verificare separată, ulterioară (`status` / `adapters`): instrumentele respective rămân pe suprafață ca agentul să poată întreba de ce nu este utilizabil nimic, în loc să ghicească.

## Niveluri de aprobare

Fiecare instrument declară un nivel, iar nivelul decide **care suprafețe îl văd** — nu doar dacă solicită aprobare. Modul plan și subagenții doar în citire sunt limitați la `read`, așa că un instrument de nivel `write` sau `exec` lipsește complet din schema lor.

| Nivel   | Semnificație                           | Instrumente aici                                   |
| ------- | -------------------------------------- | -------------------------------------------------- |
| `read`  | Fără efecte secundare                  | `lsp`, `ast_grep`, `ask_user`, `repl`, cele cinci `vibe_*` |
| `write` | Modifică fișiere                       | `lsp_rename`, `ast_edit`, `resolve`                |
| `exec`  | Pornește sau controlează un proces     | `debug`, `eval`                                    |

## Direct, disponibil doar din script sau încărcat la prima utilizare

Când serverul poate rula scripturi, o rulare apelează direct câteva instrumente și ajunge la restul dintr-un script [`repl`](#repl--rulează-un-script-care-apelează-instrumentele-tale); vezi [Mod cod](/ro-RO/manual/concepte/mod-cod/#ce-instrumente-apelează-agentul-direct) pentru regula completă. Pentru instrumentele din această pagină:

| Instrument | Cu `repl` | Fără `repl` |
| ---- | ----------- | -------------- |
| `repl` | Direct | Absent |
| `ask_user` | Direct | Direct |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Doar din script | Încărcat la prima utilizare |
| `eval` | Încărcat la prima utilizare (un script nu îl poate apela) | Încărcat la prima utilizare |
| `vibe_*` | Direct în modul vibe, niciodată dintr-un script | Direct în modul vibe |

Un instrument marcat „Doar din script” se încarcă la prima utilizare în schimb, odată ce serverul nu poate rula scripturile rulării ([Când scripturile nu pot rula](/ro-RO/manual/concepte/mod-cod/#când-scripturile-nu-pot-rula)).

## `lsp` — interogări către serverul de limbaj

Înregistrat când rularea are un supraveghetor de server de limbaj și un director de lucru. Dacă un server poate răspunde cu adevărat se detectează la momentul apelului, ca o **intersecție**: trebuie să existe un marker de rădăcină *și* binarul serverului trebuie să se rezolve. Oricare dintre ele singur înseamnă că niciun server nu pornește — `status` spune asta — în loc să fie o presupunere tăcută.

Serverele vin doar din tabelul încorporat; un fișier `lsp.json` din depozit nu este citit. Într-o rulare izolată fiecare rulare are propria sesiune de server de limbaj, deci serverele pornesc din nou la fiecare rulare. Binarele locale proiectului (`node_modules/.bin`) sunt folosite doar când rularea este izolată, iar rădăcina proiectului nu se rezolvă niciodată deasupra directorului de lucru al rulării.

Pozițiile sunt adresate prin `line` plus un subșir `symbol`, niciodată prin coloană. Un model căruia i se cere o coloană ghicește, iar o presupunere greșită se rezolvă la un alt simbol de pe aceeași linie — un răspuns care pare corect, dar este despre altceva. Omiterea lui `symbol` la o acțiune de navigare este o eroare, nu o presupunere a primei coloane.

| Acțiune           | Argumente                        | Returnează                                 |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (sau `"*"`)               | Erori și avertismente; `"*"` rulează în schimb verificatorul de proiect |
| `definition`      | `file`, `line`, `symbol`         | Unde este declarat simbolul                |
| `type_definition` | `file`, `line`, `symbol`         | Unde este declarat tipul lui               |
| `implementation`  | `file`, `line`, `symbol`         | Implementările concrete                    |
| `references`      | `file`, `line`, `symbol`         | Fiecare utilizare, plafonat la 50          |
| `hover`           | `file`, `line`, `symbol`         | Semnătura și comentariul de documentație   |
| `symbols`         | `query` sau `file`               | Căutare în spațiul de lucru cu `query` (plafonat la 100); simboluri de document cu `file` (plafonat la 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Corecturile rapide oferite de server       |
| `status`          | —                                | Ce servere rulează și pentru ce rădăcini   |
| `reload`          | —                                | Repornește serverul pentru această rădăcină |

### Diagnostice la scriere

Câștigul nu este instrumentul. `write`, `edit` și `apply_patch` sunt **învelite**: după scriere, fișierul este sincronizat și salvat prin serverul de limbaj, iar doar diagnosticele **introduse recent** sunt incluse în rezultatul instrumentului. Un agent află că a stricat build-ul în momentul în care l-a stricat, fără să fie nevoit să-și amintească să întrebe.

Diagnosticele deja raportate sunt suprimate de un registru pe rulare indexat după severitate, cod și mesaj — poziția este exclusă în mod deliberat, astfel încât un diagnostic care s-a mutat doar cu patru linii mai jos să nu fie raportat din nou ca nou.

## `lsp_rename` — redenumire la nivel de proiect

Un instrument separat, de nivel `write`, pentru exact un motiv: nivelul decide vizibilitatea. Dacă redenumirea ar fi fost inclusă în `lsp`, fie i s-ar fi dat unui explorator doar în citire capacitatea de a rescrie repo-ul, fie fiecare `hover` ar sta în spatele unei solicitări de aprobare.

| Argument   | Semnificație                                |
| ---------- | ------------------------------------------- |
| `file`     | Unde se află simbolul                       |
| `line`     | Linie indexată de la 1                      |
| `symbol`   | Subșir care îl identifică pe acea linie    |
| `new_name` | Cum să fie numit                            |

## `ast_grep` — căutare structurală

Găsește cod după **formă**, nu după text. `$NAME` potrivește orice nod, `$$$NAME` potrivește o serie de noduri frați, iar `$_` este un wildcard care nu leagă nimic.

Proprietatea care îl face un potrivitor și nu o expresie regulată cu pași în plus: o metavariabilă repetată într-un singur șablon trebuie să capteze același text.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

potrivește o gardă care eliberează exact ce a testat și **nu** potrivește una care eliberează altceva.

| Argument      | Semnificație                                                |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | Un fragment de cod cu metavariabile                         |
| `path`        | Fișierul sau directorul de căutat; implicit întregul spațiu de lucru |
| `language`    | Un id de gramatică livrat (`dart`, `python`, `rust`, `c`, …). Dedus când `path` indică un fișier |
| `max_results` | Implicit 50                                                 |

:::note[Șablonul este analizat de aceeași gramatică precum fișierul]
Astfel, `dispose(x)` potrivește apelul indiferent cum este spațiat, încadrat sau comentat — și nu potrivește niciodată aceleași caractere dintr-un literal de șir sau dintr-un comentariu.
:::

:::caution[Un fragment este analizat într-un schelet, nu în gol]
`dispose(x)` analizat la nivelul superior al Dart este o *semnătură de funcție* validă. Compilatorul de șabloane încearcă o scară de contexte (instrucțiune, expresie, membru de clasă, declarație) și îl folosește pe primul care acceptă fragmentul. Un șablon pe care niciun context nu îl acceptă este raportat ca neanalizabil sintactic, în loc să fie căutat și să nu fie găsit în tăcere.
:::

## `ast_edit` — rescriere structurală, etapizată

Aceeași potrivire, plus un șablon `rewrite` în care metavariabilele sunt substituite la loc. **Nu se scrie nimic.** Modificarea este etapizată, iar rezultatul numește un `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Argument   | Semnificație                                        |
| ---------- | --------------------------------------------------- |
| `pattern`  | Ce să potrivească                                   |
| `rewrite`  | Ce să pună acolo, cu `$NAME` substituit             |
| `path`     | Domeniul; implicit întregul spațiu de lucru         |
| `language` | Id-ul limbajului                                    |

## `resolve` — aplică sau renunță la o modificare etapizată

| Argument  | Semnificație                     |
| --------- | -------------------------------- |
| `edit_id` | Din rezultatul `(proposed)`      |
| `action`  | `accept` sau `discard`           |

Fiecare fișier este comparat cu conținutul capturat în momentul etapizării, iar **orice** nepotrivire refuză întreaga modificare. O rescriere structurală aplicată parțial lasă un arbore care nu se compilează nici cu forma veche, nici cu cea nouă.

## `debug` — condu un depanator

Înregistrat când rularea are un supraveghetor de sesiuni de depanare, un director de lucru și un id de conversație. Dacă un adaptor poate porni cu adevărat se detectează la momentul apelului, după aceeași regulă de intersecție ca la serverul de limbaj (marker de rădăcină *și* binar). Nivel `exec`; nu este sigur la rulare în paralel (o sesiune este stare între apeluri, așa că un `continue` care depășește un `stack` ar citi un cadru care s-a mișcat deja).

O singură sesiune per conversație, cu un TTL strict (30 de minute). Un al doilea `launch` este refuzat în loc să îl înlocuiască în tăcere pe primul. Într-o rulare izolată sesiunea își păstrează sandbox-ul între ture până se încheie, deci cel mult acele 30 de minute.

| Op            | Argumente                     | Note                                           |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Ce adaptoare sunt utilizabile aici și de ce nu |
| `status`      | —                             | Dacă rulează o sesiune și unde s-a oprit       |
| `breakpoints` | `file`, `lines[]`             | `lines` gol șterge fișierul. Pot fi stabilite **înainte** de lansare |
| `launch`      | `program`, `args[]`           | Pornește programul oprit la punctele tale de întrerupere |
| `attach`      | `port`                        | Se conectează la un proces depanat care rulează deja pe unul dintre porturile redirecționate ale rulării; orice alt port este refuzat înainte să pornească ceva |
| `continue`    | `thread_id?`                  | Rulează până la următoarea oprire               |
| `pause`       | `thread_id?`                  | Îl oprește acolo unde se află                  |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Avansează cu un pas                    |
| `threads`     | —                             | Id-urile și numele firelor de execuție         |
| `stack`       | `thread_id?`                  | Cadre, plafonate la 30                         |
| `scopes`      | `frame_id`                    | Scopuri pe un cadru, fiecare cu o `reference`  |
| `variables`   | `reference`                   | Copii, plafonate la 50, valori plafonate la 400 de caractere |
| `evaluate`    | `expression`, `frame_id?`     | Evaluat în scopul propriu al cadrului          |
| `output`      | —                             | stdout/stderr-ul procesului depanat, mărginit  |
| `terminate`   | —                             | Încheie sesiunea și omoară adaptorul           |

### Adaptoare

| Id        | Comandă                    | Markere de rădăcină                             |
| --------- | -------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`       | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                 | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                  | `go.mod`                                        |

`debugpy` preferă un `.venv/bin` sau `venv/bin` local proiectului în locul lui `$PATH` când rularea este izolată: un python din `$PATH` este un mediu diferit, iar atașarea din cel greșit eșuează într-un mod care se citește ca un cod stricat. Neizolat folosește doar `$PATH`, deci un depozit nu poate alege interpretorul care rulează pe gazdă.

## `repl` — rulează un script care apelează instrumentele tale

Prezent pe fiecare rulare când serverul poate rula scripturi ([Când o rulare are `repl`](/ro-RO/manual/concepte/mod-cod/#când-o-rulare-are-repl)). Scriptul este JavaScript simplu, corpul unei funcții async, și rulează într-un interpretor nou, blocat, în propriul proces: fără acces la sistemul de fișiere, la rețea, la procese sau la module. `repl` în sine aparține nivelului `read`, pentru că fiecare apel de instrument făcut de script este verificat separat. Este disponibil și pe endpoint-ul MCP, pentru rulările de agent pe un server care poate rula scripturi.

| Argument | Semnificație |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | Scriptul. Cel mult 256 KiB |
| `description` | Obligatoriu. O etichetă scurtă pentru rândul din transcriere |
| `timeout_ms` | Opțional. O limită de timp mai scurtă decât cea a spațiului de lucru; niciodată una mai lungă |
| `max_output_tokens` | Opțional. Un buget de ieșire mai mic decât cel al spațiului de lucru; niciodată unul mai mare |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

Descrierea `repl` îi spune agentului: „Un instrument care nu este unul dintre instrumentele tale directe nu are o definiție în această cerere. Înainte de primul apel către unul dintre ele, caută-l cu `describeTool(name)` sau `searchTools(query)`, cu excepția cazului în care forma exactă a apelului i-a fost deja arătată în această conversație.”

`describeTool(name)` returnează descrierea unui instrument, declarația sa, schemele de intrare și de ieșire și nota sa despre rezultat, atunci când există una: ce primește un script de la un apel încheiat, în propriile cuvinte ale instrumentului. Descrierea `repl` listează notele instrumentelor directe pe care un script le poate apela. Un rezultat care este text JSON ajunge parsat, cu excepția cazului în care conține mai mult de 131.072 de valori: atunci ajunge ca text, iar scriptul îl parsează cu `JSON.parse`. Textul unui rezultat de la un instrument al unui server MCP extern este tăiat la 262.144 de caractere, iar textul tăiat nu mai poate fi parsat.

- `tools.<name>(args)` apelează un instrument prin același filtru, aceleași guardrail-uri și aceeași aprobare ca un apel direct și eșuează cu o eroare când este refuzat sau când eșuează. Apelurile doar de citire pot rula împreună; apelurile care modifică ceva rulează pe rând, în ordinea în care le-a făcut scriptul. Cât timp unul dintre apelurile sale așteaptă o persoană, scriptul nu pornește niciun alt apel.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` și `describeNamespace(name)` găsesc instrumente, inclusiv pe cele ale serverelor MCP conectate. Un instrument din afara setului direct, pe care un script îl poate apela, este apelabil doar dintr-un script; apelându-l direct se returnează cum poate fi apelat din `repl`. Odată ce serverul nu poate rula scripturile rulării, un astfel de instrument se încarcă la prima utilizare în schimb.
- Căutările sunt limitate: o interogare de cel mult 1.024 de caractere, un nume sau namespace de cel mult 256, `limit` de la 0 la 50 și cel mult 200 de căutări care iau în total 2 secunde din timpul serverului pe script, în timp ce toate scripturile unui spațiu de lucru împart 2 secunde de timp de căutare, care se refac cu un sfert de secundă pe fiecare secundă; dincolo de oricare dintre limite, căutările următoare sunt respinse. Într-un catalog foarte mare, descrierile din `ALL_TOOLS` împart în mod egal aproximativ un milion de caractere, iar una tăiată se termină în `…`; `describeTool` returnează întotdeauna descrierea completă. Un tip prea mare pentru a fi afișat apare ca `unknown /* too large to show */`, iar un nume necunoscut primește ca răspuns cele mai apropiate nume.
- Instrumentele sunt grupate în namespace-uri: `builtin` (instrumentele proprii ale harnessului), `control-center` (instrumentele Control Center) și câte unul pentru fiecare server MCP conectat, numit după server. Un server numit `builtin`, `control-center` sau `script`, ori al cărui nume începe cu `external-`, în orice amestec de majuscule și minuscule și cu sau fără spații în jurul lui, este listat ca `external-` urmat de numele său, iar niciun instrument nu se află vreodată în `script`.
- Vine înapoi doar ce returnează scriptul sau transmite către `text()`, `image()` sau `console.*`. Ieșirea peste buget păstrează începutul și sfârșitul, iar `read_output` citește restul.
- `store(key, value)` / `load(key)` păstrează valori JSON pentru scripturile ulterioare ale aceleiași conversații și ale aceluiași agent, salvate doar când scriptul se încheie. Scripturile unui subagent nu au depozit.
- `await tools.ask_user(...)` pune o întrebare, iar răspunsul ei este adăugat și în rezultat. `sleep(ms)`, `setTimeout`, `limits()` și `models.embed` / `rank` / `classify` (embedding-uri pe dispozitiv) sunt disponibile și ele.
- `describeTool(name)` și `searchTools(query)` răspund și pentru funcțiile proprii ale scriptului, care nu sunt instrumente: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` și `models.*`, sub spațiul de nume `script`.
- Nu pot fi apelate dintr-un script: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` și verbele `vibe_*`.
- Un script citește trecutul propriei rulări: `history({start, role, tool, limit})` parcurge transcriptul conversației (cel mult 50 de rânduri la un apel; trece `next_start` din pagina anterioară ca `start`), `outputs()` listează ieșirile de unelte stocate pentru această conversație și agent, iar `loadOutput(handle)` citește 16.384 de caractere dintr-una. `storedKeys()` listează cheile stocate cu dimensiunile lor. `keep(value, label)` stochează o valoare mare ca ieșire pe care o poate citi un script ulterior sau `read_output`, salvată doar când scriptul se încheie (1 MiB o valoare, 64 de valori și 16 MiB pe rulare). `limits().returnBudgetChars` spune cât din bugetul de ieșire a mai rămas. O rulare doar în citire (o revizuire de obiectiv) poate citi, dar nu poate stoca sau păstra. Pe Claude Code și ACP, `history()` funcționează, iar `outputs()`, `loadOutput()` și `keep()` refuză, pentru că Control Center nu păstrează ieșiri de unelte ale acelor rulări.
- O eroare de la un timeout, o depășire a ieșirii sau a limitei de apeluri spune cum se remediază.

O rulare execută un singur script pe rând. Limitele și ce se întâmplă la fiecare sunt pe pagina [mod cod](/ro-RO/manual/concepte/mod-cod/#limite); fiecare script este înregistrat la **Observabilitate → Execuții de cod**.

## `eval` — interpretoare persistente

O celulă Python sau JavaScript ale cărei variabile, importuri și date încărcate supraviețuiesc între apeluri. Nivel `exec`; nu este sigur la rulare în paralel. Nu poate fi apelată dintr-un script `repl`, iar o celulă nu poate apela instrumentele rulării: pentru a apela instrumente din cod, folosește [`repl`](#repl--rulează-un-script-care-apelează-instrumentele-tale).

| Argument      | Semnificație                                     |
| ------------- | ------------------------------------------------ |
| `code`        | Celula                                           |
| `description` | Obligatoriu. 5–10 cuvinte pentru eticheta din transcriere |
| `language`    | `python` (implicit) sau `javascript`             |
| `reset`       | Elimină interpretorul și pornește curat de la început |

- Ultima expresie este afișată așa cum face un notebook.
- `display()` funcționează, un DataFrame pandas se randează ca tabel, iar o figură matplotlib revine ca o **imagine pe care transcrierea o afișează**.
- Idiomurile IPython pe care lumea le tastează reflex — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — sunt rescrise în cod simplu. `%pip` elimină și intrările din `sys.modules`, așa că următorul `import` vede ce tocmai a fost instalat.
- O celulă care tipărește mai mult decât bugetul ei de ieșire păstrează primele trei sferturi și ultimul sfert, cu o linie care spune câte caractere și imagini au fost eliminate.
- Când interpretorul a murit fără să i se fi cerut, următoarea celulă este anunțată o dată că variabilele ei de dinainte nu mai există.

:::note[Unde rulează kernelul]
În mediul izolat al conversației când aceasta are unul, altfel în sandbox-ul rulării de pe gazdă. Cu sandbox-ul oprit sau indisponibil rulează neizolat, iar `eval` cere aprobarea rulării pe gazdă. Nu pornește un mediu izolat ca să ajungă acolo — aceeași regulă care împiedică pornirea automată a unui tab de stație.
:::

## `bash` în fundal

`bash` cu `run_in_background: true` pornește comanda și returnează imediat cu un handle (`b1`, `b2`, …) în loc să aștepte. Agentul continuă să lucreze sau își încheie tura și este trezit când comanda iese.

| Argument | Semnificație |
| ------------------- | ------- |
| `run_in_background` | `true` ca să pornească și să returneze imediat |
| `timeout_seconds` | Secunde până când comanda este oprită: implicit 600, cel mult 3.600 |
| `notify` | Opțional. Un tipar simplu; fiecare linie de ieșire care se potrivește este trimisă agentului cât timp rulează comanda (cum ar fi `listening on\|FAILED`) |

- Cel mult 4 comenzi de fundal rulează deodată într-o rulare. Fiecare este oprită la timeout și la încheierea rulării, împreună cu fiecare proces pe care l-a pornit.
- Când o comandă iese, agentul primește o notificare cu codul de ieșire, ultimele 2.000 de caractere de ieșire și un handle `read_output` pentru rest.
- Un agent a cărui singură muncă rămasă este o comandă de fundal așteaptă fără să cheme modelul, iar supraveghetorul de liniște al rulării se oprește cât timp așteaptă.
- `bash_output(handle)` citește starea unei comenzi și ieșirea recentă; `bash_kill(handle)` o oprește. Ambele spun când rezultatul fusese deja livrat.
- Un script nu poate porni o comandă de fundal. Claude Code are propriul Bash de fundal; Control Center păstrează rularea deschisă cel mult 10 minute după tura care a lăsat o sarcină în curs.

## `compact` — eliberează spațiu în fereastra de context

Compactează contextul mai vechi al conversației înainte de următorul apel al modelului, păstrând ce numește `focus` (cel mult 1.000 de caractere). Cele mai noi ture rămân neschimbate. Linia de buget per tură a agentului arată utilizarea contextului la 70, 80 și 90%, iar unealta merită apelată după circa 70% înainte de o nouă fază lungă de lucru. Hook-ul `preCompact` al proprietarului serverului poate adăuga la focalizare ([Hook-uri de shell](/ro-RO/manual/referinta/configurarea-agentilor/#hook-uri-de-shell)). După o compactare, serverul adaugă un bloc „Still in flight”: obiectivul, treziri în așteptare, întrebări deschise, comenzi de fundal, lista de verificare și cheile stocate, fiecare cu apelul care le recuperează.

## `ask_user` — pune o întrebare omului

Nivel `read`. **Singurul** mod în care o rulare cere ceva operatorului. Afișează un card numerotat în conversație și blochează până când cineva răspunde, omite sau întrebarea expiră. Nu scrie niciodată întrebarea ca mesaj de chat — asta încheie tura.

| Argument       | Semnificație                               |
| -------------- | ------------------------------------------ |
| `question`     | Ce să întrebi                             |
| `context`      | Opțional: de ce întrebi și ce depinde de răspuns |
| `options[]`    | Opțiuni, fiecare `{label, description?}`   |
| `allow_free_text` | Dacă se acceptă un răspuns tastat       |
| `multi_select` | Dacă se pot alege mai multe opțiuni        |

O omitere este un succes: continuă pe baza unei presupuneri declarate și nu mai întreba din nou. Expirarea este o eroare cu aceeași instrucțiune. Solicitările de permisiune („pot să fac asta?”) sunt o poartă separată și se afișează ca același card în conversație.

Înregistrat doar când există atât un port de întrebări, cât și un spațiu țintă. Fără un om atașat, apelul **eșuează** în loc să blocheze la nesfârșit — aceeași postură cu eșec închis pe care o adoptă un `prompt` de guardrail când nu este conectat niciun aprobator.

## `vibe_*` — dirijarea workerilor din fundal

Înregistrate doar cât timp [modul vibe](/ro-RO/manual/ghiduri-practice/dirijeaza-workeri-din-fundal/) este activ. Toate cinci sunt de nivel `read`: poarta aparține instrumentelor workerului, acolo unde se produce de fapt editarea.

| Instrument   | Argumente                                | Note                                        |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | Se întoarce imediat; workerul rulează în continuare |
| `vibe_send`  | `worker_id`, `message`                   | Adaugă la brief și rulează din nou          |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | Blochează până când se stabilizează         |
| `vibe_kill`  | `worker_id`                              | Îl oprește                                  |
| `vibe_list`  | —                                        | Nivel, stare, timp scurs și ultimul rezultat |

`tier` este `fast` (muncă mecanică cu o specificație clară) sau `good` (proiectare, judecată sau revizuirea rezultatului unui worker `fast`).
