:::caution[Dacă o rulare este sandboxată depinde de gazdă]
`cc_server` decide o singură dată la pornire cum rulează agenții pe această gazdă, iar decizia rămâne valabilă până la repornire:

- **În sandbox** (`native`): sonda a găsit un backend și `--sandbox` nu este `off`. Ambele cusături de trimitere sunt învelite: CLI-ul Claude Code prin portul de sandbox, iar ACP plus instrumentul `bash` al harness-ului încorporat prin managerul de sandbox.
- **Oprit** (`off`): proprietarul serverului l-a pornit cu `--sandbox off`. Rularea agenților fiecărui membru are loc fără izolare pe această mașină, indiferent cine a pornit-o.
- **Indisponibil** (`unavailable`): sandbox-ul este pornit, dar sonda nu a găsit niciun backend (**Windows întotdeauna**, și Linux sau WSL2 fără `bwrap` și `socat`). O rulare pornește doar dacă persoana responsabilă pentru ea este [proprietarul](/ro-RO/manual/concepte/autorizare/#proprietarul-serverului) serverului: persoana care a cerut-o sau, pentru automatizare, persoana de care este legată. Rularea oricui altcuiva este refuzată înainte ca o credențială să fie emisă, un lease să fie luat sau un proces să pornească. Când nu este înregistrat niciun proprietar, nu pornește nicio rulare.

O rulare refuzată eșuează cu codul `sandbox_unavailable`. Aplicația o afișează ca **Agenții au nevoie de un sandbox pe acest server**: „Acest server nu are sandbox, deci doar proprietarul lui poate rula aici agenți. Proprietarul poate instala sandbox-ul sau poate dezactiva sandboxing-ul pentru toată lumea.”

O rulare care pornește fără sandbox (sub `off` sau rularea proprie a proprietarului sub `unavailable`) rulează direct pe gazdă. ACP și instrumentul `bash` al harness-ului pornesc în continuare cu sanitizare a mediului; Claude Code trece prin `NoSandboxAdapter` și moștenește mediul gazdei. Granițele rămase sunt worktree-ul propriu al rulării (copy-on-write acolo unde este livrat `rift`; `git worktree` pe Windows), un token de forge doar pentru citire, intermediat la fiecare lansare și revocat la desființare, push-uri care trebuie să treacă regula de push la gateway-ul rulărilor de agenți, politica de comenzi per mod, [guardrail-urile unificate de acțiuni](/ro-RO/manual/concepte/guardrail-uri/) (cu închidere la eșec), sanitizarea mediului pe căile ACP și `bash` ale harness-ului, și suprafața de instrumente pe care o permite modul său.

Instrumentele de fișiere în proces ale harness-ului (read, write, edit, apply patch, search, find, search_files) sunt în afara sandbox-ului pe orice gazdă: rulează în procesul serverului, așa că doar `bash` este învelit.

Gazda nu este niciodată o soluție de rezervă pentru un server care sandboxează. Dacă serverul sandboxează agenții, dar nu are un sandbox pentru o rulare, procesele ei de unelte și comenzile `bash` sunt refuzate, nu pornite pe gazdă. Aceeași postură decide procesele mici din jurul unei rulări: ajutoarele ACP de o singură trimitere (titluri de conversație, `/btw`, `/handoff`, `/goal`) și testele golden ale unui pull request din Review Studio rulează în sandbox când serverul sandboxează agenții, fără izolare sub `off` și, sub `unavailable`, doar pentru o cerere pentru care proprietarul serverului răspunde; altfel sunt omise.
:::

## Prezentare generală a backend-urilor

| Backend     | Valoare     | Platformă                                      | Disponibilitate                                                                                                      |
| ----------- | --------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| VM izolat | `microvm` | macOS, Linux, Windows (microVM hypervisor)    | Condiționat de sondă pe runtime-ul microVM; se aplică terminalelor interactive — shell-ul rulează într-o [stație](/ro-RO/manual/concepte/statii/), nu pe gazdă |
| Nativ      | `native`  | macOS (Seatbelt), Linux și WSL2 (bubblewrap) | Sondat la pornire; Linux refuză o rulare care necesită interdicții de scriere pe globuri de nume de fișiere, pe care bubblewrap nu le poate impune |
| Niciunul      | `none`    | Toate                                           | Implicitul la parsare și implicitul terminalului; trimiterea agenților îl folosește sub `--sandbox off` și pentru rulările proprii ale proprietarului când nu este disponibil niciun backend |

`SandboxBackend.fromName` returnează `none` pentru o valoare stocată nulă sau nerecunoscută.

**`microvm` este singurul backend cu o graniță de kernel** — sarcina de lucru
chiar nu rulează pe gazdă. Nu este niciodată o soluție de rezervă silențioasă în
niciun sens: cererea lui explicită pe o gazdă care nu poate porni un VM eșuează
cu zgomot („Am cerut un VM și am primit laptopul meu” este singura degradare pe
care izolarea nu și-o poate permite), iar doar un *implicit nespecificat* coboară
la `native`, cu o linie de jurnal care spune asta. Backend-ul real al sesiunii este
raportat înapoi clientului și marcat cu o insignă, așa că un terminal nu poate
pretinde niciodată că este izolat în timp ce rulează pe gazdă. Ciclul de viață,
imaginile și ieșirea în rețea pentru VM-ul însuși sunt acoperite de
[referința pentru stații](/ro-RO/manual/referinta/statii/).

**Windows nu are sandbox nativ.** `NativeSandboxAdapter.probe` returnează `available: false` pe orice gazdă care nu este macOS sau Linux/WSL2, deci un server Windows este `unavailable`: pornesc doar rulările agenților proprietarului serverului, fără izolare, iar ale tuturor celorlalți sunt refuzate. Ca fiecare membru să poată rula agenți acolo, proprietarul pornește serverul cu `--sandbox off`, care le rulează pe toate fără izolare. Backend-ul `microvm` este separat: este condiționat de sondă pe runtime-ul microVM și se aplică terminalelor interactive și stațiilor, nu învelirii `bash` pe gazdă.

## Rezultatele sondei

Sonda este cea care condiționează aplicarea. Rulează o dată, la pornirea serverului.

| Gazdă                                   | `available` | Notă / indiciu                                                               |
| -------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS                                  | `true`      | `sandbox-exec` (Seatbelt) — izolare la nivel de namespace, fără graniță de kernel       |
| Linux sau WSL2 cu `bwrap` și `socat` | `true`      | bubblewrap — izolare la nivel de namespace, fără graniță de kernel                      |
| Linux sau WSL2 căruia îi lipsește oricare dintre instrumente      | `false`     | `requiresInstall: true`, cu un indiciu de instalare care numește pachetele lipsă |
| Orice altă platformă                     | `false`     | Sandbox-ul nativ nu este oferit pe această platformă                            |

Serverul înregistrează rezultatul într-o singură linie de pornire: `agent sandbox ON` plus nota; `no OS-native agent sandbox on this host` plus indiciul, care adaugă că pornesc doar rulările pentru care răspunde proprietarul serverului; sau `agent sandbox DISABLED by --sandbox off`. Linia de expunere afișată la pornire poartă aceeași decizie ca `sandbox=native`, `sandbox=off` sau `sandbox=unavailable`. `GET /healthz` nu conține niciun câmp de sandbox.

`--sandbox` / `CC_SERVER_SANDBOX` acceptă `on` (implicit) sau `off`. `on` învelește fiecare rulare când gazda oferă un backend și admite doar rulările proprietarului când nu oferă. `off` rulează agenții fiecărui membru fără izolare pe această gazdă; este alegerea proprietarului pentru toți, nu o setare per rulare.

## Backend-ul nativ

### macOS: Seatbelt

Folosește mecanismul de sandbox Seatbelt al Apple (același sistem folosit de macOS App Sandbox).

Profilul generat este **permisiv implicit** (`(allow default)`) și decupează interdicții, pentru că un profil complet cu refuz implicit face un shell interactiv inutilizabil — sunt prea multe apeluri dyld, XPC și Mach de enumerat. Consecința practică este că un agent poate citi în continuare cea mai mare parte a gazdei; checkout-urile tale înregistrate sunt protejate prin interdicții explicite de scriere și de redenumire, nu prin invizibilitate.

- **Citirile din sistemul de fișiere**: interzise pentru căile secrete (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` și restul setului cu citire interzisă)
- **Scrierile în sistemul de fișiere**: resetate la refuz, apoi permisiuni explicite pe subcăi, cu căile cu interdicție obligatorie (fișierele rc ale shell-ului, `.git/hooks`, configurația Claude, checkout-urile protejate) blocate chiar și în interiorul unei rădăcini inscriptibile. `file-write-unlink` este interzis pe fiecare cale interzisă și pe strămoșii ei, așa că o redenumire nu poate ocoli o interdicție de scriere
- **Procese**: `process-exec` interzice binarele mereu periculoase, plus o blocare a execuției oricărui lucru dintr-un director inscriptibil. Directoarele de instalare cunoscute ale toolchain-urilor din directorul home (corepack, cache-urile `npx` și `pnpm dlx`, managerii de versiuni node, browserele Playwright, rustup și cargo, Go, fvm și cache-ul pub, pyenv, uv și pipx, rbenv, sdkman, mise, asdf și `~/.local/bin`) sunt redeschise sub acea blocare. Directoarele temporare partajate sunt și ele blocate. În schimb, fiecare sesiune primește un `TMPDIR` privat sub `/private/tmp`, unde pot rula programele construite de agent (un binar `go test`, un build cargo). Interdicțiile pentru binarele mereu periculoase se aplică după aceste permisiuni
- **Rețea**: restricționată la porturile proxy din proces plus DNS — loopback nu este permis în bloc, iar ascultarea TCP este interzisă. Socketurile Unix sunt permise doar în interiorul `TMPDIR`-ului privat al sesiunii, care acoperă unelte precum tsx și Chrome ce păstrează acolo un socket IPC; agentul tău SSH și celelalte socketuri rămân inaccesibile. Proxy-urile impun lista de permisiuni de domenii per sesiune (vezi [Ieșirea în rețea](#ieșirea-în-rețea))
- **Configurare**: profilurile sunt generate la fiecare lansare din `SandboxSpec`
- **Comenzile serverului**: niciun director direct al unui folder din care serverul rulează programe (fiecare intrare din `PATH` și folderele obișnuite de unelte per utilizator, precum `~/.local/bin`, cu legăturile de manageri de versiuni precum `~/fvm/default` rezolvate) nu poate fi creat, înlocuit, șters sau redenumit, nici pachetul instalat către care indică o comandă legată. Vezi [Folderele de comenzi ale serverului](#folderele-de-comenzi-ale-serverului)
- **Fișierele de pornire**: fiecare cale de acasă pe care profilul o interzice la citire este interzisă și la scriere, iar fișierele de pornire ale shell-urilor și sesiunilor utilizatorului serverului (`.zshenv`, `.zlogin`, `.bash_login`, configurația fish, unitățile de utilizator systemd, intrările de autostart și altele asemenea) sunt interzise la scriere în orice mod

Cerințe:

- `sandbox-exec` (`/usr/bin/sandbox-exec`), parte din orice instalare macOS — nu este necesar niciun instrument suplimentar

### Linux: bubblewrap

Folosește bubblewrap (`bwrap`) pentru a crea namespace-uri de montare și PID.

- **Sistemul de fișiere**: creează un namespace de montare în care sunt vizibile doar căile legate
- **Rețea**: rulează într-un namespace de rețea nepartajat; traficul ajunge la proxy-urile gazdei prin punți de socketuri Unix `socat`
- **Procese**: izolare prin namespace PID
- **Comenzile serverului și fișierele de pornire**: aceleași protecții ca pe macOS, exprimate ca montări bind bubblewrap. Nu sunt verificate încă pe Linux, iar un folder de comenzi lipsă poate fi încă creat acolo

Cerințe:

- `bubblewrap` și `socat` instalate (`sudo apt-get install bubblewrap socat` pe Debian/Ubuntu)
- Suport pentru namespace-uri în kernel (standard pe Linux-ul modern)

Bubblewrap poate umbri o cale existentă, dar nu poate interzice un fișier `.env`,
`*.key` sau `*.pem` *nou* în interiorul unei legături inscriptibile. Politica
standard de trimitere cere aceste interdicții pe globuri de nume de fișiere, așa
că trimiterea nativă a agenților **eșuează închis pe Linux/WSL2 chiar și atunci
când sonda găsește bubblewrap**. Nu rulează cu o politică slăbită în tăcere.
Este necesar un backend cu reguli de nume de fișiere la momentul creării pentru a
restabili trimiterea nativă pe Linux. Dezactivarea sandbox-ului este o renunțare
explicită la confinare, nu o soluție echivalentă.

În practică, un server Linux sau WSL2 rulează azi agenții în unul dintre două feluri. Pornit cu `--sandbox off`, rulează agenții fiecărui membru fără izolare. Fără bubblewrap sau `socat` instalate, este `unavailable` și rulează doar agenții proprietarului serverului, fără izolare. Cu ambele unelte instalate și sandbox-ul pornit, fiecare rulare se închide la eșec, inclusiv cele ale proprietarului.

## Folderele de comenzi ale serverului

Serverul găsește, o singură dată la pornire, fiecare folder din care rulează programe: fiecare intrare din `PATH`, folderele de unelte per utilizator pe care le sondează (precum `~/.local/bin`, `~/.bun/bin` și folderele globale npm, yarn și pnpm) și folderul real din spatele fiecărei legături de pe drum (legături de manageri de versiuni precum `~/fvm/default` sau un default fnm). În interiorul unui sandbox, un agent nu poate adăuga, înlocui, șterge sau redenumi o comandă în acele foldere, legătura care duce către una sau pachetul instalat către care indică o comandă legată și nu poate redenumi folderele de deasupra lor. Altfel, o rulare sandboxată ar putea planta un program pe care serverul sau persoana îl pornește mai târziu în afara sandbox-ului.

Ce schimbă asta pentru o rulare:

- Instalările globale dintr-o rulare sandboxată eșuează cu „Operation not permitted”: `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, iar `cargo install`, `go install` sau `dart pub global activate` când folderul lor bin este în `PATH`-ul serverului.
- Schimbarea unui default de versiune eșuează la fel (`fnm default`, `nvm alias default`, `fvm global`), ca și un instrument care se actualizează singur pe loc.
- Instalările locale de proiect (`node_modules/.bin`), `npx`, `pnpm dlx`, managerii de pachete gestionați de corepack, cache-urile SDK-urilor și build-urile obișnuite continuă să funcționeze.

Ca să fie disponibil un instrument global pentru agenți, instalează-l pe serverul însuși, ca utilizatorul serverului, și repornește serverul, ca și noua comandă să fie protejată. Sau instalează-l în proiect. O comandă instalată după pornirea serverului este protejată complet abia de la următoarea pornire.

Aplicată și testată pe macOS. Pe Linux, aceleași reguli sunt montări bind bubblewrap care nu sunt verificate încă. Windows nu are sandbox.

## Backend-ul none

Fără sandbox. Procesul rulează direct pe gazdă, cu accesul gazdei la sistemul de fișiere, rețea și procese. ACP și instrumentul `bash` al harness-ului primesc în continuare sanitizarea mediului și politica de comenzi; Claude Code prin `NoSandboxAdapter` moștenește mediul gazdei. Trimiterea agenților îl folosește pentru fiecare rulare sub `--sandbox off` și, pe o gazdă fără niciun backend disponibil, doar pentru rulările proprii ale proprietarului serverului; rularea oricui altcuiva este refuzată acolo. Pentru un terminal este shell-ul gazdei, pe care îl poate deschide doar proprietarul serverului.

## Terminalul găzduit de server

Terminalul găzduit de server deschide shell-ul gazdei doar pentru [proprietarul](/ro-RO/manual/concepte/autorizare/#proprietarul-serverului) serverului. Ceilalți primesc un terminal sandboxat, cu limitele unui agent, în directoarele proprii ale spațiului de lucru.

Cum se alege backend-ul pentru o sesiune:

| Cerut | Proprietarul serverului | Oricine altcineva |
| --- | --- | --- |
| Nimic | Backend-ul implicit al serverului | Implicitul, cu `none` înlocuit cu `native` |
| `none` (shell-ul gazdei) | Shell-ul gazdei | Refuzat: shell-ul gazdei rulează pe server fără sandbox |
| `native` | Sandbox nativ, profilul proprietarului | Sandbox nativ, profilul de agent |
| `microvm` | VM izolat | VM izolat |
| Un nume necunoscut | Refuzat | Refuzat |

- **Profilul proprietarului.** `$HOME` și directorul de lucru al sesiunii sunt inscriptibile, rețeaua este deschisă, iar `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` și `~/Library/Keychains` au citirea interzisă.
- **Profilul de agent** (`memberTerminalSandboxConfig`). Aceeași politică sub care rulează un agent în spațiul de lucru respectiv: scrierile rămân în directorul de lucru, într-un director privat de rulare, în `/tmp` și în părțile din `$HOME` pe care un agent le poate scrie; secretele au citirea interzisă; rețeaua este lista de permisiuni de ieșire a agentului; programele rulează doar din directorul de lucru și din toolchain-urile instalate.
- Un terminal se deschide doar în directoarele proprii ale spațiului de lucru. Un director de lucru din afara lor este refuzat, niciodată înlocuit cu altul.
- Doar persoana care a deschis un terminal îl poate citi, scrie în el, redimensiona sau închide. Pentru oricine altcineva, id-ul lui pare necunoscut.
- `microvm` cerut explicit pe o gazdă fără serviciu de stații eșuează în loc să revină la altceva. Un implicit `microvm` pe o astfel de gazdă coboară la `native` și spune asta în jurnal.

Tokenul de forge doar pentru citire și gateway-ul de push nu se aplică terminalelor: sunt probleme de trimitere. Dacă învelirea nu este acceptată, sesiunea eșuează în loc să afișeze o insignă de sandbox pe o sesiune cu shell-ul gazdei.

## Ieșirea în rețea

Când este lansat un sandbox, accesul de ieșire în rețea este impus de proxy-uri din proces, nu de reguli de firewall la nivel de kernel. O rulare care nu este sandboxată (fiecare rulare sub `--sandbox off`, sau rularea proprietarului pe o gazdă fără backend) nu primește nimic din toate acestea: un proces pornit de ea ajunge la rețea exact așa cum ar face-o utilizatorul serverului.

- Runtime-ul sandbox-ului rulează un proxy HTTP/HTTPS și un proxy SOCKS5 pe `127.0.0.1` în interiorul procesului `cc_server`, **o pereche per sesiune restricționată** (`http_proxy.dart`, `socks_proxy.dart`). Rulările concurente nu împart o pereche.
- Procesele din sandbox primesc variabile de mediu pentru proxy (`HTTP_PROXY`/`HTTPS_PROXY` → proxy-ul HTTP, `ALL_PROXY` → proxy-ul SOCKS; `GIT_SSH_COMMAND` direcționează git-over-SSH prin proxy-ul SOCKS). Pe Linux namespace-ul de rețea este nepartajat, așa că proxy-urile sunt singura cale de ieșire; pe macOS sandbox-ul împarte loopback-ul gazdei și vorbește cu ele direct.
- Gazda țintă a fiecărei conexiuni este potrivită cu lista de permisiuni de domenii a sesiunii; orice altceva este refuzat. Două forme de wildcard, fiecare cu exact un `*`: un `*.example.com` la început potrivește orice subdomeniu (inclusiv `a.b.example.com`), dar nu apexul însuși; un `bedrock.*.amazonaws.com` cu etichetă la mijloc potrivește exact o etichetă (`bedrock.us-east-1.amazonaws.com`, nu `bedrock.evil.attacker.amazonaws.com`).
- Lista de permisiuni este rezolvată per sesiune din baza de referință atent selectată (`kBaselineAllowedDomains`: furnizori de LLM, găzduire Git, registre de pachete), plus domeniile GitHub (`kGithubDomains`), plus `SandboxSpec.egressAllowlist`. Calea de trimitere nu transmite niciodată intrări suplimentare de `egressAllowlist`, așa că în practică fiecare rulare primește baza de referință plus GitHub.
- O listă fixă de interdicții (`kBaselineDeniedDomains`: puncte finale de metadate din cloud, destinații de telemetrie) are prioritate față de toate permisiunile.
- `networkEnabled: false` pornește totuși proxy-urile per sesiune, dar lista de permisiuni este goală, așa că fiecare conexiune de ieșire este refuzată. Trimiterea îl setează la pornirea rulării din regula **Accesează rețeaua**: refuzul oprește rețeaua, permite și întreabă întâi o lasă pornită.

## SandboxSpec

Specificația transmisă către `SandboxPort.launch`:

| Câmp             | Tip                                        | Descriere                                                                                                                                 |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | Identificator stabil de sesiune (de obicei id-ul spațiului)                                                                                          |
| `workspaceId`     | `String`                                    | Id-ul spațiului de lucru proprietar                                                                                                                         |
| `agentId`         | `String?`                                   | Agentul legat în prezent de sandbox, dacă există                                                                                                |
| `bindMounts`      | `List<SandboxBindMount>`                    | Montări gazdă→invitat; sandbox-ul vede doar căile de gazdă listate aici                                                                         |
| `networkEnabled`  | `bool` (implicit `true`)                     | Setat la trimitere din regula de ieșire în rețea (oprit doar când se rezolvă la refuz). Când este oprit, proxy-urile per sesiune pornesc totuși, dar lista de permisiuni este goală, așa că fiecare conexiune de ieșire este refuzată |
| `egressAllowlist` | `List<String>` (implicit `[]`)               | Domenii de ieșire suplimentare permise; wildcard-uri acceptate (`*.example.com`, plus o formă de mijloc cu o singură etichetă). Trimiterea nu populează niciodată acest câmp, așa că o rulare învelită primește baza de referință atent selectată plus domeniile GitHub |
| `guestWorkdir`    | `String?`                                   | Directorul de lucru implicit din interiorul sandbox-ului; apelurile `exec` individuale îl pot suprascrie                                                       |
| `mode`            | `Mode` (implicit `chat`)                     | Decupează regulile de scriere în sistemul de fișiere: `chat` păstrează montările bind inscriptibile; `review`, `plan` și `orchestrate` sunt doar pentru citire                      |
| `protectedPaths`  | `List<String>` (implicit `[]`)               | Căi de gazdă care nu trebuie să fie niciodată inscriptibile în interiorul sandbox-ului, în orice mod                                                                      |
| `runnerStateDirs` | `List<String>` (implicit `[]`)               | Directoare de gazdă în care runner-ul își păstrează propria stare, inscriptibile în orice mod (un `CLAUDE_CONFIG_DIR` gestionat de Control Center este cel actual) |
| `execGrantRoots`  | `List<String>` (implicit `[]`)               | Arbori de directoare aprobați de operator care redeschid blocarea de execuție pentru directoare inscriptibile pe macOS. Linux le ignoră — bwrap nu are nicio blocare de execuție pe `$HOME` de redeschis |

`protectedPaths` conține checkout-urile originale ale repo-urilor înregistrate, rezolvate la fiecare trimitere din repo-urile spațiului de lucru. Agenții lucrează exclusiv în worktree-uri copy-on-write per conversație, așa că originalele nu trebuie să fie niciodată inscriptibile din interiorul sandbox-ului — pe macOS, permisiunea generală de scriere în `$HOME` a Seatbelt le-ar lăsa altfel inscriptibile prin `bash`. Ele se alătură setului cu scriere interzisă pentru secrete în fiecare mod, inclusiv `chat`.

Fiecare cale cu citire interzisă și cu scriere interzisă este emisă atât în grafia ei literală, cât și în cea rezolvată prin symlink. Kernelul potrivește o regulă de interdicție cu calea rezolvată, așa că o regulă scrisă pe o cale cu symlink nu se declanșează niciodată — iar pe macOS acesta este cazul obișnuit, nu cel exotic, fiindcă `/tmp` se rezolvă la `/private/tmp`, iar `/var/folders/…` la `/private/var/folders/…`. Intrările care conțin `*` sau `?` sunt tratate ca globuri și lăsate în pace; o cale care nu se rezolvă este păstrată așa cum a fost scrisă.

## SandboxBindMount

| Câmp       | Tip                     | Descriere                                                                                             |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `hostPath`  | `String`                 | Cale absolută pe gazdă                                                                               |
| `guestPath` | `String`                 | Cale în interiorul sandbox-ului (cu sandbox-ul nativ aceasta este egală cu `hostPath`; păstrată pentru simetria adaptoarelor) |
| `readOnly`  | `bool` (implicit `false`) | Montează doar pentru citire când este true                                                                               |

## SandboxHandle

Returnat de `SandboxPort.launch`:

| Câmp       | Tip                   | Descriere                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | Identificator de sesiune                                                       |
| `backend`   | `SandboxBackend`       | Ce backend rulează                                                 |
| `state`     | `SandboxState`         | Starea ciclului de viață                                                          |
| `error`     | `Object?`              | Setat când `state` este `error`                                              |
| `details`   | `Map<String, Object?>` | Evidență privată a adaptorului (director de lucru, PID, calea profilului etc.) |

### SandboxState

| Stare       | Descriere                                 |
| ----------- | ------------------------------------------- |
| `created`   | Specificația a fost creată, dar VM-ul nu a pornit încă |
| `warm`      | Rulează și este gata să execute comenzi          |
| `active`    | Execută în prezent o comandă               |
| `suspended` | Pauzat / salvat ca punct de control pe disc pentru a economisi RAM   |
| `destroyed` | Desființat; handle-ul nu mai este valid    |
| `error`     | Lansarea a eșuat — vezi `SandboxHandle.error`   |

## Evenimente de sandbox

| Tip de eveniment  | Descriere                                                  |
| ----------- | ------------------------------------------------------------ |
| `stdout`    | Ieșirea standard a sandbox-ului                             |
| `stderr`    | Eroarea standard a sandbox-ului                              |
| `exit`      | Procesul sandbox-ului s-a încheiat (poartă `exitCode`)                  |
| `starting`  | Sandbox-ul pornește                                       |
| `ready`     | Sandbox-ul este gata să accepte apeluri exec                        |
| `killed`    | Procesul a fost omorât de gazdă (OOM, timeout, oprire manuală)       |
| `violation` | O politică de sandbox a fost încălcată (poartă un `SandboxViolation`) |

## SandboxViolation

| Câmp                 | Tip      | Descriere                                                                |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action`              | `String`  | Verbul refuzat (de ex. `file-read*`, `network-outbound`)                    |
| `target`              | `String`  | Calea sau gazda care a fost ținta operației refuzate                   |
| `raw`                 | `String?` | Linia brută de jurnal, utilă pentru depanare                                         |
