Acest ghid îți arată unde este stocat fiecare credențial folosit de Control Center
și cum să îl schimbi.

**Nimic nu este stocat pe mașina pe care tastezi.** Fiecare credențial se află pe
server; care dintre ele răspunde la o anumită cerere depinde de existența unui om
în spatele ei.

| Credențial                     | Unde este stocat                                          | Cine îl folosește                                                 |
| ------------------------------ | --------------------------------------------------------- | ----------------------------------------------------------------- |
| Autentificarea ta la host de cod / tichete | Fișierul de secrete 0600 al serverului, indexat după id-ul tău de utilizator | Orice faci tu: zona de PR-uri, revizuirile, îmbinările, acțiunile tale în Linear |
| Aplicațiile provider ale serverului | Același fișier, plus `server_settings` pentru cele care nu sunt secrete | Autentificarea oamenilor și tokenurile pentru un singur depozit pentru agenți, pipeline-uri și interogarea periodică |
| Cheia de instalare Connect     | Același fișier (`connect_install_key`)                     | Identificarea acestui server față de Control Center Connect       |
| Chei de provideri de modele și tokenuri OAuth | Depozitul de credențiale al serverului                    | Adaptorul încorporat, pentru fiecare spațiu de lucru din instalare |
| Credențiale de bot Slack       | `<dataDir>/<workspaceId>/chat_credentials/` pe server      | Puntea de chat pentru spațiul de lucru respectiv: tokenurile propriei tale aplicații sau grantul sigilat al aplicației partajate |
| Credențiale de CLI extern      | Orice folosește CLI-ul respectiv                           | Claude Code, pe hostul serverului                                 |

## GitHub: autentificarea ta și tokenuri pentru un singur depozit

- **Al tău**, din **Autentifică-te în GitHub**. Este cel pe care îl folosește
  fiecare cerere făcută *în numele tău*, așa că o revizuire publicată pentru
  tine îți poartă numele. Un alt membru nu îl poate folosi și se autentifică
  singur. Nu există niciun token GitHub de lipit
- **Munca pe care nu o tastează nimeni** (agenți, pipeline-uri, interogarea
  periodică, răspunsurile botului) primește un token pentru câte un singur
  depozit, emis din GitHub App a serverului sau prin Control Center Connect și
  limitat la ce poate face acolo un membru responsabil. Nu este niciodată
  autentificarea ta predată întreagă

Al tău se setează în cardul **Găzduire de cod** din **Setări → Tu → Profil**; aplicația serverului, în **Aplicații provider** din **Setări →
Server → Autentificare unică**. Vezi
[Configurează integrarea GitHub](/ro-RO/manual/ghiduri-practice/integrare-github/)
și [Creează GitHub App](/ro-RO/manual/ghiduri-practice/github-app/).

GitLab și Bitbucket primesc în continuare un token personal lipit, stocat la fel.
Vezi [Conectează un host de cod](/ro-RO/manual/ghiduri-practice/conecteaza-host-de-cod/).

:::note[Există și un ecran accesibil doar prin URL]
`/workspaces/<workspaceId>/api-keys` afișează aceleași carduri ca primul pas al
onboarding-ului. Nu are **nicio intrare de navigare nicăieri în interfață**; este
accesibil doar tastând URL-ul. Folosește în schimb Setări → Tu → Profil
pentru propriile autentificări și Setări → Spațiu de lucru → Integrări pentru
furnizorul de tichete.
:::

## Setează cheile providerilor de modele

Adaptorul încorporat autentifică singur providerii, iar acele credențiale se află
pe server.

1. Mergi la **Setări → Server → Provideri de modele**
2. Derulează până la **Provideri și modele**
3. Conectează providerul — OAuth în browser pentru OpenAI, Codex, Cursor și Kimi
   Code; o cheie API pentru Anthropic și restul

Vezi [Gestionează adaptoarele și modelele](/ro-RO/manual/ghiduri-practice/adaptoare/)
pentru lista completă și pentru adăugarea unui endpoint personalizat.

Aceste credențiale sunt **globale la nivel de host**: o singură cheie deservește
fiecare spațiu de lucru din instalare. Tokenurile OAuth sunt reîmprospătate
înainte de a expira.

Claude Code se autentifică prin **Conturi Claude Code**, din **Setări → Server → Furnizori de modele**: fiecare cont primește propriul director de configurare pe server, iar tu rulezi acolo comanda `claude auth login` pe care ți-o arată aplicația.

Dialogul **Variabile de mediu** al fiecărui adaptor pare un loc potrivit pentru a
pune o cheie pentru unul dintre ele, dar nu este: scrie pe dispozitivul tău, în
timp ce serverul citește propria copie și nimic nu le face legătura. Vezi
[Gestionează adaptoarele și modelele](/ro-RO/manual/ghiduri-practice/adaptoare/).

## Conectează un furnizor de tichete

Cardul **Ticketing** din **Setări → Spațiu de lucru → Integrări** conține partea
spațiului de lucru: la ce furnizor îți stau tichetele și cine este Control Center
când lucrează acolo de unul singur. Alegerea **Local** ascunde rândurile
Linear — tichetele locale se află în baza de date proprie a acestui server și nu
au la ce să se autentifice.

Linear are două autentificări și nicio cheie de lipit: **Linear** este a ta,
pentru ce faci tu, și se află în **Setări → Tu → Profil**; **Automatizare
Linear** este aplicația Control Center a spațiului de lucru, conectată de un
administrator din cardul Ticketing, pentru sincronizarea tichetelor, pipeline-uri
și agenți. Serverul poate deține și o **Cheie API de
serviciu** (**Aplicații provider**) pentru spațiile de lucru fără automatizare
conectată. Niciun credențial de ticketing nu este injectat în sandbox-ul unui
agent; agenții scriu tichete prin instrumentele Control Center, care întreabă
regula **Scrie într-un tracker extern**. Vezi
[Configurează integrarea Linear](/ro-RO/manual/ghiduri-practice/integrare-linear/).

## Rotește sau revocă

- **Autentificarea ta GitHub**: apasă **Deconectează**, apoi din nou
  **Autentifică-te în GitHub**. Deconectarea anulează și toate tokenurile pe
  care serverul le-a emis în numele tău
- **Un token GitLab sau Bitbucket**: apasă **Actualizează tokenul** și lipește-l
  pe cel nou, apoi revocă-l pe cel vechi pe forge
- **Aplicația serverului**: generează o cheie privată sau un client secret nou în
  pagina aplicației la provider, lipește-l în **Aplicații provider** și apasă
  **Test**
- **Cheia de instalare Connect**: proprietarul serverului apasă **Schimbă cheia**
  pe cardul **Control Center Connect**. Toți cei care s-au autentificat prin
  Connect se autentifică din nou. Dacă serverul Connect nu poate fi contactat,
  nu se schimbă nimic și ți se oferă **Rotește oricum**. Vezi
  [Rotește cheia de instalare](/ro-RO/manual/referinta/connect/#schimbă-cheia-de-instalare)
- **Un provider de modele**: pe rândul său, deconectează-te (OAuth) sau elimină
  cheia, apoi conectează-te din nou
- **Slack**: pentru propria ta aplicație, lipește din nou tokenurile în dialogul
  de conectare. Aplicația partajată Control Center nu are niciun token de rotit:
  tokenul ei de bot este reînnoit prin Connect, iar **Deconectează** îl revocă și
  dezinstalează botul din Slack. Vezi
  [Configurează integrarea Slack](/ro-RO/manual/ghiduri-practice/integrare-slack/)

## Depanare

### Un token GitLab sau Bitbucket funcționează în `curl`, dar nu aici

Verifică rândul **Găzduire de cod**. Dacă scrie „Neconectat” sau îți cere să te
conectezi din nou, tokenul tău nu a fost salvat sau a fost refuzat. Pentru
Bitbucket, introdu adresa de e-mail a contului Atlassian împreună cu tokenul API.

### Un token GitLab sau Bitbucket este acceptat, dar cererile ulterioare eșuează

Tokenul este verificat așa cum este stocat, așa că rândul indică contul din
spatele lui — dar numai contul, nu și scope-urile. Un token cu prea puține
scope-uri se conectează, apoi eșuează la cereri individuale. Verifică-i
scope-urile și expirarea pe forge.

### Un provider spune că autentificarea nu este configurată pe acest server

Serverul nu are nici aplicație proprie pentru acel provider, nici Control Center
Connect. Proprietarul serverului alege una dintre ele în **Setări → Server →
Autentificare unică**.
