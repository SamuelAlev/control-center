Dacă o rulare de agent este sandboxată se decide pe server, la pornire
(`--sandbox`). Comutatorul **Activează sandboxing-ul**, selectorul **Backend** și
comutatoarele **Capabilități implicite · spații noi** din **Setări → Server →
Diagnosticări și confidențialitate** sunt preferințe stocate pe dispozitivul tău.
Detectarea gazdei din cardul **Sandboxing** raportează ce poate înveli gazda
serverului.

Două controale ajung la o rulare și acest ghid le acoperă pe amândouă:
**Permisiuni sandbox** per agent de mai jos și flag-ul `--sandbox` al
serverului.

## Ce constrânge o rulare de agent

Un agent este ținut de șase lucruri. Primul este sandbox-ul sistemului de
operare și este singurul condiționat — celelalte cinci rezistă pe orice gazdă.

| Graniță                     | Ce face                                                                                                                                                                                            |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sandbox-ul sistemului de operare | Seatbelt pe macOS, bubblewrap pe Linux și WSL2. Învelește CLI-ul Claude Code, adaptoarele ACP și instrumentul `bash` al harness-ului. **Absent pe Windows și pe Linux fără `bwrap` și `socat`** |
| Propriul worktree           | Fiecare conversație primește un checkout copy-on-write. Checkout-ul original este inclus în rulare ca o cale cu scrierea interzisă, iar sandbox-ul este cel care impune asta                            |
| Acreditări emise de broker  | Brokerul de acreditări emite un mediu per rulare din capabilitățile agentului și îl revocă la desființare. Fără capabilitate, niciun token în mediu                                               |
| Guardrail-uri de acțiuni    | Fiecare instrument care modifică starea își declară clasele de efect, iar garda le rezolvă înainte ca apelul să ruleze. Un `prompt` fără niciun aprobator conectat este refuzat                      |
| Sanitizarea mediului        | ACP și instrumentul `bash` al harness-ului primesc un mediu filtrat. Claude Code prin `NoSandboxAdapter` moștenește mediul gazdei                                                                   |
| Suprafața de instrumente a modului | Un mod doar pentru citire elimină de tot instrumentele care modifică worktree-ul și fixează verbul de ieșire al modului, ca să poată livra totuși                                            |

Trei lucruri rămân mai slabe decât par:

- Doar **harness-ul încorporat** aplică poarta de instrumente, contractele de
  finalizare și regulile structurale ale modurilor. Adaptorul Claude Code nu.
  Claude Code în special este lansat cu `--dangerously-skip-permissions`, pentru
  că un `claude -p` neinteractiv s-ar bloca altfel la nesfârșit pe propriul
  prompt — așa că apelurile lui de citire, scriere, editare și bash nu sunt nici
  văzute, nici filtrate de Control Center. Acolo unde sandbox-ul este pornit, el
  este granița din jurul lor.
- Instrumentele de fișiere în proces ale harness-ului (read, write, edit, apply
  patch, search, find, search_files) rulează în interiorul procesului
  serverului, așa că niciun profil de sandbox nu le constrânge. Doar
  instrumentul `bash` trece prin executorul de comenzi sandboxat. Acele
  instrumente sunt limitate de propria confinare a căilor plus guardrail-urile
  de acțiuni.
- Pe o gazdă fără backend, primul rând nu se aplică deloc. ACP și instrumentul
  `bash` al harness-ului se întorc la sanitizarea mediului plus politica de
  comenzi; Claude Code moștenește mediul gazdei prin `NoSandboxAdapter`.
  Serverul spune asta în jurnalul său de pornire. Verifică-l pe al tău mai jos.

## Setează capabilitățile unui agent

Acesta este singurul control de capabilități pe care îl citește serverul. Este
per agent și decide ce pune brokerul de acreditări în mediul acelui agent.

1. Mergi la **Setări → Spațiu de lucru → Agenți**
2. Selectează agentul din listă
3. În fila **Setări**, derulează până la **Permisiuni sandbox**
4. Pornește comutatorul — legenda rândului se schimbă din **Folosește
   implicitul spațiului de lucru**
5. Setează cele patru comutatoare:

| Comutator                        | Ce controlează                                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Permite git push**             | Cu acesta oprit, rularea primește `GIT_ASKPASS=/usr/bin/false` și `GIT_TERMINAL_PROMPT=0`, așa că un push nu poate cere o acreditare                                                                                                             |
| **Permite apeluri GitHub API**   | Împreună cu **Permite git push**, controlează dacă brokerul injectează tokenul GitHub ca `GH_TOKEN` / `GITHUB_TOKEN`                                                                                                                              |
| **Permite apeluri ticketing API** | Controlează dacă brokerul injectează `TICKETING_API_KEY`                                                                                                                                                                                         |
| **Permite accesul general la rețea** | Acolo unde sandbox-ul este pornit, aceasta este o poartă reală de ieșire: cu ea oprită, lista de permisiuni a rulării este goală și fiecare cerere către exterior este refuzată la proxy. Acolo unde nu există backend, este înregistrată pe rulare, dar nu blochează nimic din ce face un proces lansat |

6. Salvează

Punct de control: redeschide agentul și comutatorul este încă pornit, cu
comutatoarele tale — un set de capabilități salvat face un dus-întors prin
server, iar un agent fără niciunul se întoarce la implicitul conservator (push
oprit, API GitHub oprit, ticketing oprit, rețea pornită).

:::caution[Două capcane]
Legenda spune **Folosește implicitul spațiului de lucru**, dar nu există nicio
setare de capabilități la nivel de spațiu de lucru pe care să o citească
serverul. Un agent cu comutatorul oprit primește implicitul conservator
încorporat.

Separat, acreditarea GitHub a rulării este întotdeauna doar a brokerului — un
token de instalare GitHub App limitat la depozit, sau varianta de rezervă PAT
din mediu — niciodată tokenul stocat al membrului care face cererea.
`actingUserId` este transmis pentru ca brokerul să poată *reține* PAT-ul
serverului de la un membru care nu este proprietarul și nu a conectat GitHub;
nu îmbină un token personal peste o capabilitate oprită. Nu trata **Permite
apeluri GitHub API** ca pe o graniță strictă de ieșire pe o gazdă fără sandbox
al sistemului de operare: un proces lansat poate ajunge totuși la rețea.
:::

## Verifică dacă rulările agenților tăi sunt sandboxate

Două lucruri decid asta, ambele pe server: dacă gazda oferă un backend și dacă
`--sandbox` este pornit. Verifică-le în această ordine.

1. Mergi la **Setări → Server → Diagnosticări și confidențialitate**
2. Citește cardul **Sandboxing**. Faptul **Gazdă** este mașina pe care rulează
   `cc_server`, nu mașina la care te uiți. Câmpul **Backend** listează **Sandbox
   nativ** (Seatbelt pe macOS, bubblewrap pe Linux și WSL2) sau **Fără
   izolare**. Faptul **În vigoare** este preferința acestui dispozitiv, nu
   învelișul pe care îl folosește de fapt serverul.
3. Citește jurnalul de pornire al serverului. Afișează exact una dintre trei
   linii:
   - `agent sandbox ON` plus nota despre backend — rulările sunt învelite
   - `no OS-native agent sandbox on this host` plus un indiciu de instalare
     acolo unde există — rulările nu sunt învelite
   - `agent sandbox DISABLED by --sandbox off` — o renunțare deliberată

`GET /healthz` nu raportează starea sandbox-ului, așa că jurnalul de pornire
este verificarea.

Ca să oprești sandbox-ul în mod deliberat — o gazdă pe care profilul se
comportă prost este motivul pentru care această opțiune există — pornește
serverul cu `--sandbox off` sau setează `CC_SERVER_SANDBOX=off`. Implicitul este
`on`, iar `on` înseamnă „folosește un backend dacă gazda are unul”, niciodată
„cere unul”.

Două situații nu primesc niciodată un înveliș de sandbox nativ. Pe **Windows**
sonda nativă raportează întotdeauna indisponibil și nu există nimic de
instalat — trimiterea agenților folosește `none`. Backendul `microvm` este
separat (terminale interactive și stații) și este condiționat de sondă pe
propriul său runtime. Pe **Linux și WSL2**, atât `bwrap`, cât și `socat`
trebuie să fie în `PATH`; fără ele, sonda raportează indisponibil și numește
pachetele lipsă.

Pe Linux/WSL2 cu bubblewrap instalat, globurile de fișiere secrete ale politicii
standard nu pot fi aplicate pentru fișierele pe care un agent le creează
ulterior. O astfel de rulare nativă eșuează acum, în loc să ignore în silențiu
regulile. O sondă de pornire pozitivă nu garantează așadar că o trimitere pe
Linux poate porni. `--sandbox off` este o renunțare deliberată la confinare, nu
o graniță de securitate substitutivă.

## Află ce interzice deja un mod

Modul este stocat per spațiu și alimentează rezolvitorul de guardrail-uri ca
strat de **presetare de mod**. Trei dintre cele patru moduri sunt doar pentru
citire, iar un mod doar pentru citire refuză categoric unsprezece clase de
efect:

| Mod                 | Worktree       | Refuzate de presetare                                                                                                                                                            |
| ------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent** (`chat`)  | Inscriptibil   | Nimic — se aplică impliciturile încorporate                                                                                                                                      |
| **Plan**            | Doar pentru citire | Șterge un fișier, scrie în afara worktree-ului, creează un commit, push către un remote, deschide un pull request, publică o revizuire sau o fuziune, scrie într-un tracker extern, instalează un pachet, rulează un proces, modifică structura spațiului de lucru, conduce un mediu izolat (stație) |
| **Revizuire**       | Doar pentru citire | Aceleași unsprezece. Nu poate fi selectat de utilizator — zona de compunere oferă doar Agent, Plan și Orchestrează                                                               |
| **Orchestrează**    | Doar pentru citire | Aceleași unsprezece                                                                                                                                                              |

Accesul la rețea și accesul la secrete nu sunt refuzate în mod deliberat de un
mod doar pentru citire: cercetarea este tocmai rostul unui astfel de mod.

## Cere aprobare înainte ca o acțiune să ruleze

Aprobarea este o decizie de guardrail, nu o setare de sandbox.

1. Mergi la **Setări → Spațiu de lucru → Permisiuni agent**
2. Setează clasa de acțiune pe **Întreabă întâi** la domeniul spațiu de lucru,
   agent sau spațiu

O decizie **Întreabă întâi** întrerupe rularea și te întreabă. Fără niciun
aprobator conectat, eșuează închis și acțiunea este refuzată. Vezi
[Configurează guardrail-urile](/ro-RO/manual/ghiduri-practice/configureaza-guardrail-uri/)
pentru ordinea completă de rezolvare.

## Depanare

### Un agent nu poate face push și nu am refuzat niciodată asta

Verifică **Permisiuni sandbox** ale agentului. Un agent fără un set personalizat
de capabilități primește implicitul conservator, în care **Permite git push**
este oprit — așa că brokerul nu injectează niciun token GitHub și git nu are cum
să se autentifice.

### Cardul Sandboxing nu raportează niciun sandbox nativ

Atunci rulările de agent de pe acea gazdă nu sunt învelite de Seatbelt sau
bubblewrap, iar granițele rămase sunt tot ce ai. Pe Linux și WSL2, instalează
ambele instrumente lipsă — `sudo apt-get install bubblewrap socat` — și
repornește serverul; jurnalul de pornire ar trebui să spună atunci că
sandbox-ul este pornit. Pe Windows nu există niciun backend nativ de instalat,
așa că strânge în schimb guardrail-urile: vezi
[Configurează guardrail-urile](/ro-RO/manual/ghiduri-practice/configureaza-guardrail-uri/).

### Un agent a ajuns la un fișier din afara worktree-ului său

Ce instrument a ajuns la el decide dacă asta este de așteptat.

Instrumentele de fișiere în proces ale harness-ului (read, write, edit, apply
patch, search, find, search_files) rulează în procesul serverului, așa că nu li
se aplică niciun profil de sandbox — limita lor este propria confinare a căilor
plus guardrail-urile. O comandă `bash` sau CLI-ul Claude Code _este_ învelit
acolo unde există un backend, iar checkout-urile tale înregistrate au scrierea
interzisă în interiorul acelui înveliș în orice mod, inclusiv grafia lor
rezolvată prin symlink (pe macOS, o cale accesată prin `/tmp` sau `/var/folders`
se rezolvă sub `/private`, iar acum ambele grafii sunt interzise). Pe o gazdă
fără backend, nimic din toate acestea nu se aplică. În orice caz,
guardrail-urile pot refuza categoric **Scrie în afara worktree-ului**.
