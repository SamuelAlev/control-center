Control Center răspunde la două întrebări de autorizare, iar ele sunt cu adevărat
diferite. **„Poate această persoană să apeleze această operațiune?”** ține de oameni,
roluri și repository-uri. **„Poate acest agent să producă acest efect?”** ține de
acțiuni, argumente și raza de impact — aceea este
[Guardrail-uri](/ro-RO/manual/concepte/guardrail-uri/).

Această pagină tratează prima întrebare, plus urma pe care o lasă amândouă.

## Un singur punct de decizie

Fiecare decizie de autorizare din partea oamenilor se rezolvă printr-o singură
funcție:

```
can(principal, permission, resource) → allow | deny + why
```

O **permisiune** este `<domain>:<tier>` — `tickets:write`,
`members:administer`, `repos:read`. Catalogul este **derivat**, nu scris manual:
este calculat din însăși suprafața operațiunilor (prefixul numelui operațiunii dă
domeniul, pragul de rol pe care îl impune deja dă nivelul), astfel încât toate
cele ~550 de operațiuni poartă o permisiune fără ca cineva să tasteze vreuna.

Această derivare este proprietatea care merită protejată. Înseamnă că o operațiune
NOUĂ este blocată implicit — modul de eșec al unui model adnotat manual este că
cineva uită, iar lucrul pe care îl uită este poarta. Un test de tip ratchet
fixează setul de domenii rezultat, astfel încât adăugarea unei operațiuni sub un
prefix nou este o decizie de denumire pe care o ia un om, nu un accident.

Cele patru niveluri corespund exact rolurilor predefinite:

| Nivel | Prag de rol | Exemplu |
|---|---|---|
| `read` | Invitat | `tickets:read` |
| `write` | Membru | `tickets:write` |
| `administer` | Admin | `members:administer` |
| `own` | Proprietar | `workspace:own` |

## Roluri

Cinci roluri predefinite — **Proprietar, Admin, Membru, Vizualizator, Invitat** —
sunt presetări peste acel catalog. Proprietatea este un singur loc per spațiu de
lucru, cedat explicit prin **Transferă proprietatea** (un proprietar care pleacă
nu mai poate fi eliminat altfel: deprovisionarea SCIM refuză orice proprietar de
spațiu de lucru — transferă mai întâi).

**Rolurile personalizate sunt substractive.** Un rol personalizat numește o
presetare de bază (`admin`, `member`, `viewer` sau `guest` — niciodată `owner`) și
un set de permisiuni ELIMINATE din ea — „admin, dar nu poate gestiona membri”. Nu
poate acorda niciodată mai mult decât baza sa, ceea ce le face sigure de introdus
într-o instalare existentă: fiecare verificare existentă rămâne o limită
superioară validă. Membrii le dețin ca `custom:<id>`, iar un client prea vechi ca
să înțeleagă acea valoare revine la Invitat în loc să ghicească.

Sub roluri stau **permisiunile per repo** (`none` / `read` / `review` /
`write`, vezi [Modificarea codului necesită grantul de scriere](#modificarea-codului-necesită-grantul-de-scriere)):
apartenența la spațiul de lucru nu depășește niciodată în silență
privilegiile forge-ului. Fiecare suprafață care expune cod le verifică — inclusiv
cele care ajung la cod pe ocolite, cum ar fi un terminal sau o sesiune de editor
deschisă pe worktree-ul unui spațiu.

## Codul urmează forge-ul

Un grant singur nu deschide codul unui repository. Ca să vadă fișierele, diff-urile sau rezultatele căutării lui ori să deschidă un terminal pe el, un membru are nevoie de grantul Control Center **și** autentificarea lui în forge trebuie să poată citi repository-ul. Administratorii spațiului de lucru nu sunt scutiți; proprietarul serverului este, pentru că checkout-ul se află pe mașina lui. Un repository fără remote de forge are nevoie doar de grant.

- Când un administrator acordă un repository cuiva al cărui cont din forge nu îl poate citi, grantul este salvat, iar administratorul vede un avertisment.
- Când forge-ul nu poate fi contactat ca să verifice, răspunsul este nu, niciodată o presupunere: persoana vede „Nu s-a putut confirma accesul tău la GitHub. Încearcă din nou.” (cu numele forge-ului ei) și încearcă mai târziu.
- Pull request-urile și tot ce se face din ele urmează aceeași regulă.

### Modificarea codului necesită grantul de scriere

Un grant pe repository are trei niveluri, iar fiecare include nivelul dinaintea lui:

- **citire**: vezi fișierele, diff-urile și rezultatele căutării repository-ului, cu condiția ca autentificarea ta în forge să îl poată citi și ea.
- **revizuire**: citire, plus aprobarea, cererea de modificări și celelalte acțiuni de revizuire asupra pull request-urilor lui.
- **scriere**: revizuire, plus modificarea codului și conducerea rulărilor de agent care scriu în repository. Modificarea codului acoperă salvarea sau anularea fișierelor în editor, sincronizarea unui worktree cu capul pull request-ului, commit-ul și push-ul, publicarea unui branch și acțiunile de stack care taie, fac checkout sau publică o parte.

Fiecare push făcut pentru o persoană, fie de ea, fie de o rulare de agent cerută de ea, verifică grantul ei de scriere pe repository-ul respectiv în momentul push-ului, pe GitHub, GitLab și Bitbucket deopotrivă. Publicarea unui stack verifică fiecare repository din stack înainte să împingă oricare dintre ele.

Un refuz numește grantul care lipsește. Fără acces de citire, aplicația spune „Nu ai acces de citire la acest depozit. Un administrator al spațiului de lucru îl poate acorda.” Cu citire, dar fără scriere, spune „Poți citi acest depozit, dar nu îl poți modifica. Un administrator al spațiului de lucru poate acorda accesul de scriere.”

### Spațiile urmează repository-urile lor

Ce au scris agenții despre cod urmează codul. Conținutul unui spațiu (mesajele, transcrierile și ieșirea uneltelor, rezultatele căutării, jurnalele de rulare, todo-urile, activitatea și notificările) poartă codul repository-urilor cu care lucrează, deci un spațiu se deschide doar pentru un membru care are un grant de citire pe fiecare repository pe care îl folosește spațiul și a cărui autentificare proprie în forge poate citi fiecare asemenea repository. Acestea sunt repository-urile selectate pentru spațiu sau toate repository-urile spațiului de lucru, când nu este înregistrată nicio selecție. Un spațiu creat fără repository-uri este deschis pentru fiecare membru.

Un spațiu pe care cineva nu îl poate deschide nu este listat pentru el nicăieri, inclusiv în căutare, jurnalele de rulare, todo-uri, activitate și notificări. Administratorii spațiului de lucru dețin fiecare grant, dar nu sunt scutiți de jumătatea din forge; proprietarul serverului este.

Pentru o conversație pe care toți ar trebui să o poată citi, creează spațiul fără repository-uri sau doar cu repository-uri pe care toți le pot citi.

## Proprietarul serverului

Persoana care a configurat serverul este **proprietarul** lui. Serverul o înregistrează o singură dată, la prima pornire, iar nimic trimis prin rețea nu schimbă asta. Un administrator sau un proprietar al unui spațiu de lucru nu este proprietarul serverului: oricine poate primi un spațiu de lucru, dar mașina serverului are un singur proprietar.

**Nimic nu rulează pe mașina serverului în afara unui sandbox, dacă proprietarul serverului nu l-a pornit sau nu a aprobat acel fel de execuție pe gazdă.** Concret, doar proprietarul serverului poate:

- Să creeze un spațiu de lucru. Ceilalți văd un ecran care le cere să îi ceară proprietarului să creeze unul sau unui administrator al spațiului de lucru să îi invite.
- Să deschidă shell-ul gazdei în terminalul găzduit pe server. Ceilalți primesc un terminal în sandbox, cu limitele unui agent, în directoarele spațiului de lucru.
- Să deschidă editorul de cod încorporat. Rulează ca utilizatorul propriu al serverului, cu terminalul, sarcinile și extensiile lui.
- Să deschidă un pull request sau worktree-ul unei conversații într-un editor nativ. Editorul pornește pe ecranul serverului, ca utilizatorul serverului.
- Să salveze sau să aprobe o definiție de [mediu](/ro-RO/manual/ghiduri-practice/medii/) care rulează ceva pe gazdă: plasare pe gazdă, o verificare care rulează o comandă sau o sarcină de provisionare ori de arhivare.
- Să ruleze agenți pe un server a cărui mașină nu are sandbox. Rulările celorlalți sunt refuzate acolo, dacă proprietarul nu a pornit serverul cu `--sandbox off`, caz în care agenții fiecărui membru rulează fără izolare (vezi [Agenții pe o gazdă fără sandbox](/ro-RO/manual/concepte/sandbox-si-securitate/#agenți-pe-o-gazdă-fără-sandbox)).
- Să lege un checkout de repository care se află în afara spațiului de stocare al spațiului de lucru, să confirme unul legat înainte de această regulă și să răsfoiască folderele serverului când adaugă un repository (vezi [Adaugă repository-uri](/ro-RO/manual/ghiduri-practice/adauga-repo-uri/)).
- Să vadă și să oprească fiecare proces de agent aflat în rulare pe server. Ceilalți văd și opresc doar rulările live ale agenților din spațiile de lucru din care fac parte.
- Adaugă un server MCP propriu care rulează o comandă pe mașina serverului. Serverele proprii ale celorlalți membri se conectează prin URL (vezi [Serverele tale proprii](/ro-RO/manual/ghiduri-practice/server-mcp/#serverele-tale-proprii)).
- Aprobă un server MCP al spațiului de lucru care rulează o comandă pe mașina serverului sau ajunge la rețeaua lui privată (vezi [Servere din spațiul de lucru](/ro-RO/manual/ghiduri-practice/server-mcp/#servere-din-spațiul-de-lucru)).
- Să confirme adresa de e-mail a unei persoane, ca autentificarea unică să o poată potrivi (vezi [Conectează un furnizor OpenID Connect](/ro-RO/manual/ghiduri-practice/sso-oidc/#cum-se-potrivesc-autentificările-cu-conturile-existente)).
- Să schimbe setările la nivel de instalare: SSO, credențialele providerilor, endpoint-ul MCP și tokenul lui, gestionarea modelelor, Connect și backupurile întregii instalări. Aceste operațiuni declară **autoritate de server** și sunt refuzate pentru toți ceilalți.

Există în mod deliberat o singură identitate de operator și o singură definiție a acesteia.

## Jurnalul de audit

Fiecare decizie de autorizare — **permis și refuzat** — este adăugată într-un
jurnal de audit înlănțuit prin hash, per spațiu de lucru.

Un jurnal doar cu refuzuri răspunde la „ce am blocat?”, dar nu la „ce a făcut de
fapt acest agent și cine a autorizat?”, care este întrebarea de la care pornește o
analiză de incident. Așa că fiecare înregistrare consemnează întregul lanț de
atribuire: principalul care acționează, persoana în numele căreia a acționat,
delegarea prin care a ajuns, acțiunea și argumentele ei (ca digest), decizia și
**regula care a decis**.

Înregistrările sunt înlănțuite: hash-ul fiecăreia îl acoperă pe cel al precedentei,
astfel încât editarea, ștergerea sau reordonarea oricărui rând rupe fiecare hash
de după el. **Verifică lanțul** rederivă totul și numește prima verigă care nu se
susține. Un jurnal de audit pe care nu îl poți verifica este un jurnal; unul pe
care îl poți rederiva este o dovadă.

Două consecințe care merită știute:

- Tabelul de audit este **exceptat de la curățarea bazată pe vechime**. Un lanț de
  hash-uri nu poate fi scurtat din mijloc. Retenția este export-apoi-trunchiere, iar
  trunchierea lasă un punct de control care poartă hash-ul terminal al segmentului
  eliminat, astfel încât ce supraviețuiește se verifică în continuare până la
  început.
- Stă **alături** de cronologia activității, nu peste ea. Cronologia arată ce au
  făcut oamenii; aceasta arată ce a fost autorizat și refuzat. Un id de corelare
  comun permite citirea unui apel în ambele.

Se exportă ca JSON delimitat prin linii noi și poate transmite în flux către un SIEM
(Splunk, Elastic, Sentinel — un endpoint HTTP cu un bearer token). Transmiterea în
flux este, prin proiectare, fără garanții: un SIEM picat nu trebuie să blocheze
niciodată apelul unui instrument de către un agent, iar copia durabilă și
verificabilă este oricum pe disc.

## Sesiuni

O instalare poate stabili o **vârstă maximă a sesiunii** și un **timeout de
inactivitate**. Ambele sunt impuse la verificarea credențialului de dispozitiv
prin care trece fiecare cale autentificată — o sesiune pe care un client ar putea
să o ignore răspunde la un chestionar, nu unui atacator. O instalare poate cere și
SSO, ceea ce dezactivează asocierea manuală pentru dispozitivele noi (cu o
protecție împotriva blocării: refuză cât timp nu există nicio conexiune SSO
funcțională).

## Ce nu este

- **Nu sunt ACL-uri per obiect.** Nu există în mod deliberat o permisiune per
  tichet sau per mesaj. Separarea la nivel de repository este ceea ce cer de fapt
  echipele și ea există; partajarea per obiect este o suprafață combinatorie fără
  cerere demonstrată aici.
- **Nu este un motor de politici pe care îl configurezi într-un DSL.** Vocabularul
  este închis intenționat, astfel încât întreaga politică poate fi redată, explicată
  și enumerată.
- **Nu este impusă nicăieri în afară de server.** Verificările din partea
  clientului există doar pentru a evita oferirea unui control care va fi refuzat.
  Decizia autoritativă este întotdeauna a serverului.
