Un pull request este deja locul unde se petrece conversația despre cod.
Conversațiile PR îl transformă într-o suprafață a unui spațiu de lucru Control
Center, la fel cum o [punte de chat](/ro-RO/manual/concepte/punti-de-chat/)
transformă Slack într-una: menționează `@usectrl` pe un PR, răspunde în firele lui de revizuire sau adaugă
eticheta `ai-review`, iar munca se desfășoară în spațiul de revizuire al
PR-ului — sub aceeași atribuire și aceleași guardrail-uri ca orice text tastat
în aplicație. Un comentariu și o etichetă sunt condiționate la fel: de membrul
care l-a scris sau a adăugat-o. Răspunsurile se întorc pe GitHub, în firul în
care a fost pusă întrebarea.

Trei decizii modelează funcționalitatea și fiecare este aceeași decizie pe care
puntea de chat a luat-o pentru chat, reformulată pentru un host de cod: **în ce
direcție rulează conexiunea**, **ce autorizează un comentariu care sosește din
exterior** și **cui este atribuită fiecare parte**.

## Interogarea periodică este transportul

Singurul canal push al GitHub pentru o aplicație este un webhook, iar un webhook
are nevoie de un URL de intrare — exact lucrul de care această suprafață nu are
niciodată nevoie, în mod deliberat. Așa că descoperirea este o scanare: câte
o căutare aliasată per instalare a aplicației cere de la GitHub PR-urile care
menționează `@usectrl` și PR-urile deschise care poartă
eticheta de revizuire, PR-urilor care au deja un spațiu de revizuire li se citesc
firele de comentarii, iar totul este comparat după id-ul comentariului cu ce s-a
văzut la scanarea anterioară. O aplicație proprie scanează în fiecare minut cel
mult 25 de PR-uri. Prin Connect, apelurile folosesc cota GitHub proprie a
membrilor, așa că scanarea rulează la fiecare două minute peste cel mult 10, iar
un spațiu de lucru sub 15% din cota lui este sărit până se reface. Connect însuși
nu vede niciodată conținutul PR-urilor.

Consecințele de design merită numite:

- **Latența este un interval de scanare, nu un eveniment.** Confirmarea 👀 apare
  în decurs de o scanare. Nimic urgent nu depinde de ea.
- **Exact o dată, per comentariu.** Id-urile comentariilor sunt unice în tot
  GitHub; fiecare este înregistrat în momentul în care este clasificat ca
  eligibil, înainte ca ceva să acționeze asupra lui. O cădere poate pierde
  procesarea unui comentariu, dar nu îl poate declanșa de două ori.
- **Timpul offline este recuperat, nu reluat.** Mulțimea celor văzute este
  persistată, așa că o repornire livrează ce a sosit cât timp serverul a fost
  oprit. Singura excepție este prima scanare din toate timpurile: fără memorie cu
  care să compare, tot ce este în așteptare este înregistrat în silență — un
  operator care a etichetat douăzeci de PR-uri înainte ca acest server să existe
  nu trebuie să se întoarcă la douăzeci de revizuiri în rulare.
- **Eticheta este o mulțime, nu un eveniment.** Căutarea raportează _prezența_
  etichetei, deci un PR etichetat se declanșează o singură dată, pentru
  totdeauna. Re-adăugarea unei etichete după eliminarea ei este invizibilă pentru
  scanare; o mențiune este calea de re-rulare.

Căutarea rulează o dată per cont de instalare, pe clientul propriu al acelui
proprietar, pentru că un token vede doar repository-urile propriei
instalări — o singură acreditare la nivel de server ar rata în silențiu fiecare
PR aflat sub celelalte instalări ale aplicației.

## Apartenența autorizează, nu comentariul

Un comentariu pe un PR sosește purtând un autor — o identitate externă
neautentificată până la proba contrarie. Serverul rezolvă id-ul numeric imuabil
al contului GitHub al autorului (niciodată loginul, care poate fi redenumit și
refolosit) prin autentificările GitHub ale membrilor spațiului de lucru,
reconstruite pe baza unui TTL, pentru că oamenii se autentifică și sunt invitați
cât timp serverul rulează. Pentru eticheta `ai-review`, persoana rezolvată este
cea care a adăugat-o cel mai recent.

Trei verificări, în ordine, iar eșecul oricăreia este tăcut — nu se postează
nimic:

- **Un membru autentificat.** Contul trebuie să aparțină unui membru al
  _acestui_ spațiu de lucru care s-a autentificat în GitHub pe acest server
- **Un rol de scriere.** `viewer` și `guest` nu pot porni muncă
- **Acces de push.** Răspunsurile folosesc un token pentru acel singur
  repozitoriu, limitat la accesul acelui membru la el. Dacă serverul nu poate
  emite unul, nu merge mai departe

Fiecare verificare rulează înaintea oricărei confirmări, așa că un străin nu
primește nicio reacție și niciun răspuns. Un comentariu nu este niciodată
atribuit cuiva care nu l-a trimis, iar vorbele unui străin nu intră niciodată
într-un spațiu de lucru pe care nu îl poate vedea.

### Revendicarea

Ultimul pas înaintea oricărei munci este o reacție 👀, adăugată cu autentificarea
GitHub proprie a autorului. GitHub răspunde `201` pentru o reacție nouă și `200`
pentru una care există deja, așa că reacția servește și ca blocare: când aceeași
persoană este autentificată pe două servere care leagă amândouă repozitoriul,
doar primul care reacționează face munca. Un comentariu pe care îl văd mai multe
spații de lucru de pe același server este oferit fiecăruia, iar aceeași
revendicare decide.

## Două identități, în mod deliberat

Fiecare parte a conversației poartă o identitate diferită, iar diferența este
chiar funcționalitatea:

- **Pe GitHub, răspunsul este automatizare în numele tău.** Fiecare răspuns
  folosește un token pentru acel singur repozitoriu, limitat la accesul
  membrului care întreabă, și este scris de contul `[bot]` al aplicației. Există
  o excepție: pe aplicația comună Control Center Connect, botul postează în
  firele de revizuire doar când operatorul Connect a inclus instalarea pe listă,
  așa că altfel un răspuns dintr-un fir de revizuire este scris de contul propriu
  al membrului care întreabă. În ambele cazuri, fiecare
  răspuns începe cu `**Control Center** (for @login):`, care spune cine a
  întrebat și servește și ca protecție anti-buclă. @-mențiunile din cuvintele
  agentului sunt neutralizate, astfel încât un răspuns nu notifică niciodată un
  utilizator sau o echipă.
- **În spațiu, întrebarea este a ta.** Mesajul este atribuit membrului în care
  s-a rezolvat autorul, iar rularea agentului se execută în numele lui:
  commit-urile rulării sunt ale lui, iar setarea de autonomie a spațiului și
  guardrail-urile de acțiune se aplică exact cum se aplică unui mesaj tastat în
  aplicație. Scrierile către host-ul de cod făcute de rulare folosesc tokenuri
  pentru un singur depozit, limitate de acel membru, niciodată autentificarea
  lui predată întreagă.

Publicarea constatărilor de revizuire înapoi pe GitHub rămâne decizia unei
persoane, luată în Control Center. O mențiune poate _începe_ o revizuire; doar
un om o publică.

## Protecția anti-buclă

Tot ce este scris de un cont de bot este eliminat înainte ca vreo poartă să
ruleze — în mod specific al nostru și orice sufix `[bot]`, așa că nici botul de
revizuire al unei alte aplicații nu îl poate trezi pe al nostru — și la fel orice
comentariu care începe cu prefixul `**Control Center** (for @`, pentru că un
răspuns dintr-un fir de revizuire prin Connect poate fi scris de contul unei
persoane. Fără asta, răspunsurile
ar sosi ca comentarii noi și ar declanșa puntea la nesfârșit.

Doar `@usectrl` pornește lucrul. Login-ul aplicației (`<slug>[bot]`) și slug-ul ei simplu nu adresează nimic: GitHub nu oferă autocomplete pentru un cont de aplicație, iar un slug simplu poate aparține unui utilizator uman.

## Ce nu este oferit în mod deliberat

- **Fără publicare automată.** Constatările ajung în spațiul de revizuire;
  publicarea pe GitHub este o acțiune separată, umană
- **Fără identitate aproximativă.** Autorul se rezolvă la exact un membru sau
  este ignorat — nu există atribuire bazată pe presupuneri
- **Fără aprobare automată.** Automatizarea poate comenta și cere modificări, dar
  o revizuire `APPROVE` este refuzată înainte de a fi trimisă. Aprobarea este
  actul unei persoane
- **Fără webhook de GitHub App.** Această suprafață nu înregistrează niciodată
  unul, așa că nu există niciun URL de intrare de expus pentru comentariile de
  PR. Alte webhook-uri de produs (pipeline-uri, sincronizare de tichete) sunt o
  configurare separată, opțională.
