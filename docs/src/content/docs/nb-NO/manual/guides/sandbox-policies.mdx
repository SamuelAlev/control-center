Om en agentkjøring er sandkasset, avgjøres på serveren, ved oppstart
(`--sandbox`). Bryteren **Slå på sandkasse**, velgeren **Backend** og bryterne
**Standardkapasiteter · nye områder** under **Innstillinger → Server →
Diagnostikk og personvern** er innstillinger som lagres på enheten din.
Sonderingen av verten i **Sandkasse**-kortet rapporterer hva serververten kan
pakke inn.

To kontroller når fram til en kjøring, og denne guiden dekker begge:
**Sandkassetillatelsene** per agent nedenfor og serverens eget
`--sandbox`-flagg.

## Hva som begrenser en agentkjøring

En agent holdes av seks ting. Den første er OS-sandkassen, og den er den eneste
som er betinget — de fem andre holder på alle verter.

| Grense                     | Hva den gjør                                                                                                                                                                                                                                                      |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OS-sandkassen              | Seatbelt på macOS, bubblewrap på Linux og WSL2. Pakker inn Claude Code-CLI-et, ACP-adaptere og harnessets `bash`-verktøy. **Finnes ikke på Windows og på Linux uten `bwrap` og `socat`** |
| Sin egen worktree          | Hver samtale får sin egen copy-on-write-arbeidskopi. Den opprinnelige arbeidskopien legges inn i kjøringen som en skrivenekt-sti, og det er sandkassen som håndhever den                                                                                          |
| Formidlet legitimasjon     | Legitimasjonsmegleren utsteder et miljø per kjøring ut fra agentens kapabiliteter og tilbakekaller det ved avslutning. Ingen kapabilitet, ingen token i miljøet                                                                                                    |
| Tillatelsesregler for handlinger | Hvert muterende verktøy deklarerer effektklassene sine, og vakten løser dem før kallet kjøres. Et `prompt` uten tilkoblet godkjenner nektes                                                                                                               |
| Sanering av miljøet        | ACP og harnessets `bash`-verktøy får et filtrert miljø. Claude Code gjennom `NoSandboxAdapter` arver vertens miljø                                                                                                                                                 |
| Modusens verktøyflate      | En skrivebeskyttet modus fjerner verktøyene som muterer worktreet, helt, og fester modusens eget utdataverb så den fortsatt kan levere                                                                            |

Tre ting er svakere enn de ser ut:

- Bare det **innebygde harnesset** håndhever verktøyporten,
  fullføringskontraktene og de strukturelle modusreglene. Claude
  Code-adapteren gjør det ikke. Nettopp Claude
  Code startes med `--dangerously-skip-permissions`, fordi en
  ikke-interaktiv `claude -p` ellers ville blokkere for alltid på sin egen prompt
  — så Claudes egne lese-, skrive-, redigerings- og bash-kall verken ses eller
  portes av Control Center. Der sandkassen er på, er den grensen rundt dem.
- Harnessets prosessinterne filverktøy (read, write, edit, apply patch, search,
  find, search_files) kjører inne i serverprosessen, så ingen sandkasseprofil
  begrenser dem. Bare `bash`-verktøyet går gjennom den sandkasseinnpakkede
  kommandokjøreren. Disse verktøyene er begrenset av sin egen stibegrensning
  pluss tillatelsesreglene for handlinger.
- På en vert uten backend gjelder den første raden ikke i det hele tatt. ACP og
  harnessets `bash`-verktøy faller tilbake på sanering av miljøet pluss
  kommandopolicyen; Claude Code arver vertens miljø gjennom `NoSandboxAdapter`.
  Serveren sier fra om dette i oppstartsloggen. Sjekk din nedenfor.

## Still inn kapabilitetene til en agent

Dette er den ene kapabilitetskontrollen serveren leser. Den er per agent, og
den avgjør hva legitimasjonsmegleren legger i miljøet til den agenten.

1. Gå til **Innstillinger → Arbeidsområde → Agenter**
2. Velg agenten i listen
3. På fanen **Innstillinger** ruller du ned til **Sandkassetillatelser**
4. Slå på bryteren — teksten på raden endres fra **Bruk standard for
   arbeidsområde**
5. Still inn de fire bryterne:

| Bryter                              | Hva den styrer                                                                                                                                                                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Tillat git push**                 | Med denne av får kjøringen `GIT_ASKPASS=/usr/bin/false` og `GIT_TERMINAL_PROMPT=0`, så en push kan ikke spørre om legitimasjon                                                                                                              |
| **Tillat GitHub API-kall**          | Sammen med **Tillat git push** styrer denne om megleren injiserer GitHub-tokenet som `GH_TOKEN` / `GITHUB_TOKEN`                                                                                                                             |
| **Tillat API-kall for saker**       | Styrer om megleren injiserer `TICKETING_API_KEY`                                                                                                                                                                                            |
| **Tillat generell nettverkstilgang** | Der sandkassen er på, er dette en ekte port for utgående trafikk: med den av er kjøringens tillatelsesliste tom, og hver utgående forespørsel avvises i proxyen. Der det ikke finnes noen backend, registreres den på kjøringen, men blokkerer ingenting en startet prosess gjør |

6. Lagre

Kontrollpunkt: åpne agenten på nytt, og bryteren er fortsatt på med bryterne
dine — et lagret kapabilitetssett går en runde gjennom serveren, og en agent
uten noe faller tilbake på den konservative standarden (push av, GitHub API av,
saker av, nettverk på).

:::caution[To måter dette biter på]
Teksten sier **Bruk standard for arbeidsområde**, men det finnes ingen
kapabilitetsinnstilling på arbeidsområdenivå som serveren leser. En agent med
bryteren av får den innebygde, konservative standarden.

Hver for seg: GitHub-legitimasjonen til kjøringen er alltid bare meglerens — et
repo-begrenset installasjonstoken for GitHub App, eller PAT-reserveløsningen fra
miljøet — aldri det egne lagrede tokenet til medlemmet som ba om kjøringen.
`actingUserId` sendes inn slik at megleren kan *holde tilbake* serverens PAT fra
et medlem som ikke er eieren og ikke har koblet til GitHub; den legger ikke et
personlig token oppå en kapabilitet som er av. Ikke behandle **Tillat GitHub
API-kall** som en hard grense for utgående trafikk på en vert uten
OS-sandkasse: en startet prosess kan fortsatt nå nettverket.
:::

## Sjekk om agentkjøringene dine er sandkasset

To ting avgjør det, begge på serveren: om verten tilbyr en backend, og om
`--sandbox` er på. Sjekk dem i den rekkefølgen.

1. Gå til **Innstillinger → Server → Diagnostikk og personvern**
2. Les **Sandkasse**-kortet. Opplysningen **Vert** er maskinen `cc_server`
   kjører på, ikke maskinen du ser på. Feltet **Backend** viser **Innebygd
   sandkasse** (Seatbelt på macOS, bubblewrap på Linux og WSL2) eller **Ingen
   isolasjon**. Opplysningen **I kraft** er denne enhetens innstilling, ikke
   innpakningen serveren faktisk bruker.
3. Les oppstartsloggen til serveren. Den skriver ut nøyaktig én av tre linjer:
   - `agent sandbox ON` pluss backend-merknaden — kjøringer pakkes inn
   - `no OS-native agent sandbox on this host` pluss et installasjonstips der
     det finnes — kjøringer pakkes ikke inn
   - `agent sandbox DISABLED by --sandbox off` — et bevisst valg om å slå den av

`GET /healthz` rapporterer ikke sandkassetilstand, så oppstartsloggen er
sjekken.

For å slå av sandkassen bevisst — en vert der profilen oppfører seg dårlig, er
grunnen til at muligheten finnes — starter du serveren med `--sandbox off`,
eller setter `CC_SERVER_SANDBOX=off`. Standarden er `on`, og `on` betyr «bruk en
backend hvis verten har én», aldri «krev én».

To situasjoner får aldri en innebygd sandkasseinnpakning. På **Windows**
rapporterer den innebygde sonderingen alltid at den ikke er tilgjengelig, og
det finnes ingenting å installere — agentutsending bruker `none`.
`microvm`-backenden er noe eget (interaktive terminaler og stasjoner) og
avhenger av sin egen sondering av kjøretidsmiljøet. På **Linux og WSL2** må
både `bwrap` og `socat` ligge på `PATH`; uten dem rapporterer sonderingen at den
ikke er tilgjengelig, og navngir pakkene som mangler.

På Linux/WSL2 med bubblewrap installert kan standardpolicyens glob-mønstre for
hemmelige filer ikke håndheves for filer en agent oppretter senere. En slik
innebygd kjøring feiler nå i stedet for å ignorere reglene i stillhet. En
positiv sondering ved oppstart garanterer derfor ikke at en Linux-utsending kan
starte. `--sandbox off` er et bevisst valg om å kjøre uten begrensninger, ikke
en erstatning for en sikkerhetsgrense.

## Vit hva en modus allerede forbyr

Modusen lagres per område og mates inn i regeløseren som laget
**modusforhåndsvalg**. Tre av de fire modusene er skrivebeskyttede, og en
skrivebeskyttet modus avviser elleve effektklasser kontant:

| Modus                    | Worktree       | Avvises av forhåndsvalget                                                                                                                                                        |
| ------------------------ | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent** (`chat`)       | Skrivbar       | Ingenting — de innebygde standardene gjelder                                                                                                                                    |
| **Plan**                 | Skrivebeskyttet | Sletting av en fil, skriving utenfor worktreet, commit, push, oppretting av en PR, publisering eller sammenslåing, skriving til et eksternt oppfølgingssystem, installasjon av en pakke, oppstart av en prosess, endring av strukturen i arbeidsområdet, start eller styring av et isolert miljø |
| **Gjennomgang**          | Skrivebeskyttet | De samme elleve. Ikke brukervalgbart — skrivefeltet tilbyr bare Agent, Plan og Orkestrer                                                                                          |
| **Orkestrer**            | Skrivebeskyttet | De samme elleve                                                                                                                                                                  |

Nettverkstilgang og tilgang til hemmeligheter nektes bevisst _ikke_ av en
skrivebeskyttet modus: forskning er hele poenget med en slik modus.

## Krev godkjenning før en handling kjøres

Godkjenning er et vedtak i tillatelsesreglene, ikke en sandkasseinnstilling.

1. Gå til **Innstillinger → Arbeidsområde → Agenttillatelser**
2. Sett handlingsklassen til **Spør først** på omfanget arbeidsområde, agent
   eller område

Et **Spør først**-vedtak avbryter kjøringen og spør deg. Uten en tilkoblet
godkjenner stenger den ved feil, og handlingen nektes. Se
[Konfigurer tillatelsesregler](/nb-NO/handbok/slik-gjor-du/konfigurer-tillatelsesregler/) for hele
løsningsrekkefølgen.

## Feilsøking

### En agent kan ikke pushe, og jeg nektet det aldri

Sjekk **Sandkassetillatelsene** til agenten. En agent uten et egendefinert
kapabilitetssett får den konservative standarden, der **Tillat git push** er av
— så megleren injiserer ingen GitHub-token, og git har ingen måte å autentisere
seg på.

### Sandkasse-kortet rapporterer ingen innebygd sandkasse

Da er ikke agentkjøringer på den verten pakket inn av Seatbelt eller bubblewrap,
og de gjenværende grensene er det du har. På Linux og WSL2 installerer du begge
verktøyene som mangler — `sudo apt-get install bubblewrap socat` — og starter
serveren på nytt; oppstartsloggen skal da si at sandkassen er på. På Windows
finnes det ingen innebygd backend å installere, så stram inn
tillatelsesreglene i stedet: se
[Konfigurer tillatelsesregler](/nb-NO/handbok/slik-gjor-du/konfigurer-tillatelsesregler/).

### En agent nådde en fil utenfor worktreet

Hvilket verktøy som nådde den, avgjør om dette er forventet.

Harnessets prosessinterne filverktøy (read, write, edit, apply patch, search,
find, search_files) kjører i serverprosessen, så ingen sandkasseprofil gjelder
for dem — grensen deres er deres egen stibegrensning pluss tillatelsesreglene.
En `bash`-kommando eller Claude Code-CLI-et _blir_ pakket inn der en backend
finnes, og de registrerte arbeidskopiene dine er skrivenekt innenfor den
innpakningen i hver modus, inkludert stavemåtene deres med symlenker løst opp
(på macOS løses en sti nådd gjennom `/tmp` eller `/var/folders` opp under
`/private`, og begge stavemåtene nektes nå). På en vert uten backend gjelder
ingenting av dette. Uansett kan tillatelsesreglene avvise **Skriv utenfor
worktree** kontant.
