Denne veiledningen viser hvor hver påloggingsinformasjon Control Center bruker,
er lagret, og hvordan du endrer den.

**Ingenting lagres på maskinen du skriver på.** All påloggingsinformasjon ligger
på serveren; hvilken av dem som besvarer en gitt forespørsel, avhenger av om det
står et menneske bak den.

| Påloggingsinformasjon                  | Lagret på                                                   | Hvem bruker den                                                    |
| -------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------ |
| Påloggingsinformasjonen din for kodevert/saker | Serverens hemmelighetsfil med modus 0600, knyttet til bruker-id-en din | Alt du ber om: PR-flaten, agentkjøringene dine, bildene dine |
| Serverens app-identitet                | Samme fil, pluss `server_settings` for det som ikke er hemmeligheter | Arbeid ingen har bedt om: webhooker, PR-polling, sakssynkronisering |
| Nøkler til modellleverandører og OAuth-tokens | Serverens eget lager for påloggingsinformasjon       | Den innebygde adapteren, for alle arbeidsområder i installasjonen  |
| Slack-bot-tokens                       | `<dataDir>/<workspaceId>/chat_credentials/` på serveren    | Chatbroen for det arbeidsområdet                                   |
| Påloggingsinformasjon for eksterne CLI-er | Det den CLI-en selv bruker                              | Claude Code, på serververten                                       |

## To sett med GitHub-påloggingsinformasjon, og de svarer på forskjellige spørsmål

- **Din**, fra innlogging (enhetsflyt) eller ved å lime inn et token. Den brukes
  av enhver forespørsel som gjøres *på dine vegne*, så en kommentar som postes
  for deg, bærer navnet ditt. Andre medlemmer kan ikke lese den, og kobler til
  sin egen
- **Serverens**, fra GitHub App-en operatøren registrerte. Den svarer på alt
  uten noen oppringer — så tilgangen til kodeverten forsvinner ikke når én
  person slutter eller roterer et token

Din settes i kortet **Kodehosting** under **Innstillinger → Arbeidsområde →
Profil og identitet**; serverens i **Leverandørapper** under **Innstillinger →
Server → Enkel pålogging**. Se
[Sett opp GitHub-integrasjon](/nb-NO/handbok/slik-gjor-du/github-integrasjon/)
og [Opprett GitHub App](/nb-NO/handbok/slik-gjor-du/github-app/).

:::note[Det finnes også en skjerm som bare nås via URL-en]
`/workspaces/<workspaceId>/api-keys` viser de samme to kortene som første steg i
onboarding. Den har **ingen navigasjonsoppføring noe sted i grensesnittet**; den
nås bare ved å skrive inn URL-en. Bruk Innstillinger → Arbeidsområde → Profil og
identitet i stedet.
:::

## Sett nøkler for modellleverandører

Den innebygde adapteren autentiserer leverandørene selv, og denne
påloggingsinformasjonen ligger på serveren.

1. Gå til **Innstillinger → Server → Modellleverandører**
2. Rull ned til **Leverandører og modeller**
3. Koble til leverandøren — OAuth i nettleseren for OpenAI, Codex, Cursor og Kimi
   Code; en API-nøkkel for Anthropic og resten

Se [Administrer adaptere og modeller](/nb-NO/handbok/slik-gjor-du/adaptere/) for
hele listen og for å legge til et egendefinert endepunkt.

Denne påloggingsinformasjonen er **vertsglobal**: én nøkkel betjener alle
arbeidsområder i installasjonen. OAuth-tokens fornyes før de utløper.

Eksterne adapter-CLI-er beholder sin egen påloggingsinformasjon, i sin egen
konfigurasjon, på serververten — Control Center administrerer dem ikke.
Autentiser Claude Code slik dens egen dokumentasjon beskriver, på maskinen der
`cc_server` kjører.

Dialogen **Miljøvariabler** per adapter ser ut som et sted å legge inn en nøkkel
for en av dem, men det er den ikke: den skriver til enheten din, mens serveren
leser sin egen kopi, og ingenting bygger bro mellom de to. Se
[Administrer adaptere og modeller](/nb-NO/handbok/slik-gjor-du/adaptere/).

## Koble til en saksleverandør

Kortet **Saker** under **Innstillinger → Arbeidsområde → Generelt** rommer begge
halvdelene av én beslutning: hvilken leverandør sakene dine ligger hos, og
påloggingsinformasjonen for den. Velger du **Lokal**, skjules raden med
påloggingsinformasjon — lokale saker ligger i serverens egen database og har
ingenting å autentisere seg mot.

Nøkkelen din lagres på serveren knyttet til bruker-id-en din, som
kodevertnøkkelen. Serveren holder sin egen Linear-nøkkel separat
(**Leverandørapper**), og det er den sakssynkroniseringen kjører på når ingen
har bedt om det. En nøkkel en agent mottar, injiseres bare når agenten har
kapasiteten **Tillat API-kall for saker**. Se
[Sett opp Linear-integrasjon](/nb-NO/handbok/slik-gjor-du/linear-integrasjon/).

## Roter eller tilbakekall

- **Din GitHub-påloggingsinformasjon**: trykk **Koble fra**, og logg deretter inn
  på nytt eller lim inn det nye tokenet. Tilbakekall det gamle på GitHub
- **Serverens app**: generer en ny privat nøkkel eller klienthemmelighet på
  appens GitHub-side, lim den inn under **Leverandørapper** og trykk **Test**
- **En modellleverandør**: i raden dens, logg ut (OAuth) eller fjern nøkkelen, og
  koble til på nytt
- **Slack**: lim inn tokenene på nytt i tilkoblingsdialogen. Se
  [Sett opp Slack-integrasjon](/nb-NO/handbok/slik-gjor-du/slack-integrasjon/)

## Feilsøking

### PR-listen er tom, men tokenet mitt virker i `curl`

Sjekk undertittelen til raden **Kodehosting**. Hvis den navngir en annen kilde
(«via denne serverens app», «fra miljøet»), er det ikke
påloggingsinformasjonen du tester som svarer — din ble ikke lagret.

### Tokenet godtas, men senere forespørsler mislykkes

Tokenet sondères slik det er lagret, så raden navngir kontoen bak det — men bare
kontoen, ikke skopene. Et token med for få skop kobler til og mislykkes
deretter på enkelte forespørsler. Sjekk skopene og utløpsdatoen:

```bash
curl -H "Authorization: token YOUR_TOKEN" https://api.github.com/user
```
