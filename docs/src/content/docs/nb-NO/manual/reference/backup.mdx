Alt Control Center kan kopiere, overlevere eller ta i bruk, og den nøyaktige formen til
hvert artefakt. For å faktisk ta en sikkerhetskopi, se
[Sikkerhetskopier og gjenopprett](/nb-NO/handbok/slik-gjor-du/sikkerhetskopier-og-gjenopprett/); for hvorfor lagringen er
delt opp slik, se [Arbeidsområder og isolasjon](/nb-NO/handbok/konsepter/arbeidsomrader/).

## Artefakter

Det finnes tre artefakter for databaskopiering, med ulikt omfang og ulik slettepolicy.

| Artefakt                     | Skrevet av                    | Form                                   | Dekker                          |
| ---------------------------- | ----------------------------- | -------------------------------------- | ------------------------------- |
| **Installasjonsøyeblikksbilde** | `server.backupNow`         | En tidsstemplet **mappe**              | Hver database i installasjonen  |
| **Workspace backup**         | `Workspace backup`-pipelinen  | Tidsstemplet mappe med én `.db`        | Databasen til ett arbeidsområde |
| **Arbeidsområdeeksport**     | `workspace.export`            | Én enkelt `.db`-**fil**                | Databasen til ett arbeidsområde |

Alle skrives med SQLite `VACUUM INTO`, som er trygt mot en aktiv WAL-database:
det tar en lesetransaksjon, lager en defragmentert og transaksjonskonsistent
kopi, og krever aldri at serveren stoppes.

Disse filene og nedlastede kopier **krypteres ikke i ro** av Control Center. Den
ende-til-ende-krypterte overføringen beskytter byter underveis mellom en paret
klient og dens `cc_server`, enten på direkte tilkoblinger eller på relébaserte
tilkoblinger. Beskytt lokal lagring og kopier utenfor maskinen separat; serveren
og enhver autorisert mottaker kan lese databasefilene.

## Oppsettet av et øyeblikksbilde

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Oppsettet speiler den aktive datamappen nøyaktig, og det er dette som gjør at
gjenoppretting av en installasjon er en tilbakekopiering i stedet for en oversettelse.
Mappenavnet er UTC-tidsstempelet med `:` og `.` erstattet av `-`, så det er
filsystemtrygt på Windows og sorterer kronologisk som en vanlig streng.

Planlagte arbeidsområdesikkerhetskopier ligger separat på
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Hver har en `manifest.json` for den ene filen og ingen `global.db`. De er ikke
installasjonsøyeblikksbilder. En gjenoppretting beholder databasen den erstatter på samme sted, som `<timestamp>-pre-restore`. Oppbevaringstrinnet i den ukentlige pipelinen fjerner
bare sikkerhetskopier av sitt eget arbeidsområde som er eldre enn den konfigurerte
alderen (30 dager som standard); manuelt opprettede installasjonsøyeblikksbilder
roteres aldri av det trinnet. `server.listBackups` lister bare
installasjonsøyeblikksbilder, inkludert uverifiserte; `workspace.listBackups` lister de
planlagte sikkerhetskopiene til ett arbeidsområde.

Når et arbeidsområde slettes, blir denne mappen stående. Arbeidsområdets plan stopper
sammen med det, så ingenting roterer disse sikkerhetskopiene lenger, og de blir liggende
til installasjonseieren fjerner dem. `server.listOrphanedBackups` rapporterer dem.


### `manifest.json`

| Felt                       | Type            | Betydning                                                           |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                  | heltall         | Manifestformat. For tiden `2`                            |
| `created_at`               | ISO-8601 UTC    | Når øyeblikksbildet ble tatt                                        |
| `global`                   | object          | Posten for `global.db`. Finnes ikke i en planlagt arbeidsområdesikkerhetskopi |
| `workspaces[]`             | array           | Én post per fanget arbeidsområde                              |
| `workspaces[].workspace_id`| streng          | Arbeidsområdet denne filen tilhører                                 |
| `skipped_workspaces[]`     | array           | Arbeidsområder sikkerhetskopien **ikke** kunne fange                  |
| `skipped_workspaces[].workspace_id` | streng | Arbeidsområdet som ble utelatt                                     |
| `skipped_workspaces[].reason` | streng       | `no_file`, `damaged` eller `failed`                                    |

`global` og hver post i `workspaces[]` registrerer én kopiert fil, målt på kopien
etter at den var skrevet:

| Felt             | Type   | Betydning                                                                      |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`                     | streng          | Sti relativ til øyeblikksbildets rot: `global.db` eller `<workspaceId>/workspace.db` |
| `bytes`       | heltall         | Størrelsen på kopien                                             |
| `sha256`         | streng | SHA-256 av kopien, i små heksadesimale tegn                                    |
| `quick_check`    | streng | Resultatet av SQLites `quick_check` for kopien: `ok`, eller det som ble funnet |
| `user_version`   | heltall | Skjemaversjonen til kopien                                                   |
| `application_id` | heltall | SQLite `application_id` for kopien                                           |

Et arbeidsområde hoppes over når det er registrert, men aldri er blitt skrevet til (`no_file`), når databasen ikke består integritetssjekken (`damaged`; en skadet kopi tas aldri), eller når kopien eller sjekken av den mislyktes (`failed`). Uansett fullføres øyeblikksbildet, og manifestet navngir det som mangler. Manifestet skrives sist.

### Fullstendighet

`server.listBackups` rapporterer et `complete`-flagg per øyeblikksbilde. Det er usant når manifestet mangler, ikke kan leses eller har et annet format, når en fil det navngir mangler eller har en annen størrelse, eller når en kopi ikke besto sin sjekk. Appen viser et slikt øyeblikksbilde som **Ikke verifisert**. Øyeblikksbilder tatt før format `2` er i den tilstanden.

Et uverifisert øyeblikksbilde listes likevel, fordi et øyeblikksbilde en operatør ikke
kan se, er et øyeblikksbilde de tror de har. Når manifestet ikke kan leses, faller
listen tilbake på selve oppsettet og rapporterer de `<workspaceId>/workspace.db`-filene
den finner — de kan fortsatt tas i bruk én og én gjennom `workspace.import`, selv om
øyeblikksbildet som helhet ikke kan gjenopprette en installasjon.

Et oppført øyeblikksbilde eller en planlagt sikkerhetskopi har `pinned_reason: "last_good_copy"` så lenge den holder den nyeste verifiserte kopien av et arbeidsområde hvis database er skadet. Oppbevaringstrinnet hopper over den til det arbeidsområdet er gjenopprettet.

## Hva en sikkerhetskopi ikke inneholder

Begge artefaktene er **bare databaser**. En arbeidsområdemappe inneholder mer enn
databasen sin, og ingenting av resten blir med:

| Sti                                 | I et øyeblikksbilde? | I en arbeidsområdeeksport? |
| ----------------------------------- | -------------------- | -------------------------- |
| `global.db`                         | Ja                   | Nei                        |
| `<workspaceId>/workspace.db`        | Ja                   | Ja (den *er* filen)        |
| `<workspaceId>/code_index.db`        | Nei                  | Nei                        |
| `<workspaceId>/blobs/`              | Nei                  | Nei                        |
| `<workspaceId>/skills/`             | Nei                  | Nei                        |
| `<workspaceId>/agents/`             | Nei                  | Nei                        |
| `<workspaceId>/chat_credentials/`   | Nei                  | Nei                        |
| `<workspaceId>/spaces/<spaceId>/`   | Nei                  | Nei                        |
| `<workspaceId>/pr_clones/`          | Nei                  | Nei                        |
| `secrets.json`                      | Nei                  | Nei                        |
| `models/`                           | Nei                  | Nei                        |
| `meetings/<meetingId>/`             | Nei                  | Nei                        |
| `rigs/`                             | Nei                  | Nei                        |
| `_agent_hooks/`                     | Nei                  | Nei                        |

Noe av dette kan kastes — `spaces/` inneholder copy-on-write-worktrees som provisjoneres på nytt fra repoene, `pr_clones/` er en cache, `code_index.db` bygges på nytt, `models/` lastes ned på nytt, og `rigs/` er maskintilstand. Annet kan ikke det: `blobs/` inneholder innlimte bilder som rader i databasen peker på, `skills/` og `agents/` inneholder filene en agent kjører med, og `secrets.json` inneholder hver parringsnøkkel, hver leverandørlegitimasjon og hver SSO-innstilling i installasjonen. Se [Sikkerhetskopier og gjenopprett](/nb-NO/handbok/slik-gjor-du/sikkerhetskopier-og-gjenopprett/#kopier-sikkerhetskopier-ut-av-maskinen) for å dekke resten.
:::note[Hemmeligheter holdes utenfor databasene]
`workspace.db` er hele arbeidsområdet: samtaler, kjøringslogger, repolenker, miljødefinisjoner og medlemmer. Webhook-tokener for pipelinen og webhook-hemmeligheter for sakssynkronisering ligger i `secrets.json`: databasen inneholder en referanse til hver, og ruteindeksen inneholder en nøkkelhash av hvert token. Et arbeidsområde som gjenopprettes på en annen installasjon, mottar derfor ingen webhooks før utløserne lagres på nytt der. Leverandørpålogginger, enhetsnøkler og brukerhemmeligheter ligger i `global.db` og `secrets.json`.
:::

:::note[Chat-tokens blir bevisst liggende igjen]
At `chat_credentials/` ligger ved siden av databasen i stedet for inne i den, er grunnen
til at et arbeidsområde som overleveres til noen andre, ikke har noen aktive bot-tokens
med seg. Se [chatbro-referansen](/nb-NO/handbok/referanse/chatbro/).
:::

## Operasjoner

Sikkerhetskopi-RPC-ene for installasjonen og eksport/import av arbeidsområder er bare
for `fullClient`: en paret telefon kan ikke utløse dem. Alle mangler helt — ikke avvist,
men strukturelt fraværende — på en server der ingen sikkerhetskopiport er koblet til,
for eksempel demoserveren.

| Op                   | Type   | Omfang    | Minste rolle | Argumenter    | Returnerer                    |
| -------------------- | ------ | --------- | ------------ | ------------- | ----------------------------- |
| `server.backupNow`   | mutate | Installasjon | installasjons**eier** | ingen  | `{ok, path}`                  |
| `server.listBackups` | read   | Installasjon | installasjons**eier** | ingen  | `{backups: [...]}`            |
| `server.deleteBackup` | mutate | Installasjon | installasjons**eier** | `name` | `{ok}`         |
| `server.listOrphanedBackups` | read | Installasjon | installasjons**eier** | ingen | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutate | Installasjon | installasjons**eier** | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | read | Arbeidsområde | `admin` | ingen | `{backups: [...]}` |
| `workspace.deleteBackup` | mutate | Arbeidsområde | `owner` | `name` | `{ok}` |
| `workspace.export`   | read   | Arbeidsområde | `admin`   | ingen         | `{ok, path}`                  |
| `workspace.import`   | mutate | Arbeidsområde | `owner`, og serverens eier | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | read | Arbeidsområde | `owner`, og serverens eier | ingen | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutate | Arbeidsområde | `owner`, og serverens eier | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | mutate | Installasjon* | `owner`  | `id`          | registerrad merket som slettet |

* `workspace.delete` er uten omfang fordi raden den markerer, ligger i det globale
registeret; behandleren sjekker at den som kaller, er medlem av det navngitte
arbeidsområdet, og krever `owner`.

`path` i hvert svar er en sti på **serververten**.

`server.listOrphanedBackups` returnerer én oppføring per arbeidsområde som ikke lenger er
aktivt: `workspace_id`, `workspace_name` når registeret fortsatt kjenner det, og `backups`.
Et slettet arbeidsområde kan ikke lenger bestå en rollesjekk for arbeidsområdet, så
sikkerhetskopiene tilhører installasjonseieren. `server.deleteOrphanedBackup` avviser et
aktivt arbeidsområde, der sikkerhetskopiene forblir bak `workspace.deleteBackup` og
arbeidsområdets egne roller. Begge sletteoperasjonene godtar bare et listet mappenavn med
tidsstempel, ikke en sti.

`workspace.importHolds.list` returnerer det som en import holdt tilbake. Hver tilbakeholdelse har en `id`, en `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` eller `invite`), `payload` den ville satt tilbake, `imported_at` og `source_install_id`. `workspace.importHolds.resolve` med `accept: true` gir den tilbake, og med `false` fjerner den. `applied` er false når den eller det tillatelsen gjaldt, ikke lenger finnes i arbeidsområdet.

:::note[Et øyeblikksbilde av hele installasjonen krever eier på begge baner]
`server.backupNow`, `server.listBackups` og `server.deleteBackup` krever
installasjons**eieren** (`ServerAuthority.serverOwner`), samme sperre som
`GET /backup/snapshot`. Et øyeblikksbilde fanger databasen til hvert arbeidsområde, så
det å være admin i ett arbeidsområde er ikke nok til å administrere de andre. Sletting
godtar bare det opplistede tidsstempelmappenavnet, ikke en vilkårlig serversti, og
fjerner hele øyeblikksbildet (inkludert uverifiserte øyeblikksbilder).
Nedlasting av eksport og planlagte sikkerhetskopier per arbeidsområde holder seg til arbeidsområde-admin.
:::

:::note[Gjenoppretting er serverens eiers]
`workspace.import` og `POST /backup/restore` får serveren til å overta en databasefil hvis rader den deretter behandler som sine egne: repolenker og hvem som laget dem, miljødefinisjoner som kjører på verten, worktree- og loggbaner. Derfor krever begge installasjonseieren (`ServerAuthority.serverOwner`), som også må være arbeidsområdets eier. Alle andre, og alle kallere på en vert uten registrert eier, avvises med `server_owner_required`. Ingen utløser, visning, kolonne eller begrensning som filen medbringer, blir overtatt.
:::

### Svaret fra `server.listBackups`

Nyeste først, sortert etter mappenavn (som er tidsstempelet, så rekkefølgen holder selv
for et øyeblikksbilde der manifestet ikke kunne leses).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` utelates når manifestet ikke kunne leses. `bytes` på toppnivå er den
virkelige størrelsen på disken for hele mappen, ikke manifestets egen sum — spørsmålet
en operatør som rydder i øyeblikksbilder stiller, er hva mappen koster, ikke hva
sikkerhetskopien hadde tenkt å skrive.

Hver `workspaces[].path` er nøyaktig det `workspace.import` tar som `source_path`. Det
er bevisst: «gjenopprett dette arbeidsområdet fra dette øyeblikksbildet» *er*
importoperasjonen, så de to kan ikke gli fra hverandre til ulik behandling av samme fil.

### Validering i `workspace.import`

Før noe erstattes, kopieres kandidatfilen til en mellomlagringsfil ved siden av målet og kontrolleres der. En avvisning berører ingenting, og den bærer sin type som `data.kind`.

| Vilkår                                           | Resultat                                                        |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| Filen finnes ikke | Avvist, `import.missing_source` |
| Ikke en lesbar SQLite-database, eller den består ikke `quick_check` | Avvist, `import.damaged` |
| Den kommer fra et øyeblikksbilde, og SHA-256-verdien avviker fra manifestets | Avvist, `import.checksum_mismatch` |
| En nyere versjon av serveren skrev den | Avvist, `import.newer_schema` |
| En annen `application_id`, eller ingen `workspace_meta` | Avvist, `import.foreign_file` |
| Den kan ikke bringes over til denne serverens skjema | Avvist, `import.schema_mismatch` |
| Webhooks eller invitasjoner i den rutes allerede til et annet arbeidsområde | Avvist, `import.route_conflict` |
| Registrert arbeidsområde-id ≠ målet              | **Tillatt**. Radene nøkles på nytt til målet. Det er slik et arbeidsområde dupliseres eller gjenopprettes under en ny id |
| Registrert installasjons-id ≠ denne installasjonen | **Tillatt**. Bruker-id-ene tilhører den installasjonen og vil ikke la seg løse her |

Ved godkjenning bringes den mellomlagrede filen til denne serverens skjema, og den må deretter samsvare med det nøyaktig. Tillatelser en fil ikke kan gi seg selv, fjernes fra den: godkjenninger til å kjøre en miljødefinisjon på verten fjernes, og handlingsregler som tillater eller spør, sandkasse-kjøretillatelser, repotillatelser over lesetilgang, roller over medlem og invitasjoner til disse rollene blir tilbakeholdelser som serverens eier skal gjennomgå. Den som importerer, beholder eller får eierrollen. Databasen som erstattes, beholdes som en planlagt sikkerhetskopi med navnet `<timestamp>-pre-restore`, den mellomlagrede filen flyttes til sin plass med arbeidsområdets tilkoblinger lukket, `code_index.db` slettes for å bygges på nytt, og FTS-indeksene bygges på nytt.

## Overføringsruter

Eksport-/import- og listoperasjonene for øyeblikksbilder ovenfor snakker om stier på
serversiden, noe som bare er et fullstendig svar når serveren er din egen maskin. Disse
HTTP-formede rutene frakter sikkerhetskopibyter **inne i den samme autentiserte,
ende-til-ende-krypterte ressurskanalen** som andre sensitive ressurser, enten
RPC-tilkoblingen er direkte eller formidlet. De er ikke offentlige
HTTP-filoverferingsendepunkter: en forespørsel til en av dem på den offentlige lytteren
returnerer `426 Upgrade Required`, også fra loopback. I den krypterte tunnelen må
enheten som er autentisert med Noise, samsvare med `d`; behandleren sjekker i tillegg
enhetens signatur over målstrengen med dens parings-PSK og rollen nedenfor.

| Rute                    | Metode | Spørring        | Signert mål                    | Krever                  |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | Arbeidsområde**admin** |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | Installasjons**eier**  |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | Arbeidsområde**admin**; installasjons**eier** når arbeidsområdet er slettet |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | Installasjons**eier** som også er arbeidsområdets **eier** (`403` med `server_owner_required` ellers) |

`w` er en arbeidsområde-id, `n` et mappenavn for et øyeblikksbilde eller en planlagt
sikkerhetskopi, `d` id-en til enheten som kaller, og `s` signaturen. På `/backup/snapshot`
løses `n` mot sikkerhetskopilisten i stedet for å settes sammen med sikkerhetskopiroten, så
ruten kan ikke rettes mot en mappe listen ikke ville ha vist. På `/backup/stored` må det
være et tidsstempelnavn, og filen må være en faktisk fil inne i det arbeidsområdets egen
sikkerhetskopimappe.

| Status | Årsak                                                                               |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | En påkrevd spørringsparameter mangler, et sikkerhetskopinavn er ugyldig, opplastingskroppen er tom, eller den opplastede filen ble avvist (kroppen er `{error, kind}` med en `import.*`-type) |
| `403`  | Ukjent eller tilbakekalt enhet, dårlig signatur, eller den som kaller, mangler rollen |
| `404`  | Ingen sikkerhetskopiport på denne verten, eller den navngitte filen for øyeblikksbildet, sikkerhetskopien eller arbeidsområdet finnes ikke |
| `405`  | `/backup/restore` kalt med noe annet enn `POST`                                      |
| `413`  | Opplastingskroppen overskrider 8 GiB, enten etter oppgitt content-length eller etter byter som faktisk er lest |
| `426`  | Enhver direkte forespørsel til en overføringssti på den offentlige HTTP-lytteren; bruk en paret klients krypterte ressurskanal |
| `500`  | Eksporten eller arkiveringen mislyktes på serversiden                                |

Alle tre nedlastingene svarer `Cache-Control: no-store` med `Accept-Ranges: none`.
`/backup/workspace` og `/backup/snapshot` lager en **fersk** kopi per forespørsel og sletter
den så snart den er strømmet ut, så et bufret eller gjenopptatt svar ville skjøte sammen
byter fra to ulike eksporter til én fil som ser gyldig ut, men ikke er det.

`/backup/stored` er unntaket: den strømmer en planlagt sikkerhetskopi som
`<workspaceId>-<name>.db` og lar filen ligge, fordi den filen er sikkerhetskopien.

`/backup/snapshot` returnerer `<name>.zip`, med oppføringer relative til
øyeblikksbildets rot, slik at utpakking gjenskaper `manifest.json` + `global.db` +
`<workspaceId>/workspace.db`. Oppføringene skrives i sortert rekkefølge, så to arkiver
av samme øyeblikksbilde er det samme arkivet.

`/backup/restore` strømmer kroppen rett til en mellomlagerfil i stedet for å bufre den,
begrenser den før og under lesingen, og sletter den mellomlagrede filen på **enhver**
vei ut, også ved en avvisning.

::::caution[Direkte og relé bruker den samme krypterte overføringen]
Reléet frakter ressursforespørsler, strømmede svar og opplastingsbyter som
chiffertekst; det kan ikke lese sikkerhetskopiinnhold. En sti på serversiden er
fortsatt en sti på serververten, ikke en fil på reléet. Tilgang krever fortsatt
den parede enheten, mål signaturen og den gjeldende arbeidsområde- eller
installasjonsrollen. Ingen av transportene krypterer de resulterende
sikkerhetskopifilene i ro.
::::

## Stier og grenser

| Ting                           | Verdi                                                        |
| ------------------------------ | ------------------------------------------------------------ |
| Øyeblikksbilder                | `<dataDir>/backups/<timestamp>/`                             |
| Planlagte arbeidsområdesikkerhetskopier | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Arbeidsområdeeksporter          | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Database erstattet av en gjenoppretting | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Databaser slik de var før en oppdatering endret formatet deres | `<dataDir>/pre_upgrade/` og `<dataDir>/<workspaceId>/pre_upgrade/`, de to nyeste av hver |
| Overføringsmellomlager         | `<dataDir>/backups/transfer/` — en arbeidsbenk, feid av ruten som skriver den |
| Navn på øyeblikksbildearkiv     | `<snapshot directory name>.zip`                              |
| Opplastingsgrense              | 8 GiB per kryptert `/backup/restore`-opplasting              |
| Oppbevaring                    | Installasjonsøyeblikksbilder: manuell sletting. Arbeidsområdesikkerhetskopier: ukentlig pipeline, 30 dager som standard, eller manuell sletting. Sikkerhetskopier av et slettet arbeidsområde: bare manuell sletting |

Mappene `exports/`, `transfer/` og `workspace-backups/` er ikke
installasjonsøyeblikksbilder og holdes utenfor `server.listBackups`. Bare den siste
mappen har planlagt oppbevaring, og bare så lenge arbeidsområdet finnes; å slette et
installasjonsøyeblikksbilde krever en uttrykkelig handling fra installasjonseieren.
