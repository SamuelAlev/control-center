Control Center ist eine Desktop-App, aber die Arbeit, die sie verfolgt, hört
nicht auf, wenn du vom Schreibtisch weggehst. Die **Fernsteuerung** koppelt
dein Telefon mit deinem `cc_server` über **[Remote](https://remote.usectrl.dev/)**,
die Begleit-App auf remote.usectrl.dev. Von dort folgst du der Flotte:
Nachrichten und Tickets lesen, einem Agenten antworten, deinen Newsfeed
triagieren — über eine Ende-zu-Ende-verschlüsselte Verbindung. Telefon und
`cc_server` sind vertrauenswürdige Klartext-Endpunkte; ein Relay überträgt nur
verschlüsselte Anwendungsdatensätze.

Stell sie dir als Begleiter vor, der vor allem liest, neben der Arbeitsfläche.
Den vollständigen Desktop-Client soll sie nicht ersetzen.

:::note[Zwei verschiedene entfernte Clients]
Die Telefon-Begleit-App und der vollständige **Web-Build** (oder ein Desktop,
der auf einen entfernten Server zeigt) können sich direkt mit `cc_server`
verbinden oder ein vermitteltes WebSocket-Relay nutzen. Beide Wege erfordern
dieselbe verschlüsselte Sitzung; das Telefon bietet einen kleineren Satz von
Operationen als der vollständige Client. Wie sich die Clients unterscheiden,
steht unter
[Bereitstellung und Clients](/de-DE/handbuch/konzepte/bereitstellung/).
:::

## Transport

Das Telefon erreicht `cc_server` über eine WebSocket-Verbindung: entweder
direkt (Loopback, LAN, Tailnet oder `wss://`) oder über einen
einladungsgeschützten Raum auf einem Signalisierungs-Broker. Beide Wege
erfordern eine authentifizierte, Ende-zu-Ende-verschlüsselte Sitzung; der
Broker leitet nur seine verschlüsselten Datensätze weiter. Einen
Peer-to-Peer-Datenkanal gibt es nicht.

## Was das Telefon kann

Das gekoppelte Telefon erreicht einen kleinen, absichtlich engen Ausschnitt
der Serveroberfläche:

- **Lesen**: Tickets, Agenten, Bereiche und ihre Nachrichten, und deinen
  Newsfeed
- **Antworten**: eine Nachricht in einem Bereich senden, ein Ticket
  aktualisieren oder zuweisen, einen Artikel als gelesen oder gespeichert
  markieren
- **Ein Playbook ausführen**: eine gespeicherte Planvorlage mit ihren
  Parametern instanziieren. Das _schlägt_ nur einen Plan vor; nichts läuft
  und nichts wird ausgegeben, bis jemand ihn in Plan-Studio auf einem
  vollständigen Client freigibt
- **Arbeitsbereiche wechseln**, über die eigene Auswahl auf dem Telefon

Mehr ist es kaum. Ein Telefon ist ein **Prinzipal mit geringeren Rechten**
als ein vollständiger Client. Es kann keine Prozesse starten, kein LLM-Budget
ausgeben, nichts zu GitHub schieben und keine Arbeitsbereiche anlegen. Wie
das durchgesetzt wird, steht im
[Zugriffsmodell](#das-zugriffsmodell).

## Wie die Verbindung entsteht

Wenn das Telefon den Server nicht direkt erreicht, nutzt die Verbindung ein
**vermitteltes Relay**: Der Server betritt als Eigentümer einen
einladungsgeschützten Raum auf einem `wss://`-Broker, und gekoppelte Clients
betreten ihn mit befristeten Einlass-Tokens. Drei Teile greifen ineinander:

| Teil | Aufgabe |
| --- | --- |
| **Remote (Telefon-App)** | Die Begleit-Web-App, standardmäßig auf `remote.usectrl.dev` gehostet oder selbst gehostet. Sie lädt im Browser und hält den Kopplungsdatensatz in IndexedDB. |
| **Relay-Broker** | Ein zustandsloses `wss://`-Relay (`cc_signaling_server`) für Räume mit N Teilnehmern. Es leitet verschlüsselte Datensätze weiter, ohne das Kopplungsgeheimnis oder App-Klartext, sieht aber Routing-IDs, IPs, Datensatzgrößen und Timing. |
| **`cc_server`** | Eigentümer des Raums. Er beantwortet die Aufrufe des Telefons über denselben Dispatcher, den jeder andere Client nutzt. |

Ein Kopplungsangebot trägt einen **Verbindungsdeskriptor**, der jeden Weg zum
Server aufführt (LAN, Tailnet, öffentliches `wss://`, Relay) plus den
Identitäts-Fingerabdruck. Der Resolver des Telefons wählt den besten
erreichbaren Weg. Der Server signiert den verschlüsselten Handshake, und der
Client legt dessen Fingerabdruck fest. Prüfe den Fingerabdruck beim ersten
Verbinden gegen einen QR-Code oder eine andere vertrauenswürdige Quelle: Eine
erste signierte Identität allein beweist nicht, welchen Server du erreicht
hast. Ein geänderter Pin wird abgelehnt, statt still erneut vertraut zu
werden. Das Relay trägt Chiffretext, wenn kein direkter Weg existiert, kann
die Verbindung aber weiterhin unterbrechen oder verzögern.

## Was der Kopplungs-Payload ist

Die Kopplung wird in der App ausgestellt und als Deep Link ausgeliefert. Den
Ablauf beschreibt [Ein Gerät koppeln](/de-DE/handbuch/anleitungen/geraet-koppeln/).
Hier zählt der Aufbau.

```
https://<pwa-host>/#<payload>
```

Der Payload liegt im URL-**Fragment**, dem Teil nach `#`, den Browser nicht in
der HTTP-Anfrage an den PWA-Host schicken. Er trägt alles, was das Telefon
braucht, um den Server zu erreichen und nachzuweisen, wer es ist: den
Verbindungsdeskriptor (jeder Weg plus der Identitäts-Fingerabdruck), eine
frisch ausgestellte Geräte-ID, einen vorab geteilten Schlüssel von 32 Byte und
einen Ablaufstempel. Das Telefon dekodiert ihn, speichert einen
Kopplungsdatensatz lokal und entfernt das Fragment aus der URL. Der Code der
Web-App kann das Fragment lesen. Nutze deshalb einen vertrauenswürdigen
App-Host und behandle den Link wie ein Geheimnis.

Es gibt zwei Payload-Formen, und sie sind **nicht austauschbar**. Der
Telefon-QR aus dem Kopplungsbereich in der App ist der v2-`PairingPayload`
oben und zeigt auf den Host der Remote-PWA. `cc_server pair --client-url`
gibt einen v1-Link aus (`{s, i, k}` — Server-URL,
Geräte-ID, Schlüssel), der nur für den **Web**-Client gedacht ist. Dies sind
Kopplungsdatenformate, keine Transport-Fallbacks: Beide Clients müssen das
aktuelle verschlüsselte Sitzungsprotokoll unterstützen.

Sie unterscheiden sich auch in der Lebensdauer, und das vertauscht man
leicht:

| Ausgestellt von | Gültigkeit der Zugangsdaten |
| --- | --- |
| Kopplungsbereich in der App (`pairing.mint`) | immer 30 Tage |
| `cc_server pair` auf der Kommandozeile | Kein Ablauf kodiert; Serverrichtlinien gelten weiterhin |

Serverweite Richtlinien für das Höchstalter von Geräten und den
Leerlauf-Timeout können beide Zugangsdaten früher ablehnen. Keines der beiden
Kopplungsformate umgeht diese Richtlinien.

## Das Zugriffsmodell

Ein gekoppeltes Gerät ist **authentifiziert, aber nicht vertrauenswürdig**.
Mehrere unabhängige Schranken halten eine freigegebene (oder durchgesickerte)
Kopplung davon ab, zur vollen Kontrolle über den Server zu werden.

### 1. Die Mitgliedschaft ist die Grenze, nicht die Kopplung

Ein gültiger Kopplungsschlüssel beweist, _welches Gerät_ du bist. Was du
lesen oder ändern darfst, entscheidet deine **Rolle im Arbeitsbereich**, bei
jedem einzelnen Aufruf neu aufgelöst, und bei allem, was Repo-Inhalt zeigt,
die Freigaben pro Repo. Ein Gerät mit einem völlig gültigen Schlüssel, das
einer Person gehört, die kein Mitglied des genannten Arbeitsbereichs ist,
wird mit „Not a member of this workspace“ abgelehnt.

Die Mindestrolle leitet sich aus der Art der Operation ab, sofern die
Operation keine eigene festlegt: Lesen braucht `guest`, Änderungen brauchen
`member`, zerstörende Operationen brauchen `admin`.

### 2. Ein Telefon ist eine niedrigere Sitzungsstufe

Über die Rollenprüfung hinaus trägt eine Telefon-Sitzung geringere
Fähigkeiten als eine Desktop- oder Web-Sitzung. Operationen, die nur für den
vollständigen Client deklariert sind, werden für ein Telefon abgelehnt, bevor
der Handler läuft, unabhängig davon, wie viele Rechte die Person dahinter
hat: Kopplungen von Geräten ausstellen, auflisten, umbenennen und
widerrufen; Tunnel-Konnektivität lesen und setzen; Server-Sicherung sowie
Export und Import eines Arbeitsbereichs; Prozesse erkennen und beenden;
Adapter-Sonden; Server-Einstellungen; SSO-Verwaltung; Steuerung der Flotte;
und einen laufenden Agenten übernehmen oder zurückgeben.

### 3. Eine Allow-List für Tools, die standardmäßig ablehnt

Für die MCP-Tool-Oberfläche (`tools/call`) gilt eine Allow-List, die
standardmäßig ablehnt. Sie legt fest, welche Tools das Telefon aufrufen darf.
Was nicht auf der Liste steht, wird abgelehnt, bevor es läuft. Die Liste ist
überwiegend Lesen und Beobachten, plus eine Handvoll **rein lokaler**
Schreibvorgänge — eine Nachricht, eine Ticket-Aktualisierung, eine
Artikelmarkierung —, die kein LLM-Budget ausgeben, keinen Prozess starten und
kein externes System berühren.

Abgelehnt wird zum Beispiel: einen Agenten befragen, eine KI-Review starten,
einen Agenten beenden, eine Review auf GitHub veröffentlichen, Agenten
einstellen oder entlassen, einen Arbeitsbereich anlegen.

### 4. Arbeitsbereich pro Aufruf

Der Server hält **keinen** „aktuellen Arbeitsbereich“. Er ist absichtlich
zustandslos: Jeder Aufruf mit Arbeitsbereich muss in seinen Argumenten die
Ziel-`workspace_id` nennen, und der Dispatcher lehnt den Aufruf sofort ab,
wenn sie fehlt oder einen Arbeitsbereich nennt, den der Server nicht
registriert hat — bevor irgendetwas eine Datenbank öffnet. Ein Telefon kann
deshalb den Geltungsbereich eines anderen Clients nie erben und auch nicht
hineingeraten. Einen fremden Arbeitsbereich zu nennen hilft ebenfalls nicht,
weil die Mitgliedschaftsprüfung aus Schranke 1 weiter gilt. Das ist dieselbe
Invariante der
[Arbeitsbereichs-Isolation](/de-DE/handbuch/konzepte/arbeitsbereiche/), die
der Rest des Produkts durchsetzt.

### 5. Ende-zu-Ende-Verschlüsselung bei direkten und über das Relay laufenden Verbindungen

Jede direkte oder über das Relay laufende Client-Sitzung erfordert einen
signierten Noise-Handshake. Der Kopplungsschlüssel authentifiziert diesen
Handshake; frische ephemere Schlüssel leiten die Verkehrsschlüssel ab, statt
mit dem Kopplungsschlüssel jeden Frame zu versiegeln. Der Server signiert
seine Identität in den Austausch hinein, und der Client prüft seinen
gespeicherten Fingerabdruck-Pin. Es gibt keinen Klartext- oder
Altclient-Fallback. Ein Relay-Einlass-Token lässt einen Client nur in einen
Raum; die Datensätze kann es nicht entschlüsseln.

In der App ausgestellte Zugangsdaten sind auf 30 Tage befristet. Danach
lehnt das Verbindungs-Gate sie ab, und das Telefon muss neu gekoppelt
werden. Der Widerruf wirkt sofort: Der Server beobachtet die Gerätetabelle
und beendet die offenen Sitzungen eines widerrufenen Geräts innerhalb von
Sekunden, statt auf die nächste Verbindung zu warten.

### 6. Ratenbegrenzung pro Prinzipal

Ein Begrenzer mit gleitendem Fenster deckelt den entfernten Tool-Verkehr auf
120 Aufrufe pro Minute, mit einer engeren Teilgrenze von 30 pro Minute für
die verändernden Verben. Das Kontingent gehört dem **Prinzipal, nicht der
Sitzung**: Drei deiner Geräte zehren von einem Kontingent. Ein gekaperter
Client verschafft sich keinen Spielraum, indem er weitere Sitzungen öffnet,
und ein lautes Mitglied kann den anderen das Kontingent nicht wegnehmen.

### 7. Ein Broker, der keine App-Inhalte lesen kann

Der Relay-Broker stellt flüchtige, einladungsgeschützte Räume bereit und
leitet verschlüsselte Datensätze weiter, ohne App-Klartext oder
Kopplungsschlüssel. Er sieht weiterhin IP-Adressen, Raum- und Peer-IDs,
Datensatzgrößen, Timing und Lebensdauer der Verbindung und kann Verkehr
verwerfen oder verzögern. Der gekoppelte Client und der gewählte `cc_server`
sind die Klartext-Endpunkte; der Serverbetreiber und Dienste, an die er
Inhalte sendet, können diese Inhalte sehen. Verschlüsselung während der
Übertragung verschlüsselt keine Serverdaten im Ruhezustand.

## Live-Aktualisierungen

Nach der Kopplung erhält das Telefon **Live-Aktualisierungen** als
Benachrichtigungs-Frames — neue Agentennachrichten, dir zugewiesene Tickets,
Statusänderungen — analog zu den Benachrichtigungen des Desktops. Der Server
prüft die Arbeitsbereichsmitgliedschaft, bevor er ein Ereignis an eine Sitzung
weiterleitet. Der Client filtert diese bereits autorisierten Ereignisse dann auf
den Arbeitsbereich, den du gerade ansiehst; dieser Anzeigefilter ist nicht die
Zugriffsgrenze.

## Wo es liegt

| Oberfläche | Was sie zeigt |
| --- | --- |
| **Einstellungen → Du → Deine Geräte** (`/workspaces/:workspaceId/settings/you/devices`) | Gekoppelte Clients mit Live-Status, dazu **Neuen Client koppeln** (Webbrowser, Desktop-App oder Telefon) und Widerrufen |

Derselbe Bereich stellt Kopplungen auch für einen zweiten Browser oder eine
Desktop-App aus, nicht nur für Telefone. Der Ablauf ist derselbe, nur der
Deep Link unterscheidet sich.

::::note
Die Fernsteuerung liegt auf dem Server und wird über MCP **nicht**
bereitgestellt. Das Telefon spricht über seine verschlüsselte direkte oder über
das Relay laufende Verbindung mit dem eigenen Dispatcher des Servers. Es ist
kein MCP-Client eines externen Servers.
::::
