Control Center beantwortet zwei Autorisierungsfragen, und die beiden meinen
nicht dasselbe. **„Darf diese Person diese Operation aufrufen?“** betrifft
Menschen, Rollen und Repositories. **„Darf dieser Agent diese Wirkung
auslösen?“** betrifft Aktionen, Argumente und den Wirkungsradius — das steht
unter [Schutzregeln](/de-DE/handbuch/konzepte/schutzregeln/).

Diese Seite ist die erste Frage, und dazu die Aufzeichnung, die beide
hinterlassen.

## Ein Entscheidungspunkt

Jede Autorisierungsentscheidung auf Menschenseite läuft durch eine einzige
Funktion:

```
can(principal, permission, resource) → allow | deny + why
```

Eine **Berechtigung** hat die Form `<domain>:<tier>` — `tickets:write`,
`members:administer`, `repos:read`. Der Katalog ist **abgeleitet**, nicht von
Hand geschrieben: Er wird aus der Operationsoberfläche selbst berechnet (das
Namenspräfix der Operation liefert die Domäne, die Mindestrolle, die sie schon
erzwingt, die Stufe). So tragen alle ~550 Operationen eine Berechtigung, ohne
dass jemand eine eintippt.

Genau diese Ableitung ist es wert, geschützt zu werden. Eine NEUE Operation
ist damit von vornherein an eine Berechtigung gebunden — beim von Hand
annotierten Modell vergisst jemand etwas, und das Vergessene ist das Gate.
Ein Ratchet-Test hält die resultierende Domänenmenge fest. Eine Operation
unter einem neuen Präfix hinzuzufügen ist damit eine Namensentscheidung, die
ein Mensch trifft, und kein Versehen.

Die vier Stufen bilden die eingebauten Rollen genau ab:

| Stufe | Mindestrolle | Beispiel |
|---|---|---|
| `read` | Gast | `tickets:read` |
| `write` | Mitglied | `tickets:write` |
| `administer` | Admin | `members:administer` |
| `own` | Eigentümer | `workspace:own` |

## Rollen

Fünf eingebaute Rollen — **Eigentümer, Admin, Mitglied, Betrachter, Gast** —
sind Voreinstellungen auf diesem Katalog. Die Eigentümerschaft ist ein
einzelner Platz pro Arbeitsbereich und wird ausdrücklich mit **Besitz
übertragen** weitergegeben (ein Eigentümer, der geht, lässt sich sonst nicht
entfernen: die SCIM-Deprovisionierung lehnt jeden Arbeitsbereichs-Eigentümer
ab — zuerst übertragen).

**Benutzerdefinierte Rollen nehmen nur weg.** Eine benutzerdefinierte Rolle
nennt eine Basisvorlage (`admin`, `member`, `viewer` oder `guest` — nie
`owner`) und eine Menge von Berechtigungen, die davon ENTFERNT werden —
„Admin, kann aber keine Mitglieder verwalten“. Sie kann nie mehr gewähren als
ihre Basis. Genau deshalb lassen sie sich in einer bestehenden Installation
einführen: jede bestehende Prüfung bleibt eine verlässliche Obergrenze.
Mitglieder führen sie als `custom:<id>`, und ein Client, der zu alt ist, um
diesen Wert zu verstehen, fällt auf Gast zurück, statt zu raten.

Unter den Rollen liegen **Freigaben pro Repo** (`none` / `read` / `review` /
`write`, siehe [Code ändern braucht den Schreibzugriff](#code-ändern-braucht-den-schreibzugriff)): die Mitgliedschaft im Arbeitsbereich gibt nie stillschweigend mehr
Rechte als der Code-Host. Jede Oberfläche, die Code zeigt, prüft sie — auch
die, die seitlich an den Code kommen, etwa ein Terminal oder eine
Editor-Sitzung auf dem Worktree eines Bereichs.

## Code folgt dem Code-Host

Eine Freigabe allein öffnet nicht den Code eines Repositorys. Um seine Dateien, Diffs oder Suchergebnisse zu sehen oder ein Terminal darauf zu öffnen, braucht ein Mitglied die Control-Center-Freigabe **und** seine eigene Anmeldung beim Code-Host muss das Repository lesen können. Arbeitsbereichs-Admins sind davon nicht ausgenommen; der Serverinhaber schon, weil der Checkout auf seiner Maschine liegt. Ein Repository ohne Remote beim Code-Host braucht nur die Freigabe.

- Gibt ein Admin einem Mitglied ein Repository frei, dessen Code-Host-Konto es nicht lesen kann, wird die Freigabe gespeichert, und der Admin sieht eine Warnung.
- Lässt sich der Code-Host zur Prüfung nicht erreichen, lautet die Antwort nein, nie eine Vermutung: die Person sieht „Dein GitHub-Zugriff konnte nicht bestätigt werden. Versuche es erneut.“ (mit dem Namen des Code-Hosts der Person) und versucht es später erneut.
- Pull Requests und alles, was aus ihnen entsteht, folgen derselben Regel.

### Code ändern braucht den Schreibzugriff

Eine Repository-Freigabe hat drei Stufen, und jede enthält die davor:

- **read**: die Dateien, Diffs und Suchergebnisse des Repositorys sehen, sofern deine eigene Anmeldung beim Code-Host es ebenfalls lesen kann.
- **review**: lesen, plus Genehmigen, Änderungen anfordern und die übrigen Review-Aktionen auf seinen Pull Requests.
- **write**: review, plus Code ändern und Agentenläufe steuern, die in das Repository schreiben. Code ändern umfasst das Speichern oder Zurücksetzen von Dateien im Editor, das Synchronisieren eines Worktrees mit dem Head seines Pull Requests, Committen und Pushen, das Veröffentlichen eines Branches sowie die Stack-Aktionen, die einen Teil anlegen, auschecken oder veröffentlichen.

Jeder Push, der für eine Person gemacht wird, selbst oder durch einen Agentenlauf, den sie angefordert hat, prüft ihre Schreibfreigabe für dieses Repository im Moment des Pushs, bei GitHub, GitLab und Bitbucket gleichermaßen. Das Veröffentlichen eines Stacks prüft jedes Repository des Stacks, bevor es eines davon pusht.

Eine Ablehnung nennt die fehlende Freigabe. Ohne Lesezugriff zeigt die App „Du hast keinen Lesezugriff auf dieses Repository. Ein Workspace-Admin kann ihn freigeben.“ Mit Lesezugriff, aber ohne Schreibzugriff heißt es „Du kannst dieses Repository lesen, aber nicht ändern. Ein Workspace-Admin kann Schreibzugriff freigeben.“

### Bereiche folgen ihren Repositorys

Was Agenten über Code geschrieben haben, folgt dem Code. Der Inhalt eines Bereichs (seine Nachrichten, Transkripte und Werkzeugausgaben, Suchergebnisse, Laufprotokolle, Todos, Aktivität und Benachrichtigungen) trägt den Code der Repositorys, an denen er arbeitet. Deshalb öffnet sich ein Bereich nur für ein Mitglied, das eine Leseberechtigung auf jedes Repository des Bereichs hält und dessen eigene Anmeldung beim Code-Host es lesen kann. Das sind die Repositorys, die für den Bereich ausgewählt sind, oder alle Repositorys des Arbeitsbereichs, wenn für den Bereich keine Auswahl gespeichert ist. Ein Bereich, der ohne Repositorys angelegt wird, steht jedem Mitglied offen.

Einen Bereich, den jemand nicht öffnen kann, wird ihm nirgends angezeigt, auch nicht in der Suche, in Laufprotokollen, Todos, Aktivität und Benachrichtigungen. Arbeitsbereichs-Admins halten jede Freigabe, sind aber vom Code-Host-Teil nicht ausgenommen; der Serverinhaber schon.

Für eine Unterhaltung, die alle lesen sollen, lege den Bereich ohne Repositorys an oder nur mit Repositorys, die alle lesen können.

## Der Serverinhaber

Die Person, die den Server eingerichtet hat, ist sein **Inhaber**. Der Server hält sie beim ersten Start fest, und nichts, was übers Netz geschickt wird, ändert das. Ein Arbeitsbereichs-Admin oder Arbeitsbereichs-Eigentümer ist nicht der Serverinhaber: Jeder kann einen Arbeitsbereich erhalten, aber die Maschine des Servers hat genau einen Inhaber.

**Auf der Maschine des Servers läuft nichts außerhalb einer Sandbox, außer der Serverinhaber hat es gestartet oder diese Art der Ausführung auf dem Host genehmigt.** Konkret kann nur der Serverinhaber:

- Einen Arbeitsbereich anlegen. Alle anderen sehen einen Bildschirm, der sie bittet, den Inhaber um einen zu bitten oder einen Arbeitsbereichs-Admin um eine Einladung.
- Die Host-Shell im serverseitigen Terminal öffnen. Alle anderen bekommen ein Terminal in der Sandbox, mit den Grenzen eines Agenten, in den Verzeichnissen des Arbeitsbereichs.
- Den eingebetteten Code-Editor öffnen. Er läuft als eigener Benutzer des Servers, mit seinem Terminal, Aufgaben und Erweiterungen.
- Einen Pull Request oder den Worktree einer Unterhaltung in einem nativen Editor öffnen. Der Editor startet auf dem Bildschirm des Servers, als Benutzer des Servers.
- Die Definition einer [Umgebung](/de-DE/handbuch/anleitungen/environments/) speichern oder genehmigen, die auf dem Host etwas ausführt: Platzierung auf dem Host, eine Prüfung, die einen Befehl ausführt, oder eine Bereitstellungs- oder Archivierungsaufgabe.
- Agenten auf einem Server ausführen, dessen Maschine keine Sandbox hat. Alle anderen Läufe werden dort abgewiesen, außer der Inhaber hat den Server mit `--sandbox off` gestartet; dann laufen die Agenten jedes Mitglieds ohne Einschränkung (siehe [Agenten auf einem Host ohne Sandbox](/de-DE/handbuch/konzepte/sandbox-und-sicherheit/#agenten-auf-einem-host-ohne-sandbox)).
- Einen Repository-Checkout verknüpfen, der außerhalb des eigenen Speichers des Arbeitsbereichs liegt, einen schon verknüpften vor dieser Regel bestätigen und beim Hinzufügen eines Repositorys die Ordner des Servers durchsuchen (siehe [Repositorys hinzufügen](/de-DE/handbuch/anleitungen/repos-hinzufuegen/)).
- Jeden laufenden Agentenprozess auf dem Server sehen und stoppen. Alle anderen sehen und stoppen nur laufende Agentenläufe in Arbeitsbereichen, denen sie angehören.
- Einen eigenen MCP-Server hinzufügen, der einen Befehl auf der Maschine des Servers ausführt. Die Server der anderen Mitglieder werden über eine URL angesprochen (siehe [Deine eigenen Server](/de-DE/handbuch/anleitungen/mcp-server/#deine-eigenen-server)).
- Einen Arbeitsbereich-MCP-Server freigeben, der einen Befehl auf der Maschine
  des Servers ausführt oder dessen privates Netzwerk erreicht (siehe
  [Arbeitsbereich-Server](/de-DE/handbuch/anleitungen/mcp-server/#arbeitsbereich-server)).
- Die E-Mail-Adresse einer Person bestätigen, damit Single Sign-on sie zuordnen kann (siehe [Mit einem OpenID-Connect-Provider verbinden](/de-DE/handbuch/anleitungen/sso-oidc/#wie-anmeldungen-zu-bestehenden-konten-passen)).
- Installationsweite Einstellungen ändern: SSO, Anbieter-Zugangsdaten, den MCP-Endpunkt und sein Token, die Modellverwaltung, Connect und Sicherungen der ganzen Installation. Diese Operationen deklarieren **Serverautorität** und werden für alle anderen abgelehnt.

Absichtlich gibt es genau eine Betreiberidentität und genau eine Definition davon.

## Das Audit-Protokoll

Jede Autorisierungsentscheidung — **Zulassen und Ablehnen** — wird an ein
Audit-Protokoll angehängt, das pro Arbeitsbereich geführt und über Hashes
verkettet ist.

Ein Protokoll nur mit Ablehnungen beantwortet „Was haben wir blockiert?“,
aber nicht „Was hat dieser Agent tatsächlich getan, und wer hat es
autorisiert?“. Mit dieser Frage beginnt eine Vorfallprüfung. Jeder Eintrag
hält deshalb die ganze Zuschreibungskette fest: den handelnden Prinzipal, den
Menschen, in dessen Auftrag er gehandelt hat, die Delegation, über die er
gekommen ist, die Aktion und ihre Argumente (als Digest), die Entscheidung
und **die Regel, die entschieden hat**.

Die Einträge sind verkettet: der Hash eines Eintrags umfasst den des
vorherigen. Wer eine Zeile ändert, löscht oder umordnet, bricht damit jeden
Hash danach. **Kette prüfen** leitet das Ganze neu ab und nennt das erste
Glied, das nicht hält. Ein Audit-Protokoll, das du nicht prüfen kannst, ist
ein Protokoll. Eines, das du neu ableiten kannst, ist ein Beweis.

Zwei Folgen, die du kennen solltest:

- Die Audit-Tabelle ist **von der altersbasierten Bereinigung ausgenommen**.
  Eine Hash-Kette lässt sich nicht aus der Mitte kürzen. Aufbewahrt wird durch
  Export und anschließendes Kürzen, und das Kürzen hinterlässt einen
  Checkpoint mit dem End-Hash des entfernten Abschnitts. Was bleibt, lässt
  sich so weiterhin bis zum Anfang prüfen.
- Es steht **neben** der Aktivitätschronologie, nicht darüber. Die Chronologie
  ist, was Menschen getan haben; hier steht, was autorisiert und abgelehnt
  wurde. Eine gemeinsame Korrelations-ID liest einen Aufruf über beide.

Es wird als zeilengetrenntes JSON exportiert und kann an ein SIEM gestreamt
werden (Splunk, Elastic, Sentinel — ein HTTP-Endpunkt mit einem
Bearer-Token). Das Streaming ist bewusst Best Effort: Fällt ein SIEM aus,
darf das einen Tool-Aufruf eines Agenten nie blockieren. Die dauerhafte,
prüfbare Kopie liegt so oder so auf der Platte.

## Sitzungen

Eine Installation kann ein **maximales Sitzungsalter** und ein
**Inaktivitätszeitlimit** setzen. Beides wird bei der Prüfung der
Geräteanmeldedaten durchgesetzt, durch die jeder authentifizierte Weg läuft —
eine Sitzungsgrenze, die ein Client ignorieren könnte, beantwortet einen
Fragebogen, keinen Angreifer. Eine Installation kann außerdem SSO verlangen.
Das schaltet die manuelle Kopplung für neue Geräte ab (mit einem
Aussperrschutz: abgelehnt wird, solange keine funktionierende
SSO-Verbindung besteht).

## Was das nicht ist

- **Keine ACLs pro Objekt.** Es gibt absichtlich keine Berechtigung pro Ticket
  oder pro Nachricht. Trennung auf Repository-Ebene ist das, wonach Teams
  tatsächlich fragen, und die gibt es. Freigabe pro Objekt ist eine
  kombinatorische Oberfläche ohne nachgewiesenen Bedarf hier.
- **Keine Policy-Engine, die du in einer DSL konfigurierst.** Das Vokabular
  ist absichtlich geschlossen, damit sich die ganze Richtlinie darstellen,
  erklären und aufzählen lässt.
- **Durchgesetzt wird nur auf dem Server.** Prüfungen auf dem Client gibt es
  nur, damit kein Steuerelement angeboten wird, das abgelehnt würde. Die
  maßgebliche Entscheidung trifft immer der Server.
