Ein Pull Request ist schon der Ort, an dem das Gespräch über Code stattfindet.
PR-Unterhaltungen machen ihn zu einer Oberfläche auf einem Arbeitsbereich von
Control Center, so wie eine
[Chat-Brücke](/de-DE/handbuch/konzepte/chat-bruecken/) Slack zu einer macht:
`@usectrl` (oder den Bot der GitHub App des Arbeitsbereichs) auf einem PR mit @
erwähnen, in seinen Review-Threads antworten oder das Label `ai-review` setzen,
und die Arbeit läuft im Review-Bereich des PR — unter derselben Zuschreibung
und denselben Schutzregeln wie alles, was in der App getippt wird. Kommentar
und Label werden gleich geprüft: anhand des Mitglieds, das ihn geschrieben
oder es gesetzt hat. Die Antworten kommen auf GitHub zurück, in der Spur, in
der die Frage gestellt wurde.

Drei Entscheidungen prägen die Funktion, und jede ist dieselbe Entscheidung,
die die Chat-Brücke für den Chat getroffen hat, hier für eine Forge neu
formuliert: **in welche Richtung die Verbindung läuft**, **was einen Kommentar
autorisiert, der von außen ankommt**, und **wem jede Seite zugeschrieben
wird**.

## Polling ist der Transport

Der einzige Push-Kanal, den GitHub einer App bietet, ist ein Webhook, und ein
Webhook braucht eine eingehende URL — genau das, was diese Oberfläche bewusst
nie verlangt. Die Erkennung ist deshalb ein Durchlauf: Eine Suche mit Alias je
App-Installation fragt GitHub nach Pull Requests, die den Bot erwähnen (oder
seinen kurzen Slug), und nach offenen Pull Requests mit dem Review-Label. Pull
Requests, die schon einen Review-Bereich haben, werden auf ihre
Kommentar-Threads gelesen, und alles wird anhand der Kommentar-ID gegen den
letzten Durchlauf abgeglichen. Eine eigene App läuft jede Minute über höchstens
25 Pull Requests. Über Connect gehen die Aufrufe auf das eigene GitHub-Kontingent
der Mitglieder, deshalb läuft der Durchlauf alle zwei Minuten über höchstens 10,
und ein Arbeitsbereich unter 15 % seines Kontingents wird übersprungen, bis es
sich erholt hat. Connect selbst sieht nie PR-Inhalte.

Die Folgen des Entwurfs lohnt es zu benennen:

- **Die Latenz ist ein Durchlaufintervall, kein Ereignis.** Die Bestätigung
  👀 trifft innerhalb eines Durchlaufs ein. Nichts Dringendes hängt daran.
- **Genau einmal, je Kommentar.** Kommentar-IDs sind auf ganz GitHub eindeutig;
  jede wird in dem Moment festgehalten, in dem sie als zulässig gilt, bevor
  irgendetwas darauf reagiert. Ein Absturz kann die Bearbeitung eines
  Kommentars verlieren, ihn aber nie doppelt auslösen.
- **Ausfallzeit wird nachgeholt, nicht erneut abgespielt.** Die Menge der
  gesehenen IDs bleibt gespeichert, ein Neustart liefert also, was während des
  Ausfalls ankam. Die eine Ausnahme ist der allererste Durchlauf: ohne
  Gedächtnis für den Abgleich wird alles Offene still festgehalten — wer
  zwanzig Pull Requests markiert hat, bevor es diesen Server gab, darf nicht
  zu zwanzig laufenden Reviews zurückkehren.
- **Das Label ist eine Menge, kein Ereignis.** Die Suche meldet die
  _Anwesenheit_ des Labels, ein markierter Pull Request löst also einmal aus,
  für immer. Ein Label nach dem Entfernen wieder zu setzen bleibt für den
  Durchlauf unsichtbar; eine Erwähnung ist der Weg zum erneuten Lauf.

Die Suche läuft einmal je Installationskonto auf dem eigenen Client dieses
Inhabers, weil ein Token nur die Repos seiner eigenen Installation sieht — ein einziges serverweites Zugangsdatum würde still jeden Pull Request
unter den übrigen Installationen der App verpassen.

## Die Mitgliedschaft autorisiert, nicht der Kommentar

Ein PR-Kommentar kommt mit einem Autor an — einer nicht authentifizierten
externen Identität, bis der Nachweis steht. Der Server löst die unveränderliche
numerische ID des GitHub-Kontos des Autors auf (nie den Login, der sich
umbenennen und neu vergeben lässt), und zwar gegen die GitHub-Anmeldungen der
Mitglieder des Arbeitsbereichs, neu aufgebaut nach einer TTL, weil sich
Menschen anmelden und eingeladen werden, während der Server läuft. Beim Label
`ai-review` wird die Person aufgelöst, die es zuletzt gesetzt hat.

Drei Prüfungen, in dieser Reihenfolge, und wer an einer scheitert, scheitert
still — es wird nichts gepostet:

- **Ein angemeldetes Mitglied.** Das Konto muss einem Mitglied _dieses_
  Arbeitsbereichs gehören, das sich auf diesem Server bei GitHub angemeldet hat
- **Eine Rolle mit Schreibrecht.** `viewer` und `guest` können keine Arbeit
  starten
- **Push-Zugriff.** Antworten nutzen ein `bot`-Token, das auf den Zugriff dieses
  Mitglieds auf das Repository begrenzt ist. Kann der Server keines ausstellen,
  geht es nicht weiter

Jede Prüfung läuft vor jeder Bestätigung, eine fremde Person bekommt also
weder eine Reaktion noch eine Antwort. Ein Kommentar wird nie jemandem
zugeschrieben, der ihn nicht geschrieben hat, und die Worte einer fremden
Person gelangen nie in einen Arbeitsbereich, den sie nicht sehen kann.

### Der Anspruch

Der letzte Schritt vor jeder Arbeit ist eine Reaktion 👀, gesetzt mit der
eigenen GitHub-Anmeldung des Autors. GitHub antwortet mit `201` auf eine neue
Reaktion und mit `200` auf eine, die schon existiert, die Reaktion dient also
zugleich als Sperre: Ist dieselbe Person auf zwei Servern angemeldet, die beide
das Repository verknüpfen, erledigt nur der die Arbeit, der zuerst reagiert.
Ein Kommentar, den mehrere Arbeitsbereiche auf einem Server sehen, wird jedem
angeboten, und derselbe Anspruch entscheidet.

## Zwei Identitäten, mit Absicht

Jede Seite der Unterhaltung trägt eine andere Identität, und der Unterschied
ist die Funktion:

- **Auf GitHub ist die Antwort Automatisierung in deinem Namen.** Jede Antwort
  läuft über ein `bot`-Token für dieses eine Repository, begrenzt auf den
  Zugriff des fragenden Mitglieds. Bei einer eigenen App ist der Autor das
  Konto `[bot]` der App. Über Connect ist ein Token für die gemeinsame App ein
  Benutzertoken, die Antwort stammt also vom Konto des fragenden Mitglieds, das
  über die App handelt. In beiden Fällen beginnt jede Antwort mit
  `**Control Center** (for @login):`. Das sagt, wer gefragt hat, und dient
  zugleich als Schleifensperre.
- **Im Bereich gehört die Frage dir.** Die Nachricht wird dem Mitglied
  zugeschrieben, zu dem der Autor aufgelöst wurde, und der Agentenlauf läuft in
  dessen Namen: Commits nennen es als Co-Autor, und der Autonomieregler des
  Bereichs sowie die Schutzregeln für Aktionen gelten genauso wie bei einer
  Nachricht, die in der App getippt wurde. Schreibvorgänge an die Forge aus dem
  Lauf nutzen Tokens für ein einzelnes Repository, begrenzt durch dieses
  Mitglied, nie seine vollständig weitergereichte Anmeldung.

Review-Befunde auf GitHub zu veröffentlichen bleibt die Entscheidung einer
Person, getroffen in Control Center. Eine Erwähnung kann ein Review _starten_;
veröffentlicht wird es nur von einem Menschen.

## Die Schleifensperre und der Kurzname

Alles, was ein Bot-Konto verfasst, wird verworfen, bevor irgendein Tor läuft —
unseres ausdrücklich, und jedes Suffix `[bot]`, damit auch der Review-Bot
einer anderen App unseren nicht weckt —, und ebenso jeder Kommentar, der mit dem
Präfix `**Control Center** (for @` beginnt, denn eine Antwort über Connect
stammt vom Konto einer Person. Ohne das kämen die Antworten als neue Kommentare
an und lösten die Brücke endlos erneut aus.

Das Suffix `[bot]` ist auch der Grund für die Kurzform. GitHub legt den Login
eines App-Kontos auf `<slug>[bot]` fest, bietet dafür keine Autovervollständigung
und löst `@slug` nie zur App auf — den bloßen Slug anzunehmen ist also die
Entscheidung _unseres_ Abgleichs, und ihn zu entdecken braucht eine rohe
Suchspur über den Kommentar-**Text**, nicht den Erwähnungsindex von GitHub. Der
Preis wird genannt, nicht geglättet: Ein Mensch, der denselben Slug trägt wie
die App, spricht den Bot mit jeder Erwähnung seiner selbst in der Kurzform an.
Unverwechselbare App-Namen machen die Kollision hypothetisch.

## Was bewusst nicht angeboten wird

- **Kein automatisches Veröffentlichen.** Befunde landen im Review-Bereich; das
  Veröffentlichen auf GitHub ist eine eigene Handlung eines Menschen
- **Keine unscharfe Identität.** Der Autor löst auf genau ein Mitglied auf oder
  wird ignoriert — eine Zuschreibung nach bestem Ermessen gibt es nicht
- **Keine automatische Genehmigung.** Automatisierung kann kommentieren und
  Änderungen anfordern, aber ein Review `APPROVE` wird abgelehnt, bevor es
  gesendet wird. Genehmigen ist die Handlung einer Person
- **Kein Webhook der GitHub App.** Diese Oberfläche registriert nie einen, es
  gibt also keine eingehende URL, die für PR-Kommentare offenzulegen wäre.
  Andere Webhooks des Produkts (Pipelines, Ticket-Sync) sind eine eigene,
  optionale Einrichtung.
