Diese Anleitung zeigt dir, wie du einem Arbeitsbereich einen Agenten hinzufügst und ihn so einrichtest, dass er wirklich läuft.

Jeder Arbeitsbereich startet mit fünf Agenten — einem CEO plus `qa`, `architect`, `engineer` und `librarian` —, du hast also meist schon Agenten, bevor du einen konfiguriert hast. Die Schritte unten gelten für einen mit dem Arbeitsbereich angelegten Agenten genauso wie für einen neuen.

## Bevor du anfängst

- Du bist in einem Arbeitsbereich. Die ganze Oberfläche liegt unter **Einstellungen → Arbeitsbereich → Agenten** (`/settings/workspace/agents`).
- Der Agent braucht ein Backend. Verbinde entweder einen Anbieter für den eingebauten Harness unter **Einstellungen → Server → Modellanbieter**, oder installiere die Claude Code CLI auf dem Rechner, der `cc_server` hostet.
- Sollen Skills mit dem Agenten mitkommen, installiere sie zuerst unter **Einstellungen → Arbeitsbereich → Fähigkeiten**. Das Formular lässt nur Skills umschalten, die es im Arbeitsbereich schon gibt.

## Den Agenten hinzufügen

1. Öffne **Einstellungen → Arbeitsbereich → Agenten**.
2. Klicke auf **Neuer Agent**.

Es gibt keinen Dialog und keine Rollenauswahl. Es entsteht sofort ein Agent namens „Unbenannter Agent“, und er ist im Detailbereich rechts ausgewählt.

Du siehst jetzt „Unbenannter Agent“ in der Liste links. Der Tab **Einstellungen** seines Detailbereichs ist offen, und das Feld **Name** enthält „Unbenannter Agent“.

## Den Agenten benennen

- **Name** — die kurze Kennung für @-Erwähnungen, zum Beispiel `alice`. Beim Erwähnen zählt `@` plus Wortzeichen, ein Name mit Bindestrich, Punkt oder Leerzeichen lässt sich deshalb nie erwähnen.
- **Titel** — die lesbare Bezeichnung, zum Beispiel „Senior-Entwickler“.
- **System-Prompt** — optionale Zusatzanweisungen, eingefügt als Abschnitt „Agent instructions“. Den Rest des zusammengesetzten Prompts ersetzen sie nicht.

Klicke unten im Formular auf **Änderungen speichern**. Diese eine Schaltfläche speichert jedes Feld auf dieser Seite.

## Adapter und Modell geben

Das Dropdown **Adapter** listet die Runner, die der Server-Host wirklich hat. Der eingebaute Adapter ist immer vorhanden, denn er ist der Server. Claude Code erscheint nur, wenn seine CLI auf diesem Host erkannt wurde:

| Adapter                   | Backend                                                 |
| ------------------------- | ------------------------------------------------------- |
| Control Center (built-in) | Die prozessinterne Agentenschleife — keine externe CLI |
| Claude Code               | `claude -p --output-format stream-json`                 |

Nur der eingebaute Adapter setzt Modi, Lenken, Pause und Fortsetzen, Abschlussverträge und Subagenten durch. Claude Code kann nichts davon. Cursor, Codex und die anderen Modellanbieter sitzen auf dem eingebauten Adapter, nicht als eigene Runner.

:::note[Ein leerer Adapter ist die eingebaute Schleife]
Ein Agent ohne gesetzten Adapter fällt auf **Control Center (built-in)** zurück, die Schleife im Server, auf dem Host muss also nichts installiert sein. Ist auch kein Modell gesetzt, fragt er Anthropic nach dessen Standard. Ein ganz ungesetzter Agent läuft deshalb nur, wenn du ein Anthropic-Konto verbunden hast. Die mit dem Arbeitsbereich angelegten Spezialisten kommen ohne beides. Setze beides bei jedem Agenten, den du nutzen willst.
:::

Das Dropdown **Modell** folgt dem Adapter, den du gewählt hast. Beim eingebauten Adapter kommt die Liste live von den Anbietern, die du unter **Einstellungen → Server → Modellanbieter** verbunden hast. Ein Anbieter ohne gespeicherte Zugangsdaten steuert null Modelle bei.

## Skills hinzufügen

**Fähigkeiten** ist eine Chip-Auswahl über die Skills, die in diesem Arbeitsbereich installiert sind. Tippe einen Chip an, um ihn umzuschalten; das Häkchen markiert die ausgewählten. Hat der Arbeitsbereich keine Skills, steht im Feld „No skills available. Create skills in Settings → Skills first.“

Die eigenen Skills eines Repos wählst du hier nicht. Bringt ein Repo sie mit (in `.agents/skills/`, `.claude/skills/` oder `.opencode/skills/`), gehen sie automatisch an den Agenten, der in diesem Repo arbeitet, und sie wechseln, wenn er in ein anderes wechselt — siehe [Repo-bezogene Skills](/de-DE/handbuch/konzepte/agentenmodell/#repo-bezogene-skills).

## Berichtslinie und Persona setzen

- **Berichtet an** — wähle einen anderen Agenten nach Namen. Daraus entsteht der Berichtsbaum, den die Schaltfläche **Organigramm** im Seitenkopf zeigt. Das ist nicht die Besetzung, aus der eine Teamleitung delegiert — die kommt aus den Mitgliedern des Teams und ihren Skills.
- **Persona** — freier Text, der Ton und Verhalten prägt, zum Beispiel: „Bevorzugt einfache, lesbare Lösungen. Schreibt Tests für jeden neuen Code.“

## Den Lauf abstimmen

- **Reasoning-Aufwand** — die Optionen sind die Stufen, die das gewählte Modell selbst veröffentlicht: Low / Medium / High, dazu Extra High bei Modellen im OpenAI-Stil und Extra High + Max bei Modellen im Claude-Stil. Das Feld ist ganz ausgeblendet, wenn das Modell keine Thinking-Stufen meldet, und es steht sonst auf dem eigenen Standard des Modells.
- **Kontextfenstergröße** — vorausgefüllt aus dem Kontextfenster des Modells, sobald du das Modell wechselst, mit Chips für den Modellstandard, 200k, 500k und 1M. Ein Wert, den du nach der Modellwahl eintippst, gilt bis zum nächsten Modellwechsel.
- **Stille-Timeout (Minuten)** — beendet einen Lauf nach dieser Zeit ohne Ausgabe. Leer lassen, dann gilt der Standard des jeweiligen Modus.

## Berechtigungen vergeben

Ein Agent hat keine eigenen Berechtigungsschalter. Was er pushen, öffnen, mergen oder erreichen darf, legen die Aktionsregeln unter **Einstellungen → Arbeitsbereich → Agent-Berechtigungen** fest, wo sich eine Regel auf diesen Agenten beschränken lässt. Ab Werk fragen ein Push, ein Pull Request, eine Review oder ein Merge und ein Schreibvorgang im Tracker jeweils zuerst dich, und Netzwerkzugriff ist zugelassen.

Das GitHub-Token des Agenten darf immer nur lesen. Ein Push läuft durch Control Center, das vor dem Weiterleiten die Regel **Zu einem Remote pushen** fragt. Wie jede Regel einen Lauf erreicht, steht unter [Sandbox-Richtlinien konfigurieren](/de-DE/handbuch/anleitungen/sandbox-richtlinien/).

:::note[Regeln und die OS-Sandbox sind getrennte Schichten]
Die Regeln entscheiden, was ein Agent tun darf; die OS-Sandbox begrenzt, wo seine Prozesse lesen, schreiben und sich verbinden können. `cc_server` hüllt Agentenläufe in die Sandbox des Hosts, wo es eine gibt — Windows hat kein natives Backend, und Linux und WSL2 brauchen `bwrap` und `socat`. Siehe [Sandbox und Sicherheit](/de-DE/handbuch/konzepte/sandbox-und-sicherheit/) für sämtliche Grenzen.
:::

## Prüfen, dass er läuft

1. Öffne **Einstellungen → Server → Modellanbieter** und prüfe, dass der Adapter, den du gewählt hast, eine installierte Version meldet und nicht „Nicht gefunden“. Klicke auf **Aktualisieren**, um die Prüfung zu wiederholen — die Prüfung läuft auf dem Rechner, der `cc_server` hostet, nicht auf dem Rechner, den du gerade ansiehst.
2. Öffne einen Bereich mit dem Agenten und schick ihm eine Nachricht, oder erwähne ihn mit @ in einem bestehenden Bereich.
3. Geh wieder zu **Einstellungen → Arbeitsbereich → Agenten**, wähle den Agenten und öffne den Tab **Protokolle**. Ein Lauf sollte erscheinen, mit Status-Badge, Dauer, Startzeit und dem Adapter, den er genutzt hat. **Ansicht** öffnet den Ereignisstrom dieses Laufs.

Erscheint gar kein Lauf, geh [Einen Agenten diagnostizieren](/de-DE/handbuch/anleitungen/agent-diagnostizieren/) durch.

## Einen Agenten löschen

Wähle ihn in der Liste aus. Auf dem Tab **Einstellungen** scrollst du zur **Gefahrenzone** unten im Formular und klickst auf **Löschen**.
