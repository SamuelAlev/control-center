Diese Anleitung zeigt, wie du mit Control Center arbeitest, ohne GitHub zu
verlassen: ein KI-Review von der PR-Seite anfordern, dem Bot in einem Kommentar
eine Frage stellen und die Unterhaltung in seinen Review-Threads weiterführen.

Antworten kommen über die GitHub-Spur des Arbeitsbereichs: die eigene
[GitHub App](/de-DE/handbuch/anleitungen/github-app/) deines Servers oder die
gemeinsame App von Control Center über Connect. Neu registriert wird nichts, und nichts muss aus dem Internet
erreichbar sein: der Server erfährt durch Polling, was auf GitHub gesagt wurde,
ein Laptop hinter NAT verhält sich also genau wie eine öffentliche
Bereitstellung.

## Voraussetzungen

- Der Arbeitsbereich hat eine GitHub-Spur: die eigene GitHub App des Servers
  oder Connect, mit der App [installiert](/de-DE/handbuch/anleitungen/github-app/#dort-installieren-wo-deine-repositories-liegen)
  auf dem Konto, dem das Repository gehört. Eine eigene App braucht
  **Pull requests** und **Issues** mit Lesen und Schreiben, was **Meine
  GitHub-App erstellen** schon vergibt
- Das Repository ist in Control Center mit einem Arbeitsbereich verknüpft
- Du bist auf diesem Server [bei GitHub angemeldet](/de-DE/handbuch/anleitungen/github-integration/)
  und darfst in das Repository pushen
- Keine Webhook-URL, kein Tunnel, kein Callback — auf der Netzwerkseite ist
  nichts zu konfigurieren

## Den Namen deines Bots finden

Erwähne `@usectrl`, das eigene GitHub-Konto von Control Center. Dies ist der Standardauslöser; die GitHub-Spur deines Arbeitsbereichs bearbeitet die Anfrage weiterhin und veröffentlicht die Antworten. Zugangsdaten für das Konto `usectrl` brauchst du nicht.

Auch der eigene App-Login `<appslug>[bot]` und die Kurzform `@appslug` funktionieren. So findest du diesen optionalen Alias bei deiner eigenen App:

1. Geh zu **Einstellungen → Server → Single sign-on** und scrolle zur Karte
   **Anbieter-Apps**
2. Öffne den Block **GitHub** und klicke auf **Testen**
3. Kopiere **Bot-Login**, sobald er erscheint. Zeigt er noch den leeren Hinweis,
   ist der Login immer `<appslug>[bot]` — tippe das, oder die Kurzform `@appslug`

GitHub bietet App-Konten in der `@`-Autovervollständigung nicht an; App-Aliasse musst du daher eintippen oder kopieren. Standardmäßig rufst du den Bot über den eigenen Nutzer `@usectrl` auf; `@myapp` und `@myapp[bot]` bleiben gültige App-Aliasse.

:::note[Wähle einen unverwechselbaren App-Namen]
Die Kurzform wird als Text abgeglichen. Teilt sich ein menschlicher
GitHub-Nutzer zufällig den Slug deiner App, erreicht die Erwähnung dieses
Nutzers in der Kurzform auch den Bot. Die volle Form `@myapp[bot]` ist immer
eindeutig.
:::

## Ein Review von GitHub aus anfordern

Zwei Wege, und beide starten dieselbe mitgelieferte Pipeline `pr_review`, die
auch die Schaltfläche **Ask AI** startet:

- **Setze das Label `ai-review`** auf dem PR. Das ist das Nächste, was GitHub
  dazu anbietet, den Bot als Reviewer zuzuweisen: App-Konten können den nativen
  Platz eines angeforderten Reviewers nicht belegen. Dein Konto reagiert auf den
  PR mit 👀, und das Review startet in Control Center; es wird kein Kommentar
  gepostet
- **Kommentiere `@usectrl review`** (oder nur `@usectrl`) in der PR-Unterhaltung.
  Auf deinem Kommentar erscheint 👀, dann meldet eine Antwort, dass das Review
  gestartet ist (oder dass bereits eines läuft)

Die Reviewer arbeiten im Review-Bereich des PR; lies und veröffentliche die
Befunde wie in
[KI-gestützte Review nutzen](/de-DE/handbuch/anleitungen/ki-review/). Zurück auf
GitHub zu veröffentlichen bleibt eine Entscheidung, die du in Control Center
triffst. Ein Review von GitHub aus zu starten veröffentlicht von sich aus nichts
auf GitHub.

Das Label löst einmal je PR aus: es zu setzen ist die Anfrage, und Entfernen
mit erneutem Setzen schärft es nicht neu. Um ein Review noch einmal laufen zu
lassen, etwa nach einem Push, erwähnst du den Bot.

## Eine Frage stellen

Kommentiere in der PR-Unterhaltung:

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

Was dann passiert, der Reihe nach:

1. Auf deinem Kommentar erscheint 👀, von deinem eigenen Konto, damit du
   siehst, dass der Kommentar angekommen ist
2. Die Frage wird im Review-Bereich des PR **als du** gepostet, mit derselben
   Zuschreibung, als hättest du sie in Control Center getippt
3. Ein Agent antwortet im Bereich, und die Antwort kommt auf dem PR zurück.
   Jede Antwort beginnt mit `**Control Center** (for @your-login):`

Eine Frage auf einem PR ohne bisheriges Review weckt den CEO-Agenten des
Arbeitsbereichs; sobald ein Review gelaufen ist, antwortet der Agent, der
zuletzt gesprochen hat, damit Nachfragen bei dem ankommen, der den Kontext hat.

## In einem Review-Thread nachfassen

Antworte in einem Inline-Review-Thread, an dem der Bot beteiligt ist: ein
Diff-Kommentar, den er hinterlassen hat, oder eine Antwort, die er in diesem
Thread gepostet hat. Eine Erwähnung brauchst du nicht; der Thread **ist** die
Adressierung:

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

Mehrere Runden funktionieren genauso: jede Antwort ist eine weitere Frage in
derselben Unterhaltung, mit dem Review-Bereich als Kontext, und die Antwort
kommt im Thread zurück.

Eine Nachfrage auf der Zeitleiste der PR-Unterhaltung ist ein neuer Kommentar
auf oberster Ebene und braucht deshalb weiterhin eine @-Erwähnung.

## Mit wem der Bot spricht

Der Server löst den Autor eines Kommentars, oder die Person, die das Label
`ai-review` gesetzt hat, auf, bevor er irgendetwas tut:

- **Das GitHub-Konto muss auf diesem Server angemeldet sein.** Abgeglichen wird
  die numerische Konto-ID von GitHub, nie der Login. Melde dich unter
  **Einstellungen → Arbeitsbereich → Profil und Identität → Code-Hosting** an
- **Die Person muss Mitglied mit einer Schreibrolle sein** (`member`, `admin`
  oder `owner`) in dem Arbeitsbereich, der das Repository verknüpft
- **Die Person muss auf GitHub in das Repository pushen dürfen.** Antworten
  nutzen ein Token, das auf den Zugriff dieser Person begrenzt ist, wer nur
  lesen darf, bekommt also keine Antwort

Alle anderen werden still ignoriert: Es wird nichts gepostet, und ihre Worte
gelangen nie in den Arbeitsbereich. Kommentare von Bots und die eigenen
Antworten von Control Center werden nie als Fragen behandelt.

### Zwei Server, ein PR

Über das 👀 einigen sich Server auch darauf, wer antwortet. Es wird mit der
eigenen Anmeldung des Autors gesetzt, und GitHub teilt dem Server mit, ob die
Reaktion neu ist. Bist du auf zwei Servern von Control Center angemeldet, die
beide das Repository verknüpfen, antwortet der erste, der reagiert, und der
andere bleibt still. Dasselbe gilt für das Label.

## Was du erwarten kannst

| Was                      | Verhalten                                                                                                |
| ------------------------ | -------------------------------------------------------------------------------------------------------- |
| Bestätigung              | 👀 von deinem Konto auf dem Kommentar (oder beim Label auf dem PR), innerhalb eines Durchlaufs           |
| Antworten                | Gepostet in der Spur, in der die Frage gestellt wurde, beginnend mit `**Control Center** (for @your-login):`. Bei einer eigenen App ist der Autor der Bot der App; über Connect ist es dein Konto, das über die gemeinsame App handelt |
| Zuschreibung im Bereich  | Die Frage gehört dir; der Agent läuft in deinem Auftrag, unter den Autonomieeinstellungen des Bereichs   |
| Reviews                  | Befunde landen im Review-Bereich; das Veröffentlichen auf GitHub ist manuell                             |

Bei einer eigenen App läuft jede Minute ein Durchlauf und prüft bis zu 25 Pull
Requests; über Connect läuft er alle zwei Minuten und prüft bis zu 10, weil sich
diese Aufrufe das eigene GitHub-Kontingent jedes Mitglieds teilen. Ein
Arbeitsbereich, dessen GitHub-Kontingent unter 15 % liegt, wird übersprungen, bis
es sich erholt hat. Die Latenz ist der Preis dafür, dass gar kein eingehender
Netzzugriff nötig ist. Solange der Server offline ist, geht nichts verloren: ein Kommentar, der während der
Ausfallzeit ankommt, wird beim nächsten Durchlauf erfasst.

## Fehlerbehebung

**Bei einem Kommentar, der den Bot erwähnt, passiert nichts.**

- Ist die App auf dem Konto **installiert**, dem das Repo gehört, und das Repo
  mit einem Arbeitsbereich **verknüpft**? Ein unverknüpftes Repo wird
  übersprungen, bevor irgendetwas festgehalten wird, das spätere Verknüpfen
  liefert also trotzdem
- Bist du auf diesem Server bei GitHub angemeldet, Mitglied mit einer
  Schreibrolle und darfst du in das Repo pushen? Alle anderen ignoriert der
  Server, ohne zu antworten
- Ist bei der gemeinsamen App von Control Center die Installation der
  Organisation für diesen Server autorisiert? Siehe
  [Diesen Server für eine Organisation autorisieren](/de-DE/handbuch/anleitungen/github-app/#diesen-server-für-eine-organisation-autorisieren)
- Immer noch nichts? Das Serverprotokoll nennt den Durchlauf und den PR, wenn
  etwas fehlschlägt; such nach `pr_conversation:` (der Poller) und
  `github_pr_conversation:` (die Brücke)

**Das Label startet kein Review.**

Es löst einmal je PR aus, und die Person, die es gesetzt hat, durchläuft
dieselben Prüfungen wie der Autor eines Kommentars. Ist bereits ein Review gelaufen, oder wurde das Label
gesetzt, bevor der Server den PR je gesehen hat (der erste Durchlauf hält den
Rückstand still fest, statt ihn loszutreten), erwähne stattdessen den Bot.
`@usectrl review` startet immer eines, solange nicht bereits ein Review unterwegs
ist.

**Die Antwort des Bots ist nie auf GitHub angekommen.**

Die Antwort selbst geht nie verloren: sie liegt im Review-Bereich des PR in
Control Center. Ein Fehler beim Posten (GitHub ausgefallen, Berechtigungen
geändert) wird protokolliert, und die Antwort wird nicht erneut versucht; frag
im Thread noch einmal, wenn es darauf ankommt.
