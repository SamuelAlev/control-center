Diese Anleitung zeigt dir, wie du einen Arbeitsbereich mit Skills von GitHub
füllst: ein Repository als Quelle hinzufügen, die Skills daraus installieren,
die du brauchst, und sie mit der Zeit aktuell halten. Du kannst außerdem eine
gespeicherte Revision gegen eine passende Vergleichsbasis evaluieren, bevor du
entscheidest, ob du sie behältst.

Das Wichtigste, bevor du anfängst: **Ein Quell-Repository ist
unvertrauenswürdig.** Name, Beschreibung und Sternzahl schreibt, wem es gehört.
Jede Installation durchläuft das Tor des Virenscans, bevor irgendetwas die
Platte oder einen Agenten-Prompt erreicht. Dieses Urteil ist eine
Zulassungsprüfung, kein Beweis, dass ein Skill sicher oder nützlich ist. Lies
den [Abschnitt Skills des Agentenmodells](/de-DE/handbuch/konzepte/agentenmodell/)
zum Installationsmodell und [Evals und Qualität](/de-DE/handbuch/konzepte/evals-und-qualitaet/)
dazu, wie sich Verhaltensnachweise von einem Scan unterscheiden.

Skills liegen unter **Einstellungen → Arbeitsbereich → Fähigkeiten**
(`/workspaces/<id>/settings/workspace/skills`). Sie gelten für diesen
Arbeitsbereich: Was du hier installierst, gehört nur hierher. Die Seite hat
zwei Tabs: **Installiert** (lokale Skills, einschließlich eines Editors
**Neuer Skill**) und **Quellen** (GitHub-Kataloge). Beide Schreibvorgänge
durchlaufen dasselbe Scan-Tor.

## Ein Skill-Repository hinzufügen

1. Öffne **Einstellungen → Arbeitsbereich → Fähigkeiten** und wechsle zum Tab
   **Quellen**.
2. Drücke **Repository hinzufügen**.
3. Füge eine GitHub-Repository-URL ein, zum Beispiel
   `https://github.com/anthropics/skills`, und bestätige.

Der Server prüft, dass das Repository existiert und mit seinen Zugangsdaten
sichtbar ist, und hängt es dann an die linke Leiste. Dazwischen sitzt kein
kuratierter Katalog: Jedes GitHub-Repository geht, und den Ruf beurteilst du
selbst — eine Sternzahl ist ein Indiz, nie eine Garantie.

Die Skills eines Repositorys sind die Verzeichnisse mit einer `SKILL.md` (bis
zu drei Ebenen tief, plus das Layout des Claude-Plugin-Marketplace
`plugins/<plugin>/skills/<skill>`; Abhängigkeits- und Vendor-Bäume werden
übersprungen). Sagt das Raster später, das Repository habe keine Skills, heißt
das genau das: Kein Verzeichnis darin folgt der Skill-Konvention.

## Einen Skill vor dem Installieren prüfen

Wähle ein Repository in der Leiste. Seine Skills erscheinen rechts als Raster,
darüber ein Filterfeld, das den Katalog nach Name, Beschreibung oder Slug
eingrenzt. Klicke eine Karte an, um die Detailansicht zu öffnen. Sie zeigt
drei Dinge:

- **Die README**, als Markdown gerendert — die `README.md` im
  Skill-Verzeichnis, oder der Rumpf der `SKILL.md`, wenn es keine README gibt.
- **Die Scan-Vorschau** — das Urteil (`pass`, `warn` oder `quarantine`), die
  Fähigkeiten, die der Inhalt des Skills deklariert (führt die Shell aus,
  schreibt Dateien, Netzwerkzugriff …), und jeden Befund, den der Scanner
  festgehalten hat.
- **Die Dateianzahl** — eine Installation schreibt das ganze Verzeichnis des
  Skills, nicht nur seine `SKILL.md`.

Die Vorschau scannt genau die Bytes, die eine Installation schreiben würde.
Das Urteil, das du siehst, ist das Urteil der Installation; hinter deinem
Rücken wird nichts neu beurteilt.

## Einen Skill installieren

1. Öffne die Detailansicht des Skills.
2. Lies das Scan-Urteil. Bei einem Urteil `warn` oder `pass` drückst du
   **Installieren**.
3. Bei einem Urteil `quarantine` bleibt die Installation deaktiviert, bis du
   **Ich akzeptiere das Risiko — trotzdem installieren** ankreuzt. Diese
   Übersteuerung wird festgehalten, nicht stillschweigend vorausgesetzt.

Die Installation schreibt das Verzeichnis des Skills in den Arbeitsbereich,
legt einen Pin in `skills-lock.json` ab (Quell-Repository, Pfad, der Commit,
von dem er stammt, und ein Inhalts-Hash), und der Skill steht den Agenten im
Arbeitsbereich zur Verfügung. Eine Karte mit **Name vergeben** heißt, dass ein
anderer Skill diesen Namen lokal schon besitzt — deinstalliere den zuerst.

## Skills mit der Zeit aktualisieren

Karten installierter Skills tragen Badges: **Installiert**, oder **Update
verfügbar**, wenn das Repository über den Commit hinaus ist, den du gepinnt
hast. Öffne die Detailansicht und drücke **Aktualisieren**, um den Skill beim
neuen Commit erneut abzurufen. Ein Update durchläuft dasselbe Scan-Tor wie
eine Installation — ein Skill, dessen neue Version unter Quarantäne fällt,
wird abgelehnt, und die Version, die du hattest, bleibt. Der Hash der alten
Version bleibt in der Lock-Datei als Referenz für ein Rollback.

## Einen Skill evaluieren

1. Öffne **Einstellungen → Arbeitsbereich → Fähigkeiten**, wähle den
   installierten Skill und speichere alle Änderungen. Prüfe unter
   **Skill-Evaluierung** den Paket-Hash.
2. Wähle **Evaluierung starten**. Wähle einen **Aufgabenkorpus**, der zum
   Zweck des Skills passt, und einen **Adapter**. Das eingebaute Harness nutzt
   einen konfigurierten Anbieter und ein werkzeugfähiges Modell. **Claude Code**
   nutzt das standardmäßig verwaltete Claude-Konto und eine konkrete
   Modellkennung; melde dich zuerst unter **Einstellungen → Adapter** an. Es
   borgt sich nicht die persönliche Anmeldung des Serverbetreibers.
3. Wähle einen **Vergleich** aus der Tabelle unten.
4. Setze **Wiederholungen pro Aufgabe** (1–20) und **Budget (US-Cent)**. Zum
   Beispiel bedeutet `100` 1 US-Dollar. Wähle **Evaluierung starten**, um die
   bezahlte Arbeit des Anbieters zu autorisieren.
5. Verfolge die Kampagne unter **Observability → Qualität**, oder kehre über
   **Qualität öffnen** im Skill-Panel zurück.

Bei Claude-Code- und Codex-OAuth-Abos ist das Budget eine **Stoppschwelle für
die API-äquivalente Nutzung**, kein Rechnungslimit und kein Maß für das
Abo-Kontingent. `100` lässt eine Schwelle von 1 US-Dollar zu: Ein laufender
Aufruf kann sie überschreiten, aber sobald die gemeldete Nutzung sie erreicht,
starten keine weiteren Aufrufe mehr. Auch unbekannte Nutzung stoppt weitere
Aufrufe. Ein kleines Budget kann den Vergleich unvollständig lassen; es
verspricht nicht, den ausgewählten Korpus zu vollenden.

Anbieter mit API-Schlüssel behalten konservative Reservierungen pro Aufruf auf
Basis dokumentierter Tokenlimits und Preise. Sie können `100` schon vor der
Ausgabe ablehnen, wenn ein sicher reservierter Aufruf mehr braucht. Der Fehler
nennt das gewählte Modell und die Mindestreservierung; wähle ein günstigeres
Modell oder erhöhe dieses Budget.

| Vergleich | Damit beantwortest du |
| --- | --- |
| **Nicht vorhanden vs verfügbar** | Verbessert die normale Entdeckung und Nutzung dieses Skills das Ergebnis gegenüber dem Fehlen? |
| **Vorherige vs aktuelle Revision** | Bewahrt oder verbessert das Update das Verhalten gegenüber einer früher erfassten Revision? |
| **Erzwungenes Laden vs nicht vorhanden** | Kann der Inhalt helfen, wenn er ausdrücklich geladen wird? Das diagnostiziert Ladeprobleme; es belegt keine normale Entdeckung. |
| **Zusammensetzung** | Hilft das Hinzufügen des Kandidaten oder kollidiert es mit den ausgewählten Umgebungs-Skills? Die Vergleichsbasis behält denselben Umgebungsbestand ohne den Kandidaten. |

**Vorherige vs aktuelle Revision** braucht einen Paket-Hash aus der
Kampagnenhistorie. Evaluiere eine Revision, bevor du sie ersetzt, wenn du sie
als Vergleichsbasis nutzen willst; beliebige Git-Historie wird nicht
importiert.

Ungespeicherte Änderungen, ein nicht verfügbarer Hash und der schreibgeschützte
Demo-Modus blockieren den Start. Der Server prüft zudem den Zugriff auf
Arbeitsbereich und Repository, Scan-Quarantäne, Aktionsrichtlinie,
Modellunterstützung, Preisgestaltung und Ausführungskapselung. Behebe eine
fehlgeschlagene Prüfung, statt sie zu umgehen. Anbieter- und Modellidentität
werden erfasst, aber ein Remote-Modellalias friert die zugrunde liegenden
Gewichte des Anbieters nicht ein.

### Prüfen, abbrechen und exportieren

Lies Abdeckung und Ausgaben zusammen mit den Ergebnissen je Aufgabe und
Regressionen. Öffne einzelne Versuche, um beobachtete Skill-Ladevorgänge,
Werkzeugereignisse, Fehler und Prüfernachweise zu untersuchen. Ergebnisse
**Teilweise**, **Veraltet** und **Nicht eindeutig** sind keine Empfehlungen,
eine Revision zu übernehmen. Der Hash eines Berichts identifiziert das
erfasste Paket, nicht unbedingt das aktuell installierte.

Nutze **Durchlauf abbrechen** für eingeplante oder aktive Arbeit.
Abgeschlossene Versuche bleiben sichtbar; ein Abbruch erstattet bereits
erbrachte Anbieterarbeit nicht. **Bereinigtes JSON kopieren** kopiert einen
begrenzten Nachweis-Export in die Zwischenablage, kein vollständiges
Replay-Bundle privater Quellen. Siehe
[Evals und Qualität](/de-DE/handbuch/konzepte/evals-und-qualitaet/) zu Nachweisen
und Plattformgrenzen.

### Nach Updates neu evaluieren

Automatische bezahlte Neuevaluierung ist **standardmäßig aus**. Wähle nach der
Evaluierung der aktuellen Revision eine Kampagne unter **Konfiguration der
Update-Richtlinie** und aktiviere **Update-Evaluierungen aktivieren**. Diese
Richtlinie zu ändern erfordert die Berechtigung eines
Arbeitsbereichsadministrators. Die ausgewählte Kampagne liefert Korpus,
Adapter, Anbieter/Modell, Vergleich, Wiederholungen und Budget.

Nachfolgende zugelassene Inhaltsänderungen planen budgetierte Arbeit ein;
unveränderte Hashes werden dedupliziert. **Update-Evaluierungen deaktivieren**
verhindert künftige automatische Zulassungen. Nutze **Durchlauf abbrechen** für
eine bereits zugelassene Kampagne. Historische Berichte bleiben an ihre
ursprünglichen Paket-Hashes gebunden; die Neuevaluierung veröffentlicht,
aktiviert oder überschreibt keinen Skill.

## Einen Skill deinstallieren, ein Repository entfernen

**Deinstallieren** (in der Detailansicht eines installierten Skills, oder
Löschen im Tab Installiert) entfernt das Verzeichnis des Skills und seinen
Lock-Pin zusammen — ein deinstallierter Skill hinterlässt nichts.

**Ein Repository entfernen** nimmt aus der Leiste nur den Katalog: Skills, die
du daraus installiert hast, bleiben installiert und lassen sich weiter
aktualisieren, weil ein Pin das Repository unter seinem Namen festhält und
nicht als Verweis auf den Quelleneintrag. Füge das Repository wieder hinzu,
wenn du es erneut durchsuchen willst.

## Einen Skill aufrufen

Skills werden unter einem eigenen Namensraum aufgerufen, damit sie nie mit den
eingebauten Slash-Befehlen kollidieren (`/plan`, `/goal`, `/loop`, `/compact`):

- `/skill:<name>` — ein Skill, der in diesem Arbeitsbereich installiert oder
  dem Agenten zugeordnet ist
- `/skill:<repo>:<name>` — ein Skill, den ein in diesem Bereich ausgechecktes
  Repo mitbringt

Ein bloßer Name, der kein eingebauter Befehl ist, wird weiter aufgelöst, für
Nachrichten aus der Zeit vor dem Namensraum. `/skill:plan` erreicht einen
Skill namens `plan`; `/plan` ist immer der eingebaute Befehl.

## Repo-bezogene Skills

Ein ausgechecktes Repo kann eigene Skills mitbringen, in `.agents/skills/`,
`.agent/skills/`, `.claude/skills/`, `.opencode/skills/` oder `skills/`. Die
installierst du über diese Seite **nicht**. Ein Agent trägt nur die Skills des
Repos, in dem er gerade arbeitet; sie wechseln, wenn er wechselt. Der Composer
ist nicht so eingegrenzt: `/skill:<repo>:<name>` erreicht jedes Repo im
Bereich.

Repo-Skills durchlaufen denselben Scan, der im Zweifel schließt (`pass` /
`warn` / `quarantine`), bevor ihr Frontmatter einen Prompt erreicht. `warn`
wird zugelassen; `quarantine` wird zurückgehalten, und auf diesem Weg kannst
du das nicht übersteuern.

Siehe [Repo-bezogene Skills](/de-DE/handbuch/konzepte/agentenmodell/#repo-bezogene-skills)
und [Slash-Befehle](/de-DE/handbuch/referenz/slash-befehle/).
