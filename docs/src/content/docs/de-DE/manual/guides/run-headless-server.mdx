Lass `cc_server` auf einer Maschine laufen, die an bleibt, und verbinde dich
dann vom Desktop, aus einem Browser oder vom Telefon aus. Der Server ist ein
natives Binary in reinem Dart, ohne Flutter-Engine, und läuft deshalb headless
unter macOS, Linux oder Windows. Ihm gehört die Datenbank, er führt die Agenten
aus und tätigt jeden externen API-Aufruf. Die Clients zeichnen nur.

## In Docker betreiben (vorgefertigte Images)

Jedes Release veröffentlicht einen selbst gehosteten Stack aus vier
GHCR-Images — das Backend, die beiden statischen Thin Clients und das optionale
Kopplungs-Relay — plus den optionalen Anmeldedienst `cc-connect`
([Einen Connect-Server betreiben](/de-DE/handbuch/anleitungen/connect-server-betreiben/))
und ein separates Image `cc-server-demo` für den öffentlichen Demo-Host. Eine selbst gehostete Installation braucht kein ausgechecktes
Quell-Repository. Pinne einen Versions-Tag
(`ghcr.io/samuelalev/<image>:v0.0.1-rc.1`) oder nimm `latest`.

| Image                                             | Was es ist                                      | Veröffentlicht   |
| ------------------------------------------------- | ----------------------------------------------- | ---------------- |
| `ghcr.io/samuelalev/cc-server`                    | Das Backend: Datenbank, Agenten, MCP, Webhooks  | `-p 9030:9030`   |
| `ghcr.io/samuelalev/cc-webapp`           | Der Web-Client (statisches nginx)               | `-p 8080:8080`  |
| `ghcr.io/samuelalev/cc-remote`        | Die Telefon-Begleit-PWA (statisches nginx)      | `-p 8081:8080`  |
| `ghcr.io/samuelalev/cc-signaling-server`     | Das verschlüsselte Verbindungs-Relay (optional) | `-p 8788:8788`   |

Der ganze Stack als Compose-Datei:

```yaml
services:
  server:
    image: ghcr.io/samuelalev/cc-server:latest
    ports: ["9030:9030"]
    volumes: ["cc_data:/data"]
    restart: unless-stopped
  web:
    image: ghcr.io/samuelalev/cc-webapp:latest
    ports: ["8080:8080"]
    restart: unless-stopped
  remote:
    image: ghcr.io/samuelalev/cc-remote:latest
    ports: ["8081:8080"]
    restart: unless-stopped
  signaling:
    image: ghcr.io/samuelalev/cc-signaling-server:latest
    ports: ["8788:8788"]
    restart: unless-stopped

volumes:
  cc_data:
```

Was du wissen solltest, bevor du davon etwas über Loopback hinaus erreichbar
machst:

- **Das Image `cc-server` bringt `CC_SERVER_INSECURE=1` mit** (es muss `0.0.0.0`
  binden, damit Verkehr über veröffentlichte Ports ankommt). Nutze einen
  TLS-terminierenden Reverse-Proxy — Caddy, Traefik, nginx oder einen
  Cloudflare Tunnel — in einem vertrauenswürdigen Netz, oder häng ein Zertifikat
  ein und setze `CC_SERVER_TLS_CERT` / `CC_SERVER_TLS_KEY` (und nimm danach
  `CC_SERVER_INSECURE` weg). Diese Einstellung steuert nur den äußeren
  HTTP/WebSocket-Listener des Servers. Sie deaktiviert nie die verpflichtende
  Ende-zu-Ende verschlüsselte Client-Sitzung. TLS schützt weiterhin
  Login-/Bootstrap-Verkehr, Verbindungsmetadaten, öffentliche Endpunkte und die
  Auslieferung des Web-Clients. Alles lässt
  sich mit `docker run -e …` oder dem Compose-Block `environment:` überschreiben.
- **Nur `/data` hält Zustand.** Die SQLite-Datenbanken, die Geheimnisse
  gekoppelter Geräte, heruntergeladene Modelle und das Audio der Besprechungen
  liegen alle im Volume. Sichere es, dann ist der Container austauschbar.
- **Anbieter-Secrets gehören in eine eingehängte `.env`, nie in `-e`.** Der
  Server verweigert den Start, wenn `GITHUB_APP_PRIVATE_KEY`,
  `GITHUB_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_SECRET`, `LINEAR_API_KEY` oder
  ein `SLACK_*SECRET*` in seiner Prozessumgebung steht. Häng die Datei nur
  lesbar unter `/app/bin/.env` ein (`-v /secure/cc.env:/app/bin/.env:ro`), oder
  konfiguriere die Apps in den Einstellungen.
- **Kopple einen Client aus dem Image heraus**, bevor die erste Verbindung
  steht. Das ist das Container-Gegenstück zu
  [Schritt 3](#schritt-3-einen-client-vor-dem-ersten-start-koppeln):

  ```bash
  docker run --rm -it -v cc_data:/data \
    --entrypoint /app/bin/cc_server ghcr.io/samuelalev/cc-server:latest pair
  ```

- **Die beiden Client-Images sind statische nginx-Hosts.** Eingebettete
  Browser-Editoren nutzen dieselbe App-Origin und dieselbe verschlüsselte
  Verbindung, wie [unten](#browser-editor-ressourcen) beschrieben. Das Verbindungsformular
  jedes Clients nimmt deine Server-URL, die Geräte-ID und den
  Kopplungsschlüssel. Das Signalisierungs-Relay braucht nur seinen Port
  (`SIGNALING_HOST` / `SIGNALING_PORT` lassen sich überschreiben). Es ist
  zustandslos, hält keine
  Kopplungsschlüssel und ist ein **Rückfall**: Ein Telefon nimmt Loopback, LAN, Tailnet
  oder einen direkten `wss://`-Weg, sobald einer erreichbar ist, und fällt nur
  auf das Relay zurück, wenn keiner es ist. Lass es weg, wenn deine Clients den
  Server immer direkt erreichen. Der Broker kann Routing-IDs, IP-Adressen, Größen
  und Timing sehen und Verkehr unterbrechen; den Ressourcenstrom zwischen Client
  und Server kann er nicht entschlüsseln.

Der Rest dieser Anleitung baut den Server aus dem Quellcode. Die Flags und das
Verhalten, die sie behandelt, sind dieselben, die die Umgebungsvariablen des
Images setzen.

## Voraussetzungen

- Das [Dart SDK](https://dart.dev/get-dart). Dieses Repo pinnt sein SDK mit [fvm](https://fvm.app), deshalb stellst du jedem Befehl `fvm` voran.
- Dieses Repository, ausgecheckt.
- Die native Toolchain, die das Bereitstellungs-Skript braucht — Rust/`cargo`, dazu `meson`, `ninja`, `pkg-config`, `git` und ein C++-Compiler. Jedes Build-Skript nennt, was es nicht findet, und wie du es installierst.
- Ein erreichbarer Host: Loopback für den lokalen Gebrauch, oder eine LAN- oder öffentliche Adresse mit TLS für entfernte Clients.

## Schritt 1: Die nativen Bibliotheken bereitstellen

Die nativen Bibliotheken sind **erforderlich**. Einen eingeschränkten Modus
gibt es nicht. Baue sie vom Wurzelverzeichnis des Repos aus, bevor du
irgendetwas anderes tust:

```bash
scripts/natives/build_natives.sh
```

Das baut `rift`, `fff`, tree-sitter samt Grammatiken, `aec`, `lame`,
`ccpty`, `cc_watcher`, `cc_inference` und das SAML-Native nach
`build/natives/`. Der Build-Hook von `cc_server` schreibt, was dort
bereitliegt, erneut ins Bundle. Überspringst du diesen Schritt, schlägt der
Build entweder sofort fehl, oder es entsteht — mit dem Ausweg unten — eine
Binärdatei, deren Startprüfung den Start verweigert und die fehlende
Bibliothek nennt.

:::note[Ausweg nur zum Kompilieren]
Eine leere Datei `.cc_natives_allow_missing` im Wurzelverzeichnis des Repos
stuft den Build-Fehler fehlender nativer Bibliotheken zu einer Warnung herab.
Sie dient der Syntaxprüfung eines frischen Klons. Ein so gebauter Server
startet nicht. Es muss eine **Datei** sein. Der Runner des Build-Hooks reicht
die Umgebung des Aufrufers nicht weiter, eine Umgebungsvariable wird also
ignoriert.
:::

## Schritt 2: Die Binärdatei bauen

```bash
cd apps/cc_server
fvm dart build cli
```

Das Bundle legt `libsqlite3` und die bereitgestellten nativen Bibliotheken
neben die Binärdatei. System-SQLite und eine Flutter-Engine brauchst du nicht.
Die ausführbare Datei liegt unter
`./build/cli/<os_arch>/bundle/bin/cc_server`.

## Schritt 3: Einen Client vor dem ersten Start koppeln

Ein frisches Datenverzeichnis hat kein gekoppeltes Gerät und keinen vorab
geteilten Schlüssel, deshalb lässt sich die Abfrage des Kopplungsschlüssels im
Client noch nicht erfüllen. Stell einen mit dem Unterbefehl `pair` aus. Er
schreibt `global.db` und `secrets.json` direkt. Ein Server, der dieses
Datenverzeichnis schon bedient, nimmt das neue Gerät ohne Neustart auf:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030
```

Er gibt drei Werte aus, die du in das Verbindungsformular eines Clients
einfügst:

```
Connect a thin client (paste into its connect form):
  Server      ws://localhost:9030/rpc
  Device id   web-client
  Pairing key <a freshly generated key>
```

Nützliche Flags: `--device` (Vorgabe `web-client`; die ID wählt auch die
Geräteklasse — `desktop`, `ios`, `android`, alles andere ist ein Web-Client),
`--label` (Vorgabe ist der Plattformname plus der Hostname dieser Maschine),
`--host` (der Host, der in der URL steht, weil Loopback von einer anderen
Maschine aus nicht erreichbar ist) und `--client-url`. Ein erneutes `pair`
rotiert den Schlüssel dieses Geräts und beendet seine laufenden Sitzungen. Die
Kopplung legt nie einen Arbeitsbereich an. Nur der Serverinhaber legt
Arbeitsbereiche an: Auf dem Client des Inhabers benennt und erstellt das
Onboarding den ersten, und alle anderen warten, bis der Inhaber einen für sie
anlegt oder ein Arbeitsbereichs-Admin sie einlädt.

Mit `--client-url` gibt er zusätzlich einen QR aus, den du im Terminal scannen
kannst. Er öffnet den Web-Client schon ausgefüllt:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030 \
  --bind any --host 192.168.1.42 --client-url https://app.usectrl.dev
```

:::caution[Dieser QR ist nicht der Telefon-QR]
`--client-url` baut einen Link für den **Web-Client**: Server-URL, Geräte-ID
und Schlüssel im URL-Fragment. Die Telefon-App **Remote** erwartet einen
anderen Payload, den vollständigen Verbindungsdeskriptor des Servers plus ein
Ablaufdatum, ausgestellt unter **Einstellungen → Du → Deine Geräte** in einem
laufenden Client. Die beiden lassen sich nicht gegeneinander austauschen. Siehe
[Ein Gerät koppeln](/de-DE/handbuch/anleitungen/geraet-koppeln/).
:::

Eine Zugangsberechtigung von `cc_server pair` läuft nach 30 Tagen ab, wie eine in der App ausgestellte; führe `pair` für dasselbe Gerät erneut aus, um eine neue auszustellen. Widerrufe ein über die
CLI ausgestelltes Gerät unter **Einstellungen → Du → Deine Geräte**, sobald du
es nicht mehr brauchst.

Der Kopplungsschlüssel authentifiziert den verpflichtenden Noise-Handshake;
jede Sitzung leitet frische Verkehrsschlüssel ab und prüft die signierte
Identität des Servers. Schütze den Kopplungsschlüssel und beziehe ihn aus einer
vertrauenswürdigen Quelle (auch aus einem vertrauenswürdigen QR-Code);
verifiziere dann einen neuen Server-Fingerabdruck über einen separaten
vertrauenswürdigen Kanal oder gegen einen bekannten Pin. Akzeptiere einen
geänderten Pin nicht stillschweigend: koppele über einen vertrauenswürdigen
Kanal neu, wenn du die Serveridentität absichtlich austauschst. TLS allein kann
diesen Ende-zu-Ende-Identitäts-Pin nicht herstellen.

## Schritt 4: Den Server starten

Auf Loopback, der Vorgabe und allem, was ein Client auf derselben Maschine
braucht:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030
```

Um ihn von einer anderen Maschine zu erreichen, binde jede Schnittstelle. Ein
Bind außerhalb von Loopback ohne TLS wird **beim Start abgelehnt** (`Refusing to bind non-loopback address …
without TLS`). Gib ihm deshalb ein Zertifikat:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --tls-cert /path/fullchain.pem --tls-key /path/privkey.pem \
  --public-url wss://server.example:9030/rpc
```

Oder terminiere TLS in einem Reverse-Proxy in einem vertrauenswürdigen
privaten Netz und gib dahinter einen Klartext-Bind frei:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --insecure --public-url wss://server.example/rpc
```

`--insecure` wird ignoriert, wenn `--tls-cert` und `--tls-key` beide gesetzt
sind. TLS gewinnt immer. Der Server gibt den Klartext-Zustand des äußeren
Listeners als `insecure: true` in `GET /healthz` bekannt. Das schaltet die
Noise-Verschlüsselung auf `/rpc` nicht ab, egal ob der Client direkt oder über
das Relay verbindet. Aktualisiere Server, Relay und Clients gemeinsam: Alte
Klartext-RPC-Clients werden abgelehnt, ohne Kompatibilitäts-Fallback.
Öffentliche Anfragen an sensible Ressourcen-Routen (einschließlich
Sicherungsübertragungen) erhalten HTTP `426`, auch von Loopback; gekoppelte
Clients nutzen stattdessen den verschlüsselten Tunnel.

Der Server läuft, bis `SIGINT` oder `SIGTERM` kommt, und fährt dann sauber
herunter.

### Die Startzeilen lesen

Zwei Zeilen zeigen dir, wie dieser Server eingerichtet ist. Die Erreichbarkeitszeile neben dem Bereitschaftsbanner beginnt mit `cc_server exposure:` und nennt, wie weit der Server erreichbar ist (`bind`, `tls`, `relay`, `tunnel`), ob ein Serverinhaber eingetragen ist (`owner`) und wie Agenten auf dieser Maschine laufen (`sandbox`):

- `sandbox=native`: Jeder Agentenlauf ist in die Betriebssystem-Sandbox eingebettet.
- `sandbox=off`: Du hast den Server mit `--sandbox off` gestartet, daher laufen die Agenten jedes Mitglieds auf dieser Maschine ohne Einschränkung.
- `sandbox=unavailable`: Der Host hat kein Sandbox-Backend (Windows oder Linux ohne `bwrap` und `socat`), daher starten nur Agentenläufe, für die der Serverinhaber einsteht. Die Läufe aller anderen werden abgewiesen mit „Dieser Server hat keine Sandbox, daher kann hier nur der Serverinhaber Agenten ausführen.“

Eine Sandbox-Zeile weiter oben im Protokoll sagt dasselbe in Worten und nennt, wenn ein Backend fehlt, was zu installieren ist. Agenten anderer Leute ohne Sandbox laufen zu lassen, ist eine Entscheidung, die der Serverinhaber einmal für alle trifft, mit `--sandbox off`. Siehe [Sandbox-Richtlinien konfigurieren](/de-DE/handbuch/anleitungen/sandbox-richtlinien/#prüfen-ob-deine-agentenläufe-in-der-sandbox-laufen).

## Schritt 5: Einen Client verbinden

Richte einen Client auf die Server-URL und den Kopplungsschlüssel aus Schritt 3
aus:

- **Desktop-App**: Klicke auf dem Bildschirm beim ersten Start auf **Mit einem Server verbinden**, oder füge den Server später unter **Einstellungen → Server → Verbindung und Status** hinzu. Siehe [Mit einem Remote-Server verbinden](/de-DE/handbuch/anleitungen/remote-server-verbinden/).
- **Web-Client**: Öffne [app.usectrl.dev](https://app.usectrl.dev) (oder deine eigene Kopie des Web-Builds), klicke auf **Mit einem Server verbinden** und gib die Server-URL und, unter **Kopplungsschlüssel verwenden**, Geräte-ID und Kopplungsschlüssel ein.
- **Telefon**: Kopple die App **Remote** von einem laufenden Client aus. Siehe [Ein Gerät koppeln](/de-DE/handbuch/anleitungen/geraet-koppeln/).

:::note[cc_server liefert kein Web-Bundle aus]
Ein eigenständiger `cc_server` hängt nie ein Web-Wurzelverzeichnis ein,
deshalb antwortet `GET /` mit 404. Der Web-Client wird getrennt gehostet. Nimm
`app.usectrl.dev`, oder hoste den Web-Build selbst auf einem beliebigen
statischen HTTPS-Host (das Image `cc-webapp` oben ist genau das). Eine
Browser-Origin außer Loopback muss in `--allowed-origins` stehen, sonst wird
das WebSocket-Upgrade nach `/rpc` abgelehnt. Die Vorgabeliste ist
`https://app.usectrl.dev`, und `localhost` sowie `127.0.0.1` sind immer
erlaubt.
:::

### Browser-Editor-Ressourcen

Das Editor-Frontend ist vertrauenswürdiger Anwendungscode und läuft auf der
eigenen Origin der Web-App. Sein Service Worker leitet HTTP- und
WebSocket-Verkehr über dieselbe authentifizierte verschlüsselte Sitzung wie der
Rest des Clients. `cc_server` entschlüsselt jede Anfrage, leitet sie an sein
lokales code-server-Backend weiter und verschlüsselt die Antwort zurück zum
Client. Die Dateien bleiben Eigentum des Servers.

Der Editor läuft auf dem Server als dessen eigener Benutzer, mit Terminal, Aufgaben und Erweiterungen. Deshalb kann nur der [Serverinhaber](/de-DE/handbuch/konzepte/autorisierung/#der-serverinhaber) ihn öffnen. Eine Sitzung gehört dem Gerät und der Person, die sie geöffnet hat. Er startet mit eingeschaltetem Arbeitsbereichsvertrauen von VS Code, also fragt VS Code, bevor es einem Ordner vertraut, und mit ausgeschalteten automatischen Aufgaben, damit die Aufgaben eines Repositorys beim Öffnen nie starten. Alle anderen behalten den eingebauten Editor der App und ihre Dateiansichten; der vollständige Editor wird ihnen nicht angeboten.

Hoste den Web-Client über HTTPS oder eine sichere Loopback-Origin, damit
Service Worker laufen können. Der normale Web-Build und die Release-Skripte
enthalten die gemeinsamen Ressourcen-Assets. Wenn du ein Bundle manuell baust,
stelle diese Assets anschließend aus dem Wurzelverzeichnis des Repositorys
bereit:

```bash
node tool/stage_resource_assets.mjs build/web
```

Für den Web-Build des Telefons setze stattdessen `apps/cc_remote/build/web`
ein. Das kopiert `cc_resource_bridge.js`, `cc_resource_worker.js` und
`cc_resource_ws_shim.js` in das App-Bundle.

Nativer Editor-Verkehr nutzt stattdessen eine Fassade mit
Capability-Begrenzung auf Loopback. Setze das private Loopback-Gateway für
Berichte und Befehle der vom Server gestarteten Editor-Erweiterung nicht über
einen öffentlichen Proxy frei. Sensible öffentliche HTTP-Anfragen werden
abgelehnt; Ressourcen erfordern eine authentifizierte verschlüsselte Sitzung.

## Schritt 6: Wählen, wie sich Personen anmelden

Der erste Client, der sich als Server-Eigentümer verbindet, wird gefragt, wie
dieser Server Personen bei GitHub, Google Calendar und Linear anmeldet: **Apps
von Control Center verwenden**, **Eigene Apps verwenden** oder **Eigenen
Connect-Server verwenden**. Im Terminal triffst du dieselbe Wahl so:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server connect status --data-dir ./data
./build/cli/<os_arch>/bundle/bin/cc_server connect enable --url https://connect.example.com --data-dir ./data
./build/cli/<os_arch>/bundle/bin/cc_server connect disable --data-dir ./data
```

`CC_CONNECT_URL` (`hosted`, `off` oder eine URL) in der Umgebung oder der `.env`
des Servers legt die Wahl stattdessen fest. Mit **Eigene Apps verwenden**
registrierst du jeden Anbieter unter **Einstellungen → Server → Single sign-on →
Anbieter-Apps**; **Meine GitHub-App erstellen** richtet GitHub in einem Schritt
ein. Anbieter-Secrets gehören in die `.env`-Datei des Servers, nie in die
exportierte Umgebung. Siehe [Die GitHub App erstellen](/de-DE/handbuch/anleitungen/github-app/)
und [Control Center Connect](/de-DE/handbuch/referenz/connect/).

Anmeldungen über Connect enden mit einem Code, den der Browser zeigt, der Server
braucht dafür also keine öffentliche Adresse. Anmeldungen über die eigenen Apps
des Servers schicken den Browser zur öffentlichen URL des Servers zurück, setze
`--public-url` also auf eine Adresse, die die Browser der Personen erreichen.

Das ist der Standard des Servers. Ein Administrator des Arbeitsbereichs kann einem Arbeitsbereich unter **Einstellungen → Arbeitsbereich → Integrationen** eine andere Wahl geben. Mit gesetztem `CC_CONNECT_URL` kann ein Arbeitsbereich zu eigenen Apps wechseln, aber nicht zu einem eigenen Connect; siehe [Die Wahl je Arbeitsbereich](/de-DE/handbuch/referenz/connect/#die-wahl-je-arbeitsbereich).

Um von diesem Server aus Connect für andere Server zu hosten, setze
`CC_SERVER_CONNECT_HOST=on`; siehe
[Einen Connect-Server betreiben](/de-DE/handbuch/anleitungen/connect-server-betreiben/#connect-in-cc_server-einhängen).

## Konfiguration

Die Flags oben sind die, die eine erste Einrichtung braucht. Die vollständige
Oberfläche, 23 Paare aus Flag und Umgebungsvariable, die vier Unterbefehle und
der Aufbau des Datenverzeichnisses, steht in der
[`cc_server`-CLI-Referenz](/de-DE/handbuch/referenz/cc-server-cli/).

:::caution[Unbekannte Flags werden stillschweigend ignoriert]
Der Argument-Parser ist von Hand geschrieben und überspringt alles, was er
nicht erkennt. Ein Tippfehler (`--tls-key-file`, `--bindany`) erzeugt also
keinen Fehler, und der Server startet einfach mit der Vorgabe. Sieh in die
Zeilen des Startlogs, wenn ein Flag keine Wirkung zu haben scheint.
:::

Die vier, die du am ehesten brauchst:

| Flag           | Vorgabe                                                          | Bedeutung                                                                                            |
| -------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `--data-dir`   | das anwendungsbezogene Datenverzeichnis des Betriebssystems je Benutzer | Datenbanken, Geheimnisse, Modelle und zwischengespeicherte Medien                               |
| `--port`       | `9030`                                                           | TCP-Port (`0` = ephemer)                                                                             |
| `--bind`       | `loopback`                                                       | `loopback`, oder `any` für jede Schnittstelle (braucht TLS oder `--insecure`)                       |
| `--public-url` | aus dem Bind abgeleitet                                          | Die RPC-URL, die gekoppelten Clients bekannt gegeben wird. **Setze sie hinter einem Proxy, NAT oder Tunnel ausdrücklich** |

Das Vorgabe-Datenverzeichnis ist `~/Library/Application Support/control-center`
unter macOS, `%APPDATA%\control-center` unter Windows und
`$XDG_DATA_HOME/control-center` (sonst `~/.local/share/control-center`) auf den
übrigen Systemen. Ein auf das Arbeitsverzeichnis bezogenes `.cc_server` wird
nur genutzt, wenn sich kein Home- oder Anwendungsdatenverzeichnis auflösen
lässt.

## Was der Server ausliefert

`cc_server` ist die ganze Produktoberfläche: der Datenweg für Repo-RPC und die
Abonnements, der MCP-Werkzeug-Endpunkt unter `POST /mcp` und `GET /sse` auf
demselben Port, eingehende Webhooks, die Proxys für Medien und Schriften, die
Callbacks für Single Sign-on, das Lease-Protokoll der Fleet, serverseitiges
Abrufen von RSS im 30-Minuten-Takt und die Vektorsuche (die Erweiterung
`sqlite_vector` ist als prozessweite Auto-Extension registriert und fällt nur
dort auf reine Volltextsuche zurück, wo die Erweiterung fehlt).

Der Dispatcher ist **zustandslos**. Eine Sitzung bindet keinen Arbeitsbereich.
Jeder arbeitsbereichsbezogene Aufruf trägt seine eigene `workspace_id`, und
über den Zugriff entscheiden Mitgliedschaft und Rolle des Aufrufers im
Arbeitsbereich. Ein Kopplungsschlüssel allein reicht dafür nicht.

Zwei Dinge, bevor du den Port über Loopback hinaus öffnest (TLS allein bietet
nicht die Ende-zu-Ende-Verschlüsselung des gekoppelten Clients und autorisiert
keine Ressourcen):

- **MCP braucht immer sein Token.** Der Server erzeugt das MCP-Token beim ersten Start, und jede Anfrage, auch von Loopback, muss es als `Authorization: Bearer <token>` senden. Es lässt sich nicht abschalten; der Serverinhaber liest und erneuert es unter **Einstellungen → Server → MCP-Server**. Anfragen aus einer Webseite, an einen unbekannten `Host` oder ein `POST`, das kein JSON ist, werden abgewiesen, bevor das Token geprüft wird. Siehe [MCP-Server nutzen](/de-DE/handbuch/anleitungen/mcp-server/).
- **`GET /healthz` ist absichtlich ohne Authentifizierung**, mit Wildcard-CORS, und veröffentlicht ID, Name, Identitätsfingerabdruck und Build-Version des Servers. Clients brauchen den Fingerabdruck, um den Server zu pinnen. Das ist so gewollt, und jeder erreichbare `cc_server` gibt genau das jedem, der fragt.
