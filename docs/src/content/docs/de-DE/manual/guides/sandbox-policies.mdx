Ob ein Agentenlauf in der Sandbox läuft, entscheidet der Server beim Start
(`--sandbox`). Der Schalter **Sandboxing aktivieren**, die Auswahl **Backend**
und die Schalter **Standardfähigkeiten · neue Konversationen** unter
**Einstellungen → Server → Diagnose und Datenschutz** sind Einstellungen auf
deinem Gerät. Die Hosterkennung der Karte **Sandboxing** meldet, was der
Server-Host umhüllen kann.

Zwei Steuerungen erreichen einen Lauf, und diese Anleitung deckt beide ab: die
**Sandbox-Berechtigungen** je Agent weiter unten und das eigene Flag
`--sandbox` des Servers.

## Was einen Agentenlauf begrenzt

Sechs Dinge halten einen Agenten. Das erste ist die Betriebssystem-Sandbox,
und sie ist die bedingte — die anderen fünf gelten auf jedem Host.

| Grenze                      | Was sie tut                                                                                                                                                                      |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Die Betriebssystem-Sandbox  | Seatbelt unter macOS, bubblewrap unter Linux und WSL2. Umhüllt die Claude-Code-CLI, ACP-Adapter und das Werkzeug `bash` des Harness. **Fehlt unter Windows und unter Linux ohne `bwrap` und `socat`** |
| Der eigene Worktree         | Jede Unterhaltung bekommt einen Copy-on-Write-Checkout. Der ursprüngliche Checkout geht als Schreibverbotspfad in den Lauf ein, und die Sandbox setzt das durch                 |
| Vermittelte Zugangsdaten    | Der Zugangsdaten-Broker stellt aus den Befugnissen des Agenten eine Umgebung je Lauf zusammen und widerruft sie beim Abbau. Keine Befugnis, kein Token in der Umgebung          |
| Aktions-Schutzregeln        | Jedes verändernde Werkzeug deklariert seine Effektklassen, und die Schutzregel löst sie auf, bevor der Aufruf läuft. Ein `prompt` ohne verbundene zuständige Person wird abgelehnt |
| Bereinigung der Umgebung    | ACP und das Werkzeug `bash` des Harness bekommen eine gefilterte Umgebung. Claude Code über `NoSandboxAdapter` erbt die Umgebung des Hosts                                      |
| Die Werkzeugfläche des Modus | Ein Nur-Lese-Modus nimmt die den Worktree verändernden Werkzeuge vollständig heraus und verankert das eigene Ausgabe-Verb des Modus, damit er trotzdem liefern kann            |

Drei Dinge sind schwächer, als sie aussehen:

- Nur der **eingebaute Harness** setzt das Werkzeugtor, die Abschlussverträge
  und die strukturellen Modusregeln durch. Der Adapter Claude Code tut das
  nicht. Claude Code startet insbesondere mit `--dangerously-skip-permissions`,
  weil ein nicht interaktives `claude -p` sonst für immer an seiner eigenen
  Nachfrage hängen bliebe — die eigenen Aufrufe von Claude zum Lesen,
  Schreiben, Bearbeiten und für die Shell sieht Control Center deshalb nicht
  und lässt sie auch nicht durch ein Tor. Wo die Sandbox an ist, ist sie die
  Grenze darum.
- Die prozessinternen Dateiwerkzeuge des Harness (read, write, edit, apply
  patch, search, find, search_files) laufen im Serverprozess, also begrenzt
  sie kein Sandbox-Profil. Nur das Werkzeug `bash` geht durch den gekapselten
  Befehlsrunner. Ihre Grenze sind die eigene Pfadbeschränkung und die
  Aktions-Schutzregeln.
- Auf einem Host ohne Backend gilt die erste Zeile gar nicht. ACP und das
  Werkzeug `bash` des Harness fallen auf die Bereinigung der Umgebung plus die
  Befehlsrichtlinie zurück. Claude Code erbt die Umgebung des Hosts über
  `NoSandboxAdapter`. Der Server sagt das in seinem Startlog. Deins prüfst du
  weiter unten.

## Die Befugnisse eines Agenten setzen

Das ist die einzige Befugnissteuerung, die der Server liest. Sie gilt je Agent
und entscheidet, was der Zugangsdaten-Broker in die Umgebung dieses Agenten
legt.

1. Öffne **Einstellungen → Arbeitsbereich → Agenten**
2. Wähle den Agenten in der Liste
3. Scrolle auf dem Tab **Einstellungen** zu **Sandbox-Berechtigungen**
4. Schalte den Schalter ein — die Beschriftung der Zeile wechselt von
   **Arbeitsbereichsstandard verwenden**
5. Setze die vier Schalter:

| Schalter                             | Was er steuert                                                                                                                                                                                                                          |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **git push erlauben**                | Ist er aus, bekommt der Lauf `GIT_ASKPASS=/usr/bin/false` und `GIT_TERMINAL_PROMPT=0`, ein Push kann also nicht nach Zugangsdaten fragen                                                                                               |
| **GitHub-API-Aufrufe erlauben**      | Steuert zusammen mit **git push erlauben**, ob der Broker das GitHub-Token als `GH_TOKEN` / `GITHUB_TOKEN` injiziert                                                                                                                   |
| **Ticketing-API-Aufrufe zulassen**   | Steuert, ob der Broker `TICKETING_API_KEY` injiziert                                                                                                                                                                                    |
| **Allgemeinen Netzwerkzugriff erlauben** | Wo die Sandbox an ist, ist das ein echtes Ausgangstor: Ist er aus, ist die Zulassungsliste des Laufs leer, und jede ausgehende Anfrage wird am Proxy abgelehnt. Wo kein Backend da ist, wird er am Lauf vermerkt, blockiert aber nichts, was ein gestarteter Prozess tut |

6. Speichern

Kontrollpunkt: Öffne den Agenten erneut, und der Schalter ist noch an, mit
deinen Schaltern — ein gespeicherter Befugnissatz kommt über den Server
unverändert zurück, und ein Agent ohne eigenen Satz fällt auf den
zurückhaltenden Standard zurück (Push aus, GitHub-API aus, Ticketing aus,
Netzwerk an).

:::caution[Zwei Stolperfallen]
Die Beschriftung sagt **Arbeitsbereichsstandard verwenden**, aber es gibt
keine Befugniseinstellung auf Arbeitsbereichsebene, die der Server liest. Ein
Agent mit ausgeschaltetem Schalter bekommt den eingebauten zurückhaltenden
Standard.

Getrennt davon sind die GitHub-Zugangsdaten des Laufs immer nur die des
Brokers — ein auf das Repo begrenztes Installationstoken der GitHub App oder
ersatzweise das PAT aus der Umgebung —, nie das gespeicherte Token des
anfragenden Mitglieds. `actingUserId` wird übergeben, damit der Broker das
Server-PAT einem Mitglied *vorenthalten* kann, das nicht der Besitzer ist und
GitHub nicht verbunden hat. Er legt kein persönliches Token über eine
Befugnis, die aus ist. Behandle **GitHub-API-Aufrufe erlauben** auf einem Host
ohne Betriebssystem-Sandbox nicht als harte Ausgangsgrenze: Ein gestarteter
Prozess erreicht das Netzwerk trotzdem.
:::

## Prüfen, ob deine Agentenläufe in der Sandbox laufen

Zwei Dinge entscheiden das, beide auf dem Server: ob der Host ein Backend
anbietet und ob `--sandbox` an ist. Prüfe sie in dieser Reihenfolge.

1. Öffne **Einstellungen → Server → Diagnose und Datenschutz**
2. Lies die Karte **Sandboxing**. Der Fakt **Host** ist der Rechner, auf dem
   `cc_server` läuft, nicht der Rechner, den du gerade ansiehst. Das Feld
   **Backend** nennt **Native sandbox** (Seatbelt unter macOS, bubblewrap unter
   Linux und WSL2) oder **No isolation**. Der Fakt **Aktiv in Kraft** ist die
   Einstellung dieses Geräts, nicht die Umhüllung, die der Server wirklich
   nutzt.
3. Lies das Startlog des Servers. Es schreibt genau eine von drei Zeilen:
   - `agent sandbox ON` plus die Backend-Notiz — die Läufe sind umhüllt
   - `no OS-native agent sandbox on this host` plus einen Installationshinweis,
     wo es einen gibt — die Läufe sind nicht umhüllt
   - `agent sandbox DISABLED by --sandbox off` — ein bewusstes Abwählen

`GET /healthz` meldet den Sandbox-Zustand nicht, also ist das Startlog die
Prüfung.

Um die Sandbox bewusst abzuschalten — der Grund dafür ist ein Host, auf dem
das Profil sich falsch verhält —, startest du den Server mit `--sandbox off`
oder setzt `CC_SERVER_SANDBOX=off`. Der Standard ist `on`, und `on` heißt
„ein Backend nutzen, wenn der Host eines hat“, nie „eines verlangen“.

Zwei Situationen bekommen nie eine native Sandbox-Umhüllung. Unter **Windows**
meldet die native Prüfung immer, dass keine verfügbar ist, und es gibt nichts
zu installieren — die Agenten-Ausführung nutzt `none`. Das Backend `microvm`
ist getrennt (interaktive Terminals und Rigs) und hängt an der Prüfung seiner
eigenen Laufzeit. Unter **Linux und WSL2** müssen `bwrap` und `socat` auf dem
`PATH` liegen. Ohne sie meldet die Prüfung, dass keine verfügbar ist, und
nennt die fehlenden Pakete.

Unter Linux/WSL2 mit installiertem bubblewrap lassen sich die Globs für
Geheimnisdateien in der Standardrichtlinie nicht für Dateien durchsetzen, die
ein Agent später anlegt. Ein solcher nativer Lauf scheitert jetzt, statt die
Regeln still zu ignorieren. Eine positive Prüfung beim Start garantiert
deshalb nicht, dass eine Ausführung unter Linux starten kann. `--sandbox off`
ist ein bewusstes Abwählen ohne Einschränkung, kein Ersatz für eine
Sicherheitsgrenze.

## Wissen, was ein Modus schon verbietet

Der Modus ist je Bereich gespeichert und speist den Schutzregel-Resolver als
Schicht **Modus-Voreinstellung**. Drei der vier Modi sind schreibgeschützt,
und ein Nur-Lese-Modus verweigert elf Effektklassen rundweg:

| Modus              | Worktree          | Von der Voreinstellung verweigert                                                                                                                                                                                                 |
| ------------------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent** (`chat`) | Beschreibbar      | Nichts — es gelten die eingebauten Vorgaben                                                                                                                                                                                       |
| **Plan**           | Schreibgeschützt  | Eine Datei löschen, außerhalb des Arbeitsbaums schreiben, einen Commit erstellen, zu einem Remote pushen, einen Pull Request öffnen, eine Review veröffentlichen oder mergen, in einen externen Tracker schreiben, ein Paket installieren, einen Prozess ausführen, Arbeitsbereichsstruktur ändern, eine Kapsel (Rig) steuern |
| **Review**         | Schreibgeschützt  | Dieselben elf. Nicht wählbar — der Composer bietet nur Agent, Plan und Orchestrate                                                                                                                                                |
| **Orchestrate**    | Schreibgeschützt  | Dieselben elf                                                                                                                                                                                                                     |

**Auf das Netzwerk zugreifen** und **Ein Geheimnis lesen** verweigert ein
Nur-Lese-Modus absichtlich nicht: Recherche ist der Sinn eines solchen.

## Eine Freigabe verlangen, bevor eine Aktion läuft

Eine Freigabe ist eine Entscheidung der Schutzregeln, keine
Sandbox-Einstellung.

1. Öffne **Einstellungen → Arbeitsbereich → Agent-Berechtigungen**
2. Setze die Aktionsklasse auf **Zuerst fragen**, im Geltungsbereich
   Arbeitsbereich, Agent oder Bereich

Eine Entscheidung **Zuerst fragen** unterbricht den Lauf und fragt dich. Ohne
verbundene zuständige Person fällt sie fail-closed aus, und die Aktion wird
abgelehnt. Die volle Auflösungsreihenfolge steht unter
[Schutzregeln konfigurieren](/de-DE/handbuch/anleitungen/schutzregeln-konfigurieren/).

## Fehlersuche

### Ein Agent kann nicht pushen, obwohl ich es nie verweigert habe

Prüfe die **Sandbox-Berechtigungen** des Agenten. Ein Agent ohne eigenen
Befugnissatz bekommt den zurückhaltenden Standard, und der hat **git push
erlauben** aus — der Broker injiziert also kein GitHub-Token, und git kann
sich nicht authentifizieren.

### Die Karte Sandboxing meldet keine native Sandbox

Dann sind die Agentenläufe auf diesem Host weder von Seatbelt noch von
bubblewrap umhüllt, und die übrigen Grenzen sind das, was du hast. Unter
Linux und WSL2 installierst du beide fehlenden Werkzeuge —
`sudo apt-get install bubblewrap socat` — und startest den Server neu. Das
Startlog sollte danach sagen, dass die Sandbox an ist. Unter Windows gibt es
kein natives Backend zum Installieren, also verschärfe stattdessen die
Schutzregeln. Siehe
[Schutzregeln konfigurieren](/de-DE/handbuch/anleitungen/schutzregeln-konfigurieren/).

### Ein Agent hat eine Datei außerhalb seines Worktrees erreicht

Welches Werkzeug sie erreicht hat, entscheidet, ob das zu erwarten ist.

Die prozessinternen Dateiwerkzeuge des Harness (read, write, edit, apply
patch, search, find, search_files) laufen im Serverprozess, also gilt für sie
kein Sandbox-Profil — ihre Grenze sind die eigene Pfadbeschränkung und die
Schutzregeln. Ein `bash`-Befehl oder die Claude-Code-CLI _ist_ umhüllt, wo
ein Backend existiert, und deine registrierten Checkouts sind in dieser
Umhüllung in jedem Modus schreibgesperrt, einschließlich ihrer über den
Symlink aufgelösten Schreibweisen (unter macOS löst sich ein Pfad über
`/tmp` oder `/var/folders` unter `/private` auf, und beide Schreibweisen sind
jetzt verboten). Auf einem Host ohne Backend gilt davon nichts. So oder so
können die Schutzregeln **Außerhalb des Arbeitsbaums schreiben** rundweg
verweigern.
