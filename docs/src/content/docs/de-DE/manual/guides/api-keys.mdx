Diese Anleitung zeigt, wo jede Zugangsdatenart, die Control Center nutzt, gespeichert ist und wie du sie änderst.

**Auf dem Rechner, an dem du tippst, liegt nichts.** Jede Zugangsdatenart liegt auf dem Server; welche eine Anfrage beantwortet, hängt davon ab, ob ein Mensch dahintersteht.

| Zugangsdaten | Gespeichert | Wer sie nutzt |
| --- | --- | --- |
| Deine Forge- und Ticket-Zugangsdaten | Die Geheimnisdatei des Servers mit Modus 0600, unter deiner Nutzer-ID | Alles, was du anfragst: die PR-Oberfläche, deine Agentenläufe, deine Bilder |
| Die App-Identität des Servers | Dieselbe Datei, dazu `server_settings` für alles, was kein Geheimnis ist | Arbeit, die kein Mensch angefordert hat: Webhooks, PR-Polling, Ticket-Synchronisierung |
| Schlüssel der Modellanbieter und OAuth-Tokens | Der eigene Zugangsdatenspeicher des Servers | Der eingebaute Adapter, für jeden Arbeitsbereich der Installation |
| Slack-Bot-Tokens | `<dataDir>/<workspaceId>/chat_credentials/` auf dem Server | Die Chat-Brücke dieses Arbeitsbereichs |
| Zugangsdaten einer externen CLI | Was diese CLI selbst verwendet | Claude Code, auf dem Server-Host |

## Zwei GitHub-Zugangsdaten, und sie beantworten verschiedene Fragen

- **Deine** stammen aus der Anmeldung (Device Flow) oder einem eingefügten Token. Sie gelten für jede Anfrage *in deinem Namen*, deshalb trägt ein Kommentar, der für dich gepostet wird, deinen Namen. Ein anderes Mitglied kann sie nicht lesen und verbindet seine eigenen
- **Die des Servers** stammen aus der GitHub App, die der Betreiber registriert hat. Sie beantworten alles ohne Aufrufer — der Forge-Zugang bleibt, wenn eine Person geht oder ein Token rotiert

Deine setzt du in der Karte **Code-Hosting** unter **Einstellungen → Arbeitsbereich → Profil und Identität**; die des Servers unter **Anbieter-Apps** bei **Einstellungen → Server → Single sign-on**. Siehe [GitHub-Integration einrichten](/de-DE/handbuch/anleitungen/github-integration/) und [Die GitHub App erstellen](/de-DE/handbuch/anleitungen/github-app/).

:::note[Es gibt auch einen Bildschirm nur über die URL]
`/workspaces/<workspaceId>/api-keys` zeigt dieselben zwei Karten wie der erste Schritt des Onboardings. **In der Oberfläche gibt es nirgends einen Navigationseintrag**; erreichbar ist er nur, indem du die URL eintippst. Nimm stattdessen Einstellungen → Arbeitsbereich → Profil und Identität.
:::

## Schlüssel der Modellanbieter setzen

Der eingebaute Adapter authentifiziert die Anbieter selbst, und diese Zugangsdaten liegen auf dem Server.

1. Geh zu **Einstellungen → Server → Modellanbieter**
2. Scrolle zu **Anbieter & Modelle**
3. Verbinde den Anbieter — Browser-OAuth für OpenAI, Codex, Cursor und Kimi Code; ein API-Schlüssel für Anthropic und die übrigen

Siehe [Adapter und Modelle verwalten](/de-DE/handbuch/anleitungen/adapter/) für die vollständige Liste und dafür, einen eigenen Endpunkt hinzuzufügen.

Diese Zugangsdaten gelten **für den ganzen Host**: ein Schlüssel bedient jeden Arbeitsbereich der Installation. OAuth-Tokens werden aufgefrischt, bevor sie ablaufen.

Externe Adapter-CLIs behalten ihre eigenen Zugangsdaten, in ihrer eigenen Konfiguration, auf dem Server-Host — Control Center verwaltet sie nicht. Authentifiziere Claude Code so, wie es seine eigene Dokumentation beschreibt, auf der Maschine, auf der `cc_server` läuft.

Der Dialog **Umgebungsvariablen** je Adapter sieht nach dem Ort für einen solchen Schlüssel aus. Er schreibt auf dein Gerät, der Server liest seine eigene Kopie, und nichts verbindet die beiden. Siehe [Adapter und Modelle verwalten](/de-DE/handbuch/anleitungen/adapter/).

## Einen Ticket-Anbieter verbinden

Die Karte **Tickets** unter **Einstellungen → Arbeitsbereich → Allgemein** hält beide Hälften einer Entscheidung: bei welchem Anbieter deine Tickets liegen und die Zugangsdaten dafür. Wählst du **Lokal**, blendet das die Zeile mit den Zugangsdaten aus — lokale Tickets liegen in der eigenen Datenbank dieses Servers und haben nichts, wogegen sie sich authentifizieren.

Dein Schlüssel liegt auf dem Server unter deiner Nutzer-ID, wie der der Forge. Seinen eigenen Linear-Schlüssel hält der Server getrennt (**Anbieter-Apps**); darauf läuft die Ticket-Synchronisierung, wenn kein Mensch sie angefordert hat. In die Sandbox eines Agenten wird kein Ticketing-Schlüssel injiziert; Agenten schreiben Tickets über die Werkzeuge von Control Center, die die Regel **In einen externen Tracker schreiben** fragen. Siehe [Linear-Integration einrichten](/de-DE/handbuch/anleitungen/linear-integration/).

## Rotieren oder widerrufen

- **Deine GitHub-Zugangsdaten**: klicke auf **Trennen**, melde dich dann erneut an oder füge das neue Token ein. Widerrufe das alte auf GitHub
- **Die App des Servers**: erzeuge auf der GitHub-Seite der App einen neuen privaten Schlüssel oder ein Client-Secret, füge es unter **Anbieter-Apps** ein und klicke auf **Testen**
- **Ein Modellanbieter**: melde dich in seiner Zeile ab (OAuth) oder entferne den Schlüssel, und verbinde ihn erneut
- **Slack**: füge die Tokens im Verbindungsdialog erneut ein. Siehe [Slack-Integration einrichten](/de-DE/handbuch/anleitungen/slack-integration/)

## Fehlersuche

### Die PR-Liste ist leer, aber mein Token funktioniert in `curl`

Prüfe den Untertitel der Zeile **Code-Hosting**. Nennt er eine andere Quelle („über die App dieses Servers“, „aus der Umgebung“), sind die Zugangsdaten, die du prüfst, nicht die, die antworten — deine wurden nicht gespeichert.

### Das Token wird angenommen, spätere Anfragen scheitern

Das Token wird so geprüft, wie es gespeichert ist, deshalb nennt die Zeile das Konto dahinter — nur das Konto, nicht die Scopes. Ein Token mit zu wenigen Scopes verbindet sich und scheitert danach an einzelnen Anfragen. Prüfe die Scopes und das Ablaufdatum:

```bash
curl -H "Authorization: token YOUR_TOKEN" https://api.github.com/user
```
