Diese Anleitung zeigt, wo jede Zugangsdatenart, die Control Center nutzt, gespeichert ist und wie du sie änderst.

**Auf dem Rechner, an dem du tippst, liegt nichts.** Jede Zugangsdatenart liegt auf dem Server; welche eine Anfrage beantwortet, hängt davon ab, ob ein Mensch dahintersteht.

| Zugangsdaten | Gespeichert | Wer sie nutzt |
| --- | --- | --- |
| Deine Forge- und Ticket-Anmeldung | Die Geheimnisdatei des Servers mit Modus 0600, unter deiner Nutzer-ID | Alles, was du tust: die PR-Oberfläche, Reviews, Merges, deine Linear-Aktionen |
| Die Anbieter-Apps des Servers | Dieselbe Datei, dazu `server_settings` für alles, was kein Geheimnis ist | Die Anmeldung von Personen und Tokens für ein einzelnes Repository für Agenten, Pipelines und Polling |
| Der Installationsschlüssel für Connect | Dieselbe Datei (`connect_install_key`) | Die Identifizierung dieses Servers gegenüber Control Center Connect |
| Schlüssel der Modellanbieter und OAuth-Tokens | Der eigene Zugangsdatenspeicher des Servers | Der eingebaute Adapter, für jeden Arbeitsbereich der Installation |
| Slack-Bot-Zugangsdaten | `<dataDir>/<workspaceId>/chat_credentials/` auf dem Server | Die Chat-Brücke dieses Arbeitsbereichs: die Tokens deiner eigenen App oder die versiegelte Berechtigung der gemeinsamen App |
| Zugangsdaten einer externen CLI | Was diese CLI selbst verwendet | Claude Code, auf dem Server-Host |

## GitHub: deine Anmeldung und Tokens für ein einzelnes Repository

- **Deine** stammt aus **Bei GitHub anmelden**. Sie gilt für jede Anfrage *in deinem Namen*, deshalb trägt ein Review, das für dich gepostet wird, deinen Namen. Ein anderes Mitglied kann sie nicht nutzen und meldet sich selbst an. Ein GitHub-Token zum Einfügen gibt es nicht
- **Arbeit, bei der niemand tippt** (Agenten, Pipelines, Polling, Bot-Antworten), bekommt ein Token für jeweils ein Repository, ausgestellt über die GitHub App des Servers oder über Control Center Connect und begrenzt auf das, was ein verantwortliches Mitglied dort tun darf. Es ist nie deine vollständig weitergereichte Anmeldung

Deine setzt du in der Karte **Code-Hosting** unter **Einstellungen → Arbeitsbereich → Profil und Identität**; die App des Servers unter **Anbieter-Apps** bei **Einstellungen → Server → Single sign-on**. Siehe [GitHub-Integration einrichten](/de-DE/handbuch/anleitungen/github-integration/) und [Die GitHub App erstellen](/de-DE/handbuch/anleitungen/github-app/).

GitLab und Bitbucket nehmen weiterhin ein eingefügtes persönliches Token, das genauso gespeichert wird. Siehe [Einen Code-Host verbinden](/de-DE/handbuch/anleitungen/code-host-verbinden/).

:::note[Es gibt auch einen Bildschirm nur über die URL]
`/workspaces/<workspaceId>/api-keys` zeigt dieselben zwei Karten wie der erste Schritt des Onboardings. **In der Oberfläche gibt es nirgends einen Navigationseintrag**; erreichbar ist er nur, indem du die URL eintippst. Nimm stattdessen Einstellungen → Arbeitsbereich → Profil und Identität.
:::

## Schlüssel der Modellanbieter setzen

Der eingebaute Adapter authentifiziert die Anbieter selbst, und diese Zugangsdaten liegen auf dem Server.

1. Geh zu **Einstellungen → Server → Modellanbieter**
2. Scrolle zu **Anbieter & Modelle**
3. Verbinde den Anbieter — Browser-OAuth für OpenAI, Codex, Cursor und Kimi Code; ein API-Schlüssel für Anthropic und die übrigen

Siehe [Adapter und Modelle verwalten](/de-DE/handbuch/anleitungen/adapter/) für die vollständige Liste und dafür, einen eigenen Endpunkt hinzuzufügen.

Diese Zugangsdaten gelten **für den ganzen Host**: ein Schlüssel bedient jeden Arbeitsbereich der Installation. OAuth-Tokens werden aufgefrischt, bevor sie ablaufen.

Externe Adapter-CLIs behalten ihre eigenen Zugangsdaten, in ihrer eigenen Konfiguration, auf dem Server-Host — Control Center verwaltet sie nicht. Authentifiziere Claude Code so, wie es seine eigene Dokumentation beschreibt, auf der Maschine, auf der `cc_server` läuft.

Der Dialog **Umgebungsvariablen** je Adapter sieht nach dem Ort für einen solchen Schlüssel aus. Er schreibt auf dein Gerät, der Server liest seine eigene Kopie, und nichts verbindet die beiden. Siehe [Adapter und Modelle verwalten](/de-DE/handbuch/anleitungen/adapter/).

## Einen Ticket-Anbieter verbinden

Die Karte **Tickets** unter **Einstellungen → Arbeitsbereich → Allgemein** hält beide Hälften einer Entscheidung: bei welchem Anbieter deine Tickets liegen und wer Control Center ist, wenn es mit ihm spricht. Wählst du **Lokal**, blendet das die Linear-Zeilen aus — lokale Tickets liegen in der eigenen Datenbank dieses Servers und haben nichts, wogegen sie sich authentifizieren.

Linear hat zwei Anmeldungen und keinen eingefügten Schlüssel: **Linear** ist deine, für das, was du tust, und **Linear-Automatisierung** ist die Control-Center-App des Arbeitsbereichs, von einem Administrator verbunden, für Ticket-Synchronisierung, Pipelines und Agenten. Der Server kann außerdem einen **Service-API-Schlüssel** (**Anbieter-Apps**) für Arbeitsbereiche ohne verbundene Automatisierung halten. In die Sandbox eines Agenten werden keine Ticketing-Zugangsdaten injiziert; Agenten schreiben Tickets über die Werkzeuge von Control Center, die die Regel **In einen externen Tracker schreiben** fragen. Siehe [Linear-Integration einrichten](/de-DE/handbuch/anleitungen/linear-integration/).

## Rotieren oder widerrufen

- **Deine GitHub-Anmeldung**: klicke auf **Trennen**, dann erneut auf **Bei GitHub anmelden**. Das Trennen verwirft auch jedes Token, das der Server in deinem Namen ausgestellt hat
- **Ein GitLab- oder Bitbucket-Token**: klicke auf **Token aktualisieren** und füge das neue ein. Widerrufe danach das alte bei der Forge
- **Die App des Servers**: erzeuge auf der Seite der App beim Anbieter einen neuen privaten Schlüssel oder ein Client-Secret, füge es unter **Anbieter-Apps** ein und klicke auf **Testen**
- **Der Installationsschlüssel für Connect**: **Schlüssel rotieren** auf der Karte **Control Center Connect** oder `cc_server connect rotate-key --yes`. Alle, die sich über Connect angemeldet haben, melden sich erneut an. Siehe [Control Center Connect](/de-DE/handbuch/referenz/connect/)
- **Ein Modellanbieter**: melde dich in seiner Zeile ab (OAuth) oder entferne den Schlüssel, und verbinde ihn erneut
- **Slack**: Bei deiner eigenen App fügst du die Tokens im Verbindungsdialog erneut ein. Die gemeinsame App von Control Center hat kein Token zum Rotieren: Ihr Bot-Token wird über Connect erneuert, und **Trennen** widerruft es und deinstalliert den Bot aus Slack. Siehe [Slack-Integration einrichten](/de-DE/handbuch/anleitungen/slack-integration/)

## Fehlersuche

### Ein GitLab- oder Bitbucket-Token funktioniert in `curl`, aber nicht hier

Prüfe den Untertitel der Zeile **Code-Hosting**. Lautet er „aus der Umgebung“, antworten die Zugangsdaten des Servers, nicht deine — deine wurden nicht gespeichert.

### Ein GitLab- oder Bitbucket-Token wird angenommen, spätere Anfragen scheitern

Das Token wird so geprüft, wie es gespeichert ist, deshalb nennt die Zeile das Konto dahinter — nur das Konto, nicht die Scopes. Ein Token mit zu wenigen Scopes verbindet sich und scheitert danach an einzelnen Anfragen. Prüfe seine Scopes und sein Ablaufdatum bei der Forge.

### Ein Anbieter meldet, dass die Anmeldung auf diesem Server nicht eingerichtet ist

Der Server hat für diesen Anbieter weder eine eigene App noch Control Center Connect. Der Server-Eigentümer wählt eins davon unter **Einstellungen → Server → Single sign-on**.
