## Was du baust

Am Ende dieses Tutorials hast du:

- einen Arbeitsbereich, der nach deinem Projekt benannt ist
- ein darin registriertes Git-Repository
- fünf angelegte Agenten, von denen du einen so weit eingerichtet hast, dass er laufen kann
- einen zweiten, leeren Arbeitsbereich, der die Isolationsgrenze belegt

Das Onboarding hat dir bereits einen Arbeitsbereich angelegt. Dieses Tutorial legt absichtlich einen neuen an, damit du jeden Teil des Vorgangs siehst.

Bevor du anfängst, wähle einen Git-Checkout, der alle drei Punkte erfüllt — der Registrierungsschritt lehnt alles andere ab:

- er liegt in einem Git-Arbeitsbaum
- er hat ein `origin`-Remote
- dieses Remote zeigt auf github.com, gitlab.com oder bitbucket.org

## Schritt 1: Einen Arbeitsbereich anlegen

1. Klicke auf den Arbeitsbereichs-Chip in der Titelleiste
2. Wähle **Arbeitsbereich hinzufügen…**
3. Gib einen Namen ein, der das Projekt bezeichnet, zum Beispiel „api-service“ oder „frontend-v2“
4. Wähle optional ein Logo
5. Klicke auf **Arbeitsbereich hinzufügen**

Control Center wechselt in den neuen Arbeitsbereich und landet in seinem Posteingang (`/workspaces/<id>/inbox`).

Dahinter veröffentlicht der Server ein Ereignis `WorkspaceCreated` und legt im Arbeitsbereich an:

- einen **CEO-Agenten**, dessen Persona Koordination und Delegation ist
- vier Spezialisten — `qa`, `architect`, `engineer` und `librarian` —, jeweils mit eigenen Anweisungen und Skills
- die eingebauten Pipeline-Vorlagen und ihre Trigger-Zeilen

Jeder Arbeitsbereich, den du anlegst, bekommt all das, nicht nur der erste.

Prüfe es: Öffne **Einstellungen → Arbeitsbereich → Agenten**. In der Liste stehen fünf Agenten, jeder mit einem hohlen Statusring.

## Schritt 2: Ein Repository registrieren

1. Geh zu **Einstellungen → Arbeitsbereich → Repositorys**
2. Klicke auf **Repository hinzufügen**
3. Navigiere zu deinem Checkout. Der Dialog geht die Ordner auf dem Rechner durch, auf dem `cc_server` läuft — nicht die deines Clients —, und bleibt in den Wurzeln, die dieser Server freigibt (standardmäßig das Home-Verzeichnis seines Benutzers). Ein Git-Checkout bekommt ein eigenes Ordnersymbol und ein Kontrollkästchen; ein gewöhnlicher Ordner bekommt keines von beiden, deshalb lassen sich nur Checkouts auswählen.
4. Hake einen oder mehrere Checkouts an und registriere den Schwung. Die Auswahl bleibt beim Navigieren erhalten, du kannst also mehrere in einem Durchgang zusammentragen, und eine falsche Auswahl lässt den Rest nie fallen.

Control Center liest das `origin`-Remote jedes Checkouts, löst Besitzer und Repo auf und legt die Repo-Zeile **in diesem Arbeitsbereich** an. Einen zweiten Schritt zum Verknüpfen gibt es nicht: Die Registrierung setzt den Geltungsbereich.

Denselben Checkout später in einem anderen Arbeitsbereich zu registrieren erzeugt eine zweite, unabhängige Repo-Zeile mit eigener ID. Über Arbeitsbereiche hinweg wird ein Checkout über seinen Dateisystempfad identifiziert, nie über die ID.

Prüfe es: Das Repo erscheint in der Liste mit seinem `owner/repo` und dem aktuellen Branch.

## Schritt 3: Einen Agenten lauffähig machen

Die fünf Agenten, die dieser Arbeitsbereich gerade angelegt hat, haben weder Adapter noch Modell. Der Dispatch lässt sie auf **Control Center (built-in)** laufen und fragt, solange kein Modell gesetzt ist, bei Anthropic dessen Standardmodell an — sie laufen also nur, wenn du ein Anthropic-Konto verbunden hast, und dann auf einem Modell, das du nicht gewählt hast, falls du eines verbunden hast. Das Onboarding beim ersten Start schreibt seine Wahl einmal auf jeden Agenten des ersten Arbeitsbereichs; ein Arbeitsbereich, den du danach anlegst, startet mit allen fünf ungesetzt. Setze jetzt einen.

1. Öffne **Einstellungen → Arbeitsbereich → Agenten**
2. Wähle `engineer` in der Liste
3. Setze auf dem Tab **Einstellungen** den **Adapter** auf `Control Center (built-in)` und wähle ein **Modell** von einem Anbieter, den du unter Einstellungen → Server → Modellanbieter verbunden hast
4. Klicke auf **Änderungen speichern**

Prüfe es: Öffne den Agenten erneut. Die beiden Felder halten deine Auswahl.

Jeder Agent trägt seinen eigenen Adapter und sein eigenes Modell. Wiederhole das also für jeden weiteren Agenten, den du nutzen willst. [Einen Agenten erstellen und konfigurieren](/de-DE/handbuch/anleitungen/agent-erstellen/) behandelt den Rest des Formulars.

## Schritt 4: Die Isolationsgrenze sehen

Lege über den Chip in der Titelleiste einen zweiten Arbeitsbereich an, genau wie in Schritt 1. Schau ihn dir dann an:

- **Einstellungen → Arbeitsbereich → Repositorys** ist leer. Das Repo, das du vor einer Minute registriert hast, ist nicht da.
- **Einstellungen → Arbeitsbereich → Agenten** enthält fünf Agenten, aber andere Zeilen — der Adapter aus Schritt 3 ist weg.
- Die Liste der Bereiche, die Tickets und das Gedächtnis sind leer.

Es ist nichts durchgesickert, denn es gibt nichts, woraus etwas sickern könnte: Die Zeilen jedes Arbeitsbereichs liegen in der eigenen Datenbankdatei dieses Arbeitsbereichs. Ein arbeitsbereichsübergreifendes Lesen ist keine Abfrage, die gefiltert wird, sondern eine Abfrage, die nirgends laufen kann. Einen Arbeitsbereich zu löschen heißt, die Verknüpfung einer Datei aufzuheben.

Wechsle mit dem Chip in der Titelleiste zurück, oder öffne **Arbeitsbereiche verwalten**, um sie nebeneinander zu sehen.

Das vollständige Modell steht in [Arbeitsbereiche und Isolation](/de-DE/handbuch/konzepte/arbeitsbereiche/).

## Rückblick

Du hast einen Arbeitsbereich angelegt, zugesehen, wie er einen CEO und vier Spezialisten anlegt, ein Repo darin registriert, einem Agenten einen Adapter und ein Modell gegeben und bestätigt, dass ein zweiter Arbeitsbereich nichts davon teilt.
