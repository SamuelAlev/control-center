Alles, was Control Center kopieren, übergeben oder übernehmen kann, und die genaue Form jedes
Artefakts. Wie du tatsächlich eine Sicherung anlegst, steht unter
[Sichern und wiederherstellen](/de-DE/handbuch/anleitungen/sichern-und-wiederherstellen/). Warum die Persistenz
so aufgeteilt ist, steht unter [Arbeitsbereiche und Isolation](/de-DE/handbuch/konzepte/arbeitsbereiche/).

## Artefakte

Es gibt drei Artefakte, die eine Datenbank kopieren, mit unterschiedlichem Geltungsbereich und unterschiedlicher Löschregel.

| Artefakt                              | Geschrieben von               | Form                                      | Umfang                                 |
| ------------------------------------- | ----------------------------- | ----------------------------------------- | -------------------------------------- |
| **Momentaufnahme der Installation**   | `server.backupNow`            | Ein **Verzeichnis** mit Zeitstempel       | Jede Datenbank der Installation        |
| **Arbeitsbereichssicherung**          | Pipeline `Workspace backup`   | Verzeichnis mit Zeitstempel und einer `.db` | Die Datenbank eines Arbeitsbereichs  |
| **Arbeitsbereichs-Export**            | `workspace.export`            | Eine einzelne `.db`-**Datei**             | Die Datenbank eines Arbeitsbereichs    |

Alle werden mit SQLite `VACUUM INTO` geschrieben. Das ist gegen eine laufende WAL-Datenbank sicher:
es nimmt eine Lesetransaktion, erzeugt eine defragmentierte und transaktional konsistente
Kopie und verlangt nie, den Server anzuhalten.

Diese Dateien und heruntergeladenen Kopien werden von Control Center **nicht im
Ruhezustand verschlüsselt**. Der Ende-zu-Ende verschlüsselte Transfer schützt die
Bytes während der Übertragung zwischen einem gekoppelten Client und seinem
`cc_server`, sowohl über direkte als auch über vermittelte Relay-Verbindungen.
Schütze lokalen Speicher und Kopien außerhalb des Rechners getrennt; der Server
und jeder autorisierte Empfänger können die Datenbankdateien lesen.

## Layout der Momentaufnahme

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Das Layout spiegelt das laufende Datenverzeichnis genau. Deshalb ist das Wiederherstellen einer
Installation ein Zurückkopieren und keine Umwandlung. Der Verzeichnisname ist der UTC-Zeitstempel,
in dem `:` und `.` durch `-` ersetzt sind. So ist er auf Windows dateisystemsicher und sortiert
als bloße Zeichenkette chronologisch.

Geplante Arbeitsbereichssicherungen liegen getrennt unter `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`. Jede hat ein `manifest.json` für genau diese eine Datei und kein `global.db`; sie sind keine Momentaufnahmen der Installation. Eine Wiederherstellung behält die Datenbank, die sie ersetzt, am selben Ort, als `<timestamp>-pre-restore`. Der Aufbewahrungsschritt der wöchentlichen Pipeline entfernt nur Sicherungen des eigenen Arbeitsbereichs, die älter sind als das konfigurierte Alter (standardmäßig 30 Tage). Manuell erstellte Momentaufnahmen der Installation fasst dieser Schritt nie an. `server.listBackups` listet nur Momentaufnahmen der Installation, auch nicht überprüfbare; `workspace.listBackups` listet die geplanten Sicherungen eines Arbeitsbereichs.

Wird ein Arbeitsbereich gelöscht, bleibt dieses Verzeichnis bestehen. Der Zeitplan des
Arbeitsbereichs endet damit, also rotiert nichts diese Sicherungen mehr, und sie bleiben, bis
der Eigentümer der Installation sie entfernt. `server.listOrphanedBackups` meldet sie.


### `manifest.json`

| Feld                         | Typ                      | Bedeutung                                                              |
| ---------------------------- | ------------------------ | ---------------------------------------------------------------------- |
| `format`                    | Ganzzahl                 | Manifest-Format. Derzeit `2`                              |
| `created_at`                 | ISO-8601 UTC             | Wann die Momentaufnahme erstellt wurde                                 |
| `global`                   | Objekt          | Der Eintrag zu `global.db`. Fehlt in einer geplanten Arbeitsbereichssicherung |
| `workspaces[]`               | Array                    | Ein Datensatz je erfasstem Arbeitsbereich                                |
| `workspaces[].workspace_id`  | Zeichenkette             | Der Arbeitsbereich, den diese Datei enthält                            |
| `skipped_workspaces[]`     | Array           | Arbeitsbereiche, die die Sicherung **nicht** erfassen konnte                         |
| `skipped_workspaces[].workspace_id` | Zeichenkette | Der Arbeitsbereich, der ausgelassen wurde                                     |
| `skipped_workspaces[].reason` | Zeichenkette | `no_file`, `damaged` oder `failed`                                    |

`global` und jeder Eintrag von `workspaces[]` beschreibt je eine kopierte Datei, gemessen an der Kopie, nachdem sie geschrieben wurde:

| Feld | Typ | Bedeutung |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`          | Zeichenkette             | Pfad relativ zur Wurzel der Momentaufnahme: `global.db` oder `<workspaceId>/workspace.db` |
| `bytes`         | Ganzzahl                 | Größe der Kopie                                                     |
| `sha256`         | Zeichenkette | SHA-256 der Kopie, in Kleinbuchstaben-Hex                                          |
| `quick_check`    | Zeichenkette | Was SQLites `quick_check` über die Kopie sagte: `ok` oder sein Befund               |
| `user_version`   | Ganzzahl     | Schemaversion der Kopie                                                     |
| `application_id` | Ganzzahl     | SQLite-`application_id` der Kopie                                            |

Ein Arbeitsbereich wird übersprungen, wenn er registriert, aber noch nie beschrieben wurde (`no_file`), wenn seine Datenbank die Integritätsprüfung nicht besteht (`damaged`; eine beschädigte Kopie wird nie angelegt), oder wenn seine Kopie oder deren Prüfung fehlgeschlagen ist (`failed`). In jedem Fall wird die Momentaufnahme trotzdem fertig, und das Manifest nennt, was fehlt. Das Manifest wird zuletzt geschrieben.

### Vollständigkeit

`server.listBackups` meldet je Momentaufnahme ein Flag `complete`. Es ist falsch, wenn das Manifest fehlt, sich nicht parsen lässt oder ein anderes Format hat, wenn eine Datei, die es nennt, fehlt oder eine andere Größe hat, oder wenn eine Kopie ihre Prüfung nicht bestanden hat. Die App zeigt eine solche Momentaufnahme als **Nicht überprüfbar** an. Momentaufnahmen, die vor Format `2` erstellt wurden, sind in diesem Zustand.

Eine nicht überprüfbare Momentaufnahme steht trotzdem in der Liste. Eine Momentaufnahme, die du nicht
siehst, ist eine, von der du glaubst, sie zu haben. Lässt sich das Manifest nicht lesen, fällt die
Auflistung auf das Layout selbst zurück und meldet die `<workspaceId>/workspace.db`-Dateien, die sie
findet. Die lassen sich weiterhin einzeln über `workspace.import` übernehmen, auch wenn die
Momentaufnahme als Ganzes eine Installation nicht wiederherstellen kann.

Eine aufgelistete Momentaufnahme oder geplante Sicherung trägt `pinned_reason: "last_good_copy"`, solange sie die neueste geprüfte Kopie eines Arbeitsbereichs enthält, dessen aktive Datenbank beschädigt ist. Der Aufbewahrungsschritt überspringt sie, bis dieser Arbeitsbereich wiederhergestellt ist.

## Was eine Sicherung nicht enthält

Beide Artefakte sind **nur Datenbanken**. Ein Arbeitsbereichsverzeichnis hält mehr als seine
Datenbank, und nichts vom Rest geht mit:

| Pfad                                | In einer Momentaufnahme? | In einem Arbeitsbereichs-Export? |
| ----------------------------------- | ------------------------ | -------------------------------- |
| `global.db`                         | Ja                       | Nein                             |
| `<workspaceId>/workspace.db`        | Ja                       | Ja (sie *ist* die Datei)         |
| `<workspaceId>/code_index.db`        | Nein                     | Nein                   |
| `<workspaceId>/blobs/`              | Nein                     | Nein                             |
| `<workspaceId>/skills/`             | Nein                     | Nein                             |
| `<workspaceId>/agents/`             | Nein                     | Nein                             |
| `<workspaceId>/chat_credentials/`   | Nein                     | Nein                             |
| `<workspaceId>/spaces/<spaceId>/`   | Nein                     | Nein                             |
| `<workspaceId>/pr_clones/`          | Nein                     | Nein                             |
| `secrets.json`                      | Nein                     | Nein                             |
| `models/`                           | Nein                     | Nein                             |
| `meetings/<meetingId>/`             | Nein                     | Nein                             |
| `rigs/`                             | Nein                     | Nein                             |
| `_agent_hooks/`                     | Nein                     | Nein                             |

Einiges davon ist entbehrlich. `spaces/` hält Copy-on-Write-Worktrees, die aus den Repos neu bereitgestellt werden, `pr_clones/` ist ein Cache, `code_index.db` wird neu aufgebaut, `models/` wird neu heruntergeladen, `rigs/` ist Maschinenzustand. Anderes nicht: `blobs/` hält eingefügte Bilder, auf die Zeilen in der Datenbank zeigen, `skills/` und `agents/` halten die Dateien, mit denen ein Agent läuft, und `secrets.json` hält jeden Kopplungsschlüssel, alle Anbieter-Zugangsdaten und alle SSO-Einstellungen der Installation. Den Rest deckt [Sichern und wiederherstellen](/de-DE/handbuch/anleitungen/sichern-und-wiederherstellen/#sicherungen-vom-rechner-kopieren) ab.
:::note[Geheimnisse bleiben aus den Datenbanken heraus]
`workspace.db` ist der ganze Arbeitsbereich: Unterhaltungen, Laufprotokolle, Repo-Verknüpfungen, Umgebungsdefinitionen und Mitglieder. Webhook-Tokens der Pipelines und Webhook-Geheimnisse der Ticket-Synchronisierung stehen in `secrets.json`: Die Datenbank enthält je einen Verweis darauf, und der Routen-Index enthält einen mit Schlüssel gebildeten Hash jedes Tokens. Ein Arbeitsbereich, der auf einer anderen Installation wiederhergestellt wird, empfängt daher keine Webhooks, bis seine Trigger dort erneut gespeichert werden. Anbieter-Anmeldungen, Gerätschlüssel und Benutzergeheimnisse stehen in `global.db` und `secrets.json`.
:::

:::note[Chat-Tokens bleiben absichtlich zurück]
`chat_credentials/` liegt neben der Datenbank und nicht darin. Deshalb trägt ein Arbeitsbereich,
den du jemand anderem gibst, keine lebenden Bot-Tokens. Siehe die
[Referenz zur Chat-Brücke](/de-DE/handbuch/referenz/chat-bruecke/).
:::

## Operationen

Die RPCs für die Sicherung der Installation sowie Export und Import eines Arbeitsbereichs gibt es nur für `fullClient`: ein gekoppeltes
Telefon kann sie nicht auslösen. Auf einem Server ohne verdrahteten Backup-Port, etwa dem Demo-Server,
fehlen sie ganz. Sie werden nicht abgelehnt, sie sind strukturell nicht da.

| Operation             | Art       | Geltungsbereich | Mindestrolle                    | Argumente     | Rückgabe                              |
| --------------------- | --------- | --------------- | ------------------------------- | ------------- | ------------------------------------- |
| `server.backupNow`    | Schreiben | Installation    | **Eigentümer** der Installation | keine         | `{ok, path}`                          |
| `server.listBackups`  | Lesen     | Installation    | **Eigentümer** der Installation | keine         | `{backups: [...]}`                    |
| `server.deleteBackup` | Schreiben | Installation    | **Eigentümer** der Installation | `name`        | `{ok}`                                |
| `server.listOrphanedBackups` | Lesen | Installation | **Eigentümer** der Installation | keine | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | Schreiben | Installation | **Eigentümer** der Installation | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | Lesen | Arbeitsbereich | `admin` | keine | `{backups: [...]}` |
| `workspace.deleteBackup` | Schreiben | Arbeitsbereich | `owner` | `name` | `{ok}` |
| `workspace.export`    | Lesen     | Arbeitsbereich  | `admin`                         | keine         | `{ok, path}`                          |
| `workspace.import`    | Schreiben | Arbeitsbereich  | `owner` und Serverinhaber       | `source_path` | `{ok, workspace_id}`                  |
| `workspace.importHolds.list` | Lesen | Arbeitsbereich | `owner` und Serverinhaber | keine | `{holds: [...]}` |
| `workspace.importHolds.resolve` | Schreiben | Arbeitsbereich | `owner` und Serverinhaber | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`    | Schreiben | Installation*   | `owner`                         | `id`          | Registry-Zeile als gelöscht markiert  |

* `workspace.delete` hat keinen Geltungsbereich, weil die Zeile, die es markiert, in der globalen
Registry lebt. Der Handler prüft die Mitgliedschaft des Aufrufers im genannten Arbeitsbereich
und verlangt `owner`.

`path` in jeder Antwort ist ein Pfad auf dem **Server-Host**.

`server.listOrphanedBackups` liefert einen Eintrag je Arbeitsbereich, der nicht mehr aktiv ist:
`workspace_id`, `workspace_name`, solange die Registry ihn noch kennt, und `backups`.
Ein gelöschter Arbeitsbereich kann keine Rollenprüfung mehr bestehen, also gehören seine
Sicherungen dem Eigentümer der Installation. `server.deleteOrphanedBackup` lehnt einen aktiven
Arbeitsbereich ab, dessen Sicherungen hinter `workspace.deleteBackup` und den Rollen dieses
Arbeitsbereichs bleiben. Beide Löschoperationen akzeptieren nur einen aufgelisteten
Zeitstempel-Verzeichnisnamen, keinen Pfad.

`workspace.importHolds.list` liefert, was ein Import zurückgehalten hat. Jede zurückgehaltene Berechtigung hat eine `id`, einen `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` oder `invite`), die `payload`, die sie wieder einsetzen würde, sowie `imported_at` und `source_install_id`. `workspace.importHolds.resolve` mit `accept: true` gewährt sie erneut, mit `false` verwirft es sie. `applied` ist false, wenn die Person oder das Objekt, für die die Freigabe galt, nicht mehr im Arbeitsbereich ist.

:::note[Eine Momentaufnahme der ganzen Installation ist auf beiden Bahnen dem Eigentümer vorbehalten]
`server.backupNow`, `server.listBackups` und `server.deleteBackup` verlangen den
**Eigentümer** der Installation (`ServerAuthority.serverOwner`), dieselbe Schranke wie
`GET /backup/snapshot`. Eine Momentaufnahme erfasst die Datenbank jedes Arbeitsbereichs. Admin
eines einzelnen Arbeitsbereichs zu sein reicht also nicht, um die anderen zu verwalten. Das Löschen
nimmt nur den gelisteten Verzeichnisnamen mit Zeitstempel an, keinen beliebigen Pfad auf dem
Server, und entfernt die ganze Momentaufnahme, auch nicht überprüfbare.
Export und geplante Sicherungs-Downloads je Arbeitsbereich bleiben beim Admin des Arbeitsbereichs.
:::

:::note[Die Wiederherstellung ist Sache des Serverinhabers]
`workspace.import` und `POST /backup/restore` lassen den Server eine Datenbankdatei übernehmen, deren Zeilen er danach als eigene behandelt: Repo-Verknüpfungen und wer sie angelegt hat, Umgebungsdefinitionen, die auf dem Host laufen, Worktree- und Log-Pfade. Deshalb brauchen beide den Serverinhaber (`ServerAuthority.serverOwner`), der außerdem Eigentümer des Arbeitsbereichs sein muss. Alle anderen und jeder Aufrufer auf einem Host ohne eingetragenen Eigentümer werden mit `server_owner_required` abgewiesen. Kein Trigger, keine Ansicht, keine Spalte und keine Einschränkung, die die Datei mitbringt, wird übernommen.
:::

### Antwort von `server.listBackups`

Neueste zuerst, sortiert nach Verzeichnisnamen. Der Name ist der Zeitstempel, die Reihenfolge hält also auch
bei einer Momentaufnahme, deren Manifest sich nicht lesen ließ.

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` fehlt, wenn sich das Manifest nicht lesen ließ. `bytes` auf der obersten Ebene ist
die echte Größe des ganzen Verzeichnisses auf der Platte, nicht die eigene Summe des Manifests. Wer
Momentaufnahmen ausdünnt, fragt, was das Verzeichnis kostet, nicht was die Sicherung schreiben wollte.

Jedes `workspaces[].path` ist genau das, was `workspace.import` als `source_path` nimmt. Das
ist Absicht: „diesen Arbeitsbereich aus dieser Momentaufnahme wiederherstellen“ *ist* die Import-Operation, die beiden
können also nicht auseinanderlaufen in der Behandlung derselben Datei.

### Prüfung von `workspace.import`

Bevor etwas ersetzt wird, wird die Kandidatendatei in eine Zwischendatei neben dem Ziel kopiert und dort geprüft. Eine Ablehnung fasst nichts an und trägt ihre Art als `data.kind`.

| Bedingung                                              | Ergebnis                                                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| Die Datei existiert nicht | Abgelehnt, `import.missing_source` |
| Keine lesbare SQLite-Datenbank, oder sie besteht `quick_check` nicht | Abgelehnt, `import.damaged` |
| Sie stammt aus einer Momentaufnahme, und ihre SHA-256 weicht von der des Manifests ab | Abgelehnt, `import.checksum_mismatch` |
| Eine neuere Serverversion hat sie geschrieben | Abgelehnt, `import.newer_schema` |
| Eine andere `application_id`, oder kein `workspace_meta` | Abgelehnt, `import.foreign_file` |
| Sie lässt sich nicht auf das Schema dieses Servers bringen | Abgelehnt, `import.schema_mismatch` |
| Ihre Webhooks oder Einladungen leiten bereits zu einem anderen Arbeitsbereich | Abgelehnt, `import.route_conflict` |
| Aufgezeichnete Arbeitsbereichs-ID ≠ das Ziel           | **Erlaubt**. Seine Zeilen erhalten die ID des Ziels. So wird ein Arbeitsbereich dupliziert oder unter einer neuen ID wiederhergestellt |
| Aufgezeichnete Installations-ID ≠ diese Installation   | **Erlaubt**. Die Benutzer-IDs gehören zu jener Installation und lösen sich hier nicht auf |

Nach der Annahme wird die Zwischendatei auf das Schema dieses Servers gebracht und muss ihm danach genau entsprechen. Berechtigungen, die eine Datei sich nicht selbst geben darf, werden ihr entnommen: Freigaben, eine Umgebungsdefinition auf dem Host auszuführen, werden gelöscht, und Aktionsregeln, die erlauben oder nachfragen, Sandbox-Ausführungsberechtigungen, Repo-Berechtigungen über Lesen hinaus, Rollen über Mitglied sowie Einladungen zu diesen Rollen werden zu Zurückhaltungen, die der Serverinhaber prüfen soll. Wer importiert, behält oder erhält die Eigentümerrolle. Die Datenbank, die ersetzt wird, bleibt als geplante Sicherung mit dem Namen `<timestamp>-pre-restore` erhalten; die Zwischendatei wird bei geschlossenen Verbindungen des Arbeitsbereichs an ihren Platz umbenannt, `code_index.db` wird gelöscht, damit sie neu aufgebaut wird, und die FTS-Indizes werden neu aufgebaut.

## Transfer-Routen

Die Operationen oben zum Exportieren/Importieren und zum Auflisten von
Momentaufnahmen sprechen in serverseitigen Pfaden, und das ist nur dann eine
vollständige Antwort, wenn der Server dein eigener Rechner ist. Diese
HTTP-förmigen Routen tragen Sicherungsbytes **innerhalb desselben
authentifizierten, Ende-zu-Ende verschlüsselten Ressourcen-Tunnels** wie andere
sensible Ressourcen, egal ob die RPC-Verbindung direkt oder vermittelt ist. Sie
sind keine öffentlichen HTTP-Dateitransfer-Endpunkte: Eine Anfrage an einen
davon am öffentlichen Listener liefert `426 Upgrade Required`, auch von
Loopback. Im verschlüsselten Tunnel muss das über Noise authentifizierte Gerät
zu `d` passen; der Handler prüft zusätzlich die Signatur des Geräts über seine
Zielzeichenkette mit seinem Kopplungs-PSK und die Rolle unten.

| Route                   | Methode | Query           | Signiertes Ziel                  | Erfordert                            |
| ----------------------- | ------- | --------------- | -------------------------------- | ------------------------------------ |
| `/backup/workspace`     | GET     | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **Admin** des Arbeitsbereichs        |
| `/backup/snapshot`      | GET     | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **Eigentümer** der Installation      |
| `/backup/stored`        | GET     | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **Admin** des Arbeitsbereichs; **Eigentümer** der Installation, sobald der Arbeitsbereich gelöscht ist |
| `/backup/restore`       | POST    | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **Eigentümer** der Installation, der außerdem **Eigentümer** des Arbeitsbereichs ist (sonst `403` mit `server_owner_required`) |

`w` ist eine Arbeitsbereichs-ID, `n` der Verzeichnisname einer Momentaufnahme oder geplanten Sicherung, `d` die Geräte-ID des Aufrufers, `s` die
Signatur. Bei `/backup/snapshot` wird `n` gegen die Sicherungsliste aufgelöst und nicht an die Wurzel der Sicherungen
gehängt, die Route lässt sich also nicht auf ein Verzeichnis richten, das die Liste nicht gezeigt hätte. Bei `/backup/stored`
muss es ein Zeitstempelname sein, und die Datei muss eine echte Datei im eigenen Sicherungsverzeichnis dieses Arbeitsbereichs sein.

| Status | Ursache                                                                              |
| ------ | ------------------------------------------------------------------------------------ |
| `400`  | Ein erforderlicher Query-Parameter fehlt, ein Sicherungsname ist ungültig, der Upload-Body ist leer, oder die hochgeladene Datei wurde abgelehnt (der Body ist `{error, kind}` mit einer `import.*`-Art) |
| `403`  | Unbekanntes oder widerrufenes Gerät, ungültige Signatur, oder dem Aufrufer fehlt die Rolle |
| `404`  | Kein Backup-Port auf diesem Host, oder die genannte Momentaufnahme, Sicherung oder Arbeitsbereichsdatei existiert nicht |
| `405`  | `/backup/restore` mit etwas anderem als `POST` aufgerufen                            |
| `413`  | Der Upload-Body überschreitet 8 GiB, nach deklariertem content-length oder nach den Bytes, die tatsächlich gelesen wurden |
| `426`  | Jede direkte Anfrage an einen Transfer-Pfad am öffentlichen HTTP-Listener; nutze den verschlüsselten Ressourcen-Tunnel eines gekoppelten Clients |
| `500`  | Export oder Archiv ist serverseitig fehlgeschlagen                                   |

Alle drei Downloads antworten mit `Cache-Control: no-store` und `Accept-Ranges: none`.
`/backup/workspace` und `/backup/snapshot` erzeugen je Anfrage eine **frische** Kopie und löschen sie, sobald sie gestreamt ist. Eine gecachte oder fortgesetzte Antwort
würde Bytes aus zwei verschiedenen Exporten zu einer Datei zusammenfügen, die gültig aussieht und es nicht ist.

`/backup/stored` ist die Ausnahme: Es streamt eine geplante Sicherung als `<workspaceId>-<name>.db`
und lässt die Datei an ihrem Platz, weil diese Datei die Sicherung ist.

`/backup/snapshot` liefert `<name>.zip`. Die Einträge liegen relativ zur Wurzel der Momentaufnahme, das
Entpacken stellt also `manifest.json` + `global.db` + `<workspaceId>/workspace.db` wieder her.
Die Einträge werden in sortierter Reihenfolge geschrieben, zwei Archive derselben Momentaufnahme sind also dasselbe
Archiv.

`/backup/restore` streamt den Body direkt in eine Staging-Datei, statt ihn zu puffern,
begrenzt ihn vor dem Lesen und währenddessen und löscht die bereitgestellte Datei auf **jedem** Weg nach draußen,
auch bei einer Ablehnung.

::::caution[Direkt und Relay nutzen denselben verschlüsselten Transfer]
Das Relay trägt Ressourcenanfragen, gestreamte Antworten und Upload-Bytes als
Chiffretext; den Inhalt der Sicherung kann es nicht lesen. Ein serverseitiger
Pfad bleibt ein Pfad auf dem Server-Host, keine Datei auf dem Relay. Der Zugriff
erfordert weiterhin das gekoppelte Gerät, die Zielsignatur und die
anwendbare Arbeitsbereichs- oder Installationsrolle. Keiner der beiden
Transportwege verschlüsselt die entstehenden Sicherungsdateien im Ruhezustand.
::::

## Pfade und Grenzen

| Eintrag                            | Wert                                                         |
| ---------------------------------- | ------------------------------------------------------------ |
| Momentaufnahmen                    | `<dataDir>/backups/<timestamp>/`                             |
| Geplante Arbeitsbereichssicherungen | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Arbeitsbereichs-Exporte            | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Datenbank, die eine Wiederherstellung ersetzt hat | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Datenbanken vor einem Update, das ihr Format änderte | `<dataDir>/pre_upgrade/` und `<dataDir>/<workspaceId>/pre_upgrade/`, jeweils die neuesten zwei |
| Transfer-Bereitstellung            | `<dataDir>/backups/transfer/` — eine Werkbank, die die Route wegräumt, die hineinschreibt |
| Archivname der Momentaufnahme      | `<snapshot directory name>.zip`                              |
| Upload-Obergrenze                  | 8 GiB je verschlüsseltem `/backup/restore`-Upload            |
| Aufbewahrung                       | Momentaufnahmen der Installation: manuelles Löschen. Arbeitsbereichssicherungen: wöchentliche Pipeline, Standard 30 Tage, oder manuelles Löschen. Sicherungen eines gelöschten Arbeitsbereichs: nur manuelles Löschen |

Die Verzeichnisse `exports/`, `transfer/` und `workspace-backups/` sind keine
Momentaufnahmen der Installation und fehlen in `server.listBackups`. Nur das letzte
Verzeichnis hat eine geplante Aufbewahrung, und nur solange sein Arbeitsbereich existiert. Eine Momentaufnahme der Installation zu löschen braucht die
ausdrückliche Handlung des Eigentümers der Installation.
