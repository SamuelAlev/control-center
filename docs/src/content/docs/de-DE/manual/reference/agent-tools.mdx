Das sind die **servergebundenen** Tools, die die eingebaute Agentenlaufzeit direkt registriert — Sprachserver, strukturelle Suche, Debugger, Kernel, Code-Modus-Skripte, Fragen und Worker-Steuerung — im Unterschied zu den [MCP-Tools](/de-DE/handbuch/referenz/mcp-tools/), die sie einbindet, und den generischen Datei-, Such- und Shell-Tools aus der Laufzeit des Harness. Sie stehen nicht in der MCP-Registrierung: Ein externer MCP-Client sieht sie nicht, weil jedes an eine laufende serverseitige Ressource gebunden ist, die zu einem Lauf gehört — einen Sprachserver-Prozess, einen Debug-Adapter, einen Interpreter.

Jedes Tool hier wird nur registriert, wenn die Ressource dahinter für den Lauf angeschlossen ist — ein Supervisor für Sprachserver oder Debugger, ein tree-sitter-Parser, eine Kernel-Fabrik, ein Frage-Port, ein Vibe-Roster. Ob ein Sprachserver oder Debug-Adapter für *diesen Checkout* da ist, ist eine eigene, spätere Prüfung (`status` / `adapters`): Diese Tools bleiben an der Oberfläche, damit der Agent fragen kann, warum nichts brauchbar ist, statt zu raten.

## Freigabestufen

Jedes Tool deklariert eine Stufe, und die Stufe entscheidet, **welche Oberflächen es sehen** — nicht bloß, ob es eine Freigabe verlangt. Planmodus und schreibgeschützte Subagenten sind auf `read` begrenzt, deshalb fehlt ein Tool der Stufe `write` oder `exec` in ihrem Schema vollständig.

| Stufe   | Bedeutung                    | Tools hier                                       |
| ------- | ---------------------------- | ------------------------------------------------ |
| `read`  | Keine Seiteneffekte          | `lsp`, `ast_grep`, `ask_user`, `repl`, die fünf `vibe_*` |
| `write` | Ändert Dateien               | `lsp_rename`, `ast_edit`, `resolve`              |
| `exec`  | Startet oder steuert einen Prozess | `debug`, `eval`                            |

## Direkt, nur aus Skripten oder beim ersten Gebrauch geladen

Wenn der Server Skripte ausführen kann, ruft ein Lauf einige Tools direkt auf und erreicht den Rest aus einem [`repl`](#repl--ein-skript-ausführen-das-deine-tools-aufruft)-Skript; die ganze Regel steht unter [Code-Modus](/de-DE/handbuch/konzepte/code-modus/#welche-tools-der-agent-direkt-aufruft). Für die Tools auf dieser Seite:

| Tool | Mit `repl` | Ohne `repl` |
| ---- | ----------- | -------------- |
| `repl` | Direkt | Nicht vorhanden |
| `ask_user` | Direkt | Direkt |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Nur aus einem Skript | Beim ersten Gebrauch geladen |
| `eval` | Beim ersten Gebrauch geladen (ein Skript kann es nicht aufrufen) | Beim ersten Gebrauch geladen |
| `vibe_*` | Direkt im Vibe-Modus, nie aus einem Skript | Direkt im Vibe-Modus |

Ein als „Nur aus einem Skript“ markiertes Tool wird beim ersten Gebrauch geladen, sobald der Server die Skripte des Laufs nicht mehr ausführen kann ([Wenn Skripte nicht laufen können](/de-DE/handbuch/konzepte/code-modus/#wenn-skripte-nicht-laufen-können)).

## `lsp` — Sprachserver-Abfragen

Registriert, wenn der Lauf einen Sprachserver-Supervisor und ein Arbeitsverzeichnis hat. Ob ein Server wirklich antworten kann, wird beim Aufruf erkannt, als **Schnittmenge**: Ein Wurzelmarker muss existieren, *und* die Binärdatei des Servers muss sich auflösen lassen. Liegt nur eines von beiden vor, startet kein Server — `status` sagt das — statt einer stillen Vermutung.

Server kommen nur aus der eingebauten Tabelle; eine `lsp.json` im Repository wird nicht gelesen. In einem Lauf in der Sandbox bekommt jeder Lauf seine eigene Sitzung des Sprachservers, daher starten die Server mit jedem Lauf neu. Projektlokale Binärdateien (`node_modules/.bin`) werden nur benutzt, wenn der Lauf in der Sandbox läuft, und die Projektwurzel löst nie über das Arbeitsverzeichnis des Laufs hinaus auf.

Positionen werden über `line` plus eine Teilzeichenkette `symbol` adressiert, nie über die Spalte. Fragt man ein Modell nach einer Spalte, rät es, und ein falscher Tipp trifft ein anderes Symbol in derselben Zeile — eine Antwort, die richtig aussieht und von etwas anderem handelt. `symbol` bei einer Navigationsaktion wegzulassen ist ein Fehler, keine Vermutung auf die erste Spalte.

| Aktion            | Argumente                        | Liefert                                    |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (oder `"*"`)              | Fehler und Warnungen; `"*"` führt stattdessen die Projektprüfung aus |
| `definition`      | `file`, `line`, `symbol`         | Wo das Symbol deklariert ist               |
| `type_definition` | `file`, `line`, `symbol`         | Wo sein Typ deklariert ist                 |
| `implementation`  | `file`, `line`, `symbol`         | Konkrete Implementierungen                 |
| `references`      | `file`, `line`, `symbol`         | Jede Verwendung, höchstens 50              |
| `hover`           | `file`, `line`, `symbol`         | Signatur und Doc-Kommentar                 |
| `symbols`         | `query` oder `file`              | Suche im Arbeitsbereich mit `query` (höchstens 100); Dokumentsymbole mit `file` (höchstens 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Schnellkorrekturen, die der Server anbietet |
| `status`          | —                                | Welche Server laufen, und für welche Wurzeln |
| `reload`          | —                                | Startet den Server für diese Wurzel neu   |

### Diagnosen beim Schreiben

Der Gewinn ist nicht das Tool. `write`, `edit` und `apply_patch` sind **umhüllt**: Nach dem Schreiben wird die Datei über den Sprachserver synchronisiert und gespeichert, und nur **neu hinzugekommene** Diagnosen fließen ins Tool-Ergebnis ein. Der Agent erfährt in dem Moment, in dem er den Build bricht, dass er ihn gebrochen hat, ohne nachfragen zu müssen.

Schon gemeldete Diagnosen unterdrückt ein Protokoll je Lauf, geschlüsselt nach Schweregrad, Code und Meldung — die Position bleibt absichtlich außen vor, damit eine Diagnose, die bloß vier Zeilen nach unten gerutscht ist, nicht noch einmal als neu gemeldet wird.

## `lsp_rename` — projektweites Umbenennen

Ein eigenes Tool der Stufe `write`, aus genau einem Grund: Die Stufe entscheidet die Sichtbarkeit. Nähme man das Umbenennen in `lsp` auf, bekäme ein schreibgeschützter Explorer die Möglichkeit, das Repo umzuschreiben, oder jedes `hover` stünde hinter einer Freigabeaufforderung.

| Argument   | Bedeutung                                 |
| ---------- | ----------------------------------------- |
| `file`     | Wo das Symbol steht                       |
| `line`     | 1-indizierte Zeile                        |
| `symbol`   | Teilzeichenkette, die es in dieser Zeile kennzeichnet |
| `new_name` | Wie es heißen soll                        |

## `ast_grep` — strukturelle Suche

Findet Code nach der **Form** statt nach dem Text. `$NAME` trifft jeden Knoten, `$$$NAME` eine Folge von Geschwistern, und `$_` ist ein Platzhalter, der nichts bindet.

Die Eigenschaft, die daraus einen Matcher macht und nicht einen Regex mit Extra-Schritten: Eine Metavariable, die in einem Muster wiederholt wird, muss denselben Text erfassen.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

trifft eine Absicherung, die `dispose` auf genau dem aufruft, was sie geprüft hat, und **nicht** eine, die `dispose` auf etwas anderem aufruft.

| Argument      | Bedeutung                                                   |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | Ein Codefragment mit Metavariablen                          |
| `path`        | Datei oder Verzeichnis für die Suche; Standard ist der ganze Arbeitsbereich |
| `language`    | Eine mitgelieferte Grammatik-Id (`dart`, `python`, `rust`, `c`, …). Wird erschlossen, wenn `path` eine Datei nennt |
| `max_results` | Standard 50                                                 |

:::note[Das Muster wird mit derselben Grammatik geparst wie die Datei]
Deshalb trifft `dispose(x)` den Aufruf, egal wie er gesetzt, umbrochen oder kommentiert ist — und dieselben Zeichen nie in einem Zeichenkettenliteral oder einem Kommentar.
:::

:::caution[Ein Fragment wird in einem Gerüst geparst, nicht nackt]
`dispose(x)` auf Darts oberster Ebene geparst ist eine gültige *Funktionssignatur*. Der Muster-Compiler probiert eine Leiter von Kontexten (Anweisung, Ausdruck, Klassenmember, Deklaration) und nimmt den ersten, der das Fragment annimmt. Ein Muster, das kein Kontext annimmt, wird als nicht parsebar gemeldet, statt gesucht und stillschweigend nicht gefunden zu werden.
:::

## `ast_edit` — strukturelle Umschreibung, im Staging

Dieselbe Suche, plus eine `rewrite`-Vorlage, in die die Metavariablen wieder eingesetzt werden. **Es wird nichts geschrieben.** Die Änderung geht ins Staging, und das Ergebnis nennt eine `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Argument   | Bedeutung                                       |
| ---------- | ----------------------------------------------- |
| `pattern`  | Was getroffen werden soll                       |
| `rewrite`  | Was dort stehen soll, mit eingesetztem `$NAME` |
| `path`     | Umfang; Standard ist der ganze Arbeitsbereich  |
| `language` | Sprach-Id                                       |

## `resolve` — eine Änderung im Staging übernehmen oder verwerfen

| Argument  | Bedeutung                      |
| --------- | ------------------------------ |
| `edit_id` | Aus dem Ergebnis `(proposed)`  |
| `action`  | `accept` oder `discard`        |

Jede Datei wird mit dem Inhalt verglichen, der beim Staging festgehalten wurde, und **jede** Abweichung lehnt die ganze Änderung ab. Eine nur teilweise angewendete strukturelle Umschreibung hinterlässt einen Baum, der weder unter der alten noch unter der neuen Form kompiliert.

## `debug` — einen Debugger steuern

Registriert, wenn der Lauf einen Supervisor für die Debug-Sitzung, ein Arbeitsverzeichnis und eine Unterhaltungs-Id hat. Ob ein Adapter wirklich starten kann, wird beim Aufruf erkannt, nach derselben Schnittmengenregel wie beim Sprachserver (Wurzelmarker *und* Binärdatei). Stufe `exec`; nicht parallel-sicher (eine Sitzung ist Zustand über die Aufrufe hinweg, deshalb läse ein `continue`, das `stack` überholt, einen Frame, der sich schon bewegt hat).

Eine Sitzung pro Unterhaltung, mit einer harten TTL (30 Minuten). Ein zweites `launch` wird abgelehnt, statt das erste stillschweigend zu ersetzen. In einem Lauf in der Sandbox behält die Sitzung ihre Sandbox über alle Züge hinweg, bis sie endet, und damit höchstens diese 30 Minuten lang.

| Operation     | Argumente                     | Hinweise                                       |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Welche Adapter hier brauchbar sind, und warum nicht |
| `status`      | —                             | Ob eine Sitzung läuft, und wo sie angehalten hat |
| `breakpoints` | `file`, `lines[]`             | Leeres `lines` leert die Datei. Darf **vor** dem Start gesetzt werden |
| `launch`      | `program`, `args[]`           | Startet das Programm, angehalten an deinen Haltepunkten |
| `attach`      | `port`                        | Verbindet sich mit einem schon laufenden Debuggee auf einem der eigenen weitergeleiteten Ports des Laufs; jeder andere Port wird abgelehnt, bevor etwas startet |
| `continue`    | `thread_id?`                  | Läuft bis zum nächsten Halt                    |
| `pause`       | `thread_id?`                  | Hält es an, wo es gerade steht                 |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Geht einen Schritt                      |
| `threads`     | —                             | Thread-Ids und Namen                           |
| `stack`       | `thread_id?`                  | Frames, höchstens 30                           |
| `scopes`      | `frame_id`                    | Scopes eines Frames, jeder mit einer `reference` |
| `variables`   | `reference`                   | Kinder, höchstens 50, Werte höchstens 400 Zeichen |
| `evaluate`    | `expression`, `frame_id?`     | Ausgewertet im eigenen Scope des Frames        |
| `output`      | —                             | stdout/stderr des Debuggee, begrenzt           |
| `terminate`   | —                             | Beendet die Sitzung und killt den Adapter      |

### Adapter

| Id        | Befehl                     | Wurzelmarker                                    |
| --------- | -------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`       | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                 | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                  | `go.mod`                                        |

`debugpy` bevorzugt ein projektlokales `.venv/bin` oder `venv/bin` gegenüber `$PATH`, wenn der Lauf in der Sandbox läuft: Ein Python aus `$PATH` ist eine andere Umgebung, und ein Attach aus der falschen scheitert so, dass es wie kaputter Code wirkt. Ohne Sandbox benutzt er nur `$PATH`, sodass ein Repository nicht bestimmen kann, welcher Interpreter auf dem Host läuft.

## `repl` — ein Skript ausführen, das deine Tools aufruft

Auf jedem Lauf vorhanden, wenn der Server Skripte ausführen kann ([Wann ein Lauf `repl` hat](/de-DE/handbuch/konzepte/code-modus/#wann-ein-lauf-repl-hat)). Das Skript ist einfaches JavaScript, der Rumpf einer async-Funktion, und läuft in einem frischen, abgeschirmten Interpreter in einem eigenen Prozess: ohne Zugriff auf Dateisystem, Netzwerk, Prozesse oder Module. `repl` selbst gehört zur Stufe `read` und sichert sich selbst ab, weil jeder Tool-Aufruf, den das Skript macht, für sich geprüft wird. Auch am MCP-Endpunkt, für Agentenläufe auf einem Server, der Skripte ausführen kann, verfügbar.

| Argument | Bedeutung |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | Das Skript, höchstens 256 KiB |
| `description` | Pflichtangabe. Eine kurze Bezeichnung für die Zeile in der Unterhaltung |
| `timeout_ms` | Optional. Ein kürzeres Zeitlimit als das des Arbeitsbereichs, nie ein längeres |
| `max_output_tokens` | Optional. Ein kleineres Ausgabebudget als das des Arbeitsbereichs, nie ein größeres |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

Die Beschreibung von `repl` sagt dem Agenten: „Ein Tool, das keines deiner direkten Tools ist, hat in dieser Anfrage keine Definition. Bevor du es zum ersten Mal aufrufst, schlage es mit `describeTool(name)` oder `searchTools(query)` nach, es sei denn, seine genaue Aufrufform wurde dir in dieser Unterhaltung bereits gezeigt.“

`describeTool(name)` liefert die Beschreibung eines Tools, seine Deklaration, seine Eingabe- und Ausgabeschemas und seine Ergebnisnotiz, falls es eine gibt: was ein Skript von einem abgeschlossenen Aufruf erhält, in den eigenen Worten des Tools. Die Beschreibung von `repl` listet die Notizen der direkten Tools auf, die ein Skript aufrufen darf. Ein Ergebnis, das JSON-Text ist, kommt geparst an, außer es enthält mehr als 131.072 Werte: Dann kommt es als Text an, und das Skript parst es mit `JSON.parse`. Der Text eines Ergebnisses von einem Tool eines externen MCP-Servers wird nach 262.144 Zeichen abgeschnitten, und abgeschnittener Text lässt sich nicht mehr parsen.

- `tools.<name>(args)` ruft ein Tool über denselben Filter, dieselben Schutzregeln und dieselbe Genehmigung wie ein direkter Aufruf auf und wird mit einem Fehler abgelehnt, wenn der Aufruf abgelehnt wird oder fehlschlägt. Lesende Aufrufe können gleichzeitig laufen; Aufrufe, die etwas ändern, laufen nacheinander in der Reihenfolge, in der das Skript sie gemacht hat. Während einer seiner Aufrufe auf eine Person wartet, startet das Skript keinen weiteren Aufruf.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` und `describeNamespace(name)` finden Tools, auch die verbundener MCP-Server. Ein Tool außerhalb der direkten Menge, das ein Skript aufrufen darf, ist nur aus einem Skript aufrufbar; ein direkter Aufruf liefert den Hinweis, wie man es aus `repl` aufruft. Sobald der Server die Skripte des Laufs nicht mehr ausführen kann, wird ein solches Tool stattdessen beim ersten Gebrauch geladen.
- Abfragen sind begrenzt: eine Anfrage von höchstens 1.024 Zeichen, ein Name oder Namensraum von höchstens 256 Zeichen, `limit` von 0 bis 50 und pro Skript höchstens 200 Abfragen, die insgesamt 2 Sekunden der Serverzeit beanspruchen; zugleich teilen sich alle Skripte eines Arbeitsbereichs 2 Sekunden Abfragezeit, die mit einer Viertelsekunde pro Sekunde zurückgegeben wird. Ist eines der beiden Limits aufgebraucht, werden weitere Abfragen abgewiesen. In einem sehr großen Katalog teilen sich die Beschreibungen in `ALL_TOOLS` etwa eine Million Zeichen gleichmäßig, und eine gekürzte endet in `…`; `describeTool` liefert immer die vollständige Beschreibung. Ein Typ, der zu groß zum Anzeigen ist, lautet `unknown /* too large to show */`, und ein unbekannter Name wird mit den nächstliegenden Namen beantwortet.
- Tools sind in Namensräumen gruppiert: `builtin` (die eigenen Tools des Harness), `control-center` (die Tools von Control Center) und einer pro verbundenem MCP-Server, benannt nach dem Server. Ein Server, der `builtin`, `control-center` oder `script` heißt oder dessen Name mit `external-` beginnt, in beliebiger Groß- und Kleinschreibung und mit oder ohne Leerzeichen drumherum, wird als `external-` gefolgt von seinem Namen aufgeführt, und kein Tool liegt jemals in `script`.
- Nur was das Skript zurückgibt oder an `text()`, `image()` oder `console.*` übergibt, kommt zurück. Ausgabe über dem Budget behält Anfang und Ende, und `read_output` liest den Rest.
- `store(key, value)` / `load(key)` behalten JSON-Werte für spätere Skripte derselben Unterhaltung und desselben Agenten; gespeichert werden sie erst, wenn das Skript abgeschlossen ist. Die Skripte eines Subagenten haben keinen Speicher.
- `await tools.ask_user(...)` stellt eine Frage; ihre Antwort wird außerdem dem Ergebnis hinzugefügt. `sleep(ms)`, `setTimeout`, `limits()` sowie `models.embed` / `rank` / `classify` (Einbettungen auf dem Gerät) sind ebenfalls verfügbar.
- `describeTool(name)` und `searchTools(query)` antworten auch für die eigenen Funktionen des Skripts, die keine Tools sind: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` und `models.*`, unter dem Namensraum `script`.
- Aus einem Skript nicht aufrufbar: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` und die `vibe_*`-Verben.
- Ein Skript liest die Vergangenheit seines eigenen Laufs: `history({start, role, tool, limit})` blättert im Transkript der Unterhaltung (höchstens 50 Zeilen pro Aufruf; übergib das `next_start` der vorherigen Seite als `start`), `outputs()` listet die Tool-Ausgaben auf, die für diese Unterhaltung und diesen Agenten gespeichert sind, und `loadOutput(handle)` liest 16.384 Zeichen einer davon. `storedKeys()` listet die gespeicherten Schlüssel mit ihrer Größe. `keep(value, label)` speichert einen großen Wert als Ausgabe, die ein späteres Skript oder `read_output` lesen kann; gespeichert wird sie erst, wenn das Skript abgeschlossen ist (1 MiB pro Wert, 64 Werte und 16 MiB pro Lauf). `limits().returnBudgetChars` sagt, wie viel vom Ausgabebudget noch übrig ist. Ein nur lesender Lauf (ein Review eines Ziels) kann lesen, aber weder speichern noch behalten. Bei Claude Code und ACP funktioniert `history()`, während `outputs()`, `loadOutput()` und `keep()` abgelehnt werden, weil Control Center für diese Läufe keine Tool-Ausgaben speichert.
- Ein Fehler wegen Timeout, Ausgabe-Überlauf oder Aufruflimit sagt, wie man ihn behebt.

Ein Lauf führt immer nur ein Skript gleichzeitig aus. Die Grenzwerte und was bei jedem geschieht, stehen auf der Seite [Code-Modus](/de-DE/handbuch/konzepte/code-modus/#grenzwerte); jedes Skript wird unter **Observability → Code-Ausführungen** aufgezeichnet.

## `eval` — persistente Interpreter

Eine Python- oder JavaScript-Zelle, deren Variablen, Importe und geladene Daten zwischen den Aufrufen erhalten bleiben. Stufe `exec`; nicht parallel-sicher. Nicht aus einem `repl`-Skript aufrufbar, und eine Zelle kann die Tools des Laufs nicht aufrufen: Um Tools aus Code aufzurufen, nutze [`repl`](#repl--ein-skript-ausführen-das-deine-tools-aufruft).

| Argument      | Bedeutung                                        |
| ------------- | ------------------------------------------------ |
| `code`        | Die Zelle                                        |
| `description` | Pflicht. 5–10 Wörter für die Beschriftung im Transkript |
| `language`    | `python` (Standard) oder `javascript`            |
| `reset`       | Verwirft den Interpreter und startet zuerst sauber |

- Der letzte Ausdruck wird wie in einem Notebook zurückgegeben.
- `display()` funktioniert, ein pandas-Frame wird als Tabelle dargestellt, und eine matplotlib-Figure kommt als **Bild zurück, das das Transkript anzeigt**.
- Die IPython-Idiome, die du reflexartig tippst — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — werden in gewöhnlichen Code umgeschrieben. `%pip` leert außerdem `sys.modules`, damit der nächste `import` sieht, was gerade installiert wurde.
- Eine Zelle, die mehr ausgibt als ihr Ausgabebudget, behält das erste Dreiviertel und das letzte Viertel, mit einer Zeile, die sagt, wie viele Zeichen und Bilder verworfen wurden.
- Ist der Interpreter beendet worden, ohne dass es verlangt wurde, erfährt die nächste Zelle einmal, dass ihre früheren Variablen weg sind.

:::note[Wo der Kernel läuft]
In der Kapsel der Unterhaltung, wenn sie eine hat, sonst in der OS-Sandbox des Laufs auf dem Host. Ohne Sandbox oder mit einer Sandbox, die nicht verfügbar ist, läuft er unbegrenzt, und `eval` fragt nach der Freigabe für die Ausführung auf dem Host. Er bootet dafür keine Kapsel — dieselbe Regel, die einen Rig-Tab am automatischen Start hindert.
:::

## `bash` im Hintergrund

`bash` mit `run_in_background: true` startet den Befehl und kehrt sofort mit einem Handle (`b1`, `b2`, …) zurück, statt zu warten. Der Agent arbeitet weiter oder beendet seinen Zug und wird geweckt, wenn der Befehl endet.

| Argument | Bedeutung |
| ------------------- | ------- |
| `run_in_background` | `true`, um zu starten und sofort zurückzukehren |
| `timeout_seconds` | Sekunden, bis der Befehl beendet wird: standardmäßig 600, höchstens 3.600 |
| `notify` | Optional. Ein einfaches Muster; jede passende Ausgabezeile wird während der Befehl läuft an den Agenten gesendet (etwa `listening on\|FAILED`) |

- Höchstens 4 Hintergrundbefehle laufen gleichzeitig in einem Lauf. Jeder wird bei seinem Timeout und am Ende des Laufs beendet, zusammen mit jedem Prozess, den er gestartet hat.
- Wenn ein Befehl endet, erhält der Agent eine Mitteilung mit dem Exit-Code, den letzten 2.000 Zeichen der Ausgabe und einem `read_output`-Handle für den Rest.
- Ein Agent, dessen einzige verbleibende Arbeit ein Hintergrundbefehl ist, wartet, ohne das Modell aufzurufen, und der Watchdog für Stille des Laufs pausiert, während er wartet.
- `bash_output(handle)` liest den Zustand und die letzte Ausgabe eines Befehls; `bash_kill(handle)` stoppt ihn. Beide sagen, wenn das Ergebnis schon zugestellt wurde.
- Ein Skript kann keinen Hintergrundbefehl starten. Claude Code hat seine eigene Hintergrund-Bash; Control Center hält diesen Lauf höchstens 10 Minuten offen, nachdem der Zug beendet wurde, der eine Aufgabe laufen gelassen hat.

## `compact` — Platz im Kontextfenster freimachen

Verdichtet den älteren Kontext der Unterhaltung vor dem nächsten Modellaufruf und behält, was `focus` nennt (höchstens 1.000 Zeichen). Die neuesten Züge bleiben wörtlich erhalten. Die Budgetzeile des Agenten pro Zug zeigt die Kontextnutzung bei 70, 80 und 90 %, und das Tool lohnt sich ab etwa 70 % vor einer langen neuen Arbeitsphase. Der Hook `preCompact` des Serverinhabers kann den Fokus ergänzen ([Shell-Hooks](/de-DE/handbuch/referenz/agentenkonfiguration/#shell-hooks)). Nach einer Verdichtung fügt der Server einen Block „Still in flight“ hinzu: das Ziel, ausstehende Weckrufe, offene Anfragen, Hintergrundbefehle, die Checkliste und gespeicherte Schlüssel, jeweils mit dem Aufruf, der sie wiederherstellt.

## `ask_user` — dem Menschen eine Frage stellen

Stufe `read`. Der **einzige** Weg, auf dem ein Lauf den Betreiber etwas fragt. Es zeichnet eine nummerierte Karte in die Unterhaltung und blockiert, bis jemand antwortet, überspringt oder die Frage ins Timeout läuft. Schreib die Frage nie als Chat-Nachricht — das beendet den Zug.

| Argument          | Bedeutung                              |
| ----------------- | -------------------------------------- |
| `question`        | Was gefragt werden soll                |
| `context`         | Optional: warum du fragst und was an der Antwort hängt |
| `options[]`       | Auswahlmöglichkeiten, jede `{label, description?}` |
| `allow_free_text` | Ob eine getippte Antwort angenommen wird |
| `multi_select`    | Ob mehrere Optionen gewählt werden dürfen |

Ein Überspringen ist Erfolg: Mach auf einer genannten Annahme weiter und frag nicht noch einmal. Ein Timeout ist ein Fehler mit derselben Anweisung. Freigabeaufforderungen („darf ich das tun?“) sind ein eigenes Tor und erscheinen als dieselbe Karte in der Unterhaltung.

Registriert nur, wenn ein Frage-Port und ein Zielbereich beide da sind. Ohne angeschlossenen Menschen **schlägt** der Aufruf **fehl**, statt für immer zu blockieren — dieselbe fail-closed-Haltung, die ein Schutzregel-`prompt` ohne verbundene zuständige Person einnimmt.

## `vibe_*` — Hintergrund-Worker steuern

Registriert nur, solange der [Vibe-Modus](/de-DE/handbuch/anleitungen/hintergrund-worker-steuern/) an ist. Alle fünf liegen auf der Stufe `read`: Das Tor gehört auf die Tools des Workers, dort, wo die Bearbeitung wirklich geschieht.

| Tool         | Argumente                                | Hinweise                                    |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | Kehrt sofort zurück; der Worker läuft weiter |
| `vibe_send`  | `worker_id`, `message`                   | Hängt an das Briefing an und startet erneut |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | Blockiert, bis er zur Ruhe kommt            |
| `vibe_kill`  | `worker_id`                              | Stoppt ihn                                  |
| `vibe_list`  | —                                        | Stufe, Status, verstrichene Zeit und letztes Ergebnis |

`tier` ist `fast` (mechanische Arbeit mit klarer Vorgabe) oder `good` (Entwurf, Einschätzung oder die Prüfung dessen, was ein `fast`-Worker erzeugt hat).
