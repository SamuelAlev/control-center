`cc_server` betreibt eine MCP-Registrierung (JSON-RPC 2.0) und stellt sie auf dem Hauptport des Servers (Standard `9030`) unter `POST /mcp` und `GET /sse` bereit, Protokollversion `2024-11-05`. Jeder Client erreicht dieselbe Registrierung: der Desktop, der Web-Build, externe MCP-Clients und die eingebaute Agentenlaufzeit. Externe MCP-Server lassen sich als dynamische Schicht in dieselbe Registrierung brücken.

## Größe der Registrierung

| Kennzahl                                                                              | Anzahl |
| ------------------------------------------------------------------------------------- | ------ |
| Tools, die `cc_server` registriert                                                    | 110    |
| Aus `packages/cc_mcp`                                                                 | 108    |
| Aus `packages/cc_mcp_client` (Tool-Suche)                                             | 2      |
| In der Basisregistrierung registriert (`server_mcp_registry.dart`)                   | 63     |
| Nach dem Start registriert, sobald ihre Dienste hochkommen (`cc_server_runtime.dart`) | 47     |
| Von den 63 der Basisregistrierung nur bei einem Code-Graph-Repository                | 5      |

Die fünf Code-Graph-Tools werden nur registriert, wenn der Host ein Code-Graph-Repository an `buildServerMcpRegistry` übergibt. `cc_server` übergibt immer eines, deshalb sind im ausgelieferten Binary alle 110 live.

Die volle Registrierung wird in `tools/list` ohne Suchfilter angeboten. Ticketbearbeitungen sind typisierte Tools.

:::note[Externe Clients sehen immer den ganzen Katalog]
`tools/list` wird nie beschnitten. MCP-Clients prüfen Tool-Namen gegen ihre eigene zwischengespeicherte Kopie dieser Liste und lehnen alles ab, was dort fehlt, ohne den Server zu fragen. Ein dort verstecktes Tool ist unerreichbar, nicht bloß still.

Der **eingebaute Harness** arbeitet anders: Er lädt je Anfrage nur eine residente Teilmenge der Definitionen und holt den Rest beim ersten Gebrauch nach. Das bleibt Verhalten des Harness und lässt diese Registrierung unangetastet. Siehe [Tool-Kontext und Prompt-Caching](/de-DE/handbuch/konzepte/tool-kontext).
:::

:::note[Jede Tool-Klasse ist registriert]
Eine Quelldatei unter `packages/cc_mcp/lib/src/tools/` ist ein Tool, das ein
Agent aufrufen kann. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
lässt den Build scheitern, wenn eine neue Tool-Klasse von niemandem
konstruiert wird.
:::

## Gemeinsame Parameter

### `workspace_id`

**Erforderlich** bei jedem Tool, das Daten im Geltungsbereich eines Arbeitsbereichs berührt. Eine fehlende oder ungültige `workspace_id` liefert einen ausdrücklichen Fehler, und ein Wert, der nicht zum Arbeitsbereich der Zieleinheit passt, wird abgelehnt, statt stillschweigend übergangen zu werden. Lass sie bei den wirklich globalen Tools weg: `list_workspaces` und die sechs Newsfeed-Tools (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), die auf der Feed-Liste des Server-Besitzers je Benutzer laufen. Such-Tools (`search_tool_bm25`, `list_my_tools`) nehmen sie optional, damit sie die Aufrufbarkeit nach dem Modus der Unterhaltung einstufen können. Wird ein Agent vom Server gestartet, erzwingt der Server den Arbeitsbereich. Eine fremde ID öffnet dem Agenten keinen anderen Arbeitsbereich.

## Tool-Suche

Beide kommen aus `cc_mcp_client`, nicht aus `cc_mcp`, und beide fragen die Modus-Sperre, damit sie melden, was im _aktuellen_ Unterhaltungsmodus aufrufbar ist.

| Tool               | Beschreibung                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `search_tool_bm25` | Sucht den Tool-Katalog nach Schlüsselwort; liefert passende Tools, ihre Argumentschemas und ob jedes jetzt aufrufbar ist |
| `list_my_tools`    | Listet die Tools, die in dieser Unterhaltung jetzt aufrufbar sind, gefiltert nach ihrem Modus                           |

Ein drittes Such-Tool, **`search_tools`**, gibt es nur im eingebauten Harness, und es gehört nicht zu dieser MCP-Registrierung. Es ordnet die eigene Tool-Oberfläche des Laufs und **lädt**, anders als `search_tool_bm25`, die Schemas dessen, was es findet, damit der Agent einen Treffer im nächsten Zug aufrufen kann. Agenten auf dem Harness sollten es vorziehen; MCP-Clients haben `search_tool_bm25`.

## Nachrichten und Delegation zwischen Agenten

Agenten sprechen miteinander über Bereiche (dauerhaft, in der Teilnehmerliste sichtbar). `ask_agent` ist Anfrage und Antwort mit einer Pflicht-Zeitüberschreitung; `delegate_task` wird serverseitig durch Tiefenobergrenze, Zykluserkennung, Budgetrahmen und Autonomieobergrenze geschützt.

| Tool            | Beschreibung                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------ |
| `send_to_agent` | Sendet eine Einwegnachricht an einen anderen Agenten, adressiert über `to_agent_id` oder exaktes `to_agent_name` |
| `ask_agent`     | Stellt einem anderen Agenten eine Frage und wartet auf die Antwort, oder läuft in die Zeitüberschreitung |
| `delegate_task` | Delegiert eine Aufgabe an einen anderen Agenten als verfolgtes Unterticket                      |
| `consult_agent` | Nimmt den nach Skills am besten passenden Spezialisten in den Bereich auf und startet ihn mit einem engen Auftrag |
| `todo_read`     | Liest die gespeicherte Aufgabenliste dieser Unterhaltung                                         |

## Kapsel-Tools (Rigs)

Steuere Wegwerfmaschinen — einen gekapselten Browser oder Linux-Desktop, einen
Android-Emulator oder einen iOS-Simulator — aus einem Lauf heraus. Sie werden
nach dem Start bedingungslos registriert: Ob eine Maschine wirklich booten
kann, ist eine Prüffrage, die die Tools bei jedem Aufruf beantworten.
Wiederholte Aufrufe in einer Unterhaltung verwenden dieselbe Maschine;
Screenshots kommen als Bildinhalt zurück, mit einem Budget von einem Bild je
Ergebnis, und ausgelesener Seiten- oder UI-Inhalt ist als nicht
vertrauenswürdige Daten eingezäunt. Die vier Use-Tools plus `rig_close`
deklarieren die [Aktionsklasse](/de-DE/handbuch/konzepte/schutzregeln/)
`enclosureControl` (die Use-Tools deklarieren außerdem `networkEgress` und
`processSpawn`; `mobile_use` und `ios_use` deklarieren außerdem
`packageInstall`), deshalb verweigern sie Nur-Lese-Modi. `rig_list` deklariert
keine — es liest nur den Zustand des Arbeitsbereichs. Das vollständige
Verbvokabular je Oberfläche steht in der
[Rigs-Referenz](/de-DE/handbuch/referenz/rigs/#aktionsverben).

| Tool           | Beschreibung                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------- |
| `computer_use` | Steuert einen Linux-Desktop in einer gekapselten VM: move, click, drag, scroll, type, resize, clipboard, screenshot |
| `browser_use`  | Steuert ein headless Chromium, Firefox oder WebKit (`engine`): navigate, click, fill, extract (a11y/DOM/console), clipboard, screenshot |
| `mobile_use`   | Steuert Android über ADB: inspect/input, Screenshots, install/start/stop/reset/uninstall von Apps, Deep Links und argv-förmige Gerätebefehle |
| `ios_use`      | Steuert den iOS-Simulator über WebDriverAgent/CoreSimulator: inspect/input, Screenshots, install/start/stop/uninstall von Apps, Deep Links und argv-förmige Simulatorprozesse |
| `rig_list`     | Listet die Rigs eines Arbeitsbereichs mit Oberfläche, Status, Anzeigegröße und Controller      |
| `rig_close`    | Zerstört ein Rig und verwirft den Maschinenzustand, den es besitzt                              |

## Nicht über MCP erreichbar

Kalender und Besprechungen haben keine MCP-Tools. Agenten können deinen Kalender, deine Besprechungen, Transkripte, Aufgaben oder Entscheidungen nicht lesen. Die Zusammenfassung, die Aufgaben und Entscheidungen erzeugt, läuft als eingebaute [`meeting_summary`-Pipeline](/de-DE/handbuch/konzepte/besprechungen/), nicht als Tool, das ein Agent aufrufen kann.

## Tools nach Modus begrenzen

Die Begrenzung wird zweimal aus einer Tabelle (`ModeToolPolicy`) durchgesetzt: einmal im MCP-Dispatcher für den Adapter von Claude Code und einmal in der Registrierung des eingebauten Harness. Ein blockierter Aufruf gibt den Grund zurück.

| Modus         | Werkzeugfläche                                                                                                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | Jedes registrierte Tool; keine Zulassungsliste                                                                                                                                                                                  |
| `plan`        | Eine kuratierte Zulassungsliste. Keine Schreibzugriffe auf den Worktree und keine Ticket-Verben `create` / `assign` / `delegate`, erlaubt sind aber Gedächtnis, Artefakte, Aufgabenlisten, `submit_plan`, `exit_plan_mode` und die Abschlussverben am Ticket des Laufs |
| `review`      | Eine kuratierte Zulassungsliste: Mitarbeit an der Review, Kommunikation, schreibgeschützte Kontextabfragen und der volle Satz an Ticket-Verben einschließlich `create_ticket` und `assign_ticket`                              |
| `orchestrate` | Eine kuratierte Zulassungsliste: Recherche- und Lese-Tools plus `propose_orchestration`, `create_playbook` und `run_playbook`. Einstellen, Zerlegen und Abschließen von Tickets laufen nach der Freigabe deterministisch, nie mitten im Lauf |

In jedem Modus erlaubt, unabhängig von der Zulassungsliste:

| Menge                    | Tools                                                                                                                                                                                                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Gedächtnis und Artefakte | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Code-Graph               | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                       |
| Laufmechanik             | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                    |

Auf einer Zulassungsliste zu stehen macht ein Tool nicht aufrufbar, und das gilt auch umgekehrt: Die Fähigkeit, den Betreiber zu fragen, ist ein **Harness**-Tool (`ask_user`) und kommt in diesem MCP-Katalog überhaupt nicht vor.

## Tools mit Freigabepflicht

Ein Tool kann `requiresApproval` deklarieren. Der Dispatcher baut dann ein `ApprovalPayload` und legt es über den `ConfirmationPort` vor, bevor das Tool läuft; `cc_server` verdrahtet diesen Port, das Tor ist also scharf.

Registrierte Tools, die es deklarieren: `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

Unabhängig davon sperren die einheitlichen Aktions-Schutzregeln jedes Tool, das eine nicht leere Menge `ActionClass` deklariert. Eine `prompt`-Entscheidung ohne verbundene zuständige Person wird abgelehnt. Siehe [Schutzregeln](/de-DE/handbuch/konzepte/schutzregeln/).

## Fähigkeiten ohne Tool

Nicht jede Fähigkeit des Produkts ist für einen Agenten erreichbar. Diese haben
gar kein Tool, deshalb liefert ein Name, den du anderswo gesehen haben
könntest, „unknown tool“ zurück:

| Fähigkeit                              | Wo sie stattdessen liegt                                                                     |
| -------------------------------------- | -------------------------------------------------------------------------------------------- |
| Einen Agenten einstellen, entlassen oder bearbeiten | Die Agenten-Oberfläche. Es gibt kein Tool `hire_agent` / `fire_agent` / `update_agent` |
| Einen Arbeitsbereich anlegen           | `workspace.upsert` über RPC, das ihn anlegt und die Eigentümerschaft stempelt                 |
| Projekte (anlegen / listen / aktualisieren / einordnen) | Die Tickets-Oberfläche. Projekte sind eine Bedienoberfläche — siehe [Arbeit mit Projekten organisieren](/de-DE/handbuch/anleitungen/projekte/) |
| Dem Betreiber eine blockierende Frage stellen | Das **Harness**-Tool `ask_user`, nicht MCP. Es zeichnet ein Formular in die Unterhaltung und blockiert auf die Antwort |
| Diagnose je Agent                      | Nichts. Es gibt kein `doctor` — siehe [Einen Agenten diagnostizieren](/de-DE/handbuch/anleitungen/agent-diagnostizieren/) |
| Kalender und Besprechungen             | RPC nur für menschliche Clients (siehe oben)                                                 |
