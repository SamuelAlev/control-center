Control Center kann **pseudonyme Nutzungsereignisse** an eine [Umami](https://umami.is)-Instanz senden. Nutzungsanalysen sind **ausgeschaltet, bis der Serverbetreiber sie einschaltet**. Die Einstellung gehört zum Server und gilt für jeden damit verbundenen Client: die Desktop-App, die Web-App, das Smartphone und den Server selbst.

Nutzungsanalysen sind unabhängig von **Absturzberichte teilen**, einer Einstellung pro Gerät für Absturz- und Fehlerdiagnosen.

## Wer entscheidet

| Schalter | Wo | Wirkung |
| --- | --- | --- |
| **Nutzungsanalysen teilen** | Onboarding (Sandbox-Schritt) und **Einstellungen → Datenschutz**. Nur der Serverbetreiber kann ihn ändern; andere Mitglieder sehen den aktuellen Wert schreibgeschützt | Serverweit. Gespeichert als `telemetry.usage_analytics` in den Servereinstellungen. Aus, solange er nicht auf `true` gesetzt ist |
| Build-Typ | Automatisch | Debug- und Profile-Builds senden nicht. Sie schreiben jedes Ereignis stattdessen ins Debug-Log |
| `CC_ANALYTICS_DEBUG=1` | Umgebung von `cc_server` oder dessen `.env` | Lässt Debug- und Profile-Builds des Servers und aller damit verbundenen Clients zum Testen tatsächlich senden. Der Schalter oben muss trotzdem an sein |
| `DO_NOT_TRACK=1` | Umgebung von `cc_server` | Stoppt die eigene Übermittlung des Servers, egal was der Schalter sagt. Clients richten sich weiterhin nach dem Schalter |
| Demo-Server | Automatisch | Der öffentliche Demo-Server sendet selbst nichts. Besucher können den Schalter nicht ändern |

Clients lesen die Einstellung vom Server (`telemetry.config`, danach live über `telemetry.watch`). Bis die Antwort eintrifft, warten Ereignisse in einem kleinen Puffer im Arbeitsspeicher. Lautet die Antwort Nein, wird der Puffer verworfen. Wird der Schalter ausgeschaltet, verwirft jeder Client sofort alles, was noch in der Warteschlange liegt, und sendet nichts mehr.

## Was nie gesendet wird

- Inhalte von Nachrichten, Tickets, Reviews oder Besprechungen, Titel, Prompts, Shell-Befehle und Suchanfragen
- Namen, Logins, E-Mail-Adressen, Avatare und Anzeigenamen
- Dateipfade, Repository-Namen, Branch-Namen, Hostnamen und URLs (ein Repository wird nur als pseudonyme `repo_id` gesendet, ein Besprechungslink nur als sein Anbieter)
- Rohe Kennungen jeglicher Art

Jedes Ereignis durchläuft eine Eigenschaftsrichtlinie, bevor es den Prozess verlässt. Text, Pfade, URLs, E-Mail-Adressen, nicht pseudonymisierte IDs sowie Zeichenketten unter Schlüsseln wie `email`, `*_name`, `path`, `title`, `prompt`, `content` oder `token` werden verworfen statt gesendet. Eine Zeichenkette wird nur gesendet, wenn sie ein kurzes Token aus einem geschlossenen Vokabular ist, etwa ein Enum-Wert, eine Version, ein Gebietsschema oder eine Modell-ID.

## Pseudonyme IDs

IDs werden gesendet, aber nur als Pseudonyme. Jede ID eines Arbeitsbereichs, Bereichs, einer Unterhaltung, eines Agenten, Laufs, Benutzers und Geräts wird durch einen HMAC-SHA256 mit dem eigenen geheimen Salt der Installation (`telemetry.pseudonym_salt`) ersetzt und auf 20 Hex-Zeichen gekürzt. Derselbe Arbeitsbereich meldet immer denselben Wert, sodass sich Ereignisse verknüpfen und zählen lassen, aber die rohe ID verlässt die Installation nie. Das Salt entsteht beim ersten Start des Servers und wird nie an den Analyseanbieter gesendet. Löschst du das Datenverzeichnis des Servers, entstehen ein neues Salt und eine neue Installations-ID, wodurch alles zuvor Erfasste nicht mehr zuzuordnen ist.

## Bildschirmaufrufe

Jede Navigation erfasst einen Seitenaufruf, dessen URL die **Routenvorlage** ist, etwa `/workspaces/:workspaceId/spaces/:spaceId`, nie die konkrete Adresse. Der Bildschirmname besteht aus den festen Segmenten der Vorlage, im Beispiel also `workspaces_spaces`. Routenparameter, die auf `Id` enden, werden als pseudonyme `*_id`-Eigenschaften angehängt, numerische (etwa eine PR-Nummer) als Zahlen. Alle anderen Parameter werden verworfen.

## Zustellung

Ereignisse werden einzeln an `<host>/api/send` gesendet, aus einer Warteschlange im Arbeitsspeicher mit bis zu 200 Ereignissen. Bei einem Netzwerkfehler, einer Zeitüberschreitung, `429` oder `5xx` bleibt das Ereignis erhalten und wird mit exponentiellem Backoff erneut versucht, von 1 Sekunde bis zu 5 Minuten. Jeder andere `4xx` verwirft es. Nichts wird auf die Festplatte geschrieben, daher gehen Ereignisse verloren, die beim Beenden der App noch in der Warteschlange liegen. Die Warteschlange wird geleert, wenn die App in den Hintergrund wechselt und wenn der Server herunterfährt.

## Einen Build auf eine andere Instanz richten

Das Ziel wird beim Build festgelegt:

```bash
--dart-define=CC_ANALYTICS_HOST=https://analytics.example.com/
--dart-define=CC_ANALYTICS_WEBSITE_ID=<website uuid>
```

Der Anbieter-Adapter liegt in `packages/cc_analytics`. Um einen anderen Analysedienst zu unterstützen, fügst du dort einen Adapter hinzu. Trackingplan und Datenschutzregeln bleiben gleich.
