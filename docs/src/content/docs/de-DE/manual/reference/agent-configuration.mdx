Diese Referenz listet jedes Feld der Agenten-Entität auf, dazu die Enums und Flags, die sie verwendet. Wie du einen Agenten in der App anlegst oder bearbeitest, steht Schritt für Schritt unter [Einen Agenten erstellen und konfigurieren](/de-DE/handbuch/anleitungen/agent-erstellen/).

## Felder der Agenten-Entität

| Feld                    | Typ                    | Erforderlich | Beschreibung                                                                                                                                                                                          |
| ----------------------- | ---------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                    | `String`               | Ja           | Eindeutige Kennung des Agenten                                                                                                                                                                        |
| `name`                  | `String`               | Ja           | Kurze Kennung für @-Erwähnungen                                                                                                                                                                       |
| `title`                 | `String`               | Ja           | Lesbare Berufsbezeichnung                                                                                                                                                                             |
| `agentMdPath`           | `String`               | Ja           | Absoluter Pfad zur `.md`-Definitionsdatei des Agenten                                                                                                                                                 |
| `workspaceId`           | `String`               | Ja           | Arbeitsbereich, dem der Agent gehört (nicht null)                                                                                                                                                     |
| `reportsTo`             | `String?`              | Nein         | ID des übergeordneten Agenten                                                                                                                                                                         |
| `skills`                | `AgentSkills`          | Ja           | Menge von Skill-Kennungen                                                                                                                                                                             |
| `persona`               | `String?`              | Nein         | Freitext mit Verhaltensanweisungen                                                                                                                                                                    |
| `systemPrompt`          | `String?`              | Nein         | Überschreibt den Standard-System-Prompt                                                                                                                                                               |
| `adapterId`             | `String?`              | Nein         | ID des Inferenzadapters                                                                                                                                                                               |
| `modelId`               | `String?`              | Nein         | Modell-ID innerhalb des Adapters                                                                                                                                                                      |
| `strictMode`            | `bool`                 | Nein         | Standard `false`. Wird in die Zeile und in die `AGENTS.md` des Agenten geschrieben                                                                                                                    |
| `effort`                | `String?`              | Nein         | ID der Denkstufe (z. B. `'low'`, `'xhigh'`), aus den `thinkingLevels` des gewählten Modells                                                                                                           |
| `contextSize`           | `int?`                 | Nein         | Maximale Größe des Kontextfensters                                                                                                                                                                    |
| `role`                  | `AgentRole?`           | Nein         | Agentenrolle                                                                                                                                                                                          |
| `monthlyBudgetMicros`    | `int`                  | Nein         | Monatliche Ausgabenobergrenze in Mikrodollar (Standard `0`, unbegrenzt)                                                                                                                                      |
| `silenceTimeoutMinutes` | `int?`                 | Nein         | Überschreibung des Stille-Timeouts in Minuten; null oder ein Wert von 1–240 (per Assertion im Konstruktor)                                                                                            |
| `maxConcurrentTasks`    | `int`                  | Nein         | Standard `1`. Kapazitätszahl, die das Präsenzmodell meldet (laufende und wartende Anzahlen werden damit verglichen)                                                                            |
| `visibility`            | `AgentVisibility`      | Nein         | Standard `workspace`                                                                                                                                                                                  |
| `lifecycleStatus`       | `AgentLifecycleStatus` | Nein         | Governance-Status (Standard `active`). Geschrieben vom harten Budgetstopp, angezeigt im Organigramm und in der Präsenzliste. Die Ausführung nimmt von einem Agenten mit `paused` weiter Arbeit an    |
| `budgetPolicyId`        | `String?`              | Nein         | ID einer gemeinsamen Budgetrichtlinie; ist der Wert null, gilt `monthlyBudgetMicros` direkt                                                                                                            |
| `runtimeProfileId`      | `String?`              | Nein         | ID eines eigenen Laufzeitprofils                                                                                                                                                                      |
| `createdAt`             | `DateTime`             | Ja           | Zeitpunkt der Erstellung                                                                                                                                                                              |

`name` und `title` dürfen nicht leer sein (per Assertion im Konstruktor). Ein
`monthlyBudgetMicros` von `0` heißt unbegrenzt. Eine Obergrenze schreibst du mit
`agents.upsert`.

## Berechtigungen

Ein Agent trägt keine Berechtigungs-Flags. Pushen, Pull Requests öffnen und veröffentlichen, in einen Tracker schreiben und ausgehender Netzwerkverkehr sind Aktionsklassen (`gitPush`, `prCreate`, `prPublish`, `vendorSyncWrite`, `networkEgress`), die die [Schutzregeln](/de-DE/handbuch/konzepte/schutzregeln/) im Geltungsbereich Arbeitsbereich, Agent oder Bereich auflösen. Das GitHub-Token eines Laufs darf immer nur lesen; Pushes laufen durch das Gateway für Agentenläufe, das vor dem Weiterleiten die Regel `gitPush` fragt.

## AgentSkills

Eine unveränderliche Menge von Skill-Kennungen, ohne Unterscheidung der Groß- und Kleinschreibung. Beim Dispatch werden diese Slugs als Skill-Links im Overlay des Agenten synchronisiert; der Harness lädt danach das Frontmatter der verlinkten Skills automatisch in den Prompt.

```
{'flutter', 'dart', 'rest-api'}
```

## Shell-Hooks

Shell-Hooks lassen den Serverinhaber eigene Skripte um einen eingebauten Harness-Lauf ausführen: einmal beim Sitzungsstart, vor jedem Tool-Aufruf und nach jedem Tool-Aufruf. Ein Hook ist beliebiger Code, daher gehören Hooks zur Host-Konfiguration. Nur der Serverinhaber richtet sie von Hand auf der Maschine des Servers ein. Es gibt keine Einstellung in der App und keine Operation, die sie schreibt.

Für einen Agenten liegen die Hooks in seinem eigenen Ordner unter dem Datenverzeichnis des Servers:

```text
<data dir>/_agent_hooks/<workspace id>/<agent slug>/hooks.json
```

`<agent slug>` ist der Name des Ordners des Agenten im Arbeitsbereich (`agents/<slug>/`). Dieser Ordner liegt außerhalb des Speichers jedes Arbeitsbereichs, und jede Sandbox verbirgt das Datenverzeichnis, daher kann kein Mitglied, kein Lauf und kein Terminal ihn beschreiben.

`hooks.json` ordnet jedem von drei Schlüsseln ein Skript zu, über einen Pfad relativ zum Hook-Ordner:

| Schlüssel      | Wann er läuft                 | Was sein Exit-Code bedeutet                                    |
| -------------- | ----------------------------- | -------------------------------------------------------------- |
| `sessionStart` | Einmal, wenn der Lauf startet | Nichts; der Hook beobachtet nur                                |
| `preTool`      | Vor jedem Tool-Aufruf         | `0` erlaubt den Aufruf; alles andere verweigert ihn            |
| `postTool`     | Nach jedem Tool-Aufruf        | Nichts; der Hook beobachtet nur                                |

- Jedes Skript wird als eigene ausführbare Datei gestartet, ohne Shell und ohne Argumente. Es muss daher ausführbar sein und mit einer Shebang-Zeile beginnen. Es bekommt das Ereignis als JSON auf stdin: den Ereignisnamen und bei den Tool-Hooks den Namen des Tools mit seinen Argumenten (`preTool`) bzw. seinem Ergebnis (`postTool`).
- Ein Hook läuft als einer der Tool-Prozesse des Laufs, im Ordner des Agenten für diesen Lauf. Lässt der Server Agenten in einer Sandbox laufen, läuft er in der Sandbox des Laufs. Er bekommt eine minimale Umgebung und keine Anmeldedaten des Laufs: kein Forge- oder Anbieter-Token und keinen Zugriff auf das Gateway.
- Jeder Hook hat 30 Sekunden. Seine Ausgabe wird gelesen und verworfen.
- `preTool` schließt im Fehlerfall: Ein Exit-Code ungleich null, ein Timeout oder ein Skript, das nicht starten kann, verweigert den Tool-Aufruf.
- Ein Pfad, der absolut ist, fehlt oder den Hook-Ordner verlässt (Links aufgelöst), wird abgelehnt, und das Log des Laufs sagt, welcher Hook warum abgelehnt wurde. Ein abgelehnter oder unlesbarer `preTool`-Hook verweigert jeden Tool-Aufruf, bis er behoben ist.
- Ein `hooks`-Block in `.agents/harness.json`, egal ob im Repository oder im eigenen Ordner des Agenten, wird ignoriert. Ein Repository ist oft fremder Code, und den Ordner des Agenten können Mitglieder und Läufe beschreiben. Das Log des Laufs sagt, dass der Block ignoriert wurde, und wo Hooks stattdessen gelesen werden.

Shell-Hooks gelten nur für den eingebauten Harness. Ist ein `preTool`- oder `postTool`-Hook konfiguriert, ruft der Lauf seine Tools nacheinander auf.

## AgentLiveState (abgeleitet)

Nicht gespeichert. Sieben Werte. Die Deklarationsreihenfolge ist die Prioritätsreihenfolge (`sortPriority`, von einem Test festgeschrieben) und damit die Reihenfolge, nach der die Liste sortiert:

| Zustand     | `sortPriority` | Bedingung                                                                                                            |
| ----------- | -------------- | -------------------------------------------------------------------------------------------------------------------- |
| `running`   | 0              | Mindestens ein Laufprotokoll hat den Status `running`                                                                |
| `blocked`   | 1              | Die Liveness des jüngsten Laufs ist `blocked`, `stalled` oder `looping`                                              |
| `failed`    | 2              | Der Status des jüngsten Laufs ist `error`, oder seine Liveness ist `failed` oder `dead`                              |
| `queued`    | 3              | Ein Lauf ist dispatched, wird aber nicht ausgeführt: Er wartet hinter einem anderen Lauf desselben Agenten, oder er ist geschrieben, aber noch nicht gestartet |
| `succeeded` | 4              | Der Lauf wurde erfolgreich abgeschlossen                                                                             |
| `idle`      | 5              | Der Agent ist schon gelaufen und hat nichts unterwegs                                                                |
| `neverRun`  | 6              | Es gibt keine Laufprotokolle                                                                                         |

`queued` und `succeeded` gelten **nur je Lauf**. `deriveAgentLiveState`, das den Listenzustand eines Agenten berechnet, liefert keines von beiden: Zurück kommen `neverRun`, `running`, `failed`, `blocked` oder `idle`.
