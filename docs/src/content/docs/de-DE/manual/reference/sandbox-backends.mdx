:::caution[Ob ein Lauf in der Sandbox läuft, hängt vom Host ab]
`cc_server` entscheidet einmal beim Start, wie Agenten auf diesem Host laufen, und die Entscheidung gilt bis zum nächsten Neustart:

- **In der Sandbox** (`native`): Die Prüfung hat ein Backend gefunden, und `--sandbox` ist nicht `off`. Beide Nahtstellen werden umhüllt: die Claude-Code-CLI über den Sandbox-Port, und ACP plus das Werkzeug `bash` des eingebauten Harness über den Sandbox-Manager.
- **Aus** (`off`): Der Serverinhaber hat den Server mit `--sandbox off` gestartet. Jeder Agent jedes Mitglieds läuft auf diesem Rechner ohne Einschränkung, wer ihn auch gestartet hat.
- **Nicht verfügbar** (`unavailable`): Die Sandbox ist eingeschaltet, aber die Prüfung hat kein Backend gefunden (**unter Windows immer**, und unter Linux oder WSL2 ohne `bwrap` und `socat`). Ein Lauf startet nur, wenn die dafür verantwortliche Person der [Serverinhaber](/de-DE/handbuch/konzepte/autorisierung/#der-serverinhaber) ist: die Person, die ihn angefragt hat, oder bei Automatisierung die Person, an die sie gebunden ist. Der Lauf aller anderen wird abgelehnt, bevor ein Zugangsdatum ausgestellt, ein Lease genommen oder ein Prozess gestartet wird. Ist kein Serverinhaber eingetragen, startet kein Lauf.

Ein abgelehnter Lauf schlägt mit dem Code `sandbox_unavailable` fehl. Die App zeigt ihn als **Agenten brauchen eine Sandbox auf diesem Server**: „Dieser Server hat keine Sandbox, daher kann hier nur der Serverinhaber Agenten ausführen. Der Inhaber kann die Sandbox installieren oder das Sandboxing für alle ausschalten.“

Ein Lauf, der ohne Sandbox startet (unter `off`, oder der eigene Lauf des Serverinhabers unter `unavailable`), läuft direkt auf dem Host. ACP und das Werkzeug `bash` des Harness starten trotzdem mit bereinigter Umgebung; Claude Code geht durch `NoSandboxAdapter` und erbt die Umgebung des Hosts. Was bleibt, sind der eigene Worktree des Laufs (Copy-on-Write, wo `rift` mitgeliefert wird; `git worktree` unter Windows), ein Forge-Token, das nur lesen darf, je Start vermittelt und beim Abbau widerrufen, Pushes, die am Gateway für Agentenläufe die Push-Regel passieren, die Befehlsrichtlinie des Modus, die einheitlichen [Aktions-Schutzregeln](/de-DE/handbuch/konzepte/schutzregeln/) (fail-closed), die Bereinigung der Umgebung auf den Pfaden von ACP und dem `bash` des Harness, und die Werkzeugfläche, die der Modus zulässt.

Die prozessinternen Dateiwerkzeuge des Harness (read, write, edit, apply patch, search, find, search_files) liegen auf jedem Host außerhalb der Sandbox: Sie laufen im Serverprozess, umhüllt wird also nur `bash`.

Der Host ist nie ein Rückfall für einen Server, der Agenten in einer Sandbox ausführt. Hat der Server Agenten in einer Sandbox, aber für einen Lauf keine Sandbox zur Hand, werden dessen Werkzeugprozesse und `bash`-Befehle abgelehnt, statt auf dem Host gestartet. Dieselbe Haltung entscheidet über die kleinen Prozesse rund um einen Lauf: ACP-Einmalhelfer (Unterhaltungstitel, `/btw`, `/handoff`, `/goal`) und die Golden-Tests eines Pull Requests in Review Studio laufen in der Sandbox, wenn der Server Agenten in einer Sandbox ausführt, ohne Einschränkung unter `off`, und unter `unavailable` nur für eine Anfrage, für die der Serverinhaber einsteht; sonst werden sie übersprungen.
:::

## Überblick über die Backends

| Backend          | Wert      | Plattform                                     | Verfügbarkeit                                                                                                                |
| ---------------- | --------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Gekapselte VM    | `microvm` | macOS, Linux, Windows (microVM-Hypervisor)    | An die Prüfung der microVM-Laufzeit gebunden; gilt für interaktive Terminals — die Shell läuft in einem [Rig](/de-DE/handbuch/konzepte/rigs/), nicht auf dem Host |
| Native sandbox   | `native`  | macOS (Seatbelt), Linux und WSL2 (bubblewrap) | Beim Start geprüft; Linux verweigert einen Lauf, der Schreibverbote per Dateinamen-Glob verlangt, die bubblewrap nicht durchsetzen kann |
| No isolation     | `none`    | Alle                                          | Der Standard beim Parsen und der Standard des Terminals; der Agenten-Dispatch nutzt es unter `--sandbox off`, und ohne verfügbares Backend nur für die eigenen Läufe des Serverinhabers |

`SandboxBackend.fromName` liefert `none` für einen Nullwert oder einen unbekannten gespeicherten Wert.

**`microvm` ist das einzige Backend mit einer Kernel-Grenze** — die Arbeit
läuft wirklich nicht auf dem Host. Es ist in keine Richtung ein stiller
Rückfall: Wer es auf einem Host ausdrücklich verlangt, der keine VM starten
kann, scheitert laut („Ich habe eine VM verlangt und meinen Laptop bekommen“
ist die eine Verschlechterung, die sich die Kapsel nicht leisten kann), und
nur ein *nicht festgelegter Standard* wird auf `native` herabgestuft, mit
einer Logzeile, die das sagt. Das tatsächliche Backend der Sitzung wird an
den Client gemeldet und mit einem Badge versehen, ein Terminal kann also nie
als gekapselt gelten, während es auf dem Host läuft. Lebenszyklus, Images und
der Ausgang der VM selbst stehen in der
[Rigs-Referenz](/de-DE/handbuch/referenz/rigs/).

**Windows hat keine native Sandbox.** `NativeSandboxAdapter.probe` liefert `available: false` auf jedem Host, der nicht macOS oder Linux/WSL2 ist, daher ist ein Windows-Server `unavailable`: Nur die Agentenläufe des Serverinhabers starten, ohne Einschränkung, und alle anderen werden abgelehnt. Damit jedes Mitglied dort Agenten laufen lassen kann, startet der Inhaber den Server mit `--sandbox off`, wodurch alle ohne Einschränkung laufen. Das Backend `microvm` ist davon getrennt: Es hängt an der microVM-Laufzeit und gilt für interaktive Terminals und Rigs, nicht für die Umhüllung von `bash` auf dem Host.

## Prüfergebnis

Die Prüfung entscheidet, ob durchgesetzt wird. Sie läuft einmal, beim Start des Servers.

| Host                                      | `available` | Notiz / Hinweis                                                                          |
| ----------------------------------------- | ----------- | ---------------------------------------------------------------------------------------- |
| macOS                                     | `true`      | `sandbox-exec` (Seatbelt) — Namespace-Isolation, keine Kernel-Grenze                     |
| Linux oder WSL2 mit `bwrap` und `socat`   | `true`      | bubblewrap — Namespace-Isolation, keine Kernel-Grenze                                    |
| Linux oder WSL2, eines der Werkzeuge fehlt | `false`    | `requiresInstall: true`, mit einem Installationshinweis, der die fehlenden Pakete nennt  |
| Jede andere Plattform                     | `false`     | Eine native Sandbox wird auf dieser Plattform nicht angeboten                            |

Der Server schreibt das Ergebnis in eine Startzeile: `agent sandbox ON` plus die Notiz; `no OS-native agent sandbox on this host` plus den Hinweis, der ergänzt, dass nur Läufe starten, für die der Serverinhaber einsteht; oder `agent sandbox DISABLED by --sandbox off`. Die Erreichbarkeitszeile beim Start trägt dieselbe Entscheidung als `sandbox=native`, `sandbox=off` oder `sandbox=unavailable`. `GET /healthz` trägt kein Sandbox-Feld.

`--sandbox` / `CC_SERVER_SANDBOX` nimmt `on` (Standard) oder `off` an. `on` umhüllt jeden Lauf, wenn der Host ein Backend anbietet, und lässt bei fehlendem Backend nur die Läufe des Serverinhabers zu. `off` lässt jeden Agenten jedes Mitglieds auf diesem Host ohne Einschränkung laufen; es ist die Entscheidung des Inhabers für alle, keine Einstellung je Lauf.

## Natives Backend

### macOS: Seatbelt

Nutzt Apples Seatbelt-Sandbox (dasselbe System wie die macOS App Sandbox).

Das erzeugte Profil ist **standardmäßig permissiv** (`(allow default)`) und schneidet Verbote aus, weil ein Profil, das standardmäßig alles verweigert, eine interaktive Shell unbenutzbar macht — es gibt zu viele dyld-, XPC- und Mach-Aufrufe, als dass man sie aufzählen könnte. Die praktische Folge: Ein Agent kann den größten Teil des Hosts weiterhin lesen; deine registrierten Checkouts sind durch ausdrückliche Verbote für Schreiben und Umbenennen geschützt, nicht durch Unsichtbarkeit.

- **Dateisystem, Lesen**: verweigert für die geheimen Pfade (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` und der Rest der Leseverbotsmenge)
- **Dateisystem, Schreiben**: zuerst auf Verweigern zurückgesetzt, dann ausdrückliche Erlaubnisse für Teilpfade; die Pfade mit zwingendem Verbot (Shell-rc-Dateien, `.git/hooks`, Claude-Konfiguration, geschützte Checkouts) bleiben auch innerhalb einer beschreibbaren Wurzel gesperrt. `file-write-unlink` ist auf jedem verweigerten Pfad und seinen Vorfahren verboten, ein Umbenennen kann ein Schreibverbot also nicht umgehen
- **Prozess**: `process-exec` verweigert die dauerhaft gefährlichen Binaries, dazu eine Sperre für alles, was aus einem beschreibbaren Verzeichnis ausgeführt wird. Bekannte Toolchain-Installationsbäume in Ihrem Home-Verzeichnis (Caches von corepack, npx und `pnpm dlx`, Node-Versionsmanager, Playwright-Browser, rustup und cargo, Go, fvm und der pub-Cache, pyenv, uv und pipx, rbenv, sdkman, mise, asdf und `~/.local/bin`) werden unter dieser Sperre wieder geöffnet. Auch die gemeinsamen temporären Verzeichnisse sind gesperrt. Jede Sitzung erhält stattdessen ein privates `TMPDIR` unter `/private/tmp`, in dem selbst gebaute Programme (eine `go test`-Binary, ein cargo-Build) laufen können. Die dauerhaft gefährlichen Verbote werden nach diesen Freigaben angewendet
- **Netzwerk**: beschränkt auf die Ports der prozessinternen Proxys plus DNS — Loopback ist nicht pauschal erlaubt, und TCP-Listening ist verweigert. Unix-Sockets sind nur innerhalb des privaten `TMPDIR` der Sitzung erlaubt, was Werkzeuge wie tsx und Chrome abdeckt, die dort einen IPC-Socket halten; Ihr SSH-Agent und andere Sockets bleiben unerreichbar. Die Proxys setzen die Domain-Zulassungsliste je Sitzung durch (siehe [Netzwerkausgang](#netzwerkausgang))
- **Konfiguration**: Profile werden je Start aus der `SandboxSpec` erzeugt
- **Die eigenen Befehle des Servers**: Kein direktes Kind eines Ordners, aus dem der Server Programme startet (jeder `PATH`-Eintrag und die üblichen Werkzeugordner je Benutzer wie `~/.local/bin`, wobei Links von Versionsmanagern wie `~/fvm/default` aufgelöst werden), kann angelegt, ersetzt, gelöscht oder umbenannt werden, ebenso wenig das installierte Paket, auf das ein verlinkter Befehl zeigt. Siehe [Die Befehlsordner des Servers](#die-befehlsordner-des-servers)
- **Startdateien**: Jeder Home-Pfad, dessen Lesen das Profil verbietet, ist auch zum Schreiben verboten, und die Startdateien der Shells und Sitzungen des Server-Benutzers (`.zshenv`, `.zlogin`, `.bash_login`, fish-Konfiguration, systemd-User-Units, Autostart-Einträge und ähnliche) sind in jedem Modus schreibgesperrt

Voraussetzungen:

- `sandbox-exec` (`/usr/bin/sandbox-exec`), Teil jeder macOS-Installation — kein zusätzliches Werkzeug nötig

### Linux: bubblewrap

Nutzt bubblewrap (`bwrap`), um Mount- und PID-Namespaces anzulegen.

- **Dateisystem**: legt einen Mount-Namespace an, in dem nur die gebundenen Pfade sichtbar sind
- **Netzwerk**: läuft in einem nicht geteilten Netzwerk-Namespace; der Verkehr erreicht die Host-Proxys über Unix-Socket-Brücken von `socat`
- **Prozess**: Isolation im PID-Namespace
- **Die eigenen Befehle und Startdateien des Servers**: dieselben Schutzmaßnahmen wie unter macOS, als bubblewrap-Bindungen ausgedrückt. Sie sind unter Linux noch nicht verifiziert, und ein fehlender Befehlsordner kann dort weiterhin angelegt werden

Voraussetzungen:

- `bubblewrap` und `socat` installiert (`sudo apt-get install bubblewrap socat` unter Debian/Ubuntu)
- Unterstützung für Kernel-Namespaces (Standard auf modernem Linux)

Bubblewrap kann einen bestehenden Pfad überlagern, aber keine *neue* Datei
`.env`, `*.key` oder `*.pem` in einem beschreibbaren Bind verbieten. Die
Standardrichtlinie des Dispatch verlangt genau diese Schreibverbote per
Dateinamen-Glob, deshalb **schlägt der native Agenten-Dispatch unter
Linux/WSL2 derzeit fail-closed fehl, auch wenn die Prüfung bubblewrap findet**. Er
läuft nicht mit einer stillschweigend schwächeren Richtlinie. Um den nativen
Dispatch unter Linux wiederherzustellen, braucht es ein Backend mit
Dateinamenregeln zum Erzeugungszeitpunkt. Das Sandboxing abzuschalten ist ein
ausdrückliches, unbeschränktes Abwählen, kein gleichwertiger Ersatz.

In der Praxis läuft ein Linux- oder WSL2-Server heute auf zwei Arten. Mit `--sandbox off` gestartet, lässt er die Agenten jedes Mitglieds ohne Einschränkung laufen. Ohne installiertes bubblewrap oder `socat` ist er `unavailable` und lässt allein die Agenten des Serverinhabers ohne Einschränkung laufen. Sind beide Werkzeuge installiert und die Sandbox eingeschaltet, schlägt jeder Lauf fail-closed fehl, auch der des Inhabers.

## Die Befehlsordner des Servers

Der Server ermittelt beim Start einmal jeden Ordner, aus dem er Programme startet: jeden Eintrag seines `PATH`, die Werkzeugordner je Benutzer, die er prüft (etwa `~/.local/bin`, `~/.bun/bin` und die globalen Ordner von npm, yarn und pnpm), und den echten Ordner hinter jedem Link auf dem Weg (Links von Versionsmanagern wie `~/fvm/default` oder ein fnm-Standard). In einer Sandbox kann ein Agent in diesen Ordnern keinen Befehl anlegen, ersetzen, löschen oder umbenennen, auch nicht den Link, der auf einen führt, oder das installierte Paket, auf das ein verlinkter Befehl zeigt, und er kann die Ordner darüber nicht umbenennen. Sonst könnte ein Lauf in der Sandbox ein Programm einpflanzen, das der Server oder die Person später außerhalb der Sandbox startet.

Was sich für einen Lauf ändert:

- Globale Installationen aus einem Lauf in der Sandbox schlagen mit „Operation not permitted“ fehl: `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, sowie `cargo install`, `go install` oder `dart pub global activate`, wenn deren bin-Ordner auf dem `PATH` des Servers liegt.
- Das Umschalten einer Standardversion schlägt ebenso fehl (`fnm default`, `nvm alias default`, `fvm global`), ebenso ein Werkzeug, das sich selbst in place aktualisiert.
- Projektlokale Installationen (`node_modules/.bin`), `npx`, `pnpm dlx`, durch corepack verwaltete Paketmanager, SDK-Caches und normale Builds funktionieren weiter.

Um ein globales Werkzeug für Agenten verfügbar zu machen, installiere es auf dem Server selbst, als Benutzer des Servers, und starte den Server neu, damit auch der neue Befehl geschützt ist. Oder installiere es im Projekt. Ein Befehl, der installiert wurde, nachdem der Server gestartet ist, ist erst ab dem nächsten Start vollständig geschützt.

Durchgesetzt und getestet ist das auf macOS. Unter Linux sind dieselben Regeln bubblewrap-Bindungen, die noch nicht verifiziert sind. Windows hat keine Sandbox.

## Backend ohne Isolation

Keine Sandbox. Der Prozess läuft direkt auf dem Host, mit Dateisystem, Netzwerk und Prozesszugriff des Hosts. ACP und das Werkzeug `bash` des Harness bekommen weiterhin die Bereinigung der Umgebung und die Befehlsrichtlinie; Claude Code über `NoSandboxAdapter` erbt die Umgebung des Hosts. Der Agenten-Dispatch nutzt es für jeden Lauf unter `--sandbox off`, und auf einem Host ohne verfügbares Backend nur für die eigenen Läufe des Serverinhabers; jeder andere Lauf wird dort abgelehnt. Für ein Terminal ist es die Host-Shell, die nur der Serverinhaber öffnen darf.

## Servergehostetes Terminal

Das servergehostete Terminal öffnet die Host-Shell nur für den [Serverinhaber](/de-DE/handbuch/konzepte/autorisierung/#der-serverinhaber). Alle anderen bekommen ein Terminal in der Sandbox, mit den Grenzen eines Agenten, in den Verzeichnissen des Arbeitsbereichs.

So wird das Backend für eine Sitzung gewählt:

| Angefragt | Serverinhaber | Alle anderen |
| --- | --- | --- |
| Nichts | Das Standard-Backend des Servers | Der Standard, wobei `none` durch `native` ersetzt wird |
| `none` (die Host-Shell) | Host-Shell | Abgelehnt: Die Host-Shell läuft auf dem Server ohne Sandbox |
| `native` | Native Sandbox, Inhaber-Profil | Native Sandbox, Agenten-Profil |
| `microvm` | Gekapselte VM | Gekapselte VM |
| Ein unbekannter Name | Abgelehnt | Abgelehnt |

- **Inhaber-Profil.** `$HOME` und das Arbeitsverzeichnis der Sitzung sind beschreibbar, das Netzwerk ist offen, und `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` und `~/Library/Keychains` sind leseverboten.
- **Agenten-Profil** (`memberTerminalSandboxConfig`). Dieselbe Richtlinie, unter der ein Agent in diesem Arbeitsbereich läuft: Schreibzugriffe bleiben im Arbeitsverzeichnis, einem privaten Lauf-Verzeichnis, `/tmp` und den Teilen von `$HOME`, in die ein Agent schreiben darf; Geheimnisse sind leseverboten; das Netzwerk ist die Ausgangs-Zulassungsliste des Agenten; Programme laufen nur aus dem Arbeitsverzeichnis und aus installierten Toolchains.
- Ein Terminal öffnet sich nur innerhalb der eigenen Verzeichnisse des Arbeitsbereichs. Ein Arbeitsverzeichnis außerhalb davon wird abgelehnt, nie gegen ein anderes getauscht.
- Nur die Person, die ein Terminal geöffnet hat, kann es lesen, Eingaben hineinschreiben, die Größe ändern oder es schließen. Für alle anderen sieht seine ID unbekannt aus.
- `microvm`, das ausdrücklich auf einem Host verlangt wird, auf dem kein Rig-Dienst läuft, schlägt fehl, statt zurückzufallen. Ein `microvm`-Standard auf einem solchen Host fällt auf `native` zurück und sagt das im Log.

Das Forge-Token, das nur lesen darf, und das Push-Gateway gelten nicht für Terminals: Das sind Sachen des Dispatch. Ist die Umhüllung nicht unterstützt, schlägt die Sitzung fehl, statt ein Sandbox-Badge auf einer Host-Shell-Sitzung zu zeigen.

## Netzwerkausgang

Wird eine Sandbox gestartet, setzen prozessinterne Proxys den ausgehenden Netzwerkzugriff durch, nicht Regeln einer Kernel-Firewall. Ein Lauf ohne Sandbox (jeder Lauf unter `--sandbox off` oder der Lauf des Serverinhabers auf einem Host ohne Backend) bekommt davon nichts: Ein Prozess, den er startet, erreicht das Netzwerk genau so, wie es der Server-Benutzer täte.

- Die Sandbox-Laufzeit betreibt einen HTTP/HTTPS-Proxy und einen SOCKS5-Proxy auf `127.0.0.1` im Prozess von `cc_server`, **ein Paar je eingeschränkter Sitzung** (`http_proxy.dart`, `socks_proxy.dart`). Gleichzeitige Läufe teilen sich kein Paar.
- Sandbox-Prozesse bekommen Proxy-Umgebungsvariablen (`HTTP_PROXY`/`HTTPS_PROXY` → der HTTP-Proxy, `ALL_PROXY` → der SOCKS-Proxy; `GIT_SSH_COMMAND` leitet Git über SSH durch den SOCKS-Proxy). Unter Linux ist der Netzwerk-Namespace nicht geteilt, die Proxys sind also der einzige Weg nach draußen; unter macOS teilt die Sandbox das Loopback des Hosts und spricht die Proxys direkt an.
- Der Zielhost jeder Verbindung wird gegen die Domain-Zulassungsliste der Sitzung geprüft; alles andere wird abgelehnt. Zwei Platzhalterformen, jede mit genau einem `*`: ein führendes `*.example.com` trifft jede Subdomain (einschließlich `a.b.example.com`), nicht aber die Apex selbst; ein mittleres Label `bedrock.*.amazonaws.com` trifft genau ein Label (`bedrock.us-east-1.amazonaws.com`, nicht `bedrock.evil.attacker.amazonaws.com`).
- Die Zulassungsliste wird je Sitzung aus der kuratierten Basis aufgelöst (`kBaselineAllowedDomains`: LLM-Anbieter, Git-Hosting, Paketregistries), plus die GitHub-Domains (`kGithubDomains`), plus `SandboxSpec.egressAllowlist`. Der Ausführungspfad übergibt nie zusätzliche Einträge in `egressAllowlist`, in der Praxis bekommt also jeder Lauf die Basis plus GitHub.
- Eine feste Verbotsliste (`kBaselineDeniedDomains`: Endpunkte für Cloud-Metadaten, Senken für Telemetrie) hat Vorrang vor allen Erlaubnissen.
- `networkEnabled: false` startet die Proxys je Sitzung trotzdem, die Zulassungsliste ist aber leer, also wird jede ausgehende Verbindung abgelehnt. Der Dispatch setzt den Wert beim Start des Laufs aus der Regel **Auf das Netzwerk zugreifen**: Verweigern schaltet das Netzwerk ab, Zulassen und Zuerst fragen lassen es an.

## SandboxSpec

Die Spezifikation, die an `SandboxPort.launch` geht:

| Feld              | Typ                                         | Beschreibung                                                                                                                                 |
| ----------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | Stabile Sitzungskennung (typischerweise die Bereichs-ID)                                                                                     |
| `workspaceId`     | `String`                                    | ID des zugehörigen Arbeitsbereichs                                                                                                           |
| `agentId`         | `String?`                                   | Agent, der gerade an die Sandbox gebunden ist, falls vorhanden                                                                               |
| `bindMounts`      | `List<SandboxBindMount>`                    | Mounts Host→Gast; die Sandbox sieht nur die hier aufgeführten Host-Pfade                                                                     |
| `networkEnabled`  | `bool` (Standard `true`)                    | Beim Dispatch aus der Regel für ausgehenden Netzwerkverkehr gesetzt (nur aus, wenn sie zu Verweigern auflöst). Ist es aus, starten die Proxys je Sitzung trotzdem, die Zulassungsliste bleibt aber leer, also wird jede ausgehende Verbindung abgelehnt |
| `egressAllowlist` | `List<String>` (Standard `[]`)              | Zusätzliche erlaubte Ausgangsdomains; Platzhalter sind möglich (`*.example.com`, dazu eine Form mit genau einem Label in der Mitte). Der Dispatch füllt das nie, ein umhüllter Lauf bekommt also die kuratierte Basis plus die GitHub-Domains |
| `guestWorkdir`    | `String?`                                   | Standard-Arbeitsverzeichnis in der Sandbox; einzelne `exec`-Aufrufe können es überschreiben                                                  |
| `mode`            | `Mode` (Standard `chat`)                    | Schneidet die Schreibregeln des Dateisystems: `chat` lässt Bind-Mounts beschreibbar; `review`, `plan` und `orchestrate` sind nur lesend       |
| `protectedPaths`  | `List<String>` (Standard `[]`)              | Host-Pfade, die in der Sandbox in keinem Modus beschreibbar sein dürfen                                                                      |
| `runnerStateDirs` | `List<String>` (Standard `[]`)              | Host-Verzeichnisse, in denen der Runner seinen eigenen Zustand hält, in jedem Modus beschreibbar (ein von Control Center verwaltetes `CLAUDE_CONFIG_DIR` ist derzeit das eine) |
| `execGrantRoots`  | `List<String>` (Standard `[]`)              | Von dir freigegebene Verzeichnisbäume, die unter macOS die Exec-Sperre für beschreibbare Verzeichnisse wieder öffnen. Linux ignoriert sie — bwrap hat keine `$HOME`-Exec-Sperre, die sich wieder öffnen ließe |

`protectedPaths` enthält die ursprünglich registrierten Repo-Checkouts, je Dispatch aus den Repos des Arbeitsbereichs aufgelöst. Agenten arbeiten ausschließlich in Copy-on-Write-Worktrees je Unterhaltung, die Originale dürfen aus der Sandbox heraus also nie beschreibbar sein — unter macOS ließe die pauschale Schreibfreigabe von Seatbelt für `$HOME` sie sonst über `bash` beschreibbar. Sie gehören in jedem Modus zur Menge der Schreibverbote für Geheimnisse, `chat` eingeschlossen.

Jeder Leseverbots- und Schreibverbotspfad wird in beiden Schreibweisen ausgegeben, der wörtlichen und der über den Symlink aufgelösten. Der Kernel prüft eine Verbotsregel gegen den aufgelösten Pfad, eine Regel gegen einen Symlink-Pfad greift also nie — und unter macOS ist das der Normalfall, nicht die Ausnahme, denn `/tmp` löst sich zu `/private/tmp` auf und `/var/folders/…` zu `/private/var/folders/…`. Einträge mit `*` oder `?` gelten als Globs und bleiben unverändert; ein Pfad, der sich nicht auflöst, bleibt, wie er geschrieben wurde.

## SandboxHandle

Zurückgegeben von `SandboxPort.launch`:

| Feld        | Typ                    | Beschreibung                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------- |
| `sessionId` | `String`               | Sitzungskennung                                                           |
| `backend`   | `SandboxBackend`       | Welches Backend gerade läuft                                              |
| `state`     | `SandboxState`         | Zustand im Lebenszyklus                                                   |
| `error`     | `Object?`              | Gesetzt, wenn `state` den Wert `error` hat                                |
| `details`   | `Map<String, Object?>` | Interne Verwaltungsdaten des Adapters (Arbeitsverzeichnis, PID, Profilpfad usw.) |

### SandboxState

| Zustand     | Beschreibung                                      |
| ----------- | ------------------------------------------------- |
| `created`   | Spezifikation angelegt, die VM ist noch nicht gestartet |
| `warm`      | Läuft und bereit für `exec`-Befehle               |
| `active`    | Führt gerade einen Befehl aus                     |
| `suspended` | Pausiert und als Checkpoint auf die Platte geschrieben, um RAM zu sparen |
| `destroyed` | Abgebaut; das Handle ist nicht mehr gültig        |
| `error`     | Start fehlgeschlagen — siehe `SandboxHandle.error` |

## Sandbox-Ereignisse

| Ereignistyp | Beschreibung                                                |
| ----------- | ----------------------------------------------------------- |
| `stdout`    | Standardausgabe der Sandbox                                 |
| `stderr`    | Standardfehler der Sandbox                                  |
| `exit`      | Der Sandbox-Prozess ist beendet (trägt `exitCode`)          |
| `starting`  | Die Sandbox startet                                         |
| `ready`     | Die Sandbox nimmt `exec`-Aufrufe an                         |
| `killed`    | Vom Host beendet (OOM, Zeitüberschreitung, manueller Stopp) |
| `violation` | Eine Sandbox-Richtlinie wurde verletzt (trägt eine `SandboxViolation`) |

## SandboxViolation

| Feld                  | Typ       | Beschreibung                                                               |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action`              | `String`  | Das verweigerte Verb (z. B. `file-read*`, `network-outbound`)              |
| `target`              | `String`  | Pfad oder Host, der Ziel der verweigerten Operation war                    |
| `raw`                 | `String?` | Rohe Logzeile, nützlich zur Fehlersuche                                    |
