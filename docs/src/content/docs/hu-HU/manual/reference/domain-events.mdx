## Eseménybusz

A `DomainEventBus` egy folyamaton belüli, szórásos publish/subscribe busz. A közzétevők a `publish(event)` metódust hívják; az előfizetők egy típusos `on<T>()` adatfolyamot fogyasztanak. Minden esemény implementálja a `DomainEvent` interfészt, és hordozza az `occurredAt` értéket.

**A busz a `cc_server` belsejében fut.** Minden közzétevő és minden élő előfizető ott él. Ezt a buszt egyetlen kliens sem látja — a szerver egy válogatott részhalmazt `notifications/*` JSON-RPC keretekként továbbít, előfizetőnként a munkaterületi tagság szerint szűrve.

| Mérőszám | Darabszám |
| --- | --- |
| Konkrét eseményosztályok | 53 |
| Forrásfájlok (`packages/cc_domain/lib/core/domain/events/`) | 14 (plusz `domain_event_bus.dart`) |
| Absztrakt alaposztályok, amelyeket soha nem teszünk közzé közvetlenül | 1 (`TaskLifecycleEvent`, lezárt hierarchia) |

Az alábbi katalógus minden eseménye ebben az egy könyvtárban él; máshol nincs deklarált domainesemény.

## PR- és átnézési események

Az első blokk magának a PR-nak az életciklusa. A második a **saját PR-ek figyelése**: jelzések egy olyan PR-ről, amelyet *Ön* nyitott meg; mindegyik hordozza a `forUserId` értéket, hogy a lekérdezés a szóban forgó személyhez irányíthassa őket, ne pedig szórva küldje.

| Esemény | Payload | Akkor tüzel, amikor |
| --- | --- | --- |
| `PullRequestPublished` | `prId`, `workspaceId`, `repoOwner`, `repoName` | Az ügynök megnyit egy PR-t |
| `PullRequestStatusChanged` | `status`, `workspaceId`, `prId?`, `repoFullName?`, `prNumber?` | A PR-t összefésülték/lecsukták/megnyitották/újranyitották/jóváhagyták |
| `PrMerged` | `prId`, `workspaceId`, `agentId` | A PR össze van fésülve — egy szűk, csak az összefésülésre vonatkozó jelzés, amelyet elemzés és értesítések céljára tartunk meg |
| `PrReviewRequested` | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle` | A GitHub a szerver felhasználójának átnézését kéri (értesítésfigyelő, `review_requested`) |
| `PrMentioned` | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle` | A szerver felhasználóját megemlítik egy PR-ben (értesítésfigyelő, `mention`) |
| `ExternalPrMerged` | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`, `mergedByLogin?` | Egy kívülről követett (nem ügynöki) PR összefésülése, amelyet a GitHub értesítésfigyelője észlel; a `prMerged` értesítési kategóriára képeződik le |
| `ExternalPrDetected` | `repoOwner`, `repoName`, `prNumber`, `prTitle`, `author`, `workspaceId?` | Lekérdezéssel talált, nem ügynöki PR — csak pipeline-hoz (az `external_pr_welcome` pipeline-t vezérli), nem kelt értesítést |

Csak akkor indul, ha létezik átnézés a lecserélt commitra, így jelzés marad, nem pedig pushonkénti ping |

## Feladat-életciklus-események

Az egységes feladat-életciklus-adatfolyam — egyetlen indított ügynökfuttatás, amelyet a futásnapló-azonosítója szerint kulcsolunk. Minden esemény hordozza a `taskId`, a feladatonként monoton `seq`, a `workspaceId?`, az `agentId?` értéket és egy `phase` mezőt; az alábbi sorok csak a további mezőket sorolják fel.

| Esemény | Payload | Akkor tüzel, amikor |
| --- | --- | --- |
| `TaskDispatched` | — | A feladatot végrehajtásra átadják egy háttérrendszernek |
| `TaskRunning` | — | A feladat elkezdett kimenetet előállítani |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | A feladat parkol — egy másik feladat birtokolja a szükséges, lemezen lévő elérésiút-zárat |
| `TaskProgress` | `note?` | Futás közbeni előrehaladási ellenőrzési pont |
| `TaskMessage` | `messageType`, `content` | Adatfolyamban érkező üzenet (text/thinking/tool_use/tool_result/error); a `progress` fázis alatt jelentve |
| `TaskCompleted` | `summary?` | A feladat sikeresen befejeződött |
| `TaskFailed` | `errorMessage` | A feladat hibával fejeződött be |
| `TaskCancelled` | — | A feladatot a befejezés előtt megszakították |

A `TaskPhase` felsorolásnak van egy `queued` tagja is, de várakozó eseményt semmi sem tesz közzé — nincs `TaskQueued` osztály. Egy feladat első megfigyelhető kerete a `TaskDispatched`.

## Állomásesemények

| Esemény | Payload | Akkor tüzel, amikor |
| --- | --- | --- |
| `RigClosedEvent` | `workspaceId`, `rigId`, `reason` | Egy állomás eltűnt, a lezárási okával együtt; a fogyasztók csak a `backendFailure` esetén cselekszenek — minden más ok kért, vagy egy `RigReaped` esemény kíséri |
| `RigControlChanged` | `workspaceId`, `rigId`, `controller?` | Egy ember kizárólagos vezérlést vett át egy állomás fölött, vagy visszaadta azt (elengedéskor a `controller` null — az esemény nem rögzíti, ki engedte el) |

Egy állomás **megnyitása** nem esemény. Az indítás befejeződik, és az állomás sora kész állapotra billen; semmi sem kerül közzétételre, így nincs `RigOpened`, amelyre elő lehetne fizetni.

## Aldomainek, amelyeknél egyáltalán nincsenek események

Több alrendszer, amely kívülről eseményvezéreltnek látszik, valójában nem az. Azért soroljuk fel őket itt, mert a hiányuk olyan tervezési döntés, amelyet érdemes ismerni, mielőtt hookot kezdene keresni:

| Aldomain | Hogyan mozog helyette az állapot |
| --- | --- |
| Memória | A `record_memory_fact` és társai írnak és visszatérnek; az előhívás olvas. Semmi sem tesz közzé tényt vagy ütközést |
| Orchestráció | A javaslat, annak jóváhagyása és a generált pipeline-futtatás sorok és RPC-hívások |
| Tervdokumentumok | A `submit_plan` ír egy revíziót; a jóváhagyás orchestrációt hoz létre. Egyik sem kerül bejelentésre |
| Artefaktumok | A `publish_artifact` / `revise_artifact` közvetlenül írja a revíziókat |
| Jóváhagyások | Az eszkalációt a jóváhagyási munkafolyamat-szolgáltatás kezeli |
| Jegyszinkronizáció | A szolgáltatói koordinátor az előbbi jegyeseményekre fizet elő; a bejövő webhookok közvetlenül kerülnek alkalmazásra |
| Naptárfrissítés | Egy szinkronizálás felvesz vagy frissít eseményeket, és a kliens újraolvassa őket; nincs frissítési szórás |
| Worktree-összefésülések | A `worktree_merge_log` rögzíti őket, és onnan olvashatók |

Az élő toastok az alábbi wire-frame-ekből érkeznek.

## Az értesítések leképezése

A szerveren a `NotificationFeedRecorder` és a `RemoteEventForwarder` alakítja ezeket az eseményeket `notifications/*` wire-frame-ekké (`notification_wire.dart`). A kliensen az `RpcNotificationMapper` → `mapNotificationFrame` alakít egy keretet `AppNotification` értékké.

Pontosan **tizenhat** értesítési kategória van. Több esemény egynél több wire-metódusra képeződik le, mert a keret az élt hordozza (meghiúsult vagy helyreállt), míg a kategória a kérdést („mit tesz a CI?”).

| Kategória | Forrásesemény | Wire-metódus |
| --- | --- | --- |
| `newMessage` | `MessageReceived` | `notifications/message_received` |
| `agentRunCompleted` | `AgentRunCompleted` | `notifications/agent_run_completed` |
| `ticketAssigned` | `TicketAssigned` | `notifications/ticket_assigned` |
| `ticketStatusChanged` | `TicketStatusChanged` | `notifications/ticket_status_changed` |
| `pullRequestPublished` | `PullRequestPublished` | `notifications/pr_published` |
| `prMerged` | `PrMerged` | `notifications/pr_merged` |
| `prMerged` | `ExternalPrMerged` | `notifications/external_pr_merged` |
| `prMentioned` | `PrMentioned` | `notifications/pr_mentioned` |
| `prMentioned` | `PrCommentMentioned` | `notifications/pr_comment_mentioned` |
| `reviewRequested` | `PrReviewRequested` | `notifications/pr_review_requested` |
| `reviewStale` | `ReviewBecameStale` | `notifications/review_stale` |
| `prMergeReadiness` | `PrMergeReadinessChanged` | `notifications/pr_ready_to_merge` / `pr_merge_blocked` |
| `prReviewDecision` | `PrReviewDecisionChanged` | `notifications/pr_approved` / `pr_changes_requested` / `pr_review_dismissed` |
| `prChecksStatus` | `PrChecksStatusChanged` | `notifications/pr_checks_failed` / `pr_checks_recovered` |
| `prThreadActivity` | `PrThreadReplied` | `notifications/pr_thread_replied` |
| `prThreadActivity` | `PrThreadResolved` | `notifications/pr_thread_resolved` |
| `meetingStartsSoon` | `MeetingStartingSoon` | `notifications/meeting_starting_soon` |
| `calendarAuthExpired` | `CalendarAuthExpired` | `notifications/calendar_auth_expired` |
| `rigStatusChanged` | `RigControlChanged` | `notifications/rig_control_changed` |
| `rigStatusChanged` | `RigReaped` | `notifications/rig_reaped` |
| `rigStatusChanged` | `RigClosedEvent` | `notifications/rig_closed` |

Az állomás átvételéről szóló keretet nem kézbesítjük vissza annak, aki átvette a kormányt, az elengedés szűretlen (az esemény nem rögzíti, ki engedte el), és csak egy `backendFailure` lezárás állít elő `rig_closed` keretet — a többi ok vagy kért, vagy már lefedi a begyűjtési keret.

Az öt saját PR-höz tartozó kategória hordozza a `forUserId` értéket, így azok a szerzőhöz jutnak el, nem a munkaterület minden tagjához.

A `RemoteEventForwarder` ezenfelül továbbítja a `TicketReassigned` eseményt `notifications/ticket_reassigned` néven, és minden `TaskLifecycleEvent` eseményt `notifications/task_<phase>` néven. Egyik sem képeződik le értesítési kategóriára — élő felületet vezérelnek, nem az értesítési központot. A tagsági események nem kerülnek továbbításra keretként: érvénytelenítik a továbbító gyorsítótárát, a munkamenet-gazdák pedig eldobják az eltávolított tag munkaterület-előfizetéseit.
