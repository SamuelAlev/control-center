## 一次審查的形態

一次 AI 審查，就是針對一個處於開啟狀態的 pull request 執行一次預置的 `pr_review`
管線。管線會開啟該 PR 的審查空間，派出多個審查代理，在該空間的隔離檢出中閱讀 diff；
每個審查者把自己的發現項以結構化的 **審查節點** 形式提交，接著由主導代理匯總成一份
走查，最後由終結器計算出一個判定：**Ship**、**Hold** 或 **Block**。管線絕不會做的一件事
就是發佈 —— 向 GitHub 發帖是一個獨立的步驟，必須由人刻意執行。

本頁其餘部分會說明各個組成部分，以及它們為何被設計成這樣。

## 每個 PR 一個審查空間

PR 的審查上下文是一個訊息空間 —— 模式為 `review`，類型為 `pr` —— 並透過
**審查空間關聯** 與該 pull request 連結。它的建立具冪等性：PR 頁面、審查管線與各聊天
介面都經由同一條程式碼路徑，解析該 PR _唯一_ 的底層空間，因此負責審查 PR 的範本與
開啟該 PR 的人，絕不會落在兩個不同的房間、看著兩份不同的檢出。

該空間的隔離工作樹會把 PR 檢出至其 head ref。同一個房間也意味著同一份檢出：所有審查者
都在同一個空間中工作，而不是各自取得一份工作區的複本。

每個審查者都會在這個空間內自己的具名資料流中發文，而發現項是 `review_node` 訊息，而非
一般的散文式文字。最後在整個空間範圍內匯總是有意為之 —— 若只根據單一討論串的發現項
計算判定，那無異於悄悄只對一個審查者作出判定。

該關聯帶有一條狀態階梯 —— `requested` → `in progress` → `awaiting approval` →
`completed` —— 正是它決定 PR 檢閱分頁上的 **發佈到 GitHub** 能否使用。

## 審查級別

審查的深入程度是一項工作區政策，共分三個級別，在 **設定 → 工作區 → 一般** 的
**工作區政策** 卡片上設定：

| 級別       | 派出的審查者                                  | 報告方式                     |
| ---------- | --------------------------------------------- | ---------------------------- |
| `light`    | 僅工程師                                      | 只報告真正重要的內容         |
| `balanced` | 工程師、QA、架構師（預設）                    | 常規的一遍檢查               |
| `thorough` | 全部五個，包括保安與效能                      | 不作任何降級                 |

級別同時撥動兩個旋鈕：一是派出哪些審查者，這由管線範本的 `runWhen` 狀態閘門強制執行，
而不是靠提示詞措辭 —— 提示詞措辭可以不理，閘門不行；二是低於閾值的發現項呈現在何處。
這兩個旋鈕都不會刪除任何發現項：報告較少的級別，提交的發現項數量完全相同，只是把其餘
部分歸為一組。

保安與效能這兩遍檢查會重用預置的架構師與工程師代理，而不是引入新的代理。專長體現在
派發審查者時所附的任務簡述，而不是每個軸向各設一個獨立代理 —— 每個軸向一個代理，只會
讓每個工作區多出五筆記錄，卻換不來任何額外能力。審查者的選擇從不檢查 diff 的語言或
領域。

## 審查節點：發現項是資料，不是散文

以 `add_review_node` 提交的發現項，會成為該 PR 上的一個 **審查節點** —— 檢閱分頁所
呈現的正是它，判定正是根據它計算出來，而「發佈到 GitHub」正是把它變成行內評論。只回傳
散文式文字的審查者，會讓管線執行看似成功，審查介面卻空無一物；真正承重的是提交這個
動作。

每個節點包含：

| 欄位       | 值                                                                   |
| ---------- | -------------------------------------------------------------------- |
| 類型       | `bug`、`suggestion`、`recommendation`、`question`、`ticket`           |
| 優先級     | P0（嚴重）→ P3（細微）                                                |
| 分診三元組 | 類別（`security`、`stability`、…）、嚴重程度、工作量                  |
| 錨點       | 檔案路徑、起始行與結束行                                             |
| 修正承載   | 建議的替換行、可選的 diff、可選的修正提示詞                          |
| 信心       | 一個 [0, 1] 分數                                                     |
| 推理過程   | 在發現項之前寫下的分析                                               |

有兩個細節是有意為之。只有當審查者提供了確切的替換行時，才會提供一鍵 GitHub 建議 ——
從 unified diff 推斷替換行，出錯時悄無聲息，而把錯誤推斷一鍵提交，比根本不提供按鈕更糟。
另外，`add_review_node` 的 schema 把 `reasoning` 放在發現項之前，因此按 schema 順序填充
物件的模型，會先寫出分析。該欄位是可選的：省略它不會令節點被拒收。承載內容格式錯誤的
節點會直接消失，而不會污染整份審查。

## 同行共識

節點會經歷 `open` → `consensus-ready` → `resolved` 或 `dismissed` 的狀態流轉。中間
這一步是整套模型的核心：**發現項必須由同行審查者確認才會升級，而代理永遠不能確認自己
提出的發現項。** MCP 工具 `publish_review_to_github` 與 RPC 的預設行為仍然只發佈經
同行確認的發現項。而檢閱分頁的 **發佈到 GitHub** 按鈕則會送出所有仍然未解決的發現項。

這條規則在三個各自獨立的地方強制執行 —— 確認工具、終結器與發佈器 —— 因此即使其中任何
一個的呼叫方有 bug，規則依然成立。所有狀態變更都經由同一個服務處理，這正是狀態能夠有
意義的原因：在此之前，兩條各走一半的路徑，可能會對同一個發現項是否已解決得出不一致的
結論。

當審查者意見分歧時 —— 同一個檔案與行號、優先級相差兩級或以上，或者一個稱之為 `bug`
而另一個稱之為 `suggestion` —— 這種分歧會顯示在發現項清單上方。那正是審查者意見出現
分歧、而人的判斷最有價值的地方。

忽略一項發現項，亦會以低信心向記憶域寫入一條軟性抑制事實 —— 一次忽略只是一種偏好，
而不是一條規則。

## 群體：審查圍繞什麼分組

審查運算這一遍會把 PR 中變更的檔案，按程式碼圖劃分為若干 **群體**：變更的檔案對應到
它們所觸及的符號，符號再對應到相連的組件，而群體則按影響範圍排序。一個群體帶有引導式
閱讀順序、圖表與洞見，而不是一份平鋪的檔案清單。

有兩條誠實性規則塑造了這一點。群體鍵由內容推導而來，並在多次 push 之間保持穩定，因此
發現項與審查進度能安然度過 rebase 或 force-push，而不會變成孤兒。另外，當程式庫沒有
程式碼索引時，分組會退回使用純路徑，並明確說明這一點 —— 這種後備做法絕不會假裝出語意
上的信心。

## 審查軸向與閘門

除了審查者的發現項之外，一次審查還會累積 **軸向結果**：六個軸向，分為兩類。

| 軸向                      | 類別          | 來源                                       |
| ------------------------- | ------------- | ------------------------------------------ |
| `correctness`、`security` | 由 token 驅動 | 審查者自己的發現項                         |
| `testGap`                 | 由 token 驅動 | 審查者的發現項                             |
| `visual`、`apiContract`   | 確定性        | 無需消耗 token 即可計算                    |
| `performance`             | 確定性        | 僅有枚舉 —— 產品中沒有任何東西會計算出結果 |

一個軸向的判定結果為 `pass`、`warn`、`fail`、`partial` 或 `unavailable` —— 而只有
`pass` 或 `warn` 能通過閘門。`fail`、`partial` 與 `unavailable` 之間的區別是承重的：
受閘門約束的軸向若無法完成或根本無法執行，會扣住總體判定不放行，而不是讓它通過。
**證據從缺，絕不會轉化為閘門綠燈。**

有些軸向是有意只作參考。由群體推導出的測試缺口軸向，看不到依賴注入或工廠的覆蓋情況
—— 從它的角度看，一個沒有索引但測試套件完備的程式庫，和一個完全沒有測試的程式庫
一模一樣，因此無論聲稱哪一種都是說謊；它只會出現在儀表板上，不參與閘門。由 token 驅動
的軸向只作參考，因為發現項的優先級已經主導了判定，再憑它們施加閘門就是重複計算。

## 判定

終結器會就狀態為 `open` 或 `consensus-ready` 的發現項計算判定：

- 任何信心 ≥ 0.7 的 P0 發現項 → **Block**
- 否則，任何 P0（低信心）或任何 P1 → **Hold**
- 否則 → **Ship**

該判定帶有一個總體信心，由各參與貢獻的信心之離散程度推導而來 —— 一致會提高它，分歧會
降低它。

主導（CEO）代理的匯總是一遍編輯整理，而不是重新羅列：手寫一份發現項的第二副本，正是
那種會逐漸偏離真實版本的東西。重複的發現項會被降級，而不是重複呈現 —— 多個審查者被
指向同一個 diff，彼此的職責範圍刻意重疊，因此同一個缺陷三次到達終結器，恰恰說明系統
運作正常；而把它發佈三次，則是系統把自己的架構洩漏進讀者的收件箱。在重新審查時，發現
項會被取指紋並與上一輪做 diff，因此浮現出來的是真正的差異。

最後，各軸向會加入，而它們只會令判定變得 **更** 嚴重：受閘門約束且失敗的軸向會強制
給出 Block —— 它不會被發現項投票推翻 —— 而受閘門約束、無法完成的軸向則至少會強制給出
Hold。

## 發佈始終由你掌握

管線有意不向 GitHub 發帖；發佈由使用者把關，因此一次審查絕不會重複發佈。當你按下
**發佈到 GitHub** 時：

- 會提交一條 GitHub 審查。已解決或已忽略的發現項會被略過。該按鈕會發佈所有仍然未解決
  的發現項（`selection: all_open`）。MCP 工具 `publish_review_to_github` 的預設行為
  仍然是只發佈經同行確認的發現項（`consensus`）。
- 錨定到檔案與行號的發現項會變成行內評論；其餘一切則歸入摘要正文，每一項都帶有
  「— Control Center AI review」頁腳，令來源一清二楚。
- 發佈時，錨點會根據 PR 的 _當前_ diff 重新驗證。對已被改寫的程式碼留下評論，是審查者
  可能留下最破壞信任的東西；如果 GitHub 仍然拒絕某個行內錨點，整份審查會重新送出，
  並把每一項發現項歸入正文，確保沒有任何東西被悄悄丟棄。
- **Block** 判定會以 `REQUEST_CHANGES` 提交；**Hold** 以 `COMMENT` 提交；**Ship** 則由
  按鈕以 `APPROVE` 提交（`approve_on_ship: true`）。除非你傳入 `approve_on_ship`，
  否則 MCP 工具會把 Ship 保留為 `COMMENT`。
- 審查會以伺服器的應用程式身分發佈。究竟是誰按下發佈，會為角色閘門與稽核日誌記錄
  下來；發佈者並不是 GitHub 上的作者。

發佈會宣告 `prPublish` 動作類別，因此護欄檢查點會像對待任何變更類操作一樣對它施加閘門
—— 它預設會彈出確認提示，並在未連接任何核准人時以失敗關閉的方式處理。
參見[護欄](/zh-HK/手冊/概念/護欄/)。

## 審查者可以做什麼

審查代理運行於 `review` 模式：一個唯讀沙箱，以及一份精心篩選的工具允許清單，涵蓋
發現項、評論、工單與同行評審 —— 但不包括任何變更操作。審查者無法修正它所批評的程式
碼；它可以附上一個建議修正，由人來套用。當某個代理仍然試圖動手時，該模式的拒絕訊息會
叫它先完成審查定稿，再讓使用者依據已發佈的摘要採取行動。
