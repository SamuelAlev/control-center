內建執行框架所發出的每一個請求都有兩件事成立：工具定義是其中最大的一筆固定成本，而它們幾乎都不會被用到。本頁說明 Control Center 如何處理這件事，以及為何答案不是單純「少送一些工具」。

## 問題在於注意力，而非位元組

Control Center 自有約 160 個工具。若完整送出，這些定義會在**每次請求**中一併攜帶——這是任何壓縮都無法觸及的成本，因為工具定義與對話位於請求中互相獨立的部分。

token 帳單是最明顯的抱怨，而有了提示快取之後，它也是較小的一項。真正的成本在於**選擇準確度**。已發表的工具呼叫評測一致顯示，當上下文中的工具數量約在 30–50 個以內時，模型能可靠地選對工具，超過之後就會逐步變差。公認的原因並非 token 數量，而是**語意重疊**：一旦工具目錄中有多個描述讀起來雷同的工具，模型就是在相似者之間做選擇，而不是在回想某項能力。

在約 160 個工具的情況下，代理在每一個回合都遠遠超出這個區間——包括許多它只需要讀取一個檔案的回合。

## 一個小型直接工具集

因此，一次執行會看到兩類內容：

- 一個**直接**集合——約十五個工具，每次請求都連同完整 schema 一併送出；
- 其餘所有工具的**名稱索引**，按「Tickets and projects」或「Memory and knowledge」之類的標題分組，整個目錄只花費數百個 token。

在測試所建立的註冊表上量度，內建代理的標準聊天工具共有 14 個工具定義：連同 `repl` 約 16.5 KB（其中 `repl` 約佔 4 KB，其定義不得超過 4,096 位元組），在無法運行指令碼的伺服器上則為 14 個定義、約 13 KB。這只是一個介面的量度，並非每個安裝的情況。其餘所有工具都由指令碼呼叫，或在首次使用時載入。

直接工具集是大多數執行在最初幾個回合會用到、且執行絕不應需要去找的工具：`read`、`write`、`edit`、`search`、`find`、`bash` 與 `read_output`；`ask_user` 與 `task`；`todo_write`、`search_memory` 與 `send_message`；以及目前[模式](/zh-HK/手冊/概念/模式/)為交出結果而必須呼叫的動詞。模式自身的輸出動詞一律屬於直接工具，執行絕不應為了找出那個產生其交付成果的呼叫而四處尋找。工具要因為大多數執行都會用到而佔一席位，而不是因為它被使用時很重要：工具集中的每個名稱，在每個執行的每一回合都是一份定義。

### 其餘工具由指令碼觸達

當伺服器能夠運行指令碼時，每次執行還會有[`repl`](/zh-HK/手冊/概念/程式碼模式/)，排在列表最前。其餘工具目錄的規則如下：

- 可由指令碼呼叫的工具，以**僅指令碼**方式觸達：它列於名稱索引中，`repl` 指令碼先以 `searchTools()` 或 `describeTool()` 查找，再以 `tools.<name>(args)` 呼叫它，直至伺服器無法運行該執行的指令碼，屆時它改為在首次使用時載入（見[指令碼無法運行時](/zh-HK/手冊/概念/程式碼模式/#指令碼無法運行時)）；
- 不可由指令碼呼叫的工具（`eval`、`task`、核准、委派及其他少數工具）會**隨需載入**：它在首次使用時載入，如下文所述；
- 當有任何工具被隨需載入時，便會加入 `search_tools`。

沒有 `repl` 的執行會取得同一套直接工具集，其餘所有工具都會被隨需載入。

直接工具集無論有沒有 `repl` 都相同，這是刻意為之。代理只需認識一個介面，每個請求的開頭都是同一批工具、按同一次序排列，而加入 `repl` 不會改變代理原本依賴的任何東西。

它省下的是：僅指令碼工具的 schema 永遠不會傳送給提供者，因此直接工具集以外、約一百個工具只需花費其名稱。一個需要其中十個工具的指令碼，不必為其中任何一個的 schema 付費，其中間結果也永遠不會進入上下文。

它的代價是：直接工具集以外的工具需要透過指令碼呼叫，而該指令碼必須先查閱工具的引數。對於一次快速的呼叫，這是直接呼叫本不需要的額外一步。這正是大多數執行在最初幾個回合會呼叫的工具仍保留為直接工具的原因。

### 隨需載入不等於不可用

這正是讓這個設計不僅便宜、而且安全的部分。**隨需載入的工具從第一回合起就可以呼叫。**被扣住的只是它的 schema。

代理會在提示中看到這個名稱。如果它直接呼叫該名稱，執行框架會在同一步內載入 schema 並執行該工具——不會報錯，也不需要來回一趟。模型無需知道這個工具曾經被「卸載」過。

當代理知道任務卻不知道名稱時，`search_tools` 會接受一段自然語言描述（「assign a ticket to someone」），對本次執行的整個工具介面排序，並回傳相符的項目，*且已載入它們的 schema*，這樣下一回合就能直接呼叫其中一個。只能由指令碼呼叫的相符項目，則改為回傳如何由指令碼呼叫它，除非該執行的指令碼已無法運行：那時它會像其他相符項目一樣載入。如果搜尋一無所獲，它會如實說明，並建議換個說法或擴大搜尋範圍——這是刻意為之，因為把空搜尋結果理解成「這項能力不存在」的代理，會自己編造一個替代品，而不是再找一次。

`search_tools` 只存在於內建執行框架中。外部 MCP 用戶端改用 `search_tool_bm25`，它對同一個索引排序，但只描述相符的項目——這些用戶端已經從 `tools/list` 收到所有 schema，因此沒有東西需要載入。

### 工具介面絕不會做的事

隨需載入與指令碼都是在模式的工具篩選**之後**套用的，絕不會取代它。它隱藏 schema，卻無法顯露模式已經拒絕的工具。已載入的工具與指令碼的呼叫，仍會像直接呼叫一樣通過核准提示與[操作護欄](/zh-HK/手冊/概念/護欄/)，而且兩者都無法觸達一個打從一開始就不在本次執行工具介面上的名稱。

外部用戶端看到的 MCP 工具介面**不會**隨需載入。`tools/list` 會回傳完整目錄，因為 MCP 用戶端會拿工具名稱與自己快取的清單核對，對未列出的名稱直接拒絕，從不詢問伺服器，所以「隱藏但可呼叫」的工具根本無法觸達。隨需載入存在於執行框架之中，因為在執行途中載入工具，是執行框架確實做得到的事。

透過 Control Center 的 MCP 端點連接其工具、且伺服器能夠運行指令碼的代理執行，是唯一的例外。其 `tools/list` 包含 `repl`、直接工具，以及指令碼不可呼叫的每一個工具；其餘工具則由指令碼呼叫。直接呼叫其中一個時，回覆會說明如何改由指令碼呼叫它。

### 關閉隨需載入

`--tool-deferral=off`（或 `CC_SERVER_TOOL_DEFERRAL=off`）會關閉隨需載入：沒有 `repl` 的執行會完整取得每個被准入的工具，而有 `repl` 的執行會完整取得指令碼不可呼叫的工具，其餘工具則只能由指令碼呼叫。參閱 [`cc_server` CLI 參考](/zh-HK/手冊/參考/cc-server-cli/)。

## 提示快取

代理的工作負載是偏斜的：它們一個回合接一個回合地送出龐大的提示、收到很小的回答，而且每次前綴都相同。供應商會快取這個前綴，而一次快取讀取的代價大約是新算一次的十分之一。因此，快取命中率是執行框架的首要特性，而不是一項優化——在 Anthropic 上它還能換來吞吐量，因為已快取的 token 不計入每分鐘的輸入上限。

快取的依據是精確的前綴比對，由此得出一條支配性規則。

### 絕不重寫已經送出的內容

任何有變動的位元組，都會使快取從該處起失效。因此執行框架只會**追加**：新訊息加在末端，而新啟用的工具 schema 是*追加*在已快取的工具區塊之後，而不是合併進去。正是這個順序讓啟用變得便宜——已快取的前綴保持完全一致，這次執行只需為剛剛載入的 schema 付費。

這個循環也會裁剪較早回合中過期的工具輸出，以回收上下文。它會等到可回收的量足夠多、值得重寫時才動手，因此裁剪是一次罕見的深度重寫，而不是持續不斷的快取未命中。

### 斷點放在哪裏

供應商允許的快取標記數量有限，Control Center 會有意識地把它們花在刀口上：

| 標記                         | 涵蓋範圍                           | 存活期   |
| ---------------------------- | ---------------------------------- | -------- |
| 最後一個**直接**工具         | 工具區塊                           | 1 小時   |
| 最後一個系統區塊             | 工具 + 系統提示                    | 1 小時   |
| 上一回合的尾端               | 截至上一次請求的歷史紀錄           | 5 分鐘   |
| 目前回合的尾端               | 完整歷史紀錄                       | 5 分鐘   |

最後兩個是一對滾動標記，而它們成對出現的理由很細微：快取查詢會往回搜尋有限數量的區塊，尋找較早某個請求所存入的內容。一個並行執行許多工具的單一回合，可能產生比這個窗口更多的區塊，此時其中一個尾端標記就會無聲地未命中，請求便得付全額費用，而回應中沒有任何資訊說明這一點。標記出上一次請求停止的確切位置，能讓命中成為結構性的，而不是一場競速。

工具加系統的那段前綴採用較長的存活期，因為它在整次執行中都是恆定的、會被每一次形態相同的執行與子代理共用，也因為計時是從請求*開始*的那一刻起算——一個持續串流數分鐘的回合，在下一請求形成之前就已經耗掉了短窗口的大部分時間。

### 子代理共用同一個前綴

同一類型的子代理會產生逐位元組完全相同的前綴，因此它們應該讀取同一個快取項目，而不是各自寫入自己的。但一個項目要等到寫入它的那個請求開始回應之後才可讀取，所以一次過全部啟動的扇出，會讓每個子代理都為它們共同分享的前綴付上額外代價。

執行框架會讓某個形態的第一個子代理先啟動，然後在它開始串流的那一刻放行它的同伴。這個等待是有界的：第一個子代理慢，代價只是一次快取命中，絕不會賠上整個扇出。基於同樣理由，每個子代理無論其設定檔為何，都會拿到同一組直接工具——按設定檔分別調整只會無謂地切碎共用的前綴，因為設定檔早已決定了子代理可以呼叫什麼。

## 觀察它如何運作

這兩半都是可觀察的，而不是靠假設：

- 對話上的**上下文瀏覽器**會報告直接工具、隨需載入索引，以及每個被扣住的 schema *原本會*花費多少；這些都由真實執行所用的同一條程式碼路徑產生。
- 每次執行都會記錄它載入了哪些隨需載入工具，以及是什麼觸發了載入，因此一次一無所獲的搜尋會以檢索未命中的形式顯露出來，而不會消失在一個悄悄去做了鄰近事情的代理身上。
- 可觀測性會把**快取率**報告為快取讀取量對所處理全部提示 token 的比例，其中包含快取寫入——一個不斷重建自身前綴的執行會得到較低的分數，而不會像從不需要快取那樣得分。
