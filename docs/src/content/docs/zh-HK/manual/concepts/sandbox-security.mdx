:::note[作業系統沙箱觸及與不觸及之處]
`cc_server` 會在開機時探測主機，並在有沙箱可用時，以作業系統原生的沙箱包裝代理指令的執行 —— macOS 上是 Seatbelt，Linux 與 WSL2 上是 bubblewrap（需要在 `PATH` 上有 `bwrap` 與 `socat`）。若沒有後端 —— Windows，或缺少這些工具的 Linux 主機 —— 只有伺服器擁有者的代理執行會啟動，且不受沙箱約束，其他人的執行則會被拒絕。伺服器擁有者也可以改以 `--sandbox off` 啟動伺服器，這會讓每位成員的代理都在該機器上不受約束地執行。啟動日誌會說明你處於哪種情況；參見[沒有沙箱的主機上的代理](#沒有沙箱的主機上的代理)。

有兩個缺口不受沙箱覆蓋，值得記住：

- 內建執行框架的**行內檔案工具**（`read`、`write`、`edit`、`apply_patch`、`search`、`find`、`search_files`）在伺服器行程內執行，因此只有 `bash` 受到包裝。約束它們的，是工具本身的路徑限制，加上動作護欄。
- **Claude Code 是以 `--dangerously-skip-permissions` 啟動的**，因為非互動式的 `claude -p` 否則會永遠卡在自己的提示上。因此它的檔案呼叫不受 Control Center 的護欄管制，shell 命令也只經過一個讀取命令列的鉤子 —— 圍住它們的界線是作業系統沙箱。
  :::

## 為何隔離在此重要

代理會代你讀取檔案、執行 shell 指令，並呼叫外部 API。你真正在意的失敗很少出於惡意 —— 而是代理看錯路徑、改寫了你的工作副本，或推送了一條你還沒審查完的分支。所以產品必須回答的問題不是「代理是否可信」，而是「它出錯時的波及範圍有多大」。

Control Center 以分層的方式回答這個問題，而這些分層刻意彼此獨立。缺了一層，其餘各層仍然成立。這點很重要，因為最外層 —— 作業系統沙箱 —— 是唯一有條件的：它取決於主機是否提供後端，而在 Windows 上沒有任何主機提供。在它缺席之處，伺服器不會悄悄地在沒有它的情況下執行所有人的代理。

## 沒有沙箱的主機上的代理

伺服器會在開機時決定代理如何在其機器上執行，並一直沿用該決定，直到重新啟動為止：

- **有沙箱。** 主機有後端，且沙箱為開啟。每次執行都會被包裝。
- **關閉。** 伺服器擁有者以 `--sandbox off` 啟動了伺服器。每位成員的代理都會在這部機器上不受約束地執行。這是擁有者為所有使用該伺服器的人所作的選擇，而不是針對單次執行的設定。
- **無法使用。** 沙箱為開啟，但主機沒有後端。只有當負責該次執行的人是伺服器[擁有者](/zh-HK/手冊/概念/授權/#伺服器擁有者)時，執行才會啟動：即提出請求的人；若為排程、webhook 或其他自動化，則是該自動化所綁定的人。其他人的執行會在憑證被鑄造或行程啟動之前被拒絕，並顯示「此伺服器沒有沙箱，因此只有其擁有者可以在此執行代理。擁有者可以安裝沙箱，或為所有人關閉沙箱功能。」

這個理由在於機器的擁有權。不受約束的代理可以做伺服器使用者帳戶能做的任何事，因此除非擁有者為所有人另行決定，否則只有擁有該帳戶的人才會執行代理。Windows 伺服器永遠處於「無法使用」的情況。Linux 另有一個小問題，見[沙箱後端參考](/zh-HK/手冊/參考/沙箱後端/#linuxbubblewrap)：即使已安裝 bubblewrap，原生派發目前在那裡仍會封閉式失敗。

同樣的規則也涵蓋那些替你啟動行程的較小事項：

- **透過 ACP CLI 執行的快速輔助程式**：對話標題、`/btw`、`/handoff` 與 `/goal`。當伺服器為代理加上沙箱時，它們會在沙箱內、以自己的工作階段執行。在 `--sandbox off` 之下，它們不受約束地執行。若沒有可用的沙箱，它們只會為伺服器擁有者負責的請求執行；對其他人則會略過，因此不會產生任何標題，而側邊問題會回報內容合成器沒有可用的執行器。不啟動任何工具的輔助程式不受影響。
- **Review Studio 視覺檢查中的 pull request golden 測試**遵循同一規則。
- **執行中的工具程序與 `bash`** 絕不會退回到主機。若伺服器設定為為代理加上沙箱，卻沒有可供某次執行使用的沙箱，它們就會被拒絕。

## 實際上以什麼約束代理

無論有無沙箱，在任何主機上，都有五件事約束著代理執行。它們全都不是核心邊界；但它們全都真實有效。當主機提供後端時，作業系統沙箱會置於它們之上，至於這帶來什麼改變，下方「沙箱增添什麼、又止於何處」一節會說明。

**它自己的寫入時複製 worktree。** 每個對話都會為每個已連結的程式庫佈建自己的工作副本，透過內建的 `rift` 原生執行檔以寫入時複製方式複製，而非逐位元組複製，因此隔離便宜得足以作為預設。你加入工作區的已註冊程式庫，並不是代理實際工作的目錄 —— 兩個碰觸同一程式庫的對話看不見彼此的修改，而兩者都沒有在編輯你的工作副本。

這裡的粒度值得說得精確：**worktree 以對話為單位，而非以代理為單位。** 同一個對話中的兩個代理會得到各自不同的覆蓋層工作目錄，而這些目錄 _共用_ 該對話的 `repos/` —— 這正是重點，因為它們正在協作同一項變更 —— 而它們各自的私人代理目錄則保持分開。凡 `rift` 有出貨的地方，寫入時複製就是唯一的後端：無法 reflink 的檔案系統，或資料目錄與程式庫位於不同磁碟區，都會令佈建失敗，而不是退回其他方式。Windows 是例外 —— 那裡沒有寫入時複製後端，所以後端是 `git worktree`，而不是悄然降級。

**內建執行框架檔案工具中的路徑限制。** 執行框架的 `read`、`write`、`edit`、`apply_patch`、`search`、`find` 與 `search_files` 工具，會以該次執行的工作目錄加上共用根目錄 —— 對話的 `repos/` 目錄（worktree 所在之處），以及空間的附件目錄（若存在）—— 來解析每一個路徑，並拒絕任何落在範圍以外的。絕對路徑只有在原本就位於範圍內時才被接受。worktree 內指向外部的符號連結也會被解析並拒絕。這就是即使完全不涉及沙箱，代理也無法 `write` 到 `~/.ssh` 的原因。

**模式所提供的工具表面。** 對話的[模式](/zh-HK/手冊/概念/模式/)決定該次執行究竟具體化了哪些工具。在唯讀模式（`plan`、`review`、`orchestrate`）中，變更類工具根本不會出現在工具註冊表裡，而那些模式的 shell 指令政策會直接拒絕所有變更指令 —— `git commit`、`git push`、`npm install`、`docker` 等等 —— 而不是為它們彈出提示。不存在的工具無法被呼叫，這比一個存在但受管制的工具是更強的保證。

**統一的動作護欄。** 每個變更類工具都會宣告它可能產生的效果類別，而政策引擎會在呼叫執行之前，把每一項判定為允許、提示或拒絕。未連接核准人的 `prompt` 會判定為 _拒絕_ —— 沒有人能回答的問題，永遠不會是「是」。判定模型請見[護欄](/zh-HK/手冊/概念/護欄/)。

**經仲介的憑證與已淨化的環境。** 憑證會按每次啟動簽發，並在執行結束時撤銷；一次執行持有的 GitHub 權杖可以讀取，但不能推送 —— 見下文「推送經由 Control Center」。ACP、執行框架的 `bash`，以及在原生包裝下的 Claude Code，都會在行程啟動之前，取得一個已剝除動態連結器與直譯器注入途徑（`LD_PRELOAD`、`DYLD_INSERT_LIBRARIES`、`NODE_OPTIONS`、`GIT_SSH_COMMAND` 之類）的環境。經由 `NoSandboxAdapter` 的 Claude Code 則繼承主機環境。

### 這些界線在哪裡變薄

執行框架的檔案工具執行於 _伺服器行程_ 之中，而非子行程，所以即使掛上了沙箱設定檔，也沒有任何設定檔能約束它們 —— 只有 `bash` 會經過受沙箱包裝的指令執行器。它們的限制就是上述的路徑檢查，因此該項檢查是承重的，而不是第二道防線。

`bash` 工具是另一個需要說清楚的地方。它的指令會先對照模式的指令政策接受評估，然後在已淨化的環境中、以 worktree 作為工作目錄被啟動。若有後端存在，該次啟動會被包裝，因此是沙箱阻止 shell 指令寫入 worktree 之外；若沒有後端（每次 `--sandbox off` 下的執行，以及擁有者自己在 Windows 或缺少 `bwrap` 與 `socat` 的 Linux 上的執行），指令政策就是指令與磁碟其餘部分之間的唯一屏障。在 `chat` 模式中，政策會硬性拒絕一份固定清單（權限提升、破壞系統與磁碟、逃逸容器與命名空間），並就遠端狀態的變更（`git push`、`gh pr create`、套件發佈與安裝）彈出提示。兩份清單都沒有列的，則會執行。shell 管線、鏈式指令與子 shell 都會被解析，每個子指令分別評估，並以最嚴格的判定為準。

Claude Code 作為配接器使用時，是沙箱承擔最多重量的一種情況。Control Center 以 `--dangerously-skip-permissions` 啟動它，因為非互動式的 `claude -p` 否則會永遠卡在自己的核准提示上。它的讀取、寫入與編輯呼叫都在自己的行程內發生，Control Center 從不會看見。它的 `Bash` 呼叫會在執行前送到伺服器上的一個鉤子，由鉤子把命令列分類並詢問對應的規則；Control Center 本身提供的 `mcp__*` 工具則照常通過閘門。若有後端存在，那些看不見的呼叫仍然在沙箱包裝之內發生，因此作業系統就是圍住它們的界線。若沒有後端，就甚麼都沒有。每個配接器都會在其強制執行矩陣中說明這一點 —— 請見[配接器誠實矩陣](/zh-HK/手冊/概念/護欄/#配接器誠實矩陣)。

## 推送經由 Control Center

不存在按代理設定的權限旗標。代理能否建立提交、推送、開啟 pull request、寫入追蹤器或存取網絡，由[護欄](/zh-HK/手冊/概念/護欄/)決定 —— 允許、先詢問或拒絕 —— 無論由哪個配接器運行代理，都適用同樣的規則。

推送是即使面對試圖繞過規則的代理也必須守住的動作，所以它是靠代理手中持有甚麼來強制執行，而不是靠它執行了甚麼。執行開始時不持有任何託管平台權杖，它的 `git` 也絕不會拿到。當它的 `gh` 需要權杖時，Control Center 會給它一個只適用於該次執行所處理的那一個 GitHub 程式庫的權杖；該權杖由工作區的 GitHub App、伺服器自己的應用程式或 Control Center Connect 簽發。該權杖只能讀取：不能推送、留言或編輯。該次執行的 git 設定會把每個 GitHub 推送 URL（`https://github.com/`、`git@github.com:`、`ssh://git@github.com/`）改寫到**代理執行閘道** —— `cc_server` 上的一個回送端點。閘道會讀取這次推送更新了哪些 ref，詢問**推送到遠端**規則 —— 因此像「拒絕推送到 `main`」這類限定分支的規則同樣生效 —— 然後才用它專為此簽發、且從不交給代理的寫入權杖把推送轉送到 GitHub。被拒絕的推送會出現在 git 自己的輸出中：

```text
 ! [remote rejected] main -> main (Control Center policy: …)
```

閘道只會把推送轉送到 worktree 自己的程式庫，或與工作區連結的 GitHub 程式庫。fetch 也經由閘道進行，適用於 GitHub、GitLab 和 Bitbucket：閘道使用一個由它自己保管、執行從不可見的憑證，為該次執行所處理的程式庫執行 fetch。在 GitLab 和 Bitbucket 上，若該次執行由你發起，便使用你自己的權杖；若無人發起，則使用該程式庫的自動化權杖。fetch 從不詢問任何人，只有把**存取網絡**設為拒絕才會拒絕它。

其他 shell 命令遇到的是一道較軟的閘門。執行框架的 `bash` 工具，以及經由鉤子的 Claude Code `Bash` 工具，會把每一行命令分類並詢問它所屬的規則：`git commit`、`merge`、`rebase`、`cherry-pick`、`revert` 與 `am` 屬於**建立提交**；`gh pr create` 屬於**開啟 pull request**；`gh pr merge`、`review`、`comment` 與 `close` 屬於**更新或合併 pull request**；`gh issue create`、`edit`、`comment` 與 `close` 屬於**寫入外部追蹤器**；安裝套件屬於**安裝套件**；`curl` 與 `wget` 屬於**存取網絡**。從 shell 寫入 GitHub 是例外：`gh pr create`、`gh pr comment`、`gh pr edit`、`gh pr merge` 與 `gh issue` 的寫入操作在執行中無法使用，因為執行的權杖只能讀取；代理會被指引至 Control Center 的工具，由這些工具去詢問這些規則。這能辨識一項動作的常見寫法，而一個鐵了心要隱藏它的代理（`eval`、腳本檔案、直接呼叫 API）做得到。推送並不依賴於此。

執行收到的每個 GitHub 權杖都受兩層限制：只適用於一個程式庫，並且只能做負責的成員（提出請求的人，否則是工作區擁有者）在那裏能做的事。沒有任何後備憑證。無法簽發權杖時，請求權杖的指令會說明原因。

沙箱中不會放入任何工單 API 金鑰。代理透過 Control Center 的 MCP 工具寫入工單，這些工具會詢問**寫入外部追蹤器**規則。

**存取網絡**規則會在執行開始時讀取一次。沙箱的網絡只有開或關兩種狀態，所以拒絕會關閉它，而允許與先詢問會讓它保持開啟；執行框架的 `web_fetch` 與 `web_search` 工具仍會在每次呼叫時詢問。執行拆除時，它的憑證控制代碼會被釋放。控制代碼背後的權杖按成員與程式庫共用，並會在大約一小時內到期；成員登出 GitHub 或離開工作區時，代表他簽發的所有權杖會一次過失效。

## 代理只能讀取的儲存庫

代理運行只能更改它所代表之人持有[寫入授權](/zh-HK/手冊/概念/授權/#修改程式碼需要寫入授權)的儲存庫的檢出副本。工作區管理員在每個已連接的儲存庫上都持有該授權。若某次運行並非由任何人要求（例如排程或其他自動化），則由與該自動化權杖所限定的同一位負責人來判斷。

在一個空間中，若有某個儲存庫是該人只能讀取的，代理仍可讀取與搜尋該儲存庫，但無法更改其檔案。它的檔案工具會拒絕，並顯示以 `<repo> is read-only for this run` 開頭的訊息，指出更改檢出副本需要寫入授權，而執行所代表之人並未持有該授權，且工作區管理員可以授予。在沙箱之內，該檢出副本對每個程序都是唯讀的，因此寫入該處的 shell 指令會以 "Operation not permitted" 失敗。這也包括 `git commit`，以及把輸出寫進檢出副本之內的建置或測試。該人可以寫入的儲存庫則照常運作，因此管理員，以及對空間中每個儲存庫都有寫入權限的人，不會看到任何差異。

此判定在運行開始時作出一次。授權變更會在代理的下一次運行時生效，在運行期間加入空間的儲存庫亦然。

在伺服器擁有者關閉了沙箱的情況下，只有代理自身的檔案工具與 Claude Code 的寫入工具會被拒絕，而 shell 指令仍然可以更改檢出副本。無論哪種情況，若沒有寫入授權，都無法推送任何內容，因為每次推送都會對照該授權進行檢查。各平台沙箱所限制的程序，見[沙箱後端](/zh-HK/手冊/參考/沙箱後端/)。

## 沙箱增添什麼、又止於何處

`SandboxBackend` 列舉有三個值 —— `native`（macOS 上的 Seatbelt，Linux 與 WSL2 上的 bubblewrap）、`none` 與 `microvm`。代理指令的包裝只用前兩個：`microvm` 是用於互動式終端機與測試機的隔離式 VM 後端，而不是 `bash` 包裝的悄然升級。理解原生形態，就能說明掛上它之後你得到什麼，以及它從來不會給你什麼。

`cc_server` 在開機時探測主機一次；若有後端回應，就會同時接上派發路徑的兩個接縫，因為這些傳輸不共用同一個。第一個（`SandboxPort`）包裝 Claude Code CLI。第二個（`SandboxManager`）包裝 ACP 配接器與內建執行框架的 `bash` 工具。只接上其中一個，會令其餘的在啟動時不受包裝，而這正是以往的情況。在 `--sandbox off` 之下，它們全都以不受包裝的方式啟動；在沒有後端的主機上，則只有擁有者的執行會啟動，同樣不受包裝。伺服器會在其啟動日誌的一行中說明你處於哪種情況。ACP 與執行框架的 `bash` 仍然會淨化環境；經由 `NoSandboxAdapter` 的 Claude Code 則繼承主機環境。

由伺服器代管的終端機只會為伺服器的[擁有者](/zh-HK/手冊/概念/授權/#伺服器擁有者)開啟主機 shell。其他人會得到一個受沙箱約束的終端機，並受代理的限制，位於工作區自己的目錄中。只有開啟終端機的人才能輸入、讀取或關閉它。

在 Linux 上，`bubblewrap` 會建立一個掛載命名空間，因此代理真正看得到的，只有被綁定進去的東西。在 macOS 上，`sandbox-exec` 會套用一個**預設寬鬆**的 Seatbelt 設定檔 —— 完全預設拒絕的設定檔會令互動式 shell 無法使用，因為要列舉的 dyld、XPC 與 Mach 呼叫數量並不實際。因此 macOS 設定檔從 `(allow default)` 開始，再劃出拒絕項：讀取機密路徑、把寫入政策重設為拒絕並在其上加上明確允許、對每個被拒路徑及其上層路徑封鎖 unlink 以免重新命名繞過寫入拒絕、對永遠危險的執行檔以及任何被複製到可寫目錄的東西拒絕 exec，並把網絡限制在回送代理伺服器連接埠加上 DNS。安裝在你主目錄下的工具鏈（corepack 的 pnpm、Node 版本管理工具、Playwright 瀏覽器、rustup、fvm、uv 等）仍可在該 exec 封鎖範圍內執行，因此代理無須繞道即可使用。永遠危險的拒絕規則仍適用於其中。每個工作階段亦會獲得自己的私有 `TMPDIR`，這是代理唯一可以執行自行建構的程式或開啟 Unix 通訊端的暫存目錄。

每種模式都另有兩項保護。沙箱不能在伺服器執行程式所用的資料夾（其 `PATH` 上的每個資料夾，以及常見的個人工具資料夾）中新增、替換、刪除或重新命名命令，因此經沙箱的執行無法植入伺服器之後會在沙箱之外啟動的程式。因此，在執行內進行的全域安裝與預設版本切換會以“Operation not permitted”失敗，而專案本地的安裝與 `npx` 式執行則照常運作；全域工具請直接安裝在伺服器上，然後重新啟動它。此外，沙箱無法讀取的每個主目錄路徑，它也無法寫入，而伺服器使用者的 shell 與工作階段啟動檔案永遠不可寫入。詳情與各平台的限制，見[伺服器的命令資料夾](/zh-HK/手冊/參考/沙箱後端/#伺服器的指令資料夾)。

一次執行的工具沙箱屬於該次執行，並在它結束時被釋放。語言伺服器會隨每次經沙箱的執行重新啟動。除錯工作階段會在各輪之間保留其沙箱，直到工作階段結束為止，最多 30 分鐘。

實際後果：在 Linux 上，代理對檔案系統的視野被收窄；在 macOS 上，代理仍可 _讀取_ 主機的大部分內容，而你已註冊的工作副本是靠明確的寫入與重新命名拒絕來保護，而不是靠隱形。兩者都是命名空間層級的隔離，不是核心保安邊界 —— 各後端在其自身的能力備註中是這樣說的。

綁定掛載的集合，就是跨代理界線劃下之處。覆蓋層派發（Claude Code 與 ACP）最多會掛載四個路徑，並按每次執行解析：代理的覆蓋層工作目錄（可讀寫）、代理的設定目錄（唯讀）、對話的共用 `repos/` 目錄（存在時可讀寫），以及空間的附件目錄（存在時唯讀）。同儕代理的目錄永遠不會被掛載。執行框架的 `bash` 包裝則較窄：它只綁定掛載該次執行的工作目錄。這與執行框架的行內路徑檢查以軟件強制執行的形態相同，所以兩者一致 —— 但只有路徑檢查涵蓋執行框架自身的檔案工具，因為它們根本不會觸及掛載命名空間。

在此之上，你已註冊的工作副本會加入拒寫集合，在每個模式中、以及在全部三個受包裝的路徑（Claude Code、ACP、執行框架的 `bash`）上皆然，而每條規則都會以其字面拼法與符號連結解析後的拼法各輸出一份。第二種拼法不是可有可無的小節：核心會以解析後的路徑來比對拒絕規則，而 macOS 令路徑解析成為常態而非罕見情況 —— `/tmp` 實際上是 `/private/tmp`，`/var/folders/…` 實際上是 `/private/var/folders/…` —— 所以經由任一種拼法抵達的工作副本，都會在設定檔看似禁止的情況下仍可寫入。

在沙箱之下，網絡是按每個工作階段的**網域**允許清單，由行內回送代理伺服器強制執行。對外流量預設拒絕：網絡關閉時，代理伺服器仍會啟動，但其允許清單是空的，因此每一個對外連線都會被拒絕。網絡開啟時，解析器會從一份精選的基準清單 —— LLM API 供應商、Git 代管、套件註冊表、模型目錄 —— 加上 GitHub 網域，來建立允許清單，並以它比對每個連線的目標主機。萬用字元有效（`*.example.com` 會匹配子網域，而非頂級網域本身）。另有一份永遠拒絕的清單會勝過允許清單，涵蓋雲端中繼資料端點與遙測接收端。*不可*設定的是清單本身：規格帶有一個用於額外網域的 `egressAllowlist` 欄位，但派發路徑中沒有任何東西會填充它，所以實際上每次執行得到的，就是基準清單加上 GitHub，僅此而已。

在 macOS 上，拒絕是可觀察的：有一個監察器會截取系統日誌中的 Sandbox 拒絕記錄，過濾已知雜訊，為重試風暴去重，並把每一項呈現為一個 `SandboxViolation`，指出嘗試了甚麼，以及甚麼被擋下。在 Linux 上，包裝路徑會解析 stderr 中的 `EPERM`、`Operation not permitted` 與 `Permission denied`，並發出同一種事件類型 —— 沒有系統日誌截取。這些會送達該次執行自己的事件串流，因此被拒的系統呼叫會出現在對話紀錄中，而不只是在日誌裡。遙測只在原生沙箱真正包裝著行程時才存在 —— 在沒有後端的主機上，沒有東西可觀察。它也與護欄無關：違規來自被拒的系統呼叫，永遠不會來自規則查詢。

## 確認提示來自護欄，而非沙箱

沙箱沒有核准路徑。它啟動、執行、發出事件然後拆除；它裡面沒有任何人類可以回答問題的地方。當你在空間中看到一個確認提示 —— 核准這次推送、核准這次刪除 —— 它是由護欄引擎（或執行框架的指令政策）在動作根本尚未到達執行階段 _之前_ 提出的。

這個順序是刻意的。在系統呼叫之後才發生的核准，會是一筆稽核記錄，而不是一道閘門。這也是失敗即拒絕的規則存在於護欄之中的原因：在沒有連接核准人時，決定會在任何東西執行之前作出，而且是一項拒絕。
