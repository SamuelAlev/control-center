Pull request 本來就是討論程式碼的地方。PR 對話把它變成 Control Center
工作區上的一個介面，就像[聊天橋接](/zh-HK/手冊/概念/聊天橋接/)把 Slack
變成介面一樣：在 PR 上 @提及 `@usectrl`、在
它的審查討論串內回覆，或加上 `ai-review` 標籤，工作就會在 PR 的審查空間中
進行——歸屬方式和護欄都與在應用程式內輸入的任何內容相同。評論和標籤受同一
道關卡限制：看的是撰寫評論或加上標籤的那位成員。答覆會回到 GitHub，就在
問題所提出的同一條渠道上。

三個決定塑造了這項功能，而每一個都是聊天橋接為聊天作過、再為程式碼託管
平台重述的同一個決定：**連線往哪個方向走**、**來自外部的評論由甚麼授權**，
以及**對話每一方歸屬於誰**。

## 輪詢就是傳輸方式

GitHub 為應用程式提供的唯一推送渠道是 webhook，而 webhook 需要一個入站
URL——這正是這個介面刻意從不要求的東西。因此探索靠一輪掃描：每個應用程式
安裝各自執行一次別名搜尋，向 GitHub 查詢提及 `@usectrl` 的 PR，
以及帶有審查標籤的開啟中 PR；已有審查空間的 PR 會讀取其評論討論串，然後所有
內容都以評論 id 與上次掃描所見的逐項比對。使用自己的應用程式時，每分鐘掃描
一次，最多涵蓋 25 個 PR。透過 Connect 時，這些呼叫用的是成員自己的 GitHub
配額，所以每兩分鐘掃描一次，最多涵蓋 10 個；配額剩餘不足 15% 的工作區會被
略過，直到配額回復為止。Connect 本身永遠看不到 PR 內容。

設計上的幾個後果值得點名：

- **延遲是一個掃描週期，而不是一個事件。** 👀 確認會在一輪掃描內出現。
  沒有急事會靠它。
- **每則評論恰好一次。** 評論 id 在 GitHub 上是唯一的；每則評論在判定為
  符合資格的那一刻就會被記錄，先於任何對它的處理。當機可能令某則評論的
  處理遺失，但絕不會令它重複觸發。
- **離線期間的內容會補上，而不是重播。** 已見集合會被持久保存，因此重新
  啟動後會處理停機期間到達的內容。唯一的例外是史上第一次掃描：沒有記憶
  可比對，所有未處理的項目都會靜靜記錄下來——在這部伺服器存在之前就為
  二十個 PR 加上標籤的操作者，回來時不應該見到二十個正在執行的審查。
- **標籤是一個狀態，而不是一個事件。** 搜尋報告的是標籤的_存在_，所以
  一個已加標籤的 PR 只會觸發一次，僅此一次。移除標籤後再次加上，掃描並
  不會察覺；要重跑就得靠提及。

搜尋會為每個安裝帳戶、以該擁有者自己的用戶端執行一次，因為權杖只看得到
自己那次安裝的程式庫——單一個伺服器層級的憑證，會靜靜漏掉應用程式
其他安裝下的每個 PR。

## 授權的是成員身分，不是評論

一則 PR 評論送達時帶着一位作者——一個未經認證的外部身分，直到被證實為止。
伺服器會以作者不可變的 GitHub 數字帳戶 id（絕不是登入名稱，因為登入名稱
可以改名，也可能被別人重用），比對工作區成員的 GitHub 登入；這份對照會按
TTL 重建，因為伺服器執行期間有人會登入、有人會受邀。至於 `ai-review` 標籤，
解析的對象是最近一次加上它的人。

依序進行三項檢查，任何一項不通過都會靜靜處理——甚麼都不會發佈：

- **已登入的成員。** 該帳戶必須屬於_這個_工作區的一位成員，而且此人已在
  這部伺服器上登入 GitHub
- **具寫入權限的角色。** `viewer` 與 `guest` 無法啟動工作
- **推送權限。** 回覆使用一個只適用於該程式庫的權杖，並限制在該成員對它的存取權之內。如果伺服器無法簽發這樣的權杖，就不會繼續

每項檢查都在任何確認之前執行，所以陌生人既不會得到表情反應，也不會得到回覆。
評論永遠不會歸屬於沒有發出它的人，陌生人的話語也永遠不會進入他看不見的工作區。

### 認領

開始任何工作之前的最後一步，是用作者自己的 GitHub 登入加上一個 👀 表情反應。
GitHub 對新的表情反應回應 `201`，對已存在的回應 `200`，所以這個表情反應同時
充當一把鎖：同一個人若在兩部都連結了該程式庫的伺服器上登入，只有先加上表情
反應的那一部會執行工作。同一部伺服器上若有幾個工作區都看到同一則評論，這則
評論會提供給每一個工作區，並由同樣的認領機制決定。

## 刻意採用兩個身分

對話的每一方都帶著不同的身分，而這個差異正是功能所在：

- **在 GitHub 上，回覆是代表你進行的自動化。** 每則回覆都使用一個只適用於那一個程式庫的權杖，並限制在提問成員的存取權之內，且由應用程式的 `[bot]` 帳戶撰寫。一個例外：在共用的 Control Center Connect 應用程式上，只有當 Connect 營運者列出了該安裝時，機械人才會在審查討論串中發言；否則，審查討論串內的回覆會以提問成員自己的帳戶撰寫。無論哪種方式，每則回覆都以 `**Control Center** (for @login):` 開頭，既說明是誰
  提問，也兼作循環防護。代理回覆中的 @ 提及會被停用，因此回覆永遠不會通知任何使用者或團隊。
- **在空間內，問題屬於你。** 訊息會歸屬於作者所解析到的成員，代理執行
  也代表該成員進行：其提交歸該成員所有，空間的自主調節與動作
  護欄也完全如同對待應用程式內輸入的訊息一樣套用。執行期間對程式碼託管
  平台的寫入，使用以該成員為界、只適用於單一程式庫的權杖，絕不是把他的
  登入整個交出去。

把審查結果發佈回 GitHub 仍然是由人在 Control Center 所作的決定。提及可以
_啟動_一次審查；發佈則只能由人來做。

## 循環防護

任何由機械人帳戶撰寫的內容，都會在任何關卡執行之前被捨棄——包括我們自己
的機械人，以及所有帶 `[bot]` 後綴的帳戶，這樣其他應用程式的審查機械人也
無法喚醒我們的——以 `**Control Center** (for @` 前綴開頭的每則評論也一樣
會被捨棄，因為透過 Connect 在審查討論串中的回覆，可能是由某個人的帳戶撰寫的。沒有這道防護，
答覆會以新評論的形式到達，令橋接永遠重複觸發。

只有 `@usectrl` 會啟動工作。應用程式自身的登入名稱（`<slug>[bot]`）與單純的 slug 都不會指向任何對象：GitHub 不會為應用程式帳戶提供自動完成，而單純的 slug 可能屬於某位人類使用者。

## 刻意不提供的功能

- **不自動發佈。** 審查結果會落在審查空間；發佈到 GitHub 是另一個由人
  執行的動作
- **不做模糊身分。** 作者只會解析到恰好一個成員，否則被忽略——沒有猜測式
  的歸屬
- **不自動核准。** 自動化可以評論和要求修改，但 `APPROVE` 審查在送出前就會
  被拒絕。核准是人的行為
- **不用 GitHub App webhook。** 這個介面從不註冊 webhook，所以沒有為 PR
  評論而暴露的入站 URL。其他產品 webhook（管線、工單同步）屬於另一項
  選用設定。
