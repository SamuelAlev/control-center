Control Center 要回答兩個授權問題，而兩者截然不同。**「這個人可以呼叫這項
操作嗎？」**談的是人、角色與程式庫。**「這個代理可以造成這個效果嗎？」**談的是
動作、參數與影響範圍——後者屬於[護欄](/zh-HK/手冊/概念/護欄/)。

本頁談的是第一個問題，以及兩者共同留下的紀錄。

## 單一決策點

每一項屬於人這一方的授權決策，都經由同一個函式裁定：

```
can(principal, permission, resource) → allow | deny + why
```

**權限**的形式是 `<domain>:<tier>`——`tickets:write`、
`members:administer`、`repos:read`。權限目錄是**推導**出來的，而不是
人手撰寫：它由操作介面本身計算得出（操作名稱的前綴給出網域，該操作
原本已強制的角色下限給出等級），因此全部約 550 項操作都帶有一項權限，
無需任何人逐一輸入。

這項推導正是值得保護的性質。它意味著新增操作預設就受到管制——
手工標註模型的失效模式，就是有人忘記標註，而他們忘記的恰恰是管制本身。
有一項棘輪測試會釘住由此得出的網域集合，因此在新的前綴下新增操作，
是人為作出的命名決定，而不是一次意外。

這四個等級與內建角色精確對應：

| 等級 | 角色下限 | 例子 |
|---|---|---|
| `read` | 訪客 | `tickets:read` |
| `write` | 成員 | `tickets:write` |
| `administer` | 管理員 | `members:administer` |
| `own` | 擁有者 | `workspace:own` |

## 角色

五個內建角色——**擁有者、管理員、成員、檢視者、訪客**——是這套目錄上的
預設組合。每個工作區的擁有權只有一個席位，須以**轉移擁有權**明確移交
（否則離任的擁有者將無法移除：SCIM 取消佈建會拒絕任何工作區擁有者——
請先移交）。

**自訂角色是減法式的。**自訂角色會指定一個基礎預設（`admin`、
`member`、`viewer` 或 `guest`——絕不能是 `owner`），以及一組從中
移除的權限——「管理員，但不能管理成員」。它授予的權限永遠不會超過其基礎
預設，這正是它們可以安全引入既有安裝的原因：所有既有檢查仍然是可靠的
上限。成員以 `custom:<id>` 的形式持有它們，而無法理解該值的舊用戶端
會退回訪客，而不是任意猜測。

角色之下還有**逐程式庫授權**（`none` / `read` / `review` /
`write`，見[修改程式碼需要寫入授權](#修改程式碼需要寫入授權)）：工作區成員身分絕不會悄悄給予高於程式碼託管的權限。所有會
曝露程式碼的介面都會檢查這些授權——包括從側面觸及程式碼的介面，例如在
空間的 worktree 上開啟的終端或編輯器工作階段。

## 程式碼跟隨程式碼託管

單一授權本身不會開啟儲存庫的程式碼。要查看其檔案、diff 或搜尋結果，或在其上開啟終端，成員需要 Control Center 的授權**，而且其本人的程式碼託管登入也必須能讀取該儲存庫。工作區管理員不享有豁免；伺服器擁有者則享有豁免，因為該工作副本位於他們的機器上。沒有程式碼託管遠端的儲存庫只需要授權。

- 當管理員把一個儲存庫授予給其程式碼託管帳戶無法讀取它的人時，授權仍會儲存，而管理員會看到一則警告。
- 當無法連接程式碼託管以作查核時，答案是否定的，絕不會猜測：該人會看到「無法確認你的 GitHub 存取權限。請再試一次。」（將 GitHub 換成其程式碼託管平台的名稱），並稍後再試。
- Pull request 及由它們產生的一切都遵循相同規則。

### 修改程式碼需要寫入授權

儲存庫授權分為三個等級，每個等級都包含其之前的等級：

- **讀取**：查看儲存庫的檔案、diff 與搜尋結果，前提是你本人的程式碼託管登入也能讀取它。
- **審查**：讀取，加上對其 pull request 進行核准、要求修改及其他審查動作。
- **寫入**：審查，加上修改程式碼，以及驅動會寫入該儲存庫的代理運行。修改程式碼包括在編輯器中儲存或還原檔案、把 worktree 同步至其 pull request 的 head、提交與推送、發佈分支，以及用於建立、檢出或發佈某一部分的堆疊動作。

為某人所作的每一次推送，無論由其本人或由其所要求的代理運行進行，都會在推送當下，於該儲存庫上檢查其寫入授權，GitHub、GitLab 與 Bitbucket 皆然。發佈堆疊時，會先檢查堆疊中的每一個儲存庫，然後才推送其中任何一個。

拒絕訊息會指出缺少的授權。沒有讀取權限時，應用程式會顯示「你沒有此存放庫的讀取權限。工作區管理員可以授予。」；有讀取但沒有寫入時，它會顯示「你可以讀取此存放庫，但無法更改。工作區管理員可以授予寫入權限。」

### 空間跟隨其儲存庫

代理對程式碼所寫的內容會跟隨程式碼。空間的內容（其訊息、逐字稿與工具輸出、搜尋結果、運行日誌、待辦事項、活動與通知）會承載它所處理之儲存庫的程式碼，因此只有持有該空間所用每個儲存庫的讀取授權，且其本人的程式碼託管登入也能讀取它的成員，才能開啟該空間。這些儲存庫是為空間選取的儲存庫；若沒有記錄任何選取，則為工作區的所有儲存庫。沒有任何儲存庫建立的空間對每位成員都開放。

無法開啟某空間的人，在任何地方都不會看到它被列出，包括搜尋、運行日誌、待辦事項、活動與通知。工作區管理員持有所有授權，但不豁免程式碼託管的那一半；伺服器擁有者則享有豁免。

若希望所有人都能讀取某個對話，請建立一個不含儲存庫的空間，或只包含所有人都能讀取的儲存庫。

## 伺服器擁有者

設定伺服器的人即是其**擁有者**。伺服器會在首次啟動時記錄他們一次，而透過網路傳送的任何內容都不會改變這一點。工作區管理員或工作區擁有者都不是伺服器擁有者：任何人都可以獲得一個工作區，但伺服器的機器只有一位擁有者。

**除非伺服器擁有者啟動了它，或批准了該類主機執行，否則伺服器自己機器上的任何東西都不會在沙盒之外執行。** 具體而言，只有伺服器擁有者可以：

- 建立工作區。其他人會看到一個畫面，要求他們請擁有者建立一個，或請工作區管理員邀請他們。
- 開啟伺服器上託管的終端中的主機 shell。其他人會得到沙盒終端，受代理的限制，位於工作區自己的目錄中。
- 開啟內嵌的程式碼編輯器。它以伺服器自身的用戶身分執行，帶有它的終端機、任務與擴充功能。
- 在原生編輯器中開啟 pull request 或對話的 worktree。編輯器會在伺服器自己的畫面上以伺服器用戶的身分啟動。
- 儲存或批准一個在主機上執行任何東西的[環境](/zh-HK/手冊/操作指南/環境/)定義：主機放置、執行指令的檢查，或佈建或封存任務。
- 在機器沒有沙盒的伺服器上執行代理。其他人的運行會在該處被拒絕，除非擁有者以 `--sandbox off` 啟動伺服器，此時會不受限制地執行每位成員的代理（參見[沒有沙盒的主機上的代理](/zh-HK/手冊/概念/沙箱與保安/#沒有沙箱的主機上的代理)）。
- 連結一個位於工作區自身儲存空間之外的儲存庫工作副本、確認在該規則之前已連結的工作副本，並在新增儲存庫時瀏覽伺服器的資料夾（參見[新增儲存庫](/zh-HK/手冊/操作指南/加入程式庫/)）。
- 查看並終止伺服器上每一個執行中的代理程序。其他人只能查看並終止他們所屬工作區中的即時代理運行。
- 讓代理使用個人 MCP 伺服器：即伺服器用戶自己工具（Claude、Codex、Cursor 等）中設定的伺服器，以及擁有者新增的伺服器。只有擁有者負責的運行才會取得它們；參見[個人伺服器](/zh-HK/手冊/操作指南/mcp-伺服器/#個人伺服器)。
- 批准一個會在伺服器所在機器上執行命令，或連接其私有網絡的工作區 MCP 伺服器（參見[工作區伺服器](/zh-HK/手冊/操作指南/mcp-伺服器/#工作區伺服器)）。
- 確認某人的電郵地址，以便單一登入能夠比對它（參見[連接 OpenID Connect 供應商](/zh-HK/手冊/操作指南/sso-oidc/#既有帳戶如何比對登入)）。
- 更改整台安裝的設定：SSO、供應商憑證、MCP 端點及其權杖、模型管理、Connect，以及整個安裝的備份。這些操作會聲明**伺服器專屬權限**，對其他所有人一律拒絕。

這裡刻意只保留一個操作員身分，以及關於它的唯一定義。

## 審計軌跡

每一個授權決策——**無論允許還是拒絕**——都會追加到按工作區劃分、
以雜湊鏈串連的審計軌跡。

只記錄拒絕的日誌能回答「我們攔截了甚麼？」，卻回答不了「這個代理究竟
做了甚麼，又是誰授權的？」——而這正是事故檢討要問的第一個問題。因此每筆
記錄都會寫下完整的歸屬鏈：執行的主體、它所代表的人、它所經由的委派、
動作及其參數（以摘要形式）、決策，以及**作出該決策的規則**。

各筆記錄串成一條鏈：每一筆的雜湊都涵蓋前一筆，因此編輯、刪除或重排任何
一行，都會破壞其後的所有雜湊。**驗證鏈**會重新推導整條鏈，並指出第一個
不成立的環節。無法核驗的審計日誌只是日誌；能重新推導的才是證據。

有兩個值得了解的後果：

- 審計表**不受按時間清理影響**。雜湊鏈無法從中間裁剪。保留的做法是先
  匯出、再截斷，而截斷會留下一個攜帶被移除區段末端雜湊的檢查點，
  因此留存下來的內容仍能一路驗證回起點。
- 它與活動時間軸**並列**，而不是疊在其上。時間軸記錄人做了甚麼；這裡
  記錄甚麼被授權、甚麼被拒絕。借助共用的關聯 id，可以在兩者中讀懂
  同一次呼叫。

它匯出為換行分隔的 JSON，並可串流傳送到 SIEM（Splunk、Elastic、
Sentinel——一個帶 bearer token 的 HTTP 端點）。串流按設計就是盡力
而為：SIEM 故障絕不能阻塞代理的工具呼叫，而且無論哪種情況，持久、
可驗證的副本都在磁碟上。

## 工作階段

安裝可以設定**工作階段最長有效時間**和**閒置逾時**。兩者都在裝置憑證
檢查處強制執行，所有經過認證的通道都會匯聚到那裡——用戶端可以無視的
工作階段約束，回答的是問卷，而不是攻擊者。安裝也可以要求使用 SSO，
這會停用新裝置的手動配對（並設有鎖定保護：在沒有可用的 SSO 連線時
會拒絕）。

## 這不是甚麼

- **不是按對象的 ACL。**這裡刻意不提供按工單或按訊息的權限。團隊真正
  需要的是程式庫層級的隔離，而它已經存在；按對象分享會造成組合爆炸，
  而這裡並沒有顯示出這種需求。
- **不是用 DSL 設定的政策引擎。**詞彙表是刻意封閉的，因此整份政策都
  可以被呈現、解釋和列舉。
- **除伺服器之外，不在任何地方強制執行。**用戶端檢查的存在，只是為了
  不提供一個必然會被拒絕的控制項。權威決策始終由伺服器作出。
