:::caution[一次執行是否受沙箱包裝，取決於主機]
`cc_server` 會在開機時決定代理在此主機上如何執行，該決定會一直有效直到重新啟動：

- **受沙箱包裝**（`native`）：探測找到後端，且 `--sandbox` 不是 `off`。派發路徑的兩個接縫都會被包裝：Claude Code CLI 經由沙箱埠，而 ACP 加上內建執行框架的 `bash` 工具則經由沙箱管理程式。
- **關閉**（`off`）：伺服器擁有者以 `--sandbox off` 啟動了它。每位成員的代理都會在這部機器上不受限制地執行，無論是誰啟動的。
- **無法使用**（`unavailable`）：沙箱已開啟，但探測找不到後端（**Windows 一律如此**，缺少 `bwrap` 與 `socat` 的 Linux 或 WSL2 亦然）。只有當對其負責的人是伺服器的[擁有者](/zh-HK/手冊/概念/授權/#伺服器擁有者)時，運行才會啟動：即請求該運行的人，或對於自動化而言，綁定到它的人。其他人的運行會在憑證被鑄造、租約被取得或行程啟動之前即被拒絕。若未記錄任何擁有者，則沒有任何人的運行會啟動。

被拒絕的運行會以代碼 `sandbox_unavailable` 失敗。應用程式會將它顯示為**代理需要此伺服器上的沙箱**：「此伺服器沒有沙箱，因此只有其擁有者可以在此執行代理。擁有者可以安裝沙箱，或為所有人關閉沙箱功能。」

不受沙箱包裝而啟動的運行（在 `off` 之下，或在 `unavailable` 之下擁有者自己的運行）會直接在主機上執行。ACP 與執行框架的 `bash` 工具仍會在淨化過的環境中啟動；Claude Code 則經由 `NoSandboxAdapter`，繼承主機環境。其餘界線包括：該次執行自己的 worktree（凡 `rift` 有出貨處即為寫入時複製；Windows 上是 `git worktree`）、按每次啟動仲介並在拆除時撤銷的唯讀程式碼託管權杖、必須在代理執行閘道通過推送規則的推送、各模式的指令政策、統一的[動作護欄](/zh-HK/手冊/概念/護欄/)（失效即拒絕）、ACP 與執行框架 `bash` 路徑上的環境淨化，以及該模式所允許的工具表面。

執行框架的行內檔案工具（read、write、edit、apply patch、search、find、search_files）在任何主機上都位於沙箱之外：它們在伺服器行程中執行，因此只有 `bash` 會受到包裝。

主機永遠不是受沙箱保護之伺服器的後備選項。若伺服器為代理配置沙箱，但沒有可供運行使用的沙箱，其工具行程與 `bash` 指令會被拒絕，而不會在主機上啟動。同樣的立場也決定了運行周圍的小型行程：ACP 的一次性輔助程式（對話標題、`/btw`、`/handoff`、`/goal`）以及 Review Studio 中 pull request 的 golden 測試，在伺服器為代理配置沙箱時於沙箱內執行，在 `off` 之下不受限制地執行，而在 `unavailable` 之下則只為伺服器擁有者負責的請求執行；否則它們會被略過。
:::

## 後端概覽

| 後端        | 值        | 平台                                          | 可用性                                                                                                            |
| ----------- | --------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 隔離式 VM   | `microvm` | macOS、Linux、Windows（microVM 虛擬機器監控程式） | 以探測為閘，取決於 microVM 執行階段；套用於互動式終端機 —— shell 在[測試機](/zh-HK/手冊/概念/測試機/)內執行，而非在主機上 |
| 原生        | `native`  | macOS（Seatbelt）、Linux 與 WSL2（bubblewrap） | 於開機時探測；對於要求以檔名 glob 拒絕寫入的執行，Linux 會拒絕，因為 bubblewrap 無法強制執行                        |
| 無          | `none`    | 全部                                          | 解析時的預設值與終端機的預設值；代理派發在 `--sandbox off` 之下使用它，而在沒有可用後端時，則只用於伺服器擁有者自己的運行 |

對於 null 或無法辨識的已儲存值，`SandboxBackend.fromName` 會傳回 `none`。

**`microvm` 是唯一具備核心邊界的後端** —— 工作負載確實不在主機上執行。它從不作為任何一方默默退回的選項：在無法啟動 VM 的主機上明確要求它，會大聲失敗（「我要求的是一部 VM，得到的卻是我的筆電」是這個隔離環境唯一承擔不起的降級），而只有*未指明的預設值*才會降級至 `native`，並以一行日誌說明。工作階段的實際後端會回報給用戶端並顯示徽章，因此終端機永遠無法在主機上執行時聲稱自己已受隔離。VM 本身的生命週期、映像與對外流量，見[測試機參考](/zh-HK/手冊/參考/測試機/)。

**Windows 沒有原生沙箱。** 對於任何不是 macOS 或 Linux/WSL2 的主機，`NativeSandboxAdapter.probe` 都會傳回 `available: false`，因此 Windows 伺服器處於 `unavailable` 狀態：只有伺服器擁有者的代理運行會啟動，且不受限制；其他人的運行則會被拒絕。若要讓每位成員都能在那裏執行代理，擁有者需以 `--sandbox off` 啟動伺服器，這會不受限制地執行所有運行。`microvm` 後端則是另一回事：它以 microVM 執行階段的探測結果為閘，套用於互動式終端機與測試機，而非包裝主機上的 `bash`。

## 探測結果

探測結果是決定是否強制執行的閘門。它只在伺服器開機時執行一次。

| 主機                                   | `available` | 備註／提示                                                                |
| -------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS                                  | `true`      | `sandbox-exec`（Seatbelt）—— 命名空間隔離，沒有核心邊界                    |
| 具備 `bwrap` 與 `socat` 的 Linux 或 WSL2 | `true`      | bubblewrap —— 命名空間隔離，沒有核心邊界                                  |
| 缺少任一工具的 Linux 或 WSL2           | `false`     | `requiresInstall: true`，並附上指出缺少哪些套件的安裝提示                  |
| 任何其他平台                           | `false`     | 此平台不提供原生沙箱                                                      |

伺服器會以一行啟動日誌記錄結果：`agent sandbox ON` 加上備註；`no OS-native agent sandbox on this host` 加上提示，其中補充了只有伺服器擁有者負責的運行才會啟動；或 `agent sandbox DISABLED by --sandbox off`。啟動時印出的暴露行會以 `sandbox=native`、`sandbox=off` 或 `sandbox=unavailable` 帶出同一決定。`GET /healthz` 不含任何沙箱欄位。

`--sandbox` / `CC_SERVER_SANDBOX` 接受 `on`（預設）或 `off`。`on` 在主機提供後端時包裝每次運行，在主機沒有後端時則只接受擁有者的運行。`off` 會在此主機上不受限制地執行每位成員的代理；它是擁有者為所有人作出的選擇，而不是每次運行的設定。

## 原生後端

### macOS：Seatbelt

使用 Apple 的 Seatbelt 沙箱機制（與 macOS App Sandbox 所用的系統相同）。

產生的設定檔**預設寬鬆**（`(allow default)`），再劃出拒絕項，因為完全預設拒絕的設定檔會令互動式 shell 無法使用 —— 要列舉的 dyld、XPC 與 Mach 呼叫實在太多。實際後果是代理仍可讀取主機的大部分內容；你已註冊的工作副本是靠明確的寫入與重新命名拒絕來保護，而不是靠隱形。

- **檔案系統讀取**：機密路徑會被拒絕（`~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config/gh`、`~/Library/Keychains`，以及拒絕讀取集合中的其餘路徑）
- **檔案系統寫入**：重設為拒絕，然後加上明確的子路徑允許；強制拒絕的路徑（shell rc 檔案、`.git/hooks`、Claude 設定、受保護的工作副本）即使在可寫入的根目錄內也會被封鎖。每一條被拒路徑及其上層路徑都會拒絕 `file-write-unlink`，因此重新命名無法繞過寫入拒絕
- **行程**：對永遠危險的二進位檔拒絕 `process-exec`，並封鎖從可寫入目錄執行任何東西。主目錄下已知的工具鏈安裝樹（corepack、npx 及 `pnpm dlx` 快取、Node 版本管理工具、Playwright 瀏覽器、rustup 與 cargo、Go、fvm 及 pub 快取、pyenv、uv 及 pipx、rbenv、sdkman、mise、asdf 及 `~/.local/bin`）會在該封鎖之下重新開放。共用的暫存目錄亦會被封鎖。改為每個工作階段獲得 `/private/tmp` 之下的私有 `TMPDIR`，供其建構的程式（例如 `go test` 二進位檔、cargo 建構結果）執行。永遠危險的拒絕規則會在這些允許之後套用
- **網絡**：限制於行內代理伺服器連接埠加上 DNS —— 回送並非一律允許，且禁止 TCP 監聽。Unix 通訊端僅允許在工作階段的私有 `TMPDIR` 內使用，涵蓋 tsx、Chrome 等把 IPC 通訊端存放於該處的工具；你的 SSH agent 及其他通訊端仍無法存取。代理伺服器會強制執行按每個工作階段的網域允許清單（見[網絡對外流量](#網絡對外流量)）
- **設定**：設定檔按每次啟動，從 `SandboxSpec` 產生
- **伺服器自己的指令**：伺服器執行程式所在的任何資料夾的直接子項（`PATH` 中的每一項，以及常見的每位用戶工具資料夾，如 `~/.local/bin`，並會解析版本管理工具的連結，例如 `~/fvm/default`），都不能被建立、替換、刪除或重新命名，連所連結指令指向的已安裝套件亦然。見[伺服器的指令資料夾](#伺服器的指令資料夾)
- **啟動檔**：設定檔拒絕讀取的每一條主目錄路徑，同樣也拒絕寫入；伺服器用戶的 shell 與工作階段的啟動檔（`.zshenv`、`.zlogin`、`.bash_login`、fish 設定、systemd 用戶單元、自動啟動項目及類似者）在每個模式下都被拒絕寫入

需求：

- `sandbox-exec`（`/usr/bin/sandbox-exec`），每個 macOS 安裝都內含 —— 無需額外工具

### Linux：bubblewrap

使用 bubblewrap（`bwrap`）建立掛載與 PID 命名空間。

- **檔案系統**：建立只看得見被綁定路徑的掛載命名空間
- **網絡**：在未共用的網絡命名空間中執行；流量經由 `socat` 的 Unix 通訊端橋接抵達主機代理伺服器
- **行程**：PID 命名空間隔離
- **伺服器自己的指令與啟動檔**：與 macOS 相同的保護，以 bubblewrap 綁定表達。它們在 Linux 上尚未經過驗證，而缺少的指令資料夾在那裏仍可能被建立。

需求：

- 已安裝 `bubblewrap` 與 `socat`（Debian/Ubuntu 上為 `sudo apt-get install bubblewrap socat`）
- 核心命名空間支援（現代 Linux 的標準配備）

Bubblewrap 可以遮蔽既有路徑，但無法禁止可寫入綁定內*新增*的 `.env`、`*.key` 或 `*.pem` 檔案。標準派發政策要求這些檔名 glob 拒絕，因此原生代理派發目前在 Linux/WSL2 上**即使探測找到 bubblewrap 也會失效即拒絕**。它不會以悄然放寬的政策執行。要有具備建立時檔名規則的後端，才能恢復 Linux 的原生派發。停用沙箱是明確、不受限制的退出做法，而不是等效的變通方式。

實際上，Linux 或 WSL2 伺服器今天以兩種方式之一執行代理。以 `--sandbox off` 啟動時，它會不受限制地執行每位成員的代理。若未安裝 bubblewrap 或 `socat`，它便處於 `unavailable`，只會執行伺服器擁有者的代理，且不受限制。兩者都安裝且沙箱開啟時，每次運行都會失效即拒絕，包括擁有者的運行。

## 伺服器的指令資料夾

伺服器在啟動時會一次找出它執行程式所在的每個資料夾：`PATH` 的每一項、它所探測的每位用戶工具資料夾（例如 `~/.local/bin`、`~/.bun/bin`，以及 npm、yarn 與 pnpm 的全域資料夾），以及沿途每個連結背後的實際資料夾（如 `~/fvm/default` 等版本管理工具連結，或 fnm 的預設連結）。在沙箱內，代理不能在這些資料夾中新增、替換、刪除或重新命名指令，也不能新增、替換、刪除或重新命名指向其中某個指令的連結，或該連結所指向的已安裝套件，並且不能重新命名其上層的資料夾。否則，沙箱化的運行便可能植入一個程式，讓伺服器或使用者日後在沙箱之外啟動它。

這對運行的影響是：

- 在沙箱化運行中進行全域安裝會以「Operation not permitted」失敗：`npm i -g`、`pnpm add -g`、`yarn global add`、`bun add -g`、`corepack enable`、`pipx install`、`uv tool install`，以及當其 bin 資料夾位於伺服器的 `PATH` 上時的 `cargo install`、`go install` 或 `dart pub global activate`。
- 切換預設版本也會以同樣方式失敗（`fnm default`、`nvm alias default`、`fvm global`），工具自行就地更新亦然。
- 專案內的安裝（`node_modules/.bin`）、`npx`、`pnpm dlx`、由 corepack 管理的套件管理員、SDK 快取與一般建構，仍會正常運作。

要讓代理可使用某個全域工具，請在伺服器本身、以伺服器用戶的身分安裝它，並重新啟動伺服器，讓新指令也受到保護。或者把它安裝在專案中。伺服器啟動後才安裝的指令，只有在下次啟動後才會完全受保護。

已在 macOS 上強制執行並測試。在 Linux 上，同樣的規則是尚未驗證的 bubblewrap 綁定。Windows 沒有沙箱。

## 無後端

不進行任何沙箱包裝。行程直接在主機上執行，擁有主機的檔案系統、網絡與行程存取權。ACP 與執行框架的 `bash` 工具仍會取得環境淨化與指令政策；經由 `NoSandboxAdapter` 的 Claude Code 則繼承主機環境。代理派發在 `--sandbox off` 之下為每次運行使用它，在沒有可用後端的主機上則只為伺服器擁有者自己的運行使用；其他人的運行會在該處被拒絕。對於終端機而言，它就是主機 shell，而只有伺服器擁有者可以開啟它。

## 由伺服器代管的終端機

由伺服器代管的終端機只為伺服器的[擁有者](/zh-HK/手冊/概念/授權/#伺服器擁有者)開啟主機 shell。其他人會得到沙箱化的終端機，受代理的限制，位於工作區自己的目錄中。

工作階段如何選擇後端：

| 要求 | 伺服器擁有者 | 其他人 |
| --- | --- | --- |
| 未指定 | 伺服器的預設後端 | 預設值，其中 `none` 會被替換為 `native` |
| `none`（主機 shell） | 主機 shell | 拒絕：主機 shell 在沒有沙箱的情況下於伺服器上執行 |
| `native` | 原生沙箱，擁有者設定檔 | 原生沙箱，代理設定檔 |
| `microvm` | 隔離式 VM | 隔離式 VM |
| 未知名稱 | 拒絕 | 拒絕 |

- **擁有者設定檔。** `$HOME` 與該工作階段的工作目錄可寫入，網絡開放，而 `~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config/gh` 與 `~/Library/Keychains` 會被拒絕讀取。
- **代理設定檔**（`memberTerminalSandboxConfig`）。與該工作區中代理執行時所用的政策相同：寫入僅限於工作目錄、私有的執行目錄、`/tmp`，以及代理可寫入的 `$HOME` 部分；機密被拒絕讀取；網絡為代理對外流量允許清單；程式只從工作目錄與已安裝的工具鏈執行。
- 終端機只會在工作區自己的目錄內開啟。位於其之外的工作目錄會被拒絕，而不會被換成另一個。
- 只有開啟終端機的人可以讀取、輸入、調整大小或關閉它。對其他任何人而言，它的 id 看起來都是未知的。
- 在沒有 rig 服務的主機上明確要求 `microvm` 會失敗，而不會退回。在此類主機上預設為 `microvm` 時，會降為 `native`，並在日誌中說明。

唯讀程式碼託管權杖與推送閘道不適用於終端機：它們屬於派發層面的事。若無法進行包裝，該工作階段會失敗，而不是在主機 shell 工作階段上顯示沙箱徽章。

## 網絡對外流量

沙箱啟動後，對外網絡存取是由行內代理伺服器強制執行，而不是靠核心防火牆規則。未受沙箱包裝的運行（在 `--sandbox off` 之下的每次運行，或在沒有後端的主機上的擁有者運行）不會享有這一切：它衍生的行程會以與伺服器使用者完全相同的方式存取網絡。

- 沙箱執行階段會在 `cc_server` 行程內、於 `127.0.0.1` 上執行一個 HTTP/HTTPS 代理伺服器與一個 SOCKS5 代理伺服器，**每個受限制的工作階段各一對**（`http_proxy.dart`、`socks_proxy.dart`）。並行執行不會共用同一對。
- 受沙箱包裝的行程會取得代理伺服器環境變數（`HTTP_PROXY`/`HTTPS_PROXY` → HTTP 代理伺服器，`ALL_PROXY` → SOCKS 代理伺服器；`GIT_SSH_COMMAND` 會將 git-over-SSH 導向 SOCKS 代理伺服器）。在 Linux 上，網絡命名空間是未共用的，因此代理伺服器是唯一的出路；在 macOS 上，沙箱共用主機的回送，並直接與它們通訊。
- 每個連線的目標主機會與該工作階段的網域允許清單比對；其他一律拒絕。萬用字元有兩種形式，各含恰好一個 `*`：前置的 `*.example.com` 會匹配任何子網域（包括 `a.b.example.com`），但不匹配頂級網域本身；中間標籤的 `bedrock.*.amazonaws.com` 則恰好匹配一個標籤（`bedrock.us-east-1.amazonaws.com`，而非 `bedrock.evil.attacker.amazonaws.com`）。
- 允許清單會按每個工作階段，從精選的基準清單（`kBaselineAllowedDomains`：LLM 供應商、Git 代管、套件註冊表）解析，再加上 GitHub 網域（`kGithubDomains`），以及 `SandboxSpec.egressAllowlist`。派發路徑從不傳入額外的 `egressAllowlist` 項目，因此實際上每次執行得到的，都是基準清單加上 GitHub。
- 一份固定的拒絕清單（`kBaselineDeniedDomains`：雲端中繼資料端點、遙測接收端）優先於所有允許項。
- `networkEnabled: false` 仍會啟動按每個工作階段的代理伺服器，但允許清單是空的，因此每一個對外連線都會被拒絕。派發會在執行開始時依**存取網絡**規則設定這個值：拒絕會關閉網絡，允許與先詢問會讓它保持開啟。

## SandboxSpec

傳遞給 `SandboxPort.launch` 的規格：

| 欄位              | 型別                                        | 說明                                                                                                                                          |
| ----------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | 穩定的工作階段識別碼（通常是空間 id）                                                                                                         |
| `workspaceId`     | `String`                                    | 所屬工作區 id                                                                                                                                 |
| `agentId`         | `String?`                                   | 目前綁定至該沙箱的代理（如有）                                                                                                                |
| `bindMounts`      | `List<SandboxBindMount>`                    | 主機 → 客體的掛載；沙箱只看得到此處列出的主機路徑                                                                                             |
| `networkEnabled`  | `bool`（預設 `true`）                       | 派發時依網絡對外連線規則設定（只有解析為拒絕時才關閉）。關閉時，按每個工作階段的代理伺服器仍會啟動，但允許清單是空的，因此每一個對外連線都會被拒絕 |
| `egressAllowlist` | `List<String>`（預設 `[]`）                 | 額外允許的對外流量網域；支援萬用字元（`*.example.com`，以及一個標籤的中間形式）。派發從不填入此欄位，因此受包裝的執行只會得到精選基準清單，加上 GitHub 網域 |
| `guestWorkdir`    | `String?`                                   | 沙箱內的預設工作目錄；個別的 `exec` 呼叫可以覆寫它                                                                                            |
| `mode`            | `Mode`（預設 `chat`）                       | 劃定檔案系統寫入規則：`chat` 讓綁定掛載保持可寫入；`review`、`plan` 與 `orchestrate` 則為唯讀                                                 |
| `protectedPaths`  | `List<String>`（預設 `[]`）                 | 在任何模式下都絕不可在沙箱內寫入的主機路徑                                                                                                    |
| `runnerStateDirs` | `List<String>`（預設 `[]`）                 | 執行器用來存放自身狀態的主機目錄，在每個模式下都可寫入（目前是由 Control Center 管理的 `CLAUDE_CONFIG_DIR`）                                  |
| `execGrantRoots`  | `List<String>`（預設 `[]`）                 | 由操作員核准的目錄樹，會在 macOS 上重新開啟「可寫入目錄的 exec 封鎖」。Linux 會忽略它們 —— bwrap 沒有 `$HOME` 的 exec 封鎖可供重新開啟        |

`protectedPaths` 存放原始的已註冊程式庫工作副本，於每次派發時從工作區的程式庫解析。代理只在按每個對話的寫入時複製 worktree 中工作，因此原始副本絕不可從沙箱內寫入 —— 否則在 macOS 上，Seatbelt 對 `$HOME` 的一律寫入允許會令它們可經由 `bash` 寫入。它們在每個模式下（包括 `chat`）都會加入機密拒絕寫入集合。

每個拒絕讀取與拒絕寫入的路徑，都會以其字面拼法與符號連結解析後的拼法各輸出一份。核心會以解析後的路徑來比對拒絕規則，因此針對符號連結路徑撰寫的規則永遠不會觸發 —— 而在 macOS 上，這是常態而非罕見情況，因為 `/tmp` 解析為 `/private/tmp`，`/var/folders/…` 解析為 `/private/var/folders/…`。含有 `*` 或 `?` 的項目會視為 glob 而不加處理；無法解析的路徑則保持原樣。

## SandboxBindMount

| 欄位        | 型別                     | 說明                                                                                                  |
| ----------- | ------------------------ | ----------------------------------------------------------------------------------------------------- |
| `hostPath`  | `String`                 | 主機上的絕對路徑                                                                                      |
| `guestPath` | `String`                 | 沙箱內的路徑（使用原生沙箱時這等於 `hostPath`；保留以維持配接器對稱）                                 |
| `readOnly`  | `bool`（預設 `false`）   | 為 true 時以唯讀方式掛載                                                                              |

## SandboxHandle

由 `SandboxPort.launch` 傳回：

| 欄位        | 型別                   | 說明                                                                     |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | 工作階段識別碼                                                           |
| `backend`   | `SandboxBackend`       | 正在執行的是哪個後端                                                     |
| `state`     | `SandboxState`         | 生命週期狀態                                                             |
| `error`     | `Object?`              | 當 `state` 為 `error` 時設定                                             |
| `details`   | `Map<String, Object?>` | 配接器私有的記帳資料（工作目錄、PID、設定檔路徑等）                      |

### SandboxState

| 狀態        | 說明                                     |
| ----------- | ---------------------------------------- |
| `created`   | 規格已建立，但 VM 尚未啟動               |
| `warm`      | 正在執行且已可接受 exec 指令             |
| `active`    | 目前正在執行指令                         |
| `suspended` | 已暫停／已檢查點至磁碟以節省 RAM         |
| `destroyed` | 已拆除；控制代碼不再有效                 |
| `error`     | 啟動失敗 —— 見 `SandboxHandle.error`     |

## 沙箱事件

| 事件類型    | 說明                                                    |
| ----------- | ------------------------------------------------------- |
| `stdout`    | 沙箱的標準輸出                                          |
| `stderr`    | 沙箱的標準錯誤                                          |
| `exit`      | 沙箱行程已結束（帶有 `exitCode`）                       |
| `starting`  | 沙箱正在啟動                                            |
| `ready`     | 沙箱已可接受 exec 呼叫                                  |
| `killed`    | 行程被主機終止（OOM、逾時、手動停止）                   |
| `violation` | 沙箱政策遭到違反（帶有一個 `SandboxViolation`）         |

## SandboxViolation

| 欄位                  | 型別      | 說明                                                              |
| --------------------- | --------- | ----------------------------------------------------------------- |
| `action`              | `String`  | 被拒的動作詞（例如 `file-read*`、`network-outbound`）             |
| `target`              | `String`  | 被拒操作所針對的路徑或主機                                        |
| `raw`                 | `String?` | 原始日誌行，可用於除錯                                            |
