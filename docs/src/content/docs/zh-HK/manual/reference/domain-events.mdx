## 事件匯流排

`DomainEventBus` 是一個進程內的廣播式發佈／訂閱匯流排。發佈方呼叫
`publish(event)`；訂閱方則消費帶類型的 `on<T>()` 串流。每個事件都實作
`DomainEvent`，並攜帶 `occurredAt`。

**匯流排運行於 `cc_server` 內部。** 每個發佈方與每個存活中的訂閱方都在其中。
沒有任何用戶端能看到這條匯流排——伺服器會把精選的子集以 `notifications/*`
JSON-RPC 訊框轉發出去，並依工作區成員關係逐一篩選每個訂閱方。

| 指標                                                        | 數量                                        |
| ----------------------------------------------------------- | ------------------------------------------- |
| 具體事件類別                                                | 53                                          |
| 來源檔案（`packages/cc_domain/lib/core/domain/events/`）    | 14（另有 `domain_event_bus.dart`）          |
| 從不直接發佈的抽象基底                                      | 1（`TaskLifecycleEvent`，一個 sealed 階層） |

下列目錄中的每個事件都位於那一個目錄裡；沒有在其他地方宣告任何領域事件。

## 任務生命週期事件

統一的任務生命週期串流——一次派發的代理執行，以其執行日誌 id 為鍵。每個事件都
攜帶 `taskId`、每個任務單調遞增的 `seq`、`workspaceId?`、`agentId?` 以及一個
`phase`；下列各列只列出額外欄位。

| 事件                        | 載荷                          | 觸發時機                                                                                         |
| --------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `TaskDispatched`            | —                             | 任務交由後端執行                                                                                 |
| `TaskRunning`               | —                             | 任務開始產生輸出                                                                                 |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | 任務被擱置——它所需的磁碟路徑鎖由另一個任務持有                                                   |
| `TaskProgress`              | `note?`                       | 執行中途的進度檢查點                                                                             |
| `TaskMessage`               | `messageType`, `content`      | 串流訊息（text／thinking／tool_use／tool_result／error）；在 `progress` 階段下回報               |
| `TaskCompleted`             | `summary?`                    | 任務成功完成                                                                                     |
| `TaskFailed`                | `errorMessage`                | 任務因錯誤而結束                                                                                 |
| `TaskCancelled`             | —                             | 任務在完成前被取消                                                                               |

`TaskPhase` 列舉還有一個 `queued` 成員，但沒有任何東西會發佈排隊事件——並不存在
`TaskQueued` 類別。任務第一個可觀察到的訊框是 `TaskDispatched`。

## 管線事件

| 事件                   | 載荷                                          | 觸發時機                                                                    |
| ---------------------- | --------------------------------------------- | --------------------------------------------------------------------------- |
| `PipelineRunCompleted` | `workspaceId`, `pipelineRunId`, `templateId`  | 執行完成                                                                    |
| `PipelineRunCancelled` | `workspaceId`, `pipelineRunId`, `templateId`  | 執行被取消（由使用者或系統發起）——是刻意的停止，不是錯誤                    |
| `PipelineRunFailed`    | `workspaceId`, `pipelineRunId`, `templateId`, `errorMessage` | 執行失敗                                                     |

只有終態轉換會被發佈。既沒有 `PipelineRunStarted`，也沒有逐步事件：步驟的進度
是透過該次執行自身的資料列，以及它所派發的任何代理的任務生命週期串流，送達
用戶端，而不是透過匯流排。

## 測試機事件

| 事件                | 載荷                                          | 觸發時機                                                                                                                         |
| ------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `RigClosedEvent`    | `workspaceId`, `rigId`, `reason`              | 測試機消失了，並附帶其關閉原因；消費者只對 `backendFailure` 採取行動——其他每個原因都是被請求的，或伴隨著 `RigReaped`            |
| `RigControlChanged` | `workspaceId`, `rigId`, `controller?`         | 有人取得測試機的專屬控制權，或將其交還（釋放時 `controller` 為 null——事件不會記錄是誰放手的）                                    |

## 完全沒有事件的子領域

有幾個從外部看起來像是事件驅動的子系統，其實並不是。這裡列出它們，是因為它們的
缺席是一項設計決定，值得你在到處尋找掛鉤之前先了解：

| 子領域              | 狀態改以何種方式推進                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| 記憶                | `record_memory_fact` 及其同類函式會寫入並返回；回想則只讀取。事實或衝突都不會發佈任何東西              |
| 編排                | 提案、其核准，以及所產生的管線執行都是資料列與 RPC 呼叫                                                 |
| 計劃文件            | `submit_plan` 寫入一個修訂；核准則具體化一次編排。兩者都不會對外公告                                   |
| 產出物              | `publish_artifact` / `revise_artifact` 直接寫入修訂                                                     |
| 核准                | 升級是在核准工作流程服務內部處理                                                                        |
| 工單同步            | 廠商協調器會訂閱上述工單事件；傳入的 webhook 則直接套用                                                 |
| 日曆重新整理        | 同步會以 upsert 方式寫入事件，用戶端再重新讀取；並沒有重新整理廣播                                      |
| 工作樹合併          | 記錄在 `worktree_merge_log`，並從那裡讀取                                                               |

## 通知對應

在伺服器上，`NotificationFeedRecorder` 與 `RemoteEventForwarder` 會把這些事件
轉成 `notifications/*` 傳輸訊框（`notification_wire.dart`）。在用戶端，
`RpcNotificationMapper` → `mapNotificationFrame` 會把訊框轉成
`AppNotification`。

通知類別恰好有**十六個**。有幾個事件會對應到多於一種傳輸方法，因為訊框承載的
是變化方向（失敗還是已恢復），而類別承載的是問題本身（「CI 現在怎麼了？」）。

| 類別                   | 來源事件                  | 傳輸方法                                                                 |
| ---------------------- | ------------------------- | ------------------------------------------------------------------------ |
| `newMessage`           | `MessageReceived`         | `notifications/message_received`                                         |
| `agentRunCompleted`    | `AgentRunCompleted`       | `notifications/agent_run_completed`                                      |
| `ticketAssigned`       | `TicketAssigned`          | `notifications/ticket_assigned`                                          |
| `ticketStatusChanged`  | `TicketStatusChanged`     | `notifications/ticket_status_changed`                                    |
| `pullRequestPublished` | `PullRequestPublished`    | `notifications/pr_published`                                             |
| `prMerged`             | `PrMerged`                | `notifications/pr_merged`                                                |
| `prMerged`             | `ExternalPrMerged`        | `notifications/external_pr_merged`                                       |
| `prMentioned`          | `PrMentioned`             | `notifications/pr_mentioned`                                             |
| `prMentioned`          | `PrCommentMentioned`      | `notifications/pr_comment_mentioned`                                     |
| `reviewRequested`      | `PrReviewRequested`       | `notifications/pr_review_requested`                                      |
| `reviewStale`          | `ReviewBecameStale`       | `notifications/review_stale`                                             |
| `prMergeReadiness`     | `PrMergeReadinessChanged` | `notifications/pr_ready_to_merge` / `pr_merge_blocked`                   |
| `prReviewDecision`     | `PrReviewDecisionChanged` | `notifications/pr_approved` / `pr_changes_requested` / `pr_review_dismissed` |
| `prChecksStatus`       | `PrChecksStatusChanged`   | `notifications/pr_checks_failed` / `pr_checks_recovered`                 |
| `prThreadActivity`     | `PrThreadReplied`         | `notifications/pr_thread_replied`                                        |
| `prThreadActivity`     | `PrThreadResolved`        | `notifications/pr_thread_resolved`                                       |
| `meetingStartsSoon`    | `MeetingStartingSoon`     | `notifications/meeting_starting_soon`                                    |
| `calendarAuthExpired`  | `CalendarAuthExpired`     | `notifications/calendar_auth_expired`                                    |
| `rigStatusChanged`     | `RigControlChanged`       | `notifications/rig_control_changed`                                      |
| `rigStatusChanged`     | `RigReaped`               | `notifications/rig_reaped`                                               |
| `rigStatusChanged`     | `RigClosedEvent`          | `notifications/rig_closed`                                               |

測試機的接管訊框不會回送給取得控制權的那個人；釋放則不經過篩選（事件不會記錄
是誰放手）；而且只有 `backendFailure` 關閉會產生 `rig_closed` 訊框——其他原因
不是被請求的，就是已由回收訊框涵蓋。

五個自己提交的 PR 類別都攜帶 `forUserId`，因此它們會送達作者，而不是工作區內的
每個人。

`RemoteEventForwarder` 另外會把 `TicketReassigned` 轉發為
`notifications/ticket_reassigned`，並把每個 `TaskLifecycleEvent` 轉發為
`notifications/task_<phase>`。兩者都不會對應到通知類別——它們驅動即時 UI，
而不是通知中心。成員關係事件不會以訊框轉發：它們會使轉發器的快取失效，而工作
階段主機則會捨棄被移除成員的工作區訂閱。
