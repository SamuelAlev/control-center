本指南說明如何在不用離開 GitHub 的情況下使用 Control Center：從 PR 頁面
要求 AI 審查、在評論中向機械人提問，並在它的審查討論串中延續對話。

回覆會經由工作區的 GitHub 通道送出：你伺服器自己的
[GitHub App](/zh-HK/手冊/操作指南/github-app/)，或經由 Connect 使用的 Control Center
共用 App。無需註冊任何新東西，也沒有
任何東西必須能從互聯網連到：伺服器以輪詢方式探索 GitHub 上說了些甚麼，所以
位於 NAT 後方的筆記型電腦，行為與公開部署完全相同。

## 開始之前

- 工作區有一條 GitHub 通道：伺服器自己的 GitHub App 或 Connect，而且該 App 已
  [安裝](/zh-HK/手冊/操作指南/github-app/#安裝到你的程式庫所在之處)在擁有該程式庫
  的帳戶上。自己的 App 需要 **Pull requests** 與 **Issues** 的讀取與寫入權限，
  **建立我的 GitHub 應用程式**已經授予這些權限
- 該程式庫已連結到 Control Center 中的一個工作區
- 你已在這部伺服器上[登入 GitHub](/zh-HK/手冊/操作指南/github-整合/)，而且你可以
  推送到該程式庫
- 沒有 webhook URL、沒有通道、沒有回呼 —— 網絡方面沒有任何東西需要設定

## 尋找你的機械人名稱

提及 `@usectrl`，這是 Control Center 專用的 GitHub 帳戶。它是唯一的觸發方式：提及應用程式自己的登入名稱不會有任何作用。工作區的 GitHub 通道仍會處理請求並發佈回覆。你毋須 `usectrl` 帳戶的憑證。

## 從 GitHub 要求審查

有兩種方式，兩者都會啟動與 **詢問 AI** 按鈕相同的預先植入 `pr_review` 管線：

- **為 PR 加上 `ai-review` 標籤**。這是 GitHub 所能提供、最接近把機械人指派為
  審查者的做法 —— 應用程式帳戶無法佔用原生的「要求審查者」欄位。你的帳戶會在
  該 PR 上加上 👀 表情反應，審查會在 Control Center 中啟動；不會發佈任何評論
- **在 PR 對話中評論 `@usectrl review`**（或只輸入 `@usectrl`）。你的評論上會出現
  👀，然後會有一則回覆說明審查已經開始（或告知已有一個正在執行）

審查者會在該 PR 的審查空間中工作；閱讀與發佈發現項的方式與
[使用 AI 輔助審查](/zh-HK/手冊/操作指南/ai-審查/)相同。發佈回 GitHub 仍然是由你
在 Control Center 所作的決定 —— 從 GitHub 啟動審查，本身不會向 GitHub
發佈任何內容。

該標籤每個 PR 只觸發一次：加上它就是提出要求，而移除後重新加上並不會
重新觸發它。若要再次執行審查 —— 例如在一次 push 之後 —— 請提及機械人。

## 提出問題

在 PR 對話中評論：

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

依序會發生以下事情：

1. 你的評論上會出現一個來自你自己帳戶的 👀，讓你知道評論已被看到
2. 問題會**以你的身分**發佈到該 PR 的審查空間 —— 歸屬方式與你在
   Control Center 中輸入完全相同
3. 一個代理會在空間中回答，而答案會發佈回 PR。每則回覆都以
   `**Control Center** (for @your-login):` 開頭

在尚未有審查的 PR 上提問，會喚醒該工作區的 CEO 代理；一旦審查執行過，
則由最後發言的代理回答，所以後續追問會落到掌握上下文的那一位身上。

## 在審查討論串中跟進

在機械人參與的行內審查討論串中回覆 —— 它留下的 diff 評論，或它在該
討論串中發佈的答案。無需提及；討論串**本身**就是定址：

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

多輪對話的運作方式相同：每次回覆都是同一則對話中的另一個問題，並以審查
空間作為上下文，而答案會回到該討論串中。

在 PR 對話時間軸上的後續追問是一則新的頂層評論，所以仍然需要 @提及。

## 機械人與誰對話

伺服器會在做任何事之前，先解析評論的作者，或加上 `ai-review` 標籤的人：

- **該 GitHub 帳戶必須已在這部伺服器上登入。** 比對依據是 GitHub 的數字帳戶
  id，絕不是登入名稱。請從 **設定 → 你 → 個人資料 → 程式碼託管** 登入
- **此人必須是具備寫入角色的成員**（`member`、`admin` 或 `owner`），且隸屬於
  連結該程式庫的工作區
- **此人必須能在 GitHub 上推送**到該程式庫。回覆使用的權杖會限制在此人的存取權
  之內，所以只能讀取的人不會得到回覆

其他任何人都會被靜靜忽略：不會發佈任何內容，而他們的話永遠不會進入工作區。來自
機械人的評論，以及 Control Center 自己的回覆，永遠不會被當作問題處理。

### 兩部伺服器，一個 PR

👀 也是各伺服器協定由誰回答的方式。它是用作者自己的登入加上的，而 GitHub 會告訴
伺服器這個表情反應是否新的。如果你在兩部都連結了該程式庫的 Control Center 伺服器
上登入，先加上表情反應的那一部會回答，另一部則保持沉默。標籤也是一樣。

## 預期會發生甚麼

| 項目       | 行為                                                          |
| ---------- | ------------------------------------------------------------- |
| 確認       | 在一輪掃描內，由你的帳戶在評論上（若是標籤則在 PR 上）加上 👀 |
| 答案       | 出現在問題所提出的同一條渠道上，以 `**Control Center** (for @your-login):` 開頭。由該應用程式的機械人撰寫。在共用的 Connect 應用程式上，審查線程內的回覆會以你自己的帳戶撰寫，除非 Connect 營運者已將此安裝列入清單 |
| 空間內歸屬 | 問題屬於你；代理代表你執行，並遵循該空間的自主程度設定        |
| 審查       | 發現項會落在審查空間；發佈到 GitHub 則需手動進行              |

使用自己的 App 時，每分鐘掃描一次，最多檢查 25 個 pull request；經由 Connect 時，
每兩分鐘掃描一次，最多檢查 10 個，因為這些呼叫共用每位成員自己的 GitHub 配額。
GitHub 配額剩餘不足 15% 的工作區會被略過，直到配額回復為止。這樣的延遲，換來的
是完全不需要任何入站網絡存取。伺服器離線期間也不會遺失任何東西 —— 停機期間到達
的評論會在下一次掃描時被捕捉到。

## 疑難排解

**提及機械人的評論沒有任何反應。**

- 應用程式是否已**安裝**在擁有該程式庫的帳戶上，而且該程式庫已**連結**到
  工作區？未連結的程式庫會在記錄任何東西之前被略過，所以稍後再連結仍然
  會送達
- 你是否已在這部伺服器上登入 GitHub、是具備寫入角色的成員，而且能推送到該
  程式庫？其他任何人都會被伺服器忽略，不會收到回覆
- 仍然沒有反應？當有東西失敗時，伺服器日誌會寫出掃描和 PR；請尋找
  `pr_conversation:`（輪詢器）和 `github_pr_conversation:`（橋接）

**該標籤沒有啟動審查。**

它每個 PR 只觸發一次，而加上它的人要通過與評論作者相同的檢查。如果審查已經
執行過，或標籤是在伺服器首次看到該 PR 之前加上的（第一次掃描會靜靜記錄積壓
項目，而不是向它蜂擁而上），請改為提及機械人 —— 除非已有審查正在進行，否則
`@usectrl review` 一定會啟動一次。

**機械人的答案一直沒有出現在 GitHub 上。**

答案本身永遠不會遺失 —— 它就在 Control Center 中該 PR 的審查空間裏。發佈
失敗（GitHub 故障、權限變更）會被記錄下來，而且不會重試該回覆；如果這件事
要緊，請在討論串中再問一次。
