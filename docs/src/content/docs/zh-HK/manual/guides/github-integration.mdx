本指南涵蓋設定中專屬於 GitHub 的部分。GitHub 是三種受支援的程式碼託管平台
之一。連接 GitLab 或 Bitbucket，以及同一個工作區如何混用它們，請參見
[連接程式碼託管](/zh-HK/手冊/操作指南/連接程式碼託管/)。

## 先決條件

- 一個 GitHub 帳戶，且能存取你想處理的程式庫
- 一部能讓人們登入 GitHub 的伺服器：它自己的 GitHub App（參見
  [建立 GitHub App](/zh-HK/手冊/操作指南/github-app/)）或 Control Center Connect，
  由伺服器擁有者在 **設定 → 伺服器 → 單一登入** 中選擇

:::note[憑證存放在伺服器上，並歸屬於你]
你正在輸入的那部機器上不會儲存任何東西。你的 GitHub 登入由你的 `cc_server`
持有，以你的使用者 id 為鍵，你登入的每部裝置都會使用它：桌面端、網頁版和手機。
同一伺服器上的其他成員無法使用它，而為他們登入這件事，得由他們自己完成。
:::

## 登入 GitHub

GitHub 只能登入：沒有可貼上的權杖。

1. 前往 **設定 → 你 → 個人資料 → 程式碼託管**（或新手導引的第一步）
2. 在 **GitHub** 一列上，按一下 **登入 GitHub**
3. 你的瀏覽器會開啟 GitHub。批准該應用程式

登入如何完成，取決於由誰執行：

- **伺服器自己的應用程式：** GitHub 會把你的瀏覽器送回伺服器，對話框會自行
  察覺。不需要輸入任何東西
- **Control Center Connect：** 瀏覽器頁面會顯示一個 8 個字元的代碼。把它輸入
  對話框，或讓瀏覽器透過 `control-center://` 連結開啟 Control Center，便不必輸入

檢查點：**GitHub** 一列顯示「已登入為 _your-username_」。

對話框會拒絕不是由它自己發起的代碼或連結，並顯示**登入並非從這裡發起**。如果有人
傳給你一條登入連結，請不要繼續：完成它會把你的帳戶連接到對方的伺服器。

按一下 **中斷連接** 即可移除你的登入。登出 GitHub，或被移出某個工作區，也會令
伺服器代表你簽發的所有權杖一併失效。

## 你的憑證代表誰

Control Center 遵循 GitHub 自身的區分：以**人的身分**行事，還是以**應用程式的身分**行事。

| 發生的事                                                                      | 在 GitHub 上顯示為                                          |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 你自己做的任何事：留言、審查、批准、合併、要求審查者                           | **你**。GitHub 會在對話中的留言上標示由 Control Center 應用程式發出；審查及其行內留言則不帶此標示 |
| AI 審查、代理在 PR 對話中的回覆和留言、標籤、管線與機械人工作                        | **Control Center 機械人**。在共用的 Connect 應用程式上，審查只有在 Connect 營運者已列入清單的安裝中才屬於機械人；否則它會顯示為負責任的人 |
| 代理為你開啟的 pull request、它對該 pull request 標題或描述的編輯、它的推送及其提交                                  | **你**。在啟用共同作者標示時，Control Center 會被記為共同作者 |
| 沒有人要求的工作（排程、webhook）                                              | **Control Center 機械人**，其提交的作者也是它。在 Control Center Connect 上，它從不推送或開啟 pull request |

- **你做的任何事**都只使用**你的**登入，不會用其他任何東西。如果你未登入，應用程式會請你登入。沒有任何其他憑證會頂替你
- **機械人工作**每次會取得一個只適用於一個程式庫的權杖，並限制在負責成員在那裏能做的事：提出請求的成員，否則是工作區擁有者。無法推送的成員會把它限制為唯讀。代表某人行事的機械人回覆會以 **Control Center (for @login)** 開頭
- **代理透過 Control Center 開啟 pull request**，絕不從它們的沙箱中開啟，因此該 pull request 是你的，而 GitHub 自身的規則會阻止你批准它。Control Center 也會拒絕請代理執行該工作之人自己的批准，以及來自 pull request 作者的批准。對於排程或 webhook 執行，這涵蓋了在其啟用期間啟用其觸發條件或編輯其流程的每位管理員。必須由其他人審查。若 Control Center 無法確認是誰開啟了 pull request，或代碼託管平台上哪個帳戶是你的，它會拒絕並請你重試
- **代理也透過 Control Center 留言。** 代理執行獲得的 GitHub 權杖只能讀取。當代理在它正在處理的 pull request 上留言時，Control Center 會以機器人身分發佈留言，若是有人請求該次執行，則以 **Control Center (for @login)** 開頭。代理只能在它自己的 pull request 上評論：必須是同一程式庫中的（不是 fork），且其最新提交由該代理推送，或為其空間分支的目前提交。代理評論中的 @ 提及不會通知任何人。代理也可以在其自己的 pull request 仍然開啟時，修改該 pull request 的標題或描述。該修改會按開啟該 pull request 的方式進行（若是你請求的執行，則以你的身分），預設會先請求核准。pull request 的描述會保留其中的 @ 提及，無論代理是打開還是修改它，它所點名的人都會收到通知
- **在 Control Center Connect 上，機器人從不推送或開啟 pull request。** 在那裡推送、建立分支或開啟 pull request，需要請求的人，並以該人的登入執行。排程或 webhook 觸發的執行若試圖推送，會停止並顯示說明訊息。若要讓無人看管的執行能夠推送，請在**設定**中為工作區提供自己的 GitHub App
- **Connect 機器人能做什麼。** 在共用的 Connect 應用程式上，機器人會留言、加標籤並作出反應。只有在 Connect 營運者已列入此伺服器的安裝時，它才會張貼審查（AI 審查、審查留言、審查者請求）。否則，審查會以負責任的人自己的登入發出，並以其名義顯示。機器人從不開啟、編輯、關閉或改名 pull request，也從不撤銷審查，或編輯或刪除留言；這些需要請求的人以自己的登入來完成。Connect 不會把你組織的安裝綁定到單一 Control Center 伺服器：任何有成員能推送至程式庫並透過 Connect 登入的伺服器，都能取得該程式庫的機器人留言權杖
- **擁有自己 GitHub App 的伺服器或工作區**，對以上所有工作（包括審查）都保留機器人身分
- **自動化永遠不會批准** pull request。批准是人的行為

當你連結程式庫時，Control Center 會檢查你的帳戶是否看得到它，並在 GitHub App 未安裝在其組織上或未包含該程式庫時發出警告，同時附上修正的連結。連結與取消連結都需要工作區管理員；位於工作區自身儲存空間之外的工作副本，只能由伺服器擁有者連結；參見[將程式庫加入工作區](/zh-HK/手冊/操作指南/加入程式庫/)。

程式庫的連結跟隨其永久的 GitHub id，因此改名或轉移不需要你做任何事。若路徑之後指向另一個程式庫，Control Center 會停止向它傳送任何東西，並顯示通知，直到工作區管理員按下**重新連接**。

開啟程式庫的程式碼（檔案、diff、搜尋、終端機）需要你在工作區中的授權，以及你本人能讀取它的 GitHub 登入。工作區管理員遵循同一規則；只有伺服器擁有者享有豁免。

## 整合為你帶來甚麼

| 功能                 | 運作方式                                                                                                       |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| PR 清單與詳情        | 由伺服器以你自己的登入呼叫 GitHub REST API                                                                     |
| 檢查執行             | GitHub Checks API                                                                                              |
| 發佈審查             | 一個需經使用者確認的步驟，會以你的身分把你的審查發佈到 PR                                                      |
| 程式庫註冊           | 只要檢出副本的 `origin` 遠端指向 github.com，或指向 gitlab.com / bitbucket.org，就會被接受                     |
| 代理的 GitHub 存取   | 在執行中，`git fetch` 經由 Control Center 進行，由它以執行永遠不持有的唯讀權杖讀取該次執行所處理的各個程式庫。`gh` 使用唯讀權杖讀取它們，該權杖由 Control Center 在被請求時簽發，並在執行結束時撤銷。推送、pull request、對它們的編輯及留言都經由 Control Center |
| 通知提示             | 伺服器端輪詢你的 GitHub 通知收件箱，觸發「在 pull request 中被提及」與「已請求審查」                           |
| 使用者個人資料       | 個人資料懸浮卡，以及按作者篩選 PR                                                                              |

部分路徑在更划算的地方會改用 GraphQL API 而非 REST：例如供撰寫 PR 選擇器使用的
分支活動，以及決定某則已請求審查通知是否仍在待處理的即時審查狀態。

## 留意 GitHub 服務中斷

當某個供應商降級時，標題列會顯示一個狀態標籤，涵蓋 GitHub、Claude、OpenAI
和 Kimi。**一切正常時它是隱藏的**：它的出現是在報告問題，而不是報告沒有問題。

按一下該標籤會開啟一個浮出面板，列出每個供應商的狀態，並帶有一個重新整理
按鈕。這些狀態每兩分鐘會自行重新整理。

## 了解代理在 GitHub 上的行為

- 在 GitHub 工作樹中工作的代理會取得一個只適用於那一個程式庫的權杖。它只能讀取程式碼、issue 與 pull request；評論依上文所述經由 Control Center。推送會經由 Control Center，它會先詢問**推送至遠端**規則，然後以代理從不持有的寫入權杖轉送推送。 參見[設定沙箱政策](/zh-HK/手冊/操作指南/沙箱政策/)
- 你所發起的工作會以你的身分提交。當你要求代理做某件事，或在 IDE 中提交時，你是作者與提交者，使用你的託管平台已驗證的位址：你在 GitHub 登入時的 GitHub noreply 位址，或在 GitLab 與 Bitbucket 上你的登入所回報的電郵。只有在沒有任何程式碼託管平台為你的位址作保的儲存庫中，由你手動提交的提交才會使用工作區的 Git 身分。若你未登入該託管平台，代理的提交會改由機器人提交，執行的備註會說明原因
- 沒有人要求的工作會以機器人身分提交。排程或 webhook 執行會以工作區的 GitHub App 身分提交（`<app>[bot]`，附其 GitHub noreply 位址），或在沒有 GitHub App 或程式庫位於 GitLab 或 Bitbucket 上時，以 `Control Center <hi@usectrl.dev>` 身分提交
- **將 Control Center 加入為共同作者**（**設定** → **你** → **提交**）會為另一方加入 `Co-Authored-By:` 尾注：在你的提交上是 Control Center，在機器人的提交上則是觸發該次運行的每位設置者。除非你關閉它，否則預設啟用。工作區管理員可以在 **設定** → **工作區** → **一般** 中的**共同作者標示**為所有人決定；此時你自己的選擇仍會被儲存，但不會在該工作區中套用。Claude Code 自帶的署名一律停用
- 你的提交可以簽署。在 **設定** → **你** → **提交** 中的**已驗證的提交**之下，選擇**建立簽署金鑰**，並把其公開部分加入你的 GitHub 或 GitLab 帳戶作為簽署金鑰；此後，你所要求的運行之提交，以及你在 IDE 中作出的提交，都會顯示為已驗證。私有部分保留在你的伺服器上，因此只要金鑰仍在你的帳戶中，控制該伺服器的人便可以以你的身分簽署提交；而在 GitHub 上，已顯示為已驗證的提交在你移除金鑰後仍會保持已驗證。Bitbucket 沒有僅用於簽署的金鑰：請勿在那裏加入該金鑰，且 Bitbucket 上的提交不會被簽署。機器人的提交從不簽署
- 你在 IDE 的 **原始檔控制** 面板中作出的提交會略過程式庫的 Git hook，如同 `git commit --no-verify` 一樣；伺服器的 Git 會忽略程式庫所設定的憑證輔助程式、編輯器、外部 diff 工具與簽署程式：它在自己的機器上執行 Git，所處理的工作樹可能會被代理或 pull request 更改。參見[從原始檔控制提交與推送](/zh-HK/手冊/操作指南/審查並合併-pr/#從原始檔控制提交並推送)
- 代理推送的每個提交都會先經過檢查，包括 `stack_publish` 為堆疊推送的各層。推送若指明他人、移除或借用任何一項署名、加上 sign-off，或未依你的設定簽署，將會被拒絕。你自己從 IDE 推送的提交屬於你，不以這種方式檢查
- 你在測試機上開啟的終端機會取得你自己的登入，並限制到那一個程式庫，因此在那裏
  的推送是你的
- 無法簽發權杖時（沒有任何負責人登入、應用程式沒有安裝在擁有者上，或該安裝已被
  暫停），請求權杖的指令會說明原因。沒有任何後備憑證

## 疑難排解

### PR 清單是空的，並顯示 GitHub 尚未連接

你未在這部伺服器上登入 GitHub。請在**設定 → 你 → 個人資料 → 程式碼託管**下按一下**登入 GitHub**。其他
託管平台上的程式庫不受影響。

### GitHub 一列表示此伺服器尚未設定登入

伺服器既沒有自己的 GitHub App，也沒有 Connect。由伺服器擁有者在 **設定 → 伺服器
→ 單一登入** 中選擇其一：**建立我的 GitHub 應用程式**約需兩分鐘。參見
[建立 GitHub App](/zh-HK/手冊/操作指南/github-app/)。

在選擇了自家應用程式的工作區中，該列會說明工作區的 GitHub App 缺失或不完整。工作區管理員在 **設定 → 工作區 → 整合** 的 **GitHub 應用程式**卡片中把它補齊；參見[為單一工作區提供自己的應用程式](/zh-HK/手冊/操作指南/github-app/#為單一工作區提供自己的應用程式)。

### 對話框表示代碼不相符

請完全按照瀏覽器顯示的內容輸入代碼：8 個字母和數字。輸錯五次會結束這次登入；
請重新開始。

### 登入表示應用程式未安裝

GitHub App 在擁有該程式庫的帳戶上沒有任何安裝。由工作區管理員從 **設定 → 工作區
→ 整合 → GitHub 應用程式安裝** 進行安裝。

### 所有人都要重新登入 GitHub

伺服器擁有者輪替了伺服器的 Connect 金鑰、切換了 Connect 伺服器，或資料目錄被還原
到另一部機器上。經由 Connect 的登入會綁定到建立它們的那部伺服器。

### 加入程式庫被拒

註冊需要同時滿足以下三項：路徑位於 git 工作樹內、它有一個 `origin` 遠端，
而且該遠端指向受支援的程式碼託管平台（github.com、gitlab.com 或
bitbucket.org）。`origin` 必須是你要連結的程式庫，而位於工作區自身儲存空間之外的資料夾只能由伺服器擁有者連結。參見[將程式庫加入工作區](/zh-HK/手冊/操作指南/加入程式庫/)。

### 我有授權，但程式庫顯示我的帳戶無法讀取它

你的 GitHub 帳戶無法讀取該程式庫，因此即使有工作區授權，其程式碼仍對你關閉。請在**程式碼託管**下登入 GitHub，或在 GitHub 上請求存取該程式庫的權限。

### 「無法確認你的 GitHub 存取權限」

GitHub 無法連線以查核你的存取權限，因此 Control Center 拒絕了，而不是猜測。請稍後再試。

### 在 Connect 上，審查顯示為我的名字，而非機器人

在共用的 Connect 應用程式上，機器人只會為 Connect 營運者列入清單的安裝張貼審查。在其他地方，審查會以負責任的人自己的登入發出。若要讓機器人張貼審查，請為工作區提供自己的 GitHub App。

### 大量使用後，一切都會停擺一陣子

那是速率限制的斷路器。GitHub 以帶有 `x-ratelimit-remaining: 0` 的 `403` 及
一個重置時間來表示已達主要限制；用戶端一旦看到，就會在該時窗過去前，令後續
請求在本機失敗，不發出網絡呼叫，因此重試風暴無法加深限制。暫時性失敗會以
指數退避最多重試三次，並遵循 `retry-after`。
