本指南涵蓋設定中專屬於 GitHub 的部分。GitHub 是三種受支援的程式碼託管平台
之一 —— 連接 GitLab 或 Bitbucket，以及同一個工作區如何混用它們，請參見
[連接程式碼託管](/zh-HK/手冊/操作指南/連接程式碼託管/)。

## 先決條件

- 一個 GitHub 帳戶，且能存取你想處理的程式庫
- 或者為你的伺服器註冊一個 GitHub App（參見
  [建立 GitHub App](/zh-HK/手冊/操作指南/github-app/)），讓你得以**登入**；
  **或者**準備一個帶 `repo` 和 `read:org` 權限、可供貼上的個人存取權杖

:::note[憑證存放在伺服器上，並歸屬於你]
你正在輸入的那部機器上不會儲存任何東西。你的憑證由你的 `cc_server` 持有，
以你的使用者 id 為鍵，你登入的每部裝置都會使用它 —— 桌面端、網頁版和手機。
同一伺服器上的其他成員無法讀取它，而為他們登入這件事，得由他們自己完成。
:::

## 使用 GitHub 登入

這是一種**裝置流程**：GitHub 向你顯示一組簡短的代碼，你在 github.com 上批准
它，伺服器隨即收到憑證 —— 沒有回呼 URL，沒有連接埠，也沒有任何東西需要對外
暴露。只要伺服器有用戶端 ID 就可用，而官方組建已經隨附。

1. 前往 **設定 → 工作區 → 個人資料與身分 → 程式碼託管**（或新手導引的第一步）
2. 在 **GitHub** 一列上，按一下 **使用 GitHub 登入**
3. 對話框會顯示一組八個字元的代碼，並在你的瀏覽器中開啟
   [github.com/login/device](https://github.com/login/device)。
   代碼已經複製到你的剪貼板
4. 貼上代碼，批准該應用程式，然後返回。該列會自行變成
   「已登入為 _your-username_」

你可以在瀏覽器中繼續操作期間關閉該對話框 —— 伺服器會持續輪詢，直到代碼過期
（約 15 分鐘），所以登入仍然會完成。

## 或貼上權杖

當伺服器沒有應用程式、應用程式未安裝在你要用的帳戶上，或者你乾脆更想使用
PAT 時，這便是後備方案。

1. 前往 **設定 → 工作區 → 個人資料與身分 → 程式碼託管**
2. 在 **GitHub** 一列上，按一下 **新增權杖**
3. 貼上一個帶 `repo` 和 `read:org` 權限的權杖（經典）並儲存。**精細權限**權杖
   則需要程式庫的 **Contents** 和 **Pull requests**（讀取及寫入），再加上
   **Checks** 和 **Actions**（讀取）。

權杖會在儲存時即時探測，因此該列能指出它屬於哪個帳戶。
按一下 **中斷連線** 即可將它移除。

檢查點：**GitHub** 一列顯示「已登入為 _your-username_」。當應答的憑證不是你的，
末尾會標出來源 —— 「透過此伺服器的應用程式」或「來自環境變數」。

:::note[優先次序固定不變]
以你的名義發出的請求只會使用**你的**憑證，不會用其他任何東西 —— 環境是伺服器
的憑證，而不是你的，所以它永遠不會頂替你。沒有真人參與的工作（webhook、PR
輪詢、工單同步）會先使用伺服器的應用程式身分，然後是伺服器擁有者的憑證，
最後才是環境。
:::

## 整合為你帶來甚麼

| 功能                 | 運作方式                                                                                                       |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| PR 清單與詳情        | 由伺服器呼叫 GitHub REST API，以應用程式身分或你自己的憑證                                                    |
| 檢查執行             | GitHub Checks API                                                                                              |
| 發佈審查             | 一個需經使用者確認的步驟，會把你的審查發佈到 PR                                                                |
| 程式庫註冊           | 只要檢出副本的 `origin` 遠端指向 github.com —— 或指向 gitlab.com / bitbucket.org —— 就會被接受                 |
| 代理的 GitHub 存取   | 憑證仲介會把權杖以 `GH_TOKEN` / `GITHUB_TOKEN` 注入，並受代理的能力所限                                        |
| 通知提示             | 伺服器端輪詢你的 GitHub 通知收件箱，觸發「在 pull request 中被提及」與「已請求審查」                           |
| 使用者個人資料       | 個人資料懸浮卡，以及按作者篩選 PR                                                                              |

部分路徑在更划算的地方會改用 GraphQL API 而非 REST —— 例如供撰寫 PR 選擇器
使用的分支活動，以及決定某則已請求審查通知是否仍在待處理的即時審查狀態。

## 留意 GitHub 服務中斷

當某個供應商降級時，標題列會顯示一個狀態標籤，涵蓋 GitHub、Claude、OpenAI
和 Kimi。**一切正常時它是隱藏的** —— 它的出現是在報告問題，而不是報告沒有
問題。

按一下該標籤會開啟一個浮出面板，列出每個供應商的狀態，並帶有一個重新整理
按鈕。這些狀態每兩分鐘會自行重新整理。

## 了解代理在 GitHub 上的行為

- 代理只有在具備**允許 GitHub API 呼叫**或**允許 git push**時，才會取得
  GitHub 權杖。參見[設定沙箱政策](/zh-HK/手冊/操作指南/沙箱政策/)
- 代理所作的提交以**代理的身分**署名 —— 顯示名稱加上 ` (agent)`，位址則是
  以代理的 id 為鍵的合成地址 —— 絕不會以真人身分署名。提出要求的人則透過
  `Co-Authored-By` 尾註記入貢獻
- 設定好 GitHub App 後，仲介會在每次啟動時簽發精細權限、限定至程式庫、
  有效期約一小時的安裝權杖，而不是交出一枚權限寬泛的權杖。安裝實例會依該次
  執行的程式庫**擁有者**來解析，因此一個安裝在多個帳戶上的應用程式，會正確
  限定到該次執行所觸及的那一個。沒有應用程式時，代理收到的是環境權杖
- 由已登入成員要求的執行，會以**該成員的** GitHub 身分行事 —— 其憑證會併入
  仲介的環境之後，因此代理代他們所作的提交或留言，都可以歸到他們名下

## 疑難排解

### PR 清單是空的，並顯示 GitHub 尚未連接

你在這部伺服器上沒有任何 GitHub 憑證。請在**程式碼託管**下登入或貼上權杖。
其他程式碼託管平台上的程式庫不受影響 —— 只有 GitHub 的程式庫不會貢獻任何
內容。

### 該列提供「新增權杖」，但沒有「使用 GitHub 登入」

伺服器沒有用戶端 ID —— 這是從原始碼組建的常態，因為憑證只會烘焙進官方組建。
參見[建立 GitHub App](/zh-HK/手冊/操作指南/github-app/)：大約只需兩分鐘，而且
只有伺服器擁有者需要動手，做一次即可。

### 登入對話框顯示供應商沒有回傳裝置碼

GitHub App 存在，但其 **Device flow** 核取方塊處於關閉狀態。請在該應用程式的
設定中（General → Device flow）將它開啟，然後重試。

### 該列顯示「透過此伺服器的應用程式」，但我預期的是自己的帳戶

你尚未登入；你看到的是伺服器的應用程式身分在應答。
請在該列按一下 **使用 GitHub 登入**。

### 精細權限 PAT 不顯示合併按鈕或檢查狀態

該權杖需要 **Contents** 和 **Pull requests**（讀取及寫入），再加上 **Checks**
和 **Actions**（讀取）。更改之後，請在程式碼託管下重新貼上。

### 加入程式庫被拒

註冊需要同時滿足以下三項：路徑位於 git 工作樹內、它有一個 `origin` 遠端，
而且該遠端指向受支援的程式碼託管平台（github.com、gitlab.com 或
bitbucket.org）。參見[將程式庫加入工作區](/zh-HK/手冊/操作指南/加入程式庫/)。

### 大量使用後，一切都會停擺一陣子

那是速率限制的斷路器。GitHub 以帶有 `x-ratelimit-remaining: 0` 的 `403` 及
一個重置時間來表示已達主要限制；用戶端一旦看到，就會在該時窗過去前，令後續
請求在本機失敗，不發出網絡呼叫，因此重試風暴無法加深限制。暫時性失敗會以
指數退避最多重試三次，並遵循 `retry-after`。
