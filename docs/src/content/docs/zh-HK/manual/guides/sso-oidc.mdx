當你的身分供應商使用 **OpenID Connect** 而非 SAML 時，請使用本指南。任何
通過 OIDC 認證的簽發者都適用 —— Pocket ID、Keycloak、Auth0、
Zitadel、Google Workspace 等全都遵循相同步驟；差別只在於
供應商顯示這些值的位置。

## 先決條件

- 一個可讓你建立用戶端的 OIDC 供應商 —— 記下其**用戶端 ID**
  及其**簽發者 URL**（`.well-known/openid-configuration`
  文件所在的基底），此外若用戶端屬於機密類型，還需其
  **用戶端密鑰**（公開的
  PKCE 用戶端則沒有），
- 一部由你管理的 Control Center 伺服器（即**伺服器擁有者**）。

## 步驟

1. 開啟 **設定 → 伺服器 → 單一登入**，並切換到
   **OpenID Connect**。
2. 填入 **簽發者 URL**、**用戶端 ID**，以及供應商有簽發時的
   **用戶端密鑰（選填）**。Control Center
   會從簽發者的標準探索文件探索端點 ——
   毋須逐個供應商設定。
3. 在供應商一方，於該用戶端註冊重新導向位址
   `https://<your-server>/oidc/callback`。
4. 若你的群組位於 `groups` 以外的宣告之下，請設定
   **群組宣告**名稱；如需要，可將群組對應到角色（SSO 永遠無法
   授予擁有者角色）。
5. 選擇成員政策（自動加入每個工作區，或每個工作區都需要個別
   邀請），開啟 **使用 OpenID Connect 登入**，然後
   按下 **儲存連線**。
6. 按下 **測試連線** —— 伺服器會擷取簽發者的探索
   文件並確認其端點，因此綠色的提示訊息代表除了瀏覽器往返之外
   一切正常。若要一併檢查用戶端註冊，
   請使用[下方的檢查器](#從本頁檢查你的設定)。
7. 進行一次登入：網頁連接畫面會顯示 **以 OpenID
   Connect 登入**，或直接開啟 `https://<your-server>/oidc/login`。

你的伺服器會透過 TLS 從簽發者的權杖端點讀取宣告（電郵、姓名、群組）
—— 瀏覽器從不提供這些資料，因此不涉及本機 JWT
簽章驗證。應允許該用戶端要求
`openid profile email` 範圍，而這正是 Control Center 所要求的。

由於該 TLS 通道是驗證這些宣告的唯一途徑，簽發者 URL 必須為
**https** —— 明文簽發者會讓任何路徑上的攻擊者任意
偽造身分。僅在本機開發時，回送簽發者
（`localhost`、`127.0.0.1`、`::1`）才接受 `http`。

:::note[公開用戶端還是機密用戶端？]
預設（也是建議）的形態是**公開用戶端**，使用
授權碼流程配合 **PKCE**（RFC 7636）：伺服器持有的一次性
驗證碼驗證器會取代密鑰，而權杖交換會
繫結到啟動它的授權請求。既沒有密鑰可洩漏，被竊取的授權碼
沒有驗證器也毫無用處。部分供應商在你建立時
會把這種用戶端類型稱為「SPA」或「原生」。

若你的供應商改為簽發**機密**用戶端，可在供應商一方將該
用戶端標記為公開（無論哪種做法，PKCE 都會保持開啟），或把
用戶端密鑰貼到連線的**用戶端密鑰（選填）**欄位。該
密鑰會儲存在伺服器的 0600 密鑰檔案中（絕不會存入資料庫），
以 `client_secret_post` 傳送到權杖端點，且永不經由
RPC 回傳；儲存時將欄位留空會保留已儲存的密鑰。當登入
在權杖交換階段失敗時，伺服器日誌會指出供應商本身的錯誤
（`invalid_client` 幾乎總是表示密鑰缺失或錯誤）。
:::

:::note[可達性]
登入本身由瀏覽器居中進行：簽發者只會將使用者的
瀏覽器重新導向回 `/oidc/callback`，而你的伺服器會對權杖端點
發出對外 HTTPS 呼叫 —— 不需要來自簽發者的連入連線，
因此只要使用者的瀏覽器能連到它（LAN、VPN、Tailscale 或隧道），
位於 NAT 之後的伺服器也能運作。**SCIM 佈建則是
例外**：IdP 會直接呼叫你的伺服器，這需要隧道或
公開 URL —— 參見[以 SCIM 佈建用戶](/zh-HK/手冊/操作指南/sso-scim)。
:::

## 既有帳戶如何比對登入

透過身分供應商的登入會依以下順序找到它的帳戶：

1. **已釘選的身分。** 第一次 SSO 登入會把供應商的主體（簽發者加上 `sub`）釘選到該帳戶。之後以該主體登入的每一次，都會是同一個帳戶。
2. **雙方都已驗證的電郵。** 否則，只有當供應商傳送 `email_verified: true`，而帳戶的地址也已驗證時，登入才會以電郵比對帳戶。地址在由 SSO 或 SCIM 設定，或由伺服器擁有者確認時即已驗證。擁有者自己的地址也算在內。

電郵地址會以小寫儲存及顯示，比對時不區分大小寫。已驗證的地址只有在恰好一個帳戶持有它時才能識別帳戶；若兩個帳戶持有同一個已驗證地址，它便與兩者都不相符。

有人在自己的個人資料中輸入的地址，或在邀請中輸入的地址，都未經驗證，也不會與任何帳戶相符。編輯地址會清除其驗證狀態，直到有人再次為它作保。登入永遠不會以用戶名比對。

若沒有任何相符，登入會在**首次登入時佈建未知使用者**開啟時建立新帳戶，關閉時則被拒絕。

### 在既有帳戶的用戶開啟 SSO 之前

請先確認他們的地址。開啟**設定 → 伺服器 → 人員**，每個帳戶在有人為其作保之前都會顯示**電郵未確認**，然後在每個人的資料列上使用**確認電郵**。只有伺服器擁有者能看到此列表。若不這樣做，他們每一位在首次 SSO 登入時都會得到第二個帳戶，或在關閉**首次登入時佈建未知使用者**時被拒絕。

當其地址未確認時，用戶在自己個人資料的電郵欄位下會看到「只有你自己輸入了這個地址。在伺服器擁有者確認之前，單一登入不會與它比對。」

### 不傳送 `email_verified` 的供應商

有些供應商會省略該宣告。Microsoft Entra ID 預設即是如此。缺少的宣告並不等於是，因此對這類供應商而言，登入只會以已釘選的身分比對，而用戶的首次登入永遠無法以電郵找到既有帳戶。以 SCIM 佈建帳戶也無助於該次首次 OIDC 登入。可行的做法有：

- 保持**首次登入時佈建未知使用者**開啟，讓首次登入建立帳戶，或
- 設定供應商發出 `email_verified`，然後如上確認相符的地址。

## 疑難排解

### 開啟 SSO 後有人多了一個帳戶

他們既有帳戶的地址在首次以 SSO 登入時尚未驗證，因此該登入沒有與之比對，而是建立了一個新帳戶。這發生在地址是在其個人資料或邀請中輸入，而伺服器擁有者尚未確認它時；或供應商沒有傳送 `email_verified: true` 時。由供應商為地址作保的新帳戶會取得該地址，而原本只是輸入了它的舊帳戶則會失去它。

為了讓下一位用戶避免此情況，請在他們登入前於**設定 → 伺服器 → 人員**中確認地址。對於已有兩個帳戶的人，新帳戶會釘選到其 SSO 身分，因此從現在開始，他們的登入會使用這一個帳戶。

### 「此帳戶已連結至另一個 SSO 身分」

登入是以已驗證的電郵比對到某帳戶，但該帳戶已釘選到另一個主體或另一個簽發者：供應商處的另一位用戶、同一人在新供應商下的身分，或由 SCIM 以其自身識別碼建立的帳戶。已釘選的帳戶會拒絕所有其他身分，因此供應商處一個被回收的地址無法奪取它。請以該帳戶最初連結的身分登入。
