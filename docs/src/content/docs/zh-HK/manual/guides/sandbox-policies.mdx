一次代理執行是否受沙箱包裹，是在伺服器啟動時決定的（`--sandbox`）。
**啟用沙箱**開關與 **設定 → 伺服器 → 診斷與私隱** 下的**後端**選擇器，都是
儲存在你裝置上的偏好設定。**沙箱**卡片的主機探測所報告的，只是伺服器主機
能夠包裹甚麼。

有兩個控制項能觸達一次執行，本指南兩者都會說明：**設定 → 工作區 → 代理權限**
中的動作規則——它們決定代理可以推送、開啟或存取甚麼——以及伺服器自己的
`--sandbox` 標誌。

## 甚麼在約束一次代理執行

有六樣東西在約束代理。第一樣是作業系統沙箱，也是唯一有條件的一樣——
其餘五樣在每部主機上都成立。

| 界線             | 它的作用                                                                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作業系統沙箱     | macOS 上是 Seatbelt，Linux 與 WSL2 上是 bubblewrap。包裹 Claude Code CLI、ACP 配接器與執行框架的 `bash` 工具。**在 Windows 上，以及缺少 `bwrap` 和 `socat` 的 Linux 上缺席，那裏只有伺服器擁有者的執行會啟動** |
| 它自己的 worktree | 每則對話都會得到一個寫入時複製的檢出。原始檢出會以拒絕寫入路徑的形式併入該次執行，而真正強制執行它的是沙箱                                                        |
| 憑證代理簽發的憑證 | 憑證代理會為每次執行簽發一份環境，並在拆除時撤銷它。其中的 GitHub 權杖可以讀取但不能推送：推送會經由 Control Center，它會先詢問推送規則 |
| 動作護欄         | 每個會變更狀態的工具都會宣告自己的效果類別，而護欄會在呼叫執行之前解析它們。未連接核准人時，`prompt` 會被拒絕                                                        |
| 環境淨化         | ACP 與執行框架的 `bash` 工具會得到一個過濾後的環境。經由 `NoSandboxAdapter` 的 Claude Code 則會繼承主機環境                                                        |
| 模式的工具介面   | 唯讀模式會直接移除會改動 worktree 的工具，並釘住該模式自己的輸出動詞，使它仍能交付                                                                                  |

有三件事比它們看上去更弱：

- 只有**內建執行框架**會強制執行工具閘門、完成契約與結構性模式規則。
  Claude Code 配接器不會。Claude Code 尤其是以
  `--dangerously-skip-permissions` 啟動的，因為非互動式的 `claude -p` 否則
  會永遠卡在自己的提示上——所以 Claude 自己的 read、write 與 edit 呼叫，
  既不會被 Control Center 看見，也不受它閘控，bash 命令也只由一個讀取命令列
  的鉤子檢查。沙箱開啟的地方，它就是圍住它們的界線。
- 執行框架的行內檔案工具（read、write、edit、apply patch、search、
  find、search_files）在伺服器行程內執行，因此沒有任何沙箱設定檔約束它們。
  只有 `bash` 工具會經過受沙箱包裹的指令執行器。這些工具的界線，是它們自身
  的路徑限制加上動作護欄。
- 在沒有後端的主機上，只有負責某次執行的人是伺服器擁有者時，該執行才會啟動，而對這些執行，第一行完全不適用。其他人的執行會被拒絕。在 `--sandbox off` 之下，每位成員的執行都會在沒有第一行的情況下啟動。無論如何，ACP 與執行框架的 `bash` 工具都會退回環境淨化加上指令政策，Claude Code 則經由 `NoSandboxAdapter` 繼承主機環境。伺服器會在其啟動日誌中說明你處於哪種情況。在下面檢查你自己的情況。

## 決定代理可以推送甚麼

git push、GitHub、工單與網絡都沒有按代理設定的開關。每一項都是一條動作規則：

| 規則                       | 內建預設 | 涵蓋範圍                                                          |
| -------------------------- | -------- | ----------------------------------------------------------------- |
| **推送到遠端**             | 先詢問   | 每一次推送到 GitHub 的 `git push`，無論使用哪個配接器             |
| **開啟 pull request**      | 先詢問   | Control Center 的 pull request 工具。`gh pr create` 在執行中無法使用                             |
| **更新或合併 pull request** | 先詢問   | 代理在其 pull request 上的留言、對其標題或描述的編輯及已發佈的審查，均透過 Control Center 的工具進行。`gh pr comment`、`gh pr edit`、`gh pr review`、`gh pr merge` 和 `gh pr close` 在執行中無法使用     |
| **寫入外部追蹤器**         | 先詢問   | 透過 Control Center 工具與 `gh issue` 寫入工單                    |
| **存取網絡**               | 允許     | 沙箱是否有網絡，以及執行框架的網頁工具                            |

1. 前往 **設定 → 工作區 → 代理權限**
2. 選擇範圍——**工作區**、**代理**或**空間**——然後在該規則那一行選擇
   **允許**、**先詢問**或**拒絕**

限定分支的推送規則，例如拒絕推送到 `main` 的規則，同樣生效：請參見
[護欄](/zh-HK/手冊/概念/護欄/)。

檢查點：請代理推送一個分支。設為**先詢問**時，你會收到一則寫明程式庫與 ref 的
核准請求；設為**拒絕**時，git 會印出
`! [remote rejected] <ref> (Control Center policy: …)`。

每條規則如何作用於執行：

- **推送**是靠執行手中持有甚麼來強制執行。它的 GitHub 權杖只涵蓋該次執行的那一個
  程式庫，而且無法推送：它能讀取內容，並在負責的成員可以推送時於 pull request
  上評論。它的 git 設定會把每一次 GitHub 推送
  送往 `cc_server` 上的回送閘道，閘道先詢問規則，然後才用代理永遠看不到的寫入
  權杖轉送推送。閘道只會轉送到 worktree 自己的程式庫，或與工作區連結的 GitHub
  程式庫。這對每個配接器都成立。
- **來自 shell 的 pull request 與 issue** 會透過命令列被辨識：在執行框架的
  `bash` 工具中，以及經由鉤子在 Claude Code 的 `Bash` 工具中。隱藏命令的代理
  （腳本、`eval`、直接呼叫 API）能繞過這項檢查，但繞不過推送閘道。
- **工單金鑰**從不放入沙箱。代理透過 Control Center 的 MCP 工具寫入工單，這些
  工具會詢問規則。
- **網絡**會在執行開始時解析一次。**拒絕**會關閉沙箱的網絡；**允許**與**先詢問**
  會讓它保持開啟，而在**先詢問**下，執行框架的 `web_fetch` 和 `web_search` 工具
  仍會在每次呼叫時詢問。只要網絡開啟，GitHub 就一律在對外允許清單中。

:::note[執行的 GitHub 權杖從哪裏來]
權杖是為該次執行，從工作區的 GitHub App、伺服器自己的應用程式或 Control Center
Connect 簽發的，並且限制在負責的成員（提出請求的人，否則是工作區擁有者）對該
程式庫能做的事。它絕不是把某位成員自己的登入整個交出去，也沒有任何後備權杖：
無法簽發時，執行會在沒有權杖的情況下開始，並在其備註中說明原因。
:::

## 檢查你的代理執行是否受沙箱包裹

有兩件事決定它，而且兩件都在伺服器上：主機是否提供後端，以及 `--sandbox`
是否開啟。請按這個順序檢查它們。

1. 前往 **設定 → 伺服器 → 診斷與私隱**
2. 查看**沙箱**卡片。**主機**一項是指執行 `cc_server` 的那部機器，而不是你
   正在看的這部機器。**後端**欄位會列出**原生沙盒**（macOS 上的 Seatbelt，
   Linux 與 WSL2 上的 bubblewrap）或**無隔離**。**生效中**一項是這部裝置的
   偏好，而不是伺服器實際使用的包裹。
3. 查看伺服器的啟動日誌。它只會印出以下三行中的一行：
   - `agent sandbox ON` 加上後端備註：執行會受包裹
   - `no OS-native agent sandbox on this host` 加上安裝提示（如有）：只有伺服器擁有者負責的執行會啟動，且不受包裹，其他人的執行會被拒絕
   - `agent sandbox DISABLED by --sandbox off`：每位成員的執行都會啟動，且不受包裹
4. 伺服器啟動時印出的暴露行，以一個詞說明同樣的事：`sandbox=native`、`sandbox=off` 或 `sandbox=unavailable`。

`GET /healthz` 不會回報沙箱狀態，因此啟動日誌才是檢查手段。

只有伺服器擁有者可以決定在沒有沙箱的情況下執行。要為所有人這樣做，請以
`--sandbox off` 啟動伺服器，或設定 `CC_SERVER_SANDBOX=off`。之後每位成員的代理
都會在該機器上不受約束地執行，因此這是針對所有使用該伺服器的人作出的決定，並在
開機時作出一次。預設值是 `on`：主機有後端時會包裹每次執行；沒有後端時，則只啟動
擁有者的執行。

有兩種情況永遠不會得到原生沙箱的包裹。在 **Windows** 上，原生探測一律回報
不可用，也沒有任何東西可安裝，因此除非擁有者傳入 `--sandbox off`，否則只有伺服器
擁有者的執行會啟動。`microvm` 後端是另一回事（互動式終端機與測試機），並按它自己
的執行時進行探測閘控。在 **Linux 與 WSL2** 上，`bwrap` 和 `socat` 都必須位於
`PATH` 上；缺少它們時，探測會回報不可用，並指出缺少的套件，而且只有擁有者的執行會啟動。

在已安裝 bubblewrap 的 Linux/WSL2 上，對於代理之後才建立的檔案，標準政策的
密鑰檔案 glob 無法強制執行，因此每一次原生執行都會失敗，而不是悄然忽略這些規則，
擁有者的執行也不例外。因此，開機探測通過並不代表 Linux 上的派發能夠啟動：目前，
Linux 伺服器要不是以 `--sandbox off` 執行代理，就是僅對擁有者而言在沒有 bubblewrap
的情況下執行代理。`--sandbox off` 是一次刻意的無約束退出，而不是替代性的保安邊界。

## 了解模式已經禁止甚麼

模式按空間儲存，並以**模式預設**層的身分輸入護欄解析器。四種模式中有三種是
唯讀的，而唯讀模式會直接拒絕十二個效果類別：

| 模式                  | Worktree | 由預設拒絕的                                                                                                                                                                                    |
| --------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **代理**（`chat`）    | 可寫入   | 無——內建預設值適用                                                                                                                                                                     |
| **計劃**              | 唯讀     | 刪除檔案、寫入工作樹之外、建立提交、推送到遠端、開啟 pull request、發佈審查或合併、寫入外部追蹤器、安裝套件、執行程序、變更工作區結構、啟動或操控隔離環境（測試機）、在主機上執行指令                          |
| **審查**              | 唯讀     | 同樣這十二項。不能由使用者選擇——輸入列只提供代理、計劃與編排                                                                                                                |
| **編排**              | 唯讀     | 同樣這十二項                                                                                                                                                                          |

網絡存取與密鑰存取是唯讀模式刻意_不_拒絕的：研究正是唯讀模式存在的全部意義。

## 要求在操作執行前獲得核准

核准是一項護欄決定，而不是沙箱設定。

1. 前往 **設定 → 工作區 → 代理權限**
2. 在工作區、代理或空間範圍，把該操作類別設為**先詢問**

一項**先詢問**決定會中斷該次執行並詢問你。未連接核准人時，它會失效即拒絕，
該操作會被拒絕。完整的解析順序請見
[設定護欄](/zh-HK/手冊/操作指南/設定護欄/)。

## 故障排查

### 代理無法推送，而我從未拒絕過它

看看 git 印出了甚麼。`Control Center policy: …` 表示某條規則拒絕了這次推送，或
一個**先詢問**沒有得到回應。`… is not linked to this workspace` 表示推送目標既
不是 worktree 自己的程式庫，也沒有與工作區連結。
`Control Center has no GitHub credential that can push …` 表示無法生成推送權杖：
在該程式庫上安裝這個 GitHub App，或登入 GitHub。

### 我的代理執行被拒絕，並顯示「此伺服器沒有沙箱」

執行會顯示**代理需要此伺服器上的沙箱**，並附上「此伺服器沒有沙箱，因此只有其擁有者可以在此執行代理。擁有者可以安裝沙箱，或為所有人關閉沙箱功能。」伺服器的主機沒有作業系統沙箱，而該次執行負責的人並非伺服器擁有者，因此什麼都沒有啟動。若是排程、webhook 或其他自動化，負責的人是該自動化所綁定的人，而不是正在查看它的人。

只有伺服器擁有者可以改變這一點。在 Linux 與 WSL2 上，他們安裝 `bubblewrap` 與 `socat` 並重新啟動伺服器（但請先閱讀上面關於 Linux 的備註）。在 Windows 上沒有可安裝的後端。另一個選擇是以 `--sandbox off` 重新啟動伺服器，這會讓每位成員的代理都在該機器上不受約束地執行。

### 沙箱卡片回報沒有原生沙箱

那麼該主機上的代理執行就不會被 Seatbelt 或 bubblewrap 包裹：只有伺服器擁有者的執行會啟動，而它們所擁有的，就是剩下那些界線。在
Linux 與 WSL2 上，安裝兩個缺少的工具（`sudo apt-get install bubblewrap socat`）
然後重新啟動伺服器；啟動日誌隨後應顯示沙箱已開啟。在 Windows 上沒有原生後端可
安裝，因此請改為為擁有者自己的執行收緊護欄：參見[設定護欄](/zh-HK/手冊/操作指南/設定護欄/)。

### 代理觸及了 worktree 以外的檔案

是哪個工具觸及它，決定了這是否在預期之內。

執行框架的行內檔案工具（read、write、edit、apply patch、search、find、
search_files）在伺服器行程內執行，因此沒有任何沙箱設定檔適用於它們——
它們的界線是自身的路徑限制加上護欄。在有後端的地方，`bash` 指令或
Claude Code CLI _會_ 受包裹，而在任何模式下，你已註冊的檢出在那層包裹內
都是拒絕寫入的，包括它們經符號連結解析後的寫法（在 macOS 上，經由 `/tmp`
或 `/var/folders` 抵達的路徑會解析到 `/private` 之下，兩種寫法都會被
拒絕）。在 `--sandbox off` 之下，或是擁有者自己在沒有後端的主機上的執行，這些全都不適用。無論哪種情況，護欄都能直接拒絕
**寫入工作樹之外**。
