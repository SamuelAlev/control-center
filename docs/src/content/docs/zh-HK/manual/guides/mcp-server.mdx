本指南說明如何把外部 MCP 用戶端——Claude Code、編輯器、MCP Inspector——連接到 Control Center 自己的工具伺服器。

Control Center 註冊了 **110** 個工具，並透過 Model Context Protocol 以協定版本
`2024-11-05` 提供它們。有些你可能預期會有的工具系列完全從缺：沒有會議或日曆工具，也沒有項目工具。

## 找到端點

MCP 介面共用主要的 `cc_server` 監聽器。沒有另外的 MCP 連接埠。

| 端點   | 方法     | 用途                                            |
| ------ | -------- | ----------------------------------------------- |
| `/mcp` | `POST`   | Streamable HTTP 傳輸——用戶端溝通的就是這個      |
| `/mcp` | `DELETE` | 結束工作階段                                    |
| `/sse` | `GET`    | 伺服器推送的通知串流                            |

因此，預設的本機安裝位於 `http://127.0.0.1:9030/mcp`。

1. 前往 **設定 → 伺服器 → MCP 伺服器**
2. 查看 **MCP 伺服器**卡片——它會顯示執行中還是已停止，以及它正在監聽的連接埠

全新安裝時該介面預設為開啟，因此回送用戶端毋須調整任何設定即可使用。**應用程式啟動時開始**決定它在重新啟動後是否再次啟動；**開始** / **停止**是工作階段層級的控制項，不會改變該偏好設定。

伺服器預設繫結回送，因此除非你以 `--bind any` 啟動它，否則只有執行 `cc_server` 的那部機器可以連到該端點。

## 連接用戶端

把你的用戶端指向 Streamable HTTP 端點。具體的設定形式由你的用戶端決定；無論哪種方式，URL 都一樣。

```json
{
  "mcpServers": {
    "control-center": {
      "type": "http",
      "url": "http://127.0.0.1:9030/mcp"
    }
  }
}
```

### Claude Code

Claude Code 不會從專案的 `.mcp.json` 讀取這份設定——它把專案範圍的 MCP 伺服器擋在一個核准提示之後，而非互動式的 `claude -p` 永遠不會回應這個提示。請明確傳入設定：

```bash
claude --mcp-config /path/to/mcp.json --strict-mcp-config
```

`--strict-mcp-config` 讓 Claude 只使用該檔案，這樣同一個伺服器就不會再從專案中被發現並註冊兩次。

檢查點：請用戶端列出它的工具。你應該會看到涵蓋工單、空間、記憶、程式碼圖與審查的 `mcp__*` 項目。

## 在本機之外提供 MCP 服務

1. 在 **設定 → 伺服器 → MCP 伺服器**的**驗證權杖**資料列上，按**設定**並貼上權杖
2. 在每個 `POST /mcp` 請求上以 `Authorization: Bearer <token>` 傳送它

未設定權杖的介面會以 403 拒絕任何非回送的呼叫者。這是刻意採用的失敗即關閉設計：權杖正是讓主機外服務得以成立的前提。

權杖變更會立即套用到運作中的介面——毋須重新啟動。

:::note[`GET /sse` 從查詢字串取得權杖]
通知串流和其他所有路由一樣會檢查權杖，但瀏覽器的 `EventSource` 無法傳送 `Authorization` 標頭——因此 `/sse` 也接受以 `?token=<token>` 形式提供的權杖。沒有權杖時它會回應 401。
:::

## 把每次呼叫限定到一個工作區

每個涉及工作區範圍資料的工具都要求提供 `workspace_id`，缺少它的呼叫會被拒絕，而不會改為對照某個「目前」工作區來解析：

```json
{
  "workspace_id": "acme",
  "title": "Fix login bug",
  "priority": "high"
}
```

這個 id 就是你瀏覽器或應用程式 URL 中的那個：`/workspaces/<workspace_id>/…`。唯一的豁免是真正跨越工作區的工具，例如 `list_workspaces` 和資訊動態工具——資訊動態是按使用者劃分的，而代理沒有屬於自己的使用者，因此那些工具操作的是伺服器擁有者的動態。

程式庫範圍的工具還會額外檢查該程式庫是否已連結到該工作區。

## 了解介面會拒絕哪些呼叫

- **模式把關。** 呼叫會在伺服器端按發起呼叫的代理所在空間的模式來解析。處於唯讀模式的代理無法藉由省略 `space_id` 來觸達寫入工具——模式會改為從它作用中的執行查找。
- **動作護欄。** 變更類工具會宣告自己的效果類別，並走產品其餘部分所用的同一套政策。參見
  [設定護欄](/zh-HK/手冊/操作指南/設定護欄/)。
- **確認。** 某些具破壞性的工具會建立一份確認載荷，必須先獲得核准，呼叫才能繼續。

完整目錄會在 `tools/list` 中公佈，沒有任何探索層面的把關——外部 MCP 用戶端會拒絕呼叫不在其快取清單中的工具，因此隱藏工具只會把它們弄壞，而不是把它們整理乾淨。

## 疑難排解

### 用戶端看不到任何工具

- 檢查 **MCP 伺服器**卡片是否顯示執行中
- 檢查連接埠是否與你的 `cc_server` 連接埠一致
- 在 Claude Code 上，檢查你是否傳入了 `--mcp-config` 和 `--strict-mcp-config`

### 從並非伺服器的機器收到 403

尚未設定 Bearer 權杖。設定一個並傳送它。

### 工具呼叫失敗並顯示「Missing or invalid argument: workspace_id」

加入 `workspace_id`。並不存在隱含的工作區。

### 工具呼叫因為未知而被拒絕

[MCP 工具](/zh-HK/手冊/參考/mcp-工具/)列出了完整目錄。請完全按照那裏出現的名稱來呼叫。
