Każde ustawienie procesu można podać flagą CLI albo zmienną środowiskową;
pierwszeństwo ma flaga, potem zmienna środowiskowa, a na końcu wartość domyślna.
Wyjątkiem są poświadczenia dostawców — patrz [Aplikacje dostawców i Connect](#aplikacje-dostawców-i-connect).

:::caution[Nieznane flagi są po cichu ignorowane]
Parser argumentów jest napisany ręcznie i pomija wszystko, czego nie rozpoznaje, więc literówka (`--tls-key-file`, `--bindany`) nie daje żadnego błędu — serwer po prostu startuje z wartością domyślną. Gdy flaga wydaje się nie działać, sprawdź wiersze logu startowego. [Flaga trybu kodu](#tryb-kodu) z wartością, której nie przyjmuje, jest inna: serwer odmawia startu.
:::

## Aplikacje dostawców i Connect

Żadna kompilacja nie zawiera poświadczeń dostawców. Przy włączonym Control Center
Connect obsługuje każdego dostawcę, a te własne aplikacje pozostają zapisane, ale
nieużywane. Przy **Użyj własnych aplikacji** każdy dostawca działa na własnej
aplikacji serwera, gdy jest ona w pełni skonfigurowana, w przeciwnym razie jest
niedostępny. Aplikacja obszaru roboczego obowiązuje w każdym z tych przypadków.
Własne aplikacje ustawia się w **Ustawienia → Serwer → Logowanie
jednokrotne → Aplikacje dostawców** albo wypełnia jednorazowo z pliku `.env`
serwera. Nie ma dla nich flag: sekret w wierszu poleceń można odczytać przez `ps`.

| Zmienna                        | Znaczenie                                                                                     |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| `GITHUB_APP_ID`                | Identyfikator GitHub App serwera                                                              |
| `GITHUB_APP_PRIVATE_KEY`       | Jej klucz prywatny, w jednym wierszu z sekwencjami `\n`. **Tylko `.env`**                   |
| `GITHUB_CLIENT_ID`             | Jej identyfikator klienta, do logowania ludzi                                                 |
| `GITHUB_CLIENT_SECRET`         | Jej sekret klienta. **Tylko `.env`**                                                          |
| `GOOGLE_OAUTH_CLIENT_ID`       | Klient Google typu Web application należący do serwera                                        |
| `GOOGLE_OAUTH_CLIENT_SECRET`   | Jego sekret. **Tylko `.env`**                                                                 |
| `LINEAR_CLIENT_ID`             | Aplikacja Linear serwera (PKCE, bez sekretu)                                                  |
| `LINEAR_API_KEY`               | Klucz usługi Linear do automatyzacji. **Tylko `.env`**                                        |
| `KLIPY_APP_KEY`                | Własny klucz Klipy serwera do wyszukiwania GIF-ów, używany tylko pod **Użyj własnych aplikacji** |
| `CC_CONNECT_URL`               | `hosted`, `off` albo adres URL Connect. Blokuje wybór Connect; Ustawienia nie mogą go wtedy zmienić |
| `CC_SERVER_CONNECT_HOST`       | `on` montuje Control Center Connect pod `<server>/connect`, konfigurowany zmiennymi `CONNECT_*`. Zobacz [Uruchom serwer Connect](/pl-PL/podrecznik/poradniki/uruchamianie-serwera-connect/#osadź-connect-w-cc_server) |

Plik `.env` jest odczytywany z katalogu roboczego serwera, obok pliku
wykonywalnego albo z checkoutu źródeł powyżej; w Dockerze zamontuj go pod
`/app/bin/.env`. Serwer **odmawia startu** (kod wyjścia `78`), gdy
`GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_SECRET`,
`LINEAR_API_KEY` albo dowolna zmienna `SLACK_*SECRET*` jest wyeksportowana
w środowisku jego procesu, gdzie mógłby ją odczytać każdy proces potomny.
Wypełnianie z `.env` odbywa się raz dla każdego pola, więc późniejszej zmiany
w Ustawieniach restart nie cofnie. Pusta wartość jest odczytywana jako
nieustawiona.

Żadne poświadczenie forge nie pochodzi ze środowiska: GitHub, GitLab i Bitbucket
działają na własnym logowaniu lub tokenie członka albo na tokenach GitHub App dla
jednego repozytorium, ograniczonych do tego członka.

### `--sandbox`

Serwer sonduje host raz przy starcie i gdy backend jest dostępny, opakowuje
wykonywanie poleceń agentów w natywny dla systemu sandbox: `sandbox-exec`
(Seatbelt) w macOS oraz `bwrap` i `socat` w Linuksie i WSL2. Decyzja zapada raz
i obowiązuje do ponownego uruchomienia serwera. Są trzy wyniki, każdy widoczny
w linii ekspozycji przy starcie:

| `sandbox=`    | Kiedy                                                                          | Czyje uruchomienia agentów startują                                                                                                                                 |
| ------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `native`      | Backend jest dostępny i `--sandbox` ma wartość `on`                            | Wszystkich, opakowane                                                                                                                                               |
| `off`         | `--sandbox off`                                                                | Wszystkich, bez ograniczeń na tym hoście                                                                                                                            |
| `unavailable` | `--sandbox on` i brak backendu (Windows albo Linux bez `bwrap` i `socat`)      | Tylko uruchomienia, za które odpowiada właściciel serwera, bez ograniczeń. Pozostałe są odrzucane komunikatem „Ten serwer nie ma piaskownicy, więc agenty mogą tu uruchamiać tylko jego właściciel.” |

Dla automatyzacji osobą odpowiedzialną jest ta, z którą automatyzacja jest powiązana. Bez zapisanego właściciela serwera na hoście `unavailable` nie startuje żadne uruchomienie. W Linuksie i WSL2 z zainstalowanym bubblewrap natywne wysyłanie obecnie zawodzi zamknięcie dla każdego uruchomienia; zob. [Backendy sandboxa](/pl-PL/podrecznik/dokumentacja-referencyjna/backendy-sandboxa/#linux-bubblewrap).

`--sandbox off` to decyzja właściciela serwera dla wszystkich, którzy z niego korzystają: uruchamia agentów wszystkich członków bez ograniczeń na tej maszynie. Użyj jej na hoście, na którym sam profil sandboxa działa niepoprawnie, albo aby pozwolić członkom uruchamiać agentów na hoście bez backendu. Nie wymaga przebudowy, a serwer przez cały czas życia procesu zapisuje ostrzeżenie, więc ten stan nigdy nie pozostaje niemy.

### `--tool-deferral`

Uruchomienia wbudowanego harnessu wysyłają mały zestaw bezpośredni definicji narzędzi oraz indeks samych nazw pozostałych, których schematy wczytują się przy pierwszym użyciu albo które są wywoływane ze skryptu `repl`. Utrzymuje to stale widoczny zestaw w przedziale, w którym modele niezawodnie wybierają narzędzia. Zmierzone na rejestrze, który budują testy, standardowe narzędzia czatu wbudowanego agenta to 14 definicji: około 16,5 KB z `repl` (w tym około 4 KB samego `repl`, którego definicja nie może przekroczyć 4 096 bajtów), około 13 KB na serwerze, który nie może uruchamiać skryptów. Odroczone narzędzia przez cały czas można wywołać po nazwie, a `search_tools` znajduje je po intencji. Zobacz [Kontekst narzędzi i cache promptów](/pl-PL/podrecznik/koncepcje/kontekst-narzedzi/).

`--tool-deferral off` wysyła definicję każdego dopuszczonego narzędzia z góry, z tym że uruchomienie z `repl` nadal wywołuje ze skryptu narzędzia, które skrypt może wywołać. To wyłącznik bezpieczeństwa dla modelu, który źle radzi sobie z dwuwarstwową powierzchnią — flaga zamiast przebudowy. Dotyczy wyłącznie wbudowanego harnessu; `tools/list` MCP, który widzą klienci zewnętrzni, to pełny katalog, z wyjątkiem uruchomienia agenta na serwerze, który może uruchamiać skrypty w [trybie kodu](/pl-PL/podrecznik/koncepcje/tryb-kodu/).

### `--credential-gate`

Uruchomienie, którego poświadczenie dostawcy brakuje lub zostało wyczerpane,
trafia do **poczekalni**, a nie kończy się niepowodzeniem: operator dostaje prośbę
o naprawienie go, a uruchomienie wznawia się, jeśli to zrobi. Domyślny termin to
900 sekund (15 minut), ograniczany do 0–3600.

Termin jest celowo znacznie dłuższy niż w przypadku prośby o zatwierdzenie:
zatwierdzenie to decyzja, którą podejmuje się w kilka sekund, a naprawienie
poświadczenia oznacza otwarcie terminala, zalogowanie się i powrót. To właśnie ten
pułap powstrzymuje uruchomienie bez nadzoru — krok potoku, wyzwalacz cron, webhook
— przed czekaniem na kogoś, kto śpi. Gdy termin upłynie, uruchomienie kończy się
niepowodzeniem z komunikatem, którym i tak by się skończyło.

`--credential-gate=0` to wyłącznik bezpieczeństwa: nic nigdy nie trafia do
poczekalni, a błędne poświadczenie kończy turę dokładnie tak, jak przed powstaniem
tej bramki.

### Tryb kodu

[Tryb kodu](/pl-PL/podrecznik/koncepcje/tryb-kodu/) pozwala agentowi uruchomić skrypt w JavaScripcie, który wywołuje jego narzędzia. Nie ma flagi, która go włącza albo wyłącza: każde uruchomienie dostaje narzędzie `repl`, gdy serwer może uruchamiać skrypty, a publiczny serwer demo nie uruchamia żadnego.

Skrypty działają w `cc_codemode`, programie dołączonym do serwera w `bin/codemode/`. Serwer nie startuje bez niego: wypisuje jedną linię z nazwą tego, czego brakuje, i kończy działanie kodem `78`. Przy starcie uruchamia autotest blokady programu i wypisuje jedną linię (wyciszaną tylko przez `--log-level error`):

```text
cc_server: code_mode=available (cc_codemode 0.1.0 quickjs-ng 0.16.2 protocol 2; 16 scripts at once, at most 12 per workspace; up to 64 more runners kept for scripts waiting on a person; heap at most 1024 MiB per script)
cc_server: code_mode=unavailable (<reason>) — runs on this host get no repl tool; scripts never run without full lockdown
```

`unavailable` oznacza, że program nie może zablokować się na tym hoście, na przykład w kontenerze, którego profil bezpieczeństwa odrzuca jeden z jego kroków, albo że program nie jest buildem wydaniowym. Serwer działa normalnie, żadne uruchomienie nie dostaje `repl`, a ustawienia trybu kodu obszaru roboczego pokazują powód.

Serwer nadal sprawdza, czy skrypty mogą działać. Gdy program nie uruchamia się z powodu innego niż skrypt, serwer ponownie uruchamia autotest, najwyżej raz na minutę. Jeśli się nie powiedzie, serwer wypisuje linię `unavailable` z powodem i nie uruchamia skryptów: uruchomienia startujące w międzyczasie nie dostają `repl`, a uruchomienie, które już go ma, wywołuje narzędzia bezpośrednio ([Gdy skrypty nie mogą działać](/pl-PL/podrecznik/koncepcje/tryb-kodu/#gdy-skrypty-nie-mogą-działać)). Nadal sprawdza, najwyżej raz na minutę, a gdy autotest znów przejdzie, wypisuje linię `available` i ponownie uruchamia skrypty. Tylko autotest, który nie przeszedł przy starcie, wymaga restartu. Powód pokazany w ustawieniach obszaru roboczego ma usunięte ścieżki hosta; linia w logu zawiera go w całości.

Dwie flagi trybu kodu ograniczają to, czego mogą używać skrypty. `--code-mode-max-processes` ogranicza skrypty działające naraz we wszystkich obszarach roboczych (domyślnie dwukrotność rdzeni procesora, najwyżej 16; akceptowane wartości 1–64). Przy limicie 2 lub większym jeden obszar roboczy używa najwyżej limitu pomniejszonego o jedną czwartą, więc żaden pojedynczy obszar roboczy nie może zająć każdego miejsca, a czekające skrypty są przyjmowane po kolei między obszarami roboczymi. Skrypt czekający na zatwierdzenie albo odpowiedź człowieka oddaje miejsce innemu skryptowi i nie startuje żadnego wywołania narzędzia, dopóki nie dostanie odpowiedzi; zachowuje się najwyżej cztery razy tyle takich czekających skryptów, ile wynosi limit, z czego najwyżej trzy czwarte z jednego obszaru roboczego, a każdy może nadal liczyć w granicach własnego limitu czasu procesora. `--code-mode-max-heap-mb` to najwięcej pamięci, jaką może zużyć jeden skrypt.

Wartość, której te flagi nie przyjmują (liczba spoza zakresu albo coś, co nie jest liczbą), zatrzymuje serwer przy starcie (kod wyjścia `78`) z komunikatem wymieniającym przyjmowane wartości. Nigdy nie jest odczytywana jako wartość domyślna.

## Podpolecenia

| Polecenie                                     | Co robi                                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `cc_server`                                   | Uruchamia serwer aż do `SIGINT`/`SIGTERM`                                                           |
| `cc_server pair`                              | Tworzy urządzenie i wypisuje jego identyfikator oraz klucz parowania. Bezpieczne wobec katalogu danych, który serwer już obsługuje — działający serwer przejmuje urządzenie bez restartu |
| `cc_server connect <command>`                 | Pokazuje lub zmienia, którego Control Center Connect używa ten serwer, bez uruchamiania go       |
| `cc_server update`                            | Sprawdza, pobiera i weryfikuje nowsze samodzielne wydanie                                           |
| `cc_server --version`                         | Wypisuje wersję kompilacji i SHA gita — tę samą tożsamość, którą ogłaszają `/healthz` i uzgadnianie RPC |

### `pair`

| Flaga          | Domyślnie                                                 | Znaczenie                                                                                                                                                            |
| -------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device`     | `web-client`                                              | Identyfikator urządzenia. Platforma jest z niego wnioskowana, więc `--device desktop` tworzy wiersz komputera, a `--device ios`/`android` wiersz telefonu; wszystko inne jest traktowane jako klient webowy |
| `--label`      | nazwa platformy plus nazwa hosta tej maszyny              | Nazwa wyświetlana na liście urządzeń                                                                                                                                 |
| `--host`       | `localhost` albo `<this-host>` przy bindowaniu do wszystkich interfejsów | Host osadzany w wypisywanym adresie URL. Ustaw go na adres IP w sieci LAN albo host tunelu, z którym klient faktycznie się połączy                                     |
| `--client-url` | nieustawione                                              | Pochodzenie hostowanego klienta **webowego**. Dodaje link bezpośredni do zeskanowania i kod QR w terminalu                                                           |

`pair` przyjmuje też podstawowe flagi `--data-dir`, `--port` i `--bind`:
wybierają one katalog danych do zapisu i kształtują wypisywany adres URL serwera
(`ws` na loopbacku, `wss` przy `--bind any`). Ponowne uruchomienie `pair` dla tego
samego `--device` rotuje jego klucz i porzuca aktywne sesje tego urządzenia.
Utworzone tu poświadczenie **nie wygasa**, inaczej niż po 30 dniach ustawianych
przez parowanie w aplikacji.

:::caution[Kod QR z `--client-url` to nie kod QR telefonu]
`pair --client-url` wypełnia formularz połączenia klienta **webowego** (adres URL
serwera, identyfikator urządzenia i klucz we fragmencie adresu URL). Telefon paruje
się z innym ładunkiem, tworzonym w panelu parowania w aplikacji — pełnym
deskryptorem połączenia serwera plus terminem ważności. Tych dwóch nie można
używać zamiennie — zobacz [Sparuj urządzenie](/pl-PL/podrecznik/poradniki/parowanie-urzadzenia/).
:::

### `connect`

Odczytuje i zapisuje te same ustawienia co karta **Control Center Connect**
w **Ustawienia → Serwer → Logowanie jednokrotne**, bezpośrednio z katalogu
danych. Działający serwer przejmuje zmianę w ciągu 10 minut albo po restarcie.

| Polecenie                       | Co robi                                                                                                          |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `cc_server connect status`      | Wypisuje tryb, adres URL, to, czy blokuje go `CC_CONNECT_URL`, identyfikator instalacji, stan i źródło każdej ścieżki logowania (`own`, `connect` lub `off`) |
| `cc_server connect enable`      | Używa hostowanego Connect od Control Center                                                                      |
| `cc_server connect enable --url <url>` | Używa własnego Connect pod tym adresem URL (HTTPS albo `http` na loopbacku)                            |
| `cc_server connect disable`     | Przestaje używać Connect. Ludzi logują tylko własne aplikacje serwera                                            |

Bez polecenia domyślne jest `status`. Każde polecenie przyjmuje `--data-dir`.
`CC_CONNECT_URL` ma pierwszeństwo przed tym, co zapisują. Nieznane polecenie
kończy się kodem `64`. Tryby, tożsamość instalacji i kody stanu opisuje
[Control Center Connect](/pl-PL/podrecznik/dokumentacja-referencyjna/connect/).

### `update`

`--apply` zastępuje instalację; jest odrzucane, dopóki serwer nadal odpowiada na
skonfigurowanym porcie, chyba że podasz `--force`. `--allow-downgrade` zezwala na
starsze wydanie.

W przypadku instalacji, których nie jest właścicielem, polecenie odmawia od razu,
podając wyjaśnienie, a nie błąd:

| Środowisko                              | Wykrywane przez                             | Co mówi                                                          |
| --------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| Wbudowany serwer aplikacji desktopowej  | `CC_EMBEDDED=1` lub `CC_BOOTSTRAP_DEVICE_ID` | Zaktualizuj zamiast tego aplikację — instalator wymienia całe drzewo |
| Źródła uruchamiane przez `dart run`     | ścieżka skryptu kończy się na `.dart`       | Zaktualizuj je za pomocą gita                                    |
| Docker                                  | znaczniki kontenera                         | Pobierz nowszy obraz                                             |

## Cykl życia procesu

`cc_server` działa aż do `SIGINT` / `SIGTERM`. Steruje tym jedna dodatkowa zmienna
środowiskowa, ustawiana przez aplikację desktopową, a nie przez Ciebie:

| Zmienna                  | Efekt                                                                                                                                                                                                            |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CC_EXIT_WITH_PARENT=1`  | Serwer kończy działanie wraz z procesem nadrzędnym; wykrywa się to po zamknięciu przez rodzica końca zapisu jego potoku stdin. Aplikacja desktopowa ustawia ją, aby zawieszona aplikacja nigdy nie pozostawiła osieroconego serwera trzymającego katalog danych |

Ustaw ją samodzielnie tylko wtedy, gdy nadzorujesz `cc_server` jako proces potomny
i chcesz mieć tę samą gwarancję.

`DO_NOT_TRACK=1` (dowolna wartość inna niż pusta, `0` lub `false`) wyłącza własną
[analitykę użycia](/pl-PL/podrecznik/dokumentacja-referencyjna/analityka-uzycia/) serwera, nawet gdy przełącznik dla całego serwera
jest włączony. Klienci nadal stosują się do przełącznika.

## Układ katalogu danych

Domyślnym katalogiem danych jest `~/Library/Application Support/control-center`
w macOS, `%APPDATA%\control-center` w Windows oraz `$XDG_DATA_HOME/control-center`
(w przeciwnym razie `~/.local/share/control-center`) gdzie indziej. Względny wobec
bieżącego katalogu `.cc_server` jest używany tylko wtedy, gdy nie da się rozwiązać
żadnego katalogu domowego ani katalogu danych aplikacji.

Serwer utrzymuje katalog danych prywatny dla swojego konta (`0700`). Odmawia startu (kod wyjścia `78`), gdy nie może tego zapewnić, gdy `global.db` jest uszkodzona albo zapisana przez nowszą wersję, albo gdy nie da się odczytać jego pliku tożsamości.

| Ścieżka                           | Zawartość                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------- |
| `global.db`                       | Rejestr obszarów roboczych, użytkownicy, sparowane urządzenia, newsfeed i kolejka floty |
| `<workspaceId>/workspace.db`      | Jedna baza danych na obszar roboczy — agenci, przestrzenie, zgłoszenia, pamięć |
| `<workspaceId>/code_index.db`     | Graf kodu tego obszaru roboczego. Odbudowywany, gdy go brakuje, nigdy nie jest kopiowany zapasowo |
| `pre_upgrade/`, `<workspaceId>/pre_upgrade/` | Dwie najnowsze kopie bazy danych sprzed aktualizacji, która zmieniła jej format |
| `<workspaceId>/chat_credentials/` | Tokeny botów czatu jako zwykły JSON, dzięki czemu podróżują razem z obszarem roboczym |
| `secrets.json`                    | Klucze parowania, klucz instalacji Connect, aplikacje dostawców, logowania ludzi (zapieczętowane, gdy powstały przez Connect), sekrety webhooków, SSO (`0600`) |
| `backups/<timestamp>/`            | Jedna migawka instalacji — `manifest.json`, `global.db` i kopia każdego obszaru roboczego |
| `backups/exports/`                | Eksporty pojedynczego obszaru roboczego, `<workspaceId>-<timestamp>.db`         |
| `backups/transfer/`               | Obszar przejściowy dla pobieranych i wysyłanych kopii zapasowych; czyszczony przez trasę, która do niego zapisuje |
| `models/`                         | Modele osadzania, diaryzacji i mowy działające na urządzeniu                     |
| `codemode/` | Wersja deweloperska runnera trybu kodu, instalowana przez `scripts/natives/build_codemode.sh`; pakiety wydania zawierają go w `bin/codemode/` |
| `meetings/<meetingId>/`           | Zachowane nagrania audio spotkań                                                |
| `rigs/images/`                    | Zaimportowane obrazy dysków rigów (powierzchnia pulpitu QEMU)                    |
| `rigs/smolvm/<rigId>/`            | Stan wykonawczy microVM poszczególnych rigów (sekret brokera, `0600`)            |
| `rigs/smolvm-packs/`              | Wstępnie rozpakowane paczki maszyn — cache, który przyspiesza kolejne starty rigów |
| `rigs/tls/`                       | Urząd certyfikacji domeny deweloperskiej dla HTTPS rigów (klucze `0600`)         |
| `rigs/run/<rigId>/`               | Nakładki QEMU, obrazy seed i klucze poszczególnych maszyn wirtualnych (`0600`)   |
