Wszystko, co Control Center potrafi skopiować, przekazać lub przejąć, oraz dokładny kształt
każdego artefaktu. Aby faktycznie wykonać kopię zapasową, zobacz
[Kopia zapasowa i przywracanie](/pl-PL/podrecznik/poradniki/kopia-zapasowa-i-przywracanie/); wyjaśnienie,
dlaczego trwałość jest podzielona w ten sposób, znajdziesz w
[Obszary robocze i izolacja](/pl-PL/podrecznik/koncepcje/obszary-robocze/).

## Artefakty

Istnieją trzy artefakty kopiowania bazy danych, o różnych zakresach i zasadach usuwania.

| Artefakt                | Zapisywany przez             | Kształt                               | Obejmuje                      |
| ----------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **Migawka instalacji**  | `server.backupNow`           | **Katalog** ze znacznikiem czasu      | Każda baza danych w instalacji |
| **Kopia zapasowa obszaru roboczego** | potok `Workspace backup`  | Katalog ze znacznikiem czasu z jednym plikiem `.db` | Baza danych jednego obszaru roboczego |
| **Eksport obszaru roboczego** | `workspace.export`     | Pojedynczy **plik** `.db`             | Baza danych jednego obszaru roboczego |

Wszystkie są zapisywane za pomocą SQLite `VACUUM INTO`, co jest bezpieczne wobec działającej
bazy danych w trybie WAL: operacja bierze transakcję odczytu, tworzy zdefragmentowaną i spójną
transakcyjnie kopię i nigdy nie wymaga zatrzymywania serwera.

Te pliki i pobrane kopie **nie są szyfrowane w spoczynku** przez Control Center.
Szyfrowany end-to-end transfer chroni bajty w tranzycie między sparowanym
klientem a jego `cc_server`, zarówno w połączeniach bezpośrednich, jak i przez
przekaźnik. Chroń lokalną pamięć i kopie poza maszyną osobno; serwer i każdy
upoważniony odbiorca mogą odczytać pliki baz danych.

## Układ migawki

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Układ dokładnie odwzorowuje działający katalog danych i właśnie dlatego przywrócenie instalacji
jest skopiowaniem go z powrotem, a nie tłumaczeniem. Nazwa katalogu to znacznik czasu UTC
z `:` i `.` zastąpionymi przez `-`, dzięki czemu jest bezpieczna dla systemu plików w Windows
i sortuje się chronologicznie jako zwykły ciąg znaków.

Zaplanowane kopie zapasowe obszarów roboczych leżą osobno w
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Każda ma `manifest.json` tylko dla tego jednego pliku i nie zawiera `global.db`; nie są to migawki instalacji. Przywracanie zachowuje bazę danych, którą zastępuje, w tym samym miejscu jako `<timestamp>-pre-restore`.
Krok retencji cotygodniowego potoku usuwa wyłącznie kopie jego własnego obszaru roboczego
starsze niż skonfigurowany wiek (domyślnie 30 dni); ręcznie utworzone migawki instalacji
nigdy nie są przez ten krok rotowane. `server.listBackups` wymienia tylko migawki instalacji,
w tym niezweryfikowane; `workspace.listBackups` wymienia zaplanowane kopie zapasowe jednego
obszaru roboczego.

Usunięcie obszaru roboczego pozostawia ten katalog na miejscu. Harmonogram obszaru roboczego
zatrzymuje się wraz z nim, więc nic już nie rotuje tych kopii i pozostają one, dopóki
właściciel instalacji ich nie usunie. `server.listOrphanedBackups` je zgłasza.


### `manifest.json`

| Pole                       | Typ             | Znaczenie                                                           |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                  | int             | Format manifestu. Obecnie `2`                               |
| `created_at`               | ISO-8601 UTC    | Kiedy wykonano migawkę                                              |
| `global`                   | object          | Zapis `global.db`. Nieobecny w zaplanowanej kopii zapasowej obszaru roboczego |
| `workspaces[]`             | array           | Jeden rekord na każdy przechwycony obszar roboczy                     |
| `workspaces[].workspace_id`| string          | Obszar roboczy przechowywany w tym pliku                            |
| `skipped_workspaces[]`     | array           | Obszary robocze, których kopia **nie** zdołała przechwycić          |
| `skipped_workspaces[].workspace_id` | string | Obszar roboczy, który został pominięty                                     |
| `skipped_workspaces[].reason` | string       | `no_file`, `damaged` lub `failed`                                    |

`global` i każdy wpis w `workspaces[]` opisują jeden skopiowany plik, mierzony na kopii po jej zapisaniu:

| Pole             | Typ    | Znaczenie                                                                      |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | string          | Ścieżka względem katalogu głównego migawki: `global.db` lub `<workspaceId>/workspace.db` |
| `bytes`       | int             | Rozmiar kopii                                                  |
| `sha256`         | string | SHA-256 kopii, małymi literami w zapisie szesnastkowym                         |
| `quick_check`    | string | Co SQLite `quick_check` powiedział o kopii: `ok` albo jego ustalenie           |
| `user_version`   | int    | Wersja schematu kopii                                                          |
| `application_id` | int    | Identyfikator SQLite `application_id` kopii                                    |

Obszar roboczy zostaje pominięty, gdy jest zarejestrowany, ale nigdy nie był zapisywany (`no_file`), gdy jego baza danych nie przechodzi kontroli integralności (`damaged`; uszkodzonej kopii nigdy nie tworzy się), albo gdy jego kopiowanie lub sprawdzenie tej kopii się nie powiodło (`failed`). W każdym z tych przypadków migawka i tak się kończy, a manifest wymienia, czego brakuje. Manifest jest zapisywany jako ostatni.

### Kompletność

`server.listBackups` zwraca flagę `complete` dla każdej migawki. Jest fałszywa, gdy manifestu nie ma, nie da się go sparsować albo jest w innym formacie, gdy plik, który wymienia, brakuje lub ma inny rozmiar, albo gdy kopia nie przeszła swojego sprawdzenia. Aplikacja pokazuje taką migawkę jako **Niezweryfikowana**. Migawki wykonane przed formatem `2` są w tym stanie.

Niezweryfikowana migawka nadal trafia na listę, bo migawka, której operator nie widzi, to migawka,
o której operator myśli, że ją ma. Gdy manifestu nie da się odczytać, lista opiera się na samym
układzie katalogów i zgłasza te pliki `<workspaceId>/workspace.db`, które znajdzie —
każdy z nich można nadal adoptować pojedynczo przez `workspace.import`, choć migawka jako całość
nie potrafi przywrócić instalacji.

Wypisana migawka lub zaplanowana kopia zapasowa ma `pinned_reason: "last_good_copy"`, dopóki przechowuje najnowszą zweryfikowaną kopię obszaru roboczego, którego żywa baza danych jest uszkodzona. Krok retencji ją pomija, dopóki ten obszar roboczy nie zostanie przywrócony.

## Czego kopia zapasowa nie zawiera

Oba artefakty to **wyłącznie bazy danych**. Katalog obszaru roboczego przechowuje więcej niż
jego bazę danych, a nic z reszty nie podróżuje:

| Ścieżka                             | W migawce?     | W eksporcie obszaru roboczego? |
| ----------------------------------- | -------------- | ---------------------- |
| `global.db`                         | Tak            | Nie                    |
| `<workspaceId>/workspace.db`        | Tak            | Tak (to *jest* ten plik) |
| `<workspaceId>/code_index.db`       | Nie             | Nie                     |
| `<workspaceId>/blobs/`              | Nie            | Nie                    |
| `<workspaceId>/skills/`             | Nie            | Nie                    |
| `<workspaceId>/agents/`             | Nie            | Nie                    |
| `<workspaceId>/chat_credentials/`   | Nie            | Nie                    |
| `<workspaceId>/spaces/<spaceId>/`   | Nie            | Nie                    |
| `<workspaceId>/pr_clones/`          | Nie            | Nie                    |
| `secrets.json`                      | Nie            | Nie                    |
| `models/`                           | Nie            | Nie                    |
| `meetings/<meetingId>/`             | Nie            | Nie                    |
| `rigs/`                             | Nie            | Nie                    |
| `_agent_hooks/`                     | Nie            | Nie                    |

Część z tego jest jednorazowa — `spaces/` przechowuje drzewa robocze z kopiowaniem przy zapisie, które są odtwarzane z repozytoriów, `pr_clones/` to cache, `code_index.db` jest odbudowywany, `models/` pobiera się ponownie, a `rigs/` to stan maszyny. Część jednak nie: `blobs/` przechowuje wklejone obrazy, na które wskazują wiersze w bazie danych, `skills/` i `agents/` przechowują pliki, z którymi działa agent, a `secrets.json` przechowuje każdy klucz parowania, poświadczenie dostawcy i ustawienie SSO w instalacji. Jak objąć resztę, opisano w [Kopia zapasowa i przywracanie](/pl-PL/podrecznik/poradniki/kopia-zapasowa-i-przywracanie/#kopiowanie-kopii-zapasowych-poza-maszynę).
:::note[Sekrety pozostają poza bazami danych]
`workspace.db` to cały obszar roboczy: rozmowy, dzienniki uruchomień, powiązania z repozytoriami, definicje środowisk i członkowie. Tokeny webhooków potoków i sekrety webhooków synchronizacji zgłoszeń znajdują się w `secrets.json`: baza danych zawiera odwołanie do każdego z nich, a indeks tras zawiera skrót z kluczem każdego tokenu. Obszar roboczy przywrócony na innej instalacji dlatego nie otrzyma żadnych webhooków, dopóki jego wyzwalacze nie zostaną tam zapisane ponownie. Logowania do dostawców, klucze urządzeń i sekrety użytkowników są w `global.db` i `secrets.json`.
:::

:::note[Tokeny czatu celowo zostają poza kopią]
To, że `chat_credentials/` leży obok bazy danych, a nie w niej, jest powodem, dla którego obszar
roboczy przekazany komuś innemu nie niesie ze sobą żadnych aktywnych tokenów bota. Zobacz
[Most czatu](/pl-PL/podrecznik/dokumentacja-referencyjna/most-czatu/).
:::

## Operacje

RPC kopii zapasowej instalacji oraz eksport i import obszaru roboczego są dostępne tylko dla
`fullClient`: sparowany telefon nie może ich wywołać. Wszystkie są całkowicie nieobecne —
nie odrzucane, lecz strukturalnie nieistniejące — na serwerze bez podłączonego portu kopii
zapasowych, takim jak serwer demonstracyjny.

| Operacja             | Rodzaj | Zakres    | Minimalna rola    | Argumenty     | Zwraca                        |
| -------------------- | ------ | --------- | ----------------- | ------------- | ----------------------------- |
| `server.backupNow`   | zapis  | Instalacja | **właściciel** instalacji | brak  | `{ok, path}`                  |
| `server.listBackups` | odczyt | Instalacja | **właściciel** instalacji | brak  | `{backups: [...]}`            |
| `server.deleteBackup` | zapis | Instalacja | **właściciel** instalacji | `name` | `{ok}` |
| `server.listOrphanedBackups` | odczyt | Instalacja | **właściciel** instalacji | brak | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | zapis | Instalacja | **właściciel** instalacji | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | odczyt | Obszar roboczy | `admin` | brak | `{backups: [...]}` |
| `workspace.deleteBackup` | zapis | Obszar roboczy | `owner` | `name` | `{ok}` |
| `workspace.export`   | odczyt | Obszar roboczy | `admin`      | brak          | `{ok, path}`                  |
| `workspace.import`   | zapis  | Obszar roboczy | `owner` i właściciel serwera | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | odczyt | Obszar roboczy | `owner` i właściciel serwera | brak | `{holds: [...]}` |
| `workspace.importHolds.resolve` | zapis | Obszar roboczy | `owner` i właściciel serwera | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | zapis  | Instalacja* | `owner`         | `id`          | wiersz rejestru oznaczony jako usunięty |

* `workspace.delete` nie ma zakresu, bo wiersz, który oznacza, mieszka w globalnym
rejestrze; jej handler sprawdza członkostwo wywołującego w nazwanym obszarze roboczym
i wymaga roli `owner`.

`path` w każdej odpowiedzi to ścieżka na **hoście serwera**.

`server.listOrphanedBackups` zwraca jeden wpis na każdy obszar roboczy, który już nie jest
aktywny: `workspace_id`, `workspace_name`, gdy rejestr wciąż go zna, oraz `backups`. Usunięty
obszar roboczy nie może już przejść sprawdzenia roli w obszarze roboczym, więc jego kopie
należą do właściciela instalacji. `server.deleteOrphanedBackup` odrzuca aktywny obszar
roboczy, którego kopie pozostają chronione przez `workspace.deleteBackup` i role tego obszaru
roboczego. Obie operacje usuwania przyjmują tylko nazwę katalogu ze znacznikiem czasu z
listy, a nie ścieżkę.

`workspace.importHolds.list` zwraca to, co import wstrzymał. Każde wstrzymanie ma `id`, `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` lub `invite`), `payload`, który zostałby przywrócony, `imported_at` i `source_install_id`. `workspace.importHolds.resolve` z `accept: true` przyznaje je ponownie, a z `false` odrzuca. `applied` ma wartość false, gdy osoba lub rzecz, której dotyczyło przyznanie, nie należy już do obszaru roboczego.

:::note[Migawka całej instalacji wymaga roli właściciela na obu torach]
`server.backupNow`, `server.listBackups` i `server.deleteBackup` wymagają roli
**właściciela** instalacji (`ServerAuthority.serverOwner`) — tego samego warunku co
`GET /backup/snapshot`. Migawka obejmuje bazę danych każdego obszaru roboczego, więc
bycie administratorem jednego obszaru roboczego nie wystarcza do zarządzania pozostałymi.
Usuwanie przyjmuje wyłącznie nazwę katalogu ze znacznikiem czasu z listy, a nie dowolną
ścieżkę serwera, i usuwa całą migawkę (w tym migawki niezweryfikowane).
Eksport obszaru roboczego i pobieranie zaplanowanych kopii zapasowych pozostają przy roli
administratora obszaru roboczego.
:::

:::note[Przywracanie należy do właściciela serwera]
`workspace.import` i `POST /backup/restore` sprawiają, że serwer przejmuje plik bazy danych,
którego wiersze traktuje jako własne: powiązania z repozytoriami i to, kto je utworzył,
definicje środowisk uruchamiane na hoście, ścieżki worktree i logów. Dlatego obie operacje
wymagają właściciela serwera (`ServerAuthority.serverOwner`), który musi być też właścicielem
obszaru roboczego. Każdy inny, a także każde wywołanie na hoście bez zapisanego właściciela,
jest odrzucane z `server_owner_required`. Żadne wyzwalacze, widoki, kolumny ani ograniczenia, które przynosi plik,
nie są przejmowane.
:::

### Odpowiedź `server.listBackups`

Od najnowszej, sortowane według nazwy katalogu (która jest znacznikiem czasu, więc kolejność
zachowuje się nawet dla migawki, której manifestu nie udało się odczytać).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` jest pomijane, gdy manifestu nie udało się odczytać. `bytes` na najwyższym poziomie
to rzeczywisty rozmiar całego katalogu na dysku, a nie suma z samego manifestu — pytanie, które
zadaje operator porządkujący migawki, brzmi, ile kosztuje katalog, a nie ile kopia zamierzała
zapisać.

Każde `workspaces[].path` to dokładnie to, co `workspace.import` przyjmuje jako `source_path`.
To celowe: „przywróć ten obszar roboczy z tej migawki” *jest* operacją importu, więc oba nie mogą
się rozjechać w różne traktowanie tego samego pliku.

### Walidacja `workspace.import`

Zanim cokolwiek zostanie zastąpione, plik-kandydat jest kopiowany do pliku pośredniego obok celu i tam sprawdzany. Odrzucenie niczego nie rusza, a jego rodzaj jest podawany jako `data.kind`.

| Warunek                                          | Wynik                                                           |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| Plik nie istnieje | Odmowa, `import.missing_source` |
| Nieczytelna baza danych SQLite albo nie przechodzi `quick_check` | Odmowa, `import.damaged` |
| Pochodzi z migawki, a jego SHA-256 różni się od tego z manifestu | Odmowa, `import.checksum_mismatch` |
| Zapisała go nowsza wersja serwera | Odmowa, `import.newer_schema` |
| Inny `application_id` albo brak `workspace_meta` | Odmowa, `import.foreign_file` |
| Nie da się doprowadzić do schematu tego serwera | Odmowa, `import.schema_mismatch` |
| Jego webhooki albo zaproszenia już kierują do innego obszaru roboczego | Odmowa, `import.route_conflict` |
| Zapisany identyfikator obszaru roboczego ≠ docelowy | **Dozwolone**. Jego wiersze zostają przypisane do celu. W ten sposób obszar roboczy jest duplikowany lub przywracany pod nowym identyfikatorem |
| Zapisany identyfikator instalacji ≠ ta instalacja | **Dozwolone**. Identyfikatory użytkowników z niej należą do tamtej instalacji i nie zostaną tu rozwiązane |

Po zaakceptowaniu przygotowany plik zostaje doprowadzony do schematu tego serwera i musi mu potem dokładnie odpowiadać. Uprawnienia, których plik nie może sam sobie przyznać, zostają z niego usunięte: zatwierdzenia uruchamiania definicji środowiska na hoście są czyszczone, a reguły akcji, które zezwalają lub pytają, granty sandbox exec, granty repozytoriów wyższe niż odczyt, role wyższe niż członek i zaproszenia do tych ról stają się wstrzymaniami do przejrzenia przez właściciela serwera. Importujący zachowuje rolę właściciela albo ją otrzymuje. Zastępowana baza danych zostaje zachowana jako zaplanowana kopia zapasowa o nazwie `<timestamp>-pre-restore`, przygotowany plik zostaje przemianowany na miejsce docelowe przy zamkniętych połączeniach obszaru roboczego, `code_index.db` zostaje usunięty, aby został odbudowany, a indeksy FTS są odbudowywane.

## Trasy transferu

Operacje eksportu/importu i wyświetlania migawek powyżej mówią ścieżkami po stronie serwera,
co jest pełną odpowiedzią tylko wtedy, gdy serwerem jest Twoja własna maszyna. Te trasy
o kształcie HTTP przenoszą bajty kopii zapasowej **wewnątrz tego samego uwierzytelnionego,
szyfrowanego end-to-end tunelu zasobów** co inne wrażliwe zasoby, niezależnie od tego, czy
połączenie RPC jest bezpośrednie, czy przez przekaźnik. Nie są to publiczne punkty końcowe
transferu plików HTTP: żądanie do jednego z nich na publicznym nasłuchu zwraca
`426 Upgrade Required`, także z loopbacku. W szyfrowanym tunelu urządzenie uwierzytelnione
przez Noise musi zgadzać się z `d`; handler dodatkowo sprawdza podpis urządzenia nad jego
ciągiem docelowym przy użyciu jego PSK parowania oraz rolę poniżej.

| Trasa                   | Metoda | Zapytanie       | Podpisany cel                  | Wymaga                  |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **administrator** obszaru roboczego |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **właściciel** instalacji |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **administrator** obszaru roboczego; **właściciel** instalacji po usunięciu obszaru roboczego |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **właściciel** instalacji, który jest też **właścicielem** obszaru roboczego (`403` z `server_owner_required` w przeciwnym razie) |

`w` to identyfikator obszaru roboczego, `n` — nazwa katalogu migawki lub zaplanowanej kopii
zapasowej, `d` — identyfikator wywołującego urządzenia, a `s` — podpis. W `/backup/snapshot`
`n` jest rozwiązywane względem listy kopii zapasowych, a nie dołączane do katalogu głównego
kopii, więc trasy nie da się wycelować w katalog, którego lista by nie pokazała. W
`/backup/stored` musi to być nazwa ze znacznikiem czasu, a plik musi być rzeczywistym plikiem
w katalogu kopii zapasowych tego właśnie obszaru roboczego.

| Status | Przyczyna                                                                          |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | Brakuje wymaganego parametru zapytania, nazwa kopii zapasowej jest nieprawidłowa, treść wysyłki jest pusta albo wysłany plik został odrzucony (treść to `{error, kind}` z rodzajem `import.*`) |
| `403`  | Nieznane lub unieważnione urządzenie, nieprawidłowy podpis albo wywołującemu brakuje roli |
| `404`  | Brak portu kopii zapasowych na tym hoście albo wskazany plik migawki, kopii zapasowej lub obszaru roboczego nie istnieje |
| `405`  | `/backup/restore` wywołane czymkolwiek innym niż `POST`                             |
| `413`  | Treść wysyłki przekracza 8 GiB — według zadeklarowanej długości treści albo według faktycznie odczytanych bajtów |
| `426`  | Każde bezpośrednie żądanie do ścieżki transferu na publicznym nasłuchu HTTP; użyj szyfrowanego tunelu zasobów sparowanego klienta |
| `500`  | Eksport albo archiwizacja nie powiodły się po stronie serwera                       |

Wszystkie trzy pobierania odpowiadają `Cache-Control: no-store` z `Accept-Ranges: none`.
`/backup/workspace` i `/backup/snapshot` tworzą **świeżą** kopię na każde żądanie i usuwają ją
po przesłaniu, więc zapamiętana w cache albo wznowiona odpowiedź skleiłaby bajty z dwóch
różnych eksportów w jeden plik, który wygląda na poprawny, a nim nie jest.

`/backup/stored` jest wyjątkiem: przesyła zaplanowaną kopię zapasową jako
`<workspaceId>-<name>.db` i pozostawia plik na miejscu, bo ten plik jest kopią zapasową.

`/backup/snapshot` zwraca `<name>.zip`, a wpisy są względne wobec katalogu głównego migawki,
więc rozpakowanie odtwarza `manifest.json` + `global.db` + `<workspaceId>/workspace.db`.
Wpisy są zapisywane w kolejności posortowanej, więc dwa archiwa tej samej migawki to to samo
archiwum.

`/backup/restore` strumieniuje treść prosto do pliku tymczasowego, zamiast ją buforować,
ogranicza ją przed odczytem i w jego trakcie oraz usuwa odłożony plik na **każdej** drodze
wyjścia, także przy odmowie.

::::caution[Połączenie bezpośrednie i przez przekaźnik używają tego samego szyfrowanego transferu]
Przekaźnik przenosi żądania zasobów, strumieniowane odpowiedzi i bajty wysyłki jako
szyfrogram; nie może odczytać zawartości kopii zapasowej. Ścieżka po stronie serwera
pozostaje ścieżką na hoście serwera, a nie plikiem na przekaźniku. Dostęp nadal wymaga
sparowanego urządzenia, podpisu celu i właściwej roli obszaru roboczego lub instalacji.
Żaden z transportów nie szyfruje powstałych plików kopii zapasowej w spoczynku.
::::

## Ścieżki i limity

| Element                        | Wartość                                                      |
| ------------------------------ | ------------------------------------------------------------ |
| Migawki                        | `<dataDir>/backups/<timestamp>/`                             |
| Zaplanowane kopie zapasowe obszarów roboczych | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Eksporty obszarów roboczych    | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Baza danych zastąpiona przywróceniem | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Bazy danych sprzed aktualizacji, która zmieniła ich format | `<dataDir>/pre_upgrade/` i `<dataDir>/<workspaceId>/pre_upgrade/`, po dwie najnowsze z każdej |
| Obszar tymczasowy transferu    | `<dataDir>/backups/transfer/` — miejsce robocze, czyszczone przez trasę, która do niego pisze |
| Nazwa archiwum migawki         | `<snapshot directory name>.zip`                              |
| Limit wysyłki                  | 8 GiB na szyfrowaną wysyłkę `/backup/restore`               |
| Retencja                       | Migawki instalacji: ręczne usuwanie. Kopie zapasowe obszarów roboczych: cotygodniowy potok, domyślnie 30 dni, lub ręczne usuwanie. Kopie zapasowe usuniętego obszaru roboczego: tylko ręczne usuwanie |

Katalogi `exports/`, `transfer/` i `workspace-backups/` nie są migawkami instalacji i są
wyłączone z `server.listBackups`. Tylko ostatni katalog ma zaplanowaną retencję i tylko
dopóki istnieje jego obszar roboczy; usunięcie migawki instalacji wymaga wyraźnego działania
właściciela instalacji.
