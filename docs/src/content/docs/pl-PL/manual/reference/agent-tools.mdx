To narzędzia **związane z serwerem**, które wbudowane środowisko uruchomieniowe agenta rejestruje bezpośrednio — serwer językowy, wyszukiwanie strukturalne, debugger, kernele, skrypty trybu kodu, pytania i sterowanie workerami — w odróżnieniu od [narzędzi MCP](/pl-PL/podrecznik/dokumentacja-referencyjna/narzedzia-mcp/), które mostkuje, oraz ogólnych narzędzi plikowych, wyszukiwania i powłoki ze środowiska uruchomieniowego harnessu. Nie ma ich w rejestrze MCP: zewnętrzny klient MCP ich nie zobaczy, bo każde jest przypisane do żywego zasobu po stronie serwera — procesu serwera językowego, adaptera debuggera, interpretera — który należy do jednego uruchomienia.

Każde narzędzie tutaj jest rejestrowane tylko wtedy, gdy jego zasób zaplecza jest podłączony na czas uruchomienia — nadzorca serwera językowego lub debugowania, parser tree-sittera, fabryka kernelów, port pytań, lista workerów vibe. Wykrywanie serwera językowego lub adaptera debuggera dla *tej kopii roboczej* to osobne, późniejsze sprawdzenie (`status` / `adapters`): te narzędzia pozostają na powierzchni, żeby agent mógł zapytać, dlaczego nic nie da się użyć, zamiast zgadywać.

## Poziomy zatwierdzania

Każde narzędzie deklaruje poziom, a poziom decyduje o tym, **które powierzchnie je widzą** — nie tylko o tym, czy pojawia się prośba o zatwierdzenie. Tryb planu i podagenci tylko do odczytu są ograniczone do poziomu `read`, więc narzędzie poziomu `write` lub `exec` jest całkowicie nieobecne w ich schemacie.

| Poziom  | Znaczenie                          | Narzędzia tutaj                                  |
| ------- | ---------------------------------- | ------------------------------------------------ |
| `read`  | Bez efektów ubocznych              | `lsp`, `ast_grep`, `ask_user`, `repl`, pięć `vibe_*` |
| `write` | Zmienia pliki                      | `lsp_rename`, `ast_edit`, `resolve`              |
| `exec`  | Uruchamia proces lub steruje nim   | `debug`, `eval`                                  |

## Bezpośrednio, tylko ze skryptu albo ładowane przy pierwszym użyciu

Gdy serwer może uruchamiać skrypty, uruchomienie wywołuje kilka narzędzi bezpośrednio, a resztę osiąga ze skryptu [`repl`](#repl--uruchamianie-skryptu-wywołującego-twoje-narzędzia); całą zasadę opisuje [Tryb kodu](/pl-PL/podrecznik/koncepcje/tryb-kodu/#które-narzędzia-agent-wywołuje-bezpośrednio). Dla narzędzi z tej strony:

| Narzędzie | Z `repl` | Bez `repl` |
| ---- | ----------- | -------------- |
| `repl` | Bezpośrednio | Nie występuje |
| `ask_user` | Bezpośrednio | Bezpośrednio |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Tylko ze skryptu | Ładowane przy pierwszym użyciu |
| `eval` | Ładowane przy pierwszym użyciu (skrypt nie może go wywołać) | Ładowane przy pierwszym użyciu |
| `vibe_*` | Bezpośrednio w trybie vibe, nigdy ze skryptu | Bezpośrednio w trybie vibe |

Narzędzie oznaczone „Tylko ze skryptu” wczytuje się zamiast tego przy pierwszym użyciu, gdy serwer nie może uruchamiać skryptów uruchomienia ([Gdy skrypty nie mogą działać](/pl-PL/podrecznik/koncepcje/tryb-kodu/#gdy-skrypty-nie-mogą-działać)).

## `lsp` — zapytania do serwera językowego

Rejestrowane, gdy uruchomienie ma nadzorcę serwera językowego i katalog roboczy. To, czy serwer faktycznie potrafi odpowiedzieć, jest wykrywane w momencie wywołania, jako **część wspólna**: znacznik korzenia musi istnieć *i* plik binarny serwera musi dać się odnaleźć. Każdy z tych warunków osobno oznacza, że żaden serwer nie startuje — `status` tak właśnie mówi — a nie ciche zgadywanie.

Serwery pochodzą wyłącznie z wbudowanej tabeli; plik `lsp.json` z repozytorium nie jest czytany. W uruchomieniu w sandboxie każde uruchomienie ma własną sesję serwera językowego, więc serwery startują ponownie przy każdym uruchomieniu. Lokalne dla projektu pliki binarne (`node_modules/.bin`) są używane tylko w uruchomieniu w sandboxie, a korzeń projektu nigdy nie rozwiązuje się powyżej katalogu roboczego uruchomienia.

Pozycje są adresowane za pomocą `line` oraz podciągu `symbol`, nigdy przez kolumnę. Model poproszony o kolumnę zgaduje, a błędne trafienie wskazuje inny symbol w tym samym wierszu — odpowiedź, która wygląda poprawnie, a dotyczy czegoś innego. Pominięcie `symbol` w akcji nawigacyjnej jest błędem, a nie zgadywaniem pierwszej kolumny.

| Akcja             | Argumenty                        | Zwraca                                     |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (albo `"*"`)              | Błędy i ostrzeżenia; `"*"` uruchamia zamiast tego sprawdzanie całego projektu |
| `definition`      | `file`, `line`, `symbol`         | Gdzie symbol jest zadeklarowany            |
| `type_definition` | `file`, `line`, `symbol`         | Gdzie zadeklarowano jego typ               |
| `implementation`  | `file`, `line`, `symbol`         | Konkretne implementacje                    |
| `references`      | `file`, `line`, `symbol`         | Każde użycie, ograniczone do 50            |
| `hover`           | `file`, `line`, `symbol`         | Sygnatura i komentarz dokumentacyjny       |
| `symbols`         | `query` albo `file`              | Wyszukiwanie w obszarze roboczym z `query` (ograniczone do 100); symbole dokumentu z `file` (ograniczone do 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Szybkie poprawki oferowane przez serwer    |
| `status`          | —                                | Które serwery działają i dla których korzeni |
| `reload`          | —                                | Restartuje serwer dla tego korzenia        |

### Diagnostyka przy zapisie

Zysk nie polega na samym narzędziu. `write`, `edit` i `apply_patch` są **opakowane**: po zapisie plik jest synchronizowany i zapisywany przez serwer językowy, a do wyniku narzędzia trafiają wyłącznie **nowo wprowadzone** komunikaty diagnostyczne. Agent dowiaduje się, że zepsuł kompilację, w momencie, w którym ją zepsuł — bez konieczności pamiętania o tym, żeby o to zapytać.

Komunikaty już zgłoszone są pomijane dzięki rejestrowi prowadzonemu dla każdego uruchomienia, z kluczem opartym na wadze, kodzie i komunikacie — pozycja jest celowo wyłączona, więc komunikat, który jedynie przesunął się o cztery linie w dół, nie zostaje ponownie zgłoszony jako nowy.

## `lsp_rename` — zmiana nazw w całym projekcie

Osobne narzędzie poziomu `write`, z dokładnie jednego powodu: to poziom decyduje o widoczności. Włączenie zmiany nazw do `lsp` albo dałoby eksploratorowi tylko do odczytu możliwość przepisywania repozytorium, albo postawiłoby każde `hover` za prośbą o zatwierdzenie.

| Argument   | Znaczenie                               |
| ---------- | --------------------------------------- |
| `file`     | Gdzie znajduje się symbol               |
| `line`     | Wiersz numerowany od 1                  |
| `symbol`   | Podciąg identyfikujący go w tym wierszu |
| `new_name` | Jak go nazwać                           |

## `ast_grep` — wyszukiwanie strukturalne

Znajduje kod po **kształcie**, a nie po tekście. `$NAME` dopasowuje dowolny węzeł, `$$$NAME` dopasowuje serię węzłów rodzeństwa, a `$_` to symbol wieloznaczny, który niczego nie wiąże.

Cechą, która czyni go dopasowywaczem, a nie wyrażeniem regularnym z dodatkowymi krokami, jest to, że metazmienna powtórzona w jednym wzorcu musi przechwycić ten sam tekst.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

pasuje do warunku ochronnego, który zwalnia to, co sprawdził, i **nie** pasuje do takiego, który zwalnia coś innego.

| Argument      | Znaczenie                                                   |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | Fragment kodu z metazmiennymi                               |
| `path`        | Plik lub katalog do przeszukania; domyślnie cały obszar roboczy |
| `language`    | Identyfikator dostarczonej gramatyki (`dart`, `python`, `rust`, `c`, …). Wnioskowany, gdy `path` wskazuje plik |
| `max_results` | Domyślnie 50                                                |

:::note[Wzorzec jest parsowany przez tę samą gramatykę co plik]
Dzięki temu `dispose(x)` dopasowuje wywołanie niezależnie od tego, jak jest rozstawione, zawinięte czy opatrzone komentarzem — i nigdy nie dopasowuje tych samych znaków wewnątrz literału tekstowego lub komentarza.
:::

:::caution[Fragment jest parsowany w rusztowaniu, a nie samodzielnie]
`dispose(x)` sparsowany na najwyższym poziomie Darta jest poprawną *sygnaturą funkcji*. Kompilator wzorców próbuje drabiny kontekstów (instrukcja, wyrażenie, składowa klasy, deklaracja) i używa pierwszego, który przyjmie fragment. Wzorzec, którego nie przyjmuje żaden kontekst, jest zgłaszany jako nieparsowalny, a nie przeszukiwany i po cichu nieznaleziony.
:::

## `ast_edit` — przepisanie strukturalne w poczekalni

To samo dopasowywanie plus szablon `rewrite` z podstawionymi z powrotem metazmiennymi. **Nic nie zostaje zapisane.** Zmiana trafia do poczekalni, a wynik podaje `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Argument   | Znaczenie                                          |
| ---------- | -------------------------------------------------- |
| `pattern`  | Co dopasować                                       |
| `rewrite`  | Co wstawić w to miejsce, z podstawionymi `$NAME`   |
| `path`     | Zakres; domyślnie cały obszar roboczy              |
| `language` | Identyfikator języka                               |

## `resolve` — zatwierdź albo odrzuć zmianę z poczekalni

| Argument  | Znaczenie                        |
| --------- | -------------------------------- |
| `edit_id` | Z wyniku `(proposed)`            |
| `action`  | `accept` albo `discard`          |

Każdy plik jest porównywany z treścią zapisaną w momencie przygotowania, a **każda** niezgodność odrzuca całą zmianę. Częściowo zastosowane przepisanie strukturalne zostawia drzewo, które nie kompiluje się ani w starym, ani w nowym kształcie.

## `debug` — sterowanie debuggerem

Rejestrowane, gdy uruchomienie ma nadzorcę sesji debugowania, katalog roboczy i identyfikator rozmowy. To, czy adapter faktycznie potrafi wystartować, jest wykrywane w momencie wywołania, według tej samej zasady części wspólnej co w przypadku serwera językowego (znacznik korzenia *i* plik binarny). Poziom `exec`; nie jest bezpieczne równolegle (sesja to stan trwający między wywołaniami, więc `continue` wyprzedzające `stack` odczytałoby ramkę, która już się przesunęła).

Jedna sesja na rozmowę, z twardym TTL (30 minut). Drugie `launch` jest odrzucane, zamiast po cichu zastępować pierwsze. W uruchomieniu w sandboxie sesja zachowuje sandbox między turami aż do zakończenia, czyli co najwyżej przez te 30 minut.

| Operacja      | Argumenty                     | Uwagi                                          |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Które adaptery są tutaj użyteczne i dlaczego nie |
| `status`      | —                             | Czy sesja działa i gdzie się zatrzymała        |
| `breakpoints` | `file`, `lines[]`             | Puste `lines` czyści plik. Można je ustawić **przed** uruchomieniem |
| `launch`      | `program`, `args[]`           | Uruchamia program zatrzymany na Twoich punktach przerwania |
| `attach`      | `port`                        | Podłącza się do już działającego debugowanego procesu na jednym z przekierowanych portów uruchomienia; każdy inny port jest odrzucany, zanim cokolwiek wystartuje |
| `continue`    | `thread_id?`                  | Biegnie do następnego zatrzymania              |
| `pause`       | `thread_id?`                  | Zatrzymuje go tam, gdzie jest                  |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Przesuwa o jeden krok                 |
| `threads`     | —                             | Identyfikatory i nazwy wątków                  |
| `stack`       | `thread_id?`                  | Ramki, ograniczone do 30                       |
| `scopes`      | `frame_id`                    | Zasięgi ramki, każdy z `reference`             |
| `variables`   | `reference`                   | Dzieci, ograniczone do 50, wartości do 400 znaków |
| `evaluate`    | `expression`, `frame_id?`     | Obliczane w zasięgu samej ramki                |
| `output`      | —                             | stdout/stderr debugowanego procesu, ograniczone |
| `terminate`   | —                             | Kończy sesję i zabija adapter                  |

### Adaptery

| Id        | Polecenie                    | Znaczniki korzenia                              |
| --------- | ---------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`         | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                   | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                    | `go.mod`                                        |

`debugpy` preferuje lokalne dla projektu `.venv/bin` lub `venv/bin` ponad `$PATH` tylko w uruchomieniu w sandboxie: Python z `$PATH` to inne środowisko, a podłączenie z niewłaściwego zawodzi w sposób, który wygląda jak zepsuty kod. Poza sandboxem używa wyłącznie `$PATH`, więc repozytorium nie może wybrać interpretera, który działa na hoście.

## `repl` — uruchamianie skryptu wywołującego twoje narzędzia

Obecne w każdym uruchomieniu, gdy serwer może uruchamiać skrypty ([Kiedy uruchomienie ma `repl`](/pl-PL/podrecznik/koncepcje/tryb-kodu/#kiedy-uruchomienie-ma-repl)). Skrypt to zwykły JavaScript, treść funkcji async, i działa w świeżym, zablokowanym interpreterze we własnym procesie: bez dostępu do systemu plików, sieci, procesów i modułów. Samo `repl` należy do poziomu `read` i pilnuje siebie, bo każde wywołanie narzędzia wykonane przez skrypt jest sprawdzane osobno. Dostępne też na endpoincie MCP, dla uruchomień agentów na serwerze, który może uruchamiać skrypty.

| Argument | Znaczenie |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | Skrypt. Najwyżej 256 KiB |
| `description` | Wymagane. Krótka etykieta wiersza w transkrypcji |
| `timeout_ms` | Opcjonalne. Krótszy limit czasu niż limit obszaru roboczego; nigdy dłuższy |
| `max_output_tokens` | Opcjonalne. Mniejszy budżet wyjścia niż obszaru roboczego; nigdy większy |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

Opis `repl` mówi agentowi: „Narzędzie, które nie jest jednym z twoich narzędzi bezpośrednich, nie ma definicji w tym żądaniu. Zanim po raz pierwszy je wywołasz, sprawdź je poleceniem `describeTool(name)` albo `searchTools(query)`, chyba że jego dokładny kształt wywołania został ci już pokazany w tej rozmowie.”

`describeTool(name)` zwraca opis narzędzia, jego deklarację, schematy wejścia i wyjścia oraz jego notę o wyniku, jeśli ją ma: to, co skrypt dostaje z zakończonego wywołania, we własnych słowach narzędzia. Opis `repl` wylicza noty bezpośrednich narzędzi, które skrypt może wywołać. Wynik narzędzia, który jest tekstem JSON, trafia już sparsowany, chyba że zawiera więcej niż 131 072 wartości: wtedy trafia jako tekst, a skrypt parsuje go za pomocą `JSON.parse`. Tekst wyniku narzędzia z zewnętrznego serwera MCP jest ucinany po 262 144 znakach, a ucięty tekst nie daje się już sparsować.

- `tools.<name>(args)` wywołuje narzędzie przez ten sam filtr, guardraile i zatwierdzenie co wywołanie bezpośrednie i odrzuca się błędem, gdy zostanie odmówione lub się nie powiedzie. Wywołania tylko do odczytu mogą działać równolegle; wywołania, które coś zmieniają, działają jedno po drugim, w kolejności, w jakiej skrypt je wykonał. Dopóki jedno z jego wywołań czeka na człowieka, żadne inne wywołanie skryptu nie startuje.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` i `describeNamespace(name)` znajdują narzędzia, także te z podłączonych serwerów MCP. Narzędzie spoza zestawu bezpośredniego, które skrypt może wywołać, jest wywoływalne tylko ze skryptu; bezpośrednie wywołanie zwraca informację, jak wywołać je z `repl`. Gdy serwer nie może uruchamiać skryptów uruchomienia, takie narzędzie zamiast tego wczytuje się przy pierwszym użyciu.
- Wyszukiwania są ograniczone: zapytanie do 1 024 znaków, nazwa lub przestrzeń nazw do 256, `limit` od 0 do 50, a najwyżej 200 wyszukiwań zajmujących łącznie 2 sekundy czasu serwera na skrypt, podczas gdy wszystkie skrypty jednego obszaru roboczego dzielą 2 sekundy czasu wyszukiwania, odzyskiwane w tempie ćwierć sekundy na każdą sekundę; po przekroczeniu któregokolwiek z tych limitów kolejne wyszukiwania są odrzucane. W bardzo dużym katalogu opisy w `ALL_TOOLS` dzielą równo około miliona znaków, a obcięty kończy się na `…`; `describeTool` zawsze zwraca cały opis. Typ zbyt duży, by go pokazać, jest oznaczony jako `unknown /* too large to show */`, a nieznana nazwa dostaje odpowiedź z najbliższymi nazwami.
- Narzędzia są pogrupowane w przestrzenie nazw: `builtin` (własne narzędzia harnessu), `control-center` (narzędzia Control Center) i po jednej dla każdego podłączonego serwera MCP, nazwanej od tego serwera. Serwer nazwany `builtin`, `control-center` lub `script`, albo którego nazwa zaczyna się od `external-`, w dowolnej mieszance wielkich i małych liter oraz z spacjami lub bez spacji wokół niej, jest wyświetlany jako `external-` plus jego nazwa, a żadne narzędzie nigdy nie znajduje się w `script`.
- Do agenta wraca tylko to, co skrypt zwróci lub przekaże do `text()`, `image()` albo `console.*`. Wyjście ponad budżet zachowuje swój początek i koniec, a resztę odczytuje `read_output`.
- `store(key, value)` / `load(key)` przechowują wartości JSON dla późniejszych skryptów tej samej rozmowy i agenta, zapisywane dopiero po zakończeniu skryptu. Skrypty subagenta nie mają magazynu.
- `await tools.ask_user(...)` zadaje pytanie; jego odpowiedź jest też dopisywana do wyniku. Dostępne są także `sleep(ms)`, `setTimeout`, `limits()` oraz `models.embed` / `rank` / `classify` (osadzenia na urządzeniu).
- `describeTool(name)` i `searchTools(query)` odpowiadają także dla funkcji własnych skryptu, które nie są narzędziami: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` i `models.*`, w przestrzeni nazw `script`.
- Nie do wywołania ze skryptu: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` i czasowniki `vibe_*`.
- Skrypt czyta przeszłość własnego uruchomienia: `history({start, role, tool, limit})` stronicuje transkrypt rozmowy (co najwyżej 50 wierszy za wywołanie; jako `start` przekaż `next_start` poprzedniej strony), `outputs()` wypisuje wyjścia narzędzi zapisane dla tej rozmowy i agenta, a `loadOutput(handle)` czyta 16 384 znaki jednego z nich. `storedKeys()` wypisuje zapisane klucze wraz z ich rozmiarami. `keep(value, label)` zapisuje dużą wartość jako wyjście, które późniejszy skrypt albo `read_output` mogą odczytać; zapisywane jest tylko wtedy, gdy skrypt się zakończy (1 MiB na wartość, 64 wartości i 16 MiB na uruchomienie). `limits().returnBudgetChars` podaje, ile z budżetu wyjścia zostało. Uruchomienie tylko do odczytu (recenzja celu) może czytać, ale nie zapisywać ani nie używać keep. W Claude Code i ACP `history()` działa, a `outputs()`, `loadOutput()` i `keep()` odmawiają działania, ponieważ Control Center nie przechowuje wyjść narzędzi tych uruchomień.
- Błąd z przekroczenia czasu, przepełnienia wyjścia albo limitu wywołań podpowiada, jak to naprawić.

Jedno uruchomienie wykonuje naraz jeden skrypt. Limity i to, co dzieje się przy każdym z nich, opisuje strona [trybu kodu](/pl-PL/podrecznik/koncepcje/tryb-kodu/#limity); każdy skrypt jest zapisywany w **Obserwowalność → Wykonania kodu**.

## `eval` — trwałe interpretery

Komórka Pythona lub JavaScriptu, której zmienne, importy i wczytane dane przetrwają między wywołaniami. Poziom `exec`; nie jest bezpieczna równolegle. Nie można jej wywołać ze skryptu `repl`, a komórka nie może wywoływać narzędzi uruchomienia: aby wywoływać narzędzia z kodu, użyj [`repl`](#repl--uruchamianie-skryptu-wywołującego-twoje-narzędzia).

| Argument      | Znaczenie                                        |
| ------------- | ------------------------------------------------ |
| `code`        | Komórka                                          |
| `description` | Wymagane. Od 5 do 10 słów na etykietę transkryptu |
| `language`    | `python` (domyślnie) albo `javascript`           |
| `reset`       | Odrzuca interpreter i zaczyna od czystego stanu  |

- Ostatnie wyrażenie jest zwracane tak, jak robi to notatnik.
- `display()` działa, ramka pandas renderuje się jako tabela, a wykres matplotlib wraca jako **obraz, który pokazuje transkrypt**.
- Idiomy IPython, które wpisuje się odruchowo — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — są przepisywane na zwykły kod. `%pip` dodatkowo usuwa moduły z `sys.modules`, więc następny `import` widzi to, co właśnie zainstalowano.
- Komórka, która wypisze więcej niż jej budżet wyjścia, zachowuje pierwsze trzy czwarte i ostatnią czwartą, z jednym wierszem mówiącym, ile znaków i obrazów zostało usuniętych.
- Gdy interpreter zginął, choć nikt tego nie zlecił, następna komórka dostaje raz informację, że jego wcześniejsze zmienne zniknęły.

:::note[Gdzie działa kernel]
W odizolowanym środowisku rozmowy, gdy rozmowa je ma; w przeciwnym razie w sandboxie systemu operacyjnego uruchomienia na hoście. Gdy sandbox jest wyłączony lub niedostępny, kernel działa bez ograniczeń, a `eval` prosi o zatwierdzenie wykonania na hoście. Nie uruchamia przy tym odizolowanego środowiska — ta sama zasada, która powstrzymuje kartę riga przed automatycznym startem.
:::

## `bash` w tle

`bash` z `run_in_background: true` uruchamia polecenie i od razu zwraca uchwyt (`b1`, `b2`, …) zamiast czekać. Agent pracuje dalej albo kończy turę i zostaje wybudzony, gdy polecenie się zakończy.

| Argument | Znaczenie |
| ------------------- | ------- |
| `run_in_background` | `true`, by uruchomić i od razu wrócić |
| `timeout_seconds` | Sekundy do zabicia polecenia: domyślnie 600, co najwyżej 3 600 |
| `notify` | Opcjonalne. Prosty wzorzec; każdy wiersz wyjścia, który pasuje, jest wysyłany do agenta, gdy polecenie działa (na przykład `listening on\|FAILED`) |

- Co najwyżej 4 polecenia w tle działają naraz w jednym uruchomieniu. Każde jest zabijane po przekroczeniu czasu i po zakończeniu uruchomienia, wraz z każdym procesem, który uruchomiło.
- Gdy polecenie się zakończy, agent dostaje powiadomienie z kodem wyjścia, ostatnimi 2 000 znakami wyjścia i uchwytem `read_output` do reszty.
- Agent, którego jedyną pozostałą pracą jest polecenie w tle, czeka bez wywoływania modelu, a strażnik ciszy uruchomienia wstrzymuje się na czas tego czekania.
- `bash_output(handle)` odczytuje stan polecenia i ostatnie wyjście; `bash_kill(handle)` je zatrzymuje. Oba mówią, czy wynik został już dostarczony.
- Skrypt nie może uruchomić polecenia w tle. Claude Code ma własny Bash w tle; Control Center utrzymuje to uruchomienie otwarte najwyżej przez 10 minut po turze, która zostawiła zadanie w toku.

## `compact` — zwolnij miejsce w oknie kontekstu

Kompaktuje starszy kontekst rozmowy przed następnym wywołaniem modelu, zachowując to, co nazywa `focus` (co najwyżej 1 000 znaków). Najnowsze tury zostają dosłownie. Wiersz budżetu tury agenta pokazuje zużycie kontekstu przy 70, 80 i 90%, a narzędzie warto wywołać po około 70%, przed długą nową fazą pracy. Hak `preCompact` właściciela serwera może dopisać do skupienia ([Haki powłoki](/pl-PL/podrecznik/dokumentacja-referencyjna/konfiguracja-agentow/#haki-powłoki)). Po kompaktowaniu serwer dodaje blok „Still in flight”: cel, oczekujące wybudzenia, otwarte pytania, polecenia w tle, listę kontrolną i zapisane klucze, każdy z wywołaniem, które go przywraca.

## `ask_user` — zadaj człowiekowi pytanie

Poziom `read`. **Jedyny** sposób, w jaki uruchomienie pyta operatora o cokolwiek. Renderuje w rozmowie kartę z numerowanymi opcjami i blokuje się, aż ktoś odpowie, pominie pytanie albo upłynie jego limit czasu. Nigdy nie zapisuj pytania jako wiadomości czatu — to kończy turę.

| Argument          | Znaczenie                                 |
| ----------------- | ----------------------------------------- |
| `question`        | O co zapytać                             |
| `context`         | Opcjonalne: dlaczego pytasz i co zależy od odpowiedzi |
| `options[]`       | Opcje, każda `{label, description?}`     |
| `allow_free_text` | Czy odpowiedź wpisana z klawiatury jest przyjmowana |
| `multi_select`    | Czy można wybrać kilka opcji             |

Pominięcie to sukces: działaj na podstawie wyraźnie podanego założenia i nie pytaj ponownie. Upłynięcie limitu czasu to błąd z tą samą instrukcją. Prośby o pozwolenie („czy mogę to zrobić?”) to osobna bramka i renderują się jako ta sama karta w rozmowie.

Rejestrowane tylko wtedy, gdy istnieje zarówno port pytań, jak i docelowa przestrzeń. Bez podłączonego człowieka wywołanie **zawodzi**, zamiast blokować się na zawsze — ta sama postawa domyślnej odmowy (fail-closed), którą przyjmuje `prompt` guardraila, gdy nie ma podłączonego zatwierdzającego.

## `vibe_*` — kierowanie workerami w tle

Rejestrowane tylko wtedy, gdy włączony jest [tryb vibe](/pl-PL/podrecznik/poradniki/kierowanie-workerami-w-tle/). Wszystkie pięć należą do poziomu `read`: bramka należy do narzędzi workera, tam gdzie faktycznie dochodzi do edycji.

| Narzędzie    | Argumenty                              | Uwagi                                  |
| ------------ | -------------------------------------- | -------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`              | Zwraca natychmiast; worker działa dalej |
| `vibe_send`  | `worker_id`, `message`                 | Dopisuje do zlecenia i uruchamia ponownie |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`        | Blokuje, aż worker się ukończy         |
| `vibe_kill`  | `worker_id`                            | Zatrzymuje go                          |
| `vibe_list`  | —                                      | Poziom, status, czas i ostatni wynik   |

`tier` to `fast` (praca mechaniczna o jasnej specyfikacji) albo `good` (projektowanie, osąd albo recenzowanie wyniku workera `fast`).
