:::caution[To, czy uruchomienie działa w sandboxie, zależy od hosta]
`cc_server` ustala raz, przy starcie, jak agenci działają na tym hoście, i ta decyzja obowiązuje do ponownego uruchomienia:

- **W piaskownicy** (`native`): sonda znalazła backend, a `--sandbox` nie ma wartości `off`. Opakowane są oba punkty podłączenia wysyłania: CLI Claude Code przez port sandboxa oraz ACP i wbudowane narzędzie `bash` harnessa przez menedżer sandboxa.
- **Wyłączony** (`off`): właściciel serwera uruchomił go z `--sandbox off`. Agenci każdego członka działają na tej maszynie bez ograniczeń, bez względu na to, kto ich uruchomił.
- **Niedostępny** (`unavailable`): sandbox jest włączony, ale sonda nie znalazła backendu (**zawsze w Windows** oraz w Linuksie lub WSL2 bez `bwrap` i `socat`). Uruchomienie startuje tylko wtedy, gdy odpowiedzialną za nie osobą jest [właściciel](/pl-PL/podrecznik/koncepcje/autoryzacja/#właściciel-serwera) serwera: osoba, która o nie poprosiła, albo, w przypadku automatyzacji, osoba, z którą jest powiązana. Uruchomienie każdej innej osoby jest odrzucane, zanim zostanie przydzielona dzierżawa, wydane poświadczenie albo uruchomiony proces. Gdy nie zapisano właściciela, nic nie startuje.

Odrzucone uruchomienie kończy się kodem `sandbox_unavailable`. Aplikacja pokazuje go jako **Agenty potrzebują piaskownicy na tym serwerze**: „Ten serwer nie ma piaskownicy, więc agenty mogą tu uruchamiać tylko jego właściciel. Właściciel może zainstalować piaskownicę albo wyłączyć piaskownicowanie dla wszystkich.”

Uruchomienie, które startuje bez sandboxa (przy `off` albo własne uruchomienie właściciela przy `unavailable`), działa bezpośrednio na hoście. ACP i narzędzie `bash` harnessa nadal startują z sanityzacją środowiska; Claude Code przechodzi przez `NoSandboxAdapter` i dziedziczy środowisko hosta. Pozostałe granice to własny worktree uruchomienia (copy-on-write tam, gdzie dostarczany jest `rift`; `git worktree` w Windows), token hosta kodu tylko do odczytu, brokerowany przy każdym starcie i odwoływany przy zamykaniu, push, który musi przejść regułę push w bramie uruchomień agentów, polityka poleceń dla danego trybu, ujednolicone [guardraile akcji](/pl-PL/podrecznik/koncepcje/guardraile/) (domyślnie odmawiające), sanityzacja środowiska na ścieżkach ACP i `bash` harnessa oraz powierzchnia narzędzi dozwolona przez jego tryb.

Narzędzia plikowe harnessa działające w procesie (read, write, edit, apply patch, search, find, search_files) są poza sandboxem na każdym hoście: działają w procesie serwera, więc opakowany jest tylko `bash`.

Host nigdy nie jest rozwiązaniem zapasowym dla serwera z sandboxem. Jeśli serwer izoluje agentów, ale nie ma sandboxa, który mógłby przydzielić uruchomieniu, jego procesy narzędzi i polecenia `bash` są odrzucane, a nie uruchamiane na hoście. Ta sama postawa rozstrzyga o małych procesach wokół uruchomienia: jednorazowe pomocnicze procesy ACP (tytuły rozmów, `/btw`, `/handoff`, `/goal`) oraz golden testy pull requesta w Review Studio działają w sandboxie, gdy serwer izoluje agentów, bez ograniczeń przy `off`, a przy `unavailable` tylko dla żądania, za które odpowiada właściciel serwera; w pozostałych przypadkach są pomijane.
:::

## Przegląd backendów

| Backend     | Wartość     | Platforma                                      | Dostępność                                                                                                      |
| ----------- | --------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Zamknięta VM | `microvm` | macOS, Linux, Windows (hypervisor microVM)    | Bramkowane sondą runtime'u microVM; dotyczy interaktywnych terminali — powłoka działa wewnątrz [riga](/pl-PL/podrecznik/koncepcje/rigi/), a nie na hoście |
| Natywny sandbox      | `native`  | macOS (Seatbelt), Linux i WSL2 (bubblewrap) | Sonduje się przy starcie; Linux odmawia uruchomienia wymagającego zakazów zapisu dla wzorców nazw plików, których bubblewrap nie potrafi wyegzekwować |
| Bez izolacji      | `none`    | Wszystkie                                           | Domyślna wartość parsowania i domyślna wartość terminala; wysyłanie agentów używa jej przy `--sandbox off` oraz dla własnych uruchomień właściciela, gdy żaden backend nie jest dostępny |

`SandboxBackend.fromName` zwraca `none` dla pustej (null) lub nierozpoznanej zapisanej wartości.

**`microvm` to jedyny backend z granicą jądra** — obciążenie naprawdę
nie działa na hoście. Nigdy nie jest cichym rozwiązaniem zapasowym w żadnym
kierunku: jawne zażądanie go na hoście, który nie potrafi uruchomić VM, kończy
się głośnym błędem („poprosiłem o VM, a dostałem swój laptop" to jedyna
degradacja, na którą ta izolacja nie może sobie pozwolić), a tylko *nieokreślona
wartość domyślna* schodzi do `native`, z linią w logu, która to komunikuje.
Rzeczywisty backend sesji jest raportowany z powrotem do klienta i oznaczany
plakietką, więc terminal nigdy nie może twierdzić, że jest zamknięty, gdy działa
na hoście. Cykl życia, obrazy i ruch wychodzący samej VM opisuje
[dokumentacja referencyjna rigów](/pl-PL/podrecznik/dokumentacja-referencyjna/rigi/).

**Windows nie ma natywnego sandboxa.** `NativeSandboxAdapter.probe` zwraca `available: false` na każdym hoście, który nie jest macOS ani Linux/WSL2, więc serwer w Windows jest `unavailable`: startują tylko uruchomienia agentów właściciela serwera, bez ograniczeń, a wszystkie pozostałe są odrzucane. Aby każdy członek mógł tam uruchamiać agentów, właściciel uruchamia serwer z `--sandbox off`, co uruchamia je wszystkie bez ograniczeń. Backend `microvm` jest odrębny: jest bramkowany sondą runtime'u microVM i dotyczy interaktywnych terminali oraz rigów, a nie opakowywania `bash` na hoście.

## Wyniki sondy

To sonda bramkuje egzekwowanie. Działa raz, przy starcie serwera.

| Host                                   | `available` | Uwaga / wskazówka                                                               |
| -------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS                                  | `true`      | `sandbox-exec` (Seatbelt) — izolacja przestrzeni nazw, bez granicy jądra       |
| Linux lub WSL2 z `bwrap` i `socat` | `true`      | bubblewrap — izolacja przestrzeni nazw, bez granicy jądra                      |
| Linux lub WSL2 bez któregokolwiek z narzędzi      | `false`     | `requiresInstall: true`, ze wskazówką instalacyjną wymieniającą brakujące pakiety |
| Każda inna platforma                     | `false`     | Natywny sandbox nie jest oferowany na tej platformie                            |

Serwer zapisuje wynik w jednej linii startowej: `agent sandbox ON` plus uwaga; `no OS-native agent sandbox on this host` plus wskazówka, która dodaje, że wystartują tylko uruchomienia, za które odpowiada właściciel serwera; albo `agent sandbox DISABLED by --sandbox off`. Wiersz ekspozycji wypisywany przy starcie niesie tę samą decyzję jako `sandbox=native`, `sandbox=off` albo `sandbox=unavailable`. `GET /healthz` nie zawiera pola sandboxa.

`--sandbox` / `CC_SERVER_SANDBOX` przyjmuje `on` (domyślnie) albo `off`. `on` opakowuje każde uruchomienie, gdy host oferuje backend, a gdy nie oferuje, dopuszcza tylko uruchomienia właściciela. `off` uruchamia agentów każdego członka na tym hoście bez ograniczeń; to wybór właściciela dla wszystkich, a nie ustawienie dla pojedynczego uruchomienia.

## Backend natywny

### macOS: Seatbelt

Wykorzystuje mechanizm sandboxa Seatbelt firmy Apple (ten sam system, którego używa macOS App Sandbox).

Generowany profil jest **domyślnie permisywny** (`(allow default)`) i wycina z niego odmowy, bo w pełni odmawiający domyślnie profil czyni interaktywną powłokę bezużyteczną — wywołań dyld, XPC i Mach jest zbyt wiele, by je wyliczyć. Praktyczna konsekwencja jest taka, że agent nadal może odczytać większość hosta; Twoje zarejestrowane kopie robocze chronią jawne odmowy zapisu i zmiany nazwy, a nie niewidzialność.

- **Odczyty systemu plików**: odmawiane dla ścieżek z sekretami (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` i pozostałych ze zbioru zakazu odczytu)
- **Zapisy systemu plików**: resetowane do odmowy, a następnie jawne zezwolenia na podścieżki, przy czym ścieżki objęte obowiązkowym zakazem (pliki rc powłoki, `.git/hooks`, konfiguracja Claude, chronione kopie robocze) są blokowane nawet wewnątrz korzenia z prawem zapisu. `file-write-unlink` jest odmawiany na każdej zabronionej ścieżce i jej przodkach, więc zmiana nazwy nie może ominąć zakazu zapisu
- **Procesy**: odmowy `process-exec` dla zawsze niebezpiecznych plików binarnych oraz blokada wykonywania czegokolwiek z katalogu z prawem zapisu. Znane katalogi instalacji narzędzi w katalogu domowym (corepack, pamięci podręczne `npx` i `pnpm dlx`, menedżery wersji node, przeglądarki Playwright, rustup i cargo, Go, fvm i pamięć podręczna pub, pyenv, uv i pipx, rbenv, sdkman, mise, asdf oraz `~/.local/bin`) są ponownie otwierane pod tą blokadą. Wspólne katalogi tymczasowe też są zablokowane. Zamiast tego każda sesja dostaje prywatny `TMPDIR` pod `/private/tmp`, w którym mogą działać programy zbudowane przez agenta (plik binarny `go test`, build cargo). Zawsze niebezpieczne odmowy są stosowane po tych zezwoleniach
- **Sieć**: ograniczona do portów proxy działających w procesie plus DNS — pętla zwrotna nie jest dozwolona hurtowo, a nasłuch TCP jest odrzucany. Gniazda Unix są dozwolone wyłącznie w prywatnym `TMPDIR` sesji, który obejmuje narzędzia takie jak tsx i Chrome trzymające tam gniazdo IPC; agent SSH i inne gniazda pozostają nieosiągalne. Proxy egzekwują listę dozwolonych domen dla sesji (zobacz [Ruch wychodzący w sieci](#ruch-wychodzący-w-sieci))
- **Konfiguracja**: profile są generowane przy każdym starcie na podstawie `SandboxSpec`
- **Polecenia serwera**: żaden bezpośredni potomek folderu, z którego serwer uruchamia programy (każdy wpis `PATH` i zwykłe foldery narzędzi użytkownika, takie jak `~/.local/bin`, z rozwiązanymi dowiązaniami menedżerów wersji, np. `~/fvm/default`), nie może zostać utworzony, zastąpiony, usunięty ani przemianowany, ani zainstalowany pakiet, na który wskazuje dowiązane polecenie. Zobacz [Foldery poleceń serwera](#foldery-poleceń-serwera)
- **Pliki startowe**: każda ścieżka domowa, której profil odmawia odczytu, jest też odmawiana do zapisu, a pliki startowe powłok i sesji użytkownika serwera (`.zshenv`, `.zlogin`, `.bash_login`, konfiguracja fish, jednostki użytkownika systemd, wpisy autostartu i podobne) mają zakaz zapisu w każdym trybie

Wymagania:

- `sandbox-exec` (`/usr/bin/sandbox-exec`), część każdej instalacji macOS — nie wymaga dodatkowych narzędzi

### Linux: bubblewrap

Używa bubblewrap (`bwrap`) do tworzenia przestrzeni nazw montowania i PID.

- **System plików**: tworzy przestrzeń nazw montowania, w której widoczne są tylko podmontowane ścieżki
- **Sieć**: działa w niewspółdzielonej przestrzeni nazw sieci; ruch dociera do proxy hosta przez mostki gniazd Unix `socat`
- **Procesy**: izolacja przestrzeni nazw PID
- **Polecenia serwera i pliki startowe**: te same zabezpieczenia co w macOS, wyrażone jako montowania bubblewrap. Nie są jeszcze zweryfikowane w Linuksie, a brakujący folder poleceń może tam nadal zostać utworzony

Wymagania:

- zainstalowane `bubblewrap` i `socat` (`sudo apt-get install bubblewrap socat` w Debianie/Ubuntu)
- obsługa przestrzeni nazw w jądrze (standard w nowoczesnym Linuksie)

Bubblewrap potrafi przesłonić istniejącą ścieżkę, ale nie potrafi zakazać *nowego* pliku `.env`,
`*.key` lub `*.pem` wewnątrz podmontowanego katalogu z prawem zapisu. Standardowa polityka wysyłania
wymaga tych zakazów dla wzorców nazw plików, więc natywne wysyłanie agentów obecnie
**odmawia działania na Linuksie/WSL2, nawet gdy sonda znajdzie bubblewrap**. Nie
działa z cicho osłabioną polityką. Aby przywrócić natywne wysyłanie w Linuksie,
potrzebny jest backend z regułami nazw plików działającymi w momencie tworzenia. Wyłączenie sandboxowania to
jawne, nieograniczone zrezygnowanie, a nie równoważne obejście.

W praktyce serwer Linux lub WSL2 uruchamia dziś agentów na jeden z dwóch sposobów. Uruchomiony z `--sandbox off` uruchamia agentów każdego członka bez ograniczeń. Bez zainstalowanego bubblewrap albo `socat` jest `unavailable` i uruchamia tylko agentów właściciela serwera, bez ograniczeń. Gdy oba narzędzia są zainstalowane, a sandbox włączony, każde uruchomienie kończy się odmową, także uruchomienia właściciela.

## Foldery poleceń serwera

Serwer znajduje przy starcie każdy folder, z którego uruchamia programy: każdy wpis swojego `PATH`, foldery narzędzi użytkownika, które sprawdza (takie jak `~/.local/bin`, `~/.bun/bin` oraz globalne foldery npm, yarn i pnpm), i prawdziwy folder za każdym dowiązaniem po drodze (dowiązania menedżerów wersji, jak `~/fvm/default` albo domyślna wersja fnm). W sandboxie agent nie może dodać, zastąpić, usunąć ani przemianować polecenia w tych folderach, dowiązania prowadzącego do takiego polecenia ani zainstalowanego pakietu, na który wskazuje dowiązane polecenie, i nie może przemianować folderów nad nimi. W przeciwnym razie uruchomienie w sandboxie mogłoby podrzucić program, który serwer lub osoba później uruchomi poza sandboxem.

Co to zmienia dla uruchomienia:

- Globalne instalacje z wnętrza uruchomienia w sandboxie kończą się błędem „Operation not permitted”: `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, a także `cargo install`, `go install` lub `dart pub global activate`, gdy ich folder binarny jest w `PATH` serwera.
- Przełączanie domyślnej wersji kończy się tak samo (`fnm default`, `nvm alias default`, `fvm global`), podobnie jak samoaktualizacja narzędzia w miejscu.
- Instalacje lokalne dla projektu (`node_modules/.bin`), `npx`, `pnpm dlx`, menedżery pakietów zarządzane przez corepack, pamięci podręczne SDK i zwykłe buildy nadal działają.

Aby udostępnić agentom globalne narzędzie, zainstaluj je na samym serwerze, jako użytkownik serwera, i uruchom serwer ponownie, aby nowe polecenie też było chronione. Albo zainstaluj je w projekcie. Polecenie zainstalowane po starcie serwera jest w pełni chronione dopiero od następnego startu.

Wymuszane i testowane na macOS. W Linuksie te same reguły są montowaniami bubblewrap, które nie są jeszcze zweryfikowane. Windows nie ma sandboxa.

## Backend bez izolacji

Brak sandboxowania. Proces działa bezpośrednio na hoście, z dostępem hosta do systemu plików, sieci i procesów. ACP i narzędzie `bash` harnessa nadal otrzymują sanityzację środowiska oraz politykę poleceń; Claude Code przez `NoSandboxAdapter` dziedziczy środowisko hosta. Wysyłanie agentów używa go w każdym uruchomieniu przy `--sandbox off`, a na hoście bez dostępnego backendu tylko dla własnych uruchomień właściciela serwera; uruchomienie każdej innej osoby jest tam odrzucane. Dla terminala jest to powłoka hosta, którą może otworzyć tylko właściciel serwera.

## Terminal hostowany na serwerze

Terminal hostowany na serwerze otwiera powłokę hosta tylko dla [właściciela](/pl-PL/podrecznik/koncepcje/autoryzacja/#właściciel-serwera) serwera. Wszyscy inni dostają terminal w sandboxie, z ograniczeniami agenta, w katalogach własnych obszaru roboczego.

Jak wybierany jest backend dla sesji:

| Zażądano | Właściciel serwera | Każdy inny |
| --- | --- | --- |
| Nic nie podano | Domyślny backend serwera | Domyślny, z `none` zastąpionym przez `native` |
| `none` (powłoka hosta) | Powłoka hosta | Odrzucane: powłoka hosta działa na serwerze bez sandboxa |
| `native` | Natywny sandbox, profil właściciela | Natywny sandbox, profil agenta |
| `microvm` | Zamknięta VM | Zamknięta VM |
| Nieznana nazwa | Odrzucane | Odrzucane |

- **Profil właściciela.** `$HOME` i katalog roboczy sesji są zapisywalne, sieć jest otwarta, a `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` i `~/Library/Keychains` mają zakaz odczytu.
- **Profil agenta** (`memberTerminalSandboxConfig`). Ta sama polityka, pod którą działa agent w tym obszarze roboczym: zapisy zostają w katalogu roboczym, prywatnym katalogu uruchomienia, w `/tmp` i w tych częściach `$HOME`, do których agent może pisać; sekrety mają zakaz odczytu; sieć to lista dozwolonych ruchu wychodzącego agenta; programy uruchamiają się tylko z katalogu roboczego i zainstalowanych toolchainów.
- Terminal otwiera się tylko w katalogach własnych obszaru roboczego. Katalog roboczy poza nimi jest odrzucany, a nigdy nie zamieniany na inny.
- Tylko osoba, która otworzyła terminal, może z niego czytać, pisać do niego, zmieniać jego rozmiar albo go zamykać. Dla każdego innego jego identyfikator wygląda jak nieznany.
- `microvm` zażądany wprost na hoście bez usługi rigów kończy się błędem zamiast przełączać się na rozwiązanie zapasowe. Domyślne `microvm` na takim hoście schodzi do `native` i mówi o tym w logu.

Token hosta kodu tylko do odczytu i brama push nie mają zastosowania do terminali: to sprawy wysyłania. Jeśli opakowanie nie jest obsługiwane, sesja kończy się błędem, zamiast pokazywać plakietkę sandboxa przy sesji z powłoką hosta.

## Ruch wychodzący w sieci

Gdy sandbox jest uruchamiany, dostęp wychodzący do sieci jest egzekwowany przez proxy działające w procesie, a nie przez reguły firewalla jądra. Uruchomienie, które nie jest w sandboxie (każde uruchomienie przy `--sandbox off` albo uruchomienie właściciela na hoście bez backendu), nie dostaje nic z tego: uruchomiony przez nie proces dociera do sieci dokładnie tak, jak zrobiłby to użytkownik serwera.

- Runtime sandboxa uruchamia proxy HTTP/HTTPS oraz proxy SOCKS5 na `127.0.0.1` wewnątrz procesu `cc_server`, **po jednej parze na ograniczoną sesję** (`http_proxy.dart`, `socks_proxy.dart`). Równoległe uruchomienia nie dzielą pary.
- Procesy w sandboxie otrzymują zmienne środowiskowe proxy (`HTTP_PROXY`/`HTTPS_PROXY` → proxy HTTP, `ALL_PROXY` → proxy SOCKS; `GIT_SSH_COMMAND` kieruje git po SSH przez proxy SOCKS). W Linuksie przestrzeń nazw sieci jest niewspółdzielona, więc proxy to jedyne wyjście; w macOS sandbox współdzieli pętlę zwrotną hosta i rozmawia z nimi bezpośrednio.
- Docelowy host każdego połączenia jest dopasowywany do listy dozwolonych domen sesji; wszystko inne jest odrzucane. Istnieją dwie formy wieloznaczne, każda z dokładnie jednym `*`: wiodąca `*.example.com` pasuje do dowolnej subdomeny (w tym `a.b.example.com`), ale nie do samej domeny głównej; środkowa etykieta `bedrock.*.amazonaws.com` pasuje do dokładnie jednej etykiety (`bedrock.us-east-1.amazonaws.com`, a nie `bedrock.evil.attacker.amazonaws.com`).
- Lista dozwolonych jest wyznaczana dla każdej sesji na podstawie wyselekcjonowanej bazy (`kBaselineAllowedDomains`: dostawcy LLM, hosting Git, rejestry pakietów) plus domeny GitHub (`kGithubDomains`), plus `SandboxSpec.egressAllowlist`. Ścieżka wysyłania nigdy nie przekazuje dodatkowych wpisów `egressAllowlist`, więc w praktyce każde uruchomienie dostaje bazę plus GitHuba.
- Stała lista zakazów (`kBaselineDeniedDomains`: punkty końcowe metadanych chmury, ujścia telemetrii) ma pierwszeństwo przed wszystkimi zezwoleniami.
- `networkEnabled: false` nadal uruchamia proxy dla sesji, ale lista dozwolonych jest pusta, więc każde połączenie wychodzące jest odrzucane. Wysyłanie ustawia tę wartość na starcie uruchomienia na podstawie reguły **Dostęp do sieci**: odmowa wyłącza sieć, zezwól i zapytaj najpierw zostawiają ją włączoną.

## SandboxSpec

Specyfikacja przekazywana do `SandboxPort.launch`:

| Pole             | Typ                                        | Opis                                                                                                                                 |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | Stabilny identyfikator sesji (zwykle identyfikator przestrzeni)                                                                                          |
| `workspaceId`     | `String`                                    | Identyfikator obszaru roboczego będącego właścicielem                                                                                                                         |
| `agentId`         | `String?`                                   | Agent aktualnie powiązany z sandboxem, jeśli istnieje                                                                                                |
| `bindMounts`      | `List<SandboxBindMount>`                    | Montowania host→gość; sandbox widzi tylko wymienione tu ścieżki hosta                                                                         |
| `networkEnabled`  | `bool` (domyślnie `true`)                     | Ustawiane przy wysyłaniu na podstawie reguły ruchu wychodzącego sieci (wyłączone tylko wtedy, gdy rozstrzyga się na odmowę). Gdy wyłączone, proxy dla sesji nadal startują, ale lista dozwolonych jest pusta, więc każde połączenie wychodzące jest odrzucane |
| `egressAllowlist` | `List<String>` (domyślnie `[]`)               | Dodatkowe dozwolone domeny ruchu wychodzącego; obsługiwane wieloznaczniki (`*.example.com` oraz środkowa forma z jedną etykietą). Wysyłanie nigdy tego nie wypełnia, więc opakowane uruchomienie dostaje wyselekcjonowaną bazę plus domeny GitHub |
| `guestWorkdir`    | `String?`                                   | Domyślny katalog roboczy wewnątrz sandboxa; pojedyncze wywołania `exec` mogą go nadpisać                                                       |
| `mode`            | `Mode` (domyślnie `chat`)                     | Wycina reguły zapisu systemu plików: `chat` pozostawia montowania z prawem zapisu; `review`, `plan` i `orchestrate` są tylko do odczytu                      |
| `protectedPaths`  | `List<String>` (domyślnie `[]`)               | Ścieżki hosta, które nigdy nie mogą mieć prawa zapisu wewnątrz sandboxa, w żadnym trybie                                                                      |
| `runnerStateDirs` | `List<String>` (domyślnie `[]`)               | Katalogi hosta, w których runner trzyma własny stan, z prawem zapisu w każdym trybie (obecnie zarządzany przez Control Center `CLAUDE_CONFIG_DIR`) |
| `execGrantRoots`  | `List<String>` (domyślnie `[]`)               | Zatwierdzone przez operatora drzewa katalogów, które ponownie otwierają blokadę wykonywania z katalogu z prawem zapisu w macOS. Linux je ignoruje — bwrap nie ma blokady wykonywania w `$HOME`, którą można by ponownie otworzyć |

`protectedPaths` zawiera oryginalne, zarejestrowane kopie robocze repozytoriów, wyznaczane przy każdym wysłaniu z repozytoriów obszaru roboczego. Agenci pracują wyłącznie w kopiowanych przy zapisie worktree przypadających na rozmowę, więc oryginały nigdy nie mogą mieć prawa zapisu z wnętrza sandboxa — w macOS ogólne zezwolenie Seatbelt na zapis w `$HOME` pozostawiłoby im prawo zapisu przez `bash`. Dołączają do zestawu zakazu zapisu dla sekretów w każdym trybie, w tym w `chat`.

Każda ścieżka zakazu odczytu i zakazu zapisu jest emitowana zarówno w dosłownym zapisie, jak i w zapisie po rozwiązaniu dowiązań symbolicznych. Jądro dopasowuje regułę zakazu do rozwiązanej ścieżki, więc reguła zapisana względem ścieżki będącej dowiązaniem symbolicznym nigdy nie zadziała — a w macOS to przypadek częsty, nie egzotyczny, bo `/tmp` rozwiązuje się do `/private/tmp`, a `/var/folders/…` do `/private/var/folders/…`. Wpisy zawierające `*` lub `?` są traktowane jako wzorce i pozostawiane bez zmian; ścieżka, która się nie rozwiązuje, jest zachowywana w zapisanej postaci.

## SandboxBindMount

| Pole       | Typ                     | Opis                                                                                             |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `hostPath`  | `String`                 | Ścieżka bezwzględna na hoście                                                                               |
| `guestPath` | `String`                 | Ścieżka wewnątrz sandboxa (w sandboxie natywnym jest równa `hostPath`; zachowana dla symetrii adapterów) |
| `readOnly`  | `bool` (domyślnie `false`) | Gdy true, montuj tylko do odczytu                                                                               |

## SandboxHandle

Zwracany przez `SandboxPort.launch`:

| Pole       | Typ                   | Opis                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | Identyfikator sesji                                                       |
| `backend`   | `SandboxBackend`       | Który backend działa                                                 |
| `state`     | `SandboxState`         | Stan cyklu życia                                                          |
| `error`     | `Object?`              | Ustawiane, gdy `state` ma wartość `error`                                              |
| `details`   | `Map<String, Object?>` | Wewnętrzna księgowość adaptera (katalog roboczy, PID, ścieżka profilu itd.) |

### SandboxState

| Stan       | Opis                                 |
| ----------- | ------------------------------------------- |
| `created`   | Specyfikacja utworzona, ale VM jeszcze nie wystartowała |
| `warm`      | Działa i jest gotowa do wykonywania poleceń          |
| `active`    | Wykonuje właśnie polecenie               |
| `suspended` | Wstrzymana / zapisana na dysk jako punkt kontrolny, aby oszczędzać RAM   |
| `destroyed` | Rozebrana; uchwyt nie jest już ważny    |
| `error`     | Uruchomienie nie powiodło się — zobacz `SandboxHandle.error`   |

## Zdarzenia sandboxa

| Typ zdarzenia  | Opis                                                  |
| ----------- | ------------------------------------------------------------ |
| `stdout`    | Standardowe wyjście z sandboxa                             |
| `stderr`    | Standardowe wyjście błędów z sandboxa                              |
| `exit`      | Proces sandboxa zakończył się (niesie `exitCode`)                  |
| `starting`  | Sandbox się uruchamia                                       |
| `ready`     | Sandbox jest gotowy przyjmować wywołania exec                        |
| `killed`    | Proces zabity przez hosta (OOM, przekroczenie limitu czasu, ręczne zatrzymanie)       |
| `violation` | Naruszono politykę sandboxa (niesie `SandboxViolation`) |

## SandboxViolation

| Pole                 | Typ      | Opis                                                                |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action`              | `String`  | Zabronione działanie (np. `file-read*`, `network-outbound`)                    |
| `target`              | `String`  | Ścieżka lub host będący celem zabronionej operacji                   |
| `raw`                 | `String?` | Surowa linia logu, przydatna przy debugowaniu                                         |
