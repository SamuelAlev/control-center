`cc_server` hostuje jeden rejestr narzędzi MCP (JSON-RPC 2.0), udostępniany na głównym porcie serwera (domyślnie `9030`) pod `POST /mcp` i `GET /sse`, w wersji protokołu `2024-11-05`. Każdy klient trafia do tego samego rejestru: aplikacja desktopowa, wersja webowa, zewnętrzni klienci MCP i wbudowany runtime agentów. Zewnętrzne serwery MCP można podłączyć do tego samego rejestru jako warstwę dynamiczną.

## Rozmiar rejestru

| Miara                                                                      | Liczba |
| -------------------------------------------------------------------------- | ------ |
| Narzędzia zarejestrowane przez `cc_server`                                 | 110    |
| Z `packages/cc_mcp`                                                        | 108    |
| Z `packages/cc_mcp_client` (odkrywanie narzędzi)                           | 2      |
| Zarejestrowane w rejestrze podstawowym (`server_mcp_registry.dart`)        | 63     |
| Zarejestrowane po starcie wraz z uruchamianiem ich usług (`cc_server_runtime.dart`) | 47     |
| Z 63 w rejestrze podstawowym — warunkowe wobec repozytorium grafu kodu     | 5      |

Pięć narzędzi grafu kodu jest rejestrowanych tylko wtedy, gdy host przekaże repozytorium grafu kodu do `buildServerMcpRegistry`. `cc_server` zawsze je przekazuje, więc w dostarczanym pliku binarnym wszystkie 110 są aktywne.

Pełny rejestr jest ogłaszany w `tools/list` bez bramkowania wykrywania. Narzędzia edytujące zgłoszenia są typowane.

:::note[Zewnętrzni klienci zawsze widzą cały katalog]
`tools/list` nigdy nie jest przycinana. Klienci MCP weryfikują nazwy narzędzi względem własnej zbuforowanej kopii tej listy i odrzucają wszystko, czego na niej nie ma, nie pytając serwera — ukryte tam narzędzie jest więc nieosiągalne, a nie tylko ciche.

**Wbudowany harness** działa inaczej: wczytuje na żądanie tylko rezydentny podzbiór definicji, a resztę dociąga przy pierwszym użyciu — to zachowanie po stronie harnessu, które nie zmienia tego rejestru. Zobacz [Kontekst narzędzi i cache promptów](/pl-PL/podrecznik/koncepcje/kontekst-narzedzi).
:::

:::note[Każda klasa narzędzi jest rejestrowana]
Plik źródłowy pod `packages/cc_mcp/lib/src/tools/` to narzędzie, które agent może
wywołać. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
przerywa build, jeśli nowa klasa narzędzia nie jest przez nic konstruowana.
:::

## Parametry wspólne

### `workspace_id`

**Wymagany** w każdym narzędziu dotykającym danych o zasięgu obszaru roboczego. Brakujący lub nieprawidłowy `workspace_id` zwraca jawny błąd, a wartość, która nie pasuje do obszaru roboczego encji docelowej, jest odrzucana, a nie po cichu ignorowana. Pomiń go w narzędziach rzeczywiście globalnych: `list_workspaces` oraz sześciu narzędziach newsfeeda (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), które korzystają z kanału właściciela serwera dla danego użytkownika. Narzędzia odkrywania (`search_tool_bm25`, `list_my_tools`) przyjmują go opcjonalnie, aby klasyfikować wywoływalność według trybu rozmowy. Gdy agent jest wysyłany przez serwer, obszar roboczy jest wymuszany po stronie serwera, więc agent nie może sięgnąć do innego obszaru roboczego, przekazując obcy identyfikator.

## Odkrywanie narzędzi

Oba pochodzą z `cc_mcp_client`, a nie z `cc_mcp`, i oba konsultują strażnika trybu, więc zgłaszają, co jest wywoływalne w _bieżącym_ trybie rozmowy.

| Narzędzie          | Opis                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `search_tool_bm25` | Przeszukuje katalog narzędzi po słowie kluczowym; zwraca pasujące narzędzia, ich schematy argumentów oraz informację, czy każde z nich jest teraz wywoływalne |
| `list_my_tools`    | Wylicza narzędzia wywoływalne teraz w tej rozmowie, przefiltrowane według jej trybu                                          |

Trzecie narzędzie odkrywania, **`search_tools`**, istnieje wyłącznie wewnątrz wbudowanego harnessu i nie należy do tego rejestru MCP. Uszeregowuje własną powierzchnię narzędzi danego uruchomienia i, w odróżnieniu od `search_tool_bm25`, **wczytuje** schematy znalezionych pozycji, aby agent mógł wywołać dopasowanie w następnej turze. Agenci działający na harnessie powinni je preferować; klienci MCP mają `search_tool_bm25`.

Agenci rozmawiają ze sobą przez przestrzenie (trwałe, widoczne na liście obecności). `ask_agent` to żądanie i odpowiedź z obowiązkowym limitem czasu; `delegate_task` jest chronione po stronie serwera przez pułap głębokości, wykrywanie cykli, kopertę budżetu i pułap autonomii.

## Narzędzia izolacji (rigi)

Sterują jednorazowymi maszynami — odizolowaną przeglądarką lub pulpitem
Linuksa, emulatorem Androida albo Symulatorem iOS — z wnętrza uruchomienia.
Rejestrowane po starcie, bezwarunkowo: to, czy maszyna rzeczywiście może się
uruchomić, jest pytaniem sondy, na które narzędzia odpowiadają przy każdym
wywołaniu. Powtarzane wywołania w jednej rozmowie korzystają z jednej maszyny;
zrzuty ekranu wracają jako treść obrazu z budżetem jednego obrazu na wynik,
a wyodrębniona treść strony/interfejsu jest ogrodzona jako niezaufane dane.
Cztery narzędzia użycia oraz `rig_close` deklarują `enclosureControl` jako
[klasę działań](/pl-PL/podrecznik/koncepcje/guardraile/) (narzędzia użycia
deklarują też `networkEgress` i `processSpawn`; `mobile_use` i `ios_use`
deklarują też `packageInstall`), więc tryby tylko do odczytu ich odmawiają.
`rig_list` nie deklaruje żadnej — odczytuje wyłącznie stan obszaru roboczego.
Pełny słownik czasowników dla każdej powierzchni znajduje się w
[dokumentacji referencyjnej rigów](/pl-PL/podrecznik/dokumentacja-referencyjna/rigi/#action-verbs).

| Narzędzie      | Opis                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------ |
| `computer_use` | Steruje pulpitem Linuksa w odizolowanej VM: ruch, kliknięcie, przeciąganie, przewijanie, wpisywanie, zmiana rozmiaru, schowek, zrzut ekranu |
| `browser_use`  | Steruje Chromium, Firefoksem lub WebKitem bez interfejsu graficznego (`engine`): nawigacja, kliknięcia, wypełnianie, ekstrakcja (a11y/DOM/konsola), schowek, zrzut ekranu |
| `mobile_use`   | Steruje Androidem przez ADB: inspekcja/wprowadzanie, zrzuty ekranu, instalowanie/uruchamianie/zatrzymywanie/resetowanie/odinstalowywanie aplikacji, deep linki i polecenia urządzenia w kształcie argv |
| `ios_use`      | Steruje Symulatorem iOS przez WebDriverAgent/CoreSimulator: inspekcja/wprowadzanie, zrzuty ekranu, instalowanie/uruchamianie/zatrzymywanie/odinstalowywanie aplikacji, deep linki i procesy symulatora w kształcie argv |
| `rig_list`     | Wylicza rigi obszaru roboczego wraz z powierzchnią, statusem, rozmiarem wyświetlania i kontrolerem |
| `rig_close`    | Niszczy riga i odrzuca należący do niego stan maszyny                                            |

## Nieudostępniane przez MCP

Kalendarz i spotkania nie mają narzędzi MCP. Agenci nie mogą czytać Twojego kalendarza, spotkań, transkrypcji, zadań ani decyzji. Podsumowanie, które tworzy zadania i decyzje, działa jako wbudowany [potok `meeting_summary`](/pl-PL/podrecznik/koncepcje/spotkania/), a nie jako narzędzie, które agent może wywołać.

## Bramkowanie narzędzi według trybu

Bramkowanie jest egzekwowane dwukrotnie z jednej tabeli (`ModeToolPolicy`): raz w dyspozytorze MCP dla adaptera Claude Code, a raz w rejestrze wbudowanego harnessu. Zablokowane wywołanie zwraca powód.

| Tryb          | Powierzchnia narzędzi                                                                                                                                                                                                               |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | Każde zarejestrowane narzędzie; bez listy dozwolonych                                                                                                                                                                               |
| `plan`        | Starannie dobrana lista dozwolonych. Brak zapisów do drzewa roboczego i brak czasowników zgłoszeń `create` / `assign` / `delegate`, ale dozwolone są pamięć, artefakty, listy zadań, `submit_plan`, `exit_plan_mode` oraz czasowniki ukończenia zgłoszenia na wysłanym zgłoszeniu |
| `review`      | Starannie dobrana lista dozwolonych: udział w recenzji, komunikacja, pobierające kontekst tylko do odczytu oraz pełny zestaw czasowników zgłoszeń, w tym `create_ticket` i `assign_ticket`                                          |
| `orchestrate` | Starannie dobrana lista dozwolonych: narzędzia badawcze i odczytu oraz `propose_orchestration`, `create_playbook` i `run_playbook`. Zatrudnianie, dekompozycja i ukończenie zgłoszenia zachodzą deterministycznie po zatwierdzeniu, nigdy w trakcie uruchomienia |

Dozwolone w każdym trybie niezależnie od listy dozwolonych:

| Zestaw                | Narzędzia                                                                                                                                                                                                                                                         |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pamięć i artefakty    | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Graf kodu             | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                       |
| Mechanika uruchomienia | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                    |

Obecność na liście dozwolonych nie czyni narzędzia wywoływalnym, a zachodzi też odwrotność: zdolność zadania pytania operatorowi to narzędzie **harnessu** (`ask_user`), więc nie pojawia się w tym katalogu MCP w ogóle.

## Narzędzia za bramką zatwierdzenia

Narzędzie może deklarować `requiresApproval`. Dyspozytor buduje wtedy `ApprovalPayload` i udostępnia go przez `ConfirmationPort`, zanim narzędzie się uruchomi; `cc_server` podłącza ten port, więc bramka działa.

Zarejestrowane narzędzia, które ją deklarują: `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

Niezależnie od tego ujednolicone guardraile działań obejmują bramką każde narzędzie, które deklaruje niepusty zbiór `ActionClass`. Decyzja `prompt` bez podłączonego zatwierdzającego jest odrzucana. Zobacz [Guardraile](/pl-PL/podrecznik/koncepcje/guardraile/).

## Możliwości bez narzędzia pod nimi

Nie każda możliwość w produkcie jest osiągalna dla agenta. Te nie mają żadnego
narzędzia, więc nazwa, którą być może widziałeś cytowaną gdzie indziej, zwraca „unknown tool”:

| Możliwość                               | Gdzie się zamiast tego znajduje                                                              |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| Zatrudnianie, zwalnianie i edycja agenta | Interfejs agentów. Nie ma narzędzia `hire_agent` / `fire_agent` / `update_agent`            |
| Tworzenie obszaru roboczego              | `workspace.upsert` przez RPC, które zasiewa i stempluje własność                             |
| Projekty (tworzenie / lista / aktualizacja / przypisanie) | Interfejs zgłoszeń. Projekty to powierzchnia operatora — zobacz [Projekty](/pl-PL/podrecznik/poradniki/projekty/) |
| Zadanie operatorowi blokującego pytania  | Narzędzie **harnessu** `ask_user`, nie MCP. Renderuje formularz w rozmowie i czeka zablokowane na odpowiedź |
| Diagnostyka poszczególnych agentów       | Nic. Nie ma `doctor` — zobacz [Diagnostyka agenta](/pl-PL/podrecznik/poradniki/diagnostyka-agenta/) |
| Kalendarz i spotkania                    | RPC tylko dla klientów-ludzi (zobacz wyżej)                                                  |
