Ten poradnik pokazuje, jak dać serwerowi własną GitHub App. Zajmuje to około
dwóch minut, robi to wyłącznie właściciel serwera i trzeba to zrobić tylko raz
na serwer.

:::note[Możesz tego nie potrzebować]
Przy włączonym Control Center Connect ludzie logują się do GitHuba przez
współdzieloną App od Control Center albo przez App, której używa Connect Twojej
organizacji. Zarejestruj własną, gdy wybrano **Użyj własnych aplikacji**: własna
aplikacja serwera jest używana tylko wtedy. Zobacz [Control Center Connect](/pl-PL/podrecznik/dokumentacja-referencyjna/connect/).
:::

Aby następnie zalogować się na własne konto, zobacz
[Skonfiguruj integrację GitHub](/pl-PL/podrecznik/poradniki/integracja-github/).

## Co robi aplikacja

Jedna rejestracja obsługuje dwa różne zadania:

| Zadanie                | Co na nie odpowiada                             | Dlaczego to ważne                                                                                 |
| ---------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Osoba się loguje**   | Identyfikator klienta i sekret klienta aplikacji | Każdy dostaje własne poświadczenie GitHub, na serwerze, na każdym urządzeniu                      |
| **Serwer działa**      | Identyfikator aplikacji i klucz prywatny        | Agenci, pipeline'y, odpytywanie i odpowiedzi bota dostają tokeny dla jednego repozytorium naraz   |

Drugie zadanie nigdy nie pożycza całego poświadczenia osoby. Każdy token, który
tworzy serwer, obejmuje jedno repozytorium i jest ograniczony do tego, co może
tam zrobić odpowiedzialny członek. Do odczytu połączonego repozytorium wystarczy
aplikacja; wszystko, co zapisuje, wymaga członka, który może wykonywać push.
Automatyzacja nigdy nie zatwierdza pull requesta.

Aplikacja serwera obowiązuje tylko przy **Użyj własnych aplikacji**. Przy aplikacjach
Control Center albo własnym Connect to Connect obsługuje każdą ścieżkę, także GitHub;
aplikacja serwera pozostaje zapisana, ale nieużywana, aż przełączysz z powrotem.
Obszar roboczy na własnych aplikacjach ([Daj jednemu obszarowi roboczemu własną aplikację](#daj-jednemu-obszarowi-roboczemu-własną-aplikację)) używa zamiast tego własnej aplikacji, niezależnie od trybu serwera. Aplikacja, której brakuje części pól, to błąd,
a nie przejście na rozwiązanie zapasowe: logowania do GitHuba są odrzucane, dopóki nie
ustawi się wszystkich pól.

## Wymagania wstępne

- Jesteś **właścicielem serwera**. Karta **Aplikacje dostawców** jest
  niewidoczna dla wszystkich innych
- Konto GitHub. Aplikacja zostanie utworzona pod nim
- Adres serwera osiągalny dla Twojej przeglądarki. Publiczny adres URL serwera
  (albo loopback w przypadku własnego serwera aplikacji desktopowej) to miejsce,
  do którego GitHub Cię odeśle

## Utwórz ją jednym kliknięciem

1. Przejdź do **Ustawienia → Serwer → Logowanie jednokrotne** i przewiń do
   karty **Aplikacje dostawców**
2. W bloku **GitHub** możesz opcjonalnie wpisać w polu **Organizacja
   (opcjonalnie)** organizację GitHub, która ma być właścicielem aplikacji.
   Pozostaw je puste, aby utworzyć aplikację na własnym koncie; utworzenie jej
   w organizacji wymaga właściciela tej organizacji
3. Kliknij **Utwórz moją aplikację GitHub**
4. Przeglądarka otwiera GitHuba z już wypełnioną aplikacją. Kliknij
   **Create GitHub App**
5. GitHub odsyła Cię z powrotem do serwera, który zapisuje identyfikator
   aplikacji, klucz prywatny, identyfikator klienta i sekret klienta, a potem
   otwiera stronę instalacji aplikacji

Nic nie jest kopiowane ręcznie, a kod konwersji trafia z GitHuba prosto na Twój
serwer. Link działa raz i wygasa po dziesięciu minutach; jeśli wygaśnie, kliknij
ponownie **Utwórz moją aplikację GitHub**.

Aplikacja nazywa się `Control Center <code>` i prosi dokładnie o to, czego
używa Control Center:

| Uprawnienie                                | Dostęp            |
| ------------------------------------------ | ----------------- |
| Metadata                                   | Odczyt            |
| Contents                                   | Odczyt i zapis    |
| Pull requests                              | Odczyt i zapis    |
| Issues                                     | Odczyt i zapis    |
| Checks, Actions, Commit statuses           | Odczyt            |
| Organization members                       | Odczyt            |

Webhooki są wyłączone: serwer sam odpytuje. Aby później przenieść aplikację
utworzoną na własnym koncie do organizacji, użyj **Transfer ownership**
w zaawansowanych ustawieniach aplikacji na GitHubie.

Punkt kontrolny: blok GitHub głosi „Serwer może działać jako on sam, a ludzie
mogą się logować.”

## Zainstaluj ją tam, gdzie są Twoje repozytoria

Aplikacja zarejestrowana, ale niezainstalowana, potrafi logować ludzi i nie
odczyta niczego.

1. Na stronie instalacji, którą otworzył GitHub, wybierz konto lub organizację,
   do której należą Twoje repozytoria
2. Wybierz **All repositories** albo zaznacz te, które ten serwer ma widzieć

Aby później zainstalować ją na innym koncie, administrator obszaru roboczego
przechodzi do **Ustawienia → Obszar roboczy → Integracje**, znajduje **Instalacje aplikacji GitHub** na karcie **Aplikacja GitHub** w sekcji Hosting kodu i klika **Zainstaluj aplikację GitHub**. Lista pokazuje każde konto, na którym aplikacja jest zainstalowana,
i oznacza zawieszoną instalację.

## Udostępnij instalację organizacji

Organizacja instaluje GitHub App jeden raz. Potem każdy w organizacji, kto loguje się do GitHuba na serwerze Control Center, może korzystać z tej instalacji, niezależnie od tego, czy serwer jest jego, kolegi, czy jego własny. Nie ma nic do autoryzowania dla poszczególnych serwerów.

Każdy token, jaki dostaje serwer, należy do zalogowanej osoby i jest ograniczony do jednego repozytorium oraz do jej roli w nim, więc nigdy nie sięga dalej, niż mogłaby na GitHubie. Dziennik audytu GitHuba pokazuje tę osobę, działającą przez aplikację.

Aby Control Center nie mógł sięgać do organizacji, właściciel organizacji usuwa instalację albo zawęża jej repozytoria na GitHubie. Usunięcie osoby z organizacji też kończy jej dostęp.

## Albo zarejestruj ją ręcznie

Karta **Aplikacje dostawców** przyjmuje też wartości bezpośrednio, dla
aplikacji, którą zarejestrowałeś sam:

| Grupa                              | Pola                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- |
| **Działanie jako serwer**          | **Identyfikator aplikacji** i **Klucz prywatny** (cały `.pem`, łącznie z wierszami `BEGIN` i `END`) |
| **Logowanie ludzi**                | **Identyfikator klienta** i **Sekret klienta**. **Adresy URL wywołania zwrotnego** pokazują adres do zarejestrowania, dosłownie |
| **Rozmowy przy pull requestach**   | **Login bota**, ustalany przy teście połączenia                                                 |

Zarejestruj adres URL wywołania zwrotnego `<server origin>/oauth/github/callback`
dokładnie tak, jak pokazuje go karta, pozostaw włączone **Expire user
authorization tokens** i przyznaj uprawnienia z tabeli powyżej. Kliknij
**Test**: pyta GitHuba, na których kontach aplikacja jest zainstalowana, więc
„zapisano” i „działa” nie zostaną pomylone.

## Skonfiguruj ją z pliku `.env` serwera

Przy instalacji bez interfejsu albo skryptowej serwer wypełnia każde pole ze
swojego pliku `.env` za pierwszym razem, gdy nie ma dla niego zapisanej wartości:

```bash
GITHUB_APP_ID=123456
GITHUB_CLIENT_ID=Iv23li0123456789abcd
GITHUB_CLIENT_SECRET=<secret>
GITHUB_APP_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\nMIIEow…\n-----END RSA PRIVATE KEY-----"
```

Umieść klucz w **jednym wierszu**: wartość w `.env` to jeden wiersz, a `\n`
w podwójnych cudzysłowach jest dekodowane jako znak nowego wiersza. Serwer
odmawia startu, gdy `GITHUB_APP_PRIVATE_KEY` albo `GITHUB_CLIENT_SECRET` jest
wyeksportowane w środowisku jego procesu, gdzie mógłby je odczytać każdy proces
potomny; trzymaj je w pliku `.env` (w Dockerze zamontuj go pod `/app/bin/.env`).
Wypełnianie następuje **raz na pole**, więc edycji w Ustawieniach nie cofnie
następny restart.

## Daj jednemu obszarowi roboczemu własną aplikację

Obszar roboczy może działać na własnej aplikacji zamiast aplikacji serwera:

1. Administrator obszaru roboczego przechodzi do **Ustawienia → Obszar roboczy → Integracje**
2. Na karcie **Control Center Connect** wybiera **Użyj własnych aplikacji** i klika **Zastosuj**. Wszyscy w obszarze roboczym logują się ponownie przez aplikacje obszaru roboczego
3. Karta **Aplikacja GitHub** w sekcji Hosting kodu zawiera teraz pola aplikacji: **Identyfikator aplikacji** i **Klucz prywatny** w sekcji **Działa w imieniu tego obszaru roboczego**, **Identyfikator klienta** i **Sekret klienta** w sekcji **Logowanie ludzi**. Po wypełnieniu kliknij **Test**

Członkowie logują się wtedy do tej aplikacji dla tego obszaru roboczego. Obszar roboczy na własnych aplikacjach nigdy nie przechodzi na aplikację serwera ani na Connect: dopóki jego pola nie są kompletne, jego praca z GitHubem jest odrzucana. Ten sam wybór obejmuje Kalendarz Google, Linear i wyszukiwanie GIF, każdy z własnymi polami obok dostawcy na tej samej stronie. Zobacz [Daj jednemu obszarowi roboczemu własną aplikację Linear](/pl-PL/podrecznik/poradniki/integracja-linear/#daj-jednemu-obszarowi-roboczemu-własną-aplikację-linear) oraz [Daj jednemu obszarowi roboczemu własnego klienta Google](/pl-PL/podrecznik/poradniki/podlaczanie-kalendarza/#daj-jednemu-obszarowi-roboczemu-własnego-klienta-google). Pozostałe wybory na tej karcie i to, co każdy z nich robi, opisuje [Wybór dla każdego obszaru roboczego](/pl-PL/podrecznik/dokumentacja-referencyjna/connect/#wybór-dla-każdego-obszaru-roboczego).

## Rozwiązywanie problemów

### Utwórz moją aplikację GitHub informuje, że serwer nie ma adresu

Serwer nie ma publicznego adresu URL, do którego mogłaby wrócić przeglądarka.
Ustaw `CC_SERVER_PUBLIC_URL` (albo `--public-url`) i spróbuj ponownie.

### GitHub informuje, że link wygasł

Jednorazowa strona została już użyta albo minęło dziesięć minut. Zacznij od
nowa w Ustawieniach.

### Test mówi, że poświadczenia działają, ale aplikacja nie jest nigdzie zainstalowana

Rejestracja i instalacja to osobne kroki. Otwórz stronę instalacji aplikacji
albo użyj **Zainstaluj aplikację GitHub** w Obszar roboczy → Integracje.

### Test mówi, że nie udało się odczytać klucza prywatnego

Wklej cały plik `.pem`, łącznie z wierszami `-----BEGIN` i `-----END`. Klucz
`ed25519` lub EC nie może zostać użyty: GitHub Apps podpisują za pomocą RSA.

### Członek się zalogował, ale nie widzi żadnych repozytoriów

Aplikacja nie jest zainstalowana na koncie, do którego należą, albo jej
instalacja obejmuje inne repozytoria. Logowanie daje dostęp tylko do tego, co
aplikacja może widzieć.

### Agenci informują, że instalacja GitHub App jest zawieszona

Ktoś zawiesił instalację na GitHubie. Wznów ją w **Settings → Applications →
Installed GitHub Apps** danego konta.
