Uruchom `cc_server` na maszynie, która jest stale włączona, a następnie połącz się
z nim ze swojego pulpitu, przeglądarki lub telefonu. Serwer to natywna binarka
napisana w czystym Dart — bez silnika Flutter — więc działa headless w systemach
macOS, Linux i Windows. Jest właścicielem bazy danych, uruchamia agentów i wykonuje
wszystkie wywołania zewnętrznych API; klienty tylko renderują interfejs.

## Uruchamianie w Dockerze (gotowe obrazy)

Każde wydanie publikuje hostowany samodzielnie stos czterech obrazów GHCR —
backend, dwa statyczne cienkie klienty i opcjonalny przekaźnik parowania — a
także opcjonalną usługę logowania `cc-connect`
([Uruchom serwer Connect](/pl-PL/podrecznik/poradniki/uruchamianie-serwera-connect/))
i osobny obraz `cc-server-demo` dla publicznego hosta demonstracyjnego.
Instalacja hostowana samodzielnie nie wymaga pobierania źródeł. Przypnij tag
wersji (`ghcr.io/samuelalev/<image>:v0.0.1-rc.1`) albo korzystaj z `latest`.

| Obraz                                        | Co to jest                                        | Publikuje      |
| -------------------------------------------- | ------------------------------------------------- | -------------- |
| `ghcr.io/samuelalev/cc-server`               | Backend: baza danych, agenci, MCP, webhooki       | `-p 9030:9030` |
| `ghcr.io/samuelalev/cc-webapp`               | Klient webowy (statyczny nginx)                   | `-p 8080:8080` |
| `ghcr.io/samuelalev/cc-remote`               | Towarzysząca aplikacja PWA na telefon (statyczny nginx) | `-p 8081:8080` |
| `ghcr.io/samuelalev/cc-signaling-server`     | Szyfrowany przekaźnik połączeń (opcjonalny)       | `-p 8788:8788` |

Cały stos jako plik compose:

```yaml
services:
  server:
    image: ghcr.io/samuelalev/cc-server:latest
    ports: ["9030:9030"]
    volumes: ["cc_data:/data"]
    restart: unless-stopped
  web:
    image: ghcr.io/samuelalev/cc-webapp:latest
    ports: ["8080:8080"]
    restart: unless-stopped
  remote:
    image: ghcr.io/samuelalev/cc-remote:latest
    ports: ["8081:8080"]
    restart: unless-stopped
  signaling:
    image: ghcr.io/samuelalev/cc-signaling-server:latest
    ports: ["8788:8788"]
    restart: unless-stopped

volumes:
  cc_data:
```

O czym warto wiedzieć, zanim wystawisz to wszystko poza loopback (sam TLS nie daje szyfrowania end-to-end sparowanego klienta ani nie autoryzuje zasobów):

- **Obraz `cc-server` zawiera `CC_SERVER_INSECURE=1`** (musi nasłuchiwać na
  `0.0.0.0`, aby odbierać ruch z opublikowanych portów). Użyj terminującego TLS
  odwrotnego proxy — Caddy, Traefik, nginx lub Cloudflare Tunnel — w zaufanej
  sieci albo zamontuj certyfikat i ustaw `CC_SERVER_TLS_CERT` /
  `CC_SERVER_TLS_KEY` (a następnie usuń `CC_SERVER_INSECURE`). To ustawienie
  steruje wyłącznie zewnętrznym nasłuchem HTTP/WebSocket serwera. Nigdy nie
  wyłącza obowiązkowej szyfrowanej end-to-end sesji klienta. TLS nadal chroni
  ruch logowania/startu, metadane połączeń, publiczne punkty końcowe i dostarczanie
  klienta webowego. Wszystko można nadpisać za pomocą `docker run -e …` lub
  bloku `environment:` w compose.
- **`/data` to cały stan.** Bazy SQLite, sekrety sparowanych urządzeń, pobrane
  modele i dźwięk ze spotkań — wszystko to mieszka w wolumenie; zrób jego kopię
  zapasową, a kontener stanie się jednorazowy.
- **Sekrety dostawców trafiają do zamontowanego `.env`, nigdy do `-e`.** Serwer
  odmawia startu, gdy `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`,
  `GOOGLE_OAUTH_CLIENT_SECRET`, `LINEAR_API_KEY` lub dowolne `SLACK_*SECRET*`
  znajduje się w środowisku jego procesu. Zamontuj plik tylko do odczytu pod
  `/app/bin/.env` (`-v /secure/cc.env:/app/bin/.env:ro`) albo skonfiguruj
  aplikacje w Ustawieniach.
- **Sparuj klienta z wnętrza obrazu** przed pierwszym połączeniem — to kontenerowy
  odpowiednik [kroku 3](#krok-3-sparuj-klienta-przed-pierwszym-uruchomieniem):

  ```bash
  docker run --rm -it -v cc_data:/data \
    --entrypoint /app/bin/cc_server ghcr.io/samuelalev/cc-server:latest pair
  ```

- **Oba obrazy klientów to statyczne hosty nginx.** Wbudowane edytory
  w przeglądarce korzystają z tego samego originu aplikacji i tego samego
  szyfrowanego połączenia, jak opisano [poniżej](#zasoby-edytora-w-przeglądarce).
  Formularz połączenia każdego klienta przyjmuje adres URL serwera,
  identyfikator urządzenia i klucz
  parowania. Przekaźnik sygnalizacyjny potrzebuje wyłącznie swojego portu
  (`SIGNALING_HOST` / `SIGNALING_PORT` można nadpisać); jest bezstanowy, nie
  przechowuje kluczy parowania i stanowi **mechanizm awaryjny** — telefon
  korzysta z loopbacku, sieci LAN, tailnetu albo bezpośredniej ścieżki `wss://`,
  gdy któraś z nich jest osiągalna, a sięga po przekaźnik tylko wtedy, gdy żadna
  nie jest. Pomiń go, jeśli Twoi klienci zawsze łączą się z serwerem
  bezpośrednio. Broker widzi identyfikatory routingu, adresy IP, rozmiary
  i czasy oraz może przerywać ruch; nie potrafi odszyfrować strumienia zasobów
  między klientem a serwerem.

Dalsza część tego poradnika buduje serwer ze źródeł; omawiane tu flagi i
zachowanie to te same, które zasilają zmienne środowiskowe obrazu.

## Wymagania wstępne

- [Dart SDK](https://dart.dev/get-dart). To repozytorium przypina swoje SDK za pomocą [fvm](https://fvm.app), więc każdą komendę poprzedź prefiksem `fvm`.
- Sklonowane to repozytorium.
- Natywny łańcuch narzędzi wymagany przez skrypt przygotowujący — Rust/`cargo` oraz `meson`, `ninja`, `pkg-config`, `git` i kompilator C++. Każdy skrypt budowania wskazuje, czego nie potrafi znaleźć i jak to zainstalować.
- Osiągalny host: loopback do użytku lokalnego albo adres LAN/publiczny z TLS dla klientów zdalnych.

## Krok 1: Przygotuj biblioteki natywne

Biblioteki natywne są **wymagane** — nie istnieje tryb zdegradowany. Zbuduj je z
katalogu głównego repozytorium, zanim zrobisz cokolwiek innego:

```bash
scripts/natives/build_natives.sh
```

To buduje `rift`, `fff`, tree-sitter wraz z jego gramatykami, `aec`, `lame`,
`ccpty`, `cc_watcher`, `cc_inference` oraz bibliotekę natywną SAML do
`build/natives/`. Hak budowania `cc_server`
ponownie emituje do pakietu wszystko, co zostało tam przygotowane, więc pominięcie
tego kroku albo od razu powoduje błąd budowania, albo — dzięki furtce awaryjnej
opisanej poniżej — daje binarkę, której kontrola wstępna podczas rozruchu odmawia
uruchomienia i wskazuje brakującą bibliotekę.

:::note[Furtka awaryjna tylko dla kompilacji]
Utworzenie pustego pliku `.cc_natives_allow_missing` w katalogu głównym
repozytorium łagodzi błąd budowania z powodu brakujących bibliotek natywnych do
ostrzeżenia. Służy do sprawdzania składni świeżego klona; serwer zbudowany w ten
sposób nie może wystartować. To musi być **plik** — runner haka budowania nie
przekazuje środowiska wywołującego, więc zmienna środowiskowa jest ignorowana.
:::

## Krok 2: Zbuduj binarkę

```bash
cd apps/cc_server
fvm dart build cli
```

Pakiet zawiera `libsqlite3` i przygotowane biblioteki natywne obok binarki — nie
potrzeba systemowego SQLite ani silnika Flutter. Plik wykonywalny trafia do
`./build/cli/<os_arch>/bundle/bin/cc_server`.

## Krok 3: Sparuj klienta przed pierwszym uruchomieniem

Świeży katalog danych nie ma sparowanego urządzenia ani współdzielonego klucza,
więc monitu klienta o klucz parowania nie da się jeszcze zaspokoić. Wygeneruj taki
klucz podkomendą `pair`. Zapisuje ona bezpośrednio pliki `global.db` i
`secrets.json`; serwer, który już obsługuje ten katalog danych, wykryje nowe
urządzenie bez restartu:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030
```

Wyświetla trzy wartości do wklejenia w formularz połączenia klienta:

```
Connect a thin client (paste into its connect form):
  Server      ws://localhost:9030/rpc
  Device id   web-client
  Pairing key <a freshly generated key>
```

Przydatne flagi: `--device` (domyślnie `web-client`; identyfikator wybiera też
klasę urządzenia — `desktop`, `ios`, `android`, cokolwiek innego to klient
webowy), `--label` (domyślnie nazwa platformy plus nazwa hosta tej maszyny),
`--host` (host wypisywany w adresie URL, ponieważ loopback nie jest osiągalny z
innej maszyny) oraz `--client-url`. Ponowne uruchomienie `pair` rotuje klucz tego
urządzenia i porzuca jego aktywne sesje. Parowanie nigdy nie tworzy obszaru
roboczego. Obszary robocze tworzy tylko właściciel serwera: na kliencie właściciela onboarding
nadaje nazwę i tworzy pierwszy z nich, a każdy inny czeka, aż właściciel utworzy dla niego
obszar albo administrator obszaru roboczego go zaprosi.

Z opcją `--client-url` wypisuje też kod QR do zeskanowania z terminala, który
otwiera klienta webowego z już wypełnionymi danymi:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030 \
  --bind any --host 192.168.1.42 --client-url https://app.usectrl.dev
```

:::caution[Ten kod QR to nie kod QR na telefon]
`--client-url` buduje link dla **klienta webowego** — adres URL serwera,
identyfikator urządzenia i klucz we fragmencie adresu. Aplikacja **Remote** na
telefon oczekuje innego ładunku (pełnego deskryptora połączenia serwera plus
terminu ważności), generowanego w **Ustawienia → Ty → Twoje urządzenia** w
działającym kliencie. Tych dwóch nie można używać zamiennie. Zobacz
[Sparuj urządzenie](/pl-PL/podrecznik/poradniki/parowanie-urzadzenia/).
:::

Poświadczenie wygenerowane przez `cc_server pair` wygasa po 30 dniach, tak jak wygenerowane w aplikacji; uruchom `pair` ponownie dla tego samego urządzenia, aby wydać nowe. Gdy urządzenie utworzone z
CLI przestanie być potrzebne, odwołaj je w
**Ustawienia → Ty → Twoje urządzenia**.

Klucz parowania uwierzytelnia obowiązkowy uścisk dłoni Noise; każda sesja
wyprowadza świeże klucze ruchu i sprawdza podpisaną tożsamość serwera. Chroń
klucz parowania i zdobądź go zaufanym źródłem (w tym zaufanym kodem QR), a
następnie zweryfikuj nowy odcisk serwera przez osobny zaufany kanał albo wobec
znanego przypięcia. Nie akceptuj po cichu zmienionego przypięcia: jeśli świadomie
wymieniasz tożsamość serwera, sparuj ponownie przez zaufany kanał. Sam TLS nie
ustali tego przypięcia tożsamości end-to-end.

## Krok 4: Uruchom serwer

Na loopbacku — to ustawienie domyślne i wszystko, czego potrzebujesz dla klienta
na tej samej maszynie:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030
```

Aby uzyskać do niego dostęp z innej maszyny, powiąż wszystkie interfejsy.
Powiązanie z adresem innym niż loopback bez TLS jest **odrzucane przy starcie**
(`Refusing to bind non-loopback address … without TLS`), więc dostarcz certyfikat:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --tls-cert /path/fullchain.pem --tls-key /path/privkey.pem \
  --public-url wss://server.example:9030/rpc
```

Albo terminuj TLS w odwrotnym proxy w zaufanej sieci prywatnej i zdecyduj się na
nieszyfrowane powiązanie za nim:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --insecure --public-url wss://server.example/rpc
```

`--insecure` jest ignorowane, gdy ustawione są jednocześnie `--tls-cert` i
`--tls-key` — TLS zawsze wygrywa. Serwer ogłasza stan nieszyfrowany zewnętrznego
nasłuchu jako `insecure: true` w `GET /healthz`. Nie wyłącza to szyfrowania Noise
na `/rpc`, niezależnie od tego, czy klient łączy się bezpośrednio, czy przez
przekaźnik. Aktualizuj serwer, przekaźnik i klientów razem: starzy klienci z
tekstem jawnym RPC są odrzucani, bez mechanizmu zgodności wstecznej. Publiczne
żądania do wrażliwych tras zasobów (w tym transferów kopii zapasowych) otrzymują
HTTP `426`, także z loopbacku; sparowani klienci korzystają zamiast tego
z szyfrowanego tunelu.

Serwer działa aż do `SIGINT`/`SIGTERM`, po czym zamyka się czysto.

### Odczytaj wiersze startowe

Dwa wiersze mówią, jak ten serwer jest skonfigurowany. Wiersz ekspozycji, wypisywany obok banera
gotowości, zaczyna się od `cc_server exposure:` i wylicza, jak daleko serwer może być osiągnięty
(`bind`, `tls`, `relay`, `tunnel`), czy zapisano właściciela serwera (`owner`) oraz jak agenci
działają na tej maszynie (`sandbox`):

- `sandbox=native`: każde uruchomienie agenta jest opakowane w sandbox systemu operacyjnego.
- `sandbox=off`: uruchomiono serwer z `--sandbox off`, więc agenci wszystkich członków działają
  na tej maszynie bez ograniczeń.
- `sandbox=unavailable`: host nie ma backendu sandboxa (Windows albo Linux bez `bwrap` i `socat`),
  więc startują tylko uruchomienia agentów, za które odpowiada właściciel serwera. Uruchomienia
  wszystkich pozostałych są odrzucane komunikatem „Ten serwer nie ma piaskownicy, więc agenty
  mogą tu uruchamiać tylko jego właściciel.”

Wiersz o piaskownicy wcześniej w logu mówi to samo słowami i, gdy brakuje backendu, podaje, co
zainstalować. Uruchamianie cudzych agentów bez piaskownicy to wybór właściciela serwera, dokonywany
raz, dla wszystkich, przez `--sandbox off`. Zobacz
[Skonfiguruj polityki sandboxa](/pl-PL/podrecznik/poradniki/polityki-sandboxa/#sprawdź-czy-uruchomienia-twojego-agenta-działają-w-sandboxie).

## Krok 5: Połącz klienta

Skieruj klienta na adres URL serwera i klucz parowania z kroku 3:

- **Aplikacja desktopowa**: na ekranie pierwszego uruchomienia kliknij **Połącz z serwerem** albo dodaj serwer później w **Ustawienia → Serwer → Połączenie i status**. Zobacz [Połącz się ze zdalnym serwerem](/pl-PL/podrecznik/poradniki/laczenie-ze-zdalnym-serwerem/).
- **Klient webowy**: otwórz [app.usectrl.dev](https://app.usectrl.dev) (lub własną kopię kompilacji webowej), kliknij **Połącz z serwerem** i podaj adres URL serwera oraz, w sekcji **Użyj klucza parowania**, identyfikator urządzenia i klucz parowania.
- **Telefon**: sparuj aplikację **Remote** z działającego klienta — zobacz [Sparuj urządzenie](/pl-PL/podrecznik/poradniki/parowanie-urzadzenia/).

:::note[cc_server nie serwuje żadnego pakietu webowego]
Samodzielny `cc_server` nigdy nie montuje katalogu głównego web, więc `GET /`
zwraca 404. Klient webowy jest hostowany osobno — użyj `app.usectrl.dev` albo
samodzielnie hostuj kompilację webową na dowolnym statycznym hoście HTTPS (obraz
`cc-webapp` powyżej to dokładnie taki host). Pochodzenie przeglądarki inne niż
loopback musi znajdować się na `--allowed-origins`, inaczej aktualizacja
WebSocket do `/rpc` jest odrzucana; domyślna lista to
`https://app.usectrl.dev`, a `localhost` / `127.0.0.1` są zawsze dozwolone.
:::

### Zasoby edytora w przeglądarce

Frontend edytora to zaufany kod aplikacji i działa w origin samej aplikacji
webowej. Jego Service Worker kieruje ruch HTTP i WebSocket przez tę samą
uwierzytelnioną szyfrowaną sesję co reszta klienta. `cc_server` odszyfrowuje
każde żądanie, przekazuje je do swojego lokalnego zaplecza code-server i
szyfruje odpowiedź z powrotem do klienta. Pliki pozostają własnością serwera.

Edytor działa na serwerze jako własny użytkownik serwera, z jego terminalem, zadaniami i
rozszerzeniami, więc tylko [właściciel serwera](/pl-PL/podrecznik/koncepcje/autoryzacja/#właściciel-serwera)
może go otworzyć. Sesja należy do urządzenia i osoby, która ją otworzyła. Otwiera się z włączonym
zaufaniem obszaru roboczego VS Code, więc VS Code pyta przed zaufaniem folderowi, i z wyłączonymi
automatycznymi zadaniami, więc zadania repozytorium nigdy nie startują przy otwarciu. Pozostali
zachowują wbudowany edytor aplikacji i widoki plików; pełny edytor nie jest im oferowany.

Hostuj klienta webowego przez HTTPS lub bezpieczny origin loopback, aby Service
Workery mogły działać. Standardowa kompilacja webowa i skrypty wydania zawierają
wspólne zasoby. Jeśli budujesz pakiet ręcznie, przygotuj te pliki później z
katalogu głównego repozytorium:

```bash
node tool/stage_resource_assets.mjs build/web
```

W przypadku kompilacji webowej telefonu użyj `apps/cc_remote/build/web`.
Kopiuje ona `cc_resource_bridge.js`, `cc_resource_worker.js` i
`cc_resource_ws_shim.js` do pakietu aplikacji.

Natywny ruch edytora korzysta zamiast tego z fasady loopback o ograniczonym
zakresie uprawnień. Nie wystawiaj prywatnej bramy raportów i poleceń rozszerzenia
edytora uruchamianego przez serwer przez publiczne proxy. Wrażliwe publiczne
żądania HTTP są odrzucane; zasoby wymagają uwierzytelnionej szyfrowanej sesji.

## Krok 6: Wybierz, jak ludzie się logują

Pierwszy klient, który połączy się jako właściciel serwera, zostanie zapytany,
jak ten serwer ma logować ludzi do GitHuba, Kalendarza Google i Linear: **Użyj
aplikacji Control Center**, **Użyj własnych aplikacji** albo **Użyj własnego
serwera Connect**. Z terminala ten sam wybór wygląda tak:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server connect status --data-dir ./data
./build/cli/<os_arch>/bundle/bin/cc_server connect enable --url https://connect.example.com --data-dir ./data
./build/cli/<os_arch>/bundle/bin/cc_server connect disable --data-dir ./data
```

`CC_CONNECT_URL` (`hosted`, `off` lub adres URL) w środowisku serwera albo
w `.env` zamiast tego przypina wybór. Przy **Użyj własnych aplikacji**
zarejestruj każdego dostawcę w **Ustawienia → Serwer → Logowanie jednokrotne →
Aplikacje dostawców**; **Utwórz moją aplikację GitHub** konfiguruje GitHub
w jednym kroku. Sekrety dostawców należą do pliku `.env` serwera, nigdy do
eksportowanego środowiska. Zobacz [Utwórz GitHub App](/pl-PL/podrecznik/poradniki/github-app/)
i [Control Center Connect](/pl-PL/podrecznik/dokumentacja-referencyjna/connect/).

Logowania przez Connect kończą się kodem, który pokazuje przeglądarka, więc
serwer nie potrzebuje dla nich publicznego adresu. Logowania przez własne
aplikacje serwera odsyłają przeglądarkę na publiczny adres URL serwera, więc
ustaw `--public-url` na adres, do którego przeglądarki ludzi mogą dotrzeć.

To jest domyślne ustawienie serwera. Administrator obszaru roboczego może dać jednemu obszarowi roboczemu inny wybór w **Ustawienia → Obszar roboczy → Integracje**. Gdy ustawiono `CC_CONNECT_URL`, obszar roboczy nadal może przełączyć się na własne aplikacje, ale nie na własny serwer Connect; zobacz [Wybór dla każdego obszaru roboczego](/pl-PL/podrecznik/dokumentacja-referencyjna/connect/#wybór-dla-każdego-obszaru-roboczego).

Aby hostować Connect dla innych serwerów z tego serwera, ustaw
`CC_SERVER_CONNECT_HOST=on`; zobacz
[Uruchom serwer Connect](/pl-PL/podrecznik/poradniki/uruchamianie-serwera-connect/#osadź-connect-w-cc_server).

## Konfiguracja

Flagi użyte powyżej to te, których potrzebuje pierwsza konfiguracja. Pełny zakres —
23 pary flag i zmiennych środowiskowych, cztery podkomendy oraz układ katalogu
danych — znajdziesz w [dokumentacji referencyjnej CLI `cc_server`](/pl-PL/podrecznik/dokumentacja-referencyjna/cc-server-cli/).

:::caution[Nieznane flagi są po cichu ignorowane]
Parser argumentów jest napisany ręcznie i pomija wszystko, czego nie rozpoznaje,
więc literówka (`--tls-key-file`, `--bindany`) nie wywołuje błędu — serwer po
prostu startuje z wartością domyślną. Gdy flaga zdaje się nie działać, sprawdź
wiersze dziennika ze startu.
:::

Cztery, które najprawdopodobniej Ci się przydadzą:

| Flaga          | Wartość domyślna                                                | Znaczenie                                                                                                            |
| -------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `--data-dir`   | katalog danych aplikacji dla użytkownika w danym systemie       | Bazy danych, sekrety, modele i pamięć podręczna multimediów                                                          |
| `--port`       | `9030`                                                          | Port TCP (`0` = efemeryczny)                                                                                         |
| `--bind`       | `loopback`                                                      | `loopback` albo `any` dla wszystkich interfejsów (wymaga TLS lub `--insecure`)                                        |
| `--public-url` | wyprowadzany z powiązania                                        | Adres URL RPC ogłaszany sparowanym klientom. **Ustaw go jawnie za proxy, NAT lub tunelem**                            |

Domyślny katalog danych to `~/Library/Application Support/control-center` w
systemie macOS, `%APPDATA%\control-center` w systemie Windows oraz
`$XDG_DATA_HOME/control-center` (a w przeciwnym razie
`~/.local/share/control-center`) w pozostałych systemach. Katalog `.cc_server`
względny wobec bieżącego katalogu roboczego jest używany tylko wtedy, gdy nie da
się ustalić katalogu domowego ani katalogu danych aplikacji.

## Co serwuje serwer

`cc_server` to cała powierzchnia produktu, a nie jej podzbiór: ścieżka danych
repo-RPC i subskrypcje, endpoint narzędzi MCP pod `POST /mcp` i `GET /sse` na tym
samym porcie, przychodzące webhooki, proxy multimediów i fontów, wywołania zwrotne
logowania jednokrotnego, protokół dzierżawy floty, pobieranie RSS po stronie
serwera według 30-minutowego harmonogramu oraz wyszukiwanie wektorowe (rozszerzenie
`sqlite_vector` jest rejestrowane jako auto-rozszerzenie globalne dla procesu,
degradując do wyszukiwania pełnotekstowego tylko tam, gdzie rozszerzenie jest
niedostępne).

Dyspozytor jest **bezstanowy**: nie ma powiązania obszaru roboczego z sesją. Każde
wywołanie w zakresie obszaru roboczego niesie własny `workspace_id`, a o dostępie
decyduje członkostwo i rola wywołującego w obszarze roboczym — nie posiadanie
klucza parowania.

Dwie rzeczy, o których warto wiedzieć, zanim wystawisz port poza loopback:

- **MCP zawsze potrzebuje swojego tokenu.** Serwer tworzy token MCP przy pierwszym uruchomieniu, a każde żądanie, także z loopbacku, musi go wysłać jako `Authorization: Bearer <token>`. Nie da się tego wyłączyć; właściciel serwera odczytuje go i rotuje w **Ustawienia → Serwer → Serwery MCP**. Żądania z przeglądarki, do nieznanego `Host` albo `POST`, który nie jest JSON-em, są odrzucane, zanim sprawdzony zostanie token. Zobacz [Użyj serwera MCP](/pl-PL/podrecznik/poradniki/serwer-mcp/).
- **`GET /healthz` jest celowo nieuwierzytelnione**, ma wieloznaczne CORS i publikuje identyfikator serwera, jego nazwę, odcisk tożsamości i wersję kompilacji. Klienty potrzebują odcisku, aby przypiąć serwer, więc jest to zamierzone — oznacza to jednak, że każdy osiągalny `cc_server` ujawnia tyle każdemu, kto o to zapyta.
