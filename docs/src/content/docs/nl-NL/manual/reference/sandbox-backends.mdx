:::caution[Of een run gesandboxed is, hangt af van de host]
`cc_server` bepaalt één keer bij het opstarten hoe agenten op deze host draaien, en die beslissing blijft gelden tot de server opnieuw start:

- **Gesandboxed** (`native`): de probe heeft een backend gevonden en `--sandbox` is niet `off`. Beide aansluitpunten van het dispatchpad worden omhuld: de Claude Code CLI via de sandboxpoort, en ACP plus de `bash`-tool van de ingebouwde harness via de sandboxmanager.
- **Uit** (`off`): de serverbeheerder heeft hem met `--sandbox off` gestart. De agents van elk lid draaien op deze machine onbeperkt, wie ze ook heeft gestart.
- **Niet beschikbaar** (`unavailable`): de sandbox staat aan, maar de probe vond geen backend (**altijd Windows**, en Linux of WSL2 zonder `bwrap` en `socat`). Een run start alleen wanneer de verantwoordelijke persoon de [serverbeheerder](/nl-NL/handleiding/concepten/autorisatie/#de-serverbeheerder) is: de persoon die erom vroeg, of voor automatisering de persoon waaraan die is gebonden. Andermans run wordt geweigerd voordat een inloggegeven wordt uitgegeven, een lease wordt genomen of een proces start. Zonder vastgelegde eigenaar start niemands run.

Een geweigerde run mislukt met de code `sandbox_unavailable`. De app toont die als **Agents hebben een sandbox nodig op deze server**: "Deze server heeft geen sandbox, dus alleen de serverbeheerder kan hier agents uitvoeren. De beheerder kan de sandbox installeren of sandboxing voor iedereen uitzetten."

Een run die zonder sandbox wel start (onder `off`, of de eigen run van de eigenaar onder `unavailable`), draait rechtstreeks op de host. ACP en de `bash`-tool van de harness starten nog steeds met omgevingssanering; Claude Code gaat via `NoSandboxAdapter` en erft de omgeving van de host. De grenzen die overblijven zijn de eigen worktree van de run (copy-on-write waar `rift` meelevert; `git worktree` op Windows), een forge-token met alleen leesrechten dat per start wordt bemiddeld en bij het afbreken wordt ingetrokken, pushes die bij de agentrun-gateway langs de pushregel moeten, het opdrachtbeleid per modus, de uniforme [actiebeveiligingen](/nl-NL/handleiding/concepten/beveiligingen/) (fail-closed), omgevingssanering op de ACP- en harness-`bash`-paden, en het tooloppervlak dat zijn modus toestaat.

De in-process bestandstools van de harness (read, write, edit, apply patch, search, find, search_files) vallen op elke host buiten de sandbox: ze draaien in het serverproces, dus alleen `bash` wordt omhuld.

De host is nooit een terugval voor een server die agents in een sandbox draait. Als de server agents sandboxt maar geen sandbox kan geven aan een run, worden de toolprocessen en `bash`-opdrachten geweigerd, niet op de host gestart. Dezelfde houding bepaalt de kleine processen rond een run: ACP-eenmalige helpers (gesprekstitels, `/btw`, `/handoff`, `/goal`) en de golden tests van een pull request in Review Studio draaien in de sandbox wanneer de server agents sandboxt, onbeperkt onder `off`, en onder `unavailable` alleen voor een verzoek waarvoor de serverbeheerder verantwoordelijk is; anders worden ze overgeslagen.
:::

## Backendoverzicht

| Backend    | Waarde    | Platform                                      | Beschikbaarheid                                                                                                     |
| ---------- | --------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Omhulde VM | `microvm` | macOS, Linux, Windows (microVM-hypervisor)    | Alleen als de probe op de microVM-runtime slaagt; geldt voor interactieve terminals — de shell draait in een [rig](/nl-NL/handleiding/concepten/rigs/), niet op de host |
| Native     | `native`  | macOS (Seatbelt), Linux en WSL2 (bubblewrap)  | Bij het opstarten geprobeerd; Linux weigert een run die schrijfweigeringen op bestandsnaamglobs vereist, wat bubblewrap niet kan afdwingen |
| Geen       | `none`    | Alle                                          | De standaardwaarde bij het parsen en de standaardwaarde van de terminal; agentdispatch gebruikt hem onder `--sandbox off`, en voor de eigen runs van de eigenaar wanneer er geen backend beschikbaar is |

`SandboxBackend.fromName` geeft `none` terug voor een null-waarde of een niet-herkende opgeslagen waarde.

**`microvm` is de enige backend met een kernelgrens** — de workload
draait echt niet op de host. Hij is nooit een stille terugval, in geen van beide
richtingen: hem expliciet aanvragen op een host die geen VM kan opstarten mislukt
luidruchtig (“ik vroeg om een VM en kreeg mijn laptop” is de ene verslechtering die de
omhulling zich niet kan permitteren), en alleen een *niet-opgegeven standaard* stapt af
naar `native`, met een logregel die dat zegt. De werkelijke backend van de sessie wordt
aan de client teruggerapporteerd en van een badge voorzien, zodat een terminal nooit kan
beweren omhuld te zijn terwijl hij op de host draait. Levenscyclus, images en uitgaand
verkeer van de VM zelf staan in de [rigs-referentie](/nl-NL/handleiding/referentie/rigs/).

**Windows heeft geen native sandbox.** `NativeSandboxAdapter.probe` geeft `available: false` terug op elke host die geen macOS of Linux/WSL2 is, dus een Windows-server is `unavailable`: alleen de agentruns van de serverbeheerder starten, onbeperkt, en die van iedereen anders worden geweigerd. Om elk lid agents daar te laten draaien, start de eigenaar de server met `--sandbox off`, wat ze allemaal onbeperkt uitvoert. De `microvm`-backend staat apart: hij is alleen beschikbaar als de probe op de microVM-runtime slaagt en geldt voor interactieve terminals en rigs, niet voor het omhullen van `bash` op de host.

## Probe-resultaten

De probe bepaalt de afdwinging. Hij draait één keer, bij het opstarten van de server.

| Host                                     | `available` | Opmerking / hint                                                          |
| ---------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS                                    | `true`      | `sandbox-exec` (Seatbelt) — namespace-isolatie, geen kernelgrens          |
| Linux of WSL2 met `bwrap` en `socat`     | `true`      | bubblewrap — namespace-isolatie, geen kernelgrens                         |
| Linux of WSL2 zonder een van beide tools | `false`     | `requiresInstall: true`, met een installatiehint die de ontbrekende pakketten noemt |
| Elk ander platform                       | `false`     | Native sandbox wordt op dit platform niet aangeboden                      |

De server logt de uitkomst op één opstartregel: `agent sandbox ON` plus de opmerking; `no OS-native agent sandbox on this host` plus de hint, die toevoegt dat alleen runs waarvoor de serverbeheerder verantwoordelijk is, starten; of `agent sandbox DISABLED by --sandbox off`. De blootstellingsregel die bij het opstarten wordt afgedrukt, bevat dezelfde beslissing als `sandbox=native`, `sandbox=off` of `sandbox=unavailable`. `GET /healthz` bevat geen sandboxveld.

`--sandbox` / `CC_SERVER_SANDBOX` accepteert `on` (standaard) of `off`. `on` omhult elke run wanneer de host een backend biedt, en laat bij geen backend alleen de runs van de eigenaar toe. `off` voert elke agent van elk lid onbeperkt uit op deze host; het is de keuze van de eigenaar voor iedereen, geen instelling per run.

## Native backend

### macOS: Seatbelt

Gebruikt Apples Seatbelt-sandboxmechanisme (hetzelfde systeem dat macOS App Sandbox gebruikt).

Het gegenereerde profiel is **standaard toestaan** (`(allow default)`) en haalt daar weigeringen uit, omdat een profiel dat standaard alles weigert een interactieve shell onbruikbaar maakt — er zijn te veel dyld-, XPC- en Mach-aanroepen om te enumereren. De praktische consequentie is dat een agent nog steeds het grootste deel van de host kan lezen; je geregistreerde checkouts worden beschermd door expliciete schrijf- en renameweigeringen, niet door onzichtbaarheid.

- **Bestandssysteemlezen**: geweigerd voor de geheime paden (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` en de rest van de set met leesweigeringen)
- **Bestandssysteemschrijven**: teruggezet naar weigeren, daarna expliciete toestemmingen voor subpaden, waarbij de verplicht te weigeren paden (shell-rc-bestanden, `.git/hooks`, Claude-configuratie, beschermde checkouts) ook binnen een beschrijfbare root geblokkeerd blijven. `file-write-unlink` wordt geweigerd op elk geweigerd pad en zijn voorouders, zodat een rename een schrijfweigering niet kan omzeilen
- **Proces**: `process-exec`-weigeringen voor de altijd gevaarlijke binaries, plus een blokkade op het uitvoeren van alles uit een beschrijfbare map. Bekende toolchain-installatiemappen onder je thuismap (corepack, `npx`- en `pnpm dlx`-caches, node-versiebeheerders, Playwright-browsers, rustup en cargo, Go, fvm en de pub-cache, pyenv, uv en pipx, rbenv, sdkman, mise, asdf en `~/.local/bin`) worden onder die blokkade weer opengezet. Gedeelde tijdelijke mappen worden ook geblokkeerd. Elke sessie krijgt in plaats daarvan een privé-`TMPDIR` onder `/private/tmp`, waar programma's die de agent bouwt (een `go test`-binary, een cargo-build) kunnen draaien. De altijd-gevaarlijke weigeringen worden na deze toestemmingen toegepast
- **Netwerk**: beperkt tot de in-process proxypoorten plus DNS — loopback is niet in het algemeen toegestaan en TCP-luisteren is geweigerd. Unix-sockets zijn alleen toegestaan binnen de privé-`TMPDIR` van de sessie, wat tools dekt zoals tsx en Chrome die daar een IPC-socket aanhouden; je SSH-agent en andere sockets blijven onbereikbaar. De proxies dwingen de domein-allowlist per sessie af (zie [Netwerk-egress](#netwerk-egress))
- **Configuratie**: profielen worden per start gegenereerd uit de `SandboxSpec`
- **De eigen commando's van de server**: geen directe kind-map van een map waaruit de server programma's draait (elk `PATH`-item en de gebruikelijke mappen met tools per gebruiker, zoals `~/.local/bin`, met versiebeheerderlinks zoals `~/fvm/default` opgelost) kan worden aangemaakt, vervangen, verwijderd of hernoemd, noch het geïnstalleerde pakket waar een gekoppeld commando naartoe wijst. Zie [De commandomappen van de server](#de-commandomappen-van-de-server)
- **Opstartbestanden**: elk thuispad dat het profiel weigert te lezen, wordt ook geweigerd om te schrijven, en de opstartbestanden van de shells en sessies van de servergebruiker (`.zshenv`, `.zlogin`, `.bash_login`, fish-config, systemd-user-units, autostart-items en dergelijke) zijn in elke modus geweigerd voor schrijven

Vereisten:

- `sandbox-exec` (`/usr/bin/sandbox-exec`), onderdeel van elke macOS-installatie — geen extra tooling nodig

### Linux: bubblewrap

Gebruikt bubblewrap (`bwrap`) om mount- en PID-namespaces te maken.

- **Bestandssysteem**: maakt een mount-namespace waarin alleen de gebonden paden zichtbaar zijn
- **Netwerk**: draait in een niet-gedeelde netwerknamespace; verkeer bereikt de host-proxies via `socat`-Unix-socketbruggen
- **Proces**: PID-namespace-isolatie
- **De eigen commando's van de server en opstartbestanden**: dezelfde beveiligingen als op macOS, uitgedrukt als bubblewrap-binds. Die zijn op Linux nog niet geverifieerd, en een ontbrekende commandomap kan daar nog steeds worden aangemaakt

Vereisten:

- `bubblewrap` en `socat` geïnstalleerd (`sudo apt-get install bubblewrap socat` op Debian/Ubuntu)
- Ondersteuning voor kernel-namespaces (standaard op moderne Linux)

Bubblewrap kan een bestaand pad overschaduwen, maar kan een *nieuw* `.env`,
`*.key`- of `*.pem`-bestand binnen een beschrijfbare bind niet verbieden. Het
standaarddispatchbeleid vereist deze weigeringen op bestandsnaamglobs, dus native
agentdispatch **faalt fail-closed op Linux/WSL2, zelfs wanneer de probe bubblewrap
vindt**. Hij draait niet met een stilzwijgend zwakker beleid. Er is een backend met
regels op bestandsnaam bij aanmaak nodig om native dispatch op Linux te herstellen.
Sandboxing uitschakelen is een expliciete onbeperkte afmelding, geen gelijkwaardige
workaround.

In de praktijk draait een Linux- of WSL2-server agents vandaag op een van twee manieren. Gestart met `--sandbox off` voert hij de agents van elk lid onbeperkt uit. Zonder bubblewrap of `socat` geïnstalleerd is hij `unavailable` en draait hij alleen de agents van de serverbeheerder, onbeperkt. Met beide tools geïnstalleerd en de sandbox aan, faalt elke run gesloten, ook die van de eigenaar.

## De commandomappen van de server

De server vindt bij het opstarten één keer elke map waaruit hij programma's draait: elk item van zijn `PATH`, de mappen met tools per gebruiker die hij controleert (zoals `~/.local/bin`, `~/.bun/bin` en de globale mappen van npm, yarn en pnpm), en de echte map achter elke link onderweg (versiebeheerderlinks zoals `~/fvm/default` of een fnm-standaard). Binnen een sandbox kan een agent geen commando in die mappen toevoegen, vervangen, verwijderen of hernoemen, ook niet de link die ernaar wijst, of het geïnstalleerde pakket waar een gekoppeld commando naartoe wijst, en ook de mappen erboven niet hernoemen. Anders zou een gesandboxde run een programma kunnen plaatsen dat de server, of de persoon, later buiten de sandbox start.

Dit verandert het volgende voor een run:

- Globale installaties vanuit een gesandboxde run mislukken met "Operation not permitted": `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, en `cargo install`, `go install` of `dart pub global activate` wanneer hun bin-map op het `PATH` van de server staat.
- Een standaardversie wisselen mislukt op dezelfde manier (`fnm default`, `nvm alias default`, `fvm global`), net als een tool die zichzelf ter plekke bijwerkt.
- Projectlokale installaties (`node_modules/.bin`), `npx`, `pnpm dlx`, pakketbeheerders die door corepack worden beheerd, SDK-caches en normale builds blijven werken.

Om een globale tool voor agents beschikbaar te maken, installeer je hem op de server zelf, als de gebruiker van de server, en herstart je de server zodat het nieuwe commando ook beschermd is. Of installeer hem in het project. Een commando dat is geïnstalleerd nadat de server is gestart, is pas vanaf de volgende start volledig beschermd.

Afgedwongen en getest op macOS. Op Linux zijn dezelfde regels bubblewrap-binds die nog niet zijn geverifieerd. Windows heeft geen sandbox.

## None-backend

Geen sandboxing. Het proces draait rechtstreeks op de host, met de bestandssysteem-, netwerk- en procestoegang van de host. ACP en de `bash`-tool van de harness krijgen nog steeds omgevingssanering en het opdrachtbeleid; Claude Code via `NoSandboxAdapter` erft de omgeving van de host. Agentdispatch gebruikt hem voor elke run onder `--sandbox off`, en op een host zonder beschikbare backend alleen voor de eigen runs van de serverbeheerder; andermans run wordt daar geweigerd. Voor een terminal is het de hostshell, die alleen de serverbeheerder mag openen.

## Door de server gehoste terminal

De door de server gehoste terminal opent de hostshell alleen voor de [eigenaar](/nl-NL/handleiding/concepten/autorisatie/#de-serverbeheerder) van de server. Iedereen anders krijgt een terminal in een sandbox, met de beperkingen van een agent, in de eigen mappen van de werkruimte.

Zo wordt het backend voor een sessie gekozen:

| Gevraagd | Serverbeheerder | Iedereen anders |
| --- | --- | --- |
| Niets | Het standaardbackend van de server | De standaard, met `none` vervangen door `native` |
| `none` (de hostshell) | Hostshell | Geweigerd: de hostshell draait op de server zonder sandbox |
| `native` | Native sandbox, eigenaarsprofiel | Native sandbox, agentprofiel |
| `microvm` | Ingesloten VM | Ingesloten VM |
| Een onbekende naam | Geweigerd | Geweigerd |

- **Eigenaarsprofiel.** `$HOME` en de werkmap van de sessie zijn beschrijfbaar, het netwerk staat open, en `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` en `~/Library/Keychains` zijn leesgeweigerd.
- **Agentprofiel** (`memberTerminalSandboxConfig`). Hetzelfde beleid waaronder een agent in die werkruimte draait: schrijven blijft in de werkmap, een privé-runmap, `/tmp` en de delen van `$HOME` die een agent mag beschrijven; geheimen zijn leesgeweigerd; het netwerk is de egress-allowlist van agents; programma's draaien alleen vanuit de werkmap en geïnstalleerde toolchains.
- Een terminal opent alleen binnen de eigen mappen van de werkruimte. Een werkmap daarbuiten wordt geweigerd, nooit door een andere vervangen.
- Alleen de persoon die een terminal heeft geopend, kan hem lezen, erin typen, het formaat wijzigen of hem sluiten. Voor iedereen anders lijkt zijn id onbekend.
- `microvm` expliciet vragen op een host zonder rig-service mislukt in plaats van terug te vallen. Een `microvm`-standaard op zo'n host valt terug op `native` en zegt dat in het log.

Het forge-token met alleen leesrechten en de push-gateway zijn niet van toepassing op terminals: dat zijn dispatchzaken. Als het omhullen niet wordt ondersteund, mislukt de sessie in plaats van een sandboxbadge te tonen op een sessie met de hostshell.

## Netwerk-egress

Wanneer een sandbox wordt gestart, wordt uitgaande netwerktoegang afgedwongen door in-process proxies, niet door kernel-firewallregels. Een run die niet gesandboxed is (elke run onder `--sandbox off`, of de run van de eigenaar op een host zonder backend) krijgt hier niets van: een proces dat hij start, bereikt het netwerk precies zoals de servergebruiker dat zou doen.

- De sandboxruntime draait een HTTP/HTTPS-proxy en een SOCKS5-proxy op `127.0.0.1` binnen het `cc_server`-proces, **één paar per beperkte sessie** (`http_proxy.dart`, `socks_proxy.dart`). Gelijktijdige runs delen geen paar.
- Gesandboxte processen krijgen proxy-omgevingsvariabelen (`HTTP_PROXY`/`HTTPS_PROXY` → de HTTP-proxy, `ALL_PROXY` → de SOCKS-proxy; `GIT_SSH_COMMAND` leidt git-over-SSH via de SOCKS-proxy). Op Linux is de netwerknamespace niet gedeeld, dus zijn de proxies de enige uitweg; op macOS deelt de sandbox de loopback van de host en praat hij er rechtstreeks mee.
- De doelhost van elke verbinding wordt gematcht tegen de domein-allowlist van de sessie; al het andere wordt geweigerd. Twee jokervormen, elk met precies één `*`: een vooraanstaande `*.example.com` matcht elk subdomein (inclusief `a.b.example.com`) maar niet het hoofddomein zelf; een middenlabel `bedrock.*.amazonaws.com` matcht precies één label (`bedrock.us-east-1.amazonaws.com`, niet `bedrock.evil.attacker.amazonaws.com`).
- De allowlist wordt per sessie samengesteld uit de samengestelde basis (`kBaselineAllowedDomains`: LLM-providers, githosting, pakketregisters), plus de GitHub-domeinen (`kGithubDomains`), plus `SandboxSpec.egressAllowlist`. Het dispatchpad geeft nooit extra `egressAllowlist`-vermeldingen door, dus in de praktijk krijgt elke run de basis plus GitHub.
- Een vaste weigerlijst (`kBaselineDeniedDomains`: cloudmetadata-eindpunten, telemetrie-sinks) gaat vóór alle toestemmingen.
- `networkEnabled: false` start de proxies per sessie nog steeds, maar de allowlist is leeg, dus elke uitgaande verbinding wordt geweigerd. Dispatch stelt de waarde bij de start van de run in op basis van de regel **Toegang tot het netwerk**: weigeren zet het netwerk uit, toestaan en eerst vragen laten het aan.

## SandboxSpec

De specificatie die aan `SandboxPort.launch` wordt doorgegeven:

| Veld              | Type                                        | Beschrijving                                                                                                                                 |
| ----------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | Stabiele sessie-identificatie (meestal het ruimte-id)                                                                                        |
| `workspaceId`     | `String`                                    | Id van de eigenaarswerkruimte                                                                                                                |
| `agentId`         | `String?`                                   | Agent die momenteel aan de sandbox is gebonden, indien van toepassing                                                                        |
| `bindMounts`      | `List<SandboxBindMount>`                    | Host→guest-mounts; de sandbox ziet alleen de hostpaden die hier worden genoemd                                                               |
| `networkEnabled`  | `bool` (standaard `true`)                   | Door dispatch ingesteld op basis van de regel voor uitgaand netwerkverkeer (alleen uit wanneer die op weigeren uitkomt). Staat het uit, dan starten de proxies per sessie nog steeds, maar is de allowlist leeg, dus wordt elke uitgaande verbinding geweigerd |
| `egressAllowlist` | `List<String>` (standaard `[]`)             | Extra toegestane egress-domeinen; jokers worden ondersteund (`*.example.com`, plus een middenvorm met één label). Dispatch vult dit nooit, dus een omhulde run krijgt de samengestelde basis plus de GitHub-domeinen |
| `guestWorkdir`    | `String?`                                   | Standaardwerkmap binnen de sandbox; afzonderlijke `exec`-aanroepen kunnen die overschrijven                                                         |
| `mode`            | `Mode` (standaard `chat`)                   | Bepaalt de schrijfregels voor het bestandssysteem: `chat` houdt bind-mounts beschrijfbaar; `review`, `plan` en `orchestrate` zijn alleen-lezen   |
| `protectedPaths`  | `List<String>` (standaard `[]`)             | Hostpaden die in geen enkele modus beschrijfbaar mogen zijn binnen de sandbox                                                                |
| `runnerStateDirs` | `List<String>` (standaard `[]`)             | Hostmappen waarin de runner zijn eigen staat bewaart, in elke modus beschrijfbaar (een door Control Center beheerde `CLAUDE_CONFIG_DIR` is de huidige) |
| `execGrantRoots`  | `List<String>` (standaard `[]`)             | Door de operator goedgekeurde mappenbomen die de exec-blokkade op beschrijfbare mappen op macOS weer openen. Linux negeert ze — bwrap heeft geen `$HOME`-execblokkade om te heropenen |

`protectedPaths` bevat de oorspronkelijke geregistreerde repo-checkouts, per dispatch bepaald uit de repo's van de werkruimte. Agenten werken uitsluitend in copy-on-write-worktrees per gesprek, dus de originelen mogen nooit beschrijfbaar zijn van binnenuit de sandbox — op macOS zou de algemene `$HOME`-schrijftoestemming van Seatbelt ze anders via `bash` beschrijfbaar laten. Ze voegen zich in elke modus bij de set met schrijfweigeringen voor geheimen, `chat` inbegrepen.

Elk pad waarvoor lezen of schrijven wordt geweigerd, wordt in zowel zijn letterlijke spelling als zijn symlink-opgeloste spelling uitgevaardigd. De kernel matcht een weigeringsregel tegen het opgeloste pad, dus een regel die tegen een symlinkpad is geschreven, vuurt nooit — en op macOS is dat het gewone geval in plaats van het exotische, aangezien `/tmp` verwijst naar `/private/tmp` en `/var/folders/…` naar `/private/var/folders/…`. Vermeldingen met `*` of `?` worden als globs behandeld en met rust gelaten; een pad dat niet resolveert, blijft staan zoals het is geschreven.

## SandboxHandle

Teruggegeven door `SandboxPort.launch`:

| Veld        | Type                   | Beschrijving                                                             |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | Sessie-identificatie                                                     |
| `backend`   | `SandboxBackend`       | Welke backend draait                                                     |
| `state`     | `SandboxState`         | Levenscyclusstatus                                                       |
| `error`     | `Object?`              | Ingesteld wanneer `state` `error` is                                     |
| `details`   | `Map<String, Object?>` | Adapter-eigen boekhouding (werkmap, PID, profielpad, enz.)               |

### SandboxState

| Status      | Beschrijving                                |
| ----------- | ------------------------------------------- |
| `created`   | Spec aangemaakt, maar de VM is nog niet gestart |
| `warm`      | Draait en klaar om commando's uit te voeren |
| `active`    | Voert momenteel een commando uit            |
| `suspended` | Gepauzeerd / gecheckpoint naar schijf om RAM te sparen |
| `destroyed` | Afgebroken; de handle is niet meer geldig   |
| `error`     | Starten mislukt — zie `SandboxHandle.error` |

## Sandbox-gebeurtenissen

| Gebeurtenistype | Beschrijving                                                |
| --------------- | ----------------------------------------------------------- |
| `stdout`        | Standaarduitvoer van de sandbox                             |
| `stderr`        | Standaardfout van de sandbox                                |
| `exit`          | Sandboxproces beëindigd (draagt `exitCode`)                 |
| `starting`      | Sandbox is aan het opstarten                                |
| `ready`         | Sandbox is klaar om exec-aanroepen te accepteren            |
| `killed`        | Proces gedood door de host (OOM, timeout, handmatige stop)  |
| `violation`     | Een sandboxbeleid is geschonden (draagt een `SandboxViolation`) |

## SandboxViolation

| Veld                  | Type      | Beschrijving                                                                |
| --------------------- | --------- | --------------------------------------------------------------------------- |
| `action`              | `String`  | Het geweigerde werkwoord (bijv. `file-read*`, `network-outbound`)           |
| `target`              | `String`  | Pad of host die het doel was van de geweigerde handeling                     |
| `raw`                 | `String?` | Ruwe logregel, nuttig voor het debuggen                                     |
