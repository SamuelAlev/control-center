Elke procesflag heeft een CLI-flag of een omgevingsvariabele; de flag wint, dan
de omgeving, dan de standaardwaarde. Inloggegevens van providers zijn de
uitzondering — zie [Provider-apps en Connect](#provider-apps-en-connect).

:::caution[Onbekende flags worden stil genegeerd]
De argumentparser is handmatig geschreven en slaat alles over wat hij niet herkent, dus een typefout (`--tls-key-file`, `--bindany`) geeft geen fout — de server start gewoon met de standaardwaarde. Controleer de logregels bij het opstarten wanneer een flag geen effect lijkt te hebben. Een [codemodus-vlag](#codemodus) met een waarde die hij niet accepteert, is anders: de server weigert te starten.
:::

## Provider-apps en Connect

Geen enkele build bevat inloggegevens van providers. Met Control Center Connect aan voert Connect elke provider uit, en eigen apps blijven opgeslagen maar ongebruikt.
Onder **Mijn eigen apps gebruiken** draait elke provider op de eigen app van de server als die volledig is
geconfigureerd, en anders is hij niet beschikbaar. De app van de werkruimte geldt in beide gevallen. Eigen apps
stel je in via **Instellingen → Server → Single sign-on → Provider-apps**, of ze
worden eenmalig gevuld vanuit het `.env`-bestand van de server. Er zijn geen
flags voor: een secret op een commandoregel is leesbaar via `ps`.

| Variabele                      | Betekenis                                                                                     |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| `GITHUB_APP_ID`                | Het id van de GitHub App van de server                                                        |
| `GITHUB_APP_PRIVATE_KEY`       | De privésleutel ervan, op één regel met `\n`-escapes. **Alleen `.env`**                       |
| `GITHUB_CLIENT_ID`             | De client-id ervan, om mensen aan te melden                                                   |
| `GITHUB_CLIENT_SECRET`         | Het client-secret ervan. **Alleen `.env`**                                                    |
| `GOOGLE_OAUTH_CLIENT_ID`       | De Google-client van de server van het type Webapplicatie                                     |
| `GOOGLE_OAUTH_CLIENT_SECRET`   | Het secret ervan. **Alleen `.env`**                                                           |
| `LINEAR_CLIENT_ID`             | De Linear-applicatie van de server (PKCE, zonder secret)                                      |
| `LINEAR_API_KEY`               | Een Linear-servicesleutel voor automatisering. **Alleen `.env`**                              |
| `KLIPY_APP_KEY`                | De eigen Klipy-sleutel van de server voor GIF-zoeken. Alleen gebruikt onder **Mijn eigen apps gebruiken**     |
| `CC_CONNECT_URL`               | `hosted`, `off` of een Connect-URL. Legt de Connect-keuze vast; Instellingen kan die dan niet wijzigen |
| `CC_SERVER_CONNECT_HOST`       | `on` bouwt Control Center Connect in op `<server>/connect`, geconfigureerd met `CONNECT_*`-variabelen. Zie [Een Connect-server draaien](/nl-NL/handleiding/gidsen/connect-server-draaien/#connect-in-cc_server-inbouwen) |

Het `.env`-bestand wordt gelezen uit de werkmap van de server, naast het
uitvoerbare bestand, of uit een source-checkout erboven; koppel het in Docker aan
`/app/bin/.env`. De server **weigert te starten** (exitcode `78`) wanneer
`GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_SECRET`,
`LINEAR_API_KEY` of een `SLACK_*SECRET*` in zijn procesomgeving is geëxporteerd,
waar elk kindproces het kan lezen. Vullen vanuit `.env` gebeurt één keer per
veld, dus een latere bewerking in Instellingen wordt niet ongedaan gemaakt door
een herstart. Een lege waarde geldt als niet ingesteld.

Geen enkel forge-inloggegeven komt uit de omgeving: GitHub, GitLab en Bitbucket
handelen allemaal op de eigen aanmelding of het token van een lid, of op
GitHub-app-tokens voor één repository die daarbij zijn begrensd.

### `--sandbox`

De server peilt de host één keer bij het opstarten en verpakt de uitvoering van
agentcommando's in de OS-native sandbox wanneer er een backend beschikbaar is:
`sandbox-exec` (Seatbelt) op macOS, `bwrap` plus `socat` op Linux en WSL2. De beslissing wordt één keer genomen en blijft geldig tot de server herstart. Er zijn drie uitkomsten, elk getoond op de blootstellingsregel bij het opstarten:

| `sandbox=`    | Wanneer                                 | Wiens agent-runs starten                                                         |
| ------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| `native`      | Een backend is beschikbaar en `--sandbox` staat op `on` | Die van iedereen, omhuld                                               |
| `off`         | `--sandbox off`                         | Die van iedereen, zonder inperking op deze host                                  |
| `unavailable` | `--sandbox on` en geen backend (Windows, of Linux zonder `bwrap` en `socat`) | Alleen runs waarvoor de servereigenaar verantwoordelijk is, zonder inperking. Bij anderen wordt geweigerd met "Deze server heeft geen sandbox, dus alleen de serverbeheerder kan hier agents uitvoeren." |

Voor automatisering is de verantwoordelijke persoon degene aan wie de automatisering is gebonden. Zonder vastgelegde servereigenaar start op een `unavailable`-host geen enkele run. Op Linux en WSL2 met bubblewrap geïnstalleerd faalt de native dispatch momenteel voor elke run; zie [Sandbackends](/nl-NL/handleiding/referentie/sandboxbackends/#linux-bubblewrap).

`--sandbox off` is de keuze van de servereigenaar voor iedereen die de server gebruikt: die laat de agents van elk lid op deze machine zonder inperking draaien. Gebruik het op een host waar het sandboxprofiel zelf zich misdraagt, of om leden agents te laten draaien op een host zonder backend. Het vraagt geen herbouw, en de server logt een waarschuwing zolang het proces leeft, zodat de toestand nooit stil blijft.

### `--tool-deferral`

Runs van de ingebouwde harness sturen een kleine directe set tooldefinities plus een naamindex van de rest mee, die schema's laden bij het eerste gebruik of worden aangeroepen vanuit een `repl`-script. Dat houdt de altijd zichtbare set binnen het bereik waarin modellen tools betrouwbaar kiezen. Gemeten op het register dat de tests opbouwen, komen de standaard chattools van de ingebouwde agent op 14 definities: ongeveer 16,5 KB met `repl` (ongeveer 4 KB daarvan is van `repl`, en de definitie daarvan mag niet groter zijn dan 4.096 bytes), en ongeveer 13 KB op een server die geen scripts kan draaien. Uitgestelde tools blijven de hele tijd op naam aanroepbaar, en `search_tools` vindt ze op intentie. Zie [Toolcontext en promptcaching](/nl-NL/handleiding/concepten/toolcontext/).

`--tool-deferral off` stuurt de definitie van elke toegelaten tool vooraf mee, behalve dat een run met `repl` de tools die een script mag aanroepen nog steeds vanuit scripts aanroept. Het is de noodschakelaar voor een model dat slecht overweg kan met het oppervlak met twee niveaus — een flag in plaats van een herbouw. Het beïnvloedt alleen de ingebouwde harness; de MCP-`tools/list` die externe clients zien, is de volledige catalogus, behalve voor een agentrun op een server die [codemodus](/nl-NL/handleiding/concepten/codemodus/)-scripts kan draaien.

### `--credential-gate`

Een run waarvan het provider-inloggegeven ontbreekt of op is, wordt
**geparkeerd** in plaats van mislukt: de beheerder krijgt een prompt om het te
herstellen, en de run gaat verder als dat gebeurt. De standaarddeadline is 900
seconden (15 minuten), begrensd op 0–3600.

De deadline is bewust veel ruimer dan die van de goedkeuringsprompt: een
goedkeuring is een beslissing die iemand in seconden neemt, terwijl het herstellen
van een inloggegeven betekent dat je een terminal opent, inlogt en terugkomt. Dat
plafond weerhoudt een onbeheerde run — een pipelinestap, een cron-trigger, een
webhook — ervan te wachten op iemand die ligt te slapen. Wanneer hij verstrijkt,
mislukt de run met de melding waarmee hij toch al zou zijn mislukt.

`--credential-gate=0` is de noodschakelaar: er wordt nooit iets geparkeerd en een
slecht inloggegeven beëindigt de beurt precies zoals voordat de gate bestond.

### Codemodus

[Codemodus](/nl-NL/handleiding/concepten/codemodus/) laat een agent een JavaScript-script draaien dat zijn tools aanroept. Er is geen vlag die het aan of uit zet: elke run krijgt de `repl`-tool wanneer de server scripts kan draaien, en een publieke demoserver draait er geen.

Scripts draaien in `cc_codemode`, een programma dat bij de server wordt meegeleverd in `bin/codemode/`. De server start niet zonder dat: hij drukt één regel af met wat ontbreekt en stopt met exitcode `78`. Bij het starten draait hij de zelftest van de afsluiting van het programma en drukt één regel af (alleen onderdrukt met `--log-level error`):

```text
cc_server: code_mode=available (cc_codemode 0.1.0 quickjs-ng 0.16.2 protocol 2; 16 scripts at once, at most 12 per workspace; up to 64 more runners kept for scripts waiting on a person; heap at most 1024 MiB per script)
cc_server: code_mode=unavailable (<reason>) — runs on this host get no repl tool; scripts never run without full lockdown
```

`unavailable` betekent dat het programma zichzelf op deze host niet kan afsluiten, bijvoorbeeld in een container waarvan het beveiligingsprofiel een van de stappen weigert, of dat het programma geen releasebuild is. De server draait gewoon door, geen enkele run krijgt `repl`, en de instellingen van codemodus in de werkruimte tonen de reden.

De server blijft controleren terwijl hij draait. Wanneer het programma niet start om een reden die niet bij het script ligt, draait de server de zelftest opnieuw, hooguit één keer per minuut. Mislukt die, dan drukt de server de regel `unavailable` af met de reden en draait hij geen scripts: runs die intussen starten krijgen geen `repl`, en een run die hem al heeft, roept zijn tools direct aan ([Wanneer scripts niet kunnen draaien](/nl-NL/handleiding/concepten/codemodus/#wanneer-scripts-niet-kunnen-draaien)). Hij blijft controleren, hooguit één keer per minuut, en wanneer de zelftest weer slaagt, drukt hij de regel `available` af en draait hij weer scripts. Alleen een zelftest die bij het starten mislukte, vereist een herstart. De reden die de instellingen van de werkruimte tonen, heeft paden van de host weggelaten; de logregel bevat ze volledig.

De twee vlaggen van codemodus begrenzen wat scripts mogen gebruiken. `--code-mode-max-processes` begrenst de scripts die tegelijk draaien over alle werkruimten (standaard twee keer het aantal processorkernen, hooguit 16; geaccepteerd 1–64). Bij een limiet van 2 of meer gebruikt één werkruimte hooguit de limiet min een kwart van de limiet, zodat geen enkele werkruimte alle plaatsen kan innemen, en wachtende scripts worden om de beurt toegelaten over werkruimten heen. Een script dat wacht op de goedkeuring of het antwoord van een persoon, maakt zijn plaats vrij voor een ander script en start geen toolaanroep tot er is geantwoord; tot vier keer de limiet aan zulke wachtende scripts wordt bewaard, waarvan hooguit driekwart van één werkruimte komt, en elk kan binnen zijn eigen limiet op processortijd nog blijven rekenen. `--code-mode-max-heap-mb` is het meeste geheugen dat één script mag gebruiken.

Een waarde die deze vlaggen niet accepteren (een getal buiten het bereik, of geen getal), stopt de server bij het starten (exitcode `78`) met een melding die de geaccepteerde waarden noemt. Ze wordt nooit als standaard gelezen.

## Subcommando's

| Commando                                      | Wat het doet                                                                                        |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `cc_server`                                   | Draait de server tot `SIGINT`/`SIGTERM`                                                             |
| `cc_server pair`                              | Provisioneert een apparaat en drukt het id en de koppelingssleutel af. Veilig tegen een datadirectory die een server al bedient — de draaiende server neemt het apparaat over zonder herstart |
| `cc_server connect <command>`                 | Toont of wijzigt welke Control Center Connect deze server gebruikt, zonder hem te starten          |
| `cc_server update`                            | Controleert op, downloadt en verifieert een nieuwere standalone release                             |
| `cc_server --version`                         | Drukt de buildversie en git-SHA af — dezelfde identiteit die `/healthz` en de RPC-handshake adverteren |

### `pair`

| Flag           | Standaard                                                 | Betekenis                                                                                                                                                            |
| -------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device`     | `web-client`                                              | Het apparaat-id. Het platform wordt eruit afgeleid, dus `--device desktop` maakt een desktoprij aan en `--device ios`/`android` een telefoonrij; al het andere wordt als web behandeld |
| `--label`      | platformnaam plus de hostnaam van deze machine            | Weergavenaam in de apparatenlijst                                                                                                                                     |
| `--host`       | `localhost`, of `<this-host>` bij een bind op elke interface | Host om in de afgedrukte URL op te nemen. Stel hem in op het LAN-IP of tunnelhost dat een client daadwerkelijk aanspreekt                                            |
| `--client-url` | niet ingesteld                                            | Origin van de gehoste **web**client. Voegt een scanbare deeplink en terminal-QR toe                                                                                  |

`pair` accepteert ook de kern-flags `--data-dir`, `--port` en `--bind`: die
kiezen de datadirectory waarin wordt geschreven en bepalen de afgedrukte
server-URL (`ws` op loopback, `wss` bij `--bind any`). Als je `pair` opnieuw
uitvoert voor hetzelfde `--device`, roteert de sleutel en vervallen de
live-sessies van dat apparaat. Een referentie die je hier aanmaakt, heeft
**geen vervaldatum**, anders dan de 30 dagen die een koppeling in de app instelt.

:::caution[De QR van `--client-url` is niet de telefoon-QR]
`pair --client-url` vult het verbindingsformulier van de **web**client in
(server-URL, apparaat-id en sleutel in het URL-fragment). De telefoon koppelt met
een andere payload, aangemaakt vanuit het koppelingspaneel in de app — de volledige
verbindingsdescriptor van de server plus een vervaldatum. De twee zijn niet
uitwisselbaar — zie [Een apparaat koppelen](/nl-NL/handleiding/gidsen/apparaat-koppelen/).
:::

### `connect`

Leest en schrijft dezelfde instellingen als de kaart **Control Center Connect** in
**Instellingen → Server → Single sign-on**, vanuit de datadirectory. Een draaiende
server pikt een wijziging binnen 10 minuten of bij een herstart op.

| Commando                        | Wat het doet                                                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `cc_server connect status`      | Drukt de modus af, de URL, of `CC_CONNECT_URL` hem vastlegt, het installatie-ID, de status en de bron van elke route (`own`, `connect` of `off`) |
| `cc_server connect enable`      | Gebruikt de gehoste Connect van Control Center                                                                   |
| `cc_server connect enable --url <url>` | Gebruikt een eigen Connect op die URL (HTTPS, of `http` op loopback)                                      |
| `cc_server connect disable`     | Stopt met Connect. Alleen de eigen apps van de server melden mensen aan                                          |

`status` zonder commando is de standaard. Elk commando accepteert `--data-dir`.
`CC_CONNECT_URL` gaat voor wat deze commando's opslaan. Een onbekend commando
sluit af met `64`. Zie [Control Center Connect](/nl-NL/handleiding/referentie/connect/)
voor de modi, installatie-identiteit en statuscodes.

### `update`

`--apply` vervangt de installatie; het wordt geweigerd zolang er nog een server
antwoordt op de geconfigureerde poort, tenzij je `--force` meegeeft. Met
`--allow-downgrade` mag je terug naar een oudere release.

Het commando weigert botweg, met een uitleg in plaats van een fout, voor
installaties die het niet bezit:

| Omgeving                          | Herkend aan                                 | Wat er staat                                                |
| --------------------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| De ingebouwde server van de desktop | `CC_EMBEDDED=1` of `CC_BOOTSTRAP_DEVICE_ID` | Werk in plaats daarvan de app bij — de installer vervangt de hele boom |
| Een source-checkout met `dart run` | het scriptpad eindigt op `.dart`            | Werk hem bij met git                                        |
| Docker                            | containermarkers                            | Haal een nieuwere image op                                  |

## Proceslevenscyclus

`cc_server` draait tot `SIGINT` / `SIGTERM`. Eén extra omgevingsvariabele bepaalt
dat, en die wordt door de desktop ingesteld, niet door jou:

| Variabele                | Effect                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `CC_EXIT_WITH_PARENT=1`  | De server stopt wanneer zijn bovenliggende proces stopt, gedetecteerd doordat het bovenliggende proces het schrijfuiteinde van zijn stdin-pipe sluit. De desktop stelt dit in zodat een gecrashte app nooit een verweesde server achterlaat die de datadirectory vasthoudt |

Stel hem alleen zelf in als je `cc_server` als kindproces aanstuurt en dezelfde
garantie wilt.

`DO_NOT_TRACK=1` (elke waarde behalve leeg, `0` of `false`) stopt de eigen
[gebruiksstatistieken](/nl-NL/handleiding/referentie/gebruiksstatistieken/) van de server, ook als de serverbrede schakelaar
aan staat. Clients volgen de schakelaar nog steeds.

## Indeling van de datadirectory

De standaard datadirectory is `~/Library/Application Support/control-center` op
macOS, `%APPDATA%\control-center` op Windows en `$XDG_DATA_HOME/control-center`
(anders `~/.local/share/control-center`) elders. Een `.cc_server` relatief aan de
cwd wordt alleen gebruikt als er geen home- of app-gegevensmap kan worden bepaald.

De server houdt de datadirectory alleen toegankelijk voor zijn eigen account (`0700`). Hij start niet (exitcode `78`) wanneer hij dat niet kan, wanneer `global.db` beschadigd is of door een nieuwere versie is geschreven, of wanneer het identiteitsbestand niet gelezen kan worden.

| Pad                               | Inhoud                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------- |
| `global.db`                       | Het werkruimteregister, gebruikers, gekoppelde apparaten, de nieuwsfeed en de fleetwachtrij |
| `<workspaceId>/workspace.db`      | Eén database per werkruimte — agenten, ruimtes, tickets, geheugen  |
| `<workspaceId>/code_index.db`     | De codegraph van die werkruimte. Wordt opnieuw opgebouwd wanneer hij ontbreekt, en nooit geback-upt        |
| `pre_upgrade/`, `<workspaceId>/pre_upgrade/` | De nieuwste twee kopieën van een database van vóór een update die het formaat ervan wijzigde |
| `<workspaceId>/chat_credentials/` | Tokens van de chatbot, als platte JSON, zodat ze met de werkruimte meegaan       |
| `secrets.json`                    | Koppelingssleutels, de installatiesleutel voor Connect, provider-apps, de aanmeldingen van mensen (verzegeld wanneer gemaakt via Connect), webhookgeheimen, SSO (`0600`) |
| `backups/<timestamp>/`            | Eén momentopname van de installatie — `manifest.json`, `global.db` en een kopie van elke werkruimte |
| `backups/exports/`                | Exportbestanden van één werkruimte, `<workspaceId>-<timestamp>.db`               |
| `backups/transfer/`               | Staging voor het downloaden en uploaden van back-ups; opgeruimd door de route die erin schrijft |
| `models/`                         | Embedding-, diarisatie- en spraakmodellen op het apparaat                        |
| `codemode/` | Een ontwikkelkopie van de codemodus-runner, geïnstalleerd door `scripts/natives/build_codemode.sh`; releasebundels bevatten hem in `bin/codemode/` |
| `meetings/<meetingId>/`           | Bewaarde vergaderaudio                                                          |
| `rigs/images/`                    | Geïmporteerde rig-schijfimages (het QEMU-desktopoppervlak)                       |
| `rigs/smolvm/<rigId>/`            | Runtime-status per rig-microVM (het brokersecret, `0600`)                        |
| `rigs/smolvm-packs/`              | Vooraf uitgepakte machinepakketten — de cache die herhaalde rig-boots snel maakt |
| `rigs/tls/`                       | De certificaatautoriteit van het dev-domein voor HTTPS van rigs (sleutels `0600`) |
| `rigs/run/<rigId>/`               | QEMU-overlays, seed-images en sleutels per VM (`0600`)                           |
