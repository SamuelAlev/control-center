Alles wat Control Center kan kopiëren, overdragen of overnemen, en de exacte vorm van elk
artefact. Hoe je daadwerkelijk een back-up maakt, staat in
[Back-uppen en herstellen](/nl-NL/handleiding/gidsen/back-uppen-en-herstellen/); waarom persistentie
zo is opgesplitst, staat in [Werkruimtes en isolatie](/nl-NL/handleiding/concepten/werkruimtes/).

## Artefacten

Er zijn drie artefacten die een database kopiëren, met verschillende bereiken en verwijderbeleid.

| Artefact                             | Geschreven door              | Vorm                                          | Dekt                          |
| ------------------------------------ | ---------------------------- | --------------------------------------------- | ----------------------------- |
| **Installatiemomentopname**          | `server.backupNow`           | Een **map** met tijdstempel                   | Elke database van de installatie |
| **Werkruimteback-up**                | Pipeline `Workspace backup`  | Map met tijdstempel met één `.db`             | De database van één werkruimte   |
| **Werkruimte-export**                | `workspace.export`           | Eén `.db`-**bestand**                         | De database van één werkruimte   |

Alle drie worden geschreven met SQLite `VACUUM INTO`, wat veilig is tegen een actieve
WAL-database: het neemt een leestransactie, produceert een gedefragmenteerde en transactioneel
consistente kopie en vraagt er nooit om de server te stoppen.

Deze bestanden en gedownloade kopieën worden door Control Center **niet in rust
versleuteld**. De end-to-end-versleutelde overdracht beschermt bytes tijdens het
transport tussen een gekoppelde client en zijn `cc_server`, op rechtstreekse of
via een relay bemiddelde verbindingen. Bescherm lokale opslag en kopieën buiten
de machine apart; de server en elke gemachtigde ontvanger kunnen de
databasebestanden lezen.

## Indeling van de momentopname

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

De indeling spiegelt de live datadir exact, en dat is wat het herstellen van een installatie een
terugkopie maakt in plaats van een vertaling. De mapnaam is de UTC-tijdstempel waarin `:` en `.`
zijn vervangen door `-`, dus hij is veilig voor het bestandssysteem op Windows en sorteert
chronologisch als een gewone tekenreeks.

Geplande werkruimteback-ups staan apart in `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`. Elke heeft een `manifest.json` voor dat ene bestand en geen `global.db`; het zijn geen installatiemomentopnamen. Een herstel bewaart de database die het vervangt op dezelfde plek, als `<timestamp>-pre-restore`. De bewaarstap van de wekelijkse pipeline verwijdert alleen back-ups van zijn eigen werkruimte die ouder zijn dan de ingestelde leeftijd (standaard 30 dagen); handmatig gemaakte installatiemomentopnamen worden door die stap nooit verwijderd. `server.listBackups` vermeldt alleen installatiemomentopnamen, ook de niet te verifiëren; `workspace.listBackups` vermeldt de geplande back-ups van één werkruimte.

Een werkruimte verwijderen laat deze map staan. Het schema van de werkruimte stopt samen
met de werkruimte, dus niets roteert die back-ups meer, en ze blijven staan tot de
eigenaar van de installatie ze verwijdert. `server.listOrphanedBackups` meldt ze.


### `manifest.json`

| Veld                       | Type                     | Betekenis                                                             |
| -------------------------- | ------------------------ | ------------------------------------------------------------------- |
| `format`                  | geheel getal             | Manifestformaat. Momenteel `2`                       |
| `created_at`               | ISO-8601 UTC             | Wanneer de momentopname is gemaakt                                  |
| `global`                   | object          | De vermelding van `global.db`. Ontbreekt in een geplande werkruimteback-up |
| `workspaces[]`             | array                    | Eén record per vastgelegde werkruimte                           |
| `workspaces[].workspace_id`| tekenreeks               | De werkruimte die dit bestand bevat                                 |
| `skipped_workspaces[]`     | array           | Werkruimtes die de back-up **niet** kon vastleggen                         |
| `skipped_workspaces[].workspace_id` | tekenreeks | De werkruimte die is overgeslagen                                     |
| `skipped_workspaces[].reason` | tekenreeks       | `no_file`, `damaged` of `failed`                                    |

`global` en elke vermelding van `workspaces[]` beschrijven elk één gekopieerd bestand, gemeten aan de kopie nadat die is geschreven:

| Veld | Type | Betekenis |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | tekenreeks               | Pad ten opzichte van de hoofdmap van de momentopname: `global.db` of `<workspaceId>/workspace.db` |
| `bytes`       | geheel getal             | Grootte van de kopie                                             |
| `sha256`         | tekenreeks   | SHA-256 van de kopie, in hexadecimaal met kleine letters                          |
| `quick_check`    | tekenreeks   | Wat SQLite's `quick_check` over de kopie zei: `ok`, of de bevinding                 |
| `user_version`   | geheel getal | Schemaversie van de kopie                                                     |
| `application_id` | geheel getal | SQLite-`application_id` van de kopie                                            |

Een werkruimte wordt overgeslagen wanneer hij is geregistreerd maar er nooit naar is geschreven (`no_file`), wanneer zijn database de integriteitscontrole niet doorstaat (`damaged`; een beschadigde kopie wordt nooit gemaakt), of wanneer zijn kopie of de controle van die kopie is mislukt (`failed`). Hoe dan ook wordt de momentopname alsnog voltooid en noemt het manifest wat er ontbreekt. Het manifest wordt als laatste geschreven.

### Volledigheid

`server.listBackups` rapporteert per momentopname een `complete`-markering. Die is onwaar wanneer het manifest ontbreekt, niet te parsen is of een ander formaat heeft, wanneer een bestand dat het noemt ontbreekt of een andere grootte heeft, of wanneer een kopie haar controle niet heeft doorstaan. De app toont zo'n momentopname als **Niet te verifiëren**. Momentopnamen die vóór formaat `2` zijn gemaakt, zitten in die toestand.

Een niet te verifiëren momentopname wordt toch vermeld, want een momentopname die een operator niet
ziet, is er een waarvan hij gelooft dat hij hem heeft. Wanneer het manifest onleesbaar is, valt
de lijst terug op de indeling zelf en rapporteert hij de `<workspaceId>/workspace.db`-bestanden
die hij vindt — die blijven afzonderlijk over te nemen via `workspace.import`, ook al kan de
momentopname als geheel geen installatie herstellen.

Een vermelde momentopname of geplande back-up draagt `pinned_reason: "last_good_copy"` zolang ze de nieuwste geverifieerde kopie bevat van een werkruimte waarvan de actieve database beschadigd is. De bewaarstap slaat haar over totdat die werkruimte is hersteld.

## Wat een back-up niet bevat

Beide artefacten zijn **alleen databases**. Een werkruimtemap bevat meer dan zijn
database, en niets daarvan reist mee:

| Pad                                 | In een momentopname? | In een werkruimte-export? |
| ----------------------------------- | -------------------- | ------------------------- |
| `global.db`                         | Ja                   | Nee                       |
| `<workspaceId>/workspace.db`        | Ja                   | Ja (het *is* het bestand) |
| `<workspaceId>/code_index.db`        | Nee                      | Nee                    |
| `<workspaceId>/blobs/`              | Nee                  | Nee                       |
| `<workspaceId>/skills/`             | Nee                  | Nee                       |
| `<workspaceId>/agents/`             | Nee                  | Nee                       |
| `<workspaceId>/chat_credentials/`   | Nee                  | Nee                       |
| `<workspaceId>/spaces/<spaceId>/`   | Nee                  | Nee                       |
| `<workspaceId>/pr_clones/`          | Nee                  | Nee                       |
| `secrets.json`                      | Nee                  | Nee                       |
| `models/`                           | Nee                  | Nee                       |
| `meetings/<meetingId>/`             | Nee                  | Nee                       |
| `rigs/`                             | Nee                  | Nee                       |
| `_agent_hooks/`                     | Nee                  | Nee                       |

Sommige daarvan is wegwerpbaar — `spaces/` bevat copy-on-write-worktrees die opnieuw worden geprovisioneerd vanuit de repo's, `pr_clones/` is een cache, `code_index.db` wordt opnieuw opgebouwd, `models/` wordt opnieuw gedownload, `rigs/` is machinestatus. Sommige niet: `blobs/` bevat geplakte afbeeldingen waar rijen in de database naar verwijzen, `skills/` en `agents/` bevatten de bestanden waarmee een agent draait, en `secrets.json` bevat elke koppelingssleutel, providerreferentie en SSO-instelling van de installatie. Zie [Back-uppen en herstellen](/nl-NL/handleiding/gidsen/back-uppen-en-herstellen/#back-ups-buiten-de-machine-kopiëren) voor het dekken van de rest.
:::note[Geheimen blijven uit de databases]
`workspace.db` is de hele werkruimte: gesprekken, runlogs, repokoppelingen, omgevingsdefinities en leden. Webhooktokens van de pipeline en webhookgeheimen van de ticketsynchronisatie staan in `secrets.json`: de database bevat een verwijzing naar elk ervan, en de routeringsindex bevat een met een sleutel gemaakte hash van elk token. Een werkruimte die op een andere installatie is hersteld, ontvangt daarom geen webhooks totdat de triggers daar opnieuw zijn opgeslagen. Aanmeldingen bij aanbieders, apparaatsleutels en gebruikersgeheimen staan in `global.db` en `secrets.json`.
:::

:::note[Chattokens blijven bewust achter]
Dat `chat_credentials/` naast de database staat in plaats van erin, is de reden dat een werkruimte
die aan iemand anders wordt gegeven geen live bottokens meedraagt. Zie de
[chatbrugreferentie](/nl-NL/handleiding/referentie/chatbrug/).
:::

## Bewerkingen

Back-up-RPC's voor de installatie en export/import van werkruimtes zijn alleen voor
`fullClient`: een gekoppelde telefoon kan ze niet starten. Ze zijn allemaal volledig afwezig
— niet geweigerd, maar structureel ontbrekend — op een server waar geen back-uppoort is
aangesloten, zoals de demoserver.

| Op                   | Soort  | Bereik    | Minimale rol | Argumenten    | Retourneert                   |
| -------------------- | ------ | --------- | ------------ | ------------- | ----------------------------- |
| `server.backupNow`   | mutate | Installatie | **eigenaar** van de installatie | geen    | `{ok, path}`                  |
| `server.listBackups` | read   | Installatie | **eigenaar** van de installatie | geen    | `{backups: [...]}`            |
| `server.deleteBackup` | mutate | Installatie | **eigenaar** van de installatie | `name` | `{ok}` |
| `server.listOrphanedBackups` | read | Installatie | **eigenaar** van de installatie | geen | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutate | Installatie | **eigenaar** van de installatie | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | read | Werkruimte | `admin` | geen | `{backups: [...]}` |
| `workspace.deleteBackup` | mutate | Werkruimte | `owner` | `name` | `{ok}` |
| `workspace.export`   | read   | Werkruimte | `admin`      | geen          | `{ok, path}`                  |
| `workspace.import`   | mutate | Werkruimte | `owner`, en de serverbeheerder | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | read | Werkruimte | `owner`, en de serverbeheerder | geen | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutate | Werkruimte | `owner`, en de serverbeheerder | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | mutate | Installatie* | `owner`    | `id`          | registerrij gemarkeerd als verwijderd |

* `workspace.delete` heeft geen bereik omdat de rij die hij markeert in het globale
register staat; zijn handler controleert het lidmaatschap van de aanroeper van de genoemde
werkruimte en vereist `owner`.

`path` in elk antwoord is een pad op de **serverhost**.

`server.listOrphanedBackups` retourneert één item per werkruimte die niet meer actief is:
`workspace_id`, `workspace_name` als het register die nog kent, en `backups`. Een
verwijderde werkruimte kan geen rolcontrole van de werkruimte meer doorstaan, dus de
back-ups ervan behoren toe aan de eigenaar van de installatie.
`server.deleteOrphanedBackup` weigert een actieve werkruimte, waarvan de back-ups achter
`workspace.deleteBackup` en de eigen rollen van die werkruimte blijven. Beide
verwijderoperaties accepteren alleen een vermelde mapnaam met tijdstempel, geen pad.

`workspace.importHolds.list` geeft terug wat een import heeft tegengehouden. Elk tegengehouden recht heeft een `id`, een `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` of `invite`), de `payload` die het zou terugzetten, `imported_at` en `source_install_id`. `workspace.importHolds.resolve` met `accept: true` verleent het opnieuw en met `false` wijst het af. `applied` is false wanneer de persoon of het ding waarvoor het recht gold niet meer in de werkruimte zit.

:::note[Een momentopname van de hele installatie is op beide banen alleen voor de eigenaar]
`server.backupNow`, `server.listBackups` en `server.deleteBackup` vereisen de
**eigenaar** van de installatie (`ServerAuthority.serverOwner`), dezelfde controle als
`GET /backup/snapshot`. Een momentopname legt de database van elke werkruimte vast, dus
beheerder zijn van één werkruimte is niet genoeg om de andere te beheren. Bij het verwijderen
wordt alleen de naam van de getoonde tijdstempelmap geaccepteerd, geen willekeurig
serverpad, en wordt de hele momentopname verwijderd (ook niet te verifiëren momentopnamen).
Export per werkruimte en downloads van geplande back-ups blijven bij de werkruimtebeheerder.
:::

:::note[Herstellen is alleen voor de serverbeheerder]
`workspace.import` en `POST /backup/restore` laten de server een databasebestand
overnemen waarvan de rijen hij daarna als eigen behandelt: repokoppelingen en wie
die heeft gemaakt, omgevingsdefinities die op de host draaien, en worktree- en
logpaden. Daarom zijn beide de serverbeheerder voorbehouden
(`ServerAuthority.serverOwner`), die ook de eigenaar van de werkruimte moet zijn.
Iedereen anders, en elke aanroeper op een host zonder vastgelegde eigenaar, wordt
geweigerd met `server_owner_required`. Triggers, views, kolommen en beperkingen die het bestand meebrengt,
worden niet overgenomen.
:::

### Antwoord van `server.listBackups`

Nieuwste eerst, gesorteerd op mapnaam (dat is de tijdstempel, dus de volgorde klopt ook
voor een momentopname waarvan het manifest niet kon worden gelezen).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` ontbreekt wanneer het manifest niet kon worden gelezen. `bytes` op het hoogste
niveau is de werkelijke grootte op schijf van de hele map, niet de som uit het manifest — de
vraag die een operator die momentopnamen opruimt stelt, is wat de map kost, niet wat de
back-up van plan was te schrijven.

Elke `workspaces[].path` is precies wat `workspace.import` als `source_path` aanneemt. Dat is
bewust: “deze werkruimte herstellen uit deze momentopname” *is* de importbewerking, dus de twee
kunnen niet uit elkaar lopen in verschillende behandelingen van hetzelfde bestand.

### Validatie van `workspace.import`

Voordat er iets wordt vervangen, wordt het kandidaatbestand naast het doel gekopieerd naar een tijdelijk bestand en daar gecontroleerd. Een weigering raakt niets aan en draagt haar soort als `data.kind`.

| Voorwaarde                                       | Resultaat                                                       |
| ------------------------------------------------ | --------------------------------------------------------------- |
| Het bestand bestaat niet | Geweigerd, `import.missing_source` |
| Geen leesbare SQLite-database, of hij slaagt niet voor `quick_check` | Geweigerd, `import.damaged` |
| Het bestand komt uit een momentopname, en de SHA-256 ervan wijkt af van die van het manifest | Geweigerd, `import.checksum_mismatch` |
| Een nieuwere versie van de server heeft het geschreven | Geweigerd, `import.newer_schema` |
| Het bestand heeft een andere `application_id`, of geen `workspace_meta` | Geweigerd, `import.foreign_file` |
| Het bestand kan niet naar het schema van deze server worden gebracht | Geweigerd, `import.schema_mismatch` |
| Zijn webhooks of uitnodigingen leiden al naar een andere werkruimte | Geweigerd, `import.route_conflict` |
| Vastgelegd werkruimte-id ≠ het doel              | **Toegestaan**. Zijn rijen krijgen de id van het doel. Zo wordt een werkruimte gedupliceerd of onder een nieuw id hersteld |
| Vastgelegd installatie-id ≠ deze installatie     | **Toegestaan**. De gebruikers-id's horen bij die installatie en worden hier niet herleid |

Na acceptatie wordt het tijdelijke bestand naar het schema van deze server gebracht en moet het daarna precies overeenkomen. Rechten die een bestand zichzelf niet mag geven, worden eruit gehaald: goedkeuringen om een omgevingsdefinitie op de host uit te voeren worden gewist, en actieregels die toestaan of vragen, sandbox-uitvoerrechten, repo-rechten boven lezen, rollen boven lid en uitnodigingen voor die rollen worden tegengehouden, zodat de serverbeheerder ze kan nakijken. Wie importeert, behoudt of krijgt de eigenaarrol. De database die wordt vervangen, wordt bewaard als geplande back-up met de naam `<timestamp>-pre-restore`; het tijdelijke bestand wordt bij gesloten verbindingen van de werkruimte op zijn plaats hernoemd, `code_index.db` wordt verwijderd om opnieuw te worden opgebouwd, en de FTS-indexen worden opnieuw opgebouwd.

## Overdrachtroutes

De export-/import- en momentopnamelijstbewerkingen hierboven spreken in paden aan de
serverkant, wat alleen een volledig antwoord is als de server je eigen machine is. Deze
HTTP-vormige routes dragen back-upbytes **binnen dezelfde geauthenticeerde,
end-to-end-versleutelde brontunnel** als andere gevoelige bronnen, of de RPC-verbinding nu
rechtstreeks of bemiddeld is. Het zijn geen openbare HTTP-bestandsoverdrachtsendpoints: een
verzoek aan een ervan op de openbare listener retourneert `426 Upgrade Required`, ook vanaf
loopback. In de versleutelde tunnel moet het met Noise geauthenticeerde apparaat overeenkomen
met `d`; de handler controleert daarnaast de handtekening van het apparaat over zijn
doeltekenreeks met zijn koppelings-PSK en de rol hieronder.

| Route                   | Methode | Query           | Ondertekend doel               | Vereist                 |
| ----------------------- | ------- | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET     | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | Werkruimte-**beheerder** |
| `/backup/snapshot`      | GET     | `n`, `d`, `s`   | `backup-snapshot:<name>`         | Installatie-**eigenaar** |
| `/backup/stored`        | GET     | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | Werkruimte-**beheerder**; installatie-**eigenaar** zodra de werkruimte is verwijderd |
| `/backup/restore`       | POST    | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | Installatie-**eigenaar** die ook werkruimte-**eigenaar** is (anders `403` met `server_owner_required`) |

`w` is een werkruimte-id, `n` de mapnaam van een momentopname of geplande back-up, `d` het id
van het aanroepende apparaat, `s` de handtekening. Bij `/backup/snapshot` wordt `n` herleid
tegen de back-uplijst in plaats van aan de backups-root te worden geplakt, zodat de route niet
kan worden gericht op een map die de lijst niet zou hebben getoond. Bij `/backup/stored` moet
het een tijdstempelnaam zijn, en moet het bestand een echt bestand zijn binnen de eigen
back-upmap van die werkruimte.

| Status | Oorzaak                                                                              |
| ------ | ------------------------------------------------------------------------------------ |
| `400`  | Een vereiste queryparameter ontbreekt, een back-upnaam is ongeldig, de body van een upload is leeg, of het geüploade bestand is geweigerd (de body is `{error, kind}` met een `import.*`-soort) |
| `403`  | Onbekend of ingetrokken apparaat, slechte handtekening, of de aanroeper mist de rol   |
| `404`  | Geen back-uppoort op deze host, of het genoemde bestand van de momentopname, back-up of werkruimte bestaat niet |
| `405`  | `/backup/restore` aangeroepen met iets anders dan `POST`                             |
| `413`  | De uploadbody is groter dan 8 GiB, volgens de opgegeven content-length of volgens de werkelijk gelezen bytes |
| `426`  | Elk rechtstreeks verzoek aan een overdrachtspad op de openbare HTTP-listener; gebruik de versleutelde brontunnel van een gekoppelde client |
| `500`  | De export of het archief is aan de serverkant mislukt                                |

Alle drie de downloads antwoorden met `Cache-Control: no-store` en `Accept-Ranges: none`.
`/backup/workspace` en `/backup/snapshot` maken per verzoek een **nieuwe** kopie aan en
verwijderen die zodra hij is gestreamd, dus een uit de cache gehaald of hervat antwoord zou
bytes van twee verschillende exports aaneenrijgen tot één bestand dat geldig lijkt en het niet is.

`/backup/stored` is de uitzondering: die route streamt een geplande back-up als
`<workspaceId>-<name>.db` en laat het bestand staan, omdat dat bestand de back-up is.

`/backup/snapshot` retourneert `<name>.zip`, met items ten opzichte van de hoofdmap van de
momentopname, zodat uitpakken `manifest.json` + `global.db` + `<workspaceId>/workspace.db`
reproduceert. De items worden in gesorteerde volgorde geschreven, dus twee archieven van dezelfde
momentopname zijn hetzelfde archief.

`/backup/restore` streamt de body rechtstreeks naar een stagingbestand in plaats van hem te
bufferen, begrenst hem vóór en tijdens het lezen, en verwijdert het klaargezette bestand op
**elk** uitpad, ook bij een weigering.

::::caution[Rechtstreeks en via een relay gebruiken dezelfde versleutelde overdracht]
De relay draagt bronverzoeken, gestreamde antwoorden en uploadbytes als ciphertext; hij
kan de inhoud van de back-up niet lezen. Een pad aan de serverkant blijft een pad op de
serverhost, geen bestand op de relay. Toegang vereist nog steeds het gekoppelde apparaat,
de doeltekenreekshandtekening en de geldende werkruimte- of installatierol. Geen van beide
transports versleutelt de resulterende back-upbestanden in rust.
::::

## Paden en limieten

| Onderdeel                      | Waarde                                                       |
| ------------------------------ | ------------------------------------------------------------ |
| Momentopnamen                  | `<dataDir>/backups/<timestamp>/`                             |
| Geplande werkruimteback-ups    | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Werkruimte-exports             | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Database die een herstel heeft vervangen | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Databases zoals ze waren vóór een update die hun formaat wijzigde | `<dataDir>/pre_upgrade/` en `<dataDir>/<workspaceId>/pre_upgrade/`, telkens de nieuwste twee |
| Staging voor overdrachten      | `<dataDir>/backups/transfer/` — een werkbank, opgeruimd door de route die hem schrijft |
| Naam van het momentopnamearchief | `<snapshot directory name>.zip`                            |
| Uploadplafond                  | 8 GiB per versleutelde `/backup/restore`-upload              |
| Bewaring                       | Installatiemomentopnamen: handmatige verwijdering. Werkruimteback-ups: wekelijkse pipeline, standaard 30 dagen, of handmatige verwijdering. Back-ups van een verwijderde werkruimte: alleen handmatige verwijdering |

De mappen `exports/`, `transfer/` en `workspace-backups/` zijn geen
installatiemomentopnamen en zijn uitgesloten van `server.listBackups`. Alleen de laatste
map heeft geplande bewaring, en alleen zolang de werkruimte bestaat; het verwijderen van
een installatiemomentopname vereist een expliciete actie van de eigenaar van de installatie.
