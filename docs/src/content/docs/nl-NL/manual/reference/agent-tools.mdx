Dit zijn de **aan de server gebonden** tools die de ingebouwde agentruntime rechtstreeks registreert — taalserver, structureel zoeken, debugger, kernels, codemodus-scripts, vragen en workerbesturing — in tegenstelling tot de [MCP-tools](/nl-NL/handleiding/referentie/mcp-tools/) die hij erin overbrugt en de generieke bestands-, zoek- en shelltools van de harnessruntime. Ze staan niet in het MCP-register: een externe MCP-client ziet ze niet, omdat elke tool gebonden is aan een levende resource aan de serverkant — een taalserverproces, een debugadapter, een interpreter — die bij één run hoort.

Elke tool hier wordt alleen geregistreerd wanneer de onderliggende resource voor de run is aangesloten — een taalserver- of debugsupervisor, een tree-sitter-parser, een factory voor kernels, een vraagpoort, een roster van vibewerkers. Detectie van een taalserver of debugadapter voor *deze checkout* is een aparte, latere controle (`status` / `adapters`): die tools blijven in het aanbod staan zodat de agent kan vragen waarom er niets bruikbaar is, in plaats van te gokken.

## Goedkeuringsniveaus

Elke tool verklaart een niveau, en dat niveau bepaalt **welke oppervlakken hem te zien krijgen** — niet alleen of hij om goedkeuring vraagt. De planmodus en alleen-lezen subagenten zijn beperkt tot `read`, dus een tool van het niveau `write` of `exec` ontbreekt volledig in hun schema.

| Niveau  | Betekenis                      | Tools hier                                       |
| ------- | ------------------------------ | ------------------------------------------------ |
| `read`  | Geen neveneffecten             | `lsp`, `ast_grep`, `ask_user`, `repl`, de vijf `vibe_*` |
| `write` | Wijzigt bestanden              | `lsp_rename`, `ast_edit`, `resolve`               |
| `exec`  | Start of bestuurt een proces   | `debug`, `eval`                                   |

## Direct, alleen vanuit een script of geladen bij eerste gebruik

Wanneer de server scripts kan draaien, roept een run een paar tools direct aan en bereikt de rest vanuit een [`repl`](#repl--een-script-draaien-dat-je-tools-aanroept)-script; zie [Codemodus](/nl-NL/handleiding/concepten/codemodus/#welke-tools-de-agent-direct-aanroept) voor de volledige regel. Voor de tools op deze pagina:

| Tool | Met `repl` | Zonder `repl` |
| ---- | ----------- | -------------- |
| `repl` | Direct | Niet aanwezig |
| `ask_user` | Direct | Direct |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Alleen vanuit een script | Geladen bij eerste gebruik |
| `eval` | Geladen bij eerste gebruik (een script kan hem niet aanroepen) | Geladen bij eerste gebruik |
| `vibe_*` | Direct in vibe-modus, nooit vanuit een script | Direct in vibe-modus |

Een tool die is gemarkeerd als “Alleen vanuit een script” wordt in plaats daarvan bij eerste gebruik geladen zodra de server de scripts van de run niet kan draaien ([Wanneer scripts niet kunnen draaien](/nl-NL/handleiding/concepten/codemodus/#wanneer-scripts-niet-kunnen-draaien)).

## `lsp` — query's op de taalserver

Wordt geregistreerd wanneer de run een taalserver-supervisor en een werkmap heeft. Of een server werkelijk kan antwoorden, wordt op het moment van de aanroep bepaald, als een **doorsnede**: er moet een marker in de root staan *en* de binary van de server moet te vinden zijn. Alleen een van beide betekent dat er geen server start — dat meldt `status` — in plaats van een stilzwijgende gok.

Servers komen alleen uit de ingebouwde tabel; een `lsp.json` in de repository wordt niet gelezen. In een gesandboxde run krijgt elke run zijn eigen taalserversessie, dus servers starten bij elke run opnieuw. Projectlokale binaries (`node_modules/.bin`) worden alleen gebruikt wanneer de run gesandboxed is, en de projectroot wordt nooit hoger opgelost dan de werkmap van de run.

Posities worden aangeduid met `line` plus een substring van `symbol`, nooit met een kolom. Een model dat om een kolom wordt gevraagd, gokt, en een verkeerde gok komt uit op een ander symbool op dezelfde regel — een antwoord dat er goed uitziet maar ergens anders over gaat. Het weglaten van `symbol` bij een navigatieactie is een fout, geen gok op de eerste kolom.

| Actie             | Argumenten                       | Retourneert                                |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (of `"*"`)                | Fouten en waarschuwingen; `"*"` draait in plaats daarvan de projectchecker |
| `definition`      | `file`, `line`, `symbol`         | Waar het symbool is gedeclareerd           |
| `type_definition` | `file`, `line`, `symbol`         | Waar het type ervan is gedeclareerd        |
| `implementation`  | `file`, `line`, `symbol`         | Concrete implementaties                    |
| `references`      | `file`, `line`, `symbol`         | Elk gebruik, gemaximeerd op 50             |
| `hover`           | `file`, `line`, `symbol`         | Signatuur en doc-commentaar                |
| `symbols`         | `query` of `file`                | Zoeken in de werkruimte met `query` (gemaximeerd op 100); documentsymbolen met `file` (gemaximeerd op 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Snelle oplossingen die de server biedt     |
| `status`          | —                                | Welke servers draaien, en voor welke roots |
| `reload`          | —                                | Herstart de server voor deze root          |

### Diagnostiek bij het schrijven

De winst zit niet in de tool. `write`, `edit` en `apply_patch` zijn **omhuld**: na de schrijfactie wordt het bestand gesynchroniseerd en via de taalserver opgeslagen, en alleen **nieuw geïntroduceerde** diagnostiek wordt in het resultaat van de tool verwerkt. Een agent merkt dat hij de build heeft gebroken op het moment dat hij hem breekt, zonder eraan te hoeven denken om ernaar te vragen.

Al gemelde diagnostiek wordt onderdrukt door een register per run, met ernst, code en bericht als sleutel — de positie is bewust uitgesloten, zodat een diagnose die alleen vier regels is opgeschoven niet opnieuw als nieuw wordt gemeld.

## `ast_grep` — structureel zoeken

Vindt code op **vorm** in plaats van op tekst. `$NAME` matcht elk knooppunt, `$$$NAME` matcht een reeks broers en zussen, en `$_` is een jokerteken dat niets vastlegt.

De eigenschap die het een matcher maakt in plaats van een regex met extra stappen: een metavariabele die in één patroon wordt herhaald, moet dezelfde tekst vastleggen.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

matcht een guard die opruimt wat hij heeft getest, en matcht **niet** een guard die iets anders opruimt.

| Argument      | Betekenis                                                   |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | Een codefragment met metavariabelen                         |
| `path`        | Bestand of map om in te zoeken; standaard de hele werkruimte |
| `language`    | Een meegeleverd grammatica-id (`dart`, `python`, `rust`, `c`, …). Wordt afgeleid wanneer `path` naar een bestand wijst |
| `max_results` | Standaard 50                                                |

:::note[Het patroon wordt geparseerd met dezelfde grammatica als het bestand]
Dus `dispose(x)` matcht de aanroep hoe die ook is gespatieerd, afgebroken of over regels verdeeld — en matcht nooit dezelfde tekens binnen een letterlijke tekenreeks of commentaar.
:::

:::caution[Een fragment wordt in een hulpconstructie geparseerd, niet kaal]
`dispose(x)`, geparseerd op het topniveau van Dart, is een geldige *functiesignatuur*. De patrooncompiler probeert een ladder van contexten (statement, expressie, klasselid, declaratie) en gebruikt de eerste die het fragment accepteert. Een patroon dat geen enkele context accepteert, wordt gemeld als onparseerbaar in plaats van te worden gezocht en stilletjes niet gevonden.
:::

## `ast_edit` — structurele herschrijving, klaargezet

Dezelfde matching, plus een `rewrite`-sjabloon waarin de metavariabelen weer worden ingevuld. **Er wordt niets geschreven.** De wijziging wordt klaargezet en het resultaat noemt een `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Argument   | Betekenis                                         |
| ---------- | ------------------------------------------------- |
| `pattern`  | Wat moet matchen                                  |
| `rewrite`  | Wat daarvoor in de plaats komt, met `$NAME` ingevuld |
| `path`     | Bereik; standaard de hele werkruimte              |
| `language` | Taal-id                                           |

## `resolve` — een klaargezette wijziging doorvoeren of weggooien

| Argument  | Betekenis                        |
| --------- | -------------------------------- |
| `edit_id` | Uit het resultaat van `(proposed)` |
| `action`  | `accept` of `discard`            |

Elk bestand wordt vergeleken met de inhoud die op het moment van klaarzetten is vastgelegd, en **elke** afwijking weigert de hele wijziging. Een gedeeltelijk toegepaste structurele herschrijving laat een boomstructuur achter die onder noch de oude noch de nieuwe vorm compileert.

## `debug` — een debugger aansturen

Wordt geregistreerd wanneer de run een debug-sessiesupervisor, een werkmap en een gespreks-id heeft. Of een adapter werkelijk kan starten, wordt op het moment van de aanroep bepaald, met dezelfde doorsnede-regel als bij de taalserver (marker *en* binary). Niveau `exec`; niet parallelveilig (een sessie is toestand over meerdere aanroepen, dus een `continue` die `stack` inhaalt, zou een frame lezen dat al is opgeschoven).

Eén sessie per gesprek, met een harde TTL (30 minuten). Een tweede `launch` wordt geweigerd in plaats van de eerste stil te vervangen. In een gesandboxde run behoudt de sessie zijn sandbox over de beurten heen tot ze eindigt, dus hooguit die 30 minuten.

| Bewerking     | Argumenten                    | Opmerkingen                                    |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Welke adapters hier bruikbaar zijn, en waarom niet |
| `status`      | —                             | Of er een sessie draait, en waar die is gestopt |
| `breakpoints` | `file`, `lines[]`             | Een lege `lines` wist het bestand. Mag **vóór** het starten worden ingesteld |
| `launch`      | `program`, `args[]`           | Start het programma en stopt bij je breakpoints |
| `attach`      | `port`                        | Verbindt met een al draaiende debuggee op een van de eigen doorgestuurde poorten van de run; elke andere poort wordt geweigerd voordat er iets start |
| `continue`    | `thread_id?`                  | Draait tot het volgende stopmoment             |
| `pause`       | `thread_id?`                  | Stopt het waar het is                          |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Gaat één stap verder                 |
| `threads`     | —                             | Thread-id's en namen                           |
| `stack`       | `thread_id?`                  | Frames, gemaximeerd op 30                      |
| `scopes`      | `frame_id`                    | Scopes op een frame, elk met een `reference`   |
| `variables`   | `reference`                   | Onderliggende waarden, gemaximeerd op 50; waarden gemaximeerd op 400 tekens |
| `evaluate`    | `expression`, `frame_id?`     | Geëvalueerd in de eigen scope van het frame    |
| `output`      | —                             | De stdout/stderr van het debugdoel, begrensd   |
| `terminate`   | —                             | Beëindigt de sessie en stopt de adapter        |

### Adapters

| Id        | Commando                     | Markers in de root                              |
| --------- | ---------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`         | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                   | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                    | `go.mod`                                        |

`debugpy` verkiest in een gesandboxde run een projectlokale `.venv/bin` of `venv/bin` boven `$PATH`: een python uit `$PATH` is een andere omgeving, en verbinden vanuit de verkeerde mislukt op een manier die leest als kapotte code. Zonder sandbox gebruikt het alleen `$PATH`, zodat een repository niet kan kiezen welke interpreter op de host draait.

## `repl` — een script draaien dat je tools aanroept

Aanwezig op elke run wanneer de server scripts kan draaien ([Wanneer een run `repl` heeft](/nl-NL/handleiding/concepten/codemodus/#wanneer-een-run-repl-heeft)). Het script is gewoon JavaScript, de body van een async-functie, en draait in een nieuwe, afgesloten interpreter in een eigen proces: geen toegang tot bestandssysteem, netwerk, processen of modules. `repl` zelf hoort bij het `read`-niveau en bewaakt zichzelf, omdat elke toolaanroep die het script doet afzonderlijk wordt gecontroleerd. Ook op het MCP-eindpunt, voor agentruns op een server die scripts kan draaien.

| Argument | Betekenis |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | Het script. Maximaal 256 KiB |
| `description` | Verplicht. Een kort label voor de regel in het transcript |
| `timeout_ms` | Optioneel. Een kortere tijdslimiet dan die van de werkruimte; nooit een langere |
| `max_output_tokens` | Optioneel. Een kleiner uitvoerbudget dan dat van de werkruimte; nooit een groter |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

De beschrijving van `repl` zegt de agent: „Een tool die geen van je directe tools is, heeft in dit verzoek geen definitie. Zoek hem op met `describeTool(name)` of `searchTools(query)` voordat je hem voor het eerst aanroept, tenzij de exacte aanroepvorm al eerder in dit gesprek aan je is getoond.”

`describeTool(name)` geeft de beschrijving van een tool, zijn declaratie, zijn invoer- en uitvoerschema's en zijn resultaatnotitie, wanneer die er is: wat een script ontvangt van een voltooide aanroep, in de eigen woorden van de tool. De `repl`-beschrijving somt de notities op van de directe tools die een script mag aanroepen. Een resultaat dat JSON-tekst is, komt geparseerd aan, tenzij het meer dan 131.072 waarden bevat: dan komt het als tekst aan, en het script parseert het met `JSON.parse`. De tekst van een resultaat van een tool van een externe MCP-server wordt afgekapt bij 262.144 tekens, en afgekapte tekst is geen geldige JSON meer.

- `tools.<name>(args)` roept een tool aan via hetzelfde filter, dezelfde beveiligingen en goedkeuring als een directe aanroep, en wordt afgewezen met een fout wanneer die wordt geweigerd of mislukt. Aanroepen die alleen lezen, kunnen tegelijk lopen; aanroepen die iets wijzigen, lopen één voor één, in de volgorde waarin het script ze deed. Terwijl een van zijn aanroepen op een persoon wacht, start het script geen andere aanroep.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` en `describeNamespace(name)` vinden tools, ook die van verbonden MCP-servers. Een tool buiten de directe set die een script mag aanroepen, is alleen vanuit een script aanroepbaar; een directe aanroep ervan geeft terug hoe je die vanuit `repl` aanroept. Zodra de server de scripts van de run niet kan draaien, wordt zo'n tool in plaats daarvan bij eerste gebruik geladen.
- Opzoekingen zijn begrensd: een zoekopdracht van hooguit 1.024 tekens, een naam of namespace van hooguit 256, `limit` van 0 tot 50, en per script hooguit 200 opzoekingen die samen 2 seconden serverstijd kosten, terwijl alle scripts van één werkruimte samen 2 seconden opzoektijd delen, die met een kwart seconde per seconde terugkomt; bij overschrijding van een van beide worden verdere opzoekingen afgewezen. In een zeer grote catalogus delen de beschrijvingen in `ALL_TOOLS` gelijkelijk ongeveer een miljoen tekens, en een afgekapte beschrijving eindigt op `…`; `describeTool` geeft altijd de volledige beschrijving terug. Een type dat te groot is om te tonen, staat als `unknown /* too large to show */`, en een onbekende naam wordt beantwoord met de dichtstbijzijnde namen.
- Tools zijn gegroepeerd in namespaces: `builtin` (de eigen tools van de harness), `control-center` (de tools van Control Center) en één per verbonden MCP-server, genoemd naar de server. Een server met de naam `builtin`, `control-center` of `script`, of waarvan de naam begint met `external-`, in welke combinatie van hoofdletters ook en met of zonder spaties eromheen, wordt getoond als `external-` gevolgd door zijn naam, en geen enkele tool staat ooit in `script`.
- Alleen wat het script teruggeeft, of doorgeeft aan `text()`, `image()` of `console.*`, komt terug bij de agent. Uitvoer die over het budget gaat, behoudt het begin en het einde, en `read_output` leest de rest.
- `store(key, value)` / `load(key)` bewaren JSON-waarden voor latere scripts van dezelfde conversatie en agent, en worden alleen opgeslagen wanneer het script klaar is. De scripts van een subagent hebben geen store.
- `await tools.ask_user(...)` stelt een vraag; het antwoord wordt ook aan het resultaat toegevoegd. `sleep(ms)`, `setTimeout`, `limits()` en `models.embed` / `rank` / `classify` (embeddings op het apparaat) zijn ook beschikbaar.
- `describeTool(name)` en `searchTools(query)` geven ook antwoord voor de eigen functies van het script, die geen tools zijn: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` en `models.*`, onder de naamruimte `script`.
- Niet aanroepbaar vanuit een script: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` en de `vibe_*`-tools.
- Een script leest het verleden van de eigen run: `history({start, role, tool, limit})` bladert door het transcript van het gesprek (maximaal 50 rijen per aanroep; geef de `next_start` van de vorige pagina mee als `start`), `outputs()` somt de toolresultaten op die voor dit gesprek en deze agent zijn opgeslagen, en `loadOutput(handle)` leest 16.384 tekens van er één. `storedKeys()` somt de opgeslagen sleutels op met hun groottes. `keep(value, label)` slaat een grote waarde op als uitvoer die een later script of `read_output` kan lezen; dat gebeurt pas wanneer het script klaar is (1 MiB per waarde, 64 waarden en 16 MiB per run). `limits().returnBudgetChars` zegt hoeveel van het uitvoerbudget nog over is. Een alleen-lezen run (een doelreview) kan lezen, maar niet opslaan of bewaren. Op Claude Code en ACP werkt `history()`, maar `outputs()`, `loadOutput()` en `keep()` weigeren, omdat Control Center geen toolresultaten van die runs bewaart.
- Een fout door een time-out, een uitvoeroverloop of de aanroeplimiet zegt hoe je hem oplost.

Eén run draait op een moment maar één script. De limieten en wat er bij elk gebeurt, staan op de pagina [codemodus](/nl-NL/handleiding/concepten/codemodus/#limieten); elk script wordt vastgelegd onder **Observeerbaarheid → Codeuitvoeringen**.

## `eval` — persistente interpreters

Een Python- of JavaScript-cel waarvan variabelen, imports en geladen data tussen aanroepen behouden blijven. Niveau `exec`; niet parallelveilig. Niet aanroepbaar vanuit een `repl`-script, en een cel kan de tools van de run niet aanroepen: wil je tools vanuit code aanroepen, gebruik dan [`repl`](#repl--een-script-draaien-dat-je-tools-aanroept).

| Argument      | Betekenis                                        |
| ------------- | ------------------------------------------------ |
| `code`        | De cel                                           |
| `description` | Vereist. 5–10 woorden voor het transcriptlabel   |
| `language`    | `python` (standaard) of `javascript`             |
| `reset`       | Gooi de interpreter weg en start eerst schoon    |

- De laatste expressie wordt weergegeven zoals een notebook dat doet.
- `display()` werkt, een pandas-frame wordt als tabel weergegeven, en een matplotlib-figuur komt terug als een **afbeelding die het transcript weergeeft**.
- De IPython-idiomen die mensen reflexmatig typen — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — worden herschreven naar gewone code. `%pip` leegt ook `sys.modules`, zodat de volgende `import` ziet wat er net is geïnstalleerd.
- Een cel die meer uitvoer afdrukt dan zijn uitvoerbudget, behoudt de eerste driekwart en het laatste kwart, met één regel die zegt hoeveel tekens en afbeeldingen zijn weggelaten.
- Wanneer de interpreter zonder verzoek is gestopt, wordt de volgende cel één keer verteld dat zijn eerdere variabelen weg zijn.

:::note[Waar de kernel draait]
In de omhulling van het gesprek als die er is, anders in de OS-sandbox van de run op de host. Met de sandbox uit of niet beschikbaar draait hij zonder inperking en vraagt `eval` om goedkeuring voor hostuitvoering. Hij start geen omhulling op om daar te komen, dezelfde regel die voorkomt dat een rigtab automatisch start.
:::

## `bash` op de achtergrond

`bash` met `run_in_background: true` start het commando en keert meteen terug met een handle (`b1`, `b2`, …) in plaats van te wachten. De agent blijft werken, of beëindigt zijn beurt en wordt gewekt wanneer het commando stopt.

| Argument | Betekenis |
| ------------------- | ------- |
| `run_in_background` | `true` om te starten en meteen terug te keren |
| `timeout_seconds` | Seconden voordat het commando wordt gestopt: standaard 600, maximaal 3.600 |
| `notify` | Optioneel. Een eenvoudig patroon; elke uitvoerregel die erbij past, wordt tijdens het draaien naar de agent gestuurd (zoals `listening on\|FAILED`) |

- Er draaien hoogstens 4 achtergrondcommando's tegelijk in één run. Elk wordt gestopt bij zijn time-out en wanneer de run eindigt, samen met elk proces dat het startte.
- Wanneer een commando stopt, krijgt de agent een melding met de exitcode, de laatste 2.000 tekens uitvoer en een `read_output`-handle voor de rest.
- Een agent wiens enige overgebleven werk een achtergrondcommando is, wacht zonder het model aan te roepen, en de stilte-watchdog van de run pauzeert terwijl hij wacht.
- `bash_output(handle)` leest de staat en recente uitvoer van een commando; `bash_kill(handle)` stopt het. Beide zeggen wanneer het resultaat al is afgeleverd.
- Een script kan geen achtergrondcommando starten. Claude Code heeft zijn eigen achtergrond-Bash; Control Center houdt die run maximaal 10 minuten open na de beurt die een taak aan het draaien liet.

## `compact` — ruimte vrijmaken in het contextvenster

Compacteert de oudere context van het gesprek vóór de volgende modelaanroep, met behoud van wat `focus` noemt (maximaal 1.000 tekens). De nieuwste beurten blijven letterlijk staan. De budgetregel per beurt van de agent toont het contextgebruik bij 70, 80 en 90%, en de tool is het waard om na ongeveer 70% aan te roepen voordat een lange nieuwe fase van werk begint. De `preCompact`-hook van de servereigenaar kan aan de focus toevoegen ([Shell-hooks](/nl-NL/handleiding/referentie/agentconfiguratie/#shell-hooks)). Na een compactie voegt de server een blok "Still in flight" toe: het doel, de wachtende wekbeurten, open vragen, achtergrondcommando's, de checklist en de opgeslagen sleutels, elk met de aanroep die het herstelt.

## `ask_user` — een mens een vraag stellen

Niveau `read`. De **enige** manier waarop een run de operator iets vraagt. Hij toont een genummerde kaart in het gesprek en blokkeert tot iemand antwoordt, overslaat, of de vraag een time-out krijgt. Schrijf de vraag nooit als chatbericht — dat beëindigt de beurt.

| Argument          | Betekenis                                |
| ----------------- | ---------------------------------------- |
| `question`        | Wat je wilt vragen                       |
| `context`         | Optioneel: waarom je het vraagt en wat er van het antwoord afhangt |
| `options[]`       | Keuzes, elk `{label, description?}`      |
| `allow_free_text` | Of een getypt antwoord wordt geaccepteerd |
| `multi_select`    | Of meerdere opties mogen worden gekozen  |

Overslaan is succes: ga verder op een uitgesproken aanname en vraag het niet nog eens. Een time-out is een fout met dezelfde instructie. Toestemmingsprompts ("mag ik dit doen?") zijn een aparte poort en verschijnen als dezelfde kaart in het gesprek.

Wordt alleen geregistreerd wanneer zowel een vraagpoort als een doelruimte bestaat. Zonder aangesloten mens **mislukt** de aanroep in plaats van voor altijd te blokkeren — dezelfde fail-closed-houding die een `prompt` van een beveiliging aanneemt wanneer er geen goedkeurder is verbonden.

## `vibe_*` — achtergrondworkers sturen

Wordt alleen geregistreerd zolang de [vibe-modus](/nl-NL/handleiding/gidsen/achtergrondworkers-sturen/) aanstaat. Alle vijf zijn van het niveau `read`: de poort hoort op de tools van de worker, waar de bewerking werkelijk plaatsvindt.

| Tool         | Argumenten                               | Opmerkingen                                 |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | Keert onmiddellijk terug; de worker draait verder |
| `vibe_send`  | `worker_id`, `message`                   | Vult de briefing aan en draait opnieuw      |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | Blokkeert tot hij is afgerond               |
| `vibe_kill`  | `worker_id`                              | Stopt hem                                   |
| `vibe_list`  | —                                        | Niveau, status, verstreken tijd en laatste resultaat |

`tier` is `fast` (mechanisch werk met een duidelijke specificatie) of `good` (ontwerp, beoordeling, of het reviewen van de output van een `fast`-worker).
