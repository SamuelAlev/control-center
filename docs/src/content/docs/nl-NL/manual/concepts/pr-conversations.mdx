Een pull request is al de plek waar het gesprek over code plaatsvindt.
PR-gesprekken maken er een oppervlak van op een Control Center-werkruimte, net
zoals een [chatbrug](/nl-NL/handleiding/concepten/chatbruggen/) van Slack er een
maakt: @-vermeld `@usectrl` in een PR,
antwoord binnen zijn reviewthreads of voeg het label `ai-review` toe, en het werk
gebeurt in de reviewruimte van de PR — onder dezelfde attributie en
beveiligingen als alles wat in de app wordt getypt. Een opmerking en een label
worden op dezelfde manier gecontroleerd: op het lid dat de opmerking schreef of
het label toevoegde. De antwoorden komen terug op GitHub, op de plek waar de
vraag is gesteld.

Drie beslissingen bepalen de functie, en elke beslissing is dezelfde die de
chatbrug voor chat nam, opnieuw geformuleerd voor een codehost: **welke richting
de verbinding opgaat**, **wat een opmerking van buitenaf autoriseert** en **aan
wie elke kant wordt toegeschreven**.

## Polling is het transport

Het enige pushkanaal dat GitHub voor een app biedt, is een webhook, en een
webhook heeft een inkomende URL nodig — precies het enige dat dit oppervlak
bewust nooit vereist. Het opsporen gebeurt dus in een pollronde: één per
appinstallatie gealiaste zoekopdracht vraagt GitHub om PR's die `@usectrl` vermelden, en om open PR's die het reviewlabel dragen; van PR's die
al een reviewruimte hebben worden de opmerkingenthreads gelezen, en alles wordt
op opmerking-id vergeleken met wat de vorige pollronde zag. Een eigen app pollt
elke minuut over hoogstens 25 PR's. Via Connect gaan de aanroepen ten koste van
het eigen GitHub-quotum van leden, dus draait de pollronde elke twee minuten over
hoogstens 10, en een werkruimte onder 15% van zijn quotum wordt overgeslagen tot
het quotum hersteld is. Connect zelf ziet nooit de inhoud van PR's.

De ontwerpgevolgen zijn het benoemen waard:

- **Latentietijd is een pollinterval, geen gebeurtenis.** De 👀-bevestiging komt
  binnen één pollronde. Er hangt niets dringends aan.
- **Precies één keer, per opmerking.** Opmerking-id's zijn uniek binnen heel
  GitHub; elk id wordt vastgelegd zodra de opmerking als in aanmerking komend is
  geclassificeerd, voordat er iets op wordt ondernomen. Een crash kan de
  verwerking van een opmerking kwijtraken, maar kan die nooit dubbel laten
  vuren.
- **Offline tijd wordt ingehaald, niet opnieuw afgespeeld.** De seen-set wordt
  opgeslagen, dus een herstart levert wat binnenkwam terwijl de server uit
  stond. De enige uitzondering is de allereerste pollronde: zonder geheugen om
  mee te vergelijken wordt alles wat nog openstaat stil geregistreerd — een
  beheerder die twintig PR's van een label voorzag voordat deze server bestond,
  mag niet terugkomen op twintig lopende reviews.
- **Het label is een verzameling, geen gebeurtenis.** De zoekopdracht
  rapporteert de _aanwezigheid_ van een label, dus een PR met label wordt één
  keer geactiveerd, ooit. Een label opnieuw toevoegen nadat je het hebt
  verwijderd, is onzichtbaar voor de pollronde; een vermelding is het pad om
  opnieuw te draaien.

De zoekopdracht draait één keer per installatieaccount met de eigen client van
die eigenaar, omdat een token alleen de repo's van zijn eigen installatie ziet — één credential voor de hele server zou stilletjes elke PR
onder de andere installaties van de app missen.

## Lidmaatschap autoriseert, niet de opmerking

Een PR-opmerking komt binnen met een auteur — een niet-geverifieerde externe
identiteit tot het tegendeel blijkt. De server herleidt het onveranderlijke
numerieke GitHub-account-id van de auteur (nooit de login, die kan worden
hernoemd en hergebruikt) via de GitHub-aanmeldingen van de leden van de
werkruimte, die op een TTL opnieuw worden opgebouwd omdat mensen zich aanmelden
en uitgenodigd worden terwijl de server draait. Voor het label `ai-review` wordt
de persoon herleid die het als laatste heeft toegevoegd.

Drie controles, in volgorde, en wie er een niet doorstaat, wordt stil
afgewezen — er wordt niets geplaatst:

- **Een aangemeld lid.** Het account moet horen bij een lid van _deze_
  werkruimte dat zich op deze server bij GitHub heeft aangemeld
- **Een rol met schrijfrechten.** `viewer` en `guest` kunnen geen werk starten
- **Pushtoegang.** Antwoorden gebruiken een token voor die ene repository, beperkt
  tot de toegang van dat lid daartoe. Kan de server er geen uitgeven, dan gaat
  hij niet verder

Elke controle draait vóór elke bevestiging, dus een vreemde krijgt geen reactie
en geen antwoord. Een opmerking wordt nooit toegeschreven aan iemand die hem niet
heeft verstuurd, en de woorden van een vreemde komen nooit een werkruimte binnen
die diegene niet kan zien.

### De claim

De laatste stap vóór enig werk is een 👀-reactie, toegevoegd met de eigen
GitHub-aanmelding van de auteur. GitHub antwoordt `201` voor een nieuwe reactie en
`200` voor een die al bestaat, dus de reactie werkt ook als slot: als dezelfde
persoon is aangemeld op twee servers die allebei de repository koppelen, doet
alleen de eerste die reageert het werk. Een opmerking die meerdere werkruimtes
op één server zien, wordt aan elk aangeboden, en dezelfde claim beslist.

## Twee identiteiten, met opzet

Elke kant van het gesprek draagt een andere identiteit, en dat verschil ís de
functie:

- **Op GitHub is het antwoord automatisering namens jou.** Elk antwoord rijdt
  mee op een token voor die ene repository, beperkt tot de toegang van het
  vragende lid, en wordt geschreven door het `[bot]`-account van de app. Eén
  uitzondering: op de gedeelde Control Center Connect-app plaatst de bot alleen
  reacties in reviewthreads als de Connect-operator de installatie heeft
  opgenomen; anders komt een antwoord binnen een reviewthread van het eigen
  account van het vragende lid. Hoe dan ook begint elk antwoord
  met `**Control Center** (for @login):`, wat zegt wie het vroeg en tegelijk als
  lusbeveiliging dient. @-vermeldingen in de woorden van de agent worden onschadelijk gemaakt, zodat een antwoord nooit een gebruiker of team een melding geeft.
- **In de ruimte is de vraag van jou.** Het bericht wordt toegeschreven aan het
  lid waaraan de auteur is herleid, en de agentrun wordt namens hen uitgevoerd:
  de commits zijn van hen, en de autonomieregelaar en
  actiebeveiligingen van de ruimte gelden precies zoals voor een bericht dat in
  de app is getypt. Schrijfacties naar de codehost vanuit de run gebruiken tokens
  voor één repository, begrensd door dat lid, nooit diens volledige, doorgegeven
  aanmelding.

Het publiceren van reviewbevindingen terug naar GitHub blijft een beslissing van
een persoon, genomen in Control Center. Een vermelding kan een review _starten_;
alleen een mens publiceert er een.

## De lusbeveiliging

Alles wat door een botaccount is geschreven, wordt weggegooid voordat er welke
poort dan ook draait — specifiek het onze, en elk achtervoegsel `[bot]`, zodat
de reviewbot van een andere app de onze ook niet kan wekken — en net zo elke
opmerking die begint met het voorvoegsel `**Control Center** (for @`, omdat een
reactie op een reviewthread via Connect van het account van een persoon kan zijn. Zonder dit zouden de
antwoorden als nieuwe opmerkingen binnenkomen en de brug voor altijd opnieuw
activeren.

Alleen `@usectrl` start werk. De eigen login van de app (`<slug>[bot]`) en de kale slug adresseren niets: GitHub biedt geen automatisch aanvullen voor een appaccount, en een kale slug kan bij een menselijke gebruiker horen.

## Wat bewust niet wordt geboden

- **Geen automatische publicatie.** Bevindingen belanden in de reviewruimte;
  publiceren naar GitHub is een aparte, menselijke actie
- **Geen fuzzy identiteit.** De auteur wordt aan precies één lid gekoppeld of
  wordt genegeerd — er is geen attributie op basis van een gok
- **Geen geautomatiseerde goedkeuring.** Automatisering kan opmerkingen plaatsen
  en wijzigingen vragen, maar een `APPROVE`-review wordt geweigerd voordat die
  wordt verstuurd. Goedkeuren is een handeling van een persoon
- **Geen webhook voor de GitHub App.** Dit oppervlak registreert er nooit een,
  dus er is geen inkomende URL om voor PR-opmerkingen bloot te stellen. Andere
  productwebhooks (pipelines, ticketsynchronisatie) zijn een aparte, optionele
  instelling.
