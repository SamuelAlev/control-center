:::note[Waar de OS-sandbox wel en niet reikt]
`cc_server` probeert de host bij het opstarten en omhult de uitvoering van
agentopdrachten in de OS-native sandbox wanneer er een beschikbaar is — Seatbelt
op macOS, bubblewrap op
Linux en WSL2 (dat `bwrap` en `socat` op het `PATH` nodig heeft). Waar geen
backend bestaat — Windows, of een Linux-machine zonder die tools — starten alleen de runs van de servereigenaar, zonder sandbox, en worden die van alle anderen geweigerd. De servereigenaar kan de server ook starten met `--sandbox off`, wat de agents van elk lid op die machine zonder sandbox laat draaien. Het opstartlog zegt in welk geval je zit; zie [Agents op een host zonder sandbox](#agents-op-een-host-zonder-sandbox).

Twee hiaten overleven de sandbox en zijn het waard om in gedachten te houden:

- De **in-process bestandstools** van de ingebouwde harness (`read`, `write`, `edit`,
  `apply_patch`, `search`, `find`, `search_files`) draaien in het serverproces,
  dus alleen `bash` wordt omhuld. Wat die tools begrenst, is de padbeperking in
  de tools zelf plus de actiebeveiligingen.
- **Claude Code wordt gestart met `--dangerously-skip-permissions`**, omdat een
  niet-interactieve `claude -p` anders voor altijd blijft hangen op zijn eigen prompt.
  De bestandsaanroepen ervan worden dus niet door de beveiligingen van Control Center bewaakt, en de shellopdrachten alleen door een hook die de opdrachtregel leest — de OS-sandbox is de grens eromheen.
  :::

## Waarom isolatie hier belangrijk is

Een agent leest bestanden, draait shellopdrachten en roept externe API's aan
namens jou. De fout waar je je zorgen over maakt is zelden kwaadwilligheid — het
is een agent die een pad verkeerd leest en je werkcheckout herschrijft, of een
die een branch pusht die je nog niet klaar had gereviewd. De vraag die het
product dus moet beantwoorden is niet “is de agent te vertrouwen”, maar “hoe
groot is het impactbereik als hij het mis heeft”.

Control Center antwoordt daarop in lagen, en de lagen zijn bewust onafhankelijk.
Ontbreekt er één, dan houden de andere nog stand. Dat is belangrijk, want de
buitenste laag — de OS-sandbox — is de enige voorwaardelijke: hij hangt ervan af
of de host een backend biedt, en op Windows doet geen enkele host dat. Waar hij ontbreekt, voert de server de agents van iedereen niet stilzwijgend zonder hem uit.

## Agents op een host zonder sandbox

De server beslist één keer bij het opstarten hoe agents op zijn machine draaien, en houdt die beslissing tot hij herstart:

- **Gesandboxed.** De host heeft een backend en de sandbox staat aan. Elke run wordt omhuld.
- **Uit.** De servereigenaar heeft de server met `--sandbox off` gestart. De agents van elk lid draaien op deze machine zonder sandbox. Dat is de keuze van de eigenaar voor iedereen die de server gebruikt, geen instelling voor één run.
- **Niet beschikbaar.** De sandbox staat aan, maar de host heeft geen backend. Een run start alleen wanneer de persoon die er verantwoordelijk voor is de [eigenaar](/nl-NL/handleiding/concepten/autorisatie/#de-serverbeheerder) van de server is: de persoon die erom vroeg, of voor een schema, webhook of andere automatisering de persoon waaraan die is gebonden. Bij alle anderen wordt de run geweigerd voordat een credential wordt geminted of een proces start, met "Deze server heeft geen sandbox, dus alleen de serverbeheerder kan hier agents uitvoeren. De beheerder kan de sandbox installeren of sandboxing voor iedereen uitzetten."

De reden is het eigendom van de machine. Een agent zonder sandbox kan alles wat het serveraccount van de server kan, dus draait alleen de persoon die dat account bezit er een, tenzij die voor iedereen anders beslist. Een Windows-server bevindt zich altijd in het geval niet beschikbaar. Linux heeft een eigen bijzonderheid, behandeld in de [sandboxbackends-referentie](/nl-NL/handleiding/referentie/sandboxbackends/#linux-bubblewrap): native dispatch faalt daar momenteel gesloten, zelfs met bubblewrap geïnstalleerd.

Dezelfde regel geldt voor de kleinere dingen die voor je een proces starten:

- **Snelle hulpjes die via een ACP-CLI draaien**: gesprekstitels, `/btw`, `/handoff` en `/goal`. Wanneer de server agents in een sandbox draait, draaien ze binnen de sandbox, in een eigen sessie. Onder `--sandbox off` draaien ze zonder inperking. Zonder beschikbare sandbox draaien ze alleen voor verzoeken waarvoor de servereigenaar verantwoordelijk is; voor anderen worden ze overgeslagen, dus er wordt geen titel gegenereerd en een zijvraag meldt dat de Content synthesizer geen werkende runner heeft. Hulpjes die geen tool starten, worden hier niet door geraakt.
- **De golden tests van een pull request** in de visuele controle van Review Studio volgen dezelfde regel.
- **Toolprocessen en `bash`** in een run vallen nooit terug op de host. Als de server agents in een sandbox wil draaien maar er voor een run geen sandbox beschikbaar is, worden ze geweigerd.

## Wat een agent daadwerkelijk beperkt

Vijf dingen begrenzen een agentrun op elke host, met of zonder sandbox. Geen
ervan is een kernelgrens; alle vijf zijn ze reëel. Waar de host een backend
biedt, zit de OS-sandbox daarbovenop, en “Wat de sandbox toevoegt en waar hij
stopt” hieronder beschrijft wat dat verandert.

**Zijn eigen copy-on-write-worktree.** Elk gesprek zet zijn eigen checkout klaar
van elke gekoppelde repo, copy-on-write gekloond via de meegeleverde
`rift`-native in plaats van byte voor byte gekopieerd, zodat isolatie goedkoop
genoeg is om de
standaard te zijn. De geregistreerde repository die je aan de werkruimte hebt
toegevoegd, is niet de map waarin de agent werkt — twee gesprekken die dezelfde
repo aanraken, zien elkaars wijzigingen niet en geen van beide bewerkt jouw
checkout.

De korrel is het preciseeren waard: **de worktree is per gesprek, niet per
agent.** Twee agents in hetzelfde gesprek krijgen aparte overlay-werkmappen die
de `repos/` van dat gesprek _delen_ — wat precies de bedoeling is, want ze werken
samen aan één wijziging — terwijl hun privémappen per agent gescheiden blijven.
Copy-on-write is de enige backend overal waar `rift` meelevert: een
bestandssysteem dat niet kan reflinken, of een datadir op een ander volume dan de
repo, laat het klaarzetten mislukken in plaats van terug te vallen. Windows is de
uitzondering — daar is geen copy-on-write-backend, dus is `git worktree` de
backend, en geen stille verslechtering.

**Padbeperking in de bestandstools van de ingebouwde harness.** De tools `read`,
`write`, `edit`, `apply_patch`, `search`, `find` en `search_files` van de harness
herleiden elk pad tegen de werkmap van de run plus gedeelde rootpaden — de map
`repos/` van het gesprek, waar de worktrees staan, en de bijlagenmap van de
ruimte als die bestaat — en weigeren alles wat daarbuiten uitkomt. Absolute paden
worden alleen geaccepteerd als ze al binnen lagen. Een symlink binnen de worktree
die naar buiten wijst, wordt ook herleid en geweigerd. Daarom kan een agent zelfs
zonder sandbox in beeld niet met `write` naar `~/.ssh` schrijven.

**Het tooloppervlak van de modus.** De [modus](/nl-NL/handleiding/concepten/modi/)
van een gesprek bepaalt welke tools überhaupt voor de run worden
gematerialiseerd. In de alleen-lezen-modi (`plan`, `review`, `orchestrate`) staan
de muteerende tools simpelweg niet in het register en weigert het
shell-opdrachtbeleid voor die modi elke muteerende opdracht onmiddellijk — `git commit`,
`git push`, `npm install`, `docker` en de rest — in plaats van erom te vragen. Een tool die er niet is, kan niet worden aangeroepen, en dat is een
sterkere garantie dan een tool die er wel is en achter een poort zit.

**De uniforme actiebeveiligingen.** Elke muteerende tool verklaart welke
effectklassen hij kan veroorzaken, en de policy-engine herleidt elk daarvan naar
toestaan, eerst vragen of weigeren voordat de aanroep draait. Een `prompt` zonder
verbonden goedkeurder wordt _geweigerd_ — een vraag die niemand kan beantwoorden
is nooit een ja. Zie [Beveiligingen](/nl-NL/handleiding/concepten/beveiligingen/)
voor het herleidingsmodel.

**Inloggegevens via de broker en een gesaneerde omgeving.** Inloggegevens worden per start aangemaakt en ingetrokken wanneer de run afloopt, en het GitHub-token van een run kan lezen maar niet pushen — zie "Pushes lopen via Control Center" hieronder. ACP, de `bash` van de harness en Claude
Code onder de native wrap krijgen een omgeving waarin de injectievectoren via de
dynamic linker en interpreters (`LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`,
`NODE_OPTIONS`, `GIT_SSH_COMMAND` en hun verwanten) zijn gestript voordat het
proces start. Claude Code via `NoSandboxAdapter` erft de omgeving van de host.

### Waar die grenzen dunner worden

De bestandstools van de harness draaien _in het serverproces_, niet in een
kindproces, dus geen enkel sandboxprofiel zou ze kunnen beperken, ook niet als er
een zou zijn bevestigd — alleen `bash` gaat door de gesandboxte
opdrachtuitvoerder. Hun beperking is de padcontrole die hierboven is beschreven,
en die controle is daarom dragend in plaats van een tweede verdedigingslinie.

De `bash`-tool is de andere plek waar precisie loont. De opdrachten ervan worden
getoetst aan het opdrachtbeleid van de modus en daarna gestart met een gesaneerde
omgeving en de worktree als werkmap. Waar een backend bestaat, wordt die start
omhuld, dus houdt de sandbox een shellopdracht tegen die buiten de worktree wil
schrijven; waar dat niet zo is (elke run onder `--sandbox off`, en de eigen runs van de eigenaar op Windows of op Linux zonder `bwrap` en `socat`) is
het opdrachtbeleid het enige tussen de opdracht en de rest van de schijf. In de
modus `chat` weigert het beleid hard een vaste lijst (rechtenescalatie,
vernietiging van systeem en schijf, ontsnapping uit containers en namespaces) en
vraagt het om bevestiging bij mutaties aan de remote-status (`git push`, `gh pr create`,
het publiceren en installeren van pakketten). Alles wat op geen van
beide lijsten staat, draait gewoon. Pijplijnen, ketens en subshells worden
geparsed en elke deelopdracht wordt apart getoetst, waarbij de meest beperkende
beslissing wint.

Claude Code, wanneer het als adapter wordt gebruikt, is het geval waarin de
sandbox het meeste gewicht draagt. Control Center start het met
`--dangerously-skip-permissions`, omdat een niet-interactieve `claude -p` anders
voor altijd blijft hangen op zijn eigen goedkeuringsprompt. De lees-, schrijf- en bewerkingsaanroepen ervan gebeuren binnen zijn eigen proces en Control Center ziet ze nooit. Zijn `Bash`-aanroepen gaan vóór uitvoering naar een hook op de server die de opdrachtregel indeelt en de bijbehorende regel raadpleegt, en de `mcp__*`-tools die Control Center serveert gaan zoals altijd langs de poort. Waar een backend bestaat, gebeuren die ongeziene
aanroepen nog steeds binnen de sandboxwrap, dus is het besturingssysteem de grens
eromheen. Waar dat niet zo is, is er niets. Elke adapter vermeldt dit in zijn
afdwingingsmatrix — zie [de eerlijkheidsmatrix per
adapter](/nl-NL/handleiding/concepten/beveiligingen/#de-eerlijkheidsmatrix-van-de-adapters).

## Pushes lopen via Control Center

Er zijn geen machtigingsvlaggen per agent. Of een agent een commit mag maken,
mag pushen, een pull request mag openen, naar een tracker mag schrijven of het
netwerk mag bereiken, beslissen de [beveiligingen](/nl-NL/handleiding/concepten/beveiligingen/) —
toestaan, eerst vragen of weigeren — en dezelfde regels gelden welke adapter de
agent ook draait.

Een push is de actie die moet standhouden, zelfs tegen een agent die een regel
probeert te omzeilen. Daarom wordt hij afgedwongen via wat de agent bezit, niet
via wat hij uitvoert. Een run heeft bij de start geen token voor de codehost, en zijn `git` krijgt er nooit een. Wanneer zijn `gh` er een nodig heeft, geeft Control Center hem een token voor één GitHub-repository waarmee de run werkt, uitgegeven via de GitHub App van de werkruimte, de eigen app van de server of Control Center Connect. Het kan alleen lezen: het kan niet pushen, opmerkingen plaatsen of iets wijzigen. De git-configuratie van de
run herschrijft elke GitHub-push-URL (`https://github.com/`,
`git@github.com:`, `ssh://git@github.com/`) naar de **agentrun-gateway**, een
loopback-eindpunt op `cc_server`. De gateway leest welke refs de push bijwerkt,
raadpleegt de regel **Naar een remote pushen** — een regel die tot branches is
beperkt, zoals "pushes naar `main` weigeren", geldt dus ook — en stuurt de push
pas daarna naar GitHub door, met een schrijftoken dat hij daarvoor aanmaakt en
nooit aan de agent geeft. Een geweigerde push verschijnt in de eigen uitvoer van
git:

```text
 ! [remote rejected] main -> main (Control Center policy: …)
```

De gateway stuurt pushes alleen door naar de eigen repo van de worktree of naar
een GitHub-repo die aan de werkruimte is gekoppeld. Fetches lopen ook via de gateway, bij GitHub, GitLab en Bitbucket: die haalt de repositories waarmee de run werkt op met een inloggegeven dat hij zelf bewaart en dat de run nooit ziet. Bij GitLab en Bitbucket is dat je eigen token als je om de run hebt gevraagd, en het automatiseringstoken van de repo als niemand erom heeft gevraagd. Een fetch vraagt niemand om toestemming, en alleen een weigering op **Toegang tot het netwerk** blokkeert hem.

Andere shellopdrachten stuiten op een zachtere poort. De `bash`-tool van de
harness en, via een hook, de `Bash`-tool van Claude Code delen elke
opdrachtregel in en raadplegen de regel waaronder die valt: `git commit`,
`merge`, `rebase`, `cherry-pick`, `revert` en `am` zijn **Een commit maken**;
`gh pr create` is **Een pull request openen**; `gh pr merge`, `review`,
`comment` en `close` zijn **Een pull request bijwerken of samenvoegen**;
`gh issue create`, `edit`, `comment` en `close` zijn **Naar een externe tracker
schrijven**; pakketinstallaties zijn **Een pakket installeren**; `curl` en
`wget` zijn **Toegang tot het netwerk**. Schrijven naar GitHub vanuit de shell is de uitzondering: `gh pr create`, `gh pr comment`, `gh pr edit`, `gh pr merge` en schrijfacties met `gh issue` werken niet in een run, waarvan het token alleen kan lezen, en de agent wordt verwezen naar de tools van Control Center, die deze regels raadplegen. Dit herkent de gebruikelijke schrijfwijze
van een actie, en een agent die er een wil verbergen (`eval`, een scriptbestand,
een directe API-aanroep) kan dat. Pushes zijn er niet van afhankelijk.

Elk GitHub-token dat een run krijgt, is dubbel begrensd: tot één repository, en
tot wat het verantwoordelijke lid (degene die het vroeg, anders de eigenaar van
de werkruimte) daar mag doen. Er zijn geen reserve-inloggegevens. Als er geen
token kan worden uitgegeven, vermeldt het commando dat erom vroeg waarom.

In een sandbox wordt geen ticketing-API-sleutel gezet. Agenten schrijven tickets
via de MCP-tools van Control Center, die **Naar een externe tracker schrijven**
raadplegen.

De regel **Toegang tot het netwerk** wordt één keer gelezen, wanneer de run
start. Het netwerk van een sandbox staat aan of uit, dus weigeren zet het uit,
terwijl toestaan en eerst vragen het aan laten; de tools `web_fetch` en
`web_search` van de harness blijven bij elke aanroep vragen. De handles voor de
inloggegevens van de run worden vrijgegeven wanneer de run wordt afgebroken. De
tokens erachter worden per lid en repository gedeeld en verlopen binnen ongeveer
een uur; een lid dat zich afmeldt bij GitHub of de werkruimte verlaat, laat in
één keer elk token vervallen dat namens hem is uitgegeven.

## Repositories die een agent alleen kan lezen

Een agentrun mag alleen de checkouts wijzigen van repositories waarop de persoon voor wie hij handelt de [schrijfgrant](/nl-NL/handleiding/concepten/autorisatie/#code-wijzigen-vereist-de-schrijfgrant) heeft. Werkruimtebeheerders hebben die op elke gekoppelde repository. Een run waar niemand om heeft gevraagd, zoals een schema of andere automatisering, wordt beoordeeld door dezelfde verantwoordelijke persoon waaraan zijn automatiseringstoken is gebonden.

In een space met een repository die die persoon alleen kan lezen, kan de agent die repository nog steeds lezen en doorzoeken, maar kan hij de bestanden ervan niet wijzigen. Zijn bestandstools weigeren met een melding die begint met `<repo> is read-only for this run` en zegt dat het wijzigen van de checkout de schrijfgrant vereist, die de persoon voor wie de run handelt niet heeft, en dat een werkruimtebeheerder die kan toekennen. Binnen een sandbox is de checkout voor elk proces alleen-lezen, dus een shellcommando dat daar schrijft mislukt met "Operation not permitted". Dat geldt ook voor `git commit` en een build of test die zijn uitvoer binnen de checkout schrijft. Repositories die de persoon wel kan schrijven, werken zoals gewoonlijk, dus beheerders, en wie schrijftoegang heeft tot elke repository van de space, zien geen verschil.

Dit wordt één keer beslist, wanneer de run start. Een wijziging van een grant werkt pas bij de volgende run van de agent, en dat geldt ook voor een repository die tijdens een run aan de space wordt toegevoegd.

Waar de serverbeheerder de sandbox heeft uitgezet, worden alleen de bestandstools van de agent zelf en de schrijftools van Claude Code geweigerd, en shellcommando's kunnen de checkout nog steeds wijzigen. Er kan in beide gevallen niets zonder de schrijfgrant worden gepusht, omdat elke push tegen die grant wordt gecontroleerd. Welke processen de sandbox per platform beperkt, staat in [Sandboxbackends](/nl-NL/handleiding/referentie/sandboxbackends/).

## Wat de sandbox toevoegt en waar hij stopt

De enum `SandboxBackend` heeft drie waarden — `native` (Seatbelt op macOS,
bubblewrap op Linux en WSL2), `none` en `microvm`. Het omhullen van
agentopdrachten gebruikt alleen de eerste twee: `microvm` is de backend met een
omhulde VM voor interactieve terminals en rigs, geen stille upgrade van een
`bash`-wrap. Als je de native vorm begrijpt, weet je wat je wint waar er een is
bevestigd en wat die je nooit had kunnen geven.

`cc_server` probeert de host één keer bij het opstarten en voorziet, waar een
backend antwoordt, beide aansluitpunten die het dispatchpad heeft, omdat de
transporten er geen delen. Het eerste (`SandboxPort`) omhult de Claude Code CLI.
Het tweede (`SandboxManager`) omhult ACP-adapters en de `bash`-tool van de
ingebouwde harness. Slechts één ervan voeden zou de andere ongehuld laten
starten, en dat gebeurde vroeger ook. Onder `--sandbox off` starten ze allemaal ongehuld; op een host zonder backend starten alleen de runs van de eigenaar, ook ongehuld. De server zegt op zijn opstartregel in welk geval je zit. ACP en de `bash` van de harness saneren de
omgeving nog steeds; Claude Code via `NoSandboxAdapter` erft de omgeving van de
host.

De door de server gehoste terminal opent de hostshell alleen voor de [eigenaar](/nl-NL/handleiding/concepten/autorisatie/#de-serverbeheerder) van de server. Iedereen anders krijgt een gesandboxde terminal, met de beperkingen van een agent, in de eigen mappen van de werkruimte. Alleen wie een terminal heeft geopend, kan erin typen, hem lezen of sluiten.

Op Linux bouwt `bubblewrap` een mount-namespace, dus ziet de agent echt alleen
wat erin is gebonden. Op macOS past `sandbox-exec` een Seatbelt-profiel toe dat
**standaard toestaat** — een profiel dat standaard alles weigert, maakt een
interactieve shell onbruikbaar, omdat het aantal dyld-, XPC- en Mach-aanroepen om
te enumereren onpraktisch is. Het macOS-profiel begint daarom bij `(allow default)`
en haalt daar weigeringen uit: het lezen van geheime paden, een
schrijfbeleid dat op weigeren wordt gezet met expliciete toestemmingen
daarbovenop, blokkering van unlink op elk geweigerd pad en zijn voorouders zodat
een rename een schrijfweigering niet kan omzeilen, exec-weigeringen voor altijd
gevaarlijke binaries en voor alles wat naar een beschrijfbare map is gekopieerd,
en een netwerk dat beperkt blijft tot de loopback-proxypoorten plus DNS. Toolchain-installaties onder je thuismap (pnpm via corepack, node-versiebeheerders, Playwright-browsers, rustup, fvm, uv en vergelijkbare) blijven binnen dat exec-blok uitvoerbaar, zodat agents ze zonder omwegen kunnen gebruiken. De altijd-gevaarlijke weigeringen blijven er binnen wel van kracht. Elke sessie krijgt bovendien een eigen privé-`TMPDIR`. Dat is de enige tijdelijke map waarin de agent zelf gebouwde programma's mag uitvoeren of Unix-sockets mag openen.

Twee extra beschermingen gelden in elke modus. Een sandbox kan geen commando toevoegen, vervangen, verwijderen of hernoemen in de mappen waaruit de server programma's start (elke map op zijn `PATH` en de gebruikelijke per-gebruiker-toolmappen), dus een gesandboxde run kan geen programma plaatsen dat de server later buiten de sandbox start. Globale installaties en wisselingen van de standaardversie vanuit een run mislukken daarom met "Operation not permitted", terwijl installaties binnen het project en `npx`-achtige runs blijven werken; installeer globale tools op de server zelf en start hem opnieuw. En elk thuispad dat een sandbox niet kan lezen, kan hij ook niet schrijven, waarbij de opstartbestanden van de shell en de sessie van de servergebruiker nooit schrijfbaar zijn. Details en platformgrenzen staan in [De opdrachtmappen van de server](/nl-NL/handleiding/referentie/sandboxbackends/#de-commandomappen-van-de-server).

Een tool-sandbox van een run hoort bij die run en wordt vrijgegeven wanneer hij eindigt. Language servers starten opnieuw bij elke gesandboxde run. Een debugsessie behoudt zijn sandbox over de beurten heen tot de sessie eindigt, hooguit 30 minuten.

De praktische consequentie: op Linux wordt het beeld dat de agent van het
bestandssysteem heeft smaller; op macOS kan de agent nog steeds het grootste deel
van de host _lezen_ en worden je geregistreerde checkouts beschermd door
expliciete schrijf- en renameweigeringen in plaats van door onzichtbaarheid.
Beide zijn isolatie op namespaceniveau, geen kernelbeveiligingsgrens — de backends
zeggen dat zelf in hun eigen beschrijving van hun mogelijkheden.

De set bind-mounts is waar de grens tussen agents wordt getrokken.
Overlay-dispatch (Claude Code en ACP) mount maximaal vier paden, per run bepaald:
de overlay-werkmap van de agent read-write, de configuratiemap van de agent
read-only, de gedeelde `repos/`-map van het gesprek read-write als die bestaat,
en de bijlagenmap van de ruimte read-only als die bestaat. De map van een
zusteragent wordt nooit gemount. De `bash`-wrap van de harness is smaller: die
bind-mount alleen de werkmap van de run. Dat is dezelfde vorm die de in-process
padcontrole van de harness in software afdwingt, dus de twee komen overeen — maar
alleen de padcontrole dekt de eigen bestandstools van de harness, die nooit een
mount-namespace bereiken.

Je geregistreerde checkouts komen daar bovenop in de deny-write-set, in elke
modus en op alle drie de omhulde paden (Claude Code, ACP, `bash` van de harness),
en elke regel wordt in zowel zijn letterlijke als zijn symlink-opgeloste spelling
uitgevaardigd. De tweede spelling is geen luxe:
de kernel matcht een weigeringsregel
tegen het opgeloste pad en macOS maakt herleiding het gewone geval in plaats van
het exotische — `/tmp` is in werkelijkheid `/private/tmp`, `/var/folders/…` is in
werkelijkheid `/private/var/folders/…` — dus een checkout die via een van beide
werd bereikt, zou beschrijfbaar zijn geweest terwijl het profiel het leek te
verbieden.

Netwerk is onder een sandbox een **domein**-allowlist per sessie, afgedwongen
door in-process loopbackproxies. Uitgaand verkeer is standaard geweigerd: staat
het netwerk uit, dan starten de proxies wel, maar is hun allowlist leeg, dus
wordt elke uitgaande verbinding geweigerd. Staat het aan, dan bouwt de resolver
de allowlist uit een samengestelde basis — LLM-API-providers, githosting,
pakketregisters, de modelcatalogus — plus de domeinen van GitHub, en matcht hij
de doelhost van elke verbinding daartegen. Jokers werken (`*.example.com` matcht
subdomeinen, niet het hoofddomein). Een aparte lijst die altijd geweigerd wordt,
wint van de allowlist en dekt cloudmetadata-eindpunten en telemetrie-sinks. Wat
_niet_ configureerbaar is, is de lijst zelf: de spec draagt een veld
`egressAllowlist` voor extra domeinen, maar niets in het dispatchpad vult dat,
dus in de praktijk krijgt elke run de basis plus GitHub en niets meer.

Weigeringen zijn op macOS waarneembaar: een monitor tapt het systeemlogboek af op
Sandbox-weigeringen, filtert bekende ruis, dedupliceert herhaalstormen en brengt
elke weigering naar buiten als een `SandboxViolation` die noemt wat werd geprobeerd en wat werd tegengehouden. Op Linux parseert het wrap-pad
stderr op `EPERM`, `Operation not permitted` en `Permission denied` en zendt
hetzelfde gebeurtenistype uit — er is geen tap op het systeemlogboek. Die komen
binnen op de eigen gebeurtenisstroom van de run, dus een geweigerde
systeemaanroep verschijnt in het transcript in plaats van alleen in een log. De
telemetrie bestaat alleen zolang een native sandbox het proces daadwerkelijk
omhult — op een host zonder backend valt er niets waar te nemen. Ze staat ook los van de beveiligingen: een schending komt van een geweigerde systeemaanroep, nooit van het opzoeken van een regel.

## Bevestigingen komen van de beveiligingen, niet van de sandbox

De sandbox heeft geen goedkeuringspad. Hij start, voert uit, zendt gebeurtenissen
uit en breekt af; er is nergens in hem ruimte voor een mens die een vraag
beantwoordt. Wanneer je een bevestiging ziet in een ruimte — keur deze push goed,
keur deze verwijdering goed — dan is die opgeworpen door de beveiligingsengine
(of het opdrachtbeleid van de harness) _voordat_ de actie de runtime überhaupt
bereikte.

Deze volgorde is bewust. Een goedkeuring die na de systeemaanroep plaatsvond, zou
een auditregistratie zijn, geen poort. Daarom ook zit de fail-closed-regel in de
beveiligingen: zonder verbonden goedkeurder wordt de beslissing genomen voordat
er iets draait, en die is negatief.
