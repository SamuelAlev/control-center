Control Center beantwoordt twee autorisatievragen, en die zijn wezenlijk
verschillend. **“Mag deze persoon deze operatie aanroepen?”** gaat over mensen,
rollen en repositories. **“Mag deze agent dit effect veroorzaken?”** gaat over
acties, argumenten en impactbereik — die vraag staat bij
[Beveiligingen](/nl-NL/handleiding/concepten/beveiligingen/).

Deze pagina gaat over de eerste vraag, plus het spoor dat beide achterlaten.

## Eén beslissingspunt

Elke autorisatiebeslissing aan de menselijke kant verloopt via één enkele
functie:

```
can(principal, permission, resource) → allow | deny + why
```

Een **permissie** heeft de vorm `<domain>:<tier>` — `tickets:write`,
`members:administer`, `repos:read`. De catalogus is **afgeleid**, niet met de
hand geschreven: hij wordt berekend uit het operatieoppervlak zelf (het
naamvoorvoegsel van de op geeft het domein, de minimumrol die de op al
afdwingt geeft het niveau), zodat alle ~550 operaties een permissie dragen
zonder dat iemand er een intypt.

Die afleiding is de eigenschap die het waard is om te beschermen. Het betekent
dat een NIEUWE operatie standaard achter een poort zit — het faalpatroon van
een met de hand geannoteerd model is dat iemand iets vergeet, en wat diegene
vergeet, is juist de poort. Een ratchet-test legt de resulterende set domeinen
vast, zodat een operatie onder een nieuw voorvoegsel toevoegen een
naamgevingsbeslissing is die een mens neemt, geen ongeluk.

De vier niveaus vallen exact samen met de ingebouwde rollen:

| Niveau | Minimumrol | Voorbeeld |
|---|---|---|
| `read` | Gast | `tickets:read` |
| `write` | Lid | `tickets:write` |
| `administer` | Beheerder | `members:administer` |
| `own` | Eigenaar | `workspace:own` |

## Rollen

Vijf ingebouwde rollen — **Eigenaar, Beheerder, Lid, Kijker, Gast** — zijn
voorinstellingen boven op die catalogus. Eigenaarschap is één plek per
werkruimte, die expliciet wordt overgedragen met **Eigenaarschap overdragen**
(een eigenaar die vertrekt, is anders niet te verwijderen: SCIM-deprovisionering
weigert elke eigenaar van een werkruimte — draag eerst over).

**Aangepaste rollen zijn subtractief.** Een aangepaste rol noemt een
basisvoorinstelling (`admin`, `member`, `viewer` of `guest` — nooit `owner`) en
een set permissies die daarvan WORDEN VERWIJDERD — “admin, maar kan geen leden
beheren”. Hij kan nooit meer toekennen dan zijn basis, en dat is precies wat ze
veilig maakt om in een bestaande installatie te introduceren: elke bestaande
controle blijft een betrouwbare bovengrens. Leden hebben ze als `custom:<id>`,
en een client die te oud is om die waarde te begrijpen, valt terug op gast in
plaats van te gokken.

Onder de rollen zitten de **verleningen per repository** (`none` / `read` /
`review` / `write`, zie [Code wijzigen vereist de schrijfgrant](#code-wijzigen-vereist-de-schrijfgrant)): lidmaatschap van een werkruimte geeft nooit stilzwijgend
meer rechten dan de codehost. Elk oppervlak dat code toont, controleert ze —
ook de oppervlakken die zijdelings bij de code komen, zoals een terminal of een
editorsessie die op de worktree van een ruimte is geopend.

## Code volgt de codehost

Een grant alleen opent de code van een repository niet. Om de bestanden, diffs
of zoekresultaten te zien, of om een terminal erop te openen, heeft een lid de
Control Center-grant **en** moet zijn eigen forge-aanmelding de repository kunnen
lezen. Werkruimtebeheerders zijn niet vrijgesteld; de serverbeheerder wel, omdat
de checkout op zijn machine staat. Een repository zonder forge-remote heeft alleen
de grant nodig.

- Wanneer een beheerder een repository geeft aan iemand wiens forge-account die
  niet kan lezen, wordt de grant opgeslagen en ziet de beheerder een waarschuwing.
- Wanneer de forge niet bereikbaar is om het te controleren, is het antwoord nee,
  nooit een gok: de persoon ziet "Je GitHub-toegang kon niet worden bevestigd. Probeer
  het opnieuw." (met de naam van zijn forge) en probeert het later opnieuw.
- Pull requests en alles wat daaruit is gemaakt, volgen dezelfde regel.

### Code wijzigen vereist de schrijfgrant

Een repositorygrant heeft drie niveaus, en elk niveau omvat het vorige:

- **read**: de bestanden, diffs en zoekresultaten van de repository zien, mits je eigen forge-aanmelding die ook kan lezen.
- **review**: lezen, plus goedkeuren, wijzigingen aanvragen en de andere reviewacties op de pull requests.
- **write**: review, plus code wijzigen en agentruns aansturen die naar de repository schrijven. Code wijzigen omvat het opslaan of terugzetten van bestanden in de editor, een worktree synchroniseren met de head van zijn pull request, committen en pushen, een branch publiceren, en de stackacties die een deel afsnijden, uitchecken of publiceren.

Elke push die voor een persoon wordt gedaan, door hemzelf of door een agentrun die hij heeft gevraagd, controleert zijn schrijfgrant op die repository op het moment van de push, bij GitHub, GitLab en Bitbucket gelijk. Het publiceren van een stack controleert elke repository in de stack voordat er een van wordt gepusht.

Een weigering noemt de grant die ontbreekt. Zonder leestoegang toont de app "Je hebt geen leestoegang tot deze repository. Een werkruimtebeheerder kan die toekennen." Met lezen maar zonder schrijven staat er "Je kunt deze repository lezen maar niet wijzigen. Een werkruimtebeheerder kan schrijftoegang toekennen."

### Ruimtes volgen hun repositories

Wat agents over code hebben geschreven, volgt de code. De inhoud van een ruimte
(haar berichten, transcripties en toolweergave, zoekresultaten, runlogs, todo's,
activiteit en meldingen) draagt de code van de repositories waarmee ze werkt, dus
een ruimte opent alleen voor een lid dat een leesgrant heeft op, en wiens eigen
forge-aanmelding kan lezen, elke repository die de ruimte gebruikt. Dat zijn de
repositories die ervoor zijn geselecteerd, of alle repositories van de werkruimte
wanneer de ruimte geen selectie heeft vastgelegd. Een ruimte die zonder
repositories is aangemaakt, is open voor elk lid.

Een ruimte die iemand niet kan openen, wordt voor hem nergens getoond, ook niet in
zoekopdrachten, runlogs, todo's, activiteit en meldingen. Werkruimtebeheerders
hebben elke grant, maar zijn niet vrijgesteld van het forge-deel; de serverbeheerder
wel.

Maak voor een gesprek dat iedereen moet kunnen lezen de ruimte zonder repositories,
of alleen met repositories die iedereen kan lezen.

## De serverbeheerder

De persoon die de server heeft ingesteld, is de **eigenaar**. De server legt dat
één keer vast, bij de eerste start, en niets dat via het netwerk binnenkomt,
verandert dat. Een werkruimtebeheerder, of een werkruimte-eigenaar, is niet de
serverbeheerder: iedereen kan een werkruimte krijgen, maar de machine van de server
heeft één eigenaar.

**Er draait niets op de eigen machine van de server buiten een sandbox, tenzij de
serverbeheerder het heeft gestart of die soort hostuitvoering heeft goedgekeurd.**
Concreet kan alleen de serverbeheerder:

- Een werkruimte aanmaken. Iedereen anders ziet een scherm dat vraagt de eigenaar
  er een te laten aanmaken of een werkruimtebeheerder hem uit te nodigen.
- De hostshell openen in de op de server gehoste terminal. Iedereen anders krijgt
  een sandboxterminal, met de beperkingen van een agent, in de eigen mappen van de
  werkruimte.
- De ingebedde codeeditor openen. Die draait als de eigen gebruiker van de server,
  met zijn terminal, taken en extensies.
- Een pull request of de worktree van een gesprek in een native editor openen. De
  editor start op het scherm van de server zelf, als de gebruiker van de server.
- Een [omgeving](/nl-NL/handleiding/gidsen/omgevingen/)-definitie opslaan of goedkeuren die
  iets op de host uitvoert: plaatsing op de host, een controle die een opdracht
  uitvoert, of een voorzien- of archiveertaak.
- Agents draaien op een server waarvan de machine geen sandbox heeft. Andermans
  runs worden daar geweigerd, tenzij de eigenaar de server met `--sandbox off` heeft
  gestart, wat de agents van elk lid onbeperkt uitvoert (zie
  [Agents op een host zonder sandbox](/nl-NL/handleiding/concepten/sandbox-en-beveiliging/#agents-op-een-host-zonder-sandbox)).
- Een repository-checkout koppelen die buiten de eigen opslag van de werkruimte ligt,
  een koppeling bevestigen die van vóór die regel dateert, en de mappen van de server
  doorbladeren bij het toevoegen van een repository (zie
  [Repository's toevoegen](/nl-NL/handleiding/gidsen/repos-toevoegen/)).
- Elk draaiend agentproces op de server zien en stoppen. Iedereen anders ziet en
  stopt alleen live agentruns in werkruimtes waar hij lid van is.
- Een eigen MCP-server toevoegen die een opdracht uitvoert op de machine van de server. Eigen servers van alle anderen worden via een URL bereikt (zie [Eigen servers](/nl-NL/handleiding/gidsen/mcp-server/#eigen-servers)).
- Een MCP-server van de werkruimte goedkeuren die een opdracht op de machine van
  de MCP-server uitvoert of het privénetwerk ervan bereikt (zie
  [Servers van de werkruimte](/nl-NL/handleiding/gidsen/mcp-server/#servers-van-de-werkruimte)).
- Het e-mailadres van een persoon bevestigen, zodat single sign-on het kan koppelen
  (zie [Een OpenID Connect-provider verbinden](/nl-NL/handleiding/gidsen/sso-oidc/#hoe-inlogs-bestaande-accounts-koppelen)).
- Installatiebrede instellingen wijzigen: SSO, inloggegevens van providers, het
  MCP-endpoint en zijn token, modelbeheer, Connect en back-ups van de hele
  installatie. Deze operaties verklaren **serverautoriteit** en worden voor iedereen
  anders geweigerd.

Er is met opzet één operatoridentiteit en één definitie daarvan.

## Het auditlogboek

Elke autorisatiebeslissing — **toestaan en weigeren** — wordt toegevoegd aan
een per werkruimte bijgehouden auditlogboek dat met hashes is geketend.

Een logboek met alleen weigeringen beantwoordt de vraag “wat hebben we
geblokkeerd?”, maar niet “wat heeft deze agent werkelijk gedaan, en wie heeft
dat geautoriseerd?” — en dat is de vraag waarmee een incidentonderzoek begint.
Elke vermelding legt daarom de volledige attributieketen vast: de handelende
principal, de mens namens wie die handelde, de delegatie waarlangs die is
binnengekomen, de actie en de argumenten daarvan (als digest), de beslissing, en
**de regel die de beslissing nam**.

De vermeldingen zijn geketend: de hash van elke vermelding dekt die van de
vorige, dus het bewerken, verwijderen of herordenen van een rij breekt elke
hash daarna. **Keten verifiëren** leidt het geheel opnieuw af en noemt de eerste
schakel die niet klopt. Een auditlog dat je niet kunt controleren, is een log;
een dat je opnieuw kunt afleiden, is bewijs.

Twee gevolgen die je moet kennen:

- De audittabel is **uitgezonderd van opschoning op basis van leeftijd**. Een
  hashketen kan niet in het midden worden ingekort. Bewaren gebeurt door te
  exporteren en daarna af te kappen, en het afkappen laat een checkpoint achter
  met de eindhash van het verwijderde segment, zodat wat overblijft nog steeds
  tot aan het begin verifieert.
- Het staat **naast** de activiteitentijdlijn, niet erbovenop. De tijdlijn laat
  zien wat mensen deden; dit laat zien wat werd geautoriseerd en geweigerd. Een
  gedeelde correlatie-id leest één aanroep in beide.

Het wordt geëxporteerd als JSON met newlines als scheidingsteken en kan naar een
SIEM streamen (Splunk, Elastic, Sentinel — een HTTP-endpoint met een
bearer-token). Streamen is met opzet best effort: een SIEM die platligt, mag
nooit de tool-aanroep van een agent blokkeren, en de duurzame, verifieerbare
kopie staat hoe dan ook op schijf.

## Sessies

Een installatie kan een **maximale sessieleeftijd** en een
**inactiviteitstime-out** instellen. Beide worden afgedwongen bij de controle
van de apparaatreferenties waar elke geauthenticeerde route doorheen gaat — een
sessiegrens die een client zou kunnen negeren, beantwoordt een vragenlijst, geen
aanvaller. Een installatie kan ook SSO verplicht stellen, wat het handmatig
koppelen van nieuwe apparaten uitschakelt (met een waarborg tegen
buitensluiting: de verplichting wordt geweigerd zolang er geen werkende
SSO-verbinding bestaat).

## Wat dit niet is

- **Geen ACL's per object.** Er is met opzet geen permissie per ticket of per
  bericht. Scheiding op repositoryniveau is waar teams echt om vragen, en die
  bestaat; delen per object is een combinatorisch oppervlak zonder aangetoonde
  vraag hier.
- **Geen beleidsengine die je in een DSL configureert.** Het vocabulaire is met
  opzet gesloten, zodat het hele beleid kan worden weergegeven, uitgelegd en
  opgesomd.
- **Nergens anders afgedwongen dan op de server.** Controles aan de clientzijde
  bestaan alleen om te voorkomen dat een bedieningselement wordt aangeboden dat
  geweigerd zou worden. De gezaghebbende beslissing is altijd die van de server.
