Deze gids laat zien waar elk inloggegeven dat Control Center gebruikt wordt
bewaard en hoe je het wijzigt.

**Er wordt niets opgeslagen op de machine waarop je typt.** Elk inloggegeven
staat op de server; welk gegeven een bepaald verzoek beantwoordt, hangt af van
of er een mens achter zit.

| Inloggegeven                                 | Opgeslagen                                                      | Wie gebruikt het                                                    |
| -------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------- |
| Je forge-/ticketingaanmelding                | Het geheimenbestand van de server met modus 0600, op je gebruikers-id | Alles wat je doet: het PR-oppervlak, reviews, merges, je Linear-acties |
| De provider-apps van de server               | Hetzelfde bestand, plus `server_settings` voor de niet-geheime waarden | Mensen aanmelden, en tokens voor één repository voor agenten, pipelines en polling |
| De installatiesleutel voor Connect           | Hetzelfde bestand (`connect_install_key`)                        | Deze server identificeren bij Control Center Connect                 |
| Sleutels van modelproviders en OAuth-tokens  | De eigen opslag van de server voor inloggegevens                 | De ingebouwde adapter, voor elke werkruimte op de installatie        |
| Slack-botgegevens                            | `<dataDir>/<workspaceId>/chat_credentials/` op de server          | De chatbrug voor die werkruimte: de tokens van je eigen app, of de verzegelde machtiging van de gedeelde app |
| Inloggegevens van externe CLI's              | Wat die CLI ook gebruikt                                          | Claude Code, op de serverhost                                       |

## GitHub: je aanmelding, en tokens voor één repository

- **Die van jou**, via **Inloggen bij GitHub**. Elk verzoek dat *namens jou*
  wordt gedaan, gebruikt die, dus een review die voor jou wordt geplaatst, draagt
  je naam. Een ander lid kan hem niet gebruiken en meldt zich zelf aan. Er is
  geen GitHub-token om te plakken
- **Werk waarbij niemand typt** (agenten, pipelines, polling, botantwoorden)
  krijgt een token voor telkens één repository, uitgegeven via de GitHub App van
  de server of via Control Center Connect, en beperkt tot wat een
  verantwoordelijk lid daar mag doen. Het is nooit je volledige, doorgegeven
  aanmelding

Die van jou stel je in op de kaart **Codehosting** bij **Instellingen → Jij → Profiel**; de app van de server op **Provider-apps**
bij **Instellingen → Server → Single sign-on**. Zie
[GitHub-integratie instellen](/nl-NL/handleiding/gidsen/github-integratie/) en
[De GitHub App maken](/nl-NL/handleiding/gidsen/github-app/).

GitLab en Bitbucket nemen nog steeds een geplakt persoonlijk token, dat op
dezelfde manier wordt opgeslagen. Zie
[Een codehost verbinden](/nl-NL/handleiding/gidsen/codehost-verbinden/).

:::note[Er is ook een scherm dat alleen via de URL bereikbaar is]
`/workspaces/<workspaceId>/api-keys` rendert dezelfde kaarten als de
eerste stap van onboarding. Het heeft **nergens in de UI een navigatie-item**;
je bereikt het alleen door de URL te typen. Gebruik in plaats daarvan
Instellingen → Jij → Profiel voor je eigen aanmeldingen, en Instellingen → Werkruimte → Integraties voor de ticketingleverancier.
:::

## Sleutels voor modelproviders instellen

De ingebouwde adapter authenticeert providers zelf en die inloggegevens staan
op de server.

1. Ga naar **Instellingen → Server → Modelaanbieders**
2. Scroll naar **Providers en modellen**
3. Verbind de provider — OAuth via de browser voor OpenAI, Codex, Cursor en
   Kimi Code; een API-sleutel voor Anthropic en de rest

Zie [Adapters en modellen beheren](/nl-NL/handleiding/gidsen/adapters/) voor de
volledige lijst en voor het toevoegen van een aangepast endpoint.

Deze inloggegevens zijn **host-globaal**: één sleutel bedient elke werkruimte op
de installatie. OAuth-tokens worden vernieuwd voordat ze verlopen.

Claude Code meldt zich aan via **Claude Code-accounts** onder **Instellingen → Server → Modelproviders**: elk account krijgt zijn eigen configuratiemap op de server, en je voert daar het commando `claude auth login` uit dat de app je toont.

Het venster **Omgevingsvariabelen** per adapter lijkt een plek om een sleutel
voor een van hen neer te zetten, maar dat is het niet: het schrijft naar je
apparaat, terwijl de server zijn eigen kopie leest en niets de twee overbrugt.
Zie [Adapters en modellen beheren](/nl-NL/handleiding/gidsen/adapters/).

## Een ticketingprovider verbinden

De kaart **Tickets** bij **Instellingen → Werkruimte → Integraties** bevat de kant van de werkruimte: bij welke leverancier je tickets staan, en wie
Control Center is wanneer het daar zelfstandig werkt. Als je **Lokaal** kiest, verdwijnen
de Linear-rijen — lokale tickets staan in de eigen database van deze server en er
valt niets te authenticeren.

Linear heeft twee aanmeldingen en geen geplakte sleutel: **Linear** is die van
jou, voor wat jij doet, en staat op **Instellingen → Jij → Profiel**; **Linear-automatisering** is de Control Center-app van
de werkruimte, verbonden door een beheerder op de kaart **Tickets**, voor ticketsynchronisatie,
pipelines en agenten. De server kan ook een **Service-API-sleutel**
(**Provider-apps**) bewaren voor werkruimtes zonder verbonden automatisering. In
de sandbox van een agent worden geen ticketinginloggegevens geïnjecteerd; agenten
schrijven tickets via de tools van Control Center, die de regel **Naar een
externe tracker schrijven** raadplegen. Zie
[Linear-integratie instellen](/nl-NL/handleiding/gidsen/linear-integratie/).

## Roteren of intrekken

- **Je GitHub-aanmelding**: klik op **Loskoppelen** en daarna opnieuw op
  **Inloggen bij GitHub**. Loskoppelen laat ook elk token vervallen dat de server
  namens jou heeft uitgegeven
- **Een GitLab- of Bitbucket-token**: klik op **Token bijwerken** en plak het
  nieuwe, en trek daarna het oude in bij de forge
- **De app van de server**: genereer een nieuwe privésleutel of een nieuw
  clientsecret op de providerpagina van de app, plak die in **Provider-apps** en
  klik op **Testen**
- **De installatiesleutel voor Connect**: de serverbeheerder drukt op
  **Sleutel vervangen** op de kaart **Control Center Connect**. Iedereen die
  zich via Connect heeft aangemeld, meldt zich opnieuw aan. Als een
  Connect-server niet bereikbaar is, verandert er niets en krijg je de optie
  **Toch vernieuwen**. Zie
  [De installatiesleutel vervangen](/nl-NL/handleiding/referentie/connect/#de-installatiesleutel-vervangen)
- **Een modelprovider**: meld je op zijn rij af (OAuth) of verwijder de sleutel,
  en maak daarna opnieuw verbinding
- **Slack**: plak voor je eigen app de tokens opnieuw in het verbindingsvenster.
  De gedeelde Control Center-app heeft geen token om te roteren: het bottoken
  wordt via Connect vernieuwd, en **Verbinding verbreken** trekt het in en
  verwijdert de bot uit Slack. Zie
  [Slack-integratie instellen](/nl-NL/handleiding/gidsen/slack-integratie/)

## Problemen oplossen

### Een GitLab- of Bitbucket-token werkt in `curl`, maar niet hier

Controleer de rij **Codehosting**. Staat er "Niet verbonden" of wordt je gevraagd
opnieuw te verbinden, dan is je token niet opgeslagen of geweigerd. Voor
Bitbucket voer je je Atlassian-accountmailadres in samen met het API-token.

### Een GitLab- of Bitbucket-token wordt geaccepteerd, maar latere verzoeken mislukken

Het token wordt getest zoals het is opgeslagen, dus de rij noemt het account
dat erachter zit — maar alleen het account, niet de scopes. Een token met te
weinig scopes maakt verbinding en laat daarna afzonderlijke verzoeken
mislukken. Controleer de scopes en de vervaldatum ervan bij de forge.

### Een provider meldt dat aanmelden op deze server niet is ingesteld

De server heeft voor die provider geen eigen app en ook geen Control Center
Connect. De servereigenaar kiest er een in **Instellingen → Server → Single
sign-on**.
