Deze gids laat zien hoe je met Control Center werkt zonder GitHub te verlaten:
vraag een AI-review aan vanaf de PR-pagina, stel de bot een vraag in een
opmerking, en houd het gesprek gaande in zijn reviewthreads.

Antwoorden komen via de GitHub-route van de werkruimte: de eigen
[GitHub App](/nl-NL/handleiding/gidsen/github-app/) van je server, of de gedeelde
App van Control Center via Connect. Er wordt niets nieuws geregistreerd, en niets hoeft vanaf het internet bereikbaar te
zijn: de server ontdekt door te pollen wat er op GitHub is gezegd, dus een
laptop achter NAT gedraagt zich precies als een openbare deployment.

## Vereisten

- De werkruimte heeft een GitHub-route: de eigen GitHub App van de server of
  Connect, met de app [geïnstalleerd](/nl-NL/handleiding/gidsen/github-app/#installeren-waar-je-repositorys-staan)
  op het account dat eigenaar is van de repository. Een eigen app heeft
  **Pull requests** en **Issues** met lezen en schrijven nodig, wat **Mijn
  GitHub-app maken** al toekent
- De repository is aan een werkruimte in Control Center gekoppeld
- Je bent op deze server [aangemeld bij GitHub](/nl-NL/handleiding/gidsen/github-integratie/)
  en je mag naar de repository pushen
- Geen webhook-URL, geen tunnel, geen callback — aan de netwerkkant valt er
  niets te configureren

## De naam van je bot vinden

Vermeld `@usectrl`, het eigen GitHub-account van Control Center. Het is de enige trigger: de eigen login van de app vermelden doet niets. De GitHub-route van je werkruimte verwerkt het verzoek nog steeds en plaatst de antwoorden. Je hebt geen inloggegevens voor het account `usectrl` nodig.

## Een review aanvragen vanuit GitHub

Twee manieren, die beide dezelfde meegeleverde `pr_review`-pipeline starten als
de knop **Ask AI**:

- **Voeg het label `ai-review` toe** aan de PR. Dichter bij het toewijzen van de bot als reviewer komt GitHub niet — appaccounts kunnen de native plek van een
  aangevraagde reviewer niet bezetten. Je account reageert op de PR met 👀 en de
  review start in Control Center; er wordt geen opmerking geplaatst
- **Plaats `@usectrl review`** (of alleen `@usectrl`) als opmerking in het
  PR-gesprek. Er verschijnt 👀 op je opmerking, en daarna meldt een antwoord dat
  de review is gestart (of dat er al een loopt)

De reviewers werken in de reviewruimte van de PR; lees en publiceer de
bevindingen zoals in [AI-gestuurde review gebruiken](/nl-NL/handleiding/gidsen/ai-review/).
Terug naar GitHub publiceren blijft een beslissing die je in Control Center
neemt — een review vanuit GitHub starten publiceert op zichzelf niets naar
GitHub.

Het label vuurt één keer per PR: het toevoegen is de aanvraag, en het wordt niet
opnieuw geactiveerd wanneer je het verwijdert en weer toevoegt. Wil je een review
nog eens laten lopen — na een push, bijvoorbeeld — vermeld dan de bot.

## Een vraag stellen

Plaats een opmerking in het PR-gesprek:

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

Wat er gebeurt, in volgorde:

1. Er verschijnt 👀 op je opmerking, vanaf je eigen account, zodat je weet dat
   de opmerking is gezien
2. De vraag wordt in de reviewruimte van de PR geplaatst **als jou** — dezelfde
   attributie als wanneer je hem in Control Center had getypt
3. Een agent antwoordt in de ruimte, en het antwoord wordt terug op de PR
   geplaatst. Elk antwoord begint met `**Control Center** (for @your-login):`

Een vraag op een PR zonder review wekt de CEO-agent van de werkruimte; zodra er
een review is gelopen, antwoordt de agent die het laatst sprak, zodat
vervolgvragen bij degene met de context terechtkomen.

## Vervolgen in een reviewthread

Antwoord binnen een inline reviewthread waar de bot deel van uitmaakt — een
diff-opmerking die hij achterliet, of een antwoord dat hij in die thread
plaatste. Een vermelding is niet nodig; de thread **is** de adressering:

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

Meerdere beurten werken hetzelfde: elk antwoord is een nieuwe vraag in hetzelfde
gesprek, met de reviewruimte als context, en het antwoord komt terug in de
thread.

Een vervolgvraag op de tijdlijn van het PR-gesprek is een nieuwe opmerking op
het hoogste niveau en heeft daarom nog steeds een @-vermelding nodig.

## Met wie de bot praat

De server herleidt de auteur van een opmerking, of degene die het label
`ai-review` toevoegde, voordat hij iets doet:

- **Het GitHub-account moet op deze server zijn aangemeld.** Er wordt gematcht op
  het numerieke account-id van GitHub, nooit op de login. Meld je aan via
  **Instellingen → Jij → Profiel → Codehosting**
- **Die persoon moet lid zijn met een schrijfrol** (`member`, `admin` of
  `owner`) in de werkruimte die de repository koppelt
- **Die persoon moet op GitHub naar de repository kunnen pushen.** Antwoorden
  gebruiken een token dat beperkt is tot de toegang van die persoon, dus iemand
  die alleen kan lezen, krijgt geen antwoord

Alle anderen worden stil genegeerd: er wordt niets geplaatst, en hun woorden
komen nooit de werkruimte binnen. Opmerkingen van bots, en de eigen antwoorden van
Control Center, worden nooit als vragen behandeld.

### Twee servers, één PR

Met de 👀 spreken servers ook af wie antwoordt. Hij wordt toegevoegd met de eigen
aanmelding van de auteur, en GitHub vertelt de server of die reactie nieuw is. Ben
je aangemeld op twee Control Center-servers die allebei de repository koppelen,
dan antwoordt de eerste die reageert en blijft de andere stil. Hetzelfde geldt
voor het label.

## Wat je kunt verwachten

| Onderdeel                | Gedrag                                                                   |
| ------------------------ | ------------------------------------------------------------------------ |
| Bevestiging              | 👀 vanaf je account op de opmerking (of op de PR, voor het label), binnen één pollronde |
| Antwoorden               | Geplaatst op de plek waar de vraag is gesteld, beginnend met `**Control Center** (for @your-login):`. Geschreven door de bot van de app. Op de gedeelde Connect-app is een antwoord binnen een reviewthread geschreven door je eigen account, tenzij de Connect-beheerder deze installatie heeft opgenomen |
| Attributie in de ruimte  | De vraag is van jou; de agent draait namens jou, onder de autonomie-instellingen van de ruimte |
| Reviews                  | Bevindingen belanden in de reviewruimte; publiceren naar GitHub is handmatig |

Een pollronde draait elke minuut bij een eigen app en controleert tot 25 pull
requests; via Connect draait hij elke twee minuten en controleert tot 10, omdat
die aanroepen het eigen GitHub-quotum van elk lid delen. Een werkruimte waarvan
het GitHub-quotum onder 15% ligt, wordt overgeslagen tot het hersteld is. De
latentie is de prijs voor het feit dat er helemaal geen inkomende netwerktoegang
nodig is. Er gaat niets verloren terwijl de server offline is — een opmerking die tijdens
downtime binnenkomt, wordt bij de volgende pollronde opgepikt.

## Problemen oplossen

**Er gebeurt niets bij een opmerking die de bot vermeldt.**

- Is de app **geïnstalleerd** op het account dat eigenaar is van de repo, en is
  de repo **gekoppeld** aan een werkruimte? Een niet-gekoppelde repo wordt
  overgeslagen voordat er iets wordt vastgelegd, dus later koppelen levert alsnog
- Ben je op deze server aangemeld bij GitHub, ben je lid met een schrijfrol, en
  mag je naar de repo pushen? De server negeert iedereen anders zonder te
  antwoorden
- Nog steeds niets? Het serverlogboek noemt de pollronde en de PR wanneer er iets
  misgaat; zoek naar `pr_conversation:` (de poller) en
  `github_pr_conversation:` (de brug)

**Het label start geen review.**

Het vuurt één keer per PR, en degene die het toevoegde doorloopt dezelfde
controles als de auteur van een opmerking. Als er al een review is gelopen, of het label is
toegevoegd voordat de server de PR ooit zag (de eerste pollronde registreert de
achterstand stil, in plaats van er een storm van te maken), vermeld dan in plaats
daarvan de bot — `@usectrl review` start er altijd een, tenzij er al een review
onderweg is.

**Het antwoord van de bot is nooit op GitHub aangekomen.**

Het antwoord zelf gaat nooit verloren — het staat in de reviewruimte van de PR in
Control Center. Een fout bij het plaatsen (GitHub plat, machtigingen gewijzigd)
wordt gelogd en het antwoord wordt niet opnieuw geprobeerd; vraag het opnieuw in
de thread als het belangrijk is.
