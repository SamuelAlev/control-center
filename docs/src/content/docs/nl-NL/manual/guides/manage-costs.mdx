Deze gids laat zien hoe je ziet wat agentruns kosten en hoe je een autonome run begrenst.

## Hoe kosten worden vastgelegd

Elke agentrun schrijft een run-log met zijn invoertokens, uitvoertokens, redeneertokens, tokens voor cachelezingen en cache-schrijfacties, geschatte kosten in centen en de kosten van eventuele subagenten die hij heeft gestart.

De prijzen komen uit de catalogus van models.dev. Die wordt alleen gebruikt om de modellenlijst te verrijken met prijs en contextvenster — nooit als bron van model-id's. Een model dat de catalogus niet kan beprijzen, registreert **$0**, en runs zonder kosten worden uitgesloten van de samenvatting **Gebruik en kosten**. Een lokaal Ollama-model toont dus helemaal geen uitgaven, al worden zijn tokentellingen nog steeds vastgelegd. Een abonnement met vast tarief (kimi-code, een Claude-abonnement) werkt hetzelfde, maar alleen wanneer de catalogus geen prijs heeft voor het bediende model; heeft hij die wel, dan worden de kosten van de run alsnog tegen die tarieven geschat. Bij een fallbackketen wordt de run beprijsd op basis van het model dat hem daadwerkelijk heeft bediend, niet het opgevraagde model.

## Zien wat je uitgeeft

### Observeerbaarheid → Overzicht

Je bereikt het via de voettekst van de zijbalk → **Observeerbaarheid**. Het tabblad **Gebruik** opent als eerste (tokentotalen over de hele levensduur); schakel over naar **Overzicht** — het tweede tabblad — voor het belangrijkste kostenoppervlak:

- Een tijdsbereikkiezer: laatste 24 uur, laatste 7 dagen, laatste 30 dagen of alles
- Facetfilters op agent, model, status en rol, als wegklikbare chips
- Een KPI-strook: totaal aantal runs, totale kosten, foutpercentage, cache-percentage, tokens per seconde, gemiddelde latentie en tijd tot het eerste token, elk met een verschil ten opzichte van de vorige periode (verborgen bij "Alles")
- Grafieken voor activiteit en kosten, plus een uitsplitsing **kosten per rol** die de uitgaven verdeelt over de hoofdagent, zijn subagenten en zijn adviseur
- Een tabel per agent, gesorteerd op kosten, met de eerste tien en een schakelaar om alles te tonen. Tik je op een rij, dan wordt elk ander oppervlak op die agent gefilterd
- Het fijnmazige run-log, dat voor een geselecteerde run een transcriptlade vastzet

:::note["Alles" is niet alles]
De runfeed abonneert zich op de 2000 meest recente run-logs van alle werkruimtes, en filtert die vervolgens op de actieve werkruimte. Op een drukke server met meerdere werkruimtes valt de oudere geschiedenis van een rustige werkruimte buiten dat venster.
:::

### Instellingen → Server → Modelaanbieders

De kaart **Gebruik en kosten** op deze pagina toont de in de afgelopen zeven dagen waargenomen uitgaven als één dollarbedrag, met een uitsplitsing per provider en, wanneer een provider die publiceert, de tijd totdat het volgende quotumvenster opnieuw begint.

### De runs van één agent

**Instellingen → Werkruimte → Agenten** → selecteer een agent → **Logboeken** vermeldt zijn runs met status, duur, begin- en eindtijd, PID en adapter. Dit tabblad toont **geen** kosten — gebruik daarvoor de tabel per agent in Observeerbaarheid → Overzicht.

## Een autonome run begrenzen

Twee slash-commando's, getypt in de composer van een ruimte, zijn de enige runs met een kostenplafond:

```
/goal ship the auth refactor --budget 20
/loop keep the flaky tests green
```

- Elk segment van een `/goal`- of `/loop`-run stopt wanneer de beprijsde uitgaven **500 cent ($5.00)** bereiken. Op 80% daarvan stuurt de lus het model eerst bij om af te ronden en een schone overdracht achter te laten, zodat hij niet midden in een taak sterft.
- Een heel duurzaam doel heeft een plafond van **5000 cent ($50.00)**, tenzij je `--budget <dollars>` meegeeft. De supervisor geeft het _resterende_ budget van het doel door aan elk segment, zodat een expliciet budget nooit met een heel segment wordt overschreden.
- `--days N` voegt een deadline in wandkloktijd toe en `--max N` een plafond op het aantal runs. Beide zijn optioneel; zonder hen wordt het doel alleen door kosten begrensd.
- Een doel dat tegen zijn grens aanloopt, stopt met `budgetExhausted` en kan alleen worden hervat door het budget te verhogen.

Omdat het plafond op prijzen is gebaseerd, bereikt een model dat de catalogus niet kan beprijzen het nooit. Zo'n run wordt in plaats daarvan begrensd door de doom-loopherhalingsbeveiliging, het opgeven van de supervisor na drie opeenvolgende fouten en jou.

Een bericht in een ruimte, een @-vermelding of een pipelinestap heeft geen kostenplafond. De run eindigt wanneer het model stopt, wanneer jij hem stopt of wanneer de doom-loopbeveiliging hem bijstuurt.

## Tokengebruik beperken

### Een lang gesprek compacteren

Typ `/compact` in de composer van de ruimte. Het commando wordt aan de clientkant onderschept en belandt nooit in het transcript; de server vouwt oudere geschiedenis samen tot een verankerde samenvatting en het gesprek gaat verder op de gecompacteerde context.

Compactie wordt geweigerd terwijl een agent midden in een beurt zit en wanneer er niets oud genoeg is om samen te vouwen. De ingebouwde harness compacteert ook zelf zodra de geschiedenis het contextvenster van het model nadert.

### Kies het inspanningsniveau bewust

De **Reasoning-inspanning** van een agent (Instellingen → Werkruimte → Agenten) biedt de niveaus die het geselecteerde model publiceert. Hogere niveaus verbruiken meer redeneertokens. Bewaar de hoogste niveaus voor werk dat ze nodig heeft.

### Kies het model per agent

Model is een veld per agent, dus een formatterings- of triage-agent kan op een goedkoop model draaien terwijl een architectuuragent op een duur model draait. Filter de tabel per agent in Observeerbaarheid → Overzicht op model om te zien welke combinatie je daadwerkelijk geld kost.

### Zoek runs met een onevenredig hoge tokentelling

Open het run-log in Overzicht (de 50 nieuwste gefilterde runs) en de transcriptlade bij alles wat ongewoon is. De gebruikelijke oorzaken zijn een te lange systeem-prompt of persona, context die gecompacteerd had moeten zijn en een taak die eigenlijk meerdere kleinere taken had moeten zijn.

## Wat er gebeurt als een budget buiten de normale weg wordt ingesteld

Voor de volledigheid: als `monthlyBudgetCents` of een budgetbeleid rechtstreeks naar een agentrij wordt geschreven:

- Budgetten worden **na** het afronden van een run geëvalueerd, niet vóór de dispatch. Een listener bij het afronden van de run vergelijkt de uitgaven van de agent van deze maand tot nu toe met zijn plafond.
- Het overschrijden van de zachte drempel (standaard 80%) legt een waarschuwingsincident vast en vuurt een `BudgetThresholdCrossed`-gebeurtenis af waaraan je een pipelinetrigger kunt hangen.
- Het uitputten van het budget legt een hard incident vast, vuurt dezelfde gebeurtenis af en zet de levenscyclusstatus van de agent op `paused`.
- Het pre-dispatchblok bestaat wel, maar wordt alleen geraadpleegd door de opruimer van verweesde runs en de reconciler van achtergebleven tickets wanneer die herstelwerkzaamheden inplannen — een normale dispatch bereikt het nooit, en niets op het dispatchpad controleert de gepauzeerde status. Het enige zichtbare signaal is de levenscyclusbadge in het organigram.
