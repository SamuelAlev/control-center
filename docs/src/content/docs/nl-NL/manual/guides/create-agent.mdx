Deze gids laat je zien hoe je een agent aan een werkruimte toevoegt en hem configureert tot hij echt kan draaien.

Elke werkruimte begint met vijf agents — een CEO plus `qa`, `architect`, `engineer` en `librarian` — dus je hebt meestal al agents voordat je er zelf een hebt geconfigureerd. De stappen hieronder gelden net zo goed voor een meegeleverde agent als voor een nieuwe.

## Voordat je begint

- Je bevindt je in een werkruimte. Het hele oppervlak staat onder **Instellingen → Werkruimte → Agenten** (`/settings/workspace/agents`).
- De agent heeft een backend nodig. Verbind een provider voor de ingebouwde harness onder **Instellingen → Server → Modelaanbieders**, of installeer de Claude Code CLI op de machine die `cc_server` host.
- Wil je dat de agent skills meedraagt, installeer ze dan eerst onder **Instellingen → Werkruimte → Vaardigheden**. Het agentformulier laat je alleen skills aan- en uitzetten die al in de werkruimte bestaan.

## De agent toevoegen

1. Open **Instellingen → Werkruimte → Agenten**.
2. Klik op **Nieuwe agent**.

Er is geen dialoogvenster en geen rollenkiezer. Er wordt meteen een agent met de naam “Naamloze agent” aangemaakt, die in het detailpaneel rechts wordt geselecteerd.

Je ziet “Naamloze agent” nu in de agentenlijst links, met het tabblad **Instellingen** van het detailpaneel open en een veld **Naam** met daarin “Naamloze agent”.

## De agent een naam geven

- **Naam** — de korte identificatie die in @-vermeldingen wordt gebruikt, bijvoorbeeld `alice`. Bij het parsen van vermeldingen matcht `@` gevolgd door woordtekens, dus een naam met een koppelteken, een punt of een spatie kan nooit worden vermeld.
- **Titel** — het leesbare label, bijvoorbeeld “Senior-ontwikkelaar”.
- **Systeem-prompt** — optionele extra instructies, geïnjecteerd als een sectie Agent instructions; ze vervangen de rest van de samengestelde prompt niet.

Klik onderaan het formulier op **Wijzigingen opslaan**. Elk veld op deze pagina wordt door die ene knop opgeslagen.

## Een adapter en een model geven

De vervolgkeuzelijst **Adapter** toont de runners die de serverhost daadwerkelijk heeft. De ingebouwde adapter wordt altijd gevonden (hij is de server). Claude Code verschijnt alleen wanneer zijn CLI op die host is gedetecteerd:

| Adapter                   | Backend                                     |
| ------------------------- | ------------------------------------------- |
| Control Center (built-in) | De in-process agentloop — geen externe CLI  |
| Claude Code               | `claude -p --output-format stream-json`     |

Alleen de ingebouwde adapter handhaaft modi, bijsturing, pauzeren/hervatten, afrondingscontracten en subagenten. Claude Code geeft je niets daarvan. Cursor, Codex en de andere modelproviders hangen aan de ingebouwde adapter, niet als afzonderlijke runners.

:::note[Een lege adapter betekent de ingebouwde lus]
Een agent waarvan de adapter niet is ingesteld, wordt gedispatcht naar **Control Center (built-in)**, de agentloop in de server, dus er hoeft niets op de host te worden geïnstalleerd. Is er ook geen model ingesteld, dan vraagt hij Anthropic om diens standaard, dus een volledig oningestelde agent draait alleen als je een Anthropic-account hebt verbonden. De meegeleverde specialisten komen zonder beide; stel ze allebei in bij elke agent die je wilt gebruiken.
:::

De vervolgkeuzelijst **Model** wordt bepaald door de adapter die je hebt gekozen. Voor de ingebouwde adapter komt de lijst rechtstreeks van de providers die je onder **Instellingen → Server → Modelaanbieders** hebt verbonden, dus een provider zonder opgeslagen inloggegevens draagt nul modellen bij.

## Skills toevoegen

**Vaardigheden** is een chipkiezer over de skillbundels die in deze werkruimte zijn geïnstalleerd. Tik op een chip om hem aan of uit te zetten; het vinkje markeert de geselecteerde chips. Heeft de werkruimte geen skills, dan lees je in het veld “No skills available. Create skills in Settings → Skills first.”

De eigen skills van een repo kies je hier niet. Een repo die ze meelevert (in `.agents/skills/`, `.claude/skills/` of `.opencode/skills/`) draagt ze automatisch bij aan de agent die in die repo werkt, en ze wisselen wanneer hij naar een andere verhuist — zie [Repo-gebonden skills](/nl-NL/handleiding/concepten/agentmodel/#repo-scoped-skills).

## De rapportagelijn en persona instellen

- **Rapporteert aan** — kies een andere agent op naam. Dit bouwt de rapportageboom die de knop **Organigram** in de paginakop toont. Het is niet de ledenlijst die een teamleider gebruikt bij het delegeren — die komt uit de leden van het team en hun skills.
- **Persona** — vrije tekst die toon en gedrag vormgeeft, bijvoorbeeld: “Geeft de voorkeur aan eenvoudige, leesbare oplossingen. Schrijft tests voor alle nieuwe code.”

## De run afstemmen

- **Reasoning-inspanning** — de opties komen uit de eigen gepubliceerde niveaus van het geselecteerde model: Low / Medium / High, plus Extra High bij modellen in OpenAI-stijl en Extra High + Max bij modellen in Claude-stijl. Het veld wordt volledig verborgen wanneer het geselecteerde model geen denkniveaus aangeeft, en anders staat het op de eigen standaard van het model.
- **Contextvenstergrootte** — vooraf ingevuld vanuit het contextvenster van het model telkens wanneer je van model wisselt, met chips waarmee je met één tik de modelstandaard, 200k, 500k en 1M kiest. Een waarde die je typt nadat je het model hebt gekozen, geldt tot de volgende modelwissel.
- **Stilte-time-out (minuten)** — beëindig een run na deze tijd zonder uitvoer. Laat het veld leeg om de standaard per modus te gebruiken.

## Machtigingen verlenen

Een agent heeft geen eigen machtigingsschakelaars. Wat hij mag pushen, openen, mergen of bereiken, leggen de actieregels vast onder **Instellingen → Werkruimte → Agentmachtigingen**, waar je een regel tot deze agent kunt beperken. Standaard vragen een push, een pull request, een review of merge en een schrijfactie naar een tracker het jou elk eerst, en is netwerktoegang toegestaan.

Het GitHub-token van de agent heeft altijd alleen leesrechten. Een push loopt via Control Center, dat de regel **Naar een remote pushen** raadpleegt voordat het hem doorstuurt. Zie [Sandboxbeleid configureren](/nl-NL/handleiding/gidsen/sandboxbeleid/) voor hoe elke regel een run bereikt.

:::note[Regels en de OS-sandbox zijn aparte lagen]
De regels bepalen wat een agent mag doen; de OS-sandbox begrenst waar zijn processen kunnen lezen, schrijven en verbinden. `cc_server` wikkelt agentruns in de sandbox van de host waar die bestaat — Windows heeft geen native backend, en Linux en WSL2 hebben `bwrap` en `socat` nodig. Zie [Sandbox en beveiliging](/nl-NL/handleiding/concepten/sandbox-en-beveiliging/) voor alle grenzen.
:::

## Controleren of hij draait

1. Open **Instellingen → Server → Modelaanbieders** en controleer dat de adapter die je hebt gekozen een geïnstalleerde versie meldt en niet “Niet gevonden”. Klik op **Vernieuwen** om de detectie opnieuw uit te voeren — de detectie draait op de machine die `cc_server` host, niet op de machine waarnaar je kijkt.
2. Open een ruimte met de agent en stuur hem een bericht, of @-vermeld hem in een bestaande ruimte.
3. Ga terug naar **Instellingen → Werkruimte → Agenten**, selecteer de agent en open het tabblad **Logboeken**. Er zou een run moeten verschijnen met een statusbadge, een duur, een starttijd en de adapter die hij heeft gebruikt. Met **Bekijken** open je de gebeurtenissenstroom van die run.

Verschijnt er helemaal geen run, doorloop dan [Een agent diagnosticeren](/nl-NL/handleiding/gidsen/agent-diagnosticeren/).

## Een agent verwijderen

Selecteer hem in de agentenlijst. Scrol op het tabblad **Instellingen** naar de **Gevarenzone** onderaan het formulier en klik op **Verwijderen**.
