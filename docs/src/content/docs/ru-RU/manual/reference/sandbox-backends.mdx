:::caution[Изолирован ли запуск — зависит от хоста]
`cc_server` один раз определяет при загрузке, как агенты работают на этом хосте, и это решение действует до перезапуска:

- **В песочнице** (`native`): проверка нашла бэкенд, и `--sandbox` не равен `off`. Оба стыка диспетчеризации обёрнуты: CLI Claude Code — через порт песочницы, а ACP и инструмент `bash` встроенного харнесса — через менеджер песочницы.
- **Выключено** (`off`): владелец сервера запустил его с `--sandbox off`. Запуски агентов каждого участника выполняются на этой машине без ограничений, кто бы их ни запустил.
- **Недоступно** (`unavailable`): песочница включена, но проверка не нашла бэкенда (**всегда в Windows**, а также в Linux или WSL2 без `bwrap` и `socat`). Запуск стартует, только если отвечающий за него человек — [владелец сервера](/ru-RU/руководство/понятия/авторизация/#владелец-сервера): тот, кто его запросил, или, для автоматизации, человек, к которому она привязана. Запуск любого другого отклоняется до выдачи учётных данных, взятия аренды или старта процесса. Если владелец не записан, ничей запуск не стартует.

Отклонённый запуск завершается с кодом `sandbox_unavailable`. Приложение показывает его как **Агентам нужна песочница на этом сервере**: «На этом сервере нет песочницы, поэтому агентов здесь может запускать только его владелец. Владелец может установить песочницу или отключить её для всех.»

Запуск, который всё же стартует без песочницы (при `off` или собственный запуск владельца при `unavailable`), выполняется напрямую на хосте. ACP и инструмент `bash` харнесса всё равно порождаются с очисткой окружения; Claude Code идёт через `NoSandboxAdapter` и наследует окружение хоста. Остальные границы — это собственный worktree запуска (copy-on-write там, где поставляется `rift`; `git worktree` в Windows), токен хоста кода только для чтения, выдаваемый брокером при каждом запуске и отзываемый при сворачивании, push, которому нужно пройти правило push в шлюзе запусков агентов, политика команд для каждого режима, единые [ограничения действий](/ru-RU/руководство/понятия/ограничения/) (fail-closed), очистка окружения на путях ACP и `bash` харнесса, а также поверхность инструментов, которую допускает режим запуска.

Внутрипроцессные файловые инструменты харнесса (read, write, edit, apply patch, search, find, search_files) находятся вне песочницы на любом хосте: они выполняются в процессе сервера, поэтому обёрнут только `bash`.

Хост никогда не служит запасным вариантом для сервера с песочницей. Если сервер изолирует агентов, но не может выделить запуску песочницу, его процессы инструментов и команды `bash` отклоняются, а не запускаются на хосте. Та же логика определяет небольшие процессы вокруг запуска: одноразовые помощники ACP (заголовки бесед, `/btw`, `/handoff`, `/goal`) и golden-тесты pull request в Review Studio выполняются в песочнице, когда сервер изолирует агентов, без ограничений при `off`, а при `unavailable` — только для запроса, за который отвечает владелец сервера; иначе они пропускаются.

## Обзор бэкендов

| Бэкенд            | Значение  | Платформа                                     | Доступность                                                                                                       |
| ----------------- | --------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Изолированная VM  | `microvm` | macOS, Linux, Windows (гипервизор microVM)    | Допускается только после проверки среды выполнения microVM; применяется к интерактивным терминалам — оболочка работает внутри [rig](/ru-RU/руководство/понятия/rigs/), а не на хосте |
| Нативная песочница | `native`  | macOS (Seatbelt), Linux и WSL2 (bubblewrap)   | Проверяется при загрузке; Linux отказывает запуску, который требует запретов записи по glob-шаблонам имён файлов, — их bubblewrap обеспечить не может |
| Без изоляции      | `none`    | Все                                           | Значение по умолчанию при разборе и значение по умолчанию терминала; диспетчеризация агента использует его при `--sandbox off`, а для собственных запусков владельца — когда бэкенд недоступен |

`SandboxBackend.fromName` возвращает `none` для пустого или нераспознанного сохранённого значения.

**`microvm` — единственный бэкенд с границей ядра** — рабочая нагрузка
действительно не выполняется на хосте. Он никогда не бывает тихим запасным
вариантом ни в одну, ни в другую сторону: явный запрос его на хосте, который не
может загрузить VM, завершается громкой ошибкой («я просил VM, а получил свой
ноутбук» — единственная деградация, которую изолирующая среда не может себе
позволить), и только *неуказанное значение по умолчанию* опускается до
`native`, о чём сообщает строка журнала. Фактический бэкенд сессии сообщается
обратно клиенту и помечается значком, поэтому терминал никогда не может
заявить, что он изолирован, работая на хосте. Жизненный цикл, образы и
исходящий трафик самой VM описаны в [справочнике по rig](/ru-RU/руководство/справка/rigs/).

**В Windows нет нативной песочницы.** `NativeSandboxAdapter.probe` возвращает `available: false` на любом хосте, который не является macOS или Linux/WSL2, поэтому сервер в Windows находится в состоянии `unavailable`: запускаются только запуски агентов владельца сервера, без ограничений, а запуски всех остальных отклоняются. Чтобы каждый участник мог запускать там агентов, владелец запускает сервер с `--sandbox off`, и тогда все они выполняются без ограничений. Бэкенд `microvm` отдельный: он допускается только после проверки среды выполнения microVM и применяется к интерактивным терминалам и rig, а не к обёртке `bash` на хосте.

## Результаты проверки

Именно проверка управляет принуждением. Она выполняется один раз, при загрузке сервера.

| Хост                                        | `available` | Заметка / подсказка                                                          |
| ------------------------------------------- | ----------- | ---------------------------------------------------------------------------- |
| macOS                                       | `true`      | `sandbox-exec` (Seatbelt) — изоляция пространств имён, без границы ядра      |
| Linux или WSL2 с `bwrap` и `socat`          | `true`      | bubblewrap — изоляция пространств имён, без границы ядра                     |
| Linux или WSL2, где нет одного из инструментов | `false`  | `requiresInstall: true`, с подсказкой об установке, называющей недостающие пакеты |
| Любая другая платформа                      | `false`     | Нативная песочница на этой платформе не предлагается                         |

Сервер записывает результат в одну строку при запуске: `agent sandbox ON` плюс заметка; `no OS-native agent sandbox on this host` плюс подсказка, в которой добавлено, что стартуют только запуски, за которые отвечает владелец сервера; или `agent sandbox DISABLED by --sandbox off`. Строка экспозиции, выводимая при запуске, содержит то же решение как `sandbox=native`, `sandbox=off` или `sandbox=unavailable`. `GET /healthz` не содержит поля песочницы.

`--sandbox` / `CC_SERVER_SANDBOX` принимает `on` (по умолчанию) или `off`. `on` оборачивает каждый запуск, когда хост предлагает бэкенд, и допускает только запуски владельца, когда не предлагает. `off` запускает агентов каждого участника на этом хосте без ограничений; это выбор владельца для всех, а не настройка отдельного запуска.

## Нативный бэкенд

### macOS: Seatbelt

Использует механизм песочницы Seatbelt от Apple (ту же систему, что и macOS App Sandbox).

Создаваемый профиль **по умолчанию разрешающий** (`(allow default)`) и вырезает из него запреты, потому что полностью запрещающий по умолчанию профиль делает интерактивную оболочку непригодной — вызовов dyld, XPC и Mach слишком много, чтобы их перечислить. Практическое следствие: агент по-прежнему может читать большую часть хоста; ваши зарегистрированные рабочие копии защищены явными запретами записи и переименования, а не невидимостью.

- **Чтение файловой системы**: запрещено для секретных путей (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` и остального набора запрета чтения)
- **Запись в файловую систему**: сбрасывается в запрет, затем следуют явные разрешения для подпутей, а пути с обязательным запретом (файлы rc оболочки, `.git/hooks`, конфигурация Claude, защищённые рабочие копии) заблокированы даже внутри записываемого корня. `file-write-unlink` запрещён для каждого запрещённого пути и его предков, поэтому переименование не может обойти запрет записи
- **Процессы**: запреты `process-exec` для всегда опасных бинарников плюс блокировка выполнения чего угодно из записываемого каталога. Известные деревья установки инструментов в домашнем каталоге (кэши corepack, npx и `pnpm dlx`, менеджеры версий node, браузеры Playwright, rustup и cargo, Go, fvm и кэш pub, pyenv, uv и pipx, rbenv, sdkman, mise, asdf и `~/.local/bin`) снова открываются под этим блоком. Общие временные каталоги тоже заблокированы. Вместо этого каждая сессия получает приватный `TMPDIR` в `/private/tmp`, где могут запускаться программы, которые она собрала (бинарник `go test`, сборка cargo). Запреты для всегда опасных бинарников применяются после этих разрешений
- **Сеть**: ограничена портами внутрипроцессных прокси плюс DNS — loopback не разрешён огульно, а прослушивание TCP запрещено. Unix-сокеты разрешены только внутри приватного `TMPDIR` сессии: его используют инструменты вроде tsx и Chrome, которые держат там IPC-сокет; ваш SSH-агент и прочие сокеты остаются недоступны. Прокси обеспечивают доменный список разрешённых для каждой сессии (см. [Исходящий сетевой трафик](#исходящий-сетевой-трафик))
- **Конфигурация**: профили создаются при каждом запуске из `SandboxSpec`
- **Команды самого сервера**: ни один прямой потомок папки, из которой сервер запускает программы (каждая запись `PATH` и обычные папки инструментов пользователя, например `~/.local/bin`, с разрешёнными ссылками менеджеров версий вроде `~/fvm/default`), нельзя создать, заменить, удалить или переименовать, как и установленный пакет, на который указывает связанная команда. См. [Папки команд сервера](#папки-команд-сервера)
- **Файлы запуска**: каждый домашний путь, чтение которого профиль запрещает, также запрещён для записи, а файлы запуска оболочек и сеансов пользователя сервера (`.zshenv`, `.zlogin`, `.bash_login`, конфигурация fish, пользовательские юниты systemd, записи автозапуска и подобные) запрещены для записи во всех режимах

Требования:

- `sandbox-exec` (`/usr/bin/sandbox-exec`), входит в любую установку macOS — дополнительный инструментарий не нужен

### Linux: bubblewrap

Использует bubblewrap (`bwrap`) для создания пространств имён монтирования и PID.

- **Файловая система**: создаёт пространство имён монтирования, в котором видны только привязанные пути
- **Сеть**: работает в отдельном пространстве имён сети; трафик достигает хостовых прокси через мосты `socat` на Unix-сокетах
- **Процессы**: изоляция пространства имён PID
- **Команды самого сервера и файлы запуска**: те же защиты, что на macOS, выраженные как bind-монтирования bubblewrap. Они ещё не проверены на Linux, а отсутствующая папка команд там всё ещё может быть создана

Требования:

- Установленные `bubblewrap` и `socat` (`sudo apt-get install bubblewrap socat` в Debian/Ubuntu)
- Поддержка пространств имён ядром (стандартна для современного Linux)

Bubblewrap может заслонить существующий путь, но не может запретить *новый* файл
`.env`, `*.key` или `*.pem` внутри записываемого bind-монтирования. Стандартная
политика диспетчеризации требует таких запретов по glob-шаблонам имён файлов,
поэтому нативная диспетчеризация агента сейчас **завершается ошибкой в
Linux/WSL2, даже когда проверка находит bubblewrap**. Она не работает с молча
ослабленной политикой. Чтобы вернуть нативную диспетчеризацию в Linux, нужен
бэкенд с правилами имён файлов на момент создания. Отключение песочницы — это
явный отказ от изоляции, а не равноценный обходной путь.

На практике Linux или WSL2 сервер сегодня запускает агентов одним из двух способов. Запущенный с `--sandbox off`, он выполняет агентов каждого участника без ограничений. Без установленных bubblewrap или `socat` он находится в состоянии `unavailable` и запускает только агентов владельца сервера, без ограничений. При установленных обоих инструментах и включённой песочнице каждый запуск отказывает, включая запуски владельца.

## Папки команд сервера

Сервер один раз при старте находит каждую папку, из которой запускает программы: каждую запись своего `PATH`, папки инструментов пользователя, которые он проверяет (например, `~/.local/bin`, `~/.bun/bin` и глобальные папки npm, yarn и pnpm), и настоящую папку за каждой ссылкой на пути (ссылки менеджеров версий вроде `~/fvm/default` или значение fnm по умолчанию). Внутри песочницы агент не может добавить, заменить, удалить или переименовать команду в этих папках, ссылку, ведущую к такой команде, или установленный пакет, на который указывает связанная команда, и не может переименовать папки над ними. Иначе изолированный запуск мог бы подложить программу, которую сервер или человек позже запустит вне песочницы.

Что это меняет для запуска:

- Глобальные установки изнутри изолированного запуска завершаются с ошибкой «Operation not permitted»: `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, а также `cargo install`, `go install` или `dart pub global activate`, когда их папка bin находится в `PATH` сервера.
- Переключение версии по умолчанию завершается так же (`fnm default`, `nvm alias default`, `fvm global`), как и самообновление инструмента на месте.
- Локальные установки проекта (`node_modules/.bin`), `npx`, `pnpm dlx`, менеджеры пакетов, управляемые corepack, кэши SDK и обычные сборки продолжают работать.

Чтобы сделать глобальный инструмент доступным агентам, установите его на самом сервере, от имени пользователя сервера, и перезапустите сервер, чтобы новая команда тоже была защищена. Или установите его в проект. Команда, установленная после старта сервера, полностью защищена только начиная со следующего запуска.

Проверено и обеспечено на macOS. На Linux те же правила — это bind-монтирования bubblewrap, которые пока не проверены. Windows не имеет песочницы.

## Бэкенд без изоляции

Никакой изоляции. Процесс выполняется напрямую на хосте с доступом хоста к файловой системе, сети и процессам. ACP и инструмент `bash` харнесса всё равно получают очистку окружения и политику команд; Claude Code через `NoSandboxAdapter` наследует окружение хоста. Диспетчеризация агента использует его для каждого запуска при `--sandbox off`, а на хосте без доступного бэкенда — только для собственных запусков владельца сервера; запуски всех остальных там отклоняются. Для терминала это оболочка хоста, которую может открыть только владелец сервера.

## Терминал, размещённый на сервере

Серверный терминал открывает оболочку хоста только для [владельца сервера](/ru-RU/руководство/понятия/авторизация/#владелец-сервера). Все остальные получают терминал в песочнице, с ограничениями агента, в каталогах самого рабочего пространства.

Как выбирается бэкенд для сессии:

| Запрошено | Владелец сервера | Все остальные |
| --- | --- | --- |
| Ничего | Бэкенд сервера по умолчанию | Значение по умолчанию, где `none` заменён на `native` |
| `none` (оболочка хоста) | Оболочка хоста | Отказ: оболочка хоста работает на сервере без песочницы |
| `native` | Нативная песочница, профиль владельца | Нативная песочница, профиль агента |
| `microvm` | Изолированная VM | Изолированная VM |
| Неизвестное имя | Отказ | Отказ |

- **Профиль владельца.** `$HOME` и рабочий каталог сессии доступны для записи, сеть открыта, а `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` и `~/Library/Keychains` запрещены для чтения.
- **Профиль агента** (`memberTerminalSandboxConfig`). Та же политика, по которой работает агент в этом рабочем пространстве: запись остаётся в рабочем каталоге, приватном каталоге запуска, `/tmp` и тех частях `$HOME`, куда агенту разрешено писать; секреты запрещены для чтения; сеть — это список разрешённых исходящих доменов агента; программы запускаются только из рабочего каталога и установленных наборов инструментов.
- Терминал открывается только внутри собственных каталогов рабочего пространства. Рабочий каталог вне них отклоняется и никогда не подменяется другим.
- Читать, печатать в, менять размер или закрывать терминал может только тот, кто его открыл. Для всех остальных его id выглядит неизвестным.
- `microvm`, запрошенный явно на хосте без сервиса rig, завершается ошибкой вместо отката. Значение `microvm` по умолчанию на таком хосте понижается до `native`, и об этом сообщается в журнале.

Токен хоста кода только для чтения и шлюз push к терминалам не применяются: это забота диспетчеризации. Если обёртка не поддерживается, сессия завершается ошибкой, а не показывает значок песочницы на сессии оболочки хоста.

## Исходящий сетевой трафик

Когда песочница запускается, исходящий сетевой доступ обеспечивается внутрипроцессными прокси, а не правилами межсетевого экрана ядра. Запуск без песочницы (каждый запуск при `--sandbox off` или запуск владельца на хосте без бэкенда) не получает ничего из этого: порождённый им процесс выходит в сеть точно так же, как это делал бы пользователь сервера.

- Среда выполнения песочницы запускает прокси HTTP/HTTPS и прокси SOCKS5 на `127.0.0.1` внутри процесса `cc_server`, **по одной паре на ограниченную сессию** (`http_proxy.dart`, `socks_proxy.dart`). Параллельные запуски не делят одну пару.
- Изолированные процессы получают переменные окружения прокси (`HTTP_PROXY`/`HTTPS_PROXY` → прокси HTTP, `ALL_PROXY` → прокси SOCKS; `GIT_SSH_COMMAND` направляет git-over-SSH через прокси SOCKS). В Linux пространство имён сети отделено, поэтому прокси — единственный выход; в macOS песочница делит с хостом loopback и обращается к ним напрямую.
- Целевой хост каждого подключения сверяется с доменным списком разрешённых для сессии; всё остальное отклоняется. Есть две формы шаблонов, в каждой ровно один `*`: ведущий `*.example.com` совпадает с любым поддоменом (включая `a.b.example.com`), но не с самим доменом верхнего уровня; `bedrock.*.amazonaws.com` со звёздочкой в середине совпадает ровно с одной меткой (`bedrock.us-east-1.amazonaws.com`, но не `bedrock.evil.attacker.amazonaws.com`).
- Список разрешённых собирается для каждой сессии из подобранной базовой линии (`kBaselineAllowedDomains`: провайдеры LLM, хостинг Git, реестры пакетов), плюс домены GitHub (`kGithubDomains`), плюс `SandboxSpec.egressAllowlist`. Путь диспетчеризации никогда не передаёт дополнительные записи `egressAllowlist`, поэтому на практике каждый запуск получает базовую линию плюс GitHub.
- Фиксированный список запрещённых (`kBaselineDeniedDomains`: конечные точки метаданных облака, приёмники телеметрии) имеет приоритет над всеми разрешениями.
- `networkEnabled: false` всё равно запускает прокси для каждой сессии, но список разрешённых пуст, поэтому каждое исходящее подключение отклоняется. Диспетчеризация задаёт это значение при старте запуска по правилу **Обращаться к сети**: запрет выключает сеть, разрешить и спросить сначала оставляют её включённой.

## SandboxSpec

Спецификация, передаваемая в `SandboxPort.launch`:

| Поле              | Тип                                         | Описание                                                                                                                                    |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | Стабильный идентификатор сессии (обычно id пространства)                                                                                     |
| `workspaceId`     | `String`                                    | Id владеющего рабочего пространства                                                                                                         |
| `agentId`         | `String?`                                   | Агент, привязанный к песочнице в данный момент, если есть                                                                                    |
| `bindMounts`      | `List<SandboxBindMount>`                    | Монтирования хост→гость; песочница видит только перечисленные здесь пути хоста                                                               |
| `networkEnabled`  | `bool` (по умолчанию `true`)                | Задаётся при диспетчеризации по правилу исходящего сетевого трафика (выключено, только когда оно разрешается в запрет). Когда выключено, прокси для каждой сессии всё равно запускаются, но список разрешённых пуст, поэтому каждое исходящее подключение отклоняется |
| `egressAllowlist` | `List<String>` (по умолчанию `[]`)          | Дополнительные разрешённые домены исходящего трафика; поддерживаются шаблоны (`*.example.com`, а также форма со звёздочкой в середине на одну метку). Диспетчеризация никогда его не заполняет, поэтому обёрнутый запуск получает подобранную базовую линию плюс домены GitHub |
| `guestWorkdir`    | `String?`                                   | Рабочий каталог по умолчанию внутри песочницы; отдельные вызовы `exec` могут его переопределить                                              |
| `mode`            | `Mode` (по умолчанию `chat`)                | Определяет правила записи в файловую систему: `chat` оставляет bind-монтирования доступными для записи; `review`, `plan` и `orchestrate` — только для чтения |
| `protectedPaths`  | `List<String>` (по умолчанию `[]`)          | Пути хоста, которые никогда не должны быть доступны для записи внутри песочницы, ни в каком режиме                                            |
| `runnerStateDirs` | `List<String>` (по умолчанию `[]`)          | Каталоги хоста, в которых раннер хранит собственное состояние, доступные для записи в любом режиме (сейчас это `CLAUDE_CONFIG_DIR`, управляемый Control Center) |
| `execGrantRoots`  | `List<String>` (по умолчанию `[]`)          | Одобренные оператором деревья каталогов, которые вновь открывают блокировку exec из записываемого каталога в macOS. Linux их игнорирует — у bwrap нет блокировки exec по `$HOME`, которую можно вновь открыть |

`protectedPaths` содержит исходные зарегистрированные рабочие копии репозиториев,
определяемые при каждой диспетчеризации из репозиториев рабочего пространства.
Агенты работают исключительно в worktree с копированием при записи для каждого
разговора, поэтому оригиналы никогда не должны быть доступны для записи изнутри
песочницы — иначе в macOS огульное разрешение записи в `$HOME` у Seatbelt
оставило бы их доступными для записи через `bash`. Они присоединяются к набору
запрета записи для секретов в любом режиме, включая `chat`.

Каждый путь запрета чтения и запрета записи выдаётся в двух написаниях —
буквальном и после разрешения символических ссылок. Ядро сопоставляет правило
запрета с разрешённым путём, поэтому правило, написанное для пути через
символическую ссылку, никогда не срабатывает — а в macOS это обычный случай, а не
экзотический, поскольку `/tmp` разрешается в `/private/tmp`, а `/var/folders/…` —
в `/private/var/folders/…`. Записи, содержащие `*` или `?`, считаются
glob-шаблонами и не трогаются; путь, который не разрешается, сохраняется как
написан.

## SandboxBindMount

| Поле        | Тип                          | Описание                                                                                                 |
| ----------- | ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| `hostPath`  | `String`                     | Абсолютный путь на хосте                                                                                 |
| `guestPath` | `String`                     | Путь внутри песочницы (в нативной песочнице совпадает с `hostPath`; сохранён для единообразия адаптеров)  |
| `readOnly`  | `bool` (по умолчанию `false`) | Монтировать только для чтения, когда истинно                                                            |

## SandboxHandle

Возвращается методом `SandboxPort.launch`:

| Поле        | Тип                    | Описание                                                                       |
| ----------- | ---------------------- | ------------------------------------------------------------------------------ |
| `sessionId` | `String`               | Идентификатор сессии                                                           |
| `backend`   | `SandboxBackend`       | Какой бэкенд работает                                                          |
| `state`     | `SandboxState`         | Состояние жизненного цикла                                                     |
| `error`     | `Object?`              | Заполняется, когда `state` равен `error`                                       |
| `details`   | `Map<String, Object?>` | Служебные данные, приватные для адаптера (рабочий каталог, PID, путь к профилю и т. д.) |

### SandboxState

| Состояние   | Описание                                          |
| ----------- | ------------------------------------------------- |
| `created`   | Спецификация создана, но VM ещё не запущена       |
| `warm`      | Работает и готова выполнять команды               |
| `active`    | В данный момент выполняет команду                 |
| `suspended` | Приостановлена / сохранена на диск контрольной точкой для экономии ОЗУ |
| `destroyed` | Свёрнута; дескриптор больше недействителен        |
| `error`     | Запуск не удался — см. `SandboxHandle.error`      |

## События песочницы

| Тип события | Описание                                                     |
| ----------- | ------------------------------------------------------------ |
| `stdout`    | Стандартный вывод из песочницы                               |
| `stderr`    | Стандартный вывод ошибок из песочницы                        |
| `exit`      | Процесс песочницы завершился (несёт `exitCode`)              |
| `starting`  | Песочница запускается                                        |
| `ready`     | Песочница готова принимать вызовы exec                       |
| `killed`    | Процесс убит хостом (OOM, тайм-аут, ручная остановка)        |
| `violation` | Нарушена политика песочницы (несёт `SandboxViolation`)       |

## SandboxViolation

| Поле                  | Тип       | Описание                                                                   |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action`              | `String`  | Запрещённый глагол (например, `file-read*`, `network-outbound`)            |
| `target`              | `String`  | Путь или хост, бывший целью запрещённой операции                           |
| `raw`                 | `String?` | Необработанная строка журнала, полезная для отладки                        |
