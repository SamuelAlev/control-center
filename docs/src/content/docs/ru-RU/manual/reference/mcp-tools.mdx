`cc_server` содержит единый реестр инструментов MCP (JSON-RPC 2.0), обслуживаемый на основном порту сервера (по умолчанию `9030`) через `POST /mcp` и `GET /sse`, версия протокола `2024-11-05`. К этому реестру попадает каждый клиент: десктоп, веб-сборка, внешние MCP-клиенты и встроенная среда выполнения агента. Внешние MCP-серверы подключаются к тому же реестру в собственных слоях: по одному на каждое рабочее пространство для серверов, которые настраивают его администраторы, и по одному для собственных серверов каждого участника в этом рабочем пространстве. Эта конечная точка перечисляет, вызывает и ищет их только для запуска агента: серверы собственного рабочего пространства и собственные серверы участника, который начал запуск. Токен MCP и сопряжённые устройства их никогда не видят (см. [MCP-серверы, которые используют ваши агенты](/ru-RU/руководство/практические-руководства/mcp-сервер/#mcp-серверы-которые-используют-ваши-агенты)).

## Размер реестра

| Показатель | Количество |
| --- | --- |
| Инструменты, регистрируемые `cc_server` | 116 |
| Из `packages/cc_mcp` | 114 |
| Из `packages/cc_mcp_client` (обнаружение инструментов) | 2 |
| Зарегистрированы в базовом реестре (`server_mcp_registry.dart`) | 64 |
| Зарегистрированы после загрузки по мере подъёма их служб (`cc_server_runtime.dart`) | 52 |
| Из 64 в базовом реестре — зависят от репозитория графа кода | 5 |
| Из базового реестра в 64, при условии раннера режима кода (`repl`) | 1 |

Пять инструментов графа кода регистрируются, только когда хост передаёт репозиторий графа кода в `buildServerMcpRegistry`, а `repl` — только когда он передаёт раннер режима кода. `cc_server` передаёт оба (без раннера он не запускается), поэтому все 111 зарегистрированы в поставляемом бинарнике; публичный демо-сервер не регистрирует `repl`.

Полный реестр объявляется в `tools/list` без фильтрации на этапе обнаружения, за исключением запуска агента, который может запускать скрипты (см. ниже). Операции редактирования тикетов — типизированные инструменты.

:::note[Внешние клиенты всегда видят весь каталог]
`tools/list` никогда не урезается, кроме собственных MCP-серверов участников: он содержит их только для запуска, начатого их владельцем, а также [режима кода](/ru-RU/руководство/понятия/режим-кода/): `repl` попадает в список только для запуска агента на сервере, который может запускать скрипты, и такой запуск получает в списке `repl`, прямые инструменты (`read`, `write`, `edit`, `search`, `find`, `bash`, `read_output`, `ask_user`, `task`, `todo_write`, `search_memory`, `send_message` и собственные глаголы его режима, если они есть в реестре) и инструменты, которые скрипт не может вызвать. Остальные он вызывает из скрипта; прямой вызов одного из них получает ответ, как вызвать его из `repl`. Клиенты MCP сверяют имена инструментов со своей кэшированной копией этого списка и отказываются от всего, чего в нём нет, даже не спрашивая сервер, поэтому скрытый там инструмент недостижим, а не просто тих.

**Встроенный харнесс** устроен иначе: на каждый запрос он загружает только небольшой прямой набор определений, а остальные вызывает из скриптов или загружает при первом использовании; это поведение на стороне харнесса, и реестра оно не меняет. См. [Контекст инструментов и кэш промптов](/ru-RU/руководство/понятия/контекст-инструментов/).
:::

:::note[Каждый класс инструментов зарегистрирован]
Исходный файл в `packages/cc_mcp/lib/src/tools/` — это инструмент, который агент может
вызвать. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
роняет сборку, если новый класс инструмента не создаётся ничем.
:::

## Общие параметры

### `workspace_id`

**Обязателен** для каждого инструмента, который затрагивает данные уровня рабочего пространства. Отсутствующий или неверный `workspace_id` возвращает явную ошибку, а значение, не совпадающее с рабочим пространством целевой сущности, отклоняется, а не молча игнорируется. Опускайте его у действительно глобальных инструментов: `list_workspaces` и шести инструментов ленты новостей (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), которые опираются на список лент владельца сервера, привязанный к пользователю. Инструменты обнаружения (`search_tool_bm25`, `list_my_tools`) принимают его необязательно, чтобы классифицировать вызываемость по режиму разговора. Когда агента запускает сервер, рабочее пространство задаётся принудительно на стороне сервера, поэтому агент не может добраться до другого рабочего пространства, передав чужой id.

## Обнаружение инструментов

Оба приходят из `cc_mcp_client`, а не из `cc_mcp`, и оба сверяются с проверкой режима, поэтому сообщают о том, что вызываемо в _текущем_ режиме разговора.

| Инструмент | Описание |
| --- | --- |
| `search_tool_bm25` | Ищет по каталогу инструментов по ключевому слову; возвращает подходящие инструменты, схемы их аргументов и то, вызываем ли каждый прямо сейчас |
| `list_my_tools` | Перечисляет инструменты, вызываемые прямо сейчас в этом разговоре, с фильтрацией по его режиму |

Третий инструмент обнаружения, **`search_tools`**, существует только внутри встроенного харнесса и не входит в этот реестр MCP. Он ранжирует собственную поверхность инструментов запуска и, в отличие от `search_tool_bm25`, **загружает** схемы найденного, чтобы агент мог вызвать совпадение на следующем ходу. Агентам на харнессе стоит предпочитать его; у клиентов MCP есть `search_tool_bm25`.

## Режим кода

| Инструмент | Описание |
| ------ | ----------- |
| `repl` | Выполняет JavaScript-скрипт, который вызывает инструменты запуска как `tools.<id>(args)`, и возвращает только то, что нужно. Перечисляется только запуску агента на сервере, который может запускать скрипты [режима кода](/ru-RU/руководство/понятия/режим-кода/). Каждый вложенный вызов проходит ту же проверку, что и `tools/call`. Принимает `code`, `description`, `timeout_ms?`, `max_output_tokens?`   |

Скрипт не может вызвать `repl`, `search_tool_bm25`, `list_my_tools`, а также любой инструмент, который запускает или отправляет сообщение другому запуску агента, назначает тикет или оставляет к нему комментарий, отправляет сообщение, создаёт, решает или комментирует подтверждение, предлагает или меняет политику, устанавливает или меняет навыки, создаёт профиль среды выполнения, отправляет план, выходит из режима плана, завершает цель разговора или отправляет результат запуска конвейера.. Такие инструменты объявляют `scriptCallable` равным false и всегда вызываются напрямую; во встроенном харнессе инструмент вне прямого набора загружается при первом использовании. Инструмент `create_ticket` можно вызвать из скрипта только без `assignee`.

## Обмен сообщениями и делегирование между агентами

Агенты общаются друг с другом через пространства (долговечно, видно в составе). `ask_agent` либо ждёт ответа (`mode: wait`, по умолчанию 600 секунд, не более 1 800), либо сразу возвращает управление (`mode: background`); в любом случае спрашивающего пробуждают один раз с ответом, если он не пришёл в том же вызове. `send_to_agent`, `ask_agent`, `consult_agent`, `request_peer_review` и `delegate_task` проходят один и тот же серверный шлюз: глубина (3), обнаружение циклов, рамка бюджета, потолок автономии и лимит частоты для каждой пары агентов. Идентичность отправителя всегда берётся из вызывающего запуска. См. [Агенты вместе](/ru-RU/руководство/практические-руководства/агенты-вместе/).

| Инструмент | Описание |
| --- | --- |
| `send_to_agent` | Отправляет одностороннее сообщение другому агенту, адресуя его через `to_agent_id` или точный `to_agent_name`; возвращает `delivery_status` `woken`, `queued_behind_run` или `refused` |
| `ask_agent` | Задаёт другому агенту вопрос; ждёт ответа или продолжает работу и пробуждается, когда он придёт |
| `delegate_task` | Делегирует задачу другому агенту как отслеживаемый дочерний тикет |
| `consult_agent` | Добавляет в пространство наиболее подходящего по навыкам специалиста и запускает его с точечным брифом |
| `todo_read` | Читает сохранённый контрольный список задач этого разговора |
| `agent_activity` | Прочитать, что другой агент делает сейчас и что делал в последний раз (статус, текущий инструмент, последние сообщения), не пробуждая его |

## Инструменты пробуждения и цели

Агент использует эти инструменты вместо ожидания или опроса. Каждый действует только для вызывающего агента в его разговоре; агент никогда не передаётся аргументом. См. [Расписания и пробуждения](/ru-RU/руководство/практические-руководства/расписания-и-пробуждения/) и [Вести цель](/ru-RU/руководство/практические-руководства/вести-цель/).

| Инструмент | Описание |
| ------------- | ----------- |
| `wake_me` | Запланировать пробуждение позже: в заданное время (`in:20m`, `at:<ISO time>`), с интервалом (`every:30m`), по cron (`cron:0 9 * * 1-5`, с `tz`), в собственном темпе внутри цикла с самостоятельным темпом (`next`, с `delay` от 1 до 60 минут) или когда что-то происходит (`on:pr_checks`, `on:pr_review`, `on:pr_merged`, `on:environment`, `on:ticket:<id>`, `on:pipeline_run:<id>`). Необязательные: `note`, `max_runs`, `expires_in`, `when_busy` (`skip` или `queue`) и `deliver` (`run` или `notify`) |
| `list_wakes` | Перечислить, что агент ждёт в этом разговоре: расписания, наблюдения, ожидающие пробуждения и запросы без ответа |
| `cancel_wake` | Отменить расписание или наблюдение, которое агент поставил себе, по его id |
| `goal_status` | Прочитать активную цель агента: контракт, сегмент, расход и оставшийся бюджет, отметки об отсутствии прогресса, удержание, последнюю проверку и ожидающие пробуждения цели |

`complete_goal` (в разделе [Инструменты планов, плейбуков и артефактов](#инструменты-планов-плейбуков-и-артефактов)) — единственный способ, которым агент говорит, что цель выполнена, и это заявление, а не завершение.

## Инструменты навыков

Каждая установка и обновление проходят через шлюз проверки по принципу fail-closed, прежде чем содержимое навыка попадёт на диск или в промпт агента.

| Инструмент | Описание |
| --- | --- |
| `list_skills` | Перечисляет slug навыков, доступных в рабочем пространстве |
| `create_skill` | Создаёт новый навык из markdown-содержимого |
| `install_skill` | Устанавливает весь каталог навыка из репозитория GitHub на закреплённом ref |
| `update_skill` | Обновляет установленный навык из GitHub до нового ref, заново сканируя и закрепляя |
| `list_skill_updates` | Перечисляет навыки, для которых доступна более новая версия |
| `verify_skills` | Сверяет заблокированные навыки с хэшами их содержимого на диске |
| `pin_skill` | Хэширует существующий навык на диске в `skills-lock.json` |

## Инструменты изолированной среды (rig)

Управляют одноразовыми машинами — изолированным браузером или рабочим столом
Linux, эмулятором Android или симулятором iOS — изнутри запуска. Регистрируются
после загрузки, безусловно: может ли машина на самом деле загрузиться, — это
вопрос-зонд, на который инструменты отвечают при каждом вызове. Повторные вызовы
в одном разговоре переиспользуют одну машину; снимки экрана возвращаются как
графическое содержимое с бюджетом в одно изображение на результат, а извлечённое
содержимое страницы или интерфейса обрамляется как недоверенные данные. Четыре
инструмента использования плюс `rig_close` объявляют [класс
действий](/ru-RU/руководство/понятия/ограничения/) `enclosureControl`
(инструменты использования также объявляют `networkEgress` и `processSpawn`;
`mobile_use` и `ios_use` также объявляют `packageInstall`), поэтому режимы
только для чтения их запрещают. `rig_list` не объявляет ничего — он только читает
состояние рабочего пространства. Полный набор глаголов для каждой поверхности — в
[справочнике по rigs](/ru-RU/руководство/справка/rigs/#глаголы-действий).

| Инструмент | Описание |
| --- | --- |
| `computer_use` | Управляет рабочим столом Linux в изолированной виртуальной машине: перемещение, клик, перетаскивание, прокрутка, ввод, изменение размера, буфер обмена, снимок экрана |
| `browser_use` | Управляет headless-браузером Chromium, Firefox или WebKit (`engine`): навигация, клик, заполнение, извлечение (a11y/DOM/консоль), буфер обмена, снимок экрана |
| `mobile_use` | Управляет Android через ADB: осмотр/ввод, снимки экрана, установка/запуск/остановка/сброс/удаление приложений, глубокие ссылки и команды устройства в форме argv |
| `ios_use` | Управляет симулятором iOS через WebDriverAgent/CoreSimulator: осмотр/ввод, снимки экрана, установка/запуск/остановка/удаление приложений, глубокие ссылки и процессы симулятора в форме argv |
| `rig_list` | Перечисляет rigs пространства запуска с поверхностью, статусом, размером дисплея и контроллером |
| `rig_close` | Уничтожает rig и отбрасывает принадлежащее ему состояние машины |

Вызывать эти инструменты могут только запуски агентов; любой другой вызывающий получает отказ. Запуск достигает только rigs того пространства, для которого он был выдан: `space_id` берётся из гранта запуска, а не из вызова, а rig другого пространства или без пространства отвечает так же, как отсутствующий.

`app_use` — пятый инструмент use: он управляет окнами настольного приложения, запущенного в пространстве, напрямую на хосте, а не в ВМ, и также объявляет `fileWriteOutsideWorktree` и `fileDelete`. Он и инструменты `environment_*` описаны в разделе [Настройка окружений](/ru-RU/руководство/практические-руководства/окружения/).

## Не предоставляется через MCP

У календаря и встреч нет инструментов MCP. Агенты не могут читать ваш календарь, встречи, транскрипты, пункты действий или решения. Сводку, из которой получаются пункты действий и решения, выполняет встроенный [конвейер `meeting_summary`](/ru-RU/руководство/понятия/встречи/), а не инструмент, который агент может вызвать.

## Ограничение инструментов по режиму

Ограничение применяется дважды из одной таблицы (`ModeToolPolicy`): один раз в диспетчере MCP для адаптера Claude Code и один раз в реестре встроенного харнесса. Заблокированный вызов возвращает причину.

| Режим | Поверхность инструментов |
| --- | --- |
| `chat` | Все зарегистрированные инструменты; без списка разрешённых |
| `plan` | Тщательно подобранный список разрешённых. Никаких записей в worktree и никаких глаголов тикетов `create` / `assign` / `delegate`, но разрешены память, артефакты, todo, `submit_plan`, `exit_plan_mode` и глаголы завершения тикета для запущенного тикета |
| `review` | Тщательно подобранный список разрешённых: участие в проверке, общение, средства чтения контекста только для чтения и полный набор глаголов тикетов, включая `create_ticket` и `assign_ticket` |
| `orchestrate` | Тщательно подобранный список разрешённых: инструменты исследования и чтения плюс `propose_orchestration`, `create_playbook` и `run_playbook`. Найм, декомпозиция и завершение тикетов происходят детерминированно после утверждения, никогда — посреди запуска |

Разрешено в каждом режиме независимо от списка разрешённых:

| Набор | Инструменты |
| --- | --- |
| Память и артефакты | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Граф кода | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact` |
| Механика запуска | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read` |

Присутствие в списке разрешённых не делает инструмент вызываемым, и обратное тоже верно: возможность задать вопрос оператору — это инструмент **харнесса** (`ask_user`), поэтому в этом каталоге MCP его нет вовсе.

## Инструменты, требующие подтверждения

Инструмент может объявлять `requiresApproval`. Тогда диспетчер собирает `ApprovalPayload` и предъявляет его через `ConfirmationPort` до запуска инструмента; `cc_server` подключает этот порт, поэтому шлюз работает.

Зарегистрированные инструменты, которые его объявляют: `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

Независимо от этого единые ограничения действий пропускают через шлюз любой инструмент, объявляющий непустой набор `ActionClass`. Решение `prompt` без подключённого утверждающего отклоняется. См. [Ограничения](/ru-RU/руководство/понятия/ограничения/).

## Возможности, за которыми нет инструмента

Не каждая возможность продукта достижима для агента. У перечисленных ниже нет
инструмента вовсе, поэтому имя, которое вы могли встретить где-то ещё, вернёт «unknown tool»:

| Возможность | Где она живёт вместо этого |
| --- | --- |
| Найм, увольнение или редактирование агента | Интерфейс агентов. Инструментов `hire_agent` / `fire_agent` / `update_agent` нет |
| Создание рабочего пространства | `workspace.create` по RPC, только для владельца сервера, который заводит его и проставляет владельца |
| Проекты (создать / перечислить / обновить / отнести) | Интерфейс тикетов. Проекты — поверхность оператора, см. [Проекты](/ru-RU/руководство/практические-руководства/проекты/) |
| Задать оператору блокирующий вопрос | Инструмент **харнесса** `ask_user`, а не MCP. Он отрисовывает форму в разговоре и блокируется в ожидании ответа |
| Диагностика отдельного агента | Ничего. Инструмента `doctor` нет — см. [Диагностика агента](/ru-RU/руководство/практические-руководства/диагностика-агента/) |
| Календарь и встречи | Только RPC для человеческих клиентов (см. выше) |
