## Шина событий

`DomainEventBus` — это внутрипроцессная широковещательная шина публикации и подписки. Издатели вызывают `publish(event)`; подписчики получают типизированный поток `on<T>()`. Каждое событие реализует `DomainEvent` и несёт `occurredAt`.

**Шина работает внутри `cc_server`.** Там живёт каждый издатель и каждый живой подписчик. Ни один клиент эту шину не видит: сервер пересылает отобранное подмножество в виде кадров `notifications/*` JSON-RPC, отфильтрованных для каждого подписчика по членству в рабочем пространстве.

| Показатель                                                  | Количество                                   |
| ----------------------------------------------------------- | -------------------------------------------- |
| Конкретные классы событий                                   | 53                                           |
| Исходные файлы (`packages/cc_domain/lib/core/domain/events/`) | 14 (плюс `domain_event_bus.dart`)          |
| Абстрактные базовые классы, которые никогда не публикуются напрямую | 1 (`TaskLifecycleEvent`, sealed-иерархия) |

Каждое событие из каталога ниже живёт в этом единственном каталоге; больше нигде доменные события не объявлены.

## События pull request и ревью

Первый блок — собственный жизненный цикл PR. Второй — **наблюдение за созданными вами PR**: сигналы о PR, который открыли *вы*, и каждый из них несёт `forUserId`, чтобы опрос направлял их человеку, которого они касаются, а не рассылал всем.

| Событие                    | Полезная нагрузка                                                        | Когда возникает                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `PullRequestPublished`     | `prId`, `workspaceId`, `repoOwner`, `repoName`                           | Агент открывает PR                                                                                                                  |
| `PullRequestStatusChanged` | `status`, `workspaceId`, `prId?`, `repoFullName?`, `prNumber?`           | PR смержен, закрыт, открыт, переоткрыт или одобрен                                                                                  |
| `PrMerged`                 | `prId`, `workspaceId`, `agentId`                                         | PR смержен — узкий сигнал только о слиянии, сохранённый ради аналитики и уведомлений                                                |
| `PrReviewRequested`        | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`            | GitHub запрашивает ревью у пользователя сервера (опрос уведомлений, `review_requested`)                                             |
| `PrMentioned`              | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`            | Пользователя сервера упомянули в PR (опрос уведомлений, `mention`)                                                                  |
| `ExternalPrMerged`         | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`, `mergedByLogin?` | Внешне отслеживаемый (не агентский) PR смержен, что обнаружено опросом уведомлений GitHub; сопоставляется с категорией уведомлений `prMerged` |
| `ExternalPrDetected`       | `repoOwner`, `repoName`, `prNumber`, `prTitle`, `author`, `workspaceId?` | Неагентский PR найден через опрос — только для конвейера (управляет `external_pr_welcome`), уведомления не порождает                 |

## События жизненного цикла задач

Единый поток жизненного цикла задач — один отправленный запуск агента, ключом которому служит идентификатор его журнала запуска. Каждое событие несёт `taskId`, монотонный в пределах задачи `seq`, `workspaceId?`, `agentId?` и `phase`; в строках ниже перечислены только дополнительные поля.

| Событие                     | Полезная нагрузка             | Когда возникает                                                                                                 |
| --------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `TaskDispatched`            | —                             | Задача передана бэкенду на выполнение                                                                            |
| `TaskRunning`               | —                             | Задача начала выдавать вывод                                                                                     |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | Задача припаркована — другой задаче принадлежит нужная ей блокировка пути на диске                              |
| `TaskProgress`              | `note?`                       | Контрольная точка хода выполнения                                                                                |
| `TaskMessage`               | `messageType`, `content`      | Потоковое сообщение (text/thinking/tool_use/tool_result/error); передаётся в фазе `progress`                    |
| `TaskCompleted`             | `summary?`                    | Задача успешно завершена                                                                                         |
| `TaskFailed`                | `errorMessage`                | Задача завершилась с ошибкой                                                                                     |
| `TaskCancelled`             | —                             | Задача отменена до завершения                                                                                    |

У перечисления `TaskPhase` есть также член `queued`, но событие очереди никто не публикует — класса `TaskQueued` нет. Первый наблюдаемый кадр задачи — `TaskDispatched`.

| Событие             | Полезная нагрузка                             | Когда возникает                                                                                                                  |

**Открытие** rig событием не является. Загрузка завершается, и строка rig переключается в состояние «готов»; ничего не публикуется, поэтому подписаться на `RigOpened` не на что.

## Поддомены, в которых нет ни одного события

Несколько подсистем, которые снаружи выглядят событийными, таковыми не являются. Они перечислены здесь потому, что их отсутствие — осознанное проектное решение, о котором стоит знать, прежде чем искать хук:

| Поддомен            | Как вместо этого меняется состояние                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| Память              | `record_memory_fact` и компания пишут и возвращают; извлечение читает. На факт или конфликт ничего не публикуется |
| Оркестрация         | Предложение, его согласование и порождённый запуск конвейера — это строки и вызовы RPC                  |
| Документы планов    | `submit_plan` записывает ревизию; согласование материализует оркестрацию. Ни то, ни другое не объявляется событием |
| Артефакты           | `publish_artifact` / `revise_artifact` пишут ревизии напрямую                                           |
| Согласования        | Эскалация обрабатывается внутри службы процесса согласования                                            |
| Синхронизация тикетов | Вендорский координатор подписывается на события тикетов выше; входящие вебхуки применяются напрямую      |
| Обновление календаря | Синхронизация вставляет и обновляет события, а клиент перечитывает их; широковещательного оповещения об обновлении нет |
| Слияния worktree    | Записываются в `worktree_merge_log`, откуда их и читают                                                 |

`TicketAssigned` — это сигнал аудита и уведомлений и триггер конвейера. Назначение агенту фиксирует владение и не запускает выполнение — диспетчера тикетов нет. Исключение — назначение команде (задан `assignedTeamId`): `TeamRoutingService` отправляет лидера команды.

`TicketRemoteSyncHandler` объявлен, но в продакшен-коде никогда не создаётся, поэтому сегодня он ни на что не подписан. Живые всплывающие уведомления приходят из кадров, описанных ниже.

## Сопоставление уведомлений

На сервере `NotificationFeedRecorder` и `RemoteEventForwarder` превращают эти события в кадры `notifications/*` (`notification_wire.dart`). На клиенте `RpcNotificationMapper` → `mapNotificationFrame` превращает кадр в `AppNotification`.

Категорий уведомлений ровно **шестнадцать**. Несколько событий отображаются более чем на один метод передачи, потому что кадр несёт признак перехода (сбой или восстановление), а категория несёт вопрос («что делает CI?»).

| `rigStatusChanged`     | `RigClosedEvent`          | `notifications/rig_closed`                                             |

Кадр перехвата rig не доставляется обратно тому, кто взял управление,
освобождение не фильтруется (событие не фиксирует, кто отпустил управление), и
только закрытие с `backendFailure` порождает кадр `rig_closed` — остальные
причины либо запрошены, либо уже покрыты кадром сбора.

Пять категорий по созданным вами PR несут `forUserId`, поэтому они доходят до автора, а не до всех в рабочем пространстве.

`RemoteEventForwarder` дополнительно пересылает `TicketReassigned` как `notifications/ticket_reassigned`, а каждое `TaskLifecycleEvent` — как `notifications/task_<phase>`. Ни то, ни другое не отображается на категорию уведомлений — они управляют интерфейсом в реальном времени, а не центром уведомлений. События членства кадрами не пересылаются: они инвалидируют кеш форвардера, а хосты сессий сбрасывают подписки удалённого участника на рабочее пространство.
