Это **привязанные к серверу** инструменты, которые встроенная среда выполнения агента регистрирует напрямую: языковой сервер, структурный поиск, отладчик, ядра, скрипты режима кода, вопросы и управление воркерами — в отличие от [инструментов MCP](/ru-RU/руководство/справка/инструменты-mcp/), которые она подключает извне, и универсальных инструментов работы с файлами, поиском и оболочкой из среды выполнения харнесса. Их нет в реестре MCP: внешний клиент MCP их не увидит, потому что каждый из них привязан к живому ресурсу на стороне сервера — процессу языкового сервера, отладочному адаптеру, интерпретатору, — который принадлежит одному запуску.

Каждый инструмент здесь регистрируется, только когда для запуска подключён его опорный ресурс — супервизор языкового сервера или отладки, парсер tree-sitter, фабрика ядер, порт вопросов, состав vibe. Обнаружение языкового сервера или отладочного адаптера для *этой рабочей копии* — отдельная, более поздняя проверка (`status` / `adapters`): эти инструменты остаются на поверхности, чтобы агент мог спросить, почему ничего не работает, а не гадать.

## Уровни подтверждения

Каждый инструмент объявляет уровень, и уровень решает, **какие поверхности его видят**, — а не просто то, спрашивает ли он подтверждение. Режим плана и субагенты только для чтения ограничены уровнем `read`, поэтому инструмент уровня `write` или `exec` полностью отсутствует в их схеме.

| Уровень | Значение                       | Инструменты здесь                                |
| ------- | ------------------------------ | ------------------------------------------------ |
| `read`  | Без побочных эффектов          | `lsp`, `ast_grep`, `ask_user`, `repl`, пять `vibe_*` |
| `write` | Изменяет файлы                 | `lsp_rename`, `ast_edit`, `resolve`              |
| `exec`  | Запускает процесс или управляет им | `debug`, `eval`                              |

## Прямой, только из скрипта или загружается при первом использовании

Когда сервер может запускать скрипты, запуск вызывает несколько инструментов напрямую, а до остальных доходит через скрипт [`repl`](#repl--запуск-скрипта-который-вызывает-ваши-инструменты); всё правило см. в разделе [Режим кода](/ru-RU/руководство/понятия/режим-кода/#какие-инструменты-агент-вызывает-напрямую). Для инструментов на этой странице:

| Инструмент | С `repl` | Без `repl` |
| ---- | ----------- | -------------- |
| `repl` | Прямой | Отсутствует |
| `ask_user` | Прямой | Прямой |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Только из скрипта | Загружается при первом использовании |
| `eval` | Загружается при первом использовании (скрипт не может его вызвать) | Загружается при первом использовании |
| `vibe_*` | Прямой в режиме vibe, никогда из скрипта | Прямой в режиме vibe |

Инструмент, помеченный как «Только из скрипта», вместо этого загружается при первом использовании, как только сервер не может запускать скрипты запуска ([Когда скрипты не могут работать](/ru-RU/руководство/понятия/режим-кода/#когда-скрипты-не-могут-работать)).

## `lsp` — запросы к языковому серверу

Регистрируется, когда у запуска есть супервизор языкового сервера и рабочий каталог. Способен ли сервер на самом деле ответить, определяется в момент вызова как **пересечение**: маркер корня должен существовать, *и* бинарник сервера должен разрешаться. Каждое из условий само по себе означает, что сервер не запустится — `status` так и говорит, — а не молчаливое предположение.

Серверы берутся только из встроенной таблицы; `lsp.json` из репозитория не читается. В запуске в песочнице каждый запуск получает собственную сессию языкового сервера, поэтому серверы стартуют заново в каждом запуске. Бинарники внутри проекта (`node_modules/.bin`) используются только в песочнице, а корень проекта никогда не поднимается выше рабочего каталога запуска.

Позиции адресуются строкой `line` плюс подстрокой `symbol`, никогда — столбцом. Модель, у которой просят столбец, гадает, а неверная догадка разрешается в другой символ на той же строке — ответ, который выглядит правильным, но говорит о другом. Пропуск `symbol` в навигационном действии — это ошибка, а не догадка о первом столбце.

| Действие          | Аргументы                        | Возвращает                                 |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (или `"*"`)               | Ошибки и предупреждения; `"*"` вместо этого запускает проверку проекта |
| `definition`      | `file`, `line`, `symbol`         | Где объявлен символ                        |
| `type_definition` | `file`, `line`, `symbol`         | Где объявлен его тип                       |
| `implementation`  | `file`, `line`, `symbol`         | Конкретные реализации                      |
| `references`      | `file`, `line`, `symbol`         | Все использования, не более 50             |
| `hover`           | `file`, `line`, `symbol`         | Сигнатура и doc-комментарий                |
| `symbols`         | `query` или `file`               | Поиск по рабочему пространству с `query` (не более 100); символы документа с `file` (не более 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Быстрые исправления, которые предлагает сервер |
| `status`          | —                                | Какие серверы работают и для каких корней  |
| `reload`          | —                                | Перезапускает сервер для этого корня       |

### Диагностика при записи

Выигрыш не в самом инструменте. `write`, `edit` и `apply_patch` **обёрнуты**: после записи файл синхронизируется и сохраняется через языковой сервер, и в результат инструмента подмешиваются только **вновь появившиеся** диагностики. Агент узнаёт, что сломал сборку, в тот самый момент, когда он её сломал, и ему не нужно помнить, чтобы спросить.

Уже отчитанные диагностики подавляются реестром уровня запуска, ключ которого строится по серьёзности, коду и сообщению, — позиция намеренно исключена, поэтому диагностика, которая всего лишь сместилась на четыре строки вниз, не отчитывается заново как новая.

## `lsp_rename` — переименование в пределах проекта

Отдельный инструмент уровня `write` ровно по одной причине: уровень решает видимость. Добавление переименования в `lsp` либо дало бы исследователю только для чтения возможность переписать репозиторий, либо поставило бы каждый `hover` за запрос подтверждения.

| Аргумент   | Значение                               |
| ---------- | -------------------------------------- |
| `file`     | Где находится символ                   |
| `line`     | Строка с нумерацией от 1               |
| `symbol`   | Подстрока, опознающая его в этой строке |
| `new_name` | Как его назвать                        |

## `ast_grep` — структурный поиск

Находит код по **форме**, а не по тексту. `$NAME` сопоставляется с любым узлом, `$$$NAME` — с последовательностью соседних узлов, а `$_` — это подстановочный знак, который ничего не связывает.

Свойство, которое делает его сопоставителем, а не регулярным выражением с лишними шагами: метапеременная, повторённая в одном шаблоне, должна захватить один и тот же текст.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

находит проверку, которая освобождает то же, что проверяла, и **не** находит ту, что освобождает что-то другое.

| Аргумент      | Значение                                                     |
| ------------- | ------------------------------------------------------------ |
| `pattern`     | Фрагмент кода с метапеременными                              |
| `path`        | Файл или каталог для поиска; по умолчанию всё рабочее пространство |
| `language`    | Идентификатор поставляемой грамматики (`dart`, `python`, `rust`, `c`, …). Выводится, когда `path` указывает на файл |
| `max_results` | По умолчанию 50                                              |

:::note[Шаблон разбирается той же грамматикой, что и файл]
Поэтому `dispose(x)` находит вызов, как бы он ни был расставлен пробелами, перенесён по строкам или закомментирован, — и никогда не находит те же символы внутри строкового литерала или комментария.
:::

:::caution[Фрагмент разбирается в каркасе, а не сам по себе]
`dispose(x)`, разобранный на верхнем уровне Dart, — это допустимая *сигнатура функции*. Компилятор шаблонов перебирает лестницу контекстов (инструкция, выражение, член класса, объявление) и использует первый, который принимает фрагмент. Шаблон, который не принимает ни один контекст, сообщается как неразбираемый, а не ищется и молча не находится.
:::

## `ast_edit` — структурная перезапись с подготовкой

То же сопоставление, плюс шаблон `rewrite`, в который подставляются обратно метапеременные. **Ничего не записывается.** Изменение подготавливается, и результат называет `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Аргумент   | Значение                                            |
| ---------- | --------------------------------------------------- |
| `pattern`  | Что сопоставлять                                    |
| `rewrite`  | Что подставить на это место, с подстановкой `$NAME` |
| `path`     | Область; по умолчанию всё рабочее пространство      |
| `language` | Идентификатор языка                                 |

## `resolve` — зафиксировать или отбросить подготовленное изменение

| Аргумент  | Значение                         |
| --------- | -------------------------------- |
| `edit_id` | Из результата `(proposed)`       |
| `action`  | `accept` или `discard`           |

Каждый файл сверяется с содержимым, зафиксированным в момент подготовки изменения, и **любое** несовпадение отклоняет изменение целиком. Частично применённая структурная перезапись оставляет дерево, которое не компилируется ни под старой формой, ни под новой.

## `debug` — управление отладчиком

Регистрируется, когда у запуска есть супервизор отладочных сессий, рабочий каталог и идентификатор разговора. Способен ли адаптер на самом деле запуститься, определяется в момент вызова по тому же правилу пересечения, что и для языкового сервера (маркер корня *и* бинарник). Уровень `exec`; небезопасен при параллельном выполнении (сессия — это состояние между вызовами, поэтому `continue`, обогнавший `stack`, прочитал бы кадр, который уже сдвинулся).

Одна сессия на разговор, с жёстким TTL (30 минут). Второй `launch` отклоняется, а не заменяет первый молча. В запуске в песочнице сессия сохраняет свою песочницу между ходами до своего завершения, поэтому не дольше этих 30 минут.

| Операция      | Аргументы                     | Примечания                                     |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Какие адаптеры здесь пригодны и почему нет     |
| `status`      | —                             | Работает ли сессия и где она остановилась      |
| `breakpoints` | `file`, `lines[]`             | Пустой `lines` очищает файл. Можно ставить **до** запуска |
| `launch`      | `program`, `args[]`           | Запускает программу остановленной на ваших точках останова |
| `attach`      | `port`                        | Подключается к уже запущенной отлаживаемой программе на одном из собственных проброшенных портов запуска; любой другой порт отклоняется до старта чего-либо |
| `continue`    | `thread_id?`                  | Выполняет до следующей остановки               |
| `pause`       | `thread_id?`                  | Останавливает её там, где она есть             |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Делает один шаг                     |
| `threads`     | —                             | Идентификаторы и имена потоков                 |
| `stack`       | `thread_id?`                  | Кадры, не более 30                             |
| `scopes`      | `frame_id`                    | Области видимости кадра, у каждой есть `reference` |
| `variables`   | `reference`                   | Дочерние элементы, не более 50; значения не длиннее 400 символов |
| `evaluate`    | `expression`, `frame_id?`     | Вычисляется в собственной области видимости кадра |
| `output`      | —                             | stdout/stderr отлаживаемой программы, с ограничением размера |
| `terminate`   | —                             | Завершает сессию и убивает адаптер             |

### Адаптеры

| Идентификатор | Команда                      | Маркеры корня                                   |
| ------------- | ---------------------------- | ----------------------------------------------- |
| `dart`        | `dart debug_adapter`         | `pubspec.yaml`                                  |
| `debugpy`     | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`        | `lldb-dap`                   | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`       | `dlv dap`                    | `go.mod`                                        |

`debugpy` предпочитает локальные для проекта `.venv/bin` или `venv/bin` вместо `$PATH`, когда запуск в песочнице: python из `$PATH` — это другое окружение, и подключение не из того окружения падает так, что это читается как сломанный код. Вне песочницы он использует только `$PATH`, поэтому репозиторий не может выбрать интерпретатор, который работает на хосте.

## `repl` — запуск скрипта, который вызывает ваши инструменты

Присутствует при каждом запуске, когда сервер может запускать скрипты ([Когда у запуска есть `repl`](/ru-RU/руководство/понятия/режим-кода/#когда-у-запуска-есть-repl)). Скрипт — это обычный JavaScript, тело асинхронной функции; он выполняется в новом, заблокированном интерпретаторе в собственном процессе: без доступа к файловой системе, сети, процессам и модулям. Сам `repl` относится к уровню `read` и проверяет себя сам, поскольку каждый вызов инструмента, который делает скрипт, проверяется отдельно. Также доступен на конечной точке MCP для запусков агентов на сервере, который может запускать скрипты.

| Аргумент | Значение |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | Скрипт. Не более 256 КиБ |
| `description` | Обязательно. Короткая подпись для строки в разговоре |
| `timeout_ms` | Необязательно. Более короткий временной лимит, чем у рабочего пространства; никогда не более длинный |
| `max_output_tokens` | Необязательно. Меньший бюджет вывода, чем у рабочего пространства; никогда не больший |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

Описание `repl` сообщает агенту: «Инструмент, который не входит в ваш прямой набор, не имеет определения в этом запросе. Перед первым вызовом такого инструмента найдите его через `describeTool(name)` или `searchTools(query)`, если его точная форма вызова уже не показывалась вам в этом разговоре».

`describeTool(name)` возвращает описание инструмента, его объявление, схемы входа и выхода и примечание к результату, если оно есть: то, что скрипт получает от завершённого вызова, в словах самого инструмента. Описание `repl` перечисляет примечания прямых инструментов, которые скрипт может вызвать. Результат, который является JSON-текстом, приходит уже разобранным, если только он не содержит больше 131 072 значений: тогда он приходит как текст, и скрипт разбирает его сам с помощью `JSON.parse`. Текст результата инструмента внешнего сервера MCP обрезается после 262 144 символов, а обрезанный текст больше не разбирается как JSON.

- `tools.<name>(args)` вызывает инструмент через тот же фильтр, ограничения и подтверждение, что и прямой вызов, и отклоняется с ошибкой, если вызов отклонён или не удался. Вызовы только для чтения могут выполняться одновременно; вызовы, которые что-то меняют, выполняются по одному, в том порядке, в котором их сделал скрипт. Пока один из её вызовов ждёт человека, никакой другой вызов скрипта не начинается.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` и `describeNamespace(name)` находят инструменты, в том числе инструменты подключённых серверов MCP. Инструмент вне прямого набора, который может вызвать скрипт, доступен только из скрипта; прямой вызов такого инструмента возвращает, как вызвать его из `repl`. Как только сервер не может запускать скрипты запуска, такой инструмент вместо этого загружается при первом использовании.
- Поиски ограничены: запрос не длиннее 1 024 символов, имя или пространство имён не длиннее 256, `limit` от 0 до 50, и не более 200 поисков, занимающих в общей сложности 2 секунды времени сервера, на каждый скрипт; все скрипты одного рабочего пространства делят 2 секунды времени поиска, которое возвращается по четверти секунды за каждую секунду. При исчерпании любого из лимитов дальнейшие поиски отклоняются. В очень большом каталоге описания в `ALL_TOOLS` делят примерно миллион символов поровну, а обрезанное заканчивается на `…`; `describeTool` всегда возвращает полное описание. Тип, который слишком велик для показа, выглядит как `unknown /* too large to show */`, а на неизвестное имя отвечают ближайшими именами.
- Инструменты группируются в пространства имён: `builtin` (собственные инструменты харнесса), `control-center` (инструменты Control Center) и по одному на каждый подключённый сервер MCP, названное по имени сервера. Сервер, названный `builtin`, `control-center` или `script`, либо имя которого начинается с `external-`, в любом сочетании регистров и с пробелами вокруг или без них, показывается как `external-` и его имя, и ни один инструмент никогда не попадает в `script`.
- Возвращается только то, что скрипт вернул или передал в `text()`, `image()` или `console.*`. Вывод сверх бюджета сохраняет начало и конец, а `read_output` читает остальное.
- `store(key, value)` / `load(key)` хранят JSON-значения для последующих скриптов того же разговора и агента и сохраняются только при завершении скрипта. У скриптов субагента хранилища нет.
- `await tools.ask_user(...)` задаёт вопрос; его ответ также добавляется в результат. Доступны также `sleep(ms)`, `setTimeout`, `limits()` и `models.embed` / `rank` / `classify` (встроенные эмбеддинги).
- `describeTool(name)` и `searchTools(query)` также отвечают за собственные функции скрипта, которые не являются инструментами: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` и `models.*`, в пространстве имён `script`.
- Нельзя вызвать из скрипта: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` и глаголы `vibe_*`.
- Скрипт читает прошлое собственного запуска: `history({start, role, tool, limit})` листает транскрипт разговора (не более 50 строк за вызов; передайте `next_start` предыдущей страницы как `start`), `outputs()` перечисляет выводы инструментов, сохранённые для этого разговора и агента, а `loadOutput(handle)` читает 16 384 символа одного из них. `storedKeys()` перечисляет сохранённые ключи с их размерами. `keep(value, label)` сохраняет большое значение как вывод, который потом может прочитать другой скрипт или `read_output`; сохраняется он только при завершении скрипта (1 МиБ на значение, 64 значения и 16 МиБ за запуск). `limits().returnBudgetChars` показывает, сколько осталось от бюджета вывода. Запуск только для чтения (ревью цели) может читать, но не сохранять и не делать keep. В Claude Code и ACP `history()` работает, а `outputs()`, `loadOutput()` и `keep()` отказывают, потому что Control Center не хранит выводы инструментов этих запусков.
- Ошибка из-за таймаута, переполнения вывода или лимита вызовов сообщает, как её исправить.

Один запуск выполняет одновременно только один скрипт. Лимиты и то, что происходит при каждом из них, описаны на странице [режима кода](/ru-RU/руководство/понятия/режим-кода/#лимиты); каждый скрипт записывается в **Наблюдаемость → Выполнения кода**.

## `eval` — постоянные интерпретаторы

Ячейка Python или JavaScript, переменные, импорты и загруженные данные которой переживают переходы между вызовами. Уровень `exec`; небезопасна при параллельном выполнении. Не может быть вызвана из скрипта `repl`, а ячейка не может вызывать инструменты запуска: чтобы вызывать инструменты из кода, используйте [`repl`](#repl--запуск-скрипта-который-вызывает-ваши-инструменты).

| Аргумент      | Значение                                         |
| ------------- | ------------------------------------------------ |
| `code`        | Ячейка                                           |
| `description` | Обязательно. 5–10 слов для метки в транскрипте   |
| `language`    | `python` (по умолчанию) или `javascript`         |
| `reset`       | Отбросить интерпретатор и сначала начать с чистого |

- Последнее выражение отражается так, как это делает блокнот.
- `display()` работает, датафрейм pandas отрисовывается как таблица, а график matplotlib возвращается как **изображение, которое показывает транскрипт**.
- Идиомы IPython, которые люди набирают рефлекторно, — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — переписываются в обычный код. `%pip` вдобавок вытесняет `sys.modules`, поэтому следующий `import` видит то, что только что установили.
- Ячейка, которая печатает больше своего бюджета вывода, сохраняет первые три четверти и последнюю четверть вместе со строкой о том, сколько символов и изображений отброшено.
- Если интерпретатор умер без запроса, следующая ячейка один раз получает сообщение, что её прежние переменные потеряны.

:::note[Где выполняется ядро]
В изолированной среде разговора, если она у него есть, иначе — в песочнице ОС запуска на хосте. При `--sandbox off` или недоступной песочнице он работает без ограничений, и `eval` запрашивает одобрение выполнения на хосте. Он не запускает изолированную среду, чтобы до неё добраться, — то же правило, которое не даёт вкладке rig запуститься автоматически.
:::

## `bash` в фоне

`bash` с `run_in_background: true` запускает команду и сразу возвращает дескриптор (`b1`, `b2`, …) вместо ожидания. Агент продолжает работать или завершает свой ход и пробуждается, когда команда завершится.

| Аргумент | Значение |
| ------------------- | ------- |
| `run_in_background` | `true`: запустить и сразу вернуть управление |
| `timeout_seconds` | Секунды до того, как команда будет убита: по умолчанию 600, не более 3 600 |
| `notify` | Необязательно. Простой шаблон; каждая строка вывода, которая совпадает с ним, отправляется агенту, пока команда работает (например, `listening on\|FAILED`) |

- Не более 4 фоновых команд одновременно в одном запуске. Каждая убивается по таймауту и при завершении запуска вместе со всеми процессами, которые она запустила.
- Когда команда завершается, агент получает уведомление с кодом выхода, последними 2 000 символами вывода и дескриптором `read_output` для остального.
- Агент, единственная оставшаяся работа которого — фоновая команда, ждёт без вызова модели, а сторож тишины запуска приостанавливается на время ожидания.
- `bash_output(handle)` читает состояние команды и её последний вывод; `bash_kill(handle)` останавливает её. Оба сообщают, если результат уже был доставлен.
- Скрипт не может запустить фоновую команду. У Claude Code есть собственный фоновый Bash; Control Center держит такой запуск открытым не дольше 10 минут после хода, оставившего задачу запущенной.

## `compact` — освободить место в окне контекста

Сжимает старый контекст разговора перед следующим вызовом модели, сохраняя то, что называет `focus` (не более 1 000 символов). Самые новые ходы остаются дословно. Строка бюджета хода агента показывает использование контекста при 70, 80 и 90%; инструмент стоит вызывать после отметки около 70% перед длинным новым этапом работы. Хук `preCompact` владельца сервера может добавить к фокусу ([Shell-хуки](/ru-RU/руководство/справка/конфигурация-агента/#shell-хуки)). После сжатия сервер добавляет блок «Still in flight»: цель, ожидающие пробуждения, открытые запросы, фоновые команды, чек-лист и сохранённые ключи, каждый с вызовом, который его восстанавливает.

## `ask_user` — задать вопрос человеку

Уровень `read`. **Единственный** способ, которым запуск может спросить что-либо у оператора. Он отрисовывает в разговоре нумерованную карточку и блокируется, пока кто-нибудь не ответит, не пропустит её или пока вопрос не истечёт по тайм-ауту. Никогда не пишите вопрос как сообщение в чате — это завершает ход.

| Аргумент          | Значение                                   |
| ----------------- | ------------------------------------------ |
| `question`        | Что спросить                               |
| `context`         | Необязательно: почему вы спрашиваете и что зависит от ответа |
| `options[]`       | Варианты, каждый `{label, description?}`   |
| `allow_free_text` | Принимается ли ответ, набранный вручную    |
| `multi_select`    | Можно ли выбрать несколько вариантов       |

Пропуск — это успех: действуйте на основании заявленного допущения и не спрашивайте снова. Тайм-аут — это ошибка с той же инструкцией. Запросы разрешения («можно мне это сделать?») — отдельный шлюз, и они отрисовываются в разговоре той же карточкой.

Регистрируется, только когда существуют и порт вопросов, и целевое пространство. Без подключённого человека вызов **падает**, а не блокируется навсегда, — та же позиция отказа по умолчанию, которую занимает `prompt` ограничения без подключённого подтверждающего.

## `vibe_*` — управление фоновыми воркерами

Регистрируются, только пока включён [режим vibe](/ru-RU/руководство/практические-руководства/направлять-фоновые-воркеры/). Все пять относятся к уровню `read`: шлюз должен стоять на инструментах воркера, там, где правка действительно происходит.

| Инструмент   | Аргументы                                | Примечания                                  |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | Возвращает управление сразу; воркер продолжает работу |
| `vibe_send`  | `worker_id`, `message`                   | Дописывает к заданию и запускает заново     |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | Блокируется, пока он не завершится          |
| `vibe_kill`  | `worker_id`                              | Останавливает его                           |
| `vibe_list`  | —                                        | Уровень, статус, затраченное время и последний результат |

`tier` — это `fast` (механическая работа с чёткой спецификацией) или `good` (проектирование, суждение или проверка результата воркера `fast`).
