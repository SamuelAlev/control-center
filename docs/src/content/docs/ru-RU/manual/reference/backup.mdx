Всё, что Control Center умеет копировать, передавать или принимать, и точная форма каждого
артефакта. О том, как снять резервную копию на практике, см.
[Резервное копирование и восстановление](/ru-RU/руководство/практические-руководства/резервное-копирование-и-восстановление/); о том, почему хранилище
устроено именно так, см. [Рабочие пространства и изоляция](/ru-RU/руководство/понятия/рабочие-пространства/).

## Артефакты

Есть три артефакта копирования баз данных, с разными областями действия и политиками удаления.

| Артефакт                | Кем создаётся                | Форма                                 | Что охватывает                |
| ----------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **Снимок установки**    | `server.backupNow`           | **Каталог** с меткой времени          | Все базы данных установки     |
| **Резервная копия рабочего пространства** | конвейер `Workspace backup`  | Каталог с меткой времени с одним `.db`  | База данных одного рабочего пространства |
| **Экспорт рабочего пространства** | `workspace.export`           | Один **файл** `.db`                   | База данных одного рабочего пространства |

Все они создаются с помощью SQLite `VACUUM INTO`, что безопасно для работающей базы данных
с WAL: команда берёт транзакцию чтения, создаёт дефрагментированную и транзакционно
согласованную копию и никогда не требует останавливать сервер.

Эти файлы и скачанные копии **не шифруются при хранении** средствами Control
Center. Зашифрованная сквозным шифрованием передача защищает байты в пути между
сопряжённым клиентом и его `cc_server` — как на прямых соединениях, так и через
брокерское реле. Защищайте локальное хранилище и копии за пределами машины
отдельно; сервер и любой авторизованный получатель могут читать файлы баз данных.

## Структура снимка

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Структура в точности повторяет живой каталог данных — именно поэтому восстановление
установки сводится к копированию обратно, а не к преобразованию. Имя каталога — это метка
времени UTC, в которой `:` и `.` заменены на `-`, поэтому оно безопасно для файловой
системы Windows и сортируется хронологически как обычная строка.

Запланированные резервные копии рабочих пространств лежат отдельно, по пути `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`. У каждой есть `manifest.json` только для этого одного файла и нет `global.db`; они не являются снимками установки. Восстановление сохраняет заменяемую базу данных в той же папке, под именем `<timestamp>-pre-restore`. Шаг удаления по сроку хранения в недельном конвейере удаляет только резервные копии его собственного рабочего пространства старше настроенного срока (по умолчанию 30 дней); снимки установки, созданные вручную, этим шагом никогда не ротируются. `server.listBackups` перечисляет только снимки установки, включая непроверенные; `workspace.listBackups` перечисляет резервные копии по расписанию одного рабочего пространства.

Удаление рабочего пространства оставляет этот каталог на месте. Расписание рабочего
пространства останавливается вместе с ним, поэтому эти резервные копии больше никто не
ротирует, и они остаются, пока их не удалит владелец установки. Их показывает
`server.listOrphanedBackups`.


### `manifest.json`

| Поле                       | Тип             | Значение                                                            |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                   | int             | Формат манифеста. Сейчас `2`                                        |
| `created_at`               | ISO-8601 UTC    | Когда был снят снимок                                               |
| `global`                   | object          | Запись о `global.db`. Отсутствует в плановой резервной копии рабочего пространства |
| `workspaces[]`             | array           | По одной записи на каждое снятое рабочее пространство               |
| `workspaces[].workspace_id`| string          | Рабочее пространство, которому принадлежит этот файл                |
| `skipped_workspaces[]`     | array           | Рабочие пространства, которые резервная копия **не** смогла снять   |
| `skipped_workspaces[].workspace_id` | string | Рабочее пространство, которое пропущено |
| `skipped_workspaces[].reason` | string | `no_file`, `damaged` или `failed` |

`global` и каждая запись `workspaces[]` описывают один скопированный файл, измеренный по копии после её записи:

| Поле | Тип | Значение |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`           | string | Путь относительно корня снимка: `global.db` или `<workspaceId>/workspace.db` |
| `bytes`          | int    | Размер копии                                                                   |
| `sha256`         | string | SHA-256 копии в шестнадцатеричной записи, в нижнем регистре                    |
| `quick_check`    | string | Что SQLite сказал о копии в `quick_check`: `ok` или его замечание              |
| `user_version`   | int    | Версия схемы копии                                                             |
| `application_id` | int    | `application_id` SQLite у копии                                                |

Рабочее пространство пропускается, когда оно зарегистрировано, но в него никогда не писали (`no_file`), когда его база данных не проходит проверку целостности (`damaged`; повреждённая копия никогда не снимается) или когда его копирование либо проверка этой копии не удались (`failed`). В любом случае снимок всё равно создаётся до конца, а манифест называет то, чего не хватает. Манифест записывается последним.

### Полнота

`server.listBackups` сообщает для каждого снимка флаг `complete`. Он равен false, когда манифест отсутствует, не читается или имеет другой формат, когда файл, который он называет, отсутствует или имеет другой размер, либо когда копия не прошла свою проверку. Приложение показывает такой снимок как **Не проверен**. Снимки, снятые до формата `2`, находятся в этом состоянии.

Непроверенный снимок всё равно попадает в список: снимок, которого оператор не видит, — это снимок, который он считает, что у него есть. Когда манифест не читается, список опирается на саму структуру и сообщает о тех файлах `<workspaceId>/workspace.db`, которые находит, — их по-прежнему можно по отдельности принять через `workspace.import`, хотя снимок в целом не может восстановить установку.

Снимок или плановая резервная копия в списке несёт `pinned_reason: "last_good_copy"`, пока хранит самую свежую проверенную копию рабочего пространства, живая база данных которого повреждена. Шаг хранения пропускает её, пока это рабочее пространство не будет восстановлено.

## Чего в резервной копии нет

Оба артефакта — **только базы данных**. Каталог рабочего пространства содержит больше, чем
его базу данных, и ничего из остального не переносится:

| Путь                                | В снимке?      | В экспорте рабочего пространства? |
| ----------------------------------- | -------------- | ---------------------- |
| `global.db`                         | Да             | Нет                    |
| `<workspaceId>/workspace.db`        | Да             | Да (это *и есть* файл) |
| `<workspaceId>/code_index.db`       | Нет            | Нет                    |
| `<workspaceId>/blobs/`              | Нет            | Нет                    |
| `<workspaceId>/skills/`             | Нет            | Нет                    |
| `<workspaceId>/agents/`             | Нет            | Нет                    |
| `<workspaceId>/chat_credentials/`   | Нет            | Нет                    |
| `<workspaceId>/spaces/<spaceId>/`   | Нет            | Нет                    |
| `<workspaceId>/pr_clones/`          | Нет            | Нет                    |
| `secrets.json`                      | Нет            | Нет                    |
| `models/`                           | Нет            | Нет                    |
| `meetings/<meetingId>/`             | Нет            | Нет                    |
| `rigs/`                             | Нет            | Нет                    |
| `_agent_hooks/`                     | Нет            | Нет                    |

Часть этого можно воссоздать — `spaces/` содержит worktree с копированием при записи, которые заново создаются из репозиториев, `pr_clones/` — это кэш, `code_index.db` перестраивается, `models/` скачивается заново, `rigs/` — это состояние машины. Часть — нет: `blobs/` содержит вставленные изображения, на которые ссылаются строки базы данных, `skills/` и `agents/` содержат файлы, с которыми работает агент, а `secrets.json` содержит все ключи сопряжения, учётные данные провайдеров и настройки SSO установки. О том, как охватить остальное, см. [Резервное копирование и восстановление](/ru-RU/руководство/практические-руководства/резервное-копирование-и-восстановление/#копируйте-резервные-копии-за-пределы-машины).
:::note[Секреты хранятся вне баз данных]
`workspace.db` — это всё рабочее пространство: разговоры, журналы запусков, связи с репозиториями, определения окружений и участники. Токены вебхуков конвейеров и секреты вебхуков синхронизации тикетов хранятся в `secrets.json`: база данных содержит ссылку на каждый из них, а индекс маршрутов содержит хэш с ключом каждого токена. Поэтому рабочее пространство, восстановленное на другой установке, не получает вебхуков, пока его триггеры не будут сохранены там заново. Входы провайдеров, ключи устройств и пользовательские секреты хранятся в `global.db` и `secrets.json`.
:::

:::note[Токены чатов намеренно остаются вне копии]
То, что `chat_credentials/` лежит рядом с базой данных, а не внутри неё, — причина, по которой
рабочее пространство, переданное кому-то другому, не несёт живых токенов ботов. См.
[справочник по чат-мосту](/ru-RU/руководство/справка/чат-мост/).
:::

## Операции

RPC резервного копирования установки, а также экспорт и импорт рабочих пространств доступны
только `fullClient`: сопряжённый телефон не может их запустить. На сервере без подключённого
порта резервного копирования, например на демонстрационном сервере, они отсутствуют
полностью — не отклоняются, а структурно отсутствуют.

| Операция             | Тип        | Область   | Минимальная роль | Аргументы     | Возвращает                    |
| -------------------- | ---------- | --------- | ---------------- | ------------- | ----------------------------- |
| `server.backupNow`   | изменение  | Установка | **владелец** установки | нет      | `{ok, path}`                  |
| `server.listBackups` | чтение     | Установка | **владелец** установки | нет      | `{backups: [...]}`            |
| `server.deleteBackup` | изменение | Установка | **владелец** установки | `name` | `{ok}` |
| `server.listOrphanedBackups` | чтение | Установка | **владелец** установки | нет | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | изменение | Установка | **владелец** установки | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | чтение | Рабочее пространство | `admin` | нет | `{backups: [...]}` |
| `workspace.deleteBackup` | изменение | Рабочее пространство | `owner` | `name` | `{ok}` |
| `workspace.export`   | чтение    | Рабочее пространство | `admin`      | нет           | `{ok, path}`                  |
| `workspace.import`   | изменение  | Рабочее пространство | `owner` и владелец сервера | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | чтение | Рабочее пространство | `owner` и владелец сервера | нет | `{holds: [...]}` |
| `workspace.importHolds.resolve` | изменение | Рабочее пространство | `owner` и владелец сервера | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | изменение  | Установка* | `owner`         | `id`          | строка реестра помечена удалённой |

* `workspace.delete` не имеет области действия, потому что строка, которую он помечает, живёт
в глобальном реестре; его обработчик проверяет членство вызывающего в указанном рабочем
пространстве и требует `owner`.

`path` в каждом ответе — это путь на **хосте сервера**.

`server.listOrphanedBackups` возвращает по одной записи на каждое рабочее пространство,
которое больше не активно: `workspace_id`, `workspace_name`, если реестр ещё его знает,
и `backups`. Удалённое рабочее пространство уже не может пройти проверку роли, поэтому
его резервные копии принадлежат владельцу установки. `server.deleteOrphanedBackup`
отказывает для активного рабочего пространства: его резервные копии остаются за
`workspace.deleteBackup` и ролями самого этого рабочего пространства. Обе операции
удаления принимают только имя каталога с меткой времени из списка, а не путь.

`workspace.importHolds.list` возвращает то, что удержал импорт. У каждого удержания есть `id`, `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` или `invite`), `payload`, который он вернул бы на место, `imported_at` и `source_install_id`. `workspace.importHolds.resolve` с `accept: true` предоставляет право снова, а с `false` убирает его. `applied` равно false, когда тот, кому или чему предназначалось право, уже не состоит в рабочем пространстве.

:::note[Снимок всей установки доступен только владельцу на обоих путях]
`server.backupNow`, `server.listBackups` и `server.deleteBackup` требуют роли
**владельца** установки (`ServerAuthority.serverOwner`) — та же проверка, что и у
`GET /backup/snapshot`. Снимок охватывает базу данных каждого рабочего пространства,
поэтому быть администратором одного рабочего пространства недостаточно, чтобы
управлять остальными. Удаление принимает только имя каталога с меткой времени из
списка, а не произвольный путь на сервере, и удаляет весь снимок (включая непроверенные снимки).
Экспорт отдельных рабочих пространств и загрузки плановых резервных копий остаются за администратором рабочего пространства.
:::

:::note[Восстановление — дело владельца сервера]
`workspace.import` и `POST /backup/restore` заставляют сервер принять файл базы данных, строки которого он затем считает своими: связи с репозиториями и то, кто их создал, определения окружений, которые работают на хосте, пути worktree и журналов. Поэтому обоим нужен владелец сервера (`ServerAuthority.serverOwner`), который также должен быть владельцем рабочего пространства. Все остальные, а также любой вызывающий на хосте без записанного владельца получают отказ с `server_owner_required`. Триггеры, представления, столбцы и ограничения, которые приносит файл, не принимаются.
:::


### Ответ `server.listBackups`

Сначала самые новые, отсортированные по имени каталога (это метка времени, поэтому порядок
сохраняется даже для снимка, манифест которого не удалось прочитать).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` опускается, когда манифест не удалось прочитать. `bytes` верхнего уровня — это
реальный размер всего каталога на диске, а не сумма из самого манифеста: вопрос, который
задаёт оператор, удаляющий лишние снимки, — сколько занимает каталог, а не сколько
резервная копия собиралась записать.

Каждый `workspaces[].path` — это ровно то, что `workspace.import` принимает как
`source_path`. Это сделано намеренно: «восстановить это рабочее пространство из этого
снимка» *и есть* операция импорта, поэтому они не могут разойтись в разном обращении
с одним и тем же файлом.

### Проверка `workspace.import`

Прежде чем что-либо будет заменено, файл-кандидат копируется в промежуточный файл рядом с целевым и проверяется там. Отказ ничего не затрагивает и несёт свой вид как `data.kind`.

| Условие                                          | Результат                                                       |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| Файл не существует | Отказано, `import.missing_source` |
| Не читаемая база данных SQLite или не проходит `quick_check` | Отказано, `import.damaged` |
| Он получен из снимка, и его SHA-256 отличается от записанного в манифесте | Отказано, `import.checksum_mismatch` |
| Его записала более новая версия сервера | Отказано, `import.newer_schema` |
| Другой `application_id` или нет `workspace_meta` | Отказано, `import.foreign_file` |
| Его не удаётся привести к схеме этого сервера | Отказано, `import.schema_mismatch` |
| Его вебхуки или приглашения уже направляются в другое рабочее пространство | Отказано, `import.route_conflict` |
| Записанный идентификатор рабочего пространства ≠ целевого | **Разрешено**. Его строки переназначаются целевому рабочему пространству. Так рабочее пространство дублируют или восстанавливают под новым идентификатором |
| Записанный идентификатор установки ≠ этой установки | **Разрешено**. Идентификаторы его пользователей принадлежат той установке и здесь не разрешатся |

При принятии промежуточный файл приводится к схеме этого сервера и затем должен ей точно соответствовать. Права, которые файл не вправе выдать сам себе, из него вынимаются: одобрения на запуск определения окружения на хосте сбрасываются, а правила действий, которые разрешают или запрашивают подтверждение, разрешения на запуск в песочнице, права доступа к репозиториям выше чтения, роли выше участника и приглашения в эти роли становятся удержаниями, которые проверяет владелец сервера. Импортирующий сохраняет роль владельца или получает её. Заменяемая база данных сохраняется как плановая резервная копия с именем `<timestamp>-pre-restore`, промежуточный файл переносится на место при закрытых подключениях рабочего пространства, `code_index.db` удаляется для перестроения, а индексы FTS перестраиваются.

## Маршруты передачи

Операции экспорта/импорта и перечисления снимков выше оперируют путями на стороне
сервера, а это исчерпывающий ответ только тогда, когда сервер — ваша собственная
машина. Эти маршруты в форме HTTP переносят байты резервных копий **внутри того
же аутентифицированного и зашифрованного сквозным шифрованием туннеля ресурсов**,
что и другие чувствительные ресурсы, независимо от того, прямое соединение RPC
или через посредника. Это не публичные эндпоинты передачи файлов по HTTP:
запрос к одному из них на публичном слушателе возвращает `426 Upgrade Required`,
даже с loopback. В зашифрованном туннеле устройство, аутентифицированное Noise,
должно совпадать с `d`; обработчик дополнительно проверяет подпись устройства на
его целевой строке, используя PSK сопряжения и роль ниже.

| Маршрут                 | Метод  | Параметры запроса | Подписанная цель               | Требуется               |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **Администратор** рабочего пространства |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **Владелец** установки  |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **Администратор** рабочего пространства; **владелец** установки, если рабочее пространство удалено |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **Владелец** установки, который также **владелец** рабочего пространства (иначе `403` с `server_owner_required`) |

`w` — идентификатор рабочего пространства, `n` — имя каталога снимка или резервной копии
по расписанию, `d` — идентификатор вызывающего устройства, `s` — подпись. В
`/backup/snapshot` `n` сопоставляется со списком резервных копий, а не присоединяется к
корню резервных копий, поэтому маршрут нельзя навести на каталог, который список не
показал бы. В `/backup/stored` это должно быть имя в виде метки времени, а файл должен
быть настоящим файлом внутри собственного каталога резервных копий этого рабочего
пространства.

| Статус | Причина                                                                             |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | Отсутствует обязательный параметр запроса, имя резервной копии недопустимо, тело загрузки пусто или загруженный файл отклонён (тело — `{error, kind}` с видом `import.*`) |
| `403`  | Неизвестное или отозванное устройство, неверная подпись или у вызывающего нет нужной роли |
| `404`  | На этом хосте нет порта резервного копирования или указанный снимок, резервная копия либо файл рабочего пространства не существует |
| `405`  | `/backup/restore` вызван с методом, отличным от `POST`                              |
| `413`  | Тело загрузки превышает 8 ГиБ по объявленному content-length или по фактически прочитанным байтам |
| `426`  | Любой прямой запрос к маршруту передачи на публичном HTTP-слушателе; используйте зашифрованный туннель ресурсов сопряжённого клиента |
| `500`  | Экспорт или архивация завершились ошибкой на стороне сервера                        |

Все три скачивания отвечают `Cache-Control: no-store` и `Accept-Ranges: none`.
`/backup/workspace` и `/backup/snapshot` создают **свежую** копию на каждый запрос и удаляют
её после передачи потоком, поэтому кэшированный ответ или ответ с докачкой склеил бы байты
из двух разных экспортов в один файл, который выглядит валидным и таковым не является.

`/backup/stored` — исключение: он передаёт резервную копию по расписанию потоком как
`<workspaceId>-<name>.db` и оставляет файл на месте, потому что этот файл и есть резервная
копия.

`/backup/snapshot` возвращает `<name>.zip`, где записи заданы относительно корня снимка,
поэтому распаковка воспроизводит `manifest.json` + `global.db` + `<workspaceId>/workspace.db`.
Записи пишутся в отсортированном порядке, поэтому два архива одного и того же снимка — это
один и тот же архив.

`/backup/restore` пишет тело потоком прямо в промежуточный файл, а не буферизует его,
ограничивает его до и во время чтения и удаляет промежуточный файл на **любом** пути
выхода, включая отказ.

::::caution[Прямое соединение и реле используют одну и ту же зашифрованную передачу]
Реле переносит запросы ресурсов, потоковые ответы и байты загрузок как шифротекст;
оно не может читать содержимое резервных копий. Путь на стороне сервера остаётся
путём на хосте сервера, а не файлом на реле. Доступ по-прежнему требует
сопряжённого устройства, подписи цели и применимой роли рабочего пространства или
установки. Ни один из транспортов не шифрует полученные файлы резервных копий при
хранении.
::::

## Пути и ограничения

| Что                            | Значение                                                     |
| ------------------------------ | ------------------------------------------------------------ |
| Снимки                         | `<dataDir>/backups/<timestamp>/`                             |
| Запланированные резервные копии рабочих пространств | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Экспорты рабочих пространств   | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| База данных, заменённая восстановлением | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Базы данных до того, как обновление изменило их формат | `<dataDir>/pre_upgrade/` и `<dataDir>/<workspaceId>/pre_upgrade/`, по две самые новые из каждой |
| Промежуточные файлы передачи   | `<dataDir>/backups/transfer/` — рабочая область, которую очищает маршрут, записывающий в неё |
| Имя архива снимка              | `<snapshot directory name>.zip`                              |
| Потолок загрузки               | 8 ГиБ на каждую зашифрованную загрузку в `/backup/restore`   |
| Срок хранения                  | Снимки установки: удаление вручную. Резервные копии рабочих пространств: недельный конвейер, по умолчанию 30 дней, или удаление вручную. Резервные копии удалённого рабочего пространства: только удаление вручную |

Каталоги `exports/`, `transfer/` и `workspace-backups/` не являются снимками установки
и исключены из `server.listBackups`. Только у последнего каталога есть автоматическое
удаление по сроку хранения, и только пока существует его рабочее пространство; удаление снимка установки требует явного действия
владельца установки.
