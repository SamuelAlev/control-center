В этом руководстве показано, как выяснить, почему агент не выдаёт запуски.

Двигайтесь сверху вниз: сначала собственные запуски агента, затем его бэкенд, затем сервер, затем хост.

## 1. Проверьте историю запусков агента

**Настройки → Рабочее пространство → Агенты** → выберите агента → **Журнал**.

Для каждого запуска показаны бейдж состояния, длительность («Running…», пока запуск выполняется), время начала и завершения, его PID и использованный адаптер. **Просмотр** открывает необработанный поток событий этого запуска. **Остановить** завершает выполняющийся процесс и помечает запуск как «Killed by user»; **Прервать выполнение** в заголовке делает то же для всех выполняющихся запусков этого агента.

Читайте это так:

- **Запусков нет вообще** — диспетчеризация так и не произошла. Упоминания в композере — это `@` плюс символы слова (буквы, цифры, подчёркивание). Сопоставление идёт по точному совпадению с именем агента или по префиксу, поэтому `@code-reviewer` разбирается как `code` и всё равно может разбудить агента с именем `code-reviewer`. Имя с пробелом нельзя упомянуть одним токеном. Тогда переходите к шагу 2.
- **Запуск, сразу завершившийся с ошибкой** — откройте **Просмотр**. Сбой запуска бэкенда виден здесь как ошибка процесса.
- **Запуск, застрявший на «Running…»** — остановите его, затем проверьте **Таймаут тишины** у агента на вкладке **Настройки**. Если таймаут не задан, используется значение по умолчанию для режима.
- **Завершённый запуск без полезного результата** — статус в журнале запуска остаётся `completed` и у запуска, завершившегося без объявленного результата; честный сигнал — текст сводки, а не бейдж.

На вкладке «Журнал» стоимость не отображается. Чтобы увидеть расходы, воспользуйтесь таблицей по каждому агенту в разделе **Наблюдаемость → Инсайты**.

## 2. Проверьте бэкенд агента

**Настройки → Сервер → Провайдеры моделей** (`/settings/server/providers`).

Список **Обнаруженные раннеры** показывает каждый адаптер с результатом пробы — установленную версию, «Проверка…» или «Не найдено» — а также найденный путь и метки возможностей для обнаруженного CLI. Нажмите **Обновить** в заголовке страницы, чтобы запустить пробу заново.

Проба выполняется на машине, где размещён `cc_server`, а не на той, которую вы видите перед собой. Если вы работаете в веб-клиенте или на привязанном устройстве, «Не найдено» означает, что CLI отсутствует на хосте сервера.

Два момента, которые стоит проверить:

- **Задан ли у агента адаптер вообще.** Агент с пустым адаптером направляется в **Control Center (built-in)**, и журнал запуска записывает `cc-harness`, поэтому в транскрипте указано, что именно выполнялось. Если и модели нет, он запрашивает у Anthropic модель по умолчанию — и это завершается ошибкой `No credential for provider "anthropic"`, если вы не подключили аккаунт Anthropic. Поставляемые специалисты идут без адаптера.
- **Есть ли модель у встроенного адаптера.** Его список моделей собирается на лету из провайдеров, подключённых ниже на этой же странице, поэтому провайдер без сохранённых учётных данных не даёт ни одной модели.

Сам каталог адаптеров фиксирован — зарегистрировать новый адаптер нельзя. Что здесь можно менять для каждого адаптера, так это его аргументы запуска и переменные окружения. Учтите, что переопределение переменных окружения на уровне адаптера молча перекрывает подключённый аккаунт провайдера, когда разрешаются учётные данные.

## 3. Проверьте сервер

**Настройки → Сервер → Подключение и состояние** (`/settings/server/connection`) показывает, с каким сервером общается этот клиент и что он сообщает.

Для headless-сервера те же сведения даёт `GET /healthz` без клиента. Он не требует аутентификации и по замыслу открыт для CORS:

```
curl http://localhost:9030/healthz
```

Он возвращает статус сервера, время работы в секундах, число активных подключений, порт привязки, версию сборки и git SHA, версию схемы рабочего пространства, версию каталога RPC, идентификатор сервера, его имя и отпечаток идентичности, признак небезопасной привязки и блок `codeGraph` со счётчиками `watching` / `indexing` / `pending`. Когда к кэшу были обращения, он также включает блок `caches`; демонстрационный сервер добавляет `demo: true`.

Два момента, о которых стоит знать, когда изменение «работает в тестах, но не в приложении»:

- Настольное приложение запускает **собранный заранее** бинарник `cc_server`, предпочитая его сборке из исходников. Новая операция RPC или инструмент MCP не появятся, пока бинарник не пересобран, а при запуске в журнал пишется предупреждение, если git SHA дочернего процесса отличается от SHA приложения.
- Настольное приложение завершает порождённый сервер, который не вывел баннер готовности в течение 20 секунд, и переходит на экран ошибки.

## 4. Проверьте хост

**Настройки → Сервер → Диагностика и конфиденциальность** (`/settings/server/diagnostics`) — это страница уровня хоста. На ней есть:

- **Песочница** — главный переключатель, обнаруженный бэкенд, подсказка об установке и переключатели возможностей по умолчанию. От сервера приходит только обнаруженный бэкенд; см. предупреждение ниже. Элемента сброса нет.
- **Семантический поиск** — жизненный цикл локальной модели эмбеддингов: установлена, скачивается с указанием процента, не установлена или ошибка установки. Пока она не установлена, поиск по памяти и по коду остаётся только по ключевым словам.
- **Поведение системы** — не давать компьютеру засыпать, пока работают агенты.
- **Движок синхронизации** — отдельные аварийные выключатели для хранилищ тикетов, сообщений и заметок. Это аварийные люки для возврата к подпискам на полный снимок; изменение влияет только на новые подписки, поэтому полностью вступает в силу после перезагрузки.
- **Уровень журнала** — повысьте его перед воспроизведением сбоя.
- **Конфиденциальность** — можно ли передавать необработанное содержимое diff модели агента и отправляются ли отчёты о сбоях.

:::caution[Этот раздел сообщает о хосте, а его элементы управления — на стороне клиента]
Обнаружение и принудительное применение теперь согласованы: там, где детектор сообщает о нативном бэкенде, запуски агентов на этом хосте действительно оборачиваются в него. Но детектор — единственное живое в этом разделе. Главный переключатель, выбор бэкенда и переключатели возможностей по умолчанию — это предпочтения, хранящиеся на вашем устройстве, и сервер не читает ни одно из них: собственный переключатель сервера — `--sandbox` (`on` по умолчанию, `off` для отказа), а для любого агента, оставленного на «По умолчанию рабочего пространства», сервер откатывается к своему консервативному значению по умолчанию: без git push, без GitHub API, без ключа тикетов, сеть включена.

Так что предупреждению здесь стоит уделить внимание, но обычно не оно причина сбоя агента. Чтобы убедиться, в каком состоянии находится сервер, прочитайте журнал его запуска: он выводит `agent sandbox ON` с пометкой о бэкенде, `no OS-native agent sandbox on this host` с подсказкой об установке или `agent sandbox DISABLED by --sandbox off`. `GET /healthz` не содержит поля о песочнице.

Там, где бэкенда нет — в Windows всегда, в Linux или WSL2 без `bwrap` и `socat` — запуски **не** изолированы песочницей, и их ограничивают собственная рабочая копия разговора, возможности, определяющие, какие учётные данные в неё выпускаются, ограничения действий, очистка окружения и поверхность инструментов, которую допускает режим.
:::

## Типичные сбои

### Запуск так и не начинается, а адаптер отображается как «Не найдено»

Установите CLI **на хосте сервера**, затем нажмите **Обновить** на странице «Провайдеры моделей». Или переключите агента на встроенный адаптер — ему CLI не нужен — и подключите провайдера на той же странице.

### Агент не может отправить изменения или открыть pull request

Шлюзом служат его возможности. Откройте **Настройки → Рабочее пространство → Агенты** → агента → **Права песочницы**, включите переключатель и включите **Разрешить git push** и **Разрешить вызовы GitHub API**. Если оставить переключатель на «По умолчанию рабочего пространства», агент не получит ни одной из них.

### Семантический поиск не даёт ничего полезного

Проверьте **Настройки → Сервер → Диагностика и конфиденциальность → Семантический поиск**. Пока модель эмбеддингов не установлена, поиск идёт только по ключевым словам. Строки, записанные до установки модели, никогда не дозаполняются, поэтому и после неё остаются только по ключевым словам.

### Сервер вообще не запускается

Нативные библиотеки обязательны, и режима с ограниченной функциональностью нет. Из-за отсутствующей dylib `cc_server` отказывается запускаться и называет виновника в ошибке. Подготовьте нативные библиотеки с помощью `scripts/natives/build_natives.sh` и пересоберите бинарник сервера.

### Действие молча отклоняется

Решение ограничения `prompt` при отсутствии подключённого одобряющего отклоняется — так и задумано. Проверьте правила рабочего пространства в разделе **Настройки → Рабочее пространство → Разрешения агента**.
