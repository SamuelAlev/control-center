Это руководство показывает, где хранятся учётные данные, которые использует
Control Center, и как их изменить.

**На машине, за которой вы печатаете, не хранится ничего.** Все учётные данные
живут на сервере; какие именно ответят на конкретный запрос, зависит от того,
есть ли за ним человек.

| Учётные данные | Где хранятся | Кто их использует |
| --- | --- | --- |
| Учётные данные хоста кода и тикетов | Файл секретов сервера с правами 0600, с ключом по вашему идентификатору пользователя | Всё, что запрашиваете вы: поверхность PR, запуски ваших агентов, ваши образы |
| Идентичность приложения сервера | Тот же файл, плюс `server_settings` для всего, что не является секретом | Работа, которую не запросил человек: вебхуки, опрос PR, синхронизация тикетов |
| Ключи провайдеров моделей и токены OAuth | Собственное хранилище учётных данных сервера | Встроенный адаптер, для каждого рабочего пространства в установке |
| Токены бота Slack | `<dataDir>/<workspaceId>/chat_credentials/` на сервере | Чат-мост этого рабочего пространства |
| Учётные данные внешней CLI | То, что использует эта CLI | Claude Code, на хосте сервера |

## Два вида учётных данных GitHub, и они отвечают на разные вопросы

- **Ваши** — из входа в систему (поток устройства) или из вставленного токена.
  Именно их использует каждый запрос, сделанный *от вашего имени*, поэтому
  комментарий, опубликованный за вас, несёт ваше имя. Другой участник не может их
  прочитать и подключает свои собственные
- **Данные сервера** — из GitHub App, которую зарегистрировал оператор. Они
  отвечают на всё, за чем нет вызывающего, — поэтому доступ к хосту кода не
  пропадает, когда кто-то уходит или меняет токен

Ваши задаются в карточке **Хостинг кода** в разделе **Настройки → Рабочее
пространство → Профиль и идентичность**, а данные сервера — в карточке **Приложения
провайдера** в разделе **Настройки → Сервер → Единый вход**. См.
[Настроить интеграцию GitHub](/ru-RU/руководство/практические-руководства/интеграция-github/)
и [Создать GitHub App](/ru-RU/руководство/практические-руководства/github-app/).

:::note[Есть ещё экран, доступный только по URL]
`/workspaces/<workspaceId>/api-keys` показывает те же две карточки, что и первый
шаг первоначальной настройки. **В интерфейсе к нему нигде нет пункта навигации**;
попасть на него можно, только введя URL. Вместо него используйте **Настройки →
Рабочее пространство → Профиль и идентичность**.
:::

## Задать ключи провайдеров моделей

Встроенный адаптер сам проходит аутентификацию у провайдеров, и эти учётные данные
живут на сервере.

1. Перейдите в **Настройки → Сервер → Провайдеры моделей**
2. Прокрутите до **Провайдеры и модели**
3. Подключите провайдера: OAuth в браузере для OpenAI, Codex, Cursor и Kimi Code;
   API-ключ для Anthropic и остальных

Полный список и порядок добавления собственной конечной точки — в разделе
[Управлять адаптерами и моделями](/ru-RU/руководство/практические-руководства/адаптеры/).

Эти учётные данные **глобальны для хоста**: один ключ обслуживает каждое рабочее
пространство в установке. Токены OAuth обновляются до истечения срока действия.

Внешние CLI адаптеров хранят свои учётные данные отдельно, в собственной
конфигурации, на хосте сервера — Control Center ими не управляет. Проходите
аутентификацию Claude Code так, как описано в её собственной документации, на
машине, где запущен `cc_server`.

Диалог **Переменные окружения** у каждого адаптера выглядит подходящим местом для
такого ключа, но это не так: он пишет на ваше устройство, а сервер читает
собственную копию, и ничто их не связывает. См.
[Управлять адаптерами и моделями](/ru-RU/руководство/практические-руководства/адаптеры/).

## Подключить вендора тикетов

Карточка **Тикеты** в разделе **Настройки → Рабочее пространство → Основные**
содержит обе половины одного решения: в каком вендоре живут ваши тикеты и какие
учётные данные для этого нужны. Выбор **Локальный** скрывает строку с учётными
данными — локальные тикеты живут в собственной базе данных этого сервера, и
аутентифицироваться им негде.

Ваш ключ хранится на сервере с привязкой к вашему идентификатору пользователя, как
и ключ хоста кода. Свой ключ Linear сервер хранит отдельно (в карточке **Приложения
провайдера**) — именно на нём работает синхронизация тикетов, когда её не запросил
человек. В песочницу агента ключ тикетов не внедряется; агенты пишут тикеты через
инструменты Control Center, которые спрашивают правило **Писать во внешний
трекер**. См. [Настроить интеграцию Linear](/ru-RU/руководство/практические-руководства/интеграция-linear/).

## Смена и отзыв

- **Учётные данные GitHub**: нажмите **Отключить**, затем войдите снова или
  вставьте новый токен. Отзовите старый на GitHub
- **Приложение сервера**: создайте новый закрытый ключ или секрет клиента на
  странице приложения в GitHub, вставьте его в карточке **Приложения провайдера** и
  нажмите **Тест**
- **Провайдер моделей**: в его строке выйдите из системы (OAuth) или удалите ключ,
  затем подключите его снова
- **Slack**: заново вставьте токены в диалоге подключения. См.
  [Настроить интеграцию Slack](/ru-RU/руководство/практические-руководства/интеграция-slack/)

## Устранение неполадок

### Список PR пуст, но мой токен работает в `curl`

Проверьте подзаголовок строки **Хостинг кода**. Если там назван другой источник
(«через приложение этого сервера», «из окружения»), отвечает не тот набор учётных
данных, который вы проверяете, — ваши не были сохранены.

### Токен принимается, но последующие запросы падают

Токен проверяется ровно в том виде, в каком он сохранён, поэтому строка называет
стоящую за ним учётную запись — но только учётную запись, а не области доступа.
Токен с недостаточными областями подключается, а затем падает на отдельных
запросах. Проверьте области доступа и срок действия:

```bash
curl -H "Authorization: token YOUR_TOKEN" https://api.github.com/user
```
