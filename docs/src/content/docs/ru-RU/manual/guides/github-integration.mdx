Это руководство охватывает части настройки, специфичные для GitHub. GitHub —
один из трёх поддерживаемых хостов кода. О подключении GitLab или Bitbucket и
о том, как рабочее пространство совмещает их, см.
[Подключить хост кода](/ru-RU/руководство/практические-руководства/подключить-хост-кода/).

## Предварительные требования

- Аккаунт GitHub с доступом к репозиториям, в которых вы хотите работать
- Сервер, который умеет выполнять вход людей в GitHub: через собственный GitHub
  App (см. [Создать GitHub App](/ru-RU/руководство/практические-руководства/github-app/))
  или через Control Center Connect — это выбирает владелец сервера в разделе
  **Настройки → Сервер → Единый вход**

:::note[Учётные данные хранятся на сервере и привязаны к вам]
На машине, на которой вы печатаете, ничего не хранится. Ваш вход в GitHub хранит
ваш `cc_server`, привязывая его к вашему идентификатору пользователя, и каждое
устройство, с которого вы входите, использует его: настольное приложение, веб и
телефон. Другой участник того же сервера не может им воспользоваться, а войти за
него — то, что он делает сам.
:::

## Войти в GitHub

В GitHub можно только войти: вставлять токен не нужно.

1. Перейдите в **Настройки → Вы → Профиль → Хостинг кода** (или на первый
   шаг онбординга)
2. В строке **GitHub** нажмите **Войти в GitHub**
3. Браузер откроет GitHub. Подтвердите приложение

Как завершается вход, зависит от того, кто его выполняет:

- **Собственное приложение сервера:** GitHub возвращает браузер на сервер, и
  диалог сам это замечает. Вводить ничего не нужно
- **Control Center Connect:** страница в браузере показывает 8-символьный код.
  Введите его в диалоге или позвольте браузеру открыть Control Center по ссылке
  `control-center://` и не вводите его

Проверка: строка **GitHub** показывает «Вы вошли как _ваше-имя-пользователя_».

Диалог отклоняет код или ссылку, которые он не запускал сам, с сообщением **Вход
начат не здесь**. Если кто-то присылает вам ссылку для входа, не продолжайте:
завершив её, вы подключите свой аккаунт к его серверу.

Чтобы удалить свой вход, нажмите **Отключить**. Выход из GitHub или удаление из
рабочего пространства также отбрасывает все токены, которые сервер выпустил от
вашего имени.

## От чьего имени говорят ваши учётные данные

Control Center следует собственному разделению GitHub между действиями **от имени человека** и действиями **от имени приложения**:

| Что происходит                                                                | Отображается на GitHub как                          |
| ----------------------------------------------------------------------------- | --------------------------------------------------- |
| Всё, что вы делаете сами: комментарий, ревью, одобрение, мердж, запрос ревьюеров | **Вы**. GitHub отмечает комментарий в разговоре как сделанный через приложение Control Center; ревью и его встроенные комментарии такой отметки не несут |
| AI-ревью, ответы и комментарии агентов в обсуждениях PR, метки, работа конвейеров и бота    | **Бот Control Center**. В общем приложении Connect ревью принадлежит боту, только если оператор Connect внёс установку в список; иначе оно показывается от имени ответственного человека |
| Pull request, который агент открывает для вас, его правки заголовка или описания этого pull request, его push-ы и его коммиты       | **Вы**. Control Center указан соавтором, когда включено указание соавторов |
| Работа, о которой никто не просил (расписания, вебхуки)                       | **Бот Control Center**, он же автор его коммитов. В Control Center Connect бот никогда не делает push и не открывает pull request |

- **Всё, что делаете вы**, выполняется через **ваш** вход и ничего больше. Если вы не вошли, приложение просит войти. Никакие другие учётные данные вас не подменяют
- **Работа бота** получает токен для одного репозитория за раз, ограниченный тем, что может делать там ответственный участник: тот, кто попросил, иначе владелец рабочего пространства. Участник, который не может делать push, ограничивает токен чтением. Ответы бота, действующие от чьего-то имени, начинаются с **Control Center (for @login)**
- **Агенты открывают pull requests через Control Center**, никогда из своей песочницы, поэтому pull request принадлежит вам, а правила самого GitHub не позволяют вам его одобрить. Control Center также отклоняет одобрение от человека, который поручил агенту работу, и от автора pull request. Для запуска по расписанию или webhook это включает каждого администратора, который включил его триггер или редактировал пайплайн, пока он был включён. Ревью должен провести кто-то другой. Если Control Center не может подтвердить, кто открыл pull request, или какой аккаунт на хосте кода ваш, он отказывает и просит попробовать снова
- **Агенты комментируют и через Control Center.** Токен GitHub, который получает запуск агента, только читает. Когда агент комментирует pull request, над которым работает, Control Center публикует комментарий от имени бота, начиная с **Control Center (for @login)**, если кто-то запросил запуск. Агент может комментировать только pull request в том же репозитории (не fork), чей последний коммит отправил агент или который является текущим коммитом ветки его пространства. @-упоминания в комментарии агента никого не уведомляют. Агент также может изменить заголовок или описание собственного pull request, пока он открыт. Такое изменение вносится так же, как был открыт pull request (от вашего имени, когда вы попросили запуск), и по умолчанию сначала требует одобрения. Описание pull request сохраняет свои @-упоминания, когда агент его открывает и когда редактирует, поэтому названные в нём люди получают уведомление
- **В Control Center Connect бот никогда не делает push и не открывает pull request.** Push, создание ветки или открытие pull request там требует человека, который это запросил, и выполняется через вход этого человека. Запуск по расписанию или webhook, который пытается сделать push, останавливается с сообщением об этом. Чтобы запуски без присмотра могли делать push, дайте рабочему пространству собственное GitHub App в **Настройки**
- **Что может бот Connect.** В общем приложении Connect бот комментирует, ставит метки и реагирует. Он публикует ревью (AI-ревью, комментарии ревью, запросы ревьюеров), только если оператор Connect внёс установку этого сервера в список. Иначе ревью уходит через собственный вход ответственного человека и отображается от его имени. Бот никогда не открывает, не редактирует, не закрывает и не переименовывает pull request, не отклоняет ревью и не редактирует и не удаляет комментарии; для этого нужен человек, который это запросил, на своём входе. Connect не привязывает установку вашей организации к одному серверу Control Center: любой сервер, на котором участник, способный делать push в репозиторий, вошёл через Connect, может получить токен комментариев бота для этого репозитория.
- **Сервер или рабочее пространство с собственным GitHub App** сохраняет за ботом все перечисленные выше действия, включая ревью.
- **Автоматизация никогда не одобряет** pull request. Одобрение — действие человека

Когда вы подключаете репозиторий, Control Center проверяет, видит ли его ваш аккаунт, и предупреждает, если GitHub App не установлен на организации репозитория или не включает его, со ссылкой на исправление. Подключать и отключать репозитории может администратор рабочего пространства, а рабочую копию вне собственного хранилища рабочего пространства может подключить только владелец сервера; см. [Добавить репозитории в рабочее пространство](/ru-RU/руководство/практические-руководства/добавить-репозитории/).

Связь следует за постоянным идентификатором репозитория на GitHub, поэтому переименование или передача ничего от вас не требуют. Если путь позже указывает на другой репозиторий, Control Center перестаёт отправлять ему что-либо и показывает уведомление, пока администратор рабочего пространства не нажмёт **Переподключить**.

Открытие кода репозитория (файлов, диффов, поиска, терминала) требует и гранта на него в рабочем пространстве, и вашего входа в GitHub, который может его читать. Администраторы рабочего пространства подчиняются тому же правилу; освобождён только владелец сервера.

## Что даёт интеграция

| Возможность              | Как                                                                                                                                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Список и детали PR       | GitHub REST API, с сервера, через ваш собственный вход                                                                                                                                          |
| Запуски проверок         | GitHub Checks API                                                                                                                                                                               |
| Публикация ревью         | Шаг, требующий подтверждения пользователя, который публикует ваше ревью в PR от вашего имени                                                                                                    |
| Регистрация репозиториев | Рабочая копия принимается, если её remote `origin` указывает на github.com или на gitlab.com / bitbucket.org                                                                                    |
| Доступ агента к GitHub   | Внутри запуска `git fetch` проходит через Control Center, который загружает репозитории, с которыми работает запуск, токеном только для чтения, которого запуск никогда не держит. `gh` читает их по токену только для чтения, который Control Center выдаёт по запросу и отзывает по окончании запуска. Push, pull requests, правки в них и комментарии проходят через Control Center |
| Оповещения               | Серверный опрос вашей ленты уведомлений GitHub поднимает «Упоминание в pull request» и «Запрошено ревью»                                                                                        |
| Профили пользователей    | Карточки профиля при наведении и фильтрация PR по автору                                                                                                                                        |

Некоторые пути используют GraphQL API вместо REST там, где это дешевле:
активность веток для выбора при создании PR и живое состояние ревью, которое
решает, остаётся ли уведомление «Запрошено ревью» в ожидании.

## Как агенты действуют на GitHub

- Агент, работающий в worktree GitHub, получает токен только для этого репозитория. Он может читать только код, issues и pull request. Комментарии идут через Control Center, как описано выше. Push проходит через Control Center, который спрашивает правило **Отправить в удалённый репозиторий**, а затем передаёт его с токеном записи, которого у агента никогда нет. См.
  [Настроить политики песочницы](/ru-RU/руководство/практические-руководства/политики-песочницы/)
- Работа, которую вы начинаете, коммитится от вашего имени. Когда вы просите агента о чём-то или коммитите в IDE, вы автор и коммитер, с адресом, который подтвердил ваш хост кода: ваш адрес noreply на GitHub из входа в GitHub или, на GitLab и Bitbucket, адрес электронной почты, который сообщает ваш вход там. Git-личность рабочего пространства используется только для коммита, который вы делаете вручную в репозитории, где ни один хост кода не подтверждает ваш адрес. Если вы не вошли в этот хост кода, коммиты агента принадлежат боту, а заметки запуска сообщают об этом
- Работа, о которой никто не просил, коммитится от имени бота. Запуск по расписанию или webhook коммитит от имени GitHub App рабочего пространства (`<app>[bot]`, с его адресом noreply на GitHub) или как `Control Center <hi@usectrl.dev>`, когда GitHub App нет или репозиторий на GitLab или Bitbucket
- **Указывать Control Center соавтором** (**Настройки** → **Вы** → **Коммиты**) добавляет трейлер `Co-Authored-By:` для другой стороны: Control Center — в ваших коммитах, а в коммитах бота — каждого человека, который включил триггер, стоящий за запуском. Оно включено, пока вы его не выключите. Администратор рабочего пространства может решить это за всех с помощью **Указание соавторов** в **Настройки** → **Рабочее пространство** → **Общие**; ваш собственный выбор тогда сохраняется, но в этом рабочем пространстве не применяется. Собственное указание авторства Claude Code всегда отключено
- Ваши коммиты можно подписывать. В разделе **Проверенные коммиты** в **Настройки** → **Вы** → **Коммиты** выберите **Создать ключ подписи** и добавьте его открытую часть в свой аккаунт GitHub или GitLab как ключ подписи; с этого момента коммиты запусков, которые вы запросили, и коммиты, которые вы делаете в IDE, отображаются как проверенные. Закрытая часть остаётся на вашем сервере, поэтому тот, кто контролирует этот сервер, может подписывать коммиты от вашего имени, пока ключ в вашем аккаунте, а на GitHub коммит, уже показанный как проверенный, остаётся проверенным после удаления ключа. У Bitbucket нет ключа только для подписи: не добавляйте туда ключ, а коммиты на Bitbucket не подписываются. Коммиты бота никогда не подписываются
- Коммиты, которые вы делаете в панели **Управление исходным кодом** IDE, пропускают Git-хуки репозитория, как это делает `git commit --no-verify`, а Git сервера игнорирует помощники учётных данных, редакторы, внешние инструменты сравнения и подписывающие программы, которые настроил репозиторий: он запускает Git на собственной машине, в дереве, которое может изменить агент или pull request. См. [Коммит и push из Управления исходным кодом](/ru-RU/руководство/практические-руководства/проверить-и-смержить-pr/#коммит-и-push-из-управления-исходным-кодом)
- Каждый коммит, который агент отправляет через push, сначала проверяется, включая слои, которые `stack_publish` отправляет для стека. Push, который называет кого-то другого, убирает или заимствует указание авторства, добавляет sign-off или не подписан так, как говорят ваши настройки, отклоняется. Коммиты, которые вы отправляете сами из IDE, ваши и этой проверке не подлежат
- Терминал, который вы открываете на rig, получает ваш собственный вход,
  суженный до одного репозитория, поэтому push оттуда — ваши
- Если выпустить токен не удаётся (никто из ответственных не вошёл, приложение не
  установлено у владельца или установка приостановлена), команда, которая его запросила, объясняет почему. Резервных учётных данных нет

## Диагностика

### Список PR пуст и сообщает, что GitHub не подключён

Вы не вошли в GitHub на этом сервере. Нажмите **Войти в GitHub** в разделе
**Настройки → Вы → Профиль → Хостинг кода**. Репозитории на других хостах кода это не затрагивает.

### Строка GitHub сообщает, что вход на этом сервере не настроен

У сервера нет ни собственного GitHub App, ни Connect. Владелец сервера выбирает
один из вариантов в разделе **Настройки → Сервер → Единый вход**: **Создать моё
приложение GitHub** занимает около двух минут. См.
[Создать GitHub App](/ru-RU/руководство/практические-руководства/github-app/).

В рабочем пространстве на собственных приложениях строка сообщает об этом, когда GitHub App рабочего пространства отсутствует или не заполнен. Администратор рабочего пространства заполняет поля на карточке **GitHub App** в разделе **Настройки → Рабочее пространство → Интеграции**; см. [Дайте одному рабочему пространству собственное приложение](/ru-RU/руководство/практические-руководства/github-app/#дайте-одному-рабочему-пространству-собственное-приложение).

### Диалог сообщает, что код не совпадает

Введите код точно так, как его показывает браузер: 8 букв и цифр. Пять неверных
кодов завершают вход; начните его заново.

### Вход сообщает, что приложение не установлено

У GitHub App нет установки на аккаунте, которому принадлежит репозиторий.
Администратор рабочего пространства устанавливает его в разделе **Настройки →
Рабочее пространство → Интеграции → Установки приложения GitHub**.

### Всем приходится входить в GitHub заново

Владелец сервера сменил ключ Connect сервера, переключился на другой сервер
Connect, или каталог данных восстановили на другой машине. Входы через Connect
привязаны к серверу, который их создал.

### Добавление репозитория отклоняется

Регистрация требует всех трёх условий: путь находится внутри рабочего дерева git,
у него есть remote `origin`, и этот remote указывает на поддерживаемый хост кода
(github.com, gitlab.com или bitbucket.org). `origin` должен быть тем репозиторием, который вы подключаете, а папку вне собственного хранилища рабочего пространства может подключить только владелец сервера. См.
[Добавить репозитории в рабочее пространство](/ru-RU/руководство/практические-руководства/добавить-репозитории/).

### У меня есть грант, но репозиторий говорит, что мой аккаунт не может его читать

Ваш аккаунт GitHub не может читать этот репозиторий, поэтому его код остаётся закрытым для вас, даже если в рабочем пространстве есть грант. Войдите в GitHub в разделе **Хостинг кода** или запросите доступ к репозиторию на GitHub.

### «Не удалось подтвердить ваш доступ к GitHub»

Не удалось связаться с GitHub для проверки вашего доступа, поэтому Control Center отказал вместо догадки. Попробуйте ещё раз немного позже.

### Ревью в Connect показываются от моего имени, а не от имени бота

В общем приложении Connect бот публикует ревью только для установок, которые оператор Connect внёс в список. В остальных случаях ревью уходит через собственный вход ответственного человека. Чтобы бот публиковал ревью, дайте рабочему пространству собственный GitHub App.

### После интенсивного использования всё на время перестаёт работать

Это автоматический выключатель при превышении лимита запросов. GitHub
сигнализирует о своём основном лимите ответом `403` с `x-ratelimit-remaining: 0` и
временем сброса; увидев такой ответ, клиент локально отклоняет дальнейшие запросы
без сетевого обращения, пока окно не истечёт, поэтому шквал повторных попыток не
может усугубить лимит. Временные сбои повторяются до трёх раз с экспоненциальной
задержкой и учётом `retry-after`.
