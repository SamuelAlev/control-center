Pull request — это уже то место, где происходит разговор о коде. Разговоры в PR
делают его поверхностью рабочего пространства Control Center — так же, как
[чат-мост](/ru-RU/руководство/понятия/чат-мосты/) делает такой поверхностью Slack:
упомяните `@usectrl` (или бота GitHub App рабочего пространства) на PR, ответьте
внутри его веток ревью или добавьте метку `ai-review` — и работа произойдёт в
пространстве проверки этого PR, с тем же закреплением авторства и теми же
ограничениями, что и всё, набранное в приложении. Комментарий и метка проверяются
одинаково: по участнику, который написал или добавил их. Ответы возвращаются в
GitHub, в ту самую ветку, где был задан вопрос.

Три решения определяют эту возможность, и каждое из них — то же решение, которое
чат-мост принял для чата, только пересказанное для хоста кода: **в каком
направлении идёт соединение**, **что подтверждает права комментария, пришедшего
извне**, и **за кем закрепляется каждая сторона**.

## Транспорт — это опрос

Единственный push-канал для приложения в GitHub — это вебхук, а вебхуку нужен
входящий URL — единственное, чего эта поверхность намеренно никогда не требует.
Поэтому обнаружение — это обход: один поисковый запрос с псевдонимом на каждую
установку приложения спрашивает у GitHub о PR, которые упоминают бота (или его
короткий slug), и об открытых PR, несущих метку проверки; у PR, которые уже имеют
пространство проверки, читаются ветки комментариев; а всё остальное сравнивается
по id комментария с тем, что было увидено в прошлый обход. Собственное приложение
обходит каждую минуту не более 25 PR. Через Connect вызовы расходуют собственную
квоту GitHub участников, поэтому обход выполняется раз в две минуты не более чем
по 10 PR, а рабочее пространство, у которого осталось меньше 15 % квоты,
пропускается, пока она не восстановится. Сам Connect никогда не видит содержимое
PR.

Последствия этого решения стоит назвать:

- **Задержка — это интервал обхода, а не событие.** Подтверждение 👀 появляется
  в течение одного обхода. Ничего срочного на этом не держится.
- **Ровно один раз на комментарий.** Идентификаторы комментариев уникальны во всём
  GitHub; каждый записывается в тот момент, когда признан подходящим, — до того,
  как по нему что-либо предпринимается. Сбой может потерять обработку
  комментария, но никогда не запустит её дважды.
- **Простой догоняется, а не воспроизводится заново.** Набор увиденного
  сохраняется, поэтому после перезапуска доставляется то, что пришло во время
  простоя. Единственное исключение — самый первый обход: сравнивать не с чем,
  поэтому всё необработанное записывается молча, — оператор, пометивший двадцать
  PR до появления этого сервера, не должен вернуться к двадцати запущенным
  проверкам.
- **Метка — это множество, а не событие.** Поиск сообщает о _наличии_ метки,
  поэтому помеченный PR срабатывает один раз и навсегда. Повторное добавление
  метки после удаления для обхода невидимо; путь к повторному запуску —
  упоминание.

Поиск выполняется по одному разу на каждый аккаунт установки, через собственный
клиент этого владельца: токен видит только репозитории своей установки, — а
единая учётная запись на весь сервер молча пропускала бы каждый
PR под другими установками приложения.

## Авторизует членство, а не комментарий

Комментарий в PR приходит с автором — неаутентифицированной внешней
идентичностью, пока не доказано обратное. Сервер сопоставляет неизменяемый
числовой id аккаунта GitHub автора (никогда не логин, который можно переименовать
и переиспользовать) с входами в GitHub участников рабочего пространства; индекс
перестраивается по TTL, потому что люди входят в систему и получают приглашения,
пока сервер работает. Для метки `ai-review` сопоставляется тот, кто добавил её
последним.

Три проверки по порядку, и непрохождение любой из них происходит молча — ничего не
публикуется:

- **Вошедший участник.** Аккаунт должен принадлежать участнику _этого_ рабочего
  пространства, который вошёл в GitHub на этом сервере
- **Роль с правом записи.** `viewer` и `guest` не могут запускать работу
- **Доступ на push.** Ответы используют токен `bot`, ограниченный доступом этого
  участника к репозиторию. Если сервер не может его выпустить, он не продолжает

Все проверки выполняются до любого подтверждения, поэтому посторонний не получает
ни реакции, ни ответа. Комментарий никогда не приписывается тому, кто его не
отправлял, и слова постороннего никогда не попадают в рабочее пространство,
которое он не видит.

### Заявка

Последний шаг перед любой работой — реакция 👀, добавленная собственным входом
автора в GitHub. GitHub отвечает `201` на новую реакцию и `200` на уже
существующую, поэтому реакция работает и как блокировка: если один и тот же
человек вошёл на двух серверах, которые оба привязали репозиторий, работу
выполняет только тот, кто отреагировал первым. Комментарий, который видят
несколько рабочих пространств на одном сервере, предлагается каждому, и решает та
же заявка.

## Две идентичности — намеренно

Каждая сторона разговора несёт свою идентичность, и эта разница — и есть суть
возможности:

- **В GitHub ответ — это автоматизация от вашего имени.** Каждый ответ уходит
  с токеном `bot` для этого одного репозитория, ограниченным доступом
  спросившего участника. На собственном приложении автором выступает аккаунт
  `[bot]` приложения. Через Connect токен общего App — это токен пользователя,
  поэтому автором ответа становится аккаунт спросившего участника, действующий
  через App. В любом случае каждый ответ начинается с
  `**Control Center** (for @login):`, что сообщает, кто спросил, и заодно служит
  защитой от циклов.
- **В пространстве вопрос принадлежит вам.** Сообщение приписывается участнику,
  с которым сопоставлен автор, и запуск агента выполняется от его имени: коммиты
  указывают его соавтором, а регулятор автономии и ограничения действий
  пространства применяются ровно так же, как к сообщению, набранному
  в приложении. Записи в хост кода из этого запуска используют токены для
  одного репозитория, ограниченные этим участником, и никогда — его вход,
  переданный целиком.

Публикация замечаний проверки обратно в GitHub остаётся решением человека,
принятым в Control Center. Упоминание может _запустить_ проверку; публикует её
только человек.

## Защита от циклов и короткое имя

Всё, что написано аккаунтом бота, отбрасывается до того, как сработает любой
шлюз, — и наш конкретно, и любой суффикс `[bot]`, чтобы бот-ревьюер другого
приложения тоже не мог разбудить нашего, — а также каждый комментарий,
начинающийся с префикса `**Control Center** (for @`, поскольку ответ через Connect
написан аккаунтом человека. Без этого ответы приходили бы как новые комментарии и
зацикливали бы мост навсегда.

Суффикс `[bot]` — ещё и причина, по которой существует короткая форма. GitHub
жёстко закрепляет логин аккаунта приложения как `<slug>[bot]`, не предлагает для
него автодополнение и никогда не сопоставляет `@slug` с приложением, — поэтому
приём голого slug — это решение _нашего_ сопоставителя, а для его обнаружения
нужна отдельная полоса поиска по необработанному **тексту** комментариев, а не
индекс упоминаний GitHub. Цена названа, а не сглажена: человек, чей логин
совпадает со slug приложения, обращается к боту каждым коротким упоминанием
самого себя. Отличительные имена приложений делают такое совпадение
гипотетическим.

## Что намеренно не предлагается

- **Никакой автопубликации.** Замечания попадают в пространство проверки;
  публикация в GitHub — отдельное действие, которое выполняет человек
- **Никакого нечёткого сопоставления.** Автор сопоставляется ровно с одним
  участником или игнорируется — авторства «на глаз» не бывает
- **Никакого автоматического одобрения.** Автоматизация может комментировать и
  запрашивать изменения, но ревью `APPROVE` отклоняется до отправки. Одобрение —
  действие человека
- **Никакого вебхука GitHub App.** Эта поверхность никогда его не регистрирует,
  поэтому входящего URL для комментариев в PR не существует. Другие вебхуки
  продукта (конвейеры, синхронизация тикетов) — отдельная необязательная
  настройка.
