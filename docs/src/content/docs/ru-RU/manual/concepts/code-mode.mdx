Агент обычно вызывает свои инструменты по одному. Каждый вызов — это ход модели: агент запрашивает вызов, результат возвращается в его контекст, и агент читает его, прежде чем запросить следующий. Для работы, которая в основном механическая, например прочитать двадцать файлов, чтобы найти три нужных, или проверить каждый открытый тикет на наличие одной метки, большинство таких ходов и большая часть контекста уходят на результаты, которые агент всё равно отбрасывает.

Режим кода — это один инструмент, `repl`. С ним агент пишет короткий скрипт на JavaScript, который вызывает его другие инструменты, перебирает их результаты в циклах, фильтрует и объединяет их и возвращает только то, что нужно. Один вызов `repl` может заменить десятки ходов с инструментами, а в контекст попадает только ответ скрипта.

Каждый запуск получает `repl`, если сервер может выполнять скрипты. Включать ничего не нужно: см. [Когда у запуска есть `repl`](#когда-у-запуска-есть-repl).

## Что может делать скрипт

Скрипт — это обычный JavaScript, записанный как тело асинхронной функции, поэтому `await` и `return` работают на верхнем уровне. Каждый вызов `repl` запускает новый, пустой интерпретатор.

- **Вызов инструментов.** `await tools.read({ path: "README.md" })` вызывает инструмент и возвращает его результат или отклоняется с ошибкой, если вызов не удался или запрещён. Независимые вызовы можно выполнять одновременно через `Promise.allSettled`.
- **Поиск инструментов.** `ALL_TOOLS` перечисляет все инструменты, которые скрипт может вызвать. `searchTools(query)` находит инструменты по тому, что они делают, `describeTool(name)` возвращает описание одного инструмента и его аргументы, а `describeNamespace(name)` перечисляет инструменты одной группы. Инструменты подключённых серверов MCP тоже доступны таким способом.
- **Возврат результатов.** Агенту возвращается только то, что скрипт вернул или передал в `text()`, `image()` или `console.log()`. Модели передаётся не более четырёх изображений.
- **Хранение значений.** `store(key, value)` и `load(key)` сохраняют небольшие JSON-значения между скриптами одного разговора и одного агента. Значения сохраняются только при завершении скрипта. У субагентов хранилища нет.
- **Вопрос человеку.** `await tools.ask_user({ question, options })` задаёт вопрос и ждёт ответа.
- **Встроенные эмбеддинги.** `models.embed`, `models.rank` и `models.classify` используют модель эмбеддингов сервера, если она установлена.
- **Ожидание.** `sleep(ms)` и `setTimeout` в пределах временного лимита скрипта. `limits()` возвращает лимиты, под которыми работает скрипт.

У скрипта нет доступа к файловой системе, сети, процессам, модулям и окружению: нет `fetch`, `require`, `import` и `process`. Единственный выход — вызов инструмента, а каждый вызов инструмента проходит те же проверки, что и вызов, сделанный агентом напрямую.

Вызовы инструментов, которые скрипт уже сделал, не отменяются, если скрипт завершится с ошибкой позже.

## Какие инструменты агент вызывает напрямую

Каждый запуск встроенного агента получает один и тот же небольшой набор инструментов, которые он вызывает по имени:

- `repl`, первым;
- инструменты для файлов и оболочки `read`, `write`, `edit`, `search`, `find`, `bash` и `read_output`;
- `ask_user` и `task`;
- `todo_write`, `search_memory` и `send_message`;
- глаголы, которые нужны [режиму](/ru-RU/руководство/понятия/режимы/) разговора, чтобы выдать свой результат или выйти из него, например `submit_plan` в режиме плана;
- `search_tools`, если какой-либо инструмент загружается при первом использовании (ниже).

Любой другой инструмент, который может понадобиться запуску, доступен одним из двух способов:

- **Только из скрипта**, если скрипт может его вызвать. Агент находит его через `searchTools()` или `describeTool()` и вызывает как `tools.<name>(args)`. Описание инструмента, доступного только из скрипта, никогда не попадает в модель, поэтому не занимает места в промпте. Если агент всё же вызывает такой инструмент напрямую, ответ советует вызвать его из скрипта. Если сервер не может запускать скрипты запуска, инструмент вместо этого загружается при первом использовании ([Когда скрипты не могут работать](#когда-скрипты-не-могут-работать)).
- **Загружается при первом использовании**, если скрипт не может его вызвать. Агент видит его имя, и вызов по имени или поиск через `search_tools` загружают инструмент.

Некоторые инструменты никогда не вызываются из скрипта, в том числе сам `repl` (скрипт не может запустить скрипт), `eval`, `task`, `checkpoint`, `rewind`, глаголы `vibe_*`, а также инструменты, которые запускают или отправляют сообщения другим запускам агента, создают подтверждения, решают или комментируют их, меняют политику или навыки либо выводят из режима плана. Агент вызывает эти инструменты напрямую.

Запуск без `repl` получает те же прямые инструменты, а всё остальное загружается при первом использовании. [Контекст инструментов и кэш промптов](/ru-RU/руководство/понятия/контекст-инструментов/) объясняет, почему набор одинаковый в обоих случаях.

Режим кода никогда не добавляет инструмент, который режим разговора не разрешает. Сначала применяется фильтр инструментов режима, и скрипт может вызвать только оставшиеся.

## Когда у запуска есть `repl`

Запуск получает `repl`, если при старте сервера раннер скриптов прошёл проверку блокировки ([Как ограничивается скрипт](#как-ограничивается-скрипт)). Ни настройка рабочего пространства, ни агента, ни сервера этого не меняет. Запуск всё равно не получает `repl`, когда:

- раннер не может заблокировать себя на машине сервера; тогда сервер вообще не запускает скрипты;
- сервер — публичная демо-версия, которая не запускает скрипты;
- запуск не принадлежит никакому рабочему пространству;
- лимиты рабочего пространства нельзя прочитать, потому что запуск с настройками по умолчанию мог бы выйти за пределы лимитов, которые администратор снизил;
- журнал запуска не удалось записать, потому что каждый скрипт записывается в свой запуск до старта.

Такой запуск вызывает все свои инструменты напрямую.

Режим кода работает для запусков встроенного агента и для агентов, которые обращаются к инструментам Control Center через его конечную точку MCP, например Claude Code. Для агента MCP список инструментов, который он получает, содержит `repl`, прямые инструменты и инструменты, которые скрипт не может вызвать; остальные он вызывает из скриптов. Только запуск, который Control Center начал и ведёт для него журнал, получает там `repl`; любому другому клиенту отправляются все инструменты, кроме `repl`.

В разделе **Статус** страницы **Настройки → Рабочее пространство → Режим кода** видно, может ли этот сервер выполнять скрипты (**Доступен** или **Недоступен**, с причиной от сервера), и указана установленная версия **Раннер**. Кнопка **Открыть выполнения кода** открывает список скриптов, которые запускались.

Владелец сервера не может выключить скрипты. Он может ограничить их: сколько их работает одновременно и сколько памяти может использовать один (см. [Лимиты](#лимиты)).

### Когда скрипты не могут работать

Запуск никогда не теряет инструмент из-за того, что сервер не может запускать его скрипты. Когда сервер отказывает скрипту по причине, которой не избежал бы ни один другой скрипт (например, скрипты недоступны, скрипт ждал половину отведённого ему времени, пока освободится место, его запись не удаётся записать, список инструментов запуска слишком велик, чтобы передать его скрипту, или раннер не может запуститься или заблокировать себя), запуск перестаёт использовать скрипты до конца своей работы:

- запуск встроенного агента сохраняет `repl`, а каждый инструмент, до которого он дотягивался только из скрипта, теперь загружается при первом использовании: агент вызывает его по имени или находит через `search_tools`;
- запуск на конечной точке MCP получает список инструментов со всеми инструментами и без `repl`, а его клиент получает уведомление, что список изменился. Сервер помнит последние 1 024 таких запуска; более старый возвращается к скриптам.

Эти инструменты проходят тот же фильтр режима, ограничения и подтверждения, что и раньше, поэтому ничего не становится доступным, чего не было. Скрипт, который терпит неудачу по своей вине (выбрасывает ошибку, достигает лимита или получает отказ в вызове), ничего не меняет.

Сервер также продолжает проверять, что скрипты могут работать. Когда раннер не может запуститься по причине, не связанной со скриптом, сервер повторяет проверку блокировки, не чаще раза в минуту. Если проверка не проходит, сервер не запускает скрипты и пишет ту же строку `code_mode=unavailable`, что и при старте; запуски, которые начинаются тем временем, не получают `repl`. Проверка продолжается, не чаще раза в минуту; когда она проходит, скрипты снова запускаются и пишется строка `code_mode=available`. Перезапуска требует только проверка, которая провалилась при старте сервера.

## Лимиты

Каждый скрипт работает под лимитами. Администратор рабочего пространства может изменить шесть из них в разделе **Лимиты** на странице **Настройки → Рабочее пространство → Режим кода** (**Настроить лимиты**); агент может попросить меньше времени или меньший бюджет вывода для одного скрипта, но никогда не больше.

| Лимит | По умолчанию | Диапазон | Что происходит при исчерпании |
| --- | --- | --- | --- |
| Время на скрипт | 5 мин | от 1 с до 25 мин | Скрипт останавливается, и агент получает сообщение, что время вышло. |
| Время процессора | 30 с | от 1 с до 2 мин | Скрипт останавливается. |
| Память | 256 МиБ | от 16 МиБ до 1 ГиБ | Скрипт останавливается. Владелец сервера может задать более низкий потолок для всего сервера. |
| Вызовы инструментов на скрипт | 500 | от 1 до 5 000 | Дальнейшие вызовы отклоняются, и скрипт получает объяснение. |
| Вызовов одновременно | 8 | от 1 до 32 | Вызовы только для чтения сверх этого предела ждут своей очереди. Вызовы, которые что-то меняют, всегда выполняются по одному. |
| Вывод, который читает агент | 10 000 токенов | от 100 до 50 000 | Вывод сокращается до начала и конца, а агент может прочитать остальное по запросу. |

Время, которое скрипт проводит в ожидании человека — подтверждения или ответа на вопрос, — не учитывается в его временном лимите. Пока он ждёт, скрипт не начинает других вызовов инструментов: вызовы, которые он делает в это время, начинаются по порядку после вашего ответа.

Некоторые лимиты фиксированы: исходный код скрипта не более 256 КиБ, аргументы одного вызова инструмента — 1 МиБ и 16 384 значения, команда, которую скрипт передаёт встроенному инструменту, который её выполняет, — 16 КиБ (имя инструмента входит в этот объём), один результат, переданный скрипту, — 4 МиБ, сохранённое значение — 256 КиБ, а всё, что один разговор и агент хранят вместе, — 1 МиБ. Один запуск выполняет одновременно только один скрипт.

Поиск инструментов из скриптов тоже ограничен: запрос `searchTools` не длиннее 1 024 символов, имя инструмента или пространства имён не длиннее 256, не более 50 результатов и не более 200 поисков, занимающих в общей сложности 2 секунды времени сервера; дальше поиски не выполняются. Все скрипты одного рабочего пространства также делят 2 секунды времени поиска, которое возвращается по четверти секунды за каждую секунду. Поисковый индекс даёт каждому инструменту равную долю примерно в миллион символов, которые сначала тратятся на имена его аргументов, а затем на описание, и всегда индексирует имя каждого инструмента, поэтому даже в очень большом каталоге инструмент находится по имени.

Владелец сервера также ограничивает, сколько скриптов работают одновременно на сервере (`--code-mode-max-processes`, по умолчанию вдвое больше ядер процессора, не более 16) и память, которую может использовать один скрипт (`--code-mode-max-heap-mb`); скрипты, ожидающие человека, учитываются отдельно, до четырёхкратного этого числа. Если этот предел больше одного, одно рабочее пространство может занять не более примерно трёх четвертей его, поэтому никакое одно рабочее пространство не может занять все места. Запуск и его субагенты вместе используют не более половины мест своего рабочего пространства (но не меньше одного), поэтому их дальнейшие скрипты ждут, пока вперёд пройдут скрипты других запусков этого рабочего пространства. См. [справочник по CLI `cc_server`](/ru-RU/руководство/справка/cc-server-cli/#режим-кода).

## Подтверждения и вопросы

Вызов инструмента из скрипта проверяется точно так же, как прямой вызов: фильтр инструментов режима, [ограничения для действий](/ru-RU/руководство/понятия/ограничения/), запрос подтверждения и собственные проверки инструмента. Скрипт не может сделать ничего, чего агент не мог бы сделать, вызвав инструмент сам.

Когда вызову скрипта нужно подтверждение, в карточке подтверждения написано **Из скрипта, который запустил агент**, а **Показать скрипт** открывает скрипт в разговоре. Чтобы скрипт не засыпал вас карточками, действуют такие правила:

- один скрипт может запросить подтверждение не более 10 раз и задать не более 10 вопросов;
- как только вы отклоняете один из его вызовов, его последующие вызовы, требующие подтверждения, отклоняются без запроса.

Для запусков встроенного агента запросы подтверждения, вызванные командами, которые запускает скрипт, например git push, учитываются в том же лимите и так же прекращаются после отказа. Когда скрипт субагента выполняется одновременно, такой запрос засчитывается для обоих скриптов, и отказ останавливает оба.

В запуске встроенного агента одобрение для инструмента внешнего сервера MCP не запоминается: каждый вызов спрашивает снова, независимо от того, делает его скрипт или сам агент, если только автономия пространства не задана как **Действовать свободно**. Каждый такой запрос, вызванный скриптом, засчитывается в его лимит, равный 10.

Если скрипт завершится до вашего ответа, карточка снимается, а ответ, данный после этого, ничего не подтверждает.

## В разговоре

Вызов `repl` отображается в разговоре как одна строка, заголовком которой служит описание скрипта, данное агентом. При раскрытии видны скрипт и его вывод, а вызовы инструментов, которые сделал скрипт, перечислены под **Вызовы инструментов** с числом тех, что выполняются, завершились успешно, завершились с ошибкой, отклонены, отменены, в очереди или пропущены.

### Как читается скрипт

Вызовы инструментов располагаются в том же порядке и структуре, что и написанный скрипт, а не одним длинным списком. Раннер сообщает строку и столбец, из которых сделан каждый вызов, а приложение читает скрипт, чтобы найти его циклы, ветвления и функции:

- **Цикл** (`for`, `while`) показывается группой **Цикл** с заголовком из первой строки цикла, а функция обратного вызова, переданная такому вызову, как `map` или `forEach`, — группой **Для каждого**. Тонкая линия отделяет один проход цикла от следующего, когда приложение может их различить.
- **Вызовы выполняются вместе** через `Promise.all`, `Promise.allSettled` или подобный комбинатор показываются группой **Параллельно**.
- **Ветвление** (`if`/`else`, `switch`, `try`/`catch`) показывает по одной группе на каждую ветку, с заголовком в виде её условия.
- **Функция**, которую скрипт определяет и вызывает, показывается группой **Функция**.

Группа внутри другой сдвигается на один шаг глубже, до восьми шагов; более глубокие группы остаются на этом отступе.

Заголовок каждой группы показывает, как закончились её вызовы на данный момент. Перед запуском вызова его строка показывает инструмент и аргументы так, как они записаны в скрипте:

| Строка | Значение |
| --- | --- |
| **В очереди** | Скрипт ещё не дошёл до этого вызова. |
| Выполняется | Вызов выполняется. |
| Завершён | Вызов завершился; строка показывает его исход и длительность. |
| **Пропущен** | Скрипт пропустил этот вызов, например ветку `if`, которая не была выбрана, или завершился, не дойдя до него. |

Вызов, написанный внутри аргументов другого вызова того же инструмента, показывается с того же места скрипта, что и тот вызов. Когда приложение не может определить, был ли сделан внешний вызов, строка не показывает никакого слова состояния вместо **Пропущен**.

Когда у группы больше восьми вызовов, её середина сворачивается: первые два и последние три остаются видны, как и каждый вызов, который ещё выполняется, завершился с ошибкой или был отклонён, вместе с вызовом, с которого начался его проход цикла. **Показать ещё N вызова** открывает ещё 100 при каждом нажатии и называет до четырёх инструментов из скрытых вызовов с их числом, самые редкие первыми, например **Показать ещё 12 вызовов** · Bash 1 · Read 11. Название инструмента длиннее 24 символов в этой надписи обрезается.

Вызов, который приложение не может поместить в скрипт, например сделанный колбэком `then`, перечисляется после дерева под **Вызовы, не привязанные к коду скрипта**. Когда приложение не может прочитать скрипт или ни один вызов не указывает, откуда он сделан, вызовы показываются простым списком в порядке, в котором были сделаны.

Каждая строка вызова показывает начало аргументов вызова и начало его результата, не более 8 КиБ каждого; когда строки одного скрипта вместе содержат 256 КиБ таких фрагментов, его последующие строки показывают только инструмент и то, как завершился вызов. Когда скрипт завершился, **Открыть запись** открывает его полную запись; если запись не найдена, открывается список скриптов этого запуска. Скрипт, которому отказано до запуска (например, потому что другой скрипт того же запуска ещё выполняется), записи не имеет и ссылки тоже.

## Запись

Каждый запускаемый скрипт записывается в своё рабочее пространство до старта, а запись дополняется при завершении. **Наблюдаемость → Выполнения кода** перечисляет их, сначала новые, и их можно фильтровать по результату. Ссылки **Скрипты в этом запуске** и **Скрипты этого агента** в записи сужают список до одного запуска или одного агента. Запись показывает:

- скрипт, его вывод и консоль;
- когда он начался, сколько длился, какое время процессора и пиковую память использовал и работал ли через встроенного агента или через внешнего;
- как он завершился простыми словами (например, вышло время или выброшена ошибка, которую ничто не перехватило);
- каждый вызов инструмента по порядку с результатом: разрешён ли он, одобрен ли человеком или запрещён, сколько человек решал, его аргументы (секреты удалены, обрезаны до 8 КиБ) и размер результата. Сам результат не хранится.

Запись сохраняет, в каком месте скрипта был сделан каждый вызов, поэтому её вызовы инструментов выстроены так же, как в разговоре. Вызов, который одобрил человек, там никогда не сворачивается.

Скрипт, который ещё выполняется, показан как выполняющийся, с вызовами инструментов, завершёнными к этому моменту; его вывод, длительность и потребление ресурсов появляются при завершении. Если сервер остановится во время работы скрипта, запись закроется при следующем запуске сервера, и в ней будет указано, что так и произошло; до её закрытия в этом рабочем пространстве никакой скрипт не выполняется.

Записи хранятся вместе со своим запуском: удаление запуска или его пространства удаляет и записи. Участники видят записи тех пространств, которые им доступны.

## Как ограничивается скрипт

Скрипты никогда не выполняются внутри сервера. Каждый скрипт запускается в собственном процессе — небольшой программе `cc_codemode`, поставляемой вместе с сервером, которая выполняет JavaScript в движке QuickJS-NG. Прежде чем прочитать скрипт, программа блокирует себя средствами самой операционной системы: в Linux — фильтром системных вызовов и ограничениями ресурсов, в macOS — профилем песочницы с запретом по умолчанию, в Windows — AppContainer и объектом задания (job object). После этого она не может открывать файлы, пользоваться сетью, запускать процессы или видеть другие программы. Она стартует без переменных окружения и не содержит учётных данных; её единственный канал — сервер, который отвечает на её вызовы инструментов.

Сервер проверяет блокировку при старте, запуская самопроверку программы. Если блокировка не работает на этой машине — например, внутри контейнера, профиль безопасности которого отказывает в одном из шагов, — сервер на ней не запускает скрипты: ни один запуск не получает `repl`, а страница настроек показывает **Недоступен** и причину. Скрипт никогда не запускается с меньшей изоляцией. Блокировка для Windows пока не проверялась на Windows.

Место вызова в скрипте сообщает раннер, поэтому оно используется только для раскладки разговора и записи. Оно никогда не решает, разрешён ли вызов.

О том, что именно покрывает блокировка и чего она не покрывает, см. в разделе [Песочница и безопасность](/ru-RU/руководство/понятия/песочница-и-безопасность/#скрипты-в-режиме-кода).
