Execute o `cc_server` numa máquina que fique ligada e depois ligue-se a ele a
partir do seu computador, de um navegador ou do seu telemóvel. O servidor é um
binário nativo em Dart puro — sem motor do Flutter — por isso é executado em modo
headless no macOS, Linux ou Windows. É ele que detém a base de dados, executa os
agentes e faz todas as chamadas a APIs externas; os clientes apenas renderizam.

## Executar no Docker (imagens pré-compiladas)

Cada versão publica um stack autoalojado de quatro imagens GHCR — o backend, os
dois clientes finos estáticos e o relay de emparelhamento opcional — mais uma
imagem `cc-server-demo` separada para o anfitrião de demonstração público. Uma
instalação autoalojada não precisa de nenhuma cópia do código-fonte. Fixe uma
etiqueta de versão (`ghcr.io/samuelalev/<image>:v0.0.1-rc.1`) ou acompanhe a
`latest`.

| Imagem                                             | O que é                                   | Publica        |
| ------------------------------------------------- | -------------------------------------------- | ---------------- |
| `ghcr.io/samuelalev/cc-server`                    | O backend: base de dados, agentes, MCP, webhooks | `-p 9030:9030`   |
| `ghcr.io/samuelalev/cc-webapp`           | O cliente web (nginx estático)                | `-p 8080:8080`  |
| `ghcr.io/samuelalev/cc-remote`        | A PWA complementar para telemóvel (nginx estático)       | `-p 8081:8080`  |
| `ghcr.io/samuelalev/cc-signaling-server`     | O relay de emparelhamento WebRTC (opcional)          | `-p 8788:8788`   |

O stack completo como ficheiro compose:

```yaml
services:
  server:
    image: ghcr.io/samuelalev/cc-server:latest
    ports: ["9030:9030"]
    volumes: ["cc_data:/data"]
    restart: unless-stopped
  web:
    image: ghcr.io/samuelalev/cc-webapp:latest
    ports: ["8080:8080"]
    restart: unless-stopped
  remote:
    image: ghcr.io/samuelalev/cc-remote:latest
    ports: ["8081:8080"]
    restart: unless-stopped
  signaling:
    image: ghcr.io/samuelalev/cc-signaling-server:latest
    ports: ["8788:8788"]
    restart: unless-stopped

volumes:
  cc_data:
```

Aspetos que vale a pena saber antes de expor isto para além do loopback:

- **A imagem `cc-server` inclui `CC_SERVER_INSECURE=1`** (tem de se ligar a
  `0.0.0.0` para receber o tráfego da porta publicada), o que só é seguro atrás
  de um reverse proxy que termina o TLS — Caddy, Traefik, nginx ou um Cloudflare
  Tunnel — numa rede de confiança. Para terminar o TLS no próprio processo, monte
  um certificado e defina `CC_SERVER_TLS_CERT` / `CC_SERVER_TLS_KEY` (e depois
  remova `CC_SERVER_INSECURE`). Tudo pode ser substituído com `docker run -e …`
  ou com o bloco `environment:` do compose.
- **`/data` é o único estado.** As bases de dados SQLite, os segredos dos
  dispositivos emparelhados, os modelos descarregados e o áudio das reuniões
  residem todos no volume — faça uma cópia de segurança dele e o contentor torna-se
  descartável.
- **Emparelhe um cliente a partir do interior da imagem** antes da primeira
  ligação, o equivalente em contentor do [passo 3](#passo-3-emparelhar-um-cliente-antes-do-primeiro-arranque):

  ```bash
  docker run --rm -it -v cc_data:/data \
    --entrypoint /app/bin/cc_server ghcr.io/samuelalev/cc-server:latest pair
  ```

- **As duas imagens de cliente são anfitriões nginx estáticos** — nada para
  configurar em tempo de execução; o formulário de ligação de cada cliente recebe
  o URL do servidor, o id do dispositivo e a chave de emparelhamento. O relay de
  sinalização, do mesmo modo, só precisa da sua porta
  (`SIGNALING_HOST` / `SIGNALING_PORT` substituíveis); não tem estado, não guarda
  segredos e é um **fallback** — um telemóvel usa loopback, LAN, tailnet ou um
  caminho `wss://` direto quando algum está acessível, e só recorre ao relay
  quando nenhum está. Ignore-o se os seus clientes chegarem sempre diretamente ao
  servidor.

O resto deste guia compila o servidor a partir do código-fonte; as flags e o
comportamento que aborda são os mesmos que as variáveis de ambiente da imagem
alimentam.

## Pré-requisitos

- O [Dart SDK](https://dart.dev/get-dart). Este repositório fixa o seu SDK com [fvm](https://fvm.app), por isso prefixe todos os comandos com `fvm`.
- Este repositório clonado.
- A cadeia de ferramentas nativa de que o script de preparação precisa — Rust/`cargo`, além de `meson`, `ninja`, `pkg-config`, `git` e um compilador de C++. Cada script de compilação indica o que não conseguiu encontrar e como o instalar.
- Um anfitrião acessível: loopback para uso local, ou um endereço de LAN/público com TLS para clientes remotos.

## Passo 1: Preparar as bibliotecas nativas

As bibliotecas nativas são **obrigatórias** — não existe modo degradado.
Compile-as a partir da raiz do repositório antes de qualquer outra coisa:

```bash
scripts/natives/build_natives.sh
```

Isto compila `rift`, `fff`, o tree-sitter e as suas gramáticas, `aec`, `lame`,
`ccpty`, `cc_watcher`, `cc_inference` e a biblioteca nativa do SAML em
`build/natives/`. O hook de compilação do `cc_server`
reemite para o pacote tudo o que estiver preparado ali, por isso saltar este passo
ou faz a compilação falhar de imediato ou — com a válvula de escape abaixo —
produz um binário cuja verificação de arranque se recusa a iniciar e indica a
biblioteca em falta.

:::note[Válvula de escape apenas para compilação]
Criar um ficheiro `.cc_natives_allow_missing` vazio na raiz do repositório
rebaixa a falha de compilação por bibliotecas nativas em falta para um aviso.
Serve para verificar a sintaxe de um clone novo; um servidor compilado assim não
consegue arrancar. Tem de ser um **ficheiro** — o executor do hook de compilação
não reencaminha o ambiente de quem o invoca, por isso uma variável de ambiente é
ignorada.
:::

## Passo 2: Compilar o binário

```bash
cd apps/cc_server
fvm dart build cli
```

O pacote inclui `libsqlite3` e as bibliotecas nativas preparadas ao lado do
binário — não é preciso o SQLite do sistema nem um motor do Flutter. O executável
fica em `./build/cli/<os_arch>/bundle/bin/cc_server`.

## Passo 3: Emparelhar um cliente antes do primeiro arranque

Um diretório de dados novo não tem nenhum dispositivo emparelhado nem chave
pré-partilhada, por isso o pedido de chave de emparelhamento de um cliente ainda
não pode ser satisfeito. Gere uma com o subcomando `pair`.
Escreve `global.db` e `secrets.json` diretamente; um servidor que já esteja a
servir esse diretório de dados reconhece o novo dispositivo sem reiniciar:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030
```

Imprime três valores para colar no formulário de ligação de um cliente:

```
Connect a thin client (paste into its connect form):
  Server      ws://localhost:9030/rpc
  Device id   web-client
  Pairing key <a freshly generated key>
```

Flags úteis: `--device` (predefinição `web-client`; o id também escolhe o nível do
dispositivo — `desktop`, `ios`, `android`, e qualquer outra coisa é um cliente
web), `--label` (a predefinição é o nome da plataforma mais o hostname desta
máquina), `--host` (o anfitrião a imprimir no URL, uma vez que o loopback não é
acessível a partir de outra máquina) e `--client-url`. Voltar a executar `pair`
roda a chave desse dispositivo e termina as suas sessões ativas. O emparelhamento
nunca cria um espaço de trabalho: o onboarding do cliente que se liga dá-lhe nome
e cria o primeiro.

Com `--client-url` imprime também um QR que pode ser lido pelo terminal e que abre
o cliente web já preenchido:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030 \
  --bind any --host 192.168.1.42 --client-url https://app.usectrl.dev
```

:::caution[Este QR não é o QR do telemóvel]
O `--client-url` constrói uma ligação para o **cliente web** — URL do servidor, id
do dispositivo e chave no fragmento do URL. A aplicação **Remote** para telemóvel
espera um payload diferente (o descritor de ligação completo do servidor mais uma
validade), gerado em **Definições → Você → Seus dispositivos** num cliente em
execução. Os dois não são intercambiáveis. Consulte
[Emparelhar um dispositivo](/pt-PT/manual/guias/emparelhar-dispositivo/).
:::

Uma credencial gerada por `cc_server pair` **não tem validade**; uma gerada na
aplicação expira sempre ao fim de 30 dias. Revogue um dispositivo gerado pela CLI
em **Definições → Você → Seus dispositivos** quando já não precisar dele.

## Passo 4: Iniciar o servidor

Em loopback — a predefinição e tudo o que precisa para um cliente na mesma
máquina:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030
```

Para o alcançar a partir de outra máquina, vincule todas as interfaces. Um bind
que não seja de loopback sem TLS é **recusado no arranque** (`Refusing to bind
non-loopback address … without TLS`), por isso forneça um certificado:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --tls-cert /path/fullchain.pem --tls-key /path/privkey.pem \
  --public-url wss://server.example:9030/rpc
```

Ou termine o TLS num reverse proxy numa rede privada de confiança e opte por um
bind em texto simples atrás dele:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --insecure --public-url wss://server.example/rpc
```

O `--insecure` é ignorado quando `--tls-cert` e `--tls-key` estão ambos definidos —
o TLS ganha sempre. O servidor anuncia o estado de texto simples como
`insecure: true` em `GET /healthz` e os clientes marcam essa ligação como
insegura.

O servidor é executado até receber `SIGINT`/`SIGTERM` e depois encerra de forma
limpa.

## Passo 5: Ligar um cliente

Aponte um cliente ao URL do servidor e à chave de emparelhamento do passo 3:

- **Aplicação para computador**: no ecrã de primeira execução (**Como o Control Center deve ser executado?**) preencha os campos de ligação em vez de **Executar nesta aplicação**, ou adicione o servidor mais tarde em **Definições → Servidor → Ligação e status**. Consulte [Ligar a um servidor remoto](/pt-PT/manual/guias/ligar-servidor-remoto/).
- **Cliente web**: abra [app.usectrl.dev](https://app.usectrl.dev) (ou a sua própria cópia da versão web) e introduza o URL do servidor, o id do dispositivo e a chave de emparelhamento.
- **Telemóvel**: emparelhe a aplicação **Remote** a partir de um cliente em execução — consulte [Emparelhar um dispositivo](/pt-PT/manual/guias/emparelhar-dispositivo/).

:::note[O cc_server não serve nenhum pacote web]
Um `cc_server` autónomo nunca monta uma raiz web, por isso `GET /` devolve 404. O
cliente web é alojado separadamente — use `app.usectrl.dev`, ou aloje você mesmo a
versão web em qualquer anfitrião HTTPS estático (a imagem `cc-webapp` acima é
exatamente isso). Uma origem de navegador que não seja de loopback tem de estar
em `--allowed-origins`, caso contrário o upgrade de WebSocket para `/rpc` é
recusado; a lista predefinida é `https://app.usectrl.dev` e `localhost` /
`127.0.0.1` são sempre permitidos.
:::

## Passo 6: Ligar um Google Calendar (opcional)

Para sincronizar o calendário de um espaço de trabalho sem nenhuma interface
gráfica ligada, use o fluxo de código de dispositivo:

```bash
GOOGLE_OAUTH_CLIENT_ID=<id> GOOGLE_OAUTH_CLIENT_SECRET=<secret> \
  ./build/cli/<os_arch>/bundle/bin/cc_server calendar connect \
  --data-dir ./data --workspace <workspace-id>
```

Imprime um código e um URL para aprovar noutro dispositivo, guarda o refresh token
do lado do servidor e termina. Uma compilação a partir do código-fonte não inclui
nenhum cliente Google, por isso as variáveis de ambiente do id e do segredo são
obrigatórias — não existe nenhuma flag `--google-client-id`. Consulte
[Ligar um Google Calendar](/pt-PT/manual/guias/ligar-calendario/).

## Configuração

As flags usadas acima são as de que uma primeira configuração precisa. A superfície
completa — 23 pares de flag e variável de ambiente, os quatro subcomandos e a
estrutura do diretório de dados — está na
[referência da CLI do `cc_server`](/pt-PT/manual/referencia/cc-server-cli/).

:::caution[As flags desconhecidas são ignoradas silenciosamente]
O analisador de argumentos é feito à mão e salta tudo o que não reconhece, por
isso um erro de escrita (`--tls-key-file`, `--bindany`) não produz erro — o
servidor apenas arranca com a predefinição. Verifique as linhas de registo do
arranque quando uma flag parecer não ter efeito.
:::

As quatro de que mais provavelmente vai precisar:

| Flag           | Predefinição                              | Significado                                                                                          |
| -------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `--data-dir`   | o diretório de dados de aplicação por utilizador do SO | Bases de dados, segredos, modelos e multimédia em cache                                                      |
| `--port`       | `9030`                               | Porta TCP (`0` = efémera)                                                                       |
| `--bind`       | `loopback`                           | `loopback`, ou `any` para todas as interfaces (precisa de TLS ou `--insecure`)                             |
| `--public-url` | derivado do bind                | O URL de RPC anunciado aos clientes emparelhados. **Defina-o explicitamente atrás de um proxy, NAT ou túnel** |

O diretório de dados predefinido é `~/Library/Application Support/control-center`
no macOS, `%APPDATA%\control-center` no Windows e `$XDG_DATA_HOME/control-center`
(ou, caso contrário, `~/.local/share/control-center`) em qualquer outro sistema.
Um `.cc_server` relativo ao diretório de trabalho atual só é usado quando não é
possível resolver nenhum diretório pessoal ou de dados de aplicação.

## O que o servidor serve

O `cc_server` é toda a superfície do produto, não um subconjunto: o caminho de
dados e as subscrições de repo-RPC, o endpoint de ferramentas MCP em `POST /mcp`
e `GET /sse` na mesma porta, os webhooks de entrada, os proxies de multimédia e de
tipos de letra, os callbacks de início de sessão único, o protocolo de lease da
frota, a recolha de RSS do lado do servidor segundo um agendamento de 30 minutos
e a pesquisa vetorial (a extensão `sqlite_vector` é registada como auto-extension
global do processo, degradando para pesquisa de texto integral apenas onde a
extensão não está disponível).

O dispatcher é **sem estado**: não existe qualquer vínculo de espaço de trabalho
por sessão. Cada chamada com âmbito de espaço de trabalho transporta o seu próprio
`workspace_id` e o acesso é decidido pela pertença e pela função do autor da
chamada no espaço de trabalho — não por deter uma chave de emparelhamento.

Duas coisas a saber antes de expor a porta para além do loopback:

- **O MCP falha em modo fechado fora do anfitrião.** Uma superfície MCP sem token responde apenas a loopback. Vincular `any` não a amplia — um pedido de fora do anfitrião é recusado com "MCP requires a bearer token to answer non-loopback clients" até configurar um token (`mcp.setToken`, ou **Definições → Servidor → Servidores MCP**).
- **`GET /healthz` não tem autenticação por conceção**, tem CORS com wildcard e publica o id, o nome, a impressão digital de identidade e a versão de compilação do servidor. Os clientes precisam da impressão digital para fixar o servidor, por isso isto é deliberado — mas significa que qualquer `cc_server` acessível divulga tudo isso a quem o pedir.
