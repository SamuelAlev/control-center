Este guia mostra-lhe como trabalhar com o Control Center sem sair do GitHub:
pedir uma revisão com IA a partir da página da PR, fazer uma pergunta ao bot num
comentário e manter a conversa a decorrer nas respetivas threads de revisão.

As respostas chegam pela faixa do GitHub do espaço de trabalho: a
[GitHub App](/pt-PT/manual/guias/github-app/) do seu próprio servidor, ou a App
partilhada do Control Center através do Connect. Não se regista nada de novo, e
nada tem de ser acessível a partir da internet: o servidor descobre o que foi
dito no GitHub por sondagem, pelo que um portátil atrás de NAT comporta-se
exatamente como uma implementação pública.

## Pré-requisitos

- O espaço de trabalho tem uma faixa do GitHub: a GitHub App do próprio
  servidor ou o Connect, com a app
  [instalada](/pt-PT/manual/guias/github-app/#instalar-onde-estão-os-seus-repositórios)
  na conta proprietária do repositório. Uma app própria precisa de **Pull
  requests** e **Issues** em leitura e escrita, que **Criar a minha app do
  GitHub** já concede
- O repositório está ligado a um espaço de trabalho no Control Center
- Tem [sessão iniciada no GitHub](/pt-PT/manual/guias/integracao-github/) neste
  servidor e pode fazer push para o repositório
- Sem URL de webhook, sem túnel, sem callback — não há nada para configurar do
  lado da rede

## Descobrir o nome do seu bot

Mencione `@usectrl`, a conta GitHub dedicada do Control Center. Este é o acionador predefinido; a faixa do GitHub do seu espaço de trabalho continua a tratar o pedido e a publicar as respostas. Não precisa das credenciais da conta `usectrl`.

O login da própria App, `<appslug>[bot]`, e a forma curta `@appslug` também funcionam. Para consultar esse alias opcional na sua própria app:

1. Vá a **Definições → Servidor → Início de sessão único** e desloque-se até ao
   cartão **Aplicações do fornecedor**
2. Abra o bloco **GitHub** e clique em **Testar**
3. Copie o **Login do bot** quando for preenchido. Se ainda mostrar a dica de
   campo vazio, o login é sempre `<appslug>[bot]` — escreva-o, ou então a forma
   curta `@appslug`

O GitHub não apresenta contas de App no preenchimento automático de `@`, pelo que os aliases da App têm de ser escritos ou copiados. O utilizador dedicado `@usectrl` é a forma predefinida de invocação; `@myapp` e `@myapp[bot]` continuam a ser aliases aceites da App.

:::note[Escolha um nome de aplicação distinto]
A forma curta é comparada como texto. Se um utilizador humano do GitHub partilhar
o slug da sua aplicação, mencionar esse utilizador pela forma curta também chega
ao bot. A forma completa `@myapp[bot]` é sempre inequívoca.
:::

## Pedir uma revisão a partir do GitHub

Duas formas, ambas iniciando o mesmo pipeline `pr_review` predefinido que o
botão **Ask AI** inicia:

- **Adicione a etiqueta `ai-review`** à PR. É a coisa mais próxima que o GitHub
  oferece de atribuir o bot como revisor — as contas de aplicação não podem
  ocupar o lugar nativo de revisor solicitado. A sua conta reage à PR com 👀 e
  a revisão começa no Control Center; não é publicado nenhum comentário
- **Comente `@usectrl review`** (ou apenas `@usectrl`) na conversa da PR. Surge
  um 👀 no seu comentário e depois uma resposta diz que a revisão começou (ou
  que uma já está a correr)

Os revisores trabalham no espaço de revisão da PR; leia e publique as
constatações como em [Usar revisão com IA](/pt-PT/manual/guias/revisao-com-ia/).
Voltar a publicar no GitHub continua a ser uma decisão que toma no Control
Center — iniciar uma revisão a partir do GitHub não publica nada no GitHub por si
só.

A etiqueta dispara uma vez por PR: adicioná-la é o pedido, e não é rearmada quando
é removida e adicionada de novo. Para executar uma revisão outra vez — depois de
um push, por exemplo — mencione o bot.

## Fazer uma pergunta

Comente na conversa da PR:

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

O que acontece, por ordem:

1. Surge um 👀 no seu comentário, vindo da sua própria conta, para que saiba que
   o comentário foi visto
2. A pergunta é publicada no espaço de revisão da PR **em seu nome** — a mesma
   atribuição que se a tivesse escrito no Control Center
3. Um agente responde no espaço, e a resposta é publicada de volta na PR. Cada
   resposta começa com `**Control Center** (for @your-login):`

Uma pergunta numa PR que ainda não tem revisão acorda o agente CEO do espaço de
trabalho; depois de uma revisão ter sido executada, responde o agente que falou
por último, pelo que as mensagens de seguimento chegam a quem tem o contexto.

## Continuar uma conversa numa thread de revisão

Responda dentro de uma thread de revisão inline da qual o bot faça parte — um
comentário de diff que tenha deixado, ou uma resposta que tenha publicado nessa
thread. Não é necessária nenhuma menção; a thread **é** o endereçamento:

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

Os vários turnos funcionam da mesma forma: cada resposta é outra pergunta na
mesma conversa, com o espaço de revisão como contexto, e a resposta volta na
thread.

Um seguimento na cronologia da conversa da PR é um novo comentário de nível
superior, pelo que continua a precisar de uma menção com @.

## Com quem o bot fala

O servidor resolve o autor de um comentário, ou quem adicionou a etiqueta
`ai-review`, antes de fazer seja o que for:

- **A conta do GitHub tem de ter sessão iniciada** neste servidor. A
  correspondência faz-se pelo id numérico da conta no GitHub, nunca pelo login.
  Inicie sessão em **Definições → Espaço de trabalho → Perfil e identidade →
  Hospedagem de código**
- **Tem de ser membro com um papel de escrita** (`member`, `admin` ou `owner`) no
  espaço de trabalho que liga o repositório
- **Tem de poder fazer push** para o repositório no GitHub. As respostas usam um
  token limitado ao acesso dessa pessoa, pelo que quem só pode ler não recebe
  resposta

Qualquer outra pessoa é ignorada em silêncio: nada é publicado, e as suas
palavras nunca entram no espaço de trabalho. Os comentários de bots, e as
próprias respostas do Control Center, nunca são tratados como perguntas.

### Dois servidores, uma PR

O 👀 é também a forma como os servidores acordam quem responde. É adicionado
com o início de sessão do próprio autor, e o GitHub indica ao servidor se essa
reação é nova. Se tiver sessão iniciada em dois servidores do Control Center
que ligam ambos o repositório, responde o primeiro a reagir e o outro fica em
silêncio. O mesmo vale para a etiqueta.

## O que esperar

| Aspeto               | Comportamento                                                            |
| -------------------- | ------------------------------------------------------------------------ |
| Reconhecimento       | 👀 da sua conta no comentário (ou na PR, no caso da etiqueta), dentro de uma varredura |
| Respostas            | Publicadas no canal onde a pergunta foi feita, a começar por `**Control Center** (for @your-login):`. Numa app própria, o autor é o bot da app; através do Connect é a sua conta, a atuar através da App partilhada |
| Atribuição no espaço | A pergunta é sua; o agente corre em seu nome, de acordo com as definições de autonomia do espaço |
| Revisões             | As constatações ficam no espaço de revisão; publicar no GitHub é manual   |

Numa app própria, corre uma varredura a cada minuto que verifica até 25 pull
requests; através do Connect corre a cada dois minutos e verifica até 10,
porque essas chamadas partilham a quota do GitHub de cada membro. Um espaço de
trabalho cuja quota do GitHub esteja abaixo de 15% é ignorado até recuperar. A
latência é o preço a pagar por não precisar de qualquer acesso de rede de
entrada. Nada se perde enquanto o servidor estiver offline — um comentário que
chega durante uma paragem é apanhado na varredura seguinte.

## Resolução de problemas

**Não acontece nada num comentário que menciona o bot.**

- A aplicação está **instalada** na conta que é proprietária do repositório, e o
  repositório está **ligado** a um espaço de trabalho? Um repositório não ligado
  é ignorado antes de algo ser registado, pelo que ligá-lo mais tarde ainda faz a
  entrega
- Tem sessão iniciada no GitHub neste servidor, é membro com um papel de
  escrita e pode fazer push para o repositório? O servidor ignora qualquer
  outra pessoa sem responder
- Na App partilhada do Control Center, a instalação da organização está
  autorizada para este servidor? Consulte
  [Autorizar este servidor para uma organização](/pt-PT/manual/guias/github-app/#autorizar-este-servidor-para-uma-organização)
- Continua sem acontecer nada? O registo do servidor indica a varredura e a PR
  quando algo falha; procure `pr_conversation:` (o componente de sondagem) e
  `github_pr_conversation:` (a ponte)

**A etiqueta não inicia uma revisão.**

Dispara uma vez por PR, e quem a adicionou passa pelas mesmas verificações que
o autor de um comentário. Se já correu uma revisão, ou se a etiqueta foi
adicionada antes de o servidor ter visto a PR (a primeira varredura regista o
trabalho acumulado em silêncio em vez de o desencadear de uma só vez), mencione
antes o bot — `@usectrl review` inicia sempre uma, a menos que já esteja uma
revisão em curso.

**A resposta do bot nunca chegou ao GitHub.**

A resposta em si nunca se perde — está no espaço de revisão da PR no Control
Center. Uma falha de publicação (GitHub em baixo, permissões alteradas) é
registada e a resposta não é repetida; volte a perguntar na thread se for
importante.
