Tudo o que o Control Center consegue copiar, entregar ou adotar, e a forma exata de cada
artefacto. Para tirar efetivamente uma cópia de segurança, consulte
[Fazer cópia de segurança e restaurar](/pt-PT/manual/guias/copia-de-seguranca-e-restauro/); para
perceber porque é que a persistência está dividida desta forma, consulte
[Espaços de trabalho e isolamento](/pt-PT/manual/conceitos/espacos-de-trabalho/).

## Artefactos

Existem três artefactos de cópia de base de dados, com âmbitos e políticas de eliminação
diferentes.

| Artefacto                                  | Escrito por                 | Forma                                        | Abrange                                |
| ------------------------------------------ | --------------------------- | -------------------------------------------- | -------------------------------------- |
| **Instantâneo da instalação**              | `server.backupNow`          | Um **diretório** com data e hora             | Todas as bases de dados da instalação  |
| **Cópia de segurança do espaço de trabalho** | Pipeline `Workspace backup` | Diretório com data e hora com um `.db`      | A base de dados de um espaço de trabalho |
| **Exportação do espaço de trabalho**       | `workspace.export`          | Um único ficheiro `.db`                      | A base de dados de um espaço de trabalho |

Todos são escritos com o `VACUUM INTO` do SQLite, que é seguro contra uma base de dados WAL
em funcionamento: abre uma transação de leitura, produz uma cópia desfragmentada e
transacionalmente consistente e nunca exige parar o servidor.

Estes ficheiros e as cópias descarregadas **não estão cifrados em repouso** pelo
Control Center. A transferência cifrada ponto a ponto protege os bytes em trânsito
entre um cliente emparelhado e o seu `cc_server`, em ligações diretas ou através do
relay. Proteja em separado o armazenamento local e as cópias fora da máquina; o
servidor e qualquer destinatário autorizado conseguem ler os ficheiros de base de
dados.

## Estrutura do instantâneo

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

A estrutura espelha exatamente o diretório de dados em funcionamento, e é isso que faz com
que restaurar uma instalação seja uma cópia de volta e não uma tradução. O nome do diretório
é a data e hora UTC com `:` e `.` substituídos por `-`, pelo que é seguro para sistemas de
ficheiros no Windows e ordena-se cronologicamente como uma cadeia simples.

As cópias de segurança agendadas de espaços de trabalho ficam à parte, em
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Cada uma tem um `manifest.json` só para esse ficheiro e não tem `global.db`; não são instantâneos da instalação. Uma restauração mantém a base de dados que ela substitui no mesmo lugar, como `<timestamp>-pre-restore`.
O passo de retenção do pipeline semanal remove apenas cópias de segurança do seu próprio espaço de trabalho mais antigas do que a idade configurada (30 dias por predefinição); os instantâneos da instalação criados manualmente nunca são rodados por esse passo. O `server.listBackups` lista apenas instantâneos da instalação, incluindo os não verificados; o `workspace.listBackups` lista as cópias de segurança agendadas de um espaço de trabalho.

Eliminar um espaço de trabalho mantém este diretório no lugar. O agendamento do espaço de
trabalho para com ele, pelo que nada volta a rodar essas cópias de segurança, e estas ficam
até o proprietário da instalação as remover. O `server.listOrphanedBackups` comunica-as.


### `manifest.json`

| Campo                       | Tipo            | Significado                                                        |
| --------------------------- | --------------- | ------------------------------------------------------------------ |
| `format`                   | int             | Formato do manifesto. Atualmente `2`                                |
| `created_at`                | ISO-8601 UTC    | Quando o instantâneo foi tirado                                    |
| `global`                   | object          | O registo de `global.db`. Ausente de uma cópia de segurança agendada de espaço de trabalho |
| `workspaces[]`              | array           | Um registo por espaço de trabalho capturado                       |
| `workspaces[].workspace_id` | string          | O espaço de trabalho que este ficheiro contém                      |
| `skipped_workspaces[]`     | array           | Espaços de trabalho que a cópia de segurança **não** conseguiu capturar                         |
| `skipped_workspaces[].workspace_id` | string | O espaço de trabalho que ficou de fora                                     |
| `skipped_workspaces[].reason` | string       | `no_file`, `damaged` ou `failed`                                    |

`global` e cada entrada de `workspaces[]` registam um ficheiro copiado, medido na cópia depois de ser escrita:

| Campo | Tipo | Significado |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`           | string | Caminho relativo à raiz do instantâneo: `global.db` ou `<workspaceId>/workspace.db` |
| `bytes`          | int             | Tamanho da cópia                                                    |
| `sha256`         | string | SHA-256 da cópia, em hexadecimal minúsculo                                          |
| `quick_check`    | string | O que o `quick_check` do SQLite disse sobre a cópia: `ok`, ou a sua constatação          |
| `user_version`   | int    | Versão do esquema da cópia                                                     |
| `application_id` | int    | `application_id` do SQLite da cópia                                            |

Um espaço de trabalho é ignorado quando está registado mas nunca foi escrito (`no_file`), quando a base de dados dele falha na verificação de integridade (`damaged`; uma cópia danificada nunca é feita), ou quando a cópia dele, ou a verificação dessa cópia, falhou (`failed`). De qualquer forma, o instantâneo conclui-se na mesma e o manifesto indica o que está em falta. O manifesto é escrito por último.

### Completude

O `server.listBackups` reporta um indicador `complete` por instantâneo. É falso quando o manifesto está ausente, não é analisável ou está noutro formato, quando um ficheiro que ele refere está em falta ou tem outro tamanho, ou quando uma cópia não passou na verificação. A aplicação mostra esse instantâneo como **Não verificado**. Os instantâneos tirados antes do formato `2` estão nesse estado.

Um instantâneo não verificado continua a ser listado, porque um instantâneo que um operador não
vê é um instantâneo que ele acredita ter. Quando o manifesto não é legível, a listagem
recorre à própria estrutura e reporta os ficheiros `<workspaceId>/workspace.db` que
encontrar — esses continuam a poder ser adotados individualmente através do
`workspace.import`, ainda que o instantâneo no seu todo não consiga restaurar uma instalação.

Um instantâneo listado ou uma cópia de segurança agendada tem `pinned_reason: "last_good_copy"` enquanto guarda a cópia verificada mais recente de um espaço de trabalho cuja base de dados ativa está danificada. A etapa de retenção o ignora até que esse espaço de trabalho seja restaurado.

## O que uma cópia de segurança não contém

Ambos os artefactos são **apenas bases de dados**. Um diretório de espaço de trabalho contém
mais do que a sua base de dados, e nada do resto viaja:

| Caminho                             | Num instantâneo? | Numa exportação de espaço de trabalho? |
| ----------------------------------- | ---------------- | -------------------------------------- |
| `global.db`                         | Sim              | Não                                    |
| `<workspaceId>/workspace.db`        | Sim              | Sim (*é* o ficheiro)                   |
| `<workspaceId>/code_index.db`       | Não              | Não                     |
| `<workspaceId>/blobs/`              | Não              | Não                                    |
| `<workspaceId>/skills/`             | Não              | Não                                    |
| `<workspaceId>/agents/`             | Não              | Não                                    |
| `<workspaceId>/chat_credentials/`   | Não              | Não                                    |
| `<workspaceId>/spaces/<spaceId>/`   | Não              | Não                                    |
| `<workspaceId>/pr_clones/`          | Não              | Não                                    |
| `secrets.json`                      | Não              | Não                                    |
| `models/`                           | Não              | Não                                    |
| `meetings/<meetingId>/`             | Não              | Não                                    |
| `rigs/`                             | Não              | Não                                    |
| `_agent_hooks/`                     | Não              | Não                                    |

Parte disso é descartável — `spaces/` contém worktrees copy-on-write que são reprovisionadas a partir dos repos, `pr_clones/` é uma cache, `code_index.db` é reconstruído, `models/` volta a ser descarregado e `rigs/` é estado da máquina. Outra parte não é: `blobs/` contém imagens coladas para as quais apontam linhas da base de dados, `skills/` e `agents/` contêm os ficheiros com que um agente é executado e `secrets.json` contém todas as chaves de emparelhamento, credenciais de fornecedor e definições de SSO da instalação. Consulte [Fazer cópia de segurança e restaurar](/pt-PT/manual/guias/copia-de-seguranca-e-restauro/#copiar-as-cópias-de-segurança-para-fora-da-máquina) para cobrir o resto.
:::note[Os segredos ficam fora das bases de dados]
O `workspace.db` é o espaço de trabalho inteiro: conversas, registos de execução, ligações a repositórios, definições de ambientes e membros. Os tokens de webhook dos pipelines e os segredos de webhook da sincronização de tickets ficam em `secrets.json`: a base de dados guarda uma referência a cada um, e o índice de rotas guarda um hash com chave de cada token. Por isso, um espaço de trabalho restaurado noutra instalação não recebe webhooks até que os gatilhos sejam guardados de novo lá. Os inícios de sessão em fornecedores, as chaves de dispositivo e os segredos de utilizador ficam em `global.db` e `secrets.json`.
:::

:::note[Os tokens de chat ficam deliberadamente para trás]
O facto de `chat_credentials/` estar ao lado da base de dados e não dentro dela é a razão
pela qual um espaço de trabalho entregue a outra pessoa não transporta tokens de bots
ativos. Consulte a
[referência de ponte de chat](/pt-PT/manual/referencia/ponte-de-chat/).
:::

## Operações

Os RPC de cópia de segurança da instalação e a exportação/importação de espaços de trabalho
são exclusivos de `fullClient`: um telefone emparelhado não os consegue acionar. Todos eles
estão totalmente ausentes — não recusados, estruturalmente em falta — num servidor sem porta
de cópia de segurança ligada, como o servidor de demonstração.

| Op                    | Tipo    | Âmbito             | Papel mínimo                      | Argumentos    | Devolve                       |
| --------------------- | ------- | ------------------ | --------------------------------- | ------------- | ----------------------------- |
| `server.backupNow`    | mutação | Instalação         | **proprietário** da instalação    | nenhum        | `{ok, path}`                  |
| `server.listBackups`  | leitura | Instalação         | **proprietário** da instalação    | nenhum        | `{backups: [...]}`            |
| `server.deleteBackup` | mutação | Instalação         | **proprietário** da instalação    | `name`        | `{ok}`                        |
| `server.listOrphanedBackups` | leitura | Instalação | **proprietário** da instalação | nenhum | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutação | Instalação | **proprietário** da instalação | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | leitura | Espaço de trabalho | `admin` | nenhum | `{backups: [...]}` |
| `workspace.deleteBackup` | mutação | Espaço de trabalho | `owner` | `name` | `{ok}` |
| `workspace.export`    | leitura | Espaço de trabalho | `admin`                           | nenhum        | `{ok, path}`                  |
| `workspace.import`    | mutação | Espaço de trabalho | `owner`, e o proprietário do servidor | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | leitura | Espaço de trabalho | `owner`, e o proprietário do servidor | nenhum | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutação | Espaço de trabalho | `owner`, e o proprietário do servidor | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`    | mutação | Instalação*        | `owner`                           | `id`          | linha do registo marcada como eliminada |

* O `workspace.delete` não tem âmbito porque a linha que marca vive no registo global; o seu
handler verifica a pertença do chamador ao espaço de trabalho indicado e exige `owner`.

O `path` em todas as respostas é um caminho no **anfitrião do servidor**.

O `server.listOrphanedBackups` devolve uma entrada por cada espaço de trabalho que já não
está ativo: `workspace_id`, `workspace_name` quando o registo ainda o conhece, e `backups`.
Um espaço de trabalho eliminado já não consegue passar numa verificação de papel do espaço
de trabalho, pelo que as suas cópias de segurança pertencem ao proprietário da instalação. O
`server.deleteOrphanedBackup` recusa um espaço de trabalho ativo, cujas cópias de segurança
continuam atrás de `workspace.deleteBackup` e dos papéis próprios desse espaço de trabalho.
Ambas as ops de eliminação aceitam apenas um nome de diretório com data e hora listado, não
um caminho.

`workspace.importHolds.list` devolve o que uma importação reteve. Cada retenção tem um `id`, um `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` ou `invite`), o `payload` que ela repunha, `imported_at` e `source_install_id`. `workspace.importHolds.resolve` com `accept: true` concede-a de novo e com `false` descarta-a. `applied` é falso quando quem ou o que a concessão era para já não está no espaço de trabalho.

:::note[Um instantâneo da instalação inteira exige o proprietário nas duas vias]
O `server.backupNow`, o `server.listBackups` e o `server.deleteBackup` exigem o
**proprietário** da instalação (`ServerAuthority.serverOwner`), o mesmo portão que o
`GET /backup/snapshot`. Um instantâneo captura a base de dados de todos os espaços de
trabalho, pelo que ser admin de um espaço de trabalho não chega para gerir os restantes. A
eliminação aceita apenas o nome do diretório com data e hora listado, não um caminho
arbitrário do servidor, e remove o instantâneo inteiro (incluindo instantâneos não verificados).
A exportação e as transferências das cópias de segurança agendadas por espaço de trabalho mantêm-se no admin do espaço de trabalho.
:::

:::note[A restauração é do proprietário do servidor]
`workspace.import` e `POST /backup/restore` fazem o servidor adotar um ficheiro de base de dados cujas linhas ele passa a tratar como suas: ligações a repositórios e quem as criou, definições de ambientes que correm no anfitrião, e caminhos de worktrees e de registos. Por isso ambos exigem o proprietário do servidor (`ServerAuthority.serverOwner`), que tem também de ser o proprietário do espaço de trabalho. Qualquer outra pessoa, e cada chamador num anfitrião sem proprietário registado, é recusado com `server_owner_required`. Nenhum gatilho, vista, coluna ou restrição que o ficheiro traga é adotado.
:::

### Resposta do `server.listBackups`

Os mais recentes primeiro, ordenados pelo nome do diretório (que é a data e hora, pelo que a
ordem se mantém mesmo para um instantâneo cujo manifesto não pôde ser lido).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

O `created_at` é omitido quando o manifesto não pôde ser lido. O `bytes` de nível superior é
o tamanho real em disco do diretório inteiro, não a soma do próprio manifesto — a pergunta
que um operador a limpar instantâneos faz é quanto custa o diretório, não o que a cópia de
segurança pretendia escrever.

Cada `workspaces[].path` é exatamente o que o `workspace.import` recebe como `source_path`.
Isso é deliberado: «restaurar este espaço de trabalho a partir deste instantâneo» *é* a
operação de importação, pelo que as duas não podem divergir para tratamentos diferentes do
mesmo ficheiro.

### Validação do `workspace.import`

Antes de se substituir seja o que for, o ficheiro candidato é copiado para um ficheiro de preparação ao lado do destino e verificado aí. Uma recusa não toca em nada e leva o seu tipo em `data.kind`.

| Condição                                              | Resultado                                                       |
| ----------------------------------------------------- | --------------------------------------------------------------- |
| O ficheiro não existe | Recusado, `import.missing_source` |
| Não é uma base de dados SQLite legível, ou falha em `quick_check` | Recusado, `import.damaged` |
| Vem de um instantâneo e a respetiva SHA-256 difere da do manifesto | Recusado, `import.checksum_mismatch` |
| Uma versão mais recente do servidor o escreveu | Recusado, `import.newer_schema` |
| Outro `application_id`, ou nenhum `workspace_meta` | Recusado, `import.foreign_file` |
| Não pode ser levado para o esquema deste servidor | Recusado, `import.schema_mismatch` |
| Os webhooks ou convites dele já são encaminhados para outro espaço de trabalho | Recusado, `import.route_conflict` |
| Id de espaço de trabalho registado ≠ o de destino     | **Permitido**. As linhas são reassociadas ao destino. É assim que um espaço de trabalho é duplicado ou restaurado com um id novo |
| Id de instalação registado ≠ esta instalação          | **Permitido**. Os ids de utilizador dela pertencem a essa instalação e não serão resolvidos aqui |

Ao ser aceite, o ficheiro de preparação é levado ao esquema deste servidor e tem então de corresponder a ele exatamente. As concessões que um ficheiro não pode dar a si próprio são-lhe retiradas: as aprovações para executar uma definição de ambiente no anfitrião são limpas, e as regras de ação que permitem ou pedem confirmação, as concessões de execução em sandbox, as concessões de repositório acima de leitura, as funções acima de membro e os convites para essas funções passam a ser retenções para o proprietário do servidor rever. Quem importa mantém ou recebe a função de proprietário. A base de dados substituída é guardada como uma cópia de segurança agendada com o nome `<timestamp>-pre-restore`; o ficheiro de preparação é renomeado para o seu lugar com as ligações do espaço de trabalho fechadas, o `code_index.db` é eliminado para ser reconstruído, e os índices de FTS são reconstruídos.

## Rotas de transferência

As operações de exportação/importação e de listagem de instantâneos acima falam em
caminhos do lado do servidor, o que só é uma resposta completa quando o servidor é
a sua própria máquina. Estas rotas em forma de HTTP transportam os bytes de cópia
de segurança **dentro do mesmo túnel de recursos autenticado e cifrado ponto a
ponto** de outros recursos sensíveis, quer a ligação RPC seja direta quer
intermediada. Não são endpoints públicos de transferência de ficheiros HTTP: um
pedido a um deles no listener público devolve `426 Upgrade Required`, mesmo do
loopback. Dentro do túnel cifrado, o dispositivo autenticado com Noise tem de
corresponder a `d`; o handler verifica ainda a assinatura do dispositivo sobre a
sua cadeia de destino usando a sua PSK de emparelhamento e o papel abaixo.

| Rota                    | Método | Query           | Alvo assinado                    | Exige                          |
| ----------------------- | ------ | --------------- | -------------------------------- | ------------------------------ |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **Admin** do espaço de trabalho |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **Proprietário** da instalação  |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **Admin** do espaço de trabalho; **proprietário** da instalação depois de o espaço de trabalho ser eliminado |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **Proprietário** da instalação que é também **proprietário** do espaço de trabalho (`403` com `server_owner_required` nos restantes casos) |

O `w` é um id de espaço de trabalho, o `n` um nome de diretório de instantâneo ou de cópia de
segurança agendada, o `d` o id do dispositivo que chama e o `s` a assinatura. Em
`/backup/snapshot`, o `n` é resolvido em relação à listagem de cópias de segurança e não
concatenado à raiz das cópias, pelo que a rota não pode ser apontada a um diretório que a
listagem não teria mostrado. Em `/backup/stored`, tem de ser um nome com data e hora, e o
ficheiro tem de ser um ficheiro real dentro do diretório de cópias de segurança desse próprio
espaço de trabalho.

| Estado | Causa                                                                               |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | Falta um parâmetro de query obrigatório, um nome de cópia de segurança é inválido, o corpo de um envio está vazio, ou o ficheiro enviado foi recusado (o corpo é `{error, kind}` com um tipo `import.*`) |
| `403`  | Dispositivo desconhecido ou revogado, assinatura inválida, ou o chamador não tem o papel |
| `404`  | Não há porta de cópia de segurança neste anfitrião, ou o ficheiro de instantâneo, cópia de segurança ou espaço de trabalho indicado não existe |
| `405`  | `/backup/restore` chamado com algo que não `POST`                                   |
| `413`  | O corpo do envio excede 8 GiB, pelo content-length declarado ou pelos bytes realmente lidos |
| `426`  | Qualquer pedido direto a uma rota de transferência no listener HTTP público; use o túnel de recursos cifrado de um cliente emparelhado |
| `500`  | A exportação ou o arquivo falhou do lado do servidor                                |

Os três descarregamentos respondem com `Cache-Control: no-store` e `Accept-Ranges: none`.
`/backup/workspace` e `/backup/snapshot` criam uma cópia **nova** por pedido e eliminam-na
assim que é transmitida em fluxo, pelo que uma resposta em cache ou retomada juntaria bytes
de duas exportações diferentes num ficheiro que parece válido e não é.

`/backup/stored` é a exceção: transmite em fluxo uma cópia de segurança agendada como
`<workspaceId>-<name>.db` e mantém o ficheiro no lugar, porque esse ficheiro é a cópia de
segurança.

O `/backup/snapshot` devolve `<name>.zip`, com entradas relativas à raiz do instantâneo, pelo
que descompactar reproduz `manifest.json` + `global.db` + `<workspaceId>/workspace.db`. As
entradas são escritas por ordem de ordenação, pelo que dois arquivos do mesmo instantâneo são
o mesmo arquivo.

O `/backup/restore` transmite o corpo diretamente para um ficheiro de preparação em vez de o
colocar em memória intermédia, limita-o antes e durante a leitura e elimina o ficheiro
preparado em **todos** os caminhos de saída, incluindo uma recusa.

::::caution[A ligação direta e o relay usam a mesma transferência cifrada]
O relay transporta pedidos de recursos, respostas em fluxo e bytes de envio como
texto cifrado; não consegue ler o conteúdo das cópias de segurança. Um caminho do
lado do servidor continua a ser um caminho no anfitrião do servidor, e não um
ficheiro no relay. O acesso continua a exigir o dispositivo emparelhado, a
assinatura do alvo e o papel aplicável de espaço de trabalho ou de instalação.
Nenhum dos transportes cifra em repouso os ficheiros de cópia de segurança
resultantes.
::::

## Caminhos e limites

| Item                                        | Valor                                                        |
| ------------------------------------------- | ------------------------------------------------------------ |
| Instantâneos                                | `<dataDir>/backups/<timestamp>/`                             |
| Cópias de segurança agendadas de espaços de trabalho | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Exportações de espaços de trabalho          | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Base de dados substituída por uma restauração | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Bases de dados como estavam antes de uma atualização mudar o formato delas | `<dataDir>/pre_upgrade/` e `<dataDir>/<workspaceId>/pre_upgrade/`, as duas mais recentes de cada |
| Preparação de transferências                | `<dataDir>/backups/transfer/` — uma bancada de trabalho, limpa pela rota que a escreve |
| Nome do arquivo do instantâneo              | `<snapshot directory name>.zip`                              |
| Limite de envio                             | 8 GiB por envio cifrado para `/backup/restore`               |
| Retenção                                    | Instantâneos da instalação: eliminação manual. Cópias de segurança de espaços de trabalho: pipeline semanal, predefinição de 30 dias, ou eliminação manual. Cópias de segurança de um espaço de trabalho eliminado: apenas eliminação manual |

Os diretórios `exports/`, `transfer/` e `workspace-backups/` não são instantâneos da
instalação e estão excluídos do `server.listBackups`. Só o último diretório tem retenção
agendada, e apenas enquanto o seu espaço de trabalho existir; eliminar um instantâneo da
instalação exige a ação explícita do proprietário da instalação.
