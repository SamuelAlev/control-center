O `cc_server` aloja um único registo de ferramentas MCP (JSON-RPC 2.0), servido na porta principal do servidor (predefinida: `9030`) em `POST /mcp` e `GET /sse`, com a versão de protocolo `2024-11-05`. Todos os clientes chegam ao mesmo registo: a aplicação de ambiente de trabalho, a build web, os clientes MCP externos e o runtime de agentes integrado. Os servidores MCP externos podem ser ligados ao mesmo registo como uma camada dinâmica.

## Dimensão do registo

| Medida                                                                                             | Quantidade |
| -------------------------------------------------------------------------------------------------- | ---------- |
| Ferramentas registadas pelo `cc_server`                                                            | 110        |
| De `packages/cc_mcp`                                                                               | 108        |
| De `packages/cc_mcp_client` (deteção de ferramentas)                                               | 2          |
| Registadas no registo base (`server_mcp_registry.dart`)                                            | 63         |
| Registadas após o arranque, à medida que os respetivos serviços ficam operacionais (`cc_server_runtime.dart`) | 47 |
| Das 63 do registo base, condicionais a um repositório de grafo de código                           | 5          |

As cinco ferramentas de grafo de código só são registadas quando o anfitrião passa um repositório de grafo de código a `buildServerMcpRegistry`. O `cc_server` passa sempre um, pelo que todas as 110 estão ativas no binário distribuído.

O registo completo é anunciado em `tools/list`, sem restrição de deteção. As edições de tickets são ferramentas tipadas.

:::note[Os clientes externos veem sempre o catálogo completo]
O `tools/list` nunca é reduzido. Os clientes MCP validam os nomes das ferramentas face à sua própria cópia em cache dessa lista e recusam tudo o que não esteja listado sem perguntar ao servidor, pelo que uma ferramenta aí oculta é inalcançável, e não apenas silenciosa.

O **harness integrado** é diferente: carrega apenas um subconjunto residente de definições por pedido e vai buscar o resto no primeiro uso, o que é um comportamento do lado do harness e não altera este registo. Ver [Contexto de ferramentas e cache de prompts](/pt-PT/manual/conceitos/contexto-de-ferramentas/).
:::

:::note[Todas as classes de ferramentas são registadas]
Um ficheiro de código-fonte em `packages/cc_mcp/lib/src/tools/` é uma ferramenta que um agente pode invocar. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart` faz falhar a build se uma nova classe de ferramenta não for construída por nada.
:::

## Parâmetros comuns

### `workspace_id`

**Obrigatório** em todas as ferramentas que tocam dados no âmbito de um espaço de trabalho. Um `workspace_id` em falta ou inválido devolve um erro explícito, e um valor que não corresponda ao espaço de trabalho da entidade de destino é rejeitado em vez de ignorado em silêncio. Omita-o nas ferramentas genuinamente globais: `list_workspaces` e as seis ferramentas do feed de notícias (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), que usam a lista de feeds por utilizador do proprietário do servidor. As ferramentas de deteção (`search_tool_bm25`, `list_my_tools`) aceitam-no opcionalmente, para poderem classificar o que é invocável consoante o modo de conversa. Quando é o servidor que despacha um agente, o espaço de trabalho é imposto do lado do servidor, pelo que o agente não consegue alcançar outro espaço de trabalho passando um id alheio.

## Deteção de ferramentas

Ambas vêm do `cc_mcp_client`, não do `cc_mcp`, e ambas consultam a proteção do modo, para indicarem o que é invocável no modo de conversa _atual_.

| Ferramenta         | Descrição                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `search_tool_bm25` | Pesquisa o catálogo de ferramentas por palavra-chave; devolve as ferramentas correspondentes, os respetivos esquemas de argumentos e se cada uma pode ser invocada neste momento |
| `list_my_tools`    | Lista as ferramentas que podem ser invocadas neste momento nesta conversa, filtradas pelo respetivo modo                         |

Uma terceira ferramenta de deteção, **`search_tools`**, existe apenas dentro do harness integrado e não faz parte deste registo MCP. Classifica a própria superfície de ferramentas da execução e, ao contrário de `search_tool_bm25`, **carrega** os esquemas do que encontra, para que o agente possa invocar uma correspondência no turno seguinte. Os agentes no harness devem preferi-la; os clientes MCP têm `search_tool_bm25`.

## Mensagens e delegação entre agentes pares

Os agentes comunicam entre si através de espaços (duráveis, visíveis no roster). O `ask_agent` é um pedido/resposta com um tempo limite obrigatório; o `delegate_task` é protegido do lado do servidor por limite de profundidade, deteção de ciclos, envelope orçamental e teto de autonomia.

| Ferramenta      | Descrição                                                                                          |
| --------------- | -------------------------------------------------------------------------------------------------- |
| `send_to_agent` | Envia uma mensagem unidirecional a outro agente, endereçada por `to_agent_id` ou por `to_agent_name` exato |
| `ask_agent`     | Coloca uma pergunta a outro agente e aguarda a resposta, ou expira                                 |
| `delegate_task` | Delega uma tarefa a outro agente como ticket acompanhado                                           |
| `consult_agent` | Adiciona ao espaço o especialista que melhor corresponde em termos de skills e despacha-o com um briefing focado |
| `todo_read`     | Lê a lista de tarefas persistida desta conversa                                                    |

## Ferramentas de recinto (rig)

Controlam máquinas descartáveis — um navegador ou ambiente de trabalho Linux em recinto fechado, um emulador Android ou um iOS Simulator — a partir de dentro de uma execução. Registadas após o arranque, incondicionalmente: saber se uma máquina consegue de facto arrancar é uma questão de sondagem que as ferramentas respondem a cada chamada. Chamadas repetidas numa mesma conversa reutilizam a mesma máquina; as capturas de ecrã são devolvidas como conteúdo de imagem, com um orçamento de uma imagem por resultado, e o conteúdo de página/interface extraído é delimitado como dados não fidedignos. As quatro ferramentas de utilização, mais a `rig_close`, declaram a [classe de ação](/pt-PT/manual/conceitos/barreiras/) `enclosureControl` (as ferramentas de utilização declaram também `networkEgress` e `processSpawn`; a `mobile_use` e a `ios_use` declaram ainda `packageInstall`), pelo que os modos só de leitura as negam. A `rig_list` não declara nenhuma — apenas lê o estado do espaço de trabalho. O vocabulário completo de verbos por superfície está na [referência de Rigs](/pt-PT/manual/referencia/rigs/#action-verbs).

| Ferramenta     | Descrição                                                                                       |
| -------------- | ----------------------------------------------------------------------------------------------- |
| `computer_use` | Controla um ambiente de trabalho Linux numa VM em recinto fechado: mover, clicar, arrastar, deslocar, escrever, redimensionar, área de transferência, captura de ecrã |
| `browser_use`  | Controla um Chromium, Firefox ou WebKit headless (`engine`): navegar, clicar, preencher, extrair (a11y/DOM/consola), área de transferência, captura de ecrã |
| `mobile_use`   | Controla o Android através de ADB: inspecionar/introduzir, capturas de ecrã, instalar/iniciar/parar/reiniciar/desinstalar aplicações, links diretos e comandos de dispositivo em formato argv |
| `ios_use`      | Controla o iOS Simulator através de WebDriverAgent/CoreSimulator: inspecionar/introduzir, capturas de ecrã, instalar/iniciar/parar/desinstalar aplicações, links diretos e processos de simulador em formato argv |
| `rig_list`     | Lista os rigs de um espaço de trabalho com a superfície, o estado, o tamanho do ecrã e o controlador |
| `rig_close`    | Destrói um rig e descarta o estado da máquina que lhe pertence                                  |

## Não expostas por MCP

O calendário e as reuniões não têm ferramentas MCP. Os agentes não conseguem ler o seu calendário, as reuniões, as transcrições, os itens de ação ou as decisões. O resumo que produz os itens de ação e as decisões é executado como o [pipeline `meeting_summary`](/pt-PT/manual/conceitos/reunioes/) integrado, e não como uma ferramenta que um agente possa invocar.

## Restrição de ferramentas por modo

A restrição é imposta duas vezes a partir de uma única tabela (`ModeToolPolicy`): uma vez no despachante MCP do adaptador Claude Code e outra no registo do harness integrado. Uma chamada bloqueada devolve o motivo.

| Modo          | Superfície de ferramentas                                                                                                                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | Todas as ferramentas registadas; sem lista de autorizações                                                                                                                                                                          |
| `plan`        | Uma lista de autorizações escolhida a dedo. Sem escritas na worktree e sem os verbos de ticket `create` / `assign` / `delegate`, mas são permitidas a memória, os artefactos, as listas de tarefas, `submit_plan`, `exit_plan_mode` e os verbos de conclusão de tickets no ticket despachado |
| `review`      | Uma lista de autorizações escolhida a dedo: participação em revisões, comunicação, obtenção de contexto só de leitura e o conjunto completo de verbos de tickets, incluindo `create_ticket` e `assign_ticket`                       |
| `orchestrate` | Uma lista de autorizações escolhida a dedo: ferramentas de investigação e de leitura, mais `propose_orchestration`, `create_playbook` e `run_playbook`. A contratação, a decomposição e a conclusão de tickets acontecem de forma determinística após a aprovação, nunca a meio da execução |

Permitidas em todos os modos, independentemente da lista de autorizações:

| Conjunto             | Ferramentas                                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Memória e artefactos | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact`    |
| Grafo de código      | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                        |
| Mecânica de execução | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                     |

Estar numa lista de autorizações não torna uma ferramenta invocável, e o inverso também é verdade: a capacidade de colocar perguntas ao operador é uma ferramenta do **harness** (`ask_user`), pelo que nunca aparece neste catálogo MCP.

## Ferramentas sujeitas a aprovação

Uma ferramenta pode declarar `requiresApproval`. O despachante constrói então um `ApprovalPayload` e apresenta-o através do `ConfirmationPort` antes de a ferramenta ser executada; o `cc_server` liga essa porta, pelo que o portão está ativo.

Ferramentas registadas que o declaram: `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

De forma independente, as barreiras de ação unificadas restringem qualquer ferramenta que declare um conjunto `ActionClass` não vazio. Uma decisão `prompt` sem nenhum aprovador ligado é negada. Ver [Barreiras](/pt-PT/manual/conceitos/barreiras/).

## Capacidades sem ferramenta por trás

Nem todas as capacidades do produto são acessíveis a um agente. Estas não têm ferramenta nenhuma, pelo que um nome que possa ter visto referido noutro sítio devolve «unknown tool»:

| Capacidade                                  | Onde reside em alternativa                                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Contratar, despedir ou editar um agente     | A interface de agentes. Não existe a ferramenta `hire_agent` / `fire_agent` / `update_agent`              |
| Criar um espaço de trabalho                 | `workspace.upsert` por RPC, que inicializa e marca a propriedade                                          |
| Projetos (criar / listar / atualizar / colocar um ticket) | A interface de tickets. Os projetos são uma superfície do operador — ver [Projetos](/pt-PT/manual/guias/projetos/) |
| Colocar ao operador uma pergunta bloqueante | A ferramenta `ask_user` do **harness**, não o MCP. Apresenta um formulário na conversa e bloqueia à espera da resposta |
| Diagnósticos por agente                     | Nada. Não existe `doctor` — ver [Diagnóstico de um agente](/pt-PT/manual/guias/diagnosticar-agente/)       |
| Calendário e reuniões                       | RPC apenas para clientes humanos (ver acima)                                                              |
