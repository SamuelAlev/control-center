Estas são as ferramentas **ligadas ao servidor** que o runtime de agente integrado regista diretamente — servidor de linguagem, pesquisa estrutural, depurador, kernels, scripts do modo de código, perguntas e controlo de workers — por oposição às [ferramentas MCP](/pt-PT/manual/referencia/ferramentas-mcp/) que interliga e às ferramentas genéricas de ficheiros, pesquisa e shell do runtime do harness. Não estão no registo MCP: um cliente MCP externo não as verá, porque cada uma está ligada a um recurso vivo do lado do servidor — um processo de servidor de linguagem, um adaptador de depuração, um interpretador — que pertence a uma execução.

Cada ferramenta aqui só é registada quando o recurso que a sustenta está ligado para a execução — um supervisor de servidor de linguagem ou de depuração, um analisador tree-sitter, uma fábrica de kernels, uma porta de perguntas, um conjunto de workers do vibe. A deteção de um servidor de linguagem ou de um adaptador de depuração para *este checkout* é uma verificação separada e posterior (`status` / `adapters`): essas ferramentas mantêm-se na superfície para que o agente possa perguntar porque é que nada é utilizável, em vez de adivinhar.

## Níveis de aprovação

Cada ferramenta declara um nível, e o nível decide **que superfícies a veem** — não apenas se emite um pedido de aprovação. O modo de plano e os subagentes só de leitura estão limitados a `read`, pelo que uma ferramenta de nível `write` ou `exec` está totalmente ausente do respetivo esquema.

| Nível   | Significado                            | Ferramentas aqui                                   |
| ------- | -------------------------------------- | -------------------------------------------------- |
| `read`  | Sem efeitos secundários                | `lsp`, `ast_grep`, `ask_user`, `repl`, as cinco `vibe_*` |
| `write` | Altera ficheiros                       | `lsp_rename`, `ast_edit`, `resolve`                |
| `exec`  | Inicia ou controla um processo         | `debug`, `eval`                                    |

## Direta, exclusiva de script ou carregada na primeira utilização

Quando o servidor consegue executar scripts, uma execução chama algumas ferramentas diretamente e alcança o resto a partir de um script [`repl`](#repl--executar-um-script-que-chama-as-suas-ferramentas); veja [Modo de código](/pt-PT/manual/conceitos/modo-de-codigo/#quais-as-ferramentas-que-o-agente-chama-diretamente) para a regra completa. Para as ferramentas desta página:

| Ferramenta | Com `repl` | Sem `repl` |
| ---- | ----------- | -------------- |
| `repl` | Direta | Não presente |
| `ask_user` | Direta | Direta |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Só a partir de um script | Carregada na primeira utilização |
| `eval` | Carregada na primeira utilização (um script não a pode chamar) | Carregada na primeira utilização |
| `vibe_*` | Direta no modo vibe, nunca a partir de um script | Direta no modo vibe |

Uma ferramenta marcada como «Só a partir de um script» passa a ser carregada na primeira utilização quando o servidor não consegue executar os scripts da execução ([Quando os scripts não podem correr](/pt-PT/manual/conceitos/modo-de-codigo/#quando-os-scripts-não-podem-correr)).

## `lsp` — consultas ao servidor de linguagem

Registada quando a execução tem um supervisor de servidor de linguagem e um diretório de trabalho. Se um servidor consegue mesmo responder é detetado no momento da chamada, como uma **interseção**: tem de existir um marcador de raiz *e* o binário do servidor tem de resolver. Qualquer um deles sozinho significa que nenhum servidor arranca — o `status` di-lo — em vez de uma suposição silenciosa.

Os servidores vêm apenas da tabela incorporada; um `lsp.json` do repositório não é lido. Numa execução em sandbox, cada execução tem a sua própria sessão de servidor de linguagem, pelo que os servidores arrancam de novo a cada execução. Os binários locais do projeto (`node_modules/.bin`) são usados apenas quando a execução está em sandbox, e a raiz do projeto nunca resolve acima do diretório de trabalho da execução.

As posições são indicadas por `line` mais uma subcadeia `symbol`, nunca por coluna. Um modelo a quem se pede uma coluna adivinha, e uma suposição errada resolve para um símbolo diferente na mesma linha — uma resposta que parece certa e é sobre outra coisa. Omitir `symbol` numa ação de navegação é um erro, não uma suposição da primeira coluna.

| Ação              | Argumentos                       | Devolve                                    |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (ou `"*"`)                | Erros e avisos; `"*"` executa o verificador do projeto em vez disso |
| `definition`      | `file`, `line`, `symbol`         | Onde o símbolo é declarado                 |
| `type_definition` | `file`, `line`, `symbol`         | Onde o seu tipo é declarado                |
| `implementation`  | `file`, `line`, `symbol`         | Implementações concretas                   |
| `references`      | `file`, `line`, `symbol`         | Cada utilização, limitada a 50             |
| `hover`           | `file`, `line`, `symbol`         | Assinatura e comentário de documentação    |
| `symbols`         | `query` ou `file`                | Pesquisa no espaço de trabalho com `query` (limitada a 100); símbolos do documento com `file` (limitados a 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Correções rápidas que o servidor oferece   |
| `status`          | —                                | Que servidores estão a correr, e para que raízes |
| `reload`          | —                                | Reinicia o servidor para esta raiz         |

### Diagnósticos ao escrever

O ganho não está na ferramenta. `write`, `edit` e `apply_patch` estão **envolvidas**: depois da escrita, o ficheiro é sincronizado e guardado através do servidor de linguagem, e apenas os diagnósticos **introduzidos recentemente** são incorporados no resultado da ferramenta. Um agente fica a saber que quebrou a build no momento em que a quebrou, sem ter de se lembrar de perguntar.

Os diagnósticos já reportados são suprimidos por um registo por execução indexado por gravidade, código e mensagem — com a posição deliberadamente excluída, para que um diagnóstico que apenas desceu quatro linhas não volte a ser reportado como novo.

## `lsp_rename` — renomear em todo o projeto

Uma ferramenta separada, de nível `write`, por um motivo exato: é o nível que decide a visibilidade. Incluir a renomeação no `lsp` daria a um explorador só de leitura a capacidade de reescrever o repo, ou colocaria cada `hover` atrás de um pedido de aprovação.

| Argumento  | Significado                                |
| ---------- | ------------------------------------------ |
| `file`     | Onde está o símbolo                        |
| `line`     | Linha com índice 1                         |
| `symbol`   | Subcadeia que o identifica nessa linha     |
| `new_name` | Como o chamar                              |

## `ast_grep` — pesquisa estrutural

Encontra código pela **forma** em vez de pelo texto. O `$NAME` corresponde a qualquer nó, o `$$$NAME` corresponde a uma sequência de irmãos, e o `$_` é um curinga que não vincula nada.

A propriedade que o torna um comparador e não uma expressão regular com passos extra: uma metavariável repetida num padrão tem de capturar o mesmo texto.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

corresponde a uma guarda que descarta aquilo que testou, e **não** corresponde a uma que descarta outra coisa.

| Argumento     | Significado                                                 |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | Um fragmento de código com metavariáveis                    |
| `path`        | Ficheiro ou diretório a pesquisar; por omissão, todo o espaço de trabalho |
| `language`    | Um id de gramática incluído (`dart`, `python`, `rust`, `c`, …). Inferido quando `path` indica um ficheiro |
| `max_results` | Por omissão 50                                              |

:::note[O padrão é analisado pela mesma gramática do ficheiro]
Assim, `dispose(x)` corresponde à chamada independentemente do espaçamento, das quebras de linha ou dos comentários — e nunca corresponde aos mesmos caracteres dentro de um literal de string ou de um comentário.
:::

:::caution[Um fragmento é analisado num andaime, não isolado]
`dispose(x)` analisado no nível superior do Dart é uma *assinatura de função* válida. O compilador de padrões tenta uma escada de contextos (instrução, expressão, membro de classe, declaração) e usa o primeiro que aceita o fragmento. Um padrão que nenhum contexto aceita é reportado como não analisável em vez de ser procurado e silenciosamente não encontrado.
:::

## `ast_edit` — reescrita estrutural, preparada

A mesma correspondência, mais um modelo `rewrite` com as metavariáveis substituídas de volta. **Nada é escrito.** A alteração é preparada e o resultado indica um `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Argumento  | Significado                                         |
| ---------- | --------------------------------------------------- |
| `pattern`  | O que corresponder                                   |
| `rewrite`  | O que colocar lá, com `$NAME` substituído            |
| `path`     | Âmbito; por omissão, todo o espaço de trabalho        |
| `language` | Id da linguagem                                      |

## `resolve` — confirmar ou descartar uma alteração preparada

| Argumento | Significado                       |
| --------- | --------------------------------- |
| `edit_id` | Do resultado `(proposed)`         |
| `action`  | `accept` ou `discard`             |

Cada ficheiro é comparado com o conteúdo capturado no momento da preparação, e **qualquer** divergência recusa a alteração inteira. Uma reescrita estrutural aplicada em parte deixa uma árvore que não compila nem na forma antiga nem na nova.

## `debug` — conduzir um depurador

Registada quando a execução tem um supervisor de sessão de depuração, um diretório de trabalho e um id de conversa. Se um adaptador consegue mesmo arrancar é detetado no momento da chamada, pela mesma regra de interseção do servidor de linguagem (marcador de raiz *e* binário). Nível `exec`; não é seguro em paralelo (uma sessão é estado entre chamadas, pelo que um `continue` a ultrapassar um `stack` leria um frame que já se moveu).

Uma sessão por conversa, com um TTL rígido (30 minutos). Um segundo `launch` é recusado em vez de substituir silenciosamente o primeiro. Numa execução em sandbox, a sessão mantém a sua sandbox entre turnos até terminar, por isso durante no máximo esses 30 minutos.

| Op            | Argumentos                    | Notas                                          |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Que adaptadores são utilizáveis aqui, e porque não |
| `status`      | —                             | Se há uma sessão a correr, e onde parou        |
| `breakpoints` | `file`, `lines[]`             | Um `lines` vazio limpa o ficheiro. Podem ser definidos **antes** de iniciar |
| `launch`      | `program`, `args[]`           | Inicia o programa parado nos seus pontos de interrupção |
| `attach`      | `port`                        | Liga-se a um programa em depuração já a correr numa das portas reencaminhadas da própria execução; qualquer outra porta é recusada antes de algo arrancar |
| `continue`    | `thread_id?`                  | Executa até à paragem seguinte                 |
| `pause`       | `thread_id?`                  | Pára-o onde está                               |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Avança um passo                        |
| `threads`     | —                             | Ids e nomes das threads                        |
| `stack`       | `thread_id?`                  | Frames, limitados a 30                         |
| `scopes`      | `frame_id`                    | Âmbitos de um frame, cada um com uma `reference` |
| `variables`   | `reference`                   | Filhos, limitados a 50; valores limitados a 400 caracteres |
| `evaluate`    | `expression`, `frame_id?`     | Avaliada no próprio âmbito do frame            |
| `output`      | —                             | O stdout/stderr do programa em depuração, limitado |
| `terminate`   | —                             | Termina a sessão e mata o adaptador            |

### Adaptadores

| Id        | Comando                      | Marcadores de raiz                              |
| --------- | ---------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`         | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                   | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                    | `go.mod`                                        |

O `debugpy` prefere um `.venv/bin` ou `venv/bin` local do projeto em vez do `$PATH` quando a execução está em sandbox: um python do `$PATH` é um ambiente diferente, e anexar a partir do errado falha de uma forma que se lê como código avariado. Fora da sandbox usa apenas o `$PATH`, pelo que um repositório não pode escolher o interpretador que corre no host.

## `repl` — executar um script que chama as suas ferramentas

Presente em todas as execuções quando o servidor consegue executar scripts ([Quando uma execução tem `repl`](/pt-PT/manual/conceitos/modo-de-codigo/#quando-uma-execução-tem-repl)). O script é JavaScript simples, o corpo de uma função assíncrona, e executa-se num interpretador novo e bloqueado, no seu próprio processo: sem acesso ao sistema de ficheiros, à rede, a processos ou a módulos. O próprio `repl` pertence ao nível `read` e protege-se a si mesmo, porque cada chamada de ferramenta que o script faz é verificada separadamente. Também no endpoint MCP, para execuções de agente num servidor que consegue executar scripts.

| Argumento | Significado |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | O script. No máximo 256 KiB |
| `description` | Obrigatório. Uma etiqueta curta para a linha da conversa |
| `timeout_ms` | Opcional. Um limite de tempo mais curto do que o do espaço de trabalho; nunca mais longo |
| `max_output_tokens` | Opcional. Um orçamento de saída menor do que o do espaço de trabalho; nunca maior |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

A descrição de `repl` diz ao agente: «Uma ferramenta que não é uma das suas ferramentas diretas não tem definição neste pedido. Antes da primeira chamada a uma delas, procure-a com `describeTool(name)` ou `searchTools(query)`, a menos que a sua forma exata de chamada já lhe tenha sido mostrada nesta conversa.»

`describeTool(name)` devolve a descrição de uma ferramenta, a sua declaração, os seus esquemas de entrada e de saída e a sua nota de resultado, quando tem uma: o que um script recebe de uma chamada concluída, nas palavras da própria ferramenta. A descrição de `repl` lista as notas das ferramentas diretas que um script pode chamar. Um resultado que é texto JSON chega já interpretado, a menos que tenha mais de 131 072 valores: nesse caso chega como texto, e o script interpreta-o com `JSON.parse`. O texto de um resultado de uma ferramenta de um servidor MCP externo é cortado a 262 144 caracteres, e o texto cortado deixa de poder ser interpretado.

- `tools.<name>(args)` chama uma ferramenta através do mesmo filtro, das mesmas barreiras e da mesma aprovação de uma chamada direta, e rejeita com um erro quando é recusada ou falha. As chamadas só de leitura podem correr em conjunto; as que alteram algo correm uma de cada vez, pela ordem em que o script as fez. Enquanto uma das suas chamadas espera por uma pessoa, nenhuma outra chamada do script começa.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` e `describeNamespace(name)` encontram ferramentas, incluindo as dos servidores MCP ligados. Uma ferramenta fora do conjunto direto que um script pode chamar só é chamável a partir de um script; chamá-la diretamente devolve a forma de a chamar a partir de `repl`. Quando o servidor não consegue executar os scripts da execução, essa ferramenta é carregada na primeira utilização.
- As consultas têm limites: uma pesquisa com no máximo 1 024 caracteres, um nome ou namespace com no máximo 256, `limit` de 0 a 50, e no máximo 200 consultas que, no total, levem 2 segundos do tempo do servidor por script, enquanto todos os scripts de um espaço de trabalho partilham 2 segundos de tempo de consulta, devolvidos à razão de um quarto de segundo por cada segundo; ao esgotar qualquer um dos dois limites, as consultas seguintes são rejeitadas. Num catálogo muito grande, as descrições em `ALL_TOOLS` partilham de forma igual cerca de um milhão de caracteres, e uma descrição cortada termina em `…`; `describeTool` devolve sempre a descrição completa. Um tipo grande demais para mostrar aparece como `unknown /* too large to show */`, e um nome desconhecido recebe como resposta os nomes mais próximos.
- As ferramentas são agrupadas em namespaces: `builtin` (as ferramentas do próprio harness), `control-center` (as ferramentas do Control Center) e um por cada servidor MCP ligado, com o nome desse servidor. Um servidor chamado `builtin`, `control-center` ou `script`, ou cujo nome comece por `external-`, em qualquer combinação de maiúsculas e minúsculas e com ou sem espaços à volta, é listado como `external-` seguido do seu nome, e nenhuma ferramenta fica alguma vez em `script`.
- Só regressa ao agente o que o script devolve ou passa a `text()`, `image()` ou `console.*`. A saída além do orçamento mantém o início e o fim, e `read_output` lê o resto.
- `store(key, value)` / `load(key)` guardam valores JSON para os scripts seguintes da mesma conversa e do mesmo agente, gravados apenas quando o script termina. Os scripts de um subagente não têm armazenamento.
- `await tools.ask_user(...)` faz uma pergunta; a resposta é também acrescentada ao resultado. `sleep(ms)`, `setTimeout`, `limits()` e `models.embed` / `rank` / `classify` (embeddings no próprio dispositivo) também estão disponíveis.
- `describeTool(name)` e `searchTools(query)` também respondem para as funções próprias do script, que não são ferramentas: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` e `models.*`, sob o espaço de nomes `script`.
- Não chamáveis a partir de um script: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` e os verbos `vibe_*`.
- Um script lê o passado da sua própria execução: `history({start, role, tool, limit})` pagina a transcrição da conversa (no máximo 50 linhas por chamada; passe o `next_start` da página anterior como `start`), `outputs()` lista os resultados de ferramentas guardados para esta conversa e este agente, e `loadOutput(handle)` lê 16 384 caracteres de um deles. `storedKeys()` lista as chaves guardadas com os respetivos tamanhos. `keep(value, label)` guarda um valor grande como resultado que um script posterior ou `read_output` pode ler, gravado apenas quando o script termina (1 MiB por valor, 64 valores e 16 MiB por execução). `limits().returnBudgetChars` indica quanto do orçamento de saída resta. Uma execução só de leitura (uma revisão de objetivo) pode ler, mas não guardar nem usar keep. No Claude Code e no ACP, `history()` funciona, e `outputs()`, `loadOutput()` e `keep()` são recusados, porque o Control Center não guarda resultados de ferramentas dessas execuções.
- Um erro de timeout, de excesso de saída ou de limite de chamadas indica como o corrigir.

Uma execução corre um script de cada vez. Os limites e o que acontece em cada caso estão na página [Modo de código](/pt-PT/manual/conceitos/modo-de-codigo/#limites); cada script fica registado em **Observabilidade → Execuções de código**.

## `eval` — interpretadores persistentes

Uma célula Python ou JavaScript cujas variáveis, importações e dados carregados sobrevivem entre chamadas. Nível `exec`; não é seguro em paralelo. Não é chamável a partir de um script `repl`, e uma célula não pode chamar as ferramentas da execução: para chamar ferramentas a partir de código, use [`repl`](#repl--executar-um-script-que-chama-as-suas-ferramentas).

| Argumento     | Significado                                      |
| ------------- | ------------------------------------------------ |
| `code`        | A célula                                         |
| `description` | Obrigatório. 5 a 10 palavras para a etiqueta da transcrição |
| `language`    | `python` (predefinição) ou `javascript`          |
| `reset`       | Descarta o interpretador e começa primeiro de forma limpa |

- A última expressão é ecoada como num notebook.
- O `display()` funciona, um DataFrame do pandas é representado como uma tabela, e uma figura do matplotlib volta como uma **imagem que a transcrição mostra**.
- Os idiomas do IPython que as pessoas escrevem por reflexo — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — são reescritos como código simples. O `%pip` também expulsa o `sys.modules`, para que o próximo `import` veja o que acabou de ser instalado.
- Uma célula que imprime mais do que o seu orçamento de saída guarda os primeiros três quartos e o último quarto, com uma linha a dizer quantos caracteres e imagens foram descartados.
- Quando o interpretador morreu sem que ninguém o pedisse, a célula seguinte é informada uma vez de que as suas variáveis anteriores desapareceram.

:::note[Onde é que o kernel é executado]
No recinto da conversa quando esta tem um, caso contrário na sandbox do sistema operativo da execução, no anfitrião. Com a sandbox desligada ou indisponível, corre sem confinamento e o `eval` pede aprovação para executar comandos no host. Não arranca um recinto para lá chegar — a mesma regra que impede um separador de rig de arrancar automaticamente.
:::

## `bash` em segundo plano

`bash` com `run_in_background: true` inicia o comando e devolve de imediato um identificador (`b1`, `b2`, …) em vez de esperar. O agente continua a trabalhar, ou termina o seu turno e é acordado quando o comando termina.

| Argumento | Significado |
| ------------------- | ------- |
| `run_in_background` | `true` para iniciar e devolver de imediato |
| `timeout_seconds` | Segundos antes de o comando ser terminado: 600 por predefinição, 3 600 no máximo |
| `notify` | Opcional. Um padrão simples; cada linha de saída que corresponde é enviada ao agente enquanto o comando corre (como `listening on\|FAILED`) |

- No máximo 4 comandos em segundo plano correm ao mesmo tempo numa execução. Cada um é terminado no seu timeout e quando a execução acaba, juntamente com todos os processos que iniciou.
- Quando um comando termina, o agente recebe um aviso com o código de saída, os últimos 2 000 caracteres de saída e um identificador de `read_output` para o resto.
- Um agente cujo único trabalho restante é um comando em segundo plano espera sem chamar o modelo, e o watchdog de silêncio da execução pausa enquanto espera.
- `bash_output(handle)` lê o estado e a saída recente de um comando; `bash_kill(handle)` para-o. Ambos indicam quando o resultado já foi entregue.
- Um script não pode iniciar um comando em segundo plano. O Claude Code tem o seu próprio Bash em segundo plano; o Control Center mantém essa execução aberta durante no máximo 10 minutos após o turno que deixou uma tarefa a correr.

## `compact` — libertar espaço na janela de contexto

Compacta o contexto mais antigo da conversa antes da próxima chamada ao modelo, mantendo o que `focus` indica (no máximo 1 000 caracteres). Os turnos mais recentes ficam textualmente. A linha de orçamento por turno do agente mostra o uso do contexto a 70, 80 e 90%, e vale a pena chamar a ferramenta depois de cerca de 70% antes de uma nova fase longa de trabalho. O hook `preCompact` do proprietário do servidor pode acrescentar ao foco ([Hooks de shell](/pt-PT/manual/referencia/configuracao-de-agentes/#hooks-de-shell)). Após uma compactação, o servidor acrescenta um bloco «Still in flight»: o objetivo, os despertares pendentes, as perguntas abertas, os comandos em segundo plano, a lista de verificação e as chaves guardadas, cada um com a chamada que o recupera.

## `ask_user` — fazer uma pergunta ao humano

Nível `read`. A **única** forma de uma execução perguntar algo ao operador. Apresenta um cartão numerado na conversa e bloqueia até alguém responder, saltar ou a pergunta expirar. Nunca escreva a pergunta como uma mensagem de chat — isso termina o turno.

| Argumento         | Significado                                |
| ----------------- | ------------------------------------------ |
| `question`        | O que perguntar                            |
| `context`         | Opcional: porque está a perguntar e o que depende da resposta |
| `options[]`       | Escolhas, cada uma `{label, description?}` |
| `allow_free_text` | Se uma resposta escrita é aceite           |
| `multi_select`    | Se podem ser escolhidas várias opções      |

Um salto é um êxito: avance com base numa suposição declarada e não volte a perguntar. Uma expiração do tempo limite é um erro com a mesma instrução. Os pedidos de permissão («posso fazer isto?») são um portão separado e são apresentados no mesmo cartão na conversa.

Só é registada quando existem tanto uma porta de perguntas como um espaço de destino. Sem um humano ligado, a chamada **falha** em vez de bloquear para sempre — a mesma postura de falha fechada que um `prompt` de barreira adota quando não há nenhum aprovador ligado.

## `vibe_*` — dirigir workers em segundo plano

Só é registada enquanto o [modo vibe](/pt-PT/manual/guias/dirigir-workers-em-segundo-plano/) está ligado. As cinco são de nível `read`: o portão pertence às ferramentas do worker, onde a edição acontece realmente.

| Ferramenta   | Argumentos                               | Notas                                       |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | Devolve imediatamente; o worker continua a correr |
| `vibe_send`  | `worker_id`, `message`                   | Acrescenta ao briefing e volta a executar   |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | Bloqueia até ele terminar                   |
| `vibe_kill`  | `worker_id`                              | Pára-o                                      |
| `vibe_list`  | —                                        | Nível, estado, tempo decorrido e último resultado |

O `tier` é `fast` (trabalho mecânico com uma especificação clara) ou `good` (conceção, discernimento ou revisão do resultado de um worker `fast`).
