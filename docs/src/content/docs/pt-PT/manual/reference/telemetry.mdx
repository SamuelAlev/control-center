O Control Center pode enviar **eventos de utilização pseudónimos** para uma instância do [Umami](https://umami.is). As análises de utilização estão **desativadas até que o operador do servidor as ative**. A definição pertence ao servidor e aplica-se a todos os clientes ligados a ele: a aplicação de ambiente de trabalho, a aplicação web, o telemóvel e o próprio servidor.

As análises de utilização são independentes de **Partilhar relatórios de falhas**, uma definição por dispositivo para diagnósticos de falhas e erros.

## Quem decide

| Interruptor | Onde | Efeito |
| --- | --- | --- |
| **Partilhar análises de utilização** | Onboarding (passo da sandbox) e **Definições → Privacidade**. Só o operador do servidor o pode alterar; os restantes membros veem o valor atual apenas para leitura | Para todo o servidor. Guardado como `telemetry.usage_analytics` nas definições do servidor. Desligado, a menos que esteja definido como `true` |
| Tipo de build | Automático | As builds de debug e de profile não enviam nada. Em vez disso, escrevem cada evento no registo de debug |
| `CC_ANALYTICS_DEBUG=1` | Ambiente do `cc_server` ou o respetivo `.env` | Permite que as builds de debug e de profile do servidor, e de todos os clientes ligados a ele, enviem eventos a sério, para testes. O interruptor acima tem de continuar ligado |
| `DO_NOT_TRACK=1` | Ambiente do `cc_server` | Interrompe os envios do próprio servidor, seja qual for o valor do interruptor. Os clientes continuam a seguir o interruptor |
| Servidor de demonstração | Automático | O servidor de demonstração público não envia nada por si próprio. Os visitantes não podem alterar o interruptor |

Os clientes leem a definição a partir do servidor (`telemetry.config` e, depois, em tempo real através de `telemetry.watch`). Até chegar a resposta, os eventos aguardam num pequeno buffer em memória. Se a resposta for não, o buffer é descartado. Desligar o interruptor descarta tudo o que ainda estiver em fila e interrompe o envio de imediato, em todos os clientes.

## O que nunca é enviado

- Conteúdo de mensagens, tickets, revisões ou reuniões, títulos, prompts, comandos de shell e consultas de pesquisa
- Nomes, logins, endereços de e-mail, avatares e nomes a apresentar
- Caminhos de ficheiros, nomes de repositórios, nomes de branches, nomes de anfitrião e URLs (um repositório só é enviado como um `repo_id` pseudónimo; a ligação de uma reunião, só como o nome do fornecedor)
- Identificadores em bruto de qualquer tipo

Todos os eventos passam por uma política de propriedades antes de saírem do processo. Textos, caminhos, URLs, endereços de e-mail, IDs não encapsulados e strings em chaves como `email`, `*_name`, `path`, `title`, `prompt`, `content` ou `token` são descartados em vez de enviados. Uma string só é enviada se for um token curto de um vocabulário fechado, como um valor de enum, uma versão, uma região ou um ID de modelo.

## IDs pseudónimos

Os IDs são enviados, mas apenas como pseudónimos. Cada ID de espaço de trabalho, espaço, conversa, agente, execução, utilizador e dispositivo é substituído por um HMAC-SHA256 calculado com o salt secreto da própria instalação (`telemetry.pseudonym_salt`), truncado a 20 caracteres hexadecimais. O mesmo espaço de trabalho comunica sempre o mesmo valor, pelo que os eventos podem ser relacionados e contados, mas o ID em bruto nunca sai da instalação. O salt é criado no primeiro arranque do servidor e nunca é enviado ao fornecedor de análises. Eliminar o diretório de dados do servidor cria um novo salt e um novo ID de instalação, o que desvincula tudo o que foi registado antes.

## Visualizações de ecrã

Cada navegação regista uma visualização de página cujo URL é o **modelo de rota**, como `/workspaces/:workspaceId/spaces/:spaceId`, e nunca o endereço concreto. O nome do ecrã é formado pelos segmentos literais do modelo, pelo que, nesse exemplo, é `workspaces_spaces`. Os parâmetros de rota terminados em `Id` são anexados como propriedades pseudónimas `*_id`, e os numéricos (como o número de um PR) como números. Todos os outros parâmetros são descartados.

## Entrega

Os eventos são enviados um de cada vez para `<host>/api/send` a partir de uma fila em memória com até 200 eventos. Um erro de rede, um timeout, um `429` ou um `5xx` mantém o evento e volta a tentar com backoff exponencial, de 1 segundo até 5 minutos. Qualquer outro `4xx` descarta-o. Nada é escrito em disco, pelo que os eventos que ainda estejam em fila quando a aplicação é fechada perdem-se. A fila é esvaziada quando a aplicação passa para segundo plano e quando o servidor é encerrado.

## Apontar uma build para outra instância

O destino é fixado no momento da build:

```bash
--dart-define=CC_ANALYTICS_HOST=https://analytics.example.com/
--dart-define=CC_ANALYTICS_WEBSITE_ID=<website uuid>
```

O adaptador do fornecedor encontra-se em `packages/cc_analytics`. Para suportar outro serviço de análises, basta acrescentar aí um adaptador. O plano de rastreio e as regras de privacidade mantêm-se iguais.
