Uma pull request já é o sítio onde acontece a conversa sobre código. As conversas
de PR transformam-na numa superfície de um espaço de trabalho do Control Center,
tal como uma [ponte de chat](/pt-PT/manual/conceitos/pontes-de-chat/) transforma o
Slack numa: mencione `@usectrl` (ou o bot da GitHub App do espaço de trabalho)
numa PR, responda dentro das respetivas threads de revisão ou adicione a
etiqueta `ai-review`, e o trabalho acontece no espaço de revisão da PR —
sujeito à mesma atribuição e às mesmas barreiras que qualquer coisa escrita na
aplicação. Um comentário e uma etiqueta são condicionados da mesma forma: pelo
membro que o escreveu ou a adicionou. As respostas voltam para o GitHub, no
canal onde a pergunta foi feita.

Três decisões moldam a funcionalidade, e cada uma é a mesma decisão que a ponte
de chat tomou para o chat, reformulada para uma forge: **em que direção corre a
ligação**, **o que autoriza um comentário que chega do exterior** e **a quem é
atribuído cada lado**.

## A sondagem é o transporte

O único canal de push que o GitHub oferece a uma aplicação é um webhook, e um
webhook precisa de um URL de entrada — exatamente a única coisa de que esta
superfície nunca precisa. Por isso, a descoberta é uma varredura: uma pesquisa
com alias por instalação da aplicação pede ao GitHub as PRs que mencionam o bot
(ou o respetivo slug curto) e as PRs abertas que têm a etiqueta de revisão, as
PRs que já têm um espaço de revisão têm as suas threads de comentários lidas, e
tudo é comparado por id de comentário com o que foi visto na varredura
anterior. Uma aplicação própria faz a varredura a cada minuto, sobre no máximo
25 PRs. Através do Connect, as chamadas usam a quota do GitHub dos próprios
membros, pelo que a varredura corre a cada dois minutos, sobre no máximo 10, e
um espaço de trabalho abaixo de 15% da quota é ignorado até recuperar. O
próprio Connect nunca vê o conteúdo das PRs.

Vale a pena nomear as consequências de conceção:

- **A latência é um intervalo de varredura, não um evento.** O reconhecimento 👀
  chega dentro de uma varredura. Nada de urgente depende disso.
- **Exatamente uma vez, por comentário.** Os ids de comentário são únicos em todo
  o GitHub; cada um é registado no momento em que é classificado como elegível,
  antes de qualquer ação sobre ele. Uma falha pode perder o tratamento de um
  comentário, nunca acioná-lo duas vezes.
- **O tempo offline é recuperado, não reproduzido.** O conjunto de comentários já
  vistos é persistido, pelo que um reinício entrega o que chegou enquanto o
  servidor estava em baixo. A única exceção é a primeira varredura de sempre: sem
  memória com que comparar, tudo o que está pendente é registado em silêncio — um
  operador que etiquetou vinte PRs antes de este servidor existir não pode voltar
  e encontrar vinte revisões a correr.
- **A etiqueta é um conjunto, não um evento.** A pesquisa comunica a _presença_
  da etiqueta, pelo que uma PR etiquetada dispara uma vez, e uma só. Voltar a
  adicionar uma etiqueta depois de a remover é invisível para a varredura; uma
  menção é a via de repetição.

A pesquisa corre uma vez por conta de instalação, no cliente do próprio
proprietário dessa conta, porque um token só vê os repos da sua própria
instalação — uma única credencial a nível de servidor deixaria passar em
silêncio todas as PRs sob as outras instalações da aplicação.

## A pertença autoriza, não o comentário

Um comentário numa PR chega com um autor — uma identidade externa não
autenticada até prova em contrário. O servidor resolve o id numérico imutável
da conta GitHub do autor (nunca o login, que pode ser renomeado e reutilizado)
com base nos inícios de sessão no GitHub dos membros do espaço de trabalho,
reconstruídos de acordo com um TTL porque há pessoas que iniciam sessão e são
convidadas enquanto o servidor corre. No caso da etiqueta `ai-review`, a pessoa
resolvida é quem a adicionou mais recentemente.

Três verificações, por esta ordem, e falhar qualquer uma delas é silencioso —
nada é publicado:

- **Um membro com sessão iniciada.** A conta tem de pertencer a um membro
  _deste_ espaço de trabalho que tenha iniciado sessão no GitHub neste servidor
- **Um papel com escrita.** `viewer` e `guest` não podem iniciar trabalho
- **Acesso de push.** As respostas usam um token `bot` limitado ao acesso desse
  membro ao repositório. Se o servidor não conseguir emitir um, não avança

Todas as verificações correm antes de qualquer reconhecimento, pelo que um
estranho não recebe nenhuma reação nem resposta. Um comentário nunca é
atribuído a alguém que não o enviou, e as palavras de um estranho nunca entram
num espaço de trabalho que não consegue ver.

### A reclamação

O último passo antes de qualquer trabalho é uma reação 👀, adicionada com o
próprio início de sessão do autor no GitHub. O GitHub responde `201` a uma
reação nova e `200` a uma que já existe, pelo que a reação serve também de
trinco: quando a mesma pessoa tem sessão iniciada em dois servidores que ligam
o repositório, só o primeiro a reagir faz o trabalho. Um comentário que vários
espaços de trabalho de um mesmo servidor veem é oferecido a cada um, e a mesma
reclamação decide.

## Duas identidades, de propósito

Cada lado da conversa transporta uma identidade diferente, e essa diferença é a
funcionalidade:

- **No GitHub, a resposta é uma automação em seu nome.** Cada resposta usa um
  token `bot` para esse único repositório, limitado ao acesso do membro que
  perguntou. Com uma aplicação própria, o autor é a conta `[bot]` da aplicação.
  Através do Connect, um token da App partilhada é um token de utilizador, pelo
  que a resposta tem como autor a conta do membro que perguntou, a agir através
  da App. Em qualquer dos casos, cada resposta começa por
  `**Control Center** (for @login):`, que diz quem perguntou e serve também de
  proteção contra ciclos.
- **No espaço, a pergunta é sua.** A mensagem é atribuída ao membro em que o
  autor foi resolvido, e a execução do agente corre em nome dele: os commits
  indicam-no como coautor, e o seletor de autonomia e as barreiras de ação do
  espaço aplicam-se exatamente como a uma mensagem escrita na aplicação. As
  escritas na forge feitas pela execução usam tokens de um único repositório
  limitados a esse membro, nunca o início de sessão dele entregue por inteiro.

Publicar os resultados da revisão de volta no GitHub continua a ser uma decisão
de uma pessoa, tomada no Control Center. Uma menção pode _iniciar_ uma revisão;
só um ser humano publica uma.

## A proteção contra ciclos e o nome curto

Tudo o que é da autoria de uma conta de bot é descartado antes de qualquer
barreira ser avaliada — a nossa especificamente, e todos os sufixos `[bot]`, para
que o bot de revisão de outra aplicação também não possa acordar o nosso —, e o
mesmo acontece a todos os comentários que começam pelo prefixo
`**Control Center** (for @`, já que uma resposta através do Connect tem como
autor a conta de uma pessoa. Sem isto, as respostas chegariam como novos
comentários e voltariam a acionar a ponte para sempre.

O sufixo `[bot]` é também a razão pela qual a forma curta existe. O GitHub fixa o
login de uma conta de aplicação em `<slug>[bot]`, não oferece preenchimento
automático para ele e nunca resolve `@slug` para a aplicação — por isso, aceitar
o slug isolado é uma decisão _do nosso_ comparador, e descobri-lo exige uma via
de pesquisa de **texto** de comentário em bruto, em vez do índice de menções do
GitHub. O custo é declarado em vez de atenuado: um utilizador humano que partilhe
o slug da aplicação endereça o bot em todas as menções curtas a si próprio. Nomes
de aplicação distintos tornam a colisão hipotética.

## O que deliberadamente não é oferecido

- **Sem publicação automática.** Os resultados ficam no espaço de revisão;
  publicar no GitHub é uma ação separada e humana
- **Sem identidade difusa.** O autor é resolvido para exatamente um membro ou é
  ignorado — não existe atribuição por tentativa
- **Sem aprovação automatizada.** A automação pode comentar e pedir alterações,
  mas uma revisão `APPROVE` é recusada antes de ser enviada. Aprovar é um ato
  de uma pessoa
- **Sem webhook da GitHub App.** Esta superfície nunca regista nenhum, pelo que
  não há um URL de entrada para expor a comentários de PR. Os outros webhooks do
  produto (pipelines, sincronização de tickets) são uma configuração separada e
  opcional.
