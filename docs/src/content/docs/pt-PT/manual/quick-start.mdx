Este é o caminho completo mais curto entre o nada e um agente a correr sobre o seu próprio código. Siga-o pela ordem indicada; cada passo depende do anterior.

Precisa de Git, de uma conta GitHub e de uma conta num fornecedor de modelos (Anthropic, OpenAI, Codex, Cursor, Kimi Code ou qualquer fornecedor com uma chave de API), ou então do CLI do Claude Code já instalado. Tudo o resto é configurado ao longo do processo.

## Passo 1: instalar e iniciar

Instale o Control Center como descrito em [Instalar](/pt-PT/manual/instalar/) e abra-o.

No primeiro arranque, a aplicação de ambiente de trabalho pergunta **«Como o Control Center deve ser executado?»**. Escolha **Executar nesta aplicação**. O Control Center lança um `cc_server` headless nesta máquina, que é o dono dos seus dados e faz todo o trabalho. Nunca o vê; em vez disso, abre-se o ecrã de onboarding.

:::note[Prefere não instalar nada?]
A mesma aplicação corre no navegador em [app.usectrl.dev](https://app.usectrl.dev), com as
mesmas funcionalidades. No entanto, um separador do navegador não consegue alojar o
servidor, por isso é você que o disponibiliza — execute o `cc_server` localmente e ligue-se
a `ws://localhost:9030`, ou aponte-o para um servidor noutra máquina. Este início rápido
segue o caminho da aplicação de ambiente de trabalho porque não exige configurar um
servidor; consulte [Instalar](/pt-PT/manual/instalar/#use-it-in-your-browser) para a via do navegador.
:::

## Passo 2: percorrer o onboarding

O onboarding tem cinco passos e são executados por ordem — não há como saltar passos.

1. **Ligar**: inicie sessão com o GitHub ou cole um token de acesso pessoal com `repo` e `read:org`. A credencial é guardada no servidor, associada à sua conta.
2. **Espaço de trabalho**: dê um nome ao seu primeiro espaço de trabalho e, opcionalmente, escolha um logótipo. Criá-lo semeia cinco agentes — um CEO, mais `qa`, `architect`, `engineer` e `librarian` — e os modelos de pipeline integrados.
3. **Sandbox**: regista uma preferência de sandbox. Qualquer das opções permite continuar.
4. **Adaptador**: escolha o adaptador e o modelo predefinidos dos agentes. Escolha **Control Center (built-in)** e, em seguida, use o seletor de fornecedores que aparece para iniciar sessão num fornecedor de modelos — a lista de modelos fica vazia enquanto não houver um ligado. Concluir este passo também fixa o adaptador e o modelo no agente CEO do espaço de trabalho.
5. **Voz (opcional)**: instale um modelo de voz no dispositivo para ditado ou ignore este passo.

O Control Center abre então a caixa de entrada do seu espaço de trabalho.

:::note[O que limita uma execução de agente]
Os comandos dos agentes são envolvidos na sandbox nativa do sistema operativo do anfitrião, quando existe — Seatbelt no macOS, bubblewrap no Linux. O Windows não tem backend nenhum, pelo que aí as execuções são limitadas apenas pelas restantes camadas: a worktree da própria conversa (`git worktree` no Windows; copy-on-write onde o `rift` existe), as credenciais negociadas em cada lançamento e revogadas no desmantelamento e as guardrails de ação. Consulte [Sandbox e segurança](/pt-PT/manual/conceitos/sandbox-e-seguranca/).
:::

## Passo 3: adicionar um repositório

Vá a **Definições → Espaço de trabalho → Repositórios** e clique em **Adicionar repositório**.

A caixa de diálogo percorre as pastas da máquina que executa o servidor, e não as do seu cliente, e mantém-se dentro das raízes que esse servidor está configurado para expor (por predefinição, o diretório pessoal do respetivo utilizador). Só os checkouts git recebem uma caixa de seleção. Assinale o seu e registe-o.

Um checkout só é aceite se estiver dentro de uma árvore de trabalho git, tiver um remoto `origin` e esse remoto apontar para um host de código suportado — github.com, gitlab.com ou bitbucket.org. Tudo o resto é recusado, com o motivo.

Os repos têm âmbito de espaço de trabalho: registar um checkout aqui coloca-o _neste_ espaço de trabalho. Não existe um passo de ligação separado.

## Passo 4: dar a um agente um adaptador e um modelo

Vá a **Definições → Espaço de trabalho → Agentes**. Selecione o agente `engineer` na lista.

No separador **Definições**, defina:

- **Adaptador**: `Control Center (built-in)`
- **Modelo**: escolha um da lista do fornecedor que ligou no onboarding

Clique em **Guardar alterações**.

Na prática, este passo não é opcional. Só o agente CEO herda o adaptador escolhido durante o onboarding; os quatro especialistas são criados sem nenhum. Recorrem ao **Control Center (built-in)** com o modelo predefinido da Anthropic, pelo que só são executados se tiver ligado uma conta Anthropic — e, nesse caso, num modelo que não escolheu.

## Passo 5: enviar uma tarefa ao agente

1. Na barra lateral, encontre a secção **Espaços** e clique no botão **+**.
2. Dê um nome ao espaço, adicione o agente `engineer` em **Adicionar agentes** e crie-o.
3. Escreva uma tarefa concreta e pequena sobre o repo que registou e prima Enter.

O Control Center aprovisiona uma worktree copy-on-write dos repos do espaço de trabalho para esta conversa, compõe um prompt a partir do papel, da persona e das skills do agente e do contexto do espaço, e despacha a execução. O seu checkout de origem nunca é tocado.

## Passo 6: vê-lo a trabalhar

Deve ver, por esta ordem:

- O botão de enviar do compositor transformar-se num botão de parar, porque há um agente a trabalhar nesta conversa
- O raciocínio, as chamadas de ferramentas e o texto do agente a surgir em fluxo na transcrição
- O botão de enviar voltar a aparecer quando a execução termina

Depois, abra **Definições → Espaço de trabalho → Agentes**, selecione o agente e consulte o separador **Registos**: uma linha de execução, com o estado, a duração, as horas de início e de fim e o adaptador em que foi executada.

É este o ciclo. Tudo o resto no Control Center — revisão de pull requests, pipelines, tickets, reuniões, Slack — depende dele.
