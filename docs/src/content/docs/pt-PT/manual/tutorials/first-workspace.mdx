## O que vai construir

No final deste tutorial, terá:

- Um espaço de trabalho com o nome do seu projeto
- Um repositório Git registado nele
- Cinco agentes semeados, um dos quais configurou o suficiente para ser executado
- Um segundo espaço de trabalho, vazio, que comprova a fronteira de isolamento

O onboarding já criou um espaço de trabalho para si. Este tutorial cria deliberadamente um novo de raiz, para que veja todas as partes do processo.

Antes de começar, escolha um checkout Git que cumpra todas estas três condições — o passo de registo recusa tudo o resto:

- está dentro de uma árvore de trabalho git
- tem um remoto `origin`
- esse remoto aponta para github.com, gitlab.com ou bitbucket.org

## Passo 1: criar um espaço de trabalho

1. Clique no chip do espaço de trabalho na barra de título
2. Escolha **Adicionar espaço de trabalho…**
3. Introduza um nome que identifique o projeto, como «api-service» ou «frontend-v2»
4. Opcionalmente, escolha um logótipo
5. Clique em **Adicionar espaço de trabalho**

O Control Center muda para o novo espaço de trabalho e abre na respetiva caixa de entrada (`/workspaces/<id>/inbox`).

Por detrás disso, o servidor publica um evento `WorkspaceCreated` e semeia o espaço de trabalho com:

- um **agente CEO**, cuja persona é a coordenação e a delegação
- quatro especialistas — `qa`, `architect`, `engineer` e `librarian` — cada um com as suas próprias instruções e skills
- os modelos de pipeline integrados e as respetivas linhas de disparadores

Todos os espaços de trabalho que criar recebem tudo isto, não apenas o primeiro.

Para confirmar: abra **Definições → Espaço de trabalho → Agentes**. Estão cinco agentes na lista, cada um com um anel de estado vazio.

## Passo 2: registar um repositório

1. Vá a **Definições → Espaço de trabalho → Repositórios**
2. Clique em **Adicionar repositório**
3. Navegue até ao seu checkout. A caixa de diálogo percorre as pastas da máquina que executa o `cc_server` — e não as do seu cliente — e mantém-se dentro das raízes que esse servidor expõe (por predefinição, o diretório pessoal do respetivo utilizador). Um checkout git recebe um ícone de pasta próprio e uma caixa de seleção; uma pasta simples não recebe nenhum dos dois, pelo que só é possível selecionar checkouts.
4. Assinale um ou mais checkouts e registe o lote. As seleções mantêm-se enquanto navega, pelo que pode reunir vários numa só passagem e uma escolha falhada nunca descarta as restantes.

O Control Center lê o remoto `origin` de cada checkout, resolve o proprietário e o repo e cria a linha do repo **dentro deste espaço de trabalho**. Não existe um segundo passo para o ligar: é o registo que lhe dá âmbito.

Registar o mesmo checkout noutro espaço de trabalho mais tarde cria uma segunda linha de repo independente, com o seu próprio id. Entre espaços de trabalho, um checkout é identificado pelo seu caminho no sistema de ficheiros, nunca pelo id.

Para confirmar: o repo aparece na lista com o seu `owner/repo` e o branch atual.

## Passo 3: tornar um agente executável

Os cinco agentes que este espaço de trabalho acabou de semear não têm adaptador nem modelo. O despacho executa-os em **Control Center (built-in)** e, sem modelo definido, pede à Anthropic o respetivo modelo predefinido — pelo que só funcionam se tiver uma conta Anthropic ligada e, nesse caso, num modelo que não escolheu. O onboarding do primeiro arranque marca a sua escolha em todos os agentes do primeiro espaço de trabalho, uma única vez; um espaço de trabalho criado depois disso começa com os cinco por definir. Defina um agora.

1. Abra **Definições → Espaço de trabalho → Agentes**
2. Selecione o agente `engineer` na lista
3. No separador **Definições**, defina o **Adaptador** como `Control Center (built-in)` e escolha um **Modelo** de um fornecedor que tenha ligado em Definições → Servidor → Fornecedores de modelos
4. Prima **Guardar alterações**

Para confirmar: volte a abrir o agente e os dois campos mantêm as suas escolhas.

Cada agente tem o seu próprio adaptador e modelo, pelo que deve repetir isto para qualquer outro agente que tencione usar. [Criar e configurar um agente](/pt-PT/manual/guias/criar-agente/) aborda o resto do formulário.

## Passo 4: ver a fronteira de isolamento

Crie um segundo espaço de trabalho a partir do chip da barra de título, exatamente como no passo 1. Depois observe-o:

- **Definições → Espaço de trabalho → Repositórios** está vazio. O repo que registou há um minuto não está lá.
- **Definições → Espaço de trabalho → Agentes** tem cinco agentes, mas são linhas diferentes — o adaptador que definiu no passo 3 desapareceu.
- A lista de espaços, os tickets e a memória estão todos vazios.

Não houve fugas, porque não há nada de onde fugir: as linhas de cada espaço de trabalho vivem no ficheiro de base de dados do próprio espaço de trabalho. Uma leitura entre espaços de trabalho não é uma consulta que é filtrada, é uma consulta que não tem onde correr. Eliminar um espaço de trabalho é desvincular um ficheiro.

Volte atrás com o chip da barra de título ou abra **Gerir espaços de trabalho** para os ver lado a lado.

Para o modelo completo, leia [Espaços de trabalho e isolamento](/pt-PT/manual/conceitos/espacos-de-trabalho/).

## Resumo

Criou um espaço de trabalho, viu-o semear um CEO e quatro especialistas, registou um repo nele, deu a um agente um adaptador e um modelo e confirmou que um segundo espaço de trabalho não partilha nada disso.
