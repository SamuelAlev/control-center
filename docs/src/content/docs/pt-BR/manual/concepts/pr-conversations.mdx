Uma pull request já é o lugar onde a conversa sobre o código acontece. As
conversas de PR a tornam uma superfície em um espaço de trabalho do Control
Center, do mesmo modo que uma [ponte de
chat](/pt-BR/manual/conceitos/pontes-de-chat/) torna o Slack uma: mencione
`@usectrl` em uma PR, responda
dentro das threads de revisão dela, ou adicione o rótulo `ai-review`, e o
trabalho acontece no espaço de revisão da PR — sob a mesma atribuição e as
mesmas barreiras que qualquer coisa digitada no app. Um comentário e um rótulo
são filtrados da mesma forma: pelo membro que o escreveu ou o adicionou. As
respostas voltam no GitHub, no mesmo canal em que a pergunta foi feita.

Três decisões moldam o recurso, e cada uma é a mesma decisão que a ponte de
chat tomou para o chat, reafirmada para uma forge: **em que direção a conexão
flui**, **o que autoriza um comentário que chega de fora** e **a quem cada lado
é atribuído**.

## Polling é o transporte

O único canal de envio que o GitHub oferece a um app é um webhook, e um webhook
precisa de uma URL de entrada — justamente a única coisa que esta superfície
deliberadamente nunca exige. Então a descoberta é uma varredura: uma busca com
alias por instalação do app pede ao GitHub as PRs que mencionam `@usectrl` e as PRs abertas que carregam o rótulo de revisão; as PRs que já
têm um espaço de revisão têm suas threads de comentários lidas, e tudo é
comparado por id de comentário com o que foi visto na varredura anterior. Um
app próprio faz a varredura a cada minuto, em no máximo 25 PRs. Pelo Connect, as
chamadas usam a cota do GitHub dos próprios membros, então a varredura roda a
cada dois minutos, em no máximo 10, e um espaço de trabalho abaixo de 15% da
cota é pulado até se recuperar. O próprio Connect nunca vê o conteúdo das PRs.

As consequências de projeto merecem ser nomeadas:

- **A latência é um intervalo de varredura, não um evento.** A confirmação de
  recebimento 👀 chega dentro de uma varredura. Nada urgente depende dela.
- **Exatamente uma vez, por comentário.** Os ids de comentário são únicos em
  todo o GitHub; cada um é registrado no momento em que é classificado como
  elegível, antes que qualquer coisa aja sobre ele. Uma falha pode perder o
  tratamento de um comentário, mas nunca dispará-lo duas vezes.
- **O tempo offline é recuperado, não reproduzido.** O conjunto de vistos é
  persistido, então um reinício entrega o que chegou enquanto ele estava fora
  do ar. A única exceção é a primeiríssima varredura: sem nenhuma memória com a
  qual comparar, tudo o que está pendente é registrado em silêncio — um
  operador que rotulou vinte PRs antes de este servidor existir não pode voltar
  e encontrar vinte revisões em execução.
- **O rótulo é um conjunto, não um evento.** A busca informa a _presença_ do
  rótulo, então uma PR rotulada dispara uma única vez, e nunca mais. Adicionar
  de novo um rótulo depois de removê-lo é invisível para a varredura; uma
  menção é o caminho para executar novamente.

A busca roda uma vez por conta de instalação, no cliente do próprio
proprietário, porque um token só enxerga os repos da própria instalação — uma
única credencial para todo o servidor deixaria passar em silêncio todas as PRs
das outras instalações do app.

## A associação autoriza, não o comentário

Um comentário de PR chega carregando um autor — uma identidade externa não
autenticada até que se prove o contrário. O servidor resolve o id numérico
imutável da conta do GitHub do autor (nunca o login, que pode ser renomeado e
reutilizado) contra os logins no GitHub dos membros do espaço de trabalho,
reconstruídos conforme um TTL, porque as pessoas entram e são convidadas
enquanto o servidor está rodando. No caso do rótulo `ai-review`, a pessoa
resolvida é quem o adicionou mais recentemente.

Três verificações, nesta ordem, e falhar em qualquer uma delas é silencioso —
nada é publicado:

- **Um membro com login feito.** A conta precisa pertencer a um membro _deste_
  espaço de trabalho que entrou no GitHub neste servidor
- **Um papel com escrita.** `viewer` e `guest` não podem iniciar trabalho
- **Acesso de push.** As respostas usam um token para esse único repositório,
  limitado ao acesso desse membro a ele. Se o servidor não conseguir emitir um,
  ele não prossegue

Todas as verificações rodam antes de qualquer confirmação de recebimento, então
um estranho não recebe nenhuma reação nem resposta. Um comentário nunca é
atribuído a alguém que não o enviou, e as palavras de um estranho nunca entram
em um espaço de trabalho que ele não pode ver.

### A reivindicação

O último passo antes de qualquer trabalho é uma reação 👀, adicionada com o
próprio login do autor no GitHub. O GitHub responde `201` para uma reação nova
e `200` para uma que já existe, então a reação também funciona como trava:
quando a mesma pessoa tem login feito em dois servidores que vinculam o
repositório, só o primeiro a reagir faz o trabalho. Um comentário que vários
espaços de trabalho de um mesmo servidor veem é oferecido a cada um, e a mesma
reivindicação decide.

## Duas identidades, de propósito

Cada lado da conversa carrega uma identidade diferente, e a diferença é o
recurso:

- **No GitHub, a resposta é uma automação em seu nome.** Cada resposta usa um
  token para aquele único repositório, limitado ao acesso do membro que
  perguntou, e é de autoria da conta `[bot]` do app. Uma exceção: no app
  compartilhado Control Center Connect, o bot publica em threads de revisão
  somente quando o operador do Connect cadastrou a instalação; caso contrário,
  uma resposta dentro de uma thread de revisão tem como autor a conta do próprio
  membro que perguntou. Em qualquer caso, toda resposta
  começa com `**Control Center** (for @login):`, que diz quem perguntou e também serve de
  proteção contra loops. As @-menções nas palavras do agente são neutralizadas, então uma resposta nunca notifica um usuário ou equipe.
- **No espaço, a pergunta é sua.** A mensagem é atribuída ao membro ao qual o
  autor foi resolvido, e a execução do agente roda em nome dele: os commits da
  execução são dele, e o dial de autonomia e as barreiras de ação do
  espaço se aplicam exatamente como a uma mensagem digitada no app. As
  gravações na forge feitas pela execução usam tokens de um único repositório
  limitados a esse membro, nunca o login dele entregue por inteiro.

Publicar as constatações da revisão de volta no GitHub continua sendo uma
decisão de uma pessoa, tomada no Control Center. Uma menção pode _iniciar_ uma
revisão; só um humano publica uma.

## A proteção contra loops

Tudo o que é de autoria de uma conta de bot é descartado antes que qualquer
filtro rode — o nosso especificamente, e qualquer sufixo `[bot]`, para que o
bot de revisão de outro app também não possa acordar o nosso —, e também todo
comentário que começa com o prefixo `**Control Center** (for @`, já que uma
resposta em thread de revisão pelo Connect pode ter como autor a conta de uma pessoa. Sem isso, as
respostas chegariam como comentários novos e disparariam a ponte de novo para
sempre.

Só `@usectrl` inicia trabalho. O login próprio do App (`<slug>[bot]`) e o slug puro não endereçam nada: o GitHub não oferece autocomplete para uma conta de app, e um slug puro pode pertencer a um usuário humano.

## O que deliberadamente não é oferecido

- **Nenhuma publicação automática.** As constatações chegam ao espaço de
  revisão; publicar no GitHub é uma ação humana separada
- **Nenhuma identidade difusa.** O autor se resolve em exatamente um membro ou
  é ignorado — não há atribuição por suposição
- **Nenhuma aprovação automatizada.** A automação pode comentar e pedir
  alterações, mas uma revisão `APPROVE` é recusada antes de ser enviada.
  Aprovar é um ato de uma pessoa
- **Nenhum webhook do GitHub App.** Esta superfície nunca registra um, então
  não há URL de entrada a expor para comentários de PR. Os outros webhooks do
  produto (pipelines, sincronização de tickets) são uma configuração separada e
  opcional.
