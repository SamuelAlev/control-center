Estas são as ferramentas **vinculadas ao servidor** que o runtime de agente integrado registra diretamente — servidor de linguagem, busca estrutural, depurador, kernels, scripts do modo de código, perguntas e controle de workers —, em oposição às [ferramentas MCP](/pt-BR/manual/referencia/ferramentas-mcp/) que ele conecta por ponte e às ferramentas genéricas de arquivo, busca e shell do runtime do harness. Elas não estão no registro MCP: um cliente MCP externo não as verá, porque cada uma está vinculada a um recurso vivo do lado do servidor — um processo de servidor de linguagem, um adaptador de depuração, um interpretador — que pertence a uma execução.

Toda ferramenta aqui só é registrada quando o recurso que a sustenta está conectado para a execução — um supervisor de servidor de linguagem ou de depuração, um analisador tree-sitter, uma fábrica de kernels, uma porta de perguntas, uma lista de workers de vibe. A detecção de um servidor de linguagem ou de um adaptador de depuração para *este checkout* é uma verificação separada e posterior (`status` / `adapters`): essas ferramentas permanecem na superfície para que o agente possa perguntar por que nada está utilizável, em vez de adivinhar.

## Níveis de aprovação

Cada ferramenta declara um nível, e o nível decide **quais superfícies a veem** — não apenas se ela pede aprovação. O modo plano e os subagentes somente leitura têm como teto o `read`, então uma ferramenta de nível `write` ou `exec` está totalmente ausente do esquema deles.

| Nível   | Significado                        | Ferramentas aqui                                  |
| ------- | ---------------------------------- | ------------------------------------------------- |
| `read`  | Sem efeitos colaterais             | `lsp`, `ast_grep`, `ask_user`, `repl`, as cinco `vibe_*` |
| `write` | Altera arquivos                    | `lsp_rename`, `ast_edit`, `resolve`                |
| `exec`  | Inicia ou controla um processo     | `debug`, `eval`                                    |

## Direta, somente de script ou carregada no primeiro uso

Quando o servidor consegue rodar scripts, uma execução chama algumas ferramentas diretamente e alcança as demais a partir de um script [`repl`](#repl--executar-um-script-que-chama-as-suas-ferramentas); veja [Modo de código](/pt-BR/manual/conceitos/modo-de-codigo/#quais-ferramentas-o-agente-chama-diretamente) para a regra completa. Para as ferramentas desta página:

| Ferramenta | Com `repl` | Sem `repl` |
| ---- | ----------- | -------------- |
| `repl` | Direta | Não presente |
| `ask_user` | Direta | Direta |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | Somente a partir de um script | Carregada no primeiro uso |
| `eval` | Carregada no primeiro uso (um script não pode chamá-la) | Carregada no primeiro uso |
| `vibe_*` | Direta no modo vibe, nunca a partir de um script | Direta no modo vibe |

Uma ferramenta marcada como “Somente a partir de um script” passa a ser carregada no primeiro uso assim que o servidor não consegue rodar os scripts da execução ([Quando os scripts não podem rodar](/pt-BR/manual/conceitos/modo-de-codigo/#quando-os-scripts-não-podem-rodar)).

## `lsp` — consultas ao servidor de linguagem

Registrada quando a execução tem um supervisor de servidor de linguagem e um diretório de trabalho. Se um servidor consegue de fato responder é detectado no momento da chamada, como uma **interseção**: um marcador de raiz precisa existir *e* o binário do servidor precisa resolver. Qualquer um dos dois sozinho significa que nenhum servidor inicia — o `status` diz isso —, em vez de um chute silencioso.

Os servidores vêm somente da tabela embutida; um `lsp.json` do repositório não é lido. Em uma execução em sandbox, cada execução tem a sua própria sessão de servidor de linguagem, então os servidores iniciam de novo a cada execução. Binários locais do projeto (`node_modules/.bin`) são usados apenas quando a execução está em sandbox, e a raiz do projeto nunca se resolve acima do diretório de trabalho da execução.

As posições são endereçadas por `line` mais uma substring `symbol`, nunca por coluna. Um modelo a quem se pede uma coluna chuta, e um chute errado resolve para outro símbolo na mesma linha — uma resposta que parece certa e trata de outra coisa. Omitir `symbol` em uma ação de navegação é um erro, não um chute para a primeira coluna.

| Ação              | Argumentos                       | Retorna                                    |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (ou `"*"`)                | Erros e avisos; `"*"` executa o verificador do projeto em vez disso |
| `definition`      | `file`, `line`, `symbol`         | Onde o símbolo é declarado                 |
| `type_definition` | `file`, `line`, `symbol`         | Onde o tipo dele é declarado               |
| `implementation`  | `file`, `line`, `symbol`         | Implementações concretas                   |
| `references`      | `file`, `line`, `symbol`         | Todos os usos, limitados a 50              |
| `hover`           | `file`, `line`, `symbol`         | Assinatura e comentário de documentação    |
| `symbols`         | `query` ou `file`                | Busca no espaço de trabalho com `query` (limitada a 100); símbolos do documento com `file` (limitados a 200) |
| `code_actions`    | `file`, `line`, `symbol`         | Correções rápidas que o servidor oferece   |
| `status`          | —                                | Quais servidores estão rodando, e para quais raízes |
| `reload`          | —                                | Reinicia o servidor para esta raiz         |

### Diagnósticos ao escrever

O ganho não está na ferramenta. `write`, `edit` e `apply_patch` são **envolvidos**: depois da escrita, o arquivo é sincronizado e salvo pelo servidor de linguagem, e apenas os diagnósticos **introduzidos recentemente** são incorporados ao resultado da ferramenta. O agente descobre que quebrou a build no momento em que a quebrou, sem precisar lembrar de perguntar.

Os diagnósticos já reportados são suprimidos por um registro por execução com chave em gravidade, código e mensagem — posição deliberadamente excluída, de modo que um diagnóstico que apenas desceu quatro linhas não é reportado de novo como novo.

## `lsp_rename` — renomeação em todo o projeto

Uma ferramenta separada, de nível `write`, por exatamente um motivo: o nível decide a visibilidade. Juntar a renomeação ao `lsp` ou daria a um explorador somente leitura a capacidade de reescrever o repo, ou colocaria todo `hover` atrás de uma solicitação de aprovação.

| Argumento  | Significado                                |
| ---------- | ------------------------------------------ |
| `file`     | Onde o símbolo está                        |
| `line`     | Linha indexada a partir de 1               |
| `symbol`   | Substring que o identifica naquela linha   |
| `new_name` | Como chamá-lo                              |

## `ast_grep` — busca estrutural

Encontra código por **forma**, e não por texto. `$NAME` casa qualquer nó, `$$$NAME` casa uma sequência de irmãos, e `$_` é um curinga que não captura nada.

A propriedade que faz dele um comparador, e não uma regex com etapas extras: uma metavariável repetida em um mesmo padrão precisa capturar o mesmo texto.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

casa com uma guarda que descarta o que ela testou e **não** casa com uma que descarta outra coisa.

| Argumento     | Significado                                                 |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | Um fragmento de código com metavariáveis                    |
| `path`        | Arquivo ou diretório a pesquisar; o padrão é todo o espaço de trabalho |
| `language`    | Um id de gramática distribuído (`dart`, `python`, `rust`, `c`, …). Inferido quando `path` nomeia um arquivo |
| `max_results` | Padrão 50                                                   |

:::note[O padrão é analisado pela mesma gramática do arquivo]
Então `dispose(x)` casa com a chamada de qualquer jeito que esteja espaçada, quebrada em várias linhas ou comentada — e nunca casa os mesmos caracteres dentro de um literal de string ou de um comentário.
:::

:::caution[Um fragmento é analisado em um andaime, e não isolado]
Analisado no nível superior do Dart, `dispose(x)` é uma *assinatura de função* válida. O compilador de padrões tenta uma escada de contextos (instrução, expressão, membro de classe, declaração) e usa o primeiro que aceita o fragmento. Um padrão que nenhum contexto aceita é reportado como não analisável, em vez de ser procurado e silenciosamente não encontrado.
:::

## `ast_edit` — reescrita estrutural, preparada

A mesma correspondência, mais um modelo `rewrite` com as metavariáveis substituídas de volta. **Nada é escrito.** A alteração é preparada e o resultado nomeia um `edit_id`.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| Argumento  | Significado                                         |
| ---------- | --------------------------------------------------- |
| `pattern`  | O que casar                                         |
| `rewrite`  | O que colocar no lugar, com `$NAME` substituído     |
| `path`     | Escopo; o padrão é todo o espaço de trabalho        |
| `language` | Id da linguagem                                     |

## `resolve` — confirmar ou descartar uma alteração preparada

| Argumento | Significado                      |
| --------- | -------------------------------- |
| `edit_id` | Do resultado `(proposed)`        |
| `action`  | `accept` ou `discard`            |

Cada arquivo é comparado com o conteúdo capturado no momento da preparação, e **qualquer** divergência recusa a alteração inteira. Uma reescrita estrutural aplicada em parte deixa uma árvore que não compila na forma antiga nem na nova.

## `debug` — conduzir um depurador

Registrada quando a execução tem um supervisor de sessão de depuração, um diretório de trabalho e um id de conversa. Se um adaptador consegue de fato iniciar é detectado no momento da chamada, pela mesma regra de interseção do servidor de linguagem (marcador de raiz *e* binário). Nível `exec`; não é segura para paralelismo (uma sessão é estado entre chamadas, então um `continue` que ultrapassasse o `stack` leria um frame que já se moveu).

Uma sessão por conversa, com um TTL rígido (30 minutos). Um segundo `launch` é recusado em vez de substituir silenciosamente o primeiro. Em uma execução em sandbox, a sessão mantém o sandbox entre os turnos até terminar, então por no máximo esses 30 minutos.

| Operação      | Argumentos                    | Observações                                    |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | Quais adaptadores são utilizáveis aqui, e por que não |
| `status`      | —                             | Se uma sessão está em execução, e onde ela parou |
| `breakpoints` | `file`, `lines[]`             | `lines` vazio limpa o arquivo. Podem ser definidos **antes** de iniciar |
| `launch`      | `program`, `args[]`           | Inicia o programa parado nos seus pontos de interrupção |
| `attach`      | `port`                        | Conecta-se a um processo já em execução, em uma das portas encaminhadas da própria execução; qualquer outra porta é recusada antes de qualquer coisa iniciar |
| `continue`    | `thread_id?`                  | Roda até a próxima parada                      |
| `pause`       | `thread_id?`                  | Para onde ele estiver                          |
| `step_over` / `step_in` / `step_out` | `thread_id?` | Avança um passo                     |
| `threads`     | —                             | Ids e nomes das threads                        |
| `stack`       | `thread_id?`                  | Frames, limitados a 30                         |
| `scopes`      | `frame_id`                    | Escopos de um frame, cada um com um `reference` |
| `variables`   | `reference`                   | Filhos, limitados a 50; valores, limitados a 400 caracteres |
| `evaluate`    | `expression`, `frame_id?`     | Avaliada no próprio escopo do frame            |
| `output`      | —                             | O stdout/stderr do processo depurado, com limite |
| `terminate`   | —                             | Encerra a sessão e mata o adaptador            |

### Adaptadores

| Id        | Comando                    | Marcadores de raiz                              |
| --------- | -------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`       | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                 | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                  | `go.mod`                                        |

O `debugpy` prefere um `.venv/bin` ou `venv/bin` local do projeto ao `$PATH` quando a execução está em sandbox: um python do `$PATH` é outro ambiente, e anexar a partir do errado falha de um jeito que se lê como código quebrado. Fora do sandbox, ele usa apenas o `$PATH`, então um repositório não consegue escolher o interpretador que roda no host.

## `repl` — executar um script que chama as suas ferramentas

Presente em toda execução quando o servidor consegue rodar scripts ([Quando uma execução tem `repl`](/pt-BR/manual/conceitos/modo-de-codigo/#quando-uma-execução-tem-repl)). O script é JavaScript simples, o corpo de uma função assíncrona, e roda em um interpretador novo e bloqueado, em um processo próprio: sem acesso a sistema de arquivos, rede, processos ou módulos. A própria `repl` pertence ao nível `read` e se protege, porque cada chamada de ferramenta que o script faz é verificada por conta própria. Também disponível no endpoint MCP, para execuções de agente em um servidor que consegue rodar scripts.

| Argumento | Significado |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | O script. No máximo 256 KiB |
| `description` | Obrigatório. Um rótulo curto para a linha da transcrição |
| `timeout_ms` | Opcional. Um limite de tempo menor que o do espaço de trabalho; nunca maior |
| `max_output_tokens` | Opcional. Um orçamento de saída menor que o do espaço de trabalho; nunca maior |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

A descrição de `repl` diz ao agente: “Uma ferramenta que não é uma das suas ferramentas diretas não tem definição nesta requisição. Antes da primeira chamada a uma delas, consulte-a com `describeTool(name)` ou `searchTools(query)`, a menos que o formato exato da chamada já tenha sido mostrado a você nesta conversa.”

`describeTool(name)` devolve a descrição de uma ferramenta, a declaração dela, os esquemas de entrada e de saída e a sua nota de resultado, quando houver: o que um script recebe de uma chamada concluída, nas próprias palavras da ferramenta. A descrição de `repl` lista as notas das ferramentas diretas que um script pode chamar. Um resultado que é texto JSON chega já analisado, a menos que tenha mais de 131.072 valores: nesse caso, chega como texto, e o script o analisa com `JSON.parse`. O texto de um resultado de uma ferramenta de um servidor MCP externo é cortado em 262.144 caracteres, e o texto cortado deixa de poder ser analisado.

- `tools.<name>(args)` chama uma ferramenta pelo mesmo filtro, pelas mesmas barreiras e pela mesma aprovação de uma chamada direta, e é rejeitada com um erro quando é recusada ou falha. Chamadas somente de leitura podem rodar juntas; chamadas que alteram algo rodam uma por vez, na ordem em que o script as fez. Enquanto uma das chamadas espera uma pessoa, nenhuma outra chamada do script começa.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)` e `describeNamespace(name)` encontram ferramentas, inclusive as dos servidores MCP conectados. Uma ferramenta fora do conjunto direto que um script pode chamar só é chamável a partir de um script; chamar uma delas diretamente retorna como chamá-la a partir de `repl`. Quando o servidor não consegue rodar os scripts da execução, essa ferramenta passa a ser carregada no primeiro uso.
- As consultas têm limite: uma consulta de no máximo 1.024 caracteres, um nome ou namespace de no máximo 256, `limit` de 0 a 50, e no máximo 200 consultas que, por script, levem 2 segundos do tempo do servidor no total, enquanto todos os scripts de um mesmo espaço de trabalho compartilham 2 segundos de tempo de consulta, devolvidos à razão de um quarto de segundo a cada segundo; uma vez esgotado qualquer um dos dois, novas consultas são rejeitadas. Em um catálogo muito grande, as descrições em `ALL_TOOLS` dividem igualmente cerca de um milhão de caracteres, e uma descrição cortada termina em `…`; `describeTool` sempre retorna a descrição inteira. Um tipo grande demais para exibir aparece como `unknown /* too large to show */`, e um nome desconhecido recebe como resposta os nomes mais próximos.
- As ferramentas são agrupadas em namespaces: `builtin` (as ferramentas do próprio harness), `control-center` (as ferramentas do Control Center) e uma para cada servidor MCP conectado, com o nome do servidor. Um servidor chamado `builtin`, `control-center` ou `script`, ou cujo nome começa com `external-`, em qualquer combinação de maiúsculas e minúsculas e com ou sem espaços ao redor, é listado como `external-` seguido do seu nome, e nenhuma ferramenta fica em `script`.
- Só o que o script retorna, ou passa para `text()`, `image()` ou `console.*`, volta. A saída além do orçamento mantém o início e o fim, e `read_output` lê o restante.
- `store(key, value)` / `load(key)` guardam valores JSON para scripts seguintes da mesma conversa e do mesmo agente, salvos somente quando o script termina. Os scripts de um subagente não têm armazenamento.
- `await tools.ask_user(...)` faz uma pergunta; a resposta também é acrescentada ao resultado. `sleep(ms)`, `setTimeout`, `limits()` e `models.embed` / `rank` / `classify` (embeddings no dispositivo) também estão disponíveis.
- `describeTool(name)` e `searchTools(query)` também respondem pelas funções próprias do script, que não são ferramentas: `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit` e `models.*`, sob o namespace `script`.
- Não chamável a partir de um script: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` e os verbos `vibe_*`.
- Um script lê o passado da própria execução: `history({start, role, tool, limit})` pagina a transcrição da conversa (no máximo 50 linhas por chamada; passe o `next_start` da página anterior como `start`), `outputs()` lista as saídas de ferramentas armazenadas para esta conversa e este agente, e `loadOutput(handle)` lê 16.384 caracteres de uma delas. `storedKeys()` lista as chaves armazenadas com seus tamanhos. `keep(value, label)` armazena um valor grande como uma saída que um script posterior ou `read_output` pode ler, salva apenas quando o script termina (1 MiB por valor, 64 valores e 16 MiB por execução). `limits().returnBudgetChars` informa quanto do orçamento de saída ainda resta. Uma execução somente leitura (uma revisão de objetivo) pode ler, mas não armazenar nem usar keep. No Claude Code e no ACP, `history()` funciona, e `outputs()`, `loadOutput()` e `keep()` recusam, porque o Control Center não guarda saídas de ferramentas dessas execuções.
- Um erro de timeout, de estouro de saída ou de limite de chamadas diz como corrigi-lo.

Uma execução roda um script por vez. Os limites e o que acontece em cada um estão na página do [modo de código](/pt-BR/manual/conceitos/modo-de-codigo/#limites); todo script é registrado em **Observabilidade → Execuções de código**.

## `eval` — interpretadores persistentes

Uma célula de Python ou JavaScript cujas variáveis, importações e dados carregados sobrevivem entre chamadas. Nível `exec`; não é segura para paralelismo. Não é chamável a partir de um script `repl`, e uma célula não pode chamar as ferramentas da execução: para chamar ferramentas a partir de código, use [`repl`](#repl--executar-um-script-que-chama-as-suas-ferramentas).

| Argumento     | Significado                                      |
| ------------- | ------------------------------------------------ |
| `code`        | A célula                                         |
| `description` | Obrigatório. 5–10 palavras para o rótulo da transcrição |
| `language`    | `python` (padrão) ou `javascript`                |
| `reset`       | Descarta o interpretador e começa do zero        |

- A última expressão é ecoada como um notebook faz.
- `display()` funciona, um frame do pandas é renderizado como tabela e uma figura do matplotlib volta como uma **imagem que a transcrição mostra**.
- As expressões idiomáticas do IPython que as pessoas digitam por reflexo — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — são reescritas como código comum. O `%pip` também esvazia o `sys.modules`, então o próximo `import` vê o que acabou de ser instalado.
- Uma célula que imprime mais do que o seu orçamento de saída mantém os primeiros três quartos e o último quarto, com uma linha dizendo quantos caracteres e imagens foram descartados.
- Quando o interpretador morreu sem ser pedido, a próxima célula é avisada uma vez de que as variáveis anteriores se perderam.

:::note[Onde o kernel roda]
No recinto da conversa quando ela tem um; caso contrário, no sandbox do sistema operacional da execução, no host. Com o sandbox desligado ou indisponível, ele roda sem confinamento e `eval` pede aprovação de execução no host. Ele não inicializa um recinto para chegar até lá — a mesma regra que impede uma aba de rig de iniciar automaticamente.
:::

## `bash` em segundo plano

`bash` com `run_in_background: true` inicia o comando e retorna na hora com um identificador (`b1`, `b2`, …) em vez de esperar. O agente continua trabalhando, ou encerra o turno e é acordado quando o comando termina.

| Argumento | Significado |
| ------------------- | ------- |
| `run_in_background` | `true` para iniciar e retornar na hora |
| `timeout_seconds` | Segundos até o comando ser encerrado: 600 por padrão, no máximo 3.600 |
| `notify` | Opcional. Um padrão simples; cada linha de saída que casa com ele é enviada ao agente enquanto o comando roda (como `listening on\|FAILED`) |

- No máximo 4 comandos em segundo plano rodam ao mesmo tempo em uma execução. Cada um é encerrado no seu timeout e quando a execução termina, junto com todo processo que ele iniciou.
- Quando um comando termina, o agente recebe um aviso com o código de saída, os últimos 2.000 caracteres da saída e um identificador de `read_output` para o restante.
- Um agente cujo único trabalho restante é um comando em segundo plano espera sem chamar o modelo, e o watchdog de silêncio da execução fica pausado enquanto ele espera.
- `bash_output(handle)` lê o estado de um comando e a saída recente; `bash_kill(handle)` o interrompe. Ambos dizem quando o resultado já foi entregue.
- Um script não pode iniciar um comando em segundo plano. O Claude Code tem o seu próprio Bash em segundo plano; o Control Center mantém essa execução aberta por no máximo 10 minutos depois do turno que deixou uma tarefa rodando.

## `compact` — liberar espaço na janela de contexto

Compacta o contexto mais antigo da conversa antes da próxima chamada ao modelo, mantendo o que `focus` nomeia (no máximo 1.000 caracteres). Os turnos mais recentes permanecem literalmente. A linha de orçamento por turno do agente mostra o uso do contexto em 70, 80 e 90%, e vale chamar a ferramenta depois de cerca de 70% antes de uma nova fase longa de trabalho. O hook `preCompact` do proprietário do servidor pode acrescentar ao foco ([Hooks de shell](/pt-BR/manual/referencia/configuracao-de-agentes/#hooks-de-shell)). Após uma compactação, o servidor acrescenta um bloco "Still in flight": o objetivo, os despertares pendentes, as perguntas abertas, os comandos em segundo plano, a lista de verificação e as chaves armazenadas, cada um com a chamada que o recupera.

## `ask_user` — fazer uma pergunta ao humano

Nível `read`. A **única** forma de uma execução perguntar algo ao operador. Ela renderiza um cartão numerado na conversa e bloqueia até que alguém responda, pule ou a pergunta expire. Nunca escreva a pergunta como mensagem de chat — isso encerra o turno.

| Argumento         | Significado                                |
| ----------------- | ------------------------------------------ |
| `question`        | O que perguntar                            |
| `context`         | Opcional: por que você está perguntando e o que depende da resposta |
| `options[]`       | Escolhas, cada uma `{label, description?}` |
| `allow_free_text` | Se uma resposta digitada é aceita          |
| `multi_select`    | Se várias opções podem ser escolhidas      |

Pular é sucesso: prossiga com uma suposição declarada e não pergunte de novo. Um tempo esgotado é um erro com a mesma instrução. As solicitações de permissão ("posso fazer isso?") são um portão separado e são renderizadas como o mesmo cartão na conversa.

Registrada apenas quando existem tanto uma porta de perguntas quanto um espaço de destino. Sem um humano conectado, a chamada **falha** em vez de bloquear para sempre — a mesma postura de falha fechada que um `prompt` de guardrail adota quando não há aprovador conectado.

## `vibe_*` — dirigir workers em segundo plano

Registradas apenas enquanto o [modo vibe](/pt-BR/manual/guias/dirigir-workers-em-segundo-plano/) está ligado. As cinco são de nível `read`: o portão pertence às ferramentas do worker, onde a edição de fato acontece.

| Ferramenta   | Argumentos                               | Observações                                 |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | Retorna imediatamente; o worker segue rodando |
| `vibe_send`  | `worker_id`, `message`                   | Anexa ao briefing e executa de novo         |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | Bloqueia até que ele termine                |
| `vibe_kill`  | `worker_id`                              | Para ele                                    |
| `vibe_list`  | —                                        | Nível, status, tempo decorrido e último resultado |

O `tier` é `fast` (trabalho mecânico com especificação clara) ou `good` (design, julgamento ou revisão do que um worker `fast` produziu).
