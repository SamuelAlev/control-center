O Control Center pode enviar **eventos de uso pseudônimos** para uma instância do [Umami](https://umami.is). As análises de uso ficam **desativadas até que o operador do servidor as ative**. A configuração pertence ao servidor e vale para todos os clientes conectados a ele: o aplicativo de desktop, o aplicativo web, o celular e o próprio servidor.

As análises de uso são separadas de **Compartilhar relatórios de falhas**, uma configuração por dispositivo para diagnósticos de falhas e erros.

## Quem decide

| Opção | Onde | Efeito |
| --- | --- | --- |
| **Compartilhar análises de uso** | Onboarding (etapa do sandbox) e **Configurações → Privacidade**. Só o operador do servidor pode alterá-la; os demais membros veem o valor atual somente para leitura | Para todo o servidor. Armazenada como `telemetry.usage_analytics` nas configurações do servidor. Desativada a menos que seja definida como `true` |
| Tipo de build | Automático | Builds de debug e de profile não enviam nada. Em vez disso, gravam cada evento no log de debug |
| `CC_ANALYTICS_DEBUG=1` | Ambiente do `cc_server` ou o `.env` dele | Permite que builds de debug e de profile do servidor, e de todos os clientes conectados a ele, enviem eventos de verdade, para testes. A opção acima ainda precisa estar ativada |
| `DO_NOT_TRACK=1` | Ambiente do `cc_server` | Interrompe os envios do próprio servidor, seja qual for o valor da opção. Os clientes continuam seguindo a opção |
| Servidor de demonstração | Automático | O servidor de demonstração público não envia nada por conta própria. Os visitantes não podem alterar a opção |

Os clientes leem a configuração do servidor (`telemetry.config` e, depois, em tempo real por `telemetry.watch`). Até a resposta chegar, os eventos aguardam em um pequeno buffer na memória. Se a resposta for não, o buffer é descartado. Desativar a opção descarta tudo o que ainda estiver na fila e interrompe o envio imediatamente, em todos os clientes.

## O que nunca é enviado

- Conteúdo de mensagens, tickets, revisões ou reuniões, títulos, prompts, comandos de shell e consultas de busca
- Nomes, logins, endereços de e-mail, avatares e nomes de exibição
- Caminhos de arquivos, nomes de repositórios, nomes de branches, nomes de host e URLs (um repositório é enviado apenas como um `repo_id` pseudônimo; o link de uma reunião, apenas como o nome do provedor)
- Identificadores brutos de qualquer tipo

Todo evento passa por uma política de propriedades antes de sair do processo. Textos, caminhos, URLs, endereços de e-mail, IDs não encapsulados e strings sob chaves como `email`, `*_name`, `path`, `title`, `prompt`, `content` ou `token` são descartados em vez de enviados. Uma string só é enviada se for um token curto de um vocabulário fechado, como um valor de enum, uma versão, uma localidade ou um ID de modelo.

## IDs pseudônimos

Os IDs são enviados, mas apenas como pseudônimos. Cada ID de espaço de trabalho, espaço, conversa, agente, execução, usuário e dispositivo é substituído por um HMAC-SHA256 calculado com o salt secreto da própria instalação (`telemetry.pseudonym_salt`), truncado em 20 caracteres hexadecimais. O mesmo espaço de trabalho sempre informa o mesmo valor, então os eventos podem ser relacionados e contados, mas o ID bruto nunca sai da instalação. O salt é criado na primeira inicialização do servidor e nunca é enviado ao provedor de análises. Excluir o diretório de dados do servidor cria um novo salt e um novo ID de instalação, o que desvincula tudo o que foi registrado antes.

## Visualizações de tela

Cada navegação registra uma visualização de página cuja URL é o **modelo de rota**, como `/workspaces/:workspaceId/spaces/:spaceId`, nunca o endereço concreto. O nome da tela é formado pelos segmentos literais do modelo, então nesse exemplo ele é `workspaces_spaces`. Parâmetros de rota terminados em `Id` são anexados como propriedades pseudônimas `*_id`, e os numéricos (como o número de um PR) como números. Todos os outros parâmetros são descartados.

## Entrega

Os eventos são enviados um de cada vez para `<host>/api/send` a partir de uma fila na memória com até 200 eventos. Um erro de rede, um timeout, um `429` ou um `5xx` mantém o evento e tenta de novo com backoff exponencial, de 1 segundo até 5 minutos. Qualquer outro `4xx` o descarta. Nada é gravado em disco, então os eventos que ainda estiverem na fila quando o aplicativo for fechado se perdem. A fila é esvaziada quando o aplicativo vai para segundo plano e quando o servidor é desligado.

## Apontar um build para outra instância

O destino é fixado no momento do build:

```bash
--dart-define=CC_ANALYTICS_HOST=https://analytics.example.com/
--dart-define=CC_ANALYTICS_WEBSITE_ID=<website uuid>
```

O adaptador do provedor fica em `packages/cc_analytics`. Para dar suporte a outro serviço de análises, basta adicionar um adaptador ali. O plano de rastreamento e as regras de privacidade continuam os mesmos.
