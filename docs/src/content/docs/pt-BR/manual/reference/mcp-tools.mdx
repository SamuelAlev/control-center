O `cc_server` hospeda um único registro de ferramentas MCP (JSON-RPC 2.0), servido na porta principal do servidor (padrão `9030`) em `POST /mcp` e `GET /sse`, com versão de protocolo `2024-11-05`. Todos os clientes chegam ao mesmo registro: o desktop, a build web, clientes MCP externos e o runtime de agentes integrado. Servidores MCP externos podem ser conectados ao mesmo registro como uma camada dinâmica.

## Tamanho do registro

| Medida                                                                             | Contagem |
| ---------------------------------------------------------------------------------- | -------- |
| Ferramentas registradas pelo `cc_server`                                           | 110      |
| De `packages/cc_mcp`                                                               | 108      |
| De `packages/cc_mcp_client` (descoberta de ferramentas)                            | 2        |
| Registradas no registro base (`server_mcp_registry.dart`)                          | 63       |
| Registradas após a inicialização, conforme seus serviços sobem (`cc_server_runtime.dart`) | 47       |
| Das 63 do registro base, condicionais a um repositório de grafo de código          | 5        |

As cinco ferramentas de grafo de código só são registradas quando o host passa um repositório de grafo de código para `buildServerMcpRegistry`. O `cc_server` sempre passa um, então todas as 110 estão ativas no binário distribuído.

O registro completo é anunciado em `tools/list`, sem restrição de descoberta. As edições de tickets são ferramentas tipadas.

:::note[Clientes externos sempre veem o catálogo inteiro]
O `tools/list` nunca é enxugado. Os clientes MCP validam nomes de ferramentas contra a própria cópia em cache dessa lista e recusam qualquer coisa não listada sem nunca perguntar ao servidor, então uma ferramenta ali escondida é inalcançável, e não apenas silenciosa.

O **harness integrado** é diferente: ele carrega apenas um subconjunto residente de definições por requisição e traz o restante no primeiro uso, o que é um comportamento do lado do harness e não altera este registro. Consulte [Contexto de ferramentas e cache de prompts](/pt-BR/manual/conceitos/contexto-de-ferramentas).
:::

:::note[Toda classe de ferramenta é registrada]
Um arquivo-fonte em `packages/cc_mcp/lib/src/tools/` é uma ferramenta que um agente pode
chamar. `packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
faz a build falhar se uma nova classe de ferramenta não for construída por nada.
:::

## Parâmetros comuns

### `workspace_id`

**Obrigatório** em toda ferramenta que toca dados no escopo do espaço de trabalho. Um `workspace_id` ausente ou inválido retorna um erro explícito, e um valor que não corresponde ao espaço de trabalho da entidade alvo é rejeitado em vez de silenciosamente ignorado. Omita-o nas ferramentas genuinamente globais: `list_workspaces` e as seis ferramentas de notícias (`list_feeds`, `list_articles`, `get_article`, `set_article_read`, `set_article_saved`, `refresh_feeds`), que usam a lista de feeds por usuário do dono do servidor. As ferramentas de descoberta (`search_tool_bm25`, `list_my_tools`) o recebem opcionalmente para poderem classificar a chamabilidade pelo modo da conversa. Quando o servidor despacha um agente, o espaço de trabalho é forçado do lado do servidor, então o agente não consegue alcançar outro espaço de trabalho passando um id estranho.

## Descoberta de ferramentas

Ambas vêm de `cc_mcp_client`, não de `cc_mcp`, e ambas consultam o guarda de modo para relatar o que é chamável no modo de conversa _atual_.

| Ferramenta         | Descrição                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `search_tool_bm25` | Pesquisa o catálogo de ferramentas por palavra-chave; retorna as ferramentas correspondentes, seus esquemas de argumentos e se cada uma é chamável agora |
| `list_my_tools`    | Lista as ferramentas chamáveis agora nesta conversa, filtradas pelo modo dela                                                        |

Uma terceira ferramenta de descoberta, **`search_tools`**, existe apenas dentro do harness integrado e não faz parte deste registro MCP. Ela classifica a própria superfície de ferramentas da execução e, ao contrário de `search_tool_bm25`, **carrega** os esquemas do que encontra para que o agente possa chamar uma correspondência no turno seguinte. Agentes no harness devem preferi-la; clientes MCP têm `search_tool_bm25`.

## Mensagens entre pares e delegação de agentes

Os agentes conversam entre si por espaços (duráveis, visíveis na lista de agentes). `ask_agent` é requisição/resposta com timeout obrigatório; `delegate_task` é protegida do lado do servidor por limite de profundidade, detecção de ciclos, envelope de orçamento e teto de autonomia.

| Ferramenta      | Descrição                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------- |
| `send_to_agent` | Envia uma mensagem de mão única a outro agente, endereçado por `to_agent_id` ou por `to_agent_name` exato |
| `ask_agent`     | Pergunta algo a outro agente e espera a resposta, ou expira                                  |
| `delegate_task` | Delega uma tarefa a outro agente como um ticket filho acompanhado                              |

| `todo_read`     | Lê a lista de tarefas persistida desta conversa                                                |

## Ferramentas de recinto (rig)

Controlam máquinas descartáveis — um navegador ou desktop Linux em recinto, um emulador
Android ou um iOS Simulator — de dentro de uma execução. Registradas após a
inicialização, incondicionalmente: se uma máquina consegue mesmo iniciar é uma pergunta
de sondagem que as ferramentas respondem a cada chamada. Chamadas repetidas em uma mesma
conversa reutilizam uma máquina; as capturas de tela voltam como conteúdo de imagem, com
um orçamento de uma imagem por resultado, e o conteúdo de página/UI extraído é cercado
como dado não confiável. As quatro ferramentas de uso, mais a `rig_close`, declaram a
[classe de ação](/pt-BR/manual/conceitos/barreiras/) `enclosureControl`
(as ferramentas de uso também declaram `networkEgress` e `processSpawn`; `mobile_use` e
`ios_use` também declaram `packageInstall`), então modos somente leitura as negam. A `rig_list`
não declara nenhuma — ela apenas lê o estado do espaço de trabalho. O vocabulário completo de verbos por superfície está na
[referência de rigs](/pt-BR/manual/referencia/rigs/#action-verbs).

| Ferramenta     | Descrição                                                                                       |
| -------------- | ----------------------------------------------------------------------------------------------- |
| `computer_use` | Controla um desktop Linux em uma VM de recinto: mover, clicar, arrastar, rolar, digitar, redimensionar, área de transferência, captura de tela |
| `browser_use`  | Controla um Chromium, Firefox ou WebKit headless (`engine`): navegar, clicar, preencher, extrair (a11y/DOM/console), área de transferência, captura de tela |
| `mobile_use`   | Controla o Android via ADB: inspecionar/entrada, capturas de tela, instalar/iniciar/parar/redefinir/desinstalar apps, deep links e comandos de dispositivo em formato argv |
| `ios_use`      | Controla o iOS Simulator por WebDriverAgent/CoreSimulator: inspecionar/entrada, capturas de tela, instalar/iniciar/parar/desinstalar apps, deep links e processos de simulador em formato argv |
| `rig_list`     | Lista os rigs de um espaço de trabalho com superfície, status, tamanho da tela e controlador  |
| `rig_close`    | Destrói um rig e descarta o estado da máquina que ele possui                                   |

## O que não é exposto por MCP

Calendário e reuniões não têm ferramentas MCP. Os agentes não conseguem ler seu calendário, suas reuniões, transcrições, itens de ação ou decisões. O resumo que produz itens de ação e decisões roda no [pipeline `meeting_summary`](/pt-BR/manual/conceitos/reunioes/) integrado, e não como uma ferramenta que um agente possa chamar.

## Restrição de ferramentas por modo

A restrição é aplicada duas vezes a partir de uma única tabela (`ModeToolPolicy`): uma no despachante MCP do adaptador Claude Code e outra no registro do harness integrado. Uma chamada bloqueada retorna o motivo.

| Modo          | Superfície de ferramentas                                                                                                                                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | Todas as ferramentas registradas; nenhuma lista de permissões                                                                                                                                                                      |
| `plan`        | Uma lista de permissões curada. Sem gravações na worktree e sem os verbos de ticket `create` / `assign` / `delegate`, mas memória, artefatos, todos, `submit_plan`, `exit_plan_mode` e os verbos de conclusão de ticket do ticket despachado são permitidos |
| `review`      | Uma lista de permissões curada: participação em revisão, comunicação, buscadores de contexto somente leitura e o conjunto completo de verbos de ticket, incluindo `create_ticket` e `assign_ticket`                              |
| `orchestrate` | Uma lista de permissões curada: ferramentas de pesquisa e leitura, mais `propose_orchestration`, `create_playbook` e `run_playbook`. Contratação, decomposição e conclusão de tickets acontecem de forma determinística após a aprovação, nunca no meio da execução |

Permitidas em todos os modos, independentemente da lista de permissões:

| Conjunto             | Ferramentas                                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Memória e artefatos  | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| Grafo de código      | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                        |
| Mecânica de execução | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                     |

Estar em uma lista de permissões não torna uma ferramenta chamável, e o inverso também vale: a capacidade de perguntar ao operador é uma ferramenta do **harness** (`ask_user`), então ela nunca aparece neste catálogo MCP.

## Ferramentas sujeitas a aprovação

Uma ferramenta pode declarar `requiresApproval`. O despachante então monta um `ApprovalPayload` e o apresenta pelo `ConfirmationPort` antes de a ferramenta rodar; o `cc_server` conecta essa porta, então o portão está ativo.

Ferramentas registradas que o declaram: `create_ticket`, `update_ticket`, `assign_ticket`, `reassign_ticket`, `close_ticket`, `ticket_relation`, `create_goal`, `update_goal_progress`, `create_approval`, `decide_approval`, `comment_approval`, `create_work_product`, `save_work_product_revision`, `create_runtime_profile`, `install_skill`, `update_skill`.

De forma independente, as barreiras unificadas de ação colocam um portão em qualquer ferramenta que declare um conjunto `ActionClass` não vazio. Uma decisão `prompt` sem nenhum aprovador conectado é negada. Consulte [Barreiras](/pt-BR/manual/conceitos/barreiras/).

## Capacidades sem ferramenta por trás

Nem toda capacidade do produto é alcançável por um agente. Estas não têm ferramenta
alguma, então um nome que você talvez tenha visto referenciado em outro lugar retorna "unknown tool":

| Capacidade                                | Onde ela vive em vez disso                                                                                     |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Contratar, demitir ou editar um agente    | A UI de agentes. Não existe ferramenta `hire_agent` / `fire_agent` / `update_agent`                             |
| Criar um espaço de trabalho               | `workspace.upsert` por RPC, que semeia e carimba a propriedade                                                  |
| Projetos (criar / listar / atualizar / registrar) | A UI de tickets. Projetos são uma superfície do operador — consulte [Projetos](/pt-BR/manual/guias/projetos/)   |
| Fazer ao operador uma pergunta bloqueante | A ferramenta `ask_user` do **harness**, não o MCP. Ela renderiza um formulário na conversa e bloqueia até a resposta |
| Diagnóstico por agente                    | Nada. Não existe um `doctor` — consulte [Diagnóstico de agente](/pt-BR/manual/guias/diagnosticar-agente/)       |
| Calendário e reuniões                     | RPC apenas para clientes humanos (veja acima)                                                                   |
