:::caution[Se uma execução roda em sandbox depende do host]
`cc_server` decide uma vez, na inicialização, como os agentes rodam neste host, e a decisão vale até ele reiniciar:

- **Em sandbox** (`native`): a sondagem encontrou um backend e `--sandbox` não é `off`. As duas costuras do despacho são envolvidas: a CLI do Claude Code pela porta de sandbox, e o ACP mais a ferramenta `bash` do harness integrado pelo gerenciador de sandbox.
- **Desligado** (`off`): o proprietário do servidor o iniciou com `--sandbox off`. Os agentes de todos os membros rodam sem confinamento nesta máquina, seja quem for que tenha iniciado.
- **Indisponível** (`unavailable`): a sandbox está ligada, mas a sondagem não encontrou backend (**Windows sempre**, e Linux ou WSL2 sem `bwrap` e `socat`). Uma execução só começa quando a pessoa responsável por ela é o [proprietário](/pt-BR/manual/conceitos/autorizacao/#o-proprietário-do-servidor) do servidor: quem pediu, ou, para a automação, a pessoa a que ela está vinculada. A execução de qualquer outra pessoa é recusada antes de uma credencial ser emitida, um lease ser obtido ou um processo começar. Sem proprietário registrado, nenhuma execução começa.

Uma execução recusada falha com o código `sandbox_unavailable`. O app a mostra como **Agentes precisam de uma sandbox neste servidor**: "Este servidor não tem sandbox, então somente o proprietário pode executar agentes aqui. O proprietário pode instalar a sandbox ou desligar o sandboxing para todos."

Uma execução que começa sem sandbox (em `off`, ou a execução do próprio proprietário em `unavailable`) roda diretamente no host. O ACP e a ferramenta `bash` do harness ainda iniciam com sanitização do ambiente; o Claude Code passa pelo `NoSandboxAdapter` e herda o ambiente do host. As fronteiras restantes são a worktree da própria execução (copy-on-write onde o `rift` é distribuído; `git worktree` no Windows), um token de forge somente leitura, intermediado a cada inicialização e revogado no encerramento, pushes que precisam passar pela regra de push no gateway de execuções de agentes, a política de comandos de cada modo, as [barreiras de ação](/pt-BR/manual/conceitos/barreiras/) unificadas (com falha fechada), a sanitização do ambiente nos caminhos do ACP e do `bash` do harness, e a superfície de ferramentas que o modo permite.

As ferramentas de arquivo em processo do harness (read, write, edit, apply patch, search, find, search_files) ficam fora do sandbox em todo host: elas rodam no processo do servidor, então só o `bash` é envolvido.

O host nunca é fallback para um servidor com sandbox. Se o servidor coloca agentes em sandbox mas não tem sandbox para dar a uma execução, os processos de ferramenta e os comandos `bash` dela são recusados, não iniciados no host. A mesma postura decide os pequenos processos em volta de uma execução: os auxiliares one-shot do ACP (títulos de conversas, `/btw`, `/handoff`, `/goal`) e os testes golden de uma pull request no Review Studio rodam em sandbox quando o servidor coloca agentes em sandbox, sem confinamento sob `off`, e sob `unavailable` somente para uma solicitação pela qual o proprietário do servidor é responsável; do contrário são ignorados.
:::

## Visão geral dos backends

| Backend     | Valor     | Plataforma                                    | Disponibilidade                                                                                                      |
| ----------- | --------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| VM fechada | `microvm` | macOS, Linux, Windows (hipervisor de microVM) | Condicionado à sondagem do runtime de microVM; aplica-se a terminais interativos — o shell roda dentro de um [rig](/pt-BR/manual/conceitos/rigs/), não no host |
| Nativo | `native` | macOS (Seatbelt), Linux e WSL2 (bubblewrap) | Sondado na inicialização; o Linux recusa uma execução que exija negações de escrita por glob de nome de arquivo, que o bubblewrap não consegue aplicar |
| Nenhum | `none` | Todos | O padrão da análise e o padrão do terminal; a execução de agentes o usa sob `--sandbox off`, e, para as execuções do próprio proprietário, quando nenhum backend está disponível |

`SandboxBackend.fromName` retorna `none` para um valor armazenado nulo ou não reconhecido.

**`microvm` é o único backend com fronteira de kernel** — a carga de trabalho
genuinamente não roda no host. Ele nunca é um fallback silencioso em nenhuma das
direções: pedi-lo explicitamente em um host que não consegue inicializar uma VM
falha de forma ruidosa ("pedi uma VM e recebi meu notebook" é a única degradação
que o recinto não pode se permitir), e apenas um *padrão não especificado*
recorre a `native`, com uma linha de log dizendo isso. O backend real da sessão é
reportado de volta ao cliente e recebe um selo, então um terminal nunca pode
alegar estar fechado enquanto roda no host. Ciclo de vida, imagens e saída de rede
da própria VM estão cobertos pela [referência de rigs](/pt-BR/manual/referencia/rigs/).

**O Windows não tem sandbox nativo.** `NativeSandboxAdapter.probe` retorna `available: false` em todo host que não seja macOS ou Linux/WSL2, então um servidor no Windows fica `unavailable`: só começam as execuções de agentes do proprietário do servidor, sem confinamento, e as de todos os demais são recusadas. Para que todo membro rode agentes ali, o proprietário inicia o servidor com `--sandbox off`, o que roda todos sem confinamento. O backend `microvm` é separado: ele é condicionado à sondagem do runtime de microVM e se aplica a terminais interativos e rigs, não a envolver o `bash` no host.

## Resultados da sondagem

A sondagem é o que condiciona a aplicação. Ela roda uma vez, na inicialização do servidor.

| Host                                   | `available` | Nota / dica                                                               |
| -------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS | `true` | `sandbox-exec` (Seatbelt) — isolamento de namespace, sem fronteira de kernel |
| Linux ou WSL2 com `bwrap` e `socat` | `true` | bubblewrap — isolamento de namespace, sem fronteira de kernel |
| Linux ou WSL2 sem qualquer uma das ferramentas | `false` | `requiresInstall: true`, com uma dica de instalação que nomeia os pacotes ausentes |
| Qualquer outra plataforma | `false` | O sandbox nativo não é oferecido nesta plataforma |

O servidor registra o resultado em uma única linha de inicialização: `agent sandbox ON` mais a nota; `no OS-native agent sandbox on this host` mais a dica, que acrescenta que só começarão as execuções pelas quais o proprietário do servidor é responsável; ou `agent sandbox DISABLED by --sandbox off`. A linha de exposição impressa na inicialização traz a mesma decisão como `sandbox=native`, `sandbox=off` ou `sandbox=unavailable`. `GET /healthz` não carrega nenhum campo de sandbox.

`--sandbox` / `CC_SERVER_SANDBOX` aceita `on` (padrão) ou `off`. `on` envolve toda execução quando o host oferece um backend, e admite só as execuções do proprietário quando não oferece. `off` roda os agentes de todos os membros sem confinamento neste host; é a escolha do proprietário para todos, não uma configuração por execução.

## Backend nativo

### macOS: Seatbelt

Usa o mecanismo de sandbox Seatbelt da Apple (o mesmo sistema usado pelo App Sandbox do macOS).

O perfil gerado é **permissivo por padrão** (`(allow default)`) e recorta negações, porque um perfil totalmente de negação por padrão torna um shell interativo inutilizável — há chamadas demais de dyld, XPC e Mach para enumerar. A consequência prática é que um agente ainda consegue ler a maior parte do host; seus checkouts registrados são protegidos por negações explícitas de escrita e de renomeação, não por invisibilidade.

- **Leituras do sistema de arquivos**: negadas para os caminhos secretos (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` e o resto do conjunto de leitura negada)
- **Escritas no sistema de arquivos**: redefinidas para negar e depois permitidas em subcaminhos explícitos, com os caminhos de negação obrigatória (arquivos rc do shell, `.git/hooks`, a configuração do Claude, checkouts protegidos) bloqueados mesmo dentro de uma raiz gravável. `file-write-unlink` é negado em todo caminho negado e em seus ancestrais, de modo que uma renomeação não pode contornar uma negação de escrita
- **Processos**: negações de `process-exec` para os binários sempre perigosos, além de um bloqueio à execução de qualquer coisa a partir de um diretório gravável. Os diretórios de instalação de toolchains conhecidos sob o seu home (corepack, caches de `npx` e `pnpm dlx`, gerenciadores de versão do node, navegadores do Playwright, rustup e cargo, Go, fvm e o cache do pub, pyenv, uv e pipx, rbenv, sdkman, mise, asdf e `~/.local/bin`) são reabertos sob esse bloqueio. Os diretórios temporários compartilhados também são bloqueados. Em vez disso, cada sessão recebe um `TMPDIR` privado em `/private/tmp`, onde podem rodar os programas que ela compila (um binário de `go test`, um build do cargo). As negações sempre perigosas são aplicadas depois dessas permissões
- **Rede**: restrita às portas do proxy em processo mais o DNS — o loopback não é permitido de forma irrestrita e a escuta TCP é negada. Sockets Unix são permitidos somente dentro do `TMPDIR` privado da sessão, que cobre ferramentas como tsx e Chrome que mantêm um socket IPC ali; o seu agente SSH e os demais sockets continuam inacessíveis. Os proxies aplicam a lista de permissões de domínios por sessão (veja [Saída de rede](#saída-de-rede))
- **Configuração**: os perfis são gerados a cada inicialização a partir do `SandboxSpec`
- **Comandos do próprio servidor**: nenhum filho direto de uma pasta de onde o servidor executa programas (toda entrada de `PATH` e as pastas comuns de ferramentas por usuário, como `~/.local/bin`, com links de gerenciadores de versão como `~/fvm/default` resolvidos) pode ser criado, substituído, excluído ou renomeado, nem o pacote instalado para onde um comando vinculado aponta. Veja [As pastas de comandos do servidor](#as-pastas-de-comandos-do-servidor)
- **Arquivos de inicialização**: todo caminho da home que o perfil nega a leitura também é negado para escrita, e os arquivos de inicialização dos shells e sessões do usuário do servidor (`.zshenv`, `.zlogin`, `.bash_login`, configuração do fish, unidades de usuário do systemd, entradas de inicialização automática e afins) têm escrita negada em todo modo

Requisitos:

- `sandbox-exec` (`/usr/bin/sandbox-exec`), presente em toda instalação do macOS — nenhuma ferramenta adicional é necessária

### Linux: bubblewrap

Usa o bubblewrap (`bwrap`) para criar namespaces de montagem e de PID.

- **Sistema de arquivos**: cria um namespace de montagem com apenas os caminhos vinculados visíveis
- **Rede**: roda em um namespace de rede não compartilhado; o tráfego chega aos proxies do host por pontes de socket Unix do `socat`
- **Processos**: isolamento de namespace de PID
- **Comandos do próprio servidor e arquivos de inicialização**: as mesmas proteções do macOS, expressas como montagens bind do bubblewrap. Elas ainda não foram verificadas no Linux, e uma pasta de comandos ausente ali ainda pode ser criada

Requisitos:

- `bubblewrap` e `socat` instalados (`sudo apt-get install bubblewrap socat` no Debian/Ubuntu)
- Suporte a namespaces do kernel (padrão no Linux moderno)

O bubblewrap consegue ocultar um caminho existente, mas não consegue proibir um arquivo `.env`, `*.key` ou `*.pem` *novo* dentro de um bind gravável. A política de despacho padrão exige essas negações por glob de nome de arquivo, então o despacho nativo de agentes hoje **falha de forma fechada no Linux/WSL2 mesmo quando a sondagem encontra o bubblewrap**. Ele não roda com uma política silenciosamente mais fraca. É preciso um backend com regras de nome de arquivo no momento da criação para restaurar o despacho nativo no Linux. Desativar o sandbox é uma desativação explícita e sem confinamento, não uma alternativa equivalente.

Na prática, um servidor Linux ou WSL2 roda agentes hoje de duas formas. Iniciado com `--sandbox off`, ele roda os agentes de todos os membros sem confinamento. Sem bubblewrap ou `socat` instalados, ele fica `unavailable` e roda somente os agentes do proprietário do servidor, sem confinamento. Com as duas ferramentas instaladas e a sandbox ligada, toda execução falha de forma fechada, inclusive a do proprietário.

## As pastas de comandos do servidor

O servidor descobre, uma vez na inicialização, toda pasta de onde ele executa programas: cada entrada do seu `PATH`, as pastas de ferramentas por usuário que ele verifica (como `~/.local/bin`, `~/.bun/bin` e as pastas globais do npm, do yarn e do pnpm), e a pasta real por trás de cada link no caminho (links de gerenciadores de versão como `~/fvm/default` ou um padrão do fnm). Dentro de uma sandbox, um agente não consegue adicionar, substituir, excluir ou renomear um comando nessas pastas, o link que leva a um deles, ou o pacote instalado para onde um comando vinculado aponta, e não consegue renomear as pastas acima delas. Do contrário, uma execução em sandbox poderia plantar um programa que o servidor, ou a pessoa, depois inicia fora da sandbox.

O que isso muda para uma execução:

- Instalações globais feitas de dentro de uma execução em sandbox falham com "Operation not permitted": `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, e `cargo install`, `go install` ou `dart pub global activate` quando a pasta de binários deles está no `PATH` do servidor.
- Trocar uma versão padrão falha do mesmo jeito (`fnm default`, `nvm alias default`, `fvm global`), assim como uma ferramenta que se atualiza sozinha no lugar.
- Instalações locais ao projeto (`node_modules/.bin`), `npx`, `pnpm dlx`, gerenciadores de pacotes gerenciados pelo corepack, caches de SDK e builds normais continuam funcionando.

Para tornar uma ferramenta global disponível aos agentes, instale-a no próprio servidor, como o usuário do servidor, e reinicie o servidor para que o novo comando também fique protegido. Ou instale-a no projeto. Um comando instalado depois que o servidor iniciou só fica totalmente protegido a partir da próxima inicialização.

Aplicado e testado no macOS. No Linux, as mesmas regras são montagens bind do bubblewrap que ainda não foram verificadas. O Windows não tem sandbox.

## Backend `none`

Nenhum sandbox. O processo roda diretamente no host, com o acesso a sistema de arquivos, rede e processos do host. O ACP e a ferramenta `bash` do harness ainda recebem a sanitização do ambiente e a política de comandos; o Claude Code pelo `NoSandboxAdapter` herda o ambiente do host. O despacho de agentes o usa para toda execução sob `--sandbox off`, e em um host sem backend disponível somente para as execuções do próprio proprietário do servidor; a execução de qualquer outra pessoa é recusada ali. Para um terminal, é o shell do host, que somente o proprietário do servidor pode abrir.

## Terminal hospedado no servidor

O terminal hospedado no servidor abre o shell do host somente para o [proprietário](/pt-BR/manual/conceitos/autorizacao/#o-proprietário-do-servidor) do servidor. Todos os demais recebem um terminal em sandbox, com os limites de um agente, nos diretórios do próprio espaço de trabalho.

Veja como o backend é escolhido para uma sessão:

| Solicitado | Proprietário do servidor | Qualquer outra pessoa |
| --- | --- | --- |
| Nada | O backend padrão do servidor | O padrão, com `none` trocado por `native` |
| `none` (o shell do host) | Shell do host | Recusado: o shell do host roda no servidor sem sandbox |
| `native` | Sandbox nativa, perfil do proprietário | Sandbox nativa, perfil de agente |
| `microvm` | VM fechada | VM fechada |
| Um nome desconhecido | Recusado | Recusado |

- **Perfil do proprietário.** `$HOME` e o diretório de trabalho da sessão são graváveis, a rede fica aberta, e a leitura de `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh` e `~/Library/Keychains` é negada.
- **Perfil de agente** (`memberTerminalSandboxConfig`). A mesma política sob a qual um agente naquele espaço de trabalho roda: as escritas ficam no diretório de trabalho, em um diretório de execução privado, em `/tmp` e nas partes de `$HOME` que um agente pode escrever; segredos têm leitura negada; a rede é a lista de permissões de saída de agentes; programas rodam somente a partir do diretório de trabalho e das toolchains instaladas.
- Um terminal só abre dentro dos diretórios do próprio espaço de trabalho. Um diretório de trabalho fora deles é recusado, nunca trocado por outro.
- Somente a pessoa que abriu um terminal consegue lê-lo, digitar nele, redimensioná-lo ou fechá-lo. Para qualquer outra pessoa, o id dele parece desconhecido.
- `microvm` pedido explicitamente em um host sem serviço de rig falha em vez de recorrer a outro. Um padrão `microvm` nesse tipo de host desce para `native` e informa isso no log.

O token de forge somente leitura e o gateway de push não se aplicam aos terminais: são questões do despacho. Se o envolvimento não for suportado, a sessão falha em vez de mostrar um selo de sandbox em uma sessão de shell do host.

## Saída de rede

Quando um sandbox é iniciado, o acesso de rede de saída é aplicado por proxies em processo, não por regras de firewall do kernel. Uma execução sem sandbox (toda execução sob `--sandbox off`, ou a execução do proprietário em um host sem backend) não recebe nada disso: um processo que ela gera chega à rede exatamente como o próprio usuário do servidor chegaria.

- O runtime do sandbox executa um proxy HTTP/HTTPS e um proxy SOCKS5 em `127.0.0.1` dentro do processo do `cc_server`, **um par por sessão restrita** (`http_proxy.dart`, `socks_proxy.dart`). Execuções simultâneas não compartilham um par.
- Processos em sandbox recebem variáveis de ambiente de proxy (`HTTP_PROXY`/`HTTPS_PROXY` → o proxy HTTP, `ALL_PROXY` → o proxy SOCKS; `GIT_SSH_COMMAND` encaminha git-over-SSH pelo proxy SOCKS). No Linux o namespace de rede não é compartilhado, então os proxies são a única saída; no macOS o sandbox compartilha o loopback do host e fala com eles diretamente.
- O host de destino de cada conexão é comparado com a lista de permissões de domínios da sessão; qualquer outra coisa é negada. Há duas formas de curinga, cada uma com exatamente um `*`: um `*.example.com` no início casa com qualquer subdomínio (incluindo `a.b.example.com`), mas não com o próprio domínio raiz; um `bedrock.*.amazonaws.com` com rótulo no meio casa exatamente com um rótulo (`bedrock.us-east-1.amazonaws.com`, não `bedrock.evil.attacker.amazonaws.com`).
- A lista de permissões é resolvida por sessão a partir da base curada (`kBaselineAllowedDomains`: provedores de LLM, hospedagem de Git, registros de pacotes), mais os domínios do GitHub (`kGithubDomains`), mais `SandboxSpec.egressAllowlist`. O caminho de despacho nunca passa entradas extras de `egressAllowlist`, então na prática toda execução recebe a base mais o GitHub.
- Uma lista fixa de negação (`kBaselineDeniedDomains`: endpoints de metadados de nuvem, destinos de telemetria) tem precedência sobre todas as permissões.
- `networkEnabled: false` ainda inicia os proxies por sessão, mas a lista de permissões fica vazia, então toda conexão de saída é recusada. O despacho o define quando a execução começa a partir da regra **Acessar a rede**: negar desliga a rede; permitir e perguntar primeiro a mantêm ligada.

## SandboxSpec

A especificação passada para `SandboxPort.launch`:

| Campo             | Tipo                                        | Descrição                                                                                                                                 |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId` | `String` | Identificador estável da sessão (normalmente o id do espaço) |
| `workspaceId` | `String` | Id do espaço de trabalho proprietário |
| `agentId` | `String?` | Agente atualmente vinculado ao sandbox, se houver |
| `bindMounts` | `List<SandboxBindMount>` | Montagens host→guest; o sandbox vê apenas os caminhos do host listados aqui |
| `networkEnabled` | `bool` (padrão `true`) | Definido no despacho a partir da regra de saída de rede (desligado só quando ela resolve para negar). Quando desativado, os proxies por sessão ainda iniciam, mas a lista de permissões fica vazia, então toda conexão de saída é recusada |
| `egressAllowlist` | `List<String>` (padrão `[]`) | Domínios de saída adicionais permitidos; curingas são suportados (`*.example.com`, além de uma forma intermediária de um único rótulo). O despacho nunca preenche isto, então uma execução envolvida recebe a base curada mais os domínios do GitHub |
| `guestWorkdir` | `String?` | Diretório de trabalho padrão dentro do sandbox; chamadas `exec` individuais podem sobrescrevê-lo |
| `mode` | `Mode` (padrão `chat`) | Recorta as regras de escrita do sistema de arquivos: `chat` mantém as montagens bind graváveis; `review`, `plan` e `orchestrate` são somente leitura |
| `protectedPaths` | `List<String>` (padrão `[]`) | Caminhos do host que nunca podem ser graváveis dentro do sandbox, em nenhum modo |
| `runnerStateDirs` | `List<String>` (padrão `[]`) | Diretórios do host onde o runner mantém o próprio estado, graváveis em todos os modos (um `CLAUDE_CONFIG_DIR` gerenciado pelo Control Center é o atual) |
| `execGrantRoots` | `List<String>` (padrão `[]`) | Árvores de diretórios aprovadas pelo operador que reabrem o bloqueio de exec em diretórios graváveis no macOS. O Linux as ignora — o bwrap não tem nenhum bloqueio de exec em `$HOME` a reabrir |

`protectedPaths` contém os checkouts originais dos repos registrados, resolvidos a cada despacho a partir dos repos do espaço de trabalho. Os agentes trabalham exclusivamente em worktrees de copy-on-write por conversa, então os originais nunca podem ser graváveis de dentro do sandbox — no macOS, a permissão geral de escrita do Seatbelt sobre `$HOME` os deixaria graváveis via `bash` caso contrário. Eles se juntam ao conjunto de negação de escrita de segredos em todos os modos, `chat` incluído.

Todo caminho de leitura negada e de escrita negada é emitido tanto na sua forma literal quanto na sua forma resolvida por symlink. O kernel casa uma regra de negação com o caminho resolvido, então uma regra escrita contra um caminho com symlink nunca dispara — e no macOS esse é o caso comum, e não o exótico, já que `/tmp` resolve para `/private/tmp` e `/var/folders/…` para `/private/var/folders/…`. Entradas que contêm `*` ou `?` são tratadas como globs e deixadas como estão; um caminho que não resolve é mantido como escrito.

## SandboxBindMount

| Campo       | Tipo                     | Descrição                                                                                             |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `hostPath` | `String` | Caminho absoluto no host |
| `guestPath` | `String` | Caminho dentro do sandbox (com o sandbox nativo isto é igual a `hostPath`; mantido por simetria entre adaptadores) |

## SandboxHandle

Retornado por `SandboxPort.launch`:

| Campo       | Tipo                   | Descrição                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String` | Identificador da sessão |
| `backend` | `SandboxBackend` | Qual backend está rodando |
| `state` | `SandboxState` | Estado de ciclo de vida |
| `error` | `Object?` | Definido quando `state` é `error` |
| `details` | `Map<String, Object?>` | Contabilidade interna do adaptador (diretório de trabalho, PID, caminho do perfil etc.) |

### SandboxState

| Estado       | Descrição                                 |
| ----------- | ------------------------------------------- |
| `created` | Especificação criada, mas a VM ainda não iniciou |
| `warm` | Em execução e pronta para executar comandos |
| `active` | Executando um comando no momento |
| `suspended` | Pausado / com checkpoint em disco para economizar RAM |
| `destroyed` | Desmontado; o handle não é mais válido |
| `error` | A inicialização falhou — veja `SandboxHandle.error` |

## Eventos do sandbox

| Tipo de evento  | Descrição                                                  |
| ----------- | ------------------------------------------------------------ |
| `stdout` | Saída padrão do sandbox |
| `stderr` | Erro padrão do sandbox |
| `exit` | O processo do sandbox saiu (carrega `exitCode`) |
| `starting` | O sandbox está iniciando |
| `ready` | O sandbox está pronto para aceitar chamadas exec |
| `killed` | Processo morto pelo host (OOM, timeout, parada manual) |
| `violation` | Uma política do sandbox foi violada (carrega um `SandboxViolation`) |

## SandboxViolation

| Campo                 | Tipo      | Descrição                                                                |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action` | `String` | O verbo negado (por exemplo, `file-read*`, `network-outbound`) |
| `target` | `String` | Caminho ou host que foi alvo da operação negada |
| `raw` | `String?` | Linha de log bruta, útil para depuração |
