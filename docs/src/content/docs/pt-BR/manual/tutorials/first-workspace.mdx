## O que você vai construir

Ao final deste tutorial, você terá:

- Um espaço de trabalho com o nome do seu projeto
- Um repositório Git registrado nele
- Cinco agentes semeados, um dos quais você configurou o suficiente para executar
- Um segundo espaço de trabalho, vazio, que comprova a fronteira de isolamento

O onboarding já criou um espaço de trabalho para você. Este tutorial cria um novo de propósito, para que você veja cada parte do processo.

Antes de começar, escolha um checkout do Git que atenda a estas três condições — a etapa de registro recusa qualquer outro caso:

- ele está dentro de uma árvore de trabalho do git
- ele tem um remoto `origin`
- esse remoto aponta para github.com, gitlab.com ou bitbucket.org

## Etapa 1: Criar um espaço de trabalho

1. Clique no chip do espaço de trabalho na barra de título
2. Escolha **Adicionar espaço de trabalho…**
3. Digite um nome que identifique o projeto, como "api-service" ou "frontend-v2"
4. Opcionalmente, escolha um logotipo
5. Clique em **Adicionar espaço de trabalho**

O Control Center muda para o novo espaço de trabalho e abre na caixa de entrada dele (`/workspaces/<id>/inbox`).

Por trás disso, o servidor publica um evento `WorkspaceCreated` e semeia o espaço de trabalho com:

- um **agente CEO**, cuja persona é coordenação e delegação
- quatro especialistas — `qa`, `architect`, `engineer` e `librarian` — cada um com suas próprias instruções e skills
- os modelos de pipeline integrados e suas linhas de gatilho

Todo espaço de trabalho que você criar recebe tudo isso, não apenas o primeiro.

Confirme: abra **Configurações → Espaço de trabalho → Agentes**. Há cinco agentes na lista, cada um com um anel de status vazio.

## Etapa 2: Registrar um repositório

1. Acesse **Configurações → Espaço de trabalho → Repositórios**
2. Clique em **Adicionar repositório**
3. Navegue até o seu checkout. A caixa de diálogo percorre as pastas da máquina que executa o `cc_server` — não do seu cliente — e permanece dentro das raízes que esse servidor expõe (por padrão, o diretório pessoal do usuário dele). Um checkout do git recebe um ícone de pasta distinto e uma caixa de seleção; uma pasta comum não recebe nenhum dos dois, então só checkouts podem ser selecionados.
4. Marque um ou mais checkouts e registre o lote. As seleções são mantidas enquanto você navega, então você pode reunir vários de uma vez e uma escolha ruim nunca descarta o restante.

O Control Center lê o remoto `origin` de cada checkout, resolve o proprietário e o repositório e cria a linha do repositório **dentro deste espaço de trabalho**. Não há uma segunda etapa para vinculá-lo: o registro é o que define o escopo dele.

Registrar o mesmo checkout em outro espaço de trabalho depois cria uma segunda linha de repositório independente, com id próprio. Entre espaços de trabalho, um checkout é identificado pelo caminho no sistema de arquivos, nunca pelo id.

Confirme: o repositório aparece na lista com seu `owner/repo` e o branch atual.

## Etapa 3: Tornar um agente executável

Os cinco agentes que este espaço de trabalho acabou de semear não têm adaptador nem modelo. O despacho os executa em **Control Center (built-in)** e, sem modelo definido, pede à Anthropic o modelo padrão dela — então eles só funcionam se você tiver conectado uma conta da Anthropic e, se tiver, em um modelo que você não escolheu. O onboarding da primeira execução grava a escolha dele em todos os agentes do primeiro espaço de trabalho, uma única vez; um espaço de trabalho criado depois começa com os cinco sem definição. Defina um agora.

1. Abra **Configurações → Espaço de trabalho → Agentes**
2. Selecione `engineer` na lista
3. Na aba **Configurações**, defina **Adaptador** como `Control Center (built-in)` e escolha um **Modelo** de um provedor que você conectou em Configurações → Servidor → Provedores de modelos
4. Pressione **Guardar alterações**

Confirme: reabra o agente e os dois campos mantêm suas escolhas.

Cada agente carrega o próprio adaptador e o próprio modelo, então repita isso para qualquer outro agente que você pretenda usar. [Criar e configurar um agente](/pt-BR/manual/guias/criar-agente/) cobre o restante do formulário.

## Etapa 4: Ver a fronteira de isolamento

Crie um segundo espaço de trabalho pelo chip da barra de título, exatamente como na etapa 1. Depois observe:

- **Configurações → Espaço de trabalho → Repositórios** está vazio. O repositório que você registrou há um minuto não está lá.
- **Configurações → Espaço de trabalho → Agentes** tem cinco agentes, mas são linhas diferentes — o adaptador que você definiu na etapa 3 não está lá.
- A lista de espaços, os tickets e a memória estão todos vazios.

Nada vazou, porque não há de onde vazar: as linhas de cada espaço de trabalho ficam no arquivo de banco de dados do próprio espaço de trabalho. Uma leitura entre espaços de trabalho não é uma consulta que é filtrada: é uma consulta que não tem onde rodar. Excluir um espaço de trabalho é desvincular um arquivo.

Volte pelo chip da barra de título ou abra **Gerenciar espaços de trabalho** para vê-los lado a lado.

Para o modelo completo, leia [Espaços de trabalho e isolamento](/pt-BR/manual/conceitos/espacos-de-trabalho/).

## Resumo

Você criou um espaço de trabalho, viu-o semear um CEO e quatro especialistas, registrou um repositório nele, deu a um agente um adaptador e um modelo e confirmou que um segundo espaço de trabalho não compartilha nada disso.
