Este guia mostra como trabalhar com o Control Center sem sair do GitHub: peça
uma revisão com IA na página da PR, faça uma pergunta ao bot em um comentário e
continue a conversa nas threads de revisão dela.

As respostas chegam pela faixa do GitHub do espaço de trabalho: o
[GitHub App](/pt-BR/manual/guias/github-app/) do seu próprio servidor, ou o App
compartilhado do Control Center pelo Connect. Nada novo é registrado, e nada
precisa estar acessível pela internet: o servidor descobre o que foi dito no
GitHub por polling, então um notebook atrás de um NAT se comporta exatamente
como uma implantação pública.

## Pré-requisitos

- O espaço de trabalho tem uma faixa do GitHub: o GitHub App do próprio servidor
  ou o Connect, com o app
  [instalado](/pt-BR/manual/guias/github-app/#instalar-onde-estão-os-seus-repositórios)
  na conta dona do repositório. Um app próprio precisa de **Pull requests** e
  **Issues** com leitura e gravação, que **Criar meu app do GitHub** já concede
- O repositório está vinculado a um espaço de trabalho no Control Center
- Você [entrou no GitHub](/pt-BR/manual/guias/integracao-github/) neste servidor
  e pode fazer push no repositório
- Sem URL de webhook, sem túnel, sem callback — não há nada a configurar do
  lado da rede

## Descubra o nome do seu bot

Mencione `@usectrl`, a conta dedicada do Control Center no GitHub. É o único acionamento: mencionar o login próprio do App não faz nada. A faixa do GitHub do seu espaço de trabalho continua processando a solicitação e publicando as respostas. Você não precisa das credenciais da conta `usectrl`.

## Peça uma revisão pelo GitHub

Duas formas, e ambas iniciam o mesmo pipeline `pr_review` predefinido que o
botão **Ask AI** inicia:

- **Adicione o rótulo `ai-review`** à PR. É o mais próximo que o GitHub oferece
  de atribuir o bot como revisor — contas de app não podem ocupar a vaga nativa
  de revisor solicitado. A sua conta reage à PR com 👀 e a revisão começa no
  Control Center; nenhum comentário é publicado
- **Comente `@usectrl review`** (ou apenas `@usectrl`) na conversa da PR. Um 👀
  aparece no seu comentário e, em seguida, uma resposta diz que a revisão
  começou (ou que uma já está em execução)

Os revisores trabalham no espaço de revisão da PR; leia e publique os achados
como em [Usar revisão com IA](/pt-BR/manual/guias/revisao-com-ia/). Publicar de
volta no GitHub continua sendo uma decisão sua no Control Center — iniciar uma
revisão pelo GitHub não publica nada no GitHub por conta própria.

O rótulo dispara uma vez por PR: adicioná-lo é o pedido, e ele não é rearmado ao
ser removido e adicionado de novo. Para executar uma revisão de novo — depois de
um push, digamos —, mencione o bot.

## Faça uma pergunta

Comente na conversa da PR:

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

O que acontece, em ordem:

1. Um 👀 aparece no seu comentário, vindo da sua própria conta, para você saber
   que o comentário foi visto
2. A pergunta é publicada no espaço de revisão da PR **como você** — a mesma
   atribuição de se você a tivesse digitado no Control Center
3. Um agente responde no espaço, e a resposta é publicada de volta na PR. Toda
   resposta começa com `**Control Center** (for @your-login):`

Uma pergunta em uma PR que ainda não tem revisão desperta o agente CEO do espaço
de trabalho; depois que uma revisão já rodou, o agente que falou por último
responde, então os acompanhamentos chegam a quem tem o contexto.

## Continue em uma thread de revisão

Responda dentro de uma thread de revisão em linha da qual o bot faz parte — um
comentário de diff que ele deixou, ou uma resposta que ele publicou naquela
thread. Não é preciso mencionar; a thread **é** o endereçamento:

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

Os vários turnos funcionam do mesmo jeito: cada resposta é outra pergunta na
mesma conversa, com o espaço de revisão como contexto, e a resposta volta na
thread.

Um acompanhamento na linha do tempo da conversa da PR é um novo comentário de
nível superior, então ainda precisa de uma menção com @.

## Com quem o bot fala

O servidor resolve o autor de um comentário, ou quem adicionou o rótulo
`ai-review`, antes de fazer qualquer coisa:

- **A conta do GitHub precisa ter entrado** neste servidor. A correspondência é
  feita pelo id numérico da conta no GitHub, nunca pelo login. Entre em
  **Configurações → Você → Perfil → Hospedagem de
  código**
- **A pessoa precisa ser um membro com um papel de escrita** (`member`, `admin`
  ou `owner`) no espaço de trabalho que vincula o repositório
- **A pessoa precisa poder fazer push** no repositório no GitHub. As respostas
  usam um token limitado ao acesso dessa pessoa, então quem só pode ler não
  recebe resposta

Qualquer outra pessoa é ignorada em silêncio: nada é publicado, e as palavras
dela nunca entram no espaço de trabalho. Comentários de bots, e as próprias
respostas do Control Center, nunca são tratados como perguntas.

### Dois servidores, uma PR

O 👀 também é a forma de os servidores combinarem quem responde. Ele é
adicionado com o próprio login do autor, e o GitHub informa ao servidor se essa
reação é nova. Se você tiver entrado em dois servidores do Control Center que
vinculam o repositório, o primeiro a reagir responde e o outro fica em
silêncio. O mesmo vale para o rótulo.

## O que esperar

| Item                 | Comportamento                                                             |
| -------------------- | ------------------------------------------------------------------------- |
| Confirmação de recebimento | 👀 da sua conta no comentário (ou na PR, no caso do rótulo), dentro de uma varredura |
| Respostas            | Publicadas no mesmo canal em que a pergunta foi feita, começando com `**Control Center** (for @your-login):`. O autor é o bot do app. No app compartilhado do Connect, uma resposta dentro de uma thread de revisão tem como autora a sua conta, a menos que o operador do Connect tenha listado esta instalação |
| Atribuição no espaço | A pergunta é sua; o agente roda em seu nome, sob as configurações de autonomia do espaço |
| Revisões             | Os achados chegam ao espaço de revisão; publicar no GitHub é manual       |

Uma varredura roda a cada minuto com um app próprio e verifica até 25 pull
requests; pelo Connect, ela roda a cada dois minutos e verifica até 10, porque
essas chamadas compartilham a cota do GitHub de cada membro. Um espaço de
trabalho com menos de 15% da cota do GitHub é pulado até se recuperar. A
latência é o preço por não precisar de nenhum acesso de rede de entrada. Nada
se perde enquanto o servidor está offline — um comentário que chega durante uma
parada é capturado na próxima varredura.

## Solução de problemas

**Nada acontece para um comentário que menciona o bot.**

- O app está **instalado** na conta que é dona do repo, e o repo está
  **vinculado** a um espaço de trabalho? Um repo não vinculado é ignorado antes
  de qualquer coisa ser registrada, então vinculá-lo depois ainda entrega
- Você entrou no GitHub neste servidor, é um membro com um papel de escrita e
  pode fazer push no repo? O servidor ignora qualquer outra pessoa sem
  responder
- Ainda nada? O log do servidor nomeia a varredura e a PR quando algo falha;
  procure por `pr_conversation:` (o mecanismo de polling) e
  `github_pr_conversation:` (a ponte)

**O rótulo não inicia uma revisão.**

Ele dispara uma vez por PR, e quem o adicionou passa pelas mesmas verificações
que o autor de um comentário. Se uma revisão já rodou, ou o rótulo foi
adicionado antes de o servidor sequer ver a PR (a primeira varredura registra o
acúmulo em silêncio, em vez de disparar tudo de uma vez), mencione o bot —
`@usectrl review` sempre inicia uma, a menos que já haja uma revisão em andamento.

**A resposta do bot nunca chegou ao GitHub.**

A resposta em si nunca se perde — ela está no espaço de revisão da PR, no
Control Center. Uma falha de publicação (GitHub fora do ar, permissões
alteradas) é registrada e a resposta não é repetida; pergunte de novo na thread
se for importante.
