Este guia mostra como criar e gerenciar tickets.

## Criar um ticket

### Pela interface

1. Clique em **Tickets** na barra lateral do espaço de trabalho.
2. Pressione **Novo ticket**.
3. Preencha:
   - **Título** — resumo breve. É o único campo obrigatório.
   - **Descrição** — markdown, com uma barra de formatação.
   - **Status** — **A fazer** (o padrão) ou **Backlog**. Os estados iniciados e
     os terminais são alcançados pelo ciclo de vida, não na criação.
   - **Prioridade** — nenhuma, urgente, alta, média ou baixa.
   - **Responsável** — você mesmo ou qualquer agente do espaço de trabalho.
   - **Projeto** — agrupamento opcional.
4. Pressione **Criar**, ou ative antes **Criar mais** para manter a caixa de
   diálogo aberta e inserir tickets rapidamente.

Não há seletor de provedor na caixa de diálogo. O ticket é criado no provedor
de tickets ativo do espaço de trabalho.

### A partir de um agente

Peça a um agente em um espaço:

> Crie um ticket para corrigir o problema de timeout de login em conexões
> lentas.

Ele chama a ferramenta MCP `create_ticket`. A prioridade nessa ferramenta é um
**inteiro**, não um nome:

```
create_ticket(
  workspace_id: "...",
  title: "Fix login timeout on slow connections",
  description: "...",
  priority: 2
)
```

| Valor | Prioridade |
| ----- | ---------- |
| `0`   | Nenhuma    |
| `1`   | Urgente    |
| `2`   | Alta       |
| `3`   | Média      |
| `4`   | Baixa      |

Apenas `workspace_id` e `title` são obrigatórios; `description`, `priority`,
`assignee` (um id de agente) e `team_id` são opcionais. A ferramenta é
classificada como uma escrita de sincronização com fornecedor e solicita sua
aprovação antes de ser executada.

## Atualizar o status de um ticket

Os tickets seguem este ciclo de vida:

```
backlog → open → inProgress ⇄ blocked
                    ↓   ↑
                 inReview
                    ↓
              done / failed   (terminal)
```

`done`, `failed` e `cancelled` são terminais. `cancelled` é alcançável a partir
de qualquer status não terminal. `done` e `failed` são alcançáveis a partir de
`inProgress` ou `inReview`; `open` também pode ir direto para `blocked`. O
seletor de status da interface lista todos os status, exceto `failed` — os
agentes marcam esse com `fail_ticket`.

Para alterá-lo, use qualquer um destes:

- a linha **Status** na barra de propriedades do ticket,
- o submenu **Status** no menu de contexto de um ticket na lista,
- o chip **Status** na barra flutuante depois de selecionar vários tickets.

:::note[O grafo do ciclo de vida vincula os agentes, não você]
Toda mudança de status feita pela interface é forçada, ignorando o grafo por
completo — você pode mover um ticket para qualquer status que o seletor liste,
inclusive reabrir um `done`, `failed` ou `cancelled`. O seletor não oferece
`failed` como destino. O diagrama acima governa os agentes e a automação: uma
transição ilegal tentada por uma ferramenta MCP ou um reconciliador é
registrada e ignorada, não aplicada.
:::

As mudanças de status emitem eventos de domínio (`TicketStatusChanged`,
`TicketCompleted` e outros) que podem disparar pipelines. Consulte
[Configurar gatilhos de pipeline](/pt-BR/manual/guias/gatilhos-de-pipeline/).

## Atribuir um ticket

1. Abra o ticket.
2. Na barra de propriedades, defina **Responsável** — você mesmo, outro membro
   do espaço de trabalho ou um agente.

:::caution[Atribuir não inicia nenhum trabalho]
A atribuição registra a responsabilidade e nada mais. Ela não cria nenhum
espaço, não muda nenhum status e não despacha nenhum agente — `TicketAssigned`
é um sinal de auditoria puro, sem nenhum despachante por trás. Para colocar um
agente para trabalhar, envie uma mensagem a ele em um espaço (consulte
[Conversar com um agente](/pt-BR/manual/guias/conversar-com-agente/)).

A única exceção: `TicketAssigned` é um tipo de evento ao qual você pode conectar
um gatilho de pipeline, de modo que um modelo seu pode reagir a uma atribuição.
:::

## Adicionar etiquetas

As etiquetas são aplicadas em massa a partir da lista de tickets, não de um
ticket individual — a barra de propriedades não tem nenhum controle de
etiquetas.

1. Passe o cursor sobre uma linha da lista de tickets e marque sua caixa de
   seleção. Marque quantas precisar; uma barra flutuante aparece assim que algo
   estiver selecionado.
2. Nessa barra, abra o chip **Etiquetas**.
3. Escolha uma etiqueta. Ela é adicionada a todos os tickets selecionados que
   ainda não a tenham; as etiquetas existentes nunca são apagadas. **Limpar
   etiquetas** remove todas elas. O seletor lista as etiquetas que já estão em
   algum ticket do espaço de trabalho. Os agentes podem adicionar um novo nome
   por meio de `update_ticket` ou `tickets.patch`.

## Vincular tickets

As relações ficam no cartão **Relações** do ticket, na barra de propriedades,
ou atrás de **Relacionar com** no menu de contexto da lista.

1. Abra o ticket e encontre o cartão **Relações**.
2. Pressione seu controle de adicionar e escolha a relação:

| Relação            | Significado                             |
| ------------------ | --------------------------------------- |
| **Subtarefa de…**  | O pai deste ticket é o outro            |
| **Pai de…**        | O outro ticket é filho deste            |
| **Bloqueado por…** | Este ticket está bloqueado pelo outro   |
| **Bloqueando…**    | Este ticket bloqueia o outro            |
| **Relacionado a…** | Simétrica, sem direção implícita        |
| **Duplicado de…**  | Este ticket duplica o outro             |

3. Escolha o ticket de destino.

**Duplicado por** aparece no cartão, mas não no seletor — é o inverso de
**Duplicado de** e é definido a partir do outro ticket. Cada relação listada é
clicável para abrir o ticket vinculado e removível ao passar o cursor.

As relações de pai e de subtarefa são armazenadas no próprio ticket, e não como
linhas de vínculo, então excluir um pai é propagado em cascata para os filhos
(veja abaixo), enquanto os vínculos de bloqueio e de relação não são.

## Adicionar colaboradores

Os colaboradores são uma lista no ticket — quem está envolvido e com qual
papel.

1. Abra o ticket.
2. Pressione o controle de pessoa com sinal de mais no cartão **Adicionar
   colaborador**.
3. Escolha um agente.

Os três papéis são **assignee**, **collaborator** (o padrão) e **reviewer**. O
seletor da interface lista apenas agentes do espaço de trabalho e sempre grava
o papel padrão; pessoas podem aparecer como linhas, mas não são oferecidas
nesse menu. A ferramenta MCP `add_ticket_collaborator` aceita um `role`.

Adicionar um colaborador grava uma linha e não publica nenhum evento de
domínio; não concede acesso a nenhum espaço. Para colocar um agente em uma
conversa, adicione-o como participante no cabeçalho do espaço — consulte
[Espaços](/pt-BR/manual/guias/espacos/).

## Excluir um ticket

Use **Excluir ticket** na parte inferior da barra de propriedades, no menu de
contexto ou na ação de exclusão da barra flutuante depois de selecionar vários
tickets.

:::caution[A exclusão é apenas local]
Um ticket que veio de um rastreador externo não é excluído lá — nenhum provedor
oferece isso —, então ele pode reaparecer na próxima sincronização. Excluir
também é propagado em cascata: os colaboradores do ticket e quaisquer tickets
filhos vão junto.
:::
