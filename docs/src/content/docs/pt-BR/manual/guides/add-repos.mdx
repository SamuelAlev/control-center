Este guia mostra como registrar um checkout do Git em um espaço de trabalho, reindexá-lo e removê-lo de novo. Adicionar um repositório a partir das pastas do servidor exige o proprietário do servidor; removê-lo exige um administrador do espaço de trabalho.

Os repos têm **escopo de espaço de trabalho**. Não existe um registro global nem uma etapa de vinculação: adicionar um repo e colocá-lo em um espaço de trabalho são o mesmo ato. O mesmo checkout registrado em dois espaços de trabalho se torna duas linhas independentes com dois ids diferentes — entre espaços de trabalho, a identidade de um repo é o caminho no sistema de arquivos, nunca o id dele.

## Antes de começar

Uma pasta só pode ser registrada se todas estas três condições forem verdadeiras:

1. Ela está dentro de uma **árvore de trabalho do git**.
2. Essa árvore de trabalho tem um **remote `origin`**.
3. O remote `origin` aponta para um **forge compatível**: github.com, gitlab.com ou bitbucket.org.

Qualquer outro caso é recusado no momento do registro com uma mensagem explícita: "Folder is not inside a git work tree.", "No `origin` remote configured for this repository." ou "The `origin` remote is not hosted on a supported forge (github.com, gitlab.com, bitbucket.org).". Não existe um modo apenas local.

O forge é lido do remote e armazenado no repo — você nunca o escolhe. Um espaço de trabalho pode conter repos dos três ao mesmo tempo, e cada um é acessado pela sua própria API com a sua própria credencial. Os namespaces aninhados do GitLab são preservados, de modo que `gitlab.com/group/subgroup/project` é registrado como owner `group/subgroup`, name `project`.

A pasta também precisa estar na máquina que hospeda o `cc_server`, dentro de um dos diretórios `--repo-roots` desse servidor. Essa lista de permissões usa por padrão o diretório home do usuário do servidor, e a navegação acima de uma raiz é recusada. A navegação pelas pastas do servidor é oferecida somente ao [proprietário do servidor](/pt-BR/manual/conceitos/autorizacao/#o-proprietário-do-servidor), porque lista os arquivos próprios da máquina. Qualquer outra pessoa vê "O proprietário do servidor adiciona repositórios a partir das pastas do servidor." onde ficaria o botão **Adicionar repositório**, e um link para um repositório que nenhum dos seus espaços de trabalho tem diz que ele não está vinculado em nenhum dos seus espaços de trabalho e para pedir ao proprietário do servidor que o adicione.

Onde o checkout pode ficar depende de quem o vincula:

- **Dentro do armazenamento próprio do espaço de trabalho** no servidor: qualquer administrador do espaço de trabalho.
- **Em qualquer outro lugar do disco do servidor**: somente o [proprietário do servidor](/pt-BR/manual/conceitos/autorizacao/#o-proprietário-do-servidor), porque só ele pode apontar o servidor para os arquivos próprios da máquina. Qualquer outra pessoa vê "Somente o proprietário do servidor pode vincular uma pasta fora do armazenamento deste espaço de trabalho."
- **A pasta de dados do servidor**, ou qualquer coisa dentro dela: nunca.

O `origin` do checkout precisa ser o repositório que você está vinculando. Uma pasta cujo `origin` nomeia outro repositório é recusada com "A origem dessa pasta é outro repositório."

### Pastas que o servidor ainda não usa

Um repositório cuja pasta está fora do armazenamento do espaço de trabalho e que o proprietário do servidor não vinculou, como um em um espaço de trabalho importado, mostra "Esta pasta está fora do armazenamento do espaço de trabalho. Confirme que este servidor pode usá-la." abaixo da linha dele, até que o proprietário do servidor a confirme. Qualquer outra pessoa vê "Esta pasta está fora do armazenamento do espaço de trabalho. Somente o proprietário do servidor pode confirmá-la." no lugar.

O proprietário confirma uma vez: **Confirmar** na linha, ou **Confirmar todos** no aviso acima da lista quando vários repositórios estão esperando. Cada um é verificado de novo como proprietário, com as mesmas verificações da vinculação. Até lá, ele continua na lista, mas não é aberto, provisionado nem indexado: nenhum editor, terminal, ambiente ou checkout de espaço o usa, e o grafo de código o ignora. Adicionar a mesma pasta de novo como proprietário do servidor faz o mesmo que confirmá-la, e mantém o id do repositório.

Um checkout que um link simbólico moveu para outro lugar é tratado do mesmo modo: continua listado e sem uso até ser vinculado de novo por alguém autorizado a vincular a pasta para a qual ele agora aponta.

Você também precisa estar conectado ao forge do repositório, e a sua própria conta precisa conseguir ver o repositório.

## Registrar um checkout

Você precisa ser o proprietário do servidor para estas etapas.

1. Abra **Configurações → Espaço de trabalho → Repositórios** (`/workspaces/<id>/settings/workspace/repositories`).
2. Clique em **Adicionar repositório**.

A caixa de diálogo é um navegador navegável pelo sistema de arquivos do **servidor**, não pelo seu. É o mesmo fluxo no desktop, na web e no celular, porque um seletor de pastas nativo escolheria uma pasta na máquina errada.

3. Navegue pelas raízes configuradas do servidor. As pastas que são checkouts do git são sinalizadas.
4. Marque quantas quiser. A seleção é mantida conforme você navega, então você pode reunir checkouts de várias pastas.
5. Registre-os em um único lote.

Uma escolha que falha nunca descarta o restante do lote — você recebe os ids que foram criados e um erro por caminho para cada uma que foi recusada. Registrar novamente um caminho que já existe neste espaço de trabalho retorna o repo existente em vez de criar um duplicado.

Cada repo registrado aparece na lista com o seu `owner/name`, um selo com o nome do seu forge e o seu caminho no servidor. Os repos do GitHub também mostram o avatar do owner; os outros forges não têm uma URL previsível de avatar do owner, então recorrem às iniciais.

O selo do forge importa em um espaço de trabalho misto: dois repos podem se chamar `acme/web` em forges diferentes, e eles se comportam de maneira diferente — o que uma revisão pode fazer e para onde um link leva.

## O que acontece em seguida

O registro dispara um evento `RepoAdded` com escopo neste espaço de trabalho, que inicia o pipeline `index_code` para esse checkout. É isso que popula o grafo de código, para que a pesquisa e a análise de impacto tenham com o que responder.

Só são indexados os arquivos cuja linguagem tem uma gramática incluída (Dart, JavaScript, TypeScript, TSX, PHP, Python, Rust, Zig, C, C++, Go, Java, Ruby, C#, Swift, Kotlin, R, Assembly, MATLAB e Ada). Consulte [Pesquisar código com o grafo de código](/pt-BR/manual/guias/pesquisar-codigo/).

## Reindexar um repo

Cada linha traz um botão **Indexar código**. Clique nele para executar o indexador de novo para esse checkout; enquanto ele é executado, o botão se transforma em um indicador de progresso que mostra os arquivos concluídos em relação ao total, com um controle de cancelamento. Quando termina, ele se firma em uma marca de confirmação com a contagem de símbolos, ou em um aviso se a execução falhou.

## Reordenar repos

Arraste a alça de uma linha. A ordem que você define é a ordem que todas as listas de repos do app retornam.

## Corrigir o link do GitHub

O ícone de link em uma linha abre um editor para o owner e o nome do repositório do repo no GitHub.

Você raramente precisa dele. Um vínculo está preso ao id permanente do repositório na forja, então um renomeio ou uma transferência é seguido automaticamente.

- Renomear um repositório no Control Center muda apenas o nome de exibição dele.
- Mudar para qual repositório da forja um vínculo aponta exige um administrador do espaço de trabalho, e é verificado na forja com o login próprio do administrador, da mesma forma que a vinculação.
- Um repositório vinculado não pode ser transformado em um somente local.

Se o caminho depois passar a indicar um repositório **diferente** (o original foi excluído e criado de novo, ou movido e substituído por outro), o Control Center deixa de enviar qualquer coisa a ele: nenhum token, push, comentário ou requisição. Isso também vale para as ações da própria pessoa: uma revisão, um merge ou um comentário seu nesse repositório é recusado, no GitHub, no GitLab e no Bitbucket igualmente. A linha e as pull requests do repositório mostram "_repo_ agora aponta para outro repositório" até que um administrador do espaço de trabalho clique em **Vincular novamente**.

## Quem pode abrir o código

Uma concessão de repositório sozinha não abre os arquivos de um repositório. Para abrir arquivos, diffs, busca ou um terminal nele, um integrante precisa da concessão do Control Center, e a própria conta dele no forge precisa conseguir ler o repositório. Administradores do espaço de trabalho não são isentos; o proprietário do servidor é. Veja [Código segue o forge](/pt-BR/manual/conceitos/autorizacao/#o-código-segue-a-forja).

Quando você concede um repositório a alguém cuja conta no forge não consegue lê-lo, a concessão é salva e você vê um aviso, como "Salvo. A conta deles em GitHub ainda não consegue ler este repositório, então ele continua oculto para eles."

A mesma regra decide quem pode abrir um espaço. Um espaço abre somente para integrantes que podem abrir o código de todos os repositórios que ele usa, e fica oculto para todos os demais, junto com seus resultados de busca, logs de execução, tarefas, atividade e notificações. Um espaço sem repositórios fica aberto a todos os integrantes. Veja [Espaços seguem os seus repositórios](/pt-BR/manual/conceitos/autorizacao/#espaços-seguem-seus-repositórios).

## Remover um repo

1. Abra **Configurações → Espaço de trabalho → Repositórios**.
2. Clique no ícone de lixeira na linha.
3. Confirme "Remover repositório do espaço de trabalho?"

A caixa de diálogo explica o que ela faz: "_name_ será removido deste espaço de trabalho. Os arquivos locais no disco não são afetados."

Remover um repositório exige um administrador do espaço de trabalho. A remoção também esquece as credenciais da forja guardadas para esse repositório, como um token de automação do GitLab ou do Bitbucket.

A remoção exclui a linha do repo deste espaço de trabalho e elimina em cascata as suas linhas do grafo de código — símbolos, arestas, arquivos e checkpoints de índice —, além de todas as concessões de repo por membro sobre ele, os seus vínculos entre espaço e repo e os seus registros de checkout isolado. O mesmo checkout registrado em outro espaço de trabalho é uma linha independente e não é afetado. Os worktrees em disco para os quais esses registros apontavam não são destruídos pela exclusão.

## Solução de problemas

### Tenho uma concessão, mas o repositório diz que minha conta não pode lê-lo

Sua própria conta no forge não consegue ler o repositório, então o Control Center mantém o código dele longe de você, mesmo que o espaço de trabalho o tenha concedido. Entre no forge em **Configurações → Você → Perfil → Hospedagem de código**, se ainda não tiver feito isso, ou peça acesso ao repositório a quem o administra no forge. O repositório abre assim que a sua conta no forge puder lê-lo.

### "Esta pasta está fora do armazenamento do espaço de trabalho"

A pasta do repositório está fora do armazenamento do espaço de trabalho e o proprietário do servidor não a vinculou, ou um link simbólico agora aponta para outro lugar. Ele continua listado, mas sem uso, até que o proprietário do servidor o confirme ou adicione a pasta de novo. Se você não for o proprietário, peça a ele. Se for, clique em **Confirmar** na linha ou em **Confirmar todos** acima da lista; veja [Pastas que o servidor ainda não usa](#pastas-que-o-servidor-ainda-não-usa).

### "Não existe mais nada neste caminho do servidor"

A pasta foi movida ou excluída na máquina do servidor. Recoloque-a, ou peça a um administrador do espaço de trabalho que remova o repositório com **Remover** no aviso e o adicione de novo a partir da pasta atual.

### "Esta pasta não pode ser usada como repositório"

A pasta armazenada é a própria pasta de dados do servidor, algo dentro dela, ou a própria pasta de armazenamento do espaço de trabalho. Nenhuma delas pode ser um repositório. Um administrador do espaço de trabalho a remove com **Remover** no aviso e depois adiciona o repositório de novo a partir da pasta real do checkout.

### "Não foi possível confirmar seu acesso na forja"

O Control Center não conseguiu alcançar a forja para verificar que a sua conta pode ler o repositório, então recusou em vez de presumir. Tente novamente em instantes.
