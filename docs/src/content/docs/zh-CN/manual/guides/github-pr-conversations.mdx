本指南介绍如何在不离开 GitHub 的情况下使用 Control Center：在 PR 页面上请求一次
AI 审查，在评论中向机器人提问，并在它的审查线程中把对话继续下去。

回复通过工作区的 GitHub 通道发出：即服务器自己的 [GitHub App](/zh-CN/手册/操作指南/github-app/)，或通过 Connect 使用的 Control Center 共享 App。无需注册任何新东西，也无需任何东西可从互联网访问：服务器通过轮询发现 GitHub 上说了什么，因此位于 NAT 之后的笔记本电脑与公网部署的表现完全一致。

## 前提条件

- 工作区拥有一条 GitHub 通道：服务器自己的 GitHub App 或 Connect，并且该应用已[安装](/zh-CN/手册/操作指南/github-app/#在你的仓库所在处安装它)在拥有该仓库的账户上。自有应用需要 **Pull requests** 与 **Issues** 的读写权限，而**创建我的 GitHub 应用**已经会授予它们
- 仓库已关联到 Control Center 中的一个工作区
- 你已在本服务器上[登录 GitHub](/zh-CN/手册/操作指南/github-集成/)，并且你对该仓库有推送权限
- 不需要 webhook URL，不需要隧道，不需要回调——网络侧没有任何要配置的东西

## 找到机器人的名称

提及 `@usectrl`，这是 Control Center 专用的 GitHub 账号。它是默认触发方式；你的工作区的 GitHub 通道仍会处理请求并发布回复。你不需要 `usectrl` 账号的凭证。

App 自身的登录名 `<appslug>[bot]` 及其短形式 `@appslug` 也能使用。如需查找自有应用的这个可选别名：

1. 前往 **设置 → 服务器 → 单点登录**，向下滚动到 **提供商应用** 卡片
2. 展开 **GitHub** 区块并点击 **测试**
3. 填充完成后复制 **机器人登录名**。如果它仍显示空白提示，那么登录名始终是
   `<appslug>[bot]`——输入它，或者使用短名 `@appslug`

GitHub 的 `@` 自动补全不显示 App 账号，因此 App 别名需要手动输入或复制。专用用户 `@usectrl` 是默认调用方式；`@myapp` 和 `@myapp[bot]` 仍作为 App 别名被接受。

:::note[选择一个有辨识度的应用名称]
短名是按文本匹配的。如果某个 GitHub 人类用户恰好与你的应用共用同一个 slug，
那么用短名提及该用户也会触达机器人。完整的 `@myapp[bot]` 形式则始终没有歧义。
:::

## 从 GitHub 请求审查

有两种方式，二者都会启动与 **询问 AI** 按钮相同的那条预置 `pr_review` 流水线：

- **给 PR 加上 `ai-review` 标签**。这是 GitHub 最接近把机器人指派为审查者的做法
  ——应用账户无法占据原生的「已请求的审查者」位置。你的账户会在该 PR 上添加 👀，
  审查直接在 Control Center 中启动；不会发布任何评论
- **在 PR 对话中评论 `@usectrl review`**（或者只写 `@usectrl`）。你的评论上会出现
  👀，随后回复会说明审查已经启动（或告知已有一个正在运行）

审查者在 PR 的审查空间中工作；按照[使用 AI 审查](/zh-CN/手册/操作指南/ai-审查/)
中的说明查看并发布发现项。发布回 GitHub 始终是你在 Control Center 中做出的
决定——从 GitHub 启动审查本身不会向 GitHub 发布任何内容。

标签在每个 PR 上只触发一次：添加它就是发起请求，移除后再添加也不会重新触发。
要再次运行审查——比如说在一次 push 之后——请 @提及机器人。

## 提问

在 PR 对话中评论：

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

发生的事情依次如下：

1. 你的评论上会出现 👀，让你知道评论已被看到
2. 问题会**以你的名义**发布到该 PR 的审查空间中——归属方式与你直接在
   Control Center 中输入完全一致
3. 智能体在空间中作答，答案会回到 PR 上作为一条评论发布。每条回复都以
   `**Control Center** (for @your-login):` 开头

在没有审查的 PR 上提问会唤醒工作区的 CEO 智能体；一旦审查运行过，就由最后发言的
那个智能体作答，因此追问会落到掌握上下文的那一个那里。

## 在审查线程中追问

在机器人参与的某条行内审查线程中回复——无论是它留下的 diff 评论，还是它在该
线程中发布的回答。无需 @提及；线程**本身**就是寻址方式：

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

多轮对话同理：每次回复都是同一对话中的又一个问题，并以该审查空间为上下文，答案
仍会回到该线程中。

在 PR 对话时间线上追问属于一条新的顶层评论，因此仍然需要 @提及。

## 机器人会与谁对话

服务器会先解析一条评论的作者（或添加 `ai-review` 标签的人），然后才会采取任何行动：

- **该 GitHub 账户必须已在本服务器上登录。** 匹配依据是 GitHub 的数字账户 ID，绝不是登录名。请在 **设置 → 工作区 → 个人资料与身份 → 代码托管** 中登录
- **他们必须是在关联该仓库的工作区中拥有写入角色的成员**（`member`、`admin` 或
  `owner`）
- **他们必须在 GitHub 上对该仓库拥有推送权限。** 回复使用的令牌仅限于该人的访问权限，因此只能读取的人不会得到回复

其他人都会被静默忽略：什么也不会发布，他们的话也绝不会进入工作区。来自机器人的评论，以及 Control Center 自己的回复，绝不会被当作问题处理。

### 两台服务器，一个 PR

👀 同时也是服务器们对“由谁回答”达成一致的方式。它使用作者自己的登录添加，而 GitHub 会告诉服务器这个表情回应是否是新的。如果你同时在两台关联了该仓库的 Control Center 服务器上登录，那么最先做出回应的那台会作答，另一台保持沉默。标签同样如此。

## 预期表现

| 事项                     | 行为                                                                     |
| ---------------------- | ------------------------------------------------------------------------ |
| 确认回应     | 在一轮扫描内，评论上（或对于标签，在 PR 上）出现你账户添加的 👀 |
| 回答             | 落在此前提问所在的通道中，以 `**Control Center** (for @your-login):` 开头。在自有应用上，作者是该应用的机器人；通过 Connect 时，作者是你的账户，并通过共享 App 行事 |
| 空间内的归属 | 问题算在你名下；智能体代表你运行，并遵循该空间的自主程度设置 |
| 审查             | 发现项落在审查空间中；发布到 GitHub 需要手动进行         |

自有应用上，扫描每分钟运行一次，最多检查 25 个 pull request；通过 Connect 时每两分钟运行一次，最多检查 10 个，因为这些调用共享每位成员自己的 GitHub 配额。GitHub 配额低于 15% 的工作区会被跳过，直到恢复。延迟是换取完全无需入站网络访问的代价。服务器离线期间也不会丢失任何内容——停机期间到达的评论会在下一轮扫描中被补上。

## 故障排查

**@提及机器人的评论没有任何反应。**

- 该 App 是否已**安装**在拥有该仓库的账户上，仓库是否已**关联**到某个工作区？
  未关联的仓库会在记录任何内容之前被跳过，所以之后再关联它，内容仍然会送达
- 你是否已在本服务器上登录 GitHub，是否为拥有写入角色的成员，并且能推送到该仓库？服务器会忽略其他人，且不作回复
- 如果使用的是 Control Center 的共享 App，该组织的安装是否已为本服务器授权？参见[为组织授权此服务器](/zh-CN/手册/操作指南/github-app/#为组织授权此服务器)
- 仍然没有任何反应？当出错时，服务器日志会指明是哪一轮扫描和哪个 PR；请查找
  `pr_conversation:`（轮询器）和 `github_pr_conversation:`（桥接器）

**标签没有启动审查。**

它在每个 PR 上只触发一次，添加它的人同样需要通过评论作者所要经过的检查。如果审查已经运行过，或者标签是在服务器首次看到该 PR
之前就加上的（第一轮扫描会静默记录积压项，而不是一次性全部触发），请改为
@提及机器人——除非已有审查正在进行，否则 `@usectrl review` 总会启动一次。

**机器人的回答始终没有出现在 GitHub 上。**

回答本身绝不会丢失——它就在 Control Center 中该 PR 的审查空间里。发布失败
（GitHub 故障、权限变更）会被记录，并且不会重试该回复；如果确实重要，就在
线程中再问一次。
