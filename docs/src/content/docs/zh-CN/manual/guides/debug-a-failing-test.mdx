本指南介绍如何让智能体在打印语句解释不了的失败上使用调试器。

`debug` 工具驱动一次真正的 Debug Adapter Protocol 会话。一个被暂停的栈帧能一次回答关于那一刻的所有问题——每个局部变量、每个调用者，以及在该栈帧自身作用域里求值的表达式——而打印语句只能回答你在运行之前就想到要问的那个问题。

## 开始之前

该工具会一直留在工具面上，这样智能体可以询问为什么什么都不可用，而不是靠猜。只有当下面**两者**同时成立时，适配器才能真正启动：

- 检出目录中存在项目标记，并且
- 适配器的二进制文件可被解析到。

让智能体检查一下：

```
debug(op: "adapters")
```

它会回答自己发现了什么，或者解释适配器需要同时满足这两半。

| 语言            | 适配器                       | 标记                                            | 安装                               |
| --------------- | ---------------------------- | ----------------------------------------------- | ---------------------------------- |
| Dart / Flutter  | `dart debug_adapter`         | `pubspec.yaml`                                   | 随 SDK 提供——无需额外操作          |
| Python          | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` | `pip install debugpy`              |
| Rust / C / C++  | `lldb-dap`                   | `Cargo.toml`, `CMakeLists.txt`                   | 随 LLVM 提供                       |
| Go              | `dlv dap`                    | `go.mod`                                         | `go install github.com/go-delve/delve/cmd/dlv@latest` |

:::note[Python 会选用项目自己的解释器]
查找 `debugpy` 时，会先看 `.venv/bin` 或 `venv/bin`，然后才轮到 `$PATH`。`$PATH` 里的 python 是另一个环境，从错误的环境附加时，失败的样子读起来像代码坏了，而不是像用错了解释器。
:::

## 先设置断点，再启动

顺序很重要，工具也会强制这个顺序：断点可以在会话存在**之前**设置，因为协议要求的就是这个次序。

这样对智能体说：

> `bin/main.dart` 里的 `compute` 函数返回了错误的值。在给 `product` 赋值的那一行设置一个断点，在调试器下启动它，然后告诉我 `a` 和 `b` 实际上是什么。

它大致会执行：

```
debug(op: "breakpoints", file: "bin/main.dart", lines: [7])
debug(op: "launch", program: "bin/main.dart")
```

启动会报告它停在了哪里：

```
Launched bin/main.dart on dart (session dart-1). Stopped: breakpoint. Use `stack` to see where.
```

:::caution[如果它报告的却是程序已退出]
断点没有绑定。空白行、注释行，或者没有被编译进构建的行都无法承载断点。对一次存活的会话调用 `breakpoints`，会报告你设置的断点里实际落位了多少个。
:::

## 读取栈帧

```
debug(op: "stack")
→ #1 compute (bin/main.dart:7:3)
  #2 main (bin/main.dart:2:18)
```

然后走进这个栈帧：

```
debug(op: "scopes", frame_id: 1)
→ Locals (reference 12)

debug(op: "variables", reference: 12)
→ a (int) = 6
  b (int) = 7
  product (int) = 42
```

带有子项的对象会报告 `[expand: reference N]`——但仅当它背后确实有东西时才报告，因此智能体用不上的展开永远不会被提供。

对于任何不是以局部变量形式可见的内容：

```
debug(op: "evaluate", expression: "config.timeout.inSeconds", frame_id: 1)
```

## 单步执行

| 你想要什么         | 操作        |
| ------------------ | ----------- |
| 运行到下一个停止点 | `continue`  |
| 下一行，同一栈帧   | `step_over` |
| 进入调用           | `step_in`   |
| 返回到调用者       | `step_out`  |
| 停止正在运行的程序 | `pause`     |

## 附加到已在运行的进程

针对的是一次卡死的进程，而不是你正在启动的那个：

```
debug(op: "attach", port: 5858)
```

## 结束

```
debug(op: "terminate")
```

务必结束会话。调试适配器拥有一个**被暂停的进程**，它占着那个进程所占有的一切——一个端口、一把锁、一个数据库连接。

:::note[它无法脱离你的掌控]
每个会话都有一个无法延长的硬性 TTL，每个对话恰好有一个会话，而服务器停止时一切都会被拆除。第二次 `launch` 会被拒绝，而不是替换掉第一个：一个没结束第一个就启动第二个的智能体，几乎可以肯定已经跟丢了第一个。
:::

## 有界输出

对深层对象图做一次 `variables` 展开，本质上就是无界的——一个 Flutter 组件就能触达整棵元素树。每个作用域的子项上限是 50，值的上限是 400 个字符，栈帧的上限是 30。一个塞满上下文窗口的工具结果，就是一个会终结它本来在帮忙的那次运行的工具。
