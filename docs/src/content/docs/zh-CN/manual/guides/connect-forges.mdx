Control Center 可与三种代码托管服务配合使用，应用内统称**代码托管平台**：**GitHub**、**GitLab** 和 **Bitbucket Cloud**。它们中没有哪一种是默认选项。连接其中一个，一切即可正常工作；连接多个，单个工作区也能同时容纳来自所有这些平台的仓库。

代码托管平台是每个**仓库**的属性，在你注册仓库时从其 `origin` 远端读取。你从不需要自行选择，也不存在会设置错的按工作区配置。

## 连接代码托管平台

1. 打开**设置 → 你 → 个人资料**（`/settings/you/profile`）。
2. 找到**代码托管**卡片。所有受支持的代码托管平台都会列出，无论是否已连接。
3. 在 **GitHub** 上点击**登录 GitHub**。在 **GitLab** 或 **Bitbucket** 上点击**添加令牌**并粘贴一个。

**GitHub 仅支持登录。** 登录通过服务器自己的 GitHub App 或 Control Center Connect 完成，具体取决于服务器所有者设置了哪一个，或取决于工作区管理员在**设置 → 工作区 → 集成**中为该工作区选择的应用（参见[设置 GitHub 集成](/zh-CN/手册/操作指南/github-集成/)）；没有可粘贴的 GitHub 令牌。GitLab 和 Bitbucket 仍然使用个人令牌。

无论哪种方式，这份凭据都是**你的，并且存放在服务器上**，以你的用户 id 为键：你输入令牌的那台机器不会保存任何令牌，你登录的每台设备都使用同一份凭据，其他成员也读不到它。它会在**下一次请求**时生效——无需重启任何东西，而断开连接会立即停止发送它。

卡片会说明你的账户在哪里使用。GitLab 和 Bitbucket 令牌在服务器上的**每个工作区**中都属于你，因此只需粘贴一次。你的 GitHub 登录也是如此，除非某个工作区有自己的登录应用：该工作区会保留自己的 GitHub 登录，卡片会点明它。

每一行都会显示**你的**凭据状态。只有你自己的凭据会代表你作答，不存在其他东西替你顶上：

| 行中显示                                                     | 含义                                                                                                                         |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `已以 octocat 身份登录`                                       | 正在使用你自己的凭据                                                        |
| `未连接`                                                     | 你没有此代码托管平台的凭据                                                                                                   |
| `你以 octocat 身份登录的 GitHub 已失效。请重新登录。`         | 你的登录在代码托管平台上已过期或被撤销                                                                                       |
| `已暂停：此工作区的登录服务已更改`                           | 此工作区已切换到另一个登录服务。你的登录会保留，切换回去后即可再次使用，因此这里没有登录按钮                                  |
| `暂时无法连接 GitHub，正在重试。`                            | 暂时性故障。Control Center 会持续重试，你无需任何操作                                                                        |
| 一句解释为何无法登录的文字                                   | 例如 `此工作区尚未设置 GitHub 登录。` 或 `此工作区的登录服务更改了身份，需要管理员确认。` 管理员会看到一个按钮，直接跳转到修复该问题的设置 |

### 各代码托管平台需要什么令牌

| 代码托管平台  | 令牌                                                                                                    | 创建位置                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **GitLab**    | 具有 `api` 范围的个人访问令牌                                                                            | gitlab.com → User settings → Access tokens                |
| **Bitbucket** | Atlassian API 令牌，外加你的账户邮箱                                                                      | id.atlassian.com → Security → API tokens                  |

Bitbucket 以你的**账户邮箱作为用户名**、API 令牌作为密码进行验证，因此 Bitbucket 对话框会同时要求这两项。Bitbucket 仓库、项目或工作区的**访问令牌**不属于任何个人，因此此对话框会拒绝它：它是[自动化令牌](#添加自动化令牌)，应改在那里添加。GitLab **项目**或**群组访问令牌**同理：保存前 GitLab 会询问该令牌属于谁，机器人的令牌在此会被拒绝。

令牌从不绑定到某一个工作区：你为每个代码托管平台持有一个，服务器上的每个工作区都会使用它。**断开连接**会将其为所有工作区移除。

### 后台工作

没有人在背后操作的工作（智能体运行、流水线、PR 轮询）同样需要凭据，而每个代码托管平台的处理方式各不相同：

- **GitHub** —— 每次只针对一个仓库的令牌，由服务器的 GitHub App 或通过 Connect 签发，并限定在某位负责任的成员在那里能做的事之内。它绝不是把某个人的登录整体交出去，也没有任何环境变量或粘贴的令牌可以替代它。参见[设置 GitHub 集成](/zh-CN/手册/操作指南/github-集成/#你的凭据代表谁)
- **GitLab** 和 **Bitbucket** —— 仅使用该仓库的**自动化令牌**：工作区管理员为该仓库，或为工作区中该代码托管平台上的每个仓库添加的机器人访问令牌。仓库自己的令牌优先于工作区的令牌。PR 轮询、AI 审查评论，以及没有人请求的推送和合并请求，都会使用它，因此在代码托管平台上它们显示为该机器人，而绝不会显示为某位成员。没有任何成员的个人令牌可以替代它，也不存在服务器范围或环境变量令牌。没有自动化令牌时，该仓库的后台工作会暂停，仓库访问通知会对此予以说明。

成员请求的工作（评论、审查，或为其打开的智能体合并请求）仍然使用该成员自己的令牌。

## 添加自动化令牌

只有工作区管理员能看到或更改自动化令牌。保存时会与代码托管平台逐一核对每个令牌：以人的身份行事的令牌会被拒绝（GitLab 个人访问令牌、Atlassian API 令牌，或任何以某人账户登录的 Bitbucket 令牌），无法读取其所对应仓库的令牌也会被拒绝。

- **针对单个仓库：** 打开**设置 → 工作区 → 仓库**。**自动化令牌**卡片会列出每个 GitLab 和 Bitbucket 仓库，以及在那里行动的机器人、**使用工作区的令牌**，或**没有令牌。此处的自动化已暂停。**在该仓库的行上点击**添加令牌**。
- **针对某个代码托管平台的每个仓库：** 打开**设置 → 工作区 → 集成**，找到**自动化令牌**卡片，并在 GitLab 或 Bitbucket 行上点击**添加令牌**。保存后，令牌无法读取的仓库会被点名，并保持暂停。

当后台工作已经暂停时，管理员还会在仓库访问通知上直接看到**添加令牌**。**更新令牌**会替换令牌；垃圾桶按钮会将其移除，任何因此没有令牌的仓库都会暂停。若代码托管平台之后拒绝了已保存的令牌（已撤销或已过期），该行会说明此事，而它所涵盖的仓库会暂停，直到你替换它为止。

| 代码托管平台  | 自动化令牌                                                                                               | 创建位置                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **GitLab**    | 一个**项目**或**群组访问令牌**，具有 `read_api` 与 `read_repository`；如需评论、合并请求和推送，请添加 `api` 与 `write_repository` | 项目或群组 → Settings → Access tokens                          |
| **Bitbucket** | 一个**仓库**、**项目**或**工作区访问令牌**，具有仓库读取权限，并具有用于评论和 pull request 的 pull request 写入权限（推送则需要仓库写入权限） | 仓库、项目或工作区 → Settings → Access tokens                  |

GitLab 会以令牌的机器人用户显示这些工作；Bitbucket 则以访问令牌的名称显示。

### Bitbucket：访问令牌还是 API 令牌

Bitbucket 有两种令牌，Control Center 会将它们分开：

- **API 令牌**（id.atlassian.com）属于你的 Atlassian 账户，并与你的邮箱一起使用。它是**你的**凭据，放在**设置 → 你 → 个人资料**中的**代码托管**下。
- **访问令牌**（在仓库、项目或工作区的设置中创建）属于该仓库、项目或工作区，而不属于某个人。它是**自动化令牌**，放在**自动化令牌**下。

每个对话框都会拒绝另一种令牌，并说明它应该放在哪里。

## 你在每个代码托管平台上都是不同的人

同一个人在 GitHub 上是 `octocat`，在 GitLab 上则完全是另一个名字。Control Center 会**按代码托管平台**解析你的身份，并为每个仓库使用正确的那一个；这正是“需要我审查”“由我创建”和“你已批准”在混合工作区中仍然正确的原因。

如果某个代码托管平台的身份尚未解析，它的仓库对收件箱的贡献为零，而不是匹配所有内容。收件箱会如实说明这一点，而不是声称你已全部处理完毕。

## 你只能看到你自己的账户能看到的内容

只有当你的工作区角色允许该仓库，**并且你在该代码托管平台上的账户也能读取它**时，该仓库的 pull request 才会呈现给你。工作区管理员和所有者遵循同一规则。当部分仓库被隐藏时，收件箱和 PR 队列会说明数量和原因，但不会点名：

- **登录 GitHub 即可查看另外 3 个仓库的 pull request**：你还没有在此连接该代码托管平台。登录后它们就会出现
- **已隐藏 3 个仓库，因为你的 GitHub 账户无法看到它们**：请向在该代码托管平台上有访问权限的人求助
- **已隐藏 3 个仓库，因为你在此工作区中没有访问权限**：请向工作区管理员申请访问权限
- **正在检查你对另外 3 个仓库的访问权限…**：Control Center 确认你的账户能读取哪些仓库时短暂显示

代码遵循同样的规则。要打开某个仓库的文件、差异或搜索，或在其上打开终端，你需要在此工作区中拥有该仓库的授权，并且你自己的代码托管平台账户必须能够读取它；工作区管理员同样如此，只有服务器所有者可以豁免。当无法联系代码托管平台进行核查时，你会看到 “无法确认你的代码托管平台访问权限。请重试。”（其中会写明代码托管平台的名称）。参见[代码遵循代码托管平台](/zh-CN/手册/概念/授权/#代码跟随代码托管平台)。

同样的规则也适用于由这些 pull request 产生的所有内容。在你看不到某个 pull request 期间，它的审查空间、消息和智能体运行都会消失；如果你失去访问权限，已打开的审查空间也会关闭。涉及被隐藏 pull request 的流水线运行会从你的运行列表中消失。代表你工作的智能体同样无法读取这些审查空间。工作区的仓库列表会显示你在此工作区中可以访问的每个仓库，即使你的代码托管平台账户暂时还无法访问它。

如果代码托管平台正在限流或宕机，Control Center 会继续显示它最后确认的内容几分钟，然后隐藏这些 pull request，直到能够再次检查为止。

## 一个收件箱，涵盖所有代码托管平台

收件箱和 PR 队列会分散查询工作区中出现的每一个代码托管平台，并将结果合并为单一的流——GitHub 的 pull request 与 Bitbucket 的 pull request 会并排出现，按时间排序，而不是按供应商分组。

故障是彼此隔离的。某个代码托管平台若宕机或受到速率限制，它不会影响其他平台，它自己的仓库会保持最后已知的状态，直到它恢复为止；它绝不会清空整个收件箱。若服务器已无法访问某个仓库，该仓库会从列表中移除，而不是显示过时的 pull request，并且**仓库访问通知**会点名它并给出修复方法：在其组织上安装 GitHub App、把仓库加入 App 的仓库列表、恢复被暂停的安装、让负责任的成员重新登录，或为 GitLab 或 Bitbucket 仓库添加自动化令牌。管理员会看到 GitHub App 相关步骤的按钮，以及添加令牌的按钮。

## 各代码托管平台能做什么

每个代码托管平台都支持核心循环：列出并打开 pull request、读取差异、行内和顶层评论、审查、合并与关闭。除此之外，它们确实各不相同，而 Control Center 会隐藏代码托管平台做不到的功能，而不是显示一个会悄悄失效的控件。

| 功能                              | GitHub | GitLab | Bitbucket |
| --------------------------------- | :----: | :----: | :-------: |
| 批量（待提交）审查                |   ✓    |   ✓    |     —     |
| 请求更改                          |   ✓    |   ✓    |     ✓     |
| 按文件同步的“已查看”状态          |   ✓    |   —    |     —     |
| 表情回应                          |   ✓    |   ✓    |     —     |
| 团队／群组审查者                  |   ✓    |   ✓    |     —     |
| 建议的审查者                      |   ✓    |   —    |     ✓     |
| PR 上的 CI 结果                   |   ✓    |   ✓    |     ✓     |
| 深入查看 CI 任务的步骤／日志      |   ✓    |   ✓    |     —     |
| 堆叠式 pull request               |   ✓    |   —    |     —     |
| PR 描述模板                       |   ✓    |   ✓    |     —     |
| 通知轮询                          |   ✓    |   —    |     —     |
| 丰富的用户资料                    |   ✓    |   ✓    |     —     |
| 服务端 PR head ref                |   ✓    |   ✓    |     —     |

当某项能力缺失时，功能的降级方式是诚实的：

- **已查看状态**仍然可用，但仅限于你设置它的那台设备。
- Bitbucket 上的**批量审查**会逐条发布评论，因此审查者看到的是它们陆续到达，而不是一次全部出现。
- Bitbucket 上**没有 PR head ref**，意味着检出某个 pull request 时会按名称抓取其源分支，而该分支一旦被删除，操作就会失败。

## 术语

GitLab 把 pull request 称为 **merge request**。Control Center 在自己的模型中始终使用“pull request”，在谈论某个代码托管平台时则使用该平台自己的说法。

## 故障排查

### PR 列表为空，并显示某个代码托管平台未连接

你在该代码托管平台上没有凭据。请在**设置 → 你 → 个人资料 → 代码托管**中登录 GitHub，或粘贴 GitLab 或 Bitbucket 令牌。其他代码托管平台的仓库不受影响。

### 我已连接代码托管平台，但它的仓库仍然什么都不显示

检查该行的状态，然后查看 PR 列表上方的通知。“登录……即可查看另外……个仓库的 pull request”表示你自己的账户尚未连接这些仓库；“……个仓库已隐藏，因为你的……账户无法看到它们”表示代码托管平台不给你访问权限。若是 GitHub，仓库访问通知会告诉你 GitHub App 是否未安装在该仓库的组织上，或未包含该仓库。

### GitLab 或 Bitbucket 仓库上的后台工作已暂停

该仓库没有能够读取它的自动化令牌。工作区管理员会为该仓库或整个工作区添加一个；参见[添加自动化令牌](#添加自动化令牌)。你自己的个人令牌无法解除暂停：后台工作从不使用成员的令牌。

### 仓库无法注册

注册需要同时满足三项条件：路径位于 git 工作树内、具有 `origin` 远端，且该远端指向 github.com、gitlab.com 或 bitbucket.org。`origin` 还必须是你正在关联的那个仓库，而位于工作区自身存储之外的文件夹只能由服务器所有者关联。参见[添加仓库到工作区](/zh-CN/手册/操作指南/添加仓库/)。

### 我有授权，但仓库显示我的账户无法读取它

你自己的代码托管平台账户无法读取该仓库，因此无论工作区授予什么权限，它的代码对你都是关闭的。请在上方的**代码托管**下登录该代码托管平台，或在代码托管平台上获得该仓库的访问权限。

### “无法确认你的代码托管平台访问权限”

无法联系代码托管平台来核实你的访问权限，因此 Control Center 拒绝了该请求，而不是凭猜测放行。请稍后重试。

### 仓库显示它现在指向另一个仓库

该路径背后的仓库已经变化：它被删除后又重新创建，或被移动并替换。在工作区管理员于通知或该仓库的行上点击**重新关联**之前，Control Center 不会向它发送任何内容。单纯的重命名或转移会自动跟随，绝不会出现此情况。

### 大量使用后，一切停滞了一段时间

这是速率限制的熔断器。当某个代码托管平台发出其主要限制的信号时，客户端会在本地使后续请求失败，不发出任何网络调用，直到该时间窗口过去——因此重试风暴无法加深限制。暂时性失败会以指数退避重试。
