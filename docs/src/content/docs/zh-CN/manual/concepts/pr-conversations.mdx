关于代码的讨论本来就发生在 Pull request 里。PR 对话让它成为 Control Center 工作区上的一个界面，就像[聊天桥接](/zh-CN/手册/概念/聊天桥接/)让 Slack 成为界面一样：在 PR 上 @提及 `@usectrl`，在它的审查线程里回复，或者加上 `ai-review` 标签，工作就会在 PR 的评审空间里进行——归属方式和护栏与在应用里输入的任何内容完全一致。评论和标签的门禁方式相同：都取决于写下或添加它的成员。机器人的回答会回到 GitHub 上，回到问题被提出的那条线程里。

有三项决策塑造了这项功能，而每一项都与聊天桥接为聊天所做的决策相同，只是针对代码托管平台重新表述：**连接朝哪个方向建立**、**从外部到来的评论由什么授权**，以及**双方分别归到谁名下**。

## 轮询就是传输方式

GitHub 为一个 App 提供的唯一推送通道是 webhook，而 webhook 需要一个入站 URL——这恰恰是这个界面刻意从不要求的东西。因此发现过程是一轮扫描：每个 App 安装都会发起一次针对该别名的搜索，向 GitHub 询问提及了 `@usectrl` 的 PR，以及带有审查标签的开放 PR；已经有评审空间的 PR 会被读取其评论线程；所有内容都会按评论 ID 与上一轮扫描看到的结果做差分。自有应用每分钟扫描一次，最多覆盖 25 个 PR。通过 Connect 时，调用会占用成员自己的 GitHub 配额，因此扫描每两分钟运行一次，最多覆盖 10 个 PR，而配额低于 15% 的工作区会被跳过，直到恢复。Connect 本身从不接触 PR 内容。

这些设计带来的后果值得点明：

- **延迟是扫描间隔，而不是事件。** 👀 确认会在一轮扫描内到达。没有什么紧急的事情依赖它。
- **每条评论恰好处理一次。** 评论 ID 在整个 GitHub 上唯一；每条评论在被判定为符合条件的那一刻就会被记录，早于任何针对它的动作。崩溃可能让某条评论的处理丢失，但绝不会让它被重复触发。
- **离线期间的内容会被补上，而不是重放。** 已见集合会持久化，因此重启后会补上停机期间到达的内容。唯一的例外是有史以来的第一轮扫描：没有可做差分的记忆，所有未处理的内容都会被静默记录——在这台服务器存在之前就给二十个 PR 打上标签的运维人员，不该回来面对二十个正在运行的审查。
- **标签是集合，而不是事件。** 搜索报告的是标签的_存在性_，因此被打上标签的 PR 只会触发一次，仅此一次。移除标签后再重新添加，对扫描来说是不可见的；重新运行的途径是 @提及。

搜索对每个安装账户在该账户自己的客户端上各运行一次，因为令牌只能看到自己这次安装下的仓库——一份服务器级的统一凭据会悄悄漏掉该 App 其他安装下的每一个 PR。

## 授权的是成员身份，而不是评论

到来的 PR 评论携带的是一个作者——在得到证实之前，它只是一个未经认证的外部身份。服务器会将作者不可变的数字 GitHub 账户 ID（而不是可能被改名和重新使用的登录名）与工作区成员的 GitHub 登录进行解析。该索引按 TTL 重建，因为服务器运行期间会有人登录，也会有人被邀请加入。对于 `ai-review` 标签，被解析的人是最近添加它的那位成员。

依次进行三项检查，任何一项失败都会悄无声息地处理——什么也不会发布：

- **已登录的成员。** 该账户必须属于_本_工作区的成员，并且在本服务器上登录过 GitHub
- **写入角色。** `viewer` 和 `guest` 不能启动工作
- **推送权限。** 回复使用一个仅针对该仓库的令牌，并限制在该成员对它的访问权限之内。如果服务器无法签发，就不会继续

每项检查都在任何确认之前运行，因此陌生人既得不到反应，也得不到回复。评论绝不会归到没有发送它的人名下，陌生人的话也绝不会进入他们看不到的工作区。

### 认领

任何工作之前的最后一步是一个 👀 表情回应，它使用作者自己的 GitHub 登录添加。GitHub 对新增的表情回应返回 `201`，对已存在的返回 `200`，因此这个表情回应兼作锁：当同一个人在两台都关联了该仓库的服务器上登录时，只有最先做出回应的那一台会执行工作。同一服务器上多个工作区都能看到的评论会分别提供给每一个工作区，由同一个认领决定归属。

## 刻意采用两种身份

对话的每一方都携带不同的身份，而这种差异正是这项功能的要点：

- **在 GitHub 上，回复是代你执行的自动化。** 每一条回复都使用针对该仓库的令牌，并限制在提问成员的权限之内，且由应用的 `[bot]` 账户署名。例外情况是：在共享的 Control Center Connect 应用上，只有当 Connect 运营方列出了该安装时，机器人才会在审查线程中发帖；否则，审查线程中的回复会以提问成员自己的账户署名。无论哪种方式，每条回复都以 `**Control Center** (for @login):` 开头，它说明了是谁提的问，同时也起到循环防护的作用。回复中智能体的 @ 提及会被失效处理，因此回复永远不会通知任何用户或团队。
- **在空间里，提问算在你名下。** 消息会归到作者解析出的那位成员名下，智能体运行也代表他们执行：其提交归该成员所有，空间的自主程度和行动护栏也完全像对待在应用里输入的消息那样生效。运行过程中对代码托管平台的写入使用仅针对该仓库、且受该成员约束的令牌，而不是把他们的登录整体交出去。

把审查发现发布回 GitHub 仍然是人的决定，并且在 Control Center 中做出。@提及可以_启动_一次审查；但只有人才能发布审查。

## 循环防护

任何由机器人账户创作的内容都会在任何门禁运行之前被丢弃——包括我们自己的机器人账户，以及所有带 `[bot]` 后缀的账户，这样其他 App 的审查机器人也无法唤醒我们的机器人。同样被丢弃的，还有每一条以 `**Control Center** (for @` 前缀开头的评论，因为通过 Connect 的审查线程回复可能以某个人的账户署名。没有这道防护，回答就会作为新评论到来，并永远重新触发这个桥接。

只有 `@usectrl` 会开始工作。App 自身的登录名（`<slug>[bot]`）和它的裸 slug 都不会触发任何操作：GitHub 不为 App 账户提供自动补全，而且裸 slug 可能属于某个人类用户。

## 刻意不提供的东西

- **不自动发布。** 发现会落在评审空间里；发布到 GitHub 是一个单独的人工操作
- **不做模糊身份匹配。** 作者要么精确解析到某一位成员，要么被忽略——没有猜测式的归属
- **不自动批准。** 自动化可以评论和请求修改，但 `APPROVE` 审查会在发送之前被拒绝。批准是人的行为
- **不使用 GitHub App webhook。** 这个界面从不注册 webhook，因此没有需要为 PR 评论暴露的入站 URL。其他产品级 webhook（流水线、工单同步）是另一套可选的设置。
