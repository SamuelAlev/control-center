聊天桥接让外部聊天产品——目前是 Slack——成为进入 Control Center 工作区的一等途径。
提及机器人，智能体就会被唤醒；在 Slack 话题里回复，对话就继续下去；输入一条斜杠命令，
就登记一张工单。在这之下，用的是与桌面应用相同的空间、转录、工单和归属。聊天是工作区上
的一个_界面_，而不是它的副本。

**随产品交付的只有 Slack 这一个提供方。** 产品中任何地方都没有 Discord、Telegram、
Teams 或 Matrix 的实现。这个特性刻意写成不感知具体提供方的形式——增加第二个产品只需
一个枚举值、一个适配器和一个插件——但今天“聊天”指的就是 Slack。

它由两个界面承载，而这两个界面属于不同的人。把工作区连接到 Slack、自定义机器人，是
**管理员**在 设置 → 工作区 → 通用 下的操作。把你自己的聊天账号关联到你的
Control Center 身份，是**成员**在 设置 → 工作区 → 个人资料与身份 下的操作。

有三个决策塑造了整个特性：**连接朝哪个方向发起**、**来自外部的消息凭什么获得授权**，
以及**特定于产品的知识允许存放在哪里**。

## 设计上主动外连

桥接从不监听提供方。它是通过 **Socket Mode** 触达 Slack 的：服务器先向 Slack 索取一个
套接字 URL 并主动外连，然后在这条连接上接收提及、私信和斜杠命令。

这个后果本身就是重点。位于 NAT 之后的笔记本电脑、没有域名的家用服务器、在不同网络之间
来回移动的机器——它们全都能运行桥接，既不需要入站端口，也不需要隧道和 TLS 证书，更不
需要在公网 URL 变化时去轮换它。没有 webhook 端点需要保护，因为根本就没有 webhook 端点。
Control Center 组装应用定义时会强制断言 Socket Mode 并剥掉任何请求 URL，因为同时配置了
两者的应用，只会是一个半残的应用。

代价是要维持一条存活的连接，而这是服务器的职责：重连采用带抖动的指数退避，上限 30 秒；
由提供方发起的套接字轮换会直接重连，不会抬高该退避；而_凭据被拒绝_是终态——无限重试一个
已吊销的令牌，只会换来速率限制，所以桥接会停下来等待新令牌，同时在设置里逐字报告提供方
自己的错误。

没有聊天应用的工作区完全不产生任何开销：没有套接字、没有定时器、没有流量。而且整件事是
在服务器打出就绪横幅_之后_才启动的，因为一个回应缓慢的聊天应用绝不能拖慢启动。

## 成员身份才是授权依据，而不是持有令牌

安装应用的人并不是发消息的人。因此每个入站事件都会先解析为一个**主体**，然后才会有任何
事情发生，并且它会默认拒绝、同时给出说明：

- **未关联的聊天账号**会在它自己发言的那个 Slack 话题里，收到如何关联的说明。
- **已关联、但其用户并非本工作区成员**的账号，会被告知去请管理员发出邀请。
- **角色为只读**（`viewer`、`guest`）**的成员**会被告知，其角色无法启动工作。

以上情况都不会继续下去。聊天消息绝不会被归属到并非其发送者的人身上——正是这一点让审计
追踪、按主体计算的速率限制和工单报告人都保持诚实。这里所依赖的成员身份模型，见
[多人协作与在线状态](/zh-CN/手册/概念/多人协作/)。

关联是身份解析，而**不是**访问授权。成员身份会在每个事件上重新检查，因此属于某个后来已
被移除之人的关联，会解析为一次拒绝，而不是他旧日的权限。建立关联有两条路径：成员在聊天
中输入一个短时效的一次性代码，或按提供方_已验证_的邮箱自动匹配——而邮箱这条路径仍然要求
被匹配到的用户已经是成员，所以一个地址恰好存在于服务器上的陌生人，什么也关联不到。

这些代码被刻意保存在内存中，存活时间为 15 分钟。把其中一个持久化，只会为一件本就该蒸发
的东西造出一行长得像凭据的持久记录；而服务器重启让所有尚未使用的代码失效，是正确行为，
不是退化——成员再点一次“关联”即可。

拒绝会**在消息所开启的那个 Slack 话题里**作为一条真正的回复给出。话题回复会给它所回应的
消息加上标记，只触达真正需要它的那一个人，同时仍然把“你尚未关联”挡在频道之外。发消息也
是每个提供方都具备的能力，因此这条说明永远不会依赖应用可能并不具备的特性。

## 来源与回声问题

双向镜像的桥接会陷入回环，除非有东西能区分两个方向。桥接带进来的每条消息都会打上
`metadata['chat']` 标记——提供方、团队、对话、话题、消息和发送者。出站镜像会跳过任何
带有该标记的消息。

正是这一条规则让双向镜像变得安全：在 Control Center 里输入的人类消息会被转发到已关联的
话题（以作者姓名作为前缀），而_来自_聊天的消息则在它进入的地方停下。

向外跨越的内容被刻意收窄。智能体的**回答**作为普通聊天文本转发出去。一句简短的思考可以
出现在卡片的 `Thinking…` 行上。工具输出是一整面 diff 墙，留在 Control Center 里——被
截断的回复也指向那里。

## 卡片报告工作进展，文本依然是消息

在提供方能够渲染卡片的地方，一个轮次会带**一张任务卡片**，在该轮次运行的整个期间原地
编辑，并位于它所解释的回答之上。

卡片是一份分组呈现的计划，而不是一段被捣烂的文字。Slack 会把同一个任务上的 `details` 和
`output` 拼接起来，所以一行的 details 只发送一次（即 `Thinking…` 上的那句思考），而
`output` 从不以流式发送。初始化只占一行，其标题会被替换（`Working on it…`、
`Cloning …`）。推理过程会新增一行 `Thinking…`。每个工具各占一行（`Read lib/main.dart`）。
回答是卡片下方的普通文本——Slack 的计划视图是从随后追加的一段 markdown 里读到它的，而
不是从混入任务里的一块内容中读到。除此之外没有别的：没有工具输出，工具参数也只来自一份很
短的白名单，因为一个未知工具的参数可能是一整个文件正文，而一行只有一行。

卡片也覆盖轮次_开始之前_的等待。第一次提及会创建对话，而创建对话会克隆智能体将要工作的
每一个仓库——在真实仓库上这意味着好几分钟，期间智能体还没有被要求做任何事，话题看起来
就像机器人忽略了这个请求。所以卡片在提及被接受的那一刻就打开（`Working on it…`），随后
那一行初始化信息会用桌面端所显示的同一批措辞更新——`Cloning acme/widgets…`、
`Setting up Reviewer…`、`Starting the agent…`——然后在智能体开始推理时立即出现一行
`Thinking…`，接着每个工具各一行。一张卡片、一条消息，从“我听到了”一路到下方作为普通
文本的回答。只有在聊天里确实有人等待时，初始化才会被报告：在应用里正在准备的对话，或在
服务器启动时恢复的滞留对话，都完全不显示卡片、直接预配。

它承载着聊天唯一无法给到读者的东西：一个 **View in Control Center** 链接，指向回复背后
的对话。聊天产品在链接里只接受 `http(s)`，别的都不行，所以这个按钮指向本服务器提供的一个
小页面，再由它把浏览器弹转到桌面应用的 `control-center://` 链接。那个页面不读取任何东西，
也不解析任何东西——它 URL 里的那些 id 只会被回填进一个深度链接，别处一律不用——而一台
没有可达公网 URL 的服务器，只会生成一张没有按钮的卡片，而不是一张坏掉的卡片。

卡片和其他能力一样，只是一种能力。不具备卡片的提供方行为与以前完全一致，只有文本；而在
调用时拒绝卡片的提供方则保留自己的流：回答的优先级永远高于描述它的卡片。当流式输出被完全
关闭时，已完成的卡片改搭那条唯一被发出的消息。登记工单也得到同样的处理——`/cc ticket`
的确认是一张已完成的卡片，它存在的理由就是指向刚刚创建的那张工单的链接。

## 能力先协商，再记住

聊天产品能渲染的东西各不相同，所以桥接是照着最丰富的界面来写的——话题内实时生长的回复、
稍纵即逝的“正在思考…”状态、带标题的话题、对斜杠命令的临时应答——然后一项一项地降级。
什么能力都没有的提供方依然可用；回复只是以单条消息的形式送达。

声明某项能力并不等于承诺它。Slack 的流式回复需要付费套餐中的一项功能，而 Slack 只在调用
时才拒绝。被标记为永久性的拒绝会在**整条连接的生命周期内**被记住：桥接从此不再请求，改为
直接发出完整回复，设置里也会直白地说明，因为“我的回复不再流式输出”这种问题，应该不读
日志就能回答。如果 Slack 拒绝了任务卡片，卡片也会以同样的方式被放弃。

每项上限都属于提供方，而不属于转发层：消息长度上限、流式分块上限，以及一个流是否需要话题
锚点，全都由适配器声明；过长的回复会按段落、行或单词边界切分，而不会把一个词从中间切开。

## 一个桥接，每个产品一个适配器

一切具有产品形态的东西都活在端口之后。通用核心只知道 markdown、聊天对话、聊天话题和
成员；它对 Slack 的事件信封、`mrkdwn` 或 gateway intents 一无所知。让这套安排成立的是
三样东西：

- **适配器**归一化一个产品：它的传输方式、它的 API 调用、它的文本编解码和它的事件信封
  怪癖。Slack 的怪癖很能说明问题——一条频道提及会到达两次（既作为 `app_mention`、_也_
  作为 `message`），而且大多数消息子类型只是装饰，而不是新请求。两者都在适配器里被解决，
  所以核心永远不知道 Slack 会重复投递。
- **描述符**是提供方的公开形态：它需要哪些凭据、这些凭据的格式是什么、哪些 URL 能帮用户
  找到它们、它能做什么，以及它的应用能否从这里创建或编辑。设置卡片、连接对话框和参数校验
  全都是从它_生成_的——客户端回传的是一个提供方，外加一个以字段 id 为键的映射。
- **插件**是服务器端的组装：凭据如何变成一条经验证的连接、适配器如何构建，以及提供方
  一侧的应用如何管理。

所以增加一个产品，就是一个枚举值、一个适配器和一个插件。没有新的 RPC 操作，没有 schema
改动，也没有客户端改动——而且客户端始终如实呈现，因为它从未听说过的一个字段，依然会带着
服务器提供的标签渲染出来。

有两个细节防止这层抽象向上泄漏。提供方没有 API 可用的那些应用管理步骤（生成令牌、安装
应用、权限变更后重新安装）会以**带各自链接的具名步骤**返回，因此收尾设置界面无需知道
自己是哪个提供方，也能把它们显示出来。而桥接写出的每一条指令都会点出提供方，以及应用
实际使用的命令，所以即便命令被改过名、或者出现了第二个提供方，读起来依然正确，无需新增
任何字符串。

:::caution[权限变更后需重新安装]
修改机器人的名称、描述或图标会立即生效。**权限**变更则需要重新安装：Slack 会应用新的
manifest，但授予的权限仍保持在当初安装时的状态。这次编辑会返回一个剩余步骤，其中带有指向
Slack“Reinstall to Workspace”页面的链接。
:::

## 凭据存放在哪里

工作区的聊天令牌存放在该工作区**自己的目录里，就在它的数据库旁边**——以纯 JSON 形式位于
`<dataDir>/<workspaceId>/chat_credentials/<provider>.json`，不放进数据库，并且刻意不放进
操作系统钥匙串。有两个后果日后很容易被忽略：删除工作区会解除该目录的链接，其中的令牌也
随之而去；而导出或备份工作区只会复制 `workspace.db`，所以一个交给别人的工作区里，不会
夹带着仍然有效的机器人令牌。该文件继承服务器主机的文件系统信任边界——凡是有权读取数据
目录的东西都能读到机器人令牌，这与数据库所处的边界完全相同。

每个提供方一个文件，原子写入且仅属主可访问：吊销一个应用只需解除一个文件的链接，而一个
损坏的文件只损失一个提供方，而不是全部。凭据只在连接操作中_进去_，永远不会再出来——状态
读取只返回连接元数据。

## 刻意不提供的东西

- **应用的结构性设置。**传输方式、权限范围和事件订阅都是强制断言的，不对外开放。一个能
  从设置界面被配置到彻底沉默的应用，是一张支持工单，而不是一个特性。
- **对话加斜杠命令，仅此而已。**Slack 界面就是消息、话题回复和斜杠命令。
- **第二个事实来源。**聊天不是存放工作的地方。Slack 话题是一个空间，回复是一份转录，
  工单就是工单——它们全都在工作区里，从每个客户端都能访问到。
