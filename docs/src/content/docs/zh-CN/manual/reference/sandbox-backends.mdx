:::caution[一次运行是否被沙盒包裹取决于主机]
`cc_server` 在启动时一次性决定智能体在这台主机上如何运行，该决定一直有效，直到它重启：

- **沙箱中**（`native`）：探测发现了后端，且 `--sandbox` 不为 `off`。两处派发接缝都会被包裹：Claude Code CLI 经由沙盒端口，ACP 加内置运行器的 `bash` 工具则经由沙盒管理器。
- **关闭**（`off`）：服务器所有者以 `--sandbox off` 启动了服务器。每位成员的智能体都在这台机器上不受限制地运行，无论是谁启动的。
- **不可用**（`unavailable`）：沙盒处于开启状态，但探测没有发现后端（**Windows 始终如此**，以及没有 `bwrap` 和 `socat` 的 Linux 或 WSL2）。只有当对某次运行负责的人是服务器[所有者](/zh-CN/手册/概念/授权/#服务器所有者)时，它才会启动：即请求该运行的人，或对于自动化而言，即其绑定的人。其他人的运行会在铸造凭据、获取租约或启动进程之前被拒绝。若未记录所有者，则没有任何人的运行会启动。

被拒绝的运行会以代码 `sandbox_unavailable` 失败。应用会将其显示为**智能体需要此服务器上的沙箱**：“此服务器没有沙箱，因此只有其所有者可以在此运行智能体。所有者可以安装沙箱，或为所有人关闭沙箱。”

不被沙盒包裹而启动的运行（在 `off` 下，或在 `unavailable` 下的所有者自身运行）会直接运行在主机上。ACP 和运行器的 `bash` 工具仍会在净化过的环境中启动；Claude Code 则经由 `NoSandboxAdapter` 继承主机环境。其余的边界包括：这次运行自己的工作树（随附 `rift` 的地方用写时复制；Windows 上用 `git worktree`）、在每次启动时中介签发、在拆除时吊销的只读代码托管令牌、必须在智能体运行网关通过推送规则的推送、按模式的命令策略、统一的[操作护栏](/zh-CN/手册/概念/护栏/)（失败即关闭）、ACP 和运行器 `bash` 路径上的环境净化，以及它的模式所允许的工具面。

运行器的进程内文件工具（read、write、edit、apply patch、search、find、search_files）在每一种主机上都位于沙盒之外：它们运行在服务器进程内部，因此只有 `bash` 被包裹。

主机永远不会成为已沙盒化服务器的回退。如果服务器对智能体进行沙盒隔离，却没有可供某次运行使用的沙盒，那么它的工具进程和 `bash` 命令会被拒绝，而不是在主机上启动。同样的姿态也决定了运行周围的小进程：ACP 的一次性辅助进程（对话标题、`/btw`、`/handoff`、`/goal`）以及 Review Studio 中 pull request 的 golden 测试，在服务器对智能体进行沙盒隔离时于沙盒内运行，在 `off` 下不受限制地运行，在 `unavailable` 下则只为服务器所有者负责的请求运行；否则它们会被跳过。
:::

## 后端概览

| 后端 | 取值 | 平台 | 可用性 |
| --- | --- | --- | --- |
| 封闭虚拟机 | `microvm` | macOS、Linux、Windows（microVM 虚拟机管理程序） | 受 microVM 运行时的探测门控；适用于交互式终端——shell 运行在一台[机台](/zh-CN/手册/概念/机台/)内，而不是主机上 |
| 原生 | `native` | macOS（Seatbelt）、Linux 和 WSL2（bubblewrap） | 在启动时探测；Linux 会拒绝一次需要基于文件名通配符的写入拒绝的运行，而 bubblewrap 无法强制执行这一点 |
| 无隔离 | `none` | 全部 | 解析时的默认值和终端的默认值；`--sandbox off` 下智能体派发使用它，而在没有可用后端时，仅用于所有者自己的运行 |

`SandboxBackend.fromName` 对 null 或无法识别的已存值返回 `none`。

**`microvm` 是唯一带内核边界的后端**——工作负载确实不在主机上运行。它在任何一个方向上都不会成为静默回退：在无法启动 VM 的主机上显式请求它会大声失败（“我要的是一台 VM，拿到的却是自己的笔记本”是这套封闭方案唯一承受不起的降级），而只有*未指定的默认值*才会降级到 `native`，并打出一行日志说明这一点。会话实际使用的后端会回报给客户端并打上徽标，因此一台终端绝不可能在主机上运行的同时声称自己已被封闭。VM 自身的生命周期、镜像和出站访问由[机台参考](/zh-CN/手册/参考/机台/)介绍。

**Windows 没有原生沙盒。** `NativeSandboxAdapter.probe` 在所有非 macOS 也非 Linux/WSL2 的主机上都返回 `available: false`。因此 Windows 服务器处于 `unavailable` 状态：只有服务器所有者的智能体运行会启动，且不受限制，其他所有人的运行都会被拒绝。要让每位成员都能在那里运行智能体，所有者需以 `--sandbox off` 启动服务器，这会不受限制地运行所有智能体。`microvm` 后端是另一回事：它受 microVM 运行时的探测门控，适用于交互式终端和机台，而不是在主机上包裹 `bash`。

## 探测结果

探测才是决定是否强制执行的那道门。它在服务器启动时运行一次。

| 主机 | `available` | 说明 / 提示 |
| --- | --- | --- |
| macOS | `true` | `sandbox-exec`（Seatbelt）——命名空间隔离，没有内核边界 |
| 装有 `bwrap` 和 `socat` 的 Linux 或 WSL2 | `true` | bubblewrap——命名空间隔离，没有内核边界 |
| Linux 或 WSL2 缺少其中任一工具 | `false` | `requiresInstall: true`，并带有指明缺失软件包的安装提示 |
| 任何其他平台 | `false` | 此平台不提供原生沙盒 |

服务器会在启动时用一行日志记录结果：`agent sandbox ON` 加说明、`no OS-native agent sandbox on this host` 加提示（提示中会补充说明只有服务器所有者负责的运行才会启动），或 `agent sandbox DISABLED by --sandbox off`。启动时打印的暴露行携带同样的决定，以 `sandbox=native`、`sandbox=off` 或 `sandbox=unavailable` 的形式呈现。`GET /healthz` 不携带任何沙盒字段。

`--sandbox` / `CC_SERVER_SANDBOX` 接受 `on`（默认）或 `off`。`on` 在主机提供后端时包裹每一次运行，在主机没有后端时只接纳所有者的运行。`off` 会在此主机上不受限制地运行每位成员的智能体；这是所有者为所有人做出的选择，而不是按次运行的设置。

## 原生后端

### macOS：Seatbelt

使用 Apple 的 Seatbelt 沙盒机制（与 macOS App Sandbox 使用的是同一套系统）。

生成的配置**默认宽松**（`(allow default)`），再在其上划出一系列拒绝，因为一份完全默认拒绝的配置会让交互式 shell 无法使用——需要枚举的 dyld、XPC 和 Mach 调用太多了。实际后果是智能体仍然可以读取主机的大部分内容；你已注册的检出靠的是显式的写入和重命名拒绝来保护，而不是靠不可见。

- **文件系统读取**：对机密路径（`~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config/gh`、`~/Library/Keychains` 以及拒绝读取集合中的其余路径）拒绝
- **文件系统写入**：先重置为拒绝，再显式放行子路径，其中强制拒绝的路径（shell rc 文件、`.git/hooks`、Claude 配置、受保护的检出）即使在可写根目录之内也会被阻止。`file-write-unlink` 在每一条被拒绝路径及其祖先路径上都被拒绝，因此重命名无法绕过一次写入拒绝
- **进程**：对始终危险的二进制文件执行 `process-exec` 拒绝，并阻止从任何可写目录执行任何东西。主目录下已知的工具链安装目录（corepack、npx 和 `pnpm dlx` 缓存、Node 版本管理器、Playwright 浏览器、rustup 和 cargo、Go、fvm 和 pub 缓存、pyenv、uv 和 pipx、rbenv、sdkman、mise、asdf 以及 `~/.local/bin`）会在该阻止之下重新开放。共享临时目录也被阻止。每个会话则改为获得 `/private/tmp` 下的私有 `TMPDIR`，供其构建的程序（如 `go test` 二进制文件、cargo 构建产物）运行。始终危险的拒绝规则在这些允许之后应用
- **网络**：限制为进程内代理端口加 DNS——回环并非一律放行，且禁止 TCP 监听。Unix 套接字仅允许在会话的私有 `TMPDIR` 内使用，涵盖了 tsx、Chrome 等将 IPC 套接字放在那里的工具；你的 SSH agent 及其他套接字仍不可访问。代理强制执行按会话的域名允许列表（见[网络出站](#网络出站)）
- **配置**：配置在每次启动时根据 `SandboxSpec` 生成
- **服务器自身的命令**：服务器运行程序所在的任何文件夹的直接子项（每个 `PATH` 条目，以及常见的按用户工具文件夹如 `~/.local/bin`，并解析 `~/fvm/default` 之类版本管理器链接）都不能被创建、替换、删除或重命名，指向的已安装包也不能。参见[服务器的命令文件夹](#服务器的命令文件夹)
- **启动文件**：沙盒配置拒绝读取的每个主目录路径也拒绝写入，并且服务器用户的 shell 与会话的启动文件（`.zshenv`、`.zlogin`、`.bash_login`、fish 配置、systemd 用户单元、自动启动项等）在每种模式下都禁止写入。

要求：

- `sandbox-exec`（`/usr/bin/sandbox-exec`），每次 macOS 安装都自带——无需额外的工具

### Linux：bubblewrap

使用 bubblewrap（`bwrap`）创建挂载和 PID 命名空间。

- **文件系统**：创建一个挂载命名空间，其中只有被绑定的路径可见
- **网络**：运行在未共享的网络命名空间中；流量经由 `socat` 的 Unix 套接字桥到达主机代理
- **进程**：PID 命名空间隔离
- **服务器自身的命令与启动文件**：与 macOS 相同的保护，以 bubblewrap 绑定表达。它们在 Linux 上尚未经过验证，且那里缺失的命令文件夹仍可能被创建。

要求：

- 已安装 `bubblewrap` 和 `socat`（Debian/Ubuntu 上为 `sudo apt-get install bubblewrap socat`）
- 内核命名空间支持（现代 Linux 上为标准配置）

Bubblewrap 可以遮蔽一个已存在的路径，但无法禁止可写绑定内*新增*的 `.env`、`*.key` 或 `*.pem` 文件。标准派发策略要求这些基于文件名的通配符拒绝，因此原生智能体派发目前在 Linux/WSL2 上**即便探测发现 bubblewrap 也会失败关闭**。它不会以静默削弱的策略运行。要恢复 Linux 原生派发，需要一个具备创建时文件名规则的后端。关闭沙盒是一种显式的无限制退出选择，而不是等效的变通办法。

实际上，今天 Linux 或 WSL2 服务器以两种方式之一运行智能体。以 `--sandbox off` 启动时，它会不受限制地运行每位成员的智能体。若未安装 bubblewrap 或 `socat`，它则处于 `unavailable` 状态，只运行服务器所有者的智能体，且不受限制。两者都已安装且沙盒开启时，每次运行都会失败关闭，包括所有者的运行。

## 服务器的命令文件夹

服务器在启动时一次性找出它运行程序所在的每个文件夹：它的 `PATH` 的每个条目，它探测的按用户工具文件夹（如 `~/.local/bin`、`~/.bun/bin` 以及 npm、yarn 和 pnpm 的全局文件夹），以及途中每个链接背后的真实文件夹（如 `~/fvm/default` 或 fnm 默认版本之类的版本管理器链接）。在沙盒内，智能体无法在这些文件夹中添加、替换、删除或重命名命令，无法替换指向其中某个命令的链接，也无法替换其指向的已安装包，更无法重命名它们之上的文件夹。否则，一次沙盒化的运行就可能埋下一个程序，之后服务器或用户会在沙盒之外启动它。

这对一次运行意味着：

- 在沙盒化运行内部进行的全局安装会以 "Operation not permitted" 失败：`npm i -g`、`pnpm add -g`、`yarn global add`、`bun add -g`、`corepack enable`、`pipx install`、`uv tool install`，以及当其 bin 文件夹位于服务器 `PATH` 上时的 `cargo install`、`go install` 或 `dart pub global activate`。
- 切换默认版本同样失败（`fnm default`、`nvm alias default`、`fvm global`），工具原地自我更新也一样。
- 项目本地安装（`node_modules/.bin`）、`npx`、`pnpm dlx`、由 corepack 管理的包管理器、SDK 缓存和普通构建仍然可以工作。

要让智能体可以使用某个全局工具，请以服务器用户的身份在服务器本机上安装它，然后重启服务器，使新命令也受到保护；或者将它安装到项目中。服务器启动后安装的命令，只有在下次启动后才会得到完全保护。

这些规则在 macOS 上已强制执行并经过测试。在 Linux 上，同样的规则是尚未经过验证的 bubblewrap 绑定。Windows 没有沙盒。

## 无隔离后端

没有沙盒。进程直接运行在主机上，拥有主机的文件系统、网络和进程访问权限。ACP 和运行器的 `bash` 工具仍会获得环境净化和命令策略；经由 `NoSandboxAdapter` 的 Claude Code 则继承主机环境。在 `--sandbox off` 下，智能体派发对每次运行都使用它；在没有可用后端的主机上，则只为服务器所有者自己的运行使用它，其他人的运行在那里会被拒绝。对于终端，它是主机 shell 的默认值，而主机 shell 只有服务器所有者才能打开。

## 服务器托管的终端

服务器托管的终端只为服务器的[所有者](/zh-CN/手册/概念/授权/#服务器所有者)打开主机 shell。其他人则会得到一个沙盒终端，受智能体的限制，位于工作区自己的目录中。

会话的后端选择方式如下：

| 请求 | 服务器所有者 | 其他人 |
| --- | --- | --- |
| 未指定 | 服务器的默认后端 | 默认值，并将 `none` 替换为 `native` |
| `none`（主机 shell） | 主机 shell | 拒绝：主机 shell 在服务器上无沙盒运行 |
| `native` | 原生沙盒，所有者配置 | 原生沙盒，智能体配置 |
| `microvm` | 封闭虚拟机 | 封闭虚拟机 |
| 未知名称 | 拒绝 | 拒绝 |

- **所有者配置。** `$HOME` 和会话的工作目录可写，网络开放，而 `~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config/gh` 和 `~/Library/Keychains` 被拒绝读取。
- **智能体配置**（`memberTerminalSandboxConfig`）。与该工作区中智能体运行所用的策略相同：写入保持在工作目录、私有运行目录、`/tmp` 以及智能体可写的 `$HOME` 部分之内；机密被拒绝读取；网络为智能体的出站允许列表；程序只从工作目录和已安装的工具链运行。
- 终端只会在工作区自己的目录中打开。位于其之外的工作目录会被拒绝，而不会被替换为其他目录。
- 只有打开终端的人可以读取、输入、调整大小或关闭它。对其他任何人来说，它的 id 看起来是未知的。
- 在没有机台服务的主机上显式请求 `microvm` 会失败，而不是回退。在这类主机上将 `microvm` 设为默认值时，会降级为 `native`，并在日志中说明。

只读代码托管令牌和推送网关不适用于终端——那是派发关心的事。如果无法进行包裹，会话会失败，而不是在主机 shell 会话上显示沙盒徽标。

## 网络出站

沙盒启动时，出站网络访问由进程内代理强制执行，而不是靠内核防火墙规则。不被沙盒包裹的运行（`--sandbox off` 下的每次运行，或没有后端的主机上所有者的运行）不享有这一切：它启动的进程会与服务器用户本人完全一样地访问网络。

- 沙盒运行时在 `cc_server` 进程内部于 `127.0.0.1` 上运行一个 HTTP/HTTPS 代理和一个 SOCKS5 代理，**每个受限会话一对**（`http_proxy.dart`、`socks_proxy.dart`）。并发运行不共享同一对。
- 被沙盒包裹的进程会收到代理环境变量（`HTTP_PROXY`/`HTTPS_PROXY` → HTTP 代理，`ALL_PROXY` → SOCKS 代理；`GIT_SSH_COMMAND` 让 git-over-SSH 走 SOCKS 代理）。在 Linux 上网络命名空间是未共享的，因此代理是唯一的出路；在 macOS 上沙盒与主机共享回环，可以直接与它们通信。
- 每个连接的目标主机都会与会话的域名允许列表比对；其他一切都被拒绝。有两种通配符形式，各自恰好含一个 `*`：前缀式 `*.example.com` 匹配任意子域名（包括 `a.b.example.com`），但不匹配裸域本身；中间标签式 `bedrock.*.amazonaws.com` 恰好匹配一个标签（`bedrock.us-east-1.amazonaws.com`，而不是 `bedrock.evil.attacker.amazonaws.com`）。
- 允许列表按会话从经过筛选的基线（`kBaselineAllowedDomains`：LLM 提供方、Git 托管、软件包注册表）解析而来，再加上 GitHub 域名（`kGithubDomains`），以及 `SandboxSpec.egressAllowlist`。派发路径从不传入额外的 `egressAllowlist` 条目，因此实际上每次运行得到的都是基线加上 GitHub。
- 一份固定的拒绝列表（`kBaselineDeniedDomains`：云元数据端点、遥测接收端）优先于所有允许项。
- `networkEnabled: false` 仍会启动按会话的代理，但允许列表为空，因此所有出站连接都会被拒绝。派发在运行开始时根据**访问网络**规则设置该值：拒绝会关闭网络，允许和先询问会让它保持开启。

## SandboxSpec

传给 `SandboxPort.launch` 的规范：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `sessionId` | `String` | 稳定的会话标识符（通常是空间 id） |
| `workspaceId` | `String` | 所属工作区 id |
| `agentId` | `String?` | 当前绑定到该沙盒的智能体（如果有） |
| `bindMounts` | `List<SandboxBindMount>` | 主机→客户机挂载；沙盒只会看到这里列出的主机路径 |
| `networkEnabled` | `bool`（默认 `true`） | 派发时根据网络出站规则设置（只有解析为拒绝时才关闭）。关闭时，按会话的代理仍会启动，但允许列表为空，因此所有出站连接都会被拒绝 |
| `egressAllowlist` | `List<String>`（默认 `[]`） | 额外允许的出站域名；支持通配符（`*.example.com`，外加一种单标签的中间形式）。派发从不填充它，因此被包裹的运行得到的是经过筛选的基线加上 GitHub 域名 |
| `guestWorkdir` | `String?` | 沙盒内的默认工作目录；单次 `exec` 调用可以覆盖它 |
| `mode` | `Mode`（默认 `chat`） | 划定文件系统写入规则：`chat` 保持绑定挂载可写；`review`、`plan` 和 `orchestrate` 为只读 |
| `protectedPaths` | `List<String>`（默认 `[]`） | 在任何模式下都绝不允许在沙盒内可写的主机路径 |
| `runnerStateDirs` | `List<String>`（默认 `[]`） | 运行器存放自身状态的主机目录，在所有模式下都可写（当前是 Control Center 管理的 `CLAUDE_CONFIG_DIR`） |
| `execGrantRoots` | `List<String>`（默认 `[]`） | 运维人员批准、用来在 macOS 上重新打开可写目录 exec 阻止的目录树。Linux 忽略它们——bwrap 没有可供重新打开的 `$HOME` exec 阻止 |

`protectedPaths` 保存着已注册的原始仓库检出，在每次派发时从工作区的仓库解析而来。智能体只在按对话划分的写时复制工作树中工作，因此原始检出从沙盒内部绝不能可写——在 macOS 上，Seatbelt 对 `$HOME` 的一揽子写入放行否则会让它们经由 `bash` 仍可写。它们在所有模式下都会加入机密拒绝写入集合，`chat` 也不例外。

每一条拒绝读取和拒绝写入路径都会同时以它的字面写法和经符号链接解析后的写法输出。内核是按解析后的路径匹配拒绝规则的，因此针对符号链接路径写下的规则永远不会触发——而这在 macOS 上是常态而非特例，因为 `/tmp` 会解析为 `/private/tmp`，`/var/folders/…` 会解析为 `/private/var/folders/…`。包含 `*` 或 `?` 的条目会被当作通配符模式，保持原样；无法解析的路径则按原样保留。

## SandboxBindMount

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `hostPath` | `String` | 主机上的绝对路径 |
| `guestPath` | `String` | 沙盒内的路径（使用原生沙盒时它等于 `hostPath`；保留它是为了适配器的对称性） |
| `readOnly` | `bool`（默认 `false`） | 为 true 时以只读方式挂载 |

## SandboxHandle

由 `SandboxPort.launch` 返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `sessionId` | `String` | 会话标识符 |
| `backend` | `SandboxBackend` | 正在运行的是哪个后端 |
| `state` | `SandboxState` | 生命周期状态 |
| `error` | `Object?` | 当 `state` 为 `error` 时设置 |
| `details` | `Map<String, Object?>` | 适配器私有的簿记信息（工作目录、PID、配置路径等） |

### SandboxState

| 状态 | 说明 |
| --- | --- |
| `created` | 规范已创建，但 VM 尚未启动 |
| `warm` | 正在运行，可以执行命令 |
| `active` | 当前正在执行命令 |
| `suspended` | 已暂停 / 已检查点保存到磁盘以节省 RAM |
| `destroyed` | 已拆除；句柄不再有效 |
| `error` | 启动失败——见 `SandboxHandle.error` |

## 沙盒事件

| 事件类型 | 说明 |
| --- | --- |
| `stdout` | 来自沙盒的标准输出 |
| `stderr` | 来自沙盒的标准错误 |
| `exit` | 沙盒进程已退出（携带 `exitCode`） |
| `starting` | 沙盒正在启动 |
| `ready` | 沙盒已准备好接受 exec 调用 |
| `killed` | 进程被主机终止（OOM、超时、手动停止） |
| `violation` | 有一条沙盒策略被违反（携带 `SandboxViolation`） |

## SandboxViolation

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `action` | `String` | 被拒绝的动词（例如 `file-read*`、`network-outbound`） |
| `target` | `String` | 被拒绝操作的目标路径或主机 |
| `raw` | `String?` | 原始日志行，便于调试 |
