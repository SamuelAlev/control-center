Control Center 能够复制、移交或接纳的一切，以及每种产物的确切形态。要实际执行一次
备份，请参阅[备份与恢复](/zh-CN/手册/操作指南/备份与恢复/)；至于持久化为何这样
拆分，请参阅[工作区与隔离](/zh-CN/手册/概念/工作区/)。

## 产物

共有三种数据库副本产物，它们的作用范围和删除策略各不相同。

| 产物                    | 写入方                       | 形态                                   | 覆盖范围                         |
| ----------------------- | ---------------------------- | -------------------------------------- | -------------------------------- |
| **安装快照**            | `server.backupNow`           | 一个带时间戳的**目录**                 | 该安装上的每一个数据库           |
| **工作区备份**          | `Workspace backup` 流水线    | 带时间戳、内含一个 `.db` 的目录        | 一个工作区的数据库               |
| **工作区导出**          | `workspace.export`           | 单个 `.db` **文件**                    | 一个工作区的数据库               |

三者都用 SQLite `VACUUM INTO` 写出，这对活跃的 WAL 数据库是安全的：它会开启一个读
事务，生成一份已整理碎片、事务上一致的副本，并且从不需要停止服务器。

这些文件以及下载下来的副本**不会被 Control Center 在静态状态下加密**。端到端加密的传输在已配对客户端与其 `cc_server` 之间保护传输途中的字节，无论是直连还是经中继的连接。请单独保护本地存储和机器之外的副本；服务器以及任何获得授权的接收方都能读取这些数据库文件。

## 快照布局

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

该布局与实时数据目录完全一致，这正是让恢复一次安装成为原样复制回来、而不是一次转换
的原因。目录名是 UTC 时间戳，其中的 `:` 和 `.` 被替换为 `-`，因此它在 Windows 上对
文件系统安全，作为普通字符串也能按时间顺序排序。

计划性的工作区备份单独存放在 `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`。每个备份都为该单一文件包含一个 `manifest.json`，且不包含 `global.db`；它们并不是安装快照。恢复会把它所替换的数据库保留在同一位置，名称为 `<timestamp>-pre-restore`。每周流水线的保留步骤只会删除它自己所属工作区中早于所配置期限（默认 30 天）的备份；手动创建的安装快照绝不会被该步骤轮换掉。`server.listBackups` 只列出安装快照，包括未验证的那些；`workspace.listBackups` 列出单个工作区的定时备份。

删除工作区会保留此目录。工作区的计划随之停止，因此不再有任何机制轮换这些备份，它们会
一直保留，直到安装所有者将其移除。`server.listOrphanedBackups` 会报告它们。


### `manifest.json`

| 字段                       | 类型            | 含义                                                                |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                  | int             | 清单格式。目前为 `2`                                            |
| `created_at`               | ISO-8601 UTC    | 快照的生成时间                                                      |
| `global`                   | object          | `global.db` 的记录。计划性工作区备份中不存在此项 |
| `workspaces[]`             | array           | 每个被捕获的工作区一条记录                                          |
| `workspaces[].workspace_id`| string          | 该文件所属的工作区                                                  |
| `skipped_workspaces[]`     | array           | 备份**未能**捕获的工作区 |
| `skipped_workspaces[].workspace_id` | string | 被略过的工作区 |
| `skipped_workspaces[].reason` | string | `no_file`、`damaged` 或 `failed` |

`global` 以及 `workspaces[]` 中的每个条目各记录一个已复制的文件，测量的是写入之后的副本：

| 字段 | 类型 | 含义 |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | string          | 相对于快照根目录的路径：`global.db` 或 `<workspaceId>/workspace.db`                |
| `bytes`       | int             | 该副本的大小                                                        |
| `sha256`         | string | 该副本的 SHA-256，小写十六进制 |
| `quick_check`    | string | SQLite 的 `quick_check` 对该副本的结论：`ok`，或其发现的问题 |
| `user_version`   | int    | 该副本的 schema 版本 |
| `application_id` | int    | 该副本的 SQLite `application_id` |

当某个工作区已注册但从未被写入（`no_file`）、其数据库未通过完整性检查（`damaged`；损坏的副本绝不会被生成），或其副本或该副本的检查失败（`failed`）时，该工作区就会被跳过。无论哪种情况，快照仍会完成，清单会指明缺失了什么。清单最后写入。

### 完整性

`server.listBackups` 会为每个快照报告一个 `complete` 标志。当清单缺失、无法解析或格式不同、它所指向的某个文件缺失或大小不同，或某个副本未通过检查时，该标志为 false。应用会将此类快照显示为**未验证**。在格式 `2` 之前生成的快照处于此状态。

未验证的快照仍会被列出，因为运维人员看不到的快照，就是他们自以为拥有的快照。当清单
无法读取时，列表会退回到目录结构本身，并报告它找到的任何 `<workspaceId>/workspace.db`
文件——即使整个快照无法恢复一次安装，这些文件仍可以逐个通过 `workspace.import` 被
接纳。

列出的快照或定时备份在其所属工作区的实时数据库已损坏时，会携带 `pinned_reason: "last_good_copy"`，即它持有该工作区最新的已验证副本。保留步骤会跳过它，直到该工作区被恢复为止。

## 备份不包含什么

两种产物都**只是数据库**。一个工作区目录所持有的东西远不止它的数据库，而其余的都不会
被带走：

| 路径                                | 在快照中？     | 在工作区导出中？       |
| ----------------------------------- | -------------- | ---------------------- |
| `global.db`                         | 是             | 否                     |
| `<workspaceId>/workspace.db`        | 是             | 是（它*就是*那个文件） |
| `<workspaceId>/code_index.db`       | 否             | 否                     |
| `<workspaceId>/blobs/`              | 否             | 否                     |
| `<workspaceId>/skills/`             | 否             | 否                     |
| `<workspaceId>/agents/`             | 否             | 否                     |
| `<workspaceId>/chat_credentials/`   | 否             | 否                     |
| `<workspaceId>/spaces/<spaceId>/`   | 否             | 否                     |
| `<workspaceId>/pr_clones/`          | 否             | 否                     |
| `secrets.json`                      | 否             | 否                     |
| `models/`                           | 否             | 否                     |
| `meetings/<meetingId>/`             | 否             | 否                     |
| `rigs/`                             | 否             | 否                     |
| `_agent_hooks/`                     | 否             | 否                     |

其中有些是可丢弃的——`spaces/` 保存的是从仓库重新预配的写时复制工作树，`pr_clones/` 是缓存，`code_index.db` 会被重建，`models/` 可重新下载，`rigs/` 是机器状态。有些则不是：`blobs/` 保存着数据库行所指向的粘贴图片，`skills/` 和 `agents/` 保存着智能体运行时使用的文件，而 `secrets.json` 保存着该安装上的每一个配对密钥、提供商凭据和 SSO 设置。如何覆盖其余内容，请参阅[备份与恢复](/zh-CN/手册/操作指南/备份与恢复/#将备份复制到机器之外)。
:::note[机密不在数据库中]
`workspace.db` 是整个工作区：对话、运行日志、仓库关联、环境定义和成员。流水线 webhook 令牌和工单同步 webhook 密钥保存在 `secrets.json` 中：数据库保存每一项的引用，路由索引保存每个令牌的带密钥哈希。因此在另一个安装上恢复的工作区，在其触发器于那里重新保存之前不会接收任何 webhook。提供方登录、设备密钥和用户机密保存在 `global.db` 和 `secrets.json` 中。
:::

:::note[聊天令牌被刻意留在原处]
`chat_credentials/` 位于数据库旁边而不是其中，正因如此，交给别人的工作区不会携带
任何有效的机器人令牌。参见[聊天桥接参考](/zh-CN/手册/参考/聊天桥接/)。
:::

## 操作

安装级备份 RPC 以及工作区导出/导入仅限 `fullClient`：已配对的手机无法触发它们。在
没有接入备份端口的服务器上（例如演示服务器），它们会完全不存在——不是被拒绝，而是在
结构上缺失。

| 操作                 | 类型   | 范围      | 最低角色          | 参数          | 返回                          |
| -------------------- | ------ | --------- | ----------------- | ------------- | ----------------------------- |
| `server.backupNow`   | mutate | 安装      | 安装**所有者**    | 无            | `{ok, path}`                  |
| `server.listBackups` | read   | 安装      | 安装**所有者**    | 无            | `{backups: [...]}`            |
| `server.deleteBackup` | mutate | 安装     | 安装**所有者**    | `name`        | `{ok}`                        |
| `server.listOrphanedBackups` | read | 安装 | 安装**所有者** | 无 | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | mutate | 安装 | 安装**所有者** | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | read | 工作区 | `admin` | 无 | `{backups: [...]}` |
| `workspace.deleteBackup` | mutate | 工作区 | `owner` | `name` | `{ok}` |
| `workspace.export`   | read   | 工作区    | `admin`           | 无            | `{ok, path}`                  |
| `workspace.import`   | mutate | 工作区    | `owner`，且需要服务器所有者 | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | read | 工作区 | `owner`，且需要服务器所有者 | 无 | `{holds: [...]}` |
| `workspace.importHolds.resolve` | mutate | 工作区 | `owner`，且需要服务器所有者 | `hold_id`、`accept` | `{ok, applied}` |
| `workspace.delete`   | mutate | 安装*     | `owner`           | `id`          | 注册表行被标记为已删除        |

* `workspace.delete` 没有作用范围，是因为它标记的那一行位于全局注册表中；其处理程序
会检查调用者对所指工作区的成员身份，并要求 `owner`。

每个响应中的 `path` 都是 **服务器主机**上的路径。

`server.listOrphanedBackups` 为每个不再有效的工作区返回一个条目：`workspace_id`、注册表
仍知道时的 `workspace_name`，以及 `backups`。已删除的工作区无法再通过工作区角色检查，
因此其备份归安装所有者所有。`server.deleteOrphanedBackup` 会拒绝仍然有效的工作区，其备份
仍由 `workspace.deleteBackup` 和该工作区自身的角色把关。这两个删除操作都只接受列表中的
时间戳目录名，不接受路径。

`workspace.importHolds.list` 返回导入所暂存的内容。每个暂存项都有 `id`、`kind`（`action_policy`、`sandbox_exec_grant`、`repo_grant`、`membership_role` 或 `invite`）、它将被放回的 `payload`、`imported_at` 和 `source_install_id`。带 `accept: true` 的 `workspace.importHolds.resolve` 会重新授予该权限，带 `false` 则会丢弃它。当该权限所针对的人或对象已不在该工作区中时，`applied` 为 false。

:::note[整个安装的快照在两条通道上都由所有者把关]
`server.backupNow`、`server.listBackups` 和 `server.deleteBackup` 都要求安装
**所有者**（`ServerAuthority.serverOwner`），与 `GET /backup/snapshot` 是同一道
关卡。一份快照会捕获每个工作区的数据库，因此仅仅是一个工作区的管理员，还不足以管理
其它工作区。删除只接受列表中出现的那个时间戳目录名，而不是任意的服务器路径，并且会
移除整个快照（包括未验证的快照）。按工作区进行的导出以及定时备份的下载仍然只要求工作区管理员。
:::

:::note[恢复由服务器所有者负责]
`workspace.import` 和 `POST /backup/restore` 会让服务器接纳一个数据库文件，并把其中的行视为它自己的：仓库关联及其创建者、在主机上运行的环境定义、工作树与日志路径。因此两者都需要服务器所有者（`ServerAuthority.serverOwner`），且该所有者还必须是工作区的所有者。其他任何人，以及在没有记录所有者的主机上的每个调用者，都会被以 `server_owner_required` 拒绝。文件带来的任何触发器、视图、列或约束都不会被采纳。
:::

### `server.listBackups` 的响应

按最新优先，以目录名排序（目录名就是时间戳，因此即使某个快照的清单无法读取，这个顺序
依然成立）。

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

当清单无法读取时，`created_at` 会被省略。顶层的 `bytes` 是整个目录在磁盘上的实际
大小，而不是清单自己汇总出的和——运维人员清理快照时，问的是这个目录占了多少空间，
而不是这次备份原本打算写多少。

每个 `workspaces[].path` 正是 `workspace.import` 接受为 `source_path` 的值。这是
刻意的：“从这个快照恢复这个工作区”*就是*导入操作，因此两者不可能对同一个文件演变出
不同的处理方式。

### `workspace.import` 的校验

在替换任何内容之前，候选文件会被复制到目标旁边的一个暂存文件中并在那里进行检查。被拒绝时不会触碰任何内容，且其类别会以 `data.kind` 携带。

| 条件                                             | 结果                                                          |
| ------------------------------------------------ | ------------------------------------------------------------- |
| 文件不存在 | 拒绝，`import.missing_source` |
| 不是可读的 SQLite 数据库，或未通过 `quick_check` | 拒绝，`import.damaged` |
| 来自快照，且其 SHA-256 与清单中的不同 | 拒绝，`import.checksum_mismatch` |
| 服务器的较新版本写入了它 | 拒绝，`import.newer_schema` |
| 另一个 `application_id`，或没有 `workspace_meta` | 拒绝，`import.foreign_file` |
| 无法被带入本服务器的 schema | 拒绝，`import.schema_mismatch` |
| 它的 webhook 或邀请已指向另一个工作区 | 拒绝，`import.route_conflict` |
| 记录的工作区 id ≠ 目标                            | **允许**。其行会被重新关联到目标。这正是把一个工作区复制或恢复到一个新 id 之下的方式 |
| 记录的安装 id ≠ 本安装                            | **允许**。它的用户 id 属于那次安装，在这里无法解析 |

接受之后，暂存文件会被调整为本服务器的 schema，之后必须与其完全一致。文件不得自行授予的权限会被从中取出：在主机上运行环境定义的审批会被清除；允许或需要提示的操作规则、沙箱执行授权、高于只读的仓库授权、高于成员的角色，以及针对这些角色的邀请，会变成供服务器所有者审阅的暂存项。导入者保留或获得所有者角色。被替换的数据库会以名为 `<timestamp>-pre-restore` 的定时备份保留下来；暂存文件在关闭工作区连接的情况下被重命名到位，`code_index.db` 被删除以便重建，FTS 索引也会被重建。

## 传输路由

上面的导出/导入与快照列表操作都以服务器端路径来表达，只有当服务器就是你自己的机器时，
这才算一个完整的答案。这些形如 HTTP 的路由在**同一条经过身份验证、端到端加密的资源隧道
内部**运送备份字节，与其它敏感资源一样，无论 RPC 连接是直连还是经代理中转。它们不是
公开的 HTTP 文件传输端点：在公开监听器上向其中之一发起请求会返回 `426 Upgrade Required`，
即使来自回环地址也是如此。在加密隧道内，经 Noise 认证的设备必须与 `d` 匹配；处理程序还会
额外校验该设备用其配对 PSK 对其目标字符串所作的签名，以及下面的角色。

| 路由                    | 方法   | 查询参数        | 签名目标                         | 要求                 |
| ----------------------- | ------ | --------------- | -------------------------------- | -------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | 工作区**管理员**     |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | 安装**所有者**       |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | 工作区**管理员**；工作区删除后为安装**所有者** |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | 安装**所有者**，且同时是工作区**所有者**（否则返回 `403` 及 `server_owner_required`） |

`w` 是工作区 id，`n` 是快照或定时备份的目录名，`d` 是发起调用的设备 id，`s` 是签名。在
`/backup/snapshot` 上，`n` 是依据备份列表解析的，而不是直接拼接到备份根目录上，因此这条
路由无法被指向一个列表本不会展示的目录。在 `/backup/stored` 上，它必须是时间戳名称，且
文件必须是该工作区自身备份目录中的真实文件。

| 状态码 | 原因                                                                                |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | 缺少必需的查询参数、备份名称无效、上传正文为空，或上传的文件被拒绝（正文为 `{error, kind}`，且带有 `import.*` 类别） |
| `403`  | 设备未知或已吊销、签名错误，或者调用方不具备该角色                                    |
| `404`  | 此主机上没有备份端口，或者所指的快照、备份或工作区文件不存在                           |
| `405`  | 用 `POST` 以外的方法调用 `/backup/restore`                                            |
| `413`  | 上传正文超过 8 GiB，无论是按声明的 content-length 还是按实际读取的字节数              |
| `426`  | 在公开 HTTP 监听器上对传输路径发起的任何直接请求；请使用已配对客户端的加密资源隧道 |
| `500`  | 导出或归档在服务器端失败                                                              |

三个下载都会返回 `Cache-Control: no-store` 与 `Accept-Ranges: none`。
`/backup/workspace` 和 `/backup/snapshot` 每次请求都会新生成一份**全新的**副本，并在流式
发送完毕后删除它，因此被缓存或被续传的响应会把两次不同导出的字节拼接成一个看起来有效、
实则无效的文件。

`/backup/stored` 是例外：它以 `<workspaceId>-<name>.db` 流式发送定时备份并保留该文件，
因为这个文件就是备份本身。

`/backup/snapshot` 返回 `<name>.zip`，其中的条目都相对于快照根目录，因此解包后会
重现 `manifest.json` + `global.db` + `<workspaceId>/workspace.db`。条目按排序后的
顺序写入，因此同一快照的两次归档会得到完全相同的归档。

`/backup/restore` 会把正文直接流式写入暂存文件，而不是缓冲它；它在读取前和读取过程中
都对大小设限，并且在**每一条**退出路径上都会删除暂存文件，包括被拒绝时。

::::caution[直连与中继使用同一套加密传输]
中继以密文形式承载资源请求、流式响应和上传字节；它无法读取备份内容。服务器端路径仍然是
服务器主机上的路径，而不是中继上的文件。访问仍然需要已配对的设备、目标签名以及适用的
工作区或安装角色。两种传输都不会对生成的备份文件进行静态加密。
::::

## 路径与限制

| 项                       | 值                                                            |
| ------------------------ | ------------------------------------------------------------- |
| 快照                     | `<dataDir>/backups/<timestamp>/`                              |
| 计划性的工作区备份       | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| 工作区导出               | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`      |
| 被恢复替换掉的数据库 | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| 更新改变其格式之前的数据库 | `<dataDir>/pre_upgrade/` 和 `<dataDir>/<workspaceId>/pre_upgrade/`，各自保留最新的两份 |
| 传输暂存                 | `<dataDir>/backups/transfer/`——一块临时工作台，由写入它的那条路由负责清扫 |
| 快照归档文件名           | `<snapshot directory name>.zip`                               |
| 上传上限                 | 每次加密的 `/backup/restore` 上传 8 GiB                        |
| 保留策略                 | 安装快照：手动删除。工作区备份：每周流水线，默认 30 天，或手动删除。已删除工作区的备份：仅手动删除 |

`exports/`、`transfer/` 和 `workspace-backups/` 目录都不是安装快照，也不在
`server.listBackups` 的范围内。只有最后一个目录有计划的保留策略，且仅在其工作区存在期间有效；删除安装快照需要
安装所有者明确操作。
