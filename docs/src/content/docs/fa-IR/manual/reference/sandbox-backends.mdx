:::caution[سندباکس‌شدن یک اجرا به میزبان بستگی دارد]
`cc_server` هنگام بوت یک‌بار تصمیم می‌گیرد عامل‌ها روی این میزبان چگونه اجرا شوند، و این تصمیم تا راه‌اندازی دوباره برقرار می‌ماند:

- **ایزوله‌شده** (`native`): بررسی یک بک‌اند پیدا کرده و `--sandbox` برابر `off` نیست. هر دو درز اعزام پیچیده می‌شوند: CLI مربوط به Claude Code از درگاه سندباکس، و ACP به‌همراه ابزار `bash` هارنس داخلی از مدیر سندباکس.
- **خاموش** (`off`): مالک سرور آن را با `--sandbox off` شروع کرده است. عامل هر عضوی، هر کس که آن را شروع کرده باشد، روی این ماشین بدون ایزوله اجرا می‌شود.
- **در دسترس نیست** (`unavailable`): سندباکس روشن است اما بررسی هیچ بک‌اندی پیدا نکرده (**همیشه Windows**، و Linux یا WSL2 بدون `bwrap` و `socat`). اجرا فقط وقتی شروع می‌شود که فردِ پاسخ‌گو برای آن، [مالک](/fa-IR/راهنمای-کاربر/مفهومها/مجوزدهی/#مالک-سرور) سرور باشد: کسی که آن را خواسته، یا برای خودکارسازی، فردی که خودکارسازی به او وصل است. اجرای هر کس دیگر پیش از صدور اعتبارنامه، گرفتن اجاره یا شروع فرایند رد می‌شود. وقتی هیچ مالکی ثبت نشده باشد، اجرای هیچ‌کس شروع نمی‌شود.

اجرای ردشده با کد `sandbox_unavailable` شکست می‌خورد. برنامه آن را با **عامل‌ها روی این سرور به سندباکس نیاز دارند** نشان می‌دهد: "این سرور سندباکس ندارد، پس فقط مالکش می‌تواند اینجا عامل اجرا کند. مالک می‌تواند سندباکس را نصب کند یا ایزوله‌سازی را برای همه خاموش کند."

اجرایی که بدون سندباکس شروع می‌شود (زیر `off`، یا اجرای خودِ مالک زیر `unavailable`) مستقیماً روی میزبان اجرا می‌شود. ACP و ابزار `bash` هارنس همچنان با پاک‌سازی محیط spawn می‌شوند؛ Claude Code از `NoSandboxAdapter` می‌گذرد و محیط میزبان را به ارث می‌برد. مرزهای باقی‌مانده عبارت‌اند از worktree خودِ اجرا (کپی-در-نوشتن هر جا `rift` عرضه شود؛ `git worktree` روی Windows)، توکن‌های فقط‌خواندنی میزبان کد که به‌ازای هر راه‌اندازی کارگزاری و هنگام برچیدن باطل می‌شوند، پوش‌هایی که باید در دروازهٔ اجرای عامل از قاعدهٔ پوش بگذرند، سیاست فرمان هر حالت، [گاردریل‌های کنش](/fa-IR/راهنمای-کاربر/مفهومها/گاردریلها/) یکپارچه (شکست بسته)، پاک‌سازی محیط در مسیرهای ACP و `bash` هارنس، و سطح ابزاری که حالتش مجاز می‌داند.

ابزارهای فایلی درون‌پردازشی هارنس (read، write، edit، apply patch، search، find، search_files) روی هر میزبان بیرون سندباکس‌اند: آن‌ها در فرایند سرور اجرا می‌شوند، پس تنها `bash` پیچیده می‌شود.

میزبان هرگز جایگزین یک سرور سندباکس‌شده نیست. اگر سرور عامل‌ها را سندباکس می‌کند اما هیچ سندباکسی برای اجرا ندارد، فرایندهای ابزار و فرمان‌های `bash` آن رد می‌شوند، نه اینکه روی میزبان شروع شوند. همین وضعیت فرایندهای کوچکی را هم که دور یک اجرا هستند تعیین می‌کند: کمک‌کننده‌های یک‌باره ACP (عنوان گفتگو، `/btw`، `/handoff`، `/goal`) و آزمون‌های طلایی یک درخواست pull در Review Studio وقتی سرور عامل‌ها را سندباکس می‌کند داخل سندباکس اجرا می‌شوند، زیر `off` بدون ایزوله، و زیر `unavailable` فقط برای درخواستی که مالک سرور پاسخ‌گوی آن است؛ در غیر این صورت کنار گذاشته می‌شوند.
:::

## نمای کلی بک‌اندها

| بک‌اند            | مقدار     | سکو                                           | دسترس‌پذیری                                                                                                                                                                       |
| ----------------- | --------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VM محفظه‌ای        | `microvm` | macOS، Linux، Windows (هایپروایزر microVM)    | مشروط به بررسی روی زمان اجرای microVM؛ به ترمینال‌های تعاملی اعمال می‌شود — پوسته درون یک [ریگ](/fa-IR/راهنمای-کاربر/مفهومها/ریگها/) اجرا می‌شود، نه روی میزبان |
| بومی              | `native`  | macOS (Seatbelt)، Linux و WSL2 (bubblewrap)   | هنگام بوت بررسی می‌شود؛ Linux اجرایی را که به ردهای نوشتن مبتنی بر الگوی نام فایل نیاز دارد رد می‌کند، چیزی که bubblewrap نمی‌تواند اعمال کند |
| بدون جداسازی      | `none`    | همه                                           | پیش‌فرض تجزیه و پیش‌فرض ترمینال؛ اعزام عامل زیر `--sandbox off` از آن استفاده می‌کند، و برای اجراهای خود مالک وقتی هیچ بک‌اندی در دسترس نیست |

`SandboxBackend.fromName` برای یک مقدار ذخیره‌شدهٔ null یا ناشناخته `none` برمی‌گرداند.

**`microvm` تنها بک‌اندی است که مرز کرنل دارد** — بار کاری واقعاً روی
میزبان اجرا نمی‌شود. هرگز در هیچ جهتی تنزل خاموش نیست: درخواست صریحش روی
میزبانی که نمی‌تواند VM بوت کند با شکستی پرصدا از کار می‌افتد («VM خواستم و
لپ‌تاپم را گرفتم» همان تنزلی است که محفظه توان تحملش را ندارد)، و تنها یک
*پیش‌فرض نامشخص* است که به `native` تنزل می‌کند، با خطی در لاگ که همین را
می‌گوید. بک‌اند واقعی نشست به کلاینت گزارش می‌شود و برچسب می‌خورد، پس یک
ترمینال هرگز نمی‌تواند ادعا کند محفظه‌ای است در حالی که روی میزبان اجرا
می‌شود. چرخهٔ عمر، ایمیج‌ها و خروج خودِ VM در
[مرجع ریگ‌ها](/fa-IR/راهنمای-کاربر/مرجع/ریگها/) پوشش داده شده‌اند.

**Windows سندباکس بومی ندارد.** `NativeSandboxAdapter.probe` روی هر میزبانی که macOS یا Linux/WSL2 نباشد `available: false` برمی‌گرداند. پس سرور Windows در وضعیت `unavailable` است: فقط اجراهای عامل مالک سرور شروع می‌شوند، بدون ایزوله، و اجراهای بقیه رد می‌شوند. برای اینکه هر عضوی بتواند آنجا عامل اجرا کند، مالک سرور آن را با `--sandbox off` شروع می‌کند که همهٔ آن‌ها را بدون ایزوله اجرا می‌کند. بک‌اند `microvm` جداگانه است: به بررسی زمان اجرای microVM مشروط است و به ترمینال‌های تعاملی و ریگ‌ها اعمال می‌شود، نه به پیچیدن `bash` روی میزبان.

## نتایج بررسی

بررسی همان چیزی است که اعمال را دروازه‌بندی می‌کند. یک‌بار، هنگام بوت سرور اجرا می‌شود.

| میزبان                                    | `available` | یادداشت / راهنما                                                                      |
| ----------------------------------------- | ----------- | ------------------------------------------------------------------------------------- |
| macOS                                     | `true`      | `sandbox-exec` (Seatbelt) — ایزوله‌سازی namespace، بدون مرز کرنل                       |
| Linux یا WSL2 با `bwrap` و `socat`        | `true`      | bubblewrap — ایزوله‌سازی namespace، بدون مرز کرنل                                       |
| Linux یا WSL2 که هر یک از این دو ابزار را ندارد | `false`     | `requiresInstall: true`، همراه با راهنمای نصب که بسته‌های غایب را نام می‌برد            |
| هر سکوی دیگر                              | `false`     | سندباکس بومی روی این سکو عرضه نمی‌شود                                                  |

سرور نتیجه را روی یک خط راه‌اندازی لاگ می‌کند: `agent sandbox ON` به‌همراه یادداشت؛ `no OS-native agent sandbox on this host` به‌همراه راهنما که اضافه می‌کند فقط اجراهایی شروع می‌شوند که مالک سرور پاسخ‌گوی آن‌هاست؛ یا `agent sandbox DISABLED by --sandbox off`. خط در معرض بودن که هنگام راه‌اندازی چاپ می‌شود همین تصمیم را با `sandbox=native`، `sandbox=off` یا `sandbox=unavailable` دارد. `GET /healthz` هیچ فیلد سندباکسی حمل نمی‌کند.

`--sandbox` / `CC_SERVER_SANDBOX` مقدار `on` (پیش‌فرض) یا `off` را می‌پذیرد. `on` هر اجرا را وقتی میزبان بک‌اندی عرضه کند می‌پیچد، و وقتی عرضه نکند فقط اجراهای مالک را می‌پذیرد. `off` عامل‌های همهٔ اعضا را روی این میزبان بدون ایزوله اجرا می‌کند؛ این انتخاب مالک برای همه است، نه تنظیم هر اجرا.

## بک‌اند بومی

### macOS: Seatbelt

از سازوکار سندباکس Seatbelt اپل استفاده می‌کند (همان سیستمی که App Sandbox در macOS به کار می‌برد).

پروفایل تولیدشده **به‌طور پیش‌فرض مجاز** است (`(allow default)`) و ردها را می‌تراشد، چون یک پروفایل کاملاً رد-به‌طور-پیش‌فرض پوستهٔ تعاملی را غیرقابل‌استفاده می‌کند — فراخوانی‌های dyld، XPC و Mach برای برشمردن بیش از حد زیادند. پیامد عملی این است که عامل هنوز می‌تواند بیشتر میزبان را بخواند؛ checkoutهای ثبت‌شدهٔ شما با ردهای صریح نوشتن و تغییر نام محافظت می‌شوند، نه با نامرئی‌بودن.

- **خواندن فایل‌سیستم**: برای مسیرهای محرمانه (`~/.ssh`، `~/.aws`، `~/.gnupg`، `~/.config/gh`، `~/Library/Keychains` و بقیهٔ مجموعهٔ رد-خواندن) رد می‌شود
- **نوشتن فایل‌سیستم**: به رد بازنشانی می‌شود، سپس اجازه‌های صریح برای زیرمسیرها، در حالی که مسیرهای الزاماً رد‌شده (فایل‌های rc پوسته، `.git/hooks`، پیکربندی Claude، checkoutهای محافظت‌شده) حتی درون ریشهٔ قابل‌نوشتن هم مسدود می‌مانند. `file-write-unlink` روی هر مسیر رد‌شده و اجدادش رد می‌شود، پس یک تغییر نام نمی‌تواند از یک رد-نوشتن بگذرد
- **فرایند**: ردهای `process-exec` برای باینری‌های همیشه‌خطرناک، به‌همراه مسدودسازی اجرای هر چیزی از یک دایرکتوری قابل‌نوشتن. دایرکتوری‌های شناخته‌شدهٔ درخت نصب ابزار زیر پوشهٔ خانگی (کش corepack، npx و `pnpm dlx`، مدیرهای نسخهٔ node، مرورگرهای Playwright، rustup و cargo، Go، fvm و کش pub، pyenv، uv و pipx، rbenv، sdkman، mise، asdf و `~/.local/bin`) زیر این مسدودسازی دوباره باز می‌شوند. دایرکتوری‌های موقت مشترک هم مسدودند. هر نشست در عوض یک `TMPDIR` خصوصی زیر `/private/tmp` می‌گیرد که برنامه‌های ساخته‌شدهٔ آن (یک باینری `go test`، یک ساخت cargo) در آن اجرا می‌شوند. رد‌های همیشه‌خطرناک پس از این مجوزها اعمال می‌شوند
- **شبکه**: محدود به پورت‌های پروکسی درون‌فرایندی به‌همراه DNS — loopback به‌صورت یکسره مجاز نیست و شنود TCP رد می‌شود. سوکت‌های Unix فقط درون `TMPDIR` خصوصی نشست مجازند، که ابزارهایی مثل tsx و Chrome را پوشش می‌دهد که سوکت IPC خود را آنجا نگه می‌دارند؛ عامل SSH شما و سوکت‌های دیگر دور از دسترس می‌مانند. پروکسی‌ها فهرست مجاز دامنهٔ هر نشست را اعمال می‌کنند (به [خروج شبکه](#خروج-شبکه) نگاه کنید)
- **پیکربندی**: پروفایل‌ها به‌ازای هر راه‌اندازی از `SandboxSpec` تولید می‌شوند
- **دستورهای خود سرور**: هیچ فرزند مستقیم پوشه‌ای که سرور برنامه‌ها را از آن اجرا می‌کند (هر ورودی `PATH` و پوشه‌های معمول ابزارهای هر کاربر، مانند `~/.local/bin`، با حل شدن پیوندهای مدیر نسخه مانند `~/fvm/default`) نمی‌تواند ساخته، جایگزین، حذف یا تغییر نام شود، و نه بسته‌ای که یک فرمان پیوندی به آن اشاره می‌کند. ببینید [پوشه‌های فرمان سرور](#پوشههای-فرمان-سرور)
- **فایل‌های راه‌اندازی**: هر مسیر خانگی‌ای که پروفایل خواندنش را رد می‌کند، نوشتنش هم رد می‌شود، و فایل‌های راه‌اندازی پوسته‌ها و نشست‌های کاربر سرور (`.zshenv`، `.zlogin`، `.bash_login`، پیکربندی fish، واحدهای systemd کاربر، ورودی‌های autostart و مانند آن) در هر حالت نوشتنشان رد می‌شود

پیش‌نیازها:

- `sandbox-exec` (`/usr/bin/sandbox-exec`)، بخشی از هر نصب macOS — هیچ ابزار اضافه‌ای لازم نیست

### Linux: bubblewrap

از bubblewrap (`bwrap`) برای ساخت namespaceهای مانت و PID استفاده می‌کند.

- **فایل‌سیستم**: یک namespace مانت می‌سازد که در آن فقط مسیرهای bind‌شده دیده می‌شوند
- **شبکه**: در یک namespace شبکهٔ جداگانه اجرا می‌شود؛ ترافیک از طریق پل‌های سوکت Unixی `socat` به پروکسی‌های میزبان می‌رسد
- **فرایند**: ایزوله‌سازی namespace PID
- **دستورهای خود سرور و فایل‌های راه‌اندازی**: همان حفاظت‌های macOS که به‌صورت bind های bubblewrap بیان می‌شوند. هنوز روی Linux تأیید نشده‌اند، و یک پوشهٔ فرمان گمشده آنجا همچنان ممکن است ساخته شود

پیش‌نیازها:

- نصب `bubblewrap` و `socat` (روی Debian/Ubuntu: `sudo apt-get install bubblewrap socat`)
- پشتیبانی کرنل از namespace (استاندارد در Linux مدرن)

Bubblewrap می‌تواند یک مسیر موجود را سایه بیندازد اما نمی‌تواند یک فایل
*جدید* `.env`، `*.key` یا `*.pem` را درون یک مانت bind قابل‌نوشتن ممنوع
کند. سیاست استاندارد اعزام این ردهای مبتنی بر الگوی نام فایل را الزام
می‌کند، پس اعزام بومی عامل در حال حاضر **روی Linux/WSL2 حتی وقتی بررسی
bubblewrap را پیدا می‌کند هم به‌صورت بسته شکست می‌خورد**. با سیاستی
خاموش‌ضعیف‌تر اجرا نمی‌شود. برای بازگرداندن اعزام بومی Linux به بک‌اندی نیاز
است که قواعد نام فایل را در زمان ساخت اعمال کند. خاموش‌کردن سندباکس یک
انصراف صریح و بدون محدودیت است، نه یک راه‌حل معادل.

در عمل یک سرور Linux یا WSL2 امروز عامل‌ها را به یکی از دو روش اجرا می‌کند. اگر با `--sandbox off` شروع شده باشد، عامل‌های همهٔ اعضا را بدون ایزوله اجرا می‌کند. بدون نصب `bubblewrap` یا `socat`، در وضعیت `unavailable` است و فقط عامل‌های مالک سرور را، بدون ایزوله، اجرا می‌کند. با نصب هر دو ابزار و روشن بودن سندباکس، هر اجرا، حتی اجرای مالک، بسته شکست می‌خورد.

## پوشه‌های فرمان سرور

سرور یک بار، هنگام راه‌اندازی، هر پوشه‌ای را که برنامه‌ها را از آن اجرا می‌کند پیدا می‌کند: هر ورودی `PATH` خودش، پوشه‌های ابزار هر کاربر که بررسی می‌کند (مانند `~/.local/bin`، `~/.bun/bin` و پوشه‌های سراسری npm، yarn و pnpm)، و پوشهٔ واقعیِ پشت هر پیوندی در مسیر (پیوندهای مدیر نسخه مانند `~/fvm/default` یا پیش‌فرض fnm). درون سندباکس، یک عامل نمی‌تواند فرمانی را در آن پوشه‌ها اضافه، جایگزین، حذف یا تغییر نام کند، نه پیوندی که به یکی از آن‌ها می‌رسد، و نه بسته‌ای نصب‌شده را که یک فرمان پیوندی به آن اشاره می‌کند؛ و نمی‌تواند پوشه‌های بالای آن‌ها را تغییر نام دهد. وگرنه یک اجرای سندباکس‌شده می‌توانست برنامه‌ای بکارد که سرور یا فرد بعداً بیرون از سندباکس اجرایش کند.

آنچه این برای یک اجرا تغییر می‌دهد:

- نصب‌های سراسری از درون یک اجرای سندباکس‌شده با "Operation not permitted" شکست می‌خورند: `npm i -g`، `pnpm add -g`، `yarn global add`، `bun add -g`، `corepack enable`، `pipx install`، `uv tool install`، و `cargo install`، `go install` یا `dart pub global activate` وقتی پوشهٔ bin آن‌ها روی `PATH` سرور است.
- تغییر نسخهٔ پیش‌فرض به همان شکل شکست می‌خورد (`fnm default`، `nvm alias default`، `fvm global`)، و همین‌طور ابزاری که خودش را در جا به‌روز می‌کند.
- نصب‌های محلی پروژه (`node_modules/.bin`)، `npx`، `pnpm dlx`، مدیرهای بسته‌ای که corepack مدیریت می‌کند، کش‌های SDK و ساخت‌های عادی همچنان کار می‌کنند.

برای اینکه یک ابزار سراسری به عامل‌ها برسد، آن را روی خود سرور، به‌عنوان کاربر سرور، نصب کنید و سرور را دوباره راه‌اندازی کنید تا فرمان تازه هم محافظت شود. یا آن را در پروژه نصب کنید. فرمانی که پس از شروع سرور نصب شود تنها از راه‌اندازی بعدی کاملاً محافظت می‌شود.

اعمال‌شده و آزموده‌شده روی macOS. روی Linux همان قواعد به‌صورت bind های bubblewrap هستند که هنوز تأیید نشده‌اند. Windows سندباکس ندارد.

## بک‌اند بدون جداسازی

بدون سندباکس. فرایند مستقیماً روی میزبان با دسترسی فایل‌سیستم، شبکه و فرایند خود میزبان اجرا می‌شود. ACP و ابزار `bash` هارنس همچنان پاک‌سازی محیط و سیاست فرمان را می‌گیرند؛ Claude Code از `NoSandboxAdapter` محیط میزبان را به ارث می‌برد. اعزام عامل آن را برای هر اجرا زیر `--sandbox off` به کار می‌برد، و روی میزبانی بدون بک‌اند در دسترس فقط برای اجراهای خود مالک سرور؛ اجرای هر کس دیگر آنجا رد می‌شود. برای یک ترمینال، این پوستهٔ میزبان است که فقط مالک سرور می‌تواند بازش کند.

## ترمینال میزبانی‌شده روی سرور

ترمینال میزبانی‌شده روی سرور فقط برای [مالک](/fa-IR/راهنمای-کاربر/مفهومها/مجوزدهی/#مالک-سرور) سرور پوستهٔ میزبان را باز می‌کند. بقیه یک ترمینال سندباکس‌شده، با محدودیت‌های یک عامل، در دایرکتوری‌های خود فضای کاری می‌گیرند.

چگونگی انتخاب بک‌اند برای یک نشست:

| درخواست | مالک سرور | هر کس دیگر |
| --- | --- | --- |
| هیچ‌چیز | بک‌اند پیش‌فرض سرور | پیش‌فرض، با جای‌گزینی `none` با `native` |
| `none` (پوستهٔ میزبان) | پوستهٔ میزبان | رد می‌شود: پوستهٔ میزبان روی سرور بدون سندباکس اجرا می‌شود |
| `native` | سندباکس بومی، پروفایل مالک | سندباکس بومی، پروفایل عامل |
| `microvm` | VM محفظه‌ای | VM محفظه‌ای |
| نام ناشناخته | رد می‌شود | رد می‌شود |

- **پروفایل مالک.** `$HOME` و دایرکتوری کاری نشست قابل‌نوشتن‌اند، شبکه باز است و خواندن `~/.ssh`، `~/.aws`، `~/.gnupg`، `~/.config/gh` و `~/Library/Keychains` رد می‌شود.
- **پروفایل عامل** (`memberTerminalSandboxConfig`). همان سیاستی که یک عامل در آن فضای کاری زیر آن اجرا می‌شود: نوشتن‌ها در دایرکتوری کاری، یک دایرکتوری اجرای خصوصی، `/tmp` و بخش‌هایی از `$HOME` که یک عامل مجاز به نوشتن در آن‌هاست می‌مانند؛ رازها خواندنی رد می‌شوند؛ شبکه فهرست مجاز خروج عامل است؛ برنامه‌ها فقط از دایرکتوری کاری و زنجیره‌ابزارهای نصب‌شده اجرا می‌شوند.
- ترمینال فقط داخل دایرکتوری‌های خود فضای کاری باز می‌شود. دایرکتوری کاری‌ای که بیرون آن‌ها باشد رد می‌شود، و هرگز با دایرکتوری دیگری جایگزین نمی‌شود.
- فقط فردی که ترمینال را باز کرده می‌تواند آن را بخواند، در آن تایپ کند، اندازه‌اش را عوض کند یا ببندد. برای هر کس دیگر، شناسهٔ آن ناشناخته به نظر می‌رسد.
- `microvm` که صریحاً روی میزبانی بدون سرویس ریگ درخواست شود، شکست می‌خورد و تنزل نمی‌کند. پیش‌فرض `microvm` روی چنین میزبانی به `native` تنزل می‌کند و این را در گزارش می‌گوید.

توکن فقط‌خواندنی و دروازهٔ پوش برای ترمینال‌ها اعمال نمی‌شوند: آن‌ها دغدغهٔ اعزام‌اند. اگر پیچش پشتیبانی نشود، نشست شکست می‌خورد به‌جای اینکه روی یک نشست پوستهٔ میزبان نشان سندباکس را نمایش دهد.

## خروج شبکه

وقتی سندباکسی راه‌اندازی می‌شود، دسترسی شبکهٔ خروجی توسط پروکسی‌های درون‌فرایندی اعمال می‌شود، نه با قواعد فایروال کرنل. اجرایی که سندباکس نشده باشد (هر اجرا زیر `--sandbox off`، یا اجرای مالک روی میزبانی بدون بک‌اند) هیچ‌کدام از این‌ها را ندارد: فرایندی که راه می‌اندازد دقیقاً همان‌طور که کاربر سرور دسترسی داشت به شبکه می‌رسد.

- زمان اجرای سندباکس یک پروکسی HTTP/HTTPS و یک پروکسی SOCKS5 روی `127.0.0.1` درون فرایند `cc_server` اجرا می‌کند، **یک جفت به‌ازای هر نشست محدودشده** (`http_proxy.dart`، `socks_proxy.dart`). اجراهای هم‌زمان یک جفت را به اشتراک نمی‌گذارند.
- فرایندهای سندباکس‌شده متغیرهای محیطی پروکسی را دریافت می‌کنند (`HTTP_PROXY`/`HTTPS_PROXY` → پروکسی HTTP، `ALL_PROXY` → پروکسی SOCKS؛ `GIT_SSH_COMMAND` مسیر git روی SSH را از پروکسی SOCKS می‌گذراند). روی Linux namespace شبکه جدا است، پس پروکسی‌ها تنها راه بیرون‌اند؛ روی macOS سندباکس loopback میزبان را به اشتراک می‌گذارد و مستقیم با آن‌ها حرف می‌زند.
- میزبان هدف هر اتصال با فهرست مجاز دامنهٔ نشست تطبیق داده می‌شود؛ هر چیز دیگری رد می‌شود. دو شکل وایلدکارد، هر کدام با دقیقاً یک `*`: یک `*.example.com` پیشرو با هر زیردامنه‌ای تطبیق می‌یابد (شامل `a.b.example.com`) اما نه با خود دامنهٔ ریشه؛ یک `bedrock.*.amazonaws.com` با برچسب میانی دقیقاً با یک برچسب تطبیق می‌یابد (`bedrock.us-east-1.amazonaws.com`، نه `bedrock.evil.attacker.amazonaws.com`).
- فهرست مجاز به‌ازای هر نشست از خط پایهٔ گزینش‌شده حل می‌شود (`kBaselineAllowedDomains`: ارائه‌دهندگان LLM، میزبانی Git، رجیستری‌های بسته)، به‌همراه دامنه‌های GitHub (`kGithubDomains`)، به‌علاوهٔ `SandboxSpec.egressAllowlist`. مسیر اعزام هرگز ورودی‌های اضافی `egressAllowlist` را نمی‌فرستد، پس در عمل هر اجرا خط پایه به‌علاوهٔ GitHub را می‌گیرد.
- یک فهرست رد ثابت (`kBaselineDeniedDomains`: نقاط پایانی فرادادهٔ ابری، مقصدهای تلمتری) بر همهٔ مجوزها تقدم دارد.
- `networkEnabled: false` همچنان پروکسی‌های هر نشست را شروع می‌کند، اما فهرست مجاز خالی است، پس هر اتصال خروجی رد می‌شود. اعزام این مقدار را در شروع اجرا از قاعدهٔ **دسترسی به شبکه** تعیین می‌کند: رد شبکه را خاموش می‌کند، اجازه و ابتدا بپرس آن را روشن نگه می‌دارند.

## SandboxSpec

specی که به `SandboxPort.launch` داده می‌شود:

| فیلد              | نوع                                         | توضیح                                                                                                                                                        |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sessionId`       | `String`                                    | شناسهٔ پایدار نشست (معمولاً شناسهٔ فضا)                                                                                                                       |
| `workspaceId`     | `String`                                    | شناسهٔ فضای کاری مالک                                                                                                                                          |
| `agentId`         | `String?`                                   | عاملی که در حال حاضر به سندباکس بسته شده، در صورت وجود                                                                                                        |
| `bindMounts`      | `List<SandboxBindMount>`                    | مانت‌های میزبان→مهمان؛ سندباکس فقط مسیرهای میزبانی را می‌بیند که اینجا فهرست شده‌اند                                                                           |
| `networkEnabled`  | `bool` (پیش‌فرض `true`)                     | در اعزام از قاعدهٔ خروج شبکه تعیین می‌شود (فقط وقتی به رد حل شود خاموش است). با خاموش بودن، پروکسی‌های هر نشست همچنان شروع می‌شوند اما فهرست مجاز خالی است، پس هر اتصال خروجی رد می‌شود |
| `egressAllowlist` | `List<String>` (پیش‌فرض `[]`)               | دامنه‌های خروج مجاز اضافی؛ وایلدکاردها پشتیبانی می‌شوند (`*.example.com`، به‌همراه شکل میانی یک‌برچسبی). اعزام هرگز این را پر نمی‌کند، پس یک اجرای پیچیده خط پایهٔ گزینش‌شده به‌علاوهٔ دامنه‌های GitHub را می‌گیرد |
| `guestWorkdir`    | `String?`                                   | دایرکتوری کاری پیش‌فرض درون سندباکس؛ فراخوانی‌های تک `exec` می‌توانند آن را بازنویسی کنند                                                                      |
| `mode`            | `Mode` (پیش‌فرض `chat`)                     | قواعد نوشتن فایل‌سیستم را می‌تراشد: `chat` مانت‌های bind را قابل‌نوشتن نگه می‌دارد؛ `review`، `plan` و `orchestrate` فقط‌خواندنی‌اند                              |
| `protectedPaths`  | `List<String>` (پیش‌فرض `[]`)               | مسیرهای میزبان که هرگز نباید درون سندباکس، در هیچ حالتی، قابل‌نوشتن باشند                                                                                      |
| `runnerStateDirs` | `List<String>` (پیش‌فرض `[]`)               | دایرکتوری‌های میزبان که رانر وضعیت خودش را در آن‌ها نگه می‌دارد، در هر حالت قابل‌نوشتن (یک `CLAUDE_CONFIG_DIR` مدیریت‌شده با Control Center مورد کنونی است)       |
| `execGrantRoots`  | `List<String>` (پیش‌فرض `[]`)               | درخت‌های دایرکتوری تأییدشدهٔ اپراتور که مسدودسازی exec دایرکتوری قابل‌نوشتن را روی macOS بازگشایی می‌کنند. Linux آن‌ها را نادیده می‌گیرد — bwrap هیچ مسدودسازی execی روی `$HOME` برای بازگشایی ندارد |

`protectedPaths` نگه‌دارندهٔ checkoutهای اصلی مخزن‌های ثبت‌شده است که به‌ازای هر اعزام از مخزن‌های فضای کاری حل می‌شوند. عامل‌ها منحصراً در worktreeهای کپی-در-نوشت هر گفتگو کار می‌کنند، پس اصل‌ها هرگز نباید از درون سندباکس قابل‌نوشتن باشند — روی macOS، مجوز نوشتن یکسرهٔ `$HOME` در Seatbelt در غیر این صورت آن‌ها را از طریق `bash` قابل‌نوشتن رها می‌کرد. آن‌ها در هر حالت، از جمله `chat`، به مجموعهٔ رد-نوشتن رازها می‌پیوندند.

هر مسیر رد-خواندن و رد-نوشتن در هر دو صورت نوشتاری‌اش منتشر می‌شود: صورت تحت‌اللفظی و صورت حل‌شدهٔ symlink. کرنل یک قاعدهٔ رد را در برابر مسیر حل‌شده تطبیق می‌دهد، پس قاعده‌ای که در برابر یک مسیر symlinkدار نوشته شده باشد هرگز فعال نمی‌شود — و روی macOS این حالت رایج است نه نامتعارف، چون `/tmp` به `/private/tmp` و `/var/folders/…` به `/private/var/folders/…` حل می‌شود. ورودی‌هایی که `*` یا `?` دارند به‌عنوان glob در نظر گرفته می‌شوند و دست‌نخورده می‌مانند؛ مسیری که حل نمی‌شود همان‌طور که نوشته شده نگه داشته می‌شود.

## SandboxHandle

بازگشتی از `SandboxPort.launch`:

| فیلد        | نوع                    | توضیح                                                                    |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | شناسهٔ نشست                                                               |
| `backend`   | `SandboxBackend`       | کدام بک‌اند در حال اجراست                                                 |
| `state`     | `SandboxState`         | وضعیت چرخهٔ عمر                                                           |
| `error`     | `Object?`              | وقتی `state` برابر `error` باشد تنظیم می‌شود                              |
| `details`   | `Map<String, Object?>` | حسابداری خصوصی آداپتور (دایرکتوری کاری، PID، مسیر پروفایل و غیره)         |

### SandboxState

| وضعیت       | توضیح                                        |
| ----------- | -------------------------------------------- |
| `created`   | spec ساخته شده اما VM هنوز راه نیفتاده است   |
| `warm`      | در حال اجرا و آماده برای اجرای فرمان‌ها       |
| `active`    | در حال اجرای یک فرمان                        |
| `suspended` | متوقف‌شده / نقطه‌گذاری‌شده روی دیسک برای صرفه‌جویی در RAM |
| `destroyed` | برچیده شده؛ دستگیره دیگر معتبر نیست          |
| `error`     | راه‌اندازی شکست خورد — `SandboxHandle.error` را ببینید |
