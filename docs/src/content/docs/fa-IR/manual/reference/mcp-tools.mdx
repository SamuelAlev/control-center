`cc_server` یک رجیستری ابزار MCP (JSON-RPC 2.0) را میزبانی می‌کند که روی پورت اصلی سرور (پیش‌فرض `9030`) در `POST /mcp` و `GET /sse` سرو می‌شود؛ نسخهٔ پروتکل `2024-11-05` است. هر کارخواه به همان رجیستری می‌رسد: برنامهٔ رومیزی، نسخهٔ وب، کارخواه‌های بیرونی MCP و زمان اجرای داخلی عامل. سرورهای بیرونی MCP را می‌توان به‌صورت یک لایهٔ پویا به همان رجیستری پل زد.

## اندازهٔ رجیستری

| سنجه                                                                                       | شمار |
| ------------------------------------------------------------------------------------------ | ----- |
| ابزارهای ثبت‌شده توسط `cc_server`                                                          | ۱۱۰   |
| از `packages/cc_mcp`                                                                       | ۱۰۸   |
| از `packages/cc_mcp_client` (کشف ابزار)                                                    | ۲     |
| ثبت‌شده در رجیستری پایه (`server_mcp_registry.dart`)                                        | ۶۳    |
| ثبت‌شده پس از بوت، هم‌زمان با بالا آمدن سرویس‌هایشان (`cc_server_runtime.dart`)              | ۴۷    |
| از ۶۳ ابزار رجیستری پایه، مشروط به یک مخزن گراف کد                                          | ۵     |

پنج ابزار گراف کد تنها زمانی ثبت می‌شوند که میزبان یک مخزن گراف کد به `buildServerMcpRegistry` بدهد. `cc_server` همیشه یکی می‌فرستد، پس هر ۱۱۰ ابزار در باینری عرضه‌شده زنده‌اند.

رجیستری کامل در `tools/list` اعلام می‌شود، بدون هیچ دروازه‌گذاری کشف. ویرایش‌های تیکت ابزارهایی نوعدارند.

:::note[کارخواه‌های بیرونی همیشه کل کاتالوگ را می‌بینند]
`tools/list` هرگز پیراسته نمی‌شود. کارخواه‌های MCP نام ابزارها را در برابر نسخهٔ کش‌شدهٔ خودشان از همان فهرست اعتبارسنجی می‌کنند و هر چیزی را که در آن فهرست نباشد، بی‌آنکه از سرور بپرسند، رد می‌کنند؛ پس ابزاری که آنجا پنهان شود، به‌جای تنها ساکت‌بودن، دست‌نیافتنی است.

**هارنس داخلی** فرق دارد: در هر درخواست تنها زیرمجموعه‌ای ساکن از تعریف‌ها را بار می‌کند و بقیه را در نخستین استفاده می‌کشد؛ این رفتاری در سمت هارنس است و این رجیستری را تغییر نمی‌دهد. [بافت ابزار و کش پرامپت(/fa-IR/راهنمای-کاربر/مفهومها/بافت-ابزار) را ببینید.
:::

:::note[هر کلاس ابزار ثبت می‌شود]
هر فایل منبعی زیر `packages/cc_mcp/lib/src/tools/` ابزاری است که یک عامل می‌تواند
فراخوانی کند. اگر کلاس ابزاری تازه توسط هیچ‌چیز ساخته نشود،
`packages/cc_server_core/test/mcp_tool_registration_ratchet_test.dart`
بیلد را شکست می‌دهد.
:::

## پارامترهای مشترک

### `workspace_id`

روی هر ابزاری که به دادهٔ محدود به فضای کاری دست می‌زند **الزامی** است. `workspace_id` گم یا نامعتبر خطای صریحی برمی‌گرداند و مقداری که با فضای کاری موجودیت هدف نمی‌خواند، به‌جای نادیده‌گرفتن بی‌صدا، رد می‌شود. روی ابزارهای واقعاً سراسری آن را حذف کنید: `list_workspaces` و شش ابزار خوراک خبری (`list_feeds`، `list_articles`، `get_article`، `set_article_read`، `set_article_saved`، `refresh_feeds`)، که روی فهرست خوراک‌های هر-کاربرِ مالک سرور سوار می‌شوند. ابزارهای کشف (`search_tool_bm25`، `list_my_tools`) آن را اختیاری می‌گیرند تا بتوانند فراخوانی‌پذیری را بر پایهٔ حالت گفتگو دسته‌بندی کنند. وقتی سرور یک عامل را اعزام می‌کند، فضای کاری سمت سرور تحمیل می‌شود، پس عامل نمی‌تواند با فرستادن شناسه‌ای بیگانه به فضای کاری دیگری برسد.

## کشف ابزار

هر دو از `cc_mcp_client` می‌آیند، نه `cc_mcp`، و هر دو نگهبان حالت را می‌پرسند تا گزارش دهند در حالت گفتگوی _کنونی_ چه چیزی فراخوانی‌پذیر است.

| ابزار              | توضیح                                                                                                                        |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `search_tool_bm25` | جست‌وجوی کاتالوگ ابزار با کلیدواژه؛ ابزارهای منطبق، اسکیمای آرگومان‌هایشان و اینکه هرکدام همین حالا فراخوانی‌پذیر است یا نه را برمی‌گرداند |
| `list_my_tools`    | فهرست‌کردن ابزارهای فراخوانی‌پذیر در همین گفتگو، پالایش‌شده بر پایهٔ حالت آن                                                     |

ابزار کشف سومی، **`search_tools`**، تنها درون هارنس داخلی وجود دارد و بخشی از این رجیستری MCP نیست. سطح ابزار خودِ اجرا را رتبه‌بندی می‌کند و برخلاف `search_tool_bm25`، اسکیمای آنچه می‌یابد را **بارگذاری** می‌کند تا عامل بتواند در نوبت بعدی‌اش یک تطبیق را فراخوانی کند. عامل‌های روی هارنس باید آن را ترجیح دهند؛ کارخواه‌های MCP `search_tool_bm25` را دارند.

## پیام‌رسانی و واگذاری میان عامل‌های همتا

عامل‌ها از طریق فضاها با یکدیگر گفتگو می‌کنند (ماندگار و در فهرست اعضا دیدنی). `ask_agent` درخواست/پاسخ است با مهلت زمانی الزامی؛ `delegate_task` سمت سرور با سقف عمق، تشخیص چرخه، پاکت بودجه و سقف خودمختاری دروازه‌بانی می‌شود.

| ابزار           | توضیح                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------- |
| `send_to_agent` | فرستادن یک پیام یک‌طرفه به عاملی دیگر، با نشانی `to_agent_id` یا `to_agent_name` دقیق          |
| `ask_agent`     | پرسیدن پرسشی از عاملی دیگر و انتظار برای پاسخش، یا پایان مهلت                                   |
| `delegate_task` | واگذاری یک کار به عاملی دیگر به‌صورت یک تیکت فرزند ردیابی‌شده                                    |
| `consult_agent` | افزودن متخصصی با بهترین تطبیق بر پایهٔ مهارت‌ها به فضا و اعزام آن با یک شرح مأموریت متمرکز       |
| `todo_read`     | خواندن چک‌لیست کار ماندگارشدهٔ این گفتگو                                                        |

تنها زمانی ثبت می‌شوند که میزبان یک مخزن گراف کد عرضه کند. این نمایه مجموعهٔ گرامرهای عرضه‌شده را پوشش می‌دهد (Dart، JS/TS، PHP، Python، Rust، Zig، C/C++، Go، Java، Ruby، C#، Swift، Kotlin، R، Assembly، MATLAB، Ada)؛ نمادهای هر زبان دیگری حاضر نیستند.

| ابزار          | توضیح                                                                               |
| -------------- | ----------------------------------------------------------------------------------- |
| `search_code`  | جست‌وجوی نمادهای نمایه‌شده با نام، امضا و توضیح مستند (ترکیبی BM25 + معنایی)          |
| `code_symbol`  | جستن نمادها با نام دقیق؛ `file:line` و امضا را برمی‌گرداند                            |

## ابزارهای محفظه (ریگ)

ماشین‌های یک‌بارمصرف — یک مرورگر یا میزکار Linux محفظه‌ای، یک شبیه‌ساز Android،
یا یک شبیه‌ساز iOS — را از درون یک اجرا برانید. پس از بوت و بدون قید و شرط ثبت
می‌شوند: اینکه ماشینی واقعاً می‌تواند بوت شود، پرسشی کاوشی است که ابزارها در هر
فراخوانی پاسخ می‌دهند. فراخوانی‌های تکراری در یک گفتگو یک ماشین را دوباره به کار
می‌گیرند؛ نماگرفت‌ها به‌صورت محتوای تصویری با بودجهٔ یک تصویر در هر نتیجه برمی‌گردند و
محتوای صفحه/رابط کاربری استخراج‌شده به‌عنوان دادهٔ نامطمئن حصار می‌شود. چهار ابزار
use به‌همراه `rig_close` [کلاس کنش(/fa-IR/راهنمای-کاربر/مفهومها/گاردریلها/)
`enclosureControl` را اعلام می‌کنند
(ابزارهای use همچنین `networkEgress` و `processSpawn` را اعلام می‌کنند؛ `mobile_use` و
`ios_use` هم `packageInstall` را)، پس حالت‌های فقط‌خواندنی آن‌ها را رد می‌کنند. `rig_list`
هیچ‌کدام را اعلام نمی‌کند — تنها وضعیت فضای کاری را می‌خواند. واژگان کامل فعل‌ها به‌ازای هر سطح در
[مرجع ریگ‌ها(/fa-IR/راهنمای-کاربر/مرجع/ریگها/#action-verbs) آمده است.

| ابزار          | توضیح                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `computer_use` | راندن یک میزکار Linux در یک VM محفظه‌ای: جابه‌جایی، کلیک، کشیدن، پیمایش، تایپ، تغییر اندازه، بریده‌دان، نماگرفت                          |
| `browser_use`  | راندن یک Chromium، Firefox یا WebKit بی‌سر (`engine`): پیمایش، کلیک، پرکردن، استخراج (a11y/DOM/کنسول)، بریده‌دان، نماگرفت            |
| `mobile_use`   | راندن Android روی ADB: بررسی/ورود، نماگرفت، نصب/شروع/توقف/بازنشانی/حذف برنامه‌ها، پیوندهای عمیق و فرمان‌های دستگاه به‌شکل argv        |
| `ios_use`      | راندن شبیه‌ساز iOS از طریق WebDriverAgent/CoreSimulator: بررسی/ورود، نماگرفت، نصب/شروع/توقف/حذف برنامه‌ها، پیوندهای عمیق و فرایندهای شبیه‌ساز به‌شکل argv |
| `rig_list`     | فهرست‌کردن ریگ‌های یک فضای کاری با سطح، وضعیت، اندازهٔ نمایشگر و کنترل‌کننده                                                       |
| `rig_close`    | نابودکردن یک ریگ و دور انداختن وضعیت ماشین تحت مالکیت آن                                                                         |

## چیزهایی که از طریق MCP عرضه نمی‌شوند

تقویم و جلسه‌ها هیچ ابزار MCP‌ای ندارند. عامل‌ها نمی‌توانند تقویم، جلسه‌ها، رونوشت‌ها، آیتم‌های کنشی یا تصمیم‌های شما را بخوانند. خلاصه‌ای که آیتم‌های کنشی و تصمیم‌ها را تولید می‌کند، به‌صورت پایپ‌لاین توکار [`meeting_summary`(/fa-IR/راهنمای-کاربر/مفهومها/جلسه-ها/) اجرا می‌شود، نه به‌صورت ابزاری که یک عامل بتواند فراخوانی کند.

## دروازه‌گذاری ابزار بر پایهٔ حالت

دروازه‌گذاری دو بار از یک جدول (`ModeToolPolicy`) اعمال می‌شود: یک‌بار در اعزام‌کنندهٔ MCP برای آداپتور Claude Code و یک‌بار در رجیستری هارنس داخلی. یک فراخوان مسدودشده دلیل را برمی‌گرداند.

| حالت          | سطح ابزار                                                                                                                                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat`        | هر ابزار ثبت‌شده؛ بدون فهرست مجاز                                                                                                                                                                                                  |
| `plan`        | یک فهرست مجاز دست‌چین‌شده. بدون نوشتن در worktree و بدون افعال تیکتی `create` / `assign` / `delegate`، اما حافظه، آرتیفکت‌ها، کارها، `submit_plan`، `exit_plan_mode` و افعال تکمیل تیکت روی تیکت اعزام‌شده مجازند                    |
| `review`      | یک فهرست مجاز دست‌چین‌شده: مشارکت در بازبینی، ارتباطات، واکش‌های زمینهٔ فقط‌خواندنی و مجموعهٔ کامل افعال تیکت، از جمله `create_ticket` و `assign_ticket`                                                                              |
| `orchestrate` | یک فهرست مجاز دست‌چین‌شده: ابزارهای پژوهش و خواندن به‌همراه `propose_orchestration`، `create_playbook` و `run_playbook`. استخدام، تجزیه و تکمیل تیکت پس از تأیید و به‌صورت قطعی رخ می‌دهند، هرگز در میانهٔ اجرا                       |

مجاز در هر حالت، صرف‌نظر از فهرست مجاز:

| مجموعه             | ابزارها                                                                                                                                                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| حافظه و آرتیفکت‌ها | `search_memory`, `propose_fact`, `propose_policy`, `supersede_fact`, `supersede_policy`, `record_observation`, `update_my_notes`, `get_my_notes`, `list_memory_domains`, `list_policies`, `publish_artifact`, `revise_artifact`, `list_artifacts`, `get_artifact` |
| گراف کد            | `search_code`, `code_symbol`, `code_callers`, `code_callees`, `code_impact`                                                                                                                                                                                       |
| سازوکار اجرا       | `search_tool_bm25`, `list_my_tools`, `todo_write`, `todo_read`                                                                                                                                                                                                    |

قرارداشتن در یک فهرست مجاز، ابزاری را فراخوانی‌پذیر نمی‌کند، و عکس آن هم درست است: قابلیت پرسیدن از اپراتور یک ابزار **هارنس** (`ask_user`) است، پس هرگز اصلاً در این کاتالوگ MCP ظاهر نمی‌شود.

## ابزارهای دروازه‌بندی‌شده با تأیید

یک ابزار می‌تواند `requiresApproval` را اعلام کند. آن‌گاه اعزام‌کننده یک `ApprovalPayload` می‌سازد و آن را پیش از اجرای ابزار از طریق `ConfirmationPort` رو می‌کند؛ `cc_server` آن درگاه را سیم‌کشی می‌کند، پس این دروازه زنده است.

ابزارهای ثبت‌شده‌ای که آن را اعلام می‌کنند: `create_ticket`، `update_ticket`، `assign_ticket`، `reassign_ticket`، `close_ticket`، `ticket_relation`، `create_goal`، `update_goal_progress`، `create_approval`، `decide_approval`، `comment_approval`، `create_work_product`، `save_work_product_revision`، `create_runtime_profile`، `install_skill`، `update_skill`.

به‌طور مستقل، گاردریل‌های کنش یکپارچه هر ابزاری را که مجموعهٔ `ActionClass` ناتهی اعلام کند، دروازه‌بانی می‌کنند. تصمیم `prompt` بدون هیچ تأییدکنندهٔ متصل، رد می‌شود. [گاردریل‌ها(/fa-IR/راهنمای-کاربر/مفهومها/گاردریلها/) را ببینید.

## قابلیت‌هایی که هیچ ابزاری پشتشان نیست

هر قابلیتی در محصول برای یک عامل قابل‌دسترس نیست. این‌ها هیچ ابزاری
ندارند، پس نامی که ممکن است جای دیگری به آن برخورده باشید، «unknown tool» برمی‌گرداند:

| قابلیت                                     | به‌جای آن کجا زندگی می‌کند                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| استخدام، اخراج یا ویرایش یک عامل            | رابط کاربری عامل‌ها. هیچ ابزار `hire_agent` / `fire_agent` / `update_agent` وجود ندارد             |
| ساختن یک فضای کاری                          | `workspace.upsert` روی RPC، که مالکیت را می‌کارد و مهر می‌زند                                      |
| پروژه‌ها (ساخت / فهرست / به‌روزرسانی / فایل)  | رابط کاربری تیکت‌ها. پروژه‌ها سطحی برای اپراتورند — [پروژه‌ها(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/پروژه-ها/) را ببینید |
| پرسیدن یک پرسش مسدودکننده از اپراتور        | ابزار `ask_user` هارنس، نه MCP. یک فرم در گفتگو رندر می‌کند و تا آمدن پاسخ مسدود می‌ماند           |
| عیب‌یابی هر عامل                             | هیچ. `doctor` وجود ندارد — [عیب‌یابی عامل(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/عیبیابی-عامل/) را ببینید |
| تقویم و جلسه‌ها                              | RPC تنها برای کارخواه‌های انسانی (بالا را ببینید)                                                 |
