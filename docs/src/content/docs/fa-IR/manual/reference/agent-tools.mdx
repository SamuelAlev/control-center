این‌ها ابزارهایی **مقید به سرور** هستند که زمان اجرای عامل داخلی مستقیماً ثبت می‌کند — سرور زبان، جست‌وجوی ساختاری، اشکال‌زدا، کرنل‌ها، اسکریپت‌های حالت کد، پرسش‌ها و کنترل کارگر — در برابر [ابزارهای MCP](/fa-IR/راهنمای-کاربر/مرجع/ابزارهای-mcp/) که پل می‌زند و ابزارهای عمومی فایل، جست‌وجو و شل از زمان اجرای هارنس. این‌ها روی رجیستری MCP نیستند: یک کارخواه بیرونی MCP آن‌ها را نمی‌بیند، چون هرکدام به یک منبع زندهٔ سمت سرور مقید است — یک فرایند سرور زبان، یک آداپتور اشکال‌زدا، یک مفسر — که به یک اجرا تعلق دارد.

هر ابزار اینجا تنها زمانی ثبت می‌شود که منبع پشتیبانش برای اجرا سیم‌کشی شده باشد — یک ناظر سرور زبان یا اشکال‌زدایی، یک تجزیه‌گر tree-sitter، یک کارخانهٔ کرنل، یک پورت پرسش، یک فهرست vibe. تشخیص یک سرور زبان یا آداپتور اشکال‌زدا برای *همین چک‌اوت* بررسی‌ای جداگانه و دیرتر است (`status` / `adapters`): آن ابزارها روی سطح می‌مانند تا عامل بتواند بپرسد چرا هیچ‌چیز قابل استفاده نیست، به‌جای اینکه حدس بزند.

## رده‌های تأیید

هر ابزار یک رده اعلام می‌کند، و رده تعیین می‌کند **کدام سطح‌ها آن را می‌بینند** — نه فقط اینکه آیا پرامپت می‌دهد یا نه. حالت برنامه و زیرعامل‌های فقط‌خواندنی تا `read` سقف‌گذاری شده‌اند، پس ابزاری در ردهٔ `write` یا `exec` به‌کل از شمای آنان غایب است.

| رده | معنا | ابزارهای اینجا |
| ------- | -------------------------------------- | -------------------------------------------------- |
| `read`  | بدون اثر جانبی                         | `lsp`، `ast_grep`، `ask_user`، `repl`، پنج `vibe_*` |
| `write` | فایل‌ها را تغییر می‌دهد                 | `lsp_rename`، `ast_edit`، `resolve`                |
| `exec`  | یک فرایند را آغاز یا کنترل می‌کند      | `debug`، `eval`                                    |

## مستقیم، فقط از اسکریپت یا با نخستین استفاده بار می‌شود

وقتی سرور بتواند اسکریپت اجرا کند، یک اجرا چند ابزار را مستقیم فراخوانی می‌کند و بقیه را از یک اسکریپت [`repl`](#repl--اجرای-اسکریپتی-که-ابزارهای-شما-را-فراخوانی-میکند) می‌رساند؛ برای قاعدهٔ کامل [حالت کد](/fa-IR/راهنمای-کاربر/مفهومها/حالت-کد/#ابزارهایی-که-عامل-مستقیم-فراخوانی-میکند) را ببینید. برای ابزارهای این صفحه:

| ابزار | با `repl` | بدون `repl` |
| ---- | ----------- | -------------- |
| `repl` | مستقیم | موجود نیست |
| `ask_user` | مستقیم | مستقیم |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | فقط از یک اسکریپت | با نخستین استفاده بار می‌شود |
| `eval` | با نخستین استفاده بار می‌شود (یک اسکریپت نمی‌تواند آن را فراخوانی کند) | با نخستین استفاده بار می‌شود |
| `vibe_*` | مستقیم در حالت vibe، هرگز از یک اسکریپت | مستقیم در حالت vibe |

ابزاری که با «فقط از یک اسکریپت» مشخص شده، وقتی سرور نتواند اسکریپت‌های یک اجرا را اجرا کند، با نخستین استفاده بار می‌شود ([وقتی اسکریپت‌ها نمی‌توانند اجرا شوند](/fa-IR/راهنمای-کاربر/مفهومها/حالت-کد/#وقتی-اسکریپتها-نمیتوانند-اجرا-شوند)).

## `lsp` — پرس‌وجوهای سرور زبان

وقتی اجرا یک ناظر سرور زبان و یک پوشهٔ کاری داشته باشد ثبت می‌شود. اینکه یک سرور واقعاً بتواند پاسخ دهد، در زمان فراخوانی به‌صورت یک **اشتراک** تشخیص داده می‌شود: هم باید نشانگر ریشه وجود داشته باشد *و* هم باینری سرور قابل یافتن باشد. هر یک به‌تنهایی یعنی هیچ سروری آغاز نمی‌شود — `status` همین را می‌گوید — نه یک حدس بی‌صدا.

سرورها فقط از جدول داخلی می‌آیند؛ فایل `lsp.json` مخزن خوانده نمی‌شود. در اجرای ایزوله، هر اجرا نشست سرور زبان خودش را دارد، پس سرورها با هر اجرا دوباره آغاز می‌شوند. باینری‌های محلی پروژه (`node_modules/.bin`) فقط وقتی استفاده می‌شوند که اجرا ایزوله باشد، و ریشهٔ پروژه هرگز بالاتر از پوشهٔ کاری اجرا حل نمی‌شود.

موقعیت‌ها با `line` به‌علاوهٔ یک زیررشتهٔ `symbol` نشانی می‌شوند، هرگز با ستون. مدلی که از او ستون بخواهند، حدس می‌زند، و یک حدس غلط به نماد دیگری در همان خط می‌رسد — پاسخی که درست به نظر می‌رسد و دربارهٔ چیز دیگری است. حذف `symbol` در یک کنش ناوبری یک خطاست، نه حدس زدن ستون نخست.

| کنش | آرگومان‌ها | برمی‌گرداند |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (یا `"*"`)                | خطاها و هشدارها؛ `"*"` به‌جایش بررسی‌کنندهٔ پروژه را اجرا می‌کند |
| `definition`      | `file`, `line`, `symbol`         | جایی که نماد اعلان شده است                 |
| `type_definition` | `file`, `line`, `symbol`         | جایی که نوعش اعلان شده است                 |
| `implementation`  | `file`, `line`, `symbol`         | پیاده‌سازی‌های عینی                         |
| `references`      | `file`, `line`, `symbol`         | هر کاربرد، حداکثر ۵۰ مورد                  |
| `hover`           | `file`, `line`, `symbol`         | امضا و کامنت مستندات                       |
| `symbols`         | `query` یا `file`                | جست‌وجوی فضای کاری با `query` (حداکثر ۱۰۰ مورد)؛ نمادهای سند با `file` (حداکثر ۲۰۰ مورد) |
| `code_actions`    | `file`, `line`, `symbol`         | اصلاح‌های سریعی که سرور عرضه می‌کند        |
| `status`          | —                                | کدام سرورها در حال اجرا هستند، و برای کدام ریشه‌ها |
| `reload`          | —                                | سرور را برای این ریشه دوباره راه‌اندازی می‌کند |

### پیام‌های تشخیصی هنگام نوشتن

سود ماجرا خودِ ابزار نیست. `write`، `edit` و `apply_patch` **پیچیده شده‌اند**: پس از نوشتن، فایل از سرور زبان همگام و ذخیره می‌شود، و تنها پیام‌های تشخیصی **تازه‌معرفی‌شده** در نتیجهٔ ابزار گنجانده می‌شوند. عامل همان لحظه‌ای که بیلد را شکسته است می‌فهمد که شکسته، بدون اینکه لازم باشد یادش باشد که بپرسد.

پیام‌های تشخیصی‌ای که پیش‌تر گزارش شده‌اند، با یک دفتر ثبت به‌ازای هر اجرا سرکوب می‌شوند که کلیدش شدت، کد و پیام است — موقعیت عمداً کنار گذاشته شده است، پس پیامی تشخیصی که فقط چهار خط پایین‌تر رفته است، دوباره به‌عنوان تازه گزارش نمی‌شود.

## `lsp_rename` — تغییر نام در سراسر پروژه

ابزاری جداگانه در ردهٔ `write`، دقیقاً به یک دلیل: رده است که دیدپذیری را تعیین می‌کند. گنجاندن تغییر نام در `lsp` یا به یک کاوشگر فقط‌خواندنی توان بازنویسی مخزن را می‌دهد، یا هر `hover` را پشت یک پرامپت تأیید می‌گذارد.

| آرگومان | معنا |
| -------- | ------------------------------------------ |
| `file`   | جایی که نماد قرار دارد                     |
| `line`   | خط با شماره‌گذاری از ۱                     |
| `symbol` | زیررشته‌ای که آن را در آن خط مشخص می‌کند    |
| `new_name` | نام تازهٔ آن                             |

## `ast_grep` — جست‌وجوی ساختاری

کد را بر پایهٔ **شکل** می‌یابد، نه بر پایهٔ متن. `$NAME` با هر گره مطابقت می‌کند، `$$$NAME` با رشته‌ای از گره‌های خواهر و برادر، و `$_` یک نویسهٔ عام است که چیزی را مقید نمی‌کند.

ویژگی‌ای که آن را به‌جای یک regex با چند مرحلهٔ اضافه، یک تطبیق‌دهنده می‌کند این است: فرامتغیری که در یک الگو تکرار می‌شود باید همان متن را بگیرد.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

با نگهبانی مطابقت می‌کند که همان چیزی را که آزموده آزاد می‌کند، و با نگهبانی که چیز دیگری را آزاد می‌کند مطابقت **نمی‌کند**.

| آرگومان | معنا |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | قطعه‌ای کد با فرامتغیرها                                    |
| `path`        | فایل یا پوشه‌ای که جست‌وجو شود؛ به‌طور پیش‌فرض کل فضای کاری   |
| `language`    | شناسهٔ یک گرامر عرضه‌شده (`dart`, `python`, `rust`, `c`, …). وقتی `path` نام یک فایل را ببرد، استنباط می‌شود |
| `max_results` | پیش‌فرض ۵۰                                                  |

:::note[الگو با همان گرامری تجزیه می‌شود که خودِ فایل]
پس `dispose(x)` آن فراخوانی را مطابقت می‌دهد، هرگونه که فاصله‌گذاری، شکسته یا کامنت‌گذاری شده باشد — و هرگز همان کاراکترها را درون یک رشتهٔ متنی یا یک کامنت مطابقت نمی‌دهد.
:::

:::caution[یک قطعه در یک داربست تجزیه می‌شود، نه به‌تنهایی]
‏`dispose(x)` وقتی در سطح بالای Dart تجزیه شود یک *امضای تابع* معتبر است. کامپایلر الگو نردبانی از زمینه‌ها را می‌آزماید (دستور، عبارت، عضو کلاس، اعلان) و نخستینی را می‌گیرد که قطعه را می‌پذیرد. الگویی که هیچ زمینه‌ای آن را نپذیرد، به‌عنوان تجزیه‌ناپذیر گزارش می‌شود، نه اینکه جست‌وجو شود و بی‌صدا پیدا نشود.
:::

## `ast_edit` — بازنویسی ساختاری، در مرحلهٔ آماده‌سازی

همان تطبیق، به‌همراه یک الگوی `rewrite` که در آن فرامتغیرها بازجای‌گذاری شده‌اند. **هیچ چیزی نوشته نمی‌شود.** تغییر در مرحلهٔ آماده‌سازی نگه داشته می‌شود و نتیجه یک `edit_id` نام می‌برد.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| آرگومان | معنا |
| ---------- | --------------------------------------------------- |
| `pattern`  | آنچه باید مطابقت داده شود                           |
| `rewrite`  | آنچه باید آنجا گذاشته شود، با جای‌گذاری `$NAME`     |
| `path`     | محدوده؛ به‌طور پیش‌فرض کل فضای کاری                  |
| `language` | شناسهٔ زبان                                         |

## `resolve` — کامیت یا دور انداختن یک تغییر آماده‌شده

| آرگومان | معنا |
| --------- | -------------------------------- |
| `edit_id` | از نتیجهٔ `(proposed)`           |
| `action`  | `accept` یا `discard`            |

هر فایل با محتوایی سنجیده می‌شود که در زمان آماده‌سازی ثبت شده است، و **هر** ناهمخوانی کل تغییر را رد می‌کند. بازنویسی ساختاری نیمه‌اعمال‌شده درختی بر جا می‌گذارد که زیر هیچ‌یک از آن دو شکل، نه شکل قدیم و نه شکل تازه، کامپایل نمی‌شود.

## `debug` — راندن یک اشکال‌زدا

وقتی اجرا یک ناظر نشست اشکال‌زدایی، یک پوشهٔ کاری و یک شناسهٔ گفتگو داشته باشد ثبت می‌شود. اینکه یک آداپتور واقعاً بتواند آغاز به کار کند، در زمان فراخوانی و با همان قاعدهٔ اشتراک سرور زبان تشخیص داده می‌شود (نشانگر ریشه *و* باینری). ردهٔ `exec`؛ موازی‌ایمن نیست (یک نشست وضعیتی است که میان فراخوانی‌ها می‌ماند، پس اگر `continue` از `stack` جلو بزند، فریمی را می‌خواند که پیش‌تر جابه‌جا شده است).

یک نشست به‌ازای هر گفتگو، با یک TTL سخت (۳۰ دقیقه). `launch` دوم رد می‌شود، نه اینکه بی‌صدا جای اولی را بگیرد. در اجرای ایزوله، نشست سندباکس خودش را در نوبت‌ها نگه می‌دارد تا پایان نشست، یعنی حداکثر برای همان ۳۰ دقیقه.

| عملیات | آرگومان‌ها | یادداشت‌ها |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | کدام آداپتورها اینجا قابل استفاده‌اند، و چرا نه |
| `status`      | —                             | آیا نشستی در حال اجراست، و کجا متوقف شده      |
| `breakpoints` | `file`, `lines[]`             | `lines` خالی فایل را پاک می‌کند. می‌تواند **پیش از** راه‌اندازی تنظیم شود |
| `launch`      | `program`, `args[]`           | برنامه را متوقف روی نقاط توقف شما آغاز می‌کند  |
| `attach`      | `port`                        | به برنامهٔ در حال اشکال‌زدایی که از قبل در حال اجراست و روی یکی از پورت‌های فورواردشدهٔ همان اجرا است وصل می‌شود؛ هر پورت دیگری پیش از آغاز هر چیزی رد می‌شود |
| `continue`    | `thread_id?`                  | تا توقف بعدی اجرا می‌کند                        |
| `pause`       | `thread_id?`                  | همان‌جا که هست متوقفش می‌کند                    |
| `step_over` / `step_in` / `step_out` | `thread_id?` | یک گام پیش می‌رود                       |
| `threads`     | —                             | شناسه‌ها و نام‌های رشته‌ها                      |
| `stack`       | `thread_id?`                  | فریم‌ها، حداکثر ۳۰ مورد                        |
| `scopes`      | `frame_id`                    | حوزه‌های یک فریم، هرکدام با یک `reference`      |
| `variables`   | `reference`                   | فرزندان، حداکثر ۵۰ مورد، مقادیر حداکثر ۴۰۰ نویسه |
| `evaluate`    | `expression`, `frame_id?`     | در حوزهٔ خودِ فریم ارزیابی می‌شود               |
| `output`      | —                             | stdout/stderr برنامهٔ در حال اشکال‌زدایی، کران‌دار |
| `terminate`   | —                             | نشست را پایان می‌دهد و آداپتور را می‌کشد       |

### آداپتورها

| شناسه | فرمان | نشانگرهای ریشه |
| --------- | -------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`       | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                 | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                  | `go.mod`                                        |

‏`debugpy` یک `.venv/bin` یا `venv/bin` محلیِ پروژه را در اجرای ایزوله به `$PATH` ترجیح می‌دهد: یک python از `$PATH` محیطی متفاوت است، و اتصال از محیط اشتباه به شکلی شکست می‌خورد که مانند کد خراب خوانده می‌شود. بدون ایزوله، فقط از `$PATH` استفاده می‌کند، پس یک مخزن نمی‌تواند مفسری را انتخاب کند که روی میزبان اجرا می‌شود.

## `repl` — اجرای اسکریپتی که ابزارهای شما را فراخوانی می‌کند

وقتی سرور بتواند اسکریپت اجرا کند، روی هر اجرا موجود است ([وقتی یک اجرا `repl` دارد](/fa-IR/راهنمای-کاربر/مفهومها/حالت-کد/#وقتی-یک-اجرا-repl-دارد)). اسکریپت یک JavaScript ساده است، بدنهٔ یک تابع async، و در یک مفسر تازه و قفل‌شده در فرایند جدای خودش اجرا می‌شود، بدون دسترسی به سیستم فایل، شبکه، فرایند یا ماژول. خود `repl` به سطح `read` تعلق دارد و از خودش محافظت می‌کند، چون هر فراخوانی ابزاری که اسکریپت انجام می‌دهد به‌تنهایی بررسی می‌شود. همچنین روی نقطهٔ پایانی MCP، برای اجراهای عامل روی سروری که می‌تواند اسکریپت اجرا کند.

| آرگومان | معنا |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | اسکریپت. حداکثر ۲۵۶ KiB |
| `description` | الزامی. برچسبی کوتاه برای ردیف گفتگو |
| `timeout_ms` | اختیاری. زمانی کوتاه‌تر از زمان فضای کاری؛ هرگز طولانی‌تر نه |
| `max_output_tokens` | اختیاری. بودجهٔ خروجی کوچک‌تر از فضای کاری؛ هرگز بزرگ‌تر نه |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

توضیح `repl` به عامل می‌گوید: «ابزاری که یکی از ابزارهای مستقیمت نیست، در این درخواست تعریفی ندارد. پیش از نخستین فراخوانی آن، با `describeTool(name)` یا `searchTools(query)` دنبالش بگرد، مگر اینکه شکل دقیق فراخوانی‌اش پیش‌تر در این گفتگو به تو نشان داده شده باشد.»

`describeTool(name)` توصیف یک ابزار، اعلان آن، اسکیمای ورودی و خروجی‌اش و یادداشت نتیجه‌اش را برمی‌گرداند، وقتی یادداشتی داشته باشد: آنچه یک اسکریپت از یک فراخوانی تمام‌شده دریافت می‌کند، به زبان خود ابزار. توضیح `repl` یادداشت‌های ابزارهای مستقیمی را که یک اسکریپت می‌تواند فراخوانی کند فهرست می‌کند. نتیجهٔ ابزاری که متن JSON است، از پیش تجزیه‌شده به اسکریپت می‌رسد، مگر اینکه بیش از ۱۳۱٬۰۷۲ مقدار داشته باشد؛ در آن صورت به‌صورت متن می‌رسد و اسکریپت آن را با `JSON.parse` تجزیه می‌کند. متن نتیجهٔ یک ابزار از یک سرور MCP بیرونی در ۲۶۲٬۱۴۴ نویسه کوتاه می‌شود، و متن کوتاه‌شده دیگر تجزیه نمی‌شود.

- `tools.<name>(args)` یک ابزار را از همان فیلتر، گاردریل‌ها و تأیید یک فراخوانی مستقیم فراخوانی می‌کند، و وقتی رد شود یا شکست بخورد با خطا رد می‌شود. فراخوانی‌های فقط‌خواندنی می‌توانند با هم اجرا شوند؛ فراخوانی‌هایی که چیزی را تغییر می‌دهند یکی‌یکی و به ترتیبی اجرا می‌شوند که اسکریپت آن‌ها را ساخته است. تا وقتی یکی از فراخوانی‌های اسکریپت منتظر یک شخص است، هیچ فراخوانی دیگری از اسکریپت آغاز نمی‌شود.
- `ALL_TOOLS`، `searchTools(query, { limit, namespace })`، `describeTool(name)` و `describeNamespace(name)` ابزارها را پیدا می‌کنند، از جمله ابزارهای سرورهای MCP متصل. یک ابزار بیرون از مجموعهٔ مستقیم که یک اسکریپت می‌تواند فراخوانی کند، فقط از یک اسکریپت قابل فراخوانی است؛ فراخوانی مستقیم آن پاسخی برمی‌گرداند که نشان می‌دهد چگونه از `repl` فراخوانی شود. وقتی سرور نتواند اسکریپت‌های اجرا را اجرا کند، چنین ابزاری در عوض با نخستین استفاده بار می‌شود.
- محدودیت جست‌وجو وجود دارد: پرس‌وجو حداکثر ۱٬۰۲۴ نویسه، نام یا فضای نام حداکثر ۲۵۶ نویسه، `limit` از ۰ تا ۵۰، و حداکثر ۲۰۰ جست‌وجو که در مجموع ۲ ثانیه از زمان سرور می‌گیرند برای هر اسکریپت؛ در حالی که همهٔ اسکریپت‌های یک فضای کاری ۲ ثانیه زمان جست‌وجو را سهیم‌اند که هر ثانیه ۰٫۲۵ ثانیه بازپس داده می‌شود. پس از رسیدن به هرکدام از این دو حد، جست‌وجوهای بیشتر شکست می‌خورند. در کاتالوگی بسیار بزرگ، توصیف‌ها در `ALL_TOOLS` به‌طور برابر حدود یک میلیون نویسه را سهیم‌اند و توصیفِ بریده‌شده با `…` پایان می‌یابد؛ `describeTool` همیشه کل توصیف را برمی‌گرداند. نوعی که برای نمایش بسیار بزرگ است `unknown /* too large to show */` می‌خواند، و نام ناشناخته با نزدیک‌ترین نام‌ها پاسخ داده می‌شود.
- ابزارها در فضای‌نام‌ها گروه‌بندی می‌شوند: `builtin` (ابزارهای خود هارنس)، `control-center` (ابزارهای Control Center) و یکی برای هر سرور MCP متصل، که به نام آن سرور است. سروری که `builtin`، `control-center` یا `script` نامیده شود، یا نامش با `external-` شروع شود، با هر ترکیبی از حروف بزرگ و کوچک و با یا بدون فاصله دور آن، به شکل `external-` و سپس نامش فهرست می‌شود، و هیچ ابزاری هرگز در `script` نیست.
- فقط آنچه اسکریپت برمی‌گرداند، یا به `text()`، `image()` یا `console.*` می‌دهد، به عامل بازمی‌گردد. خروجی بیش از بودجه ابتدا و انتهایش را نگه می‌دارد و `read_output` بقیه را می‌خواند.
- `store(key, value)` / `load(key)` مقادیر JSON را برای اسکریپت‌های بعدی همان گفتگو و همان عامل نگه می‌دارند، و فقط وقتی اسکریپت کامل شود ذخیره می‌شوند. اسکریپت‌های یک زیرعامل فضای ذخیره ندارند.
- `await tools.ask_user(...)` یک پرسش می‌پرسد؛ پاسخش هم به نتیجه اضافه می‌شود. `sleep(ms)`، `setTimeout`، `limits()` و `models.embed` / `rank` / `classify` (امبدینگ روی دستگاه) هم در دسترس‌اند.
- `describeTool(name)` و `searchTools(query)` برای توابع خود اسکریپت هم پاسخ می‌دهند، که ابزار نیستند: `text`، `image`، `store`، `load`، `sleep`، `setTimeout`، `clearTimeout`، `limits`، `exit` و `models.*`، زیر نام‌فضای `script`.
- از یک اسکریپت قابل فراخوانی نیست: `repl`، `eval`، `task`، `checkpoint`، `rewind`، `compact`، `search_tools` و فعل‌های `vibe_*`.
- یک اسکریپت گذشتهٔ همان اجرای خودش را می‌خواند: `history({start, role, tool, limit})` رونوشت گفتگو را صفحه‌صفحه می‌آورد (در هر فراخوان حداکثر 50 ردیف؛ `next_start` صفحهٔ قبل را به‌عنوان `start` بدهید)، `outputs()` خروجی‌های ابزاری را که برای این گفتگو و این عامل ذخیره شده فهرست می‌کند، و `loadOutput(handle)` 16 384 نویسهٔ یکی از آن‌ها را می‌خواند. `storedKeys()` کلیدهای ذخیره‌شده را همراه اندازه‌شان فهرست می‌کند. `keep(value, label)` یک مقدار بزرگ را به‌صورت خروجی ذخیره می‌کند تا یک اسکریپت بعدی یا `read_output` بتواند آن را بخواند، و تنها وقتی اسکریپت کامل شود ذخیره می‌شود (هر مقدار 1 MiB، 64 مقدار و 16 MiB در هر اجرا). `limits().returnBudgetChars` نشان می‌دهد چه مقدار از بودجهٔ خروجی باقی مانده است. یک اجرای فقط‌خواندنی (بازبینی یک هدف) می‌تواند بخواند، اما ذخیره یا keep نمی‌کند. در Claude Code و ACP، `history()` کار می‌کند و `outputs()`، `loadOutput()` و `keep()` رد می‌شوند، چون Control Center خروجی ابزار آن اجراها را نگه نمی‌دارد.
- خطایی از زمان‌انقضا، سرریز خروجی یا سقف فراخوان، می‌گوید چطور آن را برطرف کنید.

یک اجرا در هر لحظه فقط یک اسکریپت را اجرا می‌کند. محدودیت‌ها و آنچه در هر کدام رخ می‌دهد در صفحهٔ [حالت کد](/fa-IR/راهنمای-کاربر/مفهومها/حالت-کد/#محدودیتها) آمده است؛ هر اسکریپت زیر **مشاهده‌پذیری → اجراهای کد** ضبط می‌شود.

## `eval` — مفسرهای پایدار

سلولی پایتون یا جاوااسکریپت که متغیرها، واردات و داده‌های بارگذاری‌شده‌اش میان فراخوانی‌ها باقی می‌مانند. ردهٔ `exec`؛ موازی‌ایمن نیست. از یک اسکریپت `repl` قابل فراخوانی نیست، و یک سلول نمی‌تواند ابزارهای اجرا را فراخوانی کند: برای فراخوانی ابزارها از کد، از [`repl`](#repl--اجرای-اسکریپتی-که-ابزارهای-شما-را-فراخوانی-میکند) استفاده کنید.

| آرگومان | معنا |
| ------------- | ------------------------------------------------ |
| `code`        | سلول                                            |
| `description` | اجباری. ۵ تا ۱۰ واژه برای برچسب رونوشت           |
| `language`    | `python` (پیش‌فرض) یا `javascript`               |
| `reset`       | مفسر را دور می‌ریزد و ابتدا یکی تمیز آغاز می‌کند |

- آخرین عبارت همان‌طور که یک نوتبوک بازتاب می‌دهد، چاپ می‌شود.
- ‏`display()` کار می‌کند، یک دیتافریم pandas به‌صورت جدول رندر می‌شود، و یک شکل matplotlib به‌صورت **تصویری که رونوشت نشان می‌دهد** برمی‌گردد.
- اصطلاحات IPython که افراد به‌طور بازتابی تایپ می‌کنند — `%pip`، `%cd`، `!cmd`، `%%bash`، `%%timeit` — به کد ساده بازنویسی می‌شوند. `%pip` همچنین `sys.modules` را بیرون می‌اندازد، پس `import` بعدی چیزی را می‌بیند که همین حالا نصب شده است.
- سلولی که بیش از بودجهٔ خروجی‌اش چاپ کند، سه‌چهارم اول و یک‌چهارم آخر را نگه می‌دارد، با یک خط که می‌گوید چند نویسه و تصویر حذف شده است.
- وقتی مفسر بدون درخواست شما از کار افتاد، سلول بعدی یک‌بار خبر داده می‌شود که متغیرهای قبلی‌اش از بین رفته‌اند.

:::note[کرنل کجا اجرا می‌شود]
اگر گفتگو محفظه‌ای داشته باشد، در آن؛ در غیر این صورت، روی میزبان و در سندباکس سیستم‌عامل همان اجرا. با سندباکس خاموش یا ناموجود، بدون محدودسازی اجرا می‌شود و `eval` تأیید اجرای میزبان را می‌خواهد. برای رسیدن به آن محفظه‌ای **راه‌اندازی نمی‌کند** — همان قاعده‌ای که جلوی خودکار شروع شدن تب ریگ را می‌گیرد.
:::

## `bash` در پس‌زمینه

`bash` با `run_in_background: true` فرمان را شروع می‌کند و به‌جای انتظار، فوراً با یک دستگیره (`b1`, `b2`, …) برمی‌گردد. عامل به کار ادامه می‌دهد، یا نوبتش را تمام می‌کند و وقتی فرمان خارج شود بیدار می‌شود.

| آرگومان | معنا |
| ------------------- | ------- |
| `run_in_background` | `true` برای شروع و بازگشت فوری |
| `timeout_seconds` | ثانیه‌های پیش از کشته‌شدن فرمان: پیش‌فرض 600، حداکثر 3 600 |
| `notify` | اختیاری. یک الگوی ساده؛ هر خط خروجی که مطابقت داشته باشد در حین اجرای فرمان برای عامل فرستاده می‌شود (مانند `listening on\|FAILED`) |

- حداکثر 4 فرمان پس‌زمینه در یک اجرا همزمان اجرا می‌شوند. هر کدام در زمان‌انقضایش و وقتی اجرا تمام شود، همراه با هر فرایندی که آغاز کرده، کشته می‌شود.
- وقتی فرمانی خارج می‌شود، عامل اعلانی می‌گیرد با کد خروج، 2 000 نویسهٔ آخر خروجی و یک دستگیرهٔ `read_output` برای بقیه.
- عاملی که تنها کار باقی‌مانده‌اش یک فرمان پس‌زمینه است، بدون فراخوانی مدل منتظر می‌ماند، و نگهبان سکوت اجرا در این انتظار مکث می‌کند.
- `bash_output(handle)` وضعیت و خروجی اخیر یک فرمان را می‌خواند؛ `bash_kill(handle)` آن را متوقف می‌کند. هر دو می‌گویند آیا نتیجه قبلاً تحویل شده است.
- یک اسکریپت نمی‌تواند فرمان پس‌زمینه شروع کند. Claude Code پس‌زمینهٔ Bash خودش را دارد؛ Control Center آن اجرا را حداکثر 10 دقیقه پس از نوبتی که یک کار را در حال اجرا رها کرده باز نگه می‌دارد.

## `compact` — آزادسازی فضا در پنجرهٔ زمینه

پیش از فراخوان بعدی مدل، زمینهٔ قدیمی‌تر گفتگو را فشرده می‌کند و آنچه را `focus` نام می‌برد نگه می‌دارد (حداکثر 1 000 نویسه). نوبت‌های جدیدتر کلمه‌به‌کلمه می‌مانند. خط بودجهٔ هر نوبت عامل مصرف زمینه را در 70، 80 و 90% نشان می‌دهد، و ارزش دارد این ابزار را پیش از یک فاز کار تازهٔ طولانی، از حدود 70% به بعد فراخوانی کنید. هوک `preCompact` مالک سرور می‌تواند به کانون فشرده‌سازی بیفزاید ([هوک‌های پوسته](/fa-IR/راهنمای-کاربر/مرجع/پیکربندی-عامل/#هوکهای-پوسته)). پس از فشرده‌سازی، سرور یک بلوک «Still in flight» اضافه می‌کند: هدف، بیدارباش‌های در انتظار، پرسش‌های باز، فرمان‌های پس‌زمینه، چک‌لیست و کلیدهای ذخیره‌شده، هرکدام همراه با فراخوانی که آن را بازمی‌گرداند.

## `ask_user` — پرسیدن یک پرسش از انسان

ردهٔ `read`. **تنها** راهی که یک اجرا چیزی از اپراتور می‌پرسد. یک کارت شماره‌دار در گفتگو رندر می‌کند و تا وقتی کسی پاسخ دهد، رد کند، یا پرسش مهلتش تمام شود مسدود می‌ماند. هرگز پرسش را به‌صورت یک پیام گفتگو ننویسید — این کار نوبت را پایان می‌دهد.

| آرگومان | معنا |
| -------------- | ------------------------------------------ |
| `question`     | آنچه باید پرسید                            |
| `context`      | اختیاری: چرا می‌پرسید و چه چیزی به پاسخ بند است |
| `options[]`    | گزینه‌ها، هرکدام `{label, description?}`   |
| `allow_free_text` | آیا پاسخ تایپ‌شده پذیرفته می‌شود         |
| `multi_select` | آیا می‌توان چند گزینه را برگزید             |

رد کردن یک موفقیت است: بر پایهٔ یک فرض بیان‌شده پیش بروید و دوباره نپرسید. مهلت تمام‌شده یک خطاست با همان دستور. پرامپت‌های اجازه («آیا این کار را بکنم؟») دروازه‌ای جداگانه‌اند و به‌صورت همان کارت در گفتگو رندر می‌شوند.

فقط وقتی هم یک پورت پرسش و هم یک فضای هدف وجود داشته باشد ثبت می‌شود. بدون یک انسان متصل، فراخوانی **شکست می‌خورد**، نه اینکه تا ابد مسدود بماند — همان موضع «در خطا، بستن» که یک `prompt` گاردریل در نبود یک تأییدکنندهٔ وصل اتخاذ می‌کند.

## `vibe_*` — هدایت کارگران پس‌زمینه

فقط تا وقتی [حالت vibe](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/هدایت-کارگران-پسزمینه/) روشن است ثبت می‌شوند. هر پنج در ردهٔ `read` هستند: دروازه باید روی ابزارهای کارگر باشد، همان‌جا که ویرایش واقعاً رخ می‌دهد.

| ابزار | آرگومان‌ها | یادداشت‌ها |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | بی‌درنگ برمی‌گردد؛ کارگر به کارش ادامه می‌دهد |
| `vibe_send`  | `worker_id`, `message`                   | به بریف می‌افزاید و دوباره اجرا می‌کند       |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | تا پایان یافتن آن مسدود می‌ماند              |
| `vibe_kill`  | `worker_id`                              | متوقفش می‌کند                               |
| `vibe_list`  | —                                        | رده، وضعیت، زمان سپری‌شده و آخرین نتیجه      |

‏`tier` یکی از `fast` (کار مکانیکی با مشخصات روشن) یا `good` (طراحی، قضاوت، یا بازبینی خروجی یک کارگر `fast`) است.
