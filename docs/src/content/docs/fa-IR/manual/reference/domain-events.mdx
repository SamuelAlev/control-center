## گذرگاه رویداد

`DomainEventBus` یک گذرگاه انتشار/اشتراک پخش‌همگانی درون‌فرایندی است. ناشران `publish(event)` را فراخوانی می‌کنند؛ مشترکان یک جریان نوع‌دار `on<T>()` را مصرف می‌کنند. هر رویداد `DomainEvent` را پیاده‌سازی می‌کند و `occurredAt` را با خود دارد.

**گذرگاه درون `cc_server` اجرا می‌شود.** هر ناشر و هر مشترک زنده همان‌جا زندگی می‌کند. هیچ کلاینتی این گذرگاه را نمی‌بیند — سرور زیرمجموعه‌ای گزینش‌شده را به‌صورت فریم‌های JSON-RPC با نام `notifications/*` بازپخش می‌کند که برای هر مشترک بر پایهٔ عضویت در فضای کاری فیلتر شده است.

| سنجه                                                                    | شمار                                        |
| ----------------------------------------------------------------------- | ------------------------------------------- |
| کلاس‌های رویداد مشخص                                                    | ۵۴                                          |
| فایل‌های منبع (`packages/cc_domain/lib/core/domain/events/`)             | ۱۴ (به‌علاوهٔ `domain_event_bus.dart`)         |
| بنیادهای انتزاعی که هرگز مستقیماً منتشر نمی‌شوند                          | ۱ (`TaskLifecycleEvent`، یک سلسله‌مراتب مهروموم‌شده) |

هر رویداد در سیاههٔ زیر در همان یک دایرکتوری زندگی می‌کند؛ هیچ رویداد دامنه‌ای جای دیگری اعلام نشده است.

## رویدادهای PR و بازبینی

بلوک نخست چرخهٔ عمر خود PR است. بلوک دوم **پایش PRهای تألیف‌شده** است: نشانه‌هایی دربارهٔ PRی که *شما* باز کرده‌اید و هرکدام `forUserId` را با خود دارند تا نظرسنجی بتواند آن‌ها را به‌جای پخش همگانی، به فرد مربوطه برساند.

| رویداد                     | بار داده                                                                 | زمان انتشار                                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `PullRequestPublished`     | `prId`, `workspaceId`, `repoOwner`, `repoName`                           | عامل یک PR باز می‌کند                                                                                                                |
| `PullRequestStatusChanged` | `status`, `workspaceId`, `prId?`, `repoFullName?`, `prNumber?`           | PR ادغام/بسته/باز/بازگشایی/تأیید می‌شود                                                                                              |
| `PrMerged`                 | `prId`, `workspaceId`, `agentId`                                         | PR ادغام می‌شود — نشانه‌ای باریک و فقط مخصوص ادغام که برای تحلیل‌ها/اعلان‌ها نگه داشته شده است                                        |
| `PrReviewRequested`        | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`            | GitHub بازبینی کاربر سرور را می‌خواهد (نظرسنجی اعلان‌ها، `review_requested`)                                                          |
| `PrMentioned`              | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`            | کاربر سرور در یک PR منشن می‌شود (نظرسنجی اعلان‌ها، `mention`)                                                                        |
| `ExternalPrMerged`         | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`, `mergedByLogin?` | یک PR دارای ردیابی بیرونی (غیرعاملی) ادغام می‌شود که نظرسنجی اعلان‌های GitHub آن را شناسایی کرده است؛ به دستهٔ اعلان `prMerged` نگاشت می‌شود |
| `ExternalPrDetected`       | `repoOwner`, `repoName`, `prNumber`, `prTitle`, `author`, `workspaceId?` | PR غیرعاملی با نظرسنجی پیدا می‌شود — فقط پایپ‌لاین (برانگیزندهٔ `external_pr_welcome`)، هیچ اعلانی برنمی‌انگیزد                       |

## رویدادهای چرخهٔ عمر وظیفه

جریان یکپارچهٔ چرخهٔ عمر وظیفه — یک اجرای اعزام‌شدهٔ عامل که با شناسهٔ گزارش اجرایش کلید می‌خورد. هر رویداد `taskId`، یک `seq` یکنوا به‌ازای هر وظیفه، `workspaceId?`، `agentId?` و یک `phase` را با خود دارد؛ سطرهای زیر تنها فیلدهای افزوده را فهرست می‌کنند.

| رویداد                      | بار داده                      | زمان انتشار                                                                                     |
| --------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `TaskDispatched`            | —                             | وظیفه برای اجرا به یک بک‌اند سپرده می‌شود                                                        |
| `TaskRunning`               | —                             | وظیفه شروع به تولید خروجی می‌کند                                                                 |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | وظیفه متوقف می‌شود — وظیفهٔ دیگری مالک قفل مسیر روی دیسکی است که به آن نیاز دارد                 |
| `TaskProgress`              | `note?`                       | نقطهٔ بازرسی پیشرفت در میانهٔ اجرا                                                               |
| `TaskMessage`               | `messageType`, `content`      | پیام جریانی (text/thinking/tool_use/tool_result/error)؛ زیر فاز `progress` گزارش می‌شود         |
| `TaskCompleted`             | `summary?`                    | وظیفه با موفقیت تمام می‌شود                                                                      |
| `TaskFailed`                | `errorMessage`                | وظیفه با یک خطا تمام می‌شود                                                                      |
| `TaskCancelled`             | —                             | وظیفه پیش از تکمیل لغو می‌شود                                                                    |

enum `TaskPhase` عضوی به نام `queued` هم دارد، اما هیچ‌چیز رویداد queued را منتشر نمی‌کند — کلاسی به نام `TaskQueued` وجود ندارد. نخستین فریم قابل مشاهدهٔ یک وظیفه `TaskDispatched` است.

## رویدادهای پایپ‌لاین

| رویداد                 | بار داده                                      | زمان انتشار                                                                |
| ---------------------- | --------------------------------------------- | --------------------------------------------------------------------------- |
| `PipelineRunCompleted` | `workspaceId`, `pipelineRunId`, `templateId`  | اجرا تمام می‌شود                                                            |
| `PipelineRunCancelled` | `workspaceId`, `pipelineRunId`, `templateId`  | اجرا لغو می‌شود (توسط کاربر یا سیستم) — توقفی عامدانه، نه یک خطا            |

تنها گذارهای پایانی منتشر می‌شوند. `PipelineRunStarted` وجود ندارد و رویدادی به‌ازای هر گام هم نیست: پیشرفت یک گام از طریق سطرهای خود اجرا و جریان چرخهٔ عمر وظیفهٔ هر عاملی که اعزام کرده به کلاینت‌ها می‌رسد، نه از طریق گذرگاه.

## زیردامنه‌هایی که هیچ رویدادی ندارند

چند زیرسیستم که از بیرون رویدادمحور به نظر می‌رسند، چنین نیستند. اینجا فهرست شده‌اند چون نبودشان تصمیمی طراحی است که ارزش دانستن دارد، پیش از آنکه به دنبال قلابی بگردید:

| زیردامنه         | به‌جای آن، وضعیت چگونه جابه‌جا می‌شود                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| حافظه            | `record_memory_fact` و هم‌خانواده‌هایش می‌نویسند و بازمی‌گردند؛ recall می‌خواند. هیچ‌چیز روی یک واقعیت یا تعارض منتشر نمی‌شود |
| ارکستراسیون      | پیشنهاد، تأییدش و اجرای پایپ‌لاین تولیدشده سطر و فراخوانی RPC‌اند                                          |
| اسناد برنامه     | `submit_plan` یک بازنگری می‌نویسد؛ تأیید یک ارکستراسیون را محقق می‌کند. هیچ‌کدام اعلام نمی‌شوند            |
| مصنوعات          | `publish_artifact` / `revise_artifact` بازنگری‌ها را مستقیماً می‌نویسند                                    |
| تأییدها          | تشدید درون سرویس جریان کاری تأیید رسیدگی می‌شود                                                           |
| همگام‌سازی تیکت  | هماهنگ‌کنندهٔ سرویس‌دهنده در رویدادهای تیکت بالا مشترک می‌شود؛ وبهوک‌های ورودی مستقیماً اعمال می‌شوند       |
| بازتازه‌سازی تقویم | یک همگام‌سازی رویدادها را درج/به‌روزرسانی می‌کند و کلاینت دوباره می‌خواند؛ هیچ پخش همگانیِ بازتازه‌سازی وجود ندارد |
| ادغام‌های worktree | در `worktree_merge_log` ثبت و از همان‌جا خوانده می‌شوند                                                   |

| `RigEventListener`                  | `RigControlChanged`, `RigReaped`, `RigClosedEvent` — اطلاعیه‌ای به زبان ساده روی خط هدایت عامل گرداننده تزریق می‌کند |
| `StaleReviewWatcher`                | `PrHeadChanged` — تنها زمانی `ReviewBecameStale` را منتشر می‌کند که بازبینی‌ای تمام‌شده برای کامیت جایگزین‌شده وجود داشته باشد |
| `GitHubPrConversationBridge`        | `AgentRunCompleted` — پاسخ‌های بیرون‌روی گفتگوی PR                                                    |
| `NotificationFeedRecorder`          | بیست‌ودو رویداد کلاس اعلان در زیر                                                                     |
| `RemoteEventForwarder`              | همان بیست‌ودو رویداد به‌علاوهٔ `TicketReassigned` و هر `TaskLifecycleEvent`. سه رویداد عضویت تنها کش عضویت به‌ازای هر فضای کاری آن را باطل می‌کنند؛ به‌صورت فریم بازپخش نمی‌شوند |
| `LocalRpcServer` / `RemoteRelayHost` | `WorkspaceMemberRemoved` — اشتراک‌های فضای کاری متصل آن کاربر را می‌اندازد؛ سوکت باز می‌ماند          |

`TicketAssigned` هم‌زمان یک نشانهٔ حسابرسی و اعلان و یک تریگر پایپ‌لاین است. تخصیص به یک عامل مالکیت را ثبت می‌کند و هیچ اجرایی شروع نمی‌کند — هیچ اعزام‌کنندهٔ تیکتی وجود ندارد. تخصیص به یک تیم (با مقدارگرفتن `assignedTeamId`) استثناست: `TeamRoutingService` رهبر تیم را اعزام می‌کند.

`TicketRemoteSyncHandler` اعلام شده اما هرگز در کد تولیدی ساخته نمی‌شود، پس امروز در هیچ‌چیز مشترک نیست. `NotificationEventMapper` سمت کلاینت تنها در تست خودش ساخته می‌شود — بازماندهٔ مسیر درون‌فرایندی از پیش از تفکیک کلاینت/سرور است. نشان‌های شناور زنده از فریم‌های شبکه‌ای زیر می‌آیند.

## نگاشت اعلان

روی سرور، `NotificationFeedRecorder` و `RemoteEventForwarder` این رویدادها را به فریم‌های شبکه‌ای `notifications/*` تبدیل می‌کنند (`notification_wire.dart`). روی کلاینت، `RpcNotificationMapper` → `mapNotificationFrame` یک فریم را به یک `AppNotification` تبدیل می‌کند.

دقیقاً **هفده** دستهٔ اعلان وجود دارد. چند رویداد به بیش از یک متد شبکه‌ای نگاشت می‌شوند، چون فریم لبه را حمل می‌کند (ناموفق در برابر بهبودیافته) و دسته پرسش را («CI چه می‌کند؟»).

| ---------------------- | ------------------------- | ------------------------------------------------------------------------ |

| `agentRunCompleted`    | `MessageReceived`         | `notifications/message_received` (`is_agent_message`، بدون منشن شما)   |
| `agentAwaitingInput`   | `AgentAwaitingInput`      | `notifications/agent_awaiting_input`                                   |

فریم تحویل گرفتن ریگ به کسی که فرمان را به دست گرفته بازگردانده نمی‌شود، رهاسازی
بی‌فیلتر است (رویداد ثبت نمی‌کند که چه کسی رها کرده)، و تنها بسته‌شدنی با
`backendFailure` یک فریم `rig_closed` تولید می‌کند — دلیل‌های دیگر یا درخواستی‌اند
یا از پیش با فریم بازپس‌گیری پوشش داده شده‌اند.

`AgentAwaitingInput` را `AgentAwaitingInputPublisher` منتشر می‌کند. این ناشر
رجیستری‌های تأییدها و اعتبارنامه‌های مسدودشده را برای ورودی‌های تازه زیر نظر
دارد و `AgentQuestionService` هر پرسش `ask_user` را به آن خبر می‌دهد. هر انتظار
یک رویداد است؛ وقتی انتظار تمام می‌شود، چیزی منتشر نمی‌شود.

پنج دستهٔ PRهای تألیف‌شده `forUserId` را با خود دارند، پس به نویسنده می‌رسند نه به همهٔ اعضای فضای کاری.

`RemoteEventForwarder` به‌علاوهٔ `TicketReassigned` را به‌عنوان `notifications/ticket_reassigned` و هر `TaskLifecycleEvent` را به‌عنوان `notifications/task_<phase>` بازپخش می‌کند. هیچ‌یک به دستهٔ اعلانی نگاشت نمی‌شوند — آن‌ها رابط کاربری زنده را به حرکت درمی‌آورند، نه مرکز اعلان‌ها را. رویدادهای عضویت به‌صورت فریم بازپخش نمی‌شوند: کش بازپخش‌کننده را باطل می‌کنند و میزبان‌های نشست اشتراک‌های فضای کاری عضو حذف‌شده را می‌اندازند.
