یک pull request از پیش جایی است که گفتگو دربارهٔ کد در آن رخ می‌دهد. گفتگوهای PR آن را به یک سطح روی یک فضای کاری Control Center تبدیل می‌کنند، همان‌طور که یک [پل گفتگو](/fa-IR/راهنمای-کاربر/مفهومها/پلهای-گفتگو/) Slack را به یکی تبدیل می‌کند: روی یک PR، `@usectrl` (یا بات GitHub App فضای کاری) را منشن کنید، در رشته‌های بازبینی‌اش پاسخ دهید، یا برچسب `ai-review` را اضافه کنید، و کار در فضای بازبینی PR انجام می‌شود — با همان انتساب و گاردریل‌هایی که برای هر چیزی که در برنامه تایپ شود اعمال می‌شود. یک نظر و یک برچسب به یک شکل محدود می‌شوند: به عضوی که آن را نوشته یا اضافه کرده است. پاسخ‌ها در GitHub، در همان مسیری که پرسش در آن پرسیده شد برمی‌گردند.

سه تصمیم این قابلیت را شکل می‌دهند، و هر کدام همان تصمیمی است که پل گفتگو برای چت گرفته بود، این بار برای یک forge بیان شده: **اتصال در کدام جهت برقرار است**، **چه چیزی یک نظر وارد‌شده از بیرون را مجاز می‌کند**، و **هر طرف به چه کسی منتسب است**.

## نظرسنجی همان انتقال است

تنها کانال push که برای یک برنامه در GitHub وجود دارد webhook است، و webhook به یک نشانی ورودی نیاز دارد — دقیقاً همان چیزی که این سطح عمداً هرگز به آن نیاز ندارد. پس کشف یک بررسی است: برای هر نصب برنامه، یک جست‌وجوی تجمیع‌شده از GitHub می‌پرسد کدام PRها بات (یا slug کوتاه آن) را منشن کرده‌اند و کدام PRهای باز برچسب بازبینی را دارند؛ PRهایی که از قبل فضای بازبینی دارند رشته‌های نظرشان خوانده می‌شود، و همه‌چیز با شناسهٔ نظر در برابر آنچه در بررسی قبلی دیده شده مقایسه می‌شود. یک برنامهٔ خودی هر دقیقه بر روی حداکثر ۲۵ PR بررسی می‌کند. از طریق Connect، فراخوانی‌ها از سهمیهٔ GitHub خود اعضا استفاده می‌کنند، پس بررسی هر دو دقیقه بر روی حداکثر ۱۰ PR انجام می‌شود، و یک فضای کاری که زیر ۱۵٪ سهمیه‌اش باشد تا بازیابی رد می‌شود. خود Connect هرگز محتوای PR را نمی‌بیند.

پیامدهای این طراحی ارزش نام بردن دارند:

- **تأخیر یک بازهٔ بررسی است، نه یک رویداد.** تأیید 👀 در یک بررسی می‌رسد. چیز فوری‌ای به آن وابسته نیست.
- **دقیقاً یک‌بار، به‌ازای هر نظر.** شناسه‌های نظر در GitHub یکتا هستند؛ هر کدام لحظه‌ای ثبت می‌شود که واجد شرایط بودنش تشخیص داده شود، پیش از اینکه کاری روی آن انجام شود. یک خرابی ممکن است پردازش یک نظر را از دست بدهد، اما هرگز آن را دو بار اجرا نمی‌کند.
- **زمان آفلاین جبران می‌شود، پخش مجدد نمی‌شود.** مجموعهٔ دیده‌شده ماندگار است، پس یک راه‌اندازی مجدد آنچه را در زمان خاموشی رسیده تحویل می‌دهد. تنها استثنا اولین بررسی است: وقتی هیچ حافظه‌ای برای مقایسه وجود ندارد، هر چیز معلقی بی‌صدا ثبت می‌شود — اپراتوری که بیست PR را قبل از وجود این سرور برچسب زده نباید با بیست بازبینی در حال اجرا روبه‌رو شود.
- **برچسب یک مجموعه است، نه یک رویداد.** جست‌وجو _حضور_ برچسب را گزارش می‌دهد، پس یک PR برچسب‌خورده فقط یک‌بار، برای همیشه، فعال می‌شود. افزودن دوبارهٔ برچسب پس از حذف آن برای بررسی نامرئی است؛ منشن، مسیر اجرای مجدد است.

جست‌وجو یک بار برای هر حساب نصب روی کلاینت خود آن مالک اجرا می‌شود، چون یک توکن فقط مخازن نصب خودش را می‌بیند — یک اعتبارنامهٔ واحد سراسری بی‌صدا تمام PRهای زیر نصب‌های دیگر برنامه را از دست می‌داد.

## عضویت مجاز می‌کند، نه نظر

یک نظر PR با یک نویسنده می‌رسد — هویتی بیرونی و احراز‌نشده تا وقتی ثابت شود. سرور شناسهٔ حساب عددی و ثابت GitHub نویسنده را حل می‌کند (هرگز نام کاربری، که ممکن است تغییر یا دوباره استفاده شود) در برابر ورودهای GitHub اعضای فضای کاری، که بر اساس TTL بازسازی می‌شوند، چون افراد در زمانی که سرور اجرا می‌شود وارد می‌شوند و دعوت می‌شوند. برای برچسب `ai-review`، فرد حل‌شده کسی است که آخرین بار آن را اضافه کرده است.

سه بررسی، به ترتیب، و شکست در هر کدام بی‌صداست — چیزی منتشر نمی‌شود:

- **یک عضو واردشده.** حساب باید متعلق به یک عضو _این_ فضای کاری باشد که روی این سرور با GitHub وارد شده است
- **نقش نوشتن.** `viewer` و `guest` نمی‌توانند کار را شروع کنند
- **دسترسی push.** پاسخ‌ها از یک توکن `bot` استفاده می‌کنند که به دسترسی آن عضو به مخزن محدود است. اگر سرور نتواند یکی صادر کند، ادامه نمی‌دهد

هر بررسی پیش از هر تأییدی اجرا می‌شود، پس یک غریبه نه واکنشی می‌گیرد و نه پاسخی. یک نظر هرگز به کسی که آن را نفرستاده منتسب نمی‌شود، و کلمات یک غریبه هرگز وارد فضای کاری‌ای نمی‌شود که نتواند آن را ببیند.

### ادعا

آخرین گام پیش از هر کاری یک واکنش 👀 است که با ورود خود نویسنده به GitHub اضافه می‌شود. GitHub برای یک واکنش تازه پاسخ `201` و برای واکنشی که از قبل وجود دارد `200` می‌دهد، پس واکنش به‌عنوان قفل هم عمل می‌کند: وقتی همان فرد روی دو سرور که هر دو مخزن را متصل کرده‌اند وارد شده باشد، فقط اولی که واکنش نشان دهد کار را انجام می‌دهد. نظری که چند فضای کاری روی یک سرور می‌بینند به هر کدام پیشنهاد می‌شود، و همان ادعا تصمیم می‌گیرد.

## دو هویت، عمدی

هر طرف گفتگو هویت متفاوتی دارد و تفاوت همان قابلیت است:

- **در GitHub، پاسخ خودکارسازی به نیابت از شماست.** هر پاسخ از یک توکن `bot` برای همان یک مخزن استفاده می‌کند، که به دسترسی عضو پرسنده محدود است. در یک برنامهٔ خودی، نویسنده حساب `[bot]` برنامه است. از طریق Connect، یک توکن برای برنامهٔ مشترک یک توکن کاربر است، پس پاسخ به‌نام حساب عضوِ پرسنده نوشته می‌شود و از طریق برنامه عمل می‌کند. در هر دو حال، هر پاسخ با `**Control Center** (for @login):` شروع می‌شود، که می‌گوید چه کسی پرسیده و همچنین به‌عنوان محافظ حلقه عمل می‌کند.
- **در فضا، پرسش مال شماست.** پیام به عضوی که نویسنده به او حل شده منتسب می‌شود، و اجرای عامل به نیابت از او انجام می‌شود: کامیت‌ها او را هم‌نویسنده می‌کنند، و دیال خودمختاری فضا و گاردریل‌های کنش دقیقاً همان‌طور اعمال می‌شوند که برای پیامی که در برنامه تایپ شده اعمال می‌شد. نوشتن‌های forge از اجرا از توکن‌های تک‌مخزنی استفاده می‌کنند که به آن عضو محدود است، هرگز ورود او که به‌طور کامل واگذار شده باشد.

انتشار یافته‌های بازبینی به GitHub همچنان تصمیم یک فرد است، که در Control Center گرفته می‌شود. یک منشن می‌تواند یک بازبینی را _شروع_ کند؛ فقط یک انسان آن را منتشر می‌کند.

## محافظ حلقه، و نام کوتاه

هر چیزی که توسط یک حساب بات نوشته شده پیش از اجرای هر دروازه کنار گذاشته می‌شود — مخصوصاً بات خودمان، و هر پسوند `[bot]` — و همچنین هر نظری که با پیشوند `**Control Center** (for @` شروع شود، زیرا پاسخ از طریق Connect به‌نام حساب یک فرد نوشته می‌شود. بدون این، پاسخ‌ها به‌صورت نظرهای تازه می‌رسیدند و بریج را برای همیشه دوباره فعال می‌کردند.

پسوند `[bot]` همچنین دلیل وجود شکل کوتاه است. GitHub ورود یک حساب برنامه را روی `<slug>[bot]` ثابت می‌کند، برای آن تکمیل خودکار ارائه نمی‌دهد، و هرگز `@slug` را به برنامه حل نمی‌کند — پس پذیرفتن slug خالی تصمیم تطبیق‌دهندهٔ _خود ما_ است، و کشف آن به یک مسیر جست‌وجوی خام در **متن** نظر نیاز دارد، نه فهرست منشن‌های GitHub. هزینه بیان شده نه صاف‌شده: یک کاربر انسانی که slug برنامه را دارد، با هر منشن کوتاه از خودش، بات را هم مخاطب قرار می‌دهد. نام‌های متمایز برنامه این برخورد را فرضی می‌کنند.

## آنچه عمداً ارائه نمی‌شود

- **انتشار خودکار نیست.** یافته‌ها در فضای بازبینی قرار می‌گیرند؛ انتشار در GitHub یک کنش جداگانه و انسانی است
- **هویت مبهم نیست.** نویسنده دقیقاً به یک عضو حل می‌شود یا نادیده گرفته می‌شود — انتسابِ حدس‌زده وجود ندارد
- **تأیید خودکار نیست.** خودکارسازی می‌تواند نظر بدهد و تغییر بخواهد، اما یک بازبینی `APPROVE` پیش از ارسال رد می‌شود. تأیید کار یک فرد است
- **webhook برنامهٔ GitHub نیست.** این سطح هرگز یکی ثبت نمی‌کند، پس نشانی ورودی‌ای برای نشان دادن به نظرهای PR وجود ندارد. webhookهای دیگر محصول (پایپ‌لاین‌ها، همگام‌سازی تیکت) راه‌اندازی جداگانه و اختیاری هستند
