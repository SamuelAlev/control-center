این راهنما نشان می‌دهد چگونه گاردریل‌ها را پیکربندی کنید: قواعدی که تعیین
می‌کنند کنش یک عامل اجرا می‌شود، نخست درخواست تأیید می‌کند، یا رد می‌شود.

گاردریل‌ها سیزده کلاس اثری را پوشش می‌دهند که هر ابزار تغییردهنده اعلام می‌کند.
آن‌ها سمت سرور، درست در نقطه‌ای که ابزار فراخوانی می‌شود اعمال می‌شوند، هرگز با
دستوری در یک پرامپت.

## تنظیم یک تصمیم برای یک کلاس کنش

1. به **تنظیمات → فضای کاری → مجوزهای عامل** بروید
2. با کنترل بخش‌بندی‌شده یک محدوده انتخاب کنید: **فضای کاری**، **عامل** (سپس
   عامل را انتخاب کنید)، یا **فضا** (سپس فضا را انتخاب کنید)
3. روی ردیف کلاس کنش، **اجازه**، **ابتدا بپرس** یا **رد** را انتخاب کنید
4. برای حذف قاعده‌ای که گذاشته‌اید، دکمهٔ بازنشانی‌ای را بزنید که در انتهای همان
   ردیف ظاهر می‌شود (**پاک کردن تا مقدار ارثی**) — تصمیم به محدودهٔ گسترده‌تر
   بازمی‌گردد

هر ردیف تصمیم مؤثر را به‌صورت یک برچسب وضعیت و یک نشان برای منشأ آن نمایش
می‌دهد: **این محدوده**، **به ارث رسیده** یا **پیش‌فرض داخلی**. ماتریس در حالت
عامل (`chat`) حل می‌شود، پس **پیش‌تنظیم حالت** هرگز اینجا ظاهر نمی‌شود — برای
دیدن آن لایه، کاوشگر «اگر…؟» را با یک حالت فقط‌خواندنی انتخاب‌شده اجرا کنید.

نوشتن یک قاعده به نقش `admin` نیاز دارد. خواندن ماتریس چنین نیازی ندارد.

چک‌پوینت: در محدودهٔ فضای کاری، **پوش به یک ریموت** را روی **رد** بگذارید، سپس
کاوشگر «اگر…؟» زیر را روی `git push origin main` اجرا کنید. نتیجه `deny` را با
منبع `workspace` نشان می‌دهد.

## درک اینکه یک تصمیم چگونه حل می‌شود

حل به این ترتیب است: **نخست خاص‌بودن، سپس محدودکنندگی**:

1. قواعد **فضا**، سپس **عامل**، سپس **فضای کاری**. نخستین محدوده‌ای که قاعده‌ای
   منطبق دارد تصمیم می‌گیرد و حل در همان‌جا می‌ایستد
2. اگر هیچ قاعده‌ای منطبق نشود، **پیش‌تنظیم حالت** اعمال می‌شود — یک حالت
   فقط‌خواندنی (plan، review، orchestrate) یازده کلاس از سیزده کلاس را رد می‌کند
3. اگر حالت چیزی برای گفتن نداشته باشد، **پیش‌فرض داخلی** اعمال می‌شود

در یک محدودهٔ واحد، یک قاعدهٔ فرمان بر پایهٔ بلندترین پیشوند منطبق حل می‌شود و
یک تعارض با همان اندازه خاص‌بودن، **محدودکننده‌ترین** را برمی‌گزیند — رد از
ابتدا بپرس و ابتدا بپرس از اجازه قوی‌تر است. کنشی که چند کلاس اعلام می‌کند، هر
یک را مستقل حل می‌کند و سپس آن‌ها را به محدودکننده‌ترین شکل ترکیب می‌کند.

:::caution[اجازه بر رد نمی‌برد]
قاعده‌ای باریک‌تر بر پایهٔ خاص‌بودن برنده می‌شود و تساوی با محدودکنندگی شکسته
می‌شود — پس یک **اجازه** در محدودهٔ فضای کاری، یک **رد** را در هیچ‌جا باطل نمی‌کند.
:::

تصمیم **ابتدا بپرس** یک پرامپت تأیید بالا می‌آورد که هر کلاسی را که به `prompt`
رسیده است پوشش می‌دهد. **اگر تأییدکننده‌ای متصل نباشد، رد می‌شود** — هم برای
فرمان‌های شل و هم برای فراخوانی‌های ابزار هارنس. این عمدی است: یک اجرای بدون
دروازه بدتر از یک اجرای ردشده است.

### کلاس‌های کنش و پیش‌فرض‌های داخلی

| کلاس کنش                     | پیش‌فرض داخلی |
| ---------------------------- | ------------- |
| حذف یک فایل                  | ابتدا بپرس    |
| نوشتن بیرون از worktree      | اجازه         |
| ایجاد یک کامیت               | اجازه         |
| پوش به یک ریموت              | ابتدا بپرس    |
| باز کردن یک pull request     | ابتدا بپرس    |
| انتشار یک بازبینی یا ادغام   | ابتدا بپرس    |
| نوشتن در یک ردیاب خارجی      | ابتدا بپرس    |
| دسترسی به شبکه               | اجازه         |
| خواندن یک راز                | اجازه         |
| نصب یک بسته                  | اجازه         |
| اجرای یک فرایند              | اجازه         |
| تغییر ساختار فضای کاری       | اجازه         |
| راندن یک محفظه (ریگ)         | اجازه         |

این طبقه‌بندی بسته است. یک ابزار تازه که بدون اعلام کلاس‌هایش عرضه شود، در CI
در یک آزمون یک‌طرفهٔ سخت‌گیرانه شکست می‌خورد، پس هیچ ابزاری با مجموعهٔ اثرِ خالی
و بی‌صدا از راه نمی‌رسد.

## آزمودن یک قاعده با کاوشگر «اگر…؟»

پیش از تغییر یک قاعده، بررسی کنید که سیاست فعلی آن را چگونه حل می‌کند.

1. در همان صفحه، تا **اگر…؟** پایین بروید
2. یک **کنش** انتخاب کنید (یکی از سیزده کلاس)
3. به‌صورت اختیاری **فرمان** (برای نمونه `git push origin main`)، **عامل**،
   **فضا** و **حالت** را پر کنید
4. نتیجه را بخوانید: تصمیم، دلیل و **منبع:**

کاوشگر همان حل‌کننده‌ای را اجرا می‌کند که مسیر اعمال استفاده می‌کند، در برابر
قواعد زندهٔ شما، پس پاسخ دقیق است. اگر غافلگیرتان کرد، قاعده‌ای را در ماتریس
بالا تغییر دهید و دوباره کاوش کنید.

## تنظیم درجهٔ خودمختاری یک فضا

این درجه به‌ازای هر عامل در هر فضا تنظیم می‌شود و با قواعد ترکیب می‌شود، نه
اینکه جای آن‌ها را بگیرد.

1. فضا را باز کنید
2. از سرصفحهٔ فضا، **مدیریت مشارکت‌کنندگان** را باز کنید
3. زیر **خودمختاری** روی ردیف عامل، یک سطح انتخاب کنید:

| سطح                   | اثر                                                                                                |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| **پیش‌فرض**           | بدون تنظیم فضا — مانند **عمل با تأیید** رفتار می‌کند                                               |
| **فقط پیشنهاد**       | هر ابزار دروازه‌دار یکسره رد می‌شود، با پیامی که به عامل می‌گوید به‌جایش کنش را پیشنهاد کند       |
| **عمل با تأیید**      | کنش‌های پرخطر به دروازهٔ تأییدِ رد‌پیش‌فرض می‌خورند                                                 |
| **عمل آزاد**          | هر چیزی را که به یک رد سخت نرسیده باشد از پیش تأیید می‌کند                                          |

:::caution[عمل آزاد هر پرامپت را می‌بلعد]
تحت **عمل آزاد**، تصمیم **ابتدا بپرس** بدون پرسیدن از شما اعطا می‌شود. تنها یک
`deny` — از یک قاعده، از پیش‌تنظیم حالت، یا از یک پیش‌فرض داخلی — هنوز مسدود
می‌کند. وقتی فضا را زیر نظر دارید به آن رجوع کنید، نه به‌عنوان پیش‌فرض.
:::

این درجه فقط به هارنس داخلی می‌رسد. آداپتور Claude Code ابزارهای خودش را بیرون
از این دروازه اجرا می‌کند.

## بدانید گاردریل‌ها کجا نمی‌رسند

جدول **کجا قواعد اعمال می‌شوند** در پایین همان صفحه، نسخهٔ درون‌برنامه‌ای همین
است: به‌ازای هر کلاس اثر، می‌گوید هر اجراکننده آن را در دروازهٔ سیاست می‌گیرد،
به سندباکس واگذار می‌کند، یا اصلاً نمی‌تواند رهگیری‌اش کند.

- **آداپتور Claude Code** روی فراخوانی‌های ابزار خودش دروازه‌گذاری نمی‌شود.
  Claude Code با `--dangerously-skip-permissions` اجرا می‌شود، پس فراخوانی‌های
  خواندن، نوشتن، ویرایش و bash آن هرگز از نگهبان نمی‌گذرند. آنچه برای این
  آداپتور دروازه‌گذاری می‌شود، سطح ابزار MCP است که به آن بازمی‌گردد و فرمان
  شلی است که Control Center برای اجرای آن می‌سازد.
- **فعل خروجی خودِ یک حالت** (`submit_plan`، `propose_orchestration`) سنجاق شده
  است و هرگز نمی‌تواند رد شود — در غیر این صورت یک حالت ساختاراً نمی‌تواند تنها
  تحویل‌دادنی‌اش را تولید کند.
- **اینکه سندباکس پشتیبان این قواعد باشد به میزبان بستگی دارد.** جایی که
  `cc_server` بک‌اندی پیدا کند، CLI مربوط به Claude Code و ابزار `bash` هارنس را
  می‌پیچد، پس قاعده‌ای که شما ننوشته‌اید هم هنوز کف سیستم‌عاملی زیر خود دارد. روی
  **ویندوز هیچ‌کدام نیست** و روی Linux یا WSL2 بدون `bwrap` و `socat` هم
  هیچ‌کدام نیست — آنجا گاردریل‌ها به‌علاوهٔ سطح ابزار حالت، تمام اعمال‌اند، نه خط
  دفاعی دوم آن. با
  [پیکربندی سیاست‌های سندباکس](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/سیاستهای-سندباکس/) بررسی کنید در کدام حالت قرار دارید.
