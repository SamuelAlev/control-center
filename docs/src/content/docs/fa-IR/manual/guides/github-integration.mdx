این راهنما بخش‌های مخصوص GitHub در راه‌اندازی را پوشش می‌دهد. GitHub یکی از سه میزبان کد پشتیبانی‌شده است. برای اتصال GitLab یا Bitbucket، و برای اینکه یک فضای کاری آن‌ها را با هم ترکیب کند، ببینید [اتصال میزبان کد](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/اتصال-میزبان-کد/).

## پیش‌نیازها

- یک حساب GitHub با دسترسی به مخزن‌هایی که می‌خواهید روی آن‌ها کار کنید
- سروری که بتواند افراد را به GitHub وارد کند: یا GitHub App خودش (ببینید [ساختن GitHub App](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/github-app/))، یا Control Center Connect، که مالک سرور در **تنظیمات ← سرور ← ورود یکپارچه** انتخاب می‌کند

:::note[اعتبارنامه‌ها روی سرور زندگی می‌کنند و به شما متصل‌اند]
چیزی روی دستگاهی که با آن تایپ می‌کنید ذخیره نمی‌شود. ورود شما به GitHub توسط `cc_server` شما نگهداری می‌شود، با شناسهٔ کاربری شما کلید می‌خورد، و هر دستگاهی که از آن وارد می‌شوید از آن استفاده می‌کند: دسکتاپ، وب و تلفن. عضو دیگری از همان سرور نمی‌تواند از آن استفاده کند، و وارد کردن آن‌ها کاری است که خودشان انجام می‌دهند.
:::

## ورود به GitHub

GitHub فقط ورود است: توکنی برای چسباندن وجود ندارد.

۱. به **تنظیمات ← شما ← نمایه ← میزبانی کد** بروید (یا به گام اول راه‌اندازی اولیه)
۲. در ردیف **GitHub**، روی **ورود به GitHub** کلیک کنید
۳. مرورگر شما GitHub را باز می‌کند. برنامه را تأیید کنید

ورود چگونه تمام می‌شود، به این بستگی دارد که چه کسی آن را اجرا می‌کند:

- **برنامهٔ خود سرور:** GitHub مرورگر شما را به سرور برمی‌گرداند و گفتگو خودش آن را تشخیص می‌دهد. چیزی برای تایپ کردن نیست
- **Control Center Connect:** صفحهٔ مرورگر یک کد ۸ کاراکتری نشان می‌دهد. آن را در گفتگو تایپ کنید، یا اجازه دهید مرورگر از طریق پیوند `control-center://` خود Control Center را باز کند و تایپ را نادیده بگیرید

نقطهٔ بازبینی: ردیف **GitHub** می‌نویسد «وارد شده به‌عنوان _your-username_».

گفتگو کدی یا پیوندی را که خودش شروع نکرده رد می‌کند، با **این ورود از اینجا شروع نشده**. اگر کسی برایتان پیوند ورود فرستاد، ادامه ندهید: تکمیل آن حساب شما را به سرور آن‌ها وصل می‌کند.

برای حذف ورودتان **قطع اتصال** را بزنید. خروج از GitHub، یا حذف شدن از یک فضای کاری، هر توکنی را که سرور به نیابت از شما صادر کرده هم باطل می‌کند.

## اعتبارنامهٔ شما به نام چه کسی صحبت می‌کند

Control Center همان تفکیک GitHub را دنبال می‌کند میان عمل کردن **به‌عنوان یک فرد** و عمل کردن **به‌عنوان برنامه**:

| چه اتفاقی می‌افتد | در GitHub به‌صورت نشان داده می‌شود |
| --- | --- |
| هر کاری که خودتان انجام می‌دهید: نظر دادن، بازبینی، تأیید، ادغام، درخواست بازبین | **شما**. GitHub نظرِ داخل گفتگو را به‌عنوان نوشته‌شده با برنامهٔ Control Center علامت می‌زند؛ بازبینی و نظرهای درون‌خطی آن چنین علامتی ندارند |
| بازبینی با هوش مصنوعی، پاسخ‌ها و دیدگاه‌های عامل‌ها در گفتگوهای PR، برچسب‌ها، کار پایپ‌لاین و بات | **بات Control Center**. در برنامهٔ مشترک Connect، یک بازبینی فقط برای نصبی که اپراتور Connect فهرست کرده کار بات است؛ وگرنه به‌نام فرد مسئول نمایش داده می‌شود |
| یک pull request که عامل برای شما باز می‌کند، ویرایش‌های عنوان یا توضیح همان pull request، push ها و کامیت‌های آن | **شما**. وقتی اعتبار هم‌نویسنده روشن باشد، Control Center به‌عنوان هم‌نویسنده اعتبار می‌گیرد |
| کاری که کسی نخواسته است (زمان‌بندی‌ها، webhookها) | **بات Control Center**، به‌عنوان نویسندهٔ کامیت‌هایش نیز. در Control Center Connect هرگز push نمی‌کند و pull request باز نمی‌کند |

- **هر کاری که خودتان انجام می‌دهید** فقط با **ورود خودتان** و هیچ چیز دیگری اجرا می‌شود. اگر وارد نشده باشید، برنامه از شما می‌خواهد وارد شوید. هیچ اعتبارنامهٔ دیگری به جای شما نمی‌ایستد
- **کار بات** برای هر بار یک توکن برای یک مخزن می‌گیرد، که به آنچه یک عضو مسئول می‌تواند در آنجا انجام دهد محدود است: عضوی که درخواست کرده، وگرنه مالک فضای کاری. عضوی که نمی‌تواند push کند، توکن را به خواندن محدود می‌کند. پاسخ‌های بات که از طرف کسی عمل می‌کنند با **Control Center (برای @login)** شروع می‌شوند
- **عامل‌ها pull requestها را از طریق Control Center باز می‌کنند**، نه از sandbox خودشان، پس pull request مال شماست و قواعد خود GitHub جلوی تأیید خودتان را می‌گیرد. Control Center همچنین تأییدی را از کسی که از عامل خواسته کار را انجام دهد و از نویسندهٔ pull request رد می‌کند. برای اجرای زمان‌بندی‌شده یا webhook، این شامل هر مدیری می‌شود که تریگر آن را فعال کرده یا pipeline آن را ویرایش کرده در زمانی که فعال بوده است. باید فرد دیگری بازبینی کند. اگر Control Center نتواند تأیید کند چه کسی pull request را باز کرده، یا کدام حساب روی forge متعلق به شماست، درخواست را رد می‌کند و از شما می‌خواهد دوباره تلاش کنید
- **عامل‌ها دیدگاه‌ها را هم از طریق Control Center می‌گذارند.** توکن GitHub که یک اجرای عامل دریافت می‌کند فقط می‌خواند. وقتی عامل روی pull requestی که روی آن کار می‌کند نظر می‌گذارد، Control Center دیدگاه را به‌عنوان بات ارسال می‌کند، که با **Control Center (برای @login)** شروع می‌شود، وقتی کسی اجرا را درخواست کرده باشد. عامل فقط می‌تواند روی pull request خودش نظر بگذارد: یکی در همان مخزن، نه fork، که آخرین کامیت آن را خود عامل push کرده یا کامیت فعلی شاخهٔ فضای اوست. منشن‌های @ در دیدگاه عامل به هیچ‌کس اعلان نمی‌دهند. عامل می‌تواند عنوان یا توضیح pull request خودش را تا وقتی باز است تغییر دهد. این ویرایش همان‌طور انجام می‌شود که pull request باز شده بود (به نام شما، وقتی اجرا را درخواست کرده باشید) و به‌طور پیش‌فرض ابتدا تأیید می‌خواهد. توضیح pull request منشن‌های @ خود را نگه می‌دارد، هم وقتی عامل آن را باز می‌کند و هم وقتی آن را ویرایش می‌کند، پس کسانی که در آن نام برده شده‌اند اعلان می‌گیرند
- **در Control Center Connect، بات هرگز push یا pull request باز نمی‌کند.** push کردن، ساختن شاخه یا باز کردن pull request آنجا به فردی نیاز دارد که آن را درخواست کرده و با ورود همان فرد اجرا می‌شود. اجرای زمان‌بندی‌شده یا webhook که بخواهد push کند با پیامی که این را می‌گوید متوقف می‌شود. برای اینکه اجراهای بی‌نظارت بتوانند push کنند، به فضای کاری GitHub App اختصاصی‌اش را در **تنظیمات** بدهید
- **آنچه بات Connect می‌تواند انجام دهد.** با برنامهٔ مشترک Connect، بات دیدگاه، برچسب و واکنش می‌گذارد. بازبینی (بازبینی با هوش مصنوعی، نظرهای بازبینی، درخواست بازبین) را فقط وقتی ارسال می‌کند که اپراتور Connect نصب این سرور را فهرست کرده باشد. وگرنه بازبینی با ورود خودِ فرد مسئول منتشر می‌شود و به نام او ظاهر می‌شود. بات هرگز pull request را باز، ویرایش، بسته یا عنوانش را عوض نمی‌کند، بازبینی را لغو نمی‌کند، و دیدگاه را ویرایش یا حذف نمی‌کند؛ این کارها به فردی که درخواست کرده، با ورود خودش، نیاز دارد. Connect نصب سازمان شما را به یک سرور Control Center گره نمی‌زند: هر سروری که در آن عضوی که می‌تواند به یک مخزن push کند با ورود از طریق Connect باشد، می‌تواند توکن دیدگاه بات را برای آن مخزن بگیرد.
- **سرور یا فضای کاری‌ای که برنامهٔ GitHub خودش را دارد** همهٔ موارد بالا، از جمله بازبینی‌ها، را به بات می‌سپارد
- **خودکارسازی هرگز یک pull request را تأیید نمی‌کند.** تأیید کار یک فرد است

وقتی یک مخزن را پیوند می‌دهید، Control Center بررسی می‌کند که حساب شما بتواند آن را ببیند، و اگر GitHub App روی سازمان آن نصب نباشد یا مخزن را شامل نشود هشدار می‌دهد و پیوندی برای رفع آن نشان می‌دهد. پیوند زدن و برداشتن پیوند فقط با مدیر فضای کاری ممکن است، و یک checkout خارج از فضای ذخیره‌سازی خود فضای کاری را فقط مالک سرور می‌تواند پیوند دهد؛ ببینید [افزودن مخزن به فضای کاری](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/افزودن-مخزن/).

پیوند به شناسهٔ دائمی مخزن در GitHub وصل است، پس تغییر نام یا انتقال مخزن نیازی به کار شما ندارد. اگر مسیر بعداً به مخزن دیگری اشاره کند، Control Center دیگر هیچ چیزی به آن نمی‌فرستد و تا وقتی مدیر فضای کاری روی **پیوند دوباره** نزند، اعلانی نشان می‌دهد.

باز کردن کد یک مخزن (فایل‌ها، diffها، جستجو، یک ترمینال) هم به دسترسی آن در فضای کاری نیاز دارد و هم به ورود GitHub خودتان که بتواند آن را بخواند. مدیران فضای کاری همین قاعده را دنبال می‌کنند؛ فقط مالک سرور معاف است.

## یکپارچه‌سازی چه چیزی به شما می‌دهد

| امکان                  | روش                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| فهرست و جزئیات PR      | API مربوط به REST در GitHub، از سرور، با ورود خودتان                                                                       |
| اجراهای بررسی          | API مربوط به Checks در GitHub                                                                                               |
| انتشار بازبینی         | یک گام دارای دروازهٔ کاربر که بازبینی شما را به‌نام شما روی PR می‌گذارد                                                    |
| ثبت مخزن               | یک checkout پذیرفته می‌شود اگر remote آن `origin` به github.com، یا به gitlab.com / bitbucket.org، اشاره کند                  |
| دسترسی عامل به GitHub | در داخل یک اجرا، `git fetch` از طریق Control Center انجام می‌شود و مخزن‌هایی را که اجرا روی آن‌ها کار می‌کند با توکن فقط‌خواندنی‌ای می‌آورد که اجرا هرگز در اختیار ندارد. `gh` آن‌ها را با توکن فقط‌خواندنی‌ای می‌خواند که Control Center وقتی درخواست شود صادر می‌کند و با پایان اجرا باطل می‌شود؛ push ها، pull requestها، ویرایش‌های آن‌ها و دیدگاه‌ها از طریق Control Center انجام می‌شوند |
| اعلان‌ها               | نظرسنجی سمت سرور از صندوق اعلان‌های GitHub شما «در pull request منشن شدید» و «بازبینی درخواست شد» را می‌سازد               |
| پروفایل کاربران        | کارت‌های شناور پروفایل و فیلتر PR به‌ازای نویسنده                                                                          |

برخی مسیرها به‌جای REST از API مربوط به GraphQL استفاده می‌کنند، هرجا که ارزان‌تر است: فعالیت شاخه برای انتخاب‌گر PR ساختن، و وضعیت زندهٔ بازبینی که تعیین می‌کند آیا اعلان «بازبینی درخواست شد» هنوز در انتظار است.

## مراقب قطعی GitHub باشید

نوار عنوان وقتی یک ارائه‌دهنده دچار مشکل است یک تراشهٔ وضعیت نشان می‌دهد، که GitHub، Claude، OpenAI و Kimi را پوشش می‌دهد. **وقتی همه‌چیز سالم است پنهان است**: حضور مشکل را گزارش می‌کند، نه نبودنش را.

روی تراشه کلیک کنید تا یک فلای‌اوت با وضعیت هر ارائه‌دهنده و دکمهٔ تازه‌سازی باز شود. وضعیت‌ها هر دو دقیقه خودبه‌خود تازه می‌شوند.

## بدانید عامل‌ها چگونه روی GitHub عمل می‌کنند

- عاملی که در یک worktree گیت‌هاب کار می‌کند، توکنی برای همان مخزن واحد می‌گیرد. فقط می‌تواند کد، مسئله‌ها و pull requestها را بخواند؛ دیدگاه‌ها از طریق Control Center می‌روند، همان‌طور که در بالا گفته شد. push از طریق Control Center انجام می‌شود، که از قاعدهٔ **push به یک remote** می‌پرسد و سپس آن را با یک توکن نوشتن که عامل هرگز در دست ندارد عبور می‌دهد. ببینید [پیکربندی سیاست‌های sandbox](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/سیاستهای-سندباکس/)
- کارهایی که خودتان شروع می‌کنید با نام خودتان commit می‌شوند. وقتی از یک عامل چیزی می‌خواهید، یا در IDE commit می‌کنید، شما نویسنده و committer هستید، با نشانی‌ای که forge آن را تأیید کرده: نشانی noreply گیت‌هاب شما از ورودتان به GitHub، یا روی GitLab و Bitbucket ایمیلی که ورود شما آنجا گزارش می‌کند. هویت Git فضای کاری شما فقط برای کامیتی به کار می‌رود که دستی و در مخزنی می‌سازید که هیچ forge ای نشانیِ شما را تأیید نکرده است. اگر وارد آن forge نشده‌اید، کامیت‌های عامل در عوض مال بات هستند و یادداشت‌های اجرا این را می‌گویند
- کارهایی که کسی نخواسته با نام بات commit می‌شوند. یک اجرای زمان‌بندی‌شده یا webhook به‌نام GitHub App فضای کاری (`<app>[bot]`، با نشانی noreply گیت‌هاب آن) commit می‌کند، یا به‌نام `Control Center <hi@usectrl.dev>` وقتی GitHub App نیست یا مخزن روی GitLab یا Bitbucket است
- **ذکر Control Center به‌عنوان هم‌نویسنده** (**تنظیمات** ← **شما** ← **کامیت‌ها**) یک trailer از نوع `Co-Authored-By:` برای طرف دیگر اضافه می‌کند: Control Center روی کامیت‌های شما، و روی کامیت‌های بات هر فردی که تریگر پشت اجرا را فعال کرده است. این گزینه تا وقتی خاموش نکنید روشن است. مدیر فضای کاری می‌تواند با **اعتبار هم‌نویسنده** در **تنظیمات** ← **فضای کاری** ← **عمومی** این را برای همه تعیین کند؛ در این صورت انتخاب شما ذخیره می‌شود اما در آن فضای کاری اعمال نمی‌شود. سطر انتساب خود Claude Code همیشه غیرفعال است
- کامیت‌های شما می‌توانند امضا شوند. زیر **کامیت‌های تأییدشده** در **تنظیمات** ← **شما** ← **کامیت‌ها** گزینهٔ **ساختن کلید امضا** را بزنید و بخش عمومی آن را به‌عنوان کلید امضا به حساب GitHub یا GitLab خود اضافه کنید؛ از آن به بعد کامیت‌های اجراهایی که درخواست می‌کنید، و کامیت‌هایی که در IDE می‌سازید، تأییدشده نشان داده می‌شوند. بخش خصوصی روی سرور شما می‌ماند، پس هر کس که آن سرور را کنترل کند تا وقتی کلید در حساب شما باشد می‌تواند به‌نام شما امضا کند، و در GitHub کامیتی که از قبل تأییدشده نشان داده شده، پس از حذف کلید همچنان تأییدشده می‌ماند. Bitbucket کلید امضای جدا ندارد: کلید را آنجا اضافه نکنید، و کامیت‌های Bitbucket امضا نمی‌شوند. کامیت‌های بات هرگز امضا نمی‌شوند
- کامیت‌هایی که در پنل **کنترل منبع** در IDE می‌سازید، قلاب‌های Git مخزن را رد می‌کنند، همان‌طور که `git commit --no-verify` این کار را می‌کند؛ و Git سرور کمک‌کننده‌های اعتبارنامه، ویرایشگرها، ابزارهای diff بیرونی و امضاکننده‌هایی را که مخزن پیکربندی می‌کند نادیده می‌گیرد: Git را روی ماشین خودش اجرا می‌کند، در درختی که یک عامل یا یک pull request می‌تواند آن را تغییر دهد. ببینید [کامیت و push از کنترل منبع](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/بازبینی-و-ادغام-pr/#کامیت-و-push-از-کنترل-منبع)
- هر کامیتی که عامل push می‌کند ابتدا بررسی می‌شود، از جمله لایه‌هایی که `stack_publish` برای یک stack push می‌کند. push ای که شخص دیگری را نام ببرد، یکی از اعتبارها را حذف یا قرض کند، یک سطر امضا اضافه کند، یا آن‌طور که تنظیماتتان می‌گوید امضا نشده باشد، رد می‌شود. کامیت‌هایی که خودتان از IDE push می‌کنید مال خودتان هستند و به این شکل بررسی نمی‌شوند
- یک ترمینالی که روی یک rig باز می‌کنید ورود خودتان را دریافت می‌کند، محدود به همان یک مخزن، پس push های آنجا مال شماست
- وقتی هیچ توکنی نمی‌تواند صادر شود (هیچ‌کس مسئول وارد نشده، برنامه روی مالک نصب نیست، یا نصب معلق است)، فرمانی که آن را درخواست کرده دلیلش را می‌گوید. اعتبارنامهٔ جایگزینی وجود ندارد

## عیب‌یابی

### فهرست PR خالی است و می‌گوید GitHub متصل نیست

شما روی این سرور با GitHub وارد نشده‌اید. زیر **تنظیمات ← شما ← نمایه ← میزبانی کد** روی **ورود به GitHub** کلیک کنید. مخزن‌های forgeهای دیگر تحت‌تأثیر نیستند.

### ردیف GitHub می‌گوید ورود روی این سرور تنظیم نشده است

سرور نه GitHub App خودش را دارد و نه Connect. مالک سرور یکی از آن‌ها را در **تنظیمات ← سرور ← ورود یکپارچه** انتخاب می‌کند: **ساختن GitHub App من** حدود دو دقیقه طول می‌کشد. ببینید [ساختن GitHub App](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/github-app/).

در فضای کاری‌ای که روی برنامه‌های خودش است، ردیف وقتی برنامهٔ GitHub آن فضا کم یا ناقص باشد این را نشان می‌دهد. یک مدیر فضای کاری آن را روی کارت **برنامهٔ GitHub** در **تنظیمات ← فضای کاری ← یکپارچه‌سازی‌ها** کامل می‌کند؛ ببینید [دادن برنامهٔ اختصاصی به یک فضای کاری](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/github-app/#به-یک-فضای-کاری-برنامهٔ-اختصاصی-خودش-را-بدهید).

### گفتگو می‌گوید کد مطابقت ندارد

کد را دقیقاً همان‌طور که مرورگر نشان می‌دهد تایپ کنید: ۸ حرف و رقم. پنج کد اشتباه ورود را پایان می‌دهد؛ دوباره شروع کنید.

### ورود می‌گوید برنامه نصب نشده است

GitHub App روی حسابی که مخزن مال آن است نصب نشده. یک مدیر فضای کاری آن را از **تنظیمات ← فضای کاری ← یکپارچه‌سازی‌ها ← نصب‌های GitHub App** نصب می‌کند.

### همه باید دوباره وارد GitHub شوند

مالک سرور کلید Connect سرور را چرخانده، بین سرورهای Connect جابه‌جا شده، یا پوشهٔ داده روی ماشین دیگری بازیابی شده است. ورودهای از طریق Connect به سروری که آن‌ها را ساخته گره خورده‌اند.

### افزودن یک مخزن رد می‌شود

ثبت هر سه شرط را لازم دارد: مسیر داخل یک درخت کاری git باشد، یک remote به نام `origin` داشته باشد، و آن remote به یک forge پشتیبانی‌شده (github.com، gitlab.com یا bitbucket.org) اشاره کند. `origin` باید همان مخزنی باشد که پیوند می‌دهید، و پوشه‌ای خارج از فضای ذخیره‌سازی خود فضای کاری را فقط مالک سرور می‌تواند پیوند دهد. ببینید [افزودن مخزن به فضای کاری](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/افزودن-مخزن/).

### با وجود مجوز فضای کاری، مخزن می‌گوید حساب من نمی‌تواند آن را بخواند

حساب GitHub شما نمی‌تواند آن مخزن را بخواند، پس کدش حتی با مجوز فضای کاری برای شما بسته می‌ماند. زیر **میزبانی کد** به GitHub وارد شوید، یا برای دسترسی به مخزن در GitHub درخواست بدهید.

### "دسترسی شما به GitHub تأیید نشد"

GitHub برای بررسی دسترسی شما در دسترس نبود، پس Control Center به جای حدس زدن رد کرد. لحظه‌ای دیگر دوباره امتحان کنید.

### بازبینی‌ها روی Connect به نام من ظاهر می‌شوند، نه بات

روی برنامهٔ مشترک Connect، بات فقط برای نصب‌هایی بازبینی ارسال می‌کند که اپراتور Connect فهرستشان کرده است. در جاهای دیگر، بازبینی با ورود خودِ فرد مسئول منتشر می‌شود. برای اینکه بات بازبینی‌ها را بفرستد، به فضای کاری GitHub App اختصاصی خودش را بدهید.

### پس از استفادهٔ سنگین، برای مدتی همه‌چیز از کار می‌افتد

این کلید قطع‌کنندهٔ محدودیت نرخ است. GitHub محدودیت اصلی‌اش را با یک `403` که `x-ratelimit-remaining: 0` و زمان بازنشانی دارد اعلام می‌کند؛ وقتی کلاینت یکی را ببیند، درخواست‌های بیشتر را محلی و بدون تماس با شبکه شکست می‌دهد تا بازهٔ زمانی بگذرد، پس طوفان تلاش مجدد نمی‌تواند محدودیت را عمیق‌تر کند. خطاهای گذرا تا سه بار با backoff نمایی و با رعایت `retry-after` دوباره امتحان می‌شوند.
