Control Center با سه میزبان کد کار می‌کند که در سراسر برنامه **forge** نامیده می‌شوند: **GitHub**، **GitLab** و **Bitbucket Cloud**. هیچ‌کدام پیش‌فرض نیست. یکی را متصل کنید و همه‌چیز کار می‌کند؛ چند تا را متصل کنید و یک فضای کاری می‌تواند مخزن‌های همهٔ آن‌ها را هم‌زمان در خود جای دهد.

میزبان کد ویژگی هر **مخزن** است و هنگام ثبت آن، از ریموت `origin` آن خوانده می‌شود. هرگز آن را انتخاب نمی‌کنید و هیچ تنظیمی در سطح فضای کاری نیست که بتوانید اشتباه کنید.

## اتصال یک میزبان کد

1. **تنظیمات → شما → نمایه** را باز کنید (`/settings/you/profile`).
2. کارت **میزبانی کد** را پیدا کنید. هر میزبان کد پشتیبانی‌شده در آن فهرست شده است، متصل یا نامتصل.
3. در **GitHub**، **ورود به GitHub** را بزنید. در **GitLab** یا **Bitbucket**، **افزودن توکن** را بزنید و یکی را جای‌گذاری کنید.

**ورود به GitHub** فقط ورود است: از طریق GitHub App خود سرور یا از طریق Control Center Connect انجام می‌شود، بسته به اینکه مالک سرور کدام را تنظیم کرده باشد، یا برنامه‌هایی که یک مدیر فضای کاری برای همین فضای کاری در **تنظیمات → فضای کاری → یکپارچه‌سازی‌ها** انتخاب کرده است (به [راه‌اندازی یکپارچه‌سازی GitHub](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/یکپارچهسازی-github/) نگاه کنید). توکنی برای جای‌گذاری وجود ندارد. GitLab و Bitbucket هنوز یک توکن شخصی می‌گیرند.

در هر دو حالت، اعتبارنامه **از شماست و روی سرور می‌ماند** و با شناسهٔ کاربری شما کلید می‌خورد: هیچ توکنی روی دستگاهی که آن را در آن وارد کرده‌اید ذخیره نمی‌شود، هر دستگاهی که از آن وارد می‌شوید از همان یکی استفاده می‌کند و هیچ عضو دیگری نمی‌تواند آن را بخواند. از **درخواست بعدی** اثر می‌کند — چیزی برای راه‌اندازی مجدد نیست و قطع اتصال، ارسال آن را بلافاصله متوقف می‌کند.

کارت نشان می‌دهد حساب‌های شما کجا استفاده می‌شوند. توکن GitLab یا Bitbucket در **همهٔ فضاهای کاری روی این سرور** مال شماست، پس یک بار آن را می‌چسبانید. ورود GitHub شما هم همین‌طور است، مگر اینکه فضای کاری‌ای برنامه‌های ورود خودش را داشته باشد: آن فضای کاری ورود GitHub جدا خودش را نگه می‌دارد و کارت نامش را می‌برد.

هر ردیف وضعیت **اعتبارنامهٔ خودتان** را نشان می‌دهد. فقط اعتبارنامهٔ خودتان از طرف شما پاسخ می‌دهد؛ هیچ چیز دیگری جای آن را نمی‌گیرد:

| ردیف می‌گوید | معنا |
| --- | --- |
| `وارد شده به‌عنوان octocat` | اعتبارنامهٔ خودتان به کار می‌رود |
| `متصل نیست` | برای این میزبان کد اعتبارنامه‌ای ندارید |
| `ورود شما به GitHub با حساب octocat منقضی شده است. دوباره وارد شوید.` | ورود شما منقضی شده یا روی میزبان کد لغو شده است |
| `متوقف شده: سرویس ورود این فضای کاری تغییر کرده است` | این فضای کاری به سرویس ورود دیگری رفته است. ورود شما نگه داشته می‌شود و اگر دوباره برگردد کار می‌کند، پس دکمهٔ ورود وجود ندارد |
| `اکنون دسترسی به GitHub ممکن نیست. در حال تلاش دوباره.` | یک قطعی موقت. Control Center به تلاش ادامه می‌دهد؛ کاری لازم نیست |
| یک جمله که توضیح می‌دهد چرا ورود در دسترس نیست | برای مثال `ورود با GitHub برای این فضای کاری تنظیم نشده است.` یا `سرویس ورود این فضای کاری هویت خود را تغییر داده است. یک مدیر باید آن را تأیید کند.` مدیران دکمه‌ای به تنظیمی دارند که مشکل را برطرف می‌کند |

### هر میزبان کد چه توکنی می‌خواهد

| میزبان کد     | توکن                                                                                                              | کجا آن را بسازید                                      |
| ------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **GitLab**    | یک توکن دسترسی شخصی با `api`                                                                                       | gitlab.com → User settings → Access tokens             |
| **Bitbucket** | یک توکن API از Atlassian، به‌همراه ایمیل حساب شما                                                                  | id.atlassian.com → Security → API tokens               |

Bitbucket با **ایمیل حساب شما به‌عنوان نام کاربری** و توکن API به‌عنوان گذرواژه احراز هویت می‌کند، پس گفتگوی Bitbucket هر دو را می‌خواهد. یک **توکن دسترسی** مخزن، پروژه یا فضای کاری Bitbucket به هیچ فردی تعلق ندارد، پس این گفتگو آن را نمی‌پذیرد: به‌جایش یک [توکن خودکارسازی](#افزودن-توکن-خودکارسازی) است. همین‌طور برای توکن دسترسی **پروژه** یا **گروه** GitLab: پیش از ذخیرهٔ توکن از GitLab پرسیده می‌شود توکن مال کیست، و توکن یک بات اینجا رد می‌شود.

یک توکن هرگز به یک فضای کاری گره نمی‌خورد: برای هر میزبان یکی دارید و هر فضای کاری روی این سرور از آن استفاده می‌کند. **قطع اتصال** آن را برای همهٔ آن‌ها حذف می‌کند.

### کار در پس‌زمینه

کاری که هیچ انسانی پشت آن نیست (اجرای عامل‌ها، پایپ‌لاین‌ها، نظرسنجی PR) هم به اعتبارنامه نیاز دارد، و هر میزبان کد پاسخ متفاوتی به آن می‌دهد:

- **GitHub** — توکنی برای یک مخزن در هر بار، که از GitHub App سرور یا از طریق Connect صادر می‌شود و به آنچه یک عضو مسئول می‌تواند آنجا انجام دهد محدود است. هرگز ورود شخصی یک فرد نیست که کامل واگذار شود، و هیچ متغیر محیطی یا توکن چسبانده‌شده جای آن را نمی‌گیرد. [راه‌اندازی یکپارچه‌سازی GitHub](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/یکپارچهسازی-github/#اعتبارنامهٔ-شما-به-نام-چه-کسی-صحبت-میکند)
- **GitLab** و **Bitbucket** — فقط **توکن خودکارسازی** مخزن: یک توکن دسترسی بات که یک مدیر فضای کاری برای همان مخزن، یا برای همهٔ مخزن‌های آن میزبان در فضای کاری اضافه می‌کند. توکن خود مخزن بر توکن فضای کاری مقدم است. نظرسنجی pull requestها، نظرهای بازبینی هوش مصنوعی، و push ها و merge requestهایی که کسی درخواست نکرده از آن استفاده می‌کنند، پس در میزبان به‌صورت آن بات نمایش داده می‌شوند، نه هرگز به‌عنوان یک عضو. توکن شخصی هیچ عضوی جای آن را نمی‌گیرد، و توکن سراسری سرور یا متغیر محیطی وجود ندارد. بدون آن، کار پس‌زمینهٔ مخزن متوقف می‌شود و اعلان دسترسی به مخزن‌ها این را می‌گوید.

کاری که یک عضو درخواست می‌کند (یک دیدگاه، یک بازبینی، یا یک merge request عامل که برای او باز شده) همچنان از توکن خود آن عضو استفاده می‌کند.

## افزودن توکن خودکارسازی

فقط مدیران فضای کاری توکن‌های خودکارسازی را می‌بینند یا تغییر می‌دهند. هر توکن هنگام ذخیره با میزبان بررسی می‌شود: توکن شخصی (توکن دسترسی شخصی GitLab، توکن API آتلسین، یا هر توکن Bitbucket که به‌جای حساب کسی وارد می‌شود) رد می‌شود، و توکنی که نتواند مخزن مقصدش را بخواند هم رد می‌شود.

- **برای یک مخزن:** **تنظیمات → فضای کاری → مخزن‌ها** را باز کنید. کارت **توکن‌های خودکارسازی** هر مخزن GitLab و Bitbucket را همراه با باتی که آنجا عمل می‌کند نشان می‌دهد: **از توکن فضای کاری استفاده می‌کند**، یا **توکنی نیست. خودکارسازی اینجا متوقف شده است.** روی **افزودن توکن** در ردیف مخزن بزنید.
- **برای همهٔ مخزن‌های یک میزبان:** **تنظیمات → فضای کاری → یکپارچه‌سازی‌ها** را باز کنید، کارت **توکن‌های خودکارسازی** را پیدا کنید و روی **افزودن توکن** در ردیف GitLab یا Bitbucket بزنید. مخزن‌هایی که توکن نمی‌تواند بخواندشان بعد از ذخیره نام برده می‌شوند و متوقف می‌مانند.

وقتی کار پس‌زمینه از قبل متوقف است، مدیران **افزودن توکن** را مستقیم روی اعلان دسترسی به مخزن‌ها هم می‌بینند. **به‌روزرسانی توکن** توکن را جایگزین می‌کند؛ دکمهٔ سطل زباله آن را حذف می‌کند، و هر مخزنی که بدون توکن بماند متوقف می‌شود. اگر میزبان بعداً توکن ذخیره‌شده‌ای را رد کند (باطل‌شده یا منقضی)، ردیفش این را می‌گوید و مخزن‌هایی که پوشش می‌داد تا جایگزینی توکن متوقف می‌مانند.

| میزبان کد     | توکن خودکارسازی | کجا آن را بسازید |
| ------------- | --- | --- |
| **GitLab**    | یک **توکن دسترسی پروژه** یا **گروه** با `read_api` و `read_repository`؛ برای دیدگاه‌ها، merge requestها و push، `api` و `write_repository` را هم اضافه کنید | پروژه یا گروه → Settings → Access tokens |
| **Bitbucket** | یک **توکن دسترسی مخزن**، **پروژه** یا **فضای کاری** با خواندن مخزن، به‌همراه نوشتن pull request برای دیدگاه‌ها و pull requestها (نوشتن مخزن برای push) | مخزن، پروژه یا فضای کاری → Settings → Access tokens |

GitLab کار را به‌صورت کاربر بات آن توکن نشان می‌دهد؛ Bitbucket آن را با نام توکن دسترسی نشان می‌دهد.

### Bitbucket: توکن دسترسی یا توکن API

Bitbucket دو نوع توکن دارد و Control Center آن‌ها را جدا نگه می‌دارد:

- یک **توکن API** (id.atlassian.com) متعلق به حساب Atlassian شماست و همراه ایمیلتان به کار می‌رود. این **اعتبارنامهٔ خودتان** است و زیر **میزبانی کد** در **تنظیمات → شما → نمایه** قرار می‌گیرد.
- یک **توکن دسترسی** (که در تنظیمات یک مخزن، پروژه یا فضای کاری ساخته می‌شود) به آن مخزن، پروژه یا فضای کاری تعلق دارد، نه به یک فرد. این یک **توکن خودکارسازی** است و زیر **توکن‌های خودکارسازی** قرار می‌گیرد.

هر گفتگو نوع دیگر را رد می‌کند و می‌گوید کجا تعلق دارد.

## روی هر میزبان کد، شما آدم دیگری هستید

همان انسان روی GitHub `octocat` است و روی GitLab چیزی کاملاً دیگر. Control Center هویت شما را **به تفکیک هر میزبان کد** حل می‌کند و برای هر مخزن همان درست را به کار می‌برد؛ همین است که «نیاز به بازبینی من» را، «ساختهٔ من» را و «شما این را تأیید کردید» را در یک فضای کاری مخلوط درست می‌کند.

اگر هویت یک میزبان کد حل نشده باشد، مخزن‌هایش به‌جای اینکه با همه‌چیز مطابقت کنند، هیچ چیزی به صندوق ورودی نمی‌دهند. صندوق ورودی همین را می‌گوید، نه اینکه ادعا کند همه‌چیز را رسیدگی کرده‌اید.

## فقط چیزی را می‌بینید که حساب خودتان می‌تواند ببیند

pull requestهای یک مخزن فقط وقتی به شما می‌رسند که نقش شما در فضای کاری آن مخزن را مجاز کند **و حساب خودتان روی آن میزبان کد بتواند آن را بخواند**. مدیران فضای کاری و مالک هم همین قاعده را دنبال می‌کنند. وقتی برخی مخزن‌ها پنهان‌اند، صندوق ورودی و صف PR می‌گویند چند تا و چرا، بدون اینکه نامشان را ببرند:

- **برای دیدن pull requestهای ۳ مخزن دیگر وارد GitHub شوید**: هنوز این میزبان کد را اینجا متصل نکرده‌اید. وارد شوید تا آن‌ها ظاهر شوند
- **۳ مخزن پنهان است چون حساب GitHub شما آن‌ها را نمی‌بیند**: از کسی که در میزبان کد دسترسی دارد بخواهید
- **۳ مخزن پنهان است چون در این فضای کاری به آن‌ها دسترسی ندارید**: از یک مدیر فضای کاری بخواهید به آن‌ها دسترسی بدهد
- **در حال بررسی دسترسی شما به ۳ مخزن دیگر…**: مدتی کوتاه نشان داده می‌شود، تا Control Center تأیید کند حساب شما چه چیزی را می‌تواند بخواند

کد هم همین قاعده را دنبال می‌کند. برای باز کردن فایل‌ها، diffها یا جستجوی یک مخزن، یا ترمینالی روی آن، باید مجوزش را در این فضای کاری داشته باشید و حساب خودتان روی forge باید بتواند آن را بخواند؛ مدیران فضای کاری هم همین‌طورند و فقط مالک سرور استثنا است. وقتی forge برای بررسی در دسترس نباشد، پیام «دسترسی شما به سکوی کد تأیید نشد. دوباره امتحان کنید.» را می‌بینید (که نام سکو را هم می‌آورد). [کد از سکوی کد پیروی می‌کند](/fa-IR/راهنمای-کاربر/مفهومها/مجوزدهی/#کد-از-forge-پیروی-میکند).

همین قاعده برای هر چیزی که از آن pull requestها ساخته می‌شود نیز اعمال می‌شود. یک فضای بازبینی، پیام‌ها و اجراهای عامل آن تا زمانی که نتوانید pull request آن را ببینید ناپدید می‌شوند، و فضای بازبینی باز اگر دسترسی‌تان را از دست بدهید بسته می‌شود. اجراهای pipeline مربوط به یک pull request پنهان از فهرست اجراهای شما حذف می‌شوند. عامل‌هایی که برای شما کار می‌کنند نیز نمی‌توانند آن فضاهای بازبینی را بخوانند. فهرست مخزن‌های فضای کاری هر مخزنی را که در این فضای کاری به آن دسترسی دارید نشان می‌دهد، حتی مخزنی که حساب forge شما هنوز به آن نمی‌رسد.

اگر forge محدودیت نرخ دارد یا از کار افتاده است، Control Center چند دقیقه آخرین وضعیتی را که تأیید کرده نشان می‌دهد و سپس آن pull requestها را پنهان می‌کند تا بتواند دوباره بررسی کند.

## یک صندوق ورودی، همهٔ میزبان‌های کد

صندوق ورودی و صف PR روی هر میزبانی که در فضای کاری حاضر است پخش می‌شوند و نتایج را در یک جریان یکی می‌کنند — یک pull request از GitHub و یک pull request از Bitbucket کنار هم می‌نشینند، به ترتیب زمان، نه گروه‌بندی‌شده بر پایهٔ فروشنده.

خطاها جدا از هم‌اند. میزبانی که از کار افتاده یا به محدودیت نرخ خورده، بقیه را دست‌نخورده می‌گذارد و مخزن‌های خودش تا بهبود، آخرین وضعیت شناخته‌شده‌شان را نگه می‌دارند؛ هرگز کل صندوق ورودی را خالی نمی‌کند. مخزنی که سرور دیگر به آن دسترسی ندارد، به‌جای نشان دادن pull requestهای قدیمی از فهرست حذف می‌شود، و **اعلان دسترسی به مخزن‌ها** نام آن را همراه راه‌حل نشان می‌دهد: نصب GitHub App روی سازمانش، افزودن مخزن به مخزن‌های برنامه، از سرگیری یک نصب معلق، یا اینکه عضو مسئول دوباره وارد شود، یا افزودن یک توکن خودکارسازی برای مخزن GitLab یا Bitbucket. مدیران دکمه‌ای برای مراحل GitHub App و برای افزودن توکن دارند.

## هر میزبان کد چه کارهایی می‌تواند بکند

هر میزبان کدی از حلقهٔ اصلی پشتیبانی می‌کند: فهرست‌کردن و باز کردن pull requestها، خواندن diffها، نظر دادن به‌صورت درون‌خطی و در سطح بالا، بازبینی، ادغام و بستن. فراتر از آن، آن‌ها واقعاً با هم تفاوت دارند و Control Center آنچه را یک میزبان کد نمی‌تواند انجام دهد پنهان می‌کند، نه اینکه کنترلی نشان دهد که بی‌صدا شکست می‌خورد.

| توانایی                                | GitHub | GitLab | Bitbucket |
| -------------------------------------- | :----: | :----: | :-------: |
| بازبینی‌های دسته‌ای (در انتظار)          |   ✓    |   ✓    |     —     |
| درخواست تغییر                          |   ✓    |   ✓    |     ✓     |
| وضعیت «دیده‌شده» به تفکیک فایل، همگام‌شده |   ✓    |   —    |     —     |
| واکنش‌های ایموجی                        |   ✓    |   ✓    |     —     |
| بازبین‌های تیم / گروه                    |   ✓    |   ✓    |     —     |
| بازبین‌های پیشنهادی                      |   ✓    |   —    |     ✓     |
| نتایج CI روی یک PR                     |   ✓    |   ✓    |     ✓     |
| کندوکاو در گام‌ها/لاگ‌های یک کار CI       |   ✓    |   ✓    |     —     |
| pull requestهای پشته‌ای                  |   ✓    |   —    |     —     |
| قالب‌های توضیح PR                        |   ✓    |   ✓    |     —     |
| نظرسنجی اعلان‌ها                         |   ✓    |   —    |     —     |
| نمایه‌های کاربری غنی                     |   ✓    |   ✓    |     —     |
| ارجاع head برای PR در سمت سرور          |   ✓    |   ✓    |     —     |

آن‌جا که توانایی‌ای وجود ندارد، قابلیت صادقانه تنزل می‌کند:

- **وضعیت دیده‌شده** همچنان کار می‌کند، اما فقط روی دستگاهی که آن را رویش تنظیم کرده‌اید.
- **بازبینی‌های دسته‌ای** در Bitbucket نظر به نظر ارسال می‌شوند، پس بازبین‌ها آن‌ها را یکی‌یکی می‌بینند، نه یک‌جا.
- **نبود ارجاع head برای PR** در Bitbucket یعنی چک‌اوت کردن یک pull request شاخهٔ مبدأ آن را با نام می‌گیرد، که پس از حذف آن شاخه شکست می‌خورد.

## واژگان

GitLab به یک pull request می‌گوید **merge request**. Control Center در سراسر مدل خودش «pull request» می‌گوید و آن‌جا که دربارهٔ خود یک میزبان کد حرف می‌زند، از اسم خود همان میزبان استفاده می‌کند.

## عیب‌یابی

### فهرست PR خالی است و می‌گوید یک میزبان کد متصل نیست

برای آن میزبان کد اعتبارنامه‌ای ندارید. به GitHub در **تنظیمات → شما → نمایه → میزبانی کد** وارد شوید، یا برای GitLab یا Bitbucket توکنی جای‌گذاری کنید. مخزن‌های دیگر میزبان‌ها دست‌نخورده می‌مانند.

### یک میزبان کد را متصل کردم اما مخزن‌هایش هنوز چیزی نشان نمی‌دهند

زیرنویس ردیف و سپس اعلان‌های بالای فهرست PR را بررسی کنید. «برای دیدن pull requestهای ۳ مخزن دیگر وارد GitHub شوید» یعنی حساب خودتان برای آن مخزن‌ها متصل نیست؛ «۳ مخزن پنهان است چون حساب GitHub شما آن‌ها را نمی‌بیند» یعنی میزبان به شما دسترسی نمی‌دهد. در GitHub، اعلان دسترسی به مخزن‌ها به شما می‌گوید وقتی GitHub App روی سازمان مخزن نصب نیست یا مخزن را شامل نمی‌شود.

### کار پس‌زمینهٔ یک مخزن GitLab یا Bitbucket متوقف است

مخزن توکن خودکارسازی‌ای ندارد که بتواند آن را بخواند. یک مدیر فضای کاری یکی برای مخزن یا برای کل فضای کاری اضافه می‌کند؛ [افزودن توکن خودکارسازی](#افزودن-توکن-خودکارسازی) را ببینید. توکن شخصی خودتان آن را دوباره فعال نمی‌کند: کار پس‌زمینه هرگز از توکن یک عضو استفاده نمی‌کند.

### یک مخزن ثبت نمی‌شود

ثبت به هر سه مورد نیاز دارد: مسیر داخل یک worktree گیت باشد، ریموت `origin` داشته باشد و آن ریموت به github.com، gitlab.com یا bitbucket.org اشاره کند. همچنین `origin` باید مخزنی باشد که پیوندش می‌دهید، و پوشه‌ای بیرون از فضای ذخیره‌سازی خود فضای کاری را فقط مالک سرور می‌تواند پیوند دهد. [افزودن مخزن به فضای کاری](/fa-IR/راهنمای-کاربر/راهنماهای-عملی/افزودن-مخزن/) را ببینید.

### مجوز دارم، اما مخزن می‌گوید حساب من نمی‌تواند آن را بخواند

حساب forge خودتان نمی‌تواند آن مخزن را بخواند، پس کدش برای شما بسته می‌ماند هرچه فضای کاری مجوز داده باشد. در بالا، زیر **میزبانی کد**، به forge وارد شوید، یا روی خود forge به آن مخزن دسترسی بگیرید.

### «دسترسی شما به سکوی کد تأیید نشد»

forge برای بررسی دسترسی شما در دسترس نبود، پس Control Center به‌جای حدس زدن رد کرد. لحظه‌ای دیگر دوباره امتحان کنید.

### یک مخزن می‌گوید اکنون به مخزنی دیگر اشاره می‌کند

مخزنِ پشت آن مسیر تغییر کرده است: حذف و دوباره ساخته شده، یا جابه‌جا و جایگزین شده است. Control Center تا وقتی یک مدیر فضای کاری روی **پیوند دوباره** در اعلان یا در ردیف مخزن کلیک نکند، چیزی برایش نمی‌فرستد. یک تغییر نام یا انتقال ساده خودکار دنبال می‌شود و هرگز این را نشان نمی‌دهد.

### پس از استفادهٔ سنگین، همه‌چیز مدتی از کار می‌افتد

این همان قطع‌کنندهٔ مدار محدودیت نرخ است. میزبانی که محدودیت اصلی‌اش را اعلام کند باعث می‌شود کلاینت درخواست‌های بعدی را محلی و بدون تماس شبکه‌ای رد کند تا آن بازه بگذرد — پس طوفان تلاش‌های مجدد نمی‌تواند محدودیت را عمیق‌تر کند. خطاهای گذرا با عقب‌نشینی نمایی دوباره تلاش می‌شوند.
