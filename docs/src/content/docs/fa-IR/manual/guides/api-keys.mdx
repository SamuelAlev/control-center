این راهنما نشان می‌دهد هر اعتبارنامه‌ای که Control Center استفاده می‌کند کجا ذخیره
می‌شود و چگونه آن را تغییر دهید.

**هیچ چیز روی دستگاهی که با آن تایپ می‌کنید ذخیره نمی‌شود.** هر اعتبارنامه روی
سرور زندگی می‌کند؛ این‌که کدام‌یک به درخواستی مشخص پاسخ می‌دهد به این بستگی دارد که
انسانی پشت آن باشد یا نه.

| اعتبارنامه                            | محل ذخیره                                                     | چه کسی از آن استفاده می‌کند                                          |
| ------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| اعتبارنامهٔ میزبان کد / تیکتینگ شما     | فایل رازهای 0600 سرور، کلیدشده با شناسهٔ کاربری شما            | هر چیزی که درخواست کنید: سطح PR، اجراهای عامل شما، ایمیج‌های شما      |
| هویت برنامهٔ سرور                      | همان فایل، به‌علاوهٔ `server_settings` برای چیزهای غیرراز       | کاری که انسانی درخواستش نکرده: وب‌هوک‌ها، نظرسنجی PR، همگام‌سازی تیکت  |
| کلیدهای ارائه‌دهندهٔ مدل و توکن‌های OAuth | مخزن اعتبارنامهٔ خود سرور                                     | آداپتور داخلی، برای هر فضای کاری روی این نصب                           |
| توکن‌های ربات Slack                    | `<dataDir>/<workspaceId>/chat_credentials/` روی سرور           | پل گفتگوی همان فضای کاری                                              |
| اعتبارنامه‌های CLI بیرونی              | هر چیزی که آن CLI استفاده می‌کند                                | Claude Code، روی میزبان سرور                                          |

## دو اعتبارنامهٔ GitHub که به پرسش‌های متفاوتی پاسخ می‌دهند

- **مال شما**، از ورود (جریان دستگاه) یا چسباندن یک توکن. همان چیزی است که هر
  درخواستِ *از طرف شما* با آن انجام می‌شود، پس نظری که به نام شما ثبت شود نام شما
  را همراه دارد. عضو دیگر نمی‌تواند آن را بخواند، و آن‌ها اعتبارنامهٔ خودشان را
  متصل می‌کنند
- **مال سرور**، از GitHub Appی که اپراتور ثبت کرده است. به هر چیزی که فراخوان
  ندارد پاسخ می‌دهد — پس دسترسی به میزبان کد وقتی یک نفر می‌رود یا توکنی را تعویض
  می‌کند از دست نمی‌رود

مال شما در کارت **میزبانی کد** در **تنظیمات → فضای کاری → نمایه و هویت** تنظیم
می‌شود؛ مال سرور در **برنامه‌های ارائه‌دهنده** در **تنظیمات → سرور → ورود
یکپارچه**. [راه‌اندازی یکپارچه‌سازی
GitHub(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/یکپارچهسازی-github/) و [ایجاد GitHub
App(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/github-app/) را ببینید.

:::note[صفحه‌ای هم هست که فقط با URL در دسترس است]
`/workspaces/<workspaceId>/api-keys` همان دو کارتِ نخستین گام راه‌اندازی اولیه را
نشان می‌دهد. **هیچ ورودی‌ای در ناوبری هیچ‌جای رابط کاربری ندارد**؛ فقط با تایپ URL
در دسترس است. به‌جایش از تنظیمات → فضای کاری → نمایه و هویت استفاده کنید.
:::

## تنظیم کلیدهای ارائه‌دهندهٔ مدل

آداپتور داخلی خودش ارائه‌دهنده‌ها را احراز هویت می‌کند و آن اعتبارنامه‌ها روی سرور
زندگی می‌کنند.

1. به **تنظیمات → سرور → ارائه‌دهندگان مدل** بروید
2. تا **ارائه‌دهنده‌ها و مدل‌ها** پایین بروید
3. ارائه‌دهنده را متصل کنید — OAuth مرورگری برای OpenAI، Codex، Cursor و Kimi Code؛
   یک کلید API برای Anthropic و بقیه

برای فهرست کامل و افزودن یک اندپوینت سفارشی، [مدیریت آداپتورها و
مدل‌ها(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/آداپتورها/) را ببینید.

این اعتبارنامه‌ها **سراسری در سطح میزبان** هستند: یک کلید به هر فضای کاری روی این
نصب خدمت می‌کند. توکن‌های OAuth پیش از انقضا تازه‌سازی می‌شوند.

CLIهای آداپتور بیرونی اعتبارنامه‌های خودشان را، در پیکربندی خودشان، روی میزبان سرور
نگه می‌دارند — Control Center آن‌ها را مدیریت نمی‌کند. احراز هویت Claude Code را
همان‌طور که مستندات خودش می‌گوید، روی ماشینی که `cc_server` روی آن اجرا می‌شود انجام
دهید.

دیالوگ **متغیرهای محیطی** هر آداپتور شبیه جایی است برای گذاشتن کلید یکی از آن‌ها،
اما نیست: روی دستگاه شما می‌نویسد، در حالی که سرور نسخهٔ خودش را می‌خواند و هیچ
چیزی این دو را به هم پل نمی‌زند. [مدیریت آداپتورها و
مدل‌ها(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/آداپتورها/) را ببینید.

## اتصال یک ارائه‌دهندهٔ تیکتینگ

کارت **تیکتینگ** در **تنظیمات → فضای کاری → عمومی** هر دو نیمهٔ یک تصمیم را در خود
دارد: این‌که تیکت‌های شما در کدام ارائه‌دهنده زندگی می‌کنند، و اعتبارنامهٔ آن. انتخاب
**محلی** ردیف اعتبارنامه را پنهان می‌کند — تیکت‌های محلی در پایگاه‌دادهٔ خود همین سرور
زندگی می‌کنند و چیزی برای احراز هویت ندارند.

کلید شما روی سرور در برابر شناسهٔ کاربری‌تان ذخیره می‌شود، مثل کلید میزبان کد. سرور
کلید Linear خودش را جداگانه نگه می‌دارد (**برنامه‌های ارائه‌دهنده**)، و همگام‌سازی تیکت
وقتی انسانی درخواست نکرده روی همان اجرا می‌شود. کلیدی که یک عامل دریافت می‌کند تنها
وقتی تزریق می‌شود که عامل قابلیت **اجازهٔ فراخوانی‌های API تیکتینگ** را داشته باشد.
[راه‌اندازی یکپارچه‌سازی
Linear(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/یکپارچهسازی-linear/) را ببینید.

## تعویض یا لغو

- **اعتبارنامهٔ GitHub شما**: **قطع اتصال** را بزنید، سپس دوباره وارد شوید یا توکن
  جدید را بچسبانید. توکن قدیمی را در GitHub لغو کنید
- **برنامهٔ سرور**: یک کلید خصوصی یا راز کلاینت جدید در صفحهٔ GitHub برنامه بسازید،
  آن را در **برنامه‌های ارائه‌دهنده** بچسبانید و **آزمایش** را بزنید
- **یک ارائه‌دهندهٔ مدل**: روی ردیفش، خارج شوید (OAuth) یا کلید را حذف کنید، سپس
  دوباره متصل شوید
- **Slack**: توکن‌ها را در دیالوگ اتصال دوباره بچسبانید. [راه‌اندازی یکپارچه‌سازی
  Slack(/fa-IR/راهنمای-کاربر/راهنماهای-عملی/یکپارچهسازی-slack/) را ببینید

## عیب‌یابی

### فهرست PR خالی است ولی توکن من در `curl` کار می‌کند

زیرعنوان ردیف **میزبانی کد** را بررسی کنید. اگر منبع دیگری را نام می‌برد («از طریق
برنامهٔ این سرور»، «از محیط»)، اعتبارنامه‌ای که آزمایش می‌کنید همانی نیست که پاسخ
می‌دهد — مال شما ذخیره نشده است.

### توکن پذیرفته می‌شود ولی درخواست‌های بعدی شکست می‌خورند

توکن همان‌طور که ذخیره شده بررسی می‌شود، پس ردیف حساب پشت آن را نام می‌برد — اما فقط
حساب را، نه اسکوپ‌ها را. توکنی با اسکوپ‌های بسیار کم متصل می‌شود و سپس در
درخواست‌های تک‌تک شکست می‌خورد. اسکوپ‌ها و انقضا را بررسی کنید:

```bash
curl -H "Authorization: token YOUR_TOKEN" https://api.github.com/user
```
