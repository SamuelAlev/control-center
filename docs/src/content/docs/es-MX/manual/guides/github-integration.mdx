Esta guía cubre las partes específicas de GitHub de la configuración. GitHub es
uno de los tres hosts de código compatibles. Consulta
[Conectar un host de código](/es-MX/manual/guias/conectar-host-de-codigo/) para
conectar GitLab o Bitbucket, y para saber cómo los combina un espacio de trabajo.

## Requisitos previos

- Una cuenta de GitHub con acceso a los repos en los que quieres trabajar
- Un servidor que pueda iniciar la sesión de las personas en GitHub: con su
  propia GitHub App (consulta [Crear la GitHub App](/es-MX/manual/guias/github-app/))
  o con Control Center Connect, según elija el propietario del servidor en
  **Ajustes → Servidor → Inicio de sesión único**

:::note[Las credenciales viven en el servidor, vinculadas a ti]
No se guarda nada en la computadora en la que estás escribiendo. Tu inicio de
sesión de GitHub lo guarda tu `cc_server`, indexado por tu id de usuario, y lo
usa cada dispositivo desde el que inicias sesión — escritorio, web y teléfono.
Otro miembro del mismo servidor no puede usarlo, e iniciar sesión es algo que
cada persona hace por su cuenta.
:::

## Iniciar sesión en GitHub

GitHub solo admite inicio de sesión: no hay ningún token que pegar.

1. Ve a **Ajustes → Tú → Perfil → Alojamiento de
   código** (o al primer paso de la configuración)
2. En la fila **GitHub**, haz clic en **Iniciar sesión en GitHub**
3. Tu navegador abre GitHub. Aprueba la app

Cómo termina el inicio de sesión depende de quién lo ejecute:

- **La app propia del servidor:** GitHub regresa tu navegador al servidor y el
  diálogo lo detecta solo. No hay nada que escribir
- **Control Center Connect:** la página del navegador muestra un código de 8
  caracteres. Escríbelo en el diálogo, o deja que el navegador abra Control
  Center con el enlace `control-center://` y no tendrás que escribirlo

Punto de control: la fila **GitHub** dice «Sesión iniciada como
_tu-nombre-de-usuario_».

El diálogo rechaza un código o un enlace que no haya iniciado él mismo, con
**Inicio de sesión no iniciado aquí**. Si alguien te envía un enlace de inicio
de sesión, no continúes: completarlo conectaría tu cuenta a su servidor.

Haz clic en **Desconectar** para eliminar tu inicio de sesión. Cerrar sesión en
GitHub, o que te quiten de un espacio de trabajo, también descarta todos los
tokens que el servidor emitió en tu nombre.

## Para quién habla tu credencial

Control Center sigue la separación de GitHub entre actuar **como persona** y actuar **como app**:

| Qué pasa | Aparece en GitHub como |
| --- | --- |
| Cualquier cosa que hagas tú: comentar, revisar, aprobar, fusionar, pedir revisores | **Tú**. GitHub marca un comentario de la conversación como hecho con la app de Control Center; una revisión y sus comentarios en línea no llevan esa marca |
| Revisión con IA, respuestas y comentarios del agente en conversaciones de PR, etiquetas, trabajo de pipelines y del bot | **El bot de Control Center**. En la app compartida de Connect, una revisión es del bot solo para una instalación que el operador de Connect haya listado; en otro caso aparece como la persona responsable |
| Una pull request que un agente abre para ti, sus ediciones del título o la descripción de esa pull request, sus push y sus commits | **Tú**. Control Center figura como coautor cuando el crédito de coautoría está activado |
| Trabajo que nadie pidió (programaciones, webhooks) | **El bot de Control Center**, también como autor de sus commits. En Control Center Connect nunca hace push ni abre pull requests |

- **Todo lo que haces** se ejecuta con **tu** inicio de sesión y nada más. Si no has iniciado sesión, la aplicación te pide que lo hagas. Ninguna otra credencial te suplanta
- **El trabajo del bot** recibe un token para un solo repositorio a la vez, limitado a lo que un miembro responsable puede hacer ahí: el miembro que lo pidió o, si no, el propietario del espacio de trabajo. Un miembro que no puede hacer push limita el token a lectura. Las respuestas del bot que actúan en nombre de alguien empiezan con **Control Center (para @login)**
- **Los agentes abren pull requests a través de Control Center**, nunca desde su sandbox, así que la pull request es tuya y las propias reglas de GitHub te impiden aprobarla. Control Center también rechaza una aprobación de la persona que pidió el trabajo al agente y del autor de la pull request. En una ejecución programada o por webhook, eso cubre a cada administrador que activó su disparador o editó su pipeline mientras estaba activo. Debe revisarla otra persona. Si Control Center no puede confirmar quién abrió la pull request, ni qué cuenta de la forja es la tuya, lo rechaza y te pide que lo intentes de nuevo
- **Los agentes comentan también a través de Control Center.** El token de GitHub que recibe una ejecución de agente solo lee. Cuando un agente comenta en la pull request en la que trabaja, Control Center publica el comentario como el bot, empezando por **Control Center (para @login)** cuando alguien pidió la ejecución. Un agente solo puede comentar en su propia pull request: una del mismo repositorio, nunca un fork, cuyo último commit subió el agente o es el commit actual de la rama de su espacio. Las @-menciones en el comentario de un agente no notifican a nadie. Un agente también puede cambiar el título o la descripción de su propia pull request mientras esté abierta. Esa edición se hace igual que se abrió la pull request (en tu nombre, cuando pediste la ejecución), y pide aprobación antes por defecto. La descripción de una pull request conserva sus @-menciones, tanto cuando el agente la abre como cuando la edita, así que las personas a las que nombra sí reciben la notificación
- **En Control Center Connect, el bot nunca hace push ni abre pull requests.** Hacer push, crear una rama o abrir una pull request ahí requiere a una persona que lo haya pedido, y se ejecuta con el inicio de sesión de esa persona. Una ejecución programada o por webhook que intente hacer push se detiene con un mensaje que lo indica. Para que las ejecuciones desatendidas puedan hacer push, dale al espacio de trabajo su propia GitHub App en **Ajustes**
- **Qué puede hacer el bot de Connect.** Con la app compartida de Connect, el bot comenta, etiqueta y reacciona. Publica una revisión (una revisión con IA, comentarios de revisión, solicitudes de revisores) solo cuando el operador de Connect ha listado la instalación de este servidor. Si no, la revisión sale con el inicio de sesión de la persona responsable y aparece con su nombre. El bot nunca abre, edita, cierra ni cambia el título de una pull request, descarta una revisión, ni edita o borra un comentario; eso requiere a una persona que lo pidió, con su propio inicio de sesión. Connect no ata la instalación de tu organización a un único servidor de Control Center: cualquier servidor en el que un miembro que puede hacer push a un repositorio haya iniciado sesión mediante Connect puede obtener el token de comentarios de este bot para ese repositorio
- **Un servidor o un espacio de trabajo con su propia GitHub App** conserva el bot para todo lo anterior, incluidas las revisiones
- **La automatización nunca aprueba** una pull request. Aprobar es un acto de una persona

Al vincular un repo, Control Center comprueba que tu cuenta puede verlo, y avisa cuando la GitHub App no está instalada en su organización o no incluye el repo, con un enlace para corregirlo. Vincular y desvincular requiere a un administrador del espacio de trabajo, y un checkout fuera del almacenamiento propio del espacio de trabajo solo puede vincularlo el propietario del servidor; consulta [Agregar repos a un espacio de trabajo](/es-MX/manual/guias/agregar-repos/).

El vínculo sigue al id permanente del repositorio en GitHub, así que un cambio de nombre o una transferencia no requiere nada de tu parte. Si la ruta nombra después a otro repositorio, Control Center deja de enviarle nada y muestra un aviso hasta que un administrador del espacio de trabajo pulse **Volver a vincular**.

Abrir el código de un repositorio (archivos, diffs, búsqueda, una terminal) requiere tanto su concesión en el espacio de trabajo como un inicio de sesión tuyo en GitHub que pueda leerlo. Los administradores del espacio de trabajo siguen la misma regla; solo el propietario del servidor está exento.

## Qué te aporta la integración

| Función                       | Cómo                                                                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Lista y detalle de PR         | La API REST de GitHub, desde el servidor, con tu propio inicio de sesión                                                         |
| Ejecuciones de comprobación   | La API Checks de GitHub                                                                                                          |
| Publicación de revisiones     | Un paso que depende de la acción del usuario y que publica tu revisión en la PR, en tu nombre                                    |
| Registro de repos             | Se acepta un checkout si su remoto `origin` apunta a github.com, o a gitlab.com / bitbucket.org                                  |
| Acceso de los agentes a GitHub | Dentro de una ejecución, `git fetch` pasa por Control Center, que descarga los repositorios con los que trabaja la ejecución con un token de solo lectura que la ejecución nunca tiene. `gh` los lee con un token de solo lectura que Control Center entrega cuando se le pide y se revoca al terminar la ejecución. Los push, las pull requests, sus ediciones y los comentarios pasan por Control Center |
| Avisos de notificación        | Un sondeo en el servidor de tu bandeja de notificaciones de GitHub genera «Mencionado en pull request» y «Revisión solicitada»   |
| Perfiles de usuario           | Tarjetas de perfil al pasar el cursor y filtrado de PR por autor                                                                 |

Algunas rutas usan la API GraphQL en lugar de REST cuando resulta más barato —
la actividad de ramas del selector al redactar una PR y el estado de revisión en
vivo que decide si una notificación de revisión solicitada sigue pendiente.

## Vigila las caídas de GitHub

La barra de título muestra un indicador de estado cuando un proveedor está
degradado, e incluye GitHub, Claude, OpenAI y Kimi. **Permanece oculto mientras
todo va bien** — su presencia informa de un problema, no de su ausencia.

Haz clic en el indicador para abrir un panel flotante con el estado de cada
proveedor y un botón de actualización. Los estados se actualizan solos cada dos
minutos.

## Cómo actúan los agentes en GitHub

- Un agente que trabaja en un worktree de GitHub recibe un token para ese único
  repositorio. Solo puede leer código, issues y pull requests; los comentarios pasan
  por Control Center, como se describe arriba. Un push
  pasa por Control Center, que pregunta a la
  regla **Enviar a un remoto** y luego lo reenvía con un token de escritura que
  el agente nunca tiene. Consulta
  [Configurar políticas de sandbox](/es-MX/manual/guias/politicas-de-sandbox/)
- El trabajo que tú inicias se confirma como tú. Cuando pides algo a un agente, o haces commit en el IDE, eres el autor y el committer, con una dirección que tu forja verificó: tu dirección noreply de GitHub desde tu inicio de sesión en GitHub, o en GitLab y Bitbucket el correo que tu inicio de sesión ahí informa. Tu identidad de Git del espacio de trabajo solo se usa para un commit que haces a mano en un repositorio donde ninguna forja avala una dirección tuya. Si no has iniciado sesión en esa forja, los commits del agente son del bot en su lugar, y las notas de la ejecución lo dicen
- El trabajo que nadie pidió se confirma como el bot. Una ejecución programada o por webhook confirma como la GitHub App del espacio de trabajo (`<app>[bot]`, con su dirección noreply de GitHub), o como `Control Center <hi@usectrl.dev>` cuando no hay GitHub App o el repositorio está en GitLab o Bitbucket
- **Acreditar a Control Center como coautor** (**Ajustes** → **Tú** → **Commits**) añade un trailer `Co-Authored-By:` por la otra parte: Control Center en tus commits, y en los commits del bot cada persona que activó el disparador detrás de la ejecución. Está activado salvo que lo desactives. Un administrador del espacio de trabajo puede decidirlo para todos con **Crédito de coautoría** en **Ajustes** → **Espacio de trabajo** → **General**; tu propia elección se guarda entonces pero no se aplica en ese espacio de trabajo. La atribución propia de Claude Code siempre está desactivada
- Tus commits pueden firmarse. En **Commits verificados** en **Ajustes** → **Tú** → **Commits**, elige **Crear clave de firma** y añade su mitad pública a tu cuenta de GitHub o GitLab como clave de firma; a partir de entonces los commits de las ejecuciones que pides, y los commits que haces en el IDE, aparecen como verificados. La mitad privada se queda en tu servidor, así que quien controle ese servidor puede firmar commits como tú mientras la clave esté en tu cuenta, y en GitHub un commit que ya aparece como verificado sigue verificado después de que quites la clave. Bitbucket no tiene claves solo de firma: no añadas la clave ahí, y los commits en Bitbucket no se firman. Los commits del bot nunca se firman
- Los commits que haces en el panel **Control de código** del IDE se saltan los hooks de Git del repositorio, como lo hace `git commit --no-verify`, y el Git del servidor ignora los helpers de credenciales, editores, herramientas de diff externas y firmantes que configure el repositorio: ejecuta Git en su propia máquina, en un árbol que un agente o una pull request pueden cambiar. Consulta [Hacer commit y push desde Control de código](/es-MX/manual/guias/revisar-y-fusionar-pr/#hacer-commit-y-push-desde-control-de-código-fuente)
- Cada commit que un agente sube se comprueba antes, incluidas las capas que `stack_publish` sube para un stack. Un push que nombra a otra persona, elimina o toma prestado un crédito, añade una línea de firma, o no está firmado como dicen tus ajustes, se rechaza. Los commits que tú subes desde el IDE son tuyos y no se comprueban de esta manera
- Una terminal que abres en un rig recibe tu propio inicio de sesión,
  restringido a ese único repositorio, así que los push que hagas ahí son tuyos
- Cuando no se puede emitir ningún token (ninguna persona responsable inició
  sesión, la app no está instalada en el propietario o la instalación está
  suspendida), el comando que lo pidió explica por qué. No hay
  ninguna credencial alternativa

## Solución de problemas

### La lista de PR está vacía y dice que GitHub no está conectado

No iniciaste sesión en GitHub en este servidor. Haz clic en
**Iniciar sesión en GitHub** en **Ajustes → Tú → Perfil → Alojamiento de código**. Los repos de otros
hosts de código no se ven afectados.

### La fila de GitHub dice que el inicio de sesión no está configurado en este servidor

El servidor no tiene ni su propia GitHub App ni Connect. El propietario del
servidor elige una opción en **Ajustes → Servidor → Inicio de sesión único**:
**Crear mi app de GitHub** toma unos dos minutos. Consulta
[Crear la GitHub App](/es-MX/manual/guias/github-app/).

En un espacio de trabajo con sus propias apps, la fila lo indica cuando la GitHub App del espacio de trabajo falta o está incompleta. Un administrador del espacio de trabajo la completa en la tarjeta **App de GitHub**, en **Ajustes → Espacio de trabajo → Integraciones**; consulta [Dar a un espacio de trabajo su propia app](/es-MX/manual/guias/github-app/#dar-a-un-espacio-de-trabajo-su-propia-app).

### El diálogo dice que el código no coincide

Escribe el código exactamente como lo muestra el navegador: 8 letras y dígitos.
Cinco códigos incorrectos terminan el inicio de sesión; vuelve a empezar.

### El inicio de sesión dice que la app no está instalada

La GitHub App no tiene ninguna instalación en la cuenta propietaria del
repositorio. Un administrador del espacio de trabajo la instala desde
**Ajustes → Espacio de trabajo → Integraciones → Instalaciones de la app de GitHub**.

### Todo el mundo tiene que volver a iniciar sesión en GitHub

El propietario del servidor rotó la clave de Connect del servidor, cambió de
servidor Connect o el directorio de datos se restauró en otra máquina. Los
inicios de sesión a través de Connect están ligados al servidor que los hizo.

### Se rechaza al agregar un repo

El registro necesita las tres cosas: que la ruta esté dentro de un árbol de
trabajo de git, que tenga un remoto `origin` y que ese remoto apunte a un host de
código compatible (github.com, gitlab.com o bitbucket.org). El `origin` debe ser el repositorio que vinculas, y una carpeta fuera del almacenamiento propio del espacio de trabajo solo puede vincularla el propietario del servidor. Consulta
[Agregar repos a un espacio de trabajo](/es-MX/manual/guias/agregar-repos/).

### Tengo una concesión pero el repositorio dice que mi cuenta no puede leerlo

Tu cuenta de GitHub no puede leer ese repositorio, así que su código sigue cerrado para ti aunque tengas una concesión del espacio de trabajo. Inicia sesión en GitHub en **Alojamiento de código**, o pide acceso al repositorio en GitHub.

### No se pudo confirmar tu acceso a GitHub

No se pudo contactar a GitHub para comprobar tu acceso, así que Control Center se negó en lugar de suponer. Inténtalo de nuevo en un momento.

### Las revisiones de Connect aparecen con mi nombre, no con el del bot

En la app compartida de Connect, el bot publica revisiones solo para las instalaciones que el operador de Connect ha listado. En cualquier otro caso, la revisión sale con el inicio de sesión de la persona responsable. Para que el bot publique revisiones, dale al espacio de trabajo su propia GitHub App.

### Todo deja de funcionar un rato tras un uso intenso

Ese es el cortacircuitos del límite de velocidad. GitHub señala su límite
principal con un `403` que lleva `x-ratelimit-remaining: 0` y la hora de
restablecimiento; al ver uno, el cliente hace que las peticiones posteriores
fallen localmente, sin ninguna llamada de red, hasta que transcurra la ventana,
así que una tormenta de reintentos no puede agravar el límite. Los fallos
transitorios se reintentan hasta tres veces con retroceso exponencial,
respetando `retry-after`.
