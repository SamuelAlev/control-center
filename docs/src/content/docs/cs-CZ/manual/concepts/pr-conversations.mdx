Pull request už je místo, kde se o kódu mluví. Konverzace v PR z něj udělají
plochu pracovního prostoru Control Center, stejně jako
[chatový most](/cs-CZ/prirucka/koncepty/chatove-mosty/) udělá plochu ze Slacku:
zmíníš na PR `@usectrl` (nebo bota GitHub App pracovního prostoru), odpovíš
v jeho vláknech revize, nebo přidáš štítek `ai-review`, a práce proběhne
v prostoru kontroly toho PR — se stejným připsáním a stejnými guardraily jako
cokoli napsané v aplikaci. Komentář i štítek se hlídají stejně: podle člena,
který je napsal nebo přidal. Odpovědi se vracejí na GitHub, do té stopy, ve
které se ptalo.

Funkci tvarují tři rozhodnutí a každé je totéž rozhodnutí, které chatový most
udělal pro chat, jen přeřčené pro hostitele kódu: **kterým směrem spojení
běží**, **co autorizuje komentář, který přijde zvenku**, a **komu se připisuje
každá strana**.

## Transportem je obchůzka

Jediný push kanál, který GitHub aplikaci dává, je webhook a webhook potřebuje
příchozí URL — to jediné, co tahle plocha záměrně nikdy nevyžaduje. Objevování
je proto obchůzka: jedno hledání s aliasy na každou instalaci aplikace se
zeptá GitHubu na PR, které zmiňují bota (nebo jeho krátký slug), a na otevřené
PR se štítkem kontroly. PR, které už mají prostor kontroly, si nechají přečíst
vlákna komentářů a všechno se porovná podle id komentáře s tím, co viděla
minulá obchůzka. Vlastní aplikace obchází každou minutu nejvýš 25 PR. Přes
Connect jdou volání z vlastní kvóty GitHubu členů, takže obchůzka běží každé
dvě minuty nejvýš přes 10 PR a pracovní prostor pod 15 % kvóty se přeskakuje,
dokud se nezotaví. Samotný Connect obsah PR nikdy nevidí.

Důsledky návrhu stojí za pojmenování:

- **Latence je interval obchůzky, ne událost.** Potvrzení 👀 přijde do jedné
  obchůzky. Nic naléhavého na tom nestojí.
- **Přesně jednou, na každý komentář.** Id komentářů jsou na GitHubu
  jedinečná; každé se zapíše v okamžiku, kdy se klasifikuje jako způsobilé,
  dřív než s ním cokoli začne jednat. Pád může zpracování komentáře ztratit,
  dvakrát ho nespustí.
- **Výpadek se dožene, nepřehrává.** Množina viděného se ukládá, takže restart
  doručí to, co přišlo, když byl server dole. Jediná výjimka je úplně první
  obchůzka: bez paměti, proti které by se porovnávalo, se všechno, co ještě
  visí, zapíše potichu — operátor, který dvaceti PR přidal štítek dřív, než
  tenhle server existoval, se nesmí vrátit k dvaceti rozjetým kontrolám.
- **Štítek je množina, ne událost.** Hledání hlásí _přítomnost_ štítku, takže
  označený PR spustí akci jednou a pak už nikdy. Štítek odebraný a znovu
  přidaný obchůzka nevidí; cestou k opětovnému spuštění je zmínka.

Hledání běží jednou na každý účet instalace, na vlastním klientovi toho
vlastníka, protože token vidí jen repozitáře své instalace — jeden
přihlašovací údaj pro celý server by potichu minul každý PR pod ostatními
instalacemi aplikace.

## Autorizuje členství, ne komentář

Komentář u PR přijde s autorem — neověřenou vnější identitou, dokud se
neprokáže. Server vyřeší neměnné číselné id účtu GitHub autora (nikdy login,
který jde přejmenovat a znovu použít) proti přihlášením ke GitHubu u členů
pracovního prostoru, která se přebudují podle TTL, protože se lidé přihlašují
a dostávají pozvánky, zatímco server běží. U štítku `ai-review` se vyřeší ten,
kdo ho přidal naposledy.

Tři kontroly v daném pořadí a neúspěch kterékoli z nich je tichý — nic se
nezveřejní:

- **Přihlášený člen.** Účet musí patřit členovi _tohoto_ pracovního prostoru,
  který se na tomto serveru přihlásil ke GitHubu
- **Role se zápisem.** `viewer` a `guest` práci spustit nemůžou
- **Právo pushovat.** Odpovědi používají token `bot` omezený na přístup toho
  člena k repozitáři. Když ho server vydat nedokáže, nepokračuje

Všechny kontroly proběhnou před jakýmkoli potvrzením, takže cizí člověk
nedostane reakci ani odpověď. Komentář se nikdy nepřipíše někomu, kdo ho
neposlal, a slova cizího člověka nikdy nevstoupí do pracovního prostoru, do
kterého nevidí.

### Nárok

Posledním krokem před jakoukoli prací je reakce 👀, přidaná vlastním
přihlášením autora ke GitHubu. GitHub odpoví `201` na novou reakci a `200` na
reakci, která už existuje, takže reakce slouží zároveň jako zámek: když je
stejný člověk přihlášený na dvou serverech, které oba propojují repozitář,
práci udělá jen ten, který zareaguje první. Komentář, který vidí několik
pracovních prostorů na jednom serveru, se nabídne každému a rozhodne tentýž
nárok.

## Dvě identity, schválně

Každá strana konverzace nese jinou identitu a ten rozdíl je ta funkce:

- **Na GitHubu je odpověď automatizace tvým jménem.** Každá odpověď jede na
  tokenu `bot` pro ten jeden repozitář, omezeném na přístup člena, který se
  ptá. U vlastní aplikace je autorem účet `[bot]` aplikace. Přes Connect je
  token sdílené App uživatelský token, takže odpověď napíše účet člena, který
  se ptá, a jedná přes App. V obou případech každá odpověď začíná
  `**Control Center** (for @login):`, což říká, kdo se ptal, a zároveň slouží
  jako pojistka proti smyčce.
- **V prostoru je otázka tvoje.** Zpráva se připíše členovi, na kterého se
  autor vyřešil, a běh agenta se vykoná jeho jménem: commity ho zapíšou jako
  spoluautora a volič autonomie prostoru i guardraily akcí platí přesně tak
  jako u zprávy napsané v aplikaci. Zápisy na hostitele kódu z běhu používají
  tokeny pro jediný repozitář ohraničené tímto členem, nikdy celé předané
  přihlášení člena.

Zveřejnit zjištění kontroly zpět na GitHub zůstává rozhodnutím člověka a padá
v Control Center. Zmínka může kontrolu _spustit_; zveřejní ji jen člověk.

## Pojistka proti smyčce a krátké jméno

Všechno, co napsal účet bota, se zahodí dřív, než se spustí jakákoli brána —
náš konkrétně a každá přípona `[bot]`, aby kontrolní bot jiné aplikace
neprobudil ani toho našeho — a stejně tak každý komentář, který začíná
předponou `**Control Center** (for @`, protože odpověď přes Connect píše účet
člověka. Bez toho by odpovědi přicházely jako nové komentáře a spouštěly most
donekonečna.

Přípona `[bot]` je taky důvod, proč existuje krátký tvar. GitHub login účtu
aplikace natvrdo nastaví na `<slug>[bot]`, nenabízí na něj doplňování a
`@slug` na aplikaci nikdy nevyřeší — přijmout holý slug je tedy rozhodnutí
_našeho_ porovnávače a najít ho chce vyhledávací stopu nad surovým **textem**
komentáře, ne index zmínek GitHubu. Cena se pojmenuje, nezamlčí: člověk,
který má stejný slug jako aplikace, osloví bota každou zmínkou sebe sama
v krátkém tvaru. U výrazných jmen aplikace ta kolize zůstane hypotetická.

## Co záměrně nenabízíme

- **Žádné automatické zveřejnění.** Zjištění skončí v prostoru kontroly;
  zveřejnění na GitHub je samostatná lidská akce
- **Žádná přibližná identita.** Autor se vyřeší na právě jednoho člena, nebo
  se ignoruje — žádné připsání podle nejlepšího odhadu
- **Žádné automatické schválení.** Automatizace umí komentovat a vyžádat
  změny, ale revize `APPROVE` se odmítne dřív, než se odešle. Schválení je čin
  člověka
- **Žádný webhook GitHub App.** Tahle plocha ho nikdy neregistruje, takže
  pro komentáře u PR není příchozí URL, kterou by šlo vystavit. Ostatní
  webhooky produktu (pipelines, synchronizace ticketů) jsou samostatné
  volitelné nastavení.
