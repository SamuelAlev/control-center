## Sběrnice událostí

`DomainEventBus` je broadcastová sběrnice publish/subscribe uvnitř procesu. Publikující volají `publish(event)`, odběratelé konzumují typovaný proud `on<T>()`. Každá událost implementuje `DomainEvent` a nese `occurredAt`.

**Sběrnice běží uvnitř `cc_server`.** Každý publikující i každý živý odběratel žije tam. Žádný klient tuhle sběrnici nevidí. Server předává vybranou podmnožinu jako JSON-RPC rámce `notifications/*`, filtrované pro každého odběratele podle členství v pracovním prostoru.

| Míra                                                        | Počet                                       |
| ----------------------------------------------------------- | ------------------------------------------- |
| Konkrétní třídy událostí                                    | 54                                          |
| Zdrojové soubory (`packages/cc_domain/lib/core/domain/events/`) | 14 (plus `domain_event_bus.dart`)       |
| Abstraktní báze, které se nikdy nepublikují přímo           | 1 (`TaskLifecycleEvent`, sealed hierarchie) |

Každá událost v katalogu níže žije v tom jednom adresáři. Jinde se doménové události nedeklarují.

## Události PR a kontroly

První blok je vlastní životní cyklus PR. Druhý je **sledování vlastních PR**: signály o PR, který *jsi* otevřel. Každý nese `forUserId`, aby je dotazování směrovalo k člověku, kterého se týkají, místo aby je rozesílalo všem.

| Událost                    | Payload                                                                  | Kdy se spustí                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `PullRequestPublished`     | `prId`, `workspaceId`, `repoOwner`, `repoName`                           | Agent otevře PR                                                                                                                        |
| `PullRequestStatusChanged` | `status`, `workspaceId`, `prId?`, `repoFullName?`, `prNumber?`           | PR se sloučí, zavře, otevře, znovu otevře nebo schválí                                                                                 |
| `PrMerged`                 | `prId`, `workspaceId`, `agentId`                                         | PR se sloučí. Úzký signál jen pro sloučení, ponechaný pro analytiku a oznámení                                                         |

| `PrMentioned`              | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`            | Uživatel serveru je zmíněn na PR (dotazování na oznámení, `mention`)                                                                   |

| `PrHeadChanged`            | `repoOwner`, `repoName`, `prNumber`, `prTitle`, `previousHeadSha`, `headSha`, `workspaceId` | Head SHA pull requestu se posunul. Autor pushnul                                                    |

## Události životního cyklu úkolu

Jednotný proud životního cyklu úkolu: jeden odeslaný běh agenta, klíčovaný id svého run logu. Každá událost nese `taskId`, monotónní `seq` v rámci úkolu, `workspaceId?`, `agentId?` a `phase`. Řádky níže uvádějí jen další pole.

| Událost                     | Payload                       | Kdy se spustí                                                                                       |
| --------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------- |
| `TaskDispatched`            | —                             | Úkol se předá backendu k provedení                                                                  |
| `TaskRunning`               | —                             | Úkol začne produkovat výstup                                                                        |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | Úkol je odstavený. Jiný úkol drží zámek cesty na disku, který potřebuje                             |
| `TaskProgress`              | `note?`                       | Kontrolní bod průběhu uprostřed běhu                                                                |
| `TaskMessage`               | `messageType`, `content`      | Streamovaná zpráva (text/thinking/tool_use/tool_result/error); hlásí se ve fázi `progress`          |
| `TaskCompleted`             | `summary?`                    | Úkol úspěšně skončí                                                                                 |
| `TaskFailed`                | `errorMessage`                | Úkol skončí chybou                                                                                  |
| `TaskCancelled`             | —                             | Úkol se zruší před dokončením                                                                       |

Enum `TaskPhase` má i člen `queued`, ale nic nepublikuje událost ve frontě. Třída `TaskQueued` neexistuje. První pozorovatelný rámec úkolu je `TaskDispatched`.

## Subdomény zcela bez událostí

Několik subsystémů vypadá zvenku jako řízených událostmi. Nejsou. Jsou tu proto, že jejich absence je rozhodnutí návrhu, které stojí za to znát, než půjdeš hledat hook:

| Subdoména           | Jak se stav hýbe místo toho                                                                                 |
| ------------------- | ----------------------------------------------------------------------------------------------------------- |
| Paměť               | `record_memory_fact` a spol. zapíšou a vrátí se. Vyvolání jen čte. Na fakt ani na konflikt se nic nepublikuje |
| Orchestrace         | Návrh, jeho schválení a vygenerovaný běh pipeline jsou řádky a volání RPC                                  |
| Dokumenty plánu     | `submit_plan` zapíše revizi. Schválení zhmotní orchestraci. Ani jedno se neoznamuje                        |
| Artefakty           | `publish_artifact` / `revise_artifact` zapisují revize přímo                                                |
| Schválení           | Eskalaci řeší služba workflow schválení                                                                     |
| Synchronizace ticketů | Koordinátor dodavatele se přihlásí k událostem ticketu výše. Příchozí webhooky se aplikují přímo         |
| Obnovení kalendáře  | Synchronizace události upsertuje a klient si je znovu přečte. Broadcast obnovení neexistuje                |
| Sloučení worktree   | Zapisuje se do `worktree_merge_log` a čte se odtud                                                         |

`TicketAssigned` je signál auditu i oznámení a zároveň spouštěč pipeline. Přiřazení agentovi zapíše vlastnictví a nespustí běh. Dispečer ticketů neexistuje. Výjimka je přiřazení týmu (nastavené `assignedTeamId`): `TeamRoutingService` odešle vedoucího týmu.

`TicketRemoteSyncHandler` je deklarovaný, ale v produkčním kódu se nikdy nekonstruuje, takže dnes neodebírá nic. Klientský `NotificationEventMapper` se konstruuje jen ve vlastním testu. Je to zbytek cesty uvnitř procesu z doby před rozdělením klienta a serveru. Živé toasty přicházejí z rámců na drátě níže.

## Mapování oznámení

Na serveru z těchto událostí `NotificationFeedRecorder` a `RemoteEventForwarder` udělají rámce na drátě `notifications/*` (`notification_wire.dart`). Na klientovi z rámce `RpcNotificationMapper` → `mapNotificationFrame` udělá `AppNotification`.

Kategorií oznámení je přesně **sedmnáct**. Několik událostí se mapuje na víc než jednu metodu na drátě, protože rámec nese hranu (selhání, nebo zotavení) a kategorie nese otázku („co dělá CI?“).

| Kategorie              | Zdrojová událost          | Metoda na drátě                                                            |
| ---------------------- | ------------------------- | -------------------------------------------------------------------------- |
| `newMessage`           | `MessageReceived`         | `notifications/message_received` (zmiňuje tě)                              |
| `agentRunCompleted`    | `MessageReceived`         | `notifications/message_received` (`is_agent_message`, bez tvé zmínky)      |
| `agentAwaitingInput`   | `AgentAwaitingInput`      | `notifications/agent_awaiting_input`                                       |
| `ticketAssigned`       | `TicketAssigned`          | `notifications/ticket_assigned`                                            |
| `ticketStatusChanged`  | `TicketStatusChanged`     | `notifications/ticket_status_changed`                                      |
| `pullRequestPublished` | `PullRequestPublished`    | `notifications/pr_published`                                               |
| `prMerged`             | `PrMerged`                | `notifications/pr_merged`                                                  |
| `prMerged`             | `ExternalPrMerged`        | `notifications/external_pr_merged`                                         |
| `prMentioned`          | `PrMentioned`             | `notifications/pr_mentioned`                                               |
| `prMentioned`          | `PrCommentMentioned`      | `notifications/pr_comment_mentioned`                                       |
| `reviewRequested`      | `PrReviewRequested`       | `notifications/pr_review_requested`                                        |
| `reviewStale`          | `ReviewBecameStale`       | `notifications/review_stale`                                               |
| `prMergeReadiness`     | `PrMergeReadinessChanged` | `notifications/pr_ready_to_merge` / `pr_merge_blocked`                     |
| `prReviewDecision`     | `PrReviewDecisionChanged` | `notifications/pr_approved` / `pr_changes_requested` / `pr_review_dismissed` |
| `prChecksStatus`       | `PrChecksStatusChanged`   | `notifications/pr_checks_failed` / `pr_checks_recovered`                   |
| `prThreadActivity`     | `PrThreadReplied`         | `notifications/pr_thread_replied`                                          |
| `prThreadActivity`     | `PrThreadResolved`        | `notifications/pr_thread_resolved`                                         |
| `meetingStartsSoon`    | `MeetingStartingSoon`     | `notifications/meeting_starting_soon`                                      |
| `calendarAuthExpired`  | `CalendarAuthExpired`     | `notifications/calendar_auth_expired`                                      |
| `rigStatusChanged`     | `RigControlChanged`       | `notifications/rig_control_changed`                                        |
| `rigStatusChanged`     | `RigReaped`               | `notifications/rig_reaped`                                                 |
| `rigStatusChanged`     | `RigClosedEvent`          | `notifications/rig_closed`                                                 |

Rámec převzetí stanice se nevrací tomu, kdo řízení převzal. Uvolnění se nefiltruje (událost nezaznamenává, kdo pustil) a jen zavření `backendFailure` vyrobí rámec `rig_closed`. Ostatní důvody jsou buď vyžádané, nebo je už pokrývá rámec reap.

`AgentAwaitingInput` publikuje `AgentAwaitingInputPublisher`. Sleduje nové záznamy v registrech schválení a blokací přihlašovacích údajů a o každé otázce `ask_user` mu dá vědět `AgentQuestionService`. Jedno čekání je jedna událost. Když čekání skončí, nepublikuje se nic.

Pět kategorií vlastních PR nese `forUserId`, takže dorazí k autorovi, ne ke všem v pracovním prostoru.

`RemoteEventForwarder` navíc přeposílá `TicketReassigned` jako `notifications/ticket_reassigned` a každou `TaskLifecycleEvent` jako `notifications/task_<phase>`. Ani jedno se nemapuje na kategorii oznámení. Pohánějí živé rozhraní, ne centrum oznámení. Události členství se jako rámce nepřeposílají: zneplatní cache přeposílače a hostitelé relací zahodí odběry pracovního prostoru odebraného člena.
