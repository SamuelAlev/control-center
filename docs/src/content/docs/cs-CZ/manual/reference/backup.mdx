Všechno, co Control Center umí zkopírovat, předat nebo převzít, a přesný tvar každého
artefaktu. Jak zálohu skutečně pořídit, je v
[Záloha a obnovení](/cs-CZ/prirucka/navody/zaloha-a-obnoveni/). Proč je ukládání
rozdělené takhle, je v [Pracovní prostory a izolace](/cs-CZ/prirucka/koncepty/pracovni-prostory/).

## Artefakty

Existují tři artefakty ve formě kopie databáze, s různým rozsahem a různou politikou mazání.

| Artefakt                         | Zapisuje                      | Tvar                                          | Pokrývá                              |
| -------------------------------- | ----------------------------- | --------------------------------------------- | ------------------------------------ |
| **Snímek instalace**             | `server.backupNow`            | **adresář** s časovým razítkem                | všechny databáze na instalaci        |
| **Záloha pracovního prostoru**   | pipeline `Workspace backup`   | adresář s časovým razítkem a jedním `.db`     | databáze jednoho pracovního prostoru |
| **Export pracovního prostoru**   | `workspace.export`            | jeden `.db` **soubor**                        | databáze jednoho pracovního prostoru |

Všechny se zapisují přes SQLite `VACUUM INTO`, což je bezpečné vůči živé databázi ve WAL:
vezme čtecí transakci, vytvoří defragmentovanou a transakčně konzistentní
kopii a server kvůli tomu není třeba zastavovat.

Tyto soubory ani stažené kopie nejsou v Control Center **v klidu šifrované**.
Přenos šifrovaný od konce ke konci chrání bajty na cestě mezi spárovaným
klientem a jeho `cc_server`, na přímých spojeních i přes zprostředkované relé.
Místní úložiště a kopie mimo stroj chraň zvlášť; databázové soubory umí přečíst
server i každý autorizovaný příjemce.

## Rozložení snímku

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

Rozložení přesně zrcadlí živý datový adresář, a proto je obnova
instalace zkopírování zpátky, ne převod. Jméno adresáře je časové razítko UTC,
v němž jsou `:` a `.` nahrazené za `-`, takže je na Windows bezpečné pro souborový systém
a jako obyčejný řetězec se řadí chronologicky.

Naplánované zálohy pracovního prostoru leží zvlášť v
`<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`.
Každá má `manifest.json` jen pro ten jeden soubor a žádný `global.db`; nejsou to snímky instalace. Obnovení uchová databázi, kterou nahradí, na stejném místě jako `<timestamp>-pre-restore`.
Krok uchování v týdenní pipeline maže jen zálohy svého pracovního prostoru starší než nastavený věk (výchozí je 30 dní). Ten krok nikdy nerotuje ručně pořízené snímky instalace. `server.listBackups` vypisuje jen snímky instalace, včetně neověřených; `workspace.listBackups` vypisuje plánované zálohy jednoho pracovního prostoru.

Smazání pracovního prostoru tenhle adresář nechá na místě. Plán pracovního prostoru s ním
skončí, takže ty zálohy už nic nerotuje a zůstanou, dokud je vlastník instalace neodstraní.
`server.listOrphanedBackups` je nahlásí.


### `manifest.json`

| Pole                         | Typ             | Význam                                                                    |
| ---------------------------- | --------------- | ------------------------------------------------------------------------- |
| `format`                     | celé číslo      | Formát manifestu. Teď `2`                                                                 |
| `created_at`                 | ISO-8601 UTC    | Kdy se snímek pořídil                                                     |
| `global`                     | objekt          | Záznam `global.db`. U plánované zálohy pracovního prostoru chybí |
| `workspaces[]`               | pole            | Jeden záznam na zachycený pracovní prostor                               |
| `workspaces[].workspace_id`  | řetězec         | Pracovní prostor, který tenhle soubor drží                                |
| `skipped_workspaces[]`     | pole            | Pracovní prostory, které záloha **nezachytila**                         |
| `skipped_workspaces[].workspace_id` | řetězec | Pracovní prostor, který byl vynechán                                     |
| `skipped_workspaces[].reason` | řetězec       | `no_file`, `damaged` nebo `failed`                                    |

`global` a každý záznam v `workspaces[]` zaznamenávají jeden zkopírovaný soubor, změřený na kopii poté, co byla zapsána:

| Pole             | Typ    | Význam                                                                         |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`          | řetězec         | Cesta relativní ke kořeni snímku: `global.db` nebo `<workspaceId>/workspace.db`            |
| `bytes`         | celé číslo      | Velikost kopie                                                     |
| `sha256`         | řetězec    | SHA-256 kopie v malých hexadecimálních znacích                                 |
| `quick_check`    | řetězec    | Co SQLite `quick_check` řekl o kopii: `ok`, nebo jeho nález                    |
| `user_version`   | celé číslo | Verze schématu kopie                                                           |
| `application_id` | celé číslo | SQLite `application_id` kopie                                                  |

Pracovní prostor se přeskočí, když je zaregistrovaný, ale ještě se do něj nezapsalo (`no_file`), když jeho databáze neprojde kontrolou integrity (`damaged`; poškozená kopie se nikdy nepořizuje), nebo když jeho kopie nebo kontrola té kopie selhala (`failed`). V každém případě se snímek stejně dokončí a manifest pojmenuje, co chybí. Manifest se zapíše jako poslední.

### Úplnost

`server.listBackups` hlásí u každého snímku příznak `complete`. Je nepravdivý, když manifest chybí, nejde rozebrat nebo je v jiném formátu, když soubor, který jmenuje, chybí nebo má jinou velikost, nebo když kopie neprošla svou kontrolou. Aplikace takový snímek zobrazí jako **Neověřeno**. Snímky pořízené před formátem `2` jsou v tomhle stavu.

Neověřený snímek se pořád vypíše, protože snímek, který operátor nevidí, je
snímek, o kterém věří, že ho má. Když manifest nejde přečíst, výpis se vrátí
k samotnému rozložení a nahlásí ty soubory `<workspaceId>/workspace.db`, které najde.
Ty se pořád dají převzít jednotlivě přes `workspace.import`, i když snímek
jako celek instalaci neobnoví.

Vypsaný snímek nebo plánovaná záloha nese `pinned_reason: "last_good_copy"`, dokud drží nejnovější ověřenou kopii pracovního prostoru, jehož živá databáze je poškozená. Krok uchování ji přeskočí, dokud se ten pracovní prostor neobnoví.

## Co záloha neobsahuje

Oba artefakty jsou **jen databáze**. Adresář pracovního prostoru drží víc než svou
databázi a nic z toho zbytku se nepřenáší:

| Cesta                               | Ve snímku? | V exportu pracovního prostoru? |
| ----------------------------------- | ---------- | ------------------------------ |
| `global.db`                         | Ano        | Ne                             |
| `<workspaceId>/workspace.db`        | Ano        | Ano (ten soubor *to je*)       |
| `<workspaceId>/code_index.db`       | Ne             | Ne                     |
| `<workspaceId>/blobs/`              | Ne         | Ne                             |
| `<workspaceId>/skills/`             | Ne         | Ne                             |
| `<workspaceId>/agents/`             | Ne         | Ne                             |
| `<workspaceId>/chat_credentials/`   | Ne         | Ne                             |
| `<workspaceId>/spaces/<spaceId>/`   | Ne         | Ne                             |
| `<workspaceId>/pr_clones/`          | Ne         | Ne                             |
| `secrets.json`                      | Ne         | Ne                             |
| `models/`                           | Ne         | Ne                             |
| `meetings/<meetingId>/`             | Ne         | Ne                             |
| `rigs/`                             | Ne         | Ne                             |
| `_agent_hooks/`                     | Ne         | Ne                             |

Část z toho se dá zahodit. `spaces/` drží copy-on-write worktree a ty se znovu připraví z repozitářů, `pr_clones/` je mezipaměť, `code_index.db` se znovu sestaví, `models/` se stáhne znovu a `rigs/` je stav stroje. Část ne: `blobs/` drží vložené obrázky, na které ukazují řádky v databázi, `skills/` a `agents/` drží soubory, se kterými agent běží, a `secrets.json` drží každý klíč párování, přihlašovací údaje poskytovatele a nastavení SSO na instalaci. Zbytek pokrývá [Záloha a obnovení](/cs-CZ/prirucka/navody/zaloha-a-obnoveni/#kopíruj-zálohy-mimo-stroj).
:::note[Tajemství zůstávají mimo databáze]
`workspace.db` je celý pracovní prostor: konverzace, záznamy běhů, propojení repozitářů, definice prostředí a členové. Tokeny webhooků pipeline a tajemství webhooků synchronizace ticketů jsou v `secrets.json`: databáze drží odkaz na každé z nich a index tras drží klíčovaný hash každého tokenu. Pracovní prostor obnovený na jiné instalaci proto nedostane žádné webhooky, dokud se jeho spouštěče tam znovu neuloží. Přihlášení poskytovatelů, klíče zařízení a uživatelská tajemství jsou v `global.db` a `secrets.json`.
:::

:::note[Tokeny chatu schválně zůstávají stranou]
`chat_credentials/` leží vedle databáze, ne v ní, a proto pracovní prostor
předaný někomu jinému nenese živé tokeny bota. Viz
[Chatový most](/cs-CZ/prirucka/referencni-prirucka/chatovy-most/).
:::

## Operace

RPC zálohy instalace a export a import pracovního prostoru jsou jen pro `fullClient`:
spárovaný telefon je nespustí. Na serveru bez připojeného portu záloh, jako je
demo server, chybí úplně. Neodmítají se, ve struktuře nejsou.

| Operace               | Druh   | Rozsah      | Minimální role        | Argumenty     | Vrací                              |
| --------------------- | ------ | ----------- | --------------------- | ------------- | ---------------------------------- |
| `server.backupNow`    | zápis  | Instalace   | **vlastník** instalace | žádné        | `{ok, path}`                       |
| `server.listBackups`  | čtení  | Instalace   | **vlastník** instalace | žádné        | `{backups: [...]}`                 |
| `server.deleteBackup` | zápis  | Instalace   | **vlastník** instalace | `name`       | `{ok}`                             |
| `server.listOrphanedBackups` | čtení | Instalace | **vlastník** instalace | žádné | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | zápis | Instalace | **vlastník** instalace | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | čtení | Pracovní prostor | `admin` | žádné | `{backups: [...]}` |
| `workspace.deleteBackup` | zápis | Pracovní prostor | `owner` | `name` | `{ok}` |
| `workspace.export`    | čtení  | Pracovní prostor | `admin`          | žádné         | `{ok, path}`                       |
| `workspace.import`    | zápis  | Pracovní prostor | `owner` a vlastník serveru | `source_path` | `{ok, workspace_id}`               |
| `workspace.importHolds.list` | čtení | Pracovní prostor | `owner` a vlastník serveru | žádné | `{holds: [...]}` |
| `workspace.importHolds.resolve` | zápis | Pracovní prostor | `owner` a vlastník serveru | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`    | zápis  | Instalace*  | `owner`               | `id`          | řádek registru označený jako smazaný |

* `workspace.delete` je bez rozsahu, protože řádek, který označuje, žije v globálním
registru. Jeho obsluha zkontroluje členství volajícího v pojmenovaném pracovním prostoru
a vyžaduje `owner`.

`path` v každé odpovědi je cesta na **hostiteli serveru**.

`server.listOrphanedBackups` vrací jednu položku na každý pracovní prostor, který už není živý:
`workspace_id`, `workspace_name`, pokud ho registr ještě zná, a `backups`.
Smazaný pracovní prostor už nemůže projít kontrolou role v pracovním prostoru, takže jeho zálohy
patří vlastníkovi instalace. `server.deleteOrphanedBackup` odmítne živý pracovní prostor, jehož
zálohy zůstávají za `workspace.deleteBackup` a vlastními rolemi toho prostoru. Obě mazací
operace přijímají jen vypsané jméno adresáře s časovým razítkem, ne cestu.

`workspace.importHolds.list` vrací, co import zadržel. Každé zadržení má `id`, `kind` (`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role` nebo `invite`), `payload`, který by se vrátil zpět, `imported_at` a `source_install_id`. `workspace.importHolds.resolve` s `accept: true` ho přidělí znovu a s `false` zahodí. `applied` je nepravdivé, když komu nebo čemu grant patřil, už v pracovním prostoru není.

:::note[Snímek celé instalace je na obou linkách jen pro vlastníka]
`server.backupNow`, `server.listBackups` a `server.deleteBackup` vyžadují
**vlastníka** instalace (`ServerAuthority.serverOwner`), stejnou bránu jako
`GET /backup/snapshot`. Snímek zachytí databázi každého pracovního prostoru, takže
admin jednoho pracovního prostoru nestačí na správu ostatních. Smazání
přijme jen uvedené jméno adresáře s časovým razítkem, ne libovolnou cestu na
serveru, a odstraní celý snímek, včetně neověřených.
Export jednoho pracovního prostoru a stahování plánovaných záloh zůstávají na adminovi pracovního prostoru.
:::

:::note[Obnovení patří vlastníkovi serveru]
`workspace.import` a `POST /backup/restore` přinutí server převzít databázový soubor, jehož řádky pak bere jako své: propojení repozitářů a to, kdo je vytvořil, definice prostředí, které běží na hostiteli, cesty worktree a logů. Proto obojí vyžaduje vlastníka serveru (`ServerAuthority.serverOwner`), který musí být zároveň vlastníkem pracovního prostoru. Kdokoli jiný a každý volající na hostiteli bez zaznamenaného vlastníka je odmítnut s `server_owner_required`. Žádný spouštěč, pohled, sloupec ani omezení, které soubor přinese, se nepřevezme.
:::

### Odpověď `server.listBackups`

Nejdřív nejnovější, seřazené podle jména adresáře. To je časové razítko, takže pořadí drží i
u snímku, jehož manifest nešel přečíst.

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

`created_at` se vynechá, když manifest nešel přečíst. `bytes` na nejvyšší úrovni je
skutečná velikost celého adresáře na disku, ne vlastní součet manifestu. Operátor,
který snímky prořezává, se ptá, kolik adresář stojí, ne co záloha chtěla zapsat.

Každé `workspaces[].path` je přesně to, co `workspace.import` bere jako `source_path`. Je
to schválně: „obnov tenhle pracovní prostor z tohohle snímku“ *je* operace importu, takže se obě
nemůžou rozejít v tom, jak se stejným souborem naloží.

### Ověření `workspace.import`

Než se cokoli nahradí, kandidátní soubor se zkopíruje do přípravného souboru vedle cíle a tam se zkontroluje. Odmítnutí se ničeho nedotkne a jeho druh nese jako `data.kind`.

| Podmínka                                              | Výsledek                                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Soubor neexistuje | Odmítnuto, `import.missing_source` |
| Není to čitelná databáze SQLite, nebo neprojde `quick_check` | Odmítnuto, `import.damaged` |
| Pochází ze snímku a jeho SHA-256 se liší od hodnoty v manifestu | Odmítnuto, `import.checksum_mismatch` |
| Zapsala ho novější verze serveru | Odmítnuto, `import.newer_schema` |
| Jiné `application_id`, nebo chybí `workspace_meta` | Odmítnuto, `import.foreign_file` |
| Nejde převést na schéma tohoto serveru | Odmítnuto, `import.schema_mismatch` |
| Jeho webhooky nebo pozvánky už směrují do jiného pracovního prostoru | Odmítnuto, `import.route_conflict` |
| Zaznamenané id pracovního prostoru ≠ cíl              | **Povoleno**. Jeho řádky se přepíšou na id cíle. Takhle se pracovní prostor zduplikuje nebo obnoví pod novým id    |
| Zaznamenané id instalace ≠ tahle instalace            | **Povoleno**. Id uživatelů z něj patří té instalaci a tady se nevyřeší |

Po přijetí se přípravný soubor převede na schéma tohoto serveru a pak se s ním musí přesně shodovat. Granty, které si soubor nesmí přidělit sám, se z něj vyjmou: schválení spouštět definici prostředí na hostiteli se zruší a pravidla akcí, která povolují nebo vyžadují schválení, granty sandbox exec, repozitářové granty nad čtení, role nad člena a pozvánky do těchto rolí se stanou zadrženími, která vlastník serveru projde. Importující si zachová roli vlastníka, nebo ji získá. Nahrazovaná databáze se uchová jako plánovaná záloha s názvem `<timestamp>-pre-restore`, přípravný soubor se s uzavřenými připojeními pracovního prostoru přejmenuje na místo cíle, `code_index.db` se smaže, aby se znovu sestavil, a indexy FTS se znovu sestaví.

## Trasy přenosu

Operace exportu, importu a výpisu snímků výše mluví v cestách na straně
serveru, a to je úplná odpověď jen tehdy, když je server tvůj vlastní stroj.
Tyto cesty ve tvaru HTTP nesou bajty záloh **uvnitř stejného ověřeného,
od konce ke konci šifrovaného tunelu prostředků** jako ostatní citlivé
prostředky, ať je spojení RPC přímé, nebo zprostředkované. Nejsou to veřejné
HTTP koncové body pro přenos souborů: požadavek na některou z nich na veřejném
posluchači vrátí `426 Upgrade Required`, a to i z loopbacku. V šifrovaném
tunelu musí zařízení ověřené protokolem Noise odpovídat `d`; handler navíc
zkontroluje podpis zařízení nad jeho cílovým řetězcem pomocí jeho párovacího
PSK a roli níže.

| Trasa                   | Metoda | Dotaz           | Podepsaný cíl                    | Vyžaduje                         |
| ----------------------- | ------ | --------------- | -------------------------------- | -------------------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | **admin** pracovního prostoru    |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | **vlastník** instalace           |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | **admin** pracovního prostoru; po smazání pracovního prostoru **vlastník** instalace |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | **vlastník** instalace, který je zároveň **vlastníkem** pracovního prostoru (jinak `403` s `server_owner_required`) |

`w` je id pracovního prostoru, `n` jméno adresáře snímku nebo plánované zálohy, `d` id volajícího zařízení a `s`
podpis. U `/backup/snapshot` se `n` vyřeší proti výpisu záloh, ne spojením cesty ke kořeni záloh,
takže trasa nemůže mířit na adresář, který by výpis neukázal. U `/backup/stored` musí jít o jméno
s časovým razítkem a soubor musí být skutečný soubor uvnitř vlastního adresáře záloh toho pracovního prostoru.

| Stav   | Příčina                                                                                 |
| ------ | --------------------------------------------------------------------------------------- |
| `400`  | Chybí povinný parametr dotazu, jméno zálohy je neplatné, tělo nahrání je prázdné, nebo byl nahraný soubor odmítnut (tělo je `{error, kind}` s druhem `import.*`) |
| `403`  | Neznámé nebo odvolané zařízení, špatný podpis, nebo volající nemá roli                  |
| `404`  | Na tomhle hostiteli není port záloh, nebo pojmenovaný snímek, záloha či soubor pracovního prostoru neexistuje |
| `405`  | `/backup/restore` zavolané jinak než `POST`                                             |
| `413`  | Tělo nahrání přesahuje 8 GiB, podle deklarovaného content-length nebo podle bajtů, které se skutečně přečetly |
| `426`  | Jakýkoli přímý požadavek na trasu přenosu na veřejném HTTP posluchači; použij šifrovaný tunel prostředků spárovaného klienta |
| `500`  | Export nebo archiv selhal na straně serveru                                             |

Všechna tři stažení odpovídají `Cache-Control: no-store` a `Accept-Ranges: none`.
`/backup/workspace` a `/backup/snapshot` vytvoří pro každý požadavek **čerstvou** kopii a po odstreamování ji smažou. Jinak se bajty ze dvou různých exportů
slepí do jednoho souboru, ať už z mezipaměti, nebo z obnoveného rozsahu. Takový soubor vypadá platně a platný není.

`/backup/stored` je výjimka: streamuje plánovanou zálohu jako `<workspaceId>-<name>.db`
a soubor nechá na místě, protože ten soubor je ta záloha.

`/backup/snapshot` vrací `<name>.zip`. Položky jsou relativní ke kořeni snímku, takže
rozbalení zopakuje `manifest.json` + `global.db` + `<workspaceId>/workspace.db`.
Položky se zapisují v seřazeném pořadí, takže dva archivy téhož snímku jsou tentýž
archiv.

`/backup/restore` streamuje tělo rovnou do přípravného souboru a nebufferuje ho,
omezí ho před čtením i během něj a přípravný soubor smaže na **každé** cestě ven,
včetně odmítnutí.

::::caution[Přímé spojení i relé používají stejný šifrovaný přenos]
Relé vozí požadavky na prostředky, streamované odpovědi i bajty nahrání jako
šifrový text; obsah záloh přečíst neumí. Cesta na straně serveru zůstává cestou
na hostiteli serveru, ne souborem na relé. Přístup pořád vyžaduje spárované
zařízení, podpis cíle a příslušnou roli v pracovním prostoru nebo instalaci.
Ani jeden přenos nešifruje výsledné soubory záloh v klidu.
::::

## Cesty a limity

| Věc                                | Hodnota                                                      |
| ---------------------------------- | ------------------------------------------------------------ |
| Snímky                             | `<dataDir>/backups/<timestamp>/`                             |
| Naplánované zálohy pracovního prostoru | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| Exporty pracovního prostoru        | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| Databáze nahrazená obnovením | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| Databáze tak, jak byly před aktualizací, která změnila jejich formát | `<dataDir>/pre_upgrade/` a `<dataDir>/<workspaceId>/pre_upgrade/`, vždy dvě nejnovější kopie každé |
| Příprava přenosu                   | `<dataDir>/backups/transfer/` — mezisklad, který uklidí trasa, jež do něj zapisuje |
| Jméno archivu snímku               | `<snapshot directory name>.zip`                              |
| Strop nahrání                      | 8 GiB na šifrované nahrání `/backup/restore`                 |
| Uchování                           | Snímky instalace: ruční smazání. Zálohy pracovního prostoru: týdenní pipeline, výchozí 30 dní, nebo ruční smazání. Zálohy smazaného pracovního prostoru: jen ruční smazání |

Adresáře `exports/`, `transfer/` a `workspace-backups/` nejsou
snímky instalace a `server.listBackups` je vynechává. Naplánované uchování má jen
poslední z nich, a to jen dokud jeho pracovní prostor existuje. Smazání snímku instalace vyžaduje výslovný zásah
vlastníka instalace.
