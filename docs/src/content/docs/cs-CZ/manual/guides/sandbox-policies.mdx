Jestli běh agenta běží v sandboxu, rozhoduje se na serveru při startu
(`--sandbox`). Přepínač **Zapnout sandboxing** a výběr **Backend** v
**Nastavení → Server → Diagnostika a soukromí** jsou preference uložené na tvém
zařízení. Detekce hostitele na kartě **Sandboxing** hlásí, co umí obalit
hostitel serveru.

K běhu sahají dva ovládací prvky a tenhle návod pokrývá oba: pravidla akcí v
**Nastavení → Pracovní prostor → Oprávnění agentů**, která rozhodují, co agent
smí pushnout, otevřít nebo kam dosáhnout, a vlastní příznak `--sandbox`
serveru.

## Co omezuje běh agenta

Agenta drží šest věcí. První je sandbox operačního systému a ta je
podmíněná — zbylých pět drží na každém hostiteli.

| Hranice                  | Co dělá                                                                                                                                                                            |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sandbox operačního systému | Seatbelt na macOS, bubblewrap na Linuxu a na WSL2. Obalí CLI Claude Code, adaptéry ACP a nástroj `bash` harnessu. **Chybí na Windows a na Linuxu bez `bwrap` a `socat`, kde startují jen běhy vlastníka serveru** |
| Vlastní worktree         | Každá konverzace dostane copy-on-write checkout. Původní checkout se do běhu vloží jako cesta se zákazem zápisu a vynucuje to sandbox                                              |
| Pověření od brokera      | Broker přihlašovacích údajů vystaví prostředí pro daný běh a při úklidu ho odebere. Token GitHub v něm umí číst, ale ne pushovat: push jde přes Control Center, které se nejdřív zeptá pravidla pro push |
| Guardraily akcí          | Každý mutující nástroj deklaruje své třídy efektů a strážce je vyhodnotí, než se volání spustí. `prompt` bez připojeného schvalovatele se odmítne                                 |
| Očištění prostředí       | ACP a nástroj `bash` harnessu dostanou filtrované prostředí. Claude Code přes `NoSandboxAdapter` dědí prostředí hostitele                                                         |
| Plocha nástrojů režimu   | Režim jen pro čtení sundá nástroje, které mění worktree, a připne vlastní výstupní sloveso režimu, aby pořád uměl doručit                                                         |

Tři věci jsou slabší, než vypadají:

- Jen **vestavěný harness** vynucuje bránu nástrojů, kontrakty dokončení a
  strukturální pravidla režimu. Adaptér Claude Code ne. Claude
  Code se navíc spouští s `--dangerously-skip-permissions`, protože
  neinteraktivní `claude -p` by jinak navždy čekalo na vlastní výzvu —
  takže vlastní volání Claude na čtení, zápis a úpravy Control Center ani nevidí, ani nehlídá a jeho příkazy bash kontroluje jen hook, který čte příkazový řádek. Kde je sandbox zapnutý, je hranicí kolem nich.
- Souborové nástroje harnessu v procesu (read, write, edit, apply patch, search,
  find, search_files) běží uvnitř procesu serveru, takže je neomezuje žádný profil sandboxu.
  Sandboxovaným runnerem příkazů projde jen nástroj `bash`. Ty nástroje
  omezuje jejich vlastní omezení cest a k tomu guardraily akcí.
- Na hostiteli bez backendu startují jen běhy, za které odpovídá vlastník serveru,
  a pro ty první řádek neplatí vůbec. Ostatní běhy se odmítnou. Při `--sandbox off`
  startují všechny běhy bez prvního řádku. Tak či tak ACP a nástroj `bash` harnessu
  spadnou na očištění prostředí a politiku příkazů a Claude Code dědí prostředí
  hostitele přes `NoSandboxAdapter`. Server řekne, v jakém případu jsi, ve
  startovacím logu. Svůj si zkontroluj níže.

## Rozhodni, co agent smí pushnout

Pro git push, GitHub, ticketing ani síť neexistuje přepínač u agenta. Každé z
nich je pravidlo akce:

| Pravidlo                              | Vestavěný výchozí | Co pokrývá                                                                   |
| ------------------------------------- | ----------------- | ---------------------------------------------------------------------------- |
| **Odeslat na remote**                 | Nejdřív se zeptat | Každý `git push` na GitHub, bez ohledu na adaptér                            |
| **Otevřít pull request**              | Nejdřív se zeptat | Nástroje pro pull requesty v Control Center. `gh pr create` v běhu nefunguje                                  |
| **Aktualizovat nebo sloučit pull request** | Nejdřív se zeptat | Komentáře agenta k jeho pull requestu, úpravy jeho názvu nebo popisu a zveřejněné kontroly, přes nástroje Control Center. `gh pr comment`, `gh pr edit`, `gh pr review`, `gh pr merge` a `gh pr close` v běhu nefungují                |
| **Zápis do externího trackeru**       | Nejdřív se zeptat | Zápisy ticketů přes nástroje Control Center a `gh issue`                     |
| **Přístup k síti**                    | Povolit           | Jestli má sandbox vůbec síť, a webové nástroje harnessu                      |

1. Jdi do **Nastavení → Pracovní prostor → Oprávnění agentů**
2. Vyber rozsah — **Pracovní prostor**, **Agent** nebo **Prostor** — a na řádku
   pravidla vyber **Povolit**, **Nejdřív se zeptat** nebo **Zakázat**

Platí i pravidla pro push omezená na větve, třeba takové, které zakazuje push
na `main`: viz [Guardraily](/cs-CZ/prirucka/koncepty/guardraily/).

Kontrolní bod: požádej agenta, aby pushnul větev. U **Nejdřív se zeptat**
dostaneš žádost o schválení s repozitářem a refy; u **Zakázat** git vypíše
`! [remote rejected] <ref> (Control Center policy: …)`.

Jak se jednotlivá pravidla dostanou k běhu:

- **Push** se vynucuje tím, co běh drží. Jeho token GitHub pokrývá jediný
  repozitář běhu a pushovat neumí: umí číst obsah a, když odpovědný člen smí
  pushovat, komentovat pull requesty. Jeho konfigurace gitu posílá každý push na GitHub na loopback bránu na
  `cc_server`, která se zeptá pravidla a teprve pak push předá se zapisovacím
  tokenem, který agent nikdy neuvidí. Brána předává jen do vlastního
  repozitáře worktree nebo do repozitáře na GitHubu propojeného s pracovním
  prostorem. Platí to pro každý adaptér.
- **Pull requesty a issues ze shellu** se poznají podle příkazového řádku, v
  nástroji `bash` harnessu a přes hook v nástroji `Bash` v Claude Code. Agent,
  který příkaz schová (skript, `eval`, přímé volání API), touhle kontrolou
  projde, ale bránou pro push ne.
- **Klíče ticketingu** se do sandboxu nikdy nevkládají. Agenti zapisují tickety
  přes nástroje MCP v Control Center, které se ptají pravidla.
- **Síť** se vyhodnotí jednou, při startu běhu. **Zakázat** síť sandboxu vypne;
  **Povolit** a **Nejdřív se zeptat** ji nechají zapnutou a u **Nejdřív se
  zeptat** se nástroje harnessu `web_fetch` a `web_search` pořád ptají při
  každém volání. Dokud je síť zapnutá, je GitHub vždycky na seznamu povoleného
  odchozího provozu.

:::note[Odkud se bere token GitHubu pro běh]
Token se pro běh vydá z GitHub App pracovního prostoru, z vlastní aplikace
serveru nebo přes Control Center Connect a je omezený na to, co smí v daném
repozitáři odpovědný člen (ten, kdo požádal, jinak vlastník pracovního
prostoru). Nikdy to není celé předané přihlášení člena a žádný záložní token
neexistuje: když se žádný vydat nedá, běh nastartuje bez něj a jeho poznámky
uvedou proč.
:::

## Zkontroluj, jestli jsou běhy agenta v sandboxu

Rozhodují o tom dvě věci, obě na serveru: jestli hostitel nabízí backend a
jestli je `--sandbox` zapnutý. Zkontroluj je v tomhle pořadí.

1. Jdi do **Nastavení → Server → Diagnostika a soukromí**
2. Přečti kartu **Sandboxing**. Údaj **Hostitel** je stroj, na kterém běží
   `cc_server`, ne stroj, na který se díváš. Pole **Backend** uvádí
   **Nativní sandbox** (Seatbelt na macOS, bubblewrap na Linuxu a na WSL2) nebo
   **Bez izolace**. Údaj **V platnosti** je preference tohohle zařízení, ne
   obal, který server skutečně používá.
3. Přečti startovací log serveru. Vypíše přesně jeden ze tří řádků:
   - `agent sandbox ON` plus poznámka k backendu: běhy jsou obalené
   - `no OS-native agent sandbox on this host` plus nápověda k instalaci, kde
     nějaká je: startují jen běhy, za které odpovídá vlastník serveru, bez obalu,
     a ostatní se odmítnou
   - `agent sandbox DISABLED by --sandbox off`: startují běhy všech členů, bez obalu
4. Řádek o vystavení, který se vypíše při startu, říká totéž jedním slovem:
   `sandbox=native`, `sandbox=off` nebo `sandbox=unavailable`.

`GET /healthz` stav sandboxu nehlásí, takže kontrolou je startovací log.

Bez sandboxu běžet rozhoduje jen vlastník serveru. Aby to platilo pro všechny,
spusť server s `--sandbox off`, nebo nastav `CC_SERVER_SANDBOX=off`. Agenti všech
členů pak na tom stroji běží bez omezení, takže jde o rozhodnutí o všech, kdo
server používají, a učiní se jednou při startu. Výchozí hodnota je `on`: obalí
každý běh, když hostitel backend má, a když ho nemá, startují jen běhy vlastníka.

Nativní obal sandboxu ve dvou situacích nevznikne vůbec. Na **Windows** nativní
sonda vždycky hlásí, že není k dispozici, a není co instalovat, takže startují
jen běhy vlastníka serveru, pokud vlastník nepředá `--sandbox off`. Backend
`microvm` je zvlášť (interaktivní terminály a stanice) a pouští ho vlastní sonda
podle jeho runtime. Na **Linuxu a WSL2** musí být na `PATH` jak `bwrap`, tak
`socat`; bez nich sonda hlásí, že není k dispozici, a pojmenuje chybějící
balíčky, a startují jen běhy vlastníka.

Na Linuxu a WSL2 s nainstalovaným bubblewrapem se globy tajných souborů
standardní politiky nedají vynutit u souborů, které agent vytvoří až později,
takže každý nativní běh selže, místo aby pravidla potichu ignoroval, i běh
vlastníka. Kladná sonda při startu proto nezaručí, že se odeslání na Linuxu umí
rozběhnout: dnes Linux server spouští agenty buď s `--sandbox off`, nebo bez
bubblewrapu jen pro vlastníka. `--sandbox off` je záměrné vypnutí bez omezení,
ne náhradní bezpečnostní hranice.

## Zjisti, co režim už zakazuje

Režim se ukládá na prostor a do vyhodnocovače guardrailů vstupuje jako vrstva
**Předvolba režimu**. Tři ze čtyř režimů jsou jen pro čtení a režim jen pro
čtení odmítne dvanáct tříd efektů rovnou:

| Režim               | Worktree         | Co předvolba odmítá                                                                                                                                                                                                                     |
| ------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent** (`chat`)  | Zapisovatelný    | Nic — platí vestavěné výchozí hodnoty                                                                                                                                                                                                   |
| **Plán**            | Jen pro čtení    | Smazat soubor, zápis mimo worktree, vytvořit commit, odeslat na remote, otevřít pull request, zveřejnit kontrolu nebo sloučení, zápis do externího trackeru, nainstalovat balíček, spustit proces, změnit strukturu pracovního prostoru, ovládat izolované prostředí (stanici), spouštět příkazy na hostiteli |
| **Kontrola**        | Jen pro čtení    | Stejných dvanáct. Nejde vybrat — composer nabízí jen Agent, Plán a Orchestraci                                                                                                                                                        |
| **Orchestrace**     | Jen pro čtení    | Stejných dvanáct                                                                                                                                                                                                                       |

Přístup k síti a čtení tajemství režim jen pro čtení schválně _neodmítá_:
výzkum je jeho smysl.

## Vyžaduj schválení, než akce proběhne

Schválení je rozhodnutí guardrailu, ne nastavení sandboxu.

1. Jdi do **Nastavení → Pracovní prostor → Oprávnění agentů**
2. Nastav třídu akce na **Nejdřív se zeptat** v rozsahu pracovního prostoru, agenta nebo prostoru

Rozhodnutí **Nejdřív se zeptat** běh přeruší a zeptá se tě. Když není
připojený schvalovatel, selže uzavřeně a akce se odmítne. Celé pořadí
vyhodnocení je v
[Nastavte guardraily](/cs-CZ/prirucka/navody/nastaveni-guardrailu/).

## Řešení problémů

### Agent nemůže pushnout a já jsem to nezakázal

Přečti si, co git vypsal. `Control Center policy: …` znamená, že push zamítlo
pravidlo nebo že **Nejdřív se zeptat** zůstalo bez odpovědi.
`… is not linked to this workspace` znamená, že push míří do repozitáře, který
není repozitářem worktree ani není propojený s pracovním prostorem.
`Control Center has no GitHub credential that can push …` znamená, že se nepodařilo vygenerovat žádný push token: nainstaluj GitHub App na ten repozitář, nebo se přihlas k GitHubu.

### Můj běh byl odmítnut hláškou „Tento server nemá sandbox“

Běh ukáže **Agenti na tomto serveru potřebují sandbox** s hláškou „Tento server nemá sandbox, takže zde agenty může spouštět jen jeho vlastník. Vlastník může sandbox nainstalovat nebo sandboxing vypnout pro všechny.“ Hostitel serveru nemá sandbox operačního systému a osoba odpovědná za běh není vlastník serveru, takže nic nenastartovalo. U plánu, webhooku nebo jiné automatizace je odpovědná osoba ta, ke které je automatizace navázaná, ne ten, kdo se na ni zrovna dívá.

Jen vlastník serveru to může změnit. Na Linuxu a WSL2 nainstaluje `bubblewrap` a `socat` a restartuje server (ale nejdřív si přečte poznámku o Linuxu výš). Na Windows není backend, který by se dal nainstalovat. Druhou volbou je restartovat server s `--sandbox off`, což spustí agenty všech členů na tom stroji bez omezení.

### Karta Sandboxing nehlásí nativní sandbox

Pak běhy agenta na tom hostiteli neobaluje Seatbelt ani bubblewrap: startují jen běhy vlastníka serveru a zbývající hranice jsou to, co mají. Na Linuxu a na WSL2 nainstaluj oba chybějící
nástroje — `sudo apt-get install bubblewrap socat` — a restartuj server;
startovací log by pak měl říct, že je sandbox zapnutý. Na Windows není nativní
backend k instalaci, takže místo toho utáhni guardraily pro běhy vlastníka: viz
[Nastavte guardraily](/cs-CZ/prirucka/navody/nastaveni-guardrailu/).

### Agent se dostal k souboru mimo svůj worktree

Jestli je to očekávané, rozhoduje, který nástroj se k němu dostal.

Souborové nástroje harnessu v procesu (read, write, edit, apply patch, search,
find, search_files) běží v procesu serveru, takže se na ně žádný profil
sandboxu nevztahuje — jejich mez je vlastní omezení cest a k tomu guardraily.
Příkaz `bash` nebo CLI Claude Code se _obaluje_ tam, kde backend existuje, a
tvoje registrované checkouty jsou uvnitř toho obalu v každém režimu se zákazem
zápisu, včetně zápisů po rozřešení symlinku (na macOS se cesta dosažená přes
`/tmp` nebo `/var/folders` rozřeší pod `/private` a oba zápisy se odmítají).
Při `--sandbox off` nebo u běhů vlastníka na hostiteli bez backendu nic z toho neplatí. V obou případech umí guardraily
rovnou odmítnout **Zápis mimo worktree**.
