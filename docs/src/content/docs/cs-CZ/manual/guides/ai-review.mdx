Tenhle návod ukazuje, jak nechat recenzenty zkontrolovat pull request a jak
výsledek zveřejnit na GitHub.

## Spusť AI kontrolu

1. Otevři PR a přejdi na záložku **Přehled**
2. V řádku akcí otevři nabídku ⋯ a zvol **Zeptat se AI**

Položka se ukáže jen u otevřeného PR. Je to akce před sloučením. Stejné
tlačítko **Zeptat se AI** je i na prázdném stavu záložky **Kontrola**, dokud
žádná kontrola není.

Control Center spustí předpřipravenou pipeline `pr_review` a otevře záložku
**Kontrola** daného PR, takže průběh jde sledovat. Pipeline:

1. Otevře vlastní prostor kontroly daného PR. Jeho izolovaný worktree má PR
   checkoutnutý na head
2. Rozešle recenzenty podle úrovně kontroly pracovního prostoru. Ve výchozím
   stavu tři, předpřipravené agenty **qa**, **architect** a **engineer**,
   paralelně. Jazyk ani doména se nedetekují
3. Nechá vedoucího agenta (CEO), aby jejich zjištění složil do souvislého
   průvodce
4. Finalizuje: roztřídí zjištění podle shody a spočítá verdikt. Když asociace
   dospěje do `awaiting approval`, na záložce Kontrola se objeví **Zveřejnit na
   GitHub**

Jak hluboko kontrola jde, určuje **úroveň kontroly** pracovního prostoru:
`light` (jeden recenzent), `balanced` (tři, výchozí) nebo `thorough` (všech
pět, navíc specialisté na zabezpečení a výkon). Nastavuje se v **Nastavení →
Pracovní prostor → Obecné**, na kartě **Politika pracovního prostoru**. Lehčí
úroveň zapíše stejně zjištění a hned na začátku jich nahlásí méně.

Všichni recenzenti píší do jediného prostoru kontroly daného PR, a proto jdou
jejich zjištění porovnat. Jak do sebe díly zapadají, je v
[AI kontrola](/cs-CZ/prirucka/koncepty/ai-kontrola/).

`pr_review` má jen ruční spouštěč. Aby se spouštěla na každý zveřejněný PR,
přidej si spouštěč. Viz
[Odešlete review agenty](/cs-CZ/prirucka/navody/odeslani-review-agentu/). Spustit
ji jde i přímo z GitHubu, bez spouštěče pipeline: zmiň na PR bota serveru, nebo
přidej štítek `ai-review`. Viz
[Mluvte s Control Center z GitHub PR](/cs-CZ/prirucka/navody/konverzace-v-github-pr/).

Když toast hlásí „Pro tento pull request už běží kontrola“, jedna už běží.
Zůstaň na záložce **Kontrola**, nebo otevři **Pipelines** a najdi ji.

## Přečti zjištění

Recenzenti zapisují zjištění jako **uzly kontroly** v prostoru kontroly. Každý
nese:

| Pole           | Popis                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------ |
| Druh           | `bug`, `suggestion`, `recommendation`, `question` nebo `ticket`                            |
| Priorita       | P0 (kritická) → P3 (drobnost)                                                              |
| Kategorie      | `security`, `stability`, `data_integrity`, `correctness`, `performance` nebo `maintainability` |
| Soubor a řádek | Kam je zjištění ukotvené                                                                   |
| Původní kód    | Kód, kterého se zjištění týká                                                              |
| Navržený kód   | Navrhovaná oprava                                                                          |
| Jistota        | Jak jistý si je recenzent                                                                  |
| Stav           | `open` → `consensus-ready` → `resolved` nebo `dismissed`                                   |

Do **consensus-ready** se zjištění dostane až tehdy, když ho potvrdí _jiný_
recenzent. Agent vlastní zjištění potvrdit nemůže, takže názor jednoho
recenzenta sám od sebe nepostoupí.

Záložka **Kontrola** ukazuje seznam zjištění. Jde filtrovat podle druhu a
stavu a má přepínač zamítnutých zjištění, vedle artefaktu, který zveřejnil
agent skládající průvodce. Deterministický pohled — kohorty, víceosý přehled,
smluvní a vizuální diffy — se počítá na serveru, ale v aplikaci nemá plochu.
Co průchod vyrobí, popisuje
[Výpočet kontroly](/cs-CZ/prirucka/navody/vypocet-kontroly/).

## Podívej se na panel neshod

Když dva recenzenti ukotví zjištění na stejný soubor a řádek, ale ohodnotí je
hodně jinak — priority vzdálené o dvě a víc úrovní, nebo jeden to nazve `bug`
a druhý `suggestion` — nad seznamem zjištění se objeví panel neshod. Čti je
jako první. Tam se názory recenzentů rozcházejí a tvůj úsudek má největší cenu.

## Přečti verdikt

Když vedoucí agent finalizuje, spočítá **verdikt**:

| Verdikt   | Význam                                           |
| --------- | ------------------------------------------------ |
| **Ship**  | Nic, co by blokovalo                             |
| **Hold**  | Problémy, které se mají vyřešit před sloučením  |
| **Block** | Kritické problémy, které se musí opravit         |

Verdikt nese souhrnné skóre jistoty a počty zjištění podle priority.

Osy kontroly se do něj pak složí a umějí ho jen **zpřísnit**. Osa s bránou,
která selže, vynutí **Block**. Osa s bránou, která nedoběhla (`partial`) nebo
se vůbec nespustila (`unavailable`), vynutí aspoň **Hold**. Chybějící důkaz
bránu nikdy neotevře.

## Zveřejni kontrolu na GitHub

Zveřejnění je samostatný krok a schválně ho pouští uživatel. Pipeline
`pr_review` nechá kontrolu v Control Center a na GitHub nic neposílá.

1. Na záložce **Kontrola** počkej, až se objeví **Zveřejnit na GitHub**
2. Stiskni **Zveřejnit na GitHub**

Control Center odešle **jednu** revizi na GitHub. Zjištění už vyřešená nebo
zamítnutá se přeskočí. Tlačítko zahrne každé zbývající otevřené zjištění a při
**Ship** odešle `APPROVE`. (Nástroj MCP `publish_review_to_github` má pořád
výchozí jen zjištění potvrzená kolegou a neschválí, dokud nepředáš
`approve_on_ship`.) Zjištění s kotvou na soubor a řádek se stanou vloženými
komentáři. Všechno ostatní splyne do těla shrnutí a každé nese patičku
"— Control Center AI review", aby byl zdroj jednoznačný. Verdikt **Block** se
odešle jako `REQUEST_CHANGES`, **Hold** jako `COMMENT` a **Ship** jako
`APPROVE` z tohoto tlačítka. Toast pak hlásí **Zveřejněno**. Revize jde pod
identitou aplikace serveru.

Když GitHub odmítne vloženou kotvu, protože řádek není součástí diffu, celá
revize se pošle znovu a každé zjištění se složí do těla. Nic se potichu
nezahodí.

:::caution[Zveřejnění hlídají guardraily]
`pr_review.publishReview` deklaruje třídu akce `prPublish` a prochází úzkým
místem guardrailů. Když je vyřešené rozhodnutí `prompt` a není připojený žádný
schvalovatel, zveřejnění se zamítne. Guardraily při nejistotě zavírají.
Explicitní pravidlo nastav v Nastavení → Pracovní prostor → Oprávnění agentů,
pokud má běžet bez dohledu.
:::

Ostatní vestavěné pipeline na GitHub posílají rovnou: `cross_review`,
`pr_triage`, `ticket_to_pr` a `pre_merge_gate` končí krokem komentáře. Jen
`pr_review` výstup podrží pro tebe.

## Recenzenty odešli sám

Když chceš určit, které role PR zkontrolují a na které soubory se každá podívá,
použij v existujícím prostoru kontroly nástroj MCP `dispatch_reviewers`, nebo
do pipeline přidej uzly recenzentů. Obě cesty, včetně přesného podpisu
nástroje, jsou v
[Odešlete review agenty](/cs-CZ/prirucka/navody/odeslani-review-agentu/).
