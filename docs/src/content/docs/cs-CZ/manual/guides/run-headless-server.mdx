Spusť `cc_server` na stroji, který zůstane zapnutý, a připoj se k němu z počítače,
prohlížeče nebo telefonu. Server je nativní binárka v čistém Dartu, bez enginu
Flutteru, takže běží bez rozhraní na macOS, Linuxu i Windows. Vlastní databázi,
spouští agenty a dělá každé volání externího API. Klienti jen vykreslují.

## Spuštění v Dockeru (předpřipravené obrazy)

Každé vydání publikuje sestavu čtyř obrazů na GHCR pro vlastní hosting: backend, dva
statické tenké klienty a volitelné relé párování, plus volitelnou přihlašovací
službu `cc-connect` ([Spusťte server Connect](/cs-CZ/prirucka/navody/spusteni-serveru-connect/))
a samostatný obraz `cc-server-demo` pro veřejného hostitele dema. Instalace s vlastním hostingem
nepotřebuje checkout zdrojů. Připni tag verze
(`ghcr.io/samuelalev/<image>:v0.0.1-rc.1`), nebo jeď na `latest`.

| Obraz                                             | Co to je                                     | Publikuje        |
| ------------------------------------------------- | -------------------------------------------- | ---------------- |
| `ghcr.io/samuelalev/cc-server`                    | Backend: databáze, agenti, MCP, webhooky     | `-p 9030:9030`   |
| `ghcr.io/samuelalev/cc-webapp`           | Webový klient (statický nginx)               | `-p 8080:8080`  |
| `ghcr.io/samuelalev/cc-remote`        | PWA telefonního společníka (statický nginx)  | `-p 8081:8080`  |
| `ghcr.io/samuelalev/cc-signaling-server`     | Šifrované spojovací relé (volitelné)          | `-p 8788:8788`   |

Celá sestava jako compose soubor:

```yaml
services:
  server:
    image: ghcr.io/samuelalev/cc-server:latest
    ports: ["9030:9030"]
    volumes: ["cc_data:/data"]
    restart: unless-stopped
  web:
    image: ghcr.io/samuelalev/cc-webapp:latest
    ports: ["8080:8080"]
    restart: unless-stopped
  remote:
    image: ghcr.io/samuelalev/cc-remote:latest
    ports: ["8081:8080"]
    restart: unless-stopped
  signaling:
    image: ghcr.io/samuelalev/cc-signaling-server:latest
    ports: ["8788:8788"]
    restart: unless-stopped

volumes:
  cc_data:
```

Než cokoli z toho vystavíš mimo loopback, vyplatí se vědět:

- **Obraz `cc-server` vozí `CC_SERVER_INSECURE=1`** (musí se vázat na `0.0.0.0`,
  aby přijímal provoz z publikovaných portů). Použij reverzní proxy, která
  ukončuje TLS (Caddy, Traefik, nginx nebo Cloudflare Tunnel), v důvěryhodné
  síti, nebo připoj certifikát a nastav `CC_SERVER_TLS_CERT` /
  `CC_SERVER_TLS_KEY` (a pak zruš `CC_SERVER_INSECURE`). Toto nastavení
  ovládá jen vnější posluchač HTTP/WebSocket serveru. Nikdy nevypne povinnou
  šifrovanou klientskou relaci od konce ke konci. TLS pořád chrání přihlašovací
  a bootstrapový provoz, metadata spojení, veřejné koncové body a doručení
  webového klienta. Všechno přepíšeš přes `docker run -e …` nebo blok
  `environment:` v compose.
- **`/data` je jediný stav.** Databáze SQLite, tajemství spárovaných zařízení,
  stažené modely i zvuk schůzek žijí ve svazku. Zálohuj ho a kontejner je na
  odpis.
- **Tajemství poskytovatelů patří do připojeného `.env`, nikdy do `-e`.** Server
  odmítne nastartovat, když je `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_SECRET`,
  `GOOGLE_OAUTH_CLIENT_SECRET`, `LINEAR_API_KEY` nebo některé `SLACK_*SECRET*`
  v prostředí jeho procesu. Připoj soubor jen pro čtení na `/app/bin/.env`
  (`-v /secure/cc.env:/app/bin/.env:ro`), nebo aplikace nastav v Nastavení.
- **Klienta spáruj zevnitř obrazu** ještě před prvním připojením, ekvivalent
  kontejneru ke [kroku 3](#krok-3-spáruj-klienta-před-prvním-startem):

  ```bash
  docker run --rm -it -v cc_data:/data \
    --entrypoint /app/bin/cc_server ghcr.io/samuelalev/cc-server:latest pair
  ```

- **Oba klientské obrazy jsou statičtí hostitelé nginx.** Vložené prohlížečové
  editory používají tentýž origin aplikace a šifrovanou relaci, jak je popsáno
  [níže](#prostředky-prohlížečového-editoru). Formulář připojení každého
  klienta bere URL serveru, ID zařízení a párovací klíč. Signalizační relé
  potřebuje jen svůj port (`SIGNALING_HOST` / `SIGNALING_PORT` se dají
  přepsat). Je bezstavové, nedrží žádné párovací klíče a je to **záloha**:
  telefon použije loopback, LAN, tailnet nebo přímou cestu `wss://`, když je
  některá dosažitelná, a na relé spadne, až když žádná není. Přeskoč ho, když
  klienti na server dosáhnou vždy přímo. Zprostředkovatel vidí směrovací
  identifikátory, IP adresy, velikosti a časování a může provoz přerušit;
  dešifrovat proud prostředků mezi klientem a serverem ale neumí.

Zbytek návodu sestavuje server ze zdrojů. Příznaky a chování, které popisuje,
jsou ty samé, které do obrazu přivádějí proměnné prostředí.

## Předpoklady

- [Dart SDK](https://dart.dev/get-dart). Tohle repo si SDK připíná přes [fvm](https://fvm.app), takže před každý příkaz dej `fvm`.
- Checkout tohoto repozitáře.
- Nativní toolchain, který potřebuje přípravný skript: Rust/`cargo`, plus `meson`, `ninja`, `pkg-config`, `git` a překladač C++. Každý skript sestavení pojmenuje, co nenašel, a jak to nainstalovat.
- Dosažitelný hostitel: loopback pro místní použití, nebo adresa v LAN či veřejná adresa s TLS pro vzdálené klienty.

## Krok 1: Připrav nativní knihovny

Nativní knihovny jsou **povinné**. Zhoršený režim neexistuje. Sestav je z kořene
repozitáře dřív než cokoli jiného:

```bash
scripts/natives/build_natives.sh
```

Sestaví se `rift`, `fff`, tree-sitter i s gramatikami, `aec`, `lame`,
`ccpty`, `cc_watcher`, `cc_inference` a nativní SAML do
`build/natives/`. Build hook `cc_server`
znovu vloží do balíku, co je tam připravené, takže přeskočení tohohle kroku
buď sestavení rovnou shodí, nebo s únikovou cestou níže vyrobí binárku, jejíž
preflight při startu odmítne naběhnout a pojmenuje chybějící knihovnu.

:::note[Úniková cesta jen pro kompilaci]
Prázdný soubor `.cc_natives_allow_missing` v kořeni repozitáře sníží selhání
sestavení kvůli chybějícím nativním knihovnám na varování. Je na kontrolu
syntaxe čerstvého klonu. Server sestavený takhle nenaběhne. Musí to být
**soubor**: spouštěč build hooku nepředává prostředí volajícího, takže
proměnná prostředí se ignoruje.
:::

## Krok 2: Sestav binárku

```bash
cd apps/cc_server
fvm dart build cli
```

Balík veze `libsqlite3` a připravené nativní knihovny vedle binárky. Systémové
SQLite ani engine Flutteru nepotřebuje. Spustitelný soubor skončí v
`./build/cli/<os_arch>/bundle/bin/cc_server`.

## Krok 3: Spáruj klienta před prvním startem

Čerstvý datový adresář nemá spárované zařízení ani předem sdílený klíč, takže
výzvu na párovací klíč klient ještě neuspokojí. Vystav ho podpříkazem `pair`.
Zapíše `global.db` a `secrets.json` přímo. Server, který ten datový adresář už
obsluhuje, nové zařízení vezme bez restartu:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030
```

Vypíše tři hodnoty, které vložíš do formuláře připojení klienta:

```
Connect a thin client (paste into its connect form):
  Server      ws://localhost:9030/rpc
  Device id   web-client
  Pairing key <a freshly generated key>
```

Užitečné příznaky: `--device` (výchozí `web-client`; id zároveň volí vrstvu
zařízení, tedy `desktop`, `ios`, `android`, a cokoli jiného je webový klient),
`--label` (výchozí je název platformy plus hostname tohohle stroje), `--host`
(hostitel, který se vypíše do URL, protože loopback z jiného stroje není
dosažitelný) a `--client-url`. Opakované `pair` tomu zařízení otočí klíč a
shodí jeho živé relace. Párování pracovní prostor nikdy nezakládá. Pracovní prostory může vytvářet
jen vlastník serveru: v klientovi vlastníka onboarding ten první pojmenuje a
vytvoří, a ostatní čekají, dokud jim ho vlastník nevytvoří, nebo je nepozve
admin pracovního prostoru.

S `--client-url` navíc vypíše QR, které se dá naskenovat z terminálu a otevře
webového klienta už vyplněného:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server pair --data-dir ./data --port 9030 \
  --bind any --host 192.168.1.42 --client-url https://app.usectrl.dev
```

:::caution[Tohle QR není QR telefonu]
`--client-url` skládá odkaz pro **webového klienta**: URL serveru, ID zařízení
a klíč ve fragmentu URL. Telefonní aplikace **Remote** čeká jiný payload
(úplný deskriptor spojení serveru plus expiraci), vystavený z
**Nastavení → Vy → Vaše zařízení** v běžícím klientovi. Nejdou zaměnit. Viz
[Spárujte zařízení](/cs-CZ/prirucka/navody/parovani-zarizeni/).
:::

Pověření vystavené přes `cc_server pair` vyprší po 30 dnech, stejně jako to vystavené v aplikaci. Pro totéž zařízení spusť `pair` znovu, když chceš nové. Zařízení vystavené z CLI odvolej v
**Nastavení → Vy → Vaše zařízení**, až ho nebudeš potřebovat.

Párovací klíč ověřuje povinný handshake Noise; každá relace odvozuje čerstvé
provozní klíče a kontroluje podepsanou identitu serveru. Párovací klíč chraň a
získej ho z důvěryhodného zdroje (i z důvěryhodného QR), pak nový otisk serveru
ověř přes samostatný důvěryhodný kanál nebo proti známému pinu. Změněný pin
tiše nepřijímej: když identitu serveru schválně vyměníš, spáruj se znovu přes
důvěryhodný kanál. TLS samo o sobě ten otisk identity od konce ke konci
nedokáže prokázat.

## Krok 4: Spusť server

Na loopbacku, což je výchozí hodnota a všechno, co potřebuješ pro klienta na
tom samém stroji:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030
```

Aby na něj dosáhl jiný stroj, navaž každé rozhraní. Vazba mimo loopback bez TLS
se **při startu odmítne** (`Refusing to bind non-loopback address …
without TLS`), takže dej certifikát:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --tls-cert /path/fullchain.pem --tls-key /path/privkey.pem \
  --public-url wss://server.example:9030/rpc
```

Nebo ukonči TLS v reverzní proxy na důvěryhodné privátní síti a za ní se přihlas
k nešifrované vazbě:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server --data-dir ./data --port 9030 \
  --bind any --insecure --public-url wss://server.example/rpc
```

`--insecure` se ignoruje, když jsou nastavené `--tls-cert` i `--tls-key`. TLS
vždy vyhraje. Server inzeruje nešifrovaný stav vnějšího posluchače jako
`insecure: true` v `GET /healthz`. Nevypíná to ale šifrování Noise na `/rpc`,
ať se klient připojí přímo, nebo přes relé. Server, relé i klienty povyšuj
společně: staří klienti s otevřeným RPC se odmítají a žádná záložní varianta
pro kompatibilitu neexistuje. Veřejné požadavky na citlivé cesty prostředků
(včetně přenosů záloh) dostanou HTTP `426`, a to i z loopbacku; spárovaní
klienti místo toho používají šifrovaný tunel.

Server běží do `SIGINT`/`SIGTERM` a pak se čistě vypne.

### Přečti řádky při startu

Dva řádky ti řeknou, jak je tenhle server nastavený. Řádek o vystavení, vypsaný vedle úvodního banneru, začíná `cc_server exposure:` a uvádí, jak daleko jde server dosáhnout (`bind`, `tls`, `relay`, `tunnel`), zda je zaznamenaný vlastník serveru (`owner`) a jak na tomto stroji běží agenti (`sandbox`):

- `sandbox=native`: každý běh agenta je obalen sandboxem operačního systému.
- `sandbox=off`: server jsi spustil s `--sandbox off`, takže agenti všech členů běží na tomto stroji bez omezení.
- `sandbox=unavailable`: hostitel nemá backend sandboxu (Windows, nebo Linux bez `bwrap` a `socat`), takže startují jen běhy agentů, za které odpovídá vlastník serveru. Běhy všech ostatních jsou odmítnuty hláškou „Tento server nemá sandbox, takže zde agenty může spouštět jen jeho vlastník.“

Řádek sandboxu dřív v logu říká totéž slovy a, když chybí backend, uvádí, co nainstalovat. Spouštět cizí agenty bez sandboxu je volba, kterou vlastník serveru udělá jednou pro všechny pomocí `--sandbox off`. Viz [Nastavte politiky sandboxu](/cs-CZ/prirucka/navody/politiky-sandboxu/#zkontroluj-jestli-jsou-běhy-agenta-v-sandboxu).

## Krok 5: Připoj klienta

Namiř klienta na URL serveru a párovací klíč z kroku 3:

- **Aplikace pro počítač**: na obrazovce prvního spuštění klikni na **Připojit k serveru**, nebo server přidej později v **Nastavení → Server → Připojení a stav**. Viz [Připojte se ke vzdálenému serveru](/cs-CZ/prirucka/navody/pripojeni-ke-vzdalenemu-serveru/).
- **Webový klient**: otevři [app.usectrl.dev](https://app.usectrl.dev) (nebo vlastní kopii webového sestavení), klikni na **Připojit k serveru** a zadej URL serveru a v části **Použít párovací klíč** ID zařízení a párovací klíč.
- **Telefon**: aplikaci **Remote** spáruj z běžícího klienta. Viz [Spárujte zařízení](/cs-CZ/prirucka/navody/parovani-zarizeni/).

:::note[cc_server neservíruje webový balík]
Samostatný `cc_server` nikdy nepřipojí webový kořen, takže `GET /` vrátí 404.
Webový klient se hostuje zvlášť: použij `app.usectrl.dev`, nebo webové sestavení
hostuj sám na libovolném statickém hostiteli HTTPS (obraz `cc-webapp` výše je
přesně tohle). Origin prohlížeče jiný než loopback musí být v
`--allowed-origins`, jinak se upgrade WebSocketu na `/rpc` odmítne. Výchozí
seznam je `https://app.usectrl.dev` a `localhost` / `127.0.0.1` jsou povolené
vždy.
:::

### Prostředky prohlížečového editoru

Frontend editoru je důvěryhodný kód aplikace a běží na vlastním originu webové
aplikace. Jeho service worker vede HTTP i WebSocket provoz touž ověřenou
šifrovanou relací jako zbytek klienta. `cc_server` každý požadavek dešifruje,
předá ho svému lokálnímu backendu code-server a odpověď zašifruje zpět
klientovi. Soubory zůstávají v držení serveru.

Editor běží na serveru jako vlastní uživatel serveru, se svým terminálem, úlohami
a rozšířeními, takže ho může otevřít jen [vlastník serveru](/cs-CZ/prirucka/koncepty/autorizace/#vlastník-serveru).
Relace patří zařízení a osobě, která ji otevřela. Otevírá se se zapnutou důvěrou
pracovního prostoru ve VS Code, takže se VS Code před důvěrou ve složku zeptá,
a s vypnutými automatickými úlohami, takže úlohy repozitáře se při otevření
nespustí. Všichni ostatní zůstávají u vestavěného editoru aplikace a zobrazení
souborů; plný editor jim nabízen není.

Webového klienta hostuj přes HTTPS nebo zabezpečený origin loopbacku, aby
service workery mohly běžet. Sdílené prostředky jsou součástí běžného sestavení
webu i skriptů pro vydání. Když balík sestavuješ ručně, dožeň tyto prostředky
dodatečně z kořene repozitáře:

```bash
node tool/stage_resource_assets.mjs build/web
```

Pro webové sestavení telefonu dosaď `apps/cc_remote/build/web`. Tím se do
balíku aplikace zkopírují `cc_resource_bridge.js`, `cc_resource_worker.js` a
`cc_resource_ws_shim.js`.

Provoz nativního editoru místo toho používá fasádu loopback s rozsahem podle
schopnosti. Soukromou bránu pro hlášení a příkazy přes loopback, kterou má
rozšíření editoru spouštěné serverem, nevystavuj přes veřejnou proxy. Citlivé
veřejné HTTP požadavky se odmítají; prostředky vyžadují ověřenou šifrovanou
relaci.

## Krok 6: Zvol, jak se lidé přihlašují

Prvního klienta, který se připojí jako vlastník serveru, se server zeptá, jak
má přihlašovat lidi ke GitHubu, Google Calendar a Linear: **Použít aplikace
Control Center**, **Použít vlastní aplikace** nebo **Použít vlastní server
Connect**. Z terminálu je stejná volba:

```bash
./build/cli/<os_arch>/bundle/bin/cc_server connect status --data-dir ./data
./build/cli/<os_arch>/bundle/bin/cc_server connect enable --url https://connect.example.com --data-dir ./data
./build/cli/<os_arch>/bundle/bin/cc_server connect disable --data-dir ./data
```

`CC_CONNECT_URL` (`hosted`, `off` nebo URL) v prostředí serveru nebo v `.env`
volbu místo toho napevno určí. S **Použít vlastní aplikace** zaregistruj každého
poskytovatele v **Nastavení → Server → Jednotné přihlášení → Aplikace
poskytovatelů**; **Vytvořit moji aplikaci GitHub** nastaví GitHub v jednom
kroku. Tajemství poskytovatelů patří do souboru `.env` serveru, nikdy do
exportovaného prostředí. Viz [Vytvořte GitHub App](/cs-CZ/prirucka/navody/github-app/)
a [Control Center Connect](/cs-CZ/prirucka/referencni-prirucka/connect/).

Přihlášení přes Connect končí kódem, který ukáže prohlížeč, takže server pro
ně nepotřebuje veřejnou adresu. Přihlášení přes vlastní aplikace serveru vrací
prohlížeč na veřejnou URL serveru, takže nastav `--public-url` na adresu,
na kterou prohlížeče lidí dosáhnou.

Tohle je výchozí nastavení serveru. Admin pracovního prostoru může jednomu pracovnímu prostoru dát jinou volbu v **Nastavení → Pracovní prostor → Integrace**. S nastaveným `CC_CONNECT_URL` může pracovní prostor přejít na vlastní aplikace, ale ne na vlastní Connect; viz [Volba pro každý pracovní prostor](/cs-CZ/prirucka/referencni-prirucka/connect/#volba-pro-každý-pracovní-prostor).

Chceš-li z tohoto serveru hostovat Connect pro jiné servery, nastav
`CC_SERVER_CONNECT_HOST=on`; viz
[Spusťte server Connect](/cs-CZ/prirucka/navody/spusteni-serveru-connect/#vestav-connect-do-cc_server).

## Konfigurace

Příznaky výše stačí na první nastavení. Celá plocha, 23 dvojic příznaku a
proměnné prostředí, čtyři podpříkazy a rozložení datového adresáře, je v
[CLI `cc_server`](/cs-CZ/prirucka/referencni-prirucka/cc-server-cli/).

:::caution[Neznámé příznaky se tiše ignorují]
Parser argumentů je ruční a přeskočí všechno, co nezná, takže překlep
(`--tls-key-file`, `--bindany`) nevyvolá chybu. Server prostě naběhne s výchozí
hodnotou. Když příznak jako by nic nedělal, podívej se na řádky logu při startu.
:::

Čtyři, které budeš potřebovat nejspíš:

| Příznak        | Výchozí                              | Význam                                                                                           |
| -------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `--data-dir`   | adresář dat aplikace pro uživatele podle OS | Databáze, tajemství, modely a mezipaměť médií                                              |
| `--port`       | `9030`                               | TCP port (`0` = dočasný)                                                                         |
| `--bind`       | `loopback`                           | `loopback`, nebo `any` pro každé rozhraní (chce TLS nebo `--insecure`)                          |
| `--public-url` | odvozená z vazby                     | RPC URL inzerovaná spárovaným klientům. **Za proxy, NAT nebo tunelem ji nastav výslovně**       |

Výchozí datový adresář je `~/Library/Application Support/control-center` na
macOS, `%APPDATA%\control-center` na Windows a `$XDG_DATA_HOME/control-center`
(jinak `~/.local/share/control-center`) jinde. `.cc_server` relativní k cwd se
použije jen tehdy, když se nevyřeší domovský adresář ani adresář dat aplikace.

## Co server obsluhuje

`cc_server` je celá plocha produktu, ne její výsek: datová cesta repo-RPC a
odběry, endpoint nástrojů MCP na `POST /mcp` a `GET /sse` na tom samém portu,
příchozí webhooky, proxy médií a písem, callbacky jednotného přihlášení,
protokol zápůjčky flotily, stahování RSS na straně serveru v třicetiminutovém
rytmu a vektorové hledání (rozšíření `sqlite_vector` se registruje jako
automatické rozšíření pro celý proces a tam, kde není k dispozici, se zhorší
jen na fulltextové hledání).

Dispečer je **bezstavový**: vazba pracovního prostoru na relaci neexistuje.
Každé volání v rozsahu pracovního prostoru veze vlastní `workspace_id` a přístup
rozhoduje členství volajícího v pracovním prostoru a jeho role, ne držení
párovacího klíče.

Než port vystavíš mimo loopback, platí dvě věci (TLS samo o sobě nedodává
spárovanému klientovi šifrování od konce ke konci ani neautorizuje prostředky):

- **MCP vždy potřebuje svůj token.** Server vytvoří token MCP při prvním startu a každý požadavek, včetně loopbacku, ho musí poslat jako `Authorization: Bearer <token>`. Nedá se vypnout; vlastník serveru ho čte a otáčí v **Nastavení → Server → Servery MCP**. Požadavky z webové stránky, na neznámý `Host`, nebo `POST`, který není JSON, se odmítnou dřív, než se token zkontroluje. Viz [Používejte MCP server](/cs-CZ/prirucka/navody/mcp-server/).
- **`GET /healthz` je schválně bez ověření**, s CORS na všechny originy, a publikuje id serveru, název, otisk identity a verzi sestavení. Klienti otisk potřebují, aby si server připnuli, takže je to záměr. Znamená to ale, že každý dosažitelný `cc_server` tolik prozradí komukoli, kdo se zeptá.
