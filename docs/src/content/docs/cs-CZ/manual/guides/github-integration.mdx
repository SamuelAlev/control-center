Tenhle návod bere ty části nastavení, které patří ke GitHubu. GitHub je jeden
ze tří podporovaných hostitelů kódu. Jak připojit GitLab nebo Bitbucket a jak
je pracovní prostor míchá, je v
[Připojte hostitele kódu](/cs-CZ/prirucka/navody/pripojeni-hostitele-kodu/).

## Než začneš

- Účet na GitHubu s přístupem k repozitářům, na kterých chceš pracovat
- Server, který umí přihlašovat lidi ke GitHubu: buď vlastní GitHub App (viz
  [Vytvořte GitHub App](/cs-CZ/prirucka/navody/github-app/)), nebo Control
  Center Connect, podle volby vlastníka serveru v **Nastavení → Server →
  Jednotné přihlášení**

:::note[Přihlašovací údaje leží na serveru, u tebe]
Na stroji, na kterém píšeš, se neukládá nic. Tvoje přihlášení ke GitHubu drží
`cc_server`, klíčované tvým id uživatele, a použije ho každé zařízení, ze
kterého se přihlásíš: plocha, web i telefon. Jiný člen téhož serveru ho
použít nemůže a přihlásí se sám.
:::

## Přihlas se ke GitHubu

GitHub umí jen přihlášení: žádný token se nevkládá.

1. Jdi do **Nastavení → Pracovní prostor → Profil a identita → Hostování kódu**
   (nebo na první krok onboardingu)
2. Na řádku **GitHub** klikni na **Přihlásit se k GitHub**
3. Prohlížeč otevře GitHub. Schval aplikaci

Jak se přihlášení dokončí, záleží na tom, kdo ho provádí:

- **Vlastní aplikace serveru:** GitHub pošle prohlížeč zpět na server a dialog
  si toho všimne sám. Nic se neopisuje
- **Control Center Connect:** stránka v prohlížeči ukáže 8místný kód. Opiš ho
  do dialogu, nebo nech prohlížeč otevřít Control Center přes odkaz
  `control-center://` a opisování přeskoč

Kontrolní bod: řádek **GitHub** ukazuje „Přihlášeno jako _tvoje-uživatelské-jméno_.“.

Kód nebo odkaz, který dialog sám nezahájil, odmítne hláškou **Přihlášení nebylo
zahájeno zde**. Když ti někdo pošle odkaz na přihlášení, nepokračuj: jeho
dokončením bys připojil svůj účet k jeho serveru.

Přihlášení odebereš kliknutím na **Odpojit**. Odhlášení z GitHubu nebo
odebrání z pracovního prostoru navíc zruší všechny tokeny, které server vydal
tvým jménem.

## Za koho tvé pověření mluví

- **Všechno, co děláš ty** (otevření stránky PR, odeslání revize, schválení,
  sloučení), běží na **tvém** přihlášení a na ničem jiném. Když přihlášený
  nejsi, aplikace to řekne a vyzve tě k přihlášení. Žádné jiné pověření tě
  nezastoupí
- **Práce, u které nikdo nepíše** (běhy agentů, pipelines, dotazování na PR,
  odpovědi bota, klony), dostane token pro jeden repozitář, vydaný z GitHub App
  serveru nebo přes Connect. Je omezený na to, co tam smí odpovědný člen: člen,
  který požádal, jinak vlastník pracovního prostoru. Člen, který nesmí
  pushovat, omezí token na čtení
- **Automatizace pull request nikdy neschválí.** Schválení je čin člověka

## Co ti integrace dá

| Funkce                  | Jak                                                                                                      |
| ----------------------- | -------------------------------------------------------------------------------------------------------- |
| Seznam a detail PR      | GitHub REST API, ze serveru, na tvém vlastním přihlášení                                                 |
| Běhy kontrol            | GitHub Checks API                                                                                        |
| Publikování revize      | Krok vázaný na uživatele, který odešle tvoji revizi do PR, tvým jménem                                   |
| Registrace repozitáře   | Checkout se přijme, když remote `origin` míří na github.com, nebo na gitlab.com / bitbucket.org          |
| Přístup agenta ke GitHubu | Token pro jediný repozitář běhu jako `GH_TOKEN` / `GITHUB_TOKEN`; push jde přes Control Center        |
| Upozornění              | Dotazování na doručenou poštu oznámení GitHubu na serveru vyvolá „Zmíněn v pull requestu“ a „Vyžádána kontrola“ |
| Profily uživatelů       | Karty profilu při najetí a filtrování PR podle autora                                                    |

Některé cesty použijí GraphQL API místo REST tam, kde je to levnější: aktivita
větví pro výběr při sestavování PR a živý stav revize, podle kterého se pozná,
jestli oznámení „Vyžádána kontrola“ pořád čeká.

## Sleduj výpadky GitHubu

V záhlaví se objeví stavový čip, když některý poskytovatel hlásí problémy.
Týká se GitHubu, Claude, OpenAI a Kimi. **Dokud je všechno v pořádku, je
schovaný.** Jeho přítomnost znamená potíž.

Klikni na čip a otevře se panel **Stav služeb** se stavem každého poskytovatele
a tlačítkem **Obnovit**. Stavy se samy obnoví každé dvě minuty.

## Jak agenti na GitHubu jednají

- Agent, který pracuje ve worktree GitHubu, dostane token pro tento jediný
  repozitář. Umí číst kód a komentovat pull requesty, když odpovědný člen smí
  pushovat, a jen číst, když nesmí. Push jde přes Control Center, které se zeptá pravidla **Odeslat na
  remote** a pak ho předá se zapisovacím tokenem, který agent nikdy nedrží. Viz
  [Nastavte politiky sandboxu](/cs-CZ/prirucka/navody/politiky-sandboxu/)
- Commity agenta vždy používají Git identitu žadatele jako autora i committera. Ve výchozím nastavení trailer `Co-Authored-By: Control Center <hi@usectrl.dev>` připisuje spoluautorství účtu GitHub `@usectrl`. V **Nastavení → Vy → Připisování autorství commitů** můžeš toto spoluautorství vypnout, aniž by se změnila tvoje identita. Nastavení pracovního prostoru v **Nastavení → Pracovní prostor → Obecné** má přednost a zamkne osobní přepínač. Vlastní atribuce Claude Code je vždy vypnutá. Podepisování commitů stále vyžaduje vlastní platnou konfiguraci
- Terminál, který otevřeš na stanici, dostane tvoje vlastní přihlášení zúžené
  na ten jeden repozitář, takže pushe odtamtud jsou tvoje
- Když se token vydat nedá (nikdo odpovědný není přihlášený, aplikace není
  nainstalovaná u vlastníka, nebo je instalace pozastavená), běh nastartuje bez
  něj a jeho poznámky uvedou proč. Žádné záložní pověření neexistuje

## Řešení potíží

### Seznam PR je prázdný a hlásí, že GitHub není připojený

Na tomhle serveru nejsi přihlášený ke GitHubu. Klikni na **Přihlásit se k
GitHub** v **Hostování kódu**. Repozitáře na jiných forge to nezasáhne.

### Řádek GitHub hlásí, že přihlášení na tomto serveru není nastavené

Server nemá vlastní GitHub App ani Connect. Jedno z nich vybere vlastník
serveru v **Nastavení → Server → Jednotné přihlášení**: **Vytvořit moji
aplikaci GitHub** zabere asi dvě minuty. Viz
[Vytvořte GitHub App](/cs-CZ/prirucka/navody/github-app/).

### Dialog hlásí, že kód nesedí

Opiš kód přesně tak, jak ho ukazuje prohlížeč: 8 písmen a číslic. Pět
chybných kódů přihlášení ukončí; začni znovu.

### Přihlášení hlásí, že aplikace není nainstalovaná

GitHub App nemá instalaci na účtu, který repozitář vlastní. Admin pracovního
prostoru ji nainstaluje z **Nastavení → Pracovní prostor → Obecné → Instalace
aplikace GitHub**. U organizace na sdílené App od Control Center může být
potřeba, aby admin té organizace klikl na **Autorizovat tento server**. Viz
[Vytvořte GitHub App](/cs-CZ/prirucka/navody/github-app/#autorizuj-tento-server-pro-organizaci).

### Všichni se musí ke GitHubu přihlásit znovu

Vlastník serveru vyměnil klíč Connect serveru, přešel na jiný server Connect,
nebo se datový adresář obnovil na jiný stroj. Přihlášení přes Connect jsou
vázaná na server, který je vytvořil.

### Přidání repozitáře se odmítne

Registrace vyžaduje všechny tři podmínky: cesta leží uvnitř git work tree, má
remote `origin` a ten remote míří na podporovanou forge (github.com,
gitlab.com nebo bitbucket.org). Viz
[Přidejte repozitáře do pracovního prostoru](/cs-CZ/prirucka/navody/pridani-repozitaru/).

### Po velké zátěži na chvíli přestane fungovat všechno

To je jistič limitu požadavků. GitHub oznamuje primární limit kódem `403`
s hlavičkou `x-ratelimit-remaining: 0` a časem obnovení. Jakmile takovou
odpověď uvidí, klient další požadavky odmítne lokálně, bez volání po síti,
dokud okno nevyprší, aby opakované pokusy limit ještě neprohloubily. Přechodné
chyby se zkusí znovu nejvýš třikrát, s exponenciální prodlevou, a drží se
`retry-after`.
