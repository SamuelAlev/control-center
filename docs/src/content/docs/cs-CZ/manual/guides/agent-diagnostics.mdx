Tenhle návod ukáže, jak zjistit, proč agent nevytváří běhy.

Postupuj shora: nejdřív vlastní běhy agenta, potom jeho backend, potom server a nakonec hostitel.

## 1. Zkontroluj historii běhů agenta

**Nastavení → Pracovní prostor → Agenti** → vyber agenta → **Protokoly**.

Každý běh ukazuje odznak stavu, dobu trvání („Running…“, dokud běží), čas začátku a dokončení, PID a adaptér, který použil. **Zobrazit** otevře surový proud událostí toho běhu. **Zastavit** ukončí běžící proces a označí běh „Killed by user“; **Ukončit běžící** v záhlaví udělá totéž pro každý právě probíhající běh toho agenta.

Čti to takhle:

- **Žádné běhy** — k odeslání vůbec nedošlo. Zmínky v composeru jsou `@` a znaky slova (písmena, číslice, podtržítko). Rozlišení je přesná shoda, nebo shoda podle předpony jména agenta, takže `@code-reviewer` se parsuje jako `code` a pořád může probudit agenta jménem `code-reviewer`. Jméno s mezerou jako jeden token zmínit nejde. Pak pokračuj krokem 2.
- **Běh, který hned skončil chybou** — otevři **Zobrazit**. Selhání spuštění backendu se tu ukáže jako chyba procesu.
- **Běh zaseknutý na „Running…“** — zastav ho a pak zkontroluj **Časový limit ticha (minuty)** agenta na kartě Nastavení. Nenastavený limit použije výchozí hodnotu daného režimu.
- **Dokončený běh bez užitečného výstupu** — stav v záznamu běhu zůstane `completed` i u běhu, který skončil bez deklarovaného výstupu; poctivý signál je text shrnutí, ne odznak.

Karta Protokoly náklady neukazuje. Najdeš je v tabulce po agentech v **Observabilita → Přehledy**.

## 2. Zkontroluj backend agenta

**Nastavení → Server → Poskytovatelé modelů** (`/settings/server/providers`).

Seznam **Zjištění runneři** ukazuje každý adaptér s výsledkem sondy — nainstalovanou verzi, „Kontrola…“, nebo „Nenalezeno“ — plus vyřešenou cestu a štítky schopností u nalezeného CLI. Sonda se znovu spustí stisknutím **Obnovit** v záhlaví stránky.

Sonda běží na stroji, který hostí `cc_server`, ne na stroji, na který se díváš. Když jsi na webovém klientovi nebo na spárovaném zařízení, „Nenalezeno“ znamená, že CLI na hostiteli serveru chybí.

Ověř dvě věci:

- **Agent má vůbec nastavený adaptér.** Agent s prázdným adaptérem se odešle na **Control Center (built-in)** a záznam běhu zapíše `cc-harness`, takže v přepisu je vidět, co běželo. Když chybí i model, požádá Anthropic o výchozí — a to selže s `No credential for provider "anthropic"`, dokud nepřipojíš účet Anthropic. Založení specialisté se dodávají bez adaptéru.
- **Vestavěný adaptér má model.** Seznam modelů bere živě od poskytovatelů připojených níž na téže stránce, takže poskytovatel bez uložených přihlašovacích údajů nepřidá žádný model.

Katalog adaptérů je pevný — nový adaptér zaregistrovat nejde. U každého adaptéru tady změníš argumenty spuštění a proměnné prostředí. Přepsání prostředí u adaptéru při řešení přihlašovacích údajů potichu přebije připojený účet poskytovatele.

## 3. Zkontroluj server

**Nastavení → Server → Připojení a stav** (`/settings/server/connection`) ukazuje, se kterým serverem tenhle klient mluví a co server hlásí.

U headless serveru je `GET /healthz` totéž bez klienta. Je bez ověření a CORS má záměrně otevřené:

```
curl http://localhost:9030/healthz
```

Vrátí stav serveru, dobu provozu v sekundách, počet živých spojení, navázaný port, verzi sestavení a git SHA, verzi schématu pracovního prostoru, verzi katalogu RPC, id serveru, jméno a otisk identity, jestli je navázání nezabezpečené, a blok `codeGraph` s počty `watching` / `indexing` / `pending`. Když už nějaká cache viděla provoz, přibude i blok `caches`; demo server přidá `demo: true`.

Dvě věci, které se hodí vědět, když změna „funguje v testech, ale v aplikaci ne“:

- Aplikace na počítači spouští přednostně **předem sestavený** binární soubor `cc_server`, ne zdrojáky. Nová RPC operace ani nástroj MCP se neobjeví, dokud se binárka znovu nesestaví, a při startu se zapíše varování, když se git SHA potomka liší od SHA aplikace.
- Aplikace na počítači ukončí spuštěný server, který do 20 sekund nevypíše banner připravenosti, a přejde na chybovou obrazovku.

## 4. Zkontroluj hostitele

**Nastavení → Server → Diagnostika a soukromí** (`/settings/server/diagnostics`) je stránka na úrovni hostitele. Obsahuje:

- **Sandboxing** — hlavní přepínač, zjištěný backend, nápovědu k instalaci a výchozí přepínače schopností. Ze serveru pochází jen zjištěný backend; viz upozornění níž. Ovládání pro reset tu není.
- **Sémantické vyhledávání** — životní cyklus embeddingového modelu na zařízení: nainstalovaný, stahuje se a ukazuje procenta, není nainstalovaný, nebo chyba instalace. Dokud není nainstalovaný, paměť i hledání v kódu zůstávají jen na klíčových slovech.
- **Chování systému** — udržet počítač vzhůru, dokud agenti běží.
- **Synchronizační engine** — nouzové vypínače po úložištích pro tickety, zprávy a poznámky. Jsou to nouzové úniky zpátky k odběrům celého snímku; změna se týká jen nových odběrů, takže naplno zabere až po opětovném načtení.
- **Úroveň protokolu** — zvedni ji, než selhání zopakuješ.
- **Soukromí** — jestli se surový obsah diffu smí předat modelu agenta a jestli se posílají hlášení o pádech.

:::caution[Tahle sekce hlásí hostitele a její ovládání je na straně klienta]
Detekce a vynucení se teď shodují: kde detektor hlásí nativní backend, běhy agentů na tom hostiteli jsou jím opravdu obalené. V téhle sekci je ale živá jen detekce. Hlavní přepínač, výběr backendu a výchozí přepínače schopností jsou preference uložené na tvém zařízení a server žádnou z nich nečte — vlastní přepínač serveru je `--sandbox` (výchozí `on`, `off` pro vypnutí) a u agenta ponechaného na „Použít výchozí pracovního prostoru“ server spadne na konzervativní výchozí stav: žádný git push, žádné GitHub API, žádný klíč k ticketům, síť zapnutá.

Varování tady stojí za reakci, ale obvykle to není důvod, proč agent selhává. V jakém stavu server je, ověříš ve startovacím logu: vypíše `agent sandbox ON` s poznámkou o backendu, `no OS-native agent sandbox on this host` s nápovědou k instalaci, nebo `agent sandbox DISABLED by --sandbox off`. `GET /healthz` pole sandboxu nenese.

Kde backend není — na Windows vždy, na Linuxu nebo ve WSL2 bez `bwrap` a `socat` — běhy **nejsou** v sandboxu a ohraničuje je vlastní checkout konverzace, schopnosti, které rozhodují, jaké přihlašovací údaje se do něj vystaví, guardraily akcí, sanitizace prostředí a plocha nástrojů, kterou jeho režim povolí.
:::

## Častá selhání

### Běh se nikdy nespustí a adaptér ukazuje „Nenalezeno“

Nainstaluj CLI **na hostitele serveru** a pak na stránce Poskytovatelé modelů stiskni **Obnovit**. Nebo přepni agenta na vestavěný adaptér, který CLI nepotřebuje, a na téže stránce připoj poskytovatele.

### Agent nemůže pushnout ani otevřít pull request

Bránou jsou jeho schopnosti. Otevři **Nastavení → Pracovní prostor → Agenti** → agent → **Oprávnění sandboxu**, zapni přepínač a povol **Povolit git push** a **Povolit volání GitHub API**. Necháš-li přepínač na „Použít výchozí pracovního prostoru“, agent nedostane nic z toho.

### Sémantické vyhledávání nevrací nic užitečného

Zkontroluj **Nastavení → Server → Diagnostika a soukromí → Sémantické vyhledávání**. Dokud není embeddingový model nainstalovaný, hledání je jen podle klíčových slov. Řádky zapsané před instalací modelu se nikdy nedoplní zpětně, takže i potom zůstávají jen na klíčových slovech.

### Server se vůbec nespustí

Nativní knihovny jsou povinné a degradovaný režim není. Chybějící dylib způsobí, že `cc_server` odmítne naběhnout a v chybě jmenuje viníka. Nativní knihovny připrav skriptem `scripts/natives/build_natives.sh` a binárku serveru sestav znovu.

### Akce se potichu zamítne

Rozhodnutí guardrailu `prompt` bez připojeného schvalovatele se zamítne, a to záměrně. Pravidla pracovního prostoru jsou v **Nastavení → Pracovní prostor → Oprávnění agentů**.
