Tenhle návod ukazuje, jak pull request zkontrolovat a sloučit.

## Otevři pracovní plochu PR

1. V postranním panelu přejdi na **Pull requesty**
2. Vyber PR ze seznamu

PR se otevře jako pracovní plocha se záložkami, ne jako jedna stránka. Ve
výchozím stavu je jich pět, v tomhle pořadí: **Přehled**, **Diff**, **Správa
zdrojového kódu**, **Chat** a **Akce** (kontroly CI seskupené podle workflow).
**Kontrola** — nejdřív průběh pipeline kontroly, potom artefakt, který
zveřejnila, s lištou zjištění — mezi nimi schválně není. PR kontrolu nemá, dokud
o ni někdo nepožádá, takže ji otevře **Zeptat se AI**. Terminál, editor jednoho
souboru, vložený code-server a prohlížeč v aplikaci se otevírají na vyžádání.
Záložky náhledu nasazení se přidají samy, jakmile se na PR najde URL náhledu.
Rozložení záložek se pamatuje pro každý PR zvlášť.

Vložený code-server se nabízí jen vlastníkovi serveru, protože běží na serveru jako uživatel serveru. Relace patří zařízení a osobě, které ji otevřely, otevírá se s důvěrou pracovního prostoru ve VS Code zapnutou (VS Code se zeptá, než složce důvěří) a žádný úkol nespouští automaticky. Všichni ostatní zůstávají u editoru jednoho souboru a pohledů na soubory.

Záložka Přehled nese metadata PR (autor, větev, štítky, přiřazení, reakce,
commity, stav kontrol) a řádek akcí: obnovení, **Kontrola**, **Sloučit**,
tlačítko pojmenované podle tvého editoru (například **Otevřít v VS Code**) a rozbalovací nabídka ⋯.

Tlačítko editoru spustí nativní editor na **vlastní obrazovce serveru**, jako uživatel serveru a mimo jakýkoli sandbox, takže je nabízeno jen [vlastníkovi serveru](/cs-CZ/prirucka/koncepty/autorizace/#vlastník-serveru). Na ploše, která hostuje vlastní server, je to člověk u stolu. Totéž platí pro otevření worktree konverzace v editoru. Všichni ostatní používají vestavěné pohledy editoru. I pro vlastníka se PR otevře jen z repozitáře propojeného s pracovním prostorem.

### Otevři PR ze zásobníku prostoru

Sekce **Obecné → Pull requesty** prostoru seskupuje propojené PR a PR spárované
podle větve, a to podle repozitáře. Když je základní větev jednoho PR head větví
předchozího PR, objeví se v rozbalovacím zásobníku. Hlavička určuje spodní PR,
cílovou větev a počet; číslované řádky jdou od spodního PR (1) k vrcholu. Čísla
popisují pořadí závislostí, ne připravenost ke sloučení.

Každý řádek ukazuje název, číslo PR a stav. Najeď na řádek nebo ho zaměř a
přečteš si celý název a názvy větví; kliknutím nebo stiskem Enter otevřeš
pracovní plochu PR. Zaměř hlavičku zásobníku a stiskem Enter nebo mezerníku ji
sbalíš nebo rozbalíš. Nesouvisející PR zůstávají zvlášť a neúplné nebo
nejednoznačné vazby mezi větvemi se jako seřazený zásobník nezobrazují.

V hlavičce PR otevře odznak zásobníku (ikona vrstev s počtem pull requestů v zásobníku) **Skládané pull requesty**, výběr publikovaných částí zásobníku, od spodní části nahoru. Každá položka
ukazuje číslo PR, název části a pozici; přepnutá část je označená. Vyber položku
a otevře se pracovní plocha jejího PR. **Publikovat sadu** se objeví, jen když
doběhlo vyhledávání PR a aspoň jedna část zatím žádný PR nemá. Platí to i pro
nabídku větve. PR vytvořené mimo Control Center se taky počítají jako
publikované. Částečně publikované zásobníky nabízejí obě akce; práce v jedné
větvi si nechává samostatné akce pro vytvoření a zobrazení PR.

### Commit a push ze Správy zdrojového kódu

Commit, který uděláš v panelu **Správa zdrojového kódu**, je tvůj: autorem i committerem jsi ty, pod adresou, kterou tvůj forge ověřil pro tvoje přihlášení. Když jsi v **Nastavení** → **Vy** → **Commity** pod **Ověřené commity** vytvořil podpisový klíč, server ho před odesláním podepíše tvým vlastním podpisovým klíčem. Push nese tvoje vlastní přihlášení, zúžené na tento jediný repozitář.

Server spouští Git na svém vlastním stroji, ve stromu, který může změnit agent nebo pull request, takže nespouští žádné programy, které si repozitář může vybrat:

- Commity přeskakují Git hooky repozitáře, stejně jako to dělá `git commit --no-verify`. Pre-commit hook, commit-msg hook ani pre-push hook se nespustí
- Credential helpery, editory, externí diff nástroje a podepisovací programy, které repozitář nastavuje, se ignorují

Spusť si kontroly sám před commitem, nebo je nech běžet v CI.

Změna kódu vyžaduje [zápisové přidělení](/cs-CZ/prirucka/koncepty/autorizace/#změna-kódu-vyžaduje-zápisové-přidělení) k repozitáři: ukládání nebo vracení souborů v editoru, **Stáhnout nejnovější commity PR**, commitování a pushování, publikování větve a akce skládaných pull requestů, které část vytvoří, přepnou na ni nebo ji publikují. S pouhým čtecím nebo review přístupem vidíš soubory a diffy, a tyto akce odpoví „Tento repozitář můžete číst, ale nemůžete ho měnit. Správce pracovního prostoru vám může udělit přístup pro zápis.“

**Stáhnout nejnovější commity PR** přivede worktree kontroly k nejnovějším commitům pull requestu. Stahuje s tvým vlastním přihlášením ke GitHubu a když žádné nemáš, požádá tě o přihlášení. Nejdřív commitni nebo zahoď své změny: worktree s necommitnutými změnami se nesynchronizuje.

## Přečti diff

Otevři záložku **Diff**. Uvidíš celý diff PR najednou a strom souborů, kterým
mezi nimi přecházíš.

- Tlačítko nastavení v liště diffu přepíná **Rozdělený** (vedle sebe)
  a **Jednotný** a přepíná **Zalamovat řádky** a **Ligatury písma kódu**.
- Místo hlaviček hunků `@@` se nabízejí prvky **Show N lines** / **Show end of
  file**, které po kliknutí doplní okolní kontext.
- `j` / `k` přechází mezi soubory, `c` sbalí nebo rozbalí aktivní soubor, `t`
  vrátí postranní panel na strom souborů a `⌘F` hledá v celém diffu (`Enter` /
  `Shift+Enter` prochází shody).
- `v` označí aktivní soubor jako prohlédnutý a kurzor postoupí na další soubor.
  Na GitHubu se stav prohlédnutí ukládá na forge, takže tě doprovází mezi
  klienty. GitLab a Bitbucket takové API nemají, takže se tam pamatuje jen na
  tomhle zařízení.

Tažením myší v oblasti kódu vybereš text až po konkrétní sloupec a `⌘C`
zkopíruje surový zdroj, ne vykreslené značky diffu.

## Nech řádkové komentáře

1. Klepnutím na okraj řádku kódu otevřeš editor ukotvený k tomu řádku, nebo
   použij tlačítko `+` v hlavičce souboru pro komentář k celému souboru
2. Napiš zpětnou vazbu v Markdownu
3. Odešli

Na GitHubu a GitLabu má editor dvě odeslání: **Přidat jeden komentář** odejde
hned a **Zahájit kontrolu** / **Přidat ke kontrole** zařadí komentář do čekající
kontroly, která odchází s **Schválit**, **Vyžádat změny** nebo **Komentář**.
Bitbucket dávkování čekající kontroly nemá, takže tam každé odeslání odchází
hned. Okamžité odeslání se ukáže jako čekající, dokud ho forge nepotvrdí, a pak
se přepne na synchronizováno. Když odeslání selže, vlákno se označí chybou
a nabídne **Zopakovat**.

Koncept je jen _tělo_ kontroly. Uloží se na serveru podle (vlastník, repozitář,
číslo PR) chvíli poté, co přestaneš psát, takže přežije obnovení a jde s tebou
mezi klientem na počítači a webovým.

## Odešli kontrolu

1. Stiskni **Kontrola** v řádku akcí na Přehledu (na vlastních PR a na zavřeném
   nebo sloučeném PR je skrytá)
2. Napiš tělo kontroly. Můžeš přiložit obrázek, vložit emoji nebo GIF
   a přepínat mezi **Psát** a **Náhled**
3. Stiskni **Vyžádat změny**, **Komentář** nebo **Schválit**

Verdikt _je_ to tlačítko, bez samostatného výběru. Po **Schválit** nebo
**Vyžádat změny** se tlačítko přejmenuje na **Schváleno** nebo **Vyžádané
změny** a koncept těla se smaže. Verdikt **Komentář** nechá tlačítko s popiskem
**Kontrola**.

:::caution[Odeslání je nevratné]
`pr_review.submitReview` zveřejní kontrolu na forge a do zásobníku vrácení zpět
se nikdy nedostane. Z Control Center odeslání nejde vzít zpět.
:::

## Sloučení

Tlačítko **Sloučit** se ukáže, když máš právo zápisu a PR je otevřený a není
koncept. Barva je signál připravenosti z požadovaných schválení a stavu kontrol
(připraveno / čeká / blokováno) a jen radí. Stav kontroly tlačítko nikdy
nevypne. Pravidla vynucuje ochrana větve na forge.

1. Stiskni **Sloučit**. Otevře se panel sloučení
2. Vyber způsob sloučení: **Squash a sloučení**, **Vytvořit merge commit** nebo
   **Rebase a sloučení** (**Squash a sloučení** je výchozí). Bitbucket skutečné
   sloučení rebase nemá, takže **Rebase a sloučení** odpovídá jeho strategii
   fast-forward a selže, když se větev rozešla
3. U **Squash a sloučení** a **Vytvořit merge commit** uprav předvyplněný
   **Název commitu** a **Popis commitu**. **Rebase a sloučení** nebere ani jedno
   a obě pole skryje
4. Přečti panel upozornění. Jmenuje **Kontroly selhávají** a **Některé kontroly
   čekají**, ale nezastaví tě
5. Potvrď tlačítkem **Sloučit pull request** v panelu

Sloučení je nevratné: posílá commity na forge, takže má krok potvrzení místo
položky pro vrácení zpět. Potom se mezipaměť PR zneplatní, stav se přepne na
**Sloučeno** a vystřelí událost `PullRequestStatusChanged` se stavem `merged`.
Ta událost uvolní dočasný worktree, který otevřelo tlačítko editoru, a spustí dvě
předpřipravené pipeline: **Stale repository cleanup**, která smaže zastaralé
worktree a složky konverzací toho PR, a **Release notes**, která sepíše položku
changelogu.

:::note[Prostor kontroly PR se nearchivuje sám]
Automatická archivace konverzací prostoru kontroly je navázaná na samostatnou
doménovou událost `PrMerged`, kterou v produktu teď nic nevysílá, takže prostor
po sloučení zůstane, jak jsi ho nechal. Denní úklid jeho worktree pořád uvolní.
Když ho chceš z postranního panelu pryč, smaž prostor sám.
:::

## Předej PR review agentům

Rozbalovací nabídka ⋯ na záložce Přehled má **Zeptat se AI**. Spustí
předpřipravenou pipeline `pr_review` pro tenhle PR. Položka se ukáže, jen dokud
je PR otevřený. Co pipeline dělá a jak zveřejnit zjištění, je v
[Používejte AI kontrolu](/cs-CZ/prirucka/navody/ai-kontrola/). Deterministický
model kohort a os je ve
[Výpočet kontroly](/cs-CZ/prirucka/navody/vypocet-kontroly/).

## Zkontroluj externí PR

Control Center si bere i PR, které lidé otevřeli mimo aplikaci. Postup kontroly
nahoře je stejný. Externí PR odhaluje služba, která pull requesty pravidelně
dotazuje.

## Řešení problémů

### Můj pre-commit hook se nespustil

Commity vytvořené v panelu **Správa zdrojového kódu** v aplikaci přeskakují Git hooky repozitáře, stejně jako to dělá `git commit --no-verify`. Server spouští Git na svém vlastním stroji, ve stromu, který mohou změnit agenti a pull requesty, takže nikdy nespustí program, který si repozitář vybere. Spusť kontroly hooku sám, nebo se spolehni na CI.
