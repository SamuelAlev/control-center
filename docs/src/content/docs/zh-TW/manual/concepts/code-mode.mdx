代理通常一次只呼叫一個工具。每次呼叫都是一個模型回合：代理要求呼叫，結果回到其情境中，代理讀過後才會要求下一次呼叫。對於大多屬於機械性的工作，例如讀取二十個檔案以找出真正重要的三個，或檢查每一張開放中的工單是否帶有某個標籤，這些回合和大部分情境，都花在代理隨即丟棄的結果上。

程式碼模式只有一個工具：`repl`。有了它，代理可以撰寫一段簡短的 JavaScript 指令碼來呼叫其他工具、迴圈、篩選並合併它們的結果，最後只回傳它需要的部分。一次 `repl` 呼叫就能完成數十個工具回合的工作，而進入情境的只有指令碼的答案。

只要伺服器能執行指令碼，每次執行都會有 `repl`。無需開啟任何設定：參閱[當執行具有 `repl` 時](#當執行具有-repl-時)。

## 指令碼能做什麼

指令碼是純 JavaScript，寫成一個 async 函式的主體，因此 `await` 和 `return` 可以直接用在最上層。每次 `repl` 呼叫都會啟動一個全新、空白的直譯器。

- **呼叫工具。** `await tools.read({ path: "README.md" })` 會呼叫一個工具，並解析為其結果；若呼叫失敗或被拒絕，則以錯誤拒絕。獨立的呼叫可以透過 `Promise.allSettled` 一起執行。
- **尋找工具。** `ALL_TOOLS` 列出指令碼可以呼叫的每一個工具。`searchTools(query)` 依工具的用途找到工具，`describeTool(name)` 回傳一個工具的描述與引數，而 `describeNamespace(name)` 則列出某一群組的工具。已連接的 MCP 伺服器工具也能以同樣方式取得。
- **回傳結果。** 只有指令碼回傳的內容，或傳給 `text()`、`image()` 或 `console.log()` 的內容，才會回到代理那裡。最多會有四張圖片送達模型。
- **保存值。** `store(key, value)` 與 `load(key)` 會在同一個對話與代理的指令碼之間保存小型 JSON 值。值只在指令碼完成時才會存下。子代理沒有儲存空間。
- **詢問人員。** `await tools.ask_user({ question, options })` 會提出問題並等待回答。
- **使用裝置端嵌入。** 當伺服器已安裝嵌入模型時，`models.embed`、`models.rank` 與 `models.classify` 會使用它。
- **等待。** `sleep(ms)` 與 `setTimeout`，須在指令碼的時間限制內。`limits()` 會回傳指令碼執行時套用的限制。

指令碼沒有檔案系統、網路、處理程序、模組或環境存取權：不能使用 `fetch`、`require`、`import` 或 `process`。唯一的出口是工具呼叫，而且每一次工具呼叫都會經過與代理直接呼叫時相同的檢查。

指令碼之後失敗時，它已經做過的工具呼叫不會被復原。

## 代理直接呼叫哪些工具

內建代理的每次執行都會取得同一小組、代理以名稱呼叫的工具：

- `repl`，排第一；
- 檔案與 shell 工具 `read`、`write`、`edit`、`search`、`find`、`bash` 與 `read_output`；
- `ask_user` 與 `task`；
- `todo_write`、`search_memory` 與 `send_message`；
- 對話的[模式](/zh-TW/手冊/概念/模式/)為交出其輸出或離開模式所需的動詞，例如計畫模式中的 `submit_plan`；
- `search_tools`，在某個工具會於首次使用時載入時（見下文）。

本次執行可能使用的其他每一個工具，都可以用兩種方式之一觸及：

- **只能由指令碼呼叫**，適用於指令碼可以呼叫的工具。代理可用 `searchTools()` 或 `describeTool()` 找到它，並以 `tools.<name>(args)` 的形式呼叫。它的描述永遠不會送到模型，因此不佔用提示的任何成本。若代理仍直接呼叫其中一個，回覆會告訴它改由指令碼呼叫該工具。若伺服器無法執行該次執行的指令碼，此工具會改為在首次使用時載入（參閱[無法執行指令碼時](#無法執行指令碼時)）。
- **首次使用時載入**，適用於指令碼不可呼叫的工具。代理只會看到它的名稱；以名稱呼叫它，或以 `search_tools` 找到它，就會將它載入。

有些工具永遠無法由指令碼呼叫，其中包括 `repl` 本身（指令碼不能啟動指令碼）、`eval`、`task`、`checkpoint`、`rewind`、`vibe_*` 動詞，以及會啟動或傳訊給其他代理執行、建立、決定或留言於核准、變更政策或技能、或離開計畫模式的工具。代理會直接呼叫這些工具。

沒有 `repl` 的執行會取得同樣的直接工具，其餘一切則在首次使用時載入。[工具情境與提示快取](/zh-TW/手冊/概念/工具情境/)說明為何無論哪種情況，這組工具都相同。

程式碼模式絕不會新增對話的模式所不允許的工具。模式的工具篩選會先套用，指令碼只能呼叫剩下的工具。

## 當執行具有 `repl` 時

當伺服器的指令碼執行器在啟動時通過其鎖定檢查（[指令碼如何被限縮](#指令碼如何被限縮)），執行便會具有 `repl`。沒有任何工作區、代理或伺服器設定能改變這一點。下列情況下，執行仍然沒有 `repl`：

- 執行器無法在伺服器的機器上將自己鎖定；此時伺服器完全不執行任何指令碼；
- 伺服器是公開示範，不執行任何指令碼；
- 該執行不屬於任何工作區；
- 無法讀取工作區的限制，因為改用預設值執行，可能會超出管理員調低的限制；
- 無法寫入該次執行的紀錄，因為每個指令碼都會在啟動前記錄於其執行之下。

這樣的執行會直接呼叫其所有工具。

程式碼模式適用於內建代理的執行，以及透過 Control Center 的 MCP 端點取得其工具的代理，例如 Claude Code。對於 MCP 代理，它收到的工具清單包含 `repl`、直接工具，以及指令碼不可呼叫的工具；其餘工具則透過指令碼呼叫。只有由 Control Center 啟動並保留紀錄的執行，才會在那裡取得 `repl`；其他任何用戶端都會收到除 `repl` 之外的所有工具。

**設定 → 工作區 → 程式碼模式**的**狀態**區塊會顯示此伺服器是否執行指令碼（**可用**或**無法使用**，並附上伺服器給出的原因），以及已安裝的**執行器**版本。**檢視程式碼執行紀錄**會開啟已執行指令碼的清單。

伺服器擁有者無法關閉指令碼。擁有者可以為其設定上限：同時執行的數量，以及一個指令碼可使用的記憶體量（參閱[限制](#限制)）。

### 無法執行指令碼時

伺服器無法執行指令碼，絕不會讓某次執行失去任何工具。當伺服器因任何其他指令碼同樣無法避免的原因拒絕某個指令碼時（例如指令碼無法使用、該指令碼已等待其時限的一半以等候空位、其紀錄無法寫入、該次執行的工具清單太大而無法交給指令碼，或執行器無法啟動或無法將自己鎖定），該次執行直到結束前都停止使用指令碼：

- 某次內建代理的執行會保留 `repl`，而所有原本只能由指令碼觸及的工具，現在都改為在首次使用時載入：代理可以依名稱呼叫它，或以 `search_tools` 找到它；
- MCP 端點上的執行會收到一份包含所有工具且不含 `repl` 的工具清單，其用戶端會被告知清單已變更。伺服器會記住最近 1,024 次這類執行；更早的執行則會回到使用指令碼。

這些工具會通過與先前相同的模式篩選、護欄與核准，因此不會讓任何原本不可呼叫的工具變得可呼叫。指令碼因自身原因失敗（例如拋出錯誤、達到某項限制，或某次呼叫被拒絕）時，不會改變任何狀況，執行仍繼續使用指令碼。

伺服器也會持續檢查指令碼是否能夠執行。當執行器因非指令碼本身的原因而無法啟動時，伺服器會重新執行其鎖定檢查，頻率最多每分鐘一次。若檢查失敗，伺服器便不執行任何指令碼，並記錄與啟動時相同的 `code_mode=unavailable` 行；期間啟動的執行不會取得 `repl`。它會持續檢查，同樣最多每分鐘一次；當某次檢查通過時，它會再次執行指令碼，並記錄 `code_mode=available` 行。只有啟動時就失敗的檢查才需要重新啟動伺服器。

## 限制

每個指令碼都在限制之下執行。工作區管理員可在 **設定 → 工作區 → 程式碼模式** 中的 **限制** 下變更其中六項（按 **調整限制**）；代理可以為單一指令碼要求更短的時間或更小的輸出預算，但絕不能要求更多。

| 限制 | 預設 | 範圍 | 用完時 |
| --- | --- | --- | --- |
| 每個指令碼的時間 | 5 分鐘 | 1 秒至 25 分鐘 | 指令碼會被停止，並告知代理它已超時。 |
| 處理器時間 | 30 秒 | 1 秒至 2 分鐘 | 指令碼會被停止。 |
| 記憶體 | 256 MiB | 16 MiB 至 1 GiB | 指令碼會被停止。伺服器擁有者可為整台伺服器設定更低的上限。 |
| 每個指令碼的工具呼叫數 | 500 | 1 至 5,000 | 之後的呼叫會被拒絕，並告知指令碼原因。 |
| 同時呼叫數 | 8 | 1 至 32 | 超過此限制的唯讀呼叫會排隊等待。會改變狀態的呼叫則一律逐一執行。 |
| 代理讀取的輸出 | 10,000 個 token | 100 至 50,000 | 輸出會被縮短為開頭與結尾，代理可依要求讀取其餘部分。 |

指令碼花在等待人員的時間（核准或問題）不計入其時間限制。等待期間，指令碼不會啟動其他任何工具呼叫：它在等待期間發出的呼叫，會在你回答後依序開始。

部分限制是固定的：指令碼原始碼最多 256 KiB，單次工具呼叫的引數 1 MiB 與 16,384 個值，指令碼傳給會執行它的內建工具的指令 16 KiB（工具名稱計入其中），交給指令碼的單一結果 4 MiB，一個儲存值 256 KiB，而同一對話與代理所有儲存值合計 1 MiB。一次執行一次只會執行一個指令碼。

指令碼的工具查找同樣有限制：`searchTools` 的查詢最多 1,024 個字元，工具或命名空間名稱最多 256 個字元，最多傳回 50 筆結果；查找最多 200 次，且合計占用伺服器時間最多 2 秒，超過之後的查找都會失敗。同一工作區的所有指令碼共用 2 秒的查找時間，此時間以每秒返還 0.25 秒的速率補充。搜尋索引會將約一百萬個字元平均分配給每個工具，先用於其引數名稱，再用於其描述，且一律索引每個工具的名稱，因此即使在極大的目錄中，工具仍可依名稱找到。

伺服器擁有者也會限制伺服器上同時執行的指令碼數量（`--code-mode-max-processes`，預設為處理器核心數的兩倍，最多 16），以及一個指令碼可使用的記憶體（`--code-mode-max-heap-mb`）；等待人員的指令碼另計，最多為此數字的四倍。當此上限大於一時，單一工作區最多只能使用其約四分之三，因此沒有任何單一工作區能佔滿所有位置。一次執行及其子代理合計最多只能使用其工作區位置的一半（至少一個），因此它們之後的指令碼會等待，而工作區其他執行的指令碼則照常進行。參閱[`cc_server` CLI 參考](/zh-TW/手冊/參考/cc-server-cli/#程式碼模式)。

## 核准與問題

指令碼中的工具呼叫，檢查方式與直接呼叫完全相同：模式的工具篩選、[動作護欄](/zh-TW/手冊/概念/護欄/)、核准提示，以及工具本身的檢查。指令碼無法做出代理自己直接呼叫該工具也做不到的事。

當指令碼的呼叫需要核准時，核准卡片會顯示 **來自代理正在執行的指令碼**，而 **顯示指令碼** 會在對話中開啟該指令碼。為避免指令碼向你洗版大量卡片：

- 一個指令碼最多可要求核准 10 次，並最多提出 10 個問題；
- 一旦你拒絕它的某個呼叫，它之後需要核准的呼叫會被直接拒絕，不再詢問。

對於內建代理的執行，由指令碼執行的指令所引發的核准提示，例如推送（git push），同樣計入相同的上限，並在拒絕後以同樣方式停止。當子代理的指令碼同時執行時，此類提示同時計入兩個指令碼的上限，拒絕它會同時停止兩者。

在內建代理的執行中，對外部 MCP 伺服器工具的核准不會被記住：每次呼叫都會再次詢問，無論是指令碼還是代理本身發出，除非該空間的自主程度設為**自由行動**。指令碼所引發的每一次此類核准提示，都計入該指令碼最多可要求核准 10 次的上限。

若指令碼在你回答之前就結束，卡片會被撤回，之後才給出的回答不會核准任何東西。

## 在對話中

`repl` 呼叫在對話中會顯示為一列，標題是指令碼的描述。展開它會顯示指令碼與其輸出，以及指令碼進行的工具呼叫，這些呼叫會列在**工具呼叫**下，並計算其中有多少正在執行、成功、失敗、被拒絕、已取消、已排入佇列或已跳過。

### 指令碼如何呈現

工具呼叫的排列方式與指令碼的撰寫方式一致，而不是單一的長串清單。執行器會回報每一次呼叫所在的行與欄，應用程式會讀取指令碼，找出其迴圈、分支與函式：

- **迴圈**（`for`、`while`）會顯示為一個**迴圈**群組，以其第一行作為標題；傳入 `map` 或 `forEach` 等呼叫的回呼函式則顯示為**逐項**群組。當應用程式能夠分辨時，細線會分隔迴圈的每一輪。
- **同時執行的呼叫**（以 `Promise.all`、`Promise.allSettled` 或類似的組合器執行）會顯示為**平行**群組。
- **分支**（`if`/`else`、`switch`、`try`/`catch`）為每個分支各顯示一個群組，並以其條件為標題。
- 指令碼定義並呼叫的**函式**，會顯示為**函式**群組。

群組若位於另一個群組之內，會再縮排一級，最多縮排八級；更深的群組則維持在該縮排位置。

每個群組的標題會顯示其呼叫目前為止的結束狀況。在呼叫執行之前，其列會顯示工具以及指令碼中所寫的引數：

| 狀態 | 意義 |
| --- | --- |
| **已排入佇列** | 指令碼尚未執行到這次呼叫。 |
| 執行中 | 此呼叫正在執行。 |
| 已結束 | 呼叫已結束；該列會顯示其結果與花費的時間。 |
| **已跳過** | 指令碼跳過了這次呼叫，例如未被執行的 `if` 分支，或指令碼在執行到它之前就結束了。 |

寫在同一工具呼叫之引數中的呼叫，會與該呼叫在指令碼中回報於相同的位置。若應用程式無法判斷外層呼叫是否已執行，其列會不顯示狀態字詞，而不是顯示**已跳過**。

當群組的呼叫超過八次時，其中間部分會收合：前兩次與最後三次保持可見，所有仍在執行、失敗或被拒絕的呼叫也會保持可見，連同開始該輪迴圈的那次呼叫。每次按下 **再顯示 N 次呼叫** 會再展開 100 次呼叫，並列出隱藏呼叫中至多四種工具及其各自次數，最稀有者在前，例如 **再顯示 12 次呼叫** · Bash 1 · Read 11。超過 24 個字元的工具名稱在那裡會被截短。

應用程式無法在指令碼中定位的呼叫（例如由 `then` 回呼所發出的呼叫）會列在樹狀結構之後，於**指令碼中未能定位的工具呼叫**下。當應用程式無法讀取指令碼，或沒有任何呼叫說明它是從何處發出時，這些呼叫會以純列表的形式依發出順序顯示。

每一次呼叫列都會顯示呼叫引數與其結果開頭的部分，各以至多 8 KiB 為限；一個指令碼的各列合計達 256 KiB 的這類摘錄後，其後續的列只顯示工具與呼叫如何結束。指令碼結束後，**開啟紀錄** 會開啟完整紀錄；若找不到該紀錄，則改為開啟該次執行中指令碼的清單。在執行前就被拒絕的指令碼（例如同一次執行的另一個指令碼仍在執行中）沒有紀錄，也沒有連結。

## 紀錄

每個執行的指令碼都會在啟動前先記錄到其工作區，並在結束時完成紀錄。**可觀測性 → 程式碼執行紀錄** 會依最新在前列出它們，並可依結果篩選。紀錄中的 **本次執行的指令碼** 與 **此代理的指令碼** 連結，可將清單縮小到單一次執行或單一代理。一筆紀錄會顯示：

- 指令碼、其輸出與其主控台；
- 開始時間、執行時間、所用的處理器時間與尖峰記憶體，以及它是透過內建代理或外部代理執行；
- 結束方式，以白話說明（例如超時，或拋出一個未被捕捉的錯誤）；
- 每一次工具呼叫，依順序列出，附其結果、是否被允許、是否由人員核准或被拒絕、人員決定花了多久、其引數（已移除祕密，截至 8 KiB），以及其結果的大小。結果本身不會保存。

紀錄會保存每一次呼叫在指令碼中的位置，因此其工具呼叫的排列方式與對話中相同。由人員核准的呼叫在紀錄中絕不會被收合。

仍在執行的指令碼會顯示為執行中，並列出目前為止已完成的工具呼叫；其輸出、耗時與資源用量會在結束時出現。若伺服器在指令碼執行途中停止，紀錄會在伺服器重新啟動時結束，並註明此事；在紀錄關閉之前，該工作區不會執行任何指令碼。

紀錄與其執行一起保存：刪除該執行或其空間，就會一併刪除紀錄。成員可以看到他們能開啟的空間之紀錄。

## 指令碼如何被限縮

指令碼絕不會在伺服器內執行。每個指令碼都在自己的處理程序中執行，這個處理程序是隨伺服器附帶的小型程式 `cc_codemode`，它在 QuickJS-NG 引擎中執行 JavaScript。在讀取指令碼之前，該程式會以作業系統本身的控制機制自我鎖定：在 Linux 上是系統呼叫篩選與資源限制，在 macOS 上是預設拒絕的沙箱設定檔，在 Windows 上是 AppContainer 與工作物件（job object）。之後它無法開啟檔案、使用網路、啟動處理程序，或看見其他程式。它以空的環境變數啟動、不持有任何憑證；它唯一的通道是伺服器，由伺服器回應它的工具呼叫。

伺服器在啟動時會執行該程式的自我測試，以檢查鎖定是否生效。若鎖定在該機器上無法生效，例如在某個容器的安全設定檔拒絕了其中一個步驟的環境中，伺服器在那裡不執行任何指令碼：沒有任何執行會取得 `repl`，且設定頁面會顯示**無法使用**與原因。指令碼絕不會在限縮較弱的情況下執行。Windows 的鎖定尚未在 Windows 上實際執行過。

執行器會回報呼叫在指令碼中的位置，因此它僅用於排列對話與紀錄的版面。它絕不決定某次呼叫是否被允許。

關於鎖定涵蓋與不涵蓋的範圍，請參閱[沙箱與資安](/zh-TW/手冊/概念/沙箱與資安/#程式碼模式中的指令碼)。
