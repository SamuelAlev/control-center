關於程式碼的討論本來就發生在 pull request 裡。PR 對話讓它成為 Control Center
工作區上的一個介面，就像[聊天橋接](/zh-TW/手冊/概念/聊天橋接/)讓 Slack
成為這樣的介面一樣：在 PR 上 @提及 `@usectrl`
在它的審查討論串裡回覆，或加上 `ai-review`
標籤，工作就會在 PR 的審查空間中進行 — 歸屬與護欄和在應用程式裡輸入的任何內容完全相同。留言與標籤通過的是同一道關卡：看的是撰寫留言或加上標籤的那位成員。回答會回到 GitHub，回到問題被提出的那個討論串。

有三項決策塑造了這項功能，而每一項都跟聊天橋接為聊天所做的是同一個決策，只是為程式碼託管平台重新表述：**連線朝哪個方向建立**、**從外部到來的留言由什麼授予權限**，以及**雙方各自歸屬到誰名下**。

## 輪詢就是傳輸方式

GitHub 為應用程式提供的唯一推送通道是 webhook，而 webhook 需要一個傳入 URL — 這正是這個介面刻意從不要求的東西。因此探索機制是一輪掃描：每個 App 安裝都發起一次以自身為別名的搜尋，向 GitHub 查詢提及 `@usectrl` 的 PR，以及帶有審查標籤的開放 PR；已經有審查空間的 PR 會讀取其留言討論串；而所有內容都會依留言 ID 與上一輪掃描看到的結果做差分。使用自己的 App 時，每分鐘掃描一次，最多涵蓋 25 個 PR。透過 Connect 時，這些呼叫消耗的是成員自己的 GitHub 配額，因此每兩分鐘掃描一次，最多涵蓋 10 個；配額剩餘不到 15% 的工作區會被略過，直到配額恢復。Connect 本身永遠看不到 PR 內容。

這些設計帶來的後果值得點明：

- **延遲是掃描間隔，而不是事件。** 👀 確認會在一輪掃描內送達。沒有什麼緊急的事依賴它。
- **每則留言恰好處理一次。** 留言 ID 在整個 GitHub 上都是唯一的；每則留言在被判定為符合資格的那一刻就會被記錄下來，早於任何對它採取的行動。當機可能讓某則留言的處理遺失，但絕不會讓它被重複觸發。
- **離線期間的內容會被補上，而不是重播。** 已見集合會持久化，因此重新啟動後會補上停機期間到達的內容。唯一的例外是有史以來的第一輪掃描：沒有可供差分的記憶，所有待處理的內容都會被靜默記錄 — 在這台伺服器存在之前就為二十個 PR 加上標籤的操作者，不該回來面對二十個正在執行的審查。
- **標籤是集合，而不是事件。** 搜尋回報的是標籤的_存在性_，因此被加上標籤的 PR 只會觸發一次，而且僅此一次。移除標籤後再重新加上，對掃描來說是看不見的；重新執行的途徑是 @提及。

搜尋是對每個安裝帳戶、在該帳戶自己的用戶端上各執行一次，因為權杖只看得到自己這次安裝下的儲存庫 — 單一的全伺服器憑證會悄悄漏掉該 App 其他安裝下的每一個 PR。

## 授權的是成員身分，而不是留言

一則 PR 留言送達時帶著一位作者 — 在被證實之前，它就只是一個未經驗證的外部身分。伺服器會拿作者不可變的 GitHub 數字帳號 ID（絕不是登入名稱，因為登入名稱可以改名，也可能被他人重新使用），比對工作區成員的 GitHub 登入；這份對照依 TTL 重建，因為伺服器運作期間會有人登入，也會有人被邀請加入。對於 `ai-review` 標籤，解析的對象是最近一次加上它的人。

依序進行三項檢查，任何一項不通過都會靜默處理 — 什麼都不會張貼：

- **已登入的成員。** 該帳號必須屬於_本_工作區的一位成員，而且此人已在這台伺服器上登入 GitHub
- **具寫入權限的角色。** `viewer` 與 `guest` 無法啟動工作
- **推送權限。** 回覆使用一個只適用於該儲存庫的權杖，並限制在該成員對它的存取權內。如果伺服器無法簽發這樣的權杖，就不會繼續

每一項檢查都在任何確認之前執行，因此陌生人既不會得到表情回應，也不會得到回覆。留言絕不會歸屬到沒有送出它的人身上，而陌生人的話也絕不會進入他們看不見的工作區。

### 認領

開始任何工作之前的最後一步，是用作者自己的 GitHub 登入加上一個 👀 表情回應。GitHub 對新的表情回應回傳 `201`，對已存在的回傳 `200`，因此這個表情回應同時充當一把鎖：同一個人若在兩台都連結了該儲存庫的伺服器上登入，只有先加上表情回應的那台會執行工作。同一台伺服器上若有數個工作區都看到同一則留言，這則留言會提供給每一個工作區，並由同樣的認領機制決定。

## 刻意採用兩種身分

對話的每一方都帶著不同的身分，而這個差異正是這項功能的要點：

- **在 GitHub 上，回覆是代表你進行的自動化。** 每一則回覆都使用一個只適用於那一個儲存庫的權杖，並限制在提問成員的存取權內，且由該 App 的 `[bot]` 帳號撰寫。有一個例外：在共用的 Control Center Connect App 上，只有當 Connect 營運者列出了該安裝，機器人才會在審查討論串中張貼；否則，審查討論串中的回覆會由提問成員自己的帳號撰寫。無論哪種方式，每則回覆都以 `**Control Center** (for @login):` 開頭，既說明是誰提問，也兼作迴圈防護。代理回覆中的 @ 提及會被停用，因此回覆永遠不會通知任何使用者或團隊。
- **在空間裡，提問算在你頭上。** 訊息會歸屬到作者解析出的那位成員，代理執行也代表他們進行：提交歸他們所有，而空間的自主程度調節與動作護欄，也完全比照在應用程式裡輸入的訊息那樣套用。執行期間對程式碼託管平台的寫入使用以該成員為界、只適用於單一儲存庫的權杖，絕不是把他們的登入整個交出去。

把審查的發現發佈回 GitHub 仍然是人的決定，並且在 Control Center 中做出。@提及可以_啟動_一次審查；但只有人類能發佈審查。

## 迴圈防護

任何由機器人帳號撰寫的內容，都會在任何關卡執行之前被丟棄 — 包括我們自己的機器人帳號，以及所有帶 `[bot]` 後綴的帳號，這樣其他 App 的審查機器人也無法喚醒我們的機器人 — 以 `**Control Center** (for @` 前綴開頭的每一則留言也一樣會被丟棄，因為透過 Connect 的審查討論串回覆可能是由某個人的帳號撰寫的。少了這道防護，回答就會以新留言的形式送達，並永遠重新觸發橋接。

只有 `@usectrl` 會啟動工作。App 自己的登入名稱（`<slug>[bot]`）與其裸 slug 都不會指向任何東西：GitHub 不為 App 帳號提供自動補全，而裸 slug 可能屬於某個人類使用者。

## 刻意不提供的東西

- **不自動發佈。** 發現會落在審查空間裡；發佈到 GitHub 是另一個獨立的人工操作
- **不做模糊身分比對。** 作者要嘛精確解析到某一位成員，要嘛被忽略 — 沒有憑猜測的歸屬
- **不自動核准。** 自動化可以留言與要求變更，但 `APPROVE` 審查在送出前就會被拒絕。核准是人的行為
- **不使用 GitHub App webhook。** 這個介面從不註冊 webhook，因此沒有需要為 PR 留言暴露的傳入 URL。其他產品層級的 webhook（管線、工單同步）是另一套選用的設定。
