Control Center 回答兩個授權問題，而它們確實截然不同。**「這個人是否可
呼叫這項操作？」**談的是人、角色與儲存庫。**「這個代理是否可造成這個
效果？」**談的是動作、引數與影響範圍——那個問題屬於
[護欄](/zh-TW/手冊/概念/護欄/)。

本頁談的是第一個問題，以及兩者共同留下的紀錄。

## 單一決策點

每一項與人有關的授權決策，都透過單一函式得出結果：

```
can(principal, permission, resource) → allow | deny + why
```

一項**權限**的形式是 `<domain>:<tier>`——`tickets:write`、
`members:administer`、`repos:read`。這份目錄是**衍生**而來，而非人工
撰寫：它由操作本身計算得出（操作名稱的前綴決定領域，它原本就強制的
角色下限決定層級），因此全部約 550 項操作都帶有權限，無需任何人逐一
手打。

這項衍生正是值得保護的特性。它意味著新增的操作預設就會受到管制——
手動標註模型的失效模式，就是有人忘了標，而他忘掉的正是那道關卡。
一項棘輪測試會固定住衍生出的領域集合，因此在新前綴下新增操作，會是
人為做出的命名決定，而不是一場意外。

這四個層級恰好對應內建角色：

| 層級 | 角色下限 | 範例 |
|---|---|---|
| `read` | 訪客 | `tickets:read` |
| `write` | 成員 | `tickets:write` |
| `administer` | 管理員 | `members:administer` |
| `own` | 擁有者 | `workspace:own` |

## 角色

五個內建角色——**擁有者、管理員、成員、檢視者、訪客**——是這份目錄上
的預設組合。每個工作區只有一個擁有權席次，必須透過**轉移擁有權**明確
移交（離開的擁有者否則無法移除：SCIM 取消佈建會拒絕任何工作區擁有者
——請先轉移）。

**自訂角色是減法式的。**自訂角色會指定一個基礎預設組合（`admin`、
`member`、`viewer` 或 `guest`——絕不會是 `owner`），以及一組從中移除的
權限——「管理員，但不能管理成員」。它永遠不會授予比其基礎更多的權限，
這正是它能安全導入既有安裝的原因：每一項既有的檢查仍然是有力的上限。
成員以 `custom:<id>` 持有它們，而太舊、無法理解該值的用戶端會退回訪客，
而不是自行猜測。

角色之下還有**個別儲存庫授權**（`none` / `read` / `review` /
`write`，見[變更程式碼需要寫入授權](#變更程式碼需要寫入授權)）：工作區成員身分絕不會悄悄給予高於程式碼託管服務的權限。每一
個會接觸程式碼的介面都會檢查它們——包括從側面觸及程式碼的介面，例如
在空間工作樹上開啟的終端機或編輯器工作階段。

## 程式碼遵循託管服務

單純的授權不會開啟儲存庫的程式碼。要查看它的檔案、差異或搜尋結果，或在其上開啟終端機，
成員需要 Control Center 授權**而且**其自己的託管服務登入必須能讀取該儲存庫。工作區管理員
不享有豁免；伺服器擁有者則享有，因為檢出位於他們的機器上。沒有託管服務遠端的儲存庫只需要授權。

- 當管理員把儲存庫授予給其託管服務帳戶無法讀取它的人時，授權會被儲存，且管理員會看到一則警告。
- 當無法連上託管服務進行檢查時，答案是否定的，絕不猜測：該人會看到「無法確認你的 GitHub 存取權限。請再試一次。」，並於稍後再試。
- Pull request 以及由它們產生的所有內容，都遵循相同的規則。

### 變更程式碼需要寫入授權

儲存庫授權分三級，且每一級都包含前一級：

- **read**：查看儲存庫的檔案、差異與搜尋結果，前提是你自己的託管服務登入也能讀取它。
- **review**：read，再加上在其 pull request 上核准、要求變更及其他審查動作。
- **write**：review，再加上變更程式碼，以及驅動會寫入儲存庫的代理執行。變更程式碼涵蓋在編輯器中儲存或還原檔案、把工作樹同步到其 pull request 的 head、提交與推送、發佈分支，以及用來切出、檢出或發佈一段的堆疊動作。

每一次代表某人進行的推送，無論是他們自己做的，或是他們要求的代理執行所做的，都會在推送當下於 GitHub、GitLab 與 Bitbucket 上檢查其對該儲存庫的寫入授權。發佈堆疊時，會先檢查堆疊中的每一個儲存庫，然後才推送其中任何一個。

拒絕時會指出缺少的授權。沒有讀取權限時，應用程式會顯示「你沒有此儲存庫的讀取權限。工作區管理員可以授予。」；有讀取但沒有寫入時，則顯示「你可以讀取此儲存庫，但無法變更。工作區管理員可以授予寫入權限。」

### 空間遵循其儲存庫

空間中關於程式碼的內容會跟隨程式碼。空間的內容（其訊息、逐字稿與工具輸出、搜尋結果、執行日誌、待辦事項、活動與通知）會攜帶它所處理之儲存庫的程式碼，因此只有持有該空間所用每個儲存庫的 read 授權、且其自己的託管服務登入也能讀取它的成員，才能開啟該空間。這些儲存庫是為它選取的儲存庫，或當空間沒有記錄任何選取時，為工作區的所有儲存庫。沒有任何儲存庫的空間，對每位成員都開放。

無法開啟某個空間的人，在任何地方都不會看到它被列出，包括搜尋、執行日誌、待辦事項、活動與通知。工作區管理員持有每一項授權，但不享有託管服務那一半的豁免；伺服器擁有者則享有。

對於希望每個人都能閱讀的對話，請建立沒有儲存庫的空間，或只帶上每個人都能讀取的儲存庫。

## 伺服器擁有者

設定伺服器的人就是它的**擁有者**。伺服器會在首次啟動時記錄他們一次，而透過網路送來的任何內容都不會改變這一點。工作區管理員或工作區擁有者都不是伺服器擁有者：任何人都可以被授予某個工作區，但伺服器所在的機器只有一位擁有者。

**除非伺服器擁有者啟動它或核准那一類主機執行，否則伺服器自己機器上的任何東西都不會在沙箱之外執行。** 具體來說，只有伺服器擁有者可以：

- 建立工作區。其他人會看到一個畫面，要求他們請擁有者建立一個，或請工作區管理員邀請他們。
- 開啟伺服器託管終端機中的主機 shell。其他人會得到沙箱化的終端機，具有代理的限制，且只能在工作區自己的目錄中操作。
- 開啟內嵌的程式碼編輯器。它以伺服器自己的使用者身分執行，帶有它的終端機、工作與擴充功能。
- 在原生編輯器中開啟 pull request 或對話的工作樹。編輯器會在伺服器自己的螢幕上、以伺服器使用者身分啟動。
- 儲存或核准任何會在主機上執行東西的[環境](/zh-TW/手冊/操作指南/環境/)定義：主機放置、執行指令的檢查，或佈建與封存工作。
- 在機器沒有沙箱的伺服器上執行代理。其他人的執行在那裡會被拒絕，除非擁有者以 `--sandbox off` 啟動伺服器，此時每位成員的代理都會不受約束地執行（請參閱[沒有沙箱的主機上的代理](/zh-TW/手冊/概念/沙箱與資安/#沒有沙箱的主機上的代理)）。
- 連結位於工作區自身儲存空間之外的儲存庫檢出、確認在該規則之前已連結的檔案，並在新增儲存庫時瀏覽伺服器的資料夾（請參閱[將儲存庫加入工作區](/zh-TW/手冊/操作指南/新增儲存庫/)）。
- 查看並停止伺服器上每一個執行中的代理程序。其他人只能查看並停止他們所屬工作區中的即時代理執行。
- 讓代理使用設定在伺服器使用者自己工具中的 MCP 伺服器（Claude、Codex、Cursor 等）。只有擁有者負責的內建 harness 執行才能取得它們；請參閱[個人 MCP 伺服器仍屬於擁有者](/zh-TW/手冊/操作指南/mcp-伺服器/#個人-mcp-伺服器仍屬於擁有者)。
- 確認某人的電子郵件地址，以便單一登入能比對它（請參閱[連接 OpenID Connect 供應商](/zh-TW/手冊/操作指南/sso-oidc/#登入如何比對既有帳戶)）。
- 變更整台安裝的設定：SSO、供應商憑證、MCP 端點與其權杖、模型管理、Connect，以及整台安裝的備份。這些操作會宣告**伺服器權限**，對其他人一律拒絕。

這裡刻意只保留一個操作者身分，以及它唯一的定義。

## 稽核軌跡

每一項授權決策——**允許與拒絕**——都會附加到每個工作區各自持有的
雜湊鏈稽核軌跡。

只記錄拒絕的日誌能回答「我們阻擋了什麼？」，卻無法回答「這個代理實際
做了什麼，又是誰授權的？」，而後者正是事件檢討的起點。因此每一筆項目
都會記錄完整的歸屬鏈：實際行動的主體、它代表的人、它是透過哪一項委派
而來的、動作及其引數（以摘要表示）、決策，以及**做出決定的規則**。

項目之間彼此串鏈：每一筆的雜湊都涵蓋前一筆，因此只要編輯、刪除或重新
排序任何一列，就會使其後每一筆雜湊失效。**驗證鏈**會重新推導整條鏈，
並指出第一個不成立的環節。無法查核的稽核日誌只是日誌；能重新推導的
才是證據。

有兩個值得知道的後果：

- 稽核資料表**豁免於以時間為基礎的修剪**。雜湊鏈無法從中段修剪。保留
  策略是先匯出再截斷，而截斷會留下一個檢查點，帶著被移除區段的最終
  雜湊，因此留存下來的部分仍可一路驗證回開頭。
- 它位於活動時間軸**旁邊**，而不是疊在其上。時間軸記錄人們做了什麼；
  這裡記錄的是什麼被授權、什麼被拒絕。共用的關聯 id 讓同一通呼叫能
  貫穿兩者來閱讀。

它會以換行分隔的 JSON 匯出，並可串流到 SIEM（Splunk、Elastic、
Sentinel——一個帶有 bearer token 的 HTTP 端點）。串流在設計上採盡力
而為：SIEM 停機絕不應阻擋代理的工具呼叫，而可持久、可驗證的副本無論
如何都保存在磁碟上。

## 工作階段

一台安裝可以設定**工作階段最長存續時間**與**閒置逾時**。兩者都會在
每一條已驗證管道必經的裝置憑證檢查點強制執行——一個用戶端能忽略的
工作階段期限，應付的是問卷，而不是攻擊者。一台安裝也可以要求使用 SSO，
這會停用新裝置的手動配對（並有鎖定防護：在沒有可用 SSO 連線時會拒絕
啟用）。

## 這不是什麼

- **不是以個別物件為單位的 ACL。**這裡刻意不提供以個別工單或個別訊息
  為單位的權限。團隊真正需要的是儲存庫層級的區隔，而這樣的功能確實
  存在；以個別物件分享會帶來組合爆炸的介面，且在此處沒有展現出需求。
- **不是讓你在 DSL 中設定的原則引擎。**詞彙刻意保持封閉，因此整套原則
  可以被呈現、解釋與列舉。
- **只在伺服器端強制執行。**用戶端檢查的存在，只是為了避免提供一個
  會被拒絕的控制項。具權威性的決策永遠由伺服器做出。
