Control Center 是一款桌面應用程式，但它所追蹤的工作不會在你離開書桌時停下來。
**遠端控制**會用位於 remote.usectrl.dev 的伴侶應用程式
**[Remote](https://remote.usectrl.dev/)**，把你的手機與你的 `cc_server` 配對，讓
你可以從手機跟上機群：透過端對端加密連線閱讀訊息與工單、回覆代理、整理你的新聞
動態。手機與 `cc_server` 是受信任的明文端點；中繼只承載已加密的應用程式記錄。

不妨把它想成主介面上一個以讀取為主的伴侶。它並不是要取代完整的桌面用戶端。

:::note[兩種不同的遠端用戶端]
手機伴侶與完整的 **網頁版**（或指向遠端伺服器的桌面版）都可以直接連線
`cc_server`，也可以使用經仲介撮合的 WebSocket 中繼。兩條路徑都要求同一套加密
工作階段；手機對外提供的操作比完整用戶端更少。用戶端之間的差異見
[部署與用戶端](/zh-TW/手冊/概念/部署/)。
:::

## 傳輸方式

手機透過 WebSocket 觸達 `cc_server`：可以是直接連線（回送、LAN、tailnet 或
`wss://`），也可以是信令仲介上需邀請才能加入的房間。兩條路徑都要求經過驗證的
端對端加密工作階段；仲介只轉送自己那些已加密的記錄。這裡沒有點對點的資料通道。

## 手機能做什麼

已配對的手機只能觸達伺服器介面中一小塊刻意劃定的範圍：

- **讀取**工單、代理、空間及其訊息，以及你的新聞動態
- **回覆**：在空間中傳送訊息、更新或指派工單、把文章標示為已讀或已儲存
- **執行 Playbook**：以參數具現一個已儲存的計畫範本。它只會_提出_計畫；在操作
  人員於完整用戶端的 Plan Studio 中核准之前，不會有任何執行或花費
- **切換工作區**，在手機自己的選擇器中

差不多就是全部了。相較於完整用戶端，手機是**權限較低的主體**。它不能啟動行程、
動用 LLM 預算、推送到 GitHub，也不能建立工作區。它是如何被真正強制執行、而不只是
設計意圖，請見[存取模型](#存取模型)。

## 連線是如何建立的

當手機無法直接觸達伺服器時，連線會依托一條**仲介式中繼**：伺服器以房間擁有者的
身分，加入 `wss://` 仲介上一個需邀請才能進入的房間，已配對的用戶端憑有時限的
准入權杖加入。共有三個部分共同運作：

| 組成部分                  | 角色                                                                                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Remote（手機應用程式）** | 伴侶網頁應用程式，預設託管於 `remote.usectrl.dev`，也可自行託管。它在瀏覽器中載入，並把配對記錄保存在 IndexedDB 中。                                                                                                                                   |
| **中繼仲介**       | 一條無狀態的 `wss://` 中繼（`cc_signaling_server`），託管 N 方房間。它轉送已加密的記錄，既沒有配對密鑰也沒有應用程式明文，但看得到路由識別碼、IP、記錄大小與時序。 |
| **`cc_server`**        | 房間的擁有者。它透過其他所有用戶端所用的同一個派送器，回應手機的呼叫。                                                                                                                                                                            |

一次配對邀約會帶上一個**連線描述元**，列出通往伺服器的每一條路徑（LAN、tailnet、
公開的 `wss://`、中繼），以及伺服器的身分指紋。手機的解析器會挑選最佳的可達路徑。
伺服器會為加密握手簽署，用戶端則釘選其指紋。首次連線時，請對照 QR 碼或另一個
可信任來源檢查該指紋：單憑首次出現的已簽署身分，並不能證明你連到的是哪一台伺服器。
指紋一旦改變就會被拒絕，而不會默默再次獲得信任。當沒有直接路徑時，中繼會承載密文，
但它仍能中斷或延遲連線。

## 配對負載是什麼

配對由應用程式簽發，並以深層連結的形式交付；程序請見
[配對裝置](/zh-TW/手冊/操作指南/配對裝置/)。這裡重要的是它的結構。

```
https://<pwa-host>/#<payload>
```

負載位於 URL 的**片段**，也就是 `#` 之後、瀏覽器在傳給 PWA 主機的 HTTP 請求中
不會包含的那一段。它帶著手機觸達伺服器並證明自身身分所需的一切：連線描述元
（每一條路徑加上身分指紋）、一個新簽發的裝置 ID、一個 32 位元組的預共享金鑰，
以及一個到期時間戳。手機會將它解碼、在本機儲存配對記錄，並從 URL 移除片段。
網頁應用程式的程式碼可以讀取該片段，因此請使用可信任的應用程式主機，並把連結
當成機密看待。

負載有兩種形態，而且**不可互換**。從應用程式內配對面板簽發的手機 QR 碼，就是
上面那種指向 Remote PWA 主機的 v2 `PairingPayload`。`cc_server pair --client-url`
發出的是 v1 連結（`{s, i, k}` —— 伺服器 URL、裝置 ID、金鑰），
只供 **Web** 用戶端使用。這些是配對資料格式，而非傳輸方式的降級路徑：兩種
用戶端都必須支援目前的加密工作階段協定。

兩者的有效期也不同，這一點很容易搞錯：

| 簽發方式                              | 憑證到期時間                              |
| ------------------------------------- | ----------------------------------------- |
| 應用程式內配對面板（`pairing.mint`）  | 一律 30 天                                |
| 命令列上的 `cc_server pair`           | 未編碼到期時間；伺服器原則仍然適用        |

伺服器全域的裝置存續時間上限與閒置逾時原則，可能會更早拒絕這兩種憑證。兩種配對
格式都不會繞過這些原則。

## 存取模型

已配對的裝置是**已驗證但不受信任**的。數道各自獨立的關卡，讓一次獲准（或外洩）
的配對不會變成對伺服器的完全控制。

### 1. 邊界在於成員資格，而非配對

有效的配對金鑰只能證明你是_哪一台裝置_。你可以讀取或變更什麼，取決於你的**工作區
角色**——每一次呼叫都會重新解析——以及任何會揭露儲存庫內容的操作上依儲存庫授予
的權限。一台持有完全有效金鑰、但所屬使用者並非所指名工作區成員的裝置，會被拒絕，
並回覆「Not a member of this workspace」。

角色下限由操作的種類推導而來，除非操作自行宣告：讀取需要 `guest`，變更需要
`member`，破壞性操作需要 `admin`。

### 2. 手機屬於較低的工作階段層級

除了角色檢查之外，手機工作階段所帶的能力也低於桌面版或網頁版工作階段。宣告為
僅限完整用戶端的操作，會在處理常式執行之前就對手機拒絕，無論其背後的使用者權限有
多高：簽發、列出、重新命名與撤銷裝置配對；讀取與設定通道連線；伺服器備份與工作區
匯出／匯入；行程偵測與終止；配接器探測；伺服器設定；SSO 管理；機群控制；以及
接管或交回正在執行的代理。

### 3. 預設拒絕的工具允許清單

具體到 MCP 工具介面（`tools/call`），哪些工具可由手機叫用，是由一份預設拒絕的
允許清單決定。未列入清單的工具會在執行之前被拒絕。這份清單以讀取與觀察為主，另加
少量**僅限本機**的寫入——一則訊息、一次工單更新、一個文章標記——它們不消耗
LLM 預算、不啟動行程，也不接觸任何外部系統。

例如會被拒絕的：向代理諮詢、啟動 AI 審查、終止代理、把審查發布到 GitHub、聘用或
解僱代理、建立工作區。

### 4. 每次呼叫的工作區範圍限定

伺服器**不**保存任何「目前工作區」。它在設計上是無狀態的：每個以工作區為範圍的
呼叫，都必須在自己的引數中指名目標 `workspace_id`，而當這個引數缺失、或指名的是
一個伺服器並未註冊的工作區時，派送器會直接拒絕該呼叫——這發生在任何資料庫被開啟
之前。因此手機永遠無法繼承或漂移到另一個用戶端的範圍，指名一個外來的工作區也幫
不上忙，因為第 1 道關卡的成員資格檢查仍然適用。這與產品其餘部分所強制執行的
[工作區隔離](/zh-TW/手冊/概念/工作區/)是同一項不變式。

### 5. 直接與經中繼連線上的端對端加密

每一個直接或經中繼的用戶端工作階段，都要求已簽署的 Noise 握手。配對金鑰為該
握手提供驗證；由新的臨時金鑰推導出流量金鑰，而不是用配對金鑰密封每一個訊框。
伺服器會把自己的身分簽入這次交換，用戶端則核對自己儲存的指紋釘選值。不存在
明文或舊用戶端的降級路徑。中繼准入權杖只是讓用戶端進入房間；它無法解密那些記錄。

由應用程式簽發的憑證有時限，為 30 天；超過期限後，連線關卡會判定它失效，手機
必須重新配對。撤銷是即時的：伺服器會監看裝置表，並在數秒內中斷已撤銷裝置的現有
工作階段，而不是等它下次連線。

### 6. 依主體限制速率

滑動視窗限速器把遠端工具流量限制在每分鐘 120 次呼叫，並對變更類動詞再加上一個更
緊的每分鐘 30 次上限。這份額度屬於**主體，而不是工作階段**：你的三台裝置共用
同一份額度，因此被劫持的用戶端無法靠開更多工作階段換取餘裕，一個吵鬧的成員也無法
讓其他人挨餓。

### 7. 無法讀取應用程式內容的仲介

中繼仲介託管暫時性、需邀請才能加入的房間，並轉送已加密的記錄，其中既沒有應用
程式明文也沒有配對金鑰。但它仍看得到 IP 位址、房間與對等端識別碼、記錄大小、
時序與連線存續時間，也能丟棄或延遲流量。明文端點是已配對的用戶端與所選定的
`cc_server`；伺服器操作者以及伺服器向其傳送內容的服務都能看到那些內容。傳輸中
的加密並不會加密伺服器上的靜態資料。

## 即時更新

配對之後，手機會以通知訊框的形式收到**即時更新**——新的代理訊息、指派給你的工單、
狀態變更——與桌面版自己的通知如出一轍。伺服器在把事件轉送給某個工作階段之前，
會先檢查工作區成員資格。用戶端再把那些已獲授權的事件篩選到你目前查看的工作區；
這個顯示篩選器並不是存取邊界。

## 所在位置

| 介面                                                                                | 顯示內容                                                                                                    |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **設定 → 你 → 你的裝置**（`/workspaces/:workspaceId/settings/you/devices`）         | 已配對的用戶端及其即時狀態，另有**配對新用戶端**（網頁瀏覽器、桌面應用程式或手機）與撤銷                      |

同一個面板也會為第二個瀏覽器或桌面應用程式簽發配對，並不只限於手機——流程完全
相同，只有深層連結不同。

::::note
遠端控制屬於伺服器端，且**不**透過 MCP 對外提供。手機是透過其加密的直接或經中繼
連線，與伺服器自己的派送器通訊；它並不是外部伺服器的 MCP 用戶端。
::::
