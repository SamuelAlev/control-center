本指南說明設定過程中 GitHub 專屬的部分。GitHub 是三個受支援的程式碼託管平台之一。若要連接 GitLab 或 Bitbucket，以及了解一個工作區如何混用這些平台，請參見[連接程式碼託管](/zh-TW/手冊/操作指南/連接程式碼託管/)。

## 先決條件

- 一個可存取你想處理之儲存庫的 GitHub 帳號
- 一台能讓人們登入 GitHub 的伺服器：它自己的 GitHub App（參見[建立 GitHub App](/zh-TW/手冊/操作指南/github-app/)）或 Control Center Connect，由伺服器擁有者在 **設定 → 伺服器 → 單一登入** 中選擇

:::note[憑證存放在伺服器上，並附掛於你]
你正在輸入的機器上不會儲存任何東西。你的 GitHub 登入由你的 `cc_server` 保管，並以你的使用者 id 為鍵，而你登入的每個裝置都會使用它：桌面版、網頁版與手機版皆然。同一台伺服器上的其他成員無法使用它，而要讓他們登入，得由他們自己來做。
:::

## 登入 GitHub

GitHub 只能登入：沒有可貼上的權杖。

1. 前往 **設定 → 你 → 個人資料 → 程式碼託管**（或是新手導引的第一步）
2. 在 **GitHub** 資料列上，點擊**登入 GitHub**
3. 你的瀏覽器會開啟 GitHub。核准應用程式

登入如何完成，取決於由誰執行：

- **伺服器自己的應用程式：** GitHub 會把你的瀏覽器送回伺服器，對話框會自行察覺。不需要輸入任何東西
- **Control Center Connect：** 瀏覽器頁面會顯示一組 8 個字元的代碼。把它輸入對話框，或讓瀏覽器透過 `control-center://` 連結開啟 Control Center，就不必輸入

檢查點：**GitHub** 資料列顯示「已登入為 _your-username_」。

對話框會拒絕不是由它自己發起的代碼或連結，並顯示**登入並非從這裡發起**。如果有人傳給你一個登入連結，請不要繼續：完成它會把你的帳號連接到對方的伺服器。

點擊**中斷連線**即可移除你的登入。登出 GitHub，或被移出某個工作區，也會讓伺服器代表你簽發的所有權杖一併失效。

## 你的憑證代表誰

Control Center 遵循 GitHub 自身的區分：以**人的身分**行事，還是以**應用程式的身分**行事。

| 發生的事                                                                      | 在 GitHub 上顯示為                                          |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 你自己做的任何事：留言、審查、核准、合併、要求審查者                           | **你**。GitHub 會在對話中的留言上標示為由 Control Center App 發出；審查及其行內留言則不帶此標示 |
| AI 審查、代理在 PR 對話中的回覆和留言、標籤、管線與機器人工作                        | **Control Center 機器人**。在共用的 Connect 應用程式上，只有 Connect 營運者已列出的安裝，審查才會以機器人身分顯示；否則會顯示為負責的人 |
| 代理為你開啟的 pull request、它對該 pull request 標題或描述的編輯、它的推送與它的提交                                | **你**。開啟共同作者標示時，Control Center 會被列為共同作者 |
| 沒有人要求的工作（排程、webhook）                                              | **Control Center 機器人**，同時也是其提交的作者。在 Control Center Connect 上，它從不推送或開啟 pull request |

- **你做的任何事**都只使用**你的**登入，別無其他。如果你尚未登入，應用程式會請你登入。沒有任何其他憑證會代替你
- **機器人工作**每次會取得一個只適用於一個儲存庫的權杖，並限制在負責成員在那裡能做的事：提出請求的成員，否則是工作區擁有者。無法推送的成員會把它限縮為唯讀。代表某人行事的機器人回覆會以 **Control Center (for @login)** 開頭
- **代理透過 Control Center 開啟 pull request**，絕不從它們的沙箱中開啟，因此該 pull request 是你的，而 GitHub 自身的規則會阻止你核准它。Control Center 也會拒絕請代理執行該工作之人自己的核准，以及來自 pull request 作者的核准。對於排程或 webhook 執行，這涵蓋了在其啟用期間啟用其觸發條件或編輯其流程的每位管理員。必須由其他人審查。若 Control Center 無法確認是誰開啟了 pull request，或代碼託管平台上哪個帳號是你的，它會拒絕並請你重試
- **代理也透過 Control Center 留言。** 代理執行取得的 GitHub 權杖只能讀取。當代理在它正在處理的 pull request 上留言時，Control Center 會以機器人身分張貼留言，若是有人請求該次執行，則以 **Control Center (for @login)** 開頭。代理只能在它自己的 pull request 上留言：必須是同一儲存庫中的（不是 fork），且其最新提交由該代理推送，或為其空間分支的目前提交。代理留言中的 @ 提及不會通知任何人。代理也可以在其自己的 pull request 仍為開啟狀態時，修改該 pull request 的標題或描述。該修改會以開啟該 pull request 的方式進行（若是你請求的執行，則以你的身分），預設會先請求核准。pull request 的描述會保留其中的 @ 提及，無論代理是打開還是修改它，它所點名的人都會收到通知
- **在 Control Center Connect 上，機器人從不推送或開啟 pull request。** 在那裡推送、建立分支或開啟 pull request，需要請求的人，並以該人的登入執行。排程或 webhook 觸發的執行若試圖推送，會停止並顯示說明訊息。若要讓無人看管的執行能夠推送，請在**設定**中為工作區提供自己的 GitHub App
- **Connect 機器人能做什麼。** 使用共用的 Connect 應用程式時，機器人會留言、加標籤並回應表情符號。只有當 Connect 營運者已列出此伺服器的安裝時，它才會張貼審查（AI 審查、審查留言、審查者請求）。否則，審查會以負責人自己的登入送出，並以他的名義顯示。機器人從不開啟、編輯、關閉或改名 pull request、撤銷審查，或編輯或刪除留言；這些需要請求的人以自己的登入來完成。Connect 不會把你組織的安裝綁定到單一 Control Center 伺服器：任何有成員能推送至儲存庫並透過 Connect 登入的伺服器，都能取得該儲存庫的機器人留言權杖
- **擁有自己 GitHub App 的伺服器或工作區**，上述所有項目（包括審查）都由機器人負責
- **自動化永遠不會核准** pull request。核准是人的行為

當你連結儲存庫時，Control Center 會檢查你的帳號是否看得到它，並在 GitHub App 未安裝在其組織上或未包含該儲存庫時發出警告，同時附上修正的連結。連結與取消連結都需要工作區管理員；位於工作區自身儲存空間之外的檢出，只能由伺服器擁有者連結。請參閱[將儲存庫加入工作區](/zh-TW/手冊/操作指南/新增儲存庫/)。

連結會跟隨儲存庫永久的 GitHub id，因此更名或轉移不需要你做任何事。若路徑之後指向另一個儲存庫，Control Center 會停止向它送出任何內容，並顯示通知，直到工作區管理員按下**重新連結**為止。

開啟儲存庫的程式碼（檔案、差異、搜尋、終端機）需要工作區中的授權，以及你自己能讀取它的 GitHub 登入。工作區管理員遵循同一規則；只有伺服器擁有者享有豁免。

## 這項整合為你帶來什麼

| 功能               | 運作方式                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------- |
| PR 清單與詳細資料  | 從伺服器端、以你自己的登入呼叫 GitHub REST API                                                                 |
| 檢查執行           | GitHub Checks API                                                                                              |
| 審查發佈           | 一個由使用者把關的步驟，會以你的身分將你的審查發佈到 PR 上                                                     |
| 儲存庫註冊         | 簽出的 `origin` 遠端指向 github.com 即會被接受，或是 gitlab.com / bitbucket.org                               |
| 代理的 GitHub 存取 | 在執行中，`git fetch` 經由 Control Center 進行，由它以執行永遠不持有的唯讀權杖讀取該次執行所處理的各個儲存庫。`gh` 使用唯讀權杖讀取它們，該權杖由 Control Center 在被請求時簽發，並在執行結束時撤銷。推送、pull request、對它們的編輯及留言都經由 Control Center |
| 通知提醒           | 伺服器端輪詢你的 GitHub 通知收件匣，進而產生「在 pull request 中被提及」與「已請求審查」                       |
| 使用者個人檔案     | 個人檔案懸停卡片與依作者篩選 PR                                                                                |

有些路徑在更省資源的情況下會改用 GraphQL API，而非 REST：例如建立 PR 選擇器的分支活動，以及用來判斷某個「已請求審查」通知是否仍在等待中的即時審查狀態。

## 留意 GitHub 服務中斷

當某個供應商服務品質下降時，標題列會顯示狀態標籤，涵蓋 GitHub、Claude、OpenAI 與 Kimi。**一切正常時它不會顯示**：它出現才代表有問題，沒出現並不代表沒問題。

點擊該標籤會開啟一個彈出面板，顯示各供應商的狀態與一個重新整理按鈕。狀態每兩分鐘會自行重新整理。

## 了解代理在 GitHub 上的行為

- 在 GitHub 工作樹中工作的代理會取得一個只適用於那一個儲存庫的權杖。它只能讀取程式碼、issue 與 pull request；留言依上文所述經由 Control Center。推送會經由 Control Center，它會先詢問**推送至遠端**規則，然後以代理從不持有的寫入權杖轉送推送。 參見[設定沙箱政策](/zh-TW/手冊/操作指南/沙箱原則/)
- 你要求的工作會以你的身分提交。當你請代理執行某件事，或在 IDE 中提交時，你就是作者與提交者，並使用你的託管平台已驗證的位址：你在 GitHub 登入時的 GitHub noreply 位址，或在 GitLab 與 Bitbucket 上你的登入所回報的電子郵件。只有在沒有任何託管平台為你的位址背書的儲存庫中，你手動進行的提交才會使用你的工作區 Git 身分。若你未登入該託管平台，代理的提交則改由機器人負責，且執行的備註會說明原因
- 沒有人要求的工作會以機器人身分提交。排程或 webhook 執行會以工作區的 GitHub App 身分提交（`<app>[bot]`，附其 GitHub noreply 位址），或在沒有 GitHub App 或儲存庫位於 GitLab 或 Bitbucket 上時，以 `Control Center <hi@usectrl.dev>` 身分提交
- **將 Control Center 加入為共同作者**（**設定** → **你** → **提交**）會為另一方加上 `Co-Authored-By:` 尾注：在你的提交上是 Control Center，在機器人的提交上則是啟動該次執行之觸發條件的每一位人員。預設為開啟，除非你將它關閉。工作區管理員可以在 **設定** → **工作區** → **一般** 中以**共同作者標示**為所有人決定；之後你自己的選擇仍會被儲存，但不會套用於該工作區。Claude Code 自帶的署名一律停用
- 你的提交可以簽章。在 **設定** → **你** → **提交** 下的**已驗證的提交**中，選擇**建立簽署金鑰**，並把它的公開部分新增到你的 GitHub 或 GitLab 帳戶作為簽署金鑰；此後，你所要求之執行所產生的提交，以及你在 IDE 中進行的提交，都會顯示為已驗證。私密部分留在你的伺服器上，因此只要金鑰仍在你的帳戶上，控制該伺服器的人就能以你的身分簽署提交；而在 GitHub 上，已顯示為已驗證的提交，在你移除金鑰後仍會保持已驗證。Bitbucket 沒有僅供簽署的金鑰：請勿在那裡新增此金鑰，且 Bitbucket 上的提交不會被簽署。機器人的提交永遠不簽署
- 你在 IDE 的**原始檔控制**面板中進行的提交會略過儲存庫的 Git 掛鉤，如同 `git commit --no-verify`；伺服器的 Git 會忽略儲存庫所設定的憑證輔助程式、編輯器、外部差異工具與簽署程式：它在自己的機器上、於代理或 pull request 可以變更的工作樹中執行 Git。請參閱[從原始檔控制提交與推送](/zh-TW/手冊/操作指南/審查並合併-pr/#從原始檔控制提交與推送)
- 代理推送的每個提交都會先經過檢查，包括 `stack_publish` 為堆疊推送的各層。推送若指明他人、移除或借用任一署名、加上 sign-off，或未依你的設定簽署，將會被拒絕。你自己從 IDE 推送的提交屬於你，不以這種方式檢查
- 你在機台上開啟的終端機會取得你自己的登入，並縮限到那一個儲存庫，因此在那裡的
  推送是你的
- 無法簽發權杖時（沒有任何負責人登入、應用程式未安裝在擁有者上，或該安裝已遭
  停權），請求權杖的指令會說明原因。沒有任何退回憑證

## 疑難排解

### PR 清單是空的，並顯示 GitHub 未連接

你尚未在這台伺服器上登入 GitHub。請在**設定 → 你 → 個人資料 → 程式碼託管**下點擊**登入 GitHub**。其他託管平台上的儲存庫不受影響。

### GitHub 資料列表示此伺服器尚未設定登入

伺服器既沒有自己的 GitHub App，也沒有 Connect。由伺服器擁有者在 **設定 → 伺服器 → 單一登入** 中擇一設定：**建立我的 GitHub 應用程式**大約只需兩分鐘。參見[建立 GitHub App](/zh-TW/手冊/操作指南/github-app/)。

在選擇了自有應用程式的工作區中，該列會說明工作區的 GitHub App 缺失或不完整。工作區管理員在 **設定 → 工作區 → 整合** 的 **GitHub 應用程式**卡片中把它補齊；參見[為單一工作區提供自己的應用程式](/zh-TW/手冊/操作指南/github-app/#為單一工作區提供自己的應用程式)。

### 對話框表示代碼不相符

請完全依照瀏覽器顯示的內容輸入代碼：8 個字母與數字。輸錯五次會結束這次登入；請重新開始。

### 登入表示應用程式未安裝

GitHub App 在擁有該儲存庫的帳號上沒有任何安裝。由工作區管理員從 **設定 → 工作區 → 整合 → GitHub 應用程式安裝** 進行安裝。

### 所有人都必須重新登入 GitHub

伺服器擁有者輪替了伺服器的 Connect 金鑰、切換了 Connect 伺服器，或資料目錄被還原到另一台機器上。透過 Connect 的登入會綁定到建立它們的那台伺服器。

### 新增儲存庫時遭到拒絕

註冊必須同時滿足三個條件：路徑位於 git 工作樹內、它設有 `origin` 遠端，且該遠端指向受支援的託管平台（github.com、gitlab.com 或 bitbucket.org）。`origin` 必須是你要連結的那個儲存庫，而位於工作區自身儲存空間之外的資料夾，只能由伺服器擁有者連結。參見[將儲存庫加入工作區](/zh-TW/手冊/操作指南/新增儲存庫/)。

### 我有授權，但該儲存庫顯示我的帳戶無法讀取它

你的 GitHub 帳戶無法讀取該儲存庫，因此即使具有工作區授權，它的程式碼對你仍然是關閉的。請在**程式碼託管**下登入 GitHub，或在 GitHub 上向該儲存庫申請存取權限。

### 「無法確認你的 GitHub 存取權限」

GitHub 無法連線以檢查你的存取權限，因此 Control Center 選擇拒絕，而不是猜測。請稍後再試。

### 在 Connect 上，審查顯示在我的名下，而非機器人

在共用的 Connect 應用程式上，機器人只會為 Connect 營運者列出的安裝張貼審查。在其他地方，審查會以負責人自己的登入送出。若要讓機器人張貼審查，請為工作區提供自己的 GitHub App。

### 大量使用後所有功能會停擺一陣子

那是速率限制的斷路器。GitHub 會以帶著 `x-ratelimit-remaining: 0` 與重設時間的 `403` 來表示主要限制；用戶端一看到它，就會在不發出任何網路呼叫的情況下於本機讓後續請求失敗，直到時間窗過去，因此重試風暴無法讓限制加深。暫時性失敗最多會以指數退避重試三次，並遵守 `retry-after`。
