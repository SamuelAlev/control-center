本指南說明設定過程中 GitHub 專屬的部分。GitHub 是三個受支援的程式碼託管平台之一。若要連接 GitLab 或 Bitbucket，以及了解一個工作區如何混用這些平台，請參見[連接程式碼託管](/zh-TW/手冊/操作指南/連接程式碼託管/)。

## 先決條件

- 一個可存取你想處理之儲存庫的 GitHub 帳號
- 一台能讓人們登入 GitHub 的伺服器：它自己的 GitHub App（參見[建立 GitHub App](/zh-TW/手冊/操作指南/github-app/)）或 Control Center Connect，由伺服器擁有者在 **設定 → 伺服器 → 單一登入** 中選擇

:::note[憑證存放在伺服器上，並附掛於你]
你正在輸入的機器上不會儲存任何東西。你的 GitHub 登入由你的 `cc_server` 保管，並以你的使用者 id 為鍵，而你登入的每個裝置都會使用它：桌面版、網頁版與手機版皆然。同一台伺服器上的其他成員無法使用它，而要讓他們登入，得由他們自己來做。
:::

## 登入 GitHub

GitHub 只能登入：沒有可貼上的權杖。

1. 前往 **設定 → 工作區 → 個人資料與身分 → 程式碼託管**（或是新手導引的第一步）
2. 在 **GitHub** 資料列上，點擊**登入 GitHub**
3. 你的瀏覽器會開啟 GitHub。核准應用程式

登入如何完成，取決於由誰執行：

- **伺服器自己的應用程式：** GitHub 會把你的瀏覽器送回伺服器，對話框會自行察覺。不需要輸入任何東西
- **Control Center Connect：** 瀏覽器頁面會顯示一組 8 個字元的代碼。把它輸入對話框，或讓瀏覽器透過 `control-center://` 連結開啟 Control Center，就不必輸入

檢查點：**GitHub** 資料列顯示「已登入為 _your-username_」。

對話框會拒絕不是由它自己發起的代碼或連結，並顯示**登入並非從這裡發起**。如果有人傳給你一個登入連結，請不要繼續：完成它會把你的帳號連接到對方的伺服器。

點擊**中斷連線**即可移除你的登入。登出 GitHub，或被移出某個工作區，也會讓伺服器代表你簽發的所有權杖一併失效。

## 你的憑證代表誰

- **你做的任何事**（開啟 PR 頁面、張貼審查、核准、合併）都只使用**你的**登入，別無其他。如果你尚未登入，應用程式會告訴你並請你登入。沒有任何其他憑證會代替你
- **沒有人在輸入的工作**（代理執行、管線、PR 輪詢、機器人回覆、複製）會取得一個只適用於一個儲存庫的權杖，由伺服器的 GitHub App 或透過 Connect 簽發。它被限制在某位負責成員在那裡能做的事：提出請求的成員，否則是工作區擁有者。無法推送的成員會把權杖限縮為唯讀
- **自動化永遠不會核准** pull request。核准是人的行為

## 這項整合為你帶來什麼

| 功能               | 運作方式                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------- |
| PR 清單與詳細資料  | 從伺服器端、以你自己的登入呼叫 GitHub REST API                                                                 |
| 檢查執行           | GitHub Checks API                                                                                              |
| 審查發佈           | 一個由使用者把關的步驟，會以你的身分將你的審查發佈到 PR 上                                                     |
| 儲存庫註冊         | 簽出的 `origin` 遠端指向 github.com 即會被接受，或是 gitlab.com / bitbucket.org                               |
| 代理的 GitHub 存取 | 一個只適用於該次執行那一個儲存庫的權杖，作為 `GH_TOKEN` / `GITHUB_TOKEN`；推送經由 Control Center            |
| 通知提醒           | 伺服器端輪詢你的 GitHub 通知收件匣，進而產生「在 pull request 中被提及」與「已請求審查」                       |
| 使用者個人檔案     | 個人檔案懸停卡片與依作者篩選 PR                                                                                |

有些路徑在更省資源的情況下會改用 GraphQL API，而非 REST：例如建立 PR 選擇器的分支活動，以及用來判斷某個「已請求審查」通知是否仍在等待中的即時審查狀態。

## 留意 GitHub 服務中斷

當某個供應商服務品質下降時，標題列會顯示狀態標籤，涵蓋 GitHub、Claude、OpenAI 與 Kimi。**一切正常時它不會顯示**：它出現才代表有問題，沒出現並不代表沒問題。

點擊該標籤會開啟一個彈出面板，顯示各供應商的狀態與一個重新整理按鈕。狀態每兩分鐘會自行重新整理。

## 了解代理在 GitHub 上的行為

- 在 GitHub 工作樹中工作的代理會取得一個只適用於那一個儲存庫的權杖。當負責的
  成員可以推送時，它能讀取程式碼並在 pull request 上留言；成員無法推送時則只能
  讀取。推送會經由 Control Center，它先詢問**推送到遠端**規則，再用代理從不持有
  的寫入權杖轉送推送。參見[設定沙箱原則](/zh-TW/手冊/操作指南/沙箱原則/)
- 代理的提交始終使用提出請求者的 Git 身分作為作者與提交者。預設情況下，`Co-Authored-By: Control Center <hi@usectrl.dev>` 尾註會將 GitHub `@usectrl` 記為共同作者。你可以在 **設定 → 你 → 提交署名** 關閉這項共同作者署名，而不改變自己的身分。**設定 → 工作區 → 通用** 中的工作區設定優先，並會鎖定個人開關。Claude Code 自帶的署名一律停用。提交簽章仍須另外有效設定
- 你在機台上開啟的終端機會取得你自己的登入，並縮限到那一個儲存庫，因此在那裡的
  推送是你的
- 無法簽發權杖時（沒有任何負責人登入、應用程式未安裝在擁有者上，或該安裝已遭
  停權），執行會在沒有權杖的情況下開始，並在其備註中說明原因。沒有任何退回憑證

## 疑難排解

### PR 清單是空的，並顯示 GitHub 未連接

你尚未在這台伺服器上登入 GitHub。請在**程式碼託管**下點擊**登入 GitHub**。其他託管平台上的儲存庫不受影響。

### GitHub 資料列表示此伺服器尚未設定登入

伺服器既沒有自己的 GitHub App，也沒有 Connect。由伺服器擁有者在 **設定 → 伺服器 → 單一登入** 中擇一設定：**建立我的 GitHub 應用程式**大約只需兩分鐘。參見[建立 GitHub App](/zh-TW/手冊/操作指南/github-app/)。

### 對話框表示代碼不相符

請完全依照瀏覽器顯示的內容輸入代碼：8 個字母與數字。輸錯五次會結束這次登入；請重新開始。

### 登入表示應用程式未安裝

GitHub App 在擁有該儲存庫的帳號上沒有任何安裝。由工作區管理員從 **設定 → 工作區 → 一般 → GitHub 應用程式安裝** 進行安裝。若組織使用的是 Control Center 的共用 App，可能需要該組織的一位管理員點擊**授權此伺服器**。參見[建立 GitHub App](/zh-TW/手冊/操作指南/github-app/#為組織授權這台伺服器)。

### 所有人都必須重新登入 GitHub

伺服器擁有者輪替了伺服器的 Connect 金鑰、切換了 Connect 伺服器，或資料目錄被還原到另一台機器上。透過 Connect 的登入會綁定到建立它們的那台伺服器。

### 新增儲存庫時遭到拒絕

註冊必須同時滿足三個條件：路徑位於 git 工作樹內、它設有 `origin` 遠端，且該遠端指向受支援的託管平台（github.com、gitlab.com 或 bitbucket.org）。參見[將儲存庫加入工作區](/zh-TW/手冊/操作指南/新增儲存庫/)。

### 大量使用後所有功能會停擺一陣子

那是速率限制的斷路器。GitHub 會以帶著 `x-ratelimit-remaining: 0` 與重設時間的 `403` 來表示主要限制；用戶端一看到它，就會在不發出任何網路呼叫的情況下於本機讓後續請求失敗，直到時間窗過去，因此重試風暴無法讓限制加深。暫時性失敗最多會以指數退避重試三次，並遵守 `retry-after`。
