Control Center 支援三種程式碼託管服務，在應用程式中一律稱為**託管平台**：**GitHub**、**GitLab** 與 **Bitbucket Cloud**。它們沒有任何一個是預設值。連接一個，一切就能運作；連接多個，同一個工作區就能同時容納來自這三者的儲存庫。

託管平台是每個**儲存庫**自身的屬性，在你註冊儲存庫時從它的 `origin` 遠端讀取。你永遠不需要自行挑選，也沒有任何會設錯的工作區層級設定。

## 連接託管平台

1. 開啟**設定 → 你 → 個人資料**（`/settings/you/profile`）。
2. 找到**程式碼託管**卡片。所有支援的託管平台都會列出，無論是否已連接。
3. 在 **GitHub** 上按**登入 GitHub**。在 **GitLab** 或 **Bitbucket** 上按**新增權杖**並貼上一組。

**GitHub 只能登入。** 登入會透過伺服器自己的 GitHub App 或 Control Center Connect 進行，視伺服器擁有者設定了哪一個而定，或視工作區管理員在**設定 → 工作區 → 整合**中為該工作區選擇的應用程式而定（請見[設定 GitHub 整合](/zh-TW/手冊/操作指南/github-整合/)）；沒有可貼上的 GitHub 權杖。GitLab 與 Bitbucket 仍然使用個人權杖。

無論是哪一種，這份憑證都是**你的，而且存放在伺服器上**，以你的使用者 id 為鍵：你輸入權杖的那台機器不會儲存任何權杖，你登入的每一部裝置都用同一份憑證，其他成員也讀不到它。它會在**下一次請求**時生效——不需要重啟任何東西，而中斷連接會立刻讓它不再被送出。

卡片會說明你的帳戶在哪裡使用。GitLab 或 Bitbucket 權杖屬於你，並可用於**伺服器上的每個工作區**，因此只需貼上一次。你的 GitHub 登入也是如此，除非某個工作區有自己的登入應用程式：該工作區會保有自己的 GitHub 登入，而卡片會指出它。

每一列都會顯示**你的**憑證狀態。只有你自己的憑證會代表你回應，沒有任何其他東西代替你：

| 列上顯示                                                     | 意義                                                                                                                         |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `已登入為 octocat`                                           | 正在使用你自己的憑證                                                                                                  |
| `未連線`                                                     | 你沒有這個託管平台的憑證                                                                                                     |
| `你以 octocat 身分登入的 GitHub 已失效。請重新登入。`          | 你的登入已在託管平台上過期或被撤銷                                                                                           |
| `已暫停：此工作區的登入服務已變更`                           | 此工作區已切換到另一個登入服務。你的登入會保留，切回去後即可再次使用，因此這裡沒有登入按鈕                                    |
| `暫時無法連線至 GitHub，正在重試。`                          | 暫時性中斷。Control Center 會持續重試，你不需要做任何事                                                                      |
| 一句說明為何無法登入的文字                                   | 例如 `此工作區尚未設定 GitHub 登入。` 或 `此工作區的登入服務變更了身分，需要管理員確認。` 管理員會看到一個按鈕，可直接前往修正此問題的設定 |

### 各託管平台需要什麼權杖

| 託管平台      | 權杖                                                                                                    | 建立位置                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **GitLab**    | 具備 `api` 範圍的個人存取權杖                                                                             | gitlab.com → User settings → Access tokens                |
| **Bitbucket** | Atlassian API 權杖，外加你的帳號電子郵件                                                                  | id.atlassian.com → Security → API tokens                  |

Bitbucket 會以你的**帳號電子郵件作為使用者名稱**、API 權杖作為密碼來驗證，因此 Bitbucket 對話框會同時要求這兩項。Bitbucket 的儲存庫、專案或工作區**存取權杖**不屬於任何人，因此此對話框會拒絕它：它是[自動化權杖](#新增自動化權杖)，應改在那裡新增。GitLab 的**專案**或**群組存取權杖**也是如此：儲存前 GitLab 會詢問此權杖屬於誰，而機器人的權杖在這裡會被拒絕。

權杖絕不會綁定單一工作區：每個託管平台你只持有一組，伺服器上的每個工作區都會使用它。**中斷連線**會將它從所有工作區移除。

### 背景工作

背後沒有真人操作的工作（代理執行、管線、PR 輪詢）同樣需要憑證，而每個託管平台的處理方式各不相同：

- **GitHub** —— 每次一個只適用於單一儲存庫的權杖，由伺服器的 GitHub App 或透過 Connect 簽發，並限制在某位負責成員在那裡能做的事之內。它絕不是把某個人的登入整個交出去，也沒有任何環境變數或貼上的權杖能替代它。請見[設定 GitHub 整合](/zh-TW/手冊/操作指南/github-整合/#你的憑證代表誰)
- **GitLab** 與 **Bitbucket** —— 只使用該儲存庫的**自動化權杖**：工作區管理員為該儲存庫、或為工作區中該託管平台上的每個儲存庫所新增的機器人存取權杖。儲存庫自己的權杖優先於工作區的權杖。PR 輪詢、AI 審查留言，以及沒有人請求的推送與合併請求，都會使用它，因此在託管平台上它們會顯示為該機器人，絕不會顯示為某位成員。沒有任何成員的個人權杖能替代它，也沒有伺服器範圍或環境變數權杖。沒有自動化權杖時，該儲存庫的背景工作會暫停，而儲存庫存取通知會說明這一點。

成員請求的工作（留言、審查，或為其開啟的代理合併請求）仍使用該成員自己的權杖。

## 新增自動化權杖

只有工作區管理員能看到或變更自動化權杖。儲存時會與託管平台逐一核對每個權杖：以人的身分行事的權杖會被拒絕（GitLab 個人存取權杖、Atlassian API 權杖，或任何以某人帳號登入的 Bitbucket 權杖），無法讀取其所對應儲存庫的權杖也會被拒絕。

- **針對單一儲存庫：** 開啟**設定 → 工作區 → 存放庫**。**自動化權杖**卡片會列出每個 GitLab 與 Bitbucket 儲存庫，以及在那裡行動的機器人、**使用工作區的權杖**，或**沒有權杖。此處的自動化已暫停。**在該儲存庫的列上按**新增權杖**。
- **針對某個託管平台的每個儲存庫：** 開啟**設定 → 工作區 → 整合**，找到**自動化權杖**卡片，並在 GitLab 或 Bitbucket 列上按**新增權杖**。儲存後，權杖無法讀取的儲存庫會被指名，並保持暫停。

當背景工作已經暫停時，管理員也會在儲存庫存取通知上直接看到**新增權杖**。**更新權杖**會替換權杖；垃圾桶按鈕會移除它，而任何因此沒有權杖的儲存庫都會暫停。若託管平台之後拒絕了已儲存的權杖（已撤銷或已過期），該列會說明此事，而它所涵蓋的儲存庫會暫停，直到你替換它為止。

| 託管平台      | 自動化權杖                                                                                               | 建立位置                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **GitLab**    | 一個**專案**或**群組存取權杖**，具有 `read_api` 與 `read_repository`；若要留言、合併請求與推送，請加入 `api` 與 `write_repository` | 專案或群組 → Settings → Access tokens                          |
| **Bitbucket** | 一個**儲存庫**、**專案**或**工作區存取權杖**，具有儲存庫讀取權限，並具有用於留言與 pull request 的 pull request 寫入權限（推送則需要儲存庫寫入權限） | 儲存庫、專案或工作區 → Settings → Access tokens                |

GitLab 會以權杖的機器人使用者顯示這些工作；Bitbucket 則會以存取權杖的名稱顯示。

### Bitbucket：存取權杖或 API 權杖

Bitbucket 有兩種權杖，Control Center 會將它們分開：

- **API 權杖**（id.atlassian.com）屬於你的 Atlassian 帳號，並與你的電子郵件一起使用。它是**你的**憑證，放在**設定 → 你 → 個人資料**中的**程式碼託管**下。
- **存取權杖**（在儲存庫、專案或工作區的設定中建立）屬於該儲存庫、專案或工作區，而非某個人。它是**自動化權杖**，放在**自動化權杖**下。

每個對話框都會拒絕另一種權杖，並說明它應該放在哪裡。

## 你在每個託管平台上是不同的人

同一個人在 GitHub 上是 `octocat`，在 GitLab 上則完全是另一個名字。Control Center 會**依託管平台**解析你的身分，並為每個儲存庫使用正確的那一個；這正是「需要我審查」、「由我建立」與「你已核准」在混合式工作區中仍然正確的原因。

如果某個託管平台的身分尚未解析出來，它的儲存庫對收件匣的貢獻就是零，而不是什麼都符合。收件匣會如實說明，而不是宣稱你已經全部處理完畢。

## 你只能看到你自己的帳號能看到的內容

只有當你的工作區角色允許該儲存庫，**而且你在該託管平台上的帳號也能讀取它**時，該儲存庫的 pull request 才會送到你面前。工作區管理員與擁有者也遵循同一規則。當某些儲存庫被隱藏時，收件匣與 PR 佇列會說明數量與原因，但不會指名：

- **登入 GitHub 即可查看另外 3 個存放庫的 pull request**：你還沒有在這裡連接該託管平台。登入後它們就會出現
- **有 3 個存放庫已隱藏，因為你的 GitHub 帳號看不到它們**：請向在該託管平台上有存取權限的人求助
- **有 3 個存放庫已隱藏，因為你在此工作區中沒有存取權限**：請向工作區管理員申請存取權限
- **正在檢查你對另外 3 個存放庫的存取權限…**：Control Center 確認你的帳號能讀取哪些存放庫時短暫顯示

程式碼也遵循同一規則。要開啟某個儲存庫的檔案、差異比對或搜尋，或在其上開啟終端機，你必須在此工作區中持有它的授權，而且你自己的託管平台帳號也必須能讀取它；工作區管理員同樣如此，只有伺服器擁有者例外。當無法連到託管平台進行檢查時，你會看到「無法確認你的程式碼代管平台存取權限。請再試一次。」（並會指出是哪個託管平台）。參見[程式碼跟隨託管平台](/zh-TW/手冊/概念/授權/#程式碼遵循託管服務)。

同一規則涵蓋了由這些 pull request 產生的所有東西。在你看不到其 pull request 期間，審查空間、它的訊息與代理執行都會消失；若你失去存取權限，已開啟的審查空間也會關閉。與隱藏的 pull request 有關的管線執行，會從你的執行清單中移除。替你工作的代理同樣無法讀取那些審查空間。工作區的儲存庫清單會顯示你在此工作區中可存取的每一個儲存庫，即使你的託管平台帳號尚無法連到其中某個。

若託管平台限速或故障，Control Center 會繼續顯示它最後確認過的內容幾分鐘，然後隱藏那些 pull request，直到它能再次檢查為止。

## 一個收件匣，涵蓋所有託管平台

收件匣與 PR 佇列會分散查詢工作區中出現的每一個託管平台，並把結果合併成單一流程——GitHub 的 pull request 與 Bitbucket 的 pull request 會並排出現，依時間排序，而不是依供應商分組。

失敗是彼此隔離的。某個託管平台若故障或受到速率限制，它不會影響其他平台，它自己的儲存庫會持續顯示最後已知的狀態，直到它恢復為止；它絕不會讓整個收件匣清空。若伺服器已無法連到某個儲存庫，該儲存庫會從清單中移除，而不是顯示過時的 pull request，並且**儲存庫存取通知**會指出它以及修正方法：在其組織上安裝 GitHub App、把儲存庫加入 App 的儲存庫清單、恢復被暫停的安裝、請負責成員重新登入，或為 GitLab 或 Bitbucket 儲存庫新增自動化權杖。管理員會看到 GitHub App 相關步驟與新增權杖的按鈕。

## 各託管平台能做什麼

每個託管平台都支援核心循環：列出並開啟 pull request、讀取差異、行內與頂層留言、審查、合併與關閉。除此之外，它們確實各有差異，而 Control Center 會把託管平台做不到的事藏起來，而不是顯示一個會悄悄失敗的控制項。

| 能力                              | GitHub | GitLab | Bitbucket |
| --------------------------------- | :----: | :----: | :-------: |
| 批次（待送出）審查                |   ✓    |   ✓    |     —     |
| 要求變更                          |   ✓    |   ✓    |     ✓     |
| 每個檔案的「已檢視」狀態會同步    |   ✓    |   —    |     —     |
| 表情回應                          |   ✓    |   ✓    |     —     |
| 團隊／群組審查者                  |   ✓    |   ✓    |     —     |
| 建議審查者                        |   ✓    |   —    |     ✓     |
| PR 上的 CI 結果                   |   ✓    |   ✓    |     ✓     |
| 深入檢視 CI 工作的步驟／記錄      |   ✓    |   ✓    |     —     |
| 堆疊式 pull request               |   ✓    |   —    |     —     |
| PR 說明範本                       |   ✓    |   ✓    |     —     |
| 通知輪詢                          |   ✓    |   —    |     —     |
| 豐富的使用者設定檔                |   ✓    |   ✓    |     —     |
| 伺服器端的 PR head ref            |   ✓    |   ✓    |     —     |

當某項能力缺席時，功能的退化方式是誠實的：

- **已檢視狀態**仍然可用，但只限於你設定它的那部裝置。
- Bitbucket 上的**批次審查**會一則留言一則留言地張貼，因此審查者看到的是它們逐一送達，而不是一次全部出現。
- Bitbucket 上**沒有 PR head ref**，代表檢出某個 pull request 時會依名稱抓取它的來源分支，而該分支一旦被刪除就會失敗。

## 用語

GitLab 把 pull request 稱為 **merge request**。Control Center 在自己的模型中一律說「pull request」，而在談論某個託管平台時，則使用該平台自己的說法。

## 疑難排解

### PR 清單是空的，並顯示某個託管平台未連接

你沒有那個託管平台的憑證。請在**設定 → 你 → 個人資料 → 程式碼託管**中登入 GitHub，或貼上 GitLab 或 Bitbucket 權杖。其他託管平台的儲存庫不受影響。

### 我連接了託管平台，但它的儲存庫仍然什麼都沒顯示

檢查該列的狀態，然後看 PR 清單上方的通知。「登入……即可查看另外……個存放庫的 pull request」表示你自己的帳號尚未連接那些儲存庫；「……個存放庫已隱藏，因為你的……帳號看不到它們」表示託管平台不給你存取權限。若是 GitHub，儲存庫存取通知會告訴你 GitHub App 是否未安裝在該儲存庫的組織上，或未包含該儲存庫。

### 在 GitLab 或 Bitbucket 儲存庫上，背景工作已暫停

該儲存庫沒有能讀取它的自動化權杖。工作區管理員會為該儲存庫或整個工作區新增一個；請見[新增自動化權杖](#新增自動化權杖)。你自己的個人權杖無法解除暫停：背景工作絕不使用成員的權杖。

### 儲存庫無法註冊

註冊需要同時滿足三項條件：路徑位於 git 工作樹內、具有 `origin` 遠端，且該遠端指向 github.com、gitlab.com 或 bitbucket.org。`origin` 還必須是你正在連結的儲存庫，而位於工作區自身儲存空間之外的資料夾，只能由伺服器擁有者連結。請見[將儲存庫加入工作區](/zh-TW/手冊/操作指南/新增儲存庫/)。

### 我有授權，但儲存庫表示我的帳號無法讀取它

你自己的託管平台帳號無法讀取該儲存庫，因此無論工作區授予什麼權限，它的程式碼對你都保持關閉。請在上方的**程式碼託管**中登入該託管平台，或在託管平台上取得該儲存庫的存取權限。

### 「無法確認你的程式碼代管平台存取權限」

Control Center 無法連到託管平台來檢查你的存取權限，因此它會拒絕而不是猜測。請稍後再試一次。

### 某個儲存庫表示它現在指向另一個儲存庫

該路徑背後的儲存庫已經改變：它被刪除後重新建立，或被移動後又被取代。在工作區管理員於通知或儲存庫列上按下**重新連結**之前，Control Center 不會對它送出任何東西。單純的更名或轉移會自動跟隨，不會顯示此情況。

### 大量使用之後，所有東西都會停擺一陣子

那是速率限制的斷路器。當某個託管平台發出已觸及主要限制的訊號時，用戶端會在本地直接讓後續請求失敗，不發出任何網路呼叫，直到該時間窗過去為止——因此重試風暴不會讓限制更加嚴重。暫時性失敗會以指數退避重試。
