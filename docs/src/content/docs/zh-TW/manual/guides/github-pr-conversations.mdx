本指南說明如何在不必離開 GitHub 的情況下與 Control Center 協作：直接從 PR
頁面要求 AI 審查、在留言中向機器人提問，並在它的審查討論串中持續對話。

回覆會經由工作區的 GitHub 通道送出：你伺服器自己的
[GitHub App](/zh-TW/手冊/操作指南/github-app/)，或透過 Connect 使用的 Control Center
共用 App。不需要註冊任何新東西，也沒有任何東西
必須能從網際網路連線：伺服器以輪詢方式得知 GitHub 上說了些什麼，因此位於 NAT
後方的筆記型電腦，行為與公開部署完全相同。

## 先決條件

- 工作區有一條 GitHub 通道：伺服器自己的 GitHub App 或 Connect，且該 App 已
  [安裝](/zh-TW/手冊/操作指南/github-app/#安裝到你的儲存庫所在之處)在擁有該儲存庫
  的帳號上。自己的 App 需要 **Pull requests** 與 **Issues** 的讀取與寫入權限，
  **建立我的 GitHub 應用程式**已經授予這些權限
- 儲存庫已連結到 Control Center 中的某個工作區
- 你已在這台伺服器上[登入 GitHub](/zh-TW/手冊/操作指南/github-整合/)，而且你可以
  推送到該儲存庫
- 不需要 webhook URL、不需要通道、不需要回呼 — 網路端沒有任何要設定的東西

## 找出機器人的名稱

提及 `@usectrl`，這是 Control Center 專用的 GitHub 帳號。它是唯一的觸發方式：提及 App 自己的登入名稱不會有任何作用。工作區的 GitHub 通道仍會處理請求並發布回覆。你不需要 `usectrl` 帳號的憑證。

## 從 GitHub 要求審查

有兩種方式，兩者都會啟動與 **詢問 AI** 按鈕相同的那條預置 `pr_review` 管線：

- **為 PR 加上 `ai-review` 標籤。這是 GitHub 所能提供、最接近把機器人指派為
  審查者的做法 — App 帳號無法佔用原生的要求審查者欄位。你的帳號會在該 PR 上
  加上 👀 表情回應，審查會在 Control Center 中啟動；不會張貼任何留言
- **在 PR 對話中留言 `@usectrl review`**（或只寫 `@usectrl`）。你的留言上會出現 👀，
  接著會有一則回覆說明審查已經開始（或告知已經有一個正在執行）

審查者會在該 PR 的審查空間中工作；閱讀與發佈發現的方式與
[使用 AI 審查](/zh-TW/手冊/操作指南/ai-審查/)相同。發佈回 GitHub
始終是你在 Control Center 中做的決定 — 從 GitHub 啟動審查本身不會把任何
內容發佈到 GitHub。

標籤對每個 PR 只會觸發一次：加上它就算是提出要求，而移除後再重新加上並不會
重新觸發。若要再次執行審查 — 例如在一次推送之後 — 請提及機器人。

## 提問

在 PR 對話中留言：

```text
@usectrl why does the flaky test in runner_test.dart fail on CI but not locally?
```

接下來會依序發生的事：

1. 你的留言上會出現一個來自你自己帳號的 👀，讓你知道這則留言已被看見
2. 問題會**以你的身分**張貼到該 PR 的審查空間 — 歸屬與你直接在 Control Center
   中輸入時相同
3. 某個代理會在該空間中回答，而答案會張貼回該 PR。每則回覆都以
   `**Control Center** (for @your-login):` 開頭

對尚未經過審查的 PR 提問，會喚醒工作區的 CEO 代理；一旦執行過審查，就會由
最後發言的代理回答，因此後續追問會落在掌握脈絡的那一位身上。

## 在審查討論串中後續追問

在機器人參與的行內審查討論串中回覆 — 可能是它留下的差異留言，或它在該討論串
中張貼的答案。不需要提及；討論串**本身**就是定址方式：

```text
> @usectrl the retry loop looks O(n²) to me

what would the complexity be with the bounded queue instead?
```

多輪對話的運作方式相同：每一次回覆都是同一段對話中的另一個問題，以該審查空間
作為脈絡，而答案會回到該討論串中。

在 PR 對話時間軸上的追問是一則新的最上層留言，因此仍然需要 @提及。

## 機器人會與誰對話

伺服器會先解析留言的作者，或加上 `ai-review` 標籤的人，才會進行任何動作：

- **該 GitHub 帳號必須已在這台伺服器上登入。** 比對依據是 GitHub 的數字帳號
  ID，絕不是登入名稱。請從 **設定 → 你 → 個人資料 → 程式碼託管** 登入
- **此人必須是具備寫入角色**（`member`、`admin` 或 `owner`）的成員，且隸屬於
  連結該儲存庫的工作區
- **此人必須能在 GitHub 上推送**到該儲存庫。回覆使用的權杖被限制在此人的存取權
  內，因此只能讀取的人不會得到回覆

其他任何人都會被靜默忽略：不會張貼任何內容，而他們說的話永遠不會進入該工作區。
來自機器人的留言，以及 Control Center 自己的回覆，永遠不會被當成問題處理。

### 兩台伺服器，一個 PR

👀 也是各伺服器協議由誰回答的方式。它是用作者自己的登入加上的，而 GitHub 會告訴
伺服器這個表情回應是不是新的。如果你在兩台都連結了該儲存庫的 Control Center
伺服器上登入，先加上表情回應的那台會回答，另一台則保持沉默。標籤也是如此。

## 預期情況

| 項目 | 行為 |
| --- | --- |
| 確認 | 在一輪掃描內，由你的帳號在留言上（若是標籤則在 PR 上）加上 👀 |
| 答案 | 發佈在提問所在的對話串中，以 `**Control Center** (for @your-login):` 開頭。作者是該 App 的機器人。在共用的 Connect App 上，審查討論串中的回覆由你自己的帳號發佈，除非 Connect 營運者已將此安裝列入清單 |
| 空間內的歸屬 | 問題算在你頭上；代理代表你執行，並受該空間的自主程度設定約束 |
| 審查 | 發現會落在審查空間中；發佈到 GitHub 須由人工進行 |

使用自己的 App 時，每分鐘掃描一次，最多檢查 25 個 pull request；透過 Connect 時，
每兩分鐘掃描一次，最多檢查 10 個，因為這些呼叫共用每位成員自己的 GitHub 配額。
GitHub 配額剩餘不到 15% 的工作區會被略過，直到配額恢復。這樣的延遲，就是換取
完全不需要任何傳入網路存取所付出的代價。伺服器離線期間也不會遺失任何東西 —
在停機期間到達的留言，會在下一次掃描時被補上。

## 疑難排解

**提及機器人的留言卻毫無動靜。**

- App 是否已**安裝**在擁有該儲存庫的帳號上，且該儲存庫已**連結**到某個工作區？
  未連結的儲存庫會在記錄任何內容之前就被跳過，因此之後再連結它仍然會送達
- 你是否已在這台伺服器上登入 GitHub、是具備寫入角色的成員，而且能推送到該儲存庫？
  其他任何人都會被伺服器忽略，不會收到回覆
- 還是沒有動靜？伺服器日誌會在出錯時記下該次掃描與該 PR；請尋找
  `pr_conversation:`（輪詢器）與 `github_pr_conversation:`（橋接器）

**標籤沒有啟動審查。**

它每個 PR 只會觸發一次，而加上它的人要通過與留言作者相同的檢查。如果審查已經
執行過，或標籤是在伺服器第一次看到該 PR 之前就加上（第一輪掃描會靜默記錄待處理
的內容，而不是一次全部湧入），請改為提及機器人 — `@usectrl review` 一律會啟動
一次審查，除非已經有審查正在進行中。

**機器人的答案始終沒有送達 GitHub。**

答案本身永遠不會遺失 — 它就在 Control Center 中該 PR 的審查空間裡。發佈失敗
（GitHub 故障、權限變更）會被記錄下來，而且不會重試該回覆；如果這件事很重要，
請在討論串中再次提問。
