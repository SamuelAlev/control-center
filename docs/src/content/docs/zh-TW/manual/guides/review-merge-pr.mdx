本指南說明如何審查並合併一個 pull request。

## 開啟 PR 工作台

1. 在側邊欄中前往 **Pull requests**
2. 從清單中選擇一個 PR

PR 會以分頁式工作台開啟，而不是單一頁面。預設會依下列順序開啟五個分頁：**總覽**、
**Diff**、**原始檔控制**、**聊天**與**動作**（依工作流程分組的 CI 檢查）。**檢閱**——
先顯示檢閱管線的進度，再顯示它所發佈的成品及一旁的發現側欄——刻意不在這五者之列：
在有人請求之前，PR 沒有任何檢閱，因此由**詢問 AI** 開啟它。終端機、單一檔案編輯器、
內嵌的 code-server 與應用程式內建瀏覽器都按需開啟；在 PR 上偵測到預覽 URL 時，會自動
注入部署預覽分頁。你的分頁配置會以每個 PR 為單位記住。

**總覽**分頁承載 PR 的中繼資料（作者、分支、標籤、指派對象、表情回應、提交、檢查狀態）
以及操作列：重新整理、**檢閱**、**合併**、在 IDE 中開啟，以及一個 ⋯ 溢出選單。

## 閱讀差異

開啟 **Diff** 分頁，即可一次看到整個 PR 的差異，並有一個可在檔案之間跳轉的檔案樹。

- 差異工具列中的設定按鈕可在**並排**（左右並置）與**整合**檢視之間切換，並切換自動
  換行與程式碼字型連字。
- `@@` 差異區塊標頭會替換為 **Show N lines** / **Show end of file** 控制項，點擊後會把
  周圍的上下文拼接進來。
- 按 `j` / `k` 在檔案之間逐一步進，按 `c` 摺疊或展開聚焦的檔案，按 `t` 讓側邊欄回到
  檔案樹，按 `⌘F` 在整個差異中搜尋（`Enter` / `Shift+Enter` 巡覽各筆相符項）。
- 按 `v` 將聚焦的檔案標示為已檢視，游標便前進到下一個檔案。在 GitHub 上，已檢視狀態
  儲存在託管平台上，因此會跟著你在各用戶端之間移動；GitLab 與 Bitbucket 沒有這類 API，
  所以在那些平台上它只記憶在本裝置。

在程式碼區域拖曳滑鼠可將選取範圍精確到某一欄，`⌘C` 複製的是原始程式碼，而不是算繪後
的差異標記。

## 留下行內留言

1. 點按程式碼列的行號欄，開啟錨定到該行的撰寫框；若要新增檔案層級的留言，請使用檔案
   標頭上的 `+` 按鈕
2. 以 Markdown 撰寫你的意見
3. 提交

在 GitHub 與 GitLab 上，撰寫框提供兩種提交方式：**新增單則留言**會立即發佈，而
**開始檢閱** / **加入檢閱** 則會把留言排入一份待送出的檢閱，該檢閱會隨**核准**、
**要求變更**或**評論**一起送出。Bitbucket 沒有待送出檢閱的批次處理機制，因此在該平台上
每次提交都會立即發佈。立即發佈在託管平台確認之前會顯示為待處理狀態，接著轉為已同步。
若發佈失敗，該討論串會被標示錯誤，並提供重試。

只有檢閱的_內文_是草稿：它會在你停止輸入片刻後，以 (owner, repo, PR number) 為鍵儲存在
伺服器端，因此能挺過重新載入，並跟著你在桌面與 Web 用戶端之間移動。

## 提交檢閱

1. 在總覽的操作列中按下**檢閱**（在你自己的 PR 上，以及已關閉或已合併的 PR 上，它會
   隱藏）
2. 撰寫檢閱內文。你可以附加圖片、插入表情符號或 GIF，並在撰寫與預覽之間切換
3. 按下**要求變更**、**評論**或**核准**

判定_就是_按鈕本身——沒有另外的判定選擇器。按下**核准**或**要求變更**後，按鈕會自行
改標為**已核准**或**請求的變更**，草稿內文也會被清除。**評論**判定則讓按鈕維持
**檢閱**標籤。

:::caution[提交不可逆]
`pr_review.submitReview` 會發佈到託管平台，且永遠不會進入撤銷堆疊。Control Center 沒有
「取消提交」這種操作。
:::

## 合併

當你擁有寫入權限，且 PR 處於開啟狀態、不是草稿時，**合併**按鈕就會出現。它的顏色是
由必要核准與檢查狀態（ready / pending / blocked）推導出的就緒訊號——僅供參考。這個按鈕
永遠不會因檢閱狀態而被停用；真正強制執行規則的是託管平台自身的分支保護。

1. 按下**合併**以開啟合併彈出面板
2. 選擇一種合併方式：**squash**、**merge commit** 或 **rebase**（預設為 squash）。
   Bitbucket 沒有真正的 rebase 合併，因此 rebase 會對應到它的 fast-forward 策略，並在
   分支已分岔時失敗
3. 若選 squash 或 merge commit，可編輯已預填的提交標題與描述。rebase 兩者皆不接受，
   並會隱藏這兩個欄位
4. 閱讀警告面板——它會列出失敗的檢查與待處理的檢閱，但不會阻擋你
5. 在彈出面板中按下合併按鈕以確認

合併不可逆：它會把提交推送到託管平台，因此它得到的是確認步驟，而不是撤銷項目。之後，
該 PR 的快取會失效，其狀態轉為**已合併**，並觸發一個狀態為 `merged` 的
`PullRequestStatusChanged` 事件。該事件會釋放暫時性的「在編輯器中開啟」工作樹，並啟動
兩條植入的管線：**Stale repository cleanup**，它會移除該 PR 過時的工作樹與對話資料夾；
以及 **Release notes**，它會起草一則變更記錄項目。

:::note[PR 檢閱空間不會自動封存]
檢閱空間對話的自動封存接線到一個獨立的 `PrMerged` 領域事件，目前產品中沒有任何地方會
發出它，因此合併後該空間會保持你離開時的樣子。每日清理掃描仍會回收它的工作樹；如果你
希望它從側邊欄消失，請自行刪除該空間。
:::

## 把 PR 交給審查代理

**總覽**分頁上的 ⋯ 溢出選單帶有**詢問 AI**，它會為此 PR 啟動植入的 `pr_review` 管線。
它只在 PR 處於開啟狀態時才會出現。這條管線會做什麼、以及如何發佈它的發現，請見
[使用 AI 審查](/zh-TW/手冊/操作指南/ai-審查/)；確定性的群組與軸模型請見
[審查運算](/zh-TW/手冊/操作指南/審查運算/)。

## 審查外部 PR

Control Center 也會匯入由應用程式外部的人所開啟的 PR。上述的審查流程完全相同。外部 PR
由 PR 輪詢服務偵測。
