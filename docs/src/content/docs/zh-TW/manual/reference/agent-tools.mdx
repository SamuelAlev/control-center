這些是內建代理執行階段直接登錄的**伺服器端繫結**工具——語言伺服器、結構化搜尋、除錯工具、核心、程式碼模式指令碼、提問與工作程序控制——有別於它橋接進來的 [MCP 工具](/zh-TW/手冊/參考/mcp-工具/)，以及來自執行環境的通用檔案、搜尋與 shell 工具。它們不在 MCP 登錄表中：外部的 MCP 用戶端看不到它們，因為每一個都繫結到一個存活的伺服器端資源——語言伺服器行程、除錯配接器、直譯器——而那個資源屬於某一次執行。

這裡的每一個工具，都只有在它的後端資源已為該次執行接上時才會登錄——語言伺服器或除錯監督程式、tree-sitter 剖析器、核心工廠、提問埠、vibe 名冊。針對*這次簽出*偵測語言伺服器或除錯配接器，是另一項較晚進行的檢查（`status` / `adapters`）：這些工具會留在工具介面上，讓代理可以問為什麼什麼都不可用，而不是憑空猜測。

## 核准層級

每個工具都會宣告一個層級，而層級決定的是**哪些介面看得到它**——不只是它是否會跳出提示。計畫模式與唯讀子代理的上限是 `read`，因此 `write` 或 `exec` 層級的工具，會完全不存在於它們的結構描述中。

| 層級    | 意義                                   | 這裡的工具                                         |
| ------- | -------------------------------------- | -------------------------------------------------- |
| `read`  | 沒有副作用                             | `lsp`、`ast_grep`、`ask_user`、`repl`、五個 `vibe_*` |
| `write` | 會變更檔案                             | `lsp_rename`、`ast_edit`、`resolve`                |
| `exec`  | 會啟動或控制一個行程                   | `debug`、`eval`                                    |

## 直接、僅指令碼或首次使用時載入

當伺服器能執行指令碼時，執行會直接呼叫少數工具，其餘工具則透過[`repl`](#repl--執行呼叫你工具的指令碼)指令碼觸及；完整規則請參閱[程式碼模式](/zh-TW/手冊/概念/程式碼模式/#代理直接呼叫哪些工具)。本頁工具的情況如下：

| 工具 | 有 `repl` | 沒有 `repl` |
| ---- | ----------- | -------------- |
| `repl` | 直接呼叫 | 不提供 |
| `ask_user` | 直接呼叫 | 直接呼叫 |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | 只能由指令碼呼叫 | 首次使用時載入 |
| `eval` | 首次使用時載入（指令碼不能呼叫它） | 首次使用時載入 |
| `vibe_*` | vibe 模式中直接呼叫，絕不由指令碼呼叫 | vibe 模式中直接呼叫 |

標示為「只能由指令碼呼叫」的工具，在伺服器無法執行該次執行的指令碼後，會改為在首次使用時載入（參閱[無法執行指令碼時](/zh-TW/手冊/概念/程式碼模式/#無法執行指令碼時)）。

## `lsp` — 語言伺服器查詢

當執行具有語言伺服器監督程式與工作目錄時登錄。伺服器是否真的能作答，是在呼叫當下以**交集**方式偵測的：根標記必須存在，*而且*伺服器執行檔必須能解析得到。只有其中一項成立，就代表不會有任何伺服器啟動——`status` 會如此說明——而不是默默猜測。

伺服器只來自內建表格；儲存庫的 `lsp.json` 不會被讀取。在沙箱化的執行中，每次執行都有自己的語言伺服器工作階段，因此伺服器會隨每次執行重新啟動。專案本地的執行檔（`node_modules/.bin`）只在執行被沙箱化時才會使用，而且專案根目錄絕不會解析到該次執行工作目錄之上。

位置是以 `line` 加上 `symbol` 子字串來指定，永遠不靠欄。被要求提供欄位的模型只能用猜的，而猜錯會解析到同一行上的另一個符號——一個看起來正確、實際上卻在講別的東西的答案。在導覽動作中省略 `symbol` 是錯誤，而不是猜測第一欄。

| 動作              | 引數                             | 傳回                                       |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file`（或 `"*"`）                | 錯誤與警告；`"*"` 改為執行專案檢查器        |
| `definition`      | `file`, `line`, `symbol`         | 符號宣告的位置                             |
| `type_definition` | `file`, `line`, `symbol`         | 其型別宣告的位置                           |
| `implementation`  | `file`, `line`, `symbol`         | 具體實作                                   |
| `references`      | `file`, `line`, `symbol`         | 每一處使用，上限 50                        |
| `hover`           | `file`, `line`, `symbol`         | 簽章與文件註解                             |
| `symbols`         | `query` 或 `file`                | 以 `query` 進行工作區搜尋（上限 100）；以 `file` 取得文件符號（上限 200） |
| `code_actions`    | `file`, `line`, `symbol`         | 伺服器提供的快速修正                       |
| `status`          | —                                | 哪些伺服器正在執行，以及各自對應的根       |
| `reload`          | —                                | 為這個根重新啟動伺服器                     |

### 寫入時的診斷

真正的收穫不是這個工具。`write`、`edit` 和 `apply_patch` 都被**包了起來**：寫入之後，檔案會經過語言伺服器同步並儲存，而且只有**新產生**的診斷會併入工具結果。代理會在建置壞掉的那一刻就知道自己弄壞了它，不必記得要去問。

已回報過的診斷會由每次執行的帳本抑制，帳本以嚴重性、代碼和訊息為鍵——刻意排除位置——因此只是往下移了四行的診斷，不會被當成新問題重新回報。

## `lsp_rename` — 專案範圍的重新命名

一個獨立的 `write` 層級工具，理由只有一個：層級決定可見性。把重新命名併入 `lsp`，不是讓唯讀的探索者擁有改寫儲存庫的能力，就是讓每一次 `hover` 都必須先過核准提示。

| 引數       | 意義                                       |
| ---------- | ------------------------------------------ |
| `file`     | 符號所在的位置                             |
| `line`     | 從 1 起算的行號                            |
| `symbol`   | 在該行上識別它的子字串                     |
| `new_name` | 要改成什麼名稱                             |

## `ast_grep` — 結構化搜尋

以**形狀**而非文字來尋找程式碼。`$NAME` 比對任何節點，`$$$NAME` 比對一連串同層節點，而 `$_` 是不繫結任何東西的萬用字元。

讓它是真正的比對器、而不是「多加幾步的 regex」的關鍵性質是：同一個模式中重複出現的中繼變數，必須補抓到相同的文字。

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

會比對到「處置它剛剛檢查過的對象」的防護，而**不會**比對到處置其他東西的防護。

| 引數          | 意義                                                        |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | 帶有中繼變數的程式碼片段                                    |
| `path`        | 要搜尋的檔案或目錄；預設為整個工作區                        |
| `language`    | 隨附的文法 id（`dart`、`python`、`rust`、`c`、……）。當 `path` 指向檔案時會自動推斷 |
| `max_results` | 預設 50                                                     |

:::note[模式是以和檔案相同的文法剖析的]
因此 `dispose(x)` 找得到那個呼叫，不管它怎麼排版、換行或加上註解——也永遠不會比對到字串常值或註解裡相同的字元。
:::

:::caution[片段是在鷹架中剖析的，而不是赤裸地剖析]
`dispose(x)` 在 Dart 最上層剖析時，是完全合法的*函式簽章*。模式編譯器會依序嘗試一連串情境（陳述式、運算式、類別成員、宣告），並採用第一個接受該片段的。沒有任何情境接受的模式，會被回報為無法剖析，而不是被搜尋後無聲無息地判定找不到。
:::

## `ast_edit` — 結構化重寫，先暫存

相同的比對方式，再加上一個 `rewrite` 範本，把中繼變數替換回去。**不會寫入任何東西。** 變更會被暫存，而結果中會有一個 `edit_id`。

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| 引數       | 意義                                                |
| ---------- | --------------------------------------------------- |
| `pattern`  | 要比對什麼                                          |
| `rewrite`  | 要改成什麼，並替換 `$NAME`                          |
| `path`     | 範圍；預設為整個工作區                              |
| `language` | 語言 id                                             |

## `resolve` — 提交或捨棄暫存的變更

| 引數      | 意義                             |
| --------- | -------------------------------- |
| `edit_id` | 來自 `(proposed)` 結果           |
| `action`  | `accept` 或 `discard`            |

每個檔案都會拿來與暫存當下捕捉到的內容比對，只要**有任何**不符，整份變更都會被拒絕。只套用一半的結構化重寫，會留下一棵在新舊兩種形狀下都編譯不過的樹。

## `debug` — 驅動除錯工具

當執行具有除錯工作階段監督程式、工作目錄與對話 id 時登錄。配接器是否真的能啟動，是在呼叫當下以和語言伺服器相同的交集規則偵測（根標記*而且*執行檔）。`exec` 層級；不具平行安全性（工作階段是跨呼叫的狀態，因此 `continue` 若超車 `stack`，就會讀到一個已經移動過的框架）。

每個對話一個工作階段，並有硬性 TTL（30 分鐘）。第二次 `launch` 會被拒絕，而不是默默取代第一個。在沙箱化的執行中，工作階段會在各輪之間保留其沙箱，直到工作階段結束為止，且最多僅限這 30 分鐘。

| 操作          | 引數                          | 備註                                           |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | 這裡有哪些配接器可用，以及哪些為什麼不可用      |
| `status`      | —                             | 工作階段是否正在執行，以及它停在哪裡           |
| `breakpoints` | `file`, `lines[]`             | 空的 `lines` 會清除該檔案。可以**在**啟動之前設定 |
| `launch`      | `program`, `args[]`           | 啟動程式，並停在你設定的中斷點                  |
| `attach`      | `port`                        | 連線到該次執行自己轉送的連接埠上一個已在執行的被除錯程式；其他連接埠會在任何動作開始前被拒絕 |
| `continue`    | `thread_id?`                  | 執行到下一個停止點                             |
| `pause`       | `thread_id?`                  | 讓它在原地停下                                 |
| `step_over` / `step_in` / `step_out` | `thread_id?` | 前進一步                              |
| `threads`     | —                             | 執行緒 id 與名稱                               |
| `stack`       | `thread_id?`                  | 框架，上限 30                                  |
| `scopes`      | `frame_id`                    | 某個框架上的範圍，各自帶有一個 `reference`      |
| `variables`   | `reference`                   | 子項，上限 50，值上限 400 個字元                |
| `evaluate`    | `expression`, `frame_id?`     | 在該框架自身的範圍內求值                        |
| `output`      | —                             | 被除錯程式的 stdout/stderr，有界                 |
| `terminate`   | —                             | 結束工作階段並終止配接器                        |

### 配接器

| Id        | 命令                       | 根標記                                          |
| --------- | -------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`       | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                 | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                  | `go.mod`                                        |

`debugpy` 在執行被沙箱化時偏好專案本地的 `.venv/bin` 或 `venv/bin`，而不偏好 `$PATH`：`$PATH` 上的 python 是另一個環境，而從錯誤的那一個附加，失敗的方式會讀起來像是程式碼壞了。在未受沙箱限制時，它只使用 `$PATH`，因此儲存庫無法選擇在主機上執行的直譯器。

## `repl` — 執行呼叫你工具的指令碼

當伺服器能執行指令碼時，每次執行都會出現（[當執行具有 `repl` 時](/zh-TW/手冊/概念/程式碼模式/#當執行具有-repl-時)）。指令碼是純 JavaScript，即某個 async 函式的主體，並在其自己的處理程序中、全新且已鎖定的直譯器內執行：沒有檔案系統、網路、處理程序或模組存取權。`repl` 本身屬於 `read` 層級，並會自我把關，因為指令碼發出的每一次工具呼叫都會各自接受檢查。它也出現在 MCP 端點上，供在能執行指令碼的伺服器上執行的代理使用。

| 引數 | 意義 |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | 指令碼。最多 256 KiB |
| `description` | 必填。顯示在對話列上的簡短標籤 |
| `timeout_ms` | 選填。比工作區更短的時間限制，絕不能更長 |
| `max_output_tokens` | 選填。比工作區更小的輸出預算，絕不能更大 |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

`repl` 描述會告訴代理：「不屬於你的直接工具之一的工具，在這次請求中沒有定義。在第一次呼叫它之前，請先以 `describeTool(name)` 或 `searchTools(query)` 查詢它，除非它的確切呼叫格式已在本次對話中向你顯示過。」

`describeTool(name)` 會回傳工具的描述、其宣告、其輸入與輸出結構描述，以及其結果註記（若有）：即指令碼從已完成的呼叫所收到的內容，以工具自己的用語表達。`repl` 描述會列出指令碼可以呼叫的直接工具之註記。結果為 JSON 文字者會以解析後的形式送達，除非其內含超過 131,072 個值；此時它會以文字送達，由指令碼以 `JSON.parse` 解析。外部 MCP 伺服器工具之結果的文字若超過 262,144 個字元，會被截斷，而被截斷的文字不再能解析。

- `tools.<name>(args)` 會透過與直接呼叫相同的篩選、護欄與核准來呼叫工具，並在被拒絕或失敗時以錯誤拒絕。唯讀呼叫可以一起執行；會改變狀態的呼叫則逐一執行，順序與指令碼發出的順序相同。當指令碼的某個呼叫正在等待人員時，該指令碼不會啟動其他任何呼叫。
- `ALL_TOOLS`、`searchTools(query, { limit, namespace })`、`describeTool(name)` 與 `describeNamespace(name)` 用於尋找工具，包括已連接 MCP 伺服器的工具。直接工具集合之外、指令碼可以呼叫的工具，只能由指令碼呼叫；直接呼叫其中一個時，會回傳如何從 `repl` 呼叫它的說明。伺服器一旦無法執行該次執行的指令碼，這類工具便改為在首次使用時載入。
- 查找有限制：查詢最多 1,024 個字元，名稱或命名空間最多 256 個字元，`limit` 介於 0 到 50 之間；每個指令碼最多 200 次查找、合計占用伺服器 2 秒時間，同一工作區的所有指令碼共用 2 秒的查找時間，此時間以每秒返還 0.25 秒的速率補充。超過任一上限後，之後的查找都會失敗。在極大的目錄中，`ALL_TOOLS` 內的描述會平均分享約一百萬個字元，被截短的描述以 `…` 結尾；`describeTool` 則一律傳回完整描述。過大而無法顯示的型別會顯示為 `unknown /* too large to show */`，而未知的名稱會以最接近的名稱回覆。
- 工具會分組到命名空間中：`builtin`（執行環境自身的工具）、`control-center`（Control Center 的工具），以及每個已連接 MCP 伺服器各一個，以該伺服器命名。名稱為 `builtin`、`control-center` 或 `script` 的伺服器，或名稱以 `external-` 開頭的伺服器（不分大小寫，前後有無空白皆然），會列為 `external-` 加上其名稱，且沒有任何工具會位於 `script` 之中。
- 只有指令碼回傳的內容，或傳給 `text()`、`image()` 或 `console.*` 的內容，才會回到代理。超出預算的輸出會保留開頭與結尾，而 `read_output` 可讀取其餘部分。
- `store(key, value)` / `load(key)` 會為同一對話與代理的後續指令碼保存 JSON 值，且僅在指令碼完成時保存。子代理的指令碼沒有儲存空間。
- `await tools.ask_user(...)` 會提出問題；其回答也會加入結果。`sleep(ms)`、`setTimeout`、`limits()` 以及 `models.embed` / `rank` / `classify`（裝置端嵌入）同樣可用。
- `describeTool(name)` 與 `searchTools(query)` 也會為指令碼自身的函式作答，這些函式並非工具：`text`、`image`、`store`、`load`、`sleep`、`setTimeout`、`clearTimeout`、`limits`、`exit` 與 `models.*`，位於命名空間 `script` 之下。
- 無法由指令碼呼叫：`repl`、`eval`、`task`、`checkpoint`、`rewind`、`compact`、`search_tools` 與 `vibe_*` 動詞。
- 腳本可以讀取自己執行的過去紀錄：`history({start, role, tool, limit})` 會分頁讀取對話的逐字稿（每次呼叫最多 50 列；把前一頁的 `next_start` 當作 `start` 傳入）；`outputs()` 列出為此對話與代理儲存的工具輸出；`loadOutput(handle)` 讀取其中一筆的 16,384 個字元。`storedKeys()` 列出已儲存的鍵及其大小。`keep(value, label)` 將大型值儲存為一個輸出，之後的腳本或 `read_output` 都可以讀取；僅在腳本完成時才會儲存（每個值 1 MiB、每次執行 64 個值與 16 MiB）。`limits().returnBudgetChars` 會說明輸出預算還剩多少。唯讀執行（目標檢閱）可以讀取，但不能儲存或 keep。在 Claude Code 與 ACP 上，`history()` 可用，而 `outputs()`、`loadOutput()` 與 `keep()` 會拒絕執行，因為 Control Center 不會保存那些執行的工具輸出。
- 逾時、輸出溢出或呼叫次數上限所產生的錯誤，都會說明如何修正。

一次執行一次只會執行一個指令碼。各項限制及達到限制時的處理，請參閱[程式碼模式](/zh-TW/手冊/概念/程式碼模式/#限制)頁面；每個指令碼都會記錄在 **可觀測性 → 程式碼執行紀錄** 之下。

## `eval` — 持久直譯器

一個 Python 或 JavaScript 儲存格，其變數、匯入項目與已載入的資料都會在多次呼叫之間保留。`exec` 層級；不具平行安全性。不可由 `repl` 指令碼呼叫，且儲存格無法呼叫該次執行的工具：若要從程式碼呼叫工具，請使用[`repl`](#repl--執行呼叫你工具的指令碼)。

| 引數          | 意義                                             |
| ------------- | ------------------------------------------------ |
| `code`        | 儲存格                                           |
| `description` | 必填。逐字稿標籤用的 5–10 個字                   |
| `language`    | `python`（預設）或 `javascript`                  |
| `reset`       | 丟棄目前的直譯器，並先從乾淨的狀態開始           |

- 最後一個運算式會像 notebook 那樣被回顯。
- `display()` 可以運作，pandas 資料框架會以表格形式呈現，而 matplotlib 圖形會以**逐字稿所顯示的影像**回傳。
- 人們直覺就會輸入的 IPython 慣用寫法——`%pip`、`%cd`、`!cmd`、`%%bash`、`%%timeit`——會被改寫成一般程式碼。`%pip` 也會逐出 `sys.modules`，因此下一次 `import` 能看到剛剛安裝的內容。
- 輸出的字元數超過其輸出預算的儲存格，會保留前四分之三與最後四分之一，並以一行說明被捨去的字元與圖片數量。
- 若直譯器在未被要求的情況下結束，下一個儲存格會被告知一次：其先前的變數已不存在。

:::note[核心在哪裡執行]
對話有隔離艙時就在其中執行，否則在主機上該次執行的作業系統沙箱中執行。在沙箱關閉或無法使用時，它會不受限制地執行，而 `eval` 會要求主機執行核准。它**不會**為了做到這件事而啟動隔離艙——這和阻止機台分頁自動啟動的是同一條規則。
:::

## 背景中的 `bash`

`bash` 搭配 `run_in_background: true` 會啟動指令，並立即回傳一個控制代碼（`b1`、`b2`、…），而不是等待。代理可以繼續工作，或結束回合，並在指令結束時被喚醒。

| 引數 | 意義 |
| ------------------- | ------- |
| `run_in_background` | `true` 表示立即啟動並回傳 |
| `timeout_seconds` | 指令被終止前的秒數：預設為 600，最多 3,600 |
| `notify` | 選用。一個簡單的比對模式；指令執行時，每一符合的輸出行都會送給代理（例如 `listening on\|FAILED`） |

- 同一次執行中最多同時有 4 個背景指令。每個指令都會在逾時時被終止，並在執行結束時連同它啟動的所有程序一起被終止。
- 指令結束時，代理會收到一則通知，內容包含結束代碼、輸出的最後 2,000 個字元，以及用於取得其餘輸出的 `read_output` 控制代碼。
- 若代理剩下的唯一工作是背景指令，它會在不呼叫模型的情況下等待，且執行的靜默看門狗會在等待期間暫停。
- `bash_output(handle)` 會讀取指令的狀態與最近的輸出；`bash_kill(handle)` 會停止它。兩者都會說明結果是否已經送達。
- 腳本無法啟動背景指令。Claude Code 有自己的背景 Bash；Control Center 會在留下工作未完成的那個回合之後，最多讓該次執行保持開啟 10 分鐘。

## `compact` — 騰出上下文視窗的空間

在下一次模型呼叫之前，壓縮對話較早的上下文，並保留 `focus` 指定的內容（最多 1,000 個字元）。最新的回合會保持逐字保留。代理每回合的預算列會顯示上下文使用量達 70%、80% 與 90%，而在一段長期新工作開始前，超過約 70% 時呼叫此工具會有幫助。伺服器擁有者的 `preCompact` 掛鉤可以補充重點（[Shell 掛鉤](/zh-TW/手冊/參考/代理設定/#shell-掛鉤)）。壓縮之後，伺服器會加入一個「Still in flight」區塊：目標、等待中的喚醒、進行中的提問、背景指令、檢查清單與已儲存的鍵，每一項都附上可復原它的呼叫。

## `ask_user` — 向人類提問

`read` 層級。這是一次執行向操作者提問的**唯一**途徑。它會在對話中呈現一張編號卡片，並封鎖直到有人回答、略過，或問題逾時。絕對不要把問題寫成聊天訊息——那會結束這個回合。

| 引數              | 意義                                       |
| ----------------- | ------------------------------------------ |
| `question`        | 要問什麼                                   |
| `context`         | 選填：你為什麼要問，以及答案會影響什麼     |
| `options[]`       | 選項，每一項為 `{label, description?}`     |
| `allow_free_text` | 是否接受手動輸入的答案                     |
| `multi_select`    | 是否可以選擇多個選項                       |

略過也算成功：依一項明確陳述的假設繼續進行，不要再問一次。逾時是錯誤，並附帶同樣的指示。權限提示（「我可以做這件事嗎？」）是另一道關卡，並在對話中以相同的卡片呈現。

只有在提問埠與目標空間都存在時才會登錄。在沒有連接任何人的情況下，這個呼叫會**失敗**，而不是永遠封鎖——這與護欄 `prompt` 在沒有連接任何核准者時所採取的失效即拒絕姿態相同。

## `vibe_*` — 指揮背景工作程序

只有在 [vibe 模式](/zh-TW/手冊/操作指南/指揮背景工作程序/)開啟時才會登錄。五個全部都是 `read` 層級：閘門應該設在工作程序的工具上，因為實際的編輯是在那裡發生。

| 工具         | 引數                                     | 備註                                        |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | 立即回傳；工作程序繼續執行                  |
| `vibe_send`  | `worker_id`, `message`                   | 附加到簡報並重新執行                        |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | 封鎖直到它定案                              |
| `vibe_kill`  | `worker_id`                              | 將它停止                                    |
| `vibe_list`  | —                                        | 層級、狀態、經過時間與最近一次結果          |

`tier` 是 `fast`（規格明確的機械性工作）或 `good`（設計、判斷，或審查 `fast` 工作程序的產出）。
