## 事件匯流排

`DomainEventBus` 是一條行程內的廣播式發佈／訂閱匯流排。發佈方呼叫 `publish(event)`；訂閱者消費帶型別的 `on<T>()` 串流。每個事件都實作 `DomainEvent`，並攜帶 `occurredAt`。

**這條匯流排執行於 `cc_server` 內部。** 每個發佈方與每個存活的訂閱者都在其中。沒有任何用戶端看得見這條匯流排——伺服器會把精選的子集轉送為 `notifications/*` JSON-RPC 訊框，並依工作區成員資格為每個訂閱者篩選。

| 指標                                                        | 數量                                        |
| ----------------------------------------------------------- | --------------------------------------------- |
| 具體的事件類別                                              | 53                                          |
| 原始碼檔案（`packages/cc_domain/lib/core/domain/events/`）  | 14（加上 `domain_event_bus.dart`）          |
| 從未直接發佈的抽象基底                                      | 1（`TaskLifecycleEvent`，一個密封階層）     |

下文目錄中的每個事件都位於這一個目錄；沒有在其他地方宣告的領域事件。

## PR 與審查事件

第一組是 PR 自身的生命週期。第二組是**自己撰寫的 PR 監看**：關於*你*開啟的 PR 的訊號，每個都攜帶 `forUserId`，讓輪詢能把訊號路由給它們所關乎的人，而不是廣播出去。

| 事件                       | 承載內容                                                                 | 觸發時機                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `PullRequestPublished`     | `prId`, `workspaceId`, `repoOwner`, `repoName`                           | 代理開啟 PR                                                                                                                         |
| `PullRequestStatusChanged` | `status`, `workspaceId`, `prId?`, `repoFullName?`, `prNumber?`           | PR 合併／關閉／開啟／重新開啟／已核准                                                                                               |
| `PrMerged`                 | `prId`, `workspaceId`, `agentId`                                         | PR 已合併——僅限合併的狹隘訊號，保留給分析與通知之用                                                                                 |
| `PrReviewRequested`        | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`            | GitHub 要求伺服器使用者審查（通知輪詢，`review_requested`）                                                                         |
| `PrMentioned`              | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`            | 伺服器使用者在 PR 上被提及（通知輪詢，`mention`）                                                                                   |
| `ExternalPrMerged`         | `workspaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`, `mergedByLogin?` | 外部追蹤的（非代理）PR 已合併，由 GitHub 通知輪詢偵測到；對應至 `prMerged` 通知類別                                           |
| `ExternalPrDetected`       | `repoOwner`, `repoName`, `prNumber`, `prTitle`, `author`, `workspaceId?` | 輪詢找到的非代理 PR——僅供管線使用（驅動 `external_pr_welcome`），不會產生通知                                                       |
| `PrHeadChanged`            | `repoOwner`, `repoName`, `prNumber`, `prTitle`, `previousHeadSha`, `headSha`, `workspaceId` | PR 的 head SHA 變動——作者推送了內容                                                                          |
| `ReviewBecameStale`        | `workspaceId`, `spaceId`, `repoOwner`, `repoName`, `prNumber`, `prTitle`, `reviewedHeadSha`, `headSha` | 已完成的 AI 審查不再符合它所審查的 PR。只有在被取代的提交有審查存在時才會觸發，因此它維持為一個訊號，而不是每次推送都發一次提醒 |

## 任務生命週期事件

統一的任務生命週期串流——一次派送的代理執行，以其執行記錄 id 為鍵。每個事件都攜帶 `taskId`、每個任務單調遞增的 `seq`、`workspaceId?`、`agentId?` 與 `phase`；下表只列出額外的欄位。

| 事件                        | 承載內容                      | 觸發時機                                                                                         |
| --------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `TaskDispatched`            | —                             | 任務交給後端執行                                                                                 |
| `TaskRunning`               | —                             | 任務開始產生輸出                                                                                 |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | 任務已停放——另一個任務持有它所需的磁碟路徑鎖                                                     |
| `TaskProgress`              | `note?`                       | 執行中途的進度檢查點                                                                             |
| `TaskMessage`               | `messageType`, `content`      | 串流訊息（text／thinking／tool_use／tool_result／error）；回報於 `progress` 階段之下             |
| `TaskCompleted`             | `summary?`                    | 任務成功完成                                                                                     |
| `TaskFailed`                | `errorMessage`                | 任務因錯誤而結束                                                                                 |
| `TaskCancelled`             | —                             | 任務在完成前取消                                                                                 |

`TaskPhase` 列舉也有一個 `queued` 成員，但沒有任何東西發佈佇列事件——並不存在 `TaskQueued` 類別。任務第一個可觀察到的訊框是 `TaskDispatched`。

## 管線事件

| 事件                   | 承載內容                                      | 觸發時機                                                                    |
| ---------------------- | --------------------------------------------- | --------------------------------------------------------------------------- |
| `PipelineRunCompleted` | `workspaceId`, `pipelineRunId`, `templateId`  | 執行完成                                                                    |
| `PipelineRunCancelled` | `workspaceId`, `pipelineRunId`, `templateId`  | 執行取消（由使用者或系統發起）——刻意的停止，而非錯誤                        |
| `PipelineRunFailed`    | `workspaceId`, `pipelineRunId`, `templateId`, `errorMessage` | 執行失敗                                                     |

只會發佈終態轉換。沒有 `PipelineRunStarted`，也沒有逐步事件：步驟的進度是透過執行本身的資料列，以及它派送之代理的任務生命週期串流送達用戶端，而不是透過匯流排。

## 機台事件

| 事件                | 承載內容                                      | 觸發時機                                                                                                                         |
| ------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `RigClosedEvent`    | `workspaceId`, `rigId`, `reason`              | 機台消失，並附帶其關閉原因；消費者只對 `backendFailure` 採取行動——其他每個原因都是被要求的，或伴隨一個 `RigReaped`              |
| `RigControlChanged` | `workspaceId`, `rigId`, `controller?`         | 有人取得機台的獨佔控制權，或交還控制權（釋出時 `controller` 為 null——事件不會記錄是誰放手的）                                    |

機台**開啟**不是事件。開機完成後，機台的資料列轉為就緒；沒有任何東西被發佈，因此沒有 `RigOpened` 可以訂閱。

## 完全沒有事件的子領域

有幾個從外部看起來像是事件驅動的子系統，其實並不是。這裡列出它們，是因為它們的缺席是一項設計決策，值得你在尋找某個掛鉤之前先了解：

| 子領域              | 狀態改以何種方式流動                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| 記憶                | `record_memory_fact` 等函式寫入後就回傳；回想則是讀取。無論是事實或衝突，都沒有任何東西會發佈            |
| 編排                | 提案、其核准，以及產生的管線執行，都是資料列與 RPC 呼叫                                                 |
| 計畫文件            | `submit_plan` 寫入一個修訂版本；核准則具體化為一次編排。兩者都不會公告                                  |
| 成品                | `publish_artifact` / `revise_artifact` 直接寫入修訂版本                                                 |
| 核准                | 升級是在核准工作流程服務內部處理                                                                        |
| 工單同步            | 供應商協調器訂閱上述工單事件；傳入的 webhook 則直接套用                                                  |
| 日曆重新整理        | 同步會 upsert 活動，用戶端再重新讀取；沒有重新整理的廣播                                                |
| 工作樹合併          | 記錄在 `worktree_merge_log`，並從那裡讀取                                                               |

## 通知對應

在伺服器上，`NotificationFeedRecorder` 與 `RemoteEventForwarder` 把這些事件轉成 `notifications/*` 線上訊框（`notification_wire.dart`）。在用戶端，`RpcNotificationMapper` → `mapNotificationFrame` 會把訊框轉成 `AppNotification`。

通知類別正好有**十六個**。有幾個事件會對應到多個線上方法，因為訊框承載的是轉折（失敗還是已恢復），而類別承載的是問題（「CI 現在怎麼了？」）。

| 類別                   | 來源事件                  | 線上方法                                                                 |
| ---------------------- | ------------------------- | ------------------------------------------------------------------------ |
| `newMessage`           | `MessageReceived`         | `notifications/message_received`（提及你）                                  |
| `agentRunCompleted`    | `MessageReceived`         | `notifications/message_received`（`is_agent_message`，未提及你）              |
| `ticketAssigned`       | `TicketAssigned`          | `notifications/ticket_assigned`                                        |
| `ticketStatusChanged`  | `TicketStatusChanged`     | `notifications/ticket_status_changed`                                  |
| `pullRequestPublished` | `PullRequestPublished`    | `notifications/pr_published`                                           |
| `prMerged`             | `PrMerged`                | `notifications/pr_merged`                                              |
| `prMerged`             | `ExternalPrMerged`        | `notifications/external_pr_merged`                                     |
| `prMentioned`          | `PrMentioned`             | `notifications/pr_mentioned`                                           |
| `prMentioned`          | `PrCommentMentioned`      | `notifications/pr_comment_mentioned`                                   |
| `reviewRequested`      | `PrReviewRequested`       | `notifications/pr_review_requested`                                    |
| `reviewStale`          | `ReviewBecameStale`       | `notifications/review_stale`                                           |
| `prMergeReadiness`     | `PrMergeReadinessChanged` | `notifications/pr_ready_to_merge` / `pr_merge_blocked`                 |
| `prReviewDecision`     | `PrReviewDecisionChanged` | `notifications/pr_approved` / `pr_changes_requested` / `pr_review_dismissed` |
| `prChecksStatus`       | `PrChecksStatusChanged`   | `notifications/pr_checks_failed` / `pr_checks_recovered`               |
| `prThreadActivity`     | `PrThreadReplied`         | `notifications/pr_thread_replied`                                      |
| `prThreadActivity`     | `PrThreadResolved`        | `notifications/pr_thread_resolved`                                     |
| `meetingStartsSoon`    | `MeetingStartingSoon`     | `notifications/meeting_starting_soon`                                  |
| `calendarAuthExpired`  | `CalendarAuthExpired`     | `notifications/calendar_auth_expired`                                  |
| `rigStatusChanged`     | `RigControlChanged`       | `notifications/rig_control_changed`                                    |
| `rigStatusChanged`     | `RigReaped`               | `notifications/rig_reaped`                                             |
| `rigStatusChanged`     | `RigClosedEvent`          | `notifications/rig_closed`                                             |

機台的接管訊框不會送回給接下方向盤的人，釋出則不受篩選（事件不會記錄是誰放手的），而且只有 `backendFailure` 關閉會產生 `rig_closed` 訊框——其他原因不是被要求的，就是已由回收訊框涵蓋。

五個自己撰寫的 PR 類別都攜帶 `forUserId`，因此它們會送達作者，而不是工作區中的每個人。

`RemoteEventForwarder` 另外會把 `TicketReassigned` 轉送為 `notifications/ticket_reassigned`，並把每個 `TaskLifecycleEvent` 轉送為 `notifications/task_<phase>`。兩者都不對應到任何通知類別——它們驅動的是即時 UI，而不是通知中心。成員資格事件不會以訊框轉送：它們會使轉送器的快取失效，而工作階段主機則會捨棄被移除成員的工作區訂閱。
