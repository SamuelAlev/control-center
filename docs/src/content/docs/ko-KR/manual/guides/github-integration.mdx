이 가이드는 설정 가운데 GitHub에 특화된 부분을 다룹니다. GitHub은 지원하는 세 가지
코드 호스트 중 하나입니다 — GitLab 또는 Bitbucket 연결과, 한 워크스페이스에서 여러
코드 호스트를 함께 쓰는 방법은
[코드 호스트 연결](/ko-KR/매뉴얼/사용-가이드/코드-호스트-연결/)을 참고하십시오.

## 사전 준비

- 작업하려는 저장소에 접근할 수 있는 GitHub 계정
- 사람들을 GitHub에 로그인시킬 수 있는 서버. 서버 자체 GitHub App
  ([GitHub App 만들기](/ko-KR/매뉴얼/사용-가이드/github-app/) 참고) 또는 Control Center
  Connect 중 하나이며, 서버 소유자가 **설정 → 서버 → 싱글 사인온**에서 고릅니다

:::note[자격 증명은 서버에 있고 본인에게 연결됩니다]
지금 입력 중인 기기에는 아무것도 저장되지 않습니다. GitHub 로그인은 사용자 id를 키로 삼아
`cc_server`가 보관하며, 로그인한 모든 기기에서 이를 사용합니다 — 데스크톱, 웹, 휴대폰
모두입니다. 같은 서버의 다른 구성원은 이를 사용할 수 없고, 그 구성원의 로그인은 본인이
직접 해야 합니다.
:::

## GitHub에 로그인

GitHub는 로그인 방식만 지원합니다. 붙여 넣을 토큰은 없습니다.

1. **설정 → 나 → 프로필 → 코드 호스팅**으로 이동합니다(또는 온보딩
   첫 단계에서)
2. **GitHub** 행에서 **GitHub에 로그인**을 클릭합니다
3. 브라우저에서 GitHub가 열립니다. 앱을 승인합니다

로그인이 끝나는 방식은 누가 로그인을 실행하느냐에 따라 다릅니다.

- **서버 자체 앱:** GitHub가 브라우저를 서버로 돌려보내고 대화 상자가 알아서 이를
  감지합니다. 입력할 것은 없습니다
- **Control Center Connect:** 브라우저 페이지에 8자리 코드가 표시됩니다. 이를 대화 상자에
  입력하거나, `control-center://` 링크를 통해 브라우저가 Control Center를 열도록 해 입력을
  건너뜁니다

확인: **GitHub** 행에 "_your-username_(으)로 로그인했습니다."가 표시됩니다.

대화 상자는 자신이 시작하지 않은 코드나 링크를 **여기서 시작한 로그인이 아닙니다**라고
표시하며 거부합니다. 누군가 로그인 링크를 보내오면 계속하지 마십시오. 완료하면 내 계정이
그 사람의 서버에 연결됩니다.

로그인을 제거하려면 **연결 해제**를 클릭합니다. GitHub에서 로그아웃하거나 워크스페이스에서
제거되면 서버가 나를 대신해 발급한 모든 토큰도 함께 폐기됩니다.

## 자격 증명이 누구를 대신하는가

Control Center는 사람으로 행동하는 것과 앱으로 행동하는 것을 구분하는 GitHub 자체의 방식을 따릅니다:

| 발생하는 일                                                        | GitHub에서 표시되는 방식                                                          |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| 내가 직접 하는 모든 일: 댓글, 리뷰, 승인, 병합, 리뷰어 요청          | **나**. GitHub는 대화 속 댓글에 Control Center 앱으로 작성되었음을 표시하지만, 리뷰와 그 인라인 댓글에는 그런 표시가 없습니다 |
| AI 리뷰, PR 대화의 에이전트 답장과 댓글, 레이블, 파이프라인과 봇 작업      | **Control Center 봇**. 공유 Connect 앱에서는 Connect 운영자가 목록에 올린 설치에 대해서만 리뷰가 봇 이름으로 나가며, 그 밖에는 책임지는 사람으로 표시됩니다 |
| 에이전트가 나를 위해 여는 풀 리퀘스트, 그 풀 리퀘스트의 제목이나 설명에 대한 편집, 그 푸시, 그리고 그 커밋     | **나**. 공동 작성자 크레딧이 켜져 있으면 Control Center가 공동 작성자로 표시됩니다        |
| 아무도 요청하지 않은 작업(일정, 웹훅)                              | **Control Center 봇**. 그 커밋의 작성자도 봇입니다. Control Center Connect에서는 결코 푸시하거나 풀 리퀘스트를 열지 않습니다 |

- **내가 직접 하는 일**은 **내** 로그인으로만 실행되며, 다른 것은 쓰이지 않습니다. 로그인하지 않았다면 앱이 로그인을 요청합니다
- **봇 작업**은 한 번에 저장소 하나에 대한 토큰을 받으며, 이는 책임지는 멤버(요청한 사람, 없으면 워크스페이스 소유자)가 그곳에서 할 수 있는 범위로 제한됩니다. 푸시할 수 없는 멤버라면 읽기로 한정됩니다. 누군가를 대신해 행동하는 봇 답장은 **Control Center (@login 대행)** 문구로 시작합니다
- **에이전트는 Control Center를 통해 풀 리퀘스트를 엽니다**. 샌드박스에서 직접 열지 않습니다. 그래서 풀 리퀘스트는 내 것이 되고, GitHub 자체 규칙이 내가 그것을 승인하지 못하게 합니다. Control Center는 에이전트에게 요청한 사람과 풀 리퀘스트 작성자의 승인도 거부합니다. 예약 또는 웹훅 실행의 경우, 이는 트리거를 설정했거나 설정된 동안 파이프라인을 편집한 모든 관리자를 포함합니다. 다른 사람이 검토해야 합니다. Control Center가 풀 리퀘스트를 연 사람이나 포지에서 본인의 계정이 어느 것인지 확인할 수 없으면, 요청을 거부하고 다시 시도하도록 안내합니다
- **에이전트는 댓글도 Control Center를 통해 남깁니다.** 에이전트 실행이 받는 GitHub 토큰은 읽기만 가능합니다. 에이전트가 작업 중인 풀 리퀘스트에 댓글을 달면 Control Center가 봇으로 댓글을 게시하며, 실행을 요청한 사람이 있으면 **Control Center (@login 대행)** 문구로 시작합니다. 에이전트는 같은 저장소 안에 있고(포크가 아닌), 최신 커밋을 에이전트가 푸시했거나 해당 스페이스 브랜치의 현재 커밋인 풀 리퀘스트에만 댓글을 달 수 있습니다. 에이전트 댓글 속의 @멘션은 아무에게도 알림을 보내지 않습니다. 에이전트는 작업 중인 풀 리퀘스트가 열려 있는 동안 그 풀 리퀘스트의 제목이나 설명도 바꿀 수 있습니다. 이 편집은 풀 리퀘스트를 연 방식과 같은 방식으로 이루어지며(실행을 요청했을 때는 본인 이름으로) 그리고 기본적으로 먼저 승인을 요청합니다. 풀 리퀘스트 설명은 에이전트가 열 때와 편집할 때 @멘션을 유지하므로, 거기서 언급된 사람에게 알림이 갑니다
- **Control Center Connect에서는 봇이 푸시하거나 풀 리퀘스트를 열지 않습니다.** 거기서 푸시하거나, 브랜치를 만들거나, 풀 리퀘스트를 열려면 그것을 요청한 사람이 필요하며, 그 사람의 로그인으로 실행됩니다. 푸시를 시도하는 예약 또는 웹훅 실행은 그 사실을 알리는 메시지와 함께 중단됩니다. 사람이 없는 실행이 푸시하도록 하려면 **설정**에서 워크스페이스에 자체 GitHub App을 부여하세요
- **Connect 봇이 할 수 있는 일.** 공유 Connect 앱에서 봇은 댓글을 달고, 레이블을 붙이고, 반응을 남깁니다. 리뷰(AI 리뷰, 리뷰 댓글, 리뷰어 요청)는 Connect 운영자가 이 서버의 설치를 목록에 올린 경우에만 봇이 게시합니다. 그 밖에는 리뷰가 책임지는 사람 본인의 로그인으로 나가며, 그 사람의 이름으로 표시됩니다. 봇은 풀 리퀘스트를 열거나 편집하거나 닫거나 제목을 바꾸지 않으며, 리뷰를 해제하거나 댓글을 편집하거나 삭제하지도 않습니다. 이런 작업에는 요청한 사람이 자신의 로그인으로 해야 합니다. Connect는 여러분의 조직 설치를 하나의 Control Center 서버에 묶지 않습니다. 저장소에 푸시할 수 있는 멤버가 Connect를 통해 로그인한 어떤 서버에서든, 그 저장소의 봇 댓글 토큰을 받을 수 있습니다
- **자체 GitHub App을 가진 서버나 워크스페이스**는 리뷰를 포함해 위의 모든 작업에 봇을 유지합니다
- **자동화는 풀 리퀘스트를 결코 승인하지 않습니다**. 승인은 사람의 행위입니다

저장소를 연결하면 Control Center는 본인 계정이 저장소를 볼 수 있는지 확인하고, GitHub App이 저장소의 조직에 설치되지 않았거나 저장소를 포함하지 않으면 경고하며 해결용 링크를 제공합니다. 연결과 연결 해제에는 워크스페이스 관리자가 필요하며, 워크스페이스 자체 저장소 밖에 있는 체크아웃은 서버 소유자만 연결할 수 있습니다. [워크스페이스에 저장소 추가](/ko-KR/매뉴얼/사용-가이드/저장소-추가/)를 참고하십시오.

연결은 저장소의 영구 GitHub id를 따르므로, 이름이 바뀌거나 이전되어도 여러분이 할 일은 없습니다. 나중에 그 경로가 다른 저장소를 가리키게 되면, Control Center는 그 저장소에 아무것도 보내지 않으며 워크스페이스 관리자가 **다시 연결**을 누를 때까지 알림을 표시합니다.

저장소의 코드(파일, diff, 검색, 터미널)를 여는 데는 워크스페이스에서의 부여와 그 저장소를 읽을 수 있는 본인의 GitHub 로그인이 모두 필요합니다. 워크스페이스 관리자도 같은 규칙을 따르며, 서버 소유자만 예외입니다.

## 통합으로 얻는 것

| 기능                | 방법                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| PR 목록과 세부 정보 | 서버에서 본인의 로그인으로 호출하는 GitHub REST API                                                    |
| 검사 실행           | GitHub Checks API                                                                                      |
| 리뷰 게시           | 사용자가 승인해야 진행되는 단계로, 내 리뷰를 나로서 PR에 게시합니다                                    |
| 저장소 등록         | 체크아웃의 `origin` 리모트가 github.com 또는 gitlab.com / bitbucket.org를 가리키면 등록이 허용됩니다    |
| 에이전트의 GitHub 접근 | 실행 중에는 `git fetch`가 Control Center를 거치며, Control Center는 실행이 보유하지 않는 읽기 전용 토큰으로 실행이 작업하는 저장소를 페치합니다. `gh`는 요청 시 Control Center가 발급하고 실행이 끝나면 폐기되는 읽기 전용 토큰으로 이를 읽습니다. 푸시, 풀 리퀘스트, 그 편집, 댓글은 Control Center를 거칩니다 |
| 알림 핑             | 서버가 GitHub 알림 받은편지함을 폴링해 "풀 리퀘스트에서 멘션됨"과 "리뷰 요청됨"을 발생시킵니다         |
| 사용자 프로필       | 프로필 호버 카드와 작성자별 PR 필터링                                                                  |

일부 경로는 더 저렴한 곳에서는 REST 대신 GraphQL API를 사용합니다 — PR 작성 화면의
브랜치 선택기에서 쓰는 브랜치 활동과, 리뷰 요청 알림이 아직 대기 중인지 판단하는
실시간 리뷰 상태가 그렇습니다.

## GitHub 장애 확인하기

제목 표시줄에는 GitHub, Claude, OpenAI, Kimi 가운데 제공자 하나가 저하된 상태일 때
상태 칩이 표시됩니다. **모두 정상일 때는 이 칩이 숨겨집니다** — 칩이 있다는 사실이
문제를 알리는 것이지, 칩이 없다는 사실이 문제를 알리는 것은 아닙니다.

칩을 클릭하면 각 제공자의 상태와 새로 고침 버튼이 있는 플라이아웃이 열립니다. 상태는
2분마다 자동으로 새로 고쳐집니다.

## 에이전트가 GitHub에서 작동하는 방식

- GitHub 워크트리에서 작업하는 에이전트는 그 저장소 하나에 대한 토큰을 받습니다.
  코드, 이슈, 풀 리퀘스트를 읽을 수만 있습니다. 댓글은 위에서 설명한 대로 Control Center를 거칩니다. 푸시는 Control Center를 거치며, Control Center는
  **리모트에 푸시** 규칙에 물은 뒤 에이전트가 결코 갖지 않는 쓰기 토큰으로 이를 전달합니다.
  [샌드박스 정책 구성](/ko-KR/매뉴얼/사용-가이드/샌드박스-정책/)을 참고하십시오
- 여러분이 시작한 작업은 여러분의 이름으로 커밋됩니다. 에이전트에게 무언가를 요청하거나 IDE에서 커밋하면, 여러분이 작성자이자 커미터이며, 포지가 검증한 주소를 사용합니다. GitHub 로그인의 GitHub noreply 주소, 또는 GitLab과 Bitbucket에서는 그곳 로그인이 보고하는 이메일입니다. 워크스페이스 Git 신원은 포지가 여러분의 주소를 보증하지 않는 리포지토리에서 직접 만든 커밋에만 사용됩니다. 그 포지에 로그인하지 않았다면 에이전트의 커밋은 대신 봇의 것이 되며, 실행 메모에 그 사실이 적힙니다
- 아무도 요청하지 않은 작업은 봇 이름으로 커밋됩니다. 예약 또는 웹훅 실행은 워크스페이스의 GitHub App(`<app>[bot]`, GitHub noreply 주소 포함)으로 커밋하며, GitHub App이 없거나 리포지토리가 GitLab 또는 Bitbucket에 있으면 `Control Center <hi@usectrl.dev>`로 커밋합니다
- **Control Center를 공동 작성자로 표시**(**설정** → **나** → **커밋**)은 상대방을 위해 `Co-Authored-By:` 트레일러를 추가합니다. 여러분의 커밋에는 Control Center가, 봇의 커밋에는 실행을 일으킨 트리거를 설정한 각 사람이 표기됩니다. 끄지 않는 한 켜져 있습니다. 워크스페이스 관리자는 **설정** → **워크스페이스** → **일반**의 **공동 작성자 크레딧**으로 모든 사람에 대해 이를 정할 수 있습니다. 그러면 여러분의 선택은 저장되지만 그 워크스페이스에서는 적용되지 않습니다. Claude Code 자체의 작성자 표시는 항상 비활성화됩니다
- 여러분의 커밋은 서명할 수 있습니다. **설정** → **나** → **커밋**의 **검증된 커밋** 아래에서 **서명 키 만들기**를 선택하고, 그 공개 절반을 GitHub나 GitLab 계정에 서명 키로 추가하십시오. 그때부터 여러분이 요청한 실행의 커밋과 IDE에서 만든 커밋은 검증됨으로 표시됩니다. 비공개 절반은 서버에 남으므로, 키가 계정에 있는 동안은 그 서버를 제어하는 사람이 여러분 대신 커밋에 서명할 수 있습니다. GitHub에서는 이미 검증됨으로 표시된 커밋이 키를 제거한 뒤에도 검증됨으로 남습니다. Bitbucket에는 서명 전용 키가 없으므로 거기에는 키를 추가하지 마십시오. Bitbucket의 커밋은 서명되지 않습니다. 봇의 커밋은 결코 서명되지 않습니다
- IDE의 **소스 제어** 패널에서 만든 커밋은 `git commit --no-verify`처럼 리포지토리의 Git 훅을 건너뜁니다. 서버의 Git은 리포지토리가 구성한 자격 증명 도우미, 편집기, 외부 diff 도구, 서명기를 무시합니다. 서버 자체 머신에서, 에이전트나 풀 리퀘스트가 바꿀 수 있는 트리에서 Git을 실행하기 때문입니다. [소스 제어에서 커밋하고 푸시](/ko-KR/매뉴얼/사용-가이드/pr-리뷰-및-병합/#소스-제어에서-커밋하고-푸시하기)를 참고하십시오
- 에이전트가 푸시하는 모든 커밋은 먼저 검사됩니다. 여기에는 `stack_publish`가 스택에 대해 푸시하는 레이어도 포함됩니다. 다른 사람을 지명하거나, 표기를 빼거나 빌려 쓰거나, sign-off를 추가하거나, 서명 설정이 요구하는 대로 서명되지 않은 푸시는 거부됩니다. 여러분이 IDE에서 직접 푸시한 커밋은 여러분의 것이며 이 방식으로 검사되지 않습니다
- 리그에서 연 터미널은 저장소 하나로 좁혀진 내 로그인을 받으므로, 그곳에서의 푸시는
  내 것이 됩니다
- 토큰을 발급할 수 없으면(책임지는 사람이 로그인하지 않았거나, 앱이 소유자에게 설치되지
  않았거나, 설치가 일시 중단된 경우) 그 토큰을 요청한 명령이 그 이유를 알려 줍니다. 폴백 자격 증명은 없습니다

## 문제 해결

### PR 목록이 비어 있으면서 GitHub이 연결되지 않았다고 표시됩니다

이 서버에서 GitHub에 로그인하지 않았습니다. **설정 → 나 → 프로필 → 코드 호스팅**에서 **GitHub에 로그인**을
클릭하십시오. 다른 forge의 저장소는 영향을 받지 않습니다.

### GitHub 행에 이 서버에서는 로그인이 설정되지 않았다고 표시됩니다

서버에 자체 GitHub App도 Connect도 없습니다. 서버 소유자가 **설정 → 서버 → 싱글
사인온**에서 하나를 고릅니다. **내 GitHub 앱 만들기**는 약 2분이면 됩니다.
[GitHub App 만들기](/ko-KR/매뉴얼/사용-가이드/github-app/)를 참고하십시오.

자체 앱을 쓰는 워크스페이스에서는 워크스페이스의 GitHub App이 없거나 불완전할 때 그 행에 그렇게 표시됩니다. 워크스페이스 관리자가 **설정 → 워크스페이스 → 연동**의 **GitHub 앱** 카드에서 이를 채웁니다. [워크스페이스에 자체 앱 쓰기](/ko-KR/매뉴얼/사용-가이드/github-app/#한-워크스페이스에-자체-앱-쓰기)를 참고하세요.

### 대화 상자에 코드가 일치하지 않는다고 표시됩니다

브라우저에 표시된 그대로 코드를 입력하십시오. 영문자와 숫자 8자리입니다. 잘못된 코드를
다섯 번 입력하면 로그인이 끝나므로 다시 시작하십시오.

### 로그인 중 앱이 설치되어 있지 않다고 표시됩니다

저장소를 소유한 계정에 GitHub App 설치가 없습니다. 워크스페이스 관리자가 **설정 →
워크스페이스 → 연동 → GitHub 앱 설치**에서 설치합니다.

### 모두가 GitHub에 다시 로그인해야 합니다

서버 소유자가 서버의 Connect 키를 교체했거나, Connect 서버를 바꿨거나, 데이터 디렉터리가
다른 머신에 복원되었습니다. Connect를 통한 로그인은 그것을 만든 서버에 묶여 있습니다.

### 저장소 추가가 거부됩니다

등록에는 세 가지가 모두 필요합니다. 경로가 git 워크트리 안에 있고, `origin` 리모트가
있으며, 그 리모트가 지원되는 forge(github.com, gitlab.com 또는 bitbucket.org)를
가리켜야 합니다. `origin`은 여러분이 연결하는 저장소여야 하며, 워크스페이스 자체 저장소 밖에 있는 폴더는 서버 소유자만 연결할 수 있습니다. [워크스페이스에 저장소 추가](/ko-KR/매뉴얼/사용-가이드/저장소-추가/)를 참고하십시오.

### 부여는 있지만 저장소에서 내 계정이 읽을 수 없다고 합니다

GitHub 계정으로 그 저장소를 읽을 수 없으므로, 워크스페이스 부여가 있어도 그 코드는 여러분에게 열리지 않습니다. **코드 호스팅**에서 GitHub에 로그인하거나, GitHub에서 그 저장소에 대한 접근을 요청하십시오.

### "GitHub 접근 권한을 확인할 수 없습니다"

GitHub에 연결해 접근 권한을 확인할 수 없었으므로, Control Center는 추측하지 않고 거부했습니다. 잠시 후 다시 시도하십시오.

### Connect에서 리뷰가 봇이 아닌 내 이름으로 표시됩니다

공유 Connect 앱에서 봇은 Connect 운영자가 목록에 올린 설치에 대해서만 리뷰를 게시합니다. 그 밖의 곳에서는 리뷰가 책임지는 사람 본인의 로그인으로 나갑니다. 봇이 리뷰를 게시하게 하려면 워크스페이스에 자체 GitHub App을 설정하십시오.

### 많이 사용한 뒤 한동안 모든 것이 작동을 멈춥니다

속도 제한 서킷 브레이커입니다. GitHub은 `x-ratelimit-remaining: 0`과 재설정 시각을 담은
`403`으로 기본 한도에 도달했음을 알립니다. 이런 응답을 보면 클라이언트는 시간 창이
지날 때까지 네트워크 호출 없이 이후 요청을 로컬에서 실패시킵니다. 따라서 재시도 폭주가
한도를 더 악화시킬 수 없습니다. 일시적 실패는 `retry-after`를 준수하며 지수 백오프로
최대 세 번까지 재시도됩니다.
