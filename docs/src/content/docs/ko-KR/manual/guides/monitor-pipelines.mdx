이 페이지는 실행이 시작된 뒤의 모든 일을 다룹니다. 실행을 찾고, 각 단계가 무엇을
했는지 읽고, 실패한 실행을 다시 진행시키는 방법입니다. 실행을 시작하려면
[파이프라인 수동 실행](/ko-KR/매뉴얼/사용-가이드/파이프라인-실행/)을 참고하십시오.

## 실행 찾기

1. 워크스페이스 사이드바에서 **파이프라인**을 클릭합니다. 이 화면은 워크스페이스의
   실행 대기열로, 모든 실행이 최신순으로 표시됩니다.
2. 왼쪽 레일로 필터링합니다. 필터는 **전체**, **실행 중**, **실패** 세 가지뿐이며,
   각각 실시간 개수가 함께 표시됩니다.
3. <kbd>↑</kbd>/<kbd>↓</kbd>(또는 <kbd>j</kbd>/<kbd>k</kbd>)로 표를 이동하고
   <kbd>Enter</kbd>를 눌러 포커스된 실행을 엽니다. 행을 클릭해도 같습니다.

각 행에는 실행이 어떻게 시작되었는지 나타내는 글리프가 표시됩니다(수동 실행은
재생 아이콘, 코드 그래프 감시는 파일 글리프, 그 밖에는 자동 트리거). 툴팁에는
트리거 이름 — **수동**, **PR 게시됨**, **파일 변경** 등 — 이 표시되고, 감시
실행의 경우에는 어떤 파일이 변경되었는지도 표시됩니다. 그다음으로 파이프라인
이름, 상태 배지, 활성 소요 시간(`queued` 실행의 경우에는 대기열 순번), 그리고 이
시도가 시작된 지 얼마나 지났는지가 표시됩니다. 활성 소요 시간은 유휴
중지·재시작 사이의 공백을 제외하므로 실제 경과 시간과는 다릅니다.

완료됨, 일시 중지됨, 취소됨 실행을 위한 필터는 없고, 템플릿별 필터도, 시간
범위도, 템플릿별 실행 기록 보기도 없습니다. 한 템플릿의 실행을 비교하려면
대기열에서 그 이름을 찾아 훑는 수밖에 없습니다.

## 실행 상세 읽기

실행 페이지는 세 부분이 위아래로 쌓여 있습니다.

**메타 스트립**에는 시작 시간, 활성 소요 시간, 단계 진행률("7개 단계 중 3개"),
어느 단계가 왜 실패했는지 알려주는 실패 요약, 그리고 **재시도**와 **삭제**
동작이 있습니다.

**타이밍 워터폴**은 단계마다 막대 하나를 표시하며, 소요 시간과 — 에이전트 단계의
경우 — 센트 단위 비용을 보여 줍니다. 재시도된 단계는 소요 시간 뒤에 `×N`
접미사가 붙습니다. 이 접미사가 시도 횟수가 드러나는 유일한 곳입니다.

**그래프 캔버스**는 각 노드의 실시간 상태와 함께 템플릿을 그립니다. 노드를
선택하면 해당 단계 패널이 열립니다.

### 실행 및 단계 상태

| 상태          | 의미                                               |
| ------------- | ------------------------------------------------- |
| **대기 중** | 생성되었지만 아직 시작되지 않음                       |
| **대기열** | 승인되었지만 보류됨: 이 템플릿의 최대 병렬 상한이 가득 참. 아직 단계 행이 없음 |
| **실행 중** | 실행되고 있음                                       |
| **일시 중지됨** | 외부 요인을 기다리는 중 — 정상이며 멈춘 것이 아님       |
| **완료됨** | 성공적으로 끝남                                     |
| **실패** | 오류와 함께 종료됨                                  |
| **취소됨** | 사용자 또는 시스템에 의해 중지됨                      |

단계는 **대기열**을 뺀 위 상태들에, 라우터가 선택하지 않은 분기(그리고 이제
도달할 수 없게 된 하위 분기)를 위한 **건너뜀**을 더한 상태를 가집니다.

**일시 중지됨**은 에이전트 단계가 수명의 대부분을 보내는 상태입니다. 디스패치된
에이전트나 승인 게이트가 작업이 끝날 때까지 단계를 붙잡습니다. 두 가지 엔진
백스톱은 재개하지 않고 실행 전체를 실패시킵니다. 24시간 넘게 일시 중지된 단계
(`extras.awaitApproval` — 즉 `orchestration.awaitApproval` 본문 — 은 예외이고
`human.gate`는 아닙니다)와, 서버가 중지될 때 진행 중이던 멱등하지 않은
단계입니다.

## 단계 검사

캔버스에서 노드를 선택합니다. 단계 패널은 다음을 순서대로 표시합니다.

- 단계가 실패하면 **오류** 콜아웃이, 건너뛰었으면 이유와 함께 **건너뜀**
  콜아웃이 표시됩니다.
- **시작**, **종료** 및 소요 시간.
- **브랜치** — 병렬 분기의 경우 브랜치 인덱스.
- **대화 보기** — 단계가 실행된 대화로 이동합니다. 파이프라인 대화는
  사이드바에서 숨겨지므로 이것이 유일한 입구입니다.
- **입력**과 **출력**, 접을 수 있는 JSON 형식.
- **에이전트 활동** — 단계가 디스패치한 에이전트 실행마다 타일 하나가 표시되며,
  상태, 요약, 소요 시간, 비용이 담깁니다.

에이전트 단계에서 **출력**은 에이전트가 `submit_output`으로 제출한 구조화된
페이로드이며, 에이전트가 쓴 글이 아닙니다. 추론 트레이스는 **에이전트 활동**과
**대화 보기** 뒤의 대화에 있습니다.

bash 단계에서 **출력**은 스크립트가 종료 코드 0으로 끝날 때 작성한 stdout을
다듬은 것입니다. 0이 아닌 종료 코드는 stderr 마지막 부분을 오류 메시지로 삼아
단계를 실패시킵니다.

## 실패한 실행 복구

1. 메타 스트립의 실패 요약을 읽습니다. 실패한 단계를 알려줍니다. 자세한
   메시지는 단계 패널의 **오류** 콜아웃에 있습니다.
2. 단계의 **입력**을 확인합니다 — 상태 키가 없거나 철자가 틀린 것이 가장 흔한
   원인입니다. 프롬프트 에이전트 단계는 곧바로 실패하면서 해결되지 않은 자리
   표시자의 이름을 알려줍니다. bash 단계는 이를 빈 문자열로 렌더링하고 그대로
   실행하므로 보통 한 단계 뒤에 문제가 드러납니다.
3. 에이전트 단계라면 **대화 보기**를 열어 에이전트가 실제로 무엇을 했는지
   읽습니다.
4. 메타 스트립에서 **재시도**를 누릅니다. 완료된 단계와 건너뛴 단계는 출력을
   유지하고, 나머지는 모두 삭제되어 다시 실행되며 실행은 다시 실행 중으로
   바뀝니다. 소요 시간 시계는 이 시도에 대해 다시 시작됩니다.

먼저 확인해 볼 만한 흔한 원인은 다음과 같습니다.

- **시간 초과** — 단계가 **시간 제한 (ms)**을 초과했습니다. 이 필드가 밀리초
  단위라는 점을 기억하십시오.
- **스크립트 오류** — bash 명령이 0이 아닌 코드로 종료되었거나, 서버 호스트의
  `PATH`에 `bash`가 없습니다.
- **스키마 검증** — 에이전트의 `submit_output` 페이로드가 단계의 출력 스키마를
  만족하지 못했습니다.
- **해결되지 않은 자리 표시자** — 프롬프트 에이전트 단계가 참조한 `{{key}}`가
  업스트림에서 기록되지 않았습니다. 오류는 해결되지 않은 모든 키의 이름을
  알려줍니다.
- **미등록 본문** — 본문 키가 등록되지 않은 단계는 템플릿 로드 시 경고를 내고
  그다음에는 그냥 절대 실행되지 않습니다.

:::caution[재시도는 실패했거나 취소된 실행에서만 작동합니다]
**재시도** 버튼은 실행이 `failed` 또는 `cancelled`일 때만 표시됩니다. 엔진은
다른 상태에 대해서는 즉시 반환합니다.
:::

## 멈춘 단계 중지

실행 중인 단계를 선택하고 단계 패널 헤더의 **실행 중 강제 종료** 버튼을
누릅니다. 그러면 단계의 프로세스가 종료되고 단계가 실패로 표시되며, 따라서 실행
전체가 실패합니다 — 열려 있는 형제 분기도 모두 함께 닫힙니다.

이 화면에는 실행 취소 컨트롤이 없습니다. `pipeline.cancel`은 RPC 작업으로
존재하고 엔진도 이를 구현하지만, 파이프라인 UI에서 이를 호출하는 곳은 없습니다.
단계의 **실행 중 강제 종료** 또는 실행의 **삭제**만이 사용할 수 있는 중지
수단입니다.

## 비용 추적

비용은 단계별로 보고되며, 워터폴의 오른쪽 열과 **에이전트 활동** 아래의 각
타일에 표시됩니다. 상세 페이지에는 실행 합계가 없고 실행 대기열에는 비용 열이
없으므로, 두 실행의 비용을 비교하려면 각 단계를 더해야 합니다.
