Control Center가 복사하고, 넘겨주고, 받아들일 수 있는 모든 것과 각 산출물의 정확한
형태입니다. 실제로 백업을 뜨려면
[백업 및 복원](/ko-KR/매뉴얼/사용-가이드/백업-및-복원/)을, 영속성이 이렇게 나뉜
이유는 [워크스페이스와 격리](/ko-KR/매뉴얼/개념/워크스페이스/)를 참고하세요.

## 산출물

범위와 삭제 정책이 서로 다른 데이터베이스 사본 산출물이 세 가지 있습니다.

| 산출물                   | 작성 주체                    | 형태                                  | 포함 범위                     |
| ----------------------- | ---------------------------- | ------------------------------------- | ----------------------------- |
| **설치 스냅샷**          | `server.backupNow`           | 타임스탬프가 붙은 **디렉터리**        | 설치의 모든 데이터베이스      |
| **워크스페이스 백업**    | `Workspace backup` 파이프라인 | `.db` 하나를 담은 타임스탬프 디렉터리 | 워크스페이스 하나의 데이터베이스 |
| **워크스페이스 내보내기** | `workspace.export`           | `.db` **파일** 하나                   | 워크스페이스 하나의 데이터베이스 |

모두 SQLite `VACUUM INTO`로 작성되며, 이는 실행 중인 WAL 데이터베이스에도
안전합니다. 읽기 트랜잭션을 열고, 조각 모음된 트랜잭션 일관성 사본을 만들며,
서버를 중단할 필요가 전혀 없습니다.

이 파일들과 다운로드한 사본은 Control Center가 **저장 상태에서 암호화하지
않습니다**. 종단 간 암호화된 전송은 페어링된 클라이언트와 그 `cc_server` 사이를
이동하는 바이트를 직접 연결이든 브로커 릴레이 연결이든 보호합니다. 로컬
스토리지와 머신 밖 사본은 별도로 보호하세요. 서버와 인가된 수신자는 데이터베이스
파일을 읽을 수 있습니다.

## 스냅샷 레이아웃

```
<dataDir>/backups/2026-07-28T09-12-33-000Z/
  manifest.json
  global.db
  <workspaceId>/workspace.db      one directory per workspace
```

이 레이아웃은 실제 데이터 디렉터리를 그대로 비추므로, 설치 복원이 변환이 아니라
되복사하는 일이 됩니다. 디렉터리 이름은 `:`와 `.`를 `-`로 바꾼 UTC
타임스탬프이므로, Windows에서 파일 시스템에 안전하고 일반 문자열로도 시간순으로
정렬됩니다.

예약된 워크스페이스 백업은 `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db`에 따로 있습니다. 각각에는 그 파일 하나에 대한 `manifest.json`이 있고 `global.db`는 없습니다. 설치 스냅샷이 아닙니다. 복원은 교체되는 데이터베이스를 같은 위치에 `<timestamp>-pre-restore`로 보관합니다. 주간 파이프라인의 보존 단계는 구성된 기간(기본값 30일)보다 오래된, 그 워크스페이스 자체의 백업만 제거합니다. 수동으로 만든 설치 스냅샷은 그 단계에서 순환 삭제되는 일이 없습니다. `server.listBackups`는 확인되지 않은 것까지 포함해 설치 스냅샷만 나열하고, `workspace.listBackups`는 워크스페이스 하나의 예약 백업을 나열합니다.

워크스페이스를 삭제해도 이 디렉터리는 그대로 남습니다. 워크스페이스의 일정이 함께
멈추므로 그 백업은 더 이상 순환 삭제되지 않고, 설치 소유자가 제거할 때까지 남습니다.
`server.listOrphanedBackups`가 이를 보고합니다.


### `manifest.json`

| 필드                       | 유형            | 의미                                                             |
| -------------------------- | --------------- | ------------------------------------------------------------------- |
| `format`                  | int             | 매니페스트 형식. 현재 `2`                                       |
| `created_at`               | ISO-8601 UTC    | 스냅샷을 생성한 시각                                                 |
| `global`                   | object          | `global.db`의 기록. 예약 워크스페이스 백업에는 없습니다 |
| `workspaces[]`             | array           | 캡처한 워크스페이스마다 하나의 레코드                                   |
| `workspaces[].workspace_id`| string          | 이 파일이 담고 있는 워크스페이스                                      |
| `skipped_workspaces[]`     | array           | 백업이 캡처하지 **못한** 워크스페이스                                 |
| `skipped_workspaces[].workspace_id` | string | 제외된 워크스페이스 |
| `skipped_workspaces[].reason` | string       | `no_file`, `damaged` 또는 `failed`                                    |

`global`과 `workspaces[]`의 각 항목은 복사된 파일 하나를 기록하며, 복사본을 쓴 뒤 그 복사본을 측정한 값입니다.

| 필드 | 유형 | 의미 |
| ---------------- | ------ | ------------------------------------------------------------------------------ |
| `file`        | string          | 스냅샷 루트 기준 상대 경로: `global.db` 또는 `<workspaceId>/workspace.db`              |
| `bytes`       | int             | 복사본의 크기                                                       |
| `sha256`         | string | 복사본의 SHA-256(소문자 16진수)                                                |
| `quick_check`    | string | 복사본에 대한 SQLite `quick_check` 결과: `ok` 또는 검출 내용                  |
| `user_version`   | int    | 복사본의 스키마 버전                                                           |
| `application_id` | int    | 복사본의 SQLite `application_id`                                               |

워크스페이스는 등록되어 있지만 한 번도 기록된 적이 없는 경우(`no_file`), 데이터베이스가 무결성 검사에 실패하는 경우(`damaged`. 손상된 사본은 캡처되지 않습니다), 또는 복사본이나 그 복사본의 검사가 실패한 경우(`failed`) 건너뜁니다. 어느 경우든 스냅샷은 그대로 완료되며, 매니페스트에 무엇이 빠졌는지 적힙니다. 매니페스트는 맨 마지막에 기록됩니다.

### 완전성

`server.listBackups`는 스냅샷마다 `complete` 플래그를 보고합니다. 매니페스트가 없거나, 파싱할 수 없거나, 다른 형식이거나, 매니페스트가 가리키는 파일이 없거나 크기가 다르거나, 복사본이 검사를 통과하지 못했을 때 false입니다. 앱은 이런 스냅샷을 **확인되지 않음**으로 표시합니다. 형식 `2` 이전에 만들어진 스냅샷이 이 상태입니다.

확인되지 않은 스냅샷도 계속 나열됩니다. 운영자가 볼 수 없는 스냅샷은 가지고 있다고
믿는 스냅샷이기 때문입니다. 매니페스트를 읽을 수 없으면 목록은 레이아웃 자체로
폴백하여 찾아낸 `<workspaceId>/workspace.db` 파일을 보고합니다. 이런 파일들은
스냅샷 전체로는 설치를 복원할 수 없더라도 `workspace.import`로 개별적으로
받아들일 수 있습니다.

나열된 스냅샷이나 예약 백업은, 라이브 데이터베이스가 손상된 워크스페이스의 최신 검증된 사본을 담고 있는 동안 `pinned_reason: "last_good_copy"`를 가집니다. 보존 단계는 그 워크스페이스가 복원될 때까지 이를 건너뜁니다.

## 백업에 포함되지 않는 것

두 산출물 모두 **데이터베이스만** 담습니다. 워크스페이스 디렉터리는 데이터베이스보다
많은 것을 담고 있으며, 나머지는 어느 것도 함께 가지 않습니다.

| 경로                                | 스냅샷에 포함? | 워크스페이스 내보내기에 포함? |
| ----------------------------------- | -------------- | ---------------------- |
| `global.db`                         | 예             | 아니요                 |
| `<workspaceId>/workspace.db`        | 예             | 예(파일 *자체*입니다)  |
| `<workspaceId>/code_index.db`       | 아니요          | 아니요                     |
| `<workspaceId>/blobs/`              | 아니요         | 아니요                 |
| `<workspaceId>/skills/`             | 아니요         | 아니요                 |
| `<workspaceId>/agents/`             | 아니요         | 아니요                 |
| `<workspaceId>/chat_credentials/`   | 아니요         | 아니요                 |
| `<workspaceId>/spaces/<spaceId>/`   | 아니요         | 아니요                 |
| `<workspaceId>/pr_clones/`          | 아니요         | 아니요                 |
| `secrets.json`                      | 아니요         | 아니요                 |
| `models/`                           | 아니요         | 아니요                 |
| `meetings/<meetingId>/`             | 아니요         | 아니요                 |
| `rigs/`                             | 아니요         | 아니요                 |
| `_agent_hooks/`                     | 아니요         | 아니요                 |

그중 일부는 버려도 됩니다. `spaces/`는 저장소에서 다시 프로비저닝되는 copy-on-write 워크트리를 담고, `pr_clones/`는 캐시이며, `code_index.db`는 다시 생성되고, `models/`는 다시 내려받고, `rigs/`는 머신 상태입니다. 그렇지 않은 것도 있습니다. `blobs/`는 데이터베이스의 행이 가리키는 붙여넣은 이미지를 담고, `skills/`와 `agents/`는 에이전트가 실행에 쓰는 파일을 담고, `secrets.json`은 설치의 모든 페어링 키와 공급자 자격 증명, SSO 설정을 담습니다. 나머지를 챙기는 방법은 [백업 및 복원](/ko-KR/매뉴얼/사용-가이드/백업-및-복원/#백업을-머신-밖으로-복사하기)을 참고하세요.
:::note[시크릿은 데이터베이스 밖에 있습니다]
`workspace.db`는 워크스페이스 전체입니다. 대화, 실행 로그, 저장소 연결, 환경 정의, 구성원이 들어 있습니다. 파이프라인 웹훅 토큰과 티켓 동기화 웹훅 시크릿은 `secrets.json`에 있습니다. 데이터베이스에는 각각에 대한 참조가 있고, 라우트 인덱스에는 각 토큰의 키 해시가 있습니다. 따라서 다른 설치에 복원된 워크스페이스는 트리거가 그곳에서 다시 저장되기 전까지 웹훅을 받지 않습니다. 공급자 로그인, 기기 키, 사용자 시크릿은 `global.db`와 `secrets.json`에 있습니다.
:::

:::note[채팅 토큰은 의도적으로 남겨 둡니다]
`chat_credentials/`가 데이터베이스 안이 아니라 옆에 있기 때문에, 다른 사람에게
넘긴 워크스페이스에는 살아 있는 봇 토큰이 실리지 않습니다.
[채팅 브리지 레퍼런스](/ko-KR/매뉴얼/레퍼런스/채팅-브리지/)를 참고하세요.
:::

## 연산

설치 백업 RPC와 워크스페이스 내보내기/가져오기는 `fullClient` 전용이므로, 페어링된
휴대폰에서는 트리거할 수 없습니다. 백업 포트가 연결되지 않은 서버(예: 데모
서버)에서는 이들 모두가 아예 없습니다. 거부되는 것이 아니라 구조적으로
존재하지 않습니다.

| 연산                   | 종류   | 범위       | 최소 역할          | 인수           | 반환                          |
| -------------------- | ------ | --------- | ------------ | ------------- | ----------------------------- |
| `server.backupNow`   | 변경   | 설치      | 설치 **소유자** | 없음          | `{ok, path}`                  |
| `server.listBackups` | 읽기   | 설치      | 설치 **소유자** | 없음          | `{backups: [...]}`            |
| `server.deleteBackup` | 변경 | 설치      | 설치 **소유자** | `name`        | `{ok}`                        |
| `server.listOrphanedBackups` | 읽기 | 설치 | 설치 **소유자** | 없음 | `{workspaces: [...]}` |
| `server.deleteOrphanedBackup` | 변경 | 설치 | 설치 **소유자** | `workspace_id`, `name` | `{ok}` |
| `workspace.listBackups` | 읽기 | 워크스페이스 | `admin` | 없음 | `{backups: [...]}` |
| `workspace.deleteBackup` | 변경 | 워크스페이스 | `owner` | `name` | `{ok}` |
| `workspace.export`   | 읽기   | 워크스페이스 | `admin`      | 없음          | `{ok, path}`                  |
| `workspace.import`   | 변경   | 워크스페이스 | `owner` 및 서버 소유자 | `source_path` | `{ok, workspace_id}`          |
| `workspace.importHolds.list` | 읽기 | 워크스페이스 | `owner` 및 서버 소유자 | 없음 | `{holds: [...]}` |
| `workspace.importHolds.resolve` | 변경 | 워크스페이스 | `owner` 및 서버 소유자 | `hold_id`, `accept` | `{ok, applied}` |
| `workspace.delete`   | 변경   | 설치*      | `owner`      | `id`          | 레지스트리 행이 삭제됨으로 표시됨 |

* `workspace.delete`는 표시하는 행이 전역 레지스트리에 있으므로 범위가 없습니다.
이 연산의 핸들러는 호출자가 해당 워크스페이스의 멤버인지 확인하고 `owner`를
요구합니다.

모든 응답의 `path`는 **서버 호스트**의 경로입니다.

`server.listOrphanedBackups`는 더 이상 살아 있지 않은 워크스페이스마다 항목 하나를
반환합니다. 항목에는 `workspace_id`, 레지스트리가 아직 알고 있다면 `workspace_name`,
그리고 `backups`가 들어 있습니다. 삭제된 워크스페이스는 더 이상 워크스페이스 역할 검사를
통과할 수 없으므로, 그 백업은 설치 소유자의 것이 됩니다. `server.deleteOrphanedBackup`은
살아 있는 워크스페이스를 거부하며, 그 백업은 `workspace.deleteBackup`과 해당 워크스페이스
자체의 역할 뒤에 머뭅니다. 두 삭제 연산 모두 목록에 있는 타임스탬프 디렉터리 이름만 받으며
경로는 받지 않습니다.

`workspace.importHolds.list`는 가져오기가 보류한 항목을 반환합니다. 각 보류 항목에는 `id`, `kind`(`action_policy`, `sandbox_exec_grant`, `repo_grant`, `membership_role`, 또는 `invite`), 되돌렸을 `payload`, `imported_at`, `source_install_id`가 있습니다. `workspace.importHolds.resolve`를 `accept: true`로 호출하면 다시 부여하고, `false`로 호출하면 버립니다. 부여 대상이었던 사람이나 항목이 워크스페이스에 더 이상 없으면 `applied`는 false입니다.

:::note[설치 전체 스냅샷은 두 레인 모두 소유자 전용입니다]
`server.backupNow`, `server.listBackups`, `server.deleteBackup`은 설치
**소유자**(`ServerAuthority.serverOwner`)를 요구하며, `GET /backup/snapshot`과 같은
관문을 씁니다. 스냅샷은 모든 워크스페이스의 데이터베이스를 캡처하므로,
워크스페이스 하나의 관리자인 것만으로는 나머지를 관리하기에 충분하지 않습니다.
삭제는 나열된 타임스탬프 디렉터리 이름만 받아들이고 임의의 서버 경로는 받지
않으며, 스냅샷 전체(확인되지 않은 스냅샷 포함)를 제거합니다. 워크스페이스별 내보내기와 예약 백업 다운로드는 워크스페이스 관리자에게 남습니다.
:::

:::note[복원은 서버 소유자의 것입니다]
`workspace.import`와 `POST /backup/restore`는 서버가 데이터베이스 파일을 자기 것으로 받아들이게 합니다. 파일의 행을 서버가 자기 것으로 취급하기 때문입니다. 저장소 링크와 그것을 만든 사람, 호스트에서 실행되는 환경 정의, 워크트리와 로그 경로가 그렇습니다. 따라서 둘 다 서버 소유자(`ServerAuthority.serverOwner`)가 필요하며, 그 사람은 워크스페이스의 소유자이기도 해야 합니다. 그 밖의 사용자와 기록된 소유자가 없는 호스트의 모든 호출자는 `server_owner_required`와 함께 거부됩니다. 파일이 가져오는 트리거, 뷰, 열, 제약 조건은 하나도 채택되지 않습니다.
:::

### `server.listBackups` 응답

최신순이며 디렉터리 이름으로 정렬합니다(이름이 곧 타임스탬프이므로, 매니페스트를
읽을 수 없는 스냅샷에서도 순서가 유지됩니다).

```json
{
  "backups": [
    {
      "path": "/…/backups/2026-07-28T09-12-33-000Z",
      "name": "2026-07-28T09-12-33-000Z",
      "created_at": "2026-07-28T09:12:33.000Z",
      "bytes": 481203712,
      "complete": true,
      "workspaces": [
        {
          "workspace_id": "w_9f2c…",
          "path": "/…/backups/2026-07-28T09-12-33-000Z/w_9f2c…/workspace.db",
          "bytes": 190840832
        }
      ],
      "skipped_workspace_ids": []
    }
  ]
}
```

매니페스트를 읽을 수 없으면 `created_at`은 생략됩니다. 최상위 `bytes`는
매니페스트가 스스로 합한 값이 아니라 디렉터리 전체의 실제 디스크 크기입니다.
스냅샷을 정리하는 운영자가 묻는 것은 그 디렉터리가 차지하는 비용이지, 백업이
기록하려던 양이 아니기 때문입니다.

각 `workspaces[].path`는 `workspace.import`가 `source_path`로 받는 값과 정확히
같습니다. 이는 의도된 것으로, "이 스냅샷에서 이 워크스페이스를 복원한다"는 것이
*곧* 가져오기 연산이므로, 둘이 같은 파일을 다르게 취급하는 쪽으로 어긋날 수
없습니다.

### `workspace.import` 검증

무엇이든 교체되기 전에, 후보 파일을 대상 옆의 스테이징 파일로 복사하고 거기서 확인합니다. 거부되는 경우 아무것도 건드리지 않으며, 그 종류는 `data.kind`로 전달됩니다.

| 조건                                        | 결과                                                          |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| 파일이 존재하지 않음 | 거부, `import.missing_source` |
| 읽을 수 있는 SQLite 데이터베이스가 아니거나 `quick_check`에 실패함 | 거부, `import.damaged` |
| 스냅샷에서 가져온 파일이며 SHA-256이 매니페스트의 값과 다름 | 거부, `import.checksum_mismatch` |
| 서버의 더 새로운 버전이 기록함 | 거부, `import.newer_schema` |
| 다른 `application_id`이거나 `workspace_meta`가 없음 | 거부, `import.foreign_file` |
| 이 서버의 스키마에 맞출 수 없음 | 거부, `import.schema_mismatch` |
| 그 웹훅이나 초대가 이미 다른 워크스페이스로 라우팅됨 | 거부, `import.route_conflict` |
| 기록된 워크스페이스 id ≠ 대상                | **허용**됩니다. 그 행은 대상에 맞춰 다시 키가 지정됩니다. 이렇게 해서 워크스페이스를 복제하거나 새 id로 복원합니다 |
| 기록된 설치 id ≠ 이 설치                | **허용**됩니다. 그 사용자 id는 그 설치에 속하며 여기서는 해석되지 않습니다 |

수락되면 스테이징된 파일은 이 서버의 스키마에 맞춰지며, 그 뒤 정확히 일치해야 합니다. 파일이 스스로 부여해서는 안 되는 권한은 파일에서 제거됩니다. 호스트에서 환경 정의를 실행하는 승인은 해제되며, 허용하거나 확인을 요청하는 액션 규칙, 샌드박스 exec 권한, 읽기 이상의 저장소 권한, 멤버 이상의 역할, 그 역할에 대한 초대는 서버 소유자가 검토할 수 있도록 보류됩니다. 가져온 사람은 소유자 역할을 유지하거나 얻습니다. 교체되는 데이터베이스는 `<timestamp>-pre-restore`라는 이름의 예약 백업으로 보관되고, 스테이징된 파일은 워크스페이스 연결이 닫힌 상태에서 제자리로 이름이 바뀌며, `code_index.db`는 다시 만들어지도록 삭제되고, FTS 인덱스가 다시 빌드됩니다.

## 전송 라우트

위의 내보내기/가져오기와 스냅샷 나열 연산은 서버 측 경로로 말하며, 이는 서버가
곧 자신의 머신일 때만 완전한 답입니다. 이 HTTP 형식 라우트는 다른 민감한
리소스와 **동일한 인증·종단 간 암호화 리소스 터널 내부**에서 백업 바이트를
운반합니다. RPC 연결이 직접이든 브로커를 거치든 마찬가지입니다. 이들은 공개
HTTP 파일 전송 엔드포인트가 아닙니다. 공개 리스너에서 이 중 하나로 보낸 요청은
루프백에서도 `426 Upgrade Required`를 반환합니다. 암호화된 터널 안에서는 Noise로
인증된 기기가 `d`와 일치해야 하며, 핸들러는 추가로 페어링 PSK로 대상 문자열에
대한 기기의 서명을 확인하고 아래의 역할을 확인합니다.

| 라우트                   | 메서드 | 쿼리           | 서명 대상                      | 필요 권한               |
| ----------------------- | ------ | --------------- | ------------------------------ | ----------------------- |
| `/backup/workspace`     | GET    | `w`, `d`, `s`   | `backup-workspace:<workspaceId>` | 워크스페이스 **관리자**   |
| `/backup/snapshot`      | GET    | `n`, `d`, `s`   | `backup-snapshot:<name>`         | 설치 **소유자**     |
| `/backup/stored`        | GET    | `w`, `n`, `d`, `s` | `backup-stored:<workspaceId>:<name>` | 워크스페이스 **관리자**. 워크스페이스 삭제 후에는 설치 **소유자** |
| `/backup/restore`       | POST   | `w`, `d`, `s`   | `backup-restore:<workspaceId>`   | 설치 **소유자**이면서 워크스페이스 **소유자**(그 밖에는 `server_owner_required`와 함께 `403`) |

`w`는 워크스페이스 id, `n`은 스냅샷 또는 예약 백업 디렉터리 이름, `d`는 호출 기기 id,
`s`는 서명입니다. `/backup/snapshot`에서 `n`은 백업 루트에 이어 붙이는 것이 아니라 백업
목록을 기준으로 해석되므로, 이 라우트를 목록에 없던 디렉터리로 겨냥할 수 없습니다.
`/backup/stored`에서 `n`은 타임스탬프 이름이어야 하고, 파일은 해당 워크스페이스 자체의
백업 디렉터리 안에 있는 실제 파일이어야 합니다.

| 상태 | 원인                                                                              |
| ------ | ----------------------------------------------------------------------------------- |
| `400`  | 필수 쿼리 매개변수가 없거나, 백업 이름이 잘못되었거나, 업로드 본문이 비어 있거나, 업로드된 파일이 거부됨(본문은 `import.*` 종류를 가진 `{error, kind}`) |
| `403`  | 알 수 없거나 해지된 기기, 잘못된 서명, 또는 호출자에게 역할이 없음              |
| `404`  | 이 호스트에 백업 포트가 없거나, 지정한 스냅샷, 백업 또는 워크스페이스 파일이 없음 |
| `405`  | `/backup/restore`가 `POST`가 아닌 다른 메서드로 호출됨                                   |
| `413`  | 선언된 content-length 기준이든 실제로 읽은 바이트 기준이든 업로드 본문이 8 GiB를 초과함     |
| `426`  | 공개 HTTP 리스너의 전송 경로에 대한 직접 요청. 페어링된 클라이언트의 암호화된 리소스 터널을 사용하세요 |
| `500`  | 서버 측에서 내보내기나 아카이브가 실패함                                            |

세 다운로드 모두 `Cache-Control: no-store`와 `Accept-Ranges: none`으로 응답합니다.
`/backup/workspace`와 `/backup/snapshot`은 요청마다 **새** 사본을 만들어 내고 스트리밍이
끝나면 삭제하므로, 캐시되거나 재개된 응답은 서로 다른 두 내보내기의 바이트를 이어 붙여,
멀쩡해 보이지만 그렇지 않은 파일 하나를 만들게 됩니다.

`/backup/stored`는 예외입니다. 예약 백업을 `<workspaceId>-<name>.db`로 스트리밍하고 파일은
그대로 두는데, 그 파일이 곧 백업이기 때문입니다.

`/backup/snapshot`은 `<name>.zip`을 반환하며, 항목들은 스냅샷 루트 기준 상대
경로이므로 압축을 풀면 `manifest.json` + `global.db` + `<workspaceId>/workspace.db`가
그대로 재현됩니다. 항목은 정렬된 순서로 기록되므로, 같은 스냅샷의 두 아카이브는
같은 아카이브입니다.

`/backup/restore`는 본문을 버퍼링하지 않고 곧바로 스테이징 파일로 스트리밍하며,
읽기 전과 읽는 동안 크기를 제한하고, 거부된 경우까지 포함해 나가는 **모든**
경로에서 스테이징된 파일을 삭제합니다.

::::caution[직접 연결과 릴레이는 같은 암호화 전송을 사용합니다]
릴레이는 리소스 요청, 스트리밍된 응답, 업로드 바이트를 암호문으로 운반합니다.
백업 내용을 읽을 수는 없습니다. 서버 측 경로는 릴레이 위의 파일이 아니라 서버
호스트 위의 경로로 남습니다. 접근에는 여전히 페어링된 기기, 대상 서명, 해당
워크스페이스 또는 설치 역할이 필요합니다. 어느 전송도 생성되는 백업 파일을 저장
상태에서 암호화하지 않습니다.
::::

## 경로와 한계

| 항목                          | 값                                                        |
| ------------------------------ | ------------------------------------------------------------ |
| 스냅샷                      | `<dataDir>/backups/<timestamp>/`                             |
| 예약된 워크스페이스 백업    | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>/workspace.db` |
| 워크스페이스 내보내기              | `<dataDir>/backups/exports/<workspaceId>-<timestamp>.db`     |
| 복원으로 교체된 데이터베이스 | `<dataDir>/backups/workspace-backups/<workspaceId>/<timestamp>-pre-restore/` |
| 업데이트로 형식이 바뀌기 전의 데이터베이스 | `<dataDir>/pre_upgrade/`와 `<dataDir>/<workspaceId>/pre_upgrade/`, 각각 가장 최근 2개 |
| 전송 스테이징               | `<dataDir>/backups/transfer/` — 작업 공간이며, 여기에 쓰는 라우트가 스윕합니다 |
| 스냅샷 아카이브 이름          | `<snapshot directory name>.zip`                              |
| 업로드 상한                 | 암호화된 `/backup/restore` 업로드당 8 GiB                  |
| 보존                      | 설치 스냅샷: 수동 삭제. 워크스페이스 백업: 주간 파이프라인, 기본 30일, 또는 수동 삭제. 삭제된 워크스페이스의 백업: 수동 삭제만 가능 |

`exports/`, `transfer/`, `workspace-backups/` 디렉터리는 설치 스냅샷이 아니며
`server.listBackups`에서 제외됩니다. 마지막 디렉터리만 예약된 보존 정책을
가지되 그 워크스페이스가 존재하는 동안에만 해당하며, 설치 스냅샷을 삭제하려면 설치
소유자의 명시적인 조치가 필요합니다.
