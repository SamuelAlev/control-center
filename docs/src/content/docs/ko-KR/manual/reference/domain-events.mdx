## 이벤트 버스

`DomainEventBus`는 프로세스 내 브로드캐스트 발행/구독 버스입니다. 발행자는 `publish(event)`를 호출하고, 구독자는 타입이 지정된 `on<T>()` 스트림을 소비합니다. 모든 이벤트는 `DomainEvent`를 구현하며 `occurredAt`을 함께 전달합니다.

**버스는 `cc_server` 안에서 실행됩니다.** 모든 발행자와 살아 있는 모든 구독자가 그곳에 있습니다. 어떤 클라이언트도 이 버스를 보지 못합니다. 서버가 선별한 일부를 `notifications/*` JSON-RPC 프레임으로 전달하고, 구독자마다 워크스페이스 멤버십에 따라 필터링합니다.

| 항목                                                        | 개수                                        |
| ----------------------------------------------------------- | --------------------------------------------- |
| 구체적 이벤트 클래스                                        | 53                                          |
| 소스 파일 (`packages/cc_domain/lib/core/domain/events/`)     | 14 (`domain_event_bus.dart` 포함)           |
| 직접 발행되지 않는 추상 기반 클래스                         | 1 (`TaskLifecycleEvent`, sealed 계층 구조)  |

아래 목록의 모든 이벤트는 이 한 디렉터리에 있습니다. 다른 곳에 선언된 도메인 이벤트는 없습니다.

## 작업 수명주기 이벤트

디스패치된 에이전트 실행 하나를 실행 로그 id로 식별하는 통합 작업 수명주기 스트림입니다. 모든 이벤트는 `taskId`, 작업별로 단조 증가하는 `seq`, `workspaceId?`, `agentId?` 그리고 `phase`를 전달합니다. 아래 행은 추가 필드만 나열합니다.

| 이벤트                      | 페이로드                      | 발생 시점                                                                                        |
| --------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `TaskDispatched`            | —                             | 작업이 실행을 위해 백엔드로 넘겨질 때                                                            |
| `TaskRunning`               | —                             | 작업이 출력을 내기 시작할 때                                                                     |
| `TaskWaitingLocalDirectory` | `lockedPath`, `holderTaskId?` | 작업이 보류될 때 — 다른 작업이 이 작업에 필요한 디스크 경로 잠금을 소유하고 있습니다            |
| `TaskProgress`              | `note?`                       | 실행 중 진행 상황 체크포인트                                                                     |
| `TaskMessage`               | `messageType`, `content`      | 스트리밍된 메시지(text/thinking/tool_use/tool_result/error)이며, `progress` 단계로 보고됩니다    |
| `TaskCompleted`             | `summary?`                    | 작업이 성공적으로 끝났을 때                                                                      |
| `TaskFailed`                | `errorMessage`                | 작업이 오류와 함께 끝났을 때                                                                     |
| `TaskCancelled`             | —                             | 작업이 완료되기 전에 취소될 때                                                                   |

`TaskPhase` 열거형에는 `queued` 멤버도 있지만, 대기 중 이벤트를 발행하는 곳은 없습니다. `TaskQueued` 클래스가 없습니다. 작업에서 처음으로 관찰 가능한 프레임은 `TaskDispatched`입니다.

## 이벤트가 전혀 없는 하위 도메인

바깥에서 보면 이벤트 기반처럼 보이지만 그렇지 않은 하위 시스템이 여럿 있습니다. 훅을 찾아 나서기 전에 알아 둘 가치가 있는 설계 결정이라 여기에 나열합니다.

| 하위 도메인      | 대신 상태가 움직이는 방식                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| 메모리           | `record_memory_fact`와 그 친구들이 쓰고 반환하며, 회수는 읽기만 합니다. 팩트나 충돌에 대해 발행하는 것은 없습니다 |
| 오케스트레이션   | 제안, 그 승인, 생성된 파이프라인 실행은 모두 행과 RPC 호출입니다                                          |
| 플랜 문서        | `submit_plan`이 수정본을 씁니다. 승인이 오케스트레이션을 구체화합니다. 어느 쪽도 공지되지 않습니다         |
| 아티팩트         | `publish_artifact` / `revise_artifact`가 수정본을 직접 씁니다                                              |
| 승인             | 에스컬레이션은 승인 워크플로 서비스 내부에서 처리됩니다                                                   |
| 티켓 동기화      | 벤더 코디네이터가 위의 티켓 이벤트를 구독하며, 인바운드 웹훅은 직접 적용됩니다                            |
| 캘린더 새로 고침 | 동기화가 이벤트를 upsert하고 클라이언트가 다시 읽습니다. 새로 고침 브로드캐스트는 없습니다                |
| 워크트리 병합    | `worktree_merge_log`에 기록되고 그곳에서 읽힙니다                                                          |

| `StaleReviewWatcher`                | `PrHeadChanged` — 교체된 커밋에 대해 완료된 리뷰가 있을 때만 `ReviewBecameStale`을 발행합니다        |

`TicketAssigned`는 감사 및 알림 신호이자 파이프라인 트리거입니다. 에이전트에 할당하면 소유권이 기록될 뿐 실행은 시작되지 않습니다. 티켓 디스패처가 없습니다. 팀 할당(`assignedTeamId` 설정)은 예외입니다. `TeamRoutingService`가 팀 리더를 디스패치합니다.

`TicketRemoteSyncHandler`는 선언되어 있지만 프로덕션 코드에서는 생성되지 않으므로 오늘날 아무것도 구독하지 않습니다. 클라이언트 측 `NotificationEventMapper`는 자체 테스트에서만 생성됩니다. 클라이언트/서버 분리 이전의 프로세스 내 경로가 남긴 잔재입니다. 라이브 토스트는 아래 와이어 프레임에서 옵니다.

## 알림 매핑

서버에서는 `NotificationFeedRecorder`와 `RemoteEventForwarder`가 이 이벤트들을 `notifications/*` 와이어 프레임(`notification_wire.dart`)으로 바꿉니다. 클라이언트에서는 `RpcNotificationMapper` → `mapNotificationFrame`이 프레임을 `AppNotification`으로 바꿉니다.

알림 범주는 정확히 **16개**입니다. 여러 이벤트가 둘 이상의 와이어 메서드에 매핑되는데, 프레임은 전환(실패 대 복구)을 담고 범주는 질문(“CI가 무엇을 하고 있나?”)을 담기 때문입니다.

| 범주                   | 소스 이벤트               | 와이어 메서드                                                          |
| ---------------------- | ------------------------- | ------------------------------------------------------------------------ |
| `newMessage`           | `MessageReceived`         | `notifications/message_received`                                       |
| `agentRunCompleted`    | `AgentRunCompleted`       | `notifications/agent_run_completed`                                    |
| `ticketAssigned`       | `TicketAssigned`          | `notifications/ticket_assigned`                                        |
| `ticketStatusChanged`  | `TicketStatusChanged`     | `notifications/ticket_status_changed`                                  |
| `pullRequestPublished` | `PullRequestPublished`    | `notifications/pr_published`                                           |
| `prMerged`             | `PrMerged`                | `notifications/pr_merged`                                              |
| `prMerged`             | `ExternalPrMerged`        | `notifications/external_pr_merged`                                     |
| `prMentioned`          | `PrMentioned`             | `notifications/pr_mentioned`                                           |
| `prMentioned`          | `PrCommentMentioned`      | `notifications/pr_comment_mentioned`                                   |
| `reviewRequested`      | `PrReviewRequested`       | `notifications/pr_review_requested`                                    |
| `reviewStale`          | `ReviewBecameStale`       | `notifications/review_stale`                                           |
| `prMergeReadiness`     | `PrMergeReadinessChanged` | `notifications/pr_ready_to_merge` / `pr_merge_blocked`                 |
| `prReviewDecision`     | `PrReviewDecisionChanged` | `notifications/pr_approved` / `pr_changes_requested` / `pr_review_dismissed` |
| `prChecksStatus`       | `PrChecksStatusChanged`   | `notifications/pr_checks_failed` / `pr_checks_recovered`               |
| `prThreadActivity`     | `PrThreadReplied`         | `notifications/pr_thread_replied`                                      |
| `prThreadActivity`     | `PrThreadResolved`        | `notifications/pr_thread_resolved`                                     |
| `meetingStartsSoon`    | `MeetingStartingSoon`     | `notifications/meeting_starting_soon`                                  |
| `calendarAuthExpired`  | `CalendarAuthExpired`     | `notifications/calendar_auth_expired`                                  |
| `rigStatusChanged`     | `RigControlChanged`       | `notifications/rig_control_changed`                                    |
| `rigStatusChanged`     | `RigReaped`               | `notifications/rig_reaped`                                             |
| `rigStatusChanged`     | `RigClosedEvent`          | `notifications/rig_closed`                                             |

리그 인수 프레임은 조종권을 잡은 사람에게 다시 전달되지 않고, 해제는 필터링되지 않으며(누가 놓았는지는 이벤트에 기록되지 않습니다), `backendFailure` 종료만 `rig_closed` 프레임을 만듭니다 — 나머지 사유는 요청된 것이거나 이미 회수 프레임이 다룹니다.

작성한 PR 관련 다섯 범주는 `forUserId`를 전달하므로, 워크스페이스의 모든 사람이 아니라 작성자에게 도달합니다.

`RemoteEventForwarder`는 추가로 `TicketReassigned`를 `notifications/ticket_reassigned`로, 모든 `TaskLifecycleEvent`를 `notifications/task_<phase>`로 전달합니다. 어느 것도 알림 범주에 매핑되지 않습니다 — 알림 센터가 아니라 라이브 UI를 구동합니다. 멤버십 이벤트는 프레임으로 전달되지 않습니다. 포워더의 캐시를 무효화하고, 세션 호스트가 제거된 멤버의 워크스페이스 구독을 끊습니다.
