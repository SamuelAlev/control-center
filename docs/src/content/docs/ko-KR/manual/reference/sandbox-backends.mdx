:::caution[실행이 샌드박스로 감싸지는지는 호스트에 달려 있습니다]
`cc_server`는 부팅할 때 이 호스트에서 에이전트를 어떻게 실행할지 한 번 결정하며, 그 결정은 재시작할 때까지 유지됩니다:

- **샌드박스 적용** (`native`): 탐지가 백엔드를 찾았고 `--sandbox`가 `off`가 아닙니다. 두 디스패치 이음매가 모두 감싸집니다. Claude Code CLI는 샌드박스 포트를 통해, ACP와 기본 제공 하네스의 `bash` 도구는 샌드박스 관리자를 통해 감싸집니다.
- **끔** (`off`): 서버 소유자가 `--sandbox off`로 시작했습니다. 누가 시작했든 모든 구성원의 에이전트가 이 머신에서 제한 없이 실행됩니다.
- **사용 불가** (`unavailable`): 샌드박스는 켜져 있지만 탐지가 백엔드를 찾지 못했습니다(**항상 Windows**, 그리고 `bwrap`과 `socat`이 없는 Linux나 WSL2). 실행은 그 실행에 책임 있는 사람이 서버 [소유자](/ko-KR/매뉴얼/개념/권한-부여/#서버-소유자)일 때에만 시작됩니다. 요청한 사람이거나, 자동화라면 그것이 묶인 사람입니다. 그 밖의 사람의 실행은 자격 증명이 발급되거나, 리스가 잡히거나, 프로세스가 시작되기 전에 거부됩니다. 기록된 소유자가 없으면 누구의 실행도 시작되지 않습니다.

거부된 실행은 `sandbox_unavailable` 코드와 함께 실패합니다. 앱은 이를 **에이전트에는 이 서버의 샌드박스가 필요합니다**로 표시하며, 메시지는 "이 서버에는 샌드박스가 없으므로 서버 소유자만 여기서 에이전트를 실행할 수 있습니다. 소유자는 샌드박스를 설치하거나 모든 사용자에 대해 샌드박스를 끌 수 있습니다."입니다.

샌드박스 없이 시작되는 실행(`off` 아래, 또는 `unavailable` 아래의 소유자 본인 실행)은 호스트에서 직접 실행됩니다. ACP와 하네스 `bash` 도구는 여전히 환경 정리를 거쳐 스폰됩니다. Claude Code는 `NoSandboxAdapter`를 거치며 호스트 환경을 물려받습니다. 나머지 경계는 실행 자신의 워크트리(`rift`가 제공되는 곳에서는 쓰기 시 복사, Windows에서는 `git worktree`), 실행마다 브로커를 거쳐 발급되고 정리 시 회수되는 읽기 전용 forge 토큰, 에이전트 실행 게이트웨이에서 푸시 규칙을 통과해야 하는 푸시, 모드별 명령 정책, 통합된 [작업 가드레일](/ko-KR/매뉴얼/개념/가드레일/)(실패 시 차단), ACP와 하네스 `bash` 경로의 환경 정리, 그리고 해당 모드가 허용하는 도구 표면입니다.

하네스의 프로세스 내 파일 도구(read, write, edit, apply patch, search, find, search_files)는 모든 호스트에서 샌드박스 밖에 있습니다. 이들은 서버 프로세스 안에서 실행되므로 `bash`만 감싸집니다.

호스트는 샌드박스가 적용되는 서버의 대체 수단이 아닙니다. 서버가 에이전트를 샌드박스에 넣지만 실행에 줄 샌드박스가 없으면, 그 도구 프로세스와 `bash` 명령은 호스트에서 시작되지 않고 거부됩니다. 같은 자세가 실행 주변의 작은 프로세스도 결정합니다. ACP 일회성 도우미(대화 제목, `/btw`, `/handoff`, `/goal`)와 Review Studio의 풀 리퀘스트 골든 테스트는, 서버가 에이전트를 샌드박스에 넣을 때에는 샌드박스 안에서, `off` 아래에서는 제한 없이, `unavailable` 아래에서는 서버 소유자가 책임지는 요청에 한해서만 실행됩니다. 그 밖에는 건너뜁니다.
:::

## 백엔드 개요

| 백엔드      | 값        | 플랫폼                                        | 가용성                                                                                                      |
| ----------- | --------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 격리 VM | `microvm` | macOS, Linux, Windows (microVM hypervisor)    | microVM 런타임에 대해 탐지로 게이트됩니다. 대화형 터미널에 적용됩니다 — 셸은 호스트가 아니라 [리그](/ko-KR/매뉴얼/개념/리그/) 안에서 실행됩니다 |
| 네이티브      | `native`  | macOS(Seatbelt), Linux와 WSL2(bubblewrap) | 부팅할 때 탐지됩니다. Linux는 bubblewrap이 강제할 수 없는 파일 이름 글로브 쓰기 거부를 요구하는 실행을 거부합니다 |
| 격리 없음    | `none`    | 모두                                           | 파싱 기본값과 터미널의 기본값입니다. 에이전트 디스패치는 `--sandbox off` 아래에서 이를 사용하며, 사용할 수 있는 백엔드가 없을 때는 소유자 본인의 실행에만 사용합니다 |

`SandboxBackend.fromName`은 저장된 값이 null이거나 인식할 수 없으면 `none`을 반환합니다.

**`microvm`은 커널 경계를 가진 유일한 백엔드입니다** — 워크로드가
실제로 호스트에서 실행되지 않습니다. 어느 방향으로도 조용한 폴백이 되지
않습니다. VM을 부팅할 수 없는 호스트에서 이를 명시적으로 요청하면 크게
실패하며("VM을 요청했는데 노트북이 나왔다"는 것이 인클로저가 감당할 수 없는
유일한 저하입니다), *지정되지 않은 기본값*만이 그 사실을 로그 줄에 남기고
`native`로 내려갑니다. 세션의 실제 백엔드는 클라이언트에 보고되고 배지로
표시되므로, 터미널이 호스트에서 실행되면서 인클로저라고 주장할 수는 없습니다.
VM 자체의 수명주기, 이미지, 이그레스는 [리그 레퍼런스](/ko-KR/매뉴얼/레퍼런스/리그/)에서 다룹니다.

**Windows에는 네이티브 샌드박스가 없습니다.** `NativeSandboxAdapter.probe`는 macOS나 Linux/WSL2가 아닌 모든 호스트에서 `available: false`를 반환하므로, Windows 서버는 `unavailable`입니다. 서버 소유자의 에이전트 실행만 제한 없이 시작되며 그 밖의 실행은 모두 거부됩니다. 모든 구성원이 거기서 에이전트를 실행하게 하려면 소유자가 `--sandbox off`로 서버를 시작해야 하며, 그러면 모든 실행이 제한 없이 실행됩니다. `microvm` 백엔드는 별개입니다. microVM 런타임에 대해 탐지로 게이트되며, 호스트에서 `bash`를 감싸는 것이 아니라 대화형 터미널과 리그에 적용됩니다.

## 탐지 결과

탐지가 강제를 게이트합니다. 서버 부팅 시 한 번 실행됩니다.

| 호스트                                   | `available` | 참고 / 힌트                                                               |
| -------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| macOS                                  | `true`      | `sandbox-exec` (Seatbelt) — 네임스페이스 격리, 커널 경계 없음                 |
| `bwrap`과 `socat`이 있는 Linux 또는 WSL2 | `true`      | bubblewrap — 네임스페이스 격리, 커널 경계 없음                                |
| 도구가 하나라도 없는 Linux 또는 WSL2      | `false`     | `requiresInstall: true`, 누락된 패키지를 알려 주는 설치 힌트가 함께 제공됩니다 |
| 그 밖의 모든 플랫폼                        | `false`     | 이 플랫폼에서는 네이티브 샌드박스를 제공하지 않습니다                          |

서버는 그 결과를 시작 줄 하나에 기록합니다. `agent sandbox ON`에 해당 설명이 붙거나, 힌트가 붙은 `no OS-native agent sandbox on this host`(책임 있는 실행만 시작된다는 내용이 추가됨), 또는 `agent sandbox DISABLED by --sandbox off`입니다. 시작할 때 출력되는 노출 줄은 같은 결정을 `sandbox=native`, `sandbox=off`, `sandbox=unavailable`로 담습니다. `GET /healthz`에는 샌드박스 필드가 없습니다.

`--sandbox` / `CC_SERVER_SANDBOX`는 `on`(기본값) 또는 `off`를 받습니다. `on`은 호스트가 백엔드를 제공할 때 모든 실행을 감싸고, 제공하지 않을 때는 소유자의 실행만 허용합니다. `off`는 이 호스트에서 모든 구성원의 에이전트를 제한 없이 실행하며, 실행마다 설정하는 옵션이 아니라 모든 사용자에 대한 소유자의 선택입니다.

## 네이티브 백엔드

### macOS: Seatbelt

Apple의 Seatbelt 샌드박스 메커니즘을 사용합니다(macOS App Sandbox가 사용하는 것과 같은 시스템).

생성되는 프로필은 **기본적으로 허용하는** 방식(`(allow default)`)이며 거부 항목을 도려냅니다. 완전히 기본 거부인 프로필은 대화형 셸을 쓸 수 없게 만들기 때문입니다 — 열거해야 할 dyld, XPC, Mach 호출이 너무 많습니다. 실질적인 결과는 에이전트가 여전히 호스트의 대부분을 읽을 수 있다는 것입니다. 등록된 체크아웃은 보이지 않음으로써가 아니라 명시적인 쓰기 및 이름 바꾸기 거부로 보호됩니다.

- **파일시스템 읽기**: 시크릿 경로(`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` 및 나머지 읽기 거부 집합)에 대해 거부됩니다
- **파일시스템 쓰기**: 거부로 재설정한 뒤 하위 경로를 명시적으로 허용하며, 필수 거부 경로(셸 rc 파일, `.git/hooks`, Claude 구성, 보호된 체크아웃)는 쓰기 가능한 루트 안에서도 차단됩니다. `file-write-unlink`는 거부된 모든 경로와 그 조상에서 거부되므로 이름 바꾸기로 쓰기 거부를 우회할 수 없습니다
- **프로세스**: 항상 위험한 바이너리에 대해 `process-exec`를 거부하고, 쓰기 가능한 디렉터리에서 무언가를 실행하는 것도 차단합니다. 홈 아래의 알려진 툴체인 설치 경로(corepack, `npx`와 `pnpm dlx` 캐시, Node 버전 관리자, Playwright 브라우저, rustup과 cargo, Go, fvm과 pub 캐시, pyenv, uv와 pipx, rbenv, sdkman, mise, asdf, `~/.local/bin`)는 그 차단 아래에서 다시 열립니다. 공유 임시 디렉터리도 차단됩니다. 대신 각 세션에는 `/private/tmp` 아래의 비공개 `TMPDIR`이 주어지며, 여기서 에이전트가 빌드한 프로그램(`go test` 바이너리, cargo 빌드)을 실행할 수 있습니다. 항상 위험한 바이너리에 대한 거부 규칙은 이 허용 규칙 뒤에 적용됩니다
- **네트워크**: 프로세스 내 프록시 포트와 DNS로 제한됩니다 — 루프백이 일괄 허용되지 않으며 TCP 리스닝이 거부됩니다. Unix 소켓은 세션의 비공개 `TMPDIR` 안에서만 허용되며, 여기에 IPC 소켓을 두는 tsx나 Chrome 같은 도구가 이에 해당합니다. SSH 에이전트와 다른 소켓은 계속 접근할 수 없습니다. 프록시가 세션별 도메인 허용 목록을 강제합니다([네트워크 이그레스](#네트워크-이그레스) 참고)
- **구성**: 프로필은 실행마다 `SandboxSpec`에서 생성됩니다
- **서버 자체 명령**: 서버가 프로그램을 실행하는 폴더(모든 `PATH` 항목과 `~/.local/bin` 같은 일반적인 사용자별 도구 폴더, `~/fvm/default` 같은 버전 관리자 링크는 해석된 상태) 중 어느 것의 직접 하위 항목도 만들거나, 교체하거나, 삭제하거나, 이름을 바꿀 수 없으며, 링크된 명령이 가리키는 설치된 패키지도 마찬가지입니다. [서버의 명령 폴더](#서버의-명령-폴더)를 참고하십시오
- **시작 파일**: 프로필이 읽기를 거부하는 모든 홈 경로는 쓰기도 거부되며, 서버 사용자의 셸과 세션의 시작 파일(`.zshenv`, `.zlogin`, `.bash_login`, fish 설정, systemd 사용자 유닛, 자동 시작 항목 등)은 모든 모드에서 쓰기가 거부됩니다

요구 사항:

- `sandbox-exec`(`/usr/bin/sandbox-exec`)는 모든 macOS 설치에 포함되어 있으며 추가 도구가 필요하지 않습니다

### Linux: bubblewrap

bubblewrap(`bwrap`)을 사용해 마운트 및 PID 네임스페이스를 만듭니다.

- **파일시스템**: 바인드된 경로만 보이는 마운트 네임스페이스를 만듭니다
- **네트워크**: 공유되지 않은 네트워크 네임스페이스에서 실행되며, 트래픽은 `socat` Unix 소켓 브리지를 통해 호스트 프록시에 도달합니다
- **프로세스**: PID 네임스페이스 격리
- **서버 자체 명령과 시작 파일**: macOS와 같은 보호가 bubblewrap 바인드로 표현됩니다. 아직 Linux에서 검증되지 않았으며, 그곳에서는 명령 폴더가 없는 경우 여전히 만들어질 수 있습니다

요구 사항:

- `bubblewrap`과 `socat` 설치(Debian/Ubuntu에서는 `sudo apt-get install bubblewrap socat`)
- 커널 네임스페이스 지원(최신 Linux에서는 표준)

bubblewrap은 기존 경로를 가릴 수는 있지만 쓰기 가능한 바인드 안에 *새*
`.env`, `*.key`, `*.pem` 파일이 생기는 것을 금지할 수는 없습니다. 표준 디스패치
정책은 이런 파일 이름 글로브 거부를 요구하므로, 현재 Linux/WSL2의 네이티브
에이전트 디스패치는 **탐지가 bubblewrap을 찾아내더라도 실패 시 차단됩니다**.
조용히 더 약한 정책으로 실행되지 않습니다. Linux 네이티브 디스패치를 복원하려면
생성 시점의 파일 이름 규칙을 지원하는 백엔드가 필요합니다. 샌드박싱을 끄는 것은
명시적인 무제한 옵트아웃이며, 동등한 우회 방법이 아닙니다.

실제로 Linux나 WSL2 서버는 오늘날 두 가지 방식 중 하나로 에이전트를 실행합니다. `--sandbox off`로 시작하면 모든 구성원의 에이전트를 제한 없이 실행합니다. bubblewrap이나 `socat`이 설치되어 있지 않으면 `unavailable` 상태가 되어 서버 소유자의 에이전트만 제한 없이 실행합니다. 두 도구가 모두 설치되어 있고 샌드박스가 켜져 있으면, 소유자의 실행을 포함해 모든 실행이 실패 시 차단됩니다.

## 서버의 명령 폴더

서버는 시작할 때 한 번, 프로그램을 실행하는 모든 폴더를 찾습니다. 그 폴더는 `PATH`의 각 항목, 서버가 탐색하는 사용자별 도구 폴더(`~/.local/bin`, `~/.bun/bin`, npm, yarn, pnpm 전역 폴더 등), 그리고 그 경로상의 모든 링크 뒤에 있는 실제 폴더(`~/fvm/default` 같은 버전 관리자 링크나 fnm 기본값)입니다. 샌드박스 안에서 에이전트는 이 폴더들의 명령을 추가, 교체, 삭제, 이름 변경할 수 없고, 그 명령으로 이어지는 링크나 링크된 명령이 가리키는 설치된 패키지도 마찬가지이며, 그 위의 폴더 이름도 바꿀 수 없습니다. 그렇지 않으면 샌드박스 실행이 서버나 사람이 나중에 샌드박스 밖에서 시작할 프로그램을 심어 둘 수 있기 때문입니다.

이것이 실행에 미치는 변화는 다음과 같습니다.

- 샌드박스 실행 안에서 하는 전역 설치는 "Operation not permitted"로 실패합니다. `npm i -g`, `pnpm add -g`, `yarn global add`, `bun add -g`, `corepack enable`, `pipx install`, `uv tool install`, 그리고 bin 폴더가 서버의 `PATH`에 있을 때의 `cargo install`, `go install`, `dart pub global activate`가 해당합니다.
- 기본 버전 전환도 같은 방식으로 실패합니다(`fnm default`, `nvm alias default`, `fvm global`). 도구가 제자리에서 스스로를 업데이트하는 것도 마찬가지입니다.
- 프로젝트 로컬 설치(`node_modules/.bin`), `npx`, `pnpm dlx`, corepack이 관리하는 패키지 관리자, SDK 캐시, 일반 빌드는 계속 작동합니다.

에이전트가 전역 도구를 쓰게 하려면, 서버 사용자로 서버 자체에 설치하고 서버를 재시작해 새 명령도 보호되게 하십시오. 또는 프로젝트에 설치하십시오. 서버 시작 후에 설치된 명령은 다음 시작부터 완전히 보호됩니다.

macOS에서 시행되고 테스트되었습니다. Linux에서는 같은 규칙이 아직 검증되지 않은 bubblewrap 바인드입니다. Windows에는 샌드박스가 없습니다.

## 격리 없음 백엔드

샌드박싱이 없습니다. 프로세스는 호스트의 파일시스템, 네트워크, 프로세스 접근을 그대로 가진 채 호스트에서 직접 실행됩니다. ACP와 하네스 `bash` 도구는 여전히 환경 정리와 명령 정책을 받습니다. `NoSandboxAdapter`를 거치는 Claude Code는 호스트 환경을 물려받습니다. 에이전트 디스패치는 `--sandbox off` 아래의 모든 실행에 이를 사용하며, 사용할 수 있는 백엔드가 없는 호스트에서는 서버 소유자 본인의 실행에만 사용합니다. 그 밖의 사람의 실행은 거기서 거부됩니다. 터미널의 경우 이는 호스트 셸이며, 이는 서버 소유자만 열 수 있습니다.

## 서버 호스팅 터미널

서버 호스팅 터미널은 서버의 [소유자](/ko-KR/매뉴얼/개념/권한-부여/#서버-소유자)에게만 호스트 셸을 엽니다. 그 밖의 모든 사람은 워크스페이스 자체 디렉터리 안에서, 에이전트와 같은 제한을 받는 샌드박스 터미널을 받습니다.

세션의 백엔드가 선택되는 방식은 다음과 같습니다.

| 요청 | 서버 소유자 | 그 밖의 사람 |
| --- | --- | --- |
| 없음 | 서버의 기본 백엔드 | 기본값이며, `none`은 `native`로 대체됨 |
| `none`(호스트 셸) | 호스트 셸 | 거부됨: 호스트 셸은 샌드박스 없이 서버에서 실행됨 |
| `native` | 네이티브 샌드박스, 소유자 프로필 | 네이티브 샌드박스, 에이전트 프로필 |
| `microvm` | 격리 VM | 격리 VM |
| 알 수 없는 이름 | 거부됨 | 거부됨 |

- **소유자 프로필.** `$HOME`과 세션의 작업 디렉터리는 쓰기 가능하고, 네트워크는 열려 있으며, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains`는 읽기가 거부됩니다.
- **에이전트 프로필**(`memberTerminalSandboxConfig`). 그 워크스페이스의 에이전트가 실행되는 것과 같은 정책입니다. 쓰기는 작업 디렉터리, 비공개 실행 디렉터리, `/tmp`, 그리고 에이전트가 쓸 수 있는 `$HOME` 부분에 머무르고, 시크릿은 읽기가 거부되며, 네트워크는 에이전트 이그레스 허용 목록을 따르고, 프로그램은 작업 디렉터리와 설치된 툴체인에서만 실행됩니다.
- 터미널은 워크스페이스 자체 디렉터리 안에서만 열립니다. 그 밖의 작업 디렉터리는 다른 것으로 바꾸지 않고 거부됩니다.
- 터미널을 연 사람만 읽고, 입력하고, 크기를 바꾸고, 닫을 수 있습니다. 그 밖의 누구에게도 그 id는 알 수 없는 것으로 보입니다.
- 리그 서비스가 없는 호스트에서 `microvm`을 명시적으로 요청하면 대체하지 않고 실패합니다. 그런 호스트의 `microvm` 기본값은 `native`로 내려가며, 로그에 그 사실을 남깁니다.

읽기 전용 forge 토큰과 푸시 게이트웨이는 터미널에 적용되지 않습니다. 그것들은 디스패치의 관심사입니다. 래핑이 지원되지 않으면 세션은 호스트 셸 세션에 샌드박스 배지를 표시하는 대신 실패합니다.

## 네트워크 이그레스

샌드박스가 시작되면 아웃바운드 네트워크 접근은 커널 방화벽 규칙이 아니라 프로세스 내 프록시가 강제합니다. 샌드박스되지 않은 실행(`--sandbox off` 아래의 모든 실행, 또는 백엔드가 없는 호스트의 소유자 실행)에는 이 중 어느 것도 적용되지 않으며, 그 프로세스가 스폰하는 프로세스는 서버 사용자와 똑같이 네트워크에 접근합니다.

- 샌드박스 런타임은 `cc_server` 프로세스 안에서 `127.0.0.1`에 HTTP/HTTPS 프록시와 SOCKS5 프록시를 실행합니다. **제한된 세션마다 한 쌍**입니다(`http_proxy.dart`, `socks_proxy.dart`). 동시 실행은 한 쌍을 공유하지 않습니다.
- 샌드박스로 감싸진 프로세스는 프록시 환경 변수를 받습니다(`HTTP_PROXY`/`HTTPS_PROXY` → HTTP 프록시, `ALL_PROXY` → SOCKS 프록시, `GIT_SSH_COMMAND`는 git-over-SSH를 SOCKS 프록시로 라우팅합니다). Linux에서는 네트워크 네임스페이스가 공유되지 않으므로 프록시가 유일한 출구이고, macOS에서는 샌드박스가 호스트 루프백을 공유하며 프록시와 직접 통신합니다.
- 각 연결의 대상 호스트는 세션의 도메인 허용 목록과 대조되며, 그 밖의 모든 것은 거부됩니다. 와일드카드 형식은 두 가지이며 각각 `*`가 정확히 하나입니다. 맨 앞의 `*.example.com`은 모든 하위 도메인(`a.b.example.com` 포함)과 일치하지만 최상위 도메인 자체와는 일치하지 않습니다. 중간 레이블 형식 `bedrock.*.amazonaws.com`은 정확히 레이블 하나와 일치합니다(`bedrock.us-east-1.amazonaws.com`은 일치하고 `bedrock.evil.attacker.amazonaws.com`은 일치하지 않습니다).
- 허용 목록은 세션마다 큐레이션된 기준선(`kBaselineAllowedDomains`: LLM 공급자, Git 호스팅, 패키지 레지스트리)과 GitHub 도메인(`kGithubDomains`), 그리고 `SandboxSpec.egressAllowlist`에서 해석됩니다. 디스패치 경로는 추가 `egressAllowlist` 항목을 결코 전달하지 않으므로 실제로는 모든 실행이 기준선과 GitHub를 받습니다.
- 고정된 거부 목록(`kBaselineDeniedDomains`: 클라우드 메타데이터 엔드포인트, 텔레메트리 싱크)이 모든 허용보다 우선합니다.
- `networkEnabled: false`에서도 세션별 프록시는 시작되지만 허용 목록이 비어 있으므로 모든 아웃바운드 연결이 거부됩니다. 디스패치는 실행이 시작될 때 **네트워크 접근** 규칙에서 이 값을 정합니다. 거부는 네트워크를 끄고, 허용과 먼저 묻기는 켜 둡니다.

## SandboxSpec

`SandboxPort.launch`에 전달되는 명세입니다:

| 필드             | 타입                                        | 설명                                                                                                                                 |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId`       | `String`                                    | 안정적인 세션 식별자(일반적으로 스페이스 ID)                                                                                          |
| `workspaceId`     | `String`                                    | 소유 워크스페이스 ID                                                                                                                         |
| `agentId`         | `String?`                                   | 현재 샌드박스에 바인딩된 에이전트(있는 경우)                                                                                                |
| `bindMounts`      | `List<SandboxBindMount>`                    | 호스트→게스트 마운트. 샌드박스는 여기에 나열된 호스트 경로만 봅니다                                                                         |
| `networkEnabled`  | `bool` (기본값 `true`)                     | 디스패치 시 네트워크 이그레스 규칙에서 설정됩니다(거부로 해석될 때만 꺼짐). 꺼져 있으면 세션별 프록시는 여전히 시작되지만 허용 목록이 비어 있어 모든 아웃바운드 연결이 거부됩니다 |
| `egressAllowlist` | `List<String>` (기본값 `[]`)               | 추가로 허용되는 이그레스 도메인으로, 와일드카드(`*.example.com` 및 레이블 하나짜리 중간 형식)를 지원합니다. 디스패치는 이 필드를 채우지 않으므로 감싸진 실행은 큐레이션된 기준선과 GitHub 도메인을 받습니다 |
| `guestWorkdir`    | `String?`                                   | 샌드박스 안의 기본 작업 디렉터리로, 개별 `exec` 호출이 재정의할 수 있습니다                                                                   |
| `mode`            | `Mode` (기본값 `chat`)                     | 파일시스템 쓰기 규칙을 정합니다. `chat`은 바인드 마운트를 쓰기 가능하게 유지하고, `review`, `plan`, `orchestrate`는 읽기 전용입니다         |
| `protectedPaths`  | `List<String>` (기본값 `[]`)               | 어떤 모드에서든 샌드박스 안에서 결코 쓰기 가능해서는 안 되는 호스트 경로                                                                      |
| `runnerStateDirs` | `List<String>` (기본값 `[]`)               | 러너가 자체 상태를 보관하는 호스트 디렉터리로, 모든 모드에서 쓰기 가능합니다(현재는 Control-Center가 관리하는 `CLAUDE_CONFIG_DIR`) |
| `execGrantRoots`  | `List<String>` (기본값 `[]`)               | macOS에서 쓰기 가능 디렉터리 실행 차단을 다시 여는, 운영자가 승인한 디렉터리 트리입니다. Linux에서는 무시됩니다 — bwrap에는 다시 열 `$HOME` 실행 차단이 없습니다 |

`protectedPaths`는 등록된 원본 리포지토리 체크아웃을 담으며, 디스패치마다 워크스페이스의 리포지토리에서 해석됩니다. 에이전트는 대화별 쓰기 시 복사 워크트리에서만 작업하므로, 원본은 샌드박스 안에서 결코 쓰기 가능해서는 안 됩니다 — 그렇지 않으면 macOS에서 Seatbelt의 일괄 `$HOME` 쓰기 허용 때문에 `bash`를 통해 원본에 쓸 수 있게 됩니다. 이 경로들은 `chat`을 포함한 모든 모드에서 시크릿 쓰기 거부 집합에 합류합니다.

모든 읽기 거부 및 쓰기 거부 경로는 리터럴 표기와 심볼릭 링크 해석 표기 두 가지로 내보내집니다. 커널은 거부 규칙을 해석된 경로에 대조하므로, 심볼릭 링크된 경로를 기준으로 작성된 규칙은 결코 발동하지 않습니다 — 그리고 macOS에서는 이것이 예외가 아니라 일반적인 경우인데, `/tmp`는 `/private/tmp`로, `/var/folders/…`는 `/private/var/folders/…`로 해석되기 때문입니다. `*`나 `?`가 포함된 항목은 글로브로 취급되어 그대로 둡니다. 해석되지 않는 경로는 작성된 그대로 유지됩니다.

## SandboxBindMount

| 필드       | 타입                     | 설명                                                                                             |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `hostPath`  | `String`                 | 호스트의 절대 경로                                                                               |
| `guestPath` | `String`                 | 샌드박스 안의 경로(네이티브 샌드박스에서는 `hostPath`와 같으며, 어댑터 대칭을 위해 유지됩니다) |

## SandboxHandle

`SandboxPort.launch`가 반환합니다:

| 필드       | 타입                   | 설명                                                              |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| `sessionId` | `String`               | 세션 식별자                                                       |
| `backend`   | `SandboxBackend`       | 실행 중인 백엔드                                                 |
| `state`     | `SandboxState`         | 수명주기 상태                                                          |
| `error`     | `Object?`              | `state`가 `error`일 때 설정됩니다                                              |
| `details`   | `Map<String, Object?>` | 어댑터 내부의 부기 정보(작업 디렉터리, PID, 프로필 경로 등) |

### SandboxState

| 상태       | 설명                                 |
| ----------- | ------------------------------------------- |
| `created`   | 명세는 만들어졌지만 VM이 아직 시작되지 않음 |
| `warm`      | 실행 중이며 명령을 exec할 준비가 됨          |
| `active`    | 현재 명령을 실행 중               |
| `suspended` | RAM을 절약하기 위해 일시 중지되거나 디스크에 체크포인트됨   |
| `destroyed` | 정리되었으며 핸들이 더 이상 유효하지 않음    |
| `error`     | 시작 실패 — `SandboxHandle.error` 참고   |

## 샌드박스 이벤트

| 이벤트 유형  | 설명                                                  |
| ----------- | ------------------------------------------------------------ |
| `stdout`    | 샌드박스의 표준 출력                             |
| `stderr`    | 샌드박스의 표준 오류                              |
| `exit`      | 샌드박스 프로세스가 종료됨(`exitCode`를 함께 전달)                  |
| `starting`  | 샌드박스가 시작 중                                       |
| `ready`     | 샌드박스가 exec 호출을 받을 준비가 됨                        |
| `killed`    | 호스트가 프로세스를 종료함(OOM, 타임아웃, 수동 중지)       |
| `violation` | 샌드박스 정책이 위반됨(`SandboxViolation`을 함께 전달) |

## SandboxViolation

| 필드                 | 타입      | 설명                                                                |
| --------------------- | --------- | -------------------------------------------------------------------------- |
| `action`              | `String`  | 거부된 동작(예: `file-read*`, `network-outbound`)                    |
| `target`              | `String`  | 거부된 작업의 대상이 된 경로 또는 호스트                   |
| `raw`                 | `String?` | 디버깅에 유용한 원시 로그 줄                                         |
