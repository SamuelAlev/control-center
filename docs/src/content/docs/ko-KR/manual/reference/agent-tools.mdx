이것은 내장 에이전트 런타임이 직접 등록하는 **서버 바인딩** 도구입니다. 언어 서버, 구조적 검색, 디버거, 커널, 코드 모드 스크립트, 질문, 워커 제어가 여기에 해당합니다. 런타임이 브리지로 연결하는 [MCP 도구](/ko-KR/매뉴얼/레퍼런스/mcp-도구/)나 하네스 런타임의 일반 파일, 검색, 셸 도구와는 다릅니다. 이 도구들은 MCP 레지스트리에 없습니다. 외부 MCP 클라이언트는 이들을 볼 수 없는데, 각각이 하나의 실행에 속하는 살아 있는 서버 측 리소스(언어 서버 프로세스, 디버그 어댑터, 인터프리터)에 묶여 있기 때문입니다.

여기 있는 모든 도구는 그 도구를 뒷받침하는 리소스가 실행에 연결되어 있을 때만 등록됩니다 — 언어 서버 또는 디버그 감독자, tree-sitter 파서, 커널 팩토리, 질문 포트, 바이브 로스터가 그것입니다. *이 체크아웃*을 위한 언어 서버나 디버그 어댑터 탐지는 별개의, 이후 단계 검사(`status` / `adapters`)입니다. 그 도구들은 표면에 남아 있어, 에이전트가 아무것도 쓸 수 없는 이유를 추측하는 대신 물어볼 수 있습니다.

## 승인 티어

각 도구는 티어를 선언하고, 그 티어가 **어떤 표면이 이 도구를 보는지**를 결정합니다 — 단순히 프롬프트가 뜨는지 여부가 아닙니다. 플랜 모드와 읽기 전용 서브에이전트는 `read`로 제한되므로, `write` 또는 `exec` 티어 도구는 그들의 스키마에 아예 없습니다.

| 티어    | 의미                          | 여기 있는 도구                                     |
| ------- | ----------------------------- | -------------------------------------------------- |
| `read`  | 부작용 없음                   | `lsp`, `ast_grep`, `ask_user`, `repl`, 다섯 개의 `vibe_*` |
| `write` | 파일 변경                     | `lsp_rename`, `ast_edit`, `resolve`                |
| `exec`  | 프로세스 시작 또는 제어       | `debug`, `eval`                                    |

## 직접 호출, 스크립트에서만 호출, 처음 사용할 때 적재

서버가 스크립트를 실행할 수 있으면, 실행은 몇몇 도구를 직접 호출하고 나머지는 [`repl`](#repl--도구를-호출하는-스크립트-실행) 스크립트에서 접근합니다. 전체 규칙은 [코드 모드](/ko-KR/매뉴얼/개념/코드-모드/#에이전트가-직접-호출하는-도구)를 참고하십시오. 이 페이지의 도구에 대해서는 다음과 같습니다:

| 도구 | `repl` 있음 | `repl` 없음 |
| ---- | ----------- | -------------- |
| `repl` | 직접 호출 | 없음 |
| `ask_user` | 직접 호출 | 직접 호출 |
| `lsp`, `lsp_rename`, `ast_grep`, `ast_edit`, `resolve`, `debug` | 스크립트에서만 호출 | 처음 사용할 때 적재 |
| `eval` | 처음 사용할 때 적재 (스크립트는 호출할 수 없음) | 처음 사용할 때 적재 |
| `vibe_*` | 바이브 모드에서 직접 호출, 스크립트에서는 결코 호출 불가 | 바이브 모드에서 직접 호출 |

“스크립트에서만 호출”로 표시된 도구는 서버가 그 실행의 스크립트를 실행할 수 없게 되면 대신 처음 사용할 때 적재됩니다([스크립트를 실행할 수 없을 때](/ko-KR/매뉴얼/개념/코드-모드/#스크립트를-실행할-수-없을-때)).

## `lsp` — 언어 서버 쿼리

실행에 언어 서버 감독자와 작업 디렉터리가 있을 때 등록됩니다. 서버가 실제로 답할 수 있는지는 호출 시점에 **교집합**으로 탐지됩니다. 루트 마커가 존재해야 *하고* 서버 바이너리가 해석되어야 합니다. 둘 중 하나만 있으면 서버가 시작되지 않으며 — `status`가 그렇게 알려 줍니다 — 조용히 추측하지 않습니다.

서버는 내장 표에서만 가져오며, 저장소의 `lsp.json`은 읽지 않습니다. 샌드박스된 실행에서는 실행마다 자체 언어 서버 세션을 가지므로, 서버는 실행마다 다시 시작됩니다. 프로젝트 로컬 바이너리(`node_modules/.bin`)는 실행이 샌드박스된 경우에만 사용되며, 프로젝트 루트는 실행의 작업 디렉터리 위로 결코 해석되지 않습니다.

위치는 열(column)이 아니라 `line`과 `symbol` 부분 문자열로 지정합니다. 열을 요구받은 모델은 추측하고, 잘못된 추측은 같은 줄의 다른 기호로 해석됩니다 — 맞아 보이지만 다른 것에 대한 답입니다. 탐색 작업에서 `symbol`을 생략하면 첫 번째 열로 추측하는 것이 아니라 오류입니다.

| 작업              | 인수                             | 반환                                       |
| ----------------- | -------------------------------- | ------------------------------------------ |
| `diagnostics`     | `file` (또는 `"*"`)              | 오류와 경고; `"*"`는 대신 프로젝트 검사기를 실행 |
| `definition`      | `file`, `line`, `symbol`         | 기호가 선언된 위치                         |
| `type_definition` | `file`, `line`, `symbol`         | 타입이 선언된 위치                         |
| `implementation`  | `file`, `line`, `symbol`         | 구체 구현                                  |
| `references`      | `file`, `line`, `symbol`         | 모든 사용처, 최대 50개                     |
| `hover`           | `file`, `line`, `symbol`         | 시그니처와 문서 주석                       |
| `symbols`         | `query` 또는 `file`              | `query`로 워크스페이스 검색 (최대 100개); `file`로 문서 기호 (최대 200개) |
| `code_actions`    | `file`, `line`, `symbol`         | 서버가 제공하는 빠른 수정                  |
| `status`          | —                                | 어떤 서버가 실행 중이며, 어떤 루트를 위한 것인지 |
| `reload`          | —                                | 이 루트의 서버를 재시작                    |

### 쓰기 시 진단

성과는 도구 자체에 있지 않습니다. `write`, `edit`, `apply_patch`는 **래핑**됩니다. 쓰기 후 파일이 언어 서버를 거쳐 동기화되고 저장되며, **새로 도입된** 진단만 도구 결과에 접혀 들어갑니다. 에이전트는 빌드를 깨뜨린 바로 그 순간에 그것을 알게 되며, 물어볼 것을 기억할 필요가 없습니다.

이미 보고된 진단은 심각도, 코드, 메시지를 키로 하는 실행별 원장으로 억제됩니다 — 위치는 의도적으로 제외되므로, 네 줄 아래로 옮겨진 것뿐인 진단이 새것으로 다시 보고되지 않습니다.

## `lsp_rename` — 프로젝트 전역 이름 바꾸기

별개의 `write` 티어 도구인 데에는 이유가 정확히 하나 있습니다. 티어가 가시성을 결정하기 때문입니다. 이름 바꾸기를 `lsp`에 합치면 읽기 전용 탐색자에게 저장소를 다시 쓸 능력을 쥐여 주거나, 모든 `hover`를 승인 프롬프트 뒤에 두게 됩니다.

| 인수       | 의미                                       |
| ---------- | ------------------------------------------ |
| `file`     | 기호가 있는 위치                           |
| `line`     | 1부터 시작하는 줄                          |
| `symbol`   | 그 줄에서 기호를 식별하는 부분 문자열      |
| `new_name` | 새로 부를 이름                             |

## `ast_grep` — 구조적 검색

코드를 텍스트가 아니라 **형태**로 찾습니다. `$NAME`은 모든 노드와 일치하고, `$$$NAME`은 형제 노드의 연속과 일치하며, `$_`는 아무것도 바인딩하지 않는 와일드카드입니다.

이를 몇 단계 더 거친 정규식이 아니라 진짜 매처로 만드는 특성은, 하나의 패턴에서 반복된 메타변수가 동일한 텍스트를 캡처해야 한다는 것입니다.

```
ast_grep(pattern: "if ($X != null) $X.dispose()", language: "dart")
```

테스트한 것을 dispose하는 가드와 일치하고, 다른 것을 dispose하는 가드와는 일치하지 **않습니다**.

| 인수          | 의미                                                        |
| ------------- | ----------------------------------------------------------- |
| `pattern`     | 메타변수가 있는 코드 조각                                   |
| `path`        | 검색할 파일 또는 디렉터리; 기본값은 워크스페이스 전체        |
| `language`    | 배포된 문법 id (`dart`, `python`, `rust`, `c`, …). `path`가 파일을 가리키면 추론됩니다 |
| `max_results` | 기본값 50                                                   |

:::note[패턴은 파일과 동일한 문법으로 파싱됩니다]
따라서 `dispose(x)`는 공백, 줄바꿈, 주석이 어떻게 되어 있든 그 호출과 일치하며, 문자열 리터럴이나 주석 안의 같은 문자와는 결코 일치하지 않습니다.
:::

:::caution[조각은 맨몸이 아니라 스캐폴드 안에서 파싱됩니다]
Dart의 최상위에서 파싱된 `dispose(x)`는 유효한 *함수 시그니처*입니다. 패턴 컴파일러는 컨텍스트 사다리(문장, 표현식, 클래스 멤버, 선언)를 시도하고, 조각을 받아들이는 첫 번째 것을 사용합니다. 어떤 컨텍스트도 받아들이지 않는 패턴은 검색해서 조용히 찾지 못하는 대신 파싱 불가로 보고됩니다.
:::

## `ast_edit` — 구조적 재작성, 스테이징됨

동일한 매칭에 더해, 메타변수가 다시 치환되는 `rewrite` 템플릿이 있습니다. **아무것도 기록되지 않습니다.** 변경은 스테이징되고, 결과는 `edit_id`를 알려 줍니다.

```
ast_edit(pattern: "dispose($X)", rewrite: "$X.dispose()", language: "dart")
→ (proposed) 12 replacements in 4 files … call resolve with edit_id "edit_1"
```

| 인수       | 의미                                                |
| ---------- | --------------------------------------------------- |
| `pattern`  | 일치시킬 대상                                       |
| `rewrite`  | `$NAME`이 치환되어 들어갈 내용                      |
| `path`     | 범위; 기본값은 워크스페이스 전체                    |
| `language` | 언어 id                                             |

## `resolve` — 스테이징된 변경 커밋 또는 폐기

| 인수      | 의미                             |
| --------- | -------------------------------- |
| `edit_id` | `(proposed)` 결과에서 얻음       |
| `action`  | `accept` 또는 `discard`          |

모든 파일은 스테이징 시점에 캡처한 내용과 비교되며, **어떤** 불일치든 전체 변경을 거부합니다. 일부만 적용된 구조적 재작성은 예전 형태로도 새 형태로도 컴파일되지 않는 트리를 남깁니다.

## `debug` — 디버거 구동

실행에 디버그 세션 감독자, 작업 디렉터리, 대화 id가 있을 때 등록됩니다. 어댑터가 실제로 시작할 수 있는지는 호출 시점에 언어 서버와 같은 교집합 규칙(루트 마커 *그리고* 바이너리)으로 탐지됩니다. `exec` 티어이며 병렬 안전하지 않습니다(세션은 호출에 걸친 상태이므로, `continue`가 `stack`을 추월하면 이미 이동한 프레임을 읽게 됩니다).

대화당 세션 하나이며, 하드 TTL(30분)이 있습니다. 두 번째 `launch`는 첫 번째를 조용히 대체하는 대신 거부됩니다. 샌드박스된 실행에서 세션은 끝날 때까지 턴에 걸쳐 샌드박스를 유지하며, 그 기간은 최대 30분입니다.

| 작업          | 인수                          | 비고                                           |
| ------------- | ----------------------------- | ---------------------------------------------- |
| `adapters`    | —                             | 여기서 어떤 어댑터를 쓸 수 있는지, 그리고 왜 아닌지 |
| `status`      | —                             | 세션이 실행 중인지, 어디서 멈췄는지            |
| `breakpoints` | `file`, `lines[]`             | `lines`가 비어 있으면 파일을 지웁니다. 실행 **전에** 설정할 수 있습니다 |
| `launch`      | `program`, `args[]`           | 중지점에서 멈춘 채 프로그램을 시작             |
| `attach`      | `port`                        | 실행이 직접 전달한 포트 중 하나에서 이미 실행 중인 디버기 대상에 연결. 다른 포트는 아무것도 시작되기 전에 거부 |
| `continue`    | `thread_id?`                  | 다음 중지 지점까지 실행                        |
| `pause`       | `thread_id?`                  | 있는 자리에서 중지                             |
| `step_over` / `step_in` / `step_out` | `thread_id?` | 한 단계 이동                             |
| `threads`     | —                             | 스레드 id와 이름                               |
| `stack`       | `thread_id?`                  | 프레임, 최대 30개                              |
| `scopes`      | `frame_id`                    | 프레임의 스코프, 각각 `reference` 포함         |
| `variables`   | `reference`                   | 자식, 최대 50개, 값은 최대 400자               |
| `evaluate`    | `expression`, `frame_id?`     | 프레임 자체의 스코프에서 평가                  |
| `output`      | —                             | 디버기 대상의 stdout/stderr, 크기 제한 있음    |
| `terminate`   | —                             | 세션을 끝내고 어댑터를 종료                    |

### 어댑터

| Id        | 명령                       | 루트 마커                                       |
| --------- | -------------------------- | ----------------------------------------------- |
| `dart`    | `dart debug_adapter`       | `pubspec.yaml`                                  |
| `debugpy` | `python3 -m debugpy.adapter` | `pyproject.toml`, `setup.py`, `requirements.txt` |
| `lldb`    | `lldb-dap`                 | `Cargo.toml`, `CMakeLists.txt`                  |
| `delve`   | `dlv dap`                  | `go.mod`                                        |

`debugpy`는 실행이 샌드박스된 경우 `$PATH`보다 프로젝트 로컬 `.venv/bin` 또는 `venv/bin`을 선호합니다. `$PATH`의 python은 다른 환경이며, 잘못된 환경에서 연결하면 코드가 깨진 것처럼 읽히는 방식으로 실패합니다. 샌드박스되지 않은 실행에서는 `$PATH`만 사용하므로, 저장소가 호스트에서 실행될 인터프리터를 고를 수 없습니다.

## `repl` — 도구를 호출하는 스크립트 실행

서버가 스크립트를 실행할 수 있으면 모든 실행에 있습니다([실행에 `repl`이 있는 경우](/ko-KR/매뉴얼/개념/코드-모드/#실행에-repl이-있는-경우)). 스크립트는 일반 JavaScript이며 async 함수의 본문이고, 자체 프로세스 안의 새로 만든 잠긴 인터프리터에서 실행됩니다. 파일 시스템, 네트워크, 프로세스, 모듈에 접근할 수 없습니다. 스크립트가 하는 모든 도구 호출은 각각 따로 검사되므로, `repl` 자체는 `read` 티어이며 스스로를 보호합니다. 서버가 스크립트를 실행할 수 있는 경우의 에이전트 실행에는 MCP 엔드포인트에서도 제공됩니다.

| 인수 | 의미 |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `code` | 스크립트. 최대 256 KiB |
| `description` | 필수. 대화 기록 행에 표시되는 짧은 레이블 |
| `timeout_ms` | 선택 사항. 워크스페이스 제한보다 짧은 시간 제한이며, 더 긴 값은 안 됩니다 |
| `max_output_tokens` | 선택 사항. 워크스페이스 예산보다 작은 출력 예산이며, 더 큰 값은 안 됩니다 |

```js
// Read three files together and report only which ones failed.
const paths = ["lib/a.dart", "lib/b.dart", "lib/c.dart"];
const results = await Promise.allSettled(paths.map((path) => tools.read({ path })));
return results
  .map((r, i) => (r.status === "rejected" ? `${paths[i]}: ${r.reason.message}` : null))
  .filter(Boolean);
```

`repl` 설명은 에이전트에게 이렇게 알려 줍니다: “직접 호출 도구가 아닌 도구는 이 요청에 정의가 없습니다. 그 도구를 처음 호출하기 전에, 정확한 호출 형태가 이 대화에서 이미 제시되지 않았다면, `describeTool(name)` 또는 `searchTools(query)`로 찾아보십시오.”

`describeTool(name)`은 도구의 설명, 선언, 입력 및 출력 스키마, 그리고 있는 경우 결과 노트를 반환합니다. 결과 노트는 완료된 호출에서 스크립트가 받는 값을 도구 자신의 표현으로 설명합니다. `repl` 설명은 스크립트가 호출할 수 있는 직접 호출 도구의 노트를 나열합니다. 결과가 JSON 텍스트이면 파싱된 상태로 도착하며, 다만 값이 131,072개를 넘으면 텍스트 그대로 도착하고 스크립트가 `JSON.parse`로 파싱합니다. 외부 MCP 서버 도구의 결과 텍스트는 262,144자에서 잘리며, 잘린 텍스트는 더 이상 파싱되지 않습니다.

- `tools.<name>(args)`는 직접 호출과 같은 필터, 가드레일, 승인을 거쳐 도구를 호출하며, 거부되거나 실패하면 오류와 함께 거부(reject)됩니다. 읽기 전용 호출은 함께 실행할 수 있고, 무언가를 바꾸는 호출은 스크립트가 호출한 순서대로 한 번에 하나씩 실행됩니다. 스크립트의 호출 하나가 사람을 기다리는 동안에는 그 스크립트의 다른 호출이 시작되지 않습니다.
- `ALL_TOOLS`, `searchTools(query, { limit, namespace })`, `describeTool(name)`, `describeNamespace(name)`는 연결된 MCP 서버의 도구를 포함해 도구를 찾습니다. 직접 호출 세트 밖의 도구 중 스크립트가 호출할 수 있는 도구는 스크립트에서만 호출할 수 있으며, 직접 호출하면 `repl`에서 호출하는 방법이 반환됩니다. 서버가 그 실행의 스크립트를 실행할 수 없게 되면, 그런 도구는 대신 처음 사용할 때 적재됩니다.
- 조회에는 제한이 있습니다. 쿼리는 최대 1,024자, 이름이나 네임스페이스는 최대 256자, `limit`은 0에서 50까지입니다. 스크립트마다 조회는 최대 200회이며 서버 시간으로 합계 2초까지입니다. 한 워크스페이스의 모든 스크립트는 조회 시간 2초를 함께 나눠 쓰며, 이 시간은 매초 0.25초씩 돌아옵니다. 둘 중 하나를 넘으면 그 이후의 조회는 모두 거부(reject)됩니다. 매우 큰 카탈로그에서는 `ALL_TOOLS`의 설명들이 약 100만 자를 똑같이 나눠 쓰며, 잘린 설명은 `…`로 끝납니다. `describeTool`은 항상 설명 전체를 반환합니다. 너무 커서 보여 줄 수 없는 타입은 `unknown /* too large to show */`로 표시되며, 알 수 없는 이름에는 가장 가까운 이름들로 답합니다.
- 도구는 네임스페이스로 묶입니다: `builtin`(하네스 자체의 도구), `control-center`(Control Center의 도구), 그리고 연결된 MCP 서버마다 하나씩이며 서버 이름을 따릅니다. 서버 이름이 `builtin`, `control-center` 또는 `script`이거나 `external-`로 시작하면(대소문자가 어떻게 섞였든, 앞뒤에 공백이 있든 없든) 그 서버는 `external-` 뒤에 이름을 붙인 것으로 표시되며, 어떤 도구도 `script` 네임스페이스에 속하지 않습니다.
- 스크립트가 반환하거나 `text()`, `image()` 또는 `console.*`에 넘긴 것만 돌아옵니다. 예산을 넘는 출력은 처음과 끝을 유지하고, `read_output`으로 나머지를 읽을 수 있습니다.
- `store(key, value)` / `load(key)`는 같은 대화와 에이전트의 이후 스크립트를 위해 JSON 값을 보관하며, 스크립트가 완료될 때만 저장됩니다. 서브에이전트의 스크립트에는 보관소가 없습니다.
- `await tools.ask_user(...)`는 질문하며, 그 답변은 결과에도 추가됩니다. `sleep(ms)`, `setTimeout`, `limits()`, `models.embed` / `rank` / `classify`(온디바이스 임베딩)도 사용할 수 있습니다.
- `describeTool(name)`과 `searchTools(query)`는 도구가 아닌 스크립트 자체의 함수에 대해서도 답합니다. 해당 함수는 `script` 네임스페이스 아래에 있으며 `text`, `image`, `store`, `load`, `sleep`, `setTimeout`, `clearTimeout`, `limits`, `exit`, `models.*`입니다.
- 스크립트에서 호출할 수 없음: `repl`, `eval`, `task`, `checkpoint`, `rewind`, `compact`, `search_tools` 및 `vibe_*` 동사.
- 스크립트는 자신의 실행의 과거를 읽을 수 있습니다. `history({start, role, tool, limit})`는 대화의 기록을 페이지 단위로 가져오며(호출당 최대 50행이며, 이전 페이지의 `next_start`를 `start`로 넘깁니다), `outputs()`는 이 대화와 에이전트에 대해 저장된 도구 출력을 나열하고, `loadOutput(handle)`는 그중 하나의 16,384자를 읽습니다. `storedKeys()`는 저장된 키와 그 크기를 나열합니다. `keep(value, label)`는 큰 값을 나중의 스크립트나 `read_output`이 읽을 수 있는 출력으로 저장하며, 스크립트가 완료될 때만 저장됩니다(값당 1 MiB, 실행당 64개 값과 16 MiB). `limits().returnBudgetChars`는 출력 예산이 얼마나 남았는지 알려 줍니다. 읽기 전용 실행(목표 리뷰)은 읽을 수 있지만 저장하거나 keep할 수는 없습니다. Claude Code와 ACP에서는 `history()`가 동작하고 `outputs()`, `loadOutput()`, `keep()`는 거부됩니다. Control Center가 이 실행들의 도구 출력을 보관하지 않기 때문입니다.
- 시간 초과, 출력 초과 또는 호출 한도에서 발생한 오류는 해결 방법을 알려 줍니다.

한 실행에서는 한 번에 스크립트 하나만 실행됩니다. 각 제한과 제한에 도달했을 때 일어나는 일은 [코드 모드](/ko-KR/매뉴얼/개념/코드-모드/#제한) 페이지에 있으며, 모든 스크립트는 **옵저버빌리티 → 코드 실행**에 기록됩니다.

## `eval` — 영속 인터프리터

변수, 임포트, 로드한 데이터가 호출 사이에 유지되는 Python 또는 JavaScript 셀입니다. `exec` 티어이며 병렬 안전하지 않습니다. `repl` 스크립트에서 호출할 수 없으며, 셀은 실행의 도구를 호출할 수 없습니다. 코드에서 도구를 호출하려면 [`repl`](#repl--도구를-호출하는-스크립트-실행)을 사용하십시오.

| 인수          | 의미                                             |
| ------------- | ------------------------------------------------ |
| `code`        | 셀                                               |
| `description` | 필수입니다. 트랜스크립트 레이블용 5~10단어       |
| `language`    | `python`(기본값) 또는 `javascript`               |
| `reset`       | 인터프리터를 폐기하고 먼저 깨끗하게 시작         |

- 마지막 표현식은 노트북이 하듯이 에코됩니다.
- `display()`가 동작하고, pandas 프레임은 표로 렌더링되며, matplotlib 그림은 **트랜스크립트가 보여 주는 이미지**로 돌아옵니다.
- 사람들이 반사적으로 입력하는 IPython 관용구 — `%pip`, `%cd`, `!cmd`, `%%bash`, `%%timeit` — 는 평범한 코드로 다시 작성됩니다. `%pip`는 `sys.modules`도 비우므로, 다음 `import`는 방금 설치한 것을 봅니다.
- 출력 예산을 넘는 셀은 앞의 4분의 3과 마지막 4분의 1을 남기며, 버려진 글자 수와 이미지 수를 알려 주는 한 줄이 함께 표시됩니다.
- 인터프리터가 요청 없이 종료된 경우, 다음 셀에는 이전 변수가 사라졌다는 사실이 한 번 알려집니다.

:::note[커널이 실행되는 위치]
대화에 인클로저가 있으면 그 안에서, 없으면 호스트에서 실행의 OS 샌드박스 안에서 실행됩니다. 샌드박스가 꺼져 있거나 사용할 수 없으면 제약 없이 실행되며, `eval`은 호스트 실행 승인을 요청합니다. 그러기 위해 인클로저를 부팅하지는 않습니다. 리그 탭이 자동으로 시작되지 않게 하는 것과 같은 규칙입니다.
:::

## 백그라운드의 `bash`

`bash`를 `run_in_background: true`로 실행하면 기다리지 않고 명령을 시작한 뒤 곧바로 핸들(`b1`, `b2`, …)을 반환합니다. 에이전트는 계속 작업하거나, 턴을 끝내고 명령이 종료되면 깨어납니다.

| 인수 | 의미 |
| ------------------- | ------- |
| `run_in_background` | `true`이면 즉시 시작하고 바로 반환 |
| `timeout_seconds` | 명령이 강제 종료되기 전까지의 초: 기본 600, 최대 3,600 |
| `notify` | 선택 사항. 간단한 패턴입니다. 명령이 실행되는 동안 일치하는 출력 줄마다 에이전트에게 전달됩니다(예: `listening on\|FAILED`) |

- 한 실행에서 동시에 실행되는 백그라운드 명령은 최대 4개입니다. 각 명령은 시간 초과 시와 실행이 끝날 때, 시작한 모든 프로세스와 함께 강제 종료됩니다.
- 명령이 종료되면 에이전트는 종료 코드, 출력의 마지막 2,000자, 그리고 나머지를 위한 `read_output` 핸들이 담긴 알림을 받습니다.
- 남은 작업이 백그라운드 명령뿐인 에이전트는 모델을 호출하지 않고 기다리며, 기다리는 동안 실행의 무응답 감시 타이머는 일시 중지됩니다.
- `bash_output(handle)`은 명령의 상태와 최근 출력을 읽고, `bash_kill(handle)`은 명령을 중지합니다. 둘 다 결과가 이미 전달되었는지 알려 줍니다.
- 스크립트는 백그라운드 명령을 시작할 수 없습니다. Claude Code에는 자체 백그라운드 Bash가 있으며, Control Center는 작업을 남겨 둔 턴 이후 그 실행을 최대 10분 동안 열어 둡니다.

## `compact` — 컨텍스트 창에 여유 공간 확보

다음 모델 호출 전에 대화의 오래된 컨텍스트를 압축하며, `focus`가 지정한 내용은 유지합니다(최대 1,000자). 가장 최근 턴은 그대로 남습니다. 에이전트의 턴별 예산 줄은 컨텍스트 사용량이 70, 80, 90%일 때 이를 보여 주며, 긴 새 작업 단계 전에 약 70%를 넘었다면 이 도구를 호출할 만합니다. 서버 소유자의 `preCompact` 훅은 focus에 내용을 추가할 수 있습니다([셸 훅](/ko-KR/매뉴얼/레퍼런스/에이전트-구성/#셸-훅)). 압축 후 서버는 “Still in flight” 블록을 추가합니다. 목표, 대기 중인 깨우기, 열린 질문, 백그라운드 명령, 체크리스트, 저장된 키가 담기며, 각각 복구하는 호출과 함께 표시됩니다.

## `ask_user` — 사람에게 질문하기

`read` 티어입니다. 실행이 운영자에게 무언가를 묻는 **유일한** 방법입니다. 대화에 번호가 매겨진 카드를 렌더링하고, 누군가 답하거나 건너뛰거나 질문이 타임아웃될 때까지 차단합니다. 질문을 채팅 메시지로 쓰지 마십시오 — 그러면 턴이 끝납니다.

| 인수              | 의미                                       |
| ----------------- | ------------------------------------------ |
| `question`        | 무엇을 물을지                             |
| `context`         | 선택 사항: 왜 묻는지, 답에 무엇이 달려 있는지 |
| `options[]`       | 선택지, 각각 `{label, description?}`       |
| `allow_free_text` | 입력한 답변을 받을지 여부                  |
| `multi_select`    | 여러 선택지를 고를 수 있는지 여부          |

건너뛰기는 성공입니다. 명시한 가정 위에서 진행하고 다시 묻지 않습니다. 타임아웃은 같은 지침이 담긴 오류입니다. 권한 프롬프트("이래도 되나요?")는 별개의 게이트이며, 대화에 같은 카드로 렌더링됩니다.

질문 포트와 대상 스페이스가 모두 있을 때만 등록됩니다. 사람이 연결되어 있지 않으면 호출은 영원히 차단되는 대신 **실패**합니다 — 승인자가 연결되지 않았을 때 가드레일 `prompt`가 취하는 것과 같은 실패 시 거부 태도입니다.

## `vibe_*` — 백그라운드 워커 지시

[바이브 모드](/ko-KR/매뉴얼/사용-가이드/백그라운드-워커-지시/)가 켜져 있는 동안에만 등록됩니다. 다섯 개 모두 `read` 티어입니다. 게이트는 편집이 실제로 일어나는 워커의 도구에 속하기 때문입니다.

| 도구         | 인수                                     | 비고                                        |
| ------------ | ---------------------------------------- | ------------------------------------------- |
| `vibe_spawn` | `brief`, `label`, `tier?`                | 즉시 반환하고, 워커는 계속 실행됩니다       |
| `vibe_send`  | `worker_id`, `message`                   | 브리프에 덧붙이고 다시 실행합니다           |
| `vibe_wait`  | `worker_id`, `timeout_seconds?`          | 워커가 끝날 때까지 차단합니다               |
| `vibe_kill`  | `worker_id`                              | 워커를 중지합니다                           |
| `vibe_list`  | —                                        | 티어, 상태, 경과 시간, 마지막 결과          |

`tier`는 `fast`(명확한 명세가 있는 기계적 작업) 또는 `good`(설계, 판단, 또는 `fast` 워커의 출력 검토)입니다.
