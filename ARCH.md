# Architecture

Control Center uses Flutter clients, a pure-Dart authoritative server, Riverpod, and Drift/SQLite. Coding/build rules are in [AGENTS.md](AGENTS.md); access control and credentials in [SECURITY.md](SECURITY.md). Read the subsystem below when changing it, rather than loading every package document.

## Runtime and data flow

```text
Desktop local ── supervised cc_server ── Noise over loopback WS
Desktop remote / web ── Noise over WSS ── cc_server
Phone PWA ── Noise over direct WS / broker relay ── cc_server
MCP clients ── JSON-RPC ─────────────── tool registry
Fleet workers ── leases + events ────── cc_server
```

`lib/bootstrap/server_backend.dart` resolves the persisted local/remote choice before the authenticated Riverpod container starts. Local desktop spawns a supervised server; web is always remote. The connected `RemoteRpcClient` overrides `rpcClientProvider`; all client repository bindings use `cc_data`, including local desktop. A `*_bindings{,_io,_web}.dart` seam exists only where the targets genuinely diverge (audio capture, calendar recording, meeting signals); an identical pair collapses to one file.

Desktop setup and the web gate share one landing (`lib/shared/widgets/server_connect/`): local run on desktop, a connect dialog also used by Settings, and a paste dialog for invite and pairing links. The main action follows the last saved mode. Connecting from a dialog keeps it open and shows a failure there with the entered values. Connect reuses the saved device credential and identity pin when the URL matches exactly one remembered RPC endpoint and no new invite or pairing key is supplied. Explicit credentials take precedence; failed retries leave the saved pairing intact. Opening a dialog clears the previous attempt's error without persisting a mode until it connects. A pasted link is untrusted: the dialog names its server and connects only on an explicit Connect. Phone relay links and sealed SSO completions do not parse there, and a web link that arrives unbidden opens the connect dialog for the same review.

`SecureRpcChannel` is the shared encryption boundary above the raw direct/relay adapters. It carries JSON-RPC and `RemoteResources` HTTP/WebSocket streams with independent bounded credit windows. Native clients expose a capability-scoped loopback URL facade; web clients use the shared Service Worker/MessagePort bridge. Browser editors are trusted client code on the Flutter app's origin. Their capability-scoped HTTP/WebSocket requests travel through the encrypted session to `cc_server`, which owns the code-server process and files. `SecureResourceHost` invokes existing server HTTP handlers over private loopback with device/user binding, preserving route-specific authorization. The editor extension's open/dirty reports and command SSE use a separate server-only private bridge, not client proxy capabilities.

Web login, remembered-session resume and server switches keep the current document loaded. Resource capabilities rotate per connection but remain same-origin; they are not server origins and must never trigger a CSP-cookie reload. Both the edge Worker and self-hosted web policy keep decrypted images/media same-origin while permitting the pre-connect identity probes and encrypted WebSockets.

`cc_remote` is an operations client of the same catalog, not a second backend. Conversation routes and drafts use explicit workspace/space/conversation identities; message links validate their owning conversation rather than falling back to a standing stream. Drafts remain in session memory across navigation and transport reconnects and are dropped when pairing authority changes. Run controls, plans, supervised goals, policy edits, provider connections and uploads call the existing server services with their normal role and capability checks. See the [phone capability map](apps/cc_remote/README.md#phone-specific-behavior).

Desktop shows the localized `DesktopBootApp` only when no server choice is saved. `runDesktopBootWindow` mounts it in the setup window after essential preferences/native-window setup and waits for `waitUntilFirstFrameRasterized` before media initialization, credential reads and backend connection. A framework `endOfFrame` alone is insufficient: a headless frame can finish without a native view rendering. Configured local and remote launches skip both the temporary window and its rasterization wait, connecting directly before mounting the main app. Missing credentials or a failed connection still open the normal setup/recovery window. The boot surface has no provider container, cached workspace data or session actions. Authentication and workspace admission still precede `DesktopBackendSession` adoption; a failed session build disposes its container and the initial backend.

On macOS, `AppWindows` explicitly shows each newly created main/setup/error window through its controller's native handle before waiting for its first frame. Flutter otherwise keeps the window invisible until presentation, while a headless launch or setup→primary handoff can report `hidden` and disable the frame that would reveal it. The existing will-show hook still applies chrome before showing and arms `WindowVisibilityGuard` for stale lifecycle state afterward. This creation-only action never reopens a window in response to ordinary Hide/minimize or affects the floating HUDs.

Desktop server switches keep `AppWindows` and its primary native window mounted. The session key belongs inside the primary window and around the HUD collection, not above the native-window tree. Each switch remounts the session UI and media-proxy scopes, then disposes the old container/backend after that frame. Optional media-proxy wrappers must not become ancestors of the primary native window. Adoption never shows or focuses it again, preserving position, size, fullscreen, Hide and minimize state.

Both composition roots build a session's container from one `sessionOverrides(...)` (`lib/bootstrap/session_overrides.dart`) and hand sessions to a `ServerConnectController`, which serializes switches (a repeated request for the same server joins the one in flight; a different server is refused until it settles, so two switches can never start two local servers on one data directory) and retires the outgoing session after the remount frame. Desktop wiring lives in `desktop_session.dart` (one session), `desktop_server_switcher.dart` (adopt, switch, return to setup) and `desktop_app_host.dart` (method channel); incoming URLs dispatch through `desktop_deep_links.dart` into the owning features. Returning to setup (sign-out, a lost remote) is the one path that replaces the whole native-window tree: it runs the pre-app setup surface, then mounts a fresh `DesktopAppHost`. Quitting a local session first stops the bundled server while the session's container, client and shutdown overlay are alive to show its teardown progress, and only then disposes them. `startupReporter` is the only writer of `serverStartupStatus`: foreground attempts go through `track`, and a background reconnect holds a `StartupLease` that stops reporting once anything else claims the indicator.

Device caches that belong to one person on one server (the onboarding-complete hint, the remembered workspace id, the workspace name/logo shown before the list loads) are keyed by `SessionScope` (`'<key>@<serverId>/<userId>'`, from the supervisor descriptor and `identity.me`). A cache written for another server or user is never read. The offline mutation queue (`lib/core/offline/offline_mutation_queue.dart`) stamps every entry with the session's server and user, its workspace and its enqueue time. It restores, flushes and resumes (`resumeAfterSignIn`) only this session's entries younger than 24 hours. Anything else is dropped unsent: another session's silently, this session's expired ones as dead letters. Without a scope it loads nothing and refuses `enqueue`. A server switch or a return to sign-in (`sessionOverrides`) empties it first.

`WindowDragArea` resolves drag, manual move and double-click zoom through its enclosing Flutter `WindowScope` and `nativeWindowOf`. Never target nativeapi's focused/current window: the focus, meeting and soundscape HUDs are deliberately non-focusable, so the primary window stays focused while the pointer operates a HUD. Web window actions remain no-ops.

The tray (menu bar) icon, close-to-tray and launch at login sit behind the web-safe `DesktopShell` port (`core/desktop/`); `NativeDesktopShell` (`app/tray/`) implements it and the web build keeps `UnsupportedDesktopShell`. The shell is process-level: the icon, the main window's hidden state and the close interceptor outlive server switches. `TrayPresenter` is session-level. It wraps the HUD collection, pushes `trayStatusProvider` (connection, open questions, approvals, working spaces) to the icon and native menu through listeners rather than rebuilds, and hosts `TrayPanelWindow`, a focus-dismissed popover placed by `resolveTrayPanelBounds`. Switching workspace from the panel navigates the main router, hidden or not, because the route is the active workspace's source of truth; the panel then follows it. A hidden main window disables frames, so opening the panel forces one, and the will-show hook arms `WindowVisibilityGuard` for it. The icon is one monochrome template glyph on every OS (`tool/tray_icons/` traces it from `assets/logo_white.svg`): AppKit inks it for the menu bar, and nativeapi for the Windows taskbar theme and the StatusNotifierItem panel, following their theme changes. On Linux the shell asks the session bus (`package:dbus`, no subprocess) whether a StatusNotifierWatcher exists; stock GNOME has none, so close-to-tray stays off there. Closing the primary window asks the presenter first. It hides only when something can bring the window back (always the Dock on macOS; the tray icon elsewhere), and Windows and Linux ask once before the first hide. Hiding goes through the controller's native handle, never nativeapi's window list, which omits hidden windows on Windows. Notification clicks, deep links, `reopen` and `openSettings` reveal the window first. A login launch is `--launched-at-login` on Windows/Linux and the `keyAELaunchedAsLogInItem` Apple Event on macOS (an `SMAppService` login item cannot pass arguments). When it opts to start hidden, the will-show hook vetoes the first show on macOS and Windows; Linux, which cannot veto, hides right after. The native runners route a second launch to `reopen`, so the app stays a single instance. A login launch that finds the app already running does not raise it.

Server startup and background on-device model work share a non-modal floating **Server activity** panel in desktop boot/setup, onboarding and the connected app. Startup state is client-owned until RPC is available; model progress and retained download failures come from the server's existing `models.*Status`/`models.watch*` snapshots on both local and remote connections. Completed work disappears, failures retain technical details, and only the install owner can retry model installation. Onboarding suppresses the speech-model lane while its own inline progress is visible, without hiding background embedding/diarization work. Narrow onboarding layouts scroll the introduction with the fields and reserve activity space inside the keyboard-resized body; step actions stay pinned and activity details fold away during typing. Root modal dialogs temporarily hide the activity panel. Local reconnect activity belongs to its process holder and is released on retirement, so local health pings cannot replace remote switching progress or failures. A local child that exits before readiness reports a bounded, secret-redacted tail of stdout/stderr so bind and native-preflight failures reach setup rather than only the log.

`DesktopUpdateLifecycle` starts supported desktop updaters after the first setup or `ControlCenterApp` frame, independently of login and workspace-shell routes. Pre-connection setup uses an isolated updater-only provider scope; the connected app supplies the recording busy probe. Automatic checks run after 60 seconds and then every 24 hours, deferring prompts during recordings. Disposing the owning scope cancels the schedule and releases native callbacks.

The What's new dialog renders `usectrl.dev/changelog.md`, fetched by the server through `changelog.get` and parsed by `ChangelogRelease.parseMarkdown`; clients never contact the website. `ChangelogAfterUpdate` opens it on the first shell launch of a new `BuildInfo.buildVersion`, keyed by a client preference. A fresh install records its version silently, and an unreachable changelog leaves the version unseen so the next launch retries instead of opening an error.

The server owns external APIs and background services. `rhttp` adapters in `cc_infra` inject auth and classify failures through `network/error_mapper.dart`; unhandled transport errors are mapped at the RPC boundary. Workers execute leased jobs and stream events; they do not own databases, policy, approvals or budgets, and do not coordinate with each other. Architecture boundaries are enforced by `test/core/architecture_constraints_test.dart`.

HTTP uses rhttp's native reqwest engine, not a Flutter plugin. `cc_natives.initializeRhttp` loads the required library before client creation in each isolate. `createHttpClient` provides platform certificate roots, a default `ControlCenter` User-Agent (required by APIs such as GitHub), request normalization, retries, identity-aware deduplication and logging. Explicit client and per-request User-Agent values take precedence. Downloads use streamed bodies with receive-idle deadlines rather than a whole-transfer timeout. The headless dependency patch and native build contract are documented in [cc_natives](packages/cc_natives/README.md).

### Identity and collaboration

`Principal` is `UserPrincipal | AgentPrincipal`; use it for attribution. Users are global; membership/roles and repo grants are workspace-scoped. A username (`User.handle`) follows one rule (`Username`); generated names come only from `insertWithFreeHandle`, and the user DAO enforces uniqueness in a transaction backed by `idx_users_handle`. A person's connected accounts have no read model of their own: Settings → You → Profile lists them under the profile and reads each from the op that owns it (`forge.listConnections`, the sign-in lanes, calendar accounts, chat links), and `identity.me` carries `sso_issuer` when the caller's account is pinned to an identity provider. `ForgeConnection` carries the forge's own account id when the stored credential has one (`account_id`: the GitHub or GitLab user id, Bitbucket's `account_id`). See [authorization](SECURITY.md#authorization-and-isolation).

- Server owner: recorded once in `server_meta.server_owner_user_id` (`identity_bootstrap.dart`), never derived from account age. An op that needs the owner declares `serverAuthority: ServerAuthority.serverOwner`; the dispatcher's gate refuses everyone else with `-33002` and `data.kind: server_owner_required`, which clients map once. `identity.me.can_create_workspaces` tells the client whether to offer workspace creation, and `identity.me.can_use_host` whether to offer what runs on the server host unsandboxed (the host terminal, the embedded code-server editor, environment definitions that run on the host); `workspace.create` (`{name}`, server-minted id) is the only way to create one. `ProcessDetectionService` is server-only (`detect(visible:)`, `stopRun(pid, mayStop:)`): clients reach it through `process.detect` / `process.kill`, the catalog passes the caller's workspace filter on every call, and the server signals a pid only when it is a live agent run the caller may stop.
- Durable state: clients render full-snapshot `*.watch*` subscriptions; there is no client delta mirror. Per-field ticket edits use `tickets.patch` (per-column LWW): server receipt order, never client time, decides the last writer.
- Presence: server-hubbed, ephemeral, never persisted, humans only; agent status comes from run logs, not a presence lane. `presence.watch` redacts per subscriber through `PresenceViewer` (`catalog/presence_visibility.dart`): a member without every linked repo loses space/file/PR loci, the space they type in and worktree claims they cannot read, but keeps online state; admins and fully granted members see everything. `PresenceHub` signals only on a real state change (a heartbeat that repeats the wire entry is silent) and caches display names for five minutes, healed immediately by `UserProfileChanged`, which every writer of a username, display name or avatar publishes (`announceUserProfileChange`). The title-bar rail and space-header avatar strip show only other human users; with one human, roster chrome stays absent even while agents run.
- Follow is user-to-user only, ending when the follower navigates away or the active workspace changes. Starting a follow baselines the current route, so a target with no locus never yanks the follower later, and a spotlight never ends a follow (it only navigates when not following). Steer/interrupt/take-over and per-space autonomy use these lanes, not a CRDT.
- Take-over is one claim (`CacheDao.putIfAbsent`) before any run pauses; a failed begin resumes what it paused and drops the claim. Only the holder or a workspace admin hands back; the marker is removed first, so a failing resume never leaves a stuck takeover, and the failure is reported. Clients subscribe to `takeover.watch`, never poll.
- Agent peer messages use durable spaces, exact ID/unique-name resolution and no cross-workspace recipient search; `consult_agent` resolves its specialist the same way (the topic only frames the brief). `from_agent_id`/`delegated_by_agent_id` are forced to the trusted caller by `McpCallScope.apply` (`callerIdentityKeys`) on both transports, and dropped when there is none. `ask_agent` has a mandatory timeout (default ten minutes, workspace-capped); `PeerDelegationGate` runs its guards (parent ticket, depth, autonomy ceiling, budget, in-flight cycle) before the DM space or rate slot is touched, and the reply is the run's own message (its id is the dispatched run id) in that conversation, with stream errors returned rather than waited out. `delegate_task` and `delegate_ticket` pass the same gate (ticket hand-off: the parent only has to exist in the workspace, and depth is the parent's ticket depth) before `TicketWorkflowService.createDelegatedTicket` writes the child, so all three refuse a cycle or an exhausted budget with the same reason and an unconfigured policy refuses. `send_to_agent` refuses an in-flight cycle. Messages the server itself posts (takeover notices, delegation outcomes, compaction markers) are `SenderType.system` from sender `system`. Delegation inherits budget and autonomy ceilings, with cycle detection and a default depth cap of three. Agent-only spaces (`SpaceKind.agentPeer`) never raise unread (the activity SQL nulls their agent timestamp) or notify: one server predicate in `notification_wire.dart` decides, and desktop, web and cc_remote consume its verdict.
- Agent-finished notifications come from `MessageReceived` after the turn is persisted. Their preview uses the last non-blank `TextSegment`, capped at 120 characters, rather than the stored message content that joins all progress prose. Reasoning and tool output never supply preview text; a turn with no visible text retains its failure fallback or emits no notification. Live notifications and the durable bell feed share this preview.
- Human questions (`ask_user`) use the session's workspace, space, conversation and agent IDs, never a model-selected or implicit standing conversation. `AgentQuestionRequest.conversationId` is required; an empty destination throws, the server validates it before posting, and the awaiting-input notification carries the same conversation. `cc_infra`'s `AgentQuestionService` is the only implementation: every ending claims the waiter first, expiry is the conditional `MessagingDao.expireQuestion` (`answered != 1`), and `deliverAnswer` reports `delivered`/`notPending`/`notPersisted`, so the client shows a localized rejection rather than a false success. A boot sweep (`orphaned_wait_sweep.dart`) closes questions and resolves feed waits a previous process left open.
- A desktop awaiting-input notification is keyed by its wait (`wait-<wait_id>`) and is time-sensitive. An approval adds Approve and Deny buttons that call `confirmation.respond`. `AgentWaitReminder` follows the active workspace's feed: it re-raises an open wait at 3, 10, 25 and 45 minutes after it started (a question drops steps at or past the server's question timeout), replacing the earlier notification, and skips a reminder while an app window has focus. When the feed stamps the wait resolved, it withdraws the notification. Waits are not re-pushed from the server: the server's feed row and its resolution are the only state involved.
  Pending-question views combine workspace-scoped message snapshots with live `AgentQuestionService` waiter changes. A persisted unanswered message without an active asker is history, not an actionable request after restart. Validate an answer before consuming its waiter; competing valid replies still have one winner.
- Run-owned checklists (`todo_read`, `todo_write`) require the session's workspace and conversation and overwrite model-supplied IDs, including a space ID or another valid conversation. The model-facing schema does not require those IDs. External MCP and the harness bridge share `McpCallScope`; tools declare mandatory context with `requiredScopeKeys` and non-overridable arguments with `forcedScopeKeys`. Missing trusted context is an error, never permission to fall back to model-selected IDs.
- The General sidebar follows the focused chat in the live `EditorLayoutController`, switching its conversation-owned TODO/goal subscriptions on tab presses, split focus and layout restore. Local tab presses only publish platform history, so GoRouter's `?tab=` state is not a live selection source. Only the seeded space chat resolves its standing conversation; non-chat and empty editor selections show no conversation checklist. TODO rows and mutations use `conversationId`, with `workspaceId` retained for isolation; there is no TODO `spaceId`.
- The dispatch silence watchdog suspends only for question wait IDs matching its workspace, conversation and agent, and ignores a wait stamped with another run's id. It measures from the run start, so a run that never produces output still times out. Overlapping waits remain suspended until the last resolution, which starts a fresh inactivity window. A terminal error marks the turn failed even when the agent already emitted progress prose; an error followed by a recovered answer does not.
- `DomainEventBus` declarations under `cc_domain/lib/core/domain/events/` are authoritative. Device revocation watches `paired_devices`; there is no `UserDeviceRevoked` event. Workspace removal drops subscriptions without requiring the socket to close.

### Provider credentials and Connect

Every provider credential lives on the server and resolves per call; no build carries one. Server code is under `packages/cc_server_core/lib/src/connect/` and `forge/`; the broker is [apps/cc_connect](apps/cc_connect/README.md) and the shared contract `packages/cc_connect_core`. Trust boundaries are in [SECURITY.md](SECURITY.md).

**Sign-in lanes.** `ProviderSignInService` runs every browser sign-in (`github`, `google`, `linear`, `linear_app`, `slack`) behind `oauth.lanes|begin|status|complete|connections|disconnect`. The person is always `ctx.userId`, never an argument. Each lane binding resolves through the workspace's `ConnectRoute` (below): on its own apps, only the workspace's app (`WorkspaceGitHubAppSettings` for `github`, `WorkspaceProviderAppSettings` for `google`, `linear` and `linear_app`); inheriting a server on its own apps, the server's app from `ProviderAppSettings`; otherwise the route's Connect when its config advertises the lane; else unavailable. Completeness: GitHub needs app id, private key, client id and client secret; Google client id and secret; Linear only a client id (public PKCE client). A partial own app throws `SignInMisconfigured` and never mixes with Connect. A workspace on its own apps never routes through the server's app or any Connect (`allowsConnect` is false).

**Connect choice gates the server's own apps.** `ConnectSettings.choice()` is authoritative: the server's own apps apply only while `serverOwnAppsActive()` (mode `unset`/`off`). Under `hosted`/`custom` they stay stored but inactive everywhere, through one chokepoint in `ProviderAppSettings` (`active()`, `ProviderAppStatus.effectiveState`): sign-in lanes' `ownApp`, `GitHubClients.laneFor`, the `LINEAR_API_KEY` service-key fallback, `KlipyGifs`' own key and `connectLaneStatuses`. A workspace that overrides the server's choice never uses them. `ConnectSettings.addListener` → `ProviderAppSettings.connectChoiceChanged()` notifies every provider listener, so a choice change drops cached GitHub clients and tokens like an own-app edit.

- Own app: the browser returns to `providerOAuthRedirectUri(origin, lane)` = `<origin>/oauth/<lane>/callback` with a single-use `state`. The callback stores nothing: it keeps the provider's one-time code, reflects nothing from the request, and shows an 8-character confirm code and the `oauth-done` link. The origin is the configured public URL (or loopback), never a `Host` header; Settings shows the same string for registration.
- Connect: the browser returns to Connect, which shows a consent page (what the server will be able to do, a warning, continue or cancel, answered with the page's single-use form token) and, after continue, an 8-character confirm code and a `control-center://oauth-done?login_id=…&code=…` link (`lib/core/deep_link/deep_link_handler.dart`). `oauth.complete` claims it with the code, this server's PKCE verifier and its signed install identity. A link the local client did not start is never completed.
- Both modes end in `oauth.complete`, called by the person and workspace that began the attempt: it exchanges and stores, re-checks admin for a workspace lane, asks the provider who the grant is for, and refuses an account another person already holds (`signin.account_already_bound`, the grant revoked). GitHub is asked with `prompt=select_account`. A grant that lands after its attempt ended is revoked. The sign-in wire enums shared by server and clients live in `cc_connect_core` (`SignInFailure`, `SignInUnavailableReason`, `SignInAttemptStatus`); neither side keeps its own copy, and clients never match server message text. A claim Connect answers `rate_limited` leaves the attempt pending (`code_error: rate_limited`, `signin.claim_deferred`) and counts no wrong code.
- Attempts live 10 minutes; a wrong code comes back on the still-pending attempt as `code_error: code_mismatch` (never an exception), and the fifth fails it as `invalid_code`, kept until expiry so the client can show why; at most 256 attempts are held and 4 pending per person (`signin.evicted`), since the own-app callback is unauthenticated. `oauth.status` for an attempt the server no longer knows (restart, eviction) answers a failed attempt with `attempt_unknown`. Every `oauth.*` call carries the active workspace, checked as registered and not deleted before membership; the server, never the client, decides the slot. `oauth.lanes` gives an unavailable lane its `unavailable_reason`: `not_configured`, `misconfigured` (with `error`), `own_app_missing`, `connect_unprovisioned`, `connect_pins_pending`, `connect_unreachable`, `connect_url_invalid`, `blocked_by_environment` or `lane_not_offered`. `linear_app` and `slack` are workspace lanes that need a workspace admin; `google` needs a workspace.
- `ProviderAppSettings` seeds each field once from the `.env`-merged environment (`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `LINEAR_CLIENT_ID`, `LINEAR_API_KEY`); later Settings edits win. `refuseExportedProviderSecrets` stops the boot (exit 78) when a provider secret, `SLACK_*SECRET*`, or an embedded-Connect secret (`CONNECT_*_SECRET`, `_PRIVATE_KEY`, `_APP_KEY`, `CONNECT_SEAL_KEYS`, `CONNECT_LOG_HMAC_KEY`, `CONNECT_REDIS_URL`) is exported in the real process environment. `KLIPY_APP_KEY` is the operator's own key, used only for a workspace inheriting a server on its own apps; otherwise the route's Connect Klipy lane or nothing. A workspace on its own apps uses only its own Klipy key (none: no results), and `gif.search`/`gif.trending` (`catalog/gif_ops.dart`) are workspace-scoped for that.
- `GitHubManifestService` is **Create my GitHub App** (`github.manifest.begin`, server owner): a one-time `/oauth/github/manifest/start?ticket=` page (10 minutes, served once) auto-posts the manifest; `/oauth/github/manifest/callback` converts the code straight with GitHub (`POST /app-manifests/{code}/conversions`), checks the exact name (single-use nonce), that no permission exceeds the manifest's, and the owner, and stores all four fields. `github.install.begin` needs a workspace admin and returns the App's plain install page (on Connect, from the signed config's `app_slug`); `github.installations` lists installations with `suspended`. There is no per-server authorization: an account's installation is usable from any server a member signs in on.

**Per-workspace Connect choice.** `Workspace.connectMode` (`WorkspaceConnectMode`: `inherit`, the default, `hosted`, `custom` with `connectUrl`, or `own`) overrides the server's choice for one workspace; only `workspaceConnect.set` changes it (`workspace.upsert` keeps the stored value). `ConnectSettings.routeFor(workspaceId)` turns it into a `ConnectRoute`: `inherit` is the server's route (own apps when `serverOwnAppsActive`, else the server's Connect), `hosted` targets `hostedConnectOrigin`, `custom` the workspace's URL, and `own` targets no Connect and uses only the workspace's apps (Slack: its own app connection); an unregistered workspace gets nothing. Every lane takes its `ConnectTarget` from the route: sign-in, refresh, GitHub mints and installations, Linear, Google Calendar, Klipy and the Slack relay (`ConnectSlackRelayHub`, one long-poll per origin in use). A workspace keeps its own GitHub and Linear person slot (`ConnectRoute.workspaceSlot`) only while its sign-in target differs from the server's: its own apps, or a Connect whose target differs from the server route's. A `hosted` workspace on a `hosted` server shares the global grant. When a workspace's target changes (its mode or URL, its own app saved, rotated or removed, or the server's choice under `inherit`), its slot grants are revoked upstream and deleted, as Google's and Linear's are, and readers use an overlay grant only while the workspace owns a slot. `CC_CONNECT_URL` also forbids a workspace `hosted`/`custom` choice: `set` refuses it, and one already stored routes to nothing until an admin picks again (`blockedByEnvironment`), never to the server's apps or Connect. A workspace URL must be HTTPS and pass the `/proxy/media` SSRF rules when saved (`ConnectSettings.checkWorkspaceConnectUrl`), and such a target is `guarded`: every connection resolves, checks every address and connects to the checked one (`pinnedPermittedConnection`), so DNS rebinding cannot move it inside. `workspaceConnect.status` (member; `install_id` and `pending_pins` for admins only), `set`, `test` and `confirmPins` (admin) are in `catalog/workspace_connect_ops.dart`. A choice change (`ConnectSettings.workspaceChoiceChanged`) drops that workspace's GitHub clients and tokens, its Connect caches, rehomes its Slack relay, revalidates its Google credentials and resets its Linear grants.

**Connect choice and install identity.** `ConnectSettings` stores `connect_mode` (`unset` behaves as `off`, `hosted`, `custom`, `off`), `connect_url`, the hosted epoch high-water mark, the last verified config and custom TOFU pins; `CC_CONNECT_URL` (`hosted`, `off` or a URL) locks it. `ConnectClient` signs every call (RFC 9421) with an Ed25519 key HKDF-derived per Connect origin from the 32-byte `connect_install_key` in `FileSecretsStore`, separate from device pairing. `install_id` is 26 Crockford base32 characters of SHA-256(SPKI). Hosted config must verify against `hostedConfigRootKeys` (the public half of the offline key, [RELEASING.md](RELEASING.md#control-center-connect)) with a non-decreasing epoch; a build with an empty list reports `hosted_unprovisioned`. Tests that build a hosted `ConnectClient` pass `trustedRootKeys: const []` or a fake, never the real hosted Connect. A custom Connect pins its GitHub app/client ids, Google and Linear client ids and Slack ids on first use; a change pauses Connect lanes until `connect.confirmPins` (or, for a workspace's own custom Connect, `workspaceConnect.confirmPins`). Config, pins and pending pins are kept per `ConnectTarget.cacheKey`: the server's trust store, or a workspace's for the URL it chose, so a workspace admin confirming a change never moves the server's or another workspace's trust in the same URL; the hosted epoch high-water mark is shared. The install identity is per origin, so the same Connect sees one `install_id` whoever chose it. Config is cached 10 minutes and calls time out at 5 s; an outage serves the last good config as stale. A key-mode Klipy `app_key` is kept in memory only (the persisted config strips it), so after a restart key-mode GIF search waits for Connect. A choice or key change drops the cached config, the derived identity and every GitHub grant, whether made in Settings or by `cc_server connect` from another process (`ConnectSettings.noticeExternalChanges`, run before each config read). The seed is read and minted under one lock. An unusable `CC_CONNECT_URL` stops the boot and `cc_server connect` with exit 78 (`ConnectEnvironmentInvalid`); `choice()` never throws and reads it as off. `connect.*` ops and `cc_server connect` are server-owner only. `connect.rotateKey` (`install_key_rotation.dart`; an RPC only, because it needs the running server's lanes) revokes each Connect's sealed grants, retires the old install identity there with one of its seals (`POST /v1/install/retire`, signed with the old key; a Connect it holds no seal of is skipped), then swaps the seed by compare-and-swap; a failed retire keeps the old seed unless `force`. Access tokens already issued last until they expire.

**Seals.** A Connect grant is a `credential_seal`, AEAD-bound to provider, Connect origin, `install_id`, workspace, account, app and secret generation. A stored `ProviderToken` keeps only the seal plus `seal_install_id` and `connect_origin`; access tokens live in process memory. Reconciliation is lazy: `ForgeCredentials` (through `currentSealInstallId`, null when the slot's workspace uses no Connect or another origin) and `ServerGoogleTokenManager` compare on every read and clear a mismatched credential, which then reads as "sign in again". The slot's workspace on no Connect or another one is not a mismatch: the seal is kept, unusable until the choice comes back, and a refresh in that state is `RefreshUnavailable`. There is no startup sweep, so a restored backup or rotated key surfaces on first use. `sealStandingOf` (`ConnectClient.sealStanding`: `usable`, `parked`, `dead`) is the one rule every sealed lane applies. Refreshes are single-flight per credential (`SingleFlight`; GitHub, Connect and Linear refresh tokens are single-use): the flight re-reads the stored credential before spending a refresh token, and writes or clears only while the stored grant is still the one it refreshed, so a sign-in or sign-out that landed meanwhile wins. Only `RefreshRejected` clears. Connect's `/refresh` always rotates (a handoff replay excepted); only a scope mint reuses a still-fresh parent. A rotated seal the server cannot write is served from memory and written on the next use, since Connect already spent its parent. Connect answers a wrong confirmation code `code_mismatch` and a provider refusal after a matching code `needs_sign_in`; every post-claim failure ends the attempt (`store_failed` when the grant could not be kept, and an unstored Slack install is revoked).

**ForgeCredentials** implements `ForgeTokenStore` and `ForgeConnectionView` (`forge_credential_port.dart`) for people. GitHub is person-only: a member's own App user token or `null`, with no App, server-owner, environment or pasted-PAT fallback; `setToken` refuses GitHub, and a stored grant that is not an App sign-in (`isGitHubSignIn`) is never used. GitLab and Bitbucket stay token-based for people: the person's pasted token, one per person and used in every workspace (`slotFor` answers no workspace slot for a token forge, `credentials.setForgeToken` and `clearForgeToken` take no workspace), verified with the forge's `/user` on save (`forge/forge_viewer_probe.dart`; Bitbucket keeps `account_id` as the durable id and `nickname` as the login, and refuses an access token here; GitLab is asked `GET /user` before anything is stored, `forge/forge_person_token_check.dart`, and a project or group access token, `bot: true`, is refused toward the automation slot). `ForgeCredentials.tokenFor` without a person answers nothing on every forge. Background work on GitLab and Bitbucket (the poller, AI review chatter, unrequested agent pushes and merge requests, the link sweep) uses only `ForgeAutomationTokens` (`forge/forge_automation_tokens.dart`): an admin-stored project/group access token (GitLab, `/user` must answer `bot: true`) or repository/project/workspace access token (Bitbucket: not an `email:token` API token, and refused when `/2.0/user` answers 200 for any account but an `app_user`), per repository or per workspace and forge, the repository's own winning. `forge.setAutomationToken`/`clearAutomationToken`/`listAutomationTokens` are admin ops; the list carries the bot's name, scope and status, never the token. There is no person, server-owner or environment fallback: a repository with no usable automation token is refused locally (`ForgeCredentialUnavailable.automationTokenMissing`, RPC/poller code `automation_token_missing`), polls nothing and records `automation_token_missing`, which the clients show with an admin "Add token" action. Git over HTTPS uses `forgeGitHttpAuth` (`cc_infra`): `oauth2` on GitLab, `x-token-auth` for a Bitbucket access token, `x-bitbucket-api-token-auth` for an `email:token` API token. A person action without a usable credential throws `NeedsSignInException(lane)`, mapped to RPC `unauthorized` with `data: {kind: needs_sign_in, lane}` (`github`, `linear`, `google`, `gitlab`, `bitbucket`); the client opens that lane's sign-in or token dialog. `ForgeConnection` reports `status` (`connected`, `not_connected`, `needs_sign_in`, `paused` for a parked seal, `unreachable` for a refresh outage) and `scope` (`global`, or `workspace` for a GitHub sign-in kept for one workspace's own App or own Connect; never a pasted token); `forge.listConnections` derives `needs_sign_in` itself from a persisted lapse marker (`UserCredentialsStore`, cleared by sign-in, token set, disconnect and slot reset), so a refused grant still reads as one after a restart.

#### GitHub clients

`GitHubClients` (`forge/github_clients.dart`) is the only way the server obtains an authenticated GitHub client. Never construct one around a stored token elsewhere.

Identity follows GitHub's own split (installation token: activity attributed to the App; user token: to the person) and the industry pattern (Cursor, Copilot, OpenHands, Linear):

| Who acts | Token | GitHub shows |
| --- | --- | --- |
| A person in the UI: comment, review, approve, merge, reviewers, PR edits | their App user token (`asPerson`) | the person. GitHub names the App on issues and conversation comments only; a review and its inline comments carry no App label |
| Agent chatter and automation: AI review, PR-conversation replies, claim reactions, labels, pipelines, an agent's comment on its own PR (`comment_on_pull_request`) | one-repository installation token (`forRepo`/`forOwner`, scope clamped to the acting or accountable human) | the Control Center bot |
| A PR an agent opens for a person, the agent's pushes to it, and its edits of the PR's title or description (`update_pull_request`) | the requester's one-repository downscoped user token (`viaPerson`) | the person, so GitHub's own author/last-pusher approval rules apply |
| Work nobody requested (schedule, webhook) | installation token; on Control Center Connect at most `comment`, and `bot` (reviews) only for an install the Connect operator listed; never a push, branch or PR | the bot; a review on an unlisted Connect install goes out on the accountable person's own token |

This holds on every lane, with one Connect limit: nothing binds an organization's installation of a shared Connect App (hosted or custom) to one server, so its bot holds `read`, `review` or `comment` (`issues:write`: comments, labels, assignees, reactions) for every install, and `bot` (`pull_requests:write`: reviews) only for installs the Connect operator lists in `CONNECT_GITHUB_REVIEW_BOT_INSTALLS` (`GitHubTokenScope.connectBotMayHold`, `connectBotNeedsListing`); it never writes contents. GitHub would let a `bot` token approve, dismiss reviews, or open, edit or close a PR, but the server never approves with it and its request policy sends those edits, dismissals and comment edits only at `write`, which on Connect only a requester's own token holds. Connect cannot police what a server does with a token it handed out, and binding installations to servers was deliberately not done. Connect refuses any other `as: app` mint with `needs_requester` before asking GitHub, and the server refuses a contents write before asking (`GitHubRefusal.needsRequester`, `kGitHubNeedsRequesterMessage`): an unrequested agent push, a space stack push or PR, and opening a PR with no requester fail with that message (the gateway prints it to git). A review is the one thing that changes hands instead of failing: `connectBotOrPerson` (`github_minter.dart`, the only place this is decided) asks for the bot first and, when Connect answers `needs_requester` for an unlisted install, mints the accountable person's own one-repository token, so the review appears under their name, with no App label (GitHub puts none on a review); with nobody accountable the refusal stands. Connect's `rate_limited` is transient: never cached, never clears a grant, never asks for a sign-in. A server's or workspace's own App keeps every scope. Approving is never automated (`refuseAutomatedGitHubApproval`). Every server forge client (GitHub, GitLab, Bitbucket) is built by `forgePrClientBuilder` with a required `ForgeApprovalGuard` (`AgentPrRequesters.guardFor`) that `submitReview` runs before anything reaches the forge, so a submitted review and a published one (`approve_on_ship`) meet the same check: no person acting, anyone the agent opened that PR for (the person who asked, or, for a run nobody requested, every admin who armed its trigger or edited its template while armed), or the PR's author (matched to the actor's own forge account by durable account id when both sides carry one: GitHub/GitLab numeric id, Bitbucket `account_id`; else by login) is refused. It fails closed: a PR it cannot read, a PR without `baseRepoId` or author, or an actor whose forge account cannot be resolved is refused with a retryable "Couldn't confirm …" message. Requesters are recorded before the forge is asked (pending by forge coordinates and head branch, then by the forge's durable repository id and number: `PullRequest.baseRepoId`, GitHub's numeric id, GitLab's target project id, Bitbucket's destination repository uuid) in retention-exempt `caches` rows (`AgentPullRequestCacheKinds`) whose payload is the set of requester ids and read across every workspace, deleted ones included; a workspace that cannot be read refuses the approval. A pending row an unclear open left behind (timeout, 5xx) is promoted to its number once the open-PR poller or an approval check sees an open PR on its head branch, and dropped after seven days unmatched on a complete open-PR list (`AgentPrRequesters.reconcile`). Every PR an agent opens (`open_pull_request`, stack publish) ends with one `Opened by a Control Center agent at the request of @login` line.

- `asPerson` / `personHttp`: anything a person does (PR pages, reviews, approval, merge, publish), on their own token, read per request. Not signed in sends no credential and the caller asks the person to sign in.
- `mintScoped`: one repository linked to the workspace (`isLinkedRepo`; anything else is `access_denied`), scope `read`, `review`, `comment`, `bot` or `write` (`GitHubTokenScope`). The single exception is `forSkillSource`, a GET-only client that may mint `read` (never `viaPerson`) for a repository `isSkillSource` names: a registered skill source or the upstream of a GitHub skill in the workspace lock. `SkillSourceGitHub` tries it first and, only when a person asked and the App cannot read the repository, reads as that person (`asPerson`); without a person the refusal surfaces with its own message. `forOwner` / `httpForOwner`: an automation client that picks each request's scope through `githubScopeForRequest` (`github_request_policy.dart`: GET `read`; opening and editing issues, issue and PR-conversation comments, their reactions, labels and assignees `comment`; reviews, review comments and their reactions, and requested reviewers `bot`; opening a PR, changing its title, state, base or branch, merging, review dismissals, editing or deleting an existing comment, `contents`, `git`, `merges` and `stacks` `write`. `PATCH /issues/{n}` stays `comment`: its URL cannot tell an issue from a PR, and ticket sync edits issues with it). Any other `/repos/{o}/{r}` write (statuses, checks, actions, settings, conversation locks) has no scope and is refused, never handed `write`. `forRepo` / `httpForRepo`: an automation client for exactly one repository, where every request, GraphQL included, rides that repository's installation-lane token and any other repository is refused locally. GraphQL is parsed (`github_graphql_policy.dart`): queries are `read`; a mutation is sent only when every root field (aliases, fragments and comments resolved) is on `githubGraphQlMutationScopes`, at the highest listed scope, and an unlisted mutation, a subscription or an unreadable document is refused before any mint; `httpForRepo(viaPerson: true)` is the requester's own downscoped user token; a `401` on it drops the cached grant and re-mints once (`remintOnUnauthorized`). The owner-level client never sends a person's token: it refuses every non-repository request (GraphQL, `/user`, search) and every GraphQL mutation, whoever is acting (`refuseUnscopedGitHubWrite`; `github_clients_test.dart` pins it). A refused mint sends no credential.
- `laneFor` (`githubLaneFor` over the workspace's `ConnectRoute`): on its own apps, the workspace's App only (fail-closed when incomplete, none when absent); inheriting a server on its own apps, the server's complete App (`effectiveState`; a partial one means none); otherwise the route's Connect when its config has a GitHub lane, else none. A seal is sent only to the Connect origin that made it.
- Every mint, `read` included, is clamped by `clampGitHubScope` to the accountable human's own role on the repository (`pull` reads a private repo, `triage` a public one), so an installation token is never broader than what that person can see. Connect clamps every mint upstream (`/v1/github/scope`, which requires `as: user|app`). `as: app` is the bot: Connect reads the repository with the human's sealed user token, clamps the scope to their role, finds the installation with its App JWT (`CONNECT_GITHUB_APP_PRIVATE_KEY`; without it the GitHub lane is off) and mints an installation token for that one repository id, of `read`, `review` or `comment` for every install and `bot` only for a listed one (anything else is `needs_requester`); not installed is `not_installed`, installed without that repository `repo_not_selected`. No installation is bound to a server: the human's own access is the authorization. `as: user` reuses a live child for the same install, workspace, account, repository, permissions and parent (sealed under the caller's binding, dropped when the child is revoked) instead of minting another, since GitHub caps live user tokens. `viaPerson` (human terminal rigs, IDE commit/push/fetch) downscopes the person's user token through `/applications/{client_id}/token/scoped` even on an own App. Every scoped answer must prove it covers exactly the one repository with exactly the asked permissions and a `selected` selection (`scopedTokenMatches`, `GitHubAppTokenMinter`); a wider or unproven one is revoked and refused. Installation-token and Connect answers (`as: app` and `as: user`) must also list that one repository; GitHub's own `/token/scoped` answer has no repository list, so only that check passes `requireRepositories: false`.
- Links: a new or retargeted forge link through `repos.upsert` or `repos.addFromPath` needs a workspace admin (`catalog/repo_link_guard.dart`), then `forge/forge_link_check.dart` on every forge: an owner or name that is not a valid segment (`.`, `..`, encoded or not) is refused, the linking member must be signed in to that forge (`NeedsSignInException`) and their own credential must see the repository (GitHub `GET /repos`, GitLab `GET /projects/:id`, Bitbucket `GET /2.0/repositories/…`). Softer outcomes do not refuse: they come back as `access_warnings: [{state, message, install_url?}]` and are recorded in `RepoAccessRegistry` (App not installed on the owner, repository not selected in the installation, accountable human cannot see it or is not signed in, or no GitLab/Bitbucket automation token can read it).
- Paths: where a linked checkout may live is decided by `RepoPathGuard` (`repo_path_guard.dart`). The path is canonicalized with symlinks resolved and must exist. A path under the workspace's own directory is accepted (never that directory itself); a path that is, lies in or contains the server's data dir is refused; any other host path is accepted only when the server owner linked it (`repos.linked_by_user_id`, `Repo.linkedBy`). The same check runs when a path is linked and whenever a stored row is read: readers that reach a checkout through its path (the IDE, the space provisioner, environments, enclosed terminals) go through `GuardedRepoRepository` / `ServedWorkspaceRepository`, which leave a refused row out, so a row retargeted by a symlink is not served until the owner links it again. A forge repository's checkout must have an `origin` naming that repository (`RepoPathGuard.requireOrigin`). `repos.delete` is a workspace-admin op and forgets the forge credentials held for the repository. The other readers of a stored path are guarded the same way: both `CodeGraphTreeService` constructions, the PR worktree source (`repoPathGuard.admit`), the `list_repos` MCP tool and the `code.index` pipeline body, which reads its checkout by `repo_id` from the served repository and ignores a payload path. Readers that only use owner and name for forge calls stay on the raw repository. `repos.watchAll`, `workspace.watchReposForWorkspace` and `repos.get` list an unserved row and add `path_issue` to each repo (`null`, or `repo_path.host_path`, `repo_path.missing`, `repo_path.data_dir`, `repo_path.workspace_root`; `RepoPathGuard.refusalOf`, rendered by `reposToListingWire`): a code, not a message, and not part of the `Repo` entity. The watches re-emit when the row changes, for example after a relink; nothing polls the filesystem. `repos.addFromPath` on an unserved row relinks it for the caller with the checks of a new link and keeps its id.
- Pin: a linked repository is pinned by the forge's durable id (`Repo.forgeRepoId`: GitHub repository id, GitLab project id, Bitbucket uuid), recorded from the linker's own verified read and never taken from the client. `ForgeRepoPins` (`forge/forge_repo_pins.dart`) is the only place the pin is compared or moved. GitHub checks it in `GitHubMinter.repoFacts` (every mint, cached facts included); GitLab and Bitbucket check it in the token lookup of every per-repository client (automation and person), with the id read on that request's own token and trusted five minutes. A person's own lanes (`personHttp`, `forActor`, `personForRepo`) call `ForgeRepoPins.confirmPersonRequest` from their `requestTokenLookup`: `forgeRequestRepo` (`forge/forge_automation_request_policy.dart`) reads which linked repository a REST or GraphQL request names, and a mismatch is a local 409 that `error_mapper.dart` turns into `NetworkException(code: repo_replaced)` and the RPC mapper into `{kind: repo_replaced, forge}`. `changesForgeIdentity` (`catalog/repo_link_guard.dart`) decides when a `repos.upsert` is a link rather than a rename; a rename writes only the name. A repository renamed or transferred (same id) moves its stored owner and name in place; GitHub's 301 is followed by `GET /repositories/{id}` on the same token. A different id marks the link `repo_replaced` (`RepoAccessState.repoReplaced`) and refuses it until an admin relinks it (`repos.upsert` with `relink: true`).
- `RepoAccessRegistry` (`forge/repo_access_registry.dart`) is the one record of which linked repositories the server cannot act on, persisted per workspace (`caches` `repoAccess`/`v1`): `app_not_installed`, `repo_not_selected`, `installation_suspended`, `owner_cannot_see`, `owner_not_signed_in`, `automation_token_missing` and `transient`. Mints, link checks, automation-token lookups, the open-PR poller and `sweepLinks` (three minutes after boot, then daily: GitHub as the accountable human, GitLab and Bitbucket with each repository's automation token, after deleting tokens of unlinked repositories; each workspace is re-checked as registered and not deleted right before it is opened, `forEachLiveWorkspace`, as the open-PR poller does before each sweep) write it; a mint with no acting person refuses while a blocking record is under ten minutes old; `pr.watchRepoAccessForWorkspace` streams it as `repo_access`.
- `accountableHuman`: `actingUserId` while still a member, else the workspace owner if a member, never an unrelated server owner. There is no creator/editor fallback.
- Grants are cached per (lane, App id, workspace, human, owner, repo, scope) until 15 minutes before expiry, because GitHub caps live user tokens per user and app; the grant and repository-fact caches are size-bounded. A cached grant that writes is reused only after the repository facts are read again and still clamp to its scope (a transient read failure keeps it); otherwise it is revoked and re-minted. `mintScoped(fresh: true)` bypasses the cache for per-run tokens. `GitHubScopeRefused` is final.
- Repository reads that bound a mint (`classifyGitHubRepoRead`, and `forge_link_check.dart` for links) map `401` to `needs_sign_in`, `404` and a plain `403` to `access_denied`, a `403` rate limit (`x-ratelimit-remaining: 0`, `retry-after` or a rate-limit message) or `429` to `rate_limited` (transient: never cached, never recorded as blocking), and a SAML `403` (`x-github-sso`) to `sso_required`, recorded as `owner_not_signed_in`. The poller records only `access_denied` as `owner_cannot_see`; `not_configured`, invalid requests and outages are `transient`.
- `refuseAutomatedGitHubApproval` blocks an `APPROVE` review on every automation client, wherever it sits in the request (top-level or nested GraphQL variables); approving rides `asPerson`.
- Minted tokens are cached per (lane, App id, workspace, human, repository, scope), so a rotated App never serves its predecessor's tokens; a definite refusal (not installed, repository not selected, suspended, not configured, access denied) is cached for a minute; provider outages and rate limits are never cached. One installation listing per App is cached for 60 s, shared by the suspension check and the lookup, and re-read early only on an admin's explicit refresh; the lane a workspace resolves to and its repository links are memoized for 5 s and dropped by the forget calls. `forgetPerson` (GitHub sign-out), `forgetMember` (membership removal or role change), `forgetAll` (own App or Connect changed) and `forgetWorkspace` (a workspace's own App saved, rotated or removed, its Connect choice changed, or the workspace deleted) drop caches and revoke each cached token upstream by its kind: Connect children through Connect with the parent seal (Connect checks the seal is the same install and GitHub account the child was minted for), installation tokens with `DELETE /installation/token`, own-App user-token children with `DELETE /applications/{client_id}/token`. Cache eviction revokes the same way, and so does unlinking a repository from a workspace, which also deletes that repository's own GitLab/Bitbucket automation token (`forgetUnlinkedRepo`, called by `workspace.unlinkRepoFromWorkspace` only when that workspace owned the link); a revoke that failed or could not be confirmed logs `github.token.revoke_failed`. Disconnecting GitHub also revokes that sign-in upstream before the seal is deleted: through Connect, `/v1/github/revoke` deletes the seal's own user token (`DELETE /applications/{client_id}/token`) and the children Connect minted for the same install, workspace and GitHub account, so the person's sign-ins on other servers keep working; an own-App sign-in revokes that App's grant (`DELETE /applications/{client_id}/grant`). Removing Control Center's access entirely is done in GitHub's own settings (Applications → Authorized GitHub Apps → Revoke).
- `GitHubScopedCredentialBroker` implements `CredentialBrokerPort` on `mintScoped`: every token it hands out is for exactly one repository. `ForgeTokenScope.read` is `read` (pipeline shell steps, clones and enclosures, which get it as `GH_TOKEN`/`GITHUB_TOKEN`); `ForgeTokenScope.review` is `review` (what an agent run reads with: contents, issues, pull requests, checks, actions and statuses read, nothing that writes), minted by the [agent run gateway](#agent-run-gateway) when the run fetches or its `gh` asks, fresh per run, and revoked upstream (`DELETE /installation/token`, or the Connect child) when the run ends; an agent comments on its own PR through `comment_on_pull_request` (`AgentPullRequestCommentService`, posted as the bot bounded by the requester with the attribution prefix and inert mentions), changes its title or description through `update_pull_request` (`AgentPullRequestService.update`: an open PR only, on the token `open_pull_request` uses, the agent marker kept; a description keeps its @-mentions, opened or edited) and opens one through `open_pull_request`; its own PR is the one `AgentRunPullRequestScope` allows (a running run's linked repository the requester may read, a PR whose head repository is its base repository and whose head is a branch the run pushed at a SHA the gateway saw it push (`AgentRunView.pushedAt`) or its space branch at the checkout's current head (`spaceBranchHeadIn`)), and the gateway hook and harness runner refuse shell `gh` PR, issue and `gh api` conversation writes with directions (`kAgentShellGitHubWriteRefusal`); `write` only from the gateway and person rigs; notes name the lane and, for a refused mint, why.

#### PR visibility

PR data follows the forge, never only workspace membership. `PrRepoVisibility` (`catalog/pr_repo_visibility.dart`) decides per subscriber which linked repositories a member sees: an admin or a read grant, **and** their own forge sign-in can read the repository (`forge/person_forge_access.dart`: GitHub lists `/user/installations` and their repositories with the person's user token, falling back to `GET /repos` for public ones; GitLab and Bitbucket use the person's own token). Admins and the owner are no exception. A repository whose reach is not known yet is hidden (`checking`) until its listing lands. A listing is re-listed in the background after five minutes and serves for at most ten: one that could not be renewed by then (forge down, credential refused) reads as `checking` again, never as its old answer. Live surfaces re-evaluate at both marks on their own. Listings are single-flight per exact repo set (a repo linked while one runs gets its own), at most four server-wide. Reach is dropped on the person's credential change (`ForgeCredentials.changes`) or removal (`WorkspaceMemberRemoved`), and every live surface re-reads role and grants on `WorkspaceMemberRoleChanged`, `WorkspaceMemberAdded`, `members.setRepoGrant` and link changes; `workspace.delete` forgets the workspace.

Every workspace-wide PR surface filters through it and adds `hidden_repos: [{forge, reason, count}]` (`sign_in_required`, `no_forge_access`, `no_grant`, `checking`; counts only, never a hidden repository's name): `pr.watchOpenForWorkspace`, `pr.listOpenForWorkspace`, `pr.watchNeedsMyReviewCount` (`{count, hidden_repos}`, every forge with the caller's per-forge login in that workspace, never ending, without fast-cadence interest), the review-requested, reviewed-by and free-text searches, `pr.closedByAuthorForWorkspace` (no `login` argument; GitHub `is:merged` searches in chunks of five repositories, GitLab one call, Bitbucket per repository) and the space-branch lookups. The same rule filters review spaces (`review_space.*`, `pr.ensureSpace`), the notification feed, live notification frames and Web Push for PR-derived items (`isPrDerivedNotification`; a PR item naming no repository carries no repository data), and source control's open-PR head fallback (`publishedBranchHead`, per viewer). Per-repository ops check the same forge access after the grant, including the AI review start, review studio compute/blast-radius/cohort-impact, merge-conflict and compose-PR reads that otherwise read as the bot. Identity lookups (`githubIdentityForActor`, `github.currentUser`) take the workspace.

PR data that lives outside the PR surfaces goes through `PrDataGate` (`catalog/pr_data_gate.dart`). A review space is hidden from a member while any of its `ReviewSpaceAssociation`s names a repository they cannot see. Only workspaces that have review spaces ask the forge; others never wait on a listing. Every op and watch on a hidden space is refused (`assertSpaceOwned(ws, spaceId, userId)`), mutations included. `messaging.listSpaces`/`watchSpaces` drop hidden spaces live. A message or turn watch on a space that turns hidden ends with an error (`guardSpace`). Pipeline runs are judged by the `repo_full_name`, `repo_owner`/`repo_name`, `repo_id` and `space_id` in their trigger payload and state. Lists drop a hidden run, and `pipeline_run.getRun`, step reads and cancel/retry/kill refuse it. Agent run logs follow their space. Cross-workspace watches (`pipeline_run.watchAll`, `agent_run_log.watchRecent`) judge each row by the caller's view in its own workspace and send no frame until every workspace in it has a view. The audit log (`audit.watchLog`) keeps who, what and when for a hidden entry and drops its `target_id` and `details`. Repository lists (`repos.watchAll`, `workspace.watchReposForWorkspace`, `repos.findByPath`, `repos.get`) follow the Control Center grant only (`catalog/granted_repos.dart`: admins see every repository, members their read grants). A granted repository stays listed when the member's forge account cannot reach it, because that is where they ask for access. They re-evaluate on role and grant changes.

Code follows the forge as PR data does. Every code-bearing op (file tree and content, diffs, search, IDE data, a terminal in a space) requires, beyond the Control Center grant, that the caller's own forge sign-in can read every repository it exposes: `repoForgeReadCheck` (`catalog/repo_forge_read.dart`) is the one decision, run by the dispatcher's `requireForgeRead` gate (`RepoForgeReadGate`, single-repo and `repoAccessVia` ops) and by the catalog's `requireRepoReadGrant` / `requireAllRepoReadGrants`. Workspace admins are not exempt; the server owner is, because they own the host's disk; a repository with no forge remote is governed by the grant alone. Refusals are `needs_sign_in`, `forge_cannot_read` or `forge_unconfirmed` (the forge could not be asked, which fails closed) and are audited with source scope `forge`. `members.setRepoGrant` answers `access_warning: null | {state: not_signed_in|cannot_read|unconfirmed, message}`, so an admin learns that a grant gives nothing yet. A space's content follows the same rule through one gate: `SpaceRepoAccess` (`catalog/space_repo_access.dart`, a `SpaceReadGate`) requires membership, a read grant and forge read on every repository `spaceExposedRepos` answers (the selection; every linked repository when there is none; nothing for `no_repos`), and `PrDataGate.requireSpace` applies it, so `assertSpaceOwned`, `assertConversationOwned`, `requireRunLog`, `spaceRows` and the hidden-space filters all inherit it; `unreadable(workspace, user)` feeds the list filters with one membership lookup and one bulk selection read, on `PrRepoVisibility`'s cached reach. `context.inspect` declares the same predicate through `repoAccessVia`. The runtime constructs the one `SpaceRepoAccess` and hands it to the catalog (`spaceRepoAccess:`), to the agent MCP lane (`AgentSpaceVisibility` over a `PrDataGate` with `spaceRead`) and to `notificationDeliveryCheck` (`catalog/notification_feed_visibility.dart`), which web push and live frames share with the feed. `watchHiddenSpaces` waits on PR visibility only when review spaces exist, and `unreadable` answers at once when no space exposes a forge repository, so the first space-list frame does not block on a forge answer it does not need. Review Studio and PR-space wiring live in `runtime/server_review_studio_wiring.dart` and `runtime/server_pr_space_wiring.dart`; skill evaluation authorization in `runtime/server_skill_evaluation_wiring.dart` (`skillEvaluationAuthorizer`). IDE background fetches run on the viewer's own sign-in, never automation, and are skipped without one. A coded refusal travels as `data.kind` (`rpc_exception_mapper.dart`), so clients localize by kind and never read the message.

Agents read spaces through MCP as the person the run acts for. The harness attests the calling conversation (`McpCallScope.callerConversationKey`, forced only on an attested in-process call and stripped otherwise). `AgentSpaceVisibility.hiddenFor` hides from `get_messages` and `list_spaces` the review spaces any open run's requester cannot see in that conversation. A caller with no open run, or an unattested one, is refused every review space. A run nobody requested (schedule, webhook) is not narrowed.

`/proxy/media` fetches private forge media with the viewer's own sign-in in effect in the workspace named by `ws` (`MediaProxyConfig.forWorkspace`, the active workspace; `WorkspaceMediaProxyScope`). Membership is checked first, and the fetch is anonymous without `ws`. A credentialed fetch never enters `MediaCache`. `ServerPersonForgeAccess` records a repository as unreadable only on a 404 or an access-refusing 403, SAML SSO included (`isForgeRepoDenial`). A rate limit, 5xx, suspended installation or timeout fails the listing instead: the previous answer serves while fresh, then the repositories read `checking`, and the listing is retried after `retryAfterFailure`.

The open-PR poller sweeps up to three workspaces at once, removes a parked repository's PRs from the snapshot instead of serving stale rows, throttles `refreshNow` to one per 20 s per workspace (pausing GitHub below a 5% rate budget even then) and probes GitLab and Bitbucket cheaply before re-listing.

Pipelines carry their requester explicitly. `PipelineEnginePort.start(requestedByUserId)` records it under `kPipelineRequestedByKey` (`requested_by_user_id`) in the trigger payload; a payload that names someone is stripped, a sub-pipeline inherits its parent's, and null (schedule, webhook) leaves the workspace's accountable human. A trigger's `armedByUserIds` (every admin who armed it, plus template editors while armed: `preparePipelineTriggerWrite`, `savePipelineTemplate`) ride the same way under `kPipelineArmedByKey` (`pipelineArmedByOf`) and count as requesters for the approval guard. `pipeline.bashScript` runs in the OS sandbox and fails closed without one, with the data directory and `.env` hidden like every sandbox, `IsolatedGit.isolationEnvironment` plus a temporary `GH_CONFIG_DIR`, and a one-repository `read` token only when `repo_full_name` names a linked repo. Each placeholder value is escaped for the quoting it sits in (unquoted, `'…'`, `"…"`, command substitution), so a trigger payload is one literal word wherever the author put it. Creating or editing a template with a shell step needs a workspace admin, and so does creating or editing a trigger that points at one (`pipeline_trigger.insert`/`update`). Arming a trigger (enabled on an event, schedule or webhook) on a template with any step outside `kMemberArmableBodyKeys` also needs an admin, and so does adding such a step behind an armed trigger. The server mints webhook tokens and decides `isBuiltIn`. Only the engine writes run and step rows: it mints run ids as UUIDs, pins each run to the template graph it started with (`PipelineRun.templateSnapshot`, which resume, retry and step bodies read through `PipelineContext.definition`/`step`), and validates `pipeline.start` parent links. An event without `workspace_id` starts no trigger. Rules and enforcement: [SECURITY.md](SECURITY.md#pipeline-triggers-and-runs).

The PR conversation bridge (`pr_review/github_pr_conversation_bridge.dart`) gates each comment in order: loop guard (bots and replies carrying the attribution prefix) → author matched by numeric GitHub account id to a writing member who signed in, else ignored silently → `canPostAs` (the scope the reply will post with, bounded by that member: `comment` on the PR timeline, `bot` inside a review thread) → claim with the bot's 👀 (`201` claimed, `200` another server already did) → work. The `ai-review` label (`kGithubPrReviewLabel`) runs the same gate on the latest labeller and claims on the PR the same way. Replies post as the Control Center bot on every lane, with one exception: on a Connect install the operator has not listed, a review-thread reaction or reply goes out on the asking member's own narrowed token (`connectBotOrPerson`) and appears under their name. One that acts for a person starts `**Control Center** (for @login): `. Mentions are `@usectrl` plus the App's bot login and slug. Candidates come from one GraphQL search per accountable human, regrouped by repository owner (a lane with nothing to look for sends no filler search). `GitHubLoginDirectory` is invalidated by GitHub sign-in and disconnect (`ForgeCredentials.changes`) and by member added, removed or role changed; a comment whose author maps to nobody yet is offered again up to three sweeps before it stays seen. `PrConversationPollingService` sweeps an own App every 60 s over at most 25 PRs and a Connect lane every 120 s over at most 10; `GitHubRateBudget` skips a workspace under 15% remaining.

**Linear.** `LinearClients` separates `personAuthorization` (Bearer of the member's `linear` sign-in) from `appAuthorization` (the workspace's `linear_app` actor, `actor=app`, stored as `workspace_linear_app_<workspaceId>`; else the server's `LINEAR_API_KEY` service key, sent raw; else null). In a workspace that overrides the server's choice, person grants live in a workspace slot (`workspace_ticket_linear:<workspaceId>:<userId>`, `UserCredentialsStore.ticketKey(workspaceId:)`) instead of the global `user_ticket_linear_<userId>`. On its own apps the service key is the workspace's own (never the server's), and a grant whose `appId` is not the workspace's client id is cleared on read. Connect never holds Linear secrets: it returns a `LinearCodeGrant` and the server runs the exchange. `refreshAging()` is a daily sweep renewing grants older than 20 days (Linear refresh tokens expire after 30), skipping a deleted workspace's grants so they lapse; refreshes are single-flight because Linear rotates refresh tokens.

**Google Calendar.** Accounts are per member per workspace (`google:<workspaceId>:<userId>:<email>`), credentials `google_<accountId>` in `secrets.json`. A sealed token keeps only its seal on disk; an own-app token keeps access and refresh tokens and is dropped when its app id no longer matches the client its workspace's route uses: the workspace's own client on its own apps, else the server's. A seal from a Connect the workspace no longer uses is parked, not dropped.

**Workspace provider apps.** `WorkspaceProviderAppSettings` (`identity/workspace_provider_app_settings.dart`) holds a workspace's own Google, Linear and Klipy app in `FileSecretsStore` (`workspace_provider_app_<provider>_<workspaceId>_<field>`); clients get presence flags and `state` (`none`, `partial`, `complete`). The fields apply only while the workspace's Connect choice is `own`: then a complete app is used, an incomplete one throws `WorkspaceAppIncomplete` (sign-in `SignInMisconfigured`) rather than fall back, and a missing one leaves that provider off. `workspaceProviderApps.list|save` (`catalog/workspace_provider_app_ops.dart`) need a workspace admin; saving an empty string clears a field. A change of identity (client id, Klipy key) fires listeners wired in `runtime/server_provider_app_wiring.dart`: Google revalidates the workspace's tokens, Linear deletes and revokes the workspace's app and slot grants. Workspace deletion removes these keys, the Linear slot grants and the workspace's Google credentials through `WorkspaceGitHubAppSettings.deleteForWorkspace`.

**Embedded Connect.** `CC_SERVER_CONNECT_HOST=on` makes `buildEmbeddedConnect` (`apps/cc_server/lib/embedded_connect_host.dart`) mount the same `ConnectService` the image runs at `/connect`. Only `CONNECT_*` variables reach it, so it cannot borrow the server's own apps. `CONNECT_PUBLIC_URL` defaults to the public URL's HTTP origin plus `/connect`, must be HTTPS or loopback (checked once, by `ConnectServiceConfig`), and its path must be exactly `/connect`; `CONNECT_ALLOWED_INSTALLS` is required. It is routed after the `/oauth/*` handlers and before SAML, outside session and CORS middleware, is absent in demo mode, and a misconfigured mount fails the boot.

### Agent run gateway

Agents carry no permission flags: what a run may push, open, publish, write to a tracker or reach is action policy (`ActionClass` rules), the same for every adapter. `AgentRunGateway` (`packages/cc_infra/lib/src/dispatch/agent_run_gateway.dart`) is how that policy reaches code running inside an agent's sandbox. `cc_server_runtime.dart` constructs it over the action guard and credential broker and mounts it on the MCP surface's `/agent/` routes (`McpRequestHandler.agentRoutes`), so it rides the loopback port agents already dial for MCP.

- Dispatch resolves the repositories the run works on and opens a gateway lease for them; it mints no forge token. In a space the run's directory is a per-agent overlay, never a checkout, so the repositories come from the server's rows (`agentRunSpaceRepos`, the session's `spaceRepos` dependency: the space's worktrees joined to the workspace's linked repositories), never from git in that directory or a checkout's `origin`; outside a space they are the checkout the run starts in (`GitRepoInspector`). Their forge is also the one the run's commit identity is resolved for (none when a space mixes forges). The lease's `GIT_CONFIG_*` entries set `url.<gateway>/agent/git/github.com/.pushInsteadOf` for conventional HTTPS/SSH origins. Fetches use the gateway too, on GitHub, GitLab and Bitbucket (`AgentRunLease.fetchGitConfig`, `agent_run_fetch.dart`): for each of the run's repositories the lease rewrites its HTTPS, `git@` and `ssh://` origins to `<gateway>/agent/git/<host>/<owner>/<name>`, and the gateway forwards the fetch on a credential the run never holds: the run's `ForgeTokenScope.review` token on GitHub, the `AgentFetchCredential` lookup on GitLab and Bitbucket (`agentFetchCredential`: the requester's own sign-in, or the repository's automation token for a run nobody requested). The run's git has no credential helper. A fetch asks no one; the gateway resolves the network-egress rule for the forge's host and refuses only on a deny. A repository that is not the run's is forwarded with no credential, and only on a host in the sandbox network baseline; GitLab and Bitbucket pushes are refused with directions to `stack_publish`. A `gh` shim dispatch puts first on the run's `PATH` asks `GET /agent/forge-token?repo=…` (`AgentRunForgeTokens`, `agent_run_forge_tokens.dart`); the gateway answers only for a GitHub repository on the grant, with a `ForgeTokenScope.review` token (one repository, read only; see [GitHub clients](#github-clients)) minted once per repository per lease and revoked when the lease closes. A run that never reads GitHub mints none, which keeps a space of many repositories inside Connect's mint budgets. The repo-specific rewrite outranks a user's global `https://github.com/` to SSH rewrite, and `pushInsteadOf` still takes pushes to the gateway. Explicit credential-bearing URLs or altered Git configuration can bypass these prefixes, so shell preflight independently checks every recognized push. The gateway inspects ref updates, including compressed requests, asks `gitPush` with those refs, checks that the target is a linked GitHub repo (the worktree's own included) on which the requester holds the `RepoGrantLevel.write` grant (`agentPushRepoCheck`), then forwards on a server-held `write` token. Invalid or incomplete preambles are rejected. A policy refusal is a `report-status` `ng`, shown by git as `! [remote rejected] <ref> (Control Center policy: …)`.
- Uninspectable push preambles return HTTP `400` without approval, credential minting or upstream forwarding. Drain the remaining upload before replying; cancelling the request stream can reset the connection before the rejection reaches git.
- A policy deny during ref discovery is audited before returning `403`, just like a deny after the refs arrive. Unprompted guard denials publish `AgentActionBlocked` to the workspace-filtered live notifications and durable bell feed; answered approvals do not generate a second block notification. The “Agent needs attention” preference controls these notices. A block still notifies while its space is open because, unlike a pending approval, it has no inline approval card.
- Commit signing: a run a person asked for signs its commits with that person's commit signing key when they created one (`CommitSigningKeys`, `cc_server_core/lib/src/identity/`, behind `CommitSigningPort`); every other run turns signing off. The key never enters a sandbox. The lease's `GIT_CONFIG_*` entries set `gpg.format=ssh`, `commit.gpgsign=true` and `user.signingkey=key::<public key>`, and point `gpg.ssh.program` at a shim in the run's own directory (`AgentRunSigning.shim`) that posts the commit object to `/agent/git-sign`. The gateway signs it only when every check passes (`agent_run_signing.dart`): it is a well-formed, unsigned commit; it is the run's own by the rule a push is held to (`PushedCommitInspector.objectViolation`); it is being made now (committer date within `AgentRunSigning.clockSkew`, five minutes, of the server's clock, author date not in the future); the run asked for no more than `maxSignaturesPerRun` (1000); the person's key is still the one the run started with (`CommitSigningPort.sign` takes the expected key and refuses another); and the "Create a commit" rule allows it. An "ask" is answered by the operator's yes to the committing shell command for `shellPushApprovalWindow`, otherwise asked at the route with a 50-second deadline, because a commit built with plumbing or posted directly never passed the shell gate. Policy decisions are guard-decision records; identity, date, count and key refusals are logged. A signature therefore means "a run this person started made this commit, as them, at this time" and nothing about which repository or history it belongs to. Tags and pushes are never signed, and every other signer (`gpg.program`, `gpg.x509.program`) points at `false`. Whether a run signs is decided once, in dispatch: with no key, no gateway signer, or on Windows (the shim is a shell script) the run's identity drops its key (`AgentCommitIdentity.unsigned`) and its git gets no signer; `AgentRunGateway.open` refuses a grant whose identity and signer program disagree, so the push rule always matches what git was told. Dispatch resolves the run's Git identity before opening the lease, so the grant carries it.
- Claude Code's `--settings` installs a command PreToolUse hook on `AgentRunGateway.guardedClaudeTools` (`Bash` and Claude Code's own file-write and web tools; reading tools have no rule, because the sandbox decides what they can see). A run with no lease keeps a blocking hook on `Bash` only. The hook posts to `/agent/hooks/pre-tool-use` through the agent run client and exits 2 unless the gateway explicitly allows the action. The client is the server's own binary (`cc_server agent-run <verb>`, `package:cc_infra/agent_run_client.dart`, `dart:` imports only); the run's shims (`gh`, the commit signer, environment commands) use it too, so nothing in a run depends on `curl`. `AgentRunClientLauncher` says how to start it (a server run from source uses `packages/cc_infra/bin/agent_run_client.dart` on the same VM), and `withAgentRunClient` lets every sandbox execute it and none change it. Writes outside the run's worktree and runner state directories are classified by their target, and the request body is capped at 32 MiB so a large `Write` is still inspected. Missing leases and transport failures block, rather than silently skipping approval. Shell PR creation (`gh pr create` or its API equivalent) is refused with `kAgentShellPrCreateRefusal` even under an allow rule: agents open PRs with the `open_pull_request` MCP tool, which takes the run's grant (workspace and conversation forced from it), requires a linked repository and a head the run pushed or its space branch, opens the PR on the requester's own one-repository token (the bot when nobody requested the run) and records the requester. `ShellActionClassifier` (`cc_domain/features/guardrails/domain/services/`) is shared with the built-in harness: push, deletion, commit, PR create/publish, tracker writes, package installation and recognized network calls all meet their action rules before the shell starts. Conventional wrappers and compound commands are inspected, not arbitrary generated code. A shell approval answers the gateway's ref `ask` for the same run within `AgentRunGateway.shellPushApprovalWindow`, limited to the branches it named (see [SECURITY.md](SECURITY.md)); denies still apply. Updated hooks take effect on new runs after the server is restarted.
- Every runtime composes the space's autonomy after policy resolution: the harness gate, Claude Code's hook and pushes through `AgentRunGateway` (the grant resolves autonomy per check), ACP `session/request_permission`, and environment commands all pass it to `ActionGuardService.check`. `proposeOnly` refuses gated actions policy would allow (`kProposeOnlyReason`); `actFreely` never overrides an action-policy `prompt` or `deny`, and pinned output tools are still checked. A required approval without a connected approver denies and records the applied outcome. An asker that stops waiting (hook timeout, lease close, run cancel) withdraws its prompt through `ConfirmationRequest.withdrawn`, which resolves the pending card as a deny.
- ACP agents run only inside `SandboxPort`; with no sandbox manager the run fails closed. Agent requests are answered by the dispatch session: `fs/read_text_file` and chat-mode `fs/write_text_file` stay inside the run's roots, permission requests go through the guard, anything else is `methodNotFound`; responses complete only ids the client sent.
- Warm sandbox handles are reused only while the resolved `SandboxSpec` is unchanged; a posture change destroys the old session and launches a fresh one. Server shutdown stops every live dispatch (children killed, credentials released) and destroys sandbox sessions before the databases close; the GitHub and GitLab/Bitbucket HTTP clients are closed once the RPC listener has stopped, so no request is still riding them. Shutdown also drains the boot's unawaited database work (newsfeed sweep, workspace seeding, template reconcile) under a bounded wait before the databases close. A run's terminal state goes through one `_finish` (run-log close, `DoneEvent`, completion); a user stop records `RunStatus.error` with `Stopped by user`, and a later exit code cannot overwrite an abort's error.
- Approval prompts describe the agent's intent and the consequences of accepting or declining, rather than displaying policy codes. `ActionApprovalCopy` uses supplied target metadata and conservatively parsed literal shell targets; unspecified destinations stay explicitly unspecified. Shell source travels separately in `ConfirmationRequest.command`, never in the heading. Desktop/web and phone approval surfaces scroll the complete explanation and LTR Bash code, copy source verbatim, and keep decisions visible. Inline conversation queues expose one request at a time with a waiting count; advancing to another request resets its scroll position.
- Every Claude Code launch passes empty `attribution.commit` and `attribution.pr` values through `--settings`, preserving action hooks while disabling Claude's own commit/PR bylines above account and project settings. The shared Git attribution policy reaches the parent and native subagents (`--append-subagent-system-prompt` on supported binaries, Claude Code 2.1.205+), plus harness and ACP prompts.
- Commit identity is one rule, decided by who started the work (`AgentCommitIdentity`, resolved by `AgentCommitIdentities` in `cc_server_core/lib/src/identity/`), and the gateway rejects a run's pushes that break it (`PushedCommitInspector`). **A person started it** (a message in a space, a failed turn they retry, plan feedback, a message they queued behind a live run, a pipeline they started, a commit they make in the IDE): the commits are theirs. The person is always the session's user, taken by the op (`ctx.userId`) and never from a client argument or an owner fallback. They are author and committer under an address their forge verified for their own sign-in (their GitHub noreply `<id>+<login>@users.noreply.github.com`; on GitLab/Bitbucket the email the forge reports, `probeForgeCommitAuthor`), never a self-set profile or workspace Git email; the commits are signed with their signing key when they have one (GitHub and GitLab; never Bitbucket, where an SSH key on an account is also a login); and with attribution on they carry `Co-Authored-By: Control Center <hi@usectrl.dev>`. **Nobody did** (a schedule, a webhook): the commits are the agent's: on GitHub the bot of the workspace's App lane, `<slug>[bot]` at `<bot_user_id>+<slug>[bot]@users.noreply.github.com`; with no GitHub App, or on GitLab/Bitbucket, `Control Center <hi@usectrl.dev>`. They are never signed, and with attribution on they credit each person who armed the trigger behind the run (`accountableFor`: the run log's pipeline run, `pipelineArmedByOf`) under that person's verified address. A person who asked for a run but has no verified address there is never written as an author: the run gets the agent's identity and its notes say so. Attribution is the `agent_commit_attribution` setting: the workspace's override (`workspace_settings`), else the person's own preference, else on (`resolveAgentCommitAttribution`). Names and emails are taken as every git writes them (`AgentCommitIdentity.asGitWrites`), so they compare byte for byte with a commit. A pushed commit is refused when it names another author or committer (name or email); when its co-author credit is not exactly the run's (every line that reads like `Co-authored-by:`, in any case, anywhere, must be one of the run's and must stand where git reads trailers, the last paragraph made only of `Key: value` lines, and each of the run's lines must be there: `PushedGitObject.creditedCoAuthors`); when it declares a non-UTF-8 `encoding`, carries `Signed-off-by:`, is signed although the run has no key, or is unsigned or signed by another key although it has one (the signature is verified against the exact commit bytes, `SshSignature`). A push also publishes nothing it does not carry (`_uninspected`, `agent_run_git_objects.dart`): a ref moved onto an object the pack lacks must land on a branch or tag tip GitHub advertises for the repository (`refs/heads/`, `refs/tags/` only, never the `.have` lines of its fork network), and a parent or tag target the pack lacks must be such a tip, or a commit on the default branch or below what a pushed ref points at today (`AgentPushAncestryCheck`, answered by `githubPushAncestry` in `forge/github_push_ancestry.dart`: `GET /repos/{o}/{r}/compare/{base}...{oid}` on the token the push is forwarded with, published only on a 200 with `ahead_by == 0`; a 404 or a commit ahead is not published, a malformed owner, name or oid is refused without a request, and a transport failure, 5xx or rate limit leaves the check unanswered, which refuses the push and writes `github.push_ancestry.unanswered` to the forge audit). `stack_publish` pushes from the server through `StackLayerPusher` (`space_stack_push.dart`). It uses a scratch bare repo over the checkout's objects, the remote's own refs as the inspection base and an explicit forge URL, so the checkout's config, hooks, remotes and tracking refs are ignored. An agent run's publish is held to the runs' identities from their grants; a person's own publish only to the agent rule for commits authored as the agent (whom those credit is not compared: the publisher vouches). A commit a person makes in the IDE uses the same identity (`AgentCommitIdentities.forPerson`; their profile's git identity, unsigned, where no forge vouches for an address) and server-run git gets no signer and runs no repository hook (`IsolatedGit.isolationArgs`). Before every IDE push (`_signOutgoing`), `CommitResigner` signs the person's own unsigned commits in the outgoing range with plumbing only, never rewrites a commit another key signed or anything below it, and the push is refused if one of theirs would stay unsigned. So a run a person asks for can push what they committed by hand. A different requester changes the run's Git environment and so invalidates Claude native-session reuse. Caller and adapter environment settings cannot replace the resolved identity; a requested run whose member no longer exists, or a resolution failure, terminates the run and releases its credentials. Forge credentials remain broker-owned.
- Every local process sandbox spec (dispatch CLI transports, harness shell tools, pipeline shell steps, the native adapter's config) is built by `processSandboxSpec` / `processSandboxConfig` in `cc_infra/lib/src/sandboxing/process_sandbox.dart`, with every security input required; a structural test refuses another `SandboxSpec(` in `cc_infra/lib`. `SandboxManager.wrap` hides the data directory and `.env` for every spec (`hiddenPaths`, `hidden_roots.dart`), and `SandboxSpec.toolDirs` carries the run's shims: executable, never writable. The manager also scans the host's executable directories once at construction (`scanHostExecutables`, `sandboxing/host_executables.dart`: `PATH` entries, the binary resolver's prefixes, each symlink hop, and the install root a linked command resolves into) and carries them as `FilesystemConfig.hostExecutables` (`HostExecutableDirs`), which `MacosSandbox` turns into literal and one-segment regex write denies after every allowance and `LinuxSandbox.hostExecutableBinds` into read-only binds with writable re-binds of existing sub-directories; like hidden paths this lives in `wrap`, not in the policy resolver, because terminals, pipeline steps and hand-built configs do not all pass through the resolver. `SandboxPolicyResolver.resolve` builds `denyWrite` from the read-denied secrets as well. A dispatch resolves its network posture, Git identity/co-author credit and environment access once into an immutable `_RunContext` before any transport starts.
- `SandboxDispatchDeps.writableWorktrees` (wired from `agentWritableWorktrees` in `cc_server_core/lib/src/forge/agent_push_repo_check.dart`) answers which worktrees in a space's `repos/` a run may write. `ReadOnlyWorktrees` (`cc_infra/lib/src/dispatch/read_only_worktrees.dart`) turns the rest into read-only `SandboxBindMount`s listed after the writable `repos/` mount, `HarnessToolContext.readOnlyRoots` and `AgentRunGrant.readOnlyWorktrees`; file-changing tools call `readOnlyRefusal` before writing. The session resolves the list once at run start (`dispatch_session_repo_grants.dart`), before the gateway lease and the sandbox spec.
- `networkEgress` is resolved once at run start into `SandboxSpec.networkEnabled`: deny turns the sandbox network off, allow/ask leave it on (the harness web tools still ask per call). GitHub domains are always on the egress allowlist while the network is on. No ticketing key enters a sandbox; agents write tickets through MCP tools gated by `vendorSyncWrite`.
- Teardown closes the lease and releases its broker handles. `GitHubScopedCredentialBroker` tokens are shared per accountable human and repository (see [GitHub clients](#github-clients)), so release only forgets the handle; sign-out and member removal revoke. A refused mint leaves the environment without a token and says why in the launch notes; there is no fallback credential.
- Rigs fix the scope at open (`RigSpec.forgeTokenScope`): a human-opened terminal rig gets `write` as the member's own sign-in narrowed to the repository (`personal` mint, `viaPerson`), so its pushes are theirs; an agent-opened rig gets `read`, because a guest credential helper cannot tell a push from a fetch. The terminal's repository is the worktree's `origin` only when that names a GitHub repo linked to the workspace; otherwise the rig gets no GitHub credential.

### Disposable worktree permissions

`SandboxExecGrantService` grants execution inside server-provisioned conversation overlays and shared worktrees without a startup question or a stored allow row per conversation. Dispatch derives the managed space root from the provisioner layout and excludes roots overlapping protected source checkouts. Claude Code and the builtin harness use the same resolver; the harness resolves these server-owned roots per command, never a model-supplied `cwd`.

Stored decisions still take precedence. An explicit denied descendant withholds an implicit parent grant rather than reopening the denied subtree. Read-only mounts, original checkouts and unmanaged/fallback directories are not implicitly granted; genuine unmanaged grants keep their approval flow. Changing working directories cannot widen execution authority.


## Persistence

`cc_persistence` is pure Dart over `package:sqlite3`, without Flutter/path_provider. Only the server opens databases:

- `<dataDir>/global.db`: workspace registry, identity/preferences/devices, per-user newsfeed, fleet queue, routing and server policy/settings. The pinned global-table set is in `workspace_isolation_ratchet_test.dart`; additions require an isolation justification.
- `<dataDir>/<workspaceId>/workspace.db`: all workspace-owned data, including repos. `workspaceDatabasePath` defines the path; associated artifacts share this directory.
- `<dataDir>/<workspaceId>/code_index.db`: the workspace's code index (`CodeIndexDatabase`: `code_symbols`, `code_symbol_embeddings`, `code_edges`, `code_files`, `code_index_checkpoints`), opened through `WorkspaceDatabaseManager.codeIndexOf` on the same lease as `workspace.db`. It is derived data: written with `synchronous = OFF`, left out of snapshots and exports, and a damaged, foreign or newer file is replaced by an empty one, which the indexer fills again because a partition without a checkpoint is indexed in full.
- `WorkspaceDatabaseManager.of(workspaceId)` synchronously returns a lazy database; disk opens on first query. Hold the manager, not a resolved DAO. It throws `DeletedWorkspaceException` for a workspace the registry marks deleted instead of creating an empty file under its id. `quick_check` runs on first workspace touch, not boot; a file that fails it opens read-only ([Storage failures](#storage-failures)).
- A workspace file has one writing connection and a read pool of two (`openWorkspaceDatabase`): selects outside a transaction go to a reader, writes and everything inside `transaction()` to the writer, so a long write does not hold up message reads.
- `CrossWorkspaceQueries` is the only fan-out mechanism (`fanOut`, `fanOutKeyed`, `forEachWorkspace`, `mergeStreams`, `topN`). Its callers explain `CROSS-WORKSPACE BY DESIGN`.
- The record of who asked an agent for a pull request (`agent_pull_request_requesters`) is in `global.db`: it is keyed by forge identity and has to outlive a deleted or restored workspace.
- `workspace_routes` resolves pre-auth opaque IDs/secrets. Write the entity before its route; a route miss is not-found, never a workspace scan.
- The same checkout in two workspaces has two repo IDs. Cross-workspace repo identity is its path (`findByPath`), not its ID. Ordering/link time are `repos.position`/`linkedAt`.

### Stored files and composer uploads

- `catalog_files` lives in each workspace database. It records logical file IDs, workspace/uploader/creator identity, original name, media type, byte count, storage reference, source, lifecycle state and timestamps. Uploads and server-managed artifacts are cataloged; repository files and disposable PR image caches are not.
- Dropping, pasting or picking a local composer attachment starts its upload immediately through the encrypted resource facade's `POST /blob`. The URI-encoded `x-cc-file-name` header preserves the original name. The server returns `file_id` only after both bytes and catalog metadata are durable. Files are bounded to 24 MiB; failures remain visible with retry/remove controls, and sending waits for every upload to be ready.
- Sending, steering and provisioning queues reuse `fileId` plus the existing `blob:sha256:…` reference, never a client-local path or another upload. Repository-file mentions remain server-side references. The server validates workspace, uploader and blob identity before promoting an upload from `draft` to `attached`.
- Each upload has a separate logical ID even when identical bytes share one workspace-local blob. `files.discard` is uploader-only and rejects attached files. Removal leaves a `discarded` tombstone and reclaims bytes only when no active catalog entry or message needs them; uncataloged bytes are retained. There is no age-based draft expiry: a provisioning queue may still need an upload.
- Generated blobs, workspace logos, meeting audio and review snapshots retain their existing storage locations and are recorded as artifacts when written. Nothing backfills older files, so bytes written before the catalog stay uncataloged. Blob cache eviction (`BlobStore.evictTo`) has no caller; whatever wires it must keep uncataloged bytes, not only cataloged ones.


### Schema changes

There are no migration steps. `WorkspaceDatabase`, `GlobalDatabase` and `CodeIndexDatabase` mix in `ConvergedDatabase` (`database/schema/`). A fresh file is built from the table classes. An existing file whose `user_version` differs from the class's `currentSchemaVersion` is **converged** to the declared schema on its next open: `SchemaConverger` rebuilds every table in one transaction, copying rows by column name with their rowids. Undeclared tables, columns, indexes, triggers and views are dropped; rows that collide under a new unique key keep the newest; a reference whose parent is gone is cleared or its row removed, as the key's delete rule says; rows a new `CHECK` refuses are left behind; the version and `application_id` are stamped. Nothing is transformed, so a renamed or moved column starts empty: say what installs lose in the changelog. The `SchemaConvergeReport` is logged, and a copy of the file is written first to `pre_upgrade/v<from>.<utc>.db` beside it (two kept per database; older than 30 days pruned, the newest always kept).

A file is refused rather than guessed at when a newer build wrote it (`DatabaseNewerThanBinaryException`), when it carries another `application_id` (`ForeignDatabaseFileException`) or, for `global.db`, when it fails `quick_check` (`DatabaseDamagedException`). See [Storage failures](#storage-failures).

To change the schema:

1. Put each table in exactly one database, defaulting to `WorkspaceDatabase`. DAOs extend the matching `DatabaseAccessor` and cannot declare the other database's tables. Override `tableName` with plain snake_case. A new global table needs an isolation justification in `workspace_isolation_ratchet_test.dart`.
2. Declare everything on the table class; nothing else creates schema. Indexes, partial and expression ones included, are `@TableIndex` / `@TableIndex.sql` annotations. FTS and vector virtual tables with their triggers are the one exception: `beforeOpen` installs them idempotently.
3. Bump `currentSchemaVersion` of the database you changed and record the dump: `UPDATE_SCHEMA_DUMP=1 fvm dart test --concurrency=2 test/declared_schema_dump_test.dart` in `packages/cc_persistence`. The version differing is the only thing that makes an existing file converge. `declared_schema_dump_test.dart` fails when the declared schema changes without a bump, and the diff of `test/fixtures/schema/current_*.sql` is the change every install will make to its file.
4. Regenerate Drift output with build_runner inside `packages/cc_persistence` ([AGENTS.md](AGENTS.md#build-and-verification)).

Rules every table follows. `declared_schema_rules_test.dart` lints the mechanical ones over all three databases; the fix is in the table class, never an exception list.

- **Relations are foreign keys with a chosen delete rule.** `CASCADE` for parts of the parent, `SET NULL` for history that outlives it (runs, logs, a thread's anchor message, a ticket's parent). Deleting a subtree is an explicit service call. A column naming a row of another database file can have no key and says so in its doc comment. Every key's child columns start an index.
- **Closed sets are `CHECK (col IN (…))` built from the Dart enum** (`tables/checks/stored_values_*.dart`), so adding an enum value is a schema change. JSON columns carry `json_valid` (`isJson`, `isJsonObject`, `isJsonArray` in `tables/checks/column_checks.dart`). What a query filters on is a real column, not a `json_extract`.
- **A natural key is a unique index** and its write is one `INSERT … ON CONFLICT DO UPDATE`, never look up then insert.
- **`workspace_id`** is `NOT NULL` in a workspace file and never leads a key there (it holds one value); new workspace tables do not carry it. In `global.db` it is a real selector.
- **Hot rows stay narrow.** What lists, filters and counters read stays on the row. Payloads only a detail view or the runtime reads live in a 1:1 side table keyed by the parent id with `ON DELETE CASCADE` (`agent_run_payloads`, `pipeline_run_snapshots`, and the vectors in `memory_fact_embeddings`, `conversation_message_embeddings` and `code_symbol_embeddings`), and a transcript is one row per segment (`transcripts`, `transcript_segments`), owned by a run or by a message. List reads select the hot table alone. "Not embedded yet" means "has no side row": `BackfillEmbeddingsUseCase` fills those for facts, messages and symbols each time the embedding model reports installed, boot included.
- **Order and watermarks.** Time-ordered lists carry a tiebreaker (`(started_at, id)`); read marks store a `(created_at, rowid)` position, not a second-precision timestamp.
- **Rowids.** `conversation_messages`, `memory_facts`, `memory_fact_embeddings` and `notification_feed` are addressed by rowid (FTS `content_rowid`, read marks, vector scans). `rowid_stability_test.dart` pins that they keep an index, which is what makes `VACUUM` and snapshot copies keep rowids: never make them `WITHOUT ROWID`.
- **Money** is integer micro-dollars (`*_micros`, 1 USD = 1,000,000). Cents exist only inside display formatters and the few forms that ask for cents.
- **Soft delete** in a new table is a nullable `<verb>_at` timestamp (`archived_at`, `deleted_at`, `revoked_at`), NULL meaning live, with a partial index for live rows where a list needs one. The older spellings (`status = 'archived'`, `lifecycle_status`) stay where they are; do not add another.
- **`caches` holds no state.** Only kinds declared in `CacheKindRegistry` fit its `CHECK`, each with a retention window. Anything that must survive is a table.

`workspaceId` columns that remain support FTS and self-identification; separate files provide isolation. Vectors use sqlite_vector FLOAT32/384 dimensions with FTS-only degradation when the embedding model is unavailable, not when a required native is missing. The extension is registered process-wide and creates its own table (`_sqliteai_vector`) in every file a connection opens; convergence ignores it (`ConvergedDatabase.extensionTables`).

### Storage failures

- **A damaged workspace is read-only.** A workspace file that fails `quick_check` on open is opened `query_only`: reads work, every write is refused with `storage.read_only` (the dispatcher, MCP and webhook lanes check before running; webhooks answer `503 {"kind":"storage.read_only"}`), background writers and the retention sweep skip it, and it is left out of new snapshots. `workspace.watchAll` rows carry `storage_state: ok | read_only` and re-emit when it flips (`WorkspaceStorageAlerts.changes`). The server owner gets one durable notice in `global.db` (`server_notices`, op `server.notices`, kind `workspace_read_only`) that closes when the workspace is restored (`WorkspaceRestored`). The newest snapshot holding a verified copy of that workspace is pinned (`pinned_reason: last_good_copy`) and survives pruning until then.
- **Boot refusals.** The server exits with code 78 and one actionable line (`ServerBootRefusal`) when `global.db` is damaged, newer or foreign (`openGlobalDatabaseOrRefuse`), when the data directory cannot be made private (`0700`) or the identity file is unreadable. It never starts on a guessed or emptied global database.
- **Refusal kinds.** Storage errors reach clients as `data.kind` (`rpc_exception_mapper.dart`): `storage.busy`, `storage.full`, `storage.damaged`, `storage.read_only`, `storage.newer_schema` (with `file_version`, `server_version`), `storage.foreign_file`, `workspace.deleted`, `idempotency.in_progress`, and the `import.*` kinds below. The client words them in one place (`lib/shared/utils/failure_message.dart`). Logged storage errors never carry bound values (`describeErrorForLog`).
- **Deleted workspaces.** `WorkspaceDatabaseManager.of` throws `DeletedWorkspaceException` (declared with `WorkspaceRepository` in `cc_domain`) and fan-outs use `liveWorkspaceIds()`. Deleting a workspace stops its live runs first (`stopRunsOfWorkspace`). Work that still finishes after the file is gone, a turn's last write or a listener on the run's last event, catches that exception and ends: there is nothing left to write to. Everything else lets it surface; RPC maps it to `workspace.deleted`. `WorkspaceRouteReconciler` drops routes into workspaces that are gone at boot.
- **Idempotent writes** claim a `write_ledger` row first (`claim` / `complete` / `release`); a retry of a request still running answers `idempotency.in_progress`, and unfinished claims are dropped at boot.

### Retention

`DatabaseRetentionService` sweeps daily, one live workspace file at a time, then `global.db`. Each window is a constructor parameter: `activity_log` 90 days; `webhook_deliveries`, `cron_executions` and finished subagent run `transcripts` 30 (a turn's transcript belongs to its message and is never swept); `user_activity` 180; `write_ledger` 7; finished `index_code` pipeline runs 7 (the newest 50 kept); finished `agent_run_logs` 180, sparing any run something still points at; declared `caches` kinds by their own windows; unsaved `rss_articles` 90 days beyond each feed's newest 200; terminal fleet `jobs` and their `placement_log` 30. `server_audit` is not swept by age: it keeps its newest 20,000 rows. Every sweep filters on an indexed column. After its deletes a file hands freed pages back (`reclaimFreePages`), refreshes planner statistics and truncates its log; statistics are also refreshed hourly on files already open.

### Backup and restore

Snapshots are `backups/<ts>/{manifest.json,global.db,<workspaceId>/workspace.db}`. Each file is copied with `VACUUM INTO` on a connection of its own, `global.db` last, and `manifest.json` (format 2) is written after everything else: per file its size, SHA-256, `quick_check` result, schema version and application id, measured on the copy. A damaged or missing workspace is skipped and named in the manifest with the reason. `code_index.db` is never copied. A directory without a manifest never finished and is pruned after an hour; one whose manifest this build cannot read (snapshots taken before checksums existed) is kept and lists as not `complete` ("Unverified" in the client): its workspace files can still be restored one by one. `server.listBackups` marks pinned snapshots with `pinned_reason`.

`workspace.export/import` operate on a single workspace file; restoring one from a snapshot uses the same import. Whole-install restore is a stopped-server copy-back, not another RPC operation. An imported file is data, not authority, whoever made it (`prepareStagedWorkspace`, `database/backup/workspace_import.dart`):

1. The file is copied to `workspace.db.importing` and checked there: opened with `trusted_schema` off, `quick_check`, the manifest's checksum when it comes from a snapshot, `application_id` and version.
2. Its rows are re-keyed to the target workspace, it is converged to the declared schema and must then match it exactly (no trigger, view, column or constraint it brought survives), and its foreign keys must hold.
3. Grants it may not give itself are taken out: host approvals of environment definitions are cleared; allowing or prompting action policies, sandbox exec grants, repository grants above read, roles above member and invites to them are moved to `imported_authority_holds`. The importer keeps or gets the owner role. The server owner reviews holds in Settings → Backup & restore (`workspace.importHolds.list` / `workspace.importHolds.resolve`); accepting applies one, dismissing drops it.
4. The file it replaces is kept as a scoped backup named `<ts>-pre-restore` (the damaged bytes as they are when the live file fails its check), then the staged file is renamed into place with the workspace's connections closed, and `code_index.db` is deleted to be rebuilt.
5. `WorkspaceRestored` invalidates everything derived from the old file (membership cache, forge logins, repo access, PR visibility, the read-only notice).

A refused import replaces nothing and answers a kind: `import.missing_source`, `import.damaged`, `import.checksum_mismatch`, `import.newer_schema`, `import.foreign_file`, `import.schema_mismatch`, `import.route_conflict` (its webhooks or invites already route to another workspace). The HTTP restore route answers `400 {error, kind}`.

The install owner can remove a listed snapshot (unverified and pinned ones
included; the client asks before a workspace's last good copy goes) by
its timestamp name via `server.deleteBackup`; the server refuses paths and
symlinked directories. Built-in **Workspace backup** pipelines instead write
`backups/workspace-backups/<workspaceId>/<ts>/workspace.db` for the current
workspace only. An enabled weekly schedule runs once on recovery after missed
cron slots, then prunes only that workspace's backups older than 30 days by
default; it never prunes install snapshots or other workspaces.
`workspace.listBackups` lists them per workspace for workspace admins, separate
from `server.listBackups`; restoring one uses `workspace.import` and
`workspace.deleteBackup` (workspace owner) removes one by timestamp name. A deleted
workspace fails every workspace-scoped gate and its schedule stops, so its backups
are never pruned: `server.listOrphanedBackups` and `server.deleteOrphanedBackup`
give them to the install owner, and the delete refuses a live workspace.

RPC paths name files on the server. Remote byte transfer uses signed requests inside the authenticated encrypted resource tunnel:

| Route | Authorization and lifecycle |
| --- | --- |
| `GET /backup/workspace` | Workspace admin; stream export, delete server copy |
| `GET /backup/snapshot` | Install owner; ZIP to a temporary file rather than buffering the installation |
| `GET /backup/stored` | Workspace admin, or install owner once the workspace is deleted; stream a scheduled backup and keep it, since the stored file is the backup |
| `POST /backup/restore` | Workspace owner; stream to staging, adopt, delete staging on success or refusal |

HTTP handlers enforce their own roles behind the private resource gateway; the public versions of these routes return `426`. Downloads use `no-store` and `Accept-Ranges: none`: every request creates a fresh export. Backups are absent in demo mode and work through direct or relay sessions without a separate remote HTTP origin. Transfer progress is throttled to 100 ms with a final byte count; upload progress means bytes handed to the tunnel, while the response confirms completion. Reconnect cancels an in-flight transfer rather than replaying a restore.

## Harness and indexing

### Claude Code checklists

With a Control Center MCP config, `ClaudeCliBackend` appends explicit `todo_read`/`todo_write` instructions for multi-step work, including tool discovery, recovery after compaction and live status updates. Native `TodoWrite`, `TaskCreate`, `TaskUpdate`, `TaskGet` and `TaskList` are disabled with `--disallowedTools`: their private lists do not populate the conversation's checklist. Subagent execution tools remain available.

Without an MCP config, the launcher leaves Claude's native tool surface unchanged and adds no Control Center checklist instruction. The appended prompt and native-tool restrictions are part of the resume-policy fingerprint, so sessions created under the old policy start fresh rather than retain stale instructions.

### Native Claude sessions and accounting

Managed Claude Code accounts sign in through account-scoped `claude auth login`; creating an account opens those command instructions directly. Settings supports CLI login only, not pasted long-lived setup tokens. Account rotation and CLI credential refresh continue to use each account's own config directory. On macOS every sandboxed process finds `MacosSandbox.keychainStandIn` first on `PATH`: the profile denies the login keychain, the real `security` takes up to ~3 s to fail there, and Claude Code treats a write timeout (2 s) as transient and skips its `.credentials.json` fallback, dropping a refresh the server already rotated. The stand-in answers login-keychain password calls at once, passes everything else to `/usr/bin/security`, and is write-denied in every profile.

Subscription token renewal is owned by Claude Code, not Control Center. The network-enabled sandbox baseline allows the exact `platform.claude.com` host for OAuth exchange, refresh and revocation, alongside the Anthropic API domains. An expired access token with a usable refresh token stays eligible for a run; network-off sessions still block renewal.

`ClaudeNativeSessionStore` scopes explicit session IDs by workspace, agent, conversation, account/config directory, cwd and branch/fork policy. Resume also requires a matching standing-instruction/policy revision. Only a successful terminal result followed by normal process exit advances the delivered-context cursor; interrupted or failed turns must not suppress undelivered messages. Fresh launches receive complete context; resumed launches receive the new request and changed, authorized context entries. Ordinary idle gaps do not require keeping a CLI process alive.

`ClaudeControlSession` speaks Claude Code's stream-json control protocol: `control_request` / `control_response` frames matched by `request_id`. Three things depend on it.

- **Usage.** `ClaudeCliUsageProbe` starts the CLI, sends `get_usage` and exits. Control Center never reads a Claude OAuth token and never calls Anthropic's usage endpoint; the CLI does that with its own login (see [SECURITY.md](SECURITY.md)). Named accounts are cached for five minutes. `rate_limit_event` frames in a running turn update the same cache through `ClaudeUsageCache.observe`.
- **MCP.** On a CLI past `ClaudeCliCapabilities._controlProtocolFloor`, the Control Center server goes over stdin with `mcp_set_servers` and `--strict-mcp-config`, and the first prompt is held until the answer arrives (90 s). A failed server still lets the turn run. A CLI below the floor gets `--mcp-config <cwd>/.mcp.json` instead.
- **Stopping.** A manual stop sends `interrupt` and allows 3 s for the turn's `result`, so its spend is recorded, then signals the child. A turn that has not reported `init` is signalled straight away.

A `rate_limit_event` with a blocked status marks the account exhausted once per crossing, with the exact reset time. Extra usage keeps the account in rotation. The report outranks the wording of the failure, so an unfamiliar message still fails over. Warnings are debug events.

`superviseProcessGroup` on `SandboxSpec` runs the CLI in its own process group under a small `/bin/sh` watcher that holds a pipe to the server. When the pipe closes, including on a server crash, the watcher sends TERM and then KILL to the group, so MCP grandchildren die too. The native macOS and no-sandbox adapters honour it. Bubblewrap and Windows do not use it.

Compaction has two settings, stored per server in `claude_session_settings.json` (`ClaudeSessionSettingsStore`) and set from the Claude Code runner's detail pane. `autoCompactWindow` passes through `--settings` (100,000 to 1,000,000 tokens; unset leaves Claude Code's default). Idle compaction is off by default. When it is on, `ClaudeIdleCompactor` waits on a session above `ClaudeSessionSettings.minIdleCompactTokens` until two minutes before its prompt cache expires, then runs `/compact` through the ordinary dispatch path: the compaction only hits the cache with the same tools and system prompt, and it is real spend the run log has to show. The cache lifetime comes from the turn's `usage.cache_creation` tier. A compaction resumes the session or does nothing, never fails over, never parks for sign-in, reports failures as debug events and leaves the delivered-context cursor alone, because it delivered nothing. Timers live in memory, so a restart only loses the saving.

Manual stops record `Stopped by user` (`kRunStoppedByUserSummary`) before signalling the child. `DispatchSession.terminate()` owns terminal completion and the run-log stop reason; the Claude runner checks cancellation before classifying its exit or retrying another account. Late sandbox output cannot replace that reason or leak raw stream-json into the transcript. An unsolicited signal exit (including `-15`) remains a process failure.

Pass configured effort through the actual launch builder, constrained by the selected model and detected CLI capabilities. Preserve strict MCP configuration and action-policy hooks; do not use `--bare` to bypass them. Parse `system/init` for the observed session, model, CLI version, tools and MCP status. Discovery caching remains opt-in and requires a stable authorized catalog/configuration; it does not replace Claude's native tool discovery.

`ClaudeSubagentRuns` closes foreground children on their spawn-call results and background children on `task_updated` / `task_notification`. An `async_launched` result only acknowledges scheduling; it must not finish the child. Task/run IDs keep resumed-task notifications attached to the correct spawn, terminal runs cannot reopen on late transcript messages, and parent teardown drains pending child completion writes.

The space's Agents sidebar keeps each agent's current main run and only active subagent rows. Completed, failed and stopped children disappear immediately; still-active descendants remain under the nearest visible ancestor. Filtering applies only to the display tree, not the raw run-log stream or recorded transcripts, so activity tabs and transcript links retain completed history.

Claude's main-loop `usage` is per-turn; `total_cost_usd` and per-model whole-tree counters are cumulative. Delta those counters against the correct restorable baseline, without attributing an earlier dispatch's spend to its successor. Missing model counters retain observed main-loop usage and reconcile it once when full counters return. Counter resets, account switches and forks establish new baselines without erasing this dispatch's totals. Subscription figures are API-equivalent consumption, not invoices.

Runner settings report Claude credential expiry independently of `loggedIn`: the CLI can still report a present credential after its access token expires. Each expired account shows a **Sign-in expired** warning badge. Any expired managed account also gives the installed Claude Code runner a warning dot and status tag, including when that account is not the default. Checking/missing CLI states retain precedence. These warnings do not disable dispatch or change Claude's next-run refresh behavior; refreshed account data clears them once the credential is current.


### Repo skills

`RepoSkillCatalog` is the shared scan-gated discovery for projection and `skills.repoSkills`. `ActiveRepoTracker` observes paths at `DispatchSession.addEvent`: a write under `repos/<name>/` switches the active repo; reads only seed an unset repo. Only that repo's skills are prompt-resident.

### Skill evaluation campaigns

`SkillEvaluationService` owns revision-specific campaigns under `evals.*`; `DaoEvalsRepository` persists campaigns, attempts and opt-in policies in the owning workspace database. The server captures scan-gated, content-addressed skill packages and pins the corpus, adapter, provider/native model identifier, protocol, tool schemas and ambient inventory. Native Claude campaigns also pin the managed account and observed CLI version. Clients only select settings, observe snapshots and request actions.

`ControlledSkillEvaluation` reuses the paired evaluation engine with fresh fixtures, context and home directories. Supported executors are the built-in harness with enclosed file/process tools and native Claude Code with built-in tools disabled and an authenticated MCP bridge into that same enclosure. Executor choice is explicit; neither path falls back to the other or to fleet jobs. Claude Code and Codex OAuth use an API-equivalent usage stopping threshold that may be exceeded by one in-flight call; API-key providers retain conservative reservations. Unknown usage stops further calls. Absent, previous-revision, forced-load diagnostic and pinned-composition comparisons remain distinct. The local corpora are authored pilot cases, not imported public benchmark scores.

Campaign progress and bounded attempt evidence survive reconnects. Cancellation stops future attempts and active guest processes; restart marks unfinished campaigns interrupted rather than inventing results or known spend. `SkillUpdated` and periodic, authorized repository revision reconciliation mark historical evidence stale. Paid reruns require an explicitly enabled, revision-bound policy; changing or disabling that policy invalidates older queued admissions.

Reports retain every attempted outcome in the primary denominator, cluster repeated trials by task, and withhold recommendations when coverage, identity or cost is insufficient. Direct body/reference/script observations are not proof that a model followed the skill. Synthetic safety artifacts are separate from observed policy denials and are not evidence of real exfiltration.

Skills settings and Observability → Quality share typed campaign clients. This service is separate from the generic suite executor contract; adding skill campaigns does not supply an executor for arbitrary existing evaluation suites. See the [evaluation protocol](https://usectrl.dev/manual/concepts/evals-and-quality/) and [SECURITY.md](SECURITY.md#controlled-skill-evaluation) for containment limits.

### Deferred tool loading

- Keep external MCP `tools/list` complete. Only in-process harness schemas are deferred; tools remain callable from turn one, activating and executing in the same step.
- `McpToolRegistry`'s dynamic layer is personal: only home-config discovery writes it. Every run-facing read (`lookup`, `resolve`, `listDefinitions`, `toolNames`) takes `includePersonal`, and without it a personal tool is absent in every sense and never shadows a shared tool of the same name; `allToolDefinitions()` and `toolsetRevision` cover shared tools only. `DispatchSession._personalMcpAllowed` is the single place that sets it, through `buildHarnessToolRegistry(includePersonalMcp:)`, for the top-level harness run and its subagents; `McpToolDispatcher` always passes false.
- `HarnessToolSearchTool` uses BM25. Compatible Anthropic requests send the stable admitted catalog with `defer_loading` and search results with replayable `tool_reference` blocks. Other providers retain append-only schema activation after resident tools. A fixed resident-tool breakpoint alone does **not** preserve downstream system/history caches when an ordinary tool catalog changes.
- Apply deferral after `ToolSurfaceSpec` filtering. Activation cannot add disallowed tools or bypass approval/action guards.
- Dispatch and `ContextInspectionService` share `materializeHarnessToolSurface`. Residency comes from `ModeToolPolicy` through `ModeCapabilityProfile.toToolResidencySpec()`; reserve it for tools used in most runs.
- `test/tooling/resident_tool_names_test.dart` checks real names and the under-40 budget. `--tool-deferral=off` / `CC_SERVER_TOOL_DEFERRAL` makes every admitted tool resident.

### Prompt caching

Keep sent prefixes byte-identical where possible. `pruneToolResults` batches rewrites at `CompactionConfig.pruneThresholdTokens` (default 2000); compaction forces pruning because it already rewrites history. Opt-in stale-observation masking also accounts for provider/cache prices, rewritten-prefix size and expected remaining calls. It protects active edit targets, unresolved diagnostics and non-recoverable evidence. Calibrate prompt estimates against observed provider usage rather than treating the character heuristic as an exact tokenizer.

Anthropic uses four cache breakpoints: last resident tool and last system block with a one-hour TTL; previous and current request tails with short TTLs. The rolling pair (`cacheAnchorIndex`) survives wide parallel tool turns. `_subagentPilots` releases same-shape siblings on the first child's first event with a bounded wait, allowing its cache write to become readable. Subagent resident sets are profile-independent; model/effort differences fragment the prefix. `McpToolBridge` caches deterministic stripped schemas with stable key order.

Measure `cacheRead / (input + cacheRead + cacheWrite)` in `observability_metrics.dart`; cache writes belong in the denominator.

### Context, tool execution and measurement

Context meters, flyouts and explorer tabs carry the selected conversation ID explicitly, never resolving the space's standing conversation as a substitute. Token subscriptions and Claude Code history inspection use that ID; `context.inspect` requires workspace, space, conversation and agent IDs and validates conversation ownership before reading context. Explorer tab identity and persisted arguments include the conversation, so sibling conversations cannot share a breakdown. The meter prefers that conversation's latest provider-reported reading and otherwise shows an estimate.

Compaction input retains bounded, attributed evidence: original requirements, system steering, tool arguments/results, exact active edit anchors, verification outcomes and references to recoverable observations. Tool-output storage is workspace-authorized; ranged `read_output` retrieves bounded slices without injecting the full original into every request. Format search/file/build observations at their tool boundary, never by globally rewriting machine-consumed shell stdout.

Independent parallel-safe regions use a bounded rolling scheduler: a completed call releases its slot immediately, UI completion events stream as tools finish, and model-facing results retain deterministic order. Mutations, approvals, dependencies and relevant hooks remain barriers. Fully parsed, authorized read-only execution may overlap generation only under the explicit experiment; cancellation and retry rules prevent duplicate or late work.

Host-process tools take a `ToolProcessLauncher` (`cc_infra/lib/src/sandboxing/tool_process_launcher.dart`) from the dispatch session: `_toolProcesses` with the run's spec and `_lspProcesses` with a per-run `lsp-*` session and no loopback ports; `buildHarnessToolRegistry` registers `eval`, `debug`, `lsp` and `lsp_rename` only when a launcher is wired. `LspSupervisor` caches detection by (confined, root), clamps `findProjectRoot` to the run's working directory and uses the built-in server table only. Diagnostics-on-write never starts an unconfined server. `HostExecutionGate.admit` runs in `DispatchSession.run` right after the run log opens; the posture (`HostExecutionPosture`, `cc_domain`) is resolved at boot and the owner fact (`OwnerAccountable`) is supplied by `cc_server_core/lib/src/runtime/host_execution.dart`, the only place it is computed. Tool launchers are memoized per run session and mode; `_releaseToolProcesses` stops the run's language servers and releases its sessions (`harness-*`, `lsp-*`, `hook-*`) on every path through `_finish`. `OneShotConfinement` (`dispatch/one_shot_confinement.dart`, built from the dispatch deps) is the one decision for one-shot and Review Studio host processes. Shell hooks come from `agentHookFolder` (`dispatch/agent_hook_folder.dart`); `HarnessRunConfig.load(bases, hookBase:)` reads data settings from `.agents/harness.json` and hooks only from that folder, and `ShellAgentLoopHooks` spawns through the run's hook launcher. Run-log row writes live in `dispatch_session_run_log.dart`; `_failRun(message, code:)` sets the `ErrorEvent` code and the run log's `errorCode`.

Text compaction is the default. Snapshot/image compaction is opt-in, requires vision, checks page/source/image/context limits including reserved output, and retains source text for repeated folds and later text fallback. Source containing non-ASCII glyphs, tabs or control codes is refused before rendering because the fixed font would normalize or lose it; the host takes the text path instead. Local rendering/fit checks do not establish model OCR fidelity or end-to-end savings.

### Agent loop contract

- Every exit of `AgentLoopRunner.run` goes through one `finish(reason)`: it saves the transcript (only at a clean boundary, never after an unanswered `tool_use`), emits one `LoopError` for a failure, then exactly one `LoopDone`. A host maps `LoopError`/`LoopDone(error)` to a non-zero exit; a turn timeout is a failure (`turn_timeout`), not a notice.
- Every history rewrite (fold, rewind) runs `onHistoryRewritten`: checkpoints are remapped or dropped, the cache anchor and native tool catalog reset, and a fold force-prunes tool results. A rewind to an unknown checkpoint label fails the call and changes nothing.
- `LoopCompaction.summarized` means a model wrote the summary. A structural digest still folds (`messagesFolded > 0`) and counts as a compaction, but never reports `summarized`.
- Provider failures carry a typed `LlmError.kind` (`LlmErrorKind.classify` is the only place phrasing is read; providers pass the HTTP status). Overflow recovery, retries and `FallbackProvider` rotation read the kind, so a TPM rate limit is never treated as a context overflow. Overflow recovery is bounded per turn; truncation continuation per consecutive streak.
- An attempt abandoned after it streamed (retry, stream-rule restart, overflow recovery) emits `LoopTurnDiscarded`; hosts emit `TextRetractedEvent` and `TranscriptFolder` trims exactly that text/thinking from the tail.
- Deferred-tool support is `LlmProviderPort.supportsDeferredTools` (default false). Leaf providers `extend` the port; decorators `implement` it so the compiler forces them to forward.
- Subagents inherit the parent's tool hooks (`NestedRunHooks`: pre/post-tool forward, session start does not re-fire), a fresh advisor copy and a non-consuming steering view (`SteeringQueue.nestedView`); follow-ups and the parent's completion contract stay with the parent. `harness_run_factory.dart` owns the compactor stack and the loop-event → transcript-event mapping shared by the session, subagent and evaluation hosts.
- `ShellAgentLoopHooks` drains hook stdio; the pre-tool hook fails closed (non-zero exit, spawn failure or timeout denies), session-start and post-tool hooks are best-effort.

`HarnessRunAccounting` observes physical provider attempts, including main, compaction, advisor, side-request, subagent and failed/retried work. Attribute child usage to the child's own row and roll its cost into ancestor budgets once. Flush call records and atomic own/child cost updates before terminal completion. Store micro-USD; round only for presentation. Missing usage/pricing is unknown spend, not zero-cost work. Reasoning tokens are a subset of output unless a provider explicitly reports disjoint axes.

Latency stages distinguish dispatch/context readiness, runtime/MCP readiness, physical request send, first HTTP response-body byte, first model event, useful text/action, auxiliary work and verified completion. Provider intervals require matching request/attempt identity and provider/transport provenance. CLI stdout and `system/init` are startup observations, not HTTP TTFB.

`packages/cc_infra/bin/cc_eval.dart` runs pinned paired campaigns, independent behavioral verification, artifact replay and reports. The canonical corpus distinguishes synthetic smoke tasks from pinned real Control Center source tasks. Plans cover masking, snapshots, effort/routing, native resume, MCP discovery and read-only overlap; unsupported/no-op interventions are refused before spend. Repeated trials of one task do not substitute for independent task pairs. Keep the quality default until eligible, priced evidence satisfies the non-inferiority gate. Generic local campaigns execute trusted developer fixtures; they are not a security boundary for untrusted skill packages.


### Code graph

- The graph lives in each workspace's `code_index.db` (see Persistence); deleting a repository or a worktree deletes its partitions there (`CodeGraphDao.deleteByRepo`/`deleteByCheckout`).
- Before walking or reading file state, `RepoStateProbe` fingerprints HEAD, `git status --porcelain -z -uall`, and dirty-path mtime/size; `codeIndexerFingerprint` covers extractor version, queries and grammar libraries. Matching `code_index_checkpoints` returns `CodeIndexResult.unchanged()`. Worktrees also compare base `generation`. A null probe never skips; watcher events force indexing.
- Enumeration/hashing (`walkAndHash`), tree-sitter (`ExtractionWorker`) and embedding (`TextEmbedderWorker`, owning its FFI session) run off the main isolate. Use one long-lived extraction isolate per run; kill/replace a wedged parser.
- Embed batches outside transactions, then write 32 files per transaction. Prune with chunked `IN` lists in one transaction. `resolvePendingReferences` probes indexed COUNT and projects names, not full embedding blobs.
- Start `codeGraphWatch` after the ready banner; defer the first sweep with `--code-index-defer`. Desktop kills a server that misses its 20-second ready deadline. `--code-index off` disables indexing; `/healthz` exposes watching/indexing/pending state.
- Native `cc_watcher` is required: kernel-recursive on macOS/Windows; ignore-aware inotify setup on its own Linux thread. No scanning fallback or arm stagger. An unwatchable checkout is logged/retried by reconciliation, not fatal to the service. Share `SourceFileWalker.watchIgnoredDirs` with `affectsIndex`. See [watcher](packages/cc_natives/native/watcher/README.md).

## Enclosures

Rig domain is `cc_domain/lib/features/rigs`, adapters `cc_infra/lib/src/rigs`, viewers `lib/features/rigs`. Desktop uses QEMU/HVF or KVM with qcow2 images; exec/browser use smolvm/libkrun with pinned OCI images; Android and iOS are host-managed exceptions, not enclosed networking. `RigSurface.window` is host-managed too and contains nothing: `RigService.openHostWindowRig` opens it against running processes with no boot step, closing it leaves the app running, and the reaper and memory budget skip it. `RigSurface.environment` is a smolvm machine for compose and task components: dockerd as the workload, virtio-net because TSI cannot carry bridged container traffic, the worktree on a read-only `-v` mount under a guest overlay, no broker secret, and egress derived from the stack's images. It has no driver and its own surface so it is never taken for a `computer_use` desktop or a terminal machine. Backend selection follows `RigSpec`, never availability or a silent host-shell downgrade. Enforcement rules are in [SECURITY.md](SECURITY.md#execution-and-untrusted-input).

### Browser engines

`RigBrowserEngine` selects Chromium/CDP (`CdpClient`), Firefox/BiDi (`BidiClient`) or WebKit/W3C (`WebDriverClient`). `BrowserRigDriver` depends only on `BrowserEngineClient`; shared page scripts/action vocabulary live in `browser_engine_client.dart`. A rig keeps one engine for life; conversation reuse, in-flight open, tab dedup and provider keys all include the engine.

- Create Firefox's `--profile` directory before launch. Send the guest-side authority in its WebSocket Host header; the forwarded host port fails validation.
- Classic WebDriver POSTs require a body; GETs must not carry one (`dart:io` fixes GET content-length to zero).
- Only Chromium screencasts; others poll at at most 6 fps. WebKit PNG stills need host ffmpeg for its live lane. Firefox/WebKit cannot bypass cache on reload, expose platform accessibility trees or perform real file drops; label DOM-derived accessibility accurately.
- Use distribution Chromium, not upstream `headless-shell`, which omits audio backends. Browser workloads start system PulseAudio with a `ccout` null sink, a pulse-owned socket directory and successful `pactl` sink observation. Never mask startup failure with `|| true`. ffmpeg encodes `ccout.monitor`; packs are keyed by image, engine and audio revision.

### Input, display and worktrees

QEMU input uses QMP (`input-send-event`/`send-key`) and `virtio-tablet`; the unprivileged guest agent only captures/mode-sets and scales frames. The human display lane relays bytes at panel resolution with adaptive fps/quality; the server never decodes frames on the RPC path. The agent lane is at most 1280×800 with one image per result (`capToolImages`); compaction discards old images but keeps text.

The host worktree remains authoritative. Tar streams sync in; git bundles are fetched into `refs/rigs/<rigId>/*`, never pushed or checked out. Uncommitted changes return as a reviewable diff. `WorktreeTransport` uses SSH for QEMU and `smolvm machine exec` for microVMs.

Clipboard policy is per-user and per-direction: paste into rig defaults on, copy out defaults off and prompts before reading. Temporary grants last ten minutes for one rig/direction; persistent grants are synced user preferences. `ensureRigClipboardPermission` gates `RigInputSurface` before `/rig/clipboard`. Denial still forwards guest-local Ctrl+C/X/V on Windows/Linux so copy, paste and terminal interrupts work.

`RigService.act` rejects agent mutations while a human has control but allows observations. Log inputs with `Principal` and a per-rig monotonic `seq` in the insert transaction. Hard TTL, idle→park→close and resident-MB LRU bound resource use; parked VMs retain RAM. `RigParked` says whether idleness or an environment stop parked it. A close writes `closing`, then `closed` with its reason (`memoryPressure` for LRU eviction, `conversationEnded` when `SpaceDeleted` reaches `RigService`, `workspaceGone` from `workspace.delete`). Environment rigs record their id the moment they open, so a stack that never comes up is still closed and its worktree quarantine lifted. Shutdown tears down all owned machines.

A rig opened in a space is authorized as that space. `RigAccess` (`catalog/rig_access.dart`) is the one decision: viewing takes the space read gate (`SpaceRepoAccess`), driving takes a write grant plus the caller's forge read on every repository the space exposes, and a rig bound to no space is open to every workspace member. The rig RPC ops (`catalog/rig_ops.dart`: `buildRigOps`, `buildRigPortOps`) call it, and the HTTP lanes ask the same object through `RigLaneAccess.mayView`/`mayDrive`, which `runtime/server_rig_wiring.dart` hands them. A grant that is too low is refused with `RepoGrantRequiredException`, which travels as `data.kind: repo_grant_required` with the `level` (`read`, `review` or `write`) the caller lacks. Every rig row a client receives (`rig.list`, each `rig.watchSessions` frame, and the rig returned by `rig.open`, `restartUnrestricted`, `takeControl` and `releaseControl`) carries the per-caller `can_drive` (`RigAccess.mayDrive`) and `holder_only` flags, built only by `RigAccess.rowsFor`, and the watch re-sends on `PrRepoVisibility.changes` because `PrDataGate.spaceRows` re-emits only when the hidden-space set changes. Rules are in [SECURITY.md](SECURITY.md#sandboxes-and-rigs).

### Boot and recovery

- Desktop qcow2 downloads are user-initiated, checksum-pinned and stored in `<dataDir>/rigs/images`. `scripts/rigs/build_image.sh` bakes the guest agent; Settings imports images. `kSmolvmExecImage`/`kSmolvmDebianBrowserImage` pin OCI digests; browser engines warm gated apt installs into per-engine packs.
- Android SDK/emulator/images come from Google (`setup_android.sh` reuses Android Studio); distinguish no SDK, no emulator, no AVD and no running device. iOS requires macOS, Xcode/runtime and checksum-verified WebDriverAgent installed through owner-only `rig.installBackendSetup`. Register uniquely named owned devices atomically; teardown/orphan recovery stop WDA and delete only those devices. iOS streams fixed-size MJPEG and supports typed point/key/app actions, not file drop/audio/mic/enclosed egress. Mobile developer commands are argv-shaped device commands, never a host shell.
- `buildRigSocketPath` selects the first fitting XDG_RUNTIME_DIR/TMPDIR/`/tmp` root; Unix socket limits are 104 bytes on macOS/BSD, 108 on Linux. Keep full rig IDs, create 0700 directories, reject symlinked `ccrig` namespaces. Durable files remain under the data directory; teardown/recovery clear both trees.
- Stock Ubuntu QEMU cloud images need a `cidata` cloud-init seed creating `cc` and its SSH key, not the built-image `CCRIG` format. Readiness is sshd's banner, not a bare forwarded TCP connection or a nonexistent guest agent.
- Guest seed permissions are `0640 root:cc`; both the `User=cc` guest service and git credential helper need read access.
- A successful cloud-init exit does not prove customization. The builder requires the guest completion marker and deletes failed output. Discover firmware via `qemu -L help`, not paths derived from a symlinked binary. `verify_image.sh` must boot the output with a real seed and observe `/health` before publication; its diagnostic seed dumps the guest journal.
- Rig viewers belong to space/PR tabs, not global navigation; tools share the conversation's machine. Settings → Server → Enclosures owns setup/capabilities/sessions. Never auto-start rigs on layout restore. Restored microVM terminal tabs carry `EditorLayoutCodec.deferStartArg` and wait for “Open the shell”; host-shell terminals may attach on mount.

## Environments

An environment is the running stack of one space: an ordered list of typed components from an admin-authored definition. Domain is `cc_domain/lib/features/environments`, adapters `cc_infra/lib/src/environments`, the RPC pack `cc_server_core/lib/src/catalog/environment_ops.dart`, the client `lib/features/environments`. Security rules are in [SECURITY.md](SECURITY.md#host-environments).

- **Components.** `compose` (native driver), `cli` (a tool that owns its lifecycle; CC calls verbs and reads JSON through `statusMap` or the native contract), `process` (PTY-supervised), `task` (one-shot with triggers), `app` (a desktop window).
- **Worktree tasks.** `provision` and `archive` tasks follow the worktree, not the environment: they run in any space, see no environment values, and belong to one definition per repo.
- **Host approval.** Definitions carry `host_approved_by`, set by `saveDefinition`/`approveSource` and never taken from the wire. `EnvironmentService` enforces it at `_ensureLocked`, `_readmit`, `check`, `testDefinition`, `_runWorktreeTask` and `_onHeadChanged`, reading the owner through its `serverOwner` dependency. A refusal is `EnvironmentHostUnapprovedException`, both an `AuthException` and an `EnvironmentDriverException`, so an RPC caller gets `data.kind: environment.host_unapproved` and a held environment gets the same code in `lastError`. Definition payloads expose `runs_on_host` and `host_approved`.
- **Starts that need a person.** Every command of a definition shares one exit-code contract, read once by `EnvironmentBlocker`: 3 needs an answer at a terminal, 4 a sign-in, 5 a dependency. A blocker ends the start `blocked` (row and run), never `failed`; `EnvironmentStatus.needsAttention` covers both, and the next start picks up where that one stopped. A `cli` verb listed in the component's `interactive` that exits 3 can instead carry on inside the same start. When the caller passed `attended` (a person's client with an `EnvironmentHost` to show a terminal; `_mayUseTerminal` also requires a user principal, host placement and no fork), `_TerminalOps._runOnTerminal` runs that verb's argv again on an owned PTY with the condition value `interactive` and `CC_ENV_INTERACTIVE=1`. The row stays `creating`/`starting`, the component reads `interactive` with the `sessionId`, and exit 0 returns to the driver's wait for ready. The client follows `environment.watch` for the length of its own call (`AttendedStart.follow`) and opens each session it sees; everyone else gets a notice with **Open terminal**. The terminal ends with the verb, at `terminalTimeout` (20 minutes; `blocked` again), or when a stop, a teardown or a space release cancels it. Agents, MCP tools, PR sync and boot recovery never pass `attended`.
- **Run output.** `EnvironmentRunLog` writes a run's output to its record while it grows (at most every 500 ms), and `environment.watchRuns` streams `EnvironmentPort.watchRuns`, which re-reads on run changes as well as row changes. A tool's `step` lines are kept on its component (`EnvironmentComponentState.steps`, replaced by `id`, a string or a number; without ids each new step ends the one before, and `EnvironmentCommandExit` ends whatever was still running the way the command went). They are not rows: the client lists `SpaceEnvironment.startComponents` (no apps, no task in phase `idle`, which is a task this start has nothing for) and shows `currentStep` under its component. A `log` line is plain output, a `note` with `level: warn` joins the row's warnings, and a structured error keeps the last output lines in `EnvironmentError.output`.
- **Ports.** `EnvironmentLeaseAllocator` leases blocks from one host-wide range (`environment_slot_leases`, global.db, because ports are host-wide; IDs only). A lease is taken when a run starts in an eligible space, since `loopbackPorts` is fixed at run start. Assignments never move while the lease is held; a start after the lease was released (an archived space) assigns again from the new one. A space's lease goes only when none of its environment rows remain.
- **Compose.** Plan with `docker compose config`, preflight, write the resolved model and an override (`container_name: !reset null`, `ports: !override`, labels, injected healthchecks) to the state directory, `up -d` from those two files, never `--wait`: it exits 1 on a successful one-shot. Only planning reads the worktree's compose file, and every call but `up` goes by project name (`ComposeProject`, run from the state directory), so stop, logs, exec and teardown need no cached plan. Readiness comes from `docker events` plus `ps`. One compose component per environment, enforced by validation; `after` may only name an earlier component that starts with the stack. Component states are `EnvironmentComponentPhase` wire strings; status moves go through `EnvironmentService._update`, which refuses what `EnvironmentStatus.canBecome` forbids.
- **URLs.** CC-routed endpoints are `http://<endpoint>--<name>--<project>.localhost:<router port>`, one DNS label on purpose: `RigDomainRouter`'s rule and the `*.localhost` leaf only cover one. A tool that owns its domains uses `routing.mode: tool`: routes come from its status, and the router terminates with CC's leaf and re-encrypts to the tool's proxy. Chromium's SPKI pin accepts names the leaf doesn't list, so nothing is re-issued.
- **Teardown.** Every worktree release, PR editor worktrees included, passes through `WorktreeReleaser.release`: environment teardown (`WorktreeTaskPort.beforeRelease`) when its `WorktreeReleaseMode` is `teardownEnvironment`, then `archive` tasks, the copy, stack rows and the registry row. A space going away tears down; a finished ticket, a deselected repo or a rolled-back provision releases rows only, and the environment reconciles against what is left. Do not add a release path around it. A forced teardown whose step fails keeps the row as `failed` with code `teardown-incomplete` (its rig id, lease and state directory with it) and maintenance retries every five minutes.
- **State directory.** Besides the compose files, an environment's state directory holds `bound_roles.json` (which worktree each role ran on, read by repo reconciliation), `fork_approval.json` (who approved running a fork PR there) and `terminal.log` (the output of a verb that ran on a terminal). They are owned by the row: created at start, deleted with it, kept when a teardown is incomplete.
- **Placement.** `host`, or `rig` for definitions of only compose and tasks. Rig placement runs the compose file unmodified in a microVM with `--net-backend virtio-net`; TSI can't carry bridged container traffic. Worktrees are shared read-only with a guest overlay, and `RigWorktreeGuard` hardens every host git call on them.
- **Desktop apps.** CC never talks to an app. `HostWindowRigDriver` works at OS window level, keyed on the process tree, so no framework needs a hook. Windows can't be hidden off-display on macOS: capture fails.

## Client conventions

### Routes and onboarding

`go_router` uses `ShellRoute(ControlCenterLayout)`. In-shell routes start `/workspaces/:workspaceId/`; that URL drives `activeWorkspaceIdProvider` and `context.currentWorkspaceId`, and `workspaceUrlSyncProvider` is its only writer: deep links and pickers navigate, they never set the active id themselves. The scoped remembered id only picks the landing workspace (`landingWorkspaceIdFor`); when the first workspace list lacks it, the hint is forgotten and a route on it moves to the landing workspace. Builders take workspace ID first. `/splash`, `/onboarding` and `/workspaces` are full-screen pre-context routes. See `lib/router/{routes,app_router,guards}.dart` and `features/auth/providers/onboarding_providers.dart` for the actual route inventory.

Setup requires a forge connected for the signed-in user and a workspace. A missing credential gates nothing once that user's `users.onboarding_finished_at` says setup finished: the shell's `ForgeSignInBanner` warns in the workspace and links to its sign-in (a workspace on its own GitHub App can lack a sign-in others have). Without that flag, a missing credential means onboarding. Never infer this from workspace existence or device preferences: invited users and shared devices invalidate that inference. Hold splash while the value is unknown: `onboardingGateProvider` is pure, falling back only to the session-scoped onboarding-complete hint while the live gate resolves, and `onboardingGateEffectsProvider` (watched by the app root) does the marking and caching. `users.markOnboardingFinished` is self-targeting, idempotent and monotonic; mark on completion and when observing a complete setup. Snapshot the step list once: invited members skip workspace creation but still do personal setup. The server owner's list starts with the `signIn` step (the Connect choice, `OnboardingConnectStep`), before the forge `connect` step.

Sign-in and onboarding expose a corner settings button, not the app's Settings or a manual update button. It opens `PreAppSettingsPage`, which offers only language and theme: anything else belongs to a signed-in server. Pre-server surfaces write the same preference keys through `ConnectAppearance` because `localeProvider` and `themeModeProvider` report to analytics, which needs a server; onboarding feeds the page from those providers. `isAuthenticationRoute` suppresses the Settings shortcut, command palette and native Preferences action on `/splash` and `/onboarding`; the onboarding guard still rejects direct settings links while admission is incomplete. Its language field reuses the same searchable `LanguagePicker` as Settings, including the system-default option and native language labels.

Space sidebar folders are personal navigation organization, not workspace space entities or shared policy. `space_folder_providers.dart` reads `prefs.watchOwn` and writes a JSON folder list under `space_folders.<workspaceId>` with `prefs.set`; expanded and rail-mode sidebars share it. Workspace-specific keys prevent mixing a user's arrangements, while the workspace's visible-space stream remains the authority for which rows can be shown. Space-row and header archive actions remove the archived space from personal folder membership, so restore leaves it unfiled. Deleting a nonempty folder defaults to removing only its folder record; an explicit confirmation checkbox instead deletes its existing workspace spaces through the messaging service before removing the folder record. Folder deletion and space deletion have different scopes: the former is personal, the latter is workspace-wide.

`SpaceFoldersList` handles workspace-scoped drag payloads: folder rows accept visible spaces, space rows open the existing folder-name dialog when another space lands on them, and a filed space dropped in free sidebar space becomes unfiled. During a filed-space drag, both desktop sidebars show a bordered "Remove from folder" target between folders and unfiled spaces; its accent border confirms an eligible hover, and dropping moves only a visible space in the same workspace. Drops outside the sidebar do nothing. `SpaceFolderActions.create(spaceIds:)` moves both spaces out of previous folders and into the new one in a single personal-preference write; direct folder and unfile drops use `SpaceFolderActions.move`. The menu remains a non-drag alternative. Folder overflow uses the space row's hover-revealed trailing control; its caret appears only when visible members exist.

The phone PWA reads the same `space_folders.<workspaceId>` preference over `prefs.watchOwn` and writes through `prefs.set`, so folders follow the user between clients without adding shared workspace entities. Its Chat tab groups only active spaces from the selected workspace and offers touch-sized create, rename, move, unfile and delete controls instead of drag-only interactions. Permanent deletion verifies listed space ownership in that workspace; removing the folder alone leaves its spaces intact.

The space setup banner retries and stops provisioning through `RemoteMessagingRepository` with an explicit workspace ID, rather than relying on the RPC client's ambient workspace. Stop confirmation retains the workspace captured when the dialog opens.

The banner also opens a read-only setup logs tab through `EnvironmentHost.openProvisioningLogs`, so it works on both the messaging IDE and the PR page; a surface with no editor, and a demo, offer no button. `SpaceProvisioningLogPort` holds what preparation prints: `RepoWorkspaceProvisioner` writes it, because the background run and a dispatch's inline call share that path, and `SpaceProvisioningService` adds how the run began and ended. rift reports nothing until it returns, so the CoW copy shows a start line, a 15-second heartbeat and its duration; `git fetch` and `checkout` run with `--progress` only when someone is logging them. `provision` tasks stream as they print, except in a rig, which returns output when the command ends.

`InMemorySpaceProvisioningLog` is the single redaction chokepoint. It keeps 256 KiB per space for the 32 spaces touched most recently, never evicts a followed space, and is lost on restart, so the tab is dropped from layout snapshots. `messaging.watchSpaceProvisioningLog` (in the `space_provisioning_ops` pack) is an event stream: a progress bar rewrites its line under the same `seq`, and a client replaces an equal `seq`, appends a higher one and ignores a lower one, which is a reconnect's replay. A log's numbering starts from the clock, so a log rebuilt after a restart or eviction always numbers past what a reconnecting client has seen. Every run of a space appends to one log, so a retry keeps the failure it follows in view.

Space PR status combines explicit review associations with worktree/stack branch matches. A mixed-status sidebar glyph clips each distinct state's icon and color into an equal angular sector: two states get halves, three get thirds and four get quarters, regardless of PR counts. A 1px theme-border divider separates adjacent slices without changing their proportions. The status mask compares by value across refreshes; sector order stays stable across inventory order and RTL. Single-state inventories retain their full glyph, and mixed glyphs keep their colors on a neutral backing when selected. Tooltips and accessible labels name every represented state; numeric badges still count unread conversations.

A full merged sidebar glyph means a nonempty, fully resolved inventory in which every PR is merged. A merged sector in a mixed glyph makes no all-merged claim. `pr.watchForSpaceBranches` returns `matches` plus `complete`, using exhaustive GitHub/GitLab/Bitbucket branch history cached per workspace/repo/head and reconciled with persisted poller transitions. History refreshes after five minutes on the existing poller cadence; failed or incomplete lookups cannot trigger an archive prompt.

The messaging IDE's Source Control tab owns the space PR inventory above the worktree controls; General contains no PR section. Linked PRs remain accessible while worktrees load, provision or are absent. The inventory header groups creation actions by checked-out repository, retaining branch-PR eligibility and complete-lookup requirements for publishing missing stack parts. Existing PRs open from inventory rows, not duplicate repository footer actions.

The Source Control panel polls `repos.changesGrouped` every few seconds per repository; the Review tab reads `repos.changes` (HEAD against the working tree). Both start from one `git status --porcelain=v2` of the worktree (`ProcessSessionDiffAdapter`). It refreshes the index's stat cache and fingerprints HEAD, each changed path's index blob and its size, mtime and ctime on disk. An unchanged fingerprint answers from the last result, so an idle poll runs one git command, not a dozen. The Review diff comes from `git diff HEAD` plus the untracked files. It takes the whole-tree capture (`captureWorkingTree`) only when a deleted tracked path sits next to untracked files (a move without `git mv`, `git rm --cached`) or there are more than 24 untracked files. `IsolatedGit.run` admits at most `localConcurrency` local git commands at once, server wide; commands that reach a remote skip that queue. The server raises its soft open-file limit to the hard one at boot (`raiseOpenFileLimit`), since macOS starts it at 256.

Opening a fully merged space shows an inline archive notice above its IDE tabs. Archive uses the existing soft-archive and personal-folder unlink action. The user's answer is stored through `prefs.set` under `space_merge_archive.<workspaceId>.<spaceId>` (`keep` or `archive`); both answers suppress later prompts for that space, including after restart or restore. Preferences must load before the notice appears, and a failed preference write leaves the decline action available rather than claiming it was saved.

Space editor layouts cache the active pane and each pane's selected tab under the workspace/space layout key. A layout belongs to the person, not the workspace: `cache.read`/`cache.write` (`buildEditorLayoutCacheOps`) store each row under a key derived from the session's `userId`, and accept only `EditorLayoutCacheKinds`. Layout rows are exempt from the 21-day cache retention sweep. Reopening a space restores its last conversation or terminal, on any of that person's devices and after client restart; explicit `?tab=` links take precedence. After conversation tabs reconcile, the resolved tab is written into both GoRouter state and the URL by replacing the current history entry, preserving other query parameters. PR workbench focus behavior is unchanged.

Every editor tab has an `EditorTab.id` (its dedup key, else its kind); stackable kinds mint per-tab keys. A pane's selection is saved by id (`selKey`); a payload from another codec `schemaVersion` decodes to the default layout. A selected tab that is never restored (a diff, a review) saves the most recently visited restorable tab instead; with no history, the pane falls back to its first tab. The client's `EditorLayoutMemo` paints a revisited space in the same frame, then `_revalidate` re-reads the server and adopts a newer save from another device unless the person already changed the layout locally. An unconfirmed local save is never treated as older than the server's copy. Writes the server is known to hold are skipped, so leaving an untouched space never replaces another device's newer save. A local tab press leaves GoRouter's `?tab=` stale, so a route change only counts as a repeated tab link when it still names the open space: leaving a space must save the pressed tab, not refocus the tab it was entered on. A seed shown while the first read is in flight, or after it failed, is never persisted.

Sidebar conversation rows have their own hover and activation targets. Selecting one focuses its existing chat tab across panes or reopens it if closed, including repeated navigation to the same `?tab=` key after local tab selection changes. Background data refreshes never reapply a stale route key over local focus. The space overflow menu lists **Archived conversations** before a divider separating the reversible **Archive space** action. Its dialog watches only that workspace/space's archived streams; restore uses `ConversationRepository.setStatus(active)` and waits for the live list to reflect the change before opening the conversation tab. A failed restore leaves the dialog available for retry.

Where native editor windows can be reparented, the messaging IDE speculatively warms only the selected ready space's first provisioned worktree, after a one-second debounce and scheduler-idle admission. It skips demo, hidden/background layouts and worktrees with an existing editor. The first file adopts that same window; no editor is created for every repository or tab. An unclaimed preload expires after 60 seconds without rearming on ordinary rebuilds, and is cancelled on space changes, backgrounding or memory pressure. Memory pressure suppresses further preloading until the space changes. The booting view paints behind the foreground layout so the platform view can initialize, excludes input/focus/semantics, then becomes offstage once ready.

`codeServer.*` declares `serverAuthority: serverOwner`, and a session belongs to the device and user that opened it. Auto-disposed editor session providers balance each `codeServer.open` with a workspace-scoped `codeServer.close`, including opens that finish after disposal. Closing decrements only the caller device's reference; `discard_if_unused` stops the server process immediately only after the final reference is gone, so dropping an unused preload cannot terminate another editor's shared process.

The message feed acknowledges conversation notifications when it opens or returns to the live edge, including when an agent completes an existing message ID. Revealing a cached chat renews the acknowledgement even without a new feed snapshot. Debounced writes are cancelled while hidden and require the live edge; the host changes only the current user's matching conversation notifications, preserving other conversations and explicit unread overrides.

Space-row numeric badges count distinct conversations whose latest agent message is newer than the user's space read cursor, using the existing workspace activity breakdown. PR status remains a glyph, not a numeric inventory. The badge tooltip labels the count as unread conversations; running spaces retain the count and muted agent-only rows suppress it. Existing space-scoped read semantics remain unchanged: never-opened spaces stay quiet, and advancing the space cursor clears matching conversation unread signals. No per-row message feed is subscribed for the count.

Unsent PR comments/replies, review bodies and commit messages use session-owned, workspace/destination-scoped controllers (`textDraftControllerProvider`), not widget-owned state. Commit drafts share the actual worktree identity `(spaceId, repoId)` across source-control panes. Conversation drafts (`spaceComposerDraftProvider`) retain text/selection, picked mentions and upload state across route/tab disposal; transfers can finish offscreen and returning reuses the uploaded file IDs. Successful submission clears only its submitted draft, while failures and newer edits retain their content. These client drafts last for the backend session; review bodies also keep their existing server-backed draft save/load.

The messaging IDE's Explore tree follows the focused pane's file tab (editable or quick view). Opening or switching file tabs, returning to Explore, or returning from search to the unfiltered tree expands the file's repo and ancestors and centers its row within the scroll bounds. Lazy directory pages keep the current target aligned as they arrive; a newer tab selection supersedes the previous reveal. Manual tree scrolling or folder toggling cancels an in-flight reveal, and unrelated layout changes do not recenter it. Search mode, query and other folder expansion state remain intact.

Running agent commands in the messaging IDE's General → Terminals section open read-only output tabs, keyed by workspace, space and a server-issued output identity. Repeated clicks focus the existing tab; closing it never stops or restarts the command. The viewer polls every three seconds while running, follows the tail until the operator scrolls away, and supports selection, copying and explicit retry without discarding the last output. These process-scoped tabs are not restored after an app restart.

`AgentShellProcessService` serves output through `process.agentShellOutput`. The built-in harness captures both output streams into a bounded 65,536-code-unit tail; CLI capture reads up to 64 KiB from regular stdout/stderr files on macOS/Linux, deduplicating a shared file. Separate stdout/stderr files are shown in descriptor order, not interleaved by timestamp. Verified file descriptors remain readable after exit, with a two-minute retention window and a 128-record cap per capture source. Pipes, PTYs and commands without captured output report unavailable; opening a tab never consumes the agent's own stream. CLI output must first be opened while its process is still discoverable.

### Client forge model

The server owns every forge read and write; a client renders what `forge.*`, `pr.*` and `github.*` RPCs return and never builds a forge client of its own. Rules a client feature follows:

- **Which forge.** A PR's forge is its repo row's: `prRepoRowProvider(prRef)` matches `matchRepoForPr` on owner, name and, when stated, `PrRef.forge`. The route carries `?forge=` for a non-GitHub PR, so two repos with the same `owner/name` on different forges stay distinct. Full names split at the last `/` (`splitRepoFullName`), so a GitLab `group/sub/project` keeps `group/sub` as its owner. Only `forgeWithoutRepo` guesses a forge without a repo in hand: the only connected one, else GitHub.
- **Who am I.** `forgeConnectionsProvider` is the one source for connection state on desktop and phone (`RemoteForgeConnections` in cc_data). Each `ForgeConnection` carries the server's `status` and `scope`; "connected" means `isUsable` everywhere (onboarding gate, banner, inbox). There is no client overlay of `oauth.connections`, and every `oauth.*` call sends the active workspace; the client never derives a sign-in scope. A failed read is an `AsyncError` that keeps the previous list, and the onboarding gate treats a first-read failure as unresolved, never as "no forge". `viewerLoginsProvider` maps each forge to the lower-cased login; every "is this mine?" test goes through `currentUserLoginForPrProvider(prRef)`, the login on that PR's forge. After any sign-in, sign-out, token change, Connect apply or workspace App change, call `invalidateForgeState`, never a partial list of invalidations.
- **What can it do.** Gate affordances with `prSupportsProvider((prRef, ForgeCapability.x))` or `capabilitiesForProvider(forge)`, never `forge == ForgeHost.github`. The table is `kForgeCapabilities` in cc_domain, served by `forge.capabilities`. A server op on a forge that lacks the surface throws `ForgeUnsupportedError`, which reaches the client as a validation error carrying `unsupported_capability` and `forge`.
- **Copy.** Name the forge with `ForgeHost.displayName` ("Open on {forge}"). GitHub-only chrome (the GitHub status banner) shows only when the workspace has a GitHub repo (`workspaceForgesProvider`).
- **Hosts.** `ForgeHost` names a forge *kind* with its public host (`github.com`, `gitlab.com`, `bitbucket.org`). Self-hosted GitLab or Bitbucket is not representable: a connection carries no base URL, and the forge clients and `ForgeUrls` build public-host URLs. Supporting one means a per-connection base URL threaded through `ForgeTokenStore`/`ForgeConnectionView`, the client builders and `ForgeUrls`, not a new enum value.
- **Data access.** `prReviewRepositoryFactoryProvider` returns `RpcPrReviewRepository` for every forge with a remote and `EmptyPrReviewRepository` otherwise. There is no client-side forge provider registry.

Run-end conversion claims each card by converting it, dispatches, and on failure returns it to the queue with `steerFailedAt` and a system notice.

The server decides (`AgentTurnRetrier` behind `dispatch.retryAgentTurn`): it collapses presses that arrive while a retry is starting, judges the turn against the stored conversation, refuses a message outside the op's space, and writes `retried` only once the new run exists, so a refused dispatch leaves the turn retryable. Clients apply the same policy to the feed they show (`MessageItem.canRetry`, the phone's `retryableTurnIds`), so Retry appears only where it would be accepted. A turn's `error`/`retried` flags are read from the listed row: the full-row read behind a bubble is one snapshot and never learns of a later retry.
- Resolved `ask_user` messages share that inline transcript lane: associate each question with the latest preceding agent turn from the same sender, space and conversation, then insert its question/answer summary at the `createdAt` segment boundary before subsequent work. Pending forms stay standalone. If no matching turn is loaded, keep the resolved question visible as its own row until pagination supplies the turn.
- `TranscriptFlow` keeps segment ordering and closed-row memoization in its main library, with prose, reasoning disclosure and live status in separate parts. The feed's row construction and retained-widget cache live in `message_feed_rows.dart`; preserve widget identity and reverse-list laziness when splitting these renderers.
- Read-tool rows open by default while retaining explicit user collapse. Successful local media reads are saved by `ReadMediaCapture` into the existing workspace `BlobStore` (24 MiB original-file limit) before the result and subsequent events are published. `ToolResultEvent.attachments` travels through event transport, transcript folding and persisted segments; previews use signed workspace blob URLs, never the viewing device's filesystem. Images, video, audio and PDFs reuse attachment viewers. GIF/APNG retain their animated originals, including APNG carried in `.png`; SVG and non-native raster formats such as HEIC get persisted PNG/JPEG previews from the shared media renderer. PDF-compatible Illustrator files use the PDF viewer; legacy AI/EPS/PS and other unsupported vectors retain extracted text and an authenticated original-file download. Other documents retain extracted text and an original-file link. SVG originals are download-only, with a restrictive CSP.

### Usage analytics

One `Analytics` facade per process (`packages/cc_domain/lib/features/telemetry/`): desktop/web (`analyticsProvider`, `lib/core/providers/analytics_providers.dart`), the phone (`apps/cc_remote/lib/analytics.dart`) and the server (`ServerAnalytics`, `packages/cc_server_core/lib/src/telemetry/`). Call sites record only events from the `AnalyticsEvents` tracking plan. The facade gates collection on the server's `TelemetryConfig`, which is opt-in. Records made before the config arrives wait in a bounded buffer and are dropped if it says no. Collection is also gated on the build (`kReleaseMode` on clients, `dart.vm.product` on the server; other builds log through `LoggingAnalyticsSink` unless the server's `CC_ANALYTICS_DEBUG=1` sets `TelemetryConfig.debugBuildsAllowed`). The facade merges the context (`app_type` desktop/web/remote/server, version, platform, server mode, locale), applies `AnalyticsPropertyPolicy` and pseudonymizes IDs, then hands an `AnalyticsEnvelope` to the `AnalyticsSink` port. `AnalyticsDestination.createSink` in `cc_analytics` is the single provider switch; `UmamiAnalyticsSink` owns queueing, backoff and delivery.

Clients record UI interactions: screen views from the router's route template, sends, approvals, commands, searches, settings and the session lifecycle. The server records domain facts from the `DomainEventBus` (runs finished, workspaces, spaces, tickets, pipelines, PRs), so agent work is counted once however many clients watch. Do not record a server fact from a client. Adding an event means a factory in `AnalyticsEvents`, its call site, and a row in the manual's telemetry reference. Privacy rules are in [SECURITY.md](SECURITY.md#usage-analytics).

### Client read snapshots

Desktop and web attach a bounded `RpcSnapshotCache` to `ResilientRpcClient` after the server handshake and an uncached `identity.me` read. The namespace includes the verified server fingerprint and authenticated user; each entry includes the query/read operation and complete arguments, including workspace, repo, entity and range. Eligible subscriptions replay their snapshot before attaching to the live stream. UI-only one-shot reads opt into `watchCall`; ordinary `call`/`callResult`, mutations, credentials, presence and live control remain uncached.

Snapshots survive navigation and restart: desktop uses owner-private atomic files under `<appSupport>/client_rpc_snapshots`, web uses dedicated IndexedDB storage, with a 16 MiB per-identity working set. Fresh results, including empty results, replace stale data. Transport loss retains readable snapshots; reconnect revalidates. Storage corruption or quota failures do not block live reads. Forget/disconnect clears the server's snapshots, and authenticated membership refresh or explicit authorization rejection invalidates affected data.

This is a read cache, not an offline server or a source of mutation authority. A cold launch still requires a reachable server for authentication and workspace admission; an admitted session can continue viewing previously loaded data during an outage. Conversation feeds keep their live refresh attached while replaying snapshots. `messageDetailProvider` revalidates full agent-turn messages, including cached unfinished placeholders that have no `segments_elided` marker; completion invalidates an earlier unfinished read after the frame, guarded against disposal or a changed turn. Never invalidate it synchronously from `AgentTurn.didUpdateWidget`: refreshing the enclosing provider scope during a feed build violates Flutter's build lifecycle. The renderer uses the stored agent name when its directory lookup is unavailable, and caches finalized transcripts separately from live turn events.

### Media cache

Clients fetch external media through signed `/proxy/media` (`MediaProxyConfig`). `MediaCache` persists non-ranged images under `<dataDir>/media_cache`, keyed by `(url,w)`: upstream max-age clamped to 1 hour–7 days (default 24 hours), conditional ETag/Last-Modified refresh, stale-on-refresh-failure and same-key single-flight. Bucket requested widths **up** with `bucketMediaWidth` in `lib/shared/utils/media_width_ladder.dart` to share entries.

`DiskCachedNetworkImage` reads through the native client's `MediaDiskCache`. If the cache cannot supply bytes, the provider fetches the resolved URL's bytes and decodes them under its single `MultiFrameImageStreamCompleter`. Never share a codec with a nested `NetworkImage` completer: both would consume and dispose it. Failed loads evict the provider's own image-cache key so a later resolve can recover. Web bypasses the inert disk cache and delegates directly to `NetworkImage`.

Server raster transforms cap decoded input at `8192 × 8192` pixels; ICO conversion caps it at `4096 × 4096`. These are pixel budgets, not byte/heap limits. Over-budget images retain the existing no-transform/original-stream behavior, and animated images are not flattened into thumbnails.

Newsfeed grid and list layouts use `ScrollCacheExtent.viewport(1)` to build one viewport of nearby tiles before and after the visible region, not the whole feed. `ProxiedImage` resolves only the tiny preview while a tile is in that cache region; its first paint enables the full-size request. Both variants keep the signed proxy, disk/image caches and existing cross-fade behavior. A changed URL or target width resets the full-size paint gate.
