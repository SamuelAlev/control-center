# Architecture

Control Center uses Flutter clients, a pure-Dart authoritative server, Riverpod, and Drift/SQLite. Coding/build rules are in [AGENTS.md](AGENTS.md); access control and credentials in [SECURITY.md](SECURITY.md). Read the subsystem below when changing it, rather than loading every package document.

## Runtime and data flow

```text
Desktop local ── supervised cc_server ── Noise over loopback WS
Desktop remote / web ── Noise over WSS ── cc_server
Phone PWA ── Noise over direct WS / broker relay ── cc_server
MCP clients ── JSON-RPC ─────────────── tool registry
Fleet workers ── leases + events ────── cc_server
```

`lib/bootstrap/server_backend.dart` resolves the persisted local/remote choice before the authenticated Riverpod container starts. Local desktop spawns a supervised server; web is always remote. The connected `RemoteRpcClient` overrides `rpcClientProvider`; all client repository bindings use `cc_data`, including local desktop. A `*_bindings{,_io,_web}.dart` seam exists only where the targets genuinely diverge (audio capture, calendar recording, meeting signals); an identical pair collapses to one file.

Desktop setup and the web gate share one landing (`lib/shared/widgets/server_connect/`): local run on desktop, a connect dialog also used by Settings, and a paste dialog for invite and pairing links. The main action follows the last saved mode. Connecting from a dialog keeps it open and shows a failure there with the entered values. Connect reuses the saved device credential and identity pin when the URL matches exactly one remembered RPC endpoint and no new invite or pairing key is supplied. Explicit credentials take precedence; failed retries leave the saved pairing intact. Opening a dialog clears the previous attempt's error without persisting a mode until it connects. A pasted link is untrusted: the dialog names its server and connects only on an explicit Connect. Phone relay links and sealed SSO completions do not parse there, and a web link that arrives unbidden opens the connect dialog for the same review.

`SecureRpcChannel` is the shared encryption boundary above the raw direct/relay adapters. It carries JSON-RPC and `RemoteResources` HTTP/WebSocket streams with independent bounded credit windows. Native clients expose a capability-scoped loopback URL facade; web clients use the shared Service Worker/MessagePort bridge. Browser editors are trusted client code on the Flutter app's origin. Their capability-scoped HTTP/WebSocket requests travel through the encrypted session to `cc_server`, which owns the code-server process and files. `SecureResourceHost` invokes existing server HTTP handlers over private loopback with device/user binding, preserving route-specific authorization. The editor extension's open/dirty reports and command SSE use a separate server-only private bridge, not client proxy capabilities.

Web login, remembered-session resume and server switches keep the current document loaded. Resource capabilities rotate per connection but remain same-origin; they are not server origins and must never trigger a CSP-cookie reload. Both the edge Worker and self-hosted web policy keep decrypted images/media same-origin while permitting the pre-connect identity probes and encrypted WebSockets.

`cc_remote` is an operations client of the same catalog, not a second backend. Conversation routes and drafts use explicit workspace/space/conversation identities; message links validate their owning conversation rather than falling back to a standing stream. Drafts remain in session memory across navigation and transport reconnects and are dropped when pairing authority changes. Run controls, plans, supervised goals, policy edits, provider connections and uploads call the existing server services with their normal role and capability checks. See the [phone capability map](apps/cc_remote/README.md#phone-specific-behavior).

Desktop shows the localized `DesktopBootApp` only when no server choice is saved. `runDesktopBootWindow` mounts it in the setup window after essential preferences/native-window setup and waits for `waitUntilFirstFrameRasterized` before media initialization, credential reads and backend connection. A framework `endOfFrame` alone is insufficient: a headless frame can finish without a native view rendering. Configured local and remote launches skip both the temporary window and its rasterization wait, connecting directly before mounting the main app. Missing credentials or a failed connection still open the normal setup/recovery window. The boot surface has no provider container, cached workspace data or session actions. Authentication and workspace admission still precede `DesktopBackendSession` adoption; a failed session build disposes its container and the initial backend.

On macOS, `AppWindows` explicitly shows each newly created main/setup/error window through its controller's native handle before waiting for its first frame. Flutter otherwise keeps the window invisible until presentation, while a headless launch or setup→primary handoff can report `hidden` and disable the frame that would reveal it. The existing will-show hook still applies chrome before showing and arms `WindowVisibilityGuard` for stale lifecycle state afterward. This creation-only action never reopens a window in response to ordinary Hide/minimize or affects the floating HUDs.

Desktop server switches keep `AppWindows` and its primary native window mounted. The session key belongs inside the primary window and around the HUD collection, not above the native-window tree. Each switch remounts the session UI and media-proxy scopes, then disposes the old container/backend after that frame. Optional media-proxy wrappers must not become ancestors of the primary native window. Adoption never shows or focuses it again, preserving position, size, fullscreen, Hide and minimize state.

Both composition roots build a session's container from one `sessionOverrides(...)` (`lib/bootstrap/session_overrides.dart`) and hand sessions to a `ServerConnectController`, which serializes switches (a repeated request for the same server joins the one in flight; a different server is refused until it settles, so two switches can never start two local servers on one data directory) and retires the outgoing session after the remount frame. Desktop wiring lives in `desktop_session.dart` (one session), `desktop_server_switcher.dart` (adopt, switch, return to setup) and `desktop_app_host.dart` (method channel); incoming URLs dispatch through `desktop_deep_links.dart` into the owning features. Returning to setup (sign-out, a lost remote) is the one path that replaces the whole native-window tree: it runs the pre-app setup surface, then mounts a fresh `DesktopAppHost`. Quitting a local session first stops the bundled server while the session's container, client and shutdown overlay are alive to show its teardown progress, and only then disposes them. `startupReporter` is the only writer of `serverStartupStatus`: foreground attempts go through `track`, and a background reconnect holds a `StartupLease` that stops reporting once anything else claims the indicator.

Device caches that belong to one person on one server (the onboarding-complete hint, the remembered workspace id, the workspace name/logo shown before the list loads) are keyed by `SessionScope` (`'<key>@<serverId>/<userId>'`, from the supervisor descriptor and `identity.me`). A cache written for another server or user is never read, and unscoped keys from older builds are ignored.

`WindowDragArea` resolves drag, manual move and double-click zoom through its enclosing Flutter `WindowScope` and `nativeWindowOf`. Never target nativeapi's focused/current window: the focus, meeting and soundscape HUDs are deliberately non-focusable, so the primary window stays focused while the pointer operates a HUD. Web window actions remain no-ops.

The tray (menu bar) icon, close-to-tray and launch at login sit behind the web-safe `DesktopShell` port (`core/desktop/`); `NativeDesktopShell` (`app/tray/`) implements it and the web build keeps `UnsupportedDesktopShell`. The shell is process-level: the icon, the main window's hidden state and the close interceptor outlive server switches. `TrayPresenter` is session-level. It wraps the HUD collection, pushes `trayStatusProvider` (connection, open questions, approvals, working spaces) to the icon and native menu through listeners rather than rebuilds, and hosts `TrayPanelWindow`, a focus-dismissed popover placed by `resolveTrayPanelBounds`. Switching workspace from the panel navigates the main router, hidden or not, because the route is the active workspace's source of truth; the panel then follows it. A hidden main window disables frames, so opening the panel forces one, and the will-show hook arms `WindowVisibilityGuard` for it. The icon is one monochrome template glyph on every OS (`tool/tray_icons/` traces it from `assets/logo_white.svg`): AppKit inks it for the menu bar, and nativeapi for the Windows taskbar theme and the StatusNotifierItem panel, following their theme changes. On Linux the shell asks the session bus (`package:dbus`, no subprocess) whether a StatusNotifierWatcher exists; stock GNOME has none, so close-to-tray stays off there. Closing the primary window asks the presenter first. It hides only when something can bring the window back (always the Dock on macOS; the tray icon elsewhere), and Windows and Linux ask once before the first hide. Hiding goes through the controller's native handle, never nativeapi's window list, which omits hidden windows on Windows. Notification clicks, deep links, `reopen` and `openSettings` reveal the window first. A login launch is `--launched-at-login` on Windows/Linux and the `keyAELaunchedAsLogInItem` Apple Event on macOS (an `SMAppService` login item cannot pass arguments). When it opts to start hidden, the will-show hook vetoes the first show on macOS and Windows; Linux, which cannot veto, hides right after. The native runners route a second launch to `reopen`, so the app stays a single instance. A login launch that finds the app already running does not raise it.

Server startup and background on-device model work share a non-modal floating **Server activity** panel in desktop boot/setup, onboarding and the connected app. Startup state is client-owned until RPC is available; model progress and retained download failures come from the server's existing `models.*Status`/`models.watch*` snapshots on both local and remote connections. Completed work disappears, failures retain technical details, and only the install owner can retry model installation. Onboarding suppresses the speech-model lane while its own inline progress is visible, without hiding background embedding/diarization work. Narrow onboarding layouts scroll the introduction with the fields and reserve activity space inside the keyboard-resized body; step actions stay pinned and activity details fold away during typing. Root modal dialogs temporarily hide the activity panel. Local reconnect activity belongs to its process holder and is released on retirement, so local health pings cannot replace remote switching progress or failures. A local child that exits before readiness reports a bounded, secret-redacted tail of stdout/stderr so bind and native-preflight failures reach setup rather than only the log.

`DesktopUpdateLifecycle` starts supported desktop updaters after the first setup or `ControlCenterApp` frame, independently of login and workspace-shell routes. Pre-connection setup uses an isolated updater-only provider scope; the connected app supplies the recording busy probe. Automatic checks run after 60 seconds and then every 24 hours, deferring prompts during recordings. Disposing the owning scope cancels the schedule and releases native callbacks.

The What's new dialog renders `usectrl.dev/changelog.md`, fetched by the server through `changelog.get` and parsed by `ChangelogRelease.parseMarkdown`; clients never contact the website. `ChangelogAfterUpdate` opens it on the first shell launch of a new `BuildInfo.buildVersion`, keyed by a client preference. A fresh install records its version silently, and an unreachable changelog leaves the version unseen so the next launch retries instead of opening an error.

The server owns external APIs and background services. `rhttp` adapters in `cc_infra` inject auth and classify failures through `network/error_mapper.dart`; unhandled transport errors are mapped at the RPC boundary. Workers execute leased jobs and stream events; they do not own databases, policy, approvals or budgets, and do not coordinate with each other. Architecture boundaries are enforced by `test/core/architecture_constraints_test.dart`.

HTTP uses rhttp's native reqwest engine, not a Flutter plugin. `cc_natives.initializeRhttp` loads the required library before client creation in each isolate. `createHttpClient` provides platform certificate roots, a default `ControlCenter` User-Agent (required by APIs such as GitHub), request normalization, retries, identity-aware deduplication and logging. Explicit client and per-request User-Agent values take precedence. Downloads use streamed bodies with receive-idle deadlines rather than a whole-transfer timeout. The headless dependency patch and native build contract are documented in [cc_natives](packages/cc_natives/README.md).

### Identity and collaboration

`Principal` is `UserPrincipal | AgentPrincipal`; use it for attribution. Users are global; membership/roles and repo grants are workspace-scoped. See [authorization](SECURITY.md#authorization-and-isolation).

- Durable state: clients render full-snapshot `*.watch*` subscriptions; there is no client delta mirror. Per-field ticket edits use `tickets.patch` (per-column LWW): server receipt order, never client time, decides the last writer.
- Presence: server-hubbed, ephemeral, never persisted, humans only; agent status comes from run logs, not a presence lane. `presence.watch` redacts per subscriber through `PresenceViewer` (`catalog/presence_visibility.dart`): a member without every linked repo loses space/file/PR loci, the space they type in and worktree claims they cannot read, but keeps online state; admins and fully granted members see everything. `PresenceHub` signals only on a real state change (a heartbeat that repeats the wire entry is silent) and caches display names for five minutes, healed immediately by `users.updateProfile`. The title-bar rail and space-header avatar strip show only other human users; with one human, roster chrome stays absent even while agents run.
- Follow is user-to-user only, ending when the follower navigates away or the active workspace changes. Starting a follow baselines the current route, so a target with no locus never yanks the follower later, and a spotlight never ends a follow (it only navigates when not following). Steer/interrupt/take-over and per-space autonomy use these lanes, not a CRDT.
- Take-over is one claim (`CacheDao.putIfAbsent`) before any run pauses; a failed begin resumes what it paused and drops the claim. Only the holder or a workspace admin hands back; the marker is removed first, so a failing resume never leaves a stuck takeover, and the failure is reported. Clients subscribe to `takeover.watch`, never poll.
- Agent peer messages use durable spaces, exact ID/unique-name resolution and no cross-workspace recipient search; `consult_agent` resolves its specialist the same way (the topic only frames the brief). `from_agent_id`/`delegated_by_agent_id` are forced to the trusted caller by `McpCallScope.apply` (`callerIdentityKeys`) on both transports, and dropped when there is none. `ask_agent` has a mandatory timeout (default ten minutes, workspace-capped); `PeerDelegationGate` runs its guards (parent ticket, depth, autonomy ceiling, budget, in-flight cycle) before the DM space or rate slot is touched, and the reply is the run's own message (its id is the dispatched run id) in that conversation, with stream errors returned rather than waited out. `delegate_task` and `delegate_ticket` pass the same gate (ticket hand-off: the parent only has to exist in the workspace, and depth is the parent's ticket depth) before `TicketWorkflowService.createDelegatedTicket` writes the child, so all three refuse a cycle or an exhausted budget with the same reason and an unconfigured policy refuses. `send_to_agent` refuses an in-flight cycle. Messages the server itself posts (takeover notices, delegation outcomes, compaction markers) are `SenderType.system` from sender `system`; rows and peers older than workspace schema v23 wrote them as `agent` from `system`, which every decoder still reads as system. Delegation inherits budget and autonomy ceilings, with cycle detection and a default depth cap of three. Agent-only spaces (`SpaceKind.agentPeer`) never raise unread (the activity SQL nulls their agent timestamp) or notify: one server predicate in `notification_wire.dart` decides, and desktop, web and cc_remote consume its verdict.
- Agent-finished notifications come from `MessageReceived` after the turn is persisted. Their preview uses the last non-blank `TextSegment`, capped at 120 characters, rather than the stored message content that joins all progress prose. Reasoning and tool output never supply preview text; a turn with no visible text retains its failure fallback or emits no notification. Live notifications and the durable bell feed share this preview.
- Human questions (`ask_user`) use the session's workspace, space, conversation and agent IDs, never a model-selected or implicit standing conversation. `AgentQuestionRequest.conversationId` is required; an empty destination throws, the server validates it before posting, and the awaiting-input notification carries the same conversation. `cc_infra`'s `AgentQuestionService` is the only implementation: every ending claims the waiter first, expiry is the conditional `MessagingDao.expireQuestion` (`answered != 1`), and `deliverAnswer` reports `delivered`/`notPending`/`notPersisted`, so the client shows a localized rejection rather than a false success. A boot sweep (`orphaned_wait_sweep.dart`) closes questions and resolves feed waits a previous process left open.
- A desktop awaiting-input notification is keyed by its wait (`wait-<wait_id>`) and is time-sensitive. An approval adds Approve and Deny buttons that call `confirmation.respond`. `AgentWaitReminder` follows the active workspace's feed: it re-raises an open wait at 3, 10, 25 and 45 minutes after it started (a question drops steps at or past the server's question timeout), replacing the earlier notification, and skips a reminder while an app window has focus. When the feed stamps the wait resolved, it withdraws the notification. Waits are not re-pushed from the server: the server's feed row and its resolution are the only state involved.
  Pending-question views combine workspace-scoped message snapshots with live `AgentQuestionService` waiter changes. A persisted unanswered message without an active asker is history, not an actionable request after restart. Validate an answer before consuming its waiter; competing valid replies still have one winner.
- Run-owned checklists (`todo_read`, `todo_write`) require the session's workspace and conversation and overwrite model-supplied IDs, including a space ID or another valid conversation. The model-facing schema does not require those IDs. External MCP and the harness bridge share `McpCallScope`; tools declare mandatory context with `requiredScopeKeys` and non-overridable arguments with `forcedScopeKeys`. Missing trusted context is an error, never permission to fall back to model-selected IDs.
- The General sidebar follows the focused chat in the live `EditorLayoutController`, switching its conversation-owned TODO/goal subscriptions on tab presses, split focus and layout restore. Local tab presses only publish platform history, so GoRouter's `?tab=` state is not a live selection source. Only the seeded space chat resolves its standing conversation; non-chat and empty editor selections show no conversation checklist. TODO rows and mutations use `conversationId`, with `workspaceId` retained for isolation; there is no TODO `spaceId`.
- The dispatch silence watchdog suspends only for question wait IDs matching its workspace, conversation and agent, and ignores a wait stamped with another run's id. It measures from the run start, so a run that never produces output still times out. Overlapping waits remain suspended until the last resolution, which starts a fresh inactivity window. A terminal error marks the turn failed even when the agent already emitted progress prose; an error followed by a recovered answer does not.
- `DomainEventBus` declarations under `cc_domain/lib/core/domain/events/` are authoritative. Device revocation watches `paired_devices`; there is no `UserDeviceRevoked` event. Workspace removal drops subscriptions without requiring the socket to close.

### Provider credentials and Connect

Every provider credential lives on the server and resolves per call; no build carries one. Server code is under `packages/cc_server_core/lib/src/connect/` and `forge/`; the broker is [apps/cc_connect](apps/cc_connect/README.md) and the shared contract `packages/cc_connect_core`. Trust boundaries are in [SECURITY.md](SECURITY.md).

**Sign-in lanes.** `ProviderSignInService` runs every browser sign-in (`github`, `google`, `linear`, `linear_app`, `slack`) behind `oauth.lanes|begin|status|complete|connections|disconnect`. The person is always `ctx.userId`, never an argument. Each lane binding resolves the workspace's own app first (`WorkspaceGitHubAppSettings` for `github`, `WorkspaceProviderAppSettings` for `google`, `linear` and `linear_app`), then the server's own app from `ProviderAppSettings`, else Connect when its config advertises the lane, else unavailable. Completeness: GitHub needs app id, private key, client id and client secret; Google client id and secret; Linear only a client id (public PKCE client). A partial own app throws `SignInMisconfigured` and never mixes with Connect. A workspace on its own app signs people in to that app and never routes through the server's app or Connect (`allowsConnect` is false).

**Connect choice gates the server's own apps.** `ConnectSettings.choice()` is authoritative: the server's own apps apply only while `serverOwnAppsActive()` (mode `unset`/`off`). Under `hosted`/`custom` they stay stored but inactive everywhere, through one chokepoint in `ProviderAppSettings` (`active()`, `ProviderAppStatus.effectiveState`): sign-in lanes' `ownApp`, `GitHubClients.laneFor`, the `LINEAR_API_KEY` service-key fallback, `KlipyGifs`' own key and `connectLaneStatuses`. A workspace's own app applies in every mode. `ConnectSettings.addListener` → `ProviderAppSettings.connectChoiceChanged()` notifies every provider listener, so a choice change drops cached GitHub clients and tokens like an own-app edit.

- Own app: the browser returns to `providerOAuthRedirectUri(origin, lane)` = `<origin>/oauth/<lane>/callback` with a single-use `state`. The origin is the configured public URL (or loopback), never a `Host` header; Settings shows the same string for registration.
- Connect: the browser returns to Connect, which shows an 8-character confirm code and a `control-center://oauth-done?login_id=…&code=…` link (`lib/core/deep_link/deep_link_handler.dart`). `oauth.complete` claims it with the code, this server's PKCE verifier and its signed install identity. A link the local client did not start is never completed.
- Attempts live 10 minutes; a wrong code comes back on the still-pending attempt as `code_error: code_mismatch` (never an exception), and the fifth fails it as `invalid_code`, kept until expiry so the client can show why; at most 256 are pending, since the own-app callback is unauthenticated. `linear_app` and `slack` are workspace lanes that need a workspace admin; `google` needs a workspace.
- `ProviderAppSettings` seeds each field once from the `.env`-merged environment (`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `LINEAR_CLIENT_ID`, `LINEAR_API_KEY`); later Settings edits win. `refuseExportedProviderSecrets` stops the boot (exit 78) when a provider secret or `SLACK_*SECRET*` is exported in the real process environment. `KLIPY_APP_KEY` is the operator's own key, used only while the server's own apps are active; otherwise Connect's Klipy lane or nothing. A workspace's own Klipy key wins, and `gif.search`/`gif.trending` (`catalog/gif_ops.dart`) are workspace-scoped for that.
- `GitHubManifestService` is **Create my GitHub App** (`github.manifest.begin`, server owner): a one-time `/oauth/github/manifest/start?ticket=` page (10 minutes, served once) auto-posts the manifest; `/oauth/github/manifest/callback` converts the code straight with GitHub (`POST /app-manifests/{code}/conversions`), checks the exact name (single-use nonce), that no permission exceeds the manifest's, and the owner, and stores all four fields. `github.install.begin` and `github.authorizeServer` need a workspace admin; `github.installations` lists installations with `bound_here` and `caller_is_admin`.

**Connect choice and install identity.** `ConnectSettings` stores `connect_mode` (`unset` behaves as `off`, `hosted`, `custom`, `off`), `connect_url`, the hosted epoch high-water mark, the last verified config and custom TOFU pins; `CC_CONNECT_URL` (`hosted`, `off` or a URL) locks it. `ConnectClient` signs every call (RFC 9421) with an Ed25519 key HKDF-derived per Connect origin from the 32-byte `connect_install_key` in `FileSecretsStore`, separate from device pairing. `install_id` is 26 Crockford base32 characters of SHA-256(SPKI). Hosted config must verify against `hostedConfigRootKeys` with a non-decreasing epoch; the list is empty until the offline key exists ([RELEASING.md](RELEASING.md#control-center-connect)), so hosted mode reports `hosted_unprovisioned`. A custom Connect pins its GitHub app/client ids, Google and Linear client ids and Slack ids on first use; a change pauses Connect lanes until `connect.confirmPins`. Config is cached 10 minutes and calls time out at 5 s; an outage serves the last good config as stale. A key-mode Klipy `app_key` is kept in memory only (the persisted config strips it), so after a restart key-mode GIF search waits for Connect. A choice or key change drops the cached config, the derived identity and every GitHub grant, whether made in Settings or by `cc_server connect` from another process (`ConnectSettings.noticeExternalChanges`, run before each config read). The seed is read and minted under one lock. An unusable `CC_CONNECT_URL` stops the boot and `cc_server connect` with exit 78 (`ConnectEnvironmentInvalid`); `choice()` never throws and reads it as off. `connect.*` ops and `cc_server connect` are server-owner only; `connect.rotateKey` mints a new seed and so invalidates every seal.

**Seals.** A Connect grant is a `credential_seal`, AEAD-bound to provider, Connect origin, `install_id`, workspace, account, app and secret generation. A stored `ProviderToken` keeps only the seal plus `seal_install_id` and `connect_origin`; access tokens live in process memory. Reconciliation is lazy: `ForgeCredentials` (through `currentSealInstallId`, null when Connect is off or the origin differs) and `ServerGoogleTokenManager` compare on every read and clear a mismatched credential, which then reads as "sign in again". Connect off or pointed elsewhere is not a mismatch: the seal is kept, unusable until the choice comes back, and a refresh in that state is `RefreshUnavailable`. There is no startup sweep, so a restored backup or rotated key surfaces on first use. `sealStandingOf` (`ConnectClient.sealStanding`: `usable`, `parked`, `dead`) is the one rule every sealed lane applies. Refreshes are single-flight per credential (`SingleFlight`; GitHub, Connect and Linear refresh tokens are single-use): the flight re-reads the stored credential before spending a refresh token, and writes or clears only while the stored grant is still the one it refreshed, so a sign-in or sign-out that landed meanwhile wins. Only `RefreshRejected` clears. Connect's `/refresh` always rotates (a handoff replay excepted); only a scope mint reuses a still-fresh parent. A rotated seal the server cannot write is served from memory and written on the next use, since Connect already spent its parent. Connect answers a wrong confirmation code `code_mismatch` and a provider refusal after a matching code `needs_sign_in`; every post-claim failure ends the attempt (`store_failed` when the grant could not be kept, and an unstored Slack install is revoked).

**ForgeCredentials** is the person side of `ForgeCredentialPort`. GitHub is person-only: a member's own App user token or `null`, with no App, server-owner, environment or pasted-PAT fallback; `setToken` refuses GitHub, a stored non-App GitHub grant is cleared on read, and `purgeLegacyTokens` deletes old per-workspace PATs at boot. GitLab and Bitbucket stay token-based: the person's pasted token, and for background work the server owner's pasted token, then `GITLAB_TOKEN`/`CI_JOB_TOKEN` or `BITBUCKET_API_TOKEN`/`BITBUCKET_TOKEN` with `BITBUCKET_EMAIL`.

#### GitHub clients

`GitHubClients` (`forge/github_clients.dart`) is the only way the server obtains an authenticated GitHub client. Never construct one around a stored token elsewhere.

- `asPerson` / `personHttp`: anything a person does (PR pages, reviews, approval, merge, publish), on their own token, read per request. Not signed in sends no credential and the caller asks the person to sign in.
- `mintScoped`: one repository linked to the workspace (`isLinkedRepo`; anything else is `access_denied`), scope `read`, `review`, `bot` or `write` (`GitHubTokenScope`). `forOwner` / `httpForOwner`: an automation client that picks each request's scope through `scopeForRequest` (GET `read`; `issues/…` and PR conversation — comments, reviews, reactions, labels, assignees, requested reviewers, opening a PR — `bot`; PR edits, merges, `contents`, `git`, `merges` and `stacks` `write`). Any other `/repos/{o}/{r}` write (statuses, checks, actions, settings) has no scope and is refused, never handed `write`. GraphQL and non-repository calls ride the accountable human's own token, so without an `actingUserId` only reads pass: `refuseUnscopedWrite` refuses GraphQL mutations and other writes there. A refused mint sends no credential.
- `laneFor`: the workspace's App (`GithubAuthMode.app`, fail-closed when incomplete) → the server's complete own App while own apps are active (`effectiveState`) → a partial own App means none → Connect when its config has a GitHub lane → none.
- Every mint, `read` included, is clamped by `clampGitHubScope` to the accountable human's own role on the repository (`pull` reads a private repo, `triage` a public one), so an installation token is never broader than what that person can see. Connect clamps every mint upstream (`/v1/github/scope`). `viaPerson` (human terminal rigs, IDE commit/push/fetch) downscopes the person's user token through `/applications/{client_id}/token/scoped` even on an own App. Every scoped answer (Connect, `/token/scoped`, installation tokens) must prove it covers exactly the one repository (`scopedTokenMatches`, `GitHubAppTokenMinter`); a wider one is revoked and refused.
- Links: a new or retargeted forge link through `repos.upsert` or `repos.addFromPath` needs a workspace admin (`catalog/repo_link_guard.dart`), then `verifyLink`, which refuses an owner or name that is not a GitHub segment (`.`, `..`, encoded or not, with or without a lane) and a GitHub repo the linking member cannot see with their own sign-in. `sweepLinks` runs three minutes after boot and then daily; a repo the accountable human lost access to is paused (no automation mint without an acting person) until a later sweep or a re-link sees it again.
- `accountableHuman`: `actingUserId` while still a member, else the workspace owner if a member, never an unrelated server owner. There is no creator/editor fallback.
- Grants are cached per (lane, workspace, human, owner, repo, scope) until 15 minutes before expiry, because GitHub caps live user tokens per user and app; the grant and repository-fact caches are size-bounded. `GitHubScopeRefused` is final.
- `refuseAutomatedApproval` blocks an `APPROVE` review on every automation client, wherever it sits in the request (top-level or nested GraphQL variables); approving rides `asPerson`.
- Minted tokens are cached per (lane, App id, workspace, human, repository, scope), so a rotated App never serves its predecessor's tokens; a definite refusal (not installed, suspended, not configured, bound elsewhere) is cached for a minute. `forgetPerson` (GitHub sign-out), `forgetMember` (membership removal or role change), `forgetAll` (own App or Connect changed) and `forgetWorkspace` (a workspace's own App saved, rotated or removed, or the workspace deleted) drop caches and revoke each cached token upstream by its kind: Connect children through Connect with the parent seal (Connect checks the seal is the same install and GitHub account the child was minted for), installation tokens with `DELETE /installation/token`, own-App user-token children with `DELETE /applications/{client_id}/token`. Disconnecting GitHub also revokes the whole Connect grant (`DELETE /applications/{client_id}/grant`) before the seal is deleted.
- `GitHubScopedCredentialBroker` implements `CredentialBrokerPort` on `mintScoped`: sandboxes get `GH_TOKEN`/`GITHUB_TOKEN` for exactly one repository. `ForgeTokenScope.read` is `read` (pipeline shell steps, clones, enclosures); `ForgeTokenScope.review` is `review` clamped to `read` when the human cannot push (agent sandboxes); `write` only from the gateway and person rigs; notes name the lane.

Pipelines carry their requester explicitly. `PipelineEnginePort.start(requestedByUserId)` records it under `kPipelineRequestedByKey` (`requested_by_user_id`) in the trigger payload; a payload that names someone is stripped, a sub-pipeline inherits its parent's, and null (schedule, webhook) leaves the workspace's accountable human. `pipeline.bashScript` runs in the OS sandbox and fails closed without one, with the data directory and `.env` denied, `IsolatedGit.isolationEnvironment` plus a temporary `GH_CONFIG_DIR`, and a one-repository `read` token only when `repo_full_name` names a linked repo. Each placeholder value is escaped for the quoting it sits in (unquoted, `'…'`, `"…"`, command substitution), so a trigger payload is one literal word wherever the author put it. Creating or editing a template with a shell step needs a workspace admin, and so does creating or editing a trigger that points at one (`pipeline_trigger.insert`/`update`). Arming a trigger (enabled on an event, schedule or webhook) on a template with any step outside `kMemberArmableBodyKeys` also needs an admin, and so does adding such a step behind an armed trigger. The server mints webhook tokens and decides `isBuiltIn`. Only the engine writes run and step rows: it mints run ids as UUIDs, pins each run to the template graph it started with (`PipelineRun.templateSnapshot`, which resume, retry and step bodies read through `PipelineContext.definition`/`step`), and validates `pipeline.start` parent links. An event without `workspace_id` starts no trigger. Rules and enforcement: [SECURITY.md](SECURITY.md#pipeline-triggers-and-runs).

The PR conversation bridge (`pr_review/github_pr_conversation_bridge.dart`) gates each comment in order: loop guard (bots and replies carrying the attribution prefix) → author matched by numeric GitHub account id to a writing member who signed in, else ignored silently → `canPostAs` (a `bot` token bounded by that member) → claim with the author's own 👀 (`201` claimed, `200` another server already did) → work. The `ai-review` label (`kGithubPrReviewLabel`) runs the same gate on the latest labeller and claims with their 👀 on the PR. Every reply starts `**Control Center** (for @login): `, in every lane. Mentions are `@usectrl` plus the App's bot login and slug. Candidates come from one GraphQL search per accountable human, regrouped by repository owner (a lane with nothing to look for sends no filler search). `GitHubLoginDirectory` is invalidated by GitHub sign-in and disconnect (`ForgeCredentials.changes`) and by member added, removed or role changed; a comment whose author maps to nobody yet is offered again up to three sweeps before it stays seen. `PrConversationPollingService` sweeps an own App every 60 s over at most 25 PRs and a Connect lane every 120 s over at most 10; `GitHubRateBudget` skips a workspace under 15% remaining.

**Linear.** `LinearClients` separates `personAuthorization` (Bearer of the member's `linear` sign-in) from `appAuthorization` (the workspace's `linear_app` actor, `actor=app`, stored as `workspace_linear_app_<workspaceId>`; else the server's `LINEAR_API_KEY` service key, sent raw; else null). In a workspace on its own Linear app, person grants live in a workspace slot (`workspace_ticket_linear:<workspaceId>:<userId>`, `UserCredentialsStore.ticketKey(workspaceId:)`) instead of the global `user_ticket_linear_<userId>`, the service key is the workspace's own (never the server's), and a grant whose `appId` is not the workspace's client id is cleared on read. Connect never holds Linear secrets: it returns a `LinearCodeGrant` and the server runs the exchange. `refreshAging()` is a daily sweep renewing grants older than 20 days (Linear refresh tokens expire after 30); refreshes are single-flight because Linear rotates refresh tokens.

**Google Calendar.** Accounts are per member per workspace (`google:<workspaceId>:<userId>:<email>`), credentials `google_<accountId>` in `secrets.json`. A sealed token keeps only its seal on disk; an own-app token keeps access and refresh tokens and is dropped when its app id no longer matches the configured own client: the workspace's own client when it has one (where a sealed Connect token is dropped too), else the server's.

**Workspace provider apps.** `WorkspaceProviderAppSettings` (`identity/workspace_provider_app_settings.dart`) holds a workspace's own Google, Linear and Klipy app in `FileSecretsStore` (`workspace_provider_app_<provider>_<workspaceId>_<field>`, with an explicit `mode` marker); clients get presence flags only. `inherit` (the default) uses the server's lane; `own` uses only the workspace's app, and an incomplete one throws `WorkspaceAppIncomplete` (sign-in `SignInMisconfigured`, GIF ops `ValidationException`) rather than fall back. `workspaceProviderApps.list|setMode|save` (`catalog/workspace_provider_app_ops.dart`) need a workspace admin; `setMode(inherit)` deletes the fields. A change of identity (mode, client id, Klipy key) fires listeners wired in `runtime/server_provider_app_wiring.dart`: Google revalidates the workspace's tokens, Linear deletes and revokes the workspace's app and slot grants. Workspace deletion removes these keys, the Linear slot grants and the workspace's Google credentials through `WorkspaceGitHubAppSettings.deleteForWorkspace`.

**Embedded Connect.** `CC_SERVER_CONNECT_HOST=on` makes `buildEmbeddedConnect` (`apps/cc_server/lib/embedded_connect_host.dart`) mount the same `ConnectService` the image runs at `/connect`. Only `CONNECT_*` variables reach it, so it cannot borrow the server's own apps. `CONNECT_PUBLIC_URL` defaults to the public URL's HTTP origin plus `/connect`, must be HTTPS or loopback (checked once, by `ConnectServiceConfig`), and its path must be exactly `/connect`; `CONNECT_ALLOWED_INSTALLS` is required. It is routed after the `/oauth/*` handlers and before SAML, outside session and CORS middleware, is absent in demo mode, and a misconfigured mount fails the boot.

### Agent run gateway

Agents carry no permission flags: what a run may push, open, publish, write to a tracker or reach is action policy (`ActionClass` rules), the same for every adapter. `AgentRunGateway` (`packages/cc_infra/lib/src/dispatch/agent_run_gateway.dart`) is how that policy reaches code running inside an agent's sandbox. `cc_server_runtime.dart` constructs it over the action guard and credential broker and mounts it on the MCP surface's `/agent/` routes (`McpRequestHandler.agentRoutes`), so it rides the loopback port agents already dial for MCP.

- Dispatch mints the run a `ForgeTokenScope.review` token (one repository, `review` scope: contents read, pull requests write, clamped to `read` when the accountable human cannot push; it cannot push; see [GitHub clients](#github-clients)) and opens a gateway lease. The lease's `GIT_CONFIG_*` entries set `url.<gateway>/agent/git/github.com/.pushInsteadOf` for conventional HTTPS/SSH origins. Fetches do not use the gateway: when the run holds a forge token, the lease also rewrites its own repo to HTTPS and adds a credential helper limited to that repo's path, since a sandbox has no SSH credentials. The repo-specific rewrite outranks a user's global `https://github.com/` to SSH rewrite, and `pushInsteadOf` still takes pushes to the gateway. Explicit credential-bearing URLs or altered Git configuration can bypass these prefixes, so shell preflight independently checks every recognized push. The gateway inspects ref updates, including compressed requests, asks `gitPush` with those refs, checks that the target is the worktree's repo or a linked GitHub repo, then forwards on a server-held `write` token. Invalid or incomplete preambles are rejected. A policy refusal is a `report-status` `ng`, shown by git as `! [remote rejected] <ref> (Control Center policy: …)`.
- Uninspectable push preambles return HTTP `400` without approval, credential minting or upstream forwarding. Drain the remaining upload before replying; cancelling the request stream can reset the connection before the rejection reaches git.
- A policy deny during ref discovery is audited before returning `403`, just like a deny after the refs arrive. Unprompted guard denials publish `AgentActionBlocked` to the workspace-filtered live notifications and durable bell feed; answered approvals do not generate a second block notification. The “Agent needs attention” preference controls these notices. A block still notifies while its space is open because, unlike a pending approval, it has no inline approval card.
- Signed commits: when the user's global config signs with SSH (`gpg.format=ssh`), the macOS sandbox wrapper installs `cc-ssh-sign` next to its keychain stand-in (same exec allow and write deny). It points git's `gpg.ssh.program` at the shim with one more command-scope `GIT_CONFIG_*` entry, after the lease's entries; no config file is written. Only `-Y sign` is rerouted: the shim posts the object to `/agent/git-sign` with the lease's `CC_AGENT_GATEWAY` and secret, and `HostCommitSigner` signs it on the host (checks in [SECURITY.md](SECURITY.md#agent-run-gateway)). Every other call (`verify`, `find-principals`) execs the user's own program (`CC_GIT_SSH_PROGRAM`). Without SSH signing, git's config is untouched. Dispatch resolves the run's Git identity before opening the lease, so the grant carries the committer email. Linux bwrap and unsandboxed runs keep the user's signer.
- Claude Code's `--settings` installs a command PreToolUse hook on `AgentRunGateway.guardedClaudeTools` (`Bash` and Claude Code's own file-write and web tools; reading tools have no rule, because the sandbox decides what they can see). A run with no lease keeps a blocking hook on `Bash` only. The hook posts to `/agent/hooks/pre-tool-use` through curl and exits 2 unless the gateway explicitly allows the action. Writes outside the run's worktree and runner state directories are classified by their target, and the request body is capped at 32 MiB so a large `Write` is still inspected. Missing leases and transport failures block, rather than silently skipping approval. `ShellActionClassifier` (`cc_domain/features/guardrails/domain/services/`) is shared with the built-in harness: push, deletion, commit, PR create/publish, tracker writes, package installation and recognized network calls all meet their action rules before the shell starts. Conventional wrappers and compound commands are inspected, not arbitrary generated code. A shell approval answers the gateway's ref `ask` for the same run within `AgentRunGateway.shellPushApprovalWindow`, limited to the branches it named (see [SECURITY.md](SECURITY.md)); denies still apply. Updated hooks take effect on new runs after the server is restarted.
- Every runtime composes the space's autonomy after policy resolution: the harness gate, Claude Code's hook and pushes through `AgentRunGateway` (the grant resolves autonomy per check), ACP `session/request_permission`, and environment commands all pass it to `ActionGuardService.check`. `proposeOnly` refuses gated actions policy would allow (`kProposeOnlyReason`); `actFreely` never overrides an action-policy `prompt` or `deny`, and pinned output tools are still checked. A required approval without a connected approver denies and records the applied outcome. An asker that stops waiting (hook timeout, lease close, run cancel) withdraws its prompt through `ConfirmationRequest.withdrawn`, which resolves the pending card as a deny.
- ACP agents run only inside `SandboxPort`; with no sandbox manager the run fails closed. Agent requests are answered by the dispatch session: `fs/read_text_file` and chat-mode `fs/write_text_file` stay inside the run's roots, permission requests go through the guard, anything else is `methodNotFound`; responses complete only ids the client sent.
- Warm sandbox handles are reused only while the resolved `SandboxSpec` is unchanged; a posture change destroys the old session and launches a fresh one. Server shutdown stops every live dispatch (children killed, credentials released) and destroys sandbox sessions before the databases close. A run's terminal state goes through one `_finish` (run-log close, `DoneEvent`, completion); a user stop records `RunStatus.error` with `Stopped by user`, and a later exit code cannot overwrite an abort's error.
- Approval prompts describe the agent's intent and the consequences of accepting or declining, rather than displaying policy codes. `ActionApprovalCopy` uses supplied target metadata and conservatively parsed literal shell targets; unspecified destinations stay explicitly unspecified. Shell source travels separately in `ConfirmationRequest.command`, never in the heading. Desktop/web and phone approval surfaces scroll the complete explanation and LTR Bash code, copy source verbatim, and keep decisions visible. Inline conversation queues expose one request at a time with a waiting count; advancing to another request resets its scroll position.
- Every Claude Code launch passes empty `attribution.commit` and `attribution.pr` values through `--settings`, preserving action hooks while disabling Claude's own commit/PR bylines above account and project settings. The shared Git attribution policy reaches the parent and native subagents (`--append-subagent-system-prompt` on supported binaries, Claude Code 2.1.205+), plus harness and ACP prompts.
- Agent commit identity comes from `resolveAgentCommitIdentity` and the gateway rejects pushes that break it (`PushedCommitInspector`): the server owner's own run commits as the owner and may be signed; another member's run is authored by that member (their GitHub noreply address, else their workspace Git identity) and committed by Control Center, unsigned; a run nobody requested is Control Center throughout. When enabled, attribution adds `Co-Authored-By: Control Center <hi@usectrl.dev>` (`@usectrl`), never replaces the human. The `agent_commit_attribution` user preference defaults on; a workspace `true`/`false` override wins, while an absent override inherits each user's choice. Settings → You → Commit attribution shows the effective value and locks the personal toggle while the workspace overrides it; admins configure the override in Workspace → General. Opting out omits agent credit. Changes apply on the next run and invalidate Claude native-session reuse. Caller and adapter environment settings cannot replace the resolved attribution; a requested run whose member has no resolvable identity, or a resolution failure, terminates the run and releases its credentials. Forge credentials remain broker-owned. Only the owner's own runs may sign; every other lease gets commit, tag and push signing switched off. Identity alone does not guarantee a verified signature.
- Every local process sandbox spec (dispatch CLI transports, harness shell tools, pipeline shell steps, the native adapter's config) is built by `processSandboxSpec` / `processSandboxConfig` in `cc_infra/lib/src/sandboxing/process_sandbox.dart`, with every security input required; a structural test refuses another `SandboxSpec(` in `cc_infra/lib`. A dispatch resolves its network posture, Git identity/co-author credit and environment access once into an immutable `_RunContext` before any transport starts.
- `networkEgress` is resolved once at run start into `SandboxSpec.networkEnabled`: deny turns the sandbox network off, allow/ask leave it on (the harness web tools still ask per call). GitHub domains are always on the egress allowlist while the network is on. No ticketing key enters a sandbox; agents write tickets through MCP tools gated by `vendorSyncWrite`.
- Teardown closes the lease and releases its broker handles. `GitHubScopedCredentialBroker` tokens are shared per accountable human and repository (see [GitHub clients](#github-clients)), so release only forgets the handle; sign-out and member removal revoke. A refused mint leaves the environment without a token and says why in the launch notes; there is no fallback credential.
- Rigs fix the scope at open (`RigSpec.forgeTokenScope`): a human-opened terminal rig gets `write` as the member's own sign-in narrowed to the repository (`personal` mint, `viaPerson`), so its pushes are theirs; an agent-opened rig gets `read`, because a guest credential helper cannot tell a push from a fetch. The terminal's repository is the worktree's `origin` only when that names a GitHub repo linked to the workspace; otherwise the rig gets no GitHub credential.

### Disposable worktree permissions

`SandboxExecGrantService` grants execution inside server-provisioned conversation overlays and shared worktrees without a startup question or a stored allow row per conversation. Dispatch derives the managed space root from the provisioner layout and excludes roots overlapping protected source checkouts. Claude Code and the builtin harness use the same resolver; the harness resolves these server-owned roots per command, never a model-supplied `cwd`.

Stored decisions still take precedence. An explicit denied descendant withholds an implicit parent grant rather than reopening the denied subtree. Read-only mounts, original checkouts and unmanaged/fallback directories are not implicitly granted; genuine unmanaged grants keep their approval flow. Changing working directories cannot widen execution authority.


## Persistence

`cc_persistence` is pure Dart over `package:sqlite3`, without Flutter/path_provider. Only the server opens databases:

- `<dataDir>/global.db`: workspace registry, identity/preferences/devices, per-user newsfeed, fleet queue, routing and server policy/settings. The pinned global-table set is in `workspace_isolation_ratchet_test.dart`; additions require an isolation justification.
- `<dataDir>/<workspaceId>/workspace.db`: all workspace-owned data, including repos. `workspaceDatabasePath` defines the path; associated artifacts share this directory.
- `WorkspaceDatabaseManager.of(workspaceId)` synchronously returns a lazy database; disk opens on first query. Hold the manager, not a resolved DAO. `quick_check` runs on first workspace touch, not boot.
- `CrossWorkspaceQueries` is the only fan-out mechanism (`fanOut`, `fanOutKeyed`, `forEachWorkspace`, `mergeStreams`, `topN`). Its callers explain `CROSS-WORKSPACE BY DESIGN`.
- `workspace_routes` resolves pre-auth opaque IDs/secrets. Write the entity before its route; a route miss is not-found, never a workspace scan.
- The same checkout in two workspaces has two repo IDs. Cross-workspace repo identity is its path (`findByPath`), not its ID. Ordering/link time are `repos.position`/`linkedAt`.

### Stored files and composer uploads

- `catalog_files` lives in each workspace database. It records logical file IDs, workspace/uploader/creator identity, original name, media type, byte count, storage reference, source, lifecycle state and timestamps. Uploads and server-managed artifacts are cataloged; repository files and disposable PR image caches are not.
- Dropping, pasting or picking a local composer attachment starts its upload immediately through the encrypted resource facade's `POST /blob`. The URI-encoded `x-cc-file-name` header preserves the original name. The server returns `file_id` only after both bytes and catalog metadata are durable. Files are bounded to 24 MiB; failures remain visible with retry/remove controls, and sending waits for every upload to be ready.
- Sending, steering and provisioning queues reuse `fileId` plus the existing `blob:sha256:…` reference, never a client-local path or another upload. Repository-file mentions remain server-side references. The server validates workspace, uploader and blob identity before promoting an upload from `draft` to `attached`.
- Each upload has a separate logical ID even when identical bytes share one workspace-local blob. `files.discard` is uploader-only and rejects attached files. Removal leaves a `discarded` tombstone and reclaims bytes only when no active catalog entry or message needs them; pre-catalog bytes are conservatively retained. There is no age-based draft expiry: a provisioning queue may still need an upload.
- Generated blobs, workspace logos, meeting audio and review snapshots retain their existing storage locations and are recorded as artifacts. The v20 migration backfills old message attachments; a one-time, background `CrossWorkspaceQueries` inventory covers historical artifacts without pinning every workspace database. Cache eviction protects cataloged files and waits for successful historical inventory.


### Schema changes

1. Put each table in exactly one database, defaulting to `WorkspaceDatabase`. DAOs extend the matching `DatabaseAccessor` and cannot declare the other database's tables. Override `tableName` with plain snake_case.
2. Read current schema versions from source. Both databases have squashed baselines; append `MigrationStep(from, to, migrate)` and bump the owning database version. Do not support pre-baseline files by silently opening them.
3. Update fresh-schema expectations in `workspace_baseline_schema_test.dart`. Regenerate Drift/JSON output with the root build_runner command in [AGENTS.md](AGENTS.md#build-and-verification).
4. FTS/vector virtual tables, external-content FTS triggers and sync-feed triggers are idempotently installed in `beforeOpen`. Partial-index changes must cover installed databases: `_createPipelineIndexes` runs only in `onCreate`, so migrations changing its predicates must explicitly drop/recreate those indexes.

`workspaceId` columns support sync/FTS/self-identification; separate files provide isolation. Vectors use sqlite_vector FLOAT32/384 dimensions with FTS-only degradation when the embedding model is unavailable, not when a required native is missing.

### Backup and restore

Snapshots are `backups/<ts>/{manifest.json,global.db,<workspaceId>/workspace.db}`, written using `VACUUM INTO`. `server.listBackups` includes incomplete snapshots and marks them incomplete. `workspace.export/import` operate on a single workspace file; restoring one from a snapshot uses the same import. Whole-install restore is a stopped-server copy-back, not another RPC operation.

The install owner can remove a listed snapshot (including incomplete ones) by
its timestamp name via `server.deleteBackup`; the server refuses paths and
symlinked directories. Built-in **Workspace backup** pipelines instead write
`backups/workspace-backups/<workspaceId>/<ts>/workspace.db` for the current
workspace only. An enabled weekly schedule runs once on recovery after missed
cron slots, then prunes only that workspace's backups older than 30 days by
default; it never prunes install snapshots or other workspaces.
`workspace.listBackups` lists them per workspace for workspace admins, separate
from `server.listBackups`; restoring one uses `workspace.import` and
`workspace.deleteBackup` (workspace owner) removes one by timestamp name. A deleted
workspace fails every workspace-scoped gate and its schedule stops, so its backups
are never pruned: `server.listOrphanedBackups` and `server.deleteOrphanedBackup`
give them to the install owner, and the delete refuses a live workspace.

RPC paths name files on the server. Remote byte transfer uses signed requests inside the authenticated encrypted resource tunnel:

| Route | Authorization and lifecycle |
| --- | --- |
| `GET /backup/workspace` | Workspace admin; stream export, delete server copy |
| `GET /backup/snapshot` | Install owner; ZIP to a temporary file rather than buffering the installation |
| `GET /backup/stored` | Workspace admin, or install owner once the workspace is deleted; stream a scheduled backup and keep it, since the stored file is the backup |
| `POST /backup/restore` | Workspace owner; stream to staging, adopt, delete staging on success or refusal |

HTTP handlers enforce their own roles behind the private resource gateway; the public versions of these routes return `426`. Downloads use `no-store` and `Accept-Ranges: none`: every request creates a fresh export. Backups are absent in demo mode and work through direct or relay sessions without a separate remote HTTP origin. Transfer progress is throttled to 100 ms with a final byte count; upload progress means bytes handed to the tunnel, while the response confirms completion. Reconnect cancels an in-flight transfer rather than replaying a restore.

## Harness and indexing

### Claude Code checklists

With a Control Center MCP config, `ClaudeCliBackend` appends explicit `todo_read`/`todo_write` instructions for multi-step work, including tool discovery, recovery after compaction and live status updates. Native `TodoWrite`, `TaskCreate`, `TaskUpdate`, `TaskGet` and `TaskList` are disabled with `--disallowedTools`: their private lists do not populate the conversation's checklist. Subagent execution tools remain available.

Without an MCP config, the launcher leaves Claude's native tool surface unchanged and adds no Control Center checklist instruction. The appended prompt and native-tool restrictions are part of the resume-policy fingerprint, so sessions created under the old policy start fresh rather than retain stale instructions.

### Native Claude sessions and accounting

Managed Claude Code accounts sign in through account-scoped `claude auth login`; creating an account opens those command instructions directly. Settings supports CLI login only, not pasted long-lived setup tokens. Old `.cc-long-lived-token.json` files are ignored; token-only accounts need a normal sign-in. Account rotation and CLI credential refresh continue to use each account's own config directory. On macOS every sandboxed process finds `MacosSandbox.keychainStandIn` first on `PATH`: the profile denies the login keychain, the real `security` takes up to ~3 s to fail there, and Claude Code treats a write timeout (2 s) as transient and skips its `.credentials.json` fallback, dropping a refresh the server already rotated. The stand-in answers login-keychain password calls at once, passes everything else to `/usr/bin/security`, and is write-denied in every profile.

Subscription token renewal is owned by Claude Code, not Control Center. The network-enabled sandbox baseline allows the exact `platform.claude.com` host for OAuth exchange, refresh and revocation, alongside the Anthropic API domains. An expired access token with a usable refresh token stays eligible for a run; network-off sessions still block renewal.

`ClaudeNativeSessionStore` scopes explicit session IDs by workspace, agent, conversation, account/config directory, cwd and branch/fork policy. Resume also requires a matching standing-instruction/policy revision. Only a successful terminal result followed by normal process exit advances the delivered-context cursor; interrupted or failed turns must not suppress undelivered messages. Fresh launches receive complete context; resumed launches receive the new request and changed, authorized context entries. Ordinary idle gaps do not require keeping a CLI process alive.

`ClaudeControlSession` speaks Claude Code's stream-json control protocol: `control_request` / `control_response` frames matched by `request_id`. Three things depend on it.

- **Usage.** `ClaudeCliUsageProbe` starts the CLI, sends `get_usage` and exits. Control Center never reads a Claude OAuth token and never calls Anthropic's usage endpoint; the CLI does that with its own login (see [SECURITY.md](SECURITY.md)). Named accounts are cached for five minutes. `rate_limit_event` frames in a running turn update the same cache through `ClaudeUsageCache.observe`.
- **MCP.** On a CLI past `ClaudeCliCapabilities._controlProtocolFloor`, the Control Center server goes over stdin with `mcp_set_servers` and `--strict-mcp-config`, and the first prompt is held until the answer arrives (90 s). A failed server still lets the turn run. An older CLI gets the `<cwd>/.mcp.json` file as before.
- **Stopping.** A manual stop sends `interrupt` and allows 3 s for the turn's `result`, so its spend is recorded, then signals the child. A turn that has not reported `init` is signalled straight away.

A `rate_limit_event` with a blocked status marks the account exhausted once per crossing, with the exact reset time. Extra usage keeps the account in rotation. The report outranks the wording of the failure, so an unfamiliar message still fails over. Warnings are debug events.

`superviseProcessGroup` on `SandboxSpec` runs the CLI in its own process group under a small `/bin/sh` watcher that holds a pipe to the server. When the pipe closes, including on a server crash, the watcher sends TERM and then KILL to the group, so MCP grandchildren die too. The native macOS and no-sandbox adapters honour it. Bubblewrap and Windows do not use it.

Compaction has two settings, stored per server in `claude_session_settings.json` (`ClaudeSessionSettingsStore`) and set from the Claude Code runner's detail pane. `autoCompactWindow` passes through `--settings` (100,000 to 1,000,000 tokens; unset leaves Claude Code's default). Idle compaction is off by default. When it is on, `ClaudeIdleCompactor` waits on a session above `ClaudeSessionSettings.minIdleCompactTokens` until two minutes before its prompt cache expires, then runs `/compact` through the ordinary dispatch path: the compaction only hits the cache with the same tools and system prompt, and it is real spend the run log has to show. The cache lifetime comes from the turn's `usage.cache_creation` tier. A compaction resumes the session or does nothing, never fails over, never parks for sign-in, reports failures as debug events and leaves the delivered-context cursor alone, because it delivered nothing. Timers live in memory, so a restart only loses the saving.

Manual stops record `Terminated by user request` before signalling the child. `DispatchSession.terminate()` owns terminal completion and the run-log stop reason; the Claude runner checks cancellation before classifying its exit or retrying another account. Late sandbox output cannot replace that reason or leak raw stream-json into the transcript. An unsolicited signal exit (including `-15`) remains a process failure.

Pass configured effort through the actual launch builder, constrained by the selected model and detected CLI capabilities. Preserve strict MCP configuration and action-policy hooks; do not use `--bare` to bypass them. Parse `system/init` for the observed session, model, CLI version, tools and MCP status. Discovery caching remains opt-in and requires a stable authorized catalog/configuration; it does not replace Claude's native tool discovery.

`ClaudeSubagentRuns` closes foreground children on their spawn-call results and background children on `task_updated` / `task_notification`. An `async_launched` result only acknowledges scheduling; it must not finish the child. Task/run IDs keep resumed-task notifications attached to the correct spawn, terminal runs cannot reopen on late transcript messages, and parent teardown drains pending child completion writes.

The space's Agents sidebar keeps each agent's current main run and only active subagent rows. Completed, failed and stopped children disappear immediately; still-active descendants remain under the nearest visible ancestor. Filtering applies only to the display tree, not the raw run-log stream or recorded transcripts, so activity tabs and transcript links retain completed history.

Claude's main-loop `usage` is per-turn; `total_cost_usd` and per-model whole-tree counters are cumulative. Delta those counters against the correct restorable baseline, without attributing an earlier dispatch's spend to its successor. Missing model counters retain observed main-loop usage and reconcile it once when full counters return. Counter resets, account switches and forks establish new baselines without erasing this dispatch's totals. Subscription figures are API-equivalent consumption, not invoices.

Runner settings report Claude credential expiry independently of `loggedIn`: the CLI can still report a present credential after its access token expires. Each expired account shows a **Sign-in expired** warning badge. Any expired managed account also gives the installed Claude Code runner a warning dot and status tag, including when that account is not the default. Checking/missing CLI states retain precedence. These warnings do not disable dispatch or change Claude's next-run refresh behavior; refreshed account data clears them once the credential is current.

`RepoSkillCatalog` is the shared scan-gated discovery for projection and `skills.repoSkills`. `ActiveRepoTracker` observes paths at `DispatchSession.addEvent`: a write under `repos/<name>/` switches the active repo; reads only seed an unset repo. Only that repo's skills are prompt-resident.

### Skill evaluation campaigns

`SkillEvaluationService` owns revision-specific campaigns under `evals.*`; `DaoEvalsRepository` persists campaigns, attempts and opt-in policies in the owning workspace database. The server captures scan-gated, content-addressed skill packages and pins the corpus, adapter, provider/native model identifier, protocol, tool schemas and ambient inventory. Native Claude campaigns also pin the managed account and observed CLI version. Clients only select settings, observe snapshots and request actions.

`ControlledSkillEvaluation` reuses the paired evaluation engine with fresh fixtures, context and home directories. Supported executors are the built-in harness with enclosed file/process tools and native Claude Code with built-in tools disabled and an authenticated MCP bridge into that same enclosure. Executor choice is explicit; neither path falls back to the other or to fleet jobs. Claude Code and Codex OAuth use an API-equivalent usage stopping threshold that may be exceeded by one in-flight call; API-key providers retain conservative reservations. Unknown usage stops further calls. Absent, previous-revision, forced-load diagnostic and pinned-composition comparisons remain distinct. The local corpora are authored pilot cases, not imported public benchmark scores.

Campaign progress and bounded attempt evidence survive reconnects. Cancellation stops future attempts and active guest processes; restart marks unfinished campaigns interrupted rather than inventing results or known spend. `SkillUpdated` and periodic, authorized repository revision reconciliation mark historical evidence stale. Paid reruns require an explicitly enabled, revision-bound policy; changing or disabling that policy invalidates older queued admissions.

Reports retain every attempted outcome in the primary denominator, cluster repeated trials by task, and withhold recommendations when coverage, identity or cost is insufficient. Direct body/reference/script observations are not proof that a model followed the skill. Synthetic safety artifacts are separate from observed policy denials and are not evidence of real exfiltration.

Skills settings and Observability → Quality share typed campaign clients. This service is separate from the generic suite executor contract; adding skill campaigns does not supply an executor for arbitrary existing evaluation suites. See the [evaluation protocol](https://usectrl.dev/manual/concepts/evals-and-quality/) and [SECURITY.md](SECURITY.md#controlled-skill-evaluation) for containment limits.

### Deferred tool loading

- Keep external MCP `tools/list` complete. Only in-process harness schemas are deferred; tools remain callable from turn one, activating and executing in the same step.
- `HarnessToolSearchTool` uses BM25. Compatible Anthropic requests send the stable admitted catalog with `defer_loading` and search results with replayable `tool_reference` blocks. Other providers retain append-only schema activation after resident tools. A fixed resident-tool breakpoint alone does **not** preserve downstream system/history caches when an ordinary tool catalog changes.
- Apply deferral after `ToolSurfaceSpec` filtering. Activation cannot add disallowed tools or bypass approval/action guards.
- Dispatch and `ContextInspectionService` share `materializeHarnessToolSurface`. Residency comes from `ModeToolPolicy` through `ModeCapabilityProfile.toToolResidencySpec()`; reserve it for tools used in most runs.
- `test/tooling/resident_tool_names_test.dart` checks real names and the under-40 budget. `--tool-deferral=off` / `CC_SERVER_TOOL_DEFERRAL` makes every admitted tool resident.

### Prompt caching

Keep sent prefixes byte-identical where possible. `pruneToolResults` batches rewrites at `CompactionConfig.pruneThresholdTokens` (default 2000); compaction forces pruning because it already rewrites history. Opt-in stale-observation masking also accounts for provider/cache prices, rewritten-prefix size and expected remaining calls. It protects active edit targets, unresolved diagnostics and non-recoverable evidence. Calibrate prompt estimates against observed provider usage rather than treating the character heuristic as an exact tokenizer.

Anthropic uses four cache breakpoints: last resident tool and last system block with a one-hour TTL; previous and current request tails with short TTLs. The rolling pair (`cacheAnchorIndex`) survives wide parallel tool turns. `_subagentPilots` releases same-shape siblings on the first child's first event with a bounded wait, allowing its cache write to become readable. Subagent resident sets are profile-independent; model/effort differences fragment the prefix. `McpToolBridge` caches deterministic stripped schemas with stable key order.

Measure `cacheRead / (input + cacheRead + cacheWrite)` in `observability_metrics.dart`; cache writes belong in the denominator.

### Context, tool execution and measurement

Context meters, flyouts and explorer tabs carry the selected conversation ID explicitly, never resolving the space's standing conversation as a substitute. Token subscriptions and Claude Code history inspection use that ID; `context.inspect` requires workspace, space, conversation and agent IDs and validates conversation ownership before reading context. Explorer tab identity and persisted arguments include the conversation, so sibling conversations cannot share a breakdown. The meter prefers that conversation's latest provider-reported reading and otherwise shows an estimate.

Compaction input retains bounded, attributed evidence: original requirements, system steering, tool arguments/results, exact active edit anchors, verification outcomes and references to recoverable observations. Tool-output storage is workspace-authorized; ranged `read_output` retrieves bounded slices without injecting the full original into every request. Format search/file/build observations at their tool boundary, never by globally rewriting machine-consumed shell stdout.

Independent parallel-safe regions use a bounded rolling scheduler: a completed call releases its slot immediately, UI completion events stream as tools finish, and model-facing results retain deterministic order. Mutations, approvals, dependencies and relevant hooks remain barriers. Fully parsed, authorized read-only execution may overlap generation only under the explicit experiment; cancellation and retry rules prevent duplicate or late work.

Text compaction is the default. Snapshot/image compaction is opt-in, requires vision, checks page/source/image/context limits including reserved output, and retains source text for repeated folds and later text fallback. Source containing non-ASCII glyphs, tabs or control codes is refused before rendering because the fixed font would normalize or lose it; the host takes the text path instead. Local rendering/fit checks do not establish model OCR fidelity or end-to-end savings.

### Agent loop contract

- Every exit of `AgentLoopRunner.run` goes through one `finish(reason)`: it saves the transcript (only at a clean boundary, never after an unanswered `tool_use`), emits one `LoopError` for a failure, then exactly one `LoopDone`. A host maps `LoopError`/`LoopDone(error)` to a non-zero exit; a turn timeout is a failure (`turn_timeout`), not a notice.
- Every history rewrite (fold, rewind) runs `onHistoryRewritten`: checkpoints are remapped or dropped, the cache anchor and native tool catalog reset, and a fold force-prunes tool results. A rewind to an unknown checkpoint label fails the call and changes nothing.
- `LoopCompaction.summarized` means a model wrote the summary. A structural digest still folds (`messagesFolded > 0`) and counts as a compaction, but never reports `summarized`.
- Provider failures carry a typed `LlmError.kind` (`LlmErrorKind.classify` is the only place phrasing is read; providers pass the HTTP status). Overflow recovery, retries and `FallbackProvider` rotation read the kind, so a TPM rate limit is never treated as a context overflow. Overflow recovery is bounded per turn; truncation continuation per consecutive streak.
- An attempt abandoned after it streamed (retry, stream-rule restart, overflow recovery) emits `LoopTurnDiscarded`; hosts emit `TextRetractedEvent` and `TranscriptFolder` trims exactly that text/thinking from the tail.
- Deferred-tool support is `LlmProviderPort.supportsDeferredTools` (default false). Leaf providers `extend` the port; decorators `implement` it so the compiler forces them to forward.
- Subagents inherit the parent's tool hooks (`NestedRunHooks`: pre/post-tool forward, session start does not re-fire), a fresh advisor copy and a non-consuming steering view (`SteeringQueue.nestedView`); follow-ups and the parent's completion contract stay with the parent. `harness_run_factory.dart` owns the compactor stack and the loop-event → transcript-event mapping shared by the session, subagent and evaluation hosts.
- `ShellAgentLoopHooks` drains hook stdio; the pre-tool hook fails closed (non-zero exit, spawn failure or timeout denies), session-start and post-tool hooks are best-effort.

`HarnessRunAccounting` observes physical provider attempts, including main, compaction, advisor, side-request, subagent and failed/retried work. Attribute child usage to the child's own row and roll its cost into ancestor budgets once. Flush call records and atomic own/child cost updates before terminal completion. Store micro-USD; round only for presentation. Missing usage/pricing is unknown spend, not zero-cost work. Reasoning tokens are a subset of output unless a provider explicitly reports disjoint axes.

Latency stages distinguish dispatch/context readiness, runtime/MCP readiness, physical request send, first HTTP response-body byte, first model event, useful text/action, auxiliary work and verified completion. Provider intervals require matching request/attempt identity and provider/transport provenance. CLI stdout and `system/init` are startup observations, not HTTP TTFB.

`packages/cc_infra/bin/cc_eval.dart` runs pinned paired campaigns, independent behavioral verification, artifact replay and reports. The canonical corpus distinguishes synthetic smoke tasks from pinned real Control Center source tasks. Plans cover masking, snapshots, effort/routing, native resume, MCP discovery and read-only overlap; unsupported/no-op interventions are refused before spend. Repeated trials of one task do not substitute for independent task pairs. Keep the quality default until eligible, priced evidence satisfies the non-inferiority gate. Generic local campaigns execute trusted developer fixtures; they are not a security boundary for untrusted skill packages.


### Code graph

- Before walking or reading file state, `RepoStateProbe` fingerprints HEAD, `git status --porcelain -z -uall`, and dirty-path mtime/size; `codeIndexerFingerprint` covers extractor version, queries and grammar libraries. Matching `code_index_checkpoints` returns `CodeIndexResult.unchanged()`. Worktrees also compare base `generation`. A null probe never skips; watcher events force indexing.
- Enumeration/hashing (`walkAndHash`), tree-sitter (`ExtractionWorker`) and embedding (`TextEmbedderWorker`, owning its FFI session) run off the main isolate. Use one long-lived extraction isolate per run; kill/replace a wedged parser.
- Embed batches outside transactions, then write 32 files per transaction. Prune with chunked `IN` lists in one transaction. `resolvePendingReferences` probes indexed COUNT and projects names, not full embedding blobs.
- Start `codeGraphWatch` after the ready banner; defer the first sweep with `--code-index-defer`. Desktop kills a server that misses its 20-second ready deadline. `--code-index off` disables indexing; `/healthz` exposes watching/indexing/pending state.
- Native `cc_watcher` is required: kernel-recursive on macOS/Windows; ignore-aware inotify setup on its own Linux thread. No scanning fallback or arm stagger. An unwatchable checkout is logged/retried by reconciliation, not fatal to the service. Share `SourceFileWalker.watchIgnoredDirs` with `affectsIndex`. See [watcher](packages/cc_natives/native/watcher/README.md).

## Enclosures

Rig domain is `cc_domain/lib/features/rigs`, adapters `cc_infra/lib/src/rigs`, viewers `lib/features/rigs`. Desktop uses QEMU/HVF or KVM with qcow2 images; exec/browser use smolvm/libkrun with pinned OCI images; Android and iOS are host-managed exceptions, not enclosed networking. `RigSurface.window` is host-managed too and contains nothing: `RigService.openHostWindowRig` opens it against running processes with no boot step, closing it leaves the app running, and the reaper and memory budget skip it. `RigSurface.environment` is a smolvm machine for compose and task components: dockerd as the workload, virtio-net because TSI cannot carry bridged container traffic, the worktree on a read-only `-v` mount under a guest overlay, no broker secret, and egress derived from the stack's images. It has no driver and its own surface so it is never taken for a `computer_use` desktop or a terminal machine. Backend selection follows `RigSpec`, never availability or a silent host-shell downgrade. Enforcement rules are in [SECURITY.md](SECURITY.md#execution-and-untrusted-input).

### Browser engines

`RigBrowserEngine` selects Chromium/CDP (`CdpClient`), Firefox/BiDi (`BidiClient`) or WebKit/W3C (`WebDriverClient`). `BrowserRigDriver` depends only on `BrowserEngineClient`; shared page scripts/action vocabulary live in `browser_engine_client.dart`. A rig keeps one engine for life; conversation reuse, in-flight open, tab dedup and provider keys all include the engine.

- Create Firefox's `--profile` directory before launch. Send the guest-side authority in its WebSocket Host header; the forwarded host port fails validation.
- Classic WebDriver POSTs require a body; GETs must not carry one (`dart:io` fixes GET content-length to zero).
- Only Chromium screencasts; others poll at at most 6 fps. WebKit PNG stills need host ffmpeg for its live lane. Firefox/WebKit cannot bypass cache on reload, expose platform accessibility trees or perform real file drops; label DOM-derived accessibility accurately.
- Use distribution Chromium, not upstream `headless-shell`, which omits audio backends. Browser workloads start system PulseAudio with a `ccout` null sink, a pulse-owned socket directory and successful `pactl` sink observation. Never mask startup failure with `|| true`. ffmpeg encodes `ccout.monitor`; packs are keyed by image, engine and audio revision.

### Input, display and worktrees

QEMU input uses QMP (`input-send-event`/`send-key`) and `virtio-tablet`; the unprivileged guest agent only captures/mode-sets and scales frames. The human display lane relays bytes at panel resolution with adaptive fps/quality; the server never decodes frames on the RPC path. The agent lane is at most 1280×800 with one image per result (`capToolImages`); compaction discards old images but keeps text.

The host worktree remains authoritative. Tar streams sync in; git bundles are fetched into `refs/rigs/<rigId>/*`, never pushed or checked out. Uncommitted changes return as a reviewable diff. `WorktreeTransport` uses SSH for QEMU and `smolvm machine exec` for microVMs.

Clipboard policy is per-user and per-direction: paste into rig defaults on, copy out defaults off and prompts before reading. Temporary grants last ten minutes for one rig/direction; persistent grants are synced user preferences. `ensureRigClipboardPermission` gates `RigInputSurface` before `/rig/clipboard`. Denial still forwards guest-local Ctrl+C/X/V on Windows/Linux so copy, paste and terminal interrupts work.

`RigService.act` rejects agent mutations while a human has control but allows observations. Log inputs with `Principal` and a per-rig monotonic `seq` in the insert transaction. Hard TTL, idle→park→close and resident-MB LRU bound resource use; parked VMs retain RAM. `RigParked` says whether idleness or an environment stop parked it. A close writes `closing`, then `closed` with its reason (`memoryPressure` for LRU eviction, `conversationEnded` when `SpaceDeleted` reaches `RigService`, `workspaceGone` from `workspace.delete`). Environment rigs record their id the moment they open, so a stack that never comes up is still closed and its worktree quarantine lifted. Shutdown tears down all owned machines.

### Boot and recovery

- Desktop qcow2 downloads are user-initiated, checksum-pinned and stored in `<dataDir>/rigs/images`. `scripts/rigs/build_image.sh` bakes the guest agent; Settings imports images. `kSmolvmExecImage`/`kSmolvmDebianBrowserImage` pin OCI digests; browser engines warm gated apt installs into per-engine packs.
- Android SDK/emulator/images come from Google (`setup_android.sh` reuses Android Studio); distinguish no SDK, no emulator, no AVD and no running device. iOS requires macOS, Xcode/runtime and checksum-verified WebDriverAgent installed through owner-only `rig.installBackendSetup`. Register uniquely named owned devices atomically; teardown/orphan recovery stop WDA and delete only those devices. iOS streams fixed-size MJPEG and supports typed point/key/app actions, not file drop/audio/mic/enclosed egress. Mobile developer commands are argv-shaped device commands, never a host shell.
- `buildRigSocketPath` selects the first fitting XDG_RUNTIME_DIR/TMPDIR/`/tmp` root; Unix socket limits are 104 bytes on macOS/BSD, 108 on Linux. Keep full rig IDs, create 0700 directories, reject symlinked `ccrig` namespaces. Durable files remain under the data directory; teardown/recovery clear both trees.
- Stock Ubuntu QEMU cloud images need a `cidata` cloud-init seed creating `cc` and its SSH key, not the built-image `CCRIG` format. Readiness is sshd's banner, not a bare forwarded TCP connection or a nonexistent guest agent.
- Guest seed permissions are `0640 root:cc`; both the `User=cc` guest service and git credential helper need read access.
- A successful cloud-init exit does not prove customization. The builder requires the guest completion marker and deletes failed output. Discover firmware via `qemu -L help`, not paths derived from a symlinked binary. `verify_image.sh` must boot the output with a real seed and observe `/health` before publication; its diagnostic seed dumps the guest journal.
- Rig viewers belong to space/PR tabs, not global navigation; tools share the conversation's machine. Settings → Server → Enclosures owns setup/capabilities/sessions. Never auto-start rigs on layout restore. Restored microVM terminal tabs carry `EditorLayoutCodec.deferStartArg` and wait for “Open the shell”; host-shell terminals may attach on mount.

## Environments

An environment is the running stack of one space: an ordered list of typed components from an admin-authored definition. Domain is `cc_domain/lib/features/environments`, adapters `cc_infra/lib/src/environments`, the RPC pack `cc_server_core/lib/src/catalog/environment_ops.dart`, the client `lib/features/environments`. Security rules are in [SECURITY.md](SECURITY.md#host-environments).

- **Components.** `compose` (native driver), `cli` (a tool that owns its lifecycle; CC calls verbs and reads JSON through `statusMap` or the native contract), `process` (PTY-supervised), `task` (one-shot with triggers), `app` (a desktop window).
- **Worktree tasks.** `provision` and `archive` tasks follow the worktree, not the environment: they run in any space, see no environment values, and belong to one definition per repo.
- **Host setup.** A tool that needs a person exits 3 and the start stops. If its definition has a `setup` verb, `environment.startSetup` runs it on an owned PTY, the client opens that session as a terminal tab with a notice saying why it appeared, and exit 0 resumes the start. Only a person's Start opens it by itself: a row that was already waiting offers **Continue in terminal**, and agents have no route.
- **Ports.** `EnvironmentLeaseAllocator` leases blocks from one host-wide range (`environment_slot_leases`, global.db, because ports are host-wide; IDs only). A lease is taken when a run starts in an eligible space, since `loopbackPorts` is fixed at run start. Assignments never move while the lease is held; a start after the lease was released (an archived space) assigns again from the new one. A space's lease goes only when none of its environment rows remain.
- **Compose.** Plan with `docker compose config`, preflight, write the resolved model and an override (`container_name: !reset null`, `ports: !override`, labels, injected healthchecks) to the state directory, `up -d` from those two files, never `--wait`: it exits 1 on a successful one-shot. Only planning reads the worktree's compose file, and every call but `up` goes by project name (`ComposeProject`, run from the state directory), so stop, logs, exec and teardown need no cached plan. Readiness comes from `docker events` plus `ps`. One compose component per environment, enforced by validation; `after` may only name an earlier component that starts with the stack. Component states are `EnvironmentComponentPhase` wire strings; status moves go through `EnvironmentService._update`, which refuses what `EnvironmentStatus.canBecome` forbids.
- **URLs.** CC-routed endpoints are `http://<endpoint>--<name>--<project>.localhost:<router port>`, one DNS label on purpose: `RigDomainRouter`'s rule and the `*.localhost` leaf only cover one. A tool that owns its domains uses `routing.mode: tool`: routes come from its status, and the router terminates with CC's leaf and re-encrypts to the tool's proxy. Chromium's SPKI pin accepts names the leaf doesn't list, so nothing is re-issued.
- **Teardown.** Every worktree release, PR editor worktrees included, passes through `WorktreeReleaser.release`: environment teardown (`WorktreeTaskPort.beforeRelease`) when its `WorktreeReleaseMode` is `teardownEnvironment`, then `archive` tasks, the copy, stack rows and the registry row. A space going away tears down; a finished ticket, a deselected repo or a rolled-back provision releases rows only, and the environment reconciles against what is left. Do not add a release path around it. A forced teardown whose step fails keeps the row as `failed` with code `teardown-incomplete` (its rig id, lease and state directory with it) and maintenance retries every five minutes.
- **State directory.** Besides the compose files, an environment's state directory holds `bound_roles.json` (which worktree each role ran on, read by repo reconciliation), `fork_approval.json` (who approved running a fork PR there) and `setup.log` (the host setup terminal's output). They are owned by the row: created at start, deleted with it, kept when a teardown is incomplete.
- **Placement.** `host`, or `rig` for definitions of only compose and tasks. Rig placement runs the compose file unmodified in a microVM with `--net-backend virtio-net`; TSI can't carry bridged container traffic. Worktrees are shared read-only with a guest overlay, and `RigWorktreeGuard` hardens every host git call on them.
- **Desktop apps.** CC never talks to an app. `HostWindowRigDriver` works at OS window level, keyed on the process tree, so no framework needs a hook. Windows can't be hidden off-display on macOS: capture fails.

## Client conventions

### Routes and onboarding

`go_router` uses `ShellRoute(ControlCenterLayout)`. In-shell routes start `/workspaces/:workspaceId/`; that URL drives `activeWorkspaceIdProvider` and `context.currentWorkspaceId`, and `workspaceUrlSyncProvider` is its only writer: deep links and pickers navigate, they never set the active id themselves. The scoped remembered id only picks the landing workspace (`landingWorkspaceIdFor`); when the first workspace list lacks it, the hint is forgotten and a route on it moves to the landing workspace. Builders take workspace ID first. `/splash`, `/onboarding` and `/workspaces` are full-screen pre-context routes. See `lib/router/{routes,app_router,guards}.dart` and `features/auth/providers/onboarding_providers.dart` for the actual route inventory.

Setup requires a forge connected for the signed-in user and a workspace. A missing credential gates nothing once that user's `users.onboarding_finished_at` says setup finished: the shell's `ForgeSignInBanner` warns in the workspace and links to its sign-in (a workspace on its own GitHub App can lack a sign-in others have). Without that flag, a missing credential means onboarding. Never infer this from workspace existence or device preferences: invited users and shared devices invalidate that inference. Hold splash while the value is unknown: `onboardingGateProvider` is pure, falling back only to the session-scoped onboarding-complete hint while the live gate resolves, and `onboardingGateEffectsProvider` (watched by the app root) does the marking and caching. `users.markOnboardingFinished` is self-targeting, idempotent and monotonic; mark on completion and when observing a complete setup. Snapshot the step list once: invited members skip workspace creation but still do personal setup. The server owner's list starts with the `signIn` step (the Connect choice, `OnboardingConnectStep`), before the forge `connect` step.

Sign-in and onboarding expose a corner settings button, not the app's Settings or a manual update button. It opens `PreAppSettingsPage`, which offers only language and theme: anything else belongs to a signed-in server. Pre-server surfaces write the same preference keys through `ConnectAppearance` because `localeProvider` and `themeModeProvider` report to analytics, which needs a server; onboarding feeds the page from those providers. `isAuthenticationRoute` suppresses the Settings shortcut, command palette and native Preferences action on `/splash` and `/onboarding`; the onboarding guard still rejects direct settings links while admission is incomplete. Its language field reuses the same searchable `LanguagePicker` as Settings, including the system-default option and native language labels.

Space sidebar folders are personal navigation organization, not workspace space entities or shared policy. `space_folder_providers.dart` reads `prefs.watchOwn` and writes a JSON folder list under `space_folders.<workspaceId>` with `prefs.set`; expanded and rail-mode sidebars share it. Workspace-specific keys prevent mixing a user's arrangements, while the workspace's visible-space stream remains the authority for which rows can be shown. Space-row and header archive actions remove the archived space from personal folder membership, so restore leaves it unfiled. Deleting a nonempty folder defaults to removing only its folder record; an explicit confirmation checkbox instead deletes its existing workspace spaces through the messaging service before removing the folder record. Folder deletion and space deletion have different scopes: the former is personal, the latter is workspace-wide.

`SpaceFoldersList` handles workspace-scoped drag payloads: folder rows accept visible spaces, space rows open the existing folder-name dialog when another space lands on them, and a filed space dropped in free sidebar space becomes unfiled. During a filed-space drag, both desktop sidebars show a bordered "Remove from folder" target between folders and unfiled spaces; its accent border confirms an eligible hover, and dropping moves only a visible space in the same workspace. The space setup banner retries and stops provisioning through `RemoteMessagingRepository` with an explicit workspace ID, rather than relying on the RPC client's ambient workspace. Stop confirmation retains the workspace captured when the dialog opens.

`InMemorySpaceProvisioningLog` is the single redaction chokepoint. It keeps 256 KiB per space for the 32 spaces touched most recently, never evicts a followed space, and is lost on restart, so the tab is dropped from layout snapshots. `messaging.watchSpaceProvisioningLog` (in the `space_provisioning_ops` pack) is an event stream: a progress bar rewrites its line under the same `seq`, and a client replaces an equal `seq`, appends a higher one and ignores a lower one, which is a reconnect's replay. A log's numbering starts from the clock, so a log rebuilt after a restart or eviction always numbers past what a reconnecting client has seen. Every run of a space appends to one log, so a retry keeps the failure it follows in view.

Single-state inventories retain their full glyph, and mixed glyphs keep their colors on a neutral backing when selected. Tooltips and accessible labels name every represented state; numeric badges still count unread conversations.

The messaging IDE's Source Control tab owns the space PR inventory above the worktree controls; General contains no PR section. Linked PRs remain accessible while worktrees load, provision or are absent. The inventory header groups creation actions by checked-out repository, retaining branch-PR eligibility and complete-lookup requirements for publishing missing stack parts. Existing PRs open from inventory rows, not duplicate repository footer actions.

A seed shown while the first read is in flight, or after it failed, is never persisted.

### Client forge model

The server owns every forge read and write; a client renders what `forge.*`, `pr.*` and `github.*` RPCs return and never builds a forge client of its own. Rules a client feature follows:

- **Which forge.** A PR's forge is its repo row's: `prRepoRowProvider(prRef)` matches `matchRepoForPr` on owner, name and, when stated, `PrRef.forge`. The route carries `?forge=` for a non-GitHub PR, so two repos with the same `owner/name` on different forges stay distinct. Full names split at the last `/` (`splitRepoFullName`), so a GitLab `group/sub/project` keeps `group/sub` as its owner. Only `forgeWithoutRepo` guesses a forge without a repo in hand: the only connected one, else GitHub.
- **Who am I.** `forgeConnectionsProvider` is the one source for connection state on desktop and phone (`RemoteForgeConnections` in cc_data). It folds `oauth.connections`' `needs_sign_in` into `ForgeConnection.needsSignIn`, so a lapsed grant shows as one in Settings and in `ForgeSignInBanner`. A failed read is an `AsyncError` that keeps the previous list, and the onboarding gate treats a first-read failure as unresolved, never as "no forge". `viewerLoginsProvider` maps each forge to the lower-cased login; every "is this mine?" test goes through `currentUserLoginForPrProvider(prRef)`, the login on that PR's forge. After any sign-in, sign-out, token change, Connect apply or workspace App change, call `invalidateForgeState`, never a partial list of invalidations.
- **What can it do.** Gate affordances with `prSupportsProvider((prRef, ForgeCapability.x))` or `capabilitiesForProvider(forge)`, never `forge == ForgeHost.github`. The table is `kForgeCapabilities` in cc_domain, served by `forge.capabilities`. A server op on a forge that lacks the surface throws `ForgeUnsupportedError`, which reaches the client as a validation error carrying `unsupported_capability` and `forge`.
- **Copy.** Name the forge with `ForgeHost.displayName` ("Open on {forge}"). GitHub-only chrome (the GitHub status banner) shows only when the workspace has a GitHub repo (`workspaceForgesProvider`).
- **Hosts.** `ForgeHost` names a forge *kind* with its public host (`github.com`, `gitlab.com`, `bitbucket.org`). Self-hosted GitLab or Bitbucket is not representable: a connection carries no base URL, and the forge clients and `ForgeUrls` build public-host URLs. Supporting one means a per-connection base URL threaded through `ForgeCredentialPort`, the client builders and `ForgeUrls`, not a new enum value.
- **Data access.** `prReviewRepositoryFactoryProvider` returns `RpcPrReviewRepository` for every forge with a remote and `EmptyPrReviewRepository` otherwise. There is no client-side forge provider registry.

### Usage analytics

One `Analytics` facade per process (`packages/cc_domain/lib/features/telemetry/`): desktop/web (`analyticsProvider`, `lib/core/providers/analytics_providers.dart`), the phone (`apps/cc_remote/lib/analytics.dart`) and the server (`ServerAnalytics`, `packages/cc_server_core/lib/src/telemetry/`). Call sites record only events from the `AnalyticsEvents` tracking plan. The facade gates collection on the server's `TelemetryConfig`, which is opt-in. Records made before the config arrives wait in a bounded buffer and are dropped if it says no. Collection is also gated on the build (`kReleaseMode` on clients, `dart.vm.product` on the server; other builds log through `LoggingAnalyticsSink` unless the server's `CC_ANALYTICS_DEBUG=1` sets `TelemetryConfig.debugBuildsAllowed`). The facade merges the context (`app_type` desktop/web/remote/server, version, platform, server mode, locale), applies `AnalyticsPropertyPolicy` and pseudonymizes IDs, then hands an `AnalyticsEnvelope` to the `AnalyticsSink` port. `AnalyticsDestination.createSink` in `cc_analytics` is the single provider switch; `UmamiAnalyticsSink` owns queueing, backoff and delivery.

Clients record UI interactions: screen views from the router's route template, sends, approvals, commands, searches, settings and the session lifecycle. The server records domain facts from the `DomainEventBus` (runs finished, workspaces, spaces, tickets, pipelines, PRs), so agent work is counted once however many clients watch. Do not record a server fact from a client. Adding an event means a factory in `AnalyticsEvents`, its call site, and a row in the manual's telemetry reference. Privacy rules are in [SECURITY.md](SECURITY.md#usage-analytics).

### Client read snapshots

Desktop and web attach a bounded `RpcSnapshotCache` to `ResilientRpcClient` after the server handshake and an uncached `identity.me` read. The namespace includes the verified server fingerprint and authenticated user; each entry includes the query/read operation and complete arguments, including workspace, repo, entity and range. Eligible subscriptions replay their snapshot before attaching to the live stream. UI-only one-shot reads opt into `watchCall`; ordinary `call`/`callResult`, mutations, credentials, presence and live control remain uncached.

Snapshots survive navigation and restart: desktop uses owner-private atomic files under `<appSupport>/client_rpc_snapshots`, web uses dedicated IndexedDB storage, with a 16 MiB per-identity working set. Fresh results, including empty results, replace stale data. Transport loss retains readable snapshots; reconnect revalidates. Storage corruption or quota failures do not block live reads. Forget/disconnect clears the server's snapshots, and authenticated membership refresh or explicit authorization rejection invalidates affected data. The old workspace-only calendar preference snapshots are removed at startup.

This is a read cache, not an offline server or a source of mutation authority. A cold launch still requires a reachable server for authentication and workspace admission; an admitted session can continue viewing previously loaded data during an outage. Conversation feeds keep their live refresh attached while replaying snapshots. `messageDetailProvider` revalidates full agent-turn messages, including cached unfinished placeholders that have no `segments_elided` marker; completion invalidates an earlier unfinished read after the frame, guarded against disposal or a changed turn. Never invalidate it synchronously from `AgentTurn.didUpdateWidget`: refreshing the enclosing provider scope during a feed build violates Flutter's build lifecycle. The renderer uses the stored agent name when its directory lookup is unavailable, and caches finalized transcripts separately from live turn events.

### Media cache

Clients fetch external media through signed `/proxy/media` (`MediaProxyConfig`). `MediaCache` persists non-ranged images under `<dataDir>/media_cache`, keyed by `(url,w)`: upstream max-age clamped to 1 hour–7 days (default 24 hours), conditional ETag/Last-Modified refresh, stale-on-refresh-failure and same-key single-flight. Bucket requested widths **up** with `bucketMediaWidth` in `lib/shared/utils/media_width_ladder.dart` to share entries.

`DiskCachedNetworkImage` reads through the native client's `MediaDiskCache`. If the cache cannot supply bytes, the provider fetches the resolved URL's bytes and decodes them under its single `MultiFrameImageStreamCompleter`. Never share a codec with a nested `NetworkImage` completer: both would consume and dispose it. Failed loads evict the provider's own image-cache key so a later resolve can recover. Web bypasses the inert disk cache and delegates directly to `NetworkImage`.

Server raster transforms cap decoded input at `8192 × 8192` pixels; ICO conversion caps it at `4096 × 4096`. These are pixel budgets, not byte/heap limits. Over-budget images retain the existing no-transform/original-stream behavior, and animated images are not flattened into thumbnails.

Newsfeed grid and list layouts use `ScrollCacheExtent.viewport(1)` to build one viewport of nearby tiles before and after the visible region, not the whole feed. `ProxiedImage` resolves only the tiny preview while a tile is in that cache region; its first paint enables the full-size request. Both variants keep the signed proxy, disk/image caches and existing cross-fade behavior. A changed URL or target width resets the full-size paint gate.
