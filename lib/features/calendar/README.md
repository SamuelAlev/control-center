# Calendar

`cc_server` syncs each workspace's Google Calendar accounts into its database and makes the person's own writes (RSVP, create, move, delete) on their behalf; web and desktop clients render month/week/agenda views, drag-to-create with a floating composer, drag-to-move and resize, meeting-soon alerts, and can start a local recording linked to an event. A `CalendarEvent` is a synced entry, **not** a recorded `Meeting`; `MeetingCalendarLinksTable` links them many-to-one.

## Ownership and data flow

- Server: `packages/cc_server_core/lib/src/connect/google_sign_in_lane.dart` is the `google` lane of the browser sign-in (`oauth.begin`/`status`/`complete`), refusing a sign-in without a workspace. `packages/cc_server_core/lib/src/google_calendar_server.dart` owns credential storage (`FileGoogleCredentialsStore`), tokens (`ServerGoogleTokenManager`), the sweep (`ServerCalendarSync`) and `CalendarAccountService`, which stores a finished sign-in and upserts its account row. `packages/cc_infra/lib/src/calendar/calendar_sync_service.dart` and `packages/cc_infra/lib/src/network/google_calendar_api_client.dart` list calendars and events. `remote_rpc_catalog.dart` serves the `calendar.*` reads and watches plus `calendar.disconnect`, `calendar.refreshNow` and `calendar.ensureRangeLoaded`. `catalog/calendar_write_ops.dart` serves `calendar.rsvp`, `calendar.createEvent`, `calendar.moveEvent` and `calendar.deleteEvent` through `ServerCalendarWrites`, which refuses an account that is not the caller's own (`WorkspaceMismatchException` across workspaces) and a calendar that is not writable, writes with `sendUpdates=all` and stores Google's result so watches update without waiting for a sweep. `calendar.moveEvent` also refuses an invitation the caller does not organize (`CalendarEventReschedule.allowedFor`). The demo server refuses all four by name.
- Client: `packages/cc_data/lib/src/repositories/remote_calendar_repository.dart` reads watches. Connecting is the generic provider sign-in on the `google` lane, scoped to the workspace: `presentation/widgets/google_calendar_connect_dialog.dart` opens `showProviderSignInDialog` (`features/auth`), which runs `oauth.begin` → browser → `oauth.status` polling (own client) or the Connect confirmation code / `control-center://oauth-done` deep link. Every entry point (empty state, sidebar, reauth banner, Settings) uses it. `providers/connect_account_provider.dart` and `remote_calendar_connect.dart` only disconnect. The client **never holds Google tokens or client credentials**. `CalendarRecordAndLinkUseCase` links a locally started recording. Writes go through `presentation/providers/calendar_event_write_provider.dart`: a drag on the kalender grid (`CalendarKalenderHost.onCreate`) or the header's new-event button opens `calendarComposerProvider`, `CalendarComposerLayer` floats `CalendarEventComposer` beside the span with a placeholder tile on the grid, and only `writableCalendarsProvider` calendars (writable, own, not awaiting reauth) are offered. Tiles `canMoveCalendarEvent` allows drag and resize (`CalendarKalenderHost.onMove`); `moveCalendarEvent` opens the event after the host stores it, and a refusal resyncs the grid so the tile goes back. Delete (`calendar_event_actions.dart`) confirms with the consequence for guests.
- Accounts/events/meeting links have a non-null workspace id. DAO queries filter by workspace, accounts belong to one member and are unique on `(workspaceId, userId, accountEmail)`, and the provider follows `activeWorkspaceIdProvider`. A sign-in binds to `ctx.workspaceId` and `ctx.userId`; disconnecting another workspace's account throws `WorkspaceMismatchException`, and disconnecting another member's account is refused.
- The host sweeps every workspace every two minutes, at boot and right after a sign-in, over a rolling window of 60 days back and 90 ahead. It reconciles deleted events and updates `calendar.watch*` clients. Disconnect cascades event deletion and clears the stored credential.

The sign-in requests `openid email https://www.googleapis.com/auth/calendar.events https://www.googleapis.com/auth/calendar.calendarlist.readonly` (`googleConnectScopes`). A grant with any other set is refused at claim and on refresh. Credentials stay in the host's `secrets.json` (`FileGoogleCredentialsStore`, keys `google_<accountId>`, account id `google:<workspaceId>:<userId>:<email>`), **not** in Drift or the client. A sign-in through the server's own client stores its access and refresh tokens. A sign-in through Connect stores only its credential seal and the install id it was sealed for; its access token lives in `ServerGoogleTokenManager`'s memory, and a refresh sends the seal back to Connect for a new token and a new seal.

`ServerGoogleTokenManager` checks a credential each time it reads it. A seal whose install id is not this server's current one (key rotated, another Connect, a restored data directory) is dropped, and so is an own-client credential issued by a client id other than the configured one. Refresh is single-flight per account. Only a rejected refresh clears a credential; it flags the account for reauth and publishes `CalendarAuthExpired`. A refresh that cannot run right now keeps everything and skips the call. Authenticated Calendar requests retry once after a 401. See [SECURITY.md](../../../SECURITY.md) for the general credential boundary.

## Connect your own Google client

Without an own client, the `google` lane runs through Control Center Connect when the server owner turned it on. An own client always takes precedence.

1. In [Google Cloud Console](https://console.cloud.google.com/apis/credentials), enable the Calendar API; configure consent for `calendar.events`, `calendar.calendarlist.readonly`, `openid` and `email` and add test users while unverified. Create an OAuth client of type **Web application**.
2. Add the authorized redirect URI `<server origin>/oauth/google/callback`. Settings → Server → Single sign-on → Provider apps → Google shows it verbatim under **Callback URLs**.
3. A server owner enters the client id and secret in that Google block, or puts `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` in the server's `.env`. The environment seeds each field once. The server refuses to start when `GOOGLE_OAUTH_CLIENT_SECRET` is exported in its process environment, and the secret never leaves the host.

A client id without its secret is an incomplete own app: the lane reports it and refuses Google sign-ins rather than falling back to Connect. Changing the client drops every account's credential on its next read, so everyone reconnects. `redirect_uri_mismatch` means the registered redirect differs from **Callback URLs**; `invalid_client` means a mismatched id and secret or a deleted client; no events after connecting may mean absent test-user access or a scope left unticked on the consent page.

There is no client-side Google OAuth or sync. `providers/calendar_sync_providers.dart` only asks the host to refresh (`calendar.refreshNow`) or load a range outside its rolling window.
